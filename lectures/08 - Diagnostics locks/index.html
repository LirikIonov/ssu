    08. PostgreSQL: Diagnostics & Locks¶

    Основная лекция магистратуры · PostgreSQL 18 · REL_18_STABLE · блок 8, темы 1–15.

    Продолжение блоков о SQL-планировщике, MVCC и WAL. Здесь используем уже знакомые механизмы, чтобы исследовать производительность конкурентной работы. Внутреннее устройство подсистем статистики, Lock Manager и алгоритмов VACUUM вынесем в возможные углубления 08.1–08.3. Темы миграций, резервного копирования и пулов соединений остаются вне лекции.

    Оговорка об экспериментах: SQL со специально созданными ожиданиями, взаимными блокировками и принудительным завершением backend-процессов выполнять только в тестовой базе. В примерах psql A, psql B и psql C обозначают разные физические подключения. Время выполнения и PID иллюстративны, точные значения зависят от экземпляра. Для диагностики других сессий понадобятся соответствующие права, например роль pg_read_all_stats.

    0. Расследование: 25% CPU, а запрос отвечает пять секунд¶

    В обычный день обработчик backend-сервиса читает и обновляет строку в PostgreSQL за 20 мс. После роста трафика медианная задержка остается приемлемой, но p99 достигает пяти секунд. Разработчик смотрит график CPU: 25%. Диски тоже не уперлись в пропускную способность. Планы запросов прежние. Где потерялись секунды?

    Первая очевидная мысль — SQL-запрос стал медленно исполняться. Проверяем EXPLAIN, индекс найден, выборка короткая. Но запрос может проводить почти все время, ожидая чужую транзакцию. Backend-процесс существует, PostgreSQL показывает его состояние active, счетчик одновременных запросов растет, а полезной работы он не делает.

    Создадим минимальную учебную схему:

    -- Выполнить один раз в ОТДЕЛЬНОЙ учебной БД.
CREATE TABLE accounts (
    id bigint PRIMARY KEY,
    balance bigint NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 10000), (2, 10000);

CREATE TABLE transfers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    from_account bigint NOT NULL REFERENCES accounts(id),
    to_account bigint NOT NULL REFERENCES accounts(id),
    amount bigint NOT NULL CHECK (amount > 0)
);

CREATE TABLE jobs (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status text NOT NULL CHECK (status IN ('ready', 'running', 'done')),
    created_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    claimed_at timestamptz
);
INSERT INTO jobs(status)
SELECT 'ready' FROM generate_series(1, 1000);
CREATE INDEX jobs_ready_id_idx ON jobs(id) WHERE status = 'ready';

    Сессия A выполнит BEGIN; UPDATE accounts ... WHERE id = 1; и ничего больше не отправит. Сессия B попробует обновить ту же строку. Сессия C увидит B в pg_stat_activity как active, но с ожиданием Lock. Этот эксперимент будет проходить через всю лекцию. Постепенно добавим конкуренцию, очереди, взаимную блокировку и последствия старых XID.

    Маршрут расследования:

    Приложение: p99 вырос
        │
        ▼
pg_stat_activity: что прямо сейчас делают backend-процессы?
        │
        ├── active + нет измеримого ожидания → проверяем CPU/план/инструменты ОС
        ├── active + Lock                   → выясняем, кто блокирует
        ├── active + IO/LWLock/...          → исследуем соответствующий ресурс
        └── idle in transaction            → изучаем xact_start, блокировки, xmin
                                                    │
                                                    ▼
                                     pg_locks + pg_blocking_pids()
                                                    │
                                                    ▼
                                      Корневая блокирующая транзакция

    Главная учебная установка: симптом задержки нужно связать с ограниченным ресурсом и процессом, который этот ресурс удерживает. Попытка лечить все задержки индексами или увеличением CPU превращается в бесполезную лотерею.

    I. Диагностика работающей базы¶

    1. pg_stat_activity: чем занят каждый backend¶

    1.1. Почему одна SQL-команда вообще видна другой сессии¶

    В обычной серверной модели PostgreSQL отдельное клиентское подключение обслуживает backend-процесс (на сервере также существуют фоновые процессы). Когда клиент отправляет запрос, процесс принимает команду и выполняет ее, взаимодействуя с общими буферами и другими подсистемами. PostgreSQL публикует сведения о текущем состоянии процесса в разделяемой инфраструктуре наблюдения; системное представление pg_stat_activity дает SQL-доступ к ним.

    Важно различать три идентификатора: pid — процесс ОС; application_name — метка клиента, которую стоит назначать осмысленно; query_id — идентификатор нормализованного запроса, если вычисление идентификаторов включено. Сам текст query не является стабильным идентификатором: там могут быть литералы, усечение и последние команды при idle.

    SELECT
    pid, backend_type, usename, application_name, client_addr,
    state, wait_event_type, wait_event,
    now() - query_start AS query_age,
    now() - xact_start AS xact_age,
    backend_xid, backend_xmin,
    query_id, left(query, 140) AS query
FROM pg_stat_activity
WHERE datname = current_database()
  AND backend_type = 'client backend'
ORDER BY xact_start NULLS LAST, query_start NULLS LAST;

    query_age надо интерпретировать только вместе с state. Если state = 'idle', query_start относится к последнему выполненному запросу. Если транзакция уже закончилась, xact_start будет NULL. Отдельно есть state_change — время последней смены состояния. Для ожидания длительности простоя нужно вычислять now() - state_change, а не now() - query_start.

    1.2. Три разных времени¶

    • query_start — момент запуска текущего SQL при active, либо последнего запроса при других состояниях.
    • xact_start — начало текущей транзакции, если она существует. Несколько быстрых команд могут выполняться внутри транзакции, открытой давно.
    • state_change — момент смены состояния backend-процесса, полезный для поиска затяжного idle in transaction.

    Например, клиент выполнил BEGIN в 12:00, UPDATE в 12:01 и перестал работать в 12:01:01. В 12:10 сам UPDATE давно завершился, но транзакция все еще открыта; row lock живет до ее завершения. Ситуация, когда запрос завершен, а ресурсы удерживаются, совершенно нормальна на уровне протокола и опасна на уровне нагрузки.

    1.3. Ограничения: мгновенное наблюдение и права¶

    pg_stat_activity отражает состояние в момент наблюдения. Если короткий SQL успел завершиться, вы не увидите его «прошлую жизнь». Внутри длительной диагностической транзакции разные чтения статистики могут использовать сохраненный снимок; для свежих наблюдений выполняйте отдельные запросы в autocommit или явно применяйте pg_stat_clear_snapshot() при необходимости.

    Пользователь обычно видит детальную информацию о собственных сессиях; для остальных могут скрываться сведения о запросах и ожиданиях. Роль pg_read_all_stats дает доступ к дополнительным показателям без назначения суперпользователя. По умолчанию текст запроса обрезается до размера track_activity_query_size (обычно 1024 байта); увеличение этого параметра требует соответствующей конфигурации экземпляра.

    Цена наблюдения: отдельный SELECT к pg_stat_activity обычно дешев, но непрерывный опрос тысяч backend-процессов с интервалом в миллисекунды создает свою нагрузку. Лучше сначала поставить диагноз выборочным запросом, чем пытаться «мониторить все» без гипотезы.

    2. pg_stat_statements: систематическая нагрузка, которую мы пропустили¶

    2.1. Проблема «запрос уже закончился»¶

    В 12:05 пользователи жалуются на замедление, но в 12:06 все запросы завершились. Текущие состояния не восстановят количество вызовов и суммарную стоимость. Для этого нужен накопительный учет SQL: pg_stat_statements группирует схожие запросы и считает работу, совершенную за период наблюдения.

    В PostgreSQL 18 модуль должен быть предварительно загружен, поскольку использует общую память. Его установка — конфигурация администратора экземпляра, а не команда для произвольного соединения:

    # postgresql.conf, сервер перезапускается после изменения
shared_preload_libraries = 'pg_stat_statements'
compute_query_id = auto

    -- Выполняется в конкретной БД, где нужна функция представления.
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SHOW shared_preload_libraries;
SHOW compute_query_id;
SHOW pg_stat_statements.track_planning;

    compute_query_id = auto допускает автоматическое включение вычисления идентификаторов при работе подходящего модуля. Настройка pg_stat_statements.track_planning по умолчанию выключена: без ее включения plans и метрики планирования будут нулевыми. Сбор статистики также имеет стоимость по памяти, CPU и блокировкам внутри расширения.

    2.2. Почему в статистике $1 вместо конкретного значения¶

    Сервер формирует идентификатор нормализованного запроса, агрегируя запросы с одинаковой структурой, но разными литералами. Поэтому SELECT * FROM accounts WHERE id = 1 и такой же запрос с id = 2 обычно относятся к одной статистической записи. Но одинаковый текст в разных базах и от разных пользователей может учитываться раздельно: ключ включает dbid, userid, queryid, признак toplevel.

    Нормализация экономит пространство и дает общую картину, но прячет различия в значениях параметров. Если одна конкретная величина вызывает тяжелый план или намного больше строк, средняя задержка по группе может скрыть проблему. Это уже повод коррелировать статистику с логами запросов и конкретными параметрами, а не считать queryid универсальным объяснением.

    2.3. Находить суммарных потребителей, а не только самые медленные вызовы¶

    SELECT queryid, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS avg_ms,
       round(max_exec_time::numeric, 2) AS max_ms,
       round(stddev_exec_time::numeric, 2) AS stddev_ms,
       rows, shared_blks_read, shared_blks_hit,
       temp_blks_written, wal_bytes,
       left(query, 130) AS sample_sql
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database
              WHERE datname = current_database())
ORDER BY total_exec_time DESC
LIMIT 20;

    Сравним два вида запросов. Запрос A выполняется десять раз по 1 секунде: суммарно 10 секунд исполнительного времени. Запрос B выполняется миллион раз по 10 мс: суммарно 10 000 секунд исполнительного времени. B может создавать гораздо больше общего давления на CPU и ресурсы, хотя отдельный вызов почти незаметен. При параллельном исполнении сумма времени выполнения запросов может значительно превышать прошедшее настенное время — это не ошибка измерения.

    Дополнительные показатели:

    Поле О чем говорит Чего не доказывает
    calls Частота завершенных исполнений Ничего о хвостах задержек
    mean_exec_time Среднее по группе Не является p95/p99
    max_exec_time Наибольший зарегистрированный вызов Не описывает распределение
    stddev_exec_time Разброс задержек Не заменяет временной ряд
    shared_blks_hit/read Работу с shared buffers read не обязательно физический диск: есть page cache ОС
    temp_blks_written Использование временных файлов Не показывает конкретный текущий spill
    wal_bytes Сгенерированный WAL Не равно объему fsync или задержке COMMIT

    2.4. Что накопительная статистика скрывает¶

    Накопительные счетчики меняются не мгновенно; в них обычно учитываются завершенные действия и периодические публикации. Показатели следует сравнивать дельтами за одинаковый временной интервал, а не по «вечным» суммам. После сброса счетчиков, перезапуска в определенных режимах или вытеснения статистических записей базовая линия меняется. Нельзя вычислить точный p99 по одному среднему, максимуму и стандартному отклонению. Для точных перцентилей понадобится отдельная телеметрия на уровне приложения или трассировки.

    Таким образом, у нас два прибора: pg_stat_activity отвечает «что происходит прямо сейчас», pg_stat_statements — «какие шаблоны SQL регулярно создают нагрузку». Они дополняют друг друга, но не объясняют первопричину автоматически.

    3. active, idle, idle in transaction: запрос закончился, а проблема осталась¶

    3.1. Четыре состояния¶

    state Смысл Что проверить
    active Backend выполняет текущий запрос или ждет во время него wait_event, query_start, SQL
    idle Ждет новую команду, вне текущей транзакции Число сессий и ресурсы
    idle in transaction Внутри незаконченной транзакции, команду не исполняет xact_start, блокировки, backend_xmin
    idle in transaction (aborted) Транзакция после ошибки ожидает завершения/rollback Кто забывает отменить транзакцию

    В обычном использовании много idle не означает много заблокированных таблиц. Однако каждое подключение связано с ресурсами backend-процесса. Небезопасно считать, что 1000 idle «бесплатны». Особо опасна другая категория: незавершенная транзакция с удерживаемыми блокировками.

    3.2. Рукотворный инцидент¶

    Сессия A:

    BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- Не выполнять COMMIT до следующего наблюдения.

    Сессия B:

    UPDATE accounts SET balance = balance + 20 WHERE id = 1;
-- Этот UPDATE ожидает завершения A.

    Сессия C:

    SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start AS tx_age,
       now() - state_change AS state_age,
       left(query, 100)
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST;

    A увидим как idle in transaction, B — как active с ожиданием из категории Lock, часто transactionid. В этот момент сами SQL-операторы в A ничего не вычисляют. Но их транзакционный результат еще не подтвержден и конфликтующий UPDATE не может продолжиться. После COMMIT либо ROLLBACK в A B получит возможность завершиться (при отсутствии других блокирующих участников).

    3.3. Влияние таймаутов и границ транзакции¶

    idle_in_transaction_session_timeout может завершать бездействующие сессии с открытыми транзакциями. В PostgreSQL также существует transaction_timeout, ограничивающий длительность транзакции целиком. Они не подменяют корректное управление транзакциями в приложении: настройка ошибок и повторов должна учитывать возможный rollback. Отдельно разбираемый позже lock_timeout ограничивает конкретные ожидания блокировок, а не общий срок жизни транзакции.

    Тонкость о VACUUM: длительная открытая транзакция не обязательно всю жизнь держит один и тот же старый MVCC snapshot. Например, в READ COMMITTED видимость устанавливается для отдельных операторов. Нужно проверять фактический backend_xmin, наличие старых активных XID и удерживаемые снимки, а не автоматически приписывать каждому idle in transaction одинаковую степень препятствия очистке.

    4. wait_event: запрос «активен», но чем он занят?¶

    4.1. State не равен состоянию CPU¶

    Внутри PostgreSQL выполнение запроса состоит из участков вычисления и участков ожидания. Состояние active описывает факт обработки SQL-команды, но не обещает занятость ядра процессора. Поля wait_event_type и wait_event показывают, что backend сейчас ожидает в точке, которую инструментировал PostgreSQL.

    SELECT pid, state, wait_event_type, wait_event,
       now() - query_start AS age,
       left(query, 120) AS sql
FROM pg_stat_activity
WHERE state = 'active'
ORDER BY query_start;

    В PostgreSQL 18 доступен системный справочник pg_wait_events, позволяющий получить пояснение к известному ожиданию:

    SELECT a.pid, a.state, a.wait_event_type, a.wait_event,
       w.description
FROM pg_stat_activity AS a
LEFT JOIN pg_wait_events AS w
  ON w.type = a.wait_event_type
 AND w.name = a.wait_event
WHERE a.wait_event IS NOT NULL;

    4.2. Семейства ожиданий¶

    Тип ожидания Пример причины Следующее диагностическое действие
    Lock Ожидание relation/transactionid/tuple и др. pg_blocking_pids(), pg_locks
    LWLock Короткая внутренняя синхронизация общих структур Узнать конкретное имя, собрать частоту
    IO Операция чтения/записи/синхронизации Статистика ввода-вывода и метрики ОС
    BufferPin Ожидание освобождения закрепленного буфера Проверить длительность и тип запроса
    Client Ожидание чтения/записи данных клиенту Сеть, поведение приложения, размер результата
    IPC Координация разных процессов Выяснить конкретное событие
    Timeout / Activity Таймеры и служебные ожидания Проверить тип backend-процесса

    Lock — это одна категория. LWLock — другой механизм, обеспечивающий короткие критические участки при работе с внутренними структурами; эти внутренности относятся к углублению 08.1/08.2. Категории следует сначала отделить, а потом уже выбирать инструмент расследования.

    Ловушка: wait_event IS NULL означает лишь отсутствие зарегистрированного ожидания в момент наблюдения. Backend может выполнять инструкции CPU, быть вытеснен планировщиком ОС или находиться в неинструментированном участке. Нельзя делать вывод «100% CPU» из NULL.

    4.3. Почему одного снимка мало¶

    Одна точка измерения показывает состояние, а не накопленное за минуту время. Если транзакция попеременно выполняет 5 мс CPU и 95 мс ждет блокировку, случайный снимок может захватить любой участок. Периодическая выборка помогает оценить преобладающий тип ожидания, но не гарантирует точного профиля времени. Для точных причин связываем SQL, PID, логи блокировок, серверные счетчики и метрики приложения.

    SELECT coalesce(wait_event_type, '<без текущего wait>') AS wait_type,
       coalesce(wait_event, '<нет>') AS wait_name,
       count(*) AS backends
FROM pg_stat_activity
WHERE datname = current_database()
  AND state = 'active'
GROUP BY 1, 2
ORDER BY backends DESC;

    Если десятки запросов ожидают transactionid, вероятная следующая задача — обнаружить одну или несколько корневых транзакций, а не оптимизировать каждую SQL-команду по отдельности.

    5. Long transactions: цена даже без прямого блокирования¶

    5.1. Длинный запрос и длинная транзакция — разные вещи¶

    Транзакция может содержать десятки быстрых SQL-команд и минуты простоя между ними. xact_start покажет время жизни транзакции, query_start — команды. При обновлении строк она может долго удерживать блокировки и задерживать конкурентов. При удержании старого горизонта видимости она способна мешать удалению уже ненужных версий, что ведет к bloat и дополнительным проходам VACUUM.

    backend_xid отражает назначенный XID верхнеуровневой транзакции, а backend_xmin — ее текущий xmin-horizon. Они могут быть NULL; это важно для диагностики. Долгая транзакция с долгоживущим snapshot особенно опасна для очистки; но пустой BEGIN без старого snapshot нельзя автоматически считать причиной растущего bloat. На влияние также могут накладываться другие держатели горизонта, которые выходят за рамки основной лекции.

    SELECT pid, application_name, state,
       now() - xact_start AS tx_age,
       now() - state_change AS idle_age,
       backend_xid, backend_xmin,
       pg_blocking_pids(pid) AS blockers,
       left(query, 130) AS last_sql
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

    5.2. Почему от времени жизни страдает система целиком¶

    При частых UPDATE создаются новые версии строк. Пока какой-то snapshot все еще может видеть старую версию, обычное удаление этой версии было бы нарушением MVCC. Отложенная очистка означает больше страниц, больший размер таблиц/индексов, больше I/O и более долгие проходы обслуживания. Прямая блокировка одного accounts.id бьет в p99 конкретного сервиса; устаревший горизонт видимости может воздействовать сразу на многие горячие таблицы.

    В pg_stat_all_tables поле n_dead_tup дает оценку числа мертвых версий, а не точную мгновенную истину. Ее нужно изучать в динамике вместе с возрастом транзакций и работой VACUUM. Не стоит завершать «самую старую сессию» только по xact_age: сначала установите, держит ли она нужный lock/horizon и какое приложение ею управляет.

    5.3. pg_cancel_backend против pg_terminate_backend¶

    SELECT pg_cancel_backend(pid) отправляет сигнал отмены текущего SQL. Если backend просто простаивает внутри транзакции, отменять ему нечего; транзакция сама по себе от этого не обязана завершиться. pg_terminate_backend(pid) завершает соединение, и незавершенная транзакция откатывается. Для таких функций нужны права. В production сначала подтверждают PID, владельца, важность операции и блокирующую цепочку: ошибочное завершение может вызвать повторные операции, откаты и новые пики нагрузки.

    Итог раздела I. У нас есть конкретный путь: узнать состояние каждого backend-процесса → отличить постоянную нагрузку от текущей → увидеть ожидание → проверить время жизни транзакции и горизонт видимости → перейти к механике блокировок.

    II. Механика блокировок¶

    6. Row locks: почему MVCC не отменяет конкуренцию записей¶

    6.1. Обычный SELECT читает версию; UPDATE должен договориться с другим UPDATE¶

    Мы уже знаем, что MVCC позволяет читателям часто работать параллельно с писателями. Тогда зачем нужны блокировки строк? Потому что двум транзакциям нужно согласовать изменение одной логической записи. Прочитать старую версию и принять решение можно независимо, но одновременно «победить» в конфликтующем обновлении одной строки нельзя.

    Сессия A обновляет accounts.id = 1 и держит транзакцию открытой. Сессия B тоже обновляет id = 1 и ждет. Сессия C выполняет обычный SELECT balance FROM accounts WHERE id = 1 и, при подходящем снимке в READ COMMITTED, может получить последнюю подтвержденную версию без ожидания A. Это основа различия между видимостью версий и конфликтами изменения данных.

               Сессия A                           Сессия B
      BEGIN; UPDATE(id=1);               BEGIN; UPDATE(id=1);
          │  lock строки                      │  wait на A
          │                                   │
          ├───────── время ───────────────────┤
      COMMIT / ROLLBACK                        ▼
                                      B продолжает обработку

    Важно: PostgreSQL не обязан держать отдельную запись в RAM для каждой заблокированной строки. Сведения о блокировке хранятся в заголовке tuple, а ожидание может проходить через lock на идентификатор транзакции владельца. Это объясняет, почему pg_locks не работает как полная таблица «row ID → кто держит».

    6.2. Четыре режима строковых блокировок¶

    Режим Что защищает Типичный смысл
    FOR KEY SHARE От удаления и изменения ключа, на который могут ссылаться Ссылочная целостность
    FOR SHARE От конфликтующих изменений, допускает совместных читателей с lock Разделяемая блокировка
    FOR NO KEY UPDATE От обычных конкурирующих UPDATE без блокирования некоторых KEY SHARE Изменение неключевых полей
    FOR UPDATE Самая сильная из четырех строковых блокировок Изменение/удаление/резервирование строки

    Точная матрица конфликтов PostgreSQL 18 (X означает, что блокировка конфликтует с уже удерживаемой другим участником):

    Запрашиваемая ↓ / удерживаемая → KEY SHARE SHARE NO KEY UPDATE UPDATE
    KEY SHARE — — — X
    SHARE — — X X
    NO KEY UPDATE — X X X
    UPDATE X X X X

    Обычный UPDATE неключевого столбца обычно использует уровень FOR NO KEY UPDATE. Если обновление изменяет определенные уникальные ключевые колонки, пригодные для внешнего ключа, PostgreSQL выбирает более сильный FOR UPDATE. DELETE также использует FOR UPDATE. Указанная проверка ключей — деталь реализации PostgreSQL, а не обещание SQL-стандарта.

    6.3. Где в tuple хранится строковый lock¶

    В заголовке версии строки есть поля, среди которых xmin, xmax и биты t_infomask. xmax может означать идентификатор удаляющей/изменяющей транзакции либо владельца строки в контексте блокировки. Для совместных блокировок используется MultiXactId: он позволяет представить участие нескольких транзакций. Поэтому «xmax != 0 = строка удалена» — неверное упрощение.

    При SELECT ... FOR UPDATE PostgreSQL изменяет служебные сведения о строке, что может приводить к изменению страницы и WAL-записи. Даже «чтение с блокировкой» имеет цену записи и может создавать конкуренцию за буферы. Блокировки строк держатся до конца транзакции; блокировки, полученные после savepoint, освобождаются при откате к соответствующему savepoint.

    Ветвление на работу с заголовками и MultiXact на уровне исходников оставляем для 08.2. Сейчас нужно понимать практическое следствие: блокировать массово тысячи строк «на всякий случай» может оказаться дорогой операцией даже при очень простом SQL.

    6.4. Отдельные ограничения¶

    Строковая блокировка защищает выбранные версии строк, но не означает автоматический запрет вставки другой строки, соответствующей тому же поисковому условию. Корректность проверок диапазонов, уникальности и инвариантов может требовать других средств, уже обсужденных в блоке MVCC/изоляции. В этой лекции удерживаем фокус на конкуренции за конкретные строки.

    7. Table locks: почему один запрос может остановить чтения целой таблицы¶

    7.1. Название ROW EXCLUSIVE здесь обманывает¶

    Каждый UPDATE целевой таблицы получает табличную блокировку ROW EXCLUSIVE в дополнение к фактическим блокировкам строк. Обычный SELECT обычно получает ACCESS SHARE. Зачем? Пока запрос работает с отношением, PostgreSQL должен согласовать действия над самой таблицей — например, чтобы другая сессия не смогла одновременно выполнить несовместимую операцию, меняющую структуру или удаляющую отношение.

    Название ROW EXCLUSIVE историческое. Это режим блокировки отношения (relation). Конкретные блокировки строк — отдельный уровень. Два UPDATE разных строк могут одновременно держать ROW EXCLUSIVE на одной таблице, поскольку этот режим не конфликтует сам с собой.

    7.2. Восемь режимов и кто их получает¶

    Режим таблицы Типичный источник С чем конфликтует (кратко)
    ACCESS SHARE (AS) Обычный SELECT ACCESS EXCLUSIVE
    ROW SHARE (RS) SELECT ... FOR UPDATE EXCLUSIVE, ACCESS EXCLUSIVE
    ROW EXCLUSIVE (RX) INSERT, UPDATE, DELETE, MERGE SHARE и более сильные несовместимые
    SHARE UPDATE EXCLUSIVE (SUX) Обычные VACUUM, ANALYZE SUX, SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE
    SHARE (S) Обычный CREATE INDEX RX, SUX, SRX, EXCLUSIVE, ACCESS EXCLUSIVE
    SHARE ROW EXCLUSIVE (SRX) CREATE TRIGGER, отдельные операции RX, SUX, SHARE, SRX, EXCLUSIVE, ACCESS EXCLUSIVE
    EXCLUSIVE (X) REFRESH MATERIALIZED VIEW CONCURRENTLY Все кроме AS
    ACCESS EXCLUSIVE (AX) TRUNCATE, DROP TABLE, VACUUM FULL, часть ALTER TABLE Все режимы

    Полная матрица конфликтов (X — конфликт). Сокращения определены в таблице выше.

    ↓ / → AS RS RX SUX S SRX X AX
    AS — — — — — — — X
    RS — — — — — — X X
    RX — — — — X X X X
    SUX — — — X X X X X
    S — — X X — X X X
    SRX — — X X X X X X
    X — X X X X X X X
    AX X X X X X X X X

    Нюанс: даже ACCESS EXCLUSIVE может ожидать ранее взятый ACCESS SHARE. То есть длинное чтение может задержать сильную операцию. Но дальше начинаются еще более неприятные эффекты.

    7.3. Очередь из трех сессий: почему новое чтение тоже встало¶

    Сессия A                     Сессия B                  Сессия C
BEGIN;
SELECT ... FROM accounts;    LOCK TABLE accounts        SELECT ... FROM accounts;
-- A держит ACCESS SHARE       IN ACCESS EXCLUSIVE MODE; -- новое ACCESS SHARE
                             -- ожидает A               -- может ждать B в очереди

Время ───────────────────────────────────────────────────────────────────►

    Если B уже ожидает ACCESS EXCLUSIVE, новый ACCESS SHARE C может быть поставлен в очередь за B, хотя C совместим с еще удерживаемым ACCESS SHARE A. Это связано с политикой очередей: иначе поток новых читателей мог бы бесконечно мешать получить сильную блокировку. Так один ожидающий ACCESS EXCLUSIVE способен сформировать очередь новых читателей за собой.

    Важное уточнение: обычный SELECT вне BEGIN держит свою табличную блокировку до конца собственной короткой транзакции. Для воспроизведения долгого удержания в A нужен явный BEGIN и незавершенная транзакция, иначе пример развалится раньше, чем мы посмотрим состояние.

    7.4. Цена решения и диагностика¶

    Блокировки отношений учитываются в памяти сервера; изменение max_locks_per_transaction относится к емкости общей таблицы блокировок для объектов, а не к количеству строк, которые приложение способно заблокировать. Симптом под нагрузкой — рост active-backend-процессов с ожиданиями Lock/relation, зачастую после операции, затребовавшей сильный режим.

    Инженерный вывод: иногда правильный запрос к pg_locks важнее любого EXPLAIN — оптимальный по стоимости SELECT может ждать завершения чужой транзакции и потому медленно отвечать пользователю.

    III. Управление конфликтами¶

    8. SELECT FOR UPDATE: чтение с правом на последующее изменение¶

    8.1. Проверили остаток, а пока думали — его поменяли¶

    Рассмотрим списание средств. Читатель видит balance = 1000, затем приложение проверяет условие, а позже делает UPDATE. Другая транзакция могла изменить эту же строку между чтением и записью. Если логика требует опираться на актуальное состояние именно заблокированной записи, можно взять строковую блокировку до проверки и удержать ее до изменения.

    BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- Приложение проверяет бизнес-условие, пока держит row lock.
UPDATE accounts
   SET balance = balance - 200
 WHERE id = 1;
COMMIT;

    Во время ожидания конфликтующей строки SELECT ... FOR UPDATE может блокироваться. Если конкурент завершился, то в READ COMMITTED PostgreSQL работает с результатом обновления и повторно проверяет применимость условия; удаленная версия может не попасть в результат. При REPEATABLE READ/SERIALIZABLE изменение строки после снимка может приводить к ошибке сериализации, вместо молчаливого перехода к новой версии. Детальный разбор изоляции был в предыдущем блоке.

    8.2. Почему блокировать заранее не всегда разумно¶

    Строка остается заблокированной до завершения транзакции. Если после FOR UPDATE приложение ждет HTTP-ответ стороннего сервиса или взаимодействия с человеком, оно удерживает row lock дольше реального SQL. Входящие запросы образуют очередь, пропускная способность падает, а tail latency растет. Правильный инженерный прием — максимально короткая транзакционная секция, без неконтролируемых сетевых вызовов и долгих вычислений внутри нее.

    Кроме того, SELECT FOR UPDATE не обязателен для всякого списания. Когда операция сводится к атомарному условному изменению одной строки, часто удобнее:

    UPDATE accounts
SET balance = balance - 200
WHERE id = 1 AND balance >= 200
RETURNING balance;

    При пустом результате обновление не выполнено. Такой вариант уменьшает число round-trip к БД и связывает проверку с изменением в одном операторе. Оба подхода имеют свои ограничения; выбор определяется инвариантом, числом строк и требуемой логикой.

    8.3. Порядок блокировок¶

    Если нужно заблокировать несколько счетов, договоритесь об одном порядке: например, всегда по возрастанию id. Разные порядки A → B и B → A увеличивают вероятность deadlock. Для сложных запросов порядок фактического захвата блокировок зависит от выполнения SQL, поэтому требуемую гарантию надо обеспечить конструкцией транзакции и протестировать в условиях конкуренции.

    9. NOWAIT: быстрый отказ вместо непредсказуемой очереди¶

    9.1. Если нельзя ждать даже секунду¶

    У обработчика API есть бюджет задержки 100 мс. Обычный FOR UPDATE может ждать до конца чужой транзакции. Можно потребовать немедленный отказ при занятой строке:

    BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- При конфликтующем row lock: SQLSTATE 55P03 (lock_not_available).
ROLLBACK;

    При отсутствии конфликта блокировка будет получена. При конфликте PostgreSQL возвращает ошибку сразу на попытке получить строковую блокировку. Если ошибка возникла внутри обычной явной транзакции без специальной обработки, дальнейшие команды обычно получают 25P02 до ROLLBACK (либо требуется откат к установленному savepoint). Это принципиально для корректного кода на Go: нельзя просто проигнорировать ошибку и выполнить следующий SQL в той же неоткаченной транзакции.

    9.2. Упрощение NOWAIT ломается на уровне таблицы¶

    FOR UPDATE NOWAIT при работе с целевой таблицей также требует табличную блокировку ROW SHARE. Указание NOWAIT в locking clause действует на строки; табличная блокировка берется по обычным правилам и способна ждать. Поэтому абсолютное обещание «этот SQL никогда не блокируется» некорректно. Если важен отказ и на уровне отношения, нужно отдельно продумать явное LOCK TABLE ... NOWAIT или общий предел ожиданий.

    9.3. Когда быстрое завершение превращается в шторм повторов¶

    Если 100 клиентов в одну секунду получают 55P03 и немедленно повторяют запрос без задержки, они усиливают конкуренцию и расходуют ресурсы на бесполезные попытки. Клиентская стратегия должна иметь ограничение числа повторов, задержку с разбросом, общий deadline и понимание того, какие ошибки вообще допускают повтор. NOWAIT полезен для предсказуемой задержки отказа, но сам по себе не решает проблему перегруженного горячего ресурса.

    10. SKIP LOCKED: как разделить работу между конкурентными воркерами¶

    10.1. Почему десяти воркерам не нужна одна и та же первая строка¶

    Представим таблицу из 1000 заданий со статусом ready. Воркеры выбирают задание по минимальному id. При обычном FOR UPDATE все могут выстроиться за одним занятым заданием. SKIP LOCKED меняет правило: если строку нельзя немедленно заблокировать, выборка пропускает ее и рассматривает другие кандидаты. Для очереди это разумный компромисс: можно брать любое подходящее свободное задание, а не принципиально самое старое.

    BEGIN;
SELECT id
FROM jobs
WHERE status = 'ready'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
-- Полученный id блокируется этой транзакцией.
-- Вторая сессия с таким же запросом может выбрать следующий id.
COMMIT;

    Разумеется, после COMMIT блокировка освобождена. Если воркер сделал только SELECT и не изменил состояние задания, оно снова станет доступно. Поэтому реальный механизм должен зафиксировать захват внутри той же транзакции.

    10.2. Атомарная выдача задания¶

    WITH candidate AS (
    SELECT id
    FROM jobs
    WHERE status = 'ready'
    ORDER BY id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE jobs AS j
SET status = 'running', claimed_at = clock_timestamp()
FROM candidate AS c
WHERE j.id = c.id
RETURNING j.id, j.claimed_at;

    Один такой SQL внутри транзакции выбирает доступного кандидата и помечает его running. Конкурентные воркеры при обычных условиях возьмут другие строки. SKIP LOCKED не является строгой FIFO-гарантией: самое старое задание может долго оставаться заблокированным и постоянно пропускаться — starvation. Обязательна политика наблюдения за зависшими running и возможность безопасно переобрабатывать задачи после падения воркера. Долго держать БД-транзакцию на время фактической внешней обработки работы обычно нежелательно: лучше быстро зафиксировать claim, затем выполнять работу с ограниченным сроком владения и необходимой идемпотентностью.

    10.3. Где модель «никаких ожиданий» ломается¶

    SKIP LOCKED действует только на строковые блокировки в locking clause. Табличная ROW SHARE все еще может ждать. Запрос также может расходовать CPU и I/O, проходить большое число заблокированных кандидатов, работать с индексом и буферами. С ORDER BY и LIMIT нужно помнить о тонкостях выполнения и конкурентных изменений; у результата нет жесткой гарантии идеального распределения по времени создания.

    PostgreSQL прямо предупреждает: SKIP LOCKED дает неполное, потенциально непоследовательное представление о данных. Для обработки очередей это приемлемый выбор, для обычного отчета «покажи все долги клиента» — нарушение смысла запроса. Пропущенная строка не означает, что ее не существует.

    10.4. Сравнение трех стратегий¶

    Стратегия Если строка занята Когда подходит Цена
    FOR UPDATE Ждать Нужно дождаться именно этой записи Неограниченная очередь без таймаута
    FOR UPDATE NOWAIT Немедленно вернуть ошибку 55P03 Ограниченный latency budget, допускается отказ Ошибки и повторные попытки
    FOR UPDATE SKIP LOCKED Искать другую доступную строку Очередь независимых задач Пропуски, fairness, неполная картина

    Итог раздела III. Возможность выбрать стратегию конфликта — это возможность выбрать компромисс между корректностью, ожиданием, отказами и справедливостью очереди. Хороший SQL здесь определяется бизнес-инвариантом и свойствами нагрузки, а не только планом выполнения.

    IV. Конфликты и расследование блокировок¶

    11. Deadlocks: каждый lock взят правильно, а система стоит¶

    11.1. Почему «всего два UPDATE» могут остановить друг друга¶

    До сих пор одна сессия владела ресурсом, другая ждала. Обычная блокировка заканчивается после освобождения владельцем. Но представим две транзакции, каждая из которых уже удерживает одну строку и хочет получить строку другой. Получаем замкнутый цикл ожиданий.

    -- Сессия A                         -- Сессия B
BEGIN;                               BEGIN;
UPDATE accounts                      UPDATE accounts
SET balance = balance - 10           SET balance = balance - 20
WHERE id = 1;                        WHERE id = 2;

-- Здесь дождаться, когда обе      -- Здесь дождаться, когда обе
-- первые команды закончатся.      -- первые команды закончатся.

UPDATE accounts                      UPDATE accounts
SET balance = balance + 10           SET balance = balance + 20
WHERE id = 2;                        WHERE id = 1;
-- A ждет B                         -- B ждет A

    Граф ожиданий:

A удерживает row 1  ──►  B хочет row 1
▲                               │
│                               ▼
A хочет row 2      ◄──  B удерживает row 2

A → B → A = цикл. Ни один не сможет самостоятельно завершить команду.

    Это deadlock, взаимная блокировка. Добавление CPU, индексов или пропускной способности диска не разрывает логический цикл. PostgreSQL должен обнаружить его и прервать одного из участников.

    11.2. Как сервер обнаруживает цикл¶

    Постоянно строить полный граф зависимостей при каждой попытке lock было бы дорого. В PostgreSQL параметр deadlock_timeout определяет задержку перед проверкой на deadlock (обычно 1 секунду). Пока ожидание короткое, сервер надеется, что владелец просто закончит транзакцию. Если ожидание продолжается, запускается анализ зависимостей. При реальном цикле PostgreSQL завершает один из конфликтующих участников с ошибкой SQLSTATE 40P01 (deadlock_detected); выбор жертвы не является контрактом приложения.

    В результате прерванная транзакция откатывается. Вторая получает возможность двигаться дальше. Клиенту нельзя пытаться «продолжить с последнего UPDATE» в той же прерванной транзакции. Требуется новый транзакционный запуск всей операции и повторная проверка предпосылок. При этом повторы должны быть ограничены и безопасны относительно внешних побочных эффектов.

    11.3. Профилактика: один порядок объектов¶

    Если все транзакции обновляют счета в одном порядке, например меньший id, затем больший, цикл из разнонаправленного захвата этих же строк становится намного менее вероятным.

    Плохой порядок:        A: 1 → 2, B: 2 → 1   ⇒ потенциальный цикл.
Согласованный порядок: A: 1 → 2, B: 1 → 2   ⇒ B ждет 1, не держит 2.

    Это правило нужно соблюдать для всех путей кода, которые берут набор общих ресурсов: основной endpoint, фоновая обработка, обслуживание и редкие административные операции. «Все знают» не считается. Договоренность должна быть явной, проверяемой и воспроизводимой.

    11.4. Логирование реальных ожиданий¶

    При log_lock_waits = on сервер пишет в лог сведения о достаточно длительном ожидании блокировки, ориентируясь на deadlock_timeout. Снижение deadlock_timeout на время расследования помогает получить более ранний сигнал, но увеличивает частоту затратных проверок и потенциальный объем логов; изменение требует соответствующих прав. Ошибки deadlock также полезно фиксировать в метриках приложения по SQLSTATE, поскольку пользователь видит именно отказ операции.

    Инженерный вывод: deadlock не является свидетельством того, что PostgreSQL «сломал синхронизацию». Это следствие порядка получения конфликтующих ресурсов. Сначала устраняем циклы на уровне алгоритма работы с данными, затем настраиваем политику повторов.

    12. Advisory locks: бизнес-ключ без специальной строки¶

    12.1. Нужна блокировка, но чего именно?¶

    Представим фоновую операцию «обновить кеш клиента 123» или «вычислить отчет по договору». Возможно, здесь нет строки, которую логично удерживать через FOR UPDATE. PostgreSQL предоставляет advisory locks — блокировки по ключу, смысл которого выбирает приложение.

    BEGIN;
SELECT pg_advisory_xact_lock(12345);
-- Критическая бизнес-секция, согласованная между участниками.
COMMIT; -- Transaction-level advisory lock освобожден.

    Варианты ключей: один bigint или два значения integer; пространства этих ключей различаются. 12345 ничего не значит для PostgreSQL: сервер сравнивает lock keys, а приложение должно обеспечить отсутствие неправильных совпадений между сущностями. Без согласованного правила ключей разные сервисы способны случайно брать разные ключи на одну операцию или одинаковые ключи на несвязанные операции.

    12.2. Session-level против transaction-level¶

    Свойство Session-level Transaction-level
    Захват с ожиданием pg_advisory_lock(key) pg_advisory_xact_lock(key)
    Попытка без ожидания pg_try_advisory_lock(key) pg_try_advisory_xact_lock(key)
    Освобождение pg_advisory_unlock(key) или конец сессии Автоматически в конце транзакции
    После ROLLBACK Может оставаться, если взят ранее в сессии Освобождается
    Типичная опасность Забыли unlock и оставили соединение живым Слишком длинная транзакция

    Session-level advisory lock не подчиняется обычному откату бизнес-транзакции. Например, BEGIN; SELECT pg_advisory_lock(42); ROLLBACK; не обязан освобождать session-level lock. Если сессия продолжает существовать, блокировка продолжает жить, пока не будет снята или не закончится соединение.

    Advisory locks занимают ресурсы общего Lock Manager. Количество объектов блокировки ограничено объемом предусмотренной shared memory, а не бесконечно. Это не инструмент для хранения миллионов постоянных состояний по ключам.

    12.3. Почему advisory lock не защищает таблицу автоматически¶

    Worker A: pg_advisory_xact_lock(123)
Worker B: UPDATE accounts WHERE id = 123;  -- если B не берет тот же advisory lock,
                                             -- он не обязан ждать именно этот lock.

    PostgreSQL не связывает произвольный числовой advisory key с ключом accounts.id. Это добровольный контракт участников. Если хоть один путь кода не соблюдает его, защита логики становится неполной. Поэтому advisory locks применяем там, где можем контролировать всех конкурентов, а не вместо ограничений уникальности или необходимых транзакционных проверок.

    13. pg_locks и pg_blocking_pids(): найти первопричину¶

    13.1. Что реально хранит pg_locks¶

    Представление показывает выданные и ожидаемые блокировки объектов, управляемых соответствующими подсистемами PostgreSQL. Поля locktype, mode, granted, pid, waitstart объясняют тип ресурса, режим и факт ожидания. Для relation можно видеть OID таблицы, для transactionid — XID, завершения которого ждут. Есть также virtualxid, advisory locks и другие типы.

    SELECT pid, locktype, mode, granted, waitstart,
       CASE WHEN database = (SELECT oid FROM pg_database
                              WHERE datname = current_database())
            THEN relation::regclass::text
            ELSE NULL
       END AS relation_name,
       transactionid, virtualxid, fastpath
FROM pg_locks
WHERE NOT granted
ORDER BY waitstart NULLS LAST;

    Уточнение: даже если locktype = 'tuple' иногда встречается, полный список всех заблокированных строк тут не хранится. Строковые блокировки обычно отражены на диске в tuple metadata; ожидающий участник часто виден как ShareLock на transactionid, в то время как владелец удерживает соответствующий ExclusiveLock на своем XID. Это нормальная схема и важная диагностическая ловушка.

    13.2. Почему простое самосоединение pg_locks часто ошибочно¶

    На первый взгляд легко соединить ожидающие и удерживаемые строки по таблице и объявить владельца виновником. Но для корректного решения нужно учитывать полную матрицу конфликтов режимов, очередность ожидающих блокировок и особенности параллельных worker-процессов. pg_locks не выдает готовой информации об очереди ожиданий. Поэтому официальный рекомендуемый способ — функция pg_blocking_pids(pid).

    SELECT w.pid AS waiting_pid,
       w.application_name AS waiting_app,
       w.wait_event_type, w.wait_event,
       now() - w.query_start AS waiting_query_age,
       b.pid AS blocking_pid,
       b.state AS blocker_state,
       now() - b.xact_start AS blocker_tx_age,
       left(w.query, 100) AS waiting_sql,
       left(b.query, 100) AS blocker_last_sql
FROM pg_stat_activity AS w
JOIN LATERAL unnest(pg_blocking_pids(w.pid)) AS bp(pid) ON true
LEFT JOIN pg_stat_activity AS b ON b.pid = bp.pid
WHERE w.datname = current_database()
ORDER BY w.query_start;

    Функция учитывает и hard blockers (держат несовместимую блокировку), и soft blockers (стоят впереди в очереди с конфликтующим запросом). У prepared transactions могут отсутствовать обычные PID backend-процессов; не следует интерпретировать NULL в соединении с pg_stat_activity как доказательство отсутствия блокировки.

    13.3. Цепочка ожиданий: поиск корневого блокирующего участника¶

    Предположим:

    PID 101: idle in transaction, держит row lock
    │
    ▼
PID 202: active, ждет 101 и держит другой lock
    │
    ▼
PID 303: active, ждет 202
    │
    ▼
PID 404: active, ждет 303

    Все три ожидающих процесса могут иметь возрастающий query_age; они не обязаны быть первопричиной. Разрыв цепочки ближе к корню зачастую устраняет больше ожиданий. Но важно устанавливать именно причинный граф, а не только «самую старую транзакцию». Бывают несколько независимых корней, подготовленные транзакции, разные lock modes и конкуренция за разные отношения.

    Для первичного обзора полезна одна практическая выборка:

    SELECT pid, application_name, state,
       wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by,
       now() - xact_start AS tx_age,
       now() - query_start AS sql_age,
       left(query, 100) AS sql
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY cardinality(pg_blocking_pids(pid)) DESC,
         xact_start NULLS LAST;

    При тяжелом инциденте не следует бездумно выполнять эту функцию тысячекратно в очень частом цикле: мониторинг сам потребляет ресурсы. Выполните несколько согласованных снимков и сопоставьте с метрикой latency.

    13.4. Не забыть проверить ограничения снимка¶

    pg_locks собирает данные разных подсистем и fast-path locks не строго атомарно по всем backend-процессам. В быстро меняющейся системе одно чтение может содержать временные несовпадения. waitstart иногда остается NULL сразу после начала ожидания. При просмотре relation::regclass для другой базы нельзя просто интерпретировать OID через каталог текущей базы; для таких строк нужны отдельные сведения.

    Надежная диагностика: pg_stat_activity → pg_blocking_pids() → конкретные pg_locks → последняя команда и возраст транзакции блокирующего процесса → подтверждение бизнес-причины в приложении. Только затем решаем, что отменять или исправлять.

    14. lock_timeout: управление максимальной ценой ожидания¶

    14.1. В чем разница трех часов¶

    Ожидание может длиться сколько угодно, если не задан предел и никто не освобождает ресурс. Для deadline приложения полезно различать:

    Настройка Что ограничивает Типичный симптом
    lock_timeout Каждую отдельную попытку получить lock Ошибка при долгом ожидании объекта
    statement_timeout Продолжительность SQL-оператора в сервере SQL слишком долго работает или ждет
    idle_in_transaction_session_timeout Бездействие сессии внутри транзакции Backend закрыт после простоя

    В PostgreSQL 18 есть также transaction_timeout — общий предел времени транзакции, включая несколько команд. Он не заменяет описанные механизмы; набор настроек нужно учитывать совместно. deadlock_timeout вообще не является лимитом исполнения: он задает момент начала проверки на цикл ожиданий.

    14.2. Правильная установка локального предела¶

    BEGIN;
SET LOCAL lock_timeout = '250ms';
SET LOCAL statement_timeout = '3s';
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
COMMIT;

    lock_timeout применяется отдельно к каждой попытке получения блокировки на таблице, индексе, строке или другом объекте. Если SQL последовательно ожидает пять lock по 200 мс при лимите 250 мс, суммарное время ожиданий может приблизиться к секунде без срабатывания lock_timeout. statement_timeout при этом измеряет весь оператор, включая ожидание.

    При ошибке внутри явной транзакции нужно выполнить ROLLBACK или соответствующий откат к savepoint. В production целесообразно сравнивать deadline вызывающего API, серверные пределы и допустимое число повторов; нельзя считать время обработки равным lock_timeout.

    14.3. Почему слишком маленький timeout ухудшает систему¶

    Если короткий запрос регулярно сталкивается с живой транзакцией длительностью 300 мс, лимит 10 мс приведет к потоку ошибок и повторов, но не устранит горячую точку. Если поставлен statement_timeout = 100ms и lock_timeout = 500ms, второй почти не сможет сработать: общий предел завершит команду раньше.

    Параметры нужно выбирать после измерения обычной длительности транзакций, p95/p99 ожидания и доли отказов. Действенная профилактика начинается с сокращения времени удержания блокировки и единообразного порядка их получения; timeout лишь ограничивает последствия.

    Итог раздела IV. Разница между обычным ожиданием и deadlock принципиальна. Для ожидания нужна локализация корневого владельца, для deadlock — исправление порядка и контролируемый повтор. pg_locks и pg_blocking_pids() позволяют обосновать решение наблюдениями, а таймауты ограничивают время деградации.

    V. Frozen tuples: долг старых XID¶

    15. Frozen tuples: что случится после четырех миллиардов транзакций¶

    15.1. Почему возраст строки нельзя хранить только в бесконечно растущем счетчике¶

    В PostgreSQL обычный идентификатор транзакции (XID) имеет 32 бита. После конечного числа назначений значение по модулю 2^32 возвращается к началу диапазона. Для MVCC важно уметь сравнивать возраст транзакций: изменения из будущего не видны текущей транзакции, изменения достаточно далекого прошлого — видны.

    Числовое сравнение без учета кольцевой природы XID перестало бы работать на границе переполнения (wraparound). PostgreSQL использует специальную арифметику для относительного сравнения XID: для каждой обычной точки около половины 32-битного пространства интерпретируется как прошлое, другая половина — как будущее. Если сохранять очень старый обычный XID слишком долго, однажды он начнет восприниматься как будущий. Поэтому старые версии нужно замораживать.

    Кольцо обычных XID, условная модель:

                  текущий XID
                       │
                       ▼
          старое ◄─────●─────► новое
               (примерно по 2^31 с каждой стороны)

Версия строки с чрезмерно старым обычным XID без freezing
может оказаться «с другой стороны» кольца.

    Это логическая проблема доступности данных, а не просто место в таблице. Старые XID нельзя навсегда оставлять как обычные идентификаторы. VACUUM обязан периодически проходить данные и обеспечивать безопасную видимость старых версий.

    15.2. Что означает frozen¶

    Для достаточно старых подтвержденных вставок PostgreSQL ставит специальный признак заморозки. При проверке видимости такая версия рассматривается как имеющая «древнюю» вставляющую транзакцию, которую уже не нужно сравнивать с текущими обычными XID. Специальный FrozenTransactionId имеет значение 2. Начиная с PostgreSQL 9.4 современная реализация обычно ставит флаг в заголовке tuple, сохраняя исходное значение xmin; физическая подмена xmin числом 2 не требуется.

    Отсюда диагностическая ловушка: увидеть старое число в системной колонке xmin и заключить «строка не была заморожена» нельзя. При заморозке важен установленный флаг, а не обязательная перезапись отображаемого XID. Подробности tuple header и соответствующих битов вынесем в углубление 08.3.

    15.3. Две работы VACUUM¶

    Первая — находить версии, которые уже никому не нужны, и освобождать возможность повторного использования места. Вторая — гарантировать, что у достаточно старых живых версий не останутся опасные XID. Привычное упрощение «VACUUM нужен только для уборки мертвых строк» здесь ломается: даже почти неизменяемой таблице периодически требуется защита от XID wraparound.

    Параметры:

    • vacuum_freeze_min_age — минимальный возраст XID, при котором VACUUM рассматривает заморозку соответствующих версий.
    • vacuum_freeze_table_age — порог, после которого VACUUM применяет агрессивную стратегию, проходя страницы, которые обычная очистка могла бы пропустить.
    • autovacuum_freeze_max_age — порог принудительного anti-wraparound autovacuum; возраст исчисляется количеством XID, а не минутами или днями.
    • relfrozenxid — нижняя граница самого старого потенциально незамороженного XID в отношении; datfrozenxid — соответствующий рубеж по базе данных.

    В PostgreSQL 18 обычный VACUUM также может eagerly scan часть страниц, уже помеченных как all-visible, но еще не all-frozen. Он использует такие проходы для опережающей заморозки и уменьшения работы будущего aggressive VACUUM. Параметр vacuum_max_eager_freeze_failure_rate позволяет влиять на этот подход. Это особенность PostgreSQL 18; алгоритм внутри VACUUM здесь не разворачиваем.

    15.4. Как увидеть проблему заранее¶

    -- Возраст заморозки по базам данных.
SELECT datname,
       age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;

-- Возраст отношения с учетом TOAST.
SELECT c.oid::regclass AS relation_name,
       greatest(age(c.relfrozenxid), age(t.relfrozenxid)) AS xid_age
FROM pg_class AS c
LEFT JOIN pg_class AS t ON t.oid = c.reltoastrelid
WHERE c.relkind IN ('r', 'm')
ORDER BY xid_age DESC NULLS LAST
LIMIT 30;

-- Оценка накопленных мертвых версий и работа VACUUM.
SELECT relid::regclass AS relation_name,
       n_live_tup, n_dead_tup,
       last_vacuum, last_autovacuum,
       vacuum_count, autovacuum_count
FROM pg_stat_all_tables
ORDER BY n_dead_tup DESC
LIMIT 20;

    Сравнивайте age(relfrozenxid) прежде всего с настройками конкретного экземпляра и скоростью расходования XID. Значение 100 млн может быть терпимым при здоровом графике VACUUM и тревожным при быстром увеличении возраста без прогресса очистки. Точная граница защищена специальными механизмами PostgreSQL; если рискуют пересечь опасный рубеж, сервер пишет предупреждения и в конце концов отказывается назначать новые XID, чтобы предотвратить логическую порчу видимости.

    15.5. Связь с long transactions и производственной нагрузкой¶

    Если активные снимки данных или другие удерживающие горизонт механизмы долго не дают удалить устаревшие версии, VACUUM вынужден сохранять их. Это означает физическую цену конкурентности: больше страниц, больше сканирований и давление на storage. При неблагоприятных условиях PostgreSQL может начать более агрессивную работу по заморозке, чтобы не приблизиться к опасному XID age; соответствующие autovacuum-процессы не всегда можно безопасно прерывать ради временного снижения I/O.

    Важно: высокий n_dead_tup, длительная транзакция и большой age(datfrozenxid) — три разных сигнала. Они могут быть связаны, но ни один не доказывает причины остальных. Корректная диагностика требует сопоставить горизонты видимости, активные XID, прогресс VACUUM и возраст заморозки.

    16. Полный разбор инцидента: от пяти секунд к корневой транзакции¶

    Теперь соединим механизмы одной историей, без нового архитектурного слоя.

    Шаг 1. Симптом. Сервис показывает p99 = 5 с при низком CPU. Запросы к accounts выполняются нормально на малой конкуренции, план SELECT/UPDATE не менялся.

    Шаг 2. Текущий снимок. pg_stat_activity показывает множество active процессов с wait_event_type = 'Lock'; часть ожидает transactionid. В стороне одна сессия idle in transaction с десятиминутным xact_age.

    Шаг 3. Проверяем причинность. pg_blocking_pids(waiting_pid) указывает на PID этой сессии для нескольких ожидающих запросов. В pg_locks видим ожидаемые ShareLock и удерживаемые блокировки транзакции. Подтверждаем идентификатор клиента и его последнюю команду.

    Шаг 4. Ищем ошибку в приложении. В транзакционной секции после UPDATE был вызов внешнего сервиса. Ответ подвис, код не завершил транзакцию, но соединение осталось открытым. Строка остается заблокированной.

    Шаг 5. Разруливаем аккуратно. Оцениваем возможность прерывания операции. На тестовом стенде выполняем ROLLBACK в владельце; заблокированные команды продолжают работу. В production закрытие соединения возможно только после подтверждения влияния на бизнес-операцию и корректной стратегии повторов.

    Шаг 6. Исправляем причину. Убираем длительное ожидание внутри транзакции, делаем четкий deadline, уменьшаем время между захватом и освобождением строковых блокировок, используем lock_timeout как предохранитель и метрики SQLSTATE.

    Шаг 7. Повторно измеряем. Сравниваем до и после: p95/p99 операции, долю backend-процессов с Lock, средний возраст транзакций, частоту 55P03/40P01, пропускную способность. Только при уменьшении ожиданий и восстановлении throughput исправление можно считать подтвержденным.

    16.2. Что нельзя делать по одному счетчику¶

    Не стоит считать все active backend-процессы занятыми CPU, все idle — блокирующими, все транзакции с большим xact_age — одинаково опасными для VACUUM, а все transactionid waits — «проблемой идентификаторов». Нельзя оптимизировать один наиболее медленный запрос по max_exec_time, не проверив частоту вызовов. И нельзя отправлять pg_terminate_backend только потому, что PID стоит первым по длительности.

    Сильная диагностика соединяет данные нескольких источников, восстанавливает порядок событий и показывает, кто именно держит ресурс, почему держит и какая часть нагрузки от этого зависит.

    17. Основная модель, которую нужно унести с лекции¶

    1. Время SQL = вычисления + ожидания. active означает обработку команды, но процесс может почти целиком ждать lock, I/O или другой ресурс.
    2. Текущая и накопительная диагностика решают разные задачи. pg_stat_activity показывает состояние сейчас, pg_stat_statements — агрегированную цену шаблонов запросов за период.
    3. MVCC не исключает конфликтующие записи. Row locks согласуют изменения конкретных строк; table locks защищают отношения и могут формировать очередь обычных SELECT.
    4. Выбор поведения при конфликте — инженерное решение. FOR UPDATE ждет, NOWAIT отказывает, SKIP LOCKED пропускает; у каждого варианта своя цена и область применимости.
    5. Deadlock — цикл, а длительное ожидание — цепочка. pg_blocking_pids() помогает найти владельцев; устойчивый алгоритм задает единый порядок захвата ресурсов и ограниченные повторы.
    6. Срок жизни транзакции — ограниченный ресурс. Даже без активного SQL она может удерживать блокировки и горизонты видимости, мешать VACUUM и ухудшать p99.
    7. XID freezing защищает правильность видимости. VACUUM нужен и для очистки мертвых версий, и для предотвращения wraparound.
