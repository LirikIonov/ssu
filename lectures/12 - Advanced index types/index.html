    12. PostgreSQL Advanced Index Types¶

    Магистратура · PostgreSQL 18 · REL_18_STABLE · обязательная лекция блока 12.
    Фокус: GIN, jsonb, массивы, полнотекстовый поиск, pg_trgm, write path GIN, GiST, SP-GiST, BRIN, стоимость индексов и диагностика в production.
    Уже изучено: B-tree, heap и MVCC, планировщик / cost model / EXPLAIN ANALYZE, VACUUM, WAL, concurrency и индексы в DDL. Эти механизмы здесь не пересказываем.
    Типы утверждений: гарантии операторов и API отделены от конкретных operator classes, текущей реализации access methods и результатов отдельных измерений. SQL-примеры рассчитаны на PostgreSQL 18; эксперименты с отключением индекса, REINDEX и нагрузкой выполняем только на учебном стенде.

    0. Производственный инцидент: индекс есть, запрос все равно медленный¶

    У backend-сервиса есть каталог товаров. В каждой записи — jsonb с характеристиками, массив меток и описание. На первое время хватало обычных B-tree по id, category_id и created_at. Затем появились три запроса:

    -- Найти товары с определенными характеристиками.
SELECT id FROM products
WHERE attributes @> '{"camera": {"stabilization": true}}'::jsonb;

-- Найти товар, в описании которого встречается подстрока.
SELECT id FROM products WHERE description ILIKE '%оптическая%';

-- Показать события за последнюю минуту в таблице на сотни миллионов строк.
SELECT count(*) FROM events
WHERE created_at >= now() - interval '1 minute';

    Сейчас архитектор произносит магическое «добавим индекс». Какой именно? Если построить B-tree по attributes, он будет упорядочивать целое значение JSONB, а не отвечать автоматически на вопрос о наличии элемента внутри документа. Для ILIKE '%оптическая%' обычный B-tree не может использовать лексикографический диапазон по левому префиксу. Для большого журнала событий B-tree может оказаться весьма объемным, хотя необходима лишь приблизительная фильтрация физических диапазонов страниц.

    Здесь начинается новая модель: индекс выбирается одновременно по семантике оператора, типу данных, распределению значений и цене изменений. PostgreSQL содержит несколько методов доступа (access methods), каждый решает собственную задачу. Главный инженерный вопрос: что дешевле — хранить точные ссылки для множества ключей, хранить геометрические ограничения или записывать очень компактную сводку по группам heap-страниц?

    Запрос на SQL
    |
    +-- Есть сортируемый скаляр и сравнение?       -> B-tree (уже изучен)
    +-- Элементы внутри JSONB / массива / текста?  -> GIN
    +-- Диапазоны, геометрия, близость?            -> GiST
    +-- Пространство естественно делится на части? -> SP-GiST
    +-- Значение связано с физическим порядком?    -> BRIN
    |
    v
Индикаторы: planning time, heap blocks, recheck, index size,
           latency SELECT/INSERT/UPDATE, p95/p99 и стоимость обслуживания

    Для всей лекции будем пользоваться тремя контрольными наборами: products(attributes jsonb, tags text[], description text), bookings(during tstzrange) и events(created_at timestamptz). Ни один план или конкретная скорость не обещаны заранее: optimizer выбирает план по статистике, а результаты зависят от объема, железа и формы запросов.

    1. Index Access Methods: почему USING — часть контракта SQL¶

    1.1. Что именно выбирает PostgreSQL при CREATE INDEX¶

    Мы уже умеем создавать B-tree. Но команда CREATE INDEX имеет важный параметр USING: он выбирает физический метод доступа к индексу. PostgreSQL 18 содержит встроенные B-tree, Hash, GiST, SP-GiST, GIN и BRIN. Установка расширений может добавить operator classes, специализированные типы и методы. В этой лекции нас интересуют четыре последних; Hash упомянем только как метод для равенства, обычно не дающий принципиального преимущества перед универсальным B-tree в типичной backend-схеме.

    CREATE INDEX products_attrs_gin ON products USING gin (attributes);
CREATE INDEX bookings_during_gist ON bookings USING gist (during);
CREATE INDEX places_location_spgist ON places USING spgist (location);
CREATE INDEX events_created_brin ON events USING brin (created_at);

    Это четыре различные организации поиска. Индексный метод отвечает за хранение записей, поиск и модификации. Но метод сам по себе не знает, что означает оператор для каждого типа данных. Например, @> у массива, JSONB и диапазона имеет разные внутренние представления.

    1.2. Operator class: почему на одном столбце два GIN работают по-разному¶

    Операторный класс (operator class, opclass) связывает индекс с конкретными операторами и поддерживающими функциями для типа данных. Выражение WHERE attributes @> ... может использовать индекс только в том случае, если соответствующий индексный opclass поддерживает это условие. Одинаковая колонка может индексироваться с разной семантикой.

    CREATE INDEX p_json_ops
    ON products USING gin (attributes jsonb_ops);

CREATE INDEX p_json_path_ops
    ON products USING gin (attributes jsonb_path_ops);

    jsonb_ops — opclass по умолчанию для GIN над jsonb. jsonb_path_ops поддерживает более узкий набор операторов, оптимизируя определенные формы containment/jsonpath. Индекс размера меньше или быстрее — это распространенный результат, не универсальная гарантия. Данный opclass не ускорит условие с оператором, который не поддерживает. Проверять надо не только SQL-тип, но и пару: выражение в WHERE + operator class. См. [PG18-OPCLASS], [PG18-JSON].

    1.3. Operator family, lossiness и recheck¶

    Семейство операторов (operator family) связывает совместимые классы и операции. Для обычной прикладной разработки достаточно знать, что реализация индексного поиска может возвращать точный ответ или кандидатов. Если индекс хранит приближенную информацию, executor обязан заново проверить исходный предикат на heap-строке. Это называется recheck.

      Индекс: набор кандидатов TID
              |
              v
   Heap / Bitmap Heap Scan
              |
              v
   Recheck Cond: исходный SQL-предикат
              |
       +------+------+
       |             |
   Подходит       Не подходит
   в ответ       отбросить

    План Bitmap Heap Scan может дополнительно выполнять recheck из-за lossy bitmap pages, когда TID были укрупнены до номера heap-страницы при недостатке памяти. Это отдельная причина recheck, ее нельзя автоматически приписывать GiST или BRIN. В EXPLAIN (ANALYZE, BUFFERS) смотрим Recheck Cond, Rows Removed by Index Recheck, Heap Blocks: exact/lossy и фактические обращения к heap. См. [PG18-XINDEX], [PG18-EXPLAIN].

    1.4. Индекс не обязан побеждать Seq Scan¶

    Пользователь спрашивает: «Если индекс есть, почему EXPLAIN показывает Seq Scan?» Потому что access method лишь предлагает альтернативный путь. Планировщик сравнивает стоимость. Если предикат выбирает половину таблицы, перебор кандидатов, обращение к heap и дополнительный recheck могут стоить дороже последовательного чтения. Для короткой таблицы индекс тоже часто бессмысленен.

    Ключевая дисциплина: сначала воспроизводим характерный SQL и характерное распределение данных, выполняем ANALYZE, затем сравниваем планы, объем heap I/O и задержки. Принудительное SET enable_seqscan = off допускается только как диагностический эксперимент; это не исправление production-производительности.

    Вывод раздела: index type — это алгоритм хранения; opclass — поддерживаемый набор операторов; planner — выбор альтернативы; executor — точная проверка результата. Ошибка любого из четырех слоев объясняет фразу «индекс построили, а запрос не ускорился».

    2. GIN: инвертированный индекс, который ищет элементы внутри значения¶

    2.1. Почему один документ превращается в много индексных ключей¶

    Берем jsonb, массив или tsvector. Один документ может содержать десятки или сотни элементов, а запрос интересуется отдельным элементом. Хранить в B-tree все целые документы в некотором порядке недостаточно: нужна обратная адресация.

    GIN (Generalized Inverted Index) хранит связи вида key -> множество TID строк, содержащих этот ключ. Внутренний GIN имеет дерево по ключам, а для ключа хранит posting list или отдельное posting tree, если ссылок слишком много. Это детали текущей реализации PostgreSQL, описанные в [PG18-GIN].

       Heap                                  GIN index
 (42,1)  tags=[camera, 4k]              key=camera -> (42,1), (42,8), (73,3)
 (42,8)  tags=[camera, oled]              key=4k     -> (42,1), (90,2)
 (73,3)  tags=[camera, wifi]              key=oled   -> (42,8)
 (90,2)  tags=[4k, vr]                   key=wifi   -> (73,3)
                                         key=vr     -> (90,2)

    Поиск tags @> ARRAY['camera','4k'] сводится к поиску posting sets и их объединению по правилам оператора. Для containment с двумя обязательными элементами логически нужна пересеченная часть наборов TID. Как именно организовать обход posting lists и проверку — внутренняя оптимизация GIN, а семантику задает operator class.

    2.2. Posting list, posting tree и цена частых значений¶

    Представим 10 миллионов товаров. Ключ camera встречается в шести миллионах строк, а periscope — лишь в десяти тысячах. Для частого ключа posting list велика; GIN может хранить TID в отдельной posting tree. Индекс по-прежнему полезен для сочетания редкого и частого ключа, но запрос только по camera вернет слишком много кандидатов.

    Нечастый элемент:  periscope -> 10 000 TID
Частый элемент:    camera    -> 6 000 000 TID

WHERE tags @> ARRAY['periscope', 'camera']
  поиск по двум наборам; множество кандидатов ограничивает редкий ключ

WHERE tags @> ARRAY['camera']
  возможно чтение большой доли heap, дорогой recheck и даже Seq Scan

    Оптимизация здесь — качество фильтрации. Индекс ускоряет поиск кандидатов, но не уменьшает число строк, реально удовлетворяющих слишком широкому условию. Если предикат возвращает миллионы строк, конечную задержку определяют и heap I/O, и объем результата, и передача по сети.

    2.3. Где заканчивается GIN: heap и MVCC¶

    GIN хранит индексные ключи и ссылки, а не полноценные исходные документы. Поэтому GIN не поддерживает Index Only Scan: он обычно не может реконструировать исходное значение колонки по одному индексному ключу. Чтобы вернуть документ или проверить условие, PostgreSQL работает с heap и обычными правилами видимости. Этот принцип остается верным при SELECT id: индекс GIN не превращается автоматически в covering index по id.

    Важно разделять: для конкретного opclass индекс может дать точное логическое соответствие, но иногда реальная проверка все равно нужна; у Bitmap Heap Scan дополнительный recheck может появиться из-за lossy bitmap. И повторно: цена индекса не ограничивается чтением, ведь каждый новый документ дает много индексных ключей. См. [PG18-INDEXONLY], [PG18-GIN].

    2.4. Минимальная демонстрация¶

    CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    attributes jsonb NOT NULL,
    tags text[] NOT NULL DEFAULT '{}',
    description text NOT NULL
);

INSERT INTO products (attributes, tags, description) VALUES
 ('{"camera":{"stabilization":true},"storage":256}',
  ARRAY['camera','premium'], 'Optical stabilizer and fast sensor'),
 ('{"camera":{"stabilization":false},"storage":128}',
  ARRAY['camera','budget'], 'Entry-level phone'),
 ('{"screen":"oled","storage":512}',
  ARRAY['oled','premium'], 'Large OLED tablet');

CREATE INDEX products_tags_gin ON products USING gin(tags);
ANALYZE products;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM products WHERE tags @> ARRAY['camera'];

    На трех строках нормальным результатом будет Seq Scan: индекс здесь только для изучения механизма. Для показательной разницы понадобится большой набор данных, достаточная селективность и холодные/теплые измерения в сопоставимых условиях.

    2.5. Почему «GIN всегда быстрее B-tree» — неправильный вопрос¶

    B-tree дает хороший доступ к скалярному равенству и диапазону; GIN эффективен для операций с несколькими элементами значения. Если запрос WHERE id = $1, нужен B-tree по id. Если запрос проверяет набор тегов, нужен соответствующий GIN opclass. Если клиент фильтрует и по category_id, и по тегам, план может сочетать индексы или использовать другую стратегию; стоимость определяется количеством кандидатов.

    Вывод раздела: GIN покупает быстрый поиск по составным значениям ценой множества индексных ключей, дополнительной структуры posting lists/trees и более дорогой записи. Под нагрузкой дальше придется платить и за их обслуживание.

    3. GIN и JSONB: jsonb_ops против jsonb_path_ops¶

    3.1. Два opclass, один столбец, разные поддерживаемые запросы¶

    Возьмем документ:

    {
  "camera": {"stabilization": true, "zoom": 5},
  "tags": ["premium", "photo"],
  "brand": "example"
}

    Для полноценных документов jsonb_ops по умолчанию индексирует ключи и значения по отдельным элементам структуры. jsonb_path_ops использует более специфические ключи, учитывающие путь к значению, и поддерживает containment/jsonpath. Он не поддерживает key-exists операторы ?, ?|, ?&. Эта разница — часть контракта PostgreSQL 18, а не вопрос вкуса. См. [PG18-JSON].

    Пример WHERE jsonb_ops jsonb_path_ops
    attributes @> '{"brand":"example"}' Да Да
    attributes ? 'brand' Да Нет
    attributes ?| array['brand','tags'] Да Нет
    attributes @? '$.camera.zoom ? (@ > 3)' Да* Да*

    * Для jsonpath GIN извлекает поддерживаемые условия сравнения вида accessor_chain == constant и родственные индексируемые формы; не каждое выражение jsonpath превращается в селективный GIN-поиск. Наличие оператора @? само по себе не обещает ускорение.

    3.2. Почему jsonb_path_ops часто меньше¶

    У jsonb_ops одинаковое значение true в разных ветвях дерева дает отдельные элементы индекса, а путь и значение далее комбинируются при поиске. У jsonb_path_ops путь и значение участвуют в формировании индексного ключа. Запрос по конкретному вложенному значению может сразу сузиться до нужного пути.

    Это помогает в документах с множеством повторяющихся ключей и значений, но платим универсальностью. Кроме того, структура, не содержащая индексируемых значений (например, пустой объект по определенному пути), может обрабатываться jsonb_path_ops плохо: для @> '{"a": {}}' поиск не получает обычного точного ключа и может требовать дорогого сканирования. Нельзя выбирать opclass, не изучив реальные SQL.

    3.3. Ловушка: оператор ? проверяет верхний уровень¶

    -- key-exists на верхнем уровне JSONB:
SELECT id FROM products WHERE attributes ? 'camera';

-- Здесь мы сначала получаем вложенный JSONB, потом проверяем ключ:
SELECT id FROM products WHERE (attributes -> 'camera') ? 'zoom';

    GIN по attributes не обязательно подходит для второй формы, поскольку оператор ? применяется к выражению (attributes -> 'camera'), а не к целой колонке. Для повторяющегося запроса можно создать индекс выражения:

    CREATE INDEX products_camera_keys_gin
ON products USING gin ((attributes -> 'camera'));

    Альтернатива — переписать условие как containment по всей колонке, если семантика допускает это:

    SELECT id FROM products
WHERE attributes @> '{"camera":{"zoom":5}}'::jsonb;

    Последний SQL эквивалентен проверке конкретного значения zoom=5, а не просто существования ключа zoom. Нельзя подменять семантику ради индекса.

    3.4. Как выбирать opclass по реальным запросам¶

    Создаем две одинаковые копии таблицы для честного эксперимента и индексируем каждую своим opclass. Меряем pg_relation_size(index), EXPLAIN (ANALYZE, BUFFERS), среднюю и хвостовую задержку SELECT, время построения индекса и скорость INSERT/UPDATE. Затем добавляем ? и JSONPath-запросы.

    CREATE INDEX products_attrs_ops
 ON products USING gin (attributes jsonb_ops);

-- Альтернативный индекс в отдельном эксперименте, не обязательно рядом:
CREATE INDEX products_attrs_path_ops
 ON products USING gin (attributes jsonb_path_ops);

SELECT pg_size_pretty(pg_relation_size('products_attrs_ops')) AS ops_size,
       pg_size_pretty(pg_relation_size('products_attrs_path_ops')) AS path_size;

    Если оба индекса оставить на production-таблице, платить за поддержку придется дважды. Два индекса оправданы только при доказанной полезности разной семантики запросов.

    Вывод раздела: opclass — фактически часть API между SQL и индексом. Изменение opclass требует сверки операторов и нагрузки, а не только размера индекса.

    4. GIN для массивов: containment, overlap и цена денормализации¶

    4.1. Семантика операторов важнее названия колонки¶

    Столбец tags text[] иногда удобен: каждая строка содержит набор меток. GIN с array_ops поддерживает важные операции:

    -- Все указанные значения присутствуют:
SELECT * FROM products WHERE tags @> ARRAY['camera', 'premium'];

-- Есть хотя бы одно общее значение:
SELECT * FROM products WHERE tags && ARRAY['photo', 'budget'];

-- Значения массива слева содержатся в указанном наборе:
SELECT * FROM products WHERE tags <@ ARRAY['premium', 'camera', 'oled'];

-- Равенство массива тоже поддерживается operator class:
SELECT * FROM products WHERE tags = ARRAY['camera', 'budget'];

    @> и && дают разную селективность. Условие && ARRAY['common', 'popular'] может вернуть слишком много кандидатов. Включение нового часто встречающегося тега увеличивает posting lists и стоимость обновления индекса.

    4.2. Контрпример: массив как модель множества¶

    В PostgreSQL containment массива не считает кратность вхождений: для ARRAY[1] @> ARRAY[1,1] результат true. Индексная семантика отражает оператор, но само приложение иногда ошибочно считает теги мультисетом. Если важен порядок, число повторений или атрибут отдельного тега, массив может оказаться плохой предметной моделью.

    SELECT ARRAY[1] @> ARRAY[1,1] AS contains_duplicates;
-- true

    Нормализованная связь product_tags(product_id, tag) с уникальным ключом позволяет хранить независимые атрибуты, ограничивать уникальность и выполнять JOIN. Она увеличивает количество строк и стоимость соединений, но дает больше контроля. Массив полезен при стабильном небольшом наборе элементов и частых проверках принадлежности; нормализация — если элемент стал самостоятельной сущностью.

    4.3. Производственная цена UPDATE массива¶

    UPDATE products
SET tags = array_append(tags, 'new')
WHERE id = 42;

    С точки зрения SQL изменился один элемент. С точки зрения индекса мог измениться состав GIN-ключей для новой версии строки, а для heap возникла новая tuple в обычной модели MVCC. Цена меняется с количеством элементов и частотой обновлений. Индекс по tags может лишить UPDATE возможности быть HOT для затрагиваемой индексом колонки. Не объявляйте это бесплатным полем-массивом.

    Вывод раздела: GIN над массивом пригоден для поиска по элементам, но не заменяет предметную модель. Обязательно сверяем semantics @>, &&, <@, равенства и свойства обновлений.

    5. Full-Text Search: почему «найти слово» требует отдельной семантики¶

    5.1. Поиск слов не совпадает с поиском подстроки¶

    Предположим, пользователь ищет «оптические камеры». Наивная реализация строит ILIKE '%оптические камеры%'. Но текст может содержать «камера с оптической стабилизацией», «объективы для камер» или другую словоформу и порядок слов. ILIKE сравнивает подстроки, не знает словаря, форм слова и смысла поискового выражения.

    Полнотекстовый поиск (Full-Text Search, FTS) приводит документ к tsvector, а запрос — к tsquery. Парсер, словари и стоп-слова определяются конфигурацией. to_tsvector сохраняет нормализованные лексемы и обычно их позиции; plainto_tsquery формирует простой запрос из пользовательского текста.

    SELECT to_tsvector('russian', 'Оптические камеры и объективы');
SELECT plainto_tsquery('russian', 'оптическая камера');

SELECT to_tsvector('russian', 'Оптические камеры и объективы')
       @@ plainto_tsquery('russian', 'камера объектив');

    Здесь конфигурация является частью семантики индекса: индекс строили с одной конфигурацией, а запрос лемматизировали с другой — совпадения могут отличаться. При смешанном языке следует продумать конфигурации, а не рассчитывать на несуществующий универсальный словарь. См. [PG18-FTS-CONTROL].

    5.2. Как строить индекс для текстового поля¶

    Покажем устойчивый вариант через сохраненный вычисляемый столбец (STORED generated column), чтобы не пересчитывать лексемы на каждом SELECT:

    CREATE TABLE articles (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  body text NOT NULL,
  search_vector tsvector GENERATED ALWAYS AS (
    setweight(to_tsvector('russian'::regconfig, title), 'A') ||
    setweight(to_tsvector('russian'::regconfig, body), 'D')
  ) STORED
);

CREATE INDEX articles_search_gin
ON articles USING gin (search_vector);

SELECT id, title
FROM articles
WHERE search_vector @@ plainto_tsquery('russian', 'камера стабилизация');

    Индекс GIN содержит лексемы и ссылки на строки. Он не превращается в поисковый движок со всеми возможностями релевантности и морфологии: важны словари, обновления контента, количество документов, ranking и требования к результатам.

    5.3. Ranking: почему индекс отвечает за кандидатов, а не окончательную сортировку¶

    SELECT id, title,
       ts_rank(search_vector,
               plainto_tsquery('russian', 'камера стабилизация')) AS rank
FROM articles
WHERE search_vector @@ plainto_tsquery('russian', 'камера стабилизация')
ORDER BY rank DESC
LIMIT 20;

    GIN быстро находит кандидатов по лексемам, но ts_rank вычисляется для подходящих документов, затем результаты обычно надо упорядочить. Даже при небольшом LIMIT серверу может потребоваться вычислить релевантность для большого множества совпадений. Вводим ограничение по другим атрибутам или более селективный tsquery, если бизнес-семантика это допускает.

    Если вектор содержит весовые метки A/B/C/D, учтите, что GIN индексирует лексемы, а не сами веса; некоторые условия требуют проверки исходного tsvector. Для FTS индекс GIN предпочтителен, а GiST предлагает другой компромисс через сигнатуру. См. [PG18-FTS-INDEX].

    5.4. websearch_to_tsquery, фразовый поиск и опасные пользовательские строки¶

    to_tsquery требует синтаксис поискового языка, например camera & phone. Прямое встраивание пользовательского ввода в SQL — ошибка и с точки зрения безопасности, и с точки зрения корректной обработки кавычек. plainto_tsquery безопасно формирует AND по словам; websearch_to_tsquery понимает привычную часть поискового синтаксиса; phraseto_tsquery учитывает порядок и расстояния.

    SELECT websearch_to_tsquery('russian', 'камера -пластик');
SELECT phraseto_tsquery('russian', 'оптическая стабилизация');

    Выбираем способ формирования tsquery по требованиям продукта, а не потому, что один кажется «лучше» другого. Низкоуровневые возможности FTS расширяемы, но разработку собственных словарей и парсеров мы в курс не включаем.

    5.5. Что происходит под нагрузкой¶

    Добавим 10 000 обновлений документов в секунду. Каждый UPDATE текстового поля может переписать stored search_vector и обновить множество ключей GIN. Индекс ускоряет поиск, но цена возникает в транзакционном пути записи, autovacuum и обслуживании GIN. При высокой частоте новых документов задержка INSERT может быть неравномерной. Эту причинную цепочку продолжим в теме 7.

    Вывод раздела: для поиска слов нужна лексическая модель, индекс по tsvector и оценка итоговой стоимости ранжирования. Для поиска подстроки — другой механизм, который разбираем далее.

    6. pg_trgm: как ускорить LIKE '%...%' и поиск похожих строк¶

    6.1. Откуда берутся триграммы¶

    Триграмма — последовательность из трех символов, получаемая при разбиении текста с предусмотренными правилами нормализации и границ слов. Для поиска выражение преобразуется в набор триграмм; индекс позволяет найти строки, содержащие подходящие части. Чем длиннее и информативнее шаблон, тем меньше кандидатов.

    CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX products_description_trgm
ON products USING gin (description gin_trgm_ops);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM products WHERE description ILIKE '%оптическая%';

    Индекс gin_trgm_ops поддерживает LIKE, ILIKE, регулярные выражения и похожесть. Он полезен для текстовых поисков с незаякоренным слева шаблоном. Но триграммы ищут совпадения символов, а не нормализованные лексемы, поэтому это не замена полнотекстового поиска. См. [PG18-TRGM].

    6.2. Почему слишком короткий шаблон ломает красивую модель¶

    SELECT * FROM products WHERE description ILIKE '%ab%';

    У этого шаблона может не быть ни одной извлекаемой надежной триграммы. PostgreSQL может вынужденно просмотреть почти весь индекс или предпочесть Seq Scan. Для ILIKE '%оптическая%' извлекаемых триграмм больше, отбор кандидатов лучше.

    Аналогично с регулярными выражениями: сложный шаблон вроде .* не создает полезного ограничителя. Наличие GIN по trigram не гарантирует ускорение любых LIKE/regex. В логах и статистике нужно смотреть реальные шаблоны, включая очень короткие пользовательские запросы.

    6.3. GIN против GiST для trigram¶

    CREATE INDEX products_description_gist_trgm
ON products USING gist (description gist_trgm_ops(siglen=32));

-- Похожесть определяется порогом для оператора %:
SELECT id, description
FROM products
WHERE description % 'стабилизация';

-- Поиск ближайших строк по расстоянию:
SELECT id, description
FROM products
ORDER BY description <-> 'стабилизация'
LIMIT 10;

    Оба метода могут ускорять поиск похожих строк, однако GiST поддерживает эффективный nearest-neighbor поиск с ORDER BY <-> LIMIT, а GIN не предоставляет аналогичный индексный top-K по расстоянию. GIN хорош для поиска всех кандидатов по порогу или подстроке, GiST — часто лучше для KNN.

    Для gist_trgm_ops хранится сигнатура; увеличение siglen потенциально уменьшает число ложных кандидатов, но увеличивает размер индекса. Это компромисс конкретного operator class, а не универсальное свойство GiST.

    6.4. Ложные кандидаты и точная проверка¶

    Общая триграмма сама по себе не доказывает совпадение всего условия LIKE или regex. Индекс формирует кандидатов, исходное условие проверяется повторно при необходимости. Поэтому низкий процент совпадений и слишком общий шаблон могут превратить GIN-trgm в крупный источник heap I/O. Для trigram-GiST дополнительно возможны кандидаты из-за сигнатурных коллизий.

    Диагностика: EXPLAIN (ANALYZE, BUFFERS), фактическое число возвращенных строк, heap blocks, Rows Removed by Index Recheck, сравнение LIKE 'prefix%' и LIKE '%middle%', warm/cold cache. При большой записи — отдельное измерение INSERT и UPDATE, ведь индекс содержит множество триграмм для каждой строки.

    6.5. Как выбрать между FTS и Trigram¶

    Запрос пользователя Техническая модель Инструмент
    «Все статьи со словами камера и стабилизация» Поиск лексем, словоформ tsvector + GIN
    «Найти подстроку в описании» Последовательности символов pg_trgm + GIN/GiST
    «Похожие названия, top-10» Метрика похожести, KNN pg_trgm + GiST
    «Точное равенство идентификатора» Скалярное равенство B-tree

    Нельзя выбрать один «самый лучший текстовый индекс» без определения поискового контракта продукта.

    Вывод раздела: pg_trgm ускоряет substring/similarity за счет индексирования триграмм, но короткие шаблоны и низкая селективность делают его дорогим. GiST особенно интересен при ORDER BY distance LIMIT.

    7. GIN Write Cost: почему INSERT внезапно становится в 20 раз медленнее¶

    7.1. Проблема write amplification¶

    При вставке одной строки в heap PostgreSQL может извлечь из JSONB или tsvector десятки индексных ключей. Если немедленно вставлять каждый ключ в основное дерево GIN, одна SQL-операция превращается в множество изменений индекса. Время выполнения записи растет, а конфликтные обновления страниц становятся дороже.

    GIN умеет отложить значительную часть этой работы с помощью fastupdate и pending list. При включенном fastupdate новые элементы сначала попадают во временный несортированный список внутри GIN. Позже они массово переносятся в основную структуру. См. [PG18-GIN].

    Обычный путь                  Fast update
-----------                   -----------
INSERT document               INSERT document
    |                             |
извлечь N ключей              извлечь N ключей
    |                             |
обновить основное дерево      append в GIN pending list
    |                             |
COMMIT                        COMMIT
                                  |
                         позднее: bulk cleanup
                                  |
                         основное entry/posting tree

    7.2. Откуда берется p99 cliff¶

    Пока pending list небольшая, новые INSERT обходятся дешево. Но рано или поздно ее нужно очистить. Очистку инициирует VACUUM/autoanalyze, явный gin_clean_pending_list() или превышение gin_pending_list_limit. Если порог превышает именно пользовательский INSERT, передний запрос может оплатить дорогостоящий cleanup. Это объясняет картину: p50 записи нормальная, а отдельные p99/p99.9 резко выросли.

    INSERT latency (условно, мс):
2.1  2.0  2.5  2.0  2.2  85.0  2.1  2.0  2.3
                         ^
                 foreground pending cleanup

    При этом SELECT должен искать и в основном GIN, и в pending list. Поэтому слишком большая pending list ухудшает не только скорость очистки, но и читающие запросы. Получается обмен: дешевые записи сейчас — дополнительные расходы на чтение и редкие дорогие записи позже.

    7.3. Настройки и их реальные компромиссы¶

    -- Изменить порог на уровне конкретного индекса:
ALTER INDEX products_tags_gin
  SET (gin_pending_list_limit = 8192); -- кБ

-- Отключить fastupdate (не удаляет накопленный pending list мгновенно):
ALTER INDEX products_tags_gin
  SET (fastupdate = off);

    Увеличить порог — значит реже чистить список, но потенциально делать более дорогую очистку и дольше сканировать pending list при SELECT. Отключить fastupdate — значит сделать расходы на изменения более непосредственными и стабильными, но часто увеличить стоимость INSERT. Универсального «правильного» значения нет.

    maintenance_work_mem существенно влияет на построение GIN. Для cleanup важны условия нагрузки и память, доступная соответствующей операции; настройка не отменяет фундаментальную стоимость перемещения большого числа ключей.

    7.4. Как увидеть pending list собственными глазами¶

    Поставляемое расширение pgstattuple содержит pgstatginindex, возвращающий pending_pages и pending_tuples.

    CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT *
FROM pgstatginindex('products_tags_gin'::regclass);

-- Контролируемая очистка только в отдельном эксперименте:
SELECT gin_clean_pending_list('products_tags_gin'::regclass);

    Значения измеряются для конкретного момента и имеют характер состояния индекса; изменение pending list возможно между запросами. Установка расширения и права на диагностическую функцию могут требовать администратора или роли pg_stat_scan_tables. См. [PG18-PGSTAT].

    7.5. Что измерять, чтобы не лечить симптом¶

    1. Запустить стабильную смесь INSERT/UPDATE и SELECT по тегам, а не только чистый bulk INSERT.
    2. Собрать latency в интервалах, обязательно p95/p99, count и throughput; среднее время скрывает spikes.
    3. Периодически снимать pgstatginindex: растет ли pending_pages перед всплеском?
    4. Отдельно измерять время SELECT и стоимость буферов; увеличивается ли работа со списком?
    5. Сравнить вариант с fastupdate=off, более агрессивным autovacuum и другим порогом, не меняя одновременно остальные параметры.
    6. После каждого изменения повторить нагрузку, проверить WAL-объем, размер индекса, потребление CPU и качество хвоста задержек.

    Инженерный вывод: GIN переносит стоимость: размер, CPU и I/O никуда не исчезают. Pending list — осознанный batching-компромисс, который способен менять форму latency distribution в production.

    8. GiST: индексируем диапазоны, пересечения и пространственные отношения¶

    8.1. Почему диапазон нельзя удобно выразить одним скалярным порядком¶

    Появилась таблица бронирований: у каждой записи есть временной интервал. Нам нужно быстро найти бронирования, которые пересекаются с новым интервалом. Простого сравнения начала или конца недостаточно: длинный интервал может начаться далеко раньше искомого и все еще перекрывать его.

    GiST (Generalized Search Tree) — сбалансированная структура поиска, в которой opclass задает семантику ключей, их объединения и отбора ветвей. Для диапазонов GiST умеет индексировать пересечение &&, включение @> и другие операции. Сам GiST — инфраструктура, не единственный жестко зафиксированный алгоритм индексации.

    CREATE TABLE bookings (
  booking_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id bigint NOT NULL,
  during tstzrange NOT NULL
);

CREATE INDEX bookings_during_gist ON bookings USING gist (during);

SELECT booking_id, room_id
FROM bookings
WHERE during && tstzrange('2026-12-01 10:00+00',
                           '2026-12-01 11:00+00', '[)');

    Границы [) означают включенную левую и исключенную правую. Соприкасающиеся без пересечения интервалы не конфликтуют, если бизнес-правила соответствуют этой модели. Время и часовые пояса важно нормализовать заранее.

    8.2. От поиска пересечений к гарантии отсутствия двойных бронирований¶

    Найти конфликт мало. Если два запроса одновременно проверили отсутствие пересечения, они могут оба попытаться вставить несовместимые данные. В PostgreSQL есть exclusion constraint, позволяющий выразить запрет пересечения прямо в схеме с использованием GiST.

    CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
ADD CONSTRAINT no_overlapping_bookings
EXCLUDE USING gist (
  room_id WITH =,
  during WITH &&
);

    Здесь btree_gist дает GiST-операторный класс для сравнения room_id по равенству. Для двух строк с одним room_id интервалы не могут пересекаться. Эта операция дает транзакционную защиту инварианта средствами СУБД, включая конкурентные вставки. При конфликте возможна ошибка 23P01 (exclusion_violation).

    Это новая бизнес-применимость индексного метода: структура обслуживает не только SELECT, но и ограничение целостности. Величину накладных расходов проверяем на write-нагрузке.

    8.3. GiST для геометрии и ограничивающих областей¶

    Для геометрических типов некоторые opclass используют bounding region — геометрическую область, которая покрывает индексируемый объект. При поиске выбираются ветви, чьи ограничивающие области могут пересекаться с запросом. Кандидаты затем проверяются, если индекс хранит лишь приближение.

                    Root region
               /           \
       Bounding A          Bounding B
        /    \                /    \
       A1    A2              B1    B2
          ^
          intersect query region?

    Дерево позволяет исключать большие поддеревья. Но если ограничивающие области сильно пересекаются, поиск затрагивает много ветвей. Эффективность зависит от распределения объектов, выбора opclass и характеристик данных. См. [PG18-GIST].

    8.4. Цена GiST под нагрузкой¶

    При добавлении объектов дерево может изменяться: расширяются агрегированные представления ветвей, выполняются разбиения узлов, и расходы зависят от данных. Для tstzrange на живой системе высокая плотность перекрывающихся интервалов может приводить к большому множеству кандидатов. Для пространственных данных плохо разделенные регионы увеличивают число посещаемых ветвей.

    Вывод раздела: GiST — механизм для отношений типа «пересекается», «содержит», «поблизости». Его сила определяется соответствием operator class бизнес-оператору, а цена — структурой значений и количеством кандидатов.

    9. GiST Recheck & KNN: где исчезает время при поиске ближайших¶

    9.1. Почему приближенный индекс обязан проверять кандидата¶

    Представим индекс, хранящий прямоугольник вокруг многоугольника. Пересечение прямоугольников еще не означает пересечения самих многоугольников. Индекс вправе пропускать лишних кандидатов, но не должен потерять настоящие совпадения. Для lossy operator class он возвращает флаг, требующий повторной проверки исходного условия.

    Запрос: polygon overlaps search_area?
Индекс: bounding box overlaps? -> MAYBE
Heap: точная геометрическая проверка -> true / false

    Не каждый GiST opclass и не каждый оператор lossy. Например, отдельные операторы над диапазонами могут проверяться достаточно точно по индексным данным. Нельзя утверждать «GiST всегда приблизителен». План Bitmap Heap Scan может показать Recheck Cond из-за lossy bitmap даже для точных индексных методов. Диагностика должна различать причины.

    9.2. K-nearest neighbor: индекс может отдавать ближайшие значения по порядку¶

    Обычная схема top-K выглядит так: собрать кандидатов, посчитать расстояние, сортировать, взять LIMIT. Для подходящего GiST opclass предусмотрена индексная поддержка order-by operator, благодаря которой ближайшие результаты можно получать в порядке расстояния, сокращая необходимость собирать весь набор.

    CREATE TABLE places (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    location point NOT NULL
);

CREATE INDEX places_location_gist ON places USING gist(location);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, location
FROM places
ORDER BY location <-> point '(10,20)'
LIMIT 20;

    При подходящих статистике и объеме возможен план с Index Scan и Order By: (location <-> ...). Он не гарантирован для трех записей, как и любой другой индексный план. Семантика <-> определяется типом и opclass.

    9.3. Почему ORDER BY distance LIMIT и WHERE distance < radius — разные задачи¶

    Топ-K хочет 20 ближайших точек, независимо от абсолютной дальности. Поиск в радиусе хочет все объекты, удовлетворяющие ограничению. Первый часто выигрывает от KNN, второй — от селективного пространственного предиката и точной проверки. Для измерений сравниваем количество возвращенных строк, число кандидатов, BUFFERS, сортировки и p95 latency.

    При очень плотной геометрии первые K кандидатов могут находиться на небольшом участке; при сильно неравномерном распределении или геометрии с большим перекрытием bounding regions индекс может посещать больше узлов.

    9.4. Частая ловушка: смешали recheck и извлечение heap¶

    Rows Removed by Index Recheck — число отвергнутых строк на этапе повторной проверки индексного условия. Это не все строки, прочитанные из heap, и не прямой счетчик «ложных ключей в GiST». Heap Blocks: lossy — страницы, адреса которых в bitmap представлены без индивидуальных TID; это может быть следствием work_mem, даже если доступ по индексу точный. Для корректного вывода смотрим полную структуру плана.

    Вывод раздела: GiST дает KNN и операторы пространственных/диапазонных отношений, но конечную стоимость определяют число рассмотренных кандидатов, точность opclass и работа с heap.

    10. SP-GiST: когда поисковое пространство выгодно делить на части¶

    10.1. Другая ментальная модель: разделяем пространство, а не храним объединяющие области¶

    В GiST мы видели структуру, где внутренние узлы могут содержать ограничивающие представления набора потомков. Но что, если сами данные хорошо разделяются по дизъюнктным или относительно независимым областям? Для точек — по квадрантам; для строковых префиксов — по последовательности символов; для сетевых адресов — по префиксу битовой строки.

    SP-GiST (Space-Partitioned Generalized Search Tree) — инфраструктура для поисковых деревьев, разбивающих пространство. В зависимости от operator class она позволяет строить quadtrees, k-d деревья, radix trees/tries и другие схемы. Важный нюанс: такие деревья не обязаны быть сбалансированными как B-tree; PostgreSQL адаптирует их к дисковым страницам и стремится сохранять эффективный доступ. См. [PG18-SPGIST].

                           Пространство точек
                             |
                  +----------+----------+
                  |          |          |
              quadrant NW    NE       SW/SE ...
                  |          |
               leafs      дальнейшее разбиение

Поиск может отбросить целые области, не содержащие кандидатов.

    В отличие от обычного партиционирования таблиц здесь одно индексное дерево делит поисковое пространство для конкретного access method. Не путать с декларативными partitions и тем более с распределенным sharding.

    10.2. Пример с геометрическими точками¶

    CREATE TABLE locations (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  p point NOT NULL
);

CREATE INDEX locations_spgist
ON locations USING spgist (p);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM locations
WHERE p <@ box '(0,0),(100,100)';

    Встроенные SP-GiST operator classes для point поддерживают соответствующие пространственные операторы, а некоторые — KNN <->. quad_point_ops — обычный вариант по умолчанию; kd_point_ops — альтернативный способ разделения пространства. Выбирать нужно по данным и нагрузке, а не по названию алгоритма.

    10.3. Префиксный поиск строк¶

    Для text есть SP-GiST opclass text_ops с поддержкой операторов, включая ^@ (начинается с заданного префикса). Пример:

    CREATE TABLE routes (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  path text NOT NULL
);

CREATE INDEX routes_path_spgist
ON routes USING spgist (path text_ops);

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM routes WHERE path ^@ '/catalog/';

    Здесь удобно мыслить как trie по строкам, но физическое устройство определяется реализацией opclass. Это не повод считать SP-GiST универсальной заменой B-tree по text: для обычного сортируемого диапазона, уникальности и типовых сравнений B-tree остается естественным выбором.

    10.4. Почему отдельная лекция по SP-GiST не нужна¶

    Для backend-разработчика важны три факта: оператор и opclass задают применимость; разделение пространства может резко уменьшить число посещаемых страниц; распределение ключей и форма запроса определяют эффективность. Детальный picksplit и расположение inner/leaf tuples — уже уровень разработчика индексных методов.

    Вывод раздела: SP-GiST полезен, когда структура ключей соответствует пространственному разбиению. Проверяем SQL-операторы, реальные планы и количество затронутых heap-страниц.

    11. BRIN: как индекс на большую таблицу может быть очень маленьким¶

    11.1. Начнем с физического порядка строк¶

    Есть таблица событий на сотни миллионов строк. Каждую минуту добавляется очередная порция записей, причем created_at примерно возрастает вместе с физическим расположением новых heap-страниц. Для поиска последних минут традиционный B-tree хранит множество ключей и TID. Но нам часто достаточно заранее знать, какие диапазоны страниц точно не содержат нужной временной метки.

    BRIN (Block Range Index) хранит сводку (summary) для группы последовательных heap-страниц — block range. Для распространенного minmax opclass это минимальное и максимальное значение столбца внутри группы страниц.

    Heap: | pages 0..127 | pages 128..255 | pages 256..383 | ...
             |               |                |
             v               v                v
BRIN:    min=09:00       min=10:00        min=11:00
         max=09:59       max=10:59        max=11:59

WHERE created_at >= 11:30:
  ranges [0..127], [128..255] исключены;
  [256..383] кандидат -> чтение и точная проверка heap.

    В BRIN индексируется диапазон страниц, а не каждая строка. Поэтому он мал по сравнению с большими B-tree, но у него принципиально lossy характер: найденный range означает лишь «внутри могут быть подходящие строки». Executor проверит сами строки. См. [PG18-BRIN].

    11.2. Что значит «корреляция с физическим порядком»¶

    Допустим, события вставляются примерно по времени. Диапазон из 128 страниц содержит узкий интервал created_at. Тогда условие за одну минуту отберет мало диапазонов.

    Теперь сломаем модель: обновления created_at сдвигают значения в старых строках, данные массово вставляются с задержкой, или выполняется загрузка исторических событий вперемешку с новыми. Тогда один block range может содержать время от 2020 до 2026 года. Его (min,max) перекрывает почти любой запрос, и BRIN вынужден читать множество страниц.

    Корреляция может измеряться статистикой pg_stats.correlation после ANALYZE. Близость абсолютного значения к 1 говорит о выраженной связи физического порядка и значений; близость к 0 — о слабой линейной корреляции. Это подсказка, не безусловный предиктор полезности BRIN.

    11.3. Создание и сравнение с B-tree¶

    CREATE TABLE events (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  created_at timestamptz NOT NULL,
  payload text NOT NULL
);

-- Наполнить данными на отдельном стенде, чтобы изменение стоимости было видно.
INSERT INTO events(created_at, payload)
SELECT TIMESTAMPTZ '2025-01-01 00:00:00+00' +
       g * interval '1 second', md5(g::text)
FROM generate_series(1, 2000000) AS g;

CREATE INDEX events_created_brin
ON events USING brin(created_at) WITH (pages_per_range = 128);

ANALYZE events;

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM events
WHERE created_at >= TIMESTAMPTZ '2025-01-20 00:00:00+00'
  AND created_at <  TIMESTAMPTZ '2025-01-20 01:00:00+00';

    В данном наборе данных фиксируем не придуманные значения, а фактический план, количество Heap Blocks и время. Для сравнения можно построить отдельную копию таблицы с B-tree по created_at. BRIN редко заменяет PRIMARY KEY индекс, а для высокоселективного point lookup B-tree обычно лучше.

    11.4. Размер: оценка порядка величины¶

    Пусть таблица занимает 128 ГиБ, размер heap-страницы 8 КиБ, pages_per_range=128. Тогда:

    Количество heap-страниц = 128 * 2^30 / 8192 = 16 777 216
Количество range summaries = 16 777 216 / 128 = 131 072

    BRIN нужен примерно один summary tuple на 128 страниц, а не одна запись на строку. Реальный размер включает управляющие страницы, revmap, выравнивание, дополнительные данные и зависит от opclass. Оценка 131 072 — число диапазонов, а не обещанный размер индекса в байтах. Соотношение размеров проверяем pg_relation_size.

    11.5. Почему BRIN может проиграть Seq Scan¶

    Если в физическом порядке нет корреляции, почти каждый summary range будет перекрывать запрошенный интервал. BRIN добавит чтение индекса и передачу большого списка потенциальных heap-страниц, после чего придется прочитать почти весь heap. Seq Scan способен оказаться дешевле. Это честный результат, а не «PostgreSQL игнорирует индекс».

    Вывод раздела: BRIN особенно полезен для огромных append-heavy таблиц с локальностью значений по физическому порядку. Его сила — дешевое исключение больших диапазонов, ограничение — необходимость проверки всех кандидатов внутри оставшихся диапазонов.

    12. BRIN Summarization: почему после создания индекса новые строки еще надо учитывать¶

    12.1. Что хранится при создании и при последующих вставках¶

    При CREATE INDEX BRIN сканирует существующие heap-страницы и строит summary tuples для диапазонов. Когда новые строки попадают в уже суммаризированный range, summary может расширяться с учетом новых значений. А вот новый block range, только что появившийся при росте таблицы, не обязательно сразу получает начальную summary tuple.

    Несуммаризированные диапазоны нельзя просто объявить пустыми: они должны быть рассмотрены при поиске, иначе терялись бы совпадения. Следовательно, накопление несуммаризированных диапазонов может увеличивать число страниц, которые приходится проверять.

    12.2. Как BRIN суммаризирует новые ranges¶

    Документация PostgreSQL 18 описывает несколько путей:

    • VACUUM / autovacuum таблицы выполняет суммаризацию несуммаризированных диапазонов;
    • параметр индекса autosummarize=on просит autovacuum выполнять нужную дополнительную работу; по умолчанию он выключен;
    • администратор может явно вызвать brin_summarize_new_values(index);
    • для конкретного range существует brin_summarize_range(index, block_number).
    CREATE INDEX events_created_brin_auto
ON events USING brin(created_at)
WITH (pages_per_range = 128, autosummarize = on);

SELECT brin_summarize_new_values('events_created_brin_auto'::regclass);

    Здесь важен нюанс: запрос на autosummarization может попасть в ограниченную очередь. Если она переполнена, в журнале появляется сообщение о том, что запрос не записан, и диапазон останется несуммаризированным до следующей обычной обработки. Сам autosummarize=on не является синхронной гарантией «каждый новый диапазон мгновенно суммаризирован». См. [PG18-BRIN].

    12.3. pages_per_range: точность против размера и стоимости изменений¶

    Меньший диапазон — точнее границы значений, меньше посторонних heap-страниц, но больше summary tuples и больше работы поддержки индекса. Больший диапазон — компактнее индекс, однако больше ложных кандидатов при узком условии.

    pages_per_range=32   -> больше summaries, обычно точнее отсечение
pages_per_range=128  -> компромиссный пример
pages_per_range=512  -> меньше summaries, но шире min/max

    Никакое значение не следует рекомендовать без наблюдения фактической корреляции и ширины типичных предикатов. В таблице со случайными timestamps уменьшение range может дать небольшой выигрыш, но не восстановит естественную локальность данных.

    12.4. Обновили старый range: когда summary устаревает логически¶

    Если в диапазоне изменились значения, min/max часто только расширяются: это сохраняет безопасность отбора, но может делать summary менее точной, чем реальный набор строк. Для отдельных задач предусмотрен brin_desummarize_range, после чего диапазон можно суммаризировать заново. Это административная операция для осознанного случая, а не ежедневная профилактика каждого BRIN.

    Вывод раздела: BRIN требует обслуживания сводок. Размер индекса сам по себе не говорит о качестве поиска; несуммаризированные и слишком широкие диапазоны могут незаметно ухудшать latency.

    13. Index Cost Model: какую цену на самом деле добавляет индекс¶

    13.1. Сначала разложим стоимость запроса на этапы¶

    В предыдущих блоках мы уже вывели cost model PostgreSQL, поэтому повторять формулы планировщика не будем. Для новых типов индексов важно понимать, какие физические действия стоят за ценой.

    Метод Пример основной индексной работы Что дополнительно оплачиваем
    GIN Поиск ключей и posting sets Heap, recheck, pending list, большие обновления
    GiST Поиск подходящих ветвей / KNN Иногда bounding false positives, heap recheck
    SP-GiST Обход частей пространства Перекосы распределения, heap, opclass-specific операции
    BRIN Поиск summaries диапазонов Проверка всех строк в подходящих page ranges

    Для одного SQL итоговая цена примерно складывается из доступа к индексу, чтения подходящего heap, проверки условий и формирования результата. Это учебная декомпозиция, не копия исходной формулы cost_* в PostgreSQL.

    13.2. Рассчитаем цену BRIN через долю просмотренных диапазонов¶

    Предположим: таблица 1 000 000 heap-страниц, pages_per_range=128, условие может совпасть с 1% диапазонов. Тогда кандидатных heap-страниц порядка 10 000. При 100% перекрытии придется рассмотреть около 1 000 000 страниц, и выигрыш от маленького индекса исчезнет. Кроме того, внутри выбранных диапазонов проверяются строки.

    Cost rough order:
  candidate_heap_pages ~= total_heap_pages * selected_range_fraction

selected_range_fraction = 0.01 -> ~10 000 страниц
selected_range_fraction = 1.00 -> ~1 000 000 страниц

    На реальной нагрузке selected_range_fraction не равно автоматически селективности строк: один подходящий timestamp внутри диапазона делает весь range кандидатом. Именно поэтому корреляция и pages_per_range критичны.

    13.3. Рассчитаем потенциальный write amplification GIN¶

    Допустим, каждый документ дает в среднем 40 индексируемых ключей и система вставляет 25 000 документов/с. Получаем порядок 1 млн логических добавлений ключей в секунду. Это не число физических WAL records и не число page writes — GIN использует batching, компрессию, страницы и другие оптимизации. Но оценка показывает, почему сравнение «25 тысяч heap INSERT» со «столькими же scalar B-tree INSERT» ошибочно.

    Если среднее число ключей выросло с 40 до 150 после изменения JSONB-схемы, индекс может стать узким местом без роста количества SQL-запросов. Измеряем фактический индексный размер, WAL bytes, p95/p99 записи и pending list.

    13.4. Скорость построения, хранения и обслуживания¶

    Создание GIN на большом документном столбце может требовать значительной памяти и времени. Для построения GIN maintenance_work_mem влияет на производительность. В работающей системе новая индексная структура также участвует в WAL, autovacuum и обновлениях. Индекс, который ускорил одну редкую операцию на 20 мс, но увеличил стоимость миллионов INSERT, может быть плохим инженерным решением.

    Для GiST и SP-GiST расходы зависят от распределения объектов; для BRIN — чаще минимальны по объему, но качество отбора может деградировать при перемешивании физического порядка.

    13.5. Как не обмануться тестами¶

    Нужно сравнивать одинаковое число строк, аналогичное распределение значений и одну смесь операций. После создания индекса — ANALYZE, стабилизация кеша, несколько прогонов, медиана и p95/p99, размеры и буферы. Нельзя сравнивать GIN на 1 млн случайных документов с B-tree на 1 млн одинаковых timestamps и делать общий вывод о методах. Для честного выбора строим несколько кандидатных вариантов, измеряем на одном бизнес-запросе и учитываем цену поддержания каждого индекса.

    Вывод раздела: стоимость индекса — это стоимость всего профиля нагрузки, а не только SELECT, которому индекс был посвящен.

    14. Index Diagnostics: что реально смотреть в PostgreSQL 18¶

    14.1. Первое измерение — план с фактическими данными¶

    EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)
SELECT id FROM products
WHERE attributes @> '{"camera":{"stabilization":true}}';

    Смотрим выбранный access path, стоимость и фактическое время, фактическое число строк, разницу estimate/actual, Buffers и при наличии Bitmap Heap Scan — точные/приближенные страницы и Rows Removed by Index Recheck. WAL полезен для изменяющих SQL; чтение обычно не создает значимого пользовательского WAL только из-за самого SELECT, хотя некоторые физические операции обслуживания могут иметь побочные записи.

    Факт, что в плане выбран Seq Scan, требует объяснения через селективность, статистику и стоимость heap, а не приказа «заставить индекс работать».

    14.2. Посмотреть все индексы и их методы доступа¶

    SELECT
    t.relname  AS table_name,
    i.relname  AS index_name,
    am.amname  AS access_method,
    pg_size_pretty(pg_relation_size(i.oid)) AS index_size
FROM pg_class AS i
JOIN pg_index AS x ON x.indexrelid = i.oid
JOIN pg_class AS t ON t.oid = x.indrelid
JOIN pg_am AS am ON am.oid = i.relam
WHERE t.relname IN ('products', 'articles', 'events', 'bookings')
ORDER BY t.relname, i.relname;

    Этот запрос отображает объекты индексов и реальные размеры. Название индекса ничего не доказывает: важно смотреть amname, pg_get_indexdef(indexrelid) и при необходимости параметры pg_class.reloptions. Величина pg_relation_size — размер отношения индекса, не суммарный физический footprint всех файлов базы.

    14.3. Статистика использования индекса с важной ловушкой¶

    SELECT
    relname,
    indexrelname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname IN ('products', 'articles', 'events', 'bookings')
ORDER BY relname, idx_scan DESC;

    idx_scan — число начатых индексных поисков, не просто число SQL. idx_tup_read — индексные записи, возвращенные поисками. idx_tup_fetch на уровне конкретного индекса не учитывает heap fetch через bitmap scan так же, как обычный Index Scan: такие heap fetch относятся к статистике таблицы. Поэтому «idx_tup_fetch маленький — индекс бесполезен» является ошибочным выводом. См. [PG18-STATS].

    Статистика накопительная, счетчики зависят от перезапуска/сброса и прочих деталей. Для оценки частоты использования анализируем дельты за известный период, а не одну случайную фотографию.

    14.4. Проверка корреляции для BRIN¶

    ANALYZE events;

SELECT attname, correlation, n_distinct
FROM pg_stats
WHERE schemaname = 'public'
  AND tablename = 'events'
  AND attname = 'created_at';

    Если correlation близко к 0, особенно важно проверить фактическую избирательность BRIN по диапазонам. Но даже при высокой корреляции запрос к почти всей таблице может предпочесть Seq Scan. Не делаем вывод по одному коэффициенту.

    14.5. GIN pending list как источник редких задержек¶

    CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstatginindex('products_tags_gin'::regclass);

    Сопоставляем pending_pages, pending_tuples и p99 INSERT; после cleanup отдельно наблюдаем изменение времени SELECT. Если нет прав на расширение, работаем с административной учетной записью учебного стенда, не раздаем суперпользователя прикладному сервису.

    14.6. Сравнение кандидатов: таблица решения¶

    Симптом Проверяем Возможное решение
    JSONB containment медленный opclass, selectivity, GIN candidates jsonb_path_ops для подходящих операторов
    ? по JSONB не использует индекс jsonb_path_ops или выражение jsonb_ops/expression index
    Вставка с GIN имеет p99 spikes pending list, autovacuum, WAL настройка fastupdate/cleanup
    ILIKE '%x%' медленный длина шаблона и extractable trigrams иной контракт поиска / FTS
    KNN top-10 слишком дорогой GiST opclass и Order By в плане подходящий GiST KNN
    BRIN читает полтаблицы correlation, pages_per_range другой диапазон или B-tree
    Индекс мало используется реальные workload stats и размеры удалить только после анализа зависимостей

    14.7. Как удалять ненужные индексы без лишнего риска¶

    Перед удалением индекса проверяем DDL, зависимости ограничений, запросы в разных режимах и периодах и задержки редких операций. В production часто нужна DROP INDEX CONCURRENTLY, но ограничения этой команды мы уже разобрали в лекции о миграциях. Здесь не повторяем алгоритм DDL; фиксируем инженерную ответственность — удалять индекс только после подтверждения его ненужности и оценки риска регрессии.

    Вывод раздела: EXPLAIN показывает конкретный SQL, статистика индексов — накопительное использование, профиль latency — цену для приложения, размер и WAL — эксплуатационные расходы. Корректная диагностика объединяет все четыре источника.

    Демонстрационное продолжение: доказать работу индексов руками¶

    Эксперимент A. GIN для JSONB и выбор operator class¶

    Создаем большой набор документов на изолированном стенде; часть содержит camera.stabilization=true, часть — нет. Сравниваем jsonb_ops и jsonb_path_ops на containment и key-exists запросах. Собираем планы, BUFFERS, размер индекса, время построения и стоимость UPDATE. Затем намеренно выполняем ? при единственном jsonb_path_ops и показываем, почему метод не подходит для этого оператора.

    Эксперимент B. GIN и pending-list spike¶

    Создаем индекс fastupdate=on, генерируем многоключевые документы и многократно вставляем новые строки. Снимаем pgstatginindex и latency INSERT по батчам. Затем вызываем gin_clean_pending_list и снова проверяем число pending pages. Повторяем с fastupdate=off или другим порогом, сравниваем p95/p99. Дефекта в программе здесь нет; демонстрируется цена отложенного обслуживания индекса.

    Эксперимент C. FTS против триграмм¶

    На одинаковых текстах выполняем поиск слов через tsvector @@ tsquery, поиск подстроки через ILIKE и top-K similarity через GiST trigram. Меняем длину шаблона на 2, 5 и 15 символов. Показываем, какие запросы теряют полезную селективность и почему GIN trigram не заменяет KNN GiST.

    Эксперимент D. GiST для перекрытия интервалов¶

    Создаем таблицу бронирований, индекс GiST и exclusion constraint. В двух сессиях одновременно пытаемся забронировать один и тот же интервал для одного ресурса. Одна из операций должна столкнуться с ограничением. Воспроизводим корректное поведение без отдельной транзакционной проверки в приложении и связываем индекс с бизнес-инвариантом.

    Эксперимент E. BRIN при высокой и низкой корреляции¶

    Берем последовательные события и копию с перемешанными временными метками, строим одинаковые BRIN (pages_per_range = 32, 128, 512). Сравниваем размер, heap blocks и время узкого временного запроса. Затем добавляем новые страницы, запускаем суммаризацию, повторяем EXPLAIN. Фиксируем, что эффективность зависит от физического расположения данных, а не только от количества строк.

    Эксперимент F. Производственное решение¶

    Выбираем два индексных кандидата для одной real-like смеси: 80% чтений JSONB, 15% UPDATE документов, 5% INSERT. Сравниваем задержки SELECT и UPDATE, p99, CPU, индексные размеры, число heap blocks и WAL. Студент должен уметь защитить выбранное решение с указанием цены, а не только показать план с Bitmap Index Scan.

    Инженерный итог¶

    1. Индекс выбирается по оператору. Тип данных важен, но без соответствующего opclass предикат не станет индексируемым.
    2. GIN ищет ключи внутри составного значения. Он покупает скорость containment/FTS/array queries ценой множества ключей, heap-доступа и более дорогой записи.
    3. jsonb_ops и jsonb_path_ops не взаимозаменяемы. Проверка ключей ? требует подходящего opclass; конкретный JSONPath не всегда дает хорошую селективность.
    4. Full-text и trigram — разные контракты. Первый работает с лексемами и словоформами, второй — с символьными последовательностями и похожестью.
    5. GIN pending list меняет распределение задержек. Оптимизация среднего INSERT способна породить редкие, но дорогие cleanup и p99 spikes.
    6. GiST и SP-GiST обслуживают специальные отношения. Их применимость и точность определяют operator classes; для GiST важны KNN и иногда recheck.
    7. BRIN работает по диапазонам heap-страниц. Очень компактный индекс силен при коррелированных данных, но требует проверки кандидатов и обслуживания summaries.

    Что можно копнуть глубже — без включения в обязательную программу¶

    Если реально появится сервис с тяжелыми GIN на изменяемых JSONB, полезен следующий слой: как pending list физически переносится в entry tree/posting trees и как это распределяет CPU, I/O и WAL между пользовательским backend и VACUUM. Он закроет вопрос, почему конкретный запрос INSERT внезапно платит за накопленную работу нескольких тысяч предыдущих запросов. Для нынешней основной лекции достаточно механизма, наблюдаемых симптомов и измерений; отдельную 12.1 автоматически не добавляем.
