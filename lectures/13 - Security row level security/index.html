    13. PostgreSQL Security & Row-Level Security¶

    Магистратура · PostgreSQL 18 · REL_18_STABLE · основная лекция блока 13.
    Цель: построить точную модель того, кто может подключиться к PostgreSQL, от чьего имени исполняется SQL, к каким объектам есть доступ и какие строки доступны внутри разрешенной таблицы.
    Фокус: pg_hba.conf, SCRAM/TLS, роли и наследование, GRANT/REVOKE, ownership, search_path, SECURITY DEFINER, default privileges, RLS, обход политик, изоляция арендаторов, тестирование безопасности и production-диагностика.
    Уже изучено: SQL, MVCC, планировщик, транзакции, блокировки, WAL, миграции и PgBouncer. Их устройство не повторяем.
    Граница материала: PostgreSQL 18 и обычный backend-сервис; это не учебник криптографии и не аудит конкретной инфраструктуры. В примерах действия администратора явно отделены от запросов прикладной роли. Все опасные эксперименты выполняются только на учебном кластере.

    0. Инцидент: приложению выдали доступ к одной таблице, а оно прочитало чужие данные¶

    Представим мультиарендный backend: в одной таблице invoices хранятся счета нескольких организаций. API должен возвращать счета только той организации, к которой относится проверенный пользователь. Разработчик пишет аккуратный запрос:

    SELECT id, amount
FROM app.invoices
WHERE tenant_id = $1;

    На review все выглядит правильно. Но позже появляется новый endpoint с запросом SELECT * FROM app.invoices ORDER BY created_at DESC LIMIT 100. Фильтр потеряли. SQL синтаксически корректен, права на таблицу у роли приложения есть. И сервер возвращает чужие счета.

    Первое очевидное решение: запретить приложению читать таблицу. Но тогда оно не прочитает и свои счета. Второе: назначить каждому арендатору собственную роль PostgreSQL. Это может работать, но усложняет жизненный цикл подключений, пулов и учетных записей. Третье: настроить ограничение строк непосредственно в PostgreSQL — Row-Level Security (RLS). Теперь вопрос: кто гарантирует, что контекст арендатора нельзя подменить? И почему владелец таблицы может неожиданно обходить RLS?

    Перед тем как писать политику, нужно разобрать уровни допуска. Их нельзя смешивать.

    Клиент → сеть/TLS → pg_hba.conf → аутентификация → CONNECT к БД
                → роль / членство → USAGE схемы → привилегия объекта
                → RLS для конкретной команды и строки
                → ограничения данных / триггеры / выполнение

    Один отказ на любом уровне останавливает конкретную операцию. Но успех на первом уровне не заменяет последующие проверки. Пользователь, которому разрешили подключение, не становится автоматически владельцем таблиц. Пользователь с SELECT не получает автоматически все строки, если действует RLS. И RLS не проверяет подлинность бизнес-пользователя за приложение.

    В этой лекции один сквозной пример: схема app, таблица счетов app.invoices, владельческая роль app_owner, роль приложения app_runtime и разные арендаторы. Мы начнем с заведомо небезопасной конфигурации и постепенно закроем ее слабые места.

    Контракт безопасности: четыре вопроса¶

    Уровень Вопрос Механизм Типовая ошибка
    Подключение Кто может установить сессию? listen_addresses, HBA, SCRAM/TLS, CONNECT Широкая сеть / неверный HBA
    Объект Может ли роль обращаться к объекту? Roles, ownership, USAGE, GRANT Приложение владеет всем или имеет SUPERUSER
    Строка Какая строка видна/изменяема? RLS USING / WITH CHECK Нет политики на UPDATE или владелец обходит RLS
    Прикладной субъект Кому принадлежит запрос? Проверенный identity и серверный контекст Клиент сам задает tenant_id

    Практическое правило: проверяем все четыре уровня, иначе один успешный тест SELECT мало что доказывает.

    1. Threat model: что именно мы защищаем¶

    1.1. Угроза — это конкретная способность атакующего¶

    Начинаем с реалистичной модели. У нас есть клиентский API, приложение с ролью БД и PostgreSQL на отдельном сервере. Возможные нарушители имеют разные возможности: внешний пользователь может отправлять любые допустимые HTTP-параметры; атакующий при SQL injection способен влиять на часть SQL; злоумышленник с украденными учетными данными может открыть прямую сессию; разработчик ошибочно выдает GRANT; отдельный администратор владеет кластером. Защита от владельца кластера и суперпользователя не обеспечивается обычными RLS-политиками. Это граница доверия, а не баг.

    Под каждый сценарий формулируем свой инвариант. Например: app_runtime не умеет изменять DDL, не может читать app.secret_keys, не имеет доступа к строкам чужого арендатора; мигратор может менять схему, но не используется для HTTP-запросов; отчетная роль имеет только SELECT; администратор имеет отдельный канал доступа с аудитом.

    1.2. Матрица субъектов и операций¶

    Субъект SELECT invoices INSERT invoices DDL Смена владельца
    app_runtime Только строки текущего арендатора Только текущий арендатор Нет Нет
    report_reader Разрешенная отчетная область Нет Нет Нет
    app_migrator По задаче миграции По задаче миграции Да, в доверенной схеме Административная процедура
    app_owner Владеет таблицей Может управлять ею Да Через разрешенные операции
    PostgreSQL superuser Почти неограниченно Почти неограниченно Да Да

    Почему нельзя ограничиться одним GRANT ALL ON ALL TABLES TO app_runtime? Потому что приложение с DDL-правами превращает любую ошибку в гораздо более серьезный инцидент: возможность менять структуры, запускать опасные функции, создавать объекты в недоверенной схеме или отключить RLS через владение. Именно поэтому runtime и мигратор разделяются.

    1.3. Least privilege и defense in depth¶

    Минимальные полномочия (least privilege) означают, что субъект получает только операции, необходимые для своей роли. Глубокоэшелонированная защита (defense in depth) означает независимые проверки на API, сетевом уровне и в БД. Они нужны одновременно: RLS помогает при забытом WHERE, но не защитит, если атакующий получил superuser; проверка tenant на API помогает против произвольного пользовательского параметра, но может быть забыта в новом SQL.

    И не путайте confidentiality (конфиденциальность), integrity (целостность) и availability (доступность). Ошибка RLS — утечка строк; избыточный UPDATE — нарушение целостности; дорогостоящая функция в политике может увеличить latency и ухудшить доступность. Модель угроз определяет, какие из этих свойств проверяем.

    Инженерный вывод: безопасность PostgreSQL проектируется от возможностей конкретной роли и злоумышленника; список включенных настроек сам по себе не описывает гарантий.

    2. pg_hba.conf: первая граница допуска¶

    2.1. Запрос дошел до PostgreSQL. Почему сервер может отказать?¶

    Сначала важное разграничение: listen_addresses определяет интерфейсы, на которых postmaster слушает TCP; firewall решает, достигает ли пакет сервера; pg_hba.conf определяет допустимое правило аутентификации для уже пришедшего подключения. Нельзя заменить один из механизмов другим. Например, HBA с разрешением для подсети не откроет порт, если PostgreSQL слушает только loopback.

    pg_hba.conf читается при запуске и при reload (SELECT pg_reload_conf();) на Unix-подобных системах. В Windows файл перечитывается для новых соединений сразу. Файл состоит из упорядоченных правил. PostgreSQL выбирает первое совпавшее по типу соединения, базе, роли и адресу. Если аутентификация по нему провалилась, к следующему правилу сервер не переходит.

    # Пример для отдельного защищенного сервера; адреса учебные.
hostssl  finance  app_runtime  10.30.0.0/24  scram-sha-256
hostssl  finance  report_reader 10.31.4.0/24 scram-sha-256
host     all      all          0.0.0.0/0    reject

    Здесь важно: строка host совпадает и с TLS-, и с обычным TCP-подключением. hostssl — только с TLS. Если широкое host ... trust поставить выше hostssl ... scram-sha-256, сервер выберет первое правило и более строгое правило не сработает.

    2.2. Типы соединений и опасные допущения¶

    Тип Что соответствует Практический смысл
    local Unix-domain socket Отдельные правила для локальных процессов
    host TCP, с TLS или без него Нельзя считать автоматическим требованием шифрования
    hostssl TCP с TLS Требует включенного ssl и соответствующей сборки
    hostnossl TCP без TLS Допускает отдельную политику запрета незашифрованного доступа
    hostgssenc TCP с GSSAPI encryption Специализированная корпоративная среда

    trust означает доверять заявленному имени без парольной проверки и обычно неприемлем для удаленного production-доступа. peer для локального Unix socket сопоставляет пользователя ОС и роль БД; этот механизм не работает как замена паролю для удаленного TCP-клиента.

    2.3. Конфликт приоритетов правил: воспроизводимый случай¶

    # НЕБЕЗОПАСНО: слишком широкое правило стоит первым.
host     all      all          10.0.0.0/8    trust
hostssl  finance  app_runtime  10.30.0.0/24  scram-sha-256

    Клиент из 10.30.0.12 попадает в первую строку. Следующая строка не рассматривается. Это типовая проблема конфигурации: автор читает файл как набор независимых разрешений, хотя фактически работает первое совпадение.

    2.4. Как диагностировать правила без перебора вслепую¶

    SHOW hba_file;
SHOW listen_addresses;
SHOW ssl;

SELECT line_number, type, database, user_name,
       address, auth_method, error
FROM pg_hba_file_rules
ORDER BY line_number;

SELECT pg_reload_conf();  -- выполняет роль с соответствующим правом

    pg_hba_file_rules показывает разобранную текущую конфигурацию файла и ошибки синтаксиса. Это полезно, но не заменяет анализ реально использованного HBA-правила и журналов аутентификации. Ранее подключенные сессии не становятся автоматически другими после редактирования HBA.

    Применять разрешения «для удобства» через 0.0.0.0/0 + пароль — плохая практика для банковского контура. Требуется сетевое ограничение, строгая проверка клиента и централизованное управление секретами.

    Модель: listen_addresses → доступность TCP, firewall → доступность сети, pg_hba.conf → первое правило аутентификации, CONNECT → разрешение войти в конкретную БД. Проверка пароля не отменяет CONNECT.

    3. SCRAM, TLS и идентичность сервера¶

    3.1. Почему пароль нельзя просто отправить PostgreSQL текстом¶

    SCRAM-SHA-256 — механизм challenge-response на основе пароля. Клиент и сервер обмениваются значениями, позволяющими доказать знание пароля, не отправляя его непосредственно как открытый текст внутри протокольного сообщения. Это не заменяет TLS: защищенное хранение проверочного значения и шифрование транспорта решают разные задачи. Пароль может быть украден в приложении, логах, конфигурации или при неверной передаче секретов.

    SHOW password_encryption;  -- обычно scram-sha-256
-- Пароль задаем административно через безопасный механизм управления секретами.
-- Не храним настоящие production-пароли в SQL-миграциях и shell history.

    Поддержка MD5-парольных verifier в PostgreSQL 18 устарела; переключение инфраструктуры требует проверить совместимость драйверов и способ хранения существующих паролей. Параметр password_encryption влияет на создание/смену verifier, а не волшебным образом перевыпускает все существующие учетные данные.

    3.2. TLS: шифрование недостаточно без проверки сервера¶

    У клиента libpq есть sslmode. Важные режимы: disable, prefer, require, verify-ca, verify-full. require требует защищенное TLS-соединение, но детали проверки CA зависят от наличия корневого сертификата; verify-full явно проверяет и доверенную цепочку сертификатов, и имя сервера. Для удаленного production-доступа это сильная исходная модель.

    # Пример libpq: реальные пароль и сертификаты приходят из секретного хранилища.
psql 'host=db.internal.example dbname=finance user=app_runtime \
      sslmode=verify-full sslrootcert=/etc/ssl/db-root.crt'

    Если злоумышленник контролирует DNS/сеть, но клиент принимает произвольный сертификат, соединение может быть перехвачено. Значит, вопрос не только «зашифрован ли канал?», но и «с кем именно установлено соединение?».

    3.3. Проверка реального соединения¶

    SELECT a.pid, a.usename, a.client_addr,
       s.ssl, s.version, s.cipher
FROM pg_stat_activity AS a
LEFT JOIN pg_stat_ssl AS s USING (pid)
WHERE a.pid = pg_backend_pid();

    pg_stat_ssl.ssl = true говорит о TLS у данного backend. Но это не доказывает, что клиент проверял сертификат сервера в режиме verify-full. Эту гарантию обеспечивают настройки клиента и инфраструктура управления сертификатами.

    TLS и SCRAM дают цену в CPU и времени установки соединения. В нормальной backend-архитектуре соединения переиспользуются; на пике reconnect storm дорогое создание соединений может стать дополнительным узким местом. Устройство пулов мы уже изучили, поэтому здесь достаточно увидеть связь «строгая аутентификация → стоимость handshake → необходимость корректного пула».

    3.4. Сертификаты клиентов и обязательность TLS¶

    PostgreSQL поддерживает аутентификацию сертификатом клиента (cert) и дополнительную проверку клиентского сертификата для hostssl через clientcert=verify-ca / clientcert=verify-full. Это отдельная политика доступа, требующая управления CA, выдачей, отзывом и обновлением сертификатов. Не следует считать, что любой hostssl автоматически проверяет сертификат клиента: по умолчанию TLS устанавливает защищенный канал с сервером, а пользователь далее проходит выбранную HBA-аутентификацию.

    Инженерный вывод: аутентификация пользователя, проверка сервера и защита канала — три разных вопроса. Диагностировать их нужно раздельно.

    4. Roles: от кого сервер проверяет полномочия¶

    4.1. Роль в PostgreSQL — это субъект и группа полномочий¶

    PostgreSQL использует единый механизм ролей. Роль с LOGIN может выступать учетной записью подключения; роль без LOGIN удобно использовать как группу прав или владельца объектов. Поэтому каждая новая таблица не должна автоматически становиться собственностью прикладного логина.

    -- Выполняет администратор учебного кластера.
CREATE ROLE app_owner NOLOGIN;
CREATE ROLE app_reader NOLOGIN;
CREATE ROLE app_writer NOLOGIN;
CREATE ROLE app_runtime LOGIN;
CREATE ROLE app_migrator LOGIN;

-- Система управления секретами назначает пароль app_runtime отдельно.
GRANT app_reader, app_writer TO app_runtime;

    В реальной системе роль мигратора получает административную возможность на строго необходимой схеме, а runtime — нет. В примерах возможны временные роли для учебных проверок, но production-пароли в SQL не печатаем.

    4.2. Членство: INHERIT, SET, ADMIN — три разных права¶

    Предположим, app_runtime включен в app_reader. Но означает ли это, что ему всегда доступны права чтения? PostgreSQL 18 учитывает опции конкретного членства:

    • INHERIT TRUE — разрешает автоматически использовать полномочия группы через соответствующую цепочку членств;
    • SET TRUE — позволяет выполнить SET ROLE в эту роль;
    • ADMIN TRUE — позволяет управлять членством в этой роли с учетом правил PostgreSQL.
    GRANT app_reader TO app_runtime
  WITH INHERIT TRUE, SET FALSE;

-- app_runtime автоматически использует объектные привилегии app_reader,
-- но не получает право SET ROLE app_reader через это членство.

    Если одна цепочка членства содержит INHERIT FALSE, автоматическое наследование по ней прекращается. Специальные атрибуты вроде SUPERUSER, CREATEDB, CREATEROLE не передаются как обычные права на таблицы.

    4.3. session_user против current_user¶

    SELECT session_user, current_user;
-- После SET ROLE current_user может измениться, session_user останется логином.

SET ROLE app_reader;
SELECT session_user, current_user;
RESET ROLE;

    session_user — исходный идентификатор сессии (возможны специальные административные изменения). current_user — эффективный субъект проверки полномочий. При SECURITY DEFINER временно применяется владелец функции. Это различие критично для политики USING (owner_name = current_user): если вы ошиблись в том, кто является current_user, политика защищает не того субъекта, которого вы задумали.

    4.4. Почему SUPERUSER, CREATEROLE, BYPASSRLS запрещены прикладной роли¶

    SUPERUSER способен обходить обычные проверки доступа; BYPASSRLS обходит политики RLS; CREATEROLE расширяет административные возможности. Давать такие атрибуты runtime-сервису ради удобства — фактически выключить важные уровни изоляции. Нужны отдельные учетные записи для администрирования и приложения, раздельные секреты и аудит изменений прав.

    Для проверки:

    SELECT rolname, rolcanlogin, rolsuper, rolcreaterole,
       rolbypassrls, rolinherit
FROM pg_roles
WHERE rolname IN ('app_owner','app_reader','app_writer','app_runtime');

    Инженерный вывод: названия ролей — договоренность разработчиков; настоящие гарантии определяются атрибутами, членством и проверками конкретной команды.

    5. GRANT/REVOKE: почему право на таблицу состоит из нескольких разрешений¶

    5.1. Доступ к схеме и к объекту проверяется раздельно¶

    Итак, app_runtime успешно подключился к БД. Выполняем SELECT из app.invoices, получаем permission denied for schema app. В чем ошибка? GRANT SELECT ON app.invoices не дает автоматически USAGE ON SCHEMA app. Схема — отдельный объект доступа.

    -- Администратор создает схему, владеет ею отдельная роль.
CREATE SCHEMA app AUTHORIZATION app_owner;

GRANT USAGE ON SCHEMA app TO app_reader, app_writer;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO app_reader;
GRANT INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_writer;

    USAGE ON SCHEMA дает возможность разрешать имена объектов внутри схемы при наличии объектных разрешений; оно не дает создавать таблицы. Для создания объектов требуется CREATE ON SCHEMA. Более того, права на таблицы не передают автоматически права на последовательности: при необходимости nextval() потребуется отдельный USAGE/UPDATE на sequence или соответствующий механизм управления идентификаторами.

    5.2. Различие между объектными операциями¶

    Право Разрешает Не означает
    SELECT Читать разрешенные данные Изменять данные или обходить RLS
    INSERT Добавлять строки Читать существующие строки
    UPDATE Изменять разрешенные колонки/строки Удалять строки
    DELETE Удалять разрешенные строки TRUNCATE
    TRUNCATE Очищать таблицу Подпадает под RLS-фильтрацию строк
    REFERENCES Создавать FK-ссылки при соответствующих условиях Читать все строки напрямую
    MAINTAIN Выполнять определенные операции обслуживания Владеть таблицей

    TRUNCATE не фильтруется RLS по строкам; это отдельная privilege. Следовательно, роль приложения с TRUNCATE, полученным «за компанию», может обойти бизнес-идею «удаляй только свои строки». Это важная ловушка безопасности.

    5.3. REVOKE и членство: один путь убрали, другой остался¶

    Если роль имеет SELECT напрямую и через другую роль, удаление прямого права не заберет у нее наследуемый доступ. Права нужно проверять по эффективному субъекту.

    SELECT
  has_schema_privilege('app_runtime', 'app', 'USAGE') AS schema_usage,
  has_table_privilege('app_runtime', 'app.invoices', 'SELECT') AS select_ok,
  has_table_privilege('app_runtime', 'app.invoices', 'DELETE') AS delete_ok;

    Эти функции отвечают на вопрос об объектных разрешениях. Они не доказывают, какие строки пропустит RLS. Для строковой политики нужны отдельные поведенческие тесты.

    5.4. PUBLIC — специальная группа, которой принадлежат все роли¶

    PUBLIC в GRANT/REVOKE — псевдороль, охватывающая всех пользователей. По умолчанию для новых БД PUBLIC имеет CONNECT и TEMPORARY, для новых функций часто EXECUTE. На новых таблицах default public privileges нет. Но все это может быть изменено настройками и миграциями.

    -- Пример ужесточения для отдельной БД после оценки зависимостей.
REVOKE CONNECT ON DATABASE finance FROM PUBLIC;
GRANT CONNECT ON DATABASE finance TO app_runtime, app_migrator;

    Существующие подключения не будут автоматически разорваны при REVOKE CONNECT. Команду следует применять с учетом служебных ролей и подключений администраторов.

    5.5. Права на колонки и обход через представления¶

    PostgreSQL допускает GRANT SELECT (col1) и GRANT UPDATE (col2). Это полезно, но не заменяет модель чувствительных данных: функции, представления, SECURITY DEFINER и некорректные дополнительные GRANT могут открыть косвенный путь. Необязательно выдавать прямой SELECT на таблицу, если API работает через безопасное представление или функцию; однако тогда необходимо проверить, чьи полномочия используются внутри этой прослойки.

    Вывод: успешная аутентификация → подключение к БД → схема → объект → колонка → строка. Каждая граница имеет собственные проверки.

    6. Ownership: право владения — отдельная власть¶

    6.1. Почему GRANT не превращает пользователя во владельца¶

    Права SELECT/INSERT/UPDATE/DELETE разрешают операции с данными. Владелец объекта управляет самим объектом: меняет его определение, назначает привилегии и, в типичном случае, обходит RLS для собственной таблицы. Владение не является обычной privilege, которую можно выдать командой GRANT SELECT; это другая граница власти.

    Поэтому полезна конструкция: app_owner NOLOGIN владеет схемой и таблицами, app_migrator получает необходимое право действовать от имени владельца при миграциях, app_runtime не состоит в app_owner. Роли для разных бизнес-функций получают только рабочие привилегии. При этом реальную необходимость членства/SET нужно проектировать с учетом конкретного инструмента миграций, а не выдавать всем GRANT app_owner.

    -- Выполняет администратор. Роль, создающая объект,
-- должна иметь соответствующее CREATE в схеме.
SET ROLE app_owner;
CREATE TABLE app.invoices (
  id bigint PRIMARY KEY,
  tenant_id bigint NOT NULL,
  amount numeric(12,2) NOT NULL CHECK (amount >= 0),
  created_at timestamptz NOT NULL DEFAULT now()
);
RESET ROLE;

GRANT SELECT ON app.invoices TO app_reader;
GRANT INSERT, UPDATE, DELETE ON app.invoices TO app_writer;

    Важное различие: app_runtime не обязан владеть app.invoices, чтобы выполнять SQL. А для ALTER TABLE ... DISABLE ROW LEVEL SECURITY обычного UPDATE недостаточно.

    6.2. Как убедиться, кто владелец¶

    SELECT n.nspname AS schema_name,
       c.relname AS table_name,
       pg_get_userbyid(c.relowner) AS owner_name,
       c.relrowsecurity, c.relforcerowsecurity
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname = 'app' AND c.relname = 'invoices';

    relrowsecurity показывает, включена ли RLS, relforcerowsecurity — принудительное применение для владельца. Эти поля не описывают все возможные обходы: superuser и BYPASSRLS все равно обойдут политики.

    6.3. Схема public и исторические права¶

    В PostgreSQL 18 новый кластер обычно уже не выдает CREATE ON SCHEMA public всем через PUBLIC. Но обновленный с давней версии кластер может сохранять старые привилегии. Нельзя преподавать универсальное «в public любой может создать функцию» и нельзя автоматически считать ее защищенной. Проверяем реальные ACL:

    SELECT nspname, nspacl
FROM pg_namespace
WHERE nspname = 'public';

SELECT has_schema_privilege('app_runtime', 'public', 'CREATE');

    Если в доверенном пути поиска находится схема, доступная для CREATE недоверенной роли, эта роль может создать объект с именем, которого не ожидала вызывающая функция. Здесь abstraction начинает протекать: разрешение имен само становится частью модели безопасности.

    7. search_path: кто подставит имя объекта в SQL¶

    7.1. PostgreSQL не обязан понимать, какую именно accounts вы имели в виду¶

    SQL SELECT * FROM invoices содержит неквалифицированное имя. PostgreSQL разрешает его относительно search_path. Для таблиц, функций и операторов правила отличаются в деталях; также участвуют системная и временная схемы. Поэтому безопасная практика для привилегированных функций — квалифицировать критичные объекты и исключить из пути схемы, доступные недоверенным пользователям.

    SHOW search_path;
SELECT current_schemas(true);

-- Явная адресация лучше, чем зависимость от клиентского search_path:
SELECT id, amount FROM app.invoices WHERE id = 1;

    Теперь представим SECURITY DEFINER-функцию, читающую SELECT secret FROM settings, но ее search_path включает схему, в которой атакующий может создавать объекты. Подмена settings может изменить смысл операции. Ошибка здесь гораздо серьезнее обычного relation does not exist, поскольку функция исполняется с правами владельца.

    7.2. Неожиданная роль временной схемы¶

    pg_temp участвует в разрешении имен временных отношений. Важная особенность: для отношений и типов временная схема может искаться раньше явно заданных обычных схем, если не указать ее место. Поэтому в документации PostgreSQL для SECURITY DEFINER приведен надежный шаблон SET search_path = trusted_schema, pg_temp, где pg_temp явно стоит последней.

    Для операторов и функций все тоньше; одного «мы написали имя таблицы с префиксом» не всегда достаточно, если в запросе вызываются неквалифицированные функции или операторы. По этой причине безопасный код должен контролировать весь контекст разрешения имен и не принимать произвольный search_path вызывающей стороны.

    7.3. Ограничения REVOKE CREATE ON SCHEMA public¶

    -- Административное ужесточение; сначала проверяем зависимости.
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

    Это закрывает конкретный путь создания новых объектов, но не отменяет уже созданные объекты и не заменяет аудит search_path во всех SECURITY DEFINER-функциях. Кроме того, объект в другой схеме, доступной для записи, может быть столь же опасен.

    Вывод: схема — пространство имен и отдельная граница полномочий. Путь поиска является частью исполняемого контракта SQL и может влиять на безопасность, даже если ни один GRANT на исходную таблицу не менялся.

    8. SECURITY DEFINER: повышенные привилегии внутри функции¶

    8.1. Для чего он нужен и где возникает риск¶

    По умолчанию SQL-функция выполняется как SECURITY INVOKER, то есть с правами вызывающего пользователя. SECURITY DEFINER временно использует полномочия владельца функции. Это удобно, если надо открыть приложению строго ограниченную операцию над закрытой таблицей. Но фактически мы строим маленький привилегированный API внутри PostgreSQL.

    Пример задачи: прикладная роль не может читать таблицу admin.payments_secret, но может вызвать функцию, возвращающую агрегированный публичный статус. Если функция позволяет задавать произвольный SQL, подменять search_path или извлекать все секреты через диагностический вывод, ограничение будет бессмысленным.

    8.2. Безопасный шаблон функции¶

    -- Создание выполняет доверенная роль-владелец admin-схемы.
BEGIN;

CREATE OR REPLACE FUNCTION admin.invoice_count(p_tenant bigint)
RETURNS bigint
LANGUAGE sql
SECURITY DEFINER
SET search_path = admin, pg_temp
AS $$
  SELECT count(*)
  FROM app.invoices AS i
  WHERE i.tenant_id = p_tenant;
$$;

REVOKE ALL ON FUNCTION admin.invoice_count(bigint) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION admin.invoice_count(bigint) TO app_runtime;
COMMIT;

    Этот шаблон демонстрирует контроль пути поиска и ACL, но не является безопасной бизнес-функцией для мультиарендного приложения: вызывающий может подставить любой p_tenant. В production субъект должен определяться доверенным способом, а функция должна сама проверять, что он вправе читать запрошенный tenant. Показательно, как легко сделать синтаксически защищенную функцию с неправильной бизнес-авторизацией.

    Для действительно минимально привилегированной функции желательно выполнять только строго заданную операцию, не соединять произвольный пользовательский текст в динамический SQL и по возможности ссылаться на объекты полностью квалифицированно.

    8.3. Почему REVOKE EXECUTE FROM PUBLIC нужен в той же транзакции¶

    У новых функций EXECUTE по умолчанию выдается PUBLIC. Если создать SECURITY DEFINER, выполнить COMMIT, а затем отдельной транзакцией удалить право, существует окно, когда функция доступна шире задуманного. Поэтому CREATE/REVOKE/GRANT выполняем атомарно внутри одной миграции.

    BEGIN;
CREATE FUNCTION admin.sensitive_operation() RETURNS void
LANGUAGE plpgsql SECURITY DEFINER
SET search_path = admin, pg_temp
AS $$ BEGIN NULL; END $$;
REVOKE ALL ON FUNCTION admin.sensitive_operation() FROM PUBLIC;
GRANT EXECUTE ON FUNCTION admin.sensitive_operation() TO app_runtime;
COMMIT;

    Это демонстрационная функция-заглушка. Наличие SECURITY DEFINER должно быть оправдано конкретной операцией и сопровождено анализом входов, доступа к данным и побочных эффектов.

    8.4. Функция, принадлежащая владельцу таблицы, может обойти ее RLS¶

    Вот место, где простая модель «у приложения есть RLS, значит любая функция безопасна» рушится. Если SECURITY DEFINER исполняется от имени владельца защищаемой таблицы, и владелец не принужден к RLS, функция может увидеть все строки. Возникает обход через разрешенный вызов функции, даже когда прямая SELECT у приложения фильтруется.

    Поэтому в аудите проверяем не только pg_policies, но и владельцев функций, prosecdef, proconfig, права EXECUTE, а также каждое место, где данные RLS-таблиц читаются от привилегированного имени.

    SELECT n.nspname, p.proname,
       p.prosecdef AS security_definer,
       p.proconfig AS function_settings,
       pg_get_userbyid(p.proowner) AS owner_name
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname IN ('app', 'admin')
  AND p.prosecdef;

    8.5. Цена и диагностический смысл¶

    При неправильном использовании SECURITY DEFINER повышает риск и усложняет анализ планов/прав, но само по себе слово SECURITY DEFINER не обещает ни ускорения, ни деградации. Цена определяется выполняемыми внутри функциями SQL, количеством вызовов и возможностью оптимизатора обрабатывать выражение. В p99 важнее измерять реальные операции и их частоту, а не рассматривать «безопасность» как бесплатный флаг.

    Вывод: SECURITY DEFINER — привилегированный интерфейс. Контракт его безопасности включает владельца, search_path, права вызова, параметры и поведение RLS при исполнении.

    9. Default Privileges: почему новая таблица внезапно недоступна приложению¶

    9.1. Права существующих объектов и будущих объектов — разные состояния¶

    Допустим, администратор выполнил:

    GRANT SELECT ON ALL TABLES IN SCHEMA app TO app_reader;

    Сегодня все запросы работают. Завтра мигратор создает app.invoices_2027, и новая таблица не доступна app_reader. Причина: команда ON ALL TABLES IN SCHEMA меняет ACL существующих таблиц. Она не является подпиской на будущие объекты.

    Для будущих объектов есть ALTER DEFAULT PRIVILEGES.

    ALTER DEFAULT PRIVILEGES
  FOR ROLE app_owner IN SCHEMA app
  GRANT SELECT ON TABLES TO app_reader;

ALTER DEFAULT PRIVILEGES
  FOR ROLE app_owner IN SCHEMA app
  GRANT INSERT, UPDATE, DELETE ON TABLES TO app_writer;

    Правила применятся к объектам, которые создаст роль app_owner в соответствующей схеме. Если мигратор фактически создает таблицы от имени app_migrator, нужны настройки именно для этой роли-создателя. Членство само по себе не означает, что будущие ACL будут рассчитаны как для всех ролей, членом которых он является.

    9.2. Глобальные и per-schema default privileges¶

    PostgreSQL сначала учитывает глобальные правила роли-создателя, затем расширения для отдельных схем. Важная ловушка: ALTER DEFAULT PRIVILEGES IN SCHEMA ... REVOKE EXECUTE ... FROM PUBLIC не может отменить изначальный глобальный default PUBLIC EXECUTE для функций. Для этого нужна глобальная настройка для соответствующей роли.

    -- Для будущих функций, создаваемых app_owner:
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner
REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;

    Пересмотреть состояние:

    SELECT defaclrole::regrole AS creator,
       COALESCE(defaclnamespace::regnamespace::text, '(global)') AS scope,
       defaclobjtype, defaclacl
FROM pg_default_acl
ORDER BY creator::text, scope;

    Обратите внимание: ALTER DEFAULT PRIVILEGES не изменяет права ранее созданных объектов. Для них нужен явный аудит и GRANT/REVOKE.

    9.3. Как это связано с безопасными миграциями¶

    Новая таблица появляется при развертывании новой версии сервиса. Если мигратор выдает права неправильно, сервис получает либо permission denied, либо чрезмерные возможности. Это не проблема планировщика и не баг драйвера: это несогласованность владельца, роли-создателя и default ACL. Поэтому в миграциях можно проверять и структуру, и effective privileges прикладной роли.

    Вывод: доступность существующей схемы не гарантирует корректный доступ к вновь созданным объектам. Default privileges следует привязывать к реальному владельцу/создателю, а не к названию инструмента миграций.

    10. Row-Level Security: защищаем строки внутри разрешенной таблицы¶

    10.1. Имеется SELECT, но не все строки должны быть видны¶

    Создаем два арендатора: 101 и 202. Одна таблица app.invoices. Прикладная роль имеет SELECT/INSERT/UPDATE/DELETE, но не должна видеть чужую информацию. Здесь появляется RLS — дополнительная политика на уровне строки.

    -- Выполняет владелец таблицы или уполномоченный администратор.
INSERT INTO app.invoices (id, tenant_id, amount) VALUES
 (1, 101, 100.00), (2, 101, 200.00),
 (3, 202, 300.00), (4, 202, 400.00);

ALTER TABLE app.invoices ENABLE ROW LEVEL SECURITY;

    После ENABLE ROW LEVEL SECURITY, если для обычной роли нет подходящих разрешающих политик, действует default deny: строки скрыты, операции изменения отфильтровываются/запрещаются согласно команде. Владелец таблицы обычно обходит политику, поэтому проверять результат под владельцем нельзя.

    10.2. Первая политика на чтение: контекст арендатора¶

    Для демонстрации используем GUC (app.tenant_id), который приложение установит после проверки авторизации. current_setting('app.tenant_id', true) вернет NULL, если настройка отсутствует; выражение с NULL не даст TRUE, и строки будут скрыты.

    CREATE POLICY invoice_tenant_select
ON app.invoices
FOR SELECT TO app_runtime
USING (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
);

    Контекст должен устанавливаться внутри уже открытой транзакции. Например, для тестовой роли:

    BEGIN;
SELECT set_config('app.tenant_id', '101', true);  -- true = LOCAL
SELECT id, tenant_id, amount FROM app.invoices ORDER BY id;
COMMIT;

    При правильных правах и RLS две строки арендатора 101 видны, строки 202 — нет. Однако GUC — обычное состояние сессии/транзакции, а не подписанный токен. Если злоумышленник может произвольно выполнять SQL от имени app_runtime, он может установить app.tenant_id = 202 и обойти такую политику. Этот подход защищает от случайного отсутствия tenant-фильтра в запросе, но требует доверенного пути установки значения.

    10.3. USING и WITH CHECK: старые и новые значения¶

    USING определяет, какие существующие строки доступны данной команде. WITH CHECK определяет, допустимо ли новое значение строки при INSERT или UPDATE.

    CREATE POLICY invoice_tenant_insert
ON app.invoices
FOR INSERT TO app_runtime
WITH CHECK (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
);

CREATE POLICY invoice_tenant_update
ON app.invoices
FOR UPDATE TO app_runtime
USING (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
)
WITH CHECK (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
);

CREATE POLICY invoice_tenant_delete
ON app.invoices
FOR DELETE TO app_runtime
USING (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
);

    Если разрешить UPDATE только через USING, но не проверить новые значения там, где применяется соответствующая политика/WITH CHECK, можно допустить нежелательный перенос строки между арендаторами. Для FOR ALL и некоторых форм FOR UPDATE PostgreSQL использует правило наследования WITH CHECK из USING, если явное выражение не задано; в обучении правильнее указывать оба условия явно, чтобы не скрывать различие семантики.

    10.4. Проверка чтения, записи и обновления¶

    -- Выполнить как app_runtime на учебной БД.
BEGIN;
SELECT set_config('app.tenant_id', '101', true);
SELECT id, tenant_id FROM app.invoices ORDER BY id;
-- Ожидаются строки только tenant_id=101.

INSERT INTO app.invoices (id, tenant_id, amount)
VALUES (5, 202, 50.00);
-- ERROR: new row violates row-level security policy
ROLLBACK;

    Аналогичный тест для UPDATE должен пытаться изменить tenant_id с 101 на 202; WITH CHECK запретит переход. Для DELETE чужой строки обычно получится DELETE 0 — строка просто не считается доступной для команды. Для сложных RETURNING, ON CONFLICT DO UPDATE и MERGE проверки могут отличаться: поведение зависит от применимых SELECT и DML-политик и требует отдельного теста. В частности, ON CONFLICT DO UPDATE может выбросить ошибку вместо тихого пропуска строки, если существующая строка не проходит нужное USING.

    10.5. RLS и обычные объектные привилегии действуют вместе¶

    Если убрать GRANT SELECT, политика FOR SELECT сама по себе не выдаст право чтения. Если приложение имеет UPDATE, но политика его запрещает, наличие объектного GRANT не поможет. И если включить RLS, но выполнять запрос как superuser, вы не протестировали поведение прикладной роли.

    Точная модель: объектная privilege определяет, разрешен ли тип операции; RLS ограничивает допустимые строки внутри разрешенной операции; бизнес-identity определяет, какую политику или контекст мы должны применять.

    11. RLS Policies: комбинации, команды и неочевидная цена¶

    11.1. Почему две политики не обязательно означают «две проверки через AND»¶

    В PostgreSQL политики делятся на permissive и restrictive. Применимые разрешающие (permissive) политики объединяются через OR, ограничительные (restrictive) — через AND. Итог обычно имеет форму:

    (разрешающая_1 OR разрешающая_2 OR ...)
                    AND
(ограничительная_1 AND ограничительная_2 AND ...)

    Нужна хотя бы одна применимая permissive-политика, иначе restrictive-политики ничего не разрешают сами по себе. Это частая ошибка: разработчик создал «более строгую» политику USING (tenant_id = ...), но оставил старую permissive USING (true). Итоговый OR снова пропускает строки чужих арендаторов.

    -- ОПАСНО: разрешающая политика для всех строк.
CREATE POLICY accidental_open_read
ON app.invoices AS PERMISSIVE
FOR SELECT TO app_runtime
USING (true);

-- Новая permissive-политика НЕ исправляет первую:
-- true OR tenant_id = current_tenant -> true.

    Если нужна глобальная дополнительная проверка для всех разрешенных строк, ее логически удобно выражать restrictive-политикой. Но в любой конфигурации надо доказать полное итоговое условие с учетом ролей и команд; ничего не угадывать по имени политики.

    11.2. Командно-специфичные политики и граничные случаи¶

    Команда USING WITH CHECK
    SELECT Фильтрует возвращаемые строки Не используется
    INSERT Не применяется Проверяет новую строку
    UPDATE Проверяет доступную старую строку Проверяет новую строку
    DELETE Проверяет доступную удаляемую строку Не используется
    INSERT ... ON CONFLICT DO UPDATE Проверки INSERT + UPDATE по контракту команды Проверки вставляемых/обновленных значений

    Точная матрица для MERGE, ON CONFLICT, RETURNING и команд, использующих колонки в WHERE, сложнее; PostgreSQL 18 документирует, когда дополнительно нужны SELECT-политики. Для основной лекции важно инженерное следствие: политику надо тестировать на фактической форме SQL, которую выполняет приложение, а не на отдельно написанном SELECT.

    11.3. Права роли и выражения политики¶

    Условие RLS исполняется как часть запроса и обычно с полномочиями вызывающего пользователя. Если внутри политики вызывается функция или читается другая таблица, могут потребоваться дополнительные права. SECURITY DEFINER иногда применяется как ограниченный мост к закрытой lookup-таблице, но тогда ее владелец, путь поиска и параметры входят в модель доверия.

    Если политика вызывает дорогостоящую функцию на каждой строке, стоимость может стать значимой. Важны селективность, возможность оптимизаций, порядок вычисления предикатов и свойства функции. RLS — механизм безопасности, а не гарантия, что каждая проверка выполняется один раз на запрос. Анализируем реальные планы через EXPLAIN под прикладной ролью и измеряем задержки.

    11.4. Почему leakproof — особая метка¶

    В обычной формулировке PostgreSQL вычисляет RLS-предикаты до пользовательских выражений, которые могли бы раскрывать информацию. Для функций с признаком leakproof оптимизатор может изменить порядок проверки: такие функции обязуются не выдавать секреты через ошибки или побочные каналы от значений аргументов. Эта метка — высокопривилегированное обещание и не должна выставляться произвольной пользовательской функции ради производительности.

    Если пользовательский WHERE вызывает функцию, способную выбрасывать содержимое строки в сообщение об ошибке, важно, чтобы неразрешенная строка не стала источником утечки до проверки RLS. Именно поэтому свойства выражений влияют на возможные преобразования плана.

    11.5. security_barrier views и права владельца представления¶

    Представления могут выступать дополнительной границей доступа, но RLS и представления имеют нюансы. Обычное представление по умолчанию использует права владельца для доступа к нижележащим отношениям; PostgreSQL также поддерживает security_invoker views. Для security-sensitive views может использоваться security_barrier, ограничивающий опасное переупорядочивание условий. Нельзя считать любое CREATE VIEW автоматической заменой RLS.

    Для нашей лекции достаточно проверяемого правила: если приложение обращается к представлению, аудит должен учитывать владельца/режим представления и политики нижележащих таблиц, а не только исходный SELECT к представлению.

    Вывод: совокупность нескольких RLS-политик — логическое выражение, зависящее от команды, роли и режимов политики. Без явного вычисления этого выражения безопасность легко переоценить.

    12. RLS Bypass: владельцы, BYPASSRLS и межарендная изоляция¶

    12.1. Почему администратор видит все строки, а приложение — только две¶

    RLS включена, политики написаны. Администратор запускает SELECT * FROM app.invoices, видит все строки. Разработчик делает вывод: «RLS не работает». На самом деле он тестирует под ролью, которую PostgreSQL освобождает от политик.

    • SUPERUSER обходит RLS.
    • Роль с атрибутом BYPASSRLS обходит RLS.
    • Владелец таблицы обычно обходит RLS.
    • ALTER TABLE ... FORCE ROW LEVEL SECURITY заставляет обычного владельца подчиняться политике, но не отменяет обход суперпользователя и BYPASSRLS.
    ALTER TABLE app.invoices FORCE ROW LEVEL SECURITY;

SELECT relname, relrowsecurity, relforcerowsecurity
FROM pg_class
WHERE oid = 'app.invoices'::regclass;

    Рекомендация: приложение не должно работать от имени владельца таблиц. FORCE полезен как дополнительная защита, но разделение ролей владения и runtime остается основой.

    12.2. Почему row_security = off не отключает RLS для обычной роли¶

    В PostgreSQL параметр row_security = off не является разрешением обойти политику. Для обычной роли он приводит к ошибке, если выполнение запроса требует применения RLS, чтобы система случайно не выдала неполный результат там, где ожидаются все данные. Этот режим полезен, например, для некоторых задач выгрузки или проверки полноты, но не превращает учетную запись в администратора.

    SET row_security = off;
-- Для обычной роли запрос, требующий RLS, может завершиться ошибкой.
RESET row_security;

    Сценарий: резервная копия создана под ролью, которую RLS фильтрует. Файл существует, но содержит только разрешенные строки. Поэтому нельзя считать дамп полным, если не проверена учетная запись и режим работы инструмента. Устройство backup мы уже изучили; здесь фиксируем именно границу безопасности.

    12.3. Утечка через UNIQUE и FOREIGN KEY¶

    Проверки уникальности, первичных ключей и ссылочной целостности обходят RLS для обеспечения корректности данных. Это создает возможный побочный канал: попытка вставить значение, присутствующее в чужой строке, может получить ошибку уникальности и тем самым выдать некоторую информацию о ее существовании.

    Пример: UNIQUE(email) глобален для всей таблицы пользователей. Если tenant A пытается создать аккаунт с email tenant B, конфликт может проявиться через ошибку, несмотря на невозможность прочитать чужую строку. Это не означает, что PostgreSQL отдает чужую строку напрямую. Это означает, что безопасность API должна учитывать информацию в ошибках и структуру уникальных ограничений.

    Снизить риск помогают корректная модель ключей (UNIQUE(tenant_id, ...) там, где нужна локальная уникальность), отсутствие избыточных деталей в ошибках API, rate limiting и проверка модели угроз. Глобальная уникальность может быть осознанным бизнес-требованием, тогда ее побочные эффекты нужно учитывать отдельно.

    12.4. Общая роль БД для тысяч арендаторов: где хранить identity¶

    Популярная модель: один app_runtime на всех арендаторов, а tenant_id устанавливается через SET LOCAL app.tenant_id. Плюсы: конечное число подключений, простое применение политики к строкам, отсутствие отдельной роли на каждого клиента. Но появляется критический вопрос: кто устанавливает значение?

    HTTP request
  → проверка JWT/сессии backend-приложением
  → определение trusted tenant_id
  → BEGIN (получено одно физическое соединение)
  → SET LOCAL app.tenant_id = trusted value
  → SQL с RLS
  → COMMIT/ROLLBACK (локальный параметр сброшен)

    SET LOCAL подходит для транзакционного жизненного цикла, включая PgBouncer transaction pooling, но важно не вынести установку GUC на одно соединение, а SQL — на другое. Надо использовать одну транзакцию/одно закрепленное физическое соединение. В database/sql это достигается использованием объекта *sql.Tx, а не самостоятельными вызовами на общем *sql.DB. В примере приложения нужно следить за отменой контекста и гарантированным закрытием транзакции.

    12.5. Самая важная граница: SQL injection и подменяемый GUC¶

    Если нарушитель получил возможность выполнять произвольный SQL с правами app_runtime, он может выполнить:

    SELECT set_config('app.tenant_id', '202', true);

    И политика tenant_id = current_setting('app.tenant_id')::bigint примет новое значение. Обычный пользовательский GUC — не надежное доказательство личности арендатора. Он может защищать от забытых tenant-предикатов в коде, но не от полного произвольного SQL под той же ролью.

    Если модель угроз включает выполнение произвольного SQL, нужны более сильные механизмы: разные роли/учетные данные на различные группы субъектов, доверенная серверная проверка контекста, ограниченные операции через тщательно спроектированные функции, изоляция по БД/схеме/сервису или комбинация мер. Каждый вариант имеет эксплуатационную цену. Не следует обещать от RLS большего, чем обеспечивают полномочия вызывающей роли.

    12.6. Что остается у прикладного уровня¶

    PostgreSQL не знает автоматически, что пользователь из HTTP-токена имеет право работать с tenant 101. Приложение должно надежно проверить токен, связь пользователя с организацией и допустимую операцию. Затем оно передает доверенный контекст в БД. RLS обеспечивает дополнительную границу, снижающую вероятность межарендной утечки из-за ошибочного SQL. Безопасность строится совместной проверкой identity, role, privilege и policy.

    Инженерный вывод: проверяйте, кто может изменить tenant-контекст, кто владеет таблицей и какие боковые каналы остаются у операций с ограничениями целостности.

    13. Security Diagnostics: как доказать наличие ограничений¶

    13.1. Список ролей с опасными атрибутами¶

    SELECT rolname, rolcanlogin, rolsuper,
       rolcreaterole, rolcreatedb, rolbypassrls
FROM pg_roles
WHERE rolcanlogin OR rolsuper OR rolbypassrls
ORDER BY rolsuper DESC, rolbypassrls DESC, rolname;

    Это не означает, что каждая строка подозрительна: роли мониторинга, резервного копирования и администратора могут иметь обоснованные права. Важен инвентарь и объяснение причин каждой привилегии. Роли БД могут быть глобальны для кластера, а права на объекты зависят от конкретной базы.

    13.2. Проверка владельцев, ACL и параметров RLS¶

    SELECT n.nspname AS schema_name,
       c.relname AS table_name,
       pg_get_userbyid(c.relowner) AS owner_name,
       c.relrowsecurity AS rls_enabled,
       c.relforcerowsecurity AS rls_forced,
       c.relacl
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'app' AND c.relkind IN ('r', 'p')
ORDER BY c.relname;

    relacl IS NULL означает штатные default permissions для данного объекта, а не «доступ разрешен всем». Для диагностики effective permissions есть has_table_privilege() и has_schema_privilege(). Не стоит читать ACL как единственный источник результата — членство и владение изменяют эффективную картину.

    13.3. Проверка RLS-политик¶

    SELECT schemaname, tablename, policyname,
       permissive, roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'app'
ORDER BY tablename, policyname;

    Читаем условие как составное выражение с учетом OR/AND и применимости к конкретной команде. Особенно ищем USING (true) в permissive, отсутствие WITH CHECK там, где его ожидали, неограниченное TO PUBLIC, а также выключенный relrowsecurity при наличии созданных политик. Создание политики не включает RLS автоматически.

    13.4. Проверка текущей сессии и соединения¶

    SELECT session_user, current_user,
       current_setting('search_path') AS search_path,
       current_setting('row_security') AS row_security,
       current_setting('app.tenant_id', true) AS tenant_id;

SELECT a.pid, a.application_name, a.client_addr,
       a.usename, s.ssl, s.version
FROM pg_stat_activity a
LEFT JOIN pg_stat_ssl s USING (pid)
WHERE a.pid = pg_backend_pid();

    Эти запросы позволяют увидеть, какой эффективный субъект работает в момент операции и сохранился ли неожиданный tenant-контекст в текущей транзакции. Но они не доказывают проверку SSL-сертификата на стороне клиента, корректность JWT или отсутствие SQL injection. Эти гарантии проверяются в других слоях.

    13.5. Диагностика SECURITY DEFINER¶

    SELECT n.nspname || '.' || p.proname AS function_name,
       pg_get_userbyid(p.proowner) AS owner_name,
       p.prosecdef, p.proconfig
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE p.prosecdef
ORDER BY 1;

    Для найденных функций проверяем сигнатуры, pg_get_functiondef(p.oid), search_path, grants EXECUTE и упоминания недоверенных схем или динамического SQL. Аудит следует проводить как отдельную инженерную операцию, с проверкой поведения функции под низкопривилегированной ролью.

    13.6. Какие симптомы искать под нагрузкой¶

    Симптом Возможная причина Как подтвердить
    permission denied for schema Нет USAGE has_schema_privilege
    permission denied for table Нет объектного GRANT has_table_privilege, членство
    SELECT возвращает 0 строк RLS default-deny / некорректный tenant pg_policies, запуск под app role
    new row violates row-level security policy WITH CHECK отвергает INSERT/UPDATE Проверка старого/нового tenant, policy
    Роль видит все строки Владелец, BYPASSRLS, permissive USING(true) pg_roles, pg_class, pg_policies
    Утечка через API при отсутствии SQL-фильтра RLS выключена, неверная роль, policy Behavior tests на разных арендаторах
    После миграции появился permission denied Default ACL для другого создателя pg_default_acl, owner созданной таблицы
    Рост p99 SELECT на RLS-таблице Дорогой policy predicate / изменение плана EXPLAIN (ANALYZE, BUFFERS) под app role

    В реальной системе нельзя показывать секреты или пользовательские данные в диагностических логах. Достаточно технической информации о субъекте, операции, праве и результате проверки. Ошибки доступа тоже нельзя бездумно транслировать клиенту с внутренним текстом SQL.

    13.7. Почему EXPLAIN надо запускать под настоящей ролью приложения¶

    EXPLAIN от имени владельца таблицы может дать другой план и другое множество строк, чем запрос runtime-роли под RLS. Для анализа стоимости политики нужно воспроизвести как минимум effective role, search_path, релевантный tenant-контекст, параметры запроса и статистику. Один и тот же SQL с разной политикой или разным tenant может иметь разные фактические затраты.

    В эксперименте отдельно измеряем: количество возвращенных строк, время выполнения, число heap/shared blocks, вызовы функций в политике и пиковые задержки. Если политика читает другую таблицу на каждую строку, эта работа может стать серьезной проблемой при больших объемах данных. Оптимизацию проводим, сохраняя исходную семантику безопасности.

    14. Сквозной эксперимент: настроили, сломали, диагностировали, исправили¶

    Это демонстрация к лекции на изолированной БД. Она намеренно содержит небезопасные варианты для анализа. Их нельзя копировать как production-конфигурацию.

    Этап 1. Подготовили роли и данные¶

    Создаем собственника (app_owner NOLOGIN), прикладную роль (app_runtime LOGIN), отдельно права чтения/записи, таблицу app.invoices с двумя tenant. Убедимся, что runtime не является владельцем и не имеет BYPASSRLS. Проверяем has_schema_privilege и has_table_privilege, затем выполняем тестовый SELECT от имени app_runtime.

    Этап 2. Забыли tenant-фильтр — воспроизвели утечку¶

    При выключенном RLS запрос SELECT * FROM app.invoices возвращает счета обоих арендаторов. Мы видим, что обычный GRANT на таблицу не различает арендаторов. Это исходный дефект.

    Этап 3. Включили RLS — получили default deny¶

    ALTER TABLE app.invoices ENABLE ROW LEVEL SECURITY;
-- До добавления применимой разрешающей политики runtime не видит строки.

    Объясняем, почему «пустой результат» правильнее, чем случайная выдача всех строк. Проверяем, что администратор/владелец может при этом наблюдать иное поведение.

    Этап 4. Добавили SELECT/INSERT/UPDATE/DELETE-политики¶

    Создаем политики раздела 10 и выполняем операции под app_runtime с SET LOCAL app.tenant_id = '101'. Проверяем видимость только двух счетов, запрет INSERT в tenant 202 и попытку переместить строку через UPDATE. Отдельно фиксируем ограничения RETURNING и ON CONFLICT DO UPDATE для прикладной формы запроса.

    Этап 5. Намеренно создали ошибочную permissive-политику¶

    Добавляем USING (true) и получаем неожиданно широкую видимость. Удаляем ошибочную политику, повторно проверяем, что результирующий OR/AND действительно соответствует требованиям. Демонстрируем, почему имена политик не являются моделью безопасности.

    Этап 6. Проверили обход через владельца¶

    Запускаем запрос под app_owner: до FORCE ROW LEVEL SECURITY владелец обычно видит строки всех арендаторов. После FORCE владелец начинает подчиняться применимым политикам (для этой роли может действовать default deny). BYPASSRLS и superuser не подчиняются FORCE. Возвращаем административные настройки на требуемое состояние.

    Этап 7. Проверили SECURITY DEFINER¶

    Создаем функцию с повышенными привилегиями, которая принимает произвольный tenant, и доказываем, что даже безопасный search_path не спасает от неправильной проверки бизнес-субъекта. Затем исправляем API функции или убираем привилегированную функцию, если она не требуется.

    Этап 8. Имитировали переиспользование соединения¶

    Внутри транзакции устанавливаем SET LOCAL, выполняем запрос и завершаем транзакцию. Следующая транзакция не должна наследовать значение. Для сравнения на учебном стенде можно использовать session-level SET и наблюдать опасное сохранение значения на соединении, когда приложение не сбрасывает его перед следующим запросом. В production всегда используем проверенный tenant-контекст и явную транзакционную границу.

    Этап 9. Диагностировали под нагрузкой¶

    Создаем много строк двух арендаторов, сравниваем выполнение одного и того же SELECT под прикладной ролью с корректной политикой и с дорогостоящей дополнительной проверкой. Снимаем EXPLAIN (ANALYZE, BUFFERS). Показываем, что проверка безопасности имеет цену, а оптимизация обязана сохранять инварианты доступа.

    Этап 10. Зафиксировали приемочные условия¶

    Нужно доказать запрет для чужого tenant, включая SELECT, INSERT, UPDATE и DELETE. Нужны тесты отсутствия контекста, попытки подмены контекста, обхода через владельца и функций, а также регрессионные тесты новых миграций. Только тест «SELECT вернул ожидаемую строку» ничего не говорит об утечке чужих строк.

    15. Что студент должен запомнить¶

    1. HBA, TLS, пароль, CONNECT, объектные привилегии и RLS — независимые уровни. Успех на одном из них не открывает другие.
    2. Прикладная роль не должна владеть таблицами или иметь административные атрибуты. Владельца, мигратора и runtime разделяем по полномочиям.
    3. search_path участвует в безопасности. Привилегированные функции требуют контроля пути поиска, владельца, входных параметров и EXECUTE.
    4. RLS фильтрует строки, но не устанавливает личность HTTP-пользователя. Контекст арендатора должен поступать из доверенной проверки, а подменяемый GUC не защитит от произвольного SQL под той же ролью.
    5. USING проверяет доступность существующих строк, WITH CHECK — новые значения. Permissive/Restrictive-политики объединяются разными логическими операциями.
    6. Владелец обычно обходит RLS, а superuser и BYPASSRLS обходят ее всегда. FORCE ROW LEVEL SECURITY изменяет положение обычного владельца, но не повышает защиту от суперпользователя.
    7. Безопасность надо проверять отрицательными тестами под реальной ролью. Проверяем запрет чужих строк, новые миграции, session state и реальное влияние политик на планы и latency.

    Дополнительный технический слой — только при необходимости¶

    Можно отдельно разобрать встраивание RLS-политик в дерево запроса при rewrite и влияние security_barrier/leakproof на reorder предикатов. Это объяснит, почему некоторые фильтры нельзя безопасно проталкивать через границу политики и откуда берется стоимость выражений RLS. Для обязательной лекции 13 этого уровня достаточно коснуться; глубокий разбор исходников PostgreSQL не требуется.
