    14. PostgreSQL Sharding & Distributed Data¶

    Курс: Production backend / PostgreSQL under the hood. Версия СУБД: PostgreSQL 18 (REL_18_STABLE). Лекция: 14.0, основная. Уровень: магистратура / backend. Статус: продолжение завершенных блоков 5–13.
    Задача лекции: понять, когда одному экземпляру PostgreSQL перестает хватать ресурсов, как разделить данные между независимыми экземплярами, что происходит с SQL, транзакциями и ограничениями целостности, и как диагностировать распределенную деградацию.

    Граница: не пересказываем устройство B-tree, MVCC, planner, WAL, локальных блокировок, backup, PgBouncer, физических и логических реплик. Их используем как известные механизмы. Citus рассматриваем как конкретную реализацию sharding, без погружения в исходники distributed executor. Согласованность смены владельца с epochs/fencing tokens — факультативная 14.1.

    Маршрут лекции: один инцидент, 15 технических тем¶

    До сегодняшнего дня у нас был один PostgreSQL, пусть даже с репликами и разделенными на партиции таблицами. Реплики помогали читать данные и переживать отказ узла. Но запись продолжала ограничиваться мощностью primary, а таблицы и индексы занимали емкость его системы хранения.

    Представим сервис с событиями клиентов: events(tenant_id, event_id, created_at, payload). Размер — десятки терабайт, скорость вставки растет, дорогие арендаторы генерируют большую часть трафика. Добавляем реплику — проблема записи никуда не исчезает. Увеличиваем машину — это помогает до определенного предела. Разделяем данные на партиции — проще удалять архивные события, но все партиции по-прежнему живут внутри одного PostgreSQL-кластера.

    Значит, следующий вопрос: какие данные должен хранить каждый сервер и кто решает, куда отправить запрос? Это и есть задача шардинга (sharding).

    Сначала кажется, что достаточно hash(tenant_id) % N. Эта формула решает только начальное размещение. После нее нам еще придется решать вопросы SQL без tenant_id, горячих клиентов, глобальной уникальности, нескольких транзакций, переноса данных, временно неработающих узлов и согласования карты шардов. В этом и состоит основное содержание лекции.

    Сквозная предметная область: арендаторы (tenants), заказы (orders), платежи (payments), события (events). В примерах разные схемы развертывания сознательно отделены: обычный PostgreSQL, прикладной маршрутизатор и Citus. Концептуальный SQL для нескольких независимых серверов не выдается за встроенный синтаксис PostgreSQL 18.

    Термины, без которых дальше не разобраться¶

    • Shard — физически или логически выделенная часть набора данных, имеющая собственное размещение и управляемая правилами маршрутизации.
    • Shard key (ключ шардирования) — значение, по которому определяется shard для конкретной строки или операции.
    • Placement — размещение шарда на физическом worker-узле. Один shard может иметь копии, но количество копий и их гарантии зависят от реализации.
    • Router / coordinator — компонент, определяющий участников запроса и место выполнения. В прикладном шардинге эту роль несет backend; в Citus — соответствующие компоненты расширения.
    • Colocation — совместное размещение связанных данных так, чтобы нужные операции можно было выполнять локально.
    • Fan-out — число независимых узлов или шардов, к которым обращается один логический запрос.
    • Rebalancing / resharding — перемещение размещений и/или изменение разбиения данных при изменении топологии и нагрузки.
    • Scatter-gather — разослать запрос множеству узлов, затем собрать и объединить ответы.

    1. Когда вообще нужен sharding¶

    1.1. Восемь терабайт еще не доказывают необходимость sharding¶

    Первое плохое упрощение — «таблица большая, надо шардировать». Размер сам по себе мало говорит о производительности. Последовательное чтение больших данных может хорошо работать на одном сервере, а маленькая таблица с одним постоянно изменяемым счетчиком способна стать узким местом. Надо назвать ограниченный ресурс: емкость хранения, скорость записи, IOPS, объем RAM, CPU, время обслуживания, доступное окно восстановления или изоляция нагрузки арендаторов.

    Пусть primary способен устойчиво обрабатывать 80 000 операций записи/с при нужном p99, а приложение требует 150 000. Добавление read replica не делит эти записи между primary. Sharding допускает размещение разных операций на разных write-owning узлах. Но его стоимость — новая координация, несколько точек отказа и более сложные операции без shard key.

    1.2. Вертикальное масштабирование, репликация, партиции и шарды¶

    Механизм Что меняется Где остается узкое место
    Bigger machine CPU, RAM, storage одного узла Предел конкретной машины, стоимость, миграция
    Read replicas Дополнительные копии данных Primary по записи; задержка репликации
    Partitioning Логическая таблица разделена на отношения Обычно тот же экземпляр, shared CPU/I/O/storage
    Sharding Разные части данных на независимых write-owning узлах Cross-shard SQL, метаданные, сеть, координация

    Инженерный критерий: прежде чем шардировать, надо доказать, что проблема не решается индексом, жизненным циклом данных, устранением hot-row, оптимизацией запроса или разграничением нагрузок. После шардинга даже обычный COUNT(*) по всем данным может стать распределенной операцией.

    1.3. Что значит «независимые серверы»¶

    Один shard — не обязательно одна машина. На машине может быть несколько шардов; один логический shard может иметь реплики. Важно другое: часть данных имеет отдельную область владения записью. Если все серверы хранят полный набор записей, это репликация, а не горизонтальное распределение набора данных.

    Backend / router
  |-- tenant_id = 101 --> Shard A --> PostgreSQL worker 1
  |-- tenant_id = 202 --> Shard B --> PostgreSQL worker 2
  `-- tenant_id = 303 --> Shard C --> PostgreSQL worker 3

    Если tenant 101 генерирует 90% операций, равномерное распределение числа арендаторов не поможет. Этот неприятный сюрприз мы подробно разберем в теме 5.

    Под нагрузкой. Измеряем write TPS на каждом узле, IOPS, CPU, WAL bytes/sec, p95/p99 задержки по shard key и стоимость межузловых запросов. Результат «три узла — в три раза быстрее» никогда нельзя принимать без эксперимента.

    2. Выбор shard key: стоимость ошибки на годы вперед¶

    2.1. Один ключ определяет доступность локальных запросов¶

    Возьмем:

    CREATE TABLE orders (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    created_at timestamptz NOT NULL,
    amount numeric(14,2) NOT NULL,
    PRIMARY KEY (tenant_id, order_id)
);

    Почему ключ tenant_id выглядит привлекательным? Почти все запросы приложения адресованы одному арендатору: показать заказы, изменить заказ, получить платежи. При распределении по tenant_id все эти действия можно маршрутизировать по одному значению.

    А если распределить по order_id? Получить заказ по ID может быть дешево, но запрос «последние 100 заказов арендатора» потребует обращения к нескольким шардам. Ни один индекс на отдельном worker не спасет от неверного распределения данных для основного шаблона доступа.

    2.2. Четыре критерия ключа¶

    Кардинальность: достаточно ли разных значений, чтобы распределить нагрузку? Boolean is_active — очевидно плохой ключ. Стабильность: будет ли ключ часто меняться? Изменение shard key может требовать переноса строки между узлами. Локальность: попадают ли связанные данные и транзакции в одну область? Перекос: существуют ли значения с аномально высоким объемом записей или запросов?

    Надо изучать реальные шаблоны запросов и распределение: не только COUNT(DISTINCT tenant_id), но и GROUP BY tenant_id ORDER BY count(*) DESC, размер групп, p99 активности, соотношение чтений и записей. Ключ с хорошим равномерным распределением строк может плохо распределять CPU и I/O.

    2.3. Несколько бизнес-ключей в одной системе¶

    Сервис ищет заказ по order_id, но данные размещены по tenant_id. Тогда одного order_id недостаточно для прямой маршрутизации. Решения: передавать оба поля в API, вести отдельный каталог order_id -> tenant_id, использовать глобально кодируемый идентификатор с информацией о маршруте либо выполнять scatter-gather. У каждого решения цена: дополнительное хранилище, согласованность каталога, утечка деталей размещения или сетевой fan-out.

    Практический вывод: shard key становится частью архитектуры API и модели идентификаторов. Изменить его позже намного труднее, чем добавить B-tree индекс.

    3. Hash sharding: почему hash(key) % N сначала работает¶

    3.1. Наивное разбиение на три сервера¶

    Учебный маршрутизатор:

    shard_index = hash64(tenant_id) mod 3
0 -> worker A
1 -> worker B
2 -> worker C

    Равномерный хеш приближенно распределяет различные значения ключей. Но хеш-функция должна быть стабильной и одинаково реализованной всеми клиентами; нельзя использовать случайный process-dependent hash как постоянную карту размещения. Для реальной реализации алгоритм и его версия входят в контракт системы.

    3.2. Добавили четвертый сервер — и начались переезды¶

    Меняем mod 3 на mod 4. Для многих ключей ответ изменится. Старый worker по-прежнему хранит строки, а новый router отправляет запрос в другое место. Поэтому простая замена числа серверов без миграции данных разрушает корректность маршрутизации.

    Более управляемая модель: фиксируем пространство хеш-токенов, разбиваем его на виртуальные шарды и отдельно храним карту virtual shard -> worker. Тогда добавление worker меняет размещение части виртуальных шардов, а не формулу преобразования ключа в shard.

    hash(tenant_id) --> token range --> shard 0007 --> worker B
                               shard 0008 --> worker C
                               shard 0009 --> worker A

    Consistent hashing — одна из возможных схем минимизации перемещения ключей; она не обязательна для любого sharding. В Citus hash-distributed таблицы используют диапазоны хеш-токенов, shard placements и метаданные размещения, а не учебную формулу % число workers.

    3.3. Сколько нужно виртуальных шардов¶

    Слишком мало шардов — тяжело перемещать небольшие доли нагрузки. Слишком много — растут количество объектов, соединений, задачи планировщика, метаданные и накладные расходы обслуживания. Условный выбор 32 или 64 шардов сам по себе не является универсальной рекомендацией; важны размеры шарда, число workers, частота запросов и стоимость fan-out.

    Под нагрузкой: анализируем распределение веса шардов по storage, CPU, TPS и задержке. Вес шарда — не просто количество байтов: 5 ГБ с постоянно обновляемой строкой могут быть дороже 100 ГБ холодного архива.

    4. Range и directory sharding: когда хеш — плохой выбор¶

    4.1. Range sharding: локальность ценой перекоса¶

    Вместо хеша делим диапазоны customer_id или времени:

    [0000, 1000) -> worker A
[1000, 2000) -> worker B
[2000, 3000) -> worker C

    Достоинство: запрос по диапазону может обращаться к ограниченному числу шардов. Недостаток: монотонные новые ключи направляются в самый правый диапазон, образуя горячую точку. Дальше приходится делить диапазоны, перераспределять их и обновлять карту.

    Для событий по времени range sharding дает удобное архивирование, но все сегодняшние вставки могут упереться в один shard. Это напоминает известную проблему последней партиции, только теперь влияет на отдельный физический сервер.

    4.2. Directory sharding: явная таблица соответствий¶

    tenant_id | shard_id | placement | mapping_version
101       | 12       | worker-B  | 37
202       | 07       | worker-A  | 37

    Directory позволяет вручную переместить большого арендатора или учесть отдельные требования к региону и хранению. Но каталог становится критически важным для маршрутизации: нужна его доступность, атомарность изменений, обновление кешей и поведение при устаревшем значении.

    4.3. Гибриды и выбор по типу нагрузки¶

    Для multi-tenant SaaS часто эффективен хеш по tenant_id. Для тяжелых арендаторов — отдельные placements или специальные правила. Для time-series — комбинация распределения по устройству и временных партиций внутри шардов. Это разные оси организации: один определяет сервер, другая управляет локальными данными.

    Инженерный вывод: схема распределения — это не таблица с красивыми прямоугольниками. Это изменение цены основных запросов и операций обслуживания, которое нужно проверять на реальном распределении ключей.

    5. Data skew и hot shards: равномерное число строк ничего не гарантирует¶

    5.1. Шард на 10 ГБ может быть горячее шарда на 500 ГБ¶

    Представим 1000 арендаторов. 999 генерируют по одному запросу в секунду, один — 50 000. Hash sharding равномерно распределит ключи, но не разделит одного арендатора, если весь tenant должен жить на одном шарде. Worker с этим tenant станет узким местом.

    Три разновидности перекоса: storage skew (байты и число строк), request skew (количество операций), resource skew (CPU, IOPS, lock contention, temp files). Указывать только размеры шардов в dashboard недостаточно.

    5.2. Как считать распределение¶

    Для worker i измеряем TPS_i, CPU_i, write_i, disk_i, p99_i. При идеальном распределении входящего потока R на N одинаковых работников средняя нагрузка была бы R/N. Это лишь нижняя оценка: накладные расходы координации и неравномерность нарушают идеальную модель.

    Удобные наблюдения: max(TPS_i) / mean(TPS_i) и max(CPU_i) - min(CPU_i). Например, при TPS [800, 900, 8300] среднее 3333, а максимальный узел получает около 2.49 среднего. Похвалить систему за «три равных по размеру шарда» здесь нельзя.

    5.3. Что реально помогает¶

    Перемещение горячего tenant на менее загруженный worker; более мелкие шарды; ограничение нагрузки на арендатора; разбиение специально выбранных данных одного tenant по дополнительному признаку при готовности платить за потерю локальности; вынос тяжелой аналитики; предварительные агрегаты.

    Но не надо обещать, что resharding автоматически исправит hot row или один последовательный счетчик: если все операции требуют строго одного места сериализации, распределение этого объекта имеет фундаментальные ограничения.

    Нагрузочный симптом: растут p99 и очередь только на одном worker, хотя суммарный CPU кластера невысокий. Диагностика должна быть поключевой и поузловой.

    6. Query routing: как запрос попадает на правильный shard¶

    6.1. Point query: счастливый случай¶

    SELECT order_id, amount
FROM orders
WHERE tenant_id = 101 AND order_id = 9001;

    Шаги у прикладного маршрутизатора: извлечь tenant_id, определить виртуальный shard, найти актуальный placement, установить/получить соединение с нужным PostgreSQL, выполнить SQL, вернуть результат. Если оба ключа попадают в индекс работника — локальная часть быстрая.

    Но время запроса складывается как минимум из routing + ожидания соединения + сети + локального планирования/исполнения + возвращения результата. Даже при идеальном локальном индексе сетевые расходы остаются. В Citus распределенный планировщик может распознать router query и направить его на один shard; конкретный маршрут и режим входа в кластер зависят от конфигурации Citus.

    6.2. Почему нельзя строить маршрутизацию по SQL-тексту с регулярным выражением¶

    Запрос может содержать параметр tenant_id=$1, IN (...), JOIN, подзапрос, выражение с неочевидной семантикой. Надежная маршрутизация должна опираться на явно переданный shard key, проверенный AST/план либо официальный распределенный coordinator. Regex не гарантирует корректность при произвольном SQL.

    Для прикладного шардинга часто полезно требовать tenant_id как обязательный параметр методов репозитория. Отсутствие ключа тогда становится явным событием: отказ, обращение к каталогу или осознанный scatter-gather. Это безопаснее, чем молча отправлять запрос на случайный worker.

    6.3. Устаревшая карта размещения¶

    Вот новая ошибка: router A получил shard 7 -> worker B, router C еще держит shard 7 -> worker A. После переноса оба выполняют запросы. Если старый узел продолжает принимать запись, возможны расхождения.

    Для корректного дизайна нужны версия маршрута, контролируемое переключение, обновление кешей и отказ от записи по устаревшему размещению. Подробный протокол смены владельца и fencing оставляем 14.1. Сейчас запоминаем практическую границу: маршрутизатор — часть consistency story, а не только балансировщик TCP.

    6.4. Routing в Citus и прикладной routing — разные продукты¶

    В Citus create_distributed_table задает распределительный столбец, создаются hash shards и сохраняются метаданные размещения. Кластер принимает SQL, выбирает нужные placements и выполняет задачи. В ряде конфигураций Citus поддерживает прием запросов на worker (MX mode), поэтому жесткая учебная схема «все всегда через один coordinator» не является универсальным описанием Citus 14.x [S1, S2].

    Прикладной router не получает SQL JOIN/aggregate executor бесплатно. Он обязан сам выбрать стратегию fan-out, ошибки и согласованность. Сравнивать только миллисекунды point query без этой разницы некорректно.

    7. Scatter-gather: простой COUNT превращается в распределенный запрос¶

    7.1. WHERE без shard key¶

    SELECT count(*) FROM orders WHERE amount > 10000;

    В обычном PostgreSQL это один запрос к одному серверу. Если orders разделены по tenant_id, предикат amount > 10000 не дает информации о размещении. При общем распределенном исполнении нужно выполнить подзапрос на множестве шардов, получить частичные ответы и агрегировать их.

                  Coordinator
             /     |     \
       shard A   shard B   shard C
        COUNT     COUNT     COUNT
           \       |       /
            SUM(partial counts)

    Получение трех маленьких чисел дешево. Но локальные чтения на всех узлах могут быть дорогими и конкурировать с OLTP. Нельзя оценивать распределенный запрос только по размеру ответа.

    7.2. Агрегаты различаются по стоимости распределения¶

    Для SUM(x) можно сложить частичные суммы. Для COUNT(*) — количества. Для AVG(x) нужно переносить пару (sum, count), иначе «среднее средних» при неравных объемах данных даст неправильный результат. Для COUNT(DISTINCT customer_id) простое сложение локальных distinct обычно ошибочно: одинаковые ключи могут встречаться на нескольких шардах. Потребуется глобальная дедупликация, специальные свойства размещения или приближенная структура.

    -- Эскиз частичного результата одного worker:
SELECT SUM(amount) AS partial_sum, COUNT(*) AS partial_count
FROM orders
WHERE status = 'paid';

    Проверка точности: в лекции отличаем точные агрегаты от приблизительных; HyperLogLog и подобные структуры могут снизить передачу данных ценой контролируемой погрешности, но это отдельные инструменты.

    7.3. ORDER BY LIMIT и глобальный top-K¶

    SELECT tenant_id, order_id, amount
FROM orders
ORDER BY amount DESC, tenant_id, order_id
LIMIT 100;

    Нужно получить глобальный top-100. При подходящем полном порядке и корректной реализации можно запросить до 100 лучших кандидатов с каждого шарда и выполнить k-way merge. Но если координатор просто взял первые 100 ответов от первого worker, результат неверен. Важны полный детерминированный порядок, корректная обработка равных ключей и границы pushdown.

    7.4. Fan-out и хвостовая задержка¶

    Пусть один запрос требует ответы от N независимых узлов. Приближенно T_total ≈ max(T_1, ..., T_N) + coordination. Если каждый узел отвечает быстрее t с вероятностью F(t) и времена независимы, вероятность получить все ответы до t равна F(t)^N. Для F(t)=0.99, N=20: всего около 0.99^20 ≈ 0.818. Независимость — учебное допущение; реальные сбои и перегрузка часто коррелированы.

    Следствие: если один запрос начинает обращаться к десяткам workers, p99 может резко ухудшиться даже при неплохих локальных p99. Это одно из главных отличий распределенного SQL от локального.

    7.5. Где возникает очередь¶

    Координатор ограничен числом соединений к workers, количеством одновременных задач, CPU на слиянии результатов и сетью. Worker ограничен собственными соединениями, I/O, памятью, CPU и локальными блокировками. Рост fan-out увеличивает число внутренних задач на один клиентский SQL, поэтому увеличение числа HTTP-потоков может перегрузить БД намного раньше, чем это видно по одному локальному EXPLAIN.

    Диагностика: число задач, время каждого worker, bytes sent/received, queued vs executing tasks, скорость сети, temp files, локальный EXPLAIN для дорогих подзапросов, p99 распределенного запроса.

    8. Colocation: как сделать JOIN локальным¶

    8.1. Две таблицы и одна область владения¶

    CREATE TABLE orders (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    amount numeric(14,2) NOT NULL,
    PRIMARY KEY (tenant_id, order_id)
);
CREATE TABLE payments (
    tenant_id bigint NOT NULL,
    payment_id bigint NOT NULL,
    order_id bigint NOT NULL,
    status text NOT NULL,
    PRIMARY KEY (tenant_id, payment_id)
);

    Если оба набора данных распределены по tenant_id и соответствующие диапазоны ключей совместно размещены, то запрос:

    SELECT o.order_id, p.payment_id
FROM orders o
JOIN payments p
  ON p.tenant_id = o.tenant_id
 AND p.order_id = o.order_id
WHERE o.tenant_id = 101;

    можно выполнить на одном worker. Ключ равенства важен: совместное физическое размещение не поможет, если условия запроса не позволяют доказать соответствие групп данных.

    8.2. Зачем совместное размещение отличается от одинакового хеша¶

    Мало того, что hash(tenant_id) дает одинаковый token для обеих таблиц. Необходимо, чтобы соответствующие shard placements располагались на согласованных workers и имели совместимые границы. В Citus есть colocation groups. В простых случаях совместное размещение создается автоматически при согласованных типах ключа и количестве шардов, а при необходимости задается явно colocate_with [S3].

    -- Выполняется в Citus, после установки и настройки расширения.
SELECT create_distributed_table('orders', 'tenant_id');
SELECT create_distributed_table(
    'payments', 'tenant_id', colocate_with => 'orders'
);

    Это пример синтаксиса Citus, а не встроенный оператор PostgreSQL 18.

    8.3. Local JOIN против Cross-shard JOIN¶

    В local JOIN запрос использует обычный PostgreSQL executor на worker — его алгоритмы мы уже знаем. В cross-shard JOIN перед ним может появиться дорогое перемещение данных. Поэтому правильный shard key часто дает больший выигрыш, чем микротюнинг локального Hash Join.

    8.4. Reference tables: небольшие справочники на нескольких узлах¶

    Пусть есть справочник валют или налоговых ставок. Его можно держать на всех workers как маленькую reference table, чтобы связывать с распределенными заказами локально. Citus предоставляет create_reference_table, но согласованное изменение копий имеет свою стоимость, в ряде случаев с применением распределенного протокола фиксации [S4].

    CREATE TABLE currencies (
    code text PRIMARY KEY,
    name text NOT NULL
);
SELECT create_reference_table('currencies');

    Копировать на каждый worker миллиарды строк ради локального JOIN нельзя: reference tables хороши для небольших, сравнительно редко обновляемых данных.

    Инженерный вывод: совместное размещение — это заранее принятое решение о цене JOIN и транзакций. Если локальность не заложили в модель данных, SQL-оптимизатор не всегда сможет ее восстановить.

    9. Cross-shard операции: сеть становится частью плана¶

    9.1. JOIN без общего shard key¶

    Возьмем orders по tenant_id, а fraud_signals по device_id. Нужно соединить по device_id без ограничений по tenant. Релевантные строки могут жить на разных workers. Варианты реализации: собрать данные на coordinator, переслать меньшую таблицу на несколько workers, перегруппировать строки по join key (repartition/shuffle) или отказаться от такого запроса на горячем пути и подготовить проекцию данных.

    Ни одна стратегия не бесплатна. Разрешение repartition JOIN зависит от возможностей и настроек конкретной версии Citus; нельзя считать, что произвольный JOIN автоматически поддерживается с оптимальной стратегией.

    9.2. Считаем цену shuffle¶

    Пусть требуется переместить 10 миллионов строк по 200 байт: это примерно 2 ГБ полезной нагрузки, без overhead сериализации, протокола, индексов и промежуточных файлов. При теоретических 1 Гбит/с только передача 2 ГБ заняла бы около 16 секунд. В реальности пропускная способность ниже номинальной, и часть нагрузки распределена неравномерно.

    Если pushdown частичного агрегирования сократит поток до 50 тысяч строк по 24 байта, переносим всего около 1.2 МБ. Стоимость сокращается на несколько порядков. Вот почему распределенный план нужно читать с точки зрения движения данных, а не только локальных операторов.

    9.3. А если сделать JOIN в приложении?¶

    Это может быть оправданно для небольших множеств или заранее ограниченных ключей, но сетевая передача и согласованность никуда не исчезают. Более того, приложение берет на себя сортировку, объединение, ограничение памяти, backpressure, ошибки частичных ответов и корректность LIMIT/OFFSET.

    9.4. Pushdown не всегда возможен¶

    Функции с нестандартной семантикой, выражения, пользовательские операторы и правила группировки могут препятствовать безопасному переносу операций на worker. Конкретные допустимые операции определяет распределенный planner. Потребность в локальной обработке не является ошибкой сама по себе; проблема возникает, когда план пересылает слишком много промежуточных строк.

    Под нагрузкой: смотрим bytes shuffled, входящие/исходящие соединения, временные файлы, рабочую память, загрузку сети, количество участвующих shards, их локальные планы и асимметрию времен задач.

    10. Global constraints: почему UNIQUE внезапно перестает быть глобальным¶

    10.1. Глобальная уникальность требует глобального знания¶

    Пусть orders распределена по tenant_id. На worker A успешно вставлен (tenant_id=1, order_id=777). На worker B вставлен (tenant_id=2, order_id=777). Обе локальные таблицы могут честно соблюдать UNIQUE(order_id), потому что проверяют разные множества строк. Глобальный инвариант order_id уникален во всем кластере уже нарушен.

    Один из подходов — составной ключ, содержащий shard key. В Citus для UNIQUE/PRIMARY KEY распределенной таблицы требуется включать колонку распределения. Это дает локально проверяемую уникальность пары (tenant_id, order_id), но не глобальную уникальность order_id [S5].

    PRIMARY KEY (tenant_id, order_id)
-- Это не означает UNIQUE(order_id) во всем кластере.

    10.2. Синтаксически похожие ограничения, разные гарантии¶

    Прикладной router может выдавать globally unique ID посредством выделенных диапазонов, UUID или Snowflake-подобных идентификаторов. Но «вероятность коллизии мала» не эквивалентна транзакционной проверке уникальности в едином индексе. Другой вариант — отдельный каталог уникальных ключей с атомарным резервированием; теперь он сам становится инфраструктурным компонентом с задержками и точкой конкуренции.

    10.3. Foreign keys между шардами¶

    Транзакционная проверка FK обычно должна доказать наличие родительской строки. Если она в другом шарде, нужна межузловая проверка и согласование. В Citus поддерживаются определенные комбинации FK — например, между colocated distributed tables при включении ключа распределения или от distributed table к reference table. Произвольный глобальный FK между любыми двумя таблицами не предоставляется автоматически [S3, S5].

    10.4. Вторичные индексы остаются локальными¶

    Индекс CREATE INDEX ... ON orders(created_at) на распределенной таблице в Citus создает индексы соответствующих shards. Запрос по created_at без tenant_id все равно может потребовать fan-out. Локальный B-tree не содержит карты всех строк на других серверах.

    Инженерный вывод: при проектировании идентификаторов нужно различать ID, удобный приложению, и физическую возможность централизованно проверить инвариант.

    11. Distributed transactions: один COMMIT больше не обязательно означает один сервер¶

    11.1. Локальная операция все еще обычная транзакция PostgreSQL¶

    Если списание и запись платежа для одного tenant_id находятся на одном worker, локальная транзакция остается в границах одного PostgreSQL. Нужны уже известные гарантии MVCC, блокировок и WAL. Sharding не обязан усложнять все операции; грамотная colocation именно поэтому важна.

    Но теперь задача: перевести средства со счета арендатора 101 на счет арендатора 202, которые живут на разных workers. Локальный COMMIT на A не способен атомарно зафиксировать COMMIT на B. Отсюда появляется новая стоимость распределенного взаимодействия.

    11.2. Почему два отдельных COMMIT не дают атомарности¶

    App            Worker A                  Worker B
 |    UPDATE debit; COMMIT OK                 |
 |------------------------------------------>|
 |             network timeout / crash       |
 |                        UPDATE credit ?    |

    Если деньги списаны на A, а B недоступен, система имеет частичный результат. «Повторим оба запроса» может списать средства повторно. «Отменим A» может быть невозможно после локального COMMIT. Для ряда бизнес-процессов применяют саги и компенсирующие операции, но они дают другую семантику, чем единая атомарная транзакция.

    11.3. Two-phase commit (2PC) в общей модели¶

    Двухфазная фиксация использует внешнего координатора: сначала все участники prepare, затем координатор принимает решение commit или rollback и доводит его до участников.

    Coordinator                PostgreSQL A                PostgreSQL B
    |---- prepare -------------->|                          |
    |---- prepare ------------------------------------------>|
    |<--- prepared --------------|                          |
    |<--- prepared ------------------------------------------|
    |==== durable global decision: COMMIT ===================|
    |---- commit prepared ------>|                          |
    |---- commit prepared ---------------------------------->|

    В PostgreSQL существуют PREPARE TRANSACTION, COMMIT PREPARED, ROLLBACK PREPARED; это механизм для внешнего менеджера распределенных транзакций, а не совет писать ручные PREPARE в бизнес-коде [S6]. Подготовленная транзакция продолжает удерживать блокировки. При потере координатора может остаться in-doubt transaction: участник подготовился, но решение еще не получил. Транзакция висит до корректного завершения, мешает обслуживанию и может удерживать старые XID.

    11.4. Цена распределенной атомарности¶

    2PC добавляет сетевые обращения, устойчивое хранение решения координатора, удержание ресурсов нескольких workers и необходимость восстановить состояние после сбоев. При отказах он способен уменьшить доступность записи. Это не «магическая галочка, которая делает сеть надежной». Придется отдельно выбирать, какие операции действительно требуют глобальной атомарности.

    11.5. Как это выглядит в Citus — без обобщений на любой SQL¶

    Citus поддерживает операции над несколькими шардами и предлагает разные режимы фиксации. Для некоторых multi-shard UPDATE/DELETE по документации типичным поведением является однофазный протокол; для повышения гарантии можно использовать citus.multi_shard_commit_protocol = '2pc' в поддерживаемой конфигурации. Нельзя утверждать, что каждый распределенный запрос Citus по умолчанию имеет эквивалент полноценной общей 2PC-транзакции [S7].

    -- Пример настройки Citus для подходящих multi-shard операций;
-- проверять в документации и тестах применяемой версии.
SET citus.multi_shard_commit_protocol = '2pc';

    Инженерный вывод: основное средство масштабируемости — локальность транзакций. Глобальная атомарность возможна при определенных протоколах, но ее необходимо сознательно приобретать ценой задержки и доступности.

    12. Resharding: как перенести данные, пока система продолжает писать¶

    12.1. Почему COPY недостаточно¶

    Данные сейчас на worker A. Пока мы копируем десятки гигабайт на B, клиент продолжает делать INSERT/UPDATE/DELETE. На момент завершения копирования B уже отстает. Если просто переключить router, последние изменения будут потеряны из нового placement.

    Нужен протокол согласования начального снимка с потоком изменений, а затем короткий этап смены владельца.

    12.2. Протокол online move: логическая модель¶

    1. Выбрать source placement A и target B, проверить совместимость схемы и необходимость REPLICA IDENTITY.
    2. Создать начальную согласованную копию данных на B.
    3. Передавать изменения, которые происходят на A во время копирования; B применяет их в правильном порядке.
    4. Дождаться допустимой границы отставания и создать согласованное окно переключения.
    5. Остановить или ограничить записи в старый placement на время финальной синхронизации.
    6. Атомарно с точки зрения системы размещения изменить активный маршрут shard -> B.
    7. Проверить, что старый маршрут больше не принимает новые записи; завершить очистку старой копии после проверки.

    Это концептуальная модель. Конкретный протокол и гарантии зависят от платформы. В Citus online rebalance может использовать logical replication, а во время изменения metadata применять короткую блокировку записи. При отсутствии подходящих условий Citus может перейти к copy с блокировкой записи [S8].

    12.3. Шард и его placement — это разные объекты¶

    Увеличение числа workers может означать просто placement(shard 7): A -> B, без изменения самого диапазона ключей шарда. Изменение числа шардов (split/merge/repartition) — более сильная операция: меняется граница набора данных, которую обслуживает каждый shard, и может измениться маршрут ключей. Называть оба процесса одинаковым словом resharding в разговоре можно, но в проектной документации следует различать rebalance placements и repartition данных.

    12.4. Цена переноса¶

    Предположим, переносим shard объемом 250 ГБ по каналу с устойчивой полезной скоростью 150 МБ/с. Только начальное копирование занимает примерно 28 минут (250 * 1024 / 150 / 60), без учета snapshot, индексов, репликации новых изменений и проверок. Если source генерирует изменения со скоростью, близкой к скорости их передачи и применения, catch-up затянется или не завершится без изменения условий нагрузки.

    Обязательно измеряем: initial copy rate, change generation rate, apply rate, lag, write blocking window, дополнительный WAL, свободное место target и обратное влияние на живые запросы.

    12.5. Что делать, если перенос оборвался¶

    Нужно знать, кто авторитетен после сбоя на каждой фазе. До переключения обычно authoritative source — A; после корректного cutover — B. Недостаточно просто увидеть таблицы с одинаковыми именами на двух серверах. Система должна хранить подтвержденный статус операции и не допускать неоднозначного назначения владельца.

    Граница углубления: точные epochs, fencing tokens, проверка устаревшей маршрутизации и формальные свойства safe cutover — лекция 14.1. Здесь достаточно понимать неизбежные фазы и стоимость.

    13. Метаданные размещения: карта — часть доступности данных¶

    13.1. Почему router должен доверять карте¶

    Карта содержит shard_id, диапазон токенов, активные placements, статус перемещения и иногда версию схемы. Если она недоступна, router может не знать, куда отправить запрос. Если она устарела, запрос может быть ошибочно направлен на прежний узел.

    Значит, metadata service сам требует стратегии доступности и согласованности. Кеш метаданных снижает latency, но добавляет invalidation, TTL, версионирование и поведение при сетевых разделениях.

    13.2. Что хранит Citus¶

    Citus предоставляет собственные служебные каталоги размещения, например pg_dist_partition, pg_dist_shard, pg_dist_placement, pg_dist_node, pg_dist_colocation (состав и доступность представлений зависят от версии и режима). Их задача — знать, какие логические отношения и shard ranges существуют и на каких workers размещены физические объекты [S1, S3].

    -- Citus: просмотр размещений и размеров в поддерживаемой версии.
SELECT * FROM citus_shards LIMIT 20;

    На обычном PostgreSQL без расширения такой view отсутствует. Прямое изменение служебных таблиц Citus вручную недопустимо как универсальная процедура управления: используем документированные функции управления топологией.

    13.3. Как может сломаться routing cache¶

    Три стадии: приложение кеширует карту версии 7; shard 12 перемещен на worker C и карта стала версией 8; часть экземпляров продолжает обращаться к B. Если B не отвергает устаревшие записи, получаем риск split-brain по отдельному shard. Если отвергает — получаем ошибки и необходимость обновить маршрут.

    Инженерный вывод: cache hit в routing не является гарантией корректности. Версия карты и реакция на invalid placement важнее нескольких микросекунд маршрутизации.

    14. Partial failures: упал один worker, а клиент видит один SQL¶

    14.1. Как по-разному отказывает распределенный запрос¶

    • До выполнения на worker: запрос может не выполнить изменений; retry может быть допустим, если точно известна стадия.
    • После выполнения, но до ответа: исход может быть неизвестен; timeout нельзя переводить в «не выполнилось».
    • После локального COMMIT на части workers: если не было гарантирующего атомарность протокола, возможен частичный результат.
    • Во время resharding: нужно определить текущего владельца и фазу переноса.
    • При потере coordinator: ongoing multi-shard query может быть прерван, при этом судьбу удаленных транзакций надо выяснять отдельно.

    14.2. Идемпотентность и неопределенный результат¶

    Пример: заказ помечен как оплаченный, подтверждение клиенту потерялось. Повторное действие без бизнес-идентификатора операции может породить дублирование. Локальная уникальность idempotency key помогает лишь в пределах правильной области владения и атомарной транзакции. При переходе между шардами карта ключей и операция должны согласованно переехать.

    -- Упрощенный локальный фрагмент для одного shard;
-- универсальную cross-shard гарантию он не создает.
CREATE TABLE payment_requests (
    tenant_id bigint NOT NULL,
    request_id uuid NOT NULL,
    payment_id bigint NOT NULL,
    PRIMARY KEY (tenant_id, request_id)
);

    После timeout клиент читает состояние операции по (tenant_id, request_id) у актуального владельца, а не случайно повторяет побочный эффект. Если операция взаимодействует с внешними системами, могут потребоваться отдельные протоколы согласования.

    14.3. Почему HA одного shard не решает глобальную доступность¶

    У каждого shard могут быть физические реплики. Но глобальный запрос может зависеть от 20 шардов. Недоступность одного необходимого shard делает полный ответ невозможным или требует оговоренной деградации. Replication улучшает доступность размещения конкретного shard, но не отменяет fan-out и частичных ошибок.

    Политика ответа должна быть явной: полный отказ, частичный результат с указанием неполноты, устаревший кеш либо отложенная аналитика. Нельзя молча возвращать COUNT=900 как полный, если один shard не ответил.

    14.4. Связь с согласованностью¶

    При сетевом разделении приоритеты могут конфликтовать: не все узлы доступны, но система обязана исключить расходящиеся владельцы. В 14.0 достаточно практического тезиса: при угрозе двойной записи корректная система может временно отказать в записи. Подробный разбор fencing и лидерских поколений — факультативная 14.1, без повторения HA/Patroni из 10.1.

    15. Production diagnostics: ищем медленный shard, а не «медленный PostgreSQL»¶

    15.1. Четыре слоя наблюдения¶

    1. Приложение: latency операции, shard key, tenant ID (в безопасной и допустимой форме), тип маршрута, retries, idempotency outcome.
    2. Маршрутизатор/coordinator: fan-out, число задач, длительность routing, очереди, список placements, время merge и число перенесенных байтов.
    3. Worker: локальные планы, CPU, I/O, WAL, блокировки, connection pool, temporary files, ошибки.
    4. Топология: placement map, версия, миграция, lag, недоступные shards, скорость ребалансировки.

    Только один pg_stat_activity на coordinator не дает полной картины нагрузки workers. Диагностика должна сохранять связь «один бизнес-запрос → распределенные задачи → конкретные shard placements».

    15.2. Три конкретных диагноза¶

    А. Local hot shard. Глобальный CPU 30%, worker 2 — 95%, p99 запросов tenant 101 растет. Причина — request skew или локальная конкуренция. Исправление может состоять в перемещении placement, лимитировании арендатора или изменении модели ключа, но не в увеличении числа координаторов.

    Б. Cross-shard fan-out. Каждый worker выполняет часть за 40 мс, итоговый запрос — 1.3 с. Смотрим время ожидания соединений, число tasks, сетевые задержки и merge. Возможно, запрос требует отсутствующего shard key, а нагрузка на coordinator стала главным ограничением.

    В. Resharding-induced I/O. Во время переноса placement у worker растут I/O и WAL, при этом p95 INSERT ухудшается. Проверяем copy/apply rate, ограничение фоновой нагрузки и окно cutover. Нельзя диагностировать только локальный SQL-план.

    15.3. Citus: что смотреть в первую очередь¶

    -- Исполнять на Citus; точный набор столбцов зависит от версии.
SELECT * FROM citus_shards LIMIT 10;

-- Распределенный план: смотреть Task Count, placements,
-- удаленные/local планы и объем работы.
EXPLAIN (VERBOSE, COSTS OFF)
SELECT tenant_id, count(*)
FROM orders
WHERE tenant_id = 101
GROUP BY tenant_id;

    Для анализа query routing отдельно меняем наличие условия на tenant_id. Для объективных замеров сравниваем не один случайный запуск, а серию прогонов с одинаковым набором данных и нагрузкой. Смотрим latency p50/p95/p99, network bytes, worker CPU, I/O и число участвующих tasks. Детали форматов конкретного distributed EXPLAIN зависят от Citus [S2, S9].

    15.4. Capacity planning и сложность границ масштабирования¶

    Пусть средняя нагрузка одного shard — r, физический worker устойчиво держит C операций/с. Наивная оценка количества workers ceil(total_r/C) игнорирует перекос, ретраи, background movement, периоды отказов и cross-shard операции. Для production нужны резерв мощности и тестирование сценария «минус один worker».

    Если кластер теряет узел во время пика, нагрузка не обязана равномерно перераспределиться. Оставшиеся workers могут получить hot placements и значительный поток восстановления. Поэтому capacity planning обязан включать деградационные сценарии, а не только красивый steady state.

    Сквозной эксперимент: расширяем три сервера, затем специально ухудшаем модель¶

    Эксперимент предполагает изолированную учебную инфраструктуру с несколькими PostgreSQL 18 и совместимой версией Citus. Для произвольного кластера Citus нужны подготовленные роли, серверы, сеть и установленное на всех узлах расширение. Ниже показана логика, а не универсальный one-command deploy.

    Шаг A. Создаем распределенную модель с правильным ключом¶

    CREATE EXTENSION IF NOT EXISTS citus;

CREATE TABLE orders (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    amount numeric(14,2) NOT NULL,
    PRIMARY KEY (tenant_id, order_id)
);

CREATE TABLE payments (
    tenant_id bigint NOT NULL,
    payment_id bigint NOT NULL,
    order_id bigint NOT NULL,
    state text NOT NULL,
    PRIMARY KEY (tenant_id, payment_id)
);

SELECT create_distributed_table('orders', 'tenant_id');
SELECT create_distributed_table('payments', 'tenant_id', colocate_with => 'orders');

    Проверяем single-tenant запрос и JOIN по tenant_id, записываем число задач. Все сравнения проводим после прогрева и на одинаковом объеме данных. При отсутствии citus_add_node()/настроенной топологии пример может остаться одноузловым; для эксперимента нужны реальные workers.

    Шаг B. Убираем ключ из фильтра¶

    EXPLAIN (VERBOSE)
SELECT count(*) FROM orders WHERE amount > 5000;

    Сравниваем с WHERE tenant_id = 101, проверяем fan-out. Вопрос не в том, что COUNT(*) «всегда дорогой», а в том, сколько узлов пришлось привлечь и какую работу выполнить на каждом.

    Шаг C. Создаем hot tenant¶

    Загружаем существенно больше операций одного tenant_id и измеряем перераспределение CPU, I/O и p99. Затем пробуем перенести размещение соответствующего шарда на другой worker, фиксируем стоимость операции и влияние на запросы.

    Шаг D. Отказываем одному worker¶

    Проверяем поведение point query по оставшимся shard placements и глобального scatter-gather. Не делаем вид, что пропущенный shard можно незаметно исключить из полного ответа. Для корректного результата нужны все обязательные участники либо заранее определенная деградация.

    Шаг E. Неопределенный результат записи¶

    Выполняем операцию с внешним request_id, разрываем клиентское соединение в неопределенный момент, затем читаем сохраненное состояние по ключу операции. Показываем, что timeout не равен ROLLBACK. Для распределенных операций дополнительно фиксируем, какие узлы успели подтвердить свой этап и какой протокол применялся.

    Разбор ошибок проектирования: что запомнить¶

    1. Sharding масштабирует независимые части данных, а не любой SQL. Общие JOIN, глобальные ограничения и массовые сканы создают сетевую стоимость.
    2. Shard key определяет локальность запросов и транзакций. Это долгосрочное решение об архитектуре API и идентификаторов.
    3. Равные размеры шардов не гарантируют равной нагрузки. Анализируем traffic skew, resource skew и hot tenants.
    4. Colocation снижает стоимость JOIN, если условия запроса сохраняют связь по ключу распределения. Наличие одинаковых по названию колонок недостаточно.
    5. Cross-shard COMMIT требует явно понятных гарантий. Несколько локальных COMMIT не образуют автоматическую атомарную операцию.
    6. Resharding — перенос данных плюс согласованная смена владельца. Копия на target еще не означает безопасный cutover.
    7. Partial failure — нормальное рабочее состояние распределенной системы. Корректность полного результата и идемпотентность важнее оптимистичной повторной попытки.
    8. Диагностировать нужно распределенный путь целиком. Локальный EXPLAIN не показывает сетевое перемещение, fan-out и задержку самых медленных workers.

    Где остановимся и куда можно копнуть глубже¶

    Содержание 14.0 заканчивается на понятной рабочей модели: данные размещаются по ключу, SQL разбивается на локальные и распределенные операции, стоимость определяется локальностью, сетью и согласованностью. Внутренности самого Citus executor, детальный two-phase coordinator и реализация распределенного блокирования сюда не включаются.

    Следующий согласованный факультативный слой — 14.1. Distributed Ownership, Failover & Resharding Consistency. Там разбираем epochs, fencing tokens, stale routing, момент безопасного cutover и инварианты «только один владелец принимает запись». Он закроет вопрос: почему система не потеряет подтвержденное изменение, даже если во время переноса шарда произошли отказ сети и повторные запросы? Это полезно именно потому, что мы уже разобрали общую операцию resharding и теперь можем проверять ее корректность на уровне распределенного протокола.
