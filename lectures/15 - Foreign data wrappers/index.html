    15.0. PostgreSQL Foreign Data Wrappers¶

    Блок 15. Факультативная лекция. PostgreSQL 18–19; поведение postgres_fdw сверено с официальной документацией по состоянию на 21 ноября 2026 года. Примеры ориентированы на PostgreSQL 18 и также применимы к PostgreSQL 19, если отдельно не оговорено обратное.

    Технический фокус: postgres_fdw, foreign tables, pushdown, удаленные JOIN, стоимость сетевого обмена, транзакции, диагностика. Необходимый контекст: обычный план запроса PostgreSQL, индексы, MVCC, уровни изоляции и EXPLAIN.

    1. Зачем вообще тянуть одну базу в другую?¶

    Представим систему с двумя PostgreSQL. В одной живут заказы и клиенты, во второй формируются отчеты. Аналитикам нужно собрать отчет: выбрать оплаченные заказы, соединить их с клиентами, посчитать суммы по регионам. Из приложения это решается привычно: подключиться к двум базам, прочитать данные, соединить результаты в памяти.

    А теперь вопрос: кто будет выбирать план JOIN, где фильтровать миллион строк и кто отвечает за передачу данных по сети? Приложение получает еще один слой кода и ответственности. Кажется заманчивым выполнить обычный SQL в базе отчетности, будто удаленная таблица находится рядом с локальной.

    PostgreSQL предоставляет механизм Foreign Data Wrapper (FDW) — подключаемый модуль, через который планировщик и исполнитель PostgreSQL обращаются к внешнему источнику данных. Он основан на идеях SQL/MED (Management of External Data). Для другого PostgreSQL есть штатное расширение postgres_fdw.

      Клиент / отчетный сервис
           |
           | SELECT ... FROM fdw.orders
           v
   PostgreSQL A (локальный)
   parser -> planner -> executor
                |
                | postgres_fdw / libpq
                | сеть, отдельное соединение
                v
   PostgreSQL B (удаленный)
   SQL -> planner -> executor
                |
                v
         таблицы + индексы

    Плохая модель звучит так: «FDW делает удаленную таблицу локальной». В SQL эта иллюзия часто работает. На уровне выполнения физическая граница никуда не исчезла: каждый отправленный запрос, возвращенная строка, открытое соединение и удаленная транзакция имеют цену.

    Главный инженерный вопрос лекции: какую работу выполнит PostgreSQL B, а какую PostgreSQL A? Именно это определяет, вернем мы по сети десять агрегированных строк или сто тысяч исходных.

    2. Четыре объекта, с которых все начинается¶

    У FDW есть конкретная модель объектов:

    1. Wrapper — реализация протокола работы с источником. В нашем случае postgres_fdw использует PostgreSQL-протокол через libpq.
    2. Foreign server — запись в локальном каталоге о логическом удаленном сервере: адрес, порт, имя базы и дополнительные параметры. Это конфигурационный объект, а не созданный экземпляр PostgreSQL.
    3. User mapping — соответствие локальной роли и учетных данных для удаленного сервера. Благодаря ему SELECT одного локального пользователя выполняется от имени определенной удаленной роли.
    4. Foreign table — локальное определение колонок и указание, какая таблица или представление существует на удаленной стороне. Собственного хранилища строк у foreign table нет.

    Не путайте foreign table с foreign key. Внешний ключ проверяет ссылочную целостность. Foreign table сообщает, откуда получать строки.

    -- Выполняется в ЛОКАЛЬНОЙ базе.
CREATE EXTENSION IF NOT EXISTS postgres_fdw;

CREATE SERVER sales_remote
  FOREIGN DATA WRAPPER postgres_fdw
  OPTIONS (
    host 'remote',
    port '5432',
    dbname 'appdb',
    application_name 'fdw_lecture'
  );

-- Учетные данные ниже только для изолированного учебного стенда.
-- В production используйте отдельную роль с минимальными правами.
CREATE USER MAPPING FOR lab
  SERVER sales_remote
  OPTIONS (user 'lab', password 'labpass');

CREATE SCHEMA fdw;

CREATE FOREIGN TABLE fdw.orders (
  id bigint,
  customer_id bigint,
  created_at timestamptz,
  amount numeric(12, 2),
  status text
)
  SERVER sales_remote
  OPTIONS (schema_name 'core', table_name 'orders');

    Здесь есть тонкость: локальная foreign table — описание контракта, а не автоматическая копия удаленного DDL. Типы, имена колонок и правила сортировки должны совпадать по смыслу. Иначе можно получить некорректную фильтрацию или сравнение, особенно для строковых типов и COLLATE.

    Вместо ручного объявления обычно удобнее:

    IMPORT FOREIGN SCHEMA core
  LIMIT TO (orders, customers)
  FROM SERVER sales_remote
  INTO fdw;

    Эта команда импортирует описания таблиц. Она не переносит содержимое. В практикуме ниже используется именно IMPORT FOREIGN SCHEMA; вручную созданную fdw.orders перед импортом создавать не нужно.

    Модель после блока: foreign table хранит метаданные; при чтении данных PostgreSQL будет обращаться через FDW к удаленному источнику. Наличие таблицы в локальном каталоге не означает наличие ее строк на локальном диске.

    3. Что реально происходит с SELECT из foreign table¶

    Начнем с одного запроса:

    SELECT id, amount
FROM fdw.orders
WHERE status = 'PAID'
ORDER BY id
LIMIT 10;

    В обычном PostgreSQL планировщик выбирает, например, Seq Scan или Index Scan. Но локальный сервер не владеет страницами удаленной таблицы и не может напрямую прочитать удаленный B-tree. Как он построит план?

    Для foreign table планировщик вызывает интерфейс FDW — набор callback-функций, предоставляемых модулем. На уровне API PostgreSQL ключевые этапы выглядят так:

    Локальный SQL
   |
   v
Planner
   | GetForeignRelSize   -> оценить размер/кардинальность
   | GetForeignPaths     -> предложить варианты доступа и их стоимость
   | GetForeignJoinPaths -> предложить удаленный JOIN, если допустимо
   | GetForeignUpperPaths-> предложить удаленную агрегацию/сортировку
   | GetForeignPlan      -> сформировать ForeignScan
   v
Executor
   | BeginForeignScan    -> подготовить удаленное выполнение
   | IterateForeignScan  -> получать строки
   | EndForeignScan      -> завершить scan
   v
Результат локального SQL

    Это интерфейс расширения PostgreSQL, а не обещание конкретного количества сетевых запросов. postgres_fdw реализует его своими алгоритмами и использует отдельное подключение к удаленному PostgreSQL.

    На удаленной стороне тоже работает полноценный планировщик: он решает, использовать ли индекс, сканирование таблицы, сортировку, Hash Join. Локальный сервер выбирает сколько работы отправить наружу; удаленный — как выполнить присланный SQL.

    Вот где появляется два уровня планирования. Локальный EXPLAIN и удаленный EXPLAIN отвечают на разные вопросы.

    4. Pushdown: вынести вычисление туда, где лежат строки¶

    Pushdown — перенос операции из локального плана на удаленный сервер. Начнем с самого полезного: фильтрации и выбора колонок.

    4.1. Фильтр и проекция¶

    EXPLAIN (VERBOSE, COSTS OFF)
SELECT id, amount
FROM fdw.orders
WHERE status = 'PAID';

    В типичном плане мы ожидаем Foreign Scan и в нем строку вида:

    Foreign Scan on fdw.orders
  Output: id, amount
  Remote SQL: SELECT id, amount
              FROM core.orders
              WHERE ((status = 'PAID'::text))

    Это схематический пример плана: буквальное SQL-форматирование, алиасы, типовые приведения и положение фильтров зависят от версии и конкретного плана. Критерий один: предикат находится в Remote SQL.

    Теперь три варианта:

    План Удаленная работа Что едет по сети
    Без pushdown Читать все строки Много строк, иногда много колонок
    Pushdown WHERE Отфильтровать строки Только подходящие строки
    Pushdown WHERE и проекции Отфильтровать и выбрать поля Подходящие строки и нужные колонки

    Простой фильтр status = 'PAID' обычно безопасно передается. Для выражений с функциями правила жестче: по умолчанию postgres_fdw считает пригодными для отправки встроенные операции и функции PostgreSQL с подходящей семантикой, в частности IMMUTABLE. IMMUTABLE означает: при одинаковых аргументах функция должна возвращать одинаковое значение независимо от изменяемого состояния базы и окружения.

    Почему так осторожно? Представьте локальную пользовательскую функцию с доступом к данным локальной базы. На удаленной стороне ее может не быть. А если есть, она может работать иначе. Отправить такую функцию «для ускорения» означало бы незаметно изменить семантику запроса.

    4.2. Сейчас специально сломаем pushdown¶

    Следующий код намеренно создает условие, которое нельзя безопасно отправить через стандартный postgres_fdw. Функция PL/pgSQL выполняется локально:

    CREATE SCHEMA IF NOT EXISTS reporting;

CREATE OR REPLACE FUNCTION reporting.is_paid(value text)
RETURNS boolean
LANGUAGE plpgsql VOLATILE
AS $$
BEGIN
  RETURN value = 'PAID';
END;
$$;

EXPLAIN (ANALYZE, VERBOSE, BUFFERS)
SELECT id, amount
FROM fdw.orders
WHERE reporting.is_paid(status);

    В плане надо искать Filter: reporting.is_paid(...) на локальной стороне и отсутствие этого условия в Remote SQL. Чтобы вычислить функцию, локальной базе придется получить значение status для каждой подходящей под остальные удаленные условия строки. Если других ограничений нет, потенциально будут прочитаны и переданы все строки таблицы.

    Сравните с:

    EXPLAIN (ANALYZE, VERBOSE, BUFFERS)
SELECT id, amount
FROM fdw.orders
WHERE status = 'PAID';

    Если в таблице миллион строк, из которых оплачены 2%, разница принципиальная: вместо миллиона строк через сеть проходят около двадцати тысяч. Это примерная оценка по селективности, не результат измерения конкретного стенда.

    Инженерный вывод: для FDW важно смотреть не только на результат SQL, но и на место выполнения каждого выражения. Одна функция в WHERE может поменять стоимость запроса на порядок.

    5. Удаленный JOIN: место, где преимущество либо появляется, либо пропадает¶

    Для отчета нам нужно объединить orders и customers:

    SELECT c.region, count(*) AS paid_orders
FROM fdw.orders AS o
JOIN fdw.customers AS c ON c.id = o.customer_id
WHERE o.status = 'PAID'
GROUP BY c.region
ORDER BY paid_orders DESC;

    Наивная модель: «раз обе foreign table объявлены в одном PostgreSQL A, он их обе загрузит и соединит». Это возможный план, но не единственный.

    Если обе foreign table ссылаются на один foreign server и доступ к ним выполняется через совместимые user mapping, postgres_fdw может предложить remote join pushdown: отправить JOIN целиком на PostgreSQL B. Локальному серверу тогда не нужно перекачивать отдельно все заказы и всех клиентов.

    План А: локальный JOIN
  remote.orders ---- 100 000 строк ---> PostgreSQL A
  remote.customers - 10 000 строк ---> PostgreSQL A
                         Hash Join, Group Aggregate

План Б: удаленный JOIN + агрегирование
  PostgreSQL B: JOIN + GROUP BY
                ---- 3 строки -----> PostgreSQL A

    Числа условные, показывают различие объема сетевого обмена. Важно: удаленный JOIN не гарантируется фактом одинакового сервера. Его допустимость и выбор зависят от семантики выражений, пользователя, доступных путей и оценки стоимости. Посмотрите фактический план:

    EXPLAIN (VERBOSE, COSTS OFF)
SELECT o.id, c.region
FROM fdw.orders o
JOIN fdw.customers c ON c.id = o.customer_id
WHERE o.status = 'PAID';

    Для pushed-down JOIN характерен один Foreign Scan с Remote SQL, внутри которого присутствует JOIN. При локальном JOIN в плане будут отдельные чтения foreign tables и локальный узел Hash Join, Merge Join либо Nested Loop.

    Когда надежды на единый remote JOIN меньше: таблицы объявлены через разные foreign server; разные user mapping/пользователи запроса; условие JOIN нельзя безопасно выполнить удаленно; планировщик считает локальный вариант дешевле. Две записи CREATE SERVER, ведущие на один и тот же хост, не следует автоматически считать единым объектом для pushdown.

    5.1. А если одна таблица локальная?¶

    CREATE TABLE reporting.focus_customers (id bigint PRIMARY KEY);
INSERT INTO reporting.focus_customers
SELECT generate_series(1, 50);

SELECT c.id, o.amount
FROM reporting.focus_customers AS c
JOIN fdw.orders AS o ON o.customer_id = c.id;

    Теперь focus_customers существует только на PostgreSQL A. Удаленный PostgreSQL B ее не знает. Обычный postgres_fdw не может отправить туда весь JOIN как единое удаленное SQL-соединение. Локальный планировщик может выбрать Hash Join с передачей множества удаленных строк либо параметризованный доступ к удаленной таблице для значений c.id.

    А вот здесь начинается интересное. Если выбран Nested Loop и внутренний Foreign Scan повторяется для каждой строки внешнего источника, маленький SQL может породить множество сетевых обменов. Это тот же симптом класса N+1, но источником стала структура плана выполнения.

    При диагностике смотрим loops в EXPLAIN (ANALYZE, VERBOSE), удаленный SQL и удаленные подключения. Наличие Nested Loop само по себе еще не дефект: при малом числе внешних строк и точном индексе удаленные точечные обращения могут быть выгоднее переноса большой таблицы.

    6. GROUP BY, ORDER BY, LIMIT: почему нельзя просто отправить все подряд¶

    После WHERE и JOIN хочется перенести агрегацию:

    EXPLAIN (VERBOSE, COSTS OFF)
SELECT status, count(*)
FROM fdw.orders
GROUP BY status;

    postgres_fdw способен предложить удаленную агрегацию. Если она выбрана, в Remote SQL появится GROUP BY, а через сеть вернутся агрегированные группы, а не все заказы.

    Для верхних стадий плана используется callback GetForeignUpperPaths. В современной реализации могут удаленно выполняться допустимые операции группировки, сортировки и ограничения числа строк. Однако pushdown для GROUP BY, ORDER BY и LIMIT условен, поэтому каждый конкретный запрос проверяем по Remote SQL.

    Почему нельзя бездумно отправить LIMIT 10? Представим, что локальный сервер еще должен применить недоступный удаленной стороне фильтр. Если сначала взять удаленные «первые десять», а потом отбросить семь локальным фильтром, пользователь получит три строки вместо ожидаемых десяти. Планировщик обязан учитывать порядок и семантику операций.

    Это не мелкая оптимизация. С переносом GROUP BY сетевой объем может перейти от количества строк исходной таблицы к количеству групп результата. Для аналитических запросов это часто определяющий фактор.

    7. Цена сети: почему Foreign Scan не бывает бесплатным¶

    Разложим задержку на составляющие:

    [ T_{query}\;\approx\;T_{connect}+T_{plan,remote}+T_{execute,remote} +N_{round\,trips}\cdot RTT+\frac{Bytes}{Bandwidth}+T_{decode}+T_{local} ]

    Это инженерная модель, а не внутренний расчет planner PostgreSQL. Здесь:

    • RTT — задержка одного обмена запросом/ответом по сети (round-trip time);
    • Bandwidth — фактическая доступная пропускная способность канала;
    • Bytes — объем переданных данных, включая протокольные накладные расходы;
    • T_decode — стоимость приема, декодирования и преобразования полученных значений;
    • T_local — последующая локальная фильтрация, соединение, сортировка и т. д.

    Важно: части затрат могут перекрываться. Формула полезна для поиска источников задержки, но ее нельзя использовать как точный профилировщик.

    7.1. fetch_size: сколько строк получать за порцию¶

    postgres_fdw использует пакетное получение строк. Параметр fetch_size задает число строк за одну операцию получения; значение по умолчанию — 100.

    ALTER SERVER sales_remote OPTIONS (ADD fetch_size '1000');
-- Можно задать и на уровне конкретной foreign table:
-- ALTER FOREIGN TABLE fdw.orders OPTIONS (ADD fetch_size '1000');

    При последовательном получении 50 000 строк с fetch_size = 100 понадобится примерно 500 операций получения; с fetch_size = 1000 — примерно 50. Это не гарантирует ровно такое число физических TCP-пакетов: одна операция SQL и один TCP-пакет — разные понятия. Для иллюстрации, если одна порция требует последовательного ожидания удаленного ответа, RTT = 10 мс, только это ожидание может дать соответственно около 5 с и 0,5 с. Реальные времена зависят от конфигурации и перекрытия работы.

    Увеличивать fetch_size бесконечно нельзя: растут размер порции, буферизация и временное потребление памяти, особенно у широких строк и при множестве активных сканирований. А если запрос возвращает пять строк благодаря pushdown, настройки fetch_size почти не на что влиять.

    Порядок оптимизации: сначала сократить число передаваемых строк; затем число повторных запросов; лишь потом подбирать размер порции.

    7.2. Сетевой N+1¶

    Пусть локально имеется 500 клиентов, и для каждого выполняется отдельный запрос к удаленным заказам. Даже при быстром удаленном индексе и условных 4 мс задержки на один последовательный запрос 500 обращений дают порядка 2 секунд одного ожидания обменов, не считая SQL и передачи строк.

    -- Демонстрация намеренно неэффективного варианта:
DO $$
DECLARE
  v_customer_id bigint;
  n bigint;
BEGIN
  FOR v_customer_id IN
    SELECT id FROM reporting.focus_customers
  LOOP
    SELECT count(*) INTO n
    FROM fdw.orders
    WHERE orders.customer_id = v_customer_id;
  END LOOP;
END;
$$;

    Здесь orders.customer_id — колонка foreign table, а customer_id — переменная PL/pgSQL. В этом примере выполнение идет по одной SQL-команде на каждого локального клиента. Это демонстрационный дефект: не переносите такой цикл в production. Для реального запроса предпочтительнее SQL с JOIN или пакетной передачей ключей, после проверки плана.

    В отличие от N+1 на уровне кода, повторные удаленные вызовы могут быть спрятаны и в плане Nested Loop: смотрим loops и Remote SQL.

    8. Планировщик угадывает стоимость. Что будет, если угадает плохо?¶

    Мы обсудили дорогостоящий выбор: «загрузить и соединить локально» либо «соединить на удаленной стороне». Откуда локальный планировщик узнает, сколько строк и сколько времени займут операции PostgreSQL B?

    У postgres_fdw есть два основных подхода.

    Локальная оценка (use_remote_estimate = false, по умолчанию). Локальная сторона использует свои сведения и стоимость FDW. Это дешевле на этапе планирования, но статистика удаленной таблицы на локальной стороне может быть устаревшей или отсутствовать.

    Удаленная оценка (use_remote_estimate = true). FDW запрашивает у PostgreSQL B EXPLAIN для оценки вариантов. При этом к стоимости добавляется модель сетевых накладных расходов. План зачастую становится точнее, но каждая дополнительная удаленная оценка — это работа и задержка на этапе планирования.

    ALTER SERVER sales_remote
  OPTIONS (ADD use_remote_estimate 'true');

EXPLAIN (ANALYZE, VERBOSE, BUFFERS)
SELECT o.id, c.region
FROM fdw.orders o
JOIN fdw.customers c ON c.id = o.customer_id
WHERE o.status = 'PAID';

    Не нужно ставить use_remote_estimate=true на каждый foreign server по привычке: для коротких, часто повторяемых запросов стоимость дополнительных EXPLAIN может быть заметна. Измеряем Planning Time, Execution Time и общий клиентский отклик.

    8.1. ANALYZE для foreign table¶

    ANALYZE fdw.orders;
ANALYZE fdw.customers;

    Так локальная база обновляет статистику foreign table. Для postgres_fdw это требует чтения/выборки удаленных данных; параметр analyze_sampling определяет стратегию выборки. Важно: обычный autovacuum не обновляет автоматически статистику всех foreign tables так же, как локальных; для них ANALYZE нужно планировать явно.

    Свежая локальная статистика помогает избавиться от удаленных EXPLAIN на каждом планировании. Но если удаленные таблицы сильно меняются, она быстро устаревает.

    8.2. Параметры стоимости — это не миллисекунды¶

    • fdw_startup_cost — добавочная условная стоимость запуска удаленного обращения; по умолчанию 100.
    • fdw_tuple_cost — условная стоимость передачи одной строки; по умолчанию 0.2.
    ALTER SERVER sales_remote
  OPTIONS (ADD fdw_tuple_cost '0.5');

    Это единицы модели стоимости planner, а не задержка «0,5 мс на строку». Подкручивать их имеет смысл после измерений, иначе можно просто убедить планировщик выбирать другой плохой план.

    Модель после блока: два планировщика, разные статистики, отдельная цена сетевого обмена. Правильный удаленный индекс не спасет запрос, если локальный план заставил перекачивать лишние строки.

    9. Транзакции: вот здесь абстракция начинает протекать¶

    До сих пор мы читали данные. Но foreign tables можно обновлять:

    BEGIN;
UPDATE fdw.orders
SET status = 'PAID'
WHERE id = 42;
COMMIT;

    postgres_fdw открывает соответствующую удаленную транзакцию при первом обращении к foreign server в рамках локальной транзакции. При локальном COMMIT он отправляет фиксацию удаленной; при ROLLBACK — откат. Локальные savepoint сопоставляются с удаленными savepoint.

    Это полезно. Но значит ли это, что у нас появился единый глобальный MVCC snapshot и атомарная распределенная транзакция? Нет, и цена этого заблуждения может измеряться потерянными финансовыми операциями.

    9.1. Локальный READ COMMITTED и удаленный REPEATABLE READ¶

    Официальное правило postgres_fdw для PostgreSQL 18–19:

    Локальная транзакция Уровень удаленной транзакции
    READ COMMITTED REPEATABLE READ
    REPEATABLE READ REPEATABLE READ
    SERIALIZABLE SERIALIZABLE

    Почему так? Если в одной локальной транзакции одна foreign table читается несколько раз, postgres_fdw хочет получить последовательное представление удаленных строк. В результате удаленная транзакция использует более устойчивый snapshot.

    А теперь специально нарушим привычное ожидание от READ COMMITTED.

    -- Сессия А: ЛОКАЛЬНАЯ БД
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT count(*) FROM fdw.orders;
-- Запомнили N.

-- Сессия Б: УДАЛЕННАЯ БД, другая сессия
INSERT INTO core.orders(customer_id, amount, status)
VALUES (1, 999, 'PAID');
COMMIT; -- если Б была в явной транзакции; иначе INSERT уже зафиксирован

-- Сессия А: ЛОКАЛЬНАЯ БД, та же транзакция
SELECT count(*) FROM fdw.orders;
-- Через postgres_fdw снова видим N (при неизменных других условиях).
COMMIT;

-- После COMMIT новый SELECT увидит обновленное количество.

    Обычный локальный READ COMMITTED создает новый snapshot для каждого оператора. Здесь удаленный snapshot удерживается соответствующей remote-транзакцией REPEATABLE READ. Локальное и удаленное представления данных могут различаться по времени.

    Важная оговорка: это гарантия поведения postgres_fdw в рассматриваемых версиях, а не универсальное свойство произвольных FDW или SQL/MED.

    9.2. Savepoint не делает распределенный COMMIT атомарным¶

    BEGIN;
SAVEPOINT before_change;
UPDATE fdw.orders SET status = 'PAID' WHERE id = 42;
ROLLBACK TO SAVEPOINT before_change;
COMMIT;

    postgres_fdw умеет координировать такие вложенные операции с удаленными savepoint. Но распределенная атомарность требует другого: координатора и протокола двухфазной фиксации (two-phase commit, 2PC), позволяющего всем участникам сначала подготовить коммит, а потом согласованно завершить его.

    У стандартного postgres_fdw нет поддержки подготовки удаленной транзакции для 2PC. Более того, в реализации postgres_fdw удаленный COMMIT выполняется на этапе PRE_COMMIT локальной транзакции. Следовательно, окно для частично зафиксированного состояния реально существует: удаленный коммит мог завершиться, а локальная транзакция еще не зафиксирована.

    Локальная БД A                   Удаленная БД B
BEGIN                            BEGIN (через FDW)
локальное UPDATE                 удаленное UPDATE
COMMIT запрошен                  ...
  |-- FDW -> COMMIT ------------> фиксация B
  |-- локальный COMMIT A
          ^
          |
     сбой между этапами

    Если сервис меняет две базы как один финансовый инвариант, обычный BEGIN ... COMMIT через FDW не дает ему требуемой гарантии all-or-nothing. Одинаковые ключи и индексы, хорошие планы и небольшая задержка сети это не исправят.

    Что делать в backend: для критичных инвариантов — один транзакционный владелец записи либо явно спроектированная распределенная координация/компенсация с идемпотентностью и сверкой состояния. Выбор между ними выходит за рамки лекции; здесь достаточно точно знать границу postgres_fdw.

    9.3. Неопределенный исход при обрыве связи¶

    После отправки удаленного COMMIT сеть может оборваться до получения ответа. Локальная сторона не всегда способна достоверно вывести из ошибки связи, что именно успел зафиксировать удаленный сервер. Повторять побочный эффект «вслепую» опасно. Нужны идентификатор операции, проверка фактического состояния и политика повторов.

    10. Записи: поддерживаются, но не все сценарии равноценны¶

    postgres_fdw поддерживает SELECT, INSERT, UPDATE, DELETE, COPY и TRUNCATE, если есть права. Для части UPDATE/DELETE он может отправить изменение целиком на удаленную сторону — direct modification. При невозможности этого оптимизирования возможна более затратная обработка через локальный исполнитель.

    При массовой вставке есть параметр batch_size (по умолчанию 1), который задает размер партии отправляемых строк, если применима пакетная вставка:

    ALTER SERVER sales_remote
  OPTIONS (ADD batch_size '500');

    Число параметров протокола в одном запросе ограничено; postgres_fdw корректирует размер партии, если число_колонок × batch_size превышает предел 65535 параметров. Для COPY в foreign table есть дополнительные ограничения на фактический размер партии (в документации — до 1000 строк).

    INSERT ... ON CONFLICT DO UPDATE для postgres_fdw в PostgreSQL 18–19 не поддерживается. ON CONFLICT DO NOTHING возможен только в разрешенной форме — без определения конфликта через вывод уникального индекса.

    И еще одна граница: локальные CHECK/NOT NULL у foreign table не следует считать полной надежной валидацией удаленных данных — ядро PostgreSQL доверяет объявленным ограничениям, а основной источник истины о данных находится удаленно. В production контролировать целостность должна удаленная схема.

    11. Соединения: когда 20 подключений превращаются в сотни¶

    Постоянное FDW-подключение появляется обычно при первом использовании соответствующего foreign server в локальной сессии. По умолчанию оно сохраняется до завершения сессии и переиспользуется (keep_connections = on). Для разных user mapping могут существовать разные подключения.

    Клиенты приложения
     |
     v
100 локальных сессий PostgreSQL A
     |
     | каждая использует 3 remote server / mapping
     v
до ~300 дополнительных подключений к удаленным БД

    Это сценарная верхняя оценка для 100 сессий, каждая из которых действительно обращалась ко всем трем направлениям. Одно FDW-подключение не открывается на каждую строку. Но PostgreSQL backend на A не разделяет свое постоянное FDW-подключение с независимыми backend-процессами A как общий глобальный пул.

    Получается новая точка давления: max_connections, память на удаленные backend-процессы, число активных транзакций, удерживаемые snapshots, сетевые сокеты.

    Варианты:

    ALTER SERVER sales_remote
  OPTIONS (ADD keep_connections 'off');

    Тогда подключения закрываются по окончании транзакции. Снижается удержание соединений между транзакциями, зато возрастает цена повторных подключений. Для активной нагрузки это тоже может быть плохим решением.

    Диагностика из локальной сессии:

    SELECT * FROM postgres_fdw_get_connections();
-- На поддерживаемых платформах, в том числе Linux:
SELECT * FROM postgres_fdw_get_connections(true);

    Функция показывает подключения текущей локальной сессии, не является глобальным обзором всех backend PostgreSQL A. Поле remote_backend_pid помогает сопоставить ее подключение с pg_stat_activity на PostgreSQL B.

    11.1. Права и секреты¶

    Foreign table проходит две проверки доступа: локальный пользователь должен иметь права на foreign server/table, а удаленный пользователь — на физические объекты. Это разные роли и разные контуры доступа.

    Для production:

    • используйте отдельную удаленную роль с минимальными правами; избегайте доступа суперпользователя;
    • настраивайте TLS с проверкой сервера (sslmode=verify-full) и контролируйте доверенные сертификаты;
    • управляйте секретами как чувствительными данными: пароль user mapping может храниться в системных каталогах и попадать в бэкапы, доступ к ним должен быть ограничен;
    • не обходите проверку пароля через password_required=false без строгого понимания последствий;
    • задавайте лимиты времени выполнения и соединений с учетом всей цепочки.

    Уточнение по версиям: параметры аутентификации развиваются. Например, у postgres_fdw есть use_scram_passthrough с особыми требованиями к SCRAM-секретам и входящему соединению; это механизм для специальной схемы аутентификации, его нельзя включать как универсальную замену хранилищу секретов.

    12. Почему одно и то же выражение может дать разные данные¶

    Ограничения pushdown обусловлены корректностью. Удаленный сервер может использовать другую версию расширения, набор функций, COLLATE, системную конфигурацию. Для строковой сортировки это особенно неприятно: одинаковый текст может сравниваться или упорядочиваться по разным правилам.

    По умолчанию postgres_fdw отправляет в remote SQL только те выражения, которые считает безопасными. Для функций и операторов сторонних расширений можно явно указать опцию extensions, если совместимые расширения установлены на обеих сторонах и гарантированно ведут себя одинаково:

    -- Иллюстрация синтаксиса, не рекомендация включать произвольное расширение:
-- ALTER SERVER sales_remote OPTIONS (ADD extensions 'my_extension');

    Само наличие одноименной функции не гарантирует совместимость. Кроме того, postgres_fdw на удаленной стороне устанавливает ограниченный search_path = pg_catalog, TimeZone = UTC и другие настройки сессии. Если удаленные представления или триггеры вызывают функции с неявным search_path, возможны ошибки. Такие зависимости оформляют явной квалификацией схем и настройками функций.

    Практический вывод: pushdown — оптимизация, которая обязана сохранять смысл запроса. При сомнительной совместимости предпочтительнее локальная проверка ценой лишних строк, чем быстрый неправильный результат.

    13. Диагностика: сначала выяснить, где потрачено время¶

    Представим инцидент: «Отчет раньше занимал 300 мс, теперь 12 секунд». Распределим проверку по слоям.

    Симптом Вероятный механизм Что измерить
    Передано много строк, локальный Filter Условие не ушло в pushdown EXPLAIN (ANALYZE, VERBOSE) и Remote SQL
    Отдельные Foreign Scan, локальный Hash Join JOIN не перенесен EXPLAIN, объем строк по узлам
    Nested Loop, большой loops Повторные удаленные обращения loops, RTT, частоту SQL на удаленной стороне
    Долго строится план Много use_remote_estimate-запросов Planning Time, удаленные EXPLAIN
    Долго сканирует большой результат fetch_size, сеть, объем число возвращенных строк, сеть, fetch_size
    Удаленный запрос медленный сам по себе Индекс/план PostgreSQL B EXPLAIN (ANALYZE, BUFFERS) непосредственно на B
    Нехватка подключений Кеш соединений по сессиям pg_stat_activity на B, postgres_fdw_get_connections() на A
    Запрос завис на удаленном ожидании Сеть/удаленный lock/CPU/I/O wait events на A и B, pg_locks на B
    Разные значения в одной транзакции Различие remote snapshot Уровни изоляции, границы транзакций
    Частично завершенная запись Нет распределенного 2PC Сверка результатов на обеих сторонах

    13.1. Локальный план и точный удаленный SQL¶

    EXPLAIN (ANALYZE, VERBOSE, BUFFERS)
SELECT c.region, count(*)
FROM fdw.orders o
JOIN fdw.customers c ON c.id = o.customer_id
WHERE o.status = 'PAID'
GROUP BY c.region;

    Запоминаем ограничения интерпретации:

    • EXPLAIN VERBOSE показывает SQL, отправляемый удаленно.
    • EXPLAIN ANALYZE на A показывает фактическое время и число строк узла локального плана. Это не полноценный отчет о внутреннем плане B.
    • BUFFERS на A относится к измеряемым буферам локального выполнения; удаленные buffer hit/read надо исследовать непосредственно на B.
    • Если план B вызывает подозрение, возьмите смысл запроса из Remote SQL, подставьте необходимые параметры и отдельно выполните EXPLAIN (ANALYZE, BUFFERS) на B. В production делайте это осторожно: ANALYZE реально выполняет SQL.

    13.2. Наблюдение за сессиями¶

    На PostgreSQL B:

    SELECT pid, application_name, state,
       wait_event_type, wait_event,
       clock_timestamp() - xact_start AS xact_age,
       left(query, 150) AS sql_text
FROM pg_stat_activity
WHERE application_name = 'fdw_lecture';

    На PostgreSQL A:

    SELECT pid, wait_event_type, wait_event,
       state, left(query, 150) AS sql_text
FROM pg_stat_activity
WHERE wait_event_type = 'Extension'
  AND wait_event LIKE 'PostgresFdw%';

    В PostgreSQL 18–19 для postgres_fdw документированы, в частности, события ожидания PostgresFdwConnect (установление соединения), PostgresFdwGetResult (ожидание результатов) и PostgresFdwCleanupResult (очистка после отмены). Это моментальный срез, а не исчерпывающая метрика времени. PostgresFdwGetResult может означать ожидание как сети, так и выполнения SQL на удаленной стороне — без проверки B вывод о причине преждевременен.

    Если доступно расширение pg_stat_statements, на стороне B полезно смотреть частоту удаленных SQL и суммарное время. Рекомендовано выделить application_name для FDW-подключения, чтобы коррелировать локальную и удаленную стороны. Также помогают графики числа соединений, latency p50/p95/p99, числа возвращенных строк, сетевого трафика, планирования и блокировок.

    13.3. Таймауты и отказоустойчивость¶

    Задержка удаленной базы теперь входит в задержку локального запроса. Клиентский timeout, локальный statement_timeout, удаленный statement_timeout, connect_timeout и время ожидания блокировки должны быть согласованы. Сам по себе таймаут на стороне приложения не означает мгновенное прекращение всей работы на B.

    Если удаленный PostgreSQL недоступен, postgres_fdw не превращает его в локальный отказоустойчивый кеш: запрос к foreign table зависит от сети и состояния удаленного узла. Для жестких SLO изолируйте удаленную зависимость, ограничивайте конкурентность и заранее решайте, допускается ли деградация отчета.

    14. Под нагрузкой: три каскада, которые легко пропустить¶

    Каскад №1: медленный удаленный запрос занимает ресурсы двух PostgreSQL. На A локальный backend занят ожиданием результата; на B выполняется запрос, удерживаются ресурсы удаленной транзакции. Если таких запросов тысячи, проблема уже не ограничена одним хостом.

    Каскад №2: плохой pushdown умножает сетевой поток. 200 запросов/с × 50 МБ лишних данных на запрос = примерно 10 ГБ/с полезной нагрузки до учета накладных расходов. Это иллюстративная оценка; фактический трафик зависит от ширины кортежей, сжатия и протокола. Оптимизация одного WHERE может оказаться важнее расширения канала.

    Каскад №3: короткие локальные запросы создают дорогие remote connections и ожидания. Если пул локальных backend-сессий расширяется под нагрузкой и каждая впервые обращается к нескольким foreign server, создаются дополнительные удаленные подключения. Затем у удаленной базы растут конкуренция и время ответа, а локальная база держит больше ожидающих запросов. Получается обратная связь.

    Какие решения оправданы¶

    • Подходит: относительно редкие аналитические запросы, административные выборки, интеграция с уже существующим PostgreSQL, перенос небольшого отфильтрованного набора данных, контролируемый доступ к удаленным таблицам.
    • С осторожностью: горячие OLTP-запросы с жестким p99, тяжелые cross-server JOIN, многократные точечные обращения, высокая конкурентность, большие объемы передаваемых строк.
    • Не подходит как гарантия: атомарные изменения нескольких независимых баз, полностью единый snapshot, автоматическое кеширование данных и отказоустойчивая распределенная БД.

    Если нужны предсказуемая локальная задержка и независимость от remote-сервера, обычно рассматривают периодическую материализацию или репликацию. Если нужен единый инвариант записи, архитектура должна иметь явного владельца транзакции. Это варианты выбора, а не автоматические замены FDW.

    15. Практика: сделали, нагрузили, сломали, измерили и исправили¶

    Ниже самостоятельный стенд. Его можно выполнить на Linux/macOS с Docker. Все логины и пароли только учебные. Команды не предназначены для общего или банковского контура.

    Шаг 0. Поднять два PostgreSQL¶

    Создайте compose.yaml в пустой директории:

    services:
  local:
    image: postgres:18
    environment:
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: labpass
      POSTGRES_DB: appdb
    ports: ["55432:5432"]
  remote:
    image: postgres:18
    environment:
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: labpass
      POSTGRES_DB: appdb
    ports: ["55433:5432"]

    docker compose up -d
# Отдельно открываем два терминала:
docker compose exec local psql -U lab -d appdb
docker compose exec remote psql -U lab -d appdb

    Шаг 1. Создать исходные данные на remote¶

    Выполнить на remote, в схеме core:

    CREATE SCHEMA core;

CREATE TABLE core.customers (
  id bigint PRIMARY KEY,
  region text NOT NULL
);

CREATE TABLE core.orders (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES core.customers(id),
  created_at timestamptz NOT NULL DEFAULT now(),
  amount numeric(12, 2) NOT NULL,
  status text NOT NULL
);

INSERT INTO core.customers (id, region)
SELECT i,
       CASE i % 3
         WHEN 0 THEN 'Saratov'
         WHEN 1 THEN 'Moscow'
         ELSE 'Other'
       END
FROM generate_series(1, 10000) AS s(i);

INSERT INTO core.orders(customer_id, created_at, amount, status)
SELECT 1 + (i % 10000),
       now() - (i % 90) * interval '1 day',
       (10 + i % 5000)::numeric / 10,
       CASE WHEN i % 7 = 0 THEN 'PAID' ELSE 'NEW' END
FROM generate_series(1, 100000) AS s(i);

CREATE INDEX orders_status_created_idx
  ON core.orders(status, created_at);
CREATE INDEX orders_customer_id_idx
  ON core.orders(customer_id);

ANALYZE core.customers;
ANALYZE core.orders;

    Шаг 2. Создать FDW на local¶

    Выполнить на local:

    CREATE EXTENSION postgres_fdw;
CREATE SCHEMA fdw;
CREATE SCHEMA reporting;

CREATE SERVER sales_remote
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (
  host 'remote', port '5432', dbname 'appdb',
  application_name 'fdw_lecture'
);

CREATE USER MAPPING FOR lab
SERVER sales_remote
OPTIONS (user 'lab', password 'labpass');

IMPORT FOREIGN SCHEMA core
  LIMIT TO (orders, customers)
  FROM SERVER sales_remote INTO fdw;

SELECT count(*) FROM fdw.orders;
SELECT * FROM postgres_fdw_get_connections();

    Ожидание: запрос возвращает 100 000 строк в count(*), подключения появляются после обращения. count(*) обычно может быть агрегирован удаленно; подтвердите фактическим планом, а не предположением.

    Шаг 3. Доказать фильтрацию и pushdown¶

    EXPLAIN (ANALYZE, VERBOSE, BUFFERS)
SELECT id, amount FROM fdw.orders WHERE status = 'PAID';

    Создать функцию, которую нельзя отправить:

    CREATE FUNCTION reporting.is_paid(value text)
RETURNS boolean LANGUAGE plpgsql VOLATILE
AS $$ BEGIN RETURN value = 'PAID'; END; $$;

EXPLAIN (ANALYZE, VERBOSE, BUFFERS)
SELECT id, amount FROM fdw.orders
WHERE reporting.is_paid(status);

    Что измеряем: время, число строк в Foreign Scan, наличие локального Filter и состав Remote SQL. Затем исправляем запрос на status = 'PAID', запускаем повторно и объясняем, почему изменилась стоимость.

    Шаг 4. Найти remote JOIN и агрегацию¶

    EXPLAIN (VERBOSE, COSTS OFF)
SELECT o.id, c.region
FROM fdw.orders AS o
JOIN fdw.customers AS c ON c.id = o.customer_id
WHERE o.status = 'PAID';

EXPLAIN (VERBOSE, COSTS OFF)
SELECT c.region, count(*) AS n
FROM fdw.orders AS o
JOIN fdw.customers AS c ON c.id = o.customer_id
WHERE o.status = 'PAID'
GROUP BY c.region;

    Критерий: доказать планом, где выполняются JOIN и GROUP BY. Если локальный planner выбрал другой путь, это обсуждаемый результат, а не ошибка практики: включите use_remote_estimate, затем сравните планы.

    Шаг 5. Сломать план недостающей статистикой и сравнить оценивание¶

    -- Сначала базовый план:
EXPLAIN (ANALYZE, VERBOSE, BUFFERS)
SELECT o.id, c.region
FROM fdw.orders o
JOIN fdw.customers c ON c.id = o.customer_id
WHERE o.status = 'PAID';

-- Обновим локальную статистику вручную:
ANALYZE fdw.orders;
ANALYZE fdw.customers;

-- Снова исследуем тот же запрос.
-- Затем запросим оценку у удаленной базы:
ALTER SERVER sales_remote OPTIONS (ADD use_remote_estimate 'true');

    Повторите EXPLAIN (ANALYZE, VERBOSE, BUFFERS) и сравните Planning Time, Execution Time, кардинальности и Remote SQL. План может остаться прежним. Тогда доказательством служит различие механизма оценки и стоимости планирования; не утверждаем, что use_remote_estimate всегда быстрее.

    Шаг 6. Измерить fetch_size и число повторных обращений¶

    На local выполните запрос, возвращающий много строк, при разных размерах порции:

    -- Используйте psql \timing on и повторяйте каждый вариант несколько раз.
ALTER SERVER sales_remote OPTIONS (ADD fetch_size '100');
SELECT id, amount, status FROM fdw.orders;

ALTER SERVER sales_remote OPTIONS (SET fetch_size '1000');
SELECT id, amount, status FROM fdw.orders;

    Важно: psql печатает все строки и может исказить замеры терминалом. Для сравнительного измерения на стороне клиента используйте перенаправление результатов в файл или \o /dev/null в psql на Linux/macOS, а затем \o для возврата вывода. При локальном Docker оба экземпляра имеют малую задержку, поэтому существенного выигрыша может не быть. Для отдельного исследования RTT нужна контролируемая задержка сети (tc netem) в изолированной Linux-среде.

    Теперь демонстрационный N+1 с reporting.focus_customers:

    CREATE TABLE reporting.focus_customers (id bigint PRIMARY KEY);
INSERT INTO reporting.focus_customers SELECT generate_series(1, 50);

DO $$
DECLARE v_customer_id bigint; n bigint;
BEGIN
  FOR v_customer_id IN SELECT id FROM reporting.focus_customers LOOP
    SELECT count(*) INTO n
    FROM fdw.orders AS orders
    WHERE orders.customer_id = v_customer_id;
  END LOOP;
END;
$$;

    Здесь 50 отдельных обращений к foreign table. Исправление: выразите задачу одним SQL и проверьте результат/план:

    SELECT c.id, count(o.id)
FROM reporting.focus_customers c
LEFT JOIN fdw.orders o ON o.customer_id = c.id
GROUP BY c.id;

    Один SQL сам по себе не гарантирует один сетевой обмен: план может выбрать параметризованный Nested Loop. Сравниваем loops, количество строк и удаленную активность. Это и есть важный результат опыта.

    Шаг 7. Поймать неожиданный snapshot в READ COMMITTED¶

    Откройте отдельные окна psql: local и remote.

    В окне local:

    BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT count(*) FROM fdw.orders;

    В окне remote:

    INSERT INTO core.orders(customer_id, amount, status)
VALUES (1, 999, 'PAID');

    В первом окне, до завершения транзакции:

    SELECT count(*) FROM fdw.orders;
COMMIT;
SELECT count(*) FROM fdw.orders;

    Ожидаемая модель: значение внутри первой транзакции остается прежним; после COMMIT увеличивается на 1. Объясните связь локального READ COMMITTED и удаленного REPEATABLE READ.

    Шаг 8. Наблюдать две стороны инцидента¶

    Выполните длительный запрос на foreign table и во время выполнения посмотрите:

    -- На local, первая сессия:
SELECT count(*)
FROM fdw.orders
WHERE amount >= 0;

-- На local, другая сессия:
SELECT pid, wait_event_type, wait_event, state
FROM pg_stat_activity
WHERE wait_event_type = 'Extension';

-- На remote:
SELECT pid, application_name, state, wait_event_type, wait_event
FROM pg_stat_activity
WHERE application_name = 'fdw_lecture';

    На маленьком стенде запрос завершится слишком быстро, поэтому ожидание может не попасть в срез. Для гарантированно наблюдаемого ожидания в безопасной лаборатории можно создать удаленное представление с контролируемым pg_sleep, но это отдельный искусственный опыт; не выдавайте его за характерную производительность FDW.

    Финальный результат практики: студент должен предъявить пару фактических планов до/после изменения фильтра, Remote SQL для JOIN/агрегации, сравнение способа оценивания, объяснение поведения snapshot и измерение сетевого/пакетного эффекта (или доказательство, почему на данном стенде он не проявился).

    16. Инженерный вывод: шесть вещей, которые должны остаться¶

    1. Foreign table — локальный контракт на удаленные данные. Сами строки и индексы находятся на другом сервере, а SQL выполняется двумя PostgreSQL через сеть.
    2. Место выполнения операции определяет цену. Смотрите Remote SQL: WHERE, проекция, JOIN и агрегирование, ушедшие на B, могут сократить сетевой обмен на порядки.
    3. Оптимизация ограничена корректностью. Функции, правила сортировки, разные foreign server и user mapping могут мешать pushdown; оптимизатор выбирает путь по оценке стоимости.
    4. Цена складывается из удаленной работы, объема передачи и числа обменов. fetch_size и batch_size помогают, но не исправляют неудачный JOIN или плохую селективность.
    5. Транзакции имеют границу. Удаленный уровень изоляции для локального READ COMMITTED — REPEATABLE READ; remote savepoint поддерживаются, а распределенный 2PC через обычный postgres_fdw — нет.
    6. Production-диагностика всегда двухсторонняя. Локальный EXPLAIN, удаленный EXPLAIN, pg_stat_activity, wait events, статистика, подключения и сеть дают разные части общей картины.

    Куда копнуть глубже¶

    Следующий слой — планировщик FDW (ForeignPath, параметризованные пути и GetForeignJoinPaths). Он закроет вопрос: почему два на вид похожих JOIN превращаются то в один удаленный запрос, то в сотни параметризованных обращений? Это полезно для диагностики Nested Loop и для понимания оптимизатора PostgreSQL. Предлагаю выделить его в отдельное углубление, а не перегружать факультативную лекцию.

    Альтернативный слой — postgres_fdw и локальный transaction manager: XACT callbacks, PRE_COMMIT, savepoint и точки частичной фиксации. Он нужен, если хочется доказать невозможность гарантированного распределенного all-or-nothing на уровне конкретных вызовов исходного кода PostgreSQL.
