    3. Go memory, GC и pprof¶

    Версионная привязка: материал ориентирован на стандартный Go toolchain версии 1.27.x.

    В этой лекции важно постоянно разделять:

    • гарантии языка — что обещает спецификация;
    • решения compiler/runtime — stack/heap placement, GC и конкретные оптимизации;
    • production-поведение — allocations, GC CPU, RSS, latency, goroutine leaks.

    Детали mcache, mspan, mcentral, Green Tea queues, sweep generations и scavenger internals разбираются в отдельной дополнительной лекции.

    Главная цепочка лекции:

    значение в коде
      ↓
lifetime
      ↓
escape analysis
      ↓
stack или heap
      ↓
allocations
      ↓
heap growth
      ↓
GC
      ↓
CPU / memory pressure
      ↓
pprof
      ↓
конкретная строка кода

    Цель лекции — чтобы студент после нее не говорил:

    «GC съел память»
    «указатель значит heap»
    «маленькая GC pause значит GC дешевый»
    «RSS растет — значит leak»

    Вместо этого он должен уметь построить причинно-следственную цепочку.

    Блок 1. С чего вообще начинается разговор о памяти¶

    1. Backend живет не в абстрактной памяти¶

    Возьмем HTTP-сервис:

    func handler(w http.ResponseWriter, r *http.Request) {
    user := User{
        ID:   42,
        Name: "Alice",
    }

    data, _ := json.Marshal(user)
    w.Write(data)
}

    На уровне бизнес-кода все просто.

    Но процессу физически нужны ресурсы:

    код программы
goroutine stacks
heap objects
runtime metadata
OS thread stacks
network buffers
memory mappings

    И в какой-то момент production говорит:

    CPU = 95%
RSS = 1.8 GB
p99 = 900 ms
GC CPU высокий
goroutines = 40 000

    Чтобы понять, почему это произошло, одной синтаксической модели Go недостаточно.

    Нужно понимать lifetime данных.

    2. Главный вопрос — не «где объявлена переменная»¶

    Плохое упрощение:

    локальная переменная → stack
new() → heap
указатель → heap

    Эта таблица ломается почти сразу.

    Полезнее задавать вопрос:

    Как долго значение должно существовать и кто может на него ссылаться?

    Например:

    func answer() int {
    x := 42
    return x
}

    x нужен только во время вызова answer.

    А теперь:

    func answer() *int {
    x := 42
    return &x
}

    После return вызывающая функция все еще получает адрес x.

    Значит lifetime значения переживает execution frame функции.

    Именно здесь возникает задача compiler:

    где разместить значение,
чтобы его lifetime был корректным?

    Блок 2. Stack¶

    3. Stack — сначала ментальная модель¶

    При вызове функции ей нужна память для выполнения.

    Учебно можно представить frame:

    foo()
┌─────────────────┐
│ arguments       │
│ local values    │
│ temporary data  │
│ return state    │
└─────────────────┘

    Функция вызывает другую:

    main
 ↓
handle
 ↓
parse
 ↓
validate

    Получаем:

    goroutine stack

┌────────────┐
│ validate   │
├────────────┤
│ parse      │
├────────────┤
│ handle     │
├────────────┤
│ main       │
└────────────┘

    Когда validate заканчивается, ее frame больше не нужен.

    4. Почему stack allocation дешевая¶

    В очень упрощенной модели stack allocation похожа на:

    stack pointer
      ↓
сдвинули границу
      ↓
готово

    Когда функция возвращается:

    frame больше не нужен
↓
stack pointer возвращается

    Не нужно:

    искать отдельный свободный object
запоминать его lifetime в heap
потом искать его GC

    Поэтому stack allocation обычно значительно дешевле heap allocation.

    5. Кто освобождает stack value¶

    func calculate() int {
    x := 10
    y := 20
    return x + y
}

    Когда frame calculate исчезает:

    x
y

    исчезают вместе с ним.

    Никакой GC не обязан отдельно искать:

    x больше не нужен?
y больше не нужен?

    Lifetime уже структурирован call stack.

    6. У каждой goroutine свой stack¶

    Это важная связь с конкурентностью.

    G1 → stack1
G2 → stack2
G3 → stack3
...

    Если одновременно существует 100 000 goroutines, у каждой есть собственное stack state.

    Но было бы слишком дорого заранее выдавать каждой goroutine огромный stack.

    Поэтому goroutine stacks стартуют небольшими и runtime может увеличивать их по мере необходимости.

    7. Stack может расти¶

    Представим глубокий call chain:

    f1
↓
f2
↓
f3
↓
...
↓
f1000

    Или recursive algorithm.

    Текущего stack space может не хватить.

    Runtime Go умеет увеличить stack goroutine.

    Учебная модель:

    старый stack слишком мал
↓
runtime получает больший stack
↓
переносит stack data
↓
обновляет известные references
↓
goroutine продолжает работу

    Это implementation detail runtime, но полезное следствие:

    Размер goroutine stack не является фиксированной величиной на весь lifetime goroutine.

    8. Stack тоже потребляет память¶

    Иногда говорят:

    «Goroutine почти бесплатная».

    Нет.

    Даже если stack стартует маленьким, goroutine:

    имеет stack
имеет runtime metadata
может удерживать heap references
может вырасти

    Поэтому leak из сотен тысяч goroutines — memory problem даже до учета heap objects, которые они удерживают.

    Что важно запомнить¶

    1. Stack связан с execution frames функций.
    2. Stack values удобно освобождать вместе с завершением frame.
    3. У каждой goroutine свой stack.
    4. Goroutine stack способен расти.
    5. Stack memory тоже не бесплатна.

    Углубление. Как goroutine stack растет на практике¶

    До этого достаточно было модели:

    stack закончился
↓
runtime получает больший stack
↓
копирует содержимое
↓
goroutine продолжает работу

    Теперь сделаем ее точнее.

    Современный Go использует непрерывный stack каждой goroutine, который runtime может заменить на более крупный.

    Это принципиально отличается от модели:

    stack разбит на случайные несвязанные куски

    Полезная ментальная модель:

    старый contiguous stack
┌──────────────────┐
│ frame C          │
├──────────────────┤
│ frame B          │
├──────────────────┤
│ frame A          │
└──────────────────┘

        ↓ grow

новый более крупный stack
┌──────────────────────────┐
│                          │
│ frame C                  │
├──────────────────────────┤
│ frame B                  │
├──────────────────────────┤
│ frame A                  │
│                          │
└──────────────────────────┘

    Откуда runtime понимает, что stack заканчивается¶

    У goroutine есть информация о границе stack.

    Compiler добавляет в обычные функции проверку, достаточно ли места для следующего frame.

    Упрощенно:

    вход в функцию
↓
хватает stack?
│
├── да  → выполняем функцию
└── нет → runtime расширяет stack

    Это называется stack growth check.

    Конкретные функции runtime и точная реализация — implementation detail.

    Но важна сама причинная цепочка:

    большая глубина вызовов
↓
следующий frame не помещается
↓
runtime вмешивается
↓
stack становится больше

    Почему stack можно копировать¶

    Кажется опасным:

    мы перенесли stack
↓
все адреса stack variables изменились

    Но Go compiler и runtime знают, где внутри frames находятся pointers.

    Это позволяет при переносе stack корректировать ссылки, указывающие внутрь старого stack.

    То есть stack copying связан с той же фундаментальной способностью runtime:

    точно знать pointer layout

    которая потом понадобится GC.

    Почему unsafe.Pointer требует осторожности¶

    Если runtime должен перемещать stack, он обязан понимать references.

    Обычные Go pointers участвуют в этой модели.

    Но когда программист начинает вручную превращать pointer в integer и хранить его как обычное число:

    u := uintptr(unsafe.Pointer(&x))

    runtime уже не обязан воспринимать u как живую ссылку на x.

    Поэтому unsafe ломает часть автоматических гарантий, на которых строятся stack movement и GC.

    Для основной лекции достаточно вывода:

    Pointer в Go — не просто число с адресом. Runtime и compiler используют типовую информацию о pointers для управления памятью.

    Stack может не только расти¶

    Если goroutine когда-то имела глубокий call stack:

    2 KiB
↓
4 KiB
↓
8 KiB
↓
...
↓
1 MiB

    это не означает, что она обязана удерживать максимальный stack до завершения процесса.

    Runtime способен уменьшать избыточные goroutine stacks в рамках GC/runtime maintenance.

    Конкретная политика может меняться между версиями.

    Инженерно важно другое:

    текущий stack size

    и:

    максимальный stack size за всю жизнь goroutine

    не обязаны совпадать.

    Почему deep recursion все равно опасна¶

    Автоматический рост stack не означает:

    recursion теперь бесплатна и бесконечна

    Каждый новый frame потребляет память.

    Глубокая recursion:

    frames ↑
↓
stack growth
↓
copy cost
↓
memory ↑

    А бесконечная recursion в итоге приводит к исчерпанию допустимого stack/resources.

    Backend-вывод¶

    Обычный HTTP-handler редко упирается в stack growth.

    Но stack становится значимым, когда:

    • очень много goroutines;
    • глубокие call chains;
    • большие local values;
    • рекурсивные алгоритмы;
    • goroutine leaks.

    Например:

    200 000 goroutines
×
даже несколько KiB committed stack
=
уже заметный memory footprint

    А если leaked goroutines еще и держат heap pointers:

    goroutine stack
↓
pointer
↓
request graph
↓
buffers / DTO / context

    маленькая runtime-сущность начинает удерживать гораздо больше памяти, чем занимает сама.

    Блок 3. Heap¶

    9. Когда structured lifetime stack уже недостаточен¶

    func createUser() *User {
    u := User{
        ID: 42,
    }

    return &u
}

    После возврата:

    createUser frame

    закончился.

    Но объект должен остаться доступным вызывающему коду.

    Значит storage объекта не может зависеть от lifetime этого frame.

    Здесь появляется heap.

    10. Что такое heap в полезной модели¶

    Heap — managed memory для значений, lifetime которых нельзя удобно связать только с текущим stack frame.

    Очень грубо:

    stack:
lifetime следует call structure

heap:
lifetime определяется reachability

    Это важнее определения:

    «Heap — большая область динамической памяти».

    Нас интересует именно различие lifetime.

    11. Кто освобождает heap object¶

    Stack frame уничтожается структурно.

    С heap все сложнее.

    Например:

    A → B → C

    Пока A reachable, B и C тоже могут быть нужны.

    Потом reference на A исчезает.

    Теперь runtime должен установить:

    существует ли еще какой-либо путь к A/B/C?

    Именно эту задачу решает GC.

    12. Stack и heap — не синтаксические конструкции языка¶

    Go specification не обещает:

    new(T) обязан heap
локальная переменная обязана stack

    Storage managed implementation.

    Compiler может изменить placement между версиями, не меняя корректность программы.

    Правильный уровень рассуждения:

    семантика программы
↓
compiler определяет storage strategy

    Блок 4. Разрушаем мифы про stack и heap¶

    13. new(T) не означает «heap»¶

    func f() int {
    p := new(int)
    *p = 42
    return *p
}

    На уровне языка:

    new(int)

    создает variable и возвращает pointer.

    Но compiler может доказать:

    pointer не переживает вызов f

    и оставить storage вне heap либо оптимизировать его еще сильнее.

    Следовательно:

    new
≠
гарантированный heap allocation

    14. &x не означает «heap»¶

    func f() {
    x := 42
    p := &x
    consume(p)
}

    Сам факт взятия адреса не требует heap.

    Вопрос:

    куда pointer уходит?
как долго он живет?
может ли compiler доказать lifetime?

    15. Локальная переменная может попасть в heap¶

    func makeCounter() func() int {
    x := 0

    return func() int {
        x++
        return x
    }
}

    Closure переживает makeCounter.

    Значит captured state x должен жить дольше frame функции.

    Compiler должен обеспечить этот lifetime.

    16. Большое значение тоже может изменить решение compiler¶

    Даже если значение логически могло бы жить на stack, compiler/runtime могут учитывать ограничения реализации.

    Большие local objects, inlining и конкретные optimization passes могут влиять на storage decision.

    Поэтому нельзя строить лекцию вокруг списка:

    конструкция X всегда stack
конструкция Y всегда heap

    Надежнее:

    изучаем lifetime
↓
проверяем compiler diagnostics
↓
измеряем allocations

    Блок 5. Escape analysis¶

    17. Зачем compiler вообще анализирует escape¶

    func f() *int {
    x := 42
    return &x
}

    Compiler видит flow:

    x
↓
&x
↓
return
↓
caller

    Reference выходит за lifetime frame.

    Говорят:

    x escapes

    То есть compiler не может оставить storage только внутри обычного lifetime текущего frame.

    18. Escape — это анализ потока references¶

    Не сводим к:

    есть pointer → escape

    Compiler анализирует:

    value
↓
reference
↓
куда сохраняется?
↓
кто может пережить текущую функцию?

    Типичные причины:

    return pointer
closure capture
store into longer-lived object
store in heap structure
unknown/indirect call behavior
large object/compiler constraints

    19. Пример: return pointer¶

    func makeID() *int {
    id := 42
    return &id
}

    Lifetime:

    frame makeID закончился
↓
caller все еще использует pointer

    Storage обязан пережить frame.

    Это очевидный escape case.

    20. Пример: pointer остается локальным¶

    func local() int {
    x := 42
    p := &x
    return *p
}

    Pointer существует.

    Но:

    p не уходит наружу

    Compiler может оставить value вне heap.

    Снова:

    pointer
≠
heap

    21. Пример: closure¶

    func counter() func() int {
    n := 0

    return func() int {
        n++
        return n
    }
}

    Closure хранит доступ к n.

    После:

    counter() returned

    n все еще нужен.

    Это lifetime extension.

    22. Пример: сохранение в более долгоживущий object¶

    type Holder struct {
    P *int
}

func put(h *Holder) {
    x := 42
    h.P = &x
}

    После put:

    h.P

    может использовать x.

    Значит x не может исчезнуть вместе с frame.

    23. Inlining может изменить escape result¶

    До inlining compiler может видеть функцию отдельно.

    После inlining body вызываемой функции становится виден caller context.

    Иногда теперь можно доказать:

    reference не переживает caller

    и убрать heap allocation.

    Следствие:

    Allocation count может измениться после seemingly unrelated compiler upgrade.

    24. Go продолжает улучшать stack allocation¶

    Go 1.26 расширил возможности compiler размещать некоторые constant-sized slices на stack.

    Это хороший пример:

    код не изменился
↓
семантика не изменилась
↓
compiler доказал больше
↓
heap allocations стало меньше

    Поэтому stack/heap placement — implementation detail, а не API contract.

    Углубление. Escape analysis на неочевидных примерах¶

    Escape analysis особенно полезен там, где синтаксис обманывает.

    1. Передача pointer в другую goroutine¶

    func start() {
    x := 42

    go func() {
        fmt.Println(x)
    }()
}

    start может завершиться раньше goroutine.

    Значит captured state должен пережить frame start.

    Ментальная модель:

    start frame
↓
launch goroutine
↓
start returns
↓
new goroutine все еще использует x

    Lifetime больше не ограничен исходным frame.

    Это типичный повод для escape.

    Важно:

    Причина не в ключевом слове go. Причина в том, что compiler должен обеспечить lifetime данных при независимом исполнении goroutine.

    2. Передача адреса в goroutine¶

    func start() {
    x := 42

    go printValue(&x)
}

    Опять же:

    &x
↓
другая goroutine
↓
может жить дольше start

    Storage x должен оставаться валидным.

    3. Возврат slice¶

    func makeIDs() []int {
    ids := make([]int, 10)
    return ids
}

    Здесь наружу уходит slice header:

    pointer
len
cap

    Главный вопрос:

    где живет backing array?

    Если caller продолжает пользоваться slice после завершения функции, backing storage должен пережить frame.

    Но начиная с новых compiler optimizations конкретный путь может быть хитрее: небольшой временный backing store способен сначала жить на stack, а при необходимости быть перемещен в heap.

    Поэтому правило:

    returned slice = heap

    слишком грубое как описание реализации.

    Семантика одна:

    returned elements остаются валидными

    А конкретный storage strategy выбирает compiler/runtime.

    4. Interface может скрыть lifetime¶

    func box() any {
    x := 42
    return x
}

    any хранит type information и value representation.

    В зависимости от конкретного типа, размера, optimization context и дальнейшего использования compiler может принимать разные storage decisions.

    Поэтому фраза:

    interface = allocation

    не является гарантией.

    Проверяем:

    go build -gcflags="-m=2" .

    и benchmark.

    5. Неизвестный вызов ограничивает анализ¶

    Compiler любит код, поведение которого он видит.

    Если reference передается в место, про которое compiler не может достаточно доказать:

    что вызываемая функция сделает с pointer?
сохранит?
вернет?
передаст дальше?

    он может принять более консервативное решение.

    Это важная общая идея static analysis:

    Если доказать короткий lifetime не удалось, correctness важнее потенциальной stack optimization.

    6. Escape и heap allocation — не одно и то же наблюдение в benchmark¶

    Escape report говорит:

    значение должно пережить текущий frame / analysis conservatively sends it to heap

    Benchmark показывает:

    реально сколько heap allocations осталось после всех compiler optimizations

    Между ними есть другие optimization passes.

    Поэтому полезно смотреть оба инструмента:

    -m=2
+
-benchmem

    а не пытаться вывести одно из другого механически.

    7. Escape может измениться после рефакторинга API¶

    Представим:

    func parse(s string) Result

    Compiler видит body, функция inline'ится, temporary value остается локальным.

    После изменения:

    type Parser interface {
    Parse(string) Result
}

    28. Что именно называется allocation¶

    Кто владеет ссылкой и когда она исчезнет?

    Slice header не владеет "только len байтами"¶

    Slice:

    type SliceHeader struct {
    Data pointer
    Len  int
    Cap  int
}

    Учебно.

    Допустим:

    buf := make([]byte, 100<<20)

    small логически показывает 10 bytes.

    Но pointer все еще ведет в backing array на 100 MiB.

    Значит reachability:

    small
↓
100 MiB backing array

    GC не умеет освободить "неиспользуемые 99.999 MiB" внутри этого массива.

    Объект backing array либо reachable целиком, либо нет.

    Компактная копия как осознанный trade-off¶

    Иногда:

    small := append([]byte(nil), buf[:10]...)

    или:

    small := bytes.Clone(buf[:10])

    создает отдельный маленький backing array.

    Цена:

    новая allocation
+
copy

    Плюс:

    100 MiB могут стать unreachable

    Это отличный пример:

    Иногда дополнительная allocation уменьшает memory pressure.

    Поэтому правило:

    меньше allocations = всегда лучше

    ложно.

    Map ownership¶

    m := map[string]*User{}

    Context может удерживать больше, чем кажется¶

    context.Context полезен для cancellation и request-scoped metadata.

    то lifetime hugeObject как минимум связан с lifetime всей цепочки context.

    Queue — это буквально heap ownership¶

    Следовательно:

    channel
↓

↓

    Один pointer способен удерживать огромное дерево¶

    root
↓
A
├── B
│   ├── ...
│   └── ...
└── C
    └── ...

    Удаление тысячи внутренних references может ничего не дать, пока сохраняется root pointer на A.

    Поэтому memory profiling должен отвечать не только:

    где object allocated?

    но и:

    почему он все еще reachable?

    Go heap profile в первую очередь агрегирует по allocation sites, а не строит полноценный dominator tree как некоторые другие heap analyzers.

    Углубление. Bytes в heap не равны GC work¶

    Это одна из самых важных идей для production.

    Рассмотрим два объекта одинакового размера.

    Вариант A¶

    buf := make([]byte, 100<<20)

    100 MiB байтов.

    Внутри нет Go pointers на другие heap objects.

    Вариант B¶

    nodes := make([]*Node, n)

    Пусть backing array тоже занимает около 100 MiB.

    Но теперь внутри миллионы pointers.

    Collector должен разбирать потенциальные outgoing references.

    Получаем:

    100 MiB raw bytes
≠
100 MiB pointer-rich heap

    по стоимости marking.

    Scan и noscan как ментальная модель¶

    Runtime знает layout типов.

    Поэтому он может различать области:

    pointer-free

    и:

    содержащие pointers

    Pointer-free data после подтверждения reachability не требуют обхода каждого слова в поиске дочерних heap references.

    Это одна из причин, почему:

    live heap bytes

    недостаточно для оценки GC cost.

    Нужно учитывать:

    scannable heap

    runtime/metrics¶

    Для этого существует, например:

    /gc/scan/heap:bytes

    Она помогает ответить:

    Какой объем heap memory collector рассматривает как содержащий потенциальные pointers для scanning?

    Есть и:

    /gc/scan/stack:bytes

    То есть roots со stacks тоже создают scan work.

    Каждая goroutine имеет stack.

    Stack содержит:

    locals

    GC должен учитывать stack roots.

    Поэтому:

    Это важная связь concurrency и GC.

    Heap A:

    1 object × 1 GiB

    Heap B:

    50 000 000 маленьких objects

    Углубление. Что за GC вообще используется в Go¶

    На высоком уровне стандартный Go collector можно описать так:

    tracing
precise
concurrent
parallel
mark-and-sweep
non-generational
non-compacting

    Каждое слово что-то означает.

    Tracing¶

    GC начинает с roots и идет по graph references:

    roots
↓
reachable objects
↓
their pointers
↓
more objects

    Это не reference counting.

    Цикл:

    A → B
↑   ↓
└── C

    не является проблемой сам по себе.

    Если никакой root не ведет в цикл, весь цикл unreachable.

    Precise¶

    Collector знает, какие machine words являются Go pointers.

    Например:

    type User struct {
    ID      uint64
    Session *Session
    Active  bool
}

    GC не должен считать ID случайным pointer только потому, что его bits похожи на memory address.

    Compiler/runtime имеют type/stack metadata.

    Это уменьшает ложную retention и делает moving/copying stack machinery возможной.

    Concurrent¶

    Основная marking work идет одновременно с application.

    mutator
+
collector

    Отсюда write barriers и synchronization complexity.

    Parallel¶

    GC способен использовать несколько CPU одновременно.

    P0 → mark
P1 → mark
P2 → application
P3 → application

    Concurrent и parallel — не одно и то же.

    concurrent
= GC и application пересекаются во времени

parallel
= несколько GC workers работают одновременно

    Mark-and-sweep¶

    Mark:

    что reachable?

    Sweep:

    какие ранее allocated места теперь можно reuse?

    Эти фазы отвечают на разные вопросы.

    Non-generational¶

    Классическая generational идея:

    young objects
old objects

    и частые collections молодого поколения.

    Основной Go collector не строится вокруг такой generational heap architecture.

    Почему это важно?

    Нельзя переносить на Go автоматическую модель:

    short-lived object почти бесплатно умрет в young generation

    Short-lived heap object все равно создает allocation traffic и участвует в общей economics collector.

    Non-compacting¶

    Collector обычно не перемещает live heap objects только для того, чтобы сложить их плотнее.

    После collection heap может выглядеть:

    [A][free][C][free][E][free]

    а не:

    [A][C][E][free][free][free]

    Плюсы:

    stable object addresses
не надо постоянно переписывать pointers
нет массового copying live heap

    Цена:

    fragmentation

    Именно поэтому:

    live heap

    и:

    RSS

    могут заметно различаться даже при отсутствии leak.

    Почему Go выбрал такой набор trade-offs¶

    Backend обычно особенно чувствителен к:

    latency
predictability
concurrent progress

    Поэтому Go исторически делает ставку на короткие STW и concurrent collection, принимая постоянный CPU overhead и более сложный runtime.

    Это не "лучший GC вообще".

    Это конкретный набор компромиссов.

cache/memory bandwidth pressure

    Поэтому:

    pause маленькая

    еще не значит:

    GC дешевый

    Блок 14. Write barrier¶

    58. Проблема¶

    GC уже просканировал:

    A

    Application делает:

    A.child = C

    Heap graph изменился во время collection.

    Если collector ничего не узнает, reachable object можно потерять.

    59. Решение¶

    Во время concurrent marking определенные pointer writes сопровождаются дополнительной runtime bookkeeping.

    Это write barrier.

    Для основной лекции достаточно:

    application меняет heap graph
↓
barrier помогает GC не потерять references

    Как устроен hybrid barrier — отдельная дополнительная лекция.

    Блок 15. Green Tea¶

    60. Версионное примечание¶

    Начиная с Go 1.26 Green Tea является default garbage collector стандартного toolchain.

    Для основной лекции не нужно разбирать его внутренние queues.

    Важно понять, какую проблему он решает.

    61. Проблема pointer chasing¶

    Tracing object graph может выглядеть так:

    A → object далеко в memory
↓
B → еще дальше
↓
C → другая page

    CPU caches работают хуже.

    Green Tea лучше группирует marking/scanning work по locality.

    Практический смысл:

    меньше GC overhead на многих workloads

    Но programming model остается:

    reachable → live
unreachable → collectible

    63. Почему GC запускается¶

    Heap растет.

    Runtime имеет target:

    heap goal

    Collector должен стартовать достаточно рано, чтобы закончить работу до чрезмерного роста heap.

    Этим занимается GC pacer.

    В основной лекции достаточно идеи:

    allocation rate ↑
↓
collector должен начинать раньше / работать активнее

    Углубление. Roots тоже стоят денег¶

    В простейшем объяснении GC:

    heap grows
↓
scan heap

    Но tracing начинается не с heap "сам по себе".

    Он начинается с roots.

    Упрощенно:

    globals
goroutine stacks
runtime roots
↓
heap graph

    Поэтому workload с огромным количеством goroutines может иметь дополнительную collector work даже при умеренном heap.

    Почему stack scan связан с lifetime¶

    Представим request goroutine:

    handler frame
↓
user pointer
↓
session pointer
↓
large graph

    Пока handler не завершился, stack остается root.

    Если DB замедлилась:

    handler lifetime ↑

    references дольше остаются на stack.

    Следовательно:

    object lifetime ↑

    Даже без новых global caches.

    Это важный мост от latency к memory.

    GC root size участвует в современной GOGC модели¶

    Слишком грубая формула:

    goal = live heap × (1 + GOGC/100)

    удобна для первого объяснения.

    Более точная учебная модель учитывает и root scanning:

    target ≈
live heap
+
(live heap + roots) × GOGC / 100

    Это не API formula и не обещание точного числа.

    Но она исправляет важное заблуждение:

    Стоимость collection определяется только heap bytes.

    Нет.

    Roots тоже являются work.

    Углубление. Почему latency сама увеличивает memory: Little's Law для backend¶

    Вот здесь появляется очень полезная количественная модель.

    Для стабильного потока запросов:

    in-flight requests
≈
arrival rate × average time in system

    Это частный случай Little's Law.

    Например:

    RPS = 10 000
average request time = 20 ms

    Тогда одновременно живет примерно:

    10 000 × 0.020
=
200 requests

    Теперь DB замедлилась:

    request time = 500 ms

    Получаем:

    10 000 × 0.5
=
5 000 in-flight requests

    Код не изменился.

    RPS не изменился.

    Но одновременно живых request state стало:

    200
↓
5 000

    в 25 раз больше.

    Добавим memory per request¶

    Пусть один in-flight request удерживает в среднем:

    50 KiB

    DTO, buffers, context, parsed body, tracing state и т.д.

    Нормальный режим:

    200 × 50 KiB
≈ 10 MiB

    После роста latency:

    5 000 × 50 KiB
≈ 244 MiB

    Только request-local live data.

    Без leak.

    Без увеличения allocation/op.

    Без изменения кода.

    Теперь появляется feedback loop¶

    DB latency ↑
↓
in-flight requests ↑
↓
live heap ↑
↓
GC work ↑
↓
CPU for application ↓
↓
service latency ↑
↓
in-flight еще больше ↑

    Получаем self-amplifying degradation.

    Это одна из причин, почему memory incidents нельзя расследовать в отрыве от:

    latency
RPS
queue depth
dependency health

    То же самое с очередями¶

    Producer rate:

    20 000 jobs/s

    Consumer capacity:

    18 000 jobs/s

    Разница:

    2 000 jobs/s

    Через минуту backlog:

    120 000 jobs

    Если один queued job удерживает:

    5 KiB

    получаем примерно:

    ~586 MiB

    дополнительной reachable memory.

    GC здесь беспомощен:

    queue
↓
job
↓
payload

    все objects live.

    или:

    Углубление. Virtual memory, physical pages и page faults¶

    До этого мы говорили:

    VSS != RSS != Go heap

    Теперь разберем, почему.

    Virtual address space¶

    Процесс работает с virtual addresses.

    Например:

    0x000000c000...

    Это не означает:

    по этому номеру прямо стоит физическая ячейка DRAM

    OS и MMU поддерживают mapping:

    virtual page
↓
physical page

    или отсутствие текущего physical backing.

    Page¶

    OS управляет памятью страницами.

    Типичный размер обычной page на x86-64 Linux:

    4 KiB

    но существуют huge pages и другие конфигурации.

    Это OS page.

    Не смешивать с внутренними runtime pages Go из дополнительной лекции.

    Reserved virtual memory не равно resident memory¶

    Runtime может зарезервировать большие диапазоны address space:

    virtual addresses есть

    но это не означает:

    все backed physical RAM прямо сейчас

    Отсюда большой VSS.

    На 64-bit системе virtual address space огромен, поэтому reservation сама по себе не означает проблему.

    RSS¶

    Resident Set Size примерно отвечает:

    Какие страницы процесса сейчас считаются resident в physical memory?

    Но даже RSS не равен:

    live Go heap

    Потому что туда могут попадать:

    heap
goroutine/OS stacks
runtime metadata
code/data pages
mmap
native/cgo memory
shared mappings accounting

    Page fault¶

    Если процесс обращается к virtual page, которая еще не имеет нужного physical mapping/residency, CPU вызывает fault.

    Не каждый page fault означает:

    диск тормозит

    Есть minor faults, которые kernel способен обслужить без чтения с storage.

    Есть major faults, для которых может понадобиться I/O.

    Поэтому фраза:

    page fault = диск

    слишком грубая.

    Почему newly allocated memory может не сразу появиться в RSS целиком¶

    Программа может запросить большой диапазон:

    buf := make([]byte, 1<<30)

    Но детали physical commitment зависят от того, какие pages реально touched и от поведения OS/runtime.

    Полезная общая идея:

    virtual allocation
≠
немедленно физически записанный 1 GiB DRAM

    Почему touching memory имеет цену¶

    Если пройти весь buffer:

    for i := range buf {
    buf[i] = 1
}

    мы заставляем систему реально работать с соответствующими pages.

    Получаем:

    page mappings
zeroing
physical backing
memory bandwidth
cache traffic

    То есть allocation benchmark и benchmark полного memory initialization могут измерять разные вещи.

    Kubernetes/cgroup добавляет еще один слой¶

    Процесс видит virtual memory.

    Go runtime видит свои memory classes.

    Container runtime/kernel ведет cgroup accounting.

    Получаем:

    Go runtime metrics
↓
process mappings / RSS
↓
cgroup memory accounting
↓
host physical memory

    Это четыре разных взгляда.

    Поэтому memory incident нельзя диагностировать одной цифрой.

    Блок 24. Memory leak в языке с GC¶

    90. Что практически называть leak¶

    Полезная engineering-модель:

    Memory остается reachable/retained существенно дольше, чем требуется приложению, и usage неконтролируемо растет.

    GC при этом может работать абсолютно правильно.

    91. Unbounded cache¶

    var cache = map[string][]byte{}

func put(key string, data []byte) {
    cache[key] = data
}

    Если entries никогда не удаляются:

    global root
↓
map
↓
all entries

    GC ничего не сможет сделать.

    92. Slice удерживает большой backing array¶

    big := make([]byte, 100<<20)

small := big[:10]
return small

    Логически возвращаем:

    10 bytes

    Но small продолжает ссылаться на тот же backing array.

    В результате:

    10-byte view
↓
100 MB backing array retained

    Иногда имеет смысл скопировать маленький фрагмент в отдельный compact buffer.

    Но только если retention действительно проблема.

    93. Queue backlog¶

    Producer быстрее consumer:

    producer
>>>>>>>>>>>>>
queue
>>>>>
consumer

    Queue size:

    1k
10k
100k
1M

    Каждый queued element reachable.

    GC ничего не удаляет.

    Это не «GC leak».

    Это backpressure problem, проявившаяся ростом memory.

    94. Goroutine leak¶

    go func() {
    result := <-ch
    process(result)
}()

    Если никто никогда не отправит:

    goroutine blocked forever

    Она удерживает:

    stack
runtime metadata
references from stack

    Поэтому:

    goroutine leak
↓
memory retention

    95. Timer / ticker / lifecycle problems¶

    Long-lived timers, tickers и background goroutines при неправильном lifecycle могут удерживать references и resources дольше ожидаемого.

    Полезные вопросы:

    кто владелец?
кто завершает?
когда reference исчезает?
как работает cancellation?

    Что важно запомнить¶

    1. GC удаляет unreachable objects, а не «ненужные бизнесу».
    2. Cache, queue и goroutine leaks обычно сохраняют reachability.
    3. Маленький slice способен удерживать большой backing array.
    4. Backpressure может выглядеть как memory leak.
    5. Lifetime ownership важнее самого наличия GC.

    Вопрос:

    Углубление. Heap profile — это sampling, а не бухгалтерская книга каждого объекта¶

    pprof специально не отслеживает каждую allocation с полным stack trace.

    Это было бы слишком дорого для production.

    Heap profiling использует sampling.

    Следствие:

    Маленькие значения и редкие allocation sites могут иметь статистическую погрешность.

    Но большие устойчивые hotspots обычно видны хорошо.

    Sample type нужно выбирать осознанно¶

    Один и тот же profile можно смотреть по разным sample types.

    Например:

    inuse_space
inuse_objects
alloc_space
alloc_objects

    В pprof можно переключать sample index.

    space

    отвечает про bytes.

    objects

    про count.

    inuse

    про то, что остается live в snapshot.

    alloc

    про cumulative allocation traffic.

    5 GB/s allocation rate

    Cumulative:

    18 TB allocated

    При этом почти все objects быстро умирают.

    200 MB

    RSS:

    300 MB

    Если цель:

    Профилирование — measurement experiment. Нужно понимать, что именно вы заставили runtime сделать.

    Блок 33. Go 1.27: goroutineleak profile¶

    128. Новая возможность¶

    В Go 1.27 generally available отдельный profile:

    goroutineleak

    Endpoint:

    /debug/pprof/goroutineleak

    Он использует reachability information runtime/GC, чтобы находить определенный класс goroutines, permanently blocked на поддерживаемых concurrency primitives и не способных разблокироваться.

    покажи все goroutines

    автоматически выдели определяемый runtime класс permanent leaks

    Это не oracle.

    могут не попадать в этот profile.

    goroutineleak empty

доказательство отсутствия всех goroutine leaks

    Что важно запомнить¶

    1. Stack/heap placement в Go — решение compiler/runtime, а не прямое следствие синтаксиса.

    2. Главный вопрос — lifetime. Если value должен пережить текущий frame или compiler не может доказать обратное, может потребоваться heap storage.

    3. Pointer не означает heap. new(T) не означает heap. Локальная переменная не гарантирует stack.

    4. Stack allocation обычно значительно дешевле и не создает отдельной GC work.

    5. Цена heap allocation — не только момент allocation. Object позже может увеличивать marking, sweeping, memory bandwidth и GC assist work.

    6. Allocation rate и live heap — разные характеристики. Маленький live heap может сосуществовать с огромным GC churn.

    7. GC смотрит reachability, а не бизнес-смысл. Поэтому unbounded cache, queue backlog и goroutine leaks создают memory retention при корректном GC.

    8. Go GC выполняет основную mark work concurrent с application, но GC все равно потребляет CPU.

    9. Маленькая STW pause не доказывает, что GC дешевый. Нужно смотреть total GC CPU, cycles, assists и allocation rate.

    10. GOGC регулирует trade-off memory ↔ CPU. GOMEMLIMIT задает soft memory budget runtime.

    11. Слишком маленький memory budget может сделать приложение CPU-bound через частый GC и assists.

    12. Heap memory и RSS — разные уровни. Освобождение object для Go allocator не означает мгновенный возврат physical pages ОС.

    13. CPU profile отвечает на вопрос «где тратится CPU». Он не объясняет ожидание DB/network автоматически.

    14. inuse_space помогает искать retention. alloc_space — allocation churn.

    15. Goroutine profile показывает все goroutines; Go 1.27 goroutineleak дополнительно умеет автоматически находить определенный класс permanently blocked leaks.

    16. Оптимизация начинается с измерения. Правильная цепочка: symptom → metrics → profile → source → change → повторное measurement.

    Финальный инженерный вывод:

    Memory performance в Go начинается не с GC knobs. Она начинается с lifetime данных и allocation patterns приложения. Runtime может очень быстро выделять memory и эффективно собирать мусор, но под нагрузкой даже маленькие лишние allocations умножаются на RPS, превращаются в GC work, занимают CPU и начинают влиять на tail latency. Поэтому задача backend-разработчика — понимать, какую работу его код заставляет runtime выполнять, измерять эту работу и устранять действительно дорогие места.
