    3. Память Go, GC и pprof¶

    Материал ориентирован на Go 1.27.x.

    Во всей лекции разделяем три уровня:

    • гарантии языка — что обещает Go;
    • решения компилятора и рантайма — стек/хип, эскейп-анализ, GC и оптимизации;
    • поведение в продакшене — аллокации, CPU на GC, RSS, задержки и утечки.

    С чего вообще начинается разговор о памяти¶

    Возьмём обычный HTTP-обработчик:

    func handler(w http.ResponseWriter, r *http.Request) {
    user := User{
        ID:   42,
        Name: "Alice",
    }

    data, _ := json.Marshal(user)
    w.Write(data)
}

    На уровне бизнес-кода всё выглядит безобидно.

    А теперь продакшен:

    CPU = 95%
RSS = 1.8 GiB
p99 = 900 ms
CPU на GC высокий
goroutine = 40 000

    И начинается знакомый разговор:

    «Наверное, GC жрёт память».

    А вот здесь и начинается расследование.

    GC не создаёт ваши объекты из воздуха.

    Сначала код создаёт данные.

    У данных появляется время жизни.

    Компилятор решает, где их разместить.

    Приложение удерживает часть объектов достаточно долго.

    Хип растёт.

    И только после этого GC получает работу.

    Главная цепочка лекции:

    значение в коде
↓
время жизни
↓
эскейп-анализ
↓
стек или хип
↓
аллокации
↓
достижимость
↓
GC
↓
CPU / давление на память
↓
pprof
↓
конкретная строка кода

    После этой лекции фразы:

    «указатель значит хип»
    «GC съел память»
    «маленькая пауза GC значит GC дешёвый»
    «RSS растёт — значит утечка»

    должны вызывать один вопрос:

    Откуда именно следует этот вывод?

    1. Главный вопрос памяти — время жизни данных¶

    Самое вредное упрощение:

    локальная переменная → стек
new() → хип
указатель → хип

    Эта таблица ломается почти сразу.

    Полезнее спрашивать:

    Как долго значение должно существовать и кто может продолжать на него ссылаться?

    Например:

    func answer() int {
    x := 42
    return x
}

    x нужен только во время вызова answer.

    Теперь:

    func answer() *int {
    x := 42
    return &x
}

    Функция закончилась.

    Но вызывающий код всё ещё получил адрес x.

    Значит, время жизни значения уже не совпадает со временем жизни кадра функции.

    Вот здесь появляется задача компилятора:

    семантика программы
↓
какое время жизни нужно значению?
↓
где его безопасно разместить?

    2. Стек: память, связанная с выполнением функций¶

    При вызове функции ей нужна память для текущего выполнения.

    Упрощённо кадр стека можно представить так:

    foo()

┌─────────────────┐
│ аргументы       │
│ локальные данные│
│ временные данные│
│ служебные данные│
└─────────────────┘

    Функции вызывают друг друга:

    main
↓
handle
↓
parse
↓
validate

    На стеке goroutine появляются кадры:

    ┌────────────┐
│ validate   │
├────────────┤
│ parse      │
├────────────┤
│ handle     │
├────────────┤
│ main       │
└────────────┘

    validate закончилась — её кадр больше не нужен.

    Здесь и находится главное удобство стека:

    Время жизни памяти естественно следует структуре вызовов.

    3. Почему аллокация на стеке обычно дешёвая¶

    Очень грубая модель:

    есть указатель стека
↓
сдвинули границу
↓
получили место

    Функция завершилась:

    кадр больше не нужен
↓
граница возвращается назад

    Не нужно отдельно искать каждый объект.

    Не нужно потом выяснять, когда именно его можно освободить.

    Поэтому аллокация на стеке обычно значительно дешевле аллокации в хипе.

    Но здесь важно не создать новый миф.

    Стек — не «особая быстрая память процессора».

    Это обычная память процесса, организованная вокруг выполнения функций.

    4. У каждой goroutine свой стек¶

    Связь с лекцией про рантайм прямая:

    G1 → stack1
G2 → stack2
G3 → stack3
...

    Если одновременно живёт 100 000 goroutine, у каждой есть собственное состояние стека.

    Теперь вопрос:

    Если каждой сразу выдать огромный стек, насколько дешёвой останется goroutine?

    Недолго.

    Поэтому Go использует растущие стеки.

    Goroutine начинает с сравнительно небольшого стека, а рантайм может увеличить его при необходимости.

    5. Стек может расти¶

    Представим глубокую цепочку вызовов:

    f1
↓
f2
↓
f3
↓
...
↓
f1000

    Следующий кадр перестал помещаться.

    Рантайм должен получить больше места.

    Упрощённо:

    старый стек слишком мал
↓
получить больший стек
↓
скопировать активные кадры
↓
скорректировать нужные указатели
↓
продолжить goroutine

    Вот здесь модель «стек — фиксированный кусок памяти» заканчивается.

    6. Почему стек нельзя просто скопировать байт-в-байт¶

    Пусть:

    func f() {
    x := 10
    p := &x
    use(p)
}

    Если x находится на стеке, p содержит адрес внутри этого стека.

    Старый стек:

    0x100000 ...

    Новый:

    0x500000 ...

    После простого копирования p продолжил бы указывать по старому адресу.

    Значит рантайм должен знать:

    Где в кадре лежат указатели, а где обычные числа?

    Компилятор создаёт точные метаданные о расположении указателей.

    Они нужны и для переноса стека, и позже для GC.

    Вот здесь компилятор и рантайм начинают работать как одна система.

    7. Стек тоже стоит денег¶

    Фраза:

    «goroutine почти бесплатная»

    полезна только как сравнение с потоком ОС.

    Каждая живая goroutine удерживает:

    стек
+
метаданные рантайма
+
ссылки из стека
+
объекты в хипе, достижимые через эти ссылки

    Поэтому утечка из 100 000 goroutine — проблема памяти даже до учёта прикладных объектов.

    Особенно если каждая goroutine держит:

    • запрос;
    • буфер;
    • контекст;
    • результат;
    • граф DTO;
    • соединение;
    • таймер.

    8. Хип появляется, когда времени жизни кадра уже недостаточно¶

    func createUser() *User {
    u := User{ID: 42}
    return &u
}

    createUser закончилась.

    Но объект всё ещё нужен вызывающему коду.

    Значит его хранение нельзя привязать только к кадру функции.

    Вот здесь появляется хип.

    Полезная модель:

    стек
→ время жизни следует структуре вызовов

хип
→ время жизни определяется достижимостью

    Это важнее определения:

    Хип — область динамической памяти.

    Нас интересует именно время жизни данных.

    9. Стек и хип — не синтаксические конструкции языка¶

    Go не обещает:

    new(T) → обязательно хип
&x     → обязательно хип
local  → обязательно стек

    Компилятор выбирает размещение, сохраняя семантику программы.

    Поэтому новая версия компилятора может изменить число аллокаций без изменения исходного кода.

    Это нормально.

    Размещение — решение компилятора и рантайма.

    10. new(T) не означает хип¶

    func f() int {
    p := new(int)
    *p = 42
    return *p
}

    На уровне языка new(int) создаёт значение и возвращает указатель.

    Но если компилятор доказывает:

    указатель не переживает вызов
↓
значение не нужно после завершения функции

    отдельная аллокация в хипе может не понадобиться вообще.

    Поэтому:

    new
≠
гарантированная аллокация в хипе

    11. &x тоже не означает хип¶

    func f() int {
    x := 42
    p := &x
    return *p
}

    Указатель существует.

    Но он никуда не уходит.

    Компилятор может оставить значение на стеке или оптимизировать сильнее.

    Правильный вопрос:

    куда уходит ссылка?
↓
кто может её сохранить?
↓
как долго она нужна?

    12. Локальная переменная может попасть в хип¶

    func counter() func() int {
    n := 0

    return func() int {
        n++
        return n
    }
}

    counter() завершилась.

    Замыкание продолжает использовать n.

    Значит состояние должно жить дольше исходного кадра.

    Синтаксически n локальная переменная.

    По времени жизни — уже нет.

    13. Эскейп-анализ¶

    Эскейп-анализ — анализ, с помощью которого компилятор пытается определить, может ли значение пережить текущий кадр функции и куда уходят ссылки на него.

    func makeID() *int {
    id := 42
    return &id
}

    Компилятор видит:

    id
↓
&id
↓
return
↓
вызывающий код

    Ссылка выходит за время жизни кадра.

    Говорят:

    `id` уходит в хип

    Но важно не создать новое плохое правило:

    есть указатель → значение обязательно уходит в хип

    Нет.

    Эскейп-анализ смотрит на поток ссылок и время жизни.

    14. Что часто приводит к уходу значения в хип¶

    Типичные случаи:

    возврат указателя
замыкание
сохранение в более долгоживущий объект
передача в независимо живущую goroutine
вызов, про который компилятор не может достаточно доказать
слишком большой локальный объект

    Например:

    func start() {
    x := 42

    go func() {
        fmt.Println(x)
    }()
}

    start() может завершиться раньше новой goroutine.

    Захваченное состояние должно оставаться валидным.

    Причина не в слове go.

    Причина во времени жизни.

    15. Большой локальный объект тоже не гарантирует стек¶

    func f() {
    var buf [10 << 20]byte
    use(&buf)
}

    Даже если время жизни очевидно короткое, огромный объект создаёт давление на стек.

    Компилятор может выбрать другое размещение.

    Итоговая модель:

    время жизни
+
что смог доказать компилятор
+
ограничения реализации
↓
решение о размещении

    16. Инлайнинг может изменить аллокации¶

    До инлайнинга компилятор видит функцию отдельно.

    После инлайнинга её тело оказывается в контексте вызывающего кода.

    Иногда теперь можно доказать:

    ссылка не переживает вызов

    и убрать аллокацию в хипе.

    Поэтому обычный рефакторинг или обновление компилятора способны изменить:

    allocs/op

    даже если бизнес-логика кажется той же.

    17. Как посмотреть решение компилятора¶

    Практический инструмент:

    go build -gcflags="-m=2" ./...

    Можно увидеть сообщения вроде:

    x escapes to heap
moved to heap: x
does not escape

    Но сейчас специально не делаем следующую ошибку:

    Компилятор написал escapes — значит это нужно срочно исправлять.

    Эскейп-анализ объясняет решение компилятора.

    Он не отвечает:

    Это вообще узкое место?

    18. Одна аллокация без частоты ничего не значит¶

    Одна аллокация:

    256 B

    сама по себе почти ничего не говорит.

    Теперь:

    256 B
×
2 000 000 операций/с
≈
512 MB/с

    Совсем другая система.

    Поэтому производительность начинается с:

    частота × стоимость

    а не с охоты за каждой аллокацией.

    19. Бенчмарк: сколько памяти мы реально выделяем¶

    func BenchmarkEncode(b *testing.B) {
    for b.Loop() {
        encode(user)
    }
}

    Запуск:

    go test -bench=. -benchmem

    Например:

    850 ns/op
512 B/op
7 allocs/op

    B/op — сколько байт хипа в среднем аллоцируется на одну операцию.

    allocs/op — сколько аллокаций приходится на одну операцию.

    Это поток аллокаций.

    Не объём памяти, который останется жив после операции.

    20. Число аллокаций, объём аллокаций и живой хип — разные вещи¶

    Сервис может аллоцировать гигабайты в секунду и держать живой хип всего 200 MiB.

    И наоборот — почти ничего нового не аллоцировать, но удерживать 4 GiB старых объектов.

    Поэтому различаем:

    число аллокаций
аллокации в байтах
живой хип

    21. Две разные проблемы: поток аллокаций и удержание¶

    Сервис A:

    живой хип = 200 MiB
скорость аллокаций = 5 GiB/с

    Хип почти не растёт.

    Но рантайм постоянно создаёт и собирает временные объекты.

    Проблема — огромный поток короткоживущих аллокаций.

    Сервис B:

    живой хип = 3 GiB
скорость аллокаций = 100 MiB/с

    Нового создаётся мало.

    Но очень много памяти долго остаётся достижимой.

    Проблема — удержание.

    Обе ситуации называются «у нас проблема с памятью».

    Механизмы совершенно разные.

    22. Откуда в бэкенде берутся аллокации¶

    Обычные источники:

    • make;
    • рост среза;
    • map;
    • преобразования string / []byte;
    • JSON;
    • форматирование;
    • интерфейсы в конкретных путях вызова;
    • замыкания;
    • преобразования DTO;
    • буферы.

    Например:

    var xs []int

for i := 0; i < 1_000_000; i++ {
    xs = append(xs, i)
}

    Когда cap заканчивается:

    старый базовый массив заполнен
↓
нужен больший
↓
новая аллокация
↓
копирование
↓
срез указывает на новый массив

    Если примерный размер известен:

    xs := make([]int, 0, expected)

    можно уменьшить количество расширений.

    Но «всегда выделяй максимальный cap заранее» — тоже плохое правило.

    Слишком большая ёмкость сама удерживает память.

    23. JSON: маленькая цена умножается на RPS¶

    data, err := json.Marshal(response)

    Вокруг сериализации могут появляться:

    • временные буферы;
    • строки;
    • reflection;
    • DTO;
    • копирования;
    • аллокации.

    Пусть:

    20 аллокаций/запрос
×
30 000 RPS
=
600 000 аллокаций/с

    Вот здесь маленькая локальная стоимость превращается в реальную работу рантайма.

    24. Указатель — это ещё и связь между временем жизни объектов¶

    Request
↓
User
↓
Session
↓
Token

    Пока корень ведёт к Request, через него остаётся жив весь достижимый граф.

    GC не спрашивает:

    Нужен ли этот Session бизнесу?

    Он спрашивает:

    Существует ли путь от корней к объекту?

    Это достижимость.

    25. Достижимый не означает полезный¶

    var cache = map[string][]byte{}

    Приложение бесконечно делает:

    cache[id] = hugeData

    Старые записи бизнесу уже не нужны.

    Но:

    глобальный корень
↓
кеш
↓
entry
↓
[]byte

    всё ещё существует.

    GC обязан считать эти данные живыми.

    Получаем утечку памяти в программе с исправно работающим GC.

    26. Маленький срез способен удерживать огромный массив¶

    buf := make([]byte, 100<<20)
small := buf[:10]

    small логически показывает 10 байт.

    Но его указатель всё ещё ведёт в базовый массив на 100 MiB.

    small
↓
100 MiB базовый массив

    GC не может освободить «неиспользуемые 99.999 MiB» внутри живого массива.

    Иногда разумно сделать компактную копию:

    small := bytes.Clone(buf[:10])

    Цена:

    ещё одна аллокация
+
копирование

    Выигрыш:

    старый 100 MiB массив может стать недостижимым

    Вот почему:

    Меньше аллокаций всегда лучше.

    тоже неправильное правило.

    Иногда дополнительная аллокация уменьшает давление на память.

    27. Очередь буквально владеет памятью¶

    jobs := make(chan *Job, 100_000)

    Буфер канала хранит ссылки на задачи.

    канал
↓
буфер
↓
Job
↓
payload

    Пока задача находится в очереди, её данные достижимы.

    Если производитель быстрее потребителя:

    глубина очереди ↑
↓
живых объектов ↑
↓
хип ↑

    GC здесь ничего исправить не может.

    Это проблема пропускной способности и бэкпрешера, которая проявилась как рост памяти.

    28. Утечка goroutine тоже превращается в удержание памяти¶

    Заблокированная goroutine хранит стек.

    Стек содержит ссылки.

    goroutine WAITING
↓
стек
↓
запрос
↓
буфер
↓
большой граф объектов

    Поэтому утечка goroutine часто становится утечкой памяти.

    Не потому что сама G огромная.

    Потому что она удерживает граф.

    29. Контекст и замыкания тоже продлевают время жизни¶

    ctx = context.WithValue(ctx, key, hugeObject)

    Если контекст случайно сохранили в долгоживущей структуре:

    долгоживущий владелец
↓
контекст
↓
hugeObject

    объект живёт вместе с этой цепочкой.

    То же самое с замыканием:

    func build() func() {
    huge := make([]byte, 100<<20)

    return func() {
        fmt.Println(huge[0])
    }
}

    Пока замыкание достижимо, huge тоже достижим.

    Очень часто проблема памяти находится не в аллокаторе.

    Она находится в ссылке, которая живёт слишком долго.

    30. Зачем нужен GC¶

    Для стека всё просто:

    кадр закончился
→ память кадра больше не нужна

    Для хипа:

    A → B → C

    нужно понять, остался ли хоть один путь к объектам.

    Go использует трассирующий сборщик мусора.

    Основная идея:

    корни
↓
обойти достижимый граф
↓
всё недостижимое можно считать мусором

    31. Что такое корни¶

    Трассировка должна с чего-то начаться.

    Упрощённо корни включают:

    • глобальные переменные;
    • стеки goroutine;
    • внутренние корни рантайма.

    Из них GC идёт в хип.

    корни
↓
A
├── B
└── C

    Если объект не достижим ни по одному пути от корней, его можно собирать.

    И вот важная связь с прошлой лекцией:

    100 000 goroutine влияют на GC не только памятью стеков. Эти стеки ещё и нужно учитывать как корни.

    32. Маркировка и очистка отвечают на разные вопросы¶

    Маркировка отвечает:

    Какие объекты достижимы?

    Упрощённо:

    корень
↓
пометить объект
↓
просканировать его указатели
↓
пометить следующие объекты
↓
повторять

    После маркировки:

    помеченные = живые
непомеченные = мусор

    Очистка отвечает:

    Какие участки хипа аллокатор снова может использовать?

    То есть:

    маркировка
→ определяем живые объекты

очистка
→ возвращаем свободное место аллокатору

    33. Трёхцветная модель¶

    Для объяснения трассирующего GC удобно представить три состояния.

    white
→ объект ещё не обнаружен

grey
→ объект обнаружен, но его ссылки ещё нужно обработать

black
→ объект обнаружен и обработан

    Это учебная модель.

    Не нужно представлять, что у каждого Go-объекта буквально хранится поле color.

    34. Какой GC используется в Go¶

    На высоком уровне сборщик Go можно описать так:

    трассирующий
точный
конкурентный
параллельный
маркировка и очистка
непоколенческий
неуплотняющий

    Разберём смысл.

    Трассирующий — идёт от корней по ссылкам.

    Точный — рантайм знает, где находятся настоящие Go-указатели.

    Конкурентный — значительная часть работы GC идёт одновременно с приложением.

    Параллельный — несколько воркеров GC могут работать на разных CPU.

    Маркировка и очистка — отдельно определяем живой граф и отдельно возвращаем свободную память аллокатору.

    Непоколенческий — основной GC не построен вокруг молодых/старых поколений.

    Неуплотняющий — живые объекты хипа обычно не перемещаются только ради уплотнения памяти.

    Это набор компромиссов.

    Не «лучший GC вообще».

    35. Почему одинаковое количество байт может стоить GC по-разному¶

    Сравним:

    buf := make([]byte, 100<<20)

    и:

    nodes := make([]*Node, n)

    Пусть оба занимают примерно 100 MiB.

    В []byte нет ссылок на другие Go-объекты.

    В []*Node — миллионы указателей.

    GC должен проходить по этим ссылкам.

    Поэтому:

    100 MiB сырых байт
≠
100 MiB памяти, насыщенной указателями

    по стоимости сканирования.

    Одного размера живого хипа недостаточно, чтобы оценить цену GC.

    36. Число объектов тоже имеет значение¶

    Хип A:

    1 объект × 1 GiB

    Хип B:

    50 000 000 маленьких объектов
≈ 1 GiB

    Байты похожи.

    Работа рантайма — нет.

    Большое количество объектов увеличивает:

    • метаданные;
    • количество элементов графа;
    • служебный учёт;
    • работу маркировки.

    Поэтому полезно смотреть вместе:

    байты
число объектов
сканируемый объём
скорость аллокаций

    37. Конкурентный GC: паузы стали меньше, работа не исчезла¶

    Наивная модель GC:

    приложение работает
↓
STOP THE WORLD
↓
просканировать весь хип
↓
собрать мусор
↓
продолжить приложение

    Если хип большой, пауза растёт.

    Для бэкенда это означает скачок задержки.

    Go переносит значительную часть маркировки в конкурентную фазу:

    горутины приложения
+
воркеры GC

    работают одновременно.

    Хорошо?

    Да.

    Бесплатно?

    Нет.

    38. Цена конкурентного GC¶

    Стоимость распределена:

    CPU фоновых воркеров GC
+
барьеры записи
+
сканирование стеков
+
ассисты GC
+
короткие STW-паузы
+
давление на кеш и память

    Поэтому:

    маленькая STW-пауза
≠
дешёвый GC

    Сервис может иметь очень короткие паузы и одновременно отдавать заметную долю CPU сборщику.

    39. Барьер записи¶

    GC уже просканировал объект A.

    Приложение делает:

    A.child = C

    Граф хипа изменился прямо во время конкурентной маркировки.

    Если GC ничего об этом не узнает, можно потерять живую ссылку.

    Поэтому нужные записи указателей сопровождаются дополнительной работой рантайма.

    Это барьер записи.

    Для основной модели достаточно:

    приложение меняет граф указателей
↓
барьер записи сообщает об этом GC
↓
GC сохраняет корректность маркировки

    40. Green Tea не меняет смысл достижимости¶

    Начиная с Go 1.26 Green Tea используется как GC по умолчанию.

    Для этой лекции важно понять не внутренние очереди Green Tea, а смысл изменения.

    Основная проблема трассировки графа:

    прочитать объект
↓
увидеть указатель
↓
пойти в другое место памяти
↓
возможный промах кеша

    Green Tea лучше организует работу маркировки и сканирования с точки зрения локальности памяти.

    Но программная модель остаётся прежней:

    достижимый → живой
недостижимый → можно собрать

    Green Tea не исправляет:

    • бесконечный кеш;
    • растущую очередь;
    • утечку goroutine;
    • слишком долгий жизненный цикл объектов.

    41. Цикл GC — это не одна пауза¶

    Упрощённо:

    приложение
↓
условие запуска GC
↓
короткая STW-подготовка
↓
конкурентная маркировка
├── воркеры GC
├── сканирование стеков
├── барьеры записи
└── ассисты
↓
завершение маркировки
↓
короткая STW-фаза
↓
очистка / повторное использование памяти

    Поэтому вопрос:

    «Сколько длился GC?»

    нужно уточнять.

    Что измерено?

    • полный цикл;
    • STW-пауза;
    • CPU сборщика;
    • время ассистов?

    Это разные вещи.

    42. Почему GC вообще запускается¶

    Хип растёт.

    Рантайм не может ждать момента:

    память закончилась

    Сборщик должен стартовать заранее и закончить работу до чрезмерного роста хипа.

    Этим управляет пейсер GC.

    Для нашей модели достаточно:

    скорость аллокаций ↑
↓
хип растёт быстрее
↓
GC должен стартовать раньше / работать активнее

    43. GOGC: обмен памяти на CPU¶

    По умолчанию:

    GOGC=100

    Очень грубая модель:

    после GC живой хип = 500 MiB
↓
при GOGC=100
следующая цель порядка 1 GiB

    Реальная модель сложнее и учитывает корни и работу пейсера.

    Но смысл важнее точной формулы.

    Низкий GOGC:

    GC чаще
↓
хип обычно меньше
↓
CPU на GC обычно выше

    Высокий GOGC:

    GC реже
↓
хип больше
↓
CPU на GC обычно ниже

    То есть GOGC управляет компромиссом:

    память ↔ CPU

    44. Почему нельзя просто поставить огромный GOGC¶

    Допустим контейнер имеет:

    лимит памяти = 1 GiB

    Большой GOGC разрешает хипу сильнее вырасти между циклами GC.

    Сборщик работает реже.

    CPU можно сэкономить.

    Но памяти требуется больше.

    В контейнере это может приблизить процесс к OOM.

    Поэтому:

    GC реже

    не означает:

    система лучше.

    Нужна ещё абсолютная граница по памяти.

    45. GOMEMLIMIT: мягкий бюджет памяти рантайма¶

    Например:

    GOMEMLIMIT=450MiB

    Это ориентир для памяти, которой управляет рантайм Go.

    Ключевое слово — мягкий.

    Это не:

    жёсткий лимит RSS

    и не:

    HeapAlloc никогда не превысит значение

    Рантайм старается удерживать управляемую память около заданного бюджета, но обязан сохранять возможность выполнять приложение и сам GC.

    46. Почему GOMEMLIMIT мягкий¶

    Представим:

    GOMEMLIMIT = 500 MiB
живой набор = 490 MiB

    Приложение всё ещё должно:

    • принимать запросы;
    • создавать временные объекты;
    • выполнять код рантайма;
    • заканчивать цикл GC.

    Если запретить любой временный выход выше бюджета, можно получить почти непрерывный GC.

    Поэтому лимит мягкий.

    47. Маленький бюджет памяти может проявиться как проблема CPU¶

    Цепочка:

    бюджет памяти ↓
↓
цель хипа ↓
↓
GC запускается чаще
↓
CPU на GC ↑
↓
ассисты ↑
↓
CPU для обработчиков ↓
↓
задержка ↑

    Команда смотрит на график:

    CPU = 90%

    и начинает искать тяжёлый алгоритм.

    А первопричина — слишком тесный бюджет памяти.

    Память и CPU здесь связаны напрямую.

    48. Ассист GC: запрос сам начинает помогать сборщику¶

    Если приложение аллоцирует быстрее, чем фоновые воркеры успевают маркировать объекты, рантайм не может бесконечно позволять хипу расти.

    Тогда аллоцирующая goroutine может получить часть работы GC.

    Упрощённо:

    HTTP-запрос
↓
аллокация
↓
рантайм видит долг перед GC
↓
goroutine выполняет часть маркировки
↓
возвращается к прикладному коду

    Это ассист GC.

    Вот почему GC способен увеличивать задержку запроса вообще без большой STW-паузы.

    49. Почему медленная зависимость увеличивает память¶

    Очень важная продакшен-связь.

    Пусть:

    RPS = 10 000
среднее время запроса = 20 ms

    По закону Литтла:

    запросы в обработке
≈
RPS × среднее время запроса

    Получаем:

    10 000 × 0.020
≈
200 запросов

    Теперь PostgreSQL замедлилась:

    среднее время = 500 ms

    Получаем:

    10 000 × 0.5
≈
5 000 запросов в обработке

    Код не изменился.

    RPS не изменился.

    Но одновременно живых состояний запроса стало в 25 раз больше.

    50. Добавим память на один запрос¶

    Пусть один незавершённый запрос удерживает в среднем:

    50 KiB

    Это могут быть:

    • DTO;
    • буферы;
    • контекст;
    • разобранное тело запроса;
    • данные трассировки;
    • состояние работы с БД.

    Нормальный режим:

    200 × 50 KiB
≈
10 MiB

    После роста задержки:

    5 000 × 50 KiB
≈
244 MiB

    Только локальные данные запросов.

    Без утечки.

    Без изменения кода.

    Без роста RPS.

    51. Получаем петлю обратной связи¶

    задержка БД ↑
↓
время жизни запроса ↑
↓
запросов в обработке ↑
↓
живой хип ↑
↓
работа GC ↑
↓
CPU для приложения ↓
↓
задержка сервиса ↑
↓
запросов в обработке ещё больше

    Вот почему инцидент с памятью нельзя расследовать отдельно от:

    • RPS;
    • задержки;
    • глубины очередей;
    • состояния зависимостей.

    Иногда память растёт просто потому, что система стала медленнее.

    52. Давление на память¶

    Давление на память — режим, когда процесс всё ближе подходит к доступному бюджету памяти и рантайму остаётся всё меньше пространства для роста хипа.

    Типичная цепочка:

    живые объекты ↑
+
временные аллокации ↑
+
стеки goroutine ↑
↓
давление на память
↓
GC чаще
↓
CPU на GC ↑
↓
ассисты ↑
↓
CPU для приложения ↓
↓
задержка ↑

    После этого задержка сама начинает увеличивать время жизни объектов.

    Получаем самоподдерживающуюся деградацию.

    53. Хип и RSS — разные уровни системы¶

    Допустим:

    HeapAlloc упал
RSS почти не изменился

    Первая реакция:

    Утечка.

    Не обязательно.

    Рантайм видит свои категории памяти:

    живые объекты хипа
свободная память хипа
память хипа, возвращённая ОС
стеки
метаданные рантайма

    Операционная система видит:

    виртуальную память
резидентные страницы
отображения памяти

    Это разные модели.

    54. VSS и RSS¶

    VSS — размер виртуального адресного пространства процесса.

    Большой VSS ещё не означает, что столько физической памяти занято прямо сейчас.

    RSS — приблизительно объём страниц процесса, которые сейчас находятся в физической памяти.

    Но RSS тоже не равен живому хипу Go.

    В него могут входить:

    • хип;
    • стеки goroutine;
    • стеки потоков ОС;
    • метаданные рантайма;
    • страницы кода;
    • mmap;
    • память cgo;
    • разделяемые отображения.

    Поэтому:

    живой хип
≠
RSS
≠
VSS

    55. Почему HeapAlloc может упасть, а RSS почти не измениться¶

    Было:

    HeapAlloc = 2 GiB
RSS       = 2.5 GiB

    После GC:

    HeapAlloc = 700 MiB
RSS       = 2.2 GiB

    Возможная цепочка:

    объекты стали мусором
↓
GC сделал память доступной аллокатору
↓
рантайм может переиспользовать её
↓
страницы ещё не обязательно возвращены ОС

    Это не обязательно утечка.

    56. Очистка и возврат памяти ОС — разные вещи¶

    Очистка отвечает:

    Какие участки хипа снова можно использовать внутри Go?

    ОС интересует другой вопрос:

    Какие физические страницы можно забрать у процесса?

    Для возврата неиспользуемой памяти операционной системе рантайм использует scavenger.

    Почему не отдавать всё сразу?

    Пусть нагрузка пилообразная:

    пик 4 GiB
↓
падение до 1 GiB
↓
через минуту снова 4 GiB

    Если агрессивно вернуть страницы ОС, потом придётся снова платить за:

    • получение памяти;
    • отображение страниц;
    • page fault;
    • обнуление;
    • работу ядра.

    Получается компромисс:

    быстрый повторный reuse
↔
меньший RSS

    57. Что практически считать утечкой памяти в Go¶

    Полезная инженерная формулировка:

    Память остаётся достижимой и удерживается существенно дольше, чем требуется приложению, а её объём неконтролируемо растёт.

    GC при этом может работать идеально.

    Типичные причины:

    • бесконечный кеш;
    • растущая очередь;
    • утечка goroutine;
    • маленький срез, удерживающий большой массив;
    • долгоживущий context;
    • замыкание;
    • проблемы жизненного цикла таймеров и фоновых goroutine.

    Поэтому вопрос:

    Почему GC это не удаляет?

    очень часто имеет ответ:

    Потому что программа всё ещё держит ссылку.

    58. Теперь нужны измерения: pprof¶

    До профилирования у нас только симптомы:

    CPU = 90%
RSS = 1.7 GiB
p99 = 1.2 s
goroutine = 25 000

    Из этого нельзя честно заключить:

    проблема GC

    или:

    проблема JSON

    или:

    утечка goroutine

    Нужно связать:

    потребление ресурса
↓
цепочка вызовов
↓
конкретный код

    Эту задачу решает pprof.

    59. Подключаем диагностический эндпоинт¶

    Простейший вариант:

    package main

import (
    "log"
    "net/http"
    _ "net/http/pprof"
)

func startDiagnostics() {
    go func() {
        log.Println(http.ListenAndServe("127.0.0.1:6060", nil))
    }()
}

    С default mux становятся доступны:

    /debug/pprof/
/debug/pprof/profile
/debug/pprof/heap
/debug/pprof/goroutine

    В продакшене такой эндпоинт нельзя бездумно публиковать наружу.

    Профили могут раскрывать:

    • имена функций;
    • структуру пакетов;
    • стеки;
    • внутренние пути вызовов;
    • поведение рантайма.

    Доступ нужно ограничивать.

    60. Профиль CPU отвечает на один конкретный вопрос¶

    Где процесс реально тратит CPU?

    Снять профиль за 30 секунд:

    go tool pprof \
  http://localhost:6060/debug/pprof/profile?seconds=30

    Профиль CPU использует семплирование.

    Он не записывает каждую выполненную инструкцию.

    Он статистически показывает, где процесс проводил процессорное время.

    61. flat и cum¶

    Внутри pprof:

    (pprof) top

    flat отвечает:

    Сколько семплов попало непосредственно в эту функцию?

    cum отвечает:

    Сколько семплов приходится на функцию вместе со всем деревом вызовов под ней?

    Например:

    Handler:
flat = 1%
cum  = 60%

    Сам Handler почти ничего не считает.

    Но через него проходит дорогая работа.

    Поэтому высокий cum не означает:

    Нужно переписать тело Handler.

    Нужно идти ниже по цепочке вызовов.

    62. list возвращает нас к строке кода¶

    (pprof) list FunctionName

    Нормальный путь расследования:

    CPU высокий
↓
пакет
↓
функция
↓
цепочка вызовов
↓
строка исходного кода

    Flame graph красивый.

    Но конечная цель профилирования — найти код, который создаёт стоимость.

    63. Чего профиль CPU не показывает¶

    rows, err := db.QueryContext(ctx, query)

    PostgreSQL отвечает три секунды.

    Goroutine ждёт.

    CPU почти свободен.

    Профиль CPU может выглядеть совершенно нормально.

    И это правильно.

    Ожидание БД не является процессорным временем.

    Поэтому:

    p99 высокий
CPU = 20%

    направляет расследование в сторону:

    • ожидания БД;
    • сети;
    • конкуренции за локи;
    • ожидания пула соединений;
    • очередей;
    • блокировок.

    Профиль CPU — не универсальный молоток.

    64. Как GC проявляется в профиле CPU¶

    Можно увидеть значимый CPU вокруг:

    • аллокаций;
    • фоновой маркировки;
    • ассистов GC;
    • сканирования объектов.

    Конкретные имена внутренних функций меняются между версиями рантайма.

    Нас интересует не заучивание имён.

    Нас интересует гипотеза:

    приложение создаёт слишком много работы для GC

    Следующий вопрос:

    Кто создаёт аллокации?

    Вот здесь нужен профиль аллокаций и бенчмарк.

    65. Профиль хипа отвечает сразу на несколько вопросов¶

    Снять:

    go tool pprof \
  http://localhost:6060/debug/pprof/heap

    Профиль хипа тоже использует семплирование.

    Это статистическая картина.

    Не полная бухгалтерская книга каждого объекта.

    Главное — выбрать правильный тип данных внутри профиля.

    66. inuse_space: кто связан с живыми байтами сейчас¶

    Вопрос:

    Какие места аллокации связаны с наибольшим объёмом живой памяти прямо сейчас?

    Полезно для:

    • удержания;
    • растущего живого хипа;
    • крупных буферов;
    • поиска утечек.

    Но здесь важная ловушка:

    Место аллокации не обязательно является владельцем удерживаемой ссылки.

    Память могла быть создана в json.Marshal.

    А сохранить ссылку мог глобальный кеш совершенно в другом месте.

    Профиль показывает:

    Где объект появился?

    Но вопрос:

    Почему он всё ещё жив?

    иногда приходится расследовать по структурам владения.

    67. alloc_space: кто создаёт поток аллокаций¶

    Вопрос:

    Какие цепочки вызовов исторически аллоцировали больше всего байт?

    Это уже вопрос не удержания, а аллокационного потока.

    Сервис может иметь:

    живой хип = 200 MiB
alloc_space за час = терабайты

    Противоречия нет.

    Память создавалась и быстро умирала.

    alloc_space показывает поток.

    inuse_space — текущую живую часть семплированных аллокаций.

    68. inuse_objects и alloc_objects¶

    Байты — не единственная ось.

    inuse_objects отвечает:

    Где сейчас живёт много объектов?

    alloc_objects:

    Где было создано много объектов?

    Миллионы маленьких объектов могут создавать заметную работу рантайма даже при умеренном объёме байт.

    69. Утечку лучше искать во времени¶

    Один снимок хипа отвечает:

    Что большое сейчас?

    Утечка — это обычно вопрос:

    Что систематически растёт?

    Поэтому полезно сравнивать:

    профиль t0
профиль t1
профиль t2

    Или использовать возможности pprof для сравнения профилей.

    Ментальная модель:

    после
-
до
=
что выросло

    70. Профиль goroutine: количество превращается в место ожидания¶

    go tool pprof \
  http://localhost:6060/debug/pprof/goroutine

    Допустим метрика говорит:

    goroutine = 20 000

    Это может быть нормально при 20 000 активных соединений.

    А может быть катастрофическая утечка.

    Профиль показывает стеки и места ожидания.

    Например:

    15 000 goroutine
↓
одинаковый стек
↓
blocked on channel send

    Вот это уже содержательная гипотеза.

    71. Тысячи goroutine около database/sql ещё не означают утечку¶

    Допустим множество goroutine ждут свободное соединение.

    Причины могут быть разные:

    пул слишком мал
↓
запросы стали медленнее
↓
БД деградирует
↓
транзакции слишком долго держат соединения
↓
конкурентность слишком высокая

    Профиль показывает:

    Где ждём?

    Но первопричину всё ещё нужно расследовать.

    72. Go 1.27: профиль goroutineleak¶

    В Go 1.27 доступен отдельный профиль:

    /debug/pprof/goroutineleak

    Рантайм пытается автоматически выделить определённый класс goroutine, для которых может доказать постоянную блокировку на поддерживаемых примитивах.

    Это полезный дополнительный сигнал.

    Но это не оракул.

    Пустой профиль не доказывает отсутствие всех утечек goroutine.

    Например, рантайм может не доказать проблему вокруг:

    • сети;
    • файлового ввода-вывода;
    • пользовательской синхронизации;
    • сложного жизненного цикла.

    Обычный профиль goroutine всё равно остаётся нужен.

    73. runtime/metrics: приборная панель памяти и GC¶

    Полезные группы метрик.

    Живой хип и цель:

    /gc/heap/live:bytes
/gc/heap/goal:bytes

    Сканирование:

    /gc/scan/heap:bytes
/gc/scan/stack:bytes

    CPU сборщика:

    /cpu/classes/gc/mark/assist:cpu-seconds
/cpu/classes/gc/mark/dedicated:cpu-seconds
/cpu/classes/gc/mark/idle:cpu-seconds
/cpu/classes/gc/total:cpu-seconds

    Категории памяти:

    /memory/classes/heap/objects:bytes
/memory/classes/heap/free:bytes
/memory/classes/heap/released:bytes

    Одна метрика диагноз не даёт.

    Но вместе они помогают разделить:

    живые данные
↓
поток аллокаций
↓
объём сканирования
↓
CPU на GC
↓
свободную память рантайма
↓
память, возвращённую ОС

    74. Как выбрать инструмент по симптому¶

    Симптом Первый инструмент Что ищем
    CPU высокий профиль CPU где реально тратится процессорное время
    Живой хип растёт inuse_space какие аллокации связаны с живой памятью
    CPU на GC высокий CPU + alloc_space + метрики кто создаёт поток аллокаций
    Goroutine растут профиль goroutine где и на чём они ждут
    Подозрение на постоянную утечку goroutine goroutineleak доказуемый рантаймом класс утечек
    Конкуренция за mutex профиль mutex где долго ждём лок
    Блокировки профиль блокировок / трассировка ожидания каналов и синхронизации
    p99 высокий, CPU низкий трассировка + метрики зависимостей БД / сеть / пул / очередь
    HeapAlloc упал, RSS нет метрики рантайма + ОС/cgroup свободная / возвращённая / внешняя память

    Главное правило:

    Инструмент выбирается под вопрос.

    75. pprof — это расследование¶

    Плохой процесс:

    CPU высокий
↓
открыли flame graph
↓
увидели рантайм
↓
«GC плохой»

    Нормальный:

    симптом
↓
базовые метрики
↓
гипотеза
↓
правильный профиль
↓
репрезентативная нагрузка
↓
цепочка вызовов
↓

↓
изменение
↓
повторное измерение

    Без последнего шага оптимизация остаётся гипотезой.

    76. Продакшен-пример: медленная БД выглядит как инцидент с памятью¶

    До инцидента:

    RPS = 8 000
задержка БД = 10 ms
живой хип = 300 MiB
CPU на GC = 8%

    После деградации:

    RPS = 8 000
задержка БД = 400 ms
живой хип = 1.1 GiB
CPU на GC = 25%
p99 растёт

    Команда видит:

    память ↑
GC ↑

    и начинает искать утечку.

    Но один бесконечный кеш не находится.

    77. Восстанавливаем причинную цепочку¶

    По закону Литтла:

    8 000 × 0.010
≈ 80 запросов в обработке

    После деградации:

    8 000 × 0.400
≈ 3 200 запросов в обработке

    Каждый запрос удерживает:

    • тело запроса;
    • DTO;
    • контекст;
    • состояние работы с БД;
    • буферы ответа;
    • данные трассировки.

    Все эти объекты корректно достижимы.

    Получаем:

    задержка БД ↑
↓
время жизни запроса ↑
↓
запросов в обработке ↑
↓
живой хип ↑
↓
работа GC ↑
↓
давление на CPU ↑
↓
задержка сервиса ↑

    GC усиливает проблему.

    Но первопричина — деградация зависимости и недостаточное ограничение конкурентности.

    78. Продакшен-пример: слишком много краткоживущих аллокаций¶

    Симптом:

    RPS = 20 000
CPU = 92%
RSS = 700 MiB
живой хип = 250 MiB
p99 = 800 ms

    Живой хип не выглядит огромным.

    Но CPU на GC высокий.

    Профиль CPU показывает:

    JSON
аллокации
ассисты GC

    alloc_space ведёт в:

    Handler
↓
Transform
↓
json.Marshal

    Бенчмарк:

    40 allocs/op
18 KiB/op

    После исправления:

    18 allocs/op
7 KiB/op

    Цепочка:

    скорость аллокаций ↓
↓
работа GC ↓
↓
ассисты ↓
↓
CPU для приложения ↑
↓
p99 ↓

    Узкое место GC очень часто начинается в паттерне аллокаций приложения.

    79. Продакшен-пример: удержание памяти¶

    Симптом:

    живой хип:
500 MiB
700 MiB
950 MiB
1.3 GiB

    Количество goroutine стабильно.

    inuse_space ведёт к большим []byte, которые складываются в кеш.

    Политики удаления нет.

    глобальный кеш
↓
записи
↓
буферы

    Все объекты достижимы.

    GC работает правильно.

    Проблема — владение и жизненный цикл данных кеша.

    80. Продакшен-пример: слишком маленький GOMEMLIMIT¶

    После уменьшения бюджета памяти:

    RSS ниже
CPU: 45% → 85%
p99 ×2

    Утечки хипа нет.

    Метрики показывают:

    цель хипа близко к живому хипу
циклы GC чаще
ассисты ↑

    Цепочка:

    слишком тесный бюджет памяти
↓
GC чаще
↓

↓

↓
задержка выше

    Настройка памяти проявилась как проблема CPU.

    Сначала классифицируем симптом:

    CPU?

    Потом смотрим динамику:

    Один снимок легко вводит в заблуждение.

    Но главный вопрос остаётся:

    86. Проверяем внешнюю причину¶

    Рост памяти может быть вторичным симптомом:

    БД стала медленной
сеть стала медленной
потребитель очереди отстаёт
пул исчерпан
внешняя система отвечает поздно

    Во всех случаях механизм один:

    время операции ↑
↓
время жизни объектов ↑
↓
живая память ↑

    Поэтому расследование памяти без метрик задержки и зависимостей легко уходит в неправильную сторону.

    87. Антипаттерны оптимизации памяти¶

    «Всё переведём на указатели»¶

    Часто получаем:

    косвенных обращений ↑
кандидатов на хип ↑
указателей в графе ↑
локальность хуже
работа GC ↑

    Указатели нужны по смыслу и владению.

    Не как универсальная оптимизация.

    «Всё завернём в sync.Pool»¶

    sync.Pool полезен там, где профиль показал дорогой и повторно используемый паттерн аллокаций.

    Цена:

    • более сложный жизненный цикл;
    • необходимость очищать объект;
    • риск старых данных;
    • больший рабочий набор памяти.

    «Поднимем GOGC»¶

    Это обмен:

    CPU на GC ↓
за
память ↑

    Если проблема уже в лимите памяти, можно сделать хуже.

    «Снизим GOMEMLIMIT и точно не словим OOM»¶

    Слишком маленький лимит может превратить сервис в почти постоянную работу GC.

    «STW 100 μs — значит GC ни при чём»¶

    Цена конкурентного GC может находиться в:

    • фоновых воркерах;
    • барьерах записи;
    • ассистах;
    • пропускной способности памяти;
    • давлении на кеш.

    STW — только одна часть.

    88. Границы гарантий¶

    Важно не смешивать уровни.

    Язык гарантирует¶

    • семантику значений;
    • семантику указателей;
    • корректность времени жизни;
    • модель памяти.

    Компилятор и рантайм решают¶

    • стек или хип;
    • конкретные результаты эскейп-анализа;
    • оптимизации;
    • устройство GC;
    • рост стека;
    • внутренние категории памяти;
    • алгоритмы Green Tea.

    Продакшен показывает фактические¶

    • аллокации;
    • живой хип;
    • CPU на GC;
    • RSS;
    • задержку;
    • утечки.

    Корректность кода нельзя строить на том, что конкретная версия компилятора сегодня положила значение на стек.

    Но производительность этого решения можно и нужно измерять.

    Что важно запомнить¶

    1. Главный вопрос памяти в Go — время жизни данных, а не синтаксис new, & или локальной переменной.
    2. Стек связан с кадрами вызовов; хип нужен, когда время жизни нельзя привязать к текущему кадру.
    3. Стек/хип выбирает компилятор и рантайм. Указатель сам по себе не означает хип.
    4. Эскейп-анализ исследует поток ссылок и время жизни; его вывод нужно связывать с бенчмарком.
    5. Скорость аллокаций и живой хип — разные характеристики. Большой поток краткоживущих объектов и удержание требуют разной диагностики.
    6. GC работает с достижимостью, а не с бизнес-смыслом. Кеш, очередь и goroutine могут законно удерживать огромный граф объектов.
    7. Память, насыщенная указателями, и большое число объектов могут стоить GC дороже такого же количества сырых байт.
    8. Конкурентный GC уменьшает длинные STW-паузы, но продолжает потреблять CPU, память и пропускную способность кешей.
    9. GOGC меняет компромисс память ↔ CPU; GOMEMLIMIT задаёт мягкий бюджет памяти рантайма.
    10. Слишком тесный бюджет памяти способен увеличить CPU на GC и задержку запросов.
    11. Рост задержки зависимости увеличивает время жизни состояния запросов и способен поднять живой хип без единой утечки.
    12. Живой хип и RSS — разные уровни; свободная для Go память не обязана сразу исчезать из RSS.
    13. Профиль CPU отвечает про CPU, профиль хипа — про аллокации и живую память, профиль goroutine — про состояние goroutine.
    14. inuse_space полезен для удержания, alloc_space — для потока аллокаций.
    15. Нормальная оптимизация заканчивается повторным измерением: симптом → метрики → профиль → код → изменение → новое измерение.

    Главный инженерный вывод:

    Работа с памятью в Go начинается не с настройки GC. Она начинается со времени жизни данных, владения ссылками и паттернов аллокаций приложения. Под нагрузкой маленькие локальные решения умножаются на RPS, превращаются в поток аллокаций, работу GC, давление на CPU и хвост задержки. Поэтому расследовать нужно всю причинную цепочку, а не одну цифру.
