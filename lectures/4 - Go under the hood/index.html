    4. Go под капотом¶

    На уровне синтаксиса многие конструкции Go выглядят почти слишком просто:

    s = append(s, x)
v := m[key]
x := anyValue.(string)
jobs <- job
<-ctx.Done()

    Кажется, что тут и обсуждать нечего.

    Теперь зададим неудобные вопросы.

    Куда именно пишет append? Почему один срез иногда меняет другой, а после следующего append они внезапно начинают жить независимо?

    Как map находит один ключ среди миллиона?

    Почему nil-указатель внутри error может дать err != nil?

    Почему отправка в канал иногда заканчивается сразу, а иногда goroutine исчезает из выполнения?

    Как select ждёт сразу несколько каналов, если goroutine одна?

    И что реально происходит внутри context, когда один cancel() должен отменить тысячи дочерних операций?

    Вот здесь абстракции начинают протекать.

    Главная идея лекции:

    Удобный синтаксис Go часто скрывает небольшой дескриптор или объект рантайма, а уже под ним находятся память, хеш-таблицы, очереди ожидания, атомарные операции, блокировки и планировщик.

    Пойдём по цепочке:

    массив
↓
срез
↓
базовый массив
↓
append
↓
map
↓
Swiss Tables
↓
sync.Map
↓
интерфейс
↓
канал
↓
select
↓
контекст

    Каждый следующий механизм появляется потому, что предыдущая простая модель уже перестаёт что-то объяснять.

    1. Сначала разделим типы по модели хранения¶

    Возьмём:

    [N]T
[]T
map[K]V
интерфейс
chan T
context.Context

    Синтаксически всё это просто переменные.

    Но копирование такой переменной означает совершенно разное.

    Тип Что концептуально находится в значении
    [N]T сами элементы массива
    []T дескриптор участка массива
    map[K]V ссылка на внутреннюю структуру map
    interface информация о динамическом типе и данные
    chan T ссылка на внутренний объект канала
    context.Context интерфейс на объект цепочки контекстов

    Из этой разницы вырастает почти всё интересное дальше.

    2. Массив: самая честная структура в этой лекции¶

    a := [4]int{10, 20, 30, 40}

    Ментальная модель:

    a

┌────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │
└────┴────┴────┴────┘

    Массив содержит фиксированное количество элементов одного типа.

    Причём длина входит в тип:

    var a [4]int
var b [5]int

    [4]int и [5]int — разные типы.

    3. Копирование массива копирует его значение¶

    a := [3]int{1, 2, 3}
b := a

b[0] = 100

    Получим:

    a = [1 2 3]
b = [100 2 3]

    Почему?

    Потому что:

    b := a

    семантически копирует весь массив.

    a                  b

┌───┬───┬───┐      ┌───┬───┬───┐
│ 1 │ 2 │ 3 │      │ 1 │ 2 │ 3 │
└───┴───┴───┘      └───┴───┴───┘

    Это две независимые области данных.

    Отсюда следствие:

    func process(a [1_000_000]int) {}

    Параметр передаётся по значению.

    Компилятор может оптимизировать конкретный машинный код, но семантика языка остаётся той же: функция получает собственное значение массива.

    4. Срез: вот здесь простая модель ломается¶

    Популярное упрощение:

    Срез (срез) — динамический массив.

    Для первого знакомства терпимо.

    Дальше начинает мешать.

    Более точная модель:

    Срез — небольшой дескриптор, который описывает участок другого массива.

    Концептуально:

    type slice struct {
    ptr *T
    len int
    cap int
}

    Это учебная модель.

    На 64-битной архитектуре такой дескриптор обычно состоит из трёх машинных слов.

    Самих элементов внутри него нет.

    5. Базовый массив¶

    s := []int{10, 20, 30, 40}

    Нужно видеть две сущности.

    Дескриптор:

    s

┌───────────┐
│ ptr ─────────────┐
│ len = 4   │      │
│ cap = 4   │      │
└───────────┘      │
                   ▼

    Базовый массив:

    ┌────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │
└────┴────┴────┴────┘

    Теперь:

    a := s

    Что копируется?

    Только дескриптор.

    s                         a

┌──────────┐              ┌──────────┐
│ ptr ─────┼─────┐        │ ptr ─────┼─────┐
│ len = 4  │     │        │ len = 4  │     │
│ cap = 4  │     │        │ cap = 4  │     │
└──────────┘     │        └──────────┘     │
                 └──────────┬───────────────┘
                            ▼
                   ┌────┬────┬────┬────┐
                   │ 10 │ 20 │ 30 │ 40 │
                   └────┴────┴────┴────┘

    Поэтому:

    a[0] = 999

    изменит данные, которые видит и s.

    Фраза:

    срез передаётся по значению

    технически верна.

    Но по значению копируется дескриптор.

    Базовый массив может остаться общим.

    6. len и cap¶

    a := [6]int{10, 20, 30, 40, 50, 60}
s := a[1:4]

    Получаем:

    индекс    0    1    2    3    4    5
        ┌────┬────┬────┬────┬────┬────┐
        │ 10 │ 20 │ 30 │ 40 │ 50 │ 60 │
        └────┴────┴────┴────┴────┴────┘
              ↑
              ptr

s = [20 30 40]
len = 3
cap = 5

    len — сколько элементов входит в текущий логический срез.

    cap — сколько элементов доступно от начала среза до конца доступной части базового массива.

    Поэтому:

    s = s[:5]

    может просто изменить дескриптор.

    Новая память здесь не нужна.

    7. append: одна строка, два принципиально разных сценария¶

    s = append(s, 42)

    Сценарий №1: ёмкости хватает.

    len = 3
cap = 8

    Рантайм может записать значение в свободное место того же массива.

    После append:

    ptr = тот же
len = 4
cap = 8

    Нового массива нет.

    8. Ёмкость закончилась¶

    Теперь:

    len = 4
cap = 4

    и выполняется:

    s = append(s, 50)

    Свободного места нет.

    Рантайм должен:

    вычислить новый размер
↓
получить новый массив
↓
скопировать старые элементы
↓
добавить новый
↓
вернуть новый дескриптор среза

    После этого s.ptr может указывать уже в совершенно другую область памяти.

    Вот почему результат append нужно присваивать:

    s = append(s, x)

    Старый дескриптор сам не узнает, что данные переехали.

    9. Не стройте логику на точном росте cap¶

    Иногда говорят:

    срез всегда растёт в два раза.

    Это слишком грубое правило.

    Текущий рантайм использует собственную стратегию роста. Она зависит от старой ёмкости, необходимого размера и округления распределителем памяти.

    Go гарантирует семантику append.

    Go не гарантирует:

    newCap == oldCap * 2

    Если бизнес-логика зависит от точного значения новой ёмкости, модель уже сломана.

    10. Самая неприятная часть срезов — совместное использование массива¶

    a := make([]int, 3, 5)
a[0] = 1
a[1] = 2
a[2] = 3

b := a[:2]

b = append(b, 100)

    Что стало с a?

    У b хватает ёмкости.

    Значит append пишет в тот же базовый массив.

    до:

┌───┬───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 0 │ 0 │
└───┴───┴───┴───┴───┘

после:

┌───┬───┬─────┬───┬───┐
│ 1 │ 2 │ 100 │ 0 │ 0 │
└───┴───┴─────┴───┴───┘

    a теперь видит:

    [1 2 100]

    Вот здесь модель «срез = динамический массив» окончательно перестаёт помогать.

    11. Как ограничить ёмкость дочернего среза¶

    b := a[:2:2]

    Теперь:

    len(b) = 2
cap(b) = 2

    Следующий append уже не сможет использовать место дальше в старом массиве.

    Рантайм будет вынужден получить другой базовый массив.

    Это полезно, когда дочерний срез не должен случайно писать за пределы своего логического диапазона.

    12. Срез может удерживать огромный массив¶

    data := make([]byte, 100<<20)
header := data[:10]
return header

    На уровне API возвращаем 10 байт.

    На уровне достижимости:

    header.ptr
↓
100 MiB базовый массив

    Пока жив header, большой массив может оставаться достижимым.

    Получаем цепочку:

    маленькие срезы
↓
удерживают большие массивы
↓
живой хип ↑
↓
давление на память ↑

    Если нужна независимая маленькая копия:

    result := append([]byte(nil), data[:10]...)

    или:

    result := slices.Clone(data[:10])

    Цена — выделение памяти и копирование.

    Выигрыш — старый большой массив может стать недостижимым.

    Иногда копирование экономит память.

    13. Что важно запомнить про срезы¶

    1. Срез не содержит сами элементы.
    2. Значение среза — дескриптор указатель + len + cap.
    3. Копирование среза копирует дескриптор.
    4. Несколько срезов могут ссылаться на один базовый массив.
    5. append иногда пишет в старый массив, иногда создаёт новый.
    6. После перевыделения старые срезы продолжают ссылаться на старый массив.
    7. Маленький срез способен удерживать большой массив.
    8. Точный алгоритм роста cap не является контрактом языка.

    14. map: как найти ключ среди миллиона элементов¶

    m := map[string]int{
    "alice": 10,
    "bob":   20,
}

    Если элементов миллион, рантайм не перебирает все ключи.

    Сначала вычисляется хеш.

    Общая модель:

    ключ
↓
хеш
↓
нужная область хеш-таблицы
↓
кандидаты
↓
сравнение ключа
↓
значение

    Средний поиск в нормально заполненной хеш-таблице близок к O(1).

    Но реальная цена включает:

    вычисление хеша
+
обращения к памяти
+
промахи кеша
+
обработку коллизий
+
сравнение ключей

    Вот здесь Big O перестаёт быть всей историей.

    15. Копирование map не копирует всю таблицу¶

    a := map[string]int{"x": 1}
b := a

b["x"] = 100

    После этого:

    a["x"] == 100

    a и b работают с одной внутренней структурой map.

    Это ссылочная семантика значения map.

    16. nil-map¶

    var m map[string]int

    Читать можно:

    fmt.Println(m["x"]) // 0
len(m)              // 0
delete(m, "x")

    Но:

    m["x"] = 1

    даст panic:

    assignment to entry in nil map

    nil-map ведёт себя как пустая при чтении, но не имеет хранилища для добавления элементов.

    17. Старая и текущая реализации map — разные¶

    Здесь легко попасть в ловушку старых статей.

    До Go 1.24 встроенная map использовала модель с бакетами:

    hmap
bmap
tophash
бакеты переполнения
oldbuckets
nevacuate

    Начиная с Go 1.24 встроенная map основана на Swiss Tables.

    Семантика языка осталась.

    Внутренний алгоритм поменялся сильно.

    18. Зачем помнить старую модель¶

    Она хорошо показывает проблему, которую потом решали.

    При коллизиях структура могла выглядеть так:

    бакет
↓
бакет переполнения
↓
бакет переполнения

    Поиск превращался в переходы по указателям:

    прочитать бакет
↓
перейти по указателю
↓
прочитать другой участок памяти
↓
возможный промах кеша

    Современному CPU такое не нравится.

    19. Почему старый map рос постепенно¶

    Если полностью переносить огромную таблицу за одну операцию:

    одна запись
↓
перенос миллионов элементов
↓
всплеск задержки

    получаем плохую задержку отдельного запроса.

    Поэтому старая реализация переносила данные постепенно:

    старые бакеты
+
новые бакеты
↓
последующие операции переносят данные частями

    Общий инженерный принцип:

    Большую O(N) работу часто выгодно распределить по множеству операций, чтобы не создавать один огромный всплеск задержки.

    20. Swiss Tables: новая модель map¶

    Текущая реализация использует идею Swiss Table.

    Главная смена:

    раньше:
бакеты + цепочки переполнения

сейчас:
группы + открытая адресация + компактные метаданные

    В текущей реализации группа содержит восемь ячеек и управляющие байты рядом с ними.

    управляющие байты

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ c0 │ c1 │ c2 │ c3 │ c4 │ c5 │ c6 │ c7 │
└────┴────┴────┴────┴────┴────┴────┴────┘

ячейки

┌────┬────┬────┬────┬────┬────┬────┬────┐
│k/v │k/v │k/v │k/v │k/v │k/v │k/v │k/v │
└────┴────┴────┴────┴────┴────┴────┴────┘

    Метаданные позволяют быстро отбросить неподходящие ячейки до полного сравнения ключей.

    21. Зачем делить хеш на части¶

    Текущая реализация использует разные части хеша для разных задач.

    Упрощённо:

    хеш
├── H1 → навигация по таблице
└── H2 → короткий отпечаток ячейки

    Ищем ключ.

    Сначала сравниваем короткий H2 с метаданными группы.

    Например:

    ищем H2 = 53

метаданные:
12  91  53  38  53  пусто  7  удалено
        ↑       ↑

    Полное сравнение ключа нужно только для двух кандидатов.

    Идея простая:

    Сначала дешёвой метаданной отсеиваем большинство вариантов, потом трогаем дорогие данные.

    22. Совпадение H2 ещё не означает равенство ключей¶

    H2 короткий.

    Разные хеши могут иметь одинаковый отпечаток.

    Поэтому:

    H2 совпал?
├── нет → пропускаем ячейку
└── да
    ↓
    сравниваем настоящий ключ
    ├── не равен → коллизия
    └── равен → нашли

    Отпечаток — фильтр.

    Не доказательство равенства ключей.

    23. Пробирование¶

    Swiss Table использует открытую адресацию.

    Если нужный ключ не найден в первой группе, алгоритм проверяет следующие группы по последовательности пробирования.

    начальная группа
↓
следующая
↓
следующая
↓
...

    Поиск заканчивается, когда:

    • ключ найден;
    • или встретили настоящую пустую ячейку, которая доказывает, что дальше по этой последовательности ключа быть не должно.

    24. Почему удаление не может просто сделать ячейку пустой¶

    Представим:

    A
↓ коллизия
B
↓ коллизия
C

    Ключ оказался в C.

    Удаляем элемент из B.

    Если просто поставить там пусто, поиск дойдёт до B и решит:

    дальше искать бессмысленно.

    C станет логически недоступным.

    Поэтому нужна метка удаления:

    элемента здесь больше нет
+
поиск обязан продолжиться

    25. Почему таблицу нельзя забить до 100%¶

    Чем выше заполнение:

    коэффициент заполнения ↑
↓
последовательности пробирования длиннее
↓
обращений к памяти больше
↓
поиск дороже

    Поэтому Swiss Table намеренно оставляет свободные ячейки.

    Конкретный коэффициент заполнения текущего рантайма — деталь реализации.

    Причинная связь важнее числа.

    26. Как растёт текущая map¶

    Одна огромная Swiss Table с полным перераспределением всех элементов снова дала бы большие всплески задержки.

    Поэтому текущая Go map использует каталог и несколько таблиц.

    `map`
↓
каталог
├── таблица A
├── таблица B
├── таблица C
└── ...

    Часть хеша помогает выбрать таблицу.

    Внутри неё уже работает пробирование Swiss Table.

    Отдельные таблицы могут расти и разделяться независимо.

    Так стоимость роста распределяется лучше, чем при полном переносе одной гигантской таблицы.

    27. Почему Swiss Tables быстрее¶

    Не потому, что асимптотика внезапно стала другой.

    И старая, и новая реализация в среднем дают O(1).

    Выигрыш находится в константах:

    компактные метаданные
↓
несколько отпечатков читаются вместе
↓
меньше полных сравнений ключей
↓
меньше переходов по указателям
↓
лучше локальность
↓
меньше ожидания памяти

    Вот здесь структура данных встречается с реальным кешем CPU.

    28. make(map, hint)¶

    m := make(map[string]int, 100_000)

    100_000 — подсказка о начальном размере.

    Это не:

    максимальный размер

    и не:

    ровно 100000 ячеек

    map всё равно может расти.

    Но хороший ориентир позволяет уменьшить количество промежуточных расширений и выделений памяти.

    29. Обычная map не становится потокобезопасной¶

    go func() {
    m["x"] = 1
}()

go func() {
    fmt.Println(m["x"])
}()

    Это гонка данных.

    Рантайм умеет обнаруживать часть опасных конкурентных операций с map и может аварийно завершить программу.

    Но это диагностика.

    Не синхронизация.

    Если map разделяется между goroutine, обычно нужна:

    map + Mutex/RWMutex

    или архитектура с одним владельцем.

    Либо специализированный sync.Map.

    30. sync.Map: ещё одна ловушка версий¶

    Старые материалы объясняют sync.Map через:

    read
dirty
промахи
mutex

    Это действительно была реализация стандартной библиотеки.

    В Go 1.26/1.27 sync.Map использует internal/sync.HashTrieMap.

    Публичный API сохранился.

    Внутренний механизм изменился.

    31. Что было в старом sync.Map¶

    Историческая модель:

    sync.Map
├── read   → быстрые чтения
├── dirty  → новые/изменяемые записи
├── misses
└── mutex

    Частые чтения могли обходиться без общего mutex.

    Если ключ постоянно приходилось искать через более дорогой путь, накапливался счётчик misses.

    Когда стоимость этого пути становилась достаточно большой, структура перестраивалась.

    Интересная идея:

    Дорогая перестройка оправдывается накопленной стоимостью медленного пути.

    Сама внутренняя структура сегодня уже историческая.

    32. Текущий sync.Map: хеш-дерево¶

    Текущая реализация основана на HashTrieMap.

    Путь определяется частями хеша.

    Упрощённо:

    хеш:
1011 0010 1111 0100 ...
│    │    │
│    │    └→ следующий уровень
│    └─────→ следующий уровень
└──────────→ дочерний узел корня

    Чтение проходит по дереву через атомарные загрузки указателей.

    Для нагрузки с преобладанием чтения это позволяет не использовать один глобальный mutex на всю структуру.

    33. Изменение HashTrieMap¶

    Изменение структуры всё равно требует синхронизации.

    Но блокировка локализуется ближе к изменяемому узлу.

    Упрощённо:

    найти место
↓
заблокировать нужный узел
↓
повторно проверить состояние
↓
вставить / расширить
↓
разблокировать

    Это более мелкая область конкуренции за ресурс, чем один mutex на всю таблицу.

    34. Когда нужен sync.Map¶

    sync.Map специализирован.

    Типичные подходящие сценарии:

    • запись создаётся редко, потом много читается;
    • разные goroutine в основном работают с разными ключами.

    Но обычная:

    map[K]V + sync.RWMutex

    часто проще.

    Особенно если нужно защищать составной инвариант:

    mu.Lock()

m1[id] = ...
m2[id] = ...
counter++

mu.Unlock()

    sync.Map синхронизирует операции над самой структурой.

    Она не превращает несколько бизнес-действий в одну атомарную операцию.

    35. Интерфейс: как одна переменная хранит разные типы¶

    var x any = 42

    Как any может хранить:

    42
"hello"
*User
[]byte
http.Handler

    если все эти значения разные?

    Интерфейс хранит:

    информацию о динамическом типе
+
представление данных

    Для any полезная модель:

    ┌──────────────┐
│ тип    │
├──────────────┤
│ данные       │
└──────────────┘

    36. Статический и динамический тип¶

    var x any = 42

    Здесь:

    статический тип = any
динамический тип = int
динамическое значение = 42

    Статический тип известен компилятору.

    Динамический тип хранится во внутреннем представлении интерфейса.

    Это разные уровни.

    37. Непустой интерфейс и ITab¶

    type Writer interface {
    Write([]byte) (int, error)
}

    рантайму нужно знать не только конкретный тип значения.

    Нужно ещё понимать:

    Как этот тип реализует именно этот интерфейс?

    Для этого используется ITab.

    Полезная модель:

    значение интерфейса
├── itab
│   ├── тип интерфейса
│   ├── конкретный тип
│   └── таблица методов
└── данные

    При:

    w.Write(data)

    Рантайм использует эту информацию для вызова нужного метода.

    38. Преобразование к интерфейсу не означает хип автоматически¶

    Популярное упрощение:

    Положили значение в интерфейс — получили выделение памяти.

    Не обязательно.

    Результат зависит от:

    • конкретного типа;
    • представления значения;
    • эскейп-анализ;
    • времени жизни;
    • оптимизаций компилятора.

    Проверяем:

    go build -gcflags="-m=2" .
go test -bench=. -benchmem

    А не угадываем по синтаксису.

    39. nil-интерфейс¶

    var err error = nil
fmt.Println(err == nil)

    Получим:

    true

    Модель:

    динамический тип = nil
динамическое значение = nil

    Интерфейс действительно пуст.

    40. Типизированный nil¶

    type MyError struct{}

func (*MyError) Error() string {
    return "error"
}

var e *MyError = nil
var err error = e

    Теперь:

    fmt.Println(err == nil)

    даст:

    false

    Почему?

    Потому что внутри:

    динамический тип = *MyError
динамическое значение = nil

    Тип уже есть.

    Значит интерфейс не nil.

    41. Реальная ошибка с типизированным nil¶

    func findUser() error {
    var err *MyError
    return err
}

    Указатель err равен nil.

    Но при return происходит преобразование:

    *MyError → error

    И вызывающий код получает:

    (*MyError, nil)

    Поэтому:

    if err := findUser(); err != nil {
    // зайдём сюда
}

    Это вполне реальная ошибка бэкенд-кода.

    42. Утверждение типа¶

    v, ok := x.(string)

    Мы спрашиваем рантайм:

    Совместим ли динамический тип интерфейсного значения со string?

    С ok:

    s, ok := v.(string)

    при несовпадении:

    s = нулевое значение
ok = false

    Без ok:

    s := v.(string)

    несовместимый тип приводит к panic.

    На внешних границах API обычно безопаснее двухрезультатная форма.

    43. Что важно запомнить про интерфейсы¶

    1. Интерфейс хранит информацию о динамическом типе и данные.
    2. Статический и динамический тип — разные понятия.
    3. Интерфейс с методами использует структуру рантайма ITab.
    4. nil-интерфейс не имеет ни динамического типа, ни значения.
    5. Типизированный nil внутри интерфейса обычно не равен nil.
    6. Преобразование к интерфейсу не гарантирует выделение в хип.
    7. Утверждение типа использует информацию о динамическом типе.

    44. Канал: это не просто очередь¶

    Фраза:

    канал — потокобезопасная очередь

    ломается на небуферизованном канале.

    Более точная модель:

    Канал — объект рантайма для синхронизации, который может содержать кольцевой буфер и очереди ожидающих отправителей и получателей.

    ch := make(chan int, 4)

    Переменная ch ссылается на внутренний объект hchan.

    Полезная модель:

    hchan
├── буфер
├── qcount
├── ёмкость
├── индекс отправки
├── индекс получения
├── очередь ожидающих отправителей
├── очередь ожидающих получателей
├── признак закрытия
└── внутренняя блокировка

    Названия полей — детали реализации.

    Механика важнее.

    45. Буферизованный канал¶

    ch := make(chan int, 3)

    Буфер работает как кольцевая очередь:

    ┌────┬────┬────┐
│ 10 │ 20 │    │
└────┴────┴────┘
 ↑         ↑
recvx     sendx

    Индексы циклически двигаются по буферу.

    46. Отправка: три сценария¶

    ch <- value

    Получатель уже ждёт¶

    Рантайм может согласовать отправку непосредственно с ним.

    Получателя нет, буфер не заполнен¶

    Значение помещается в буфер.

    Буфер заполнен¶

    Отправка сейчас невозможна.

    Goroutine становится ожидающей:

    отправитель
↓
sendq
↓
парковка
↓
WAITING

    Вот здесь канал соединяется с планировщиком.

    47. Получение устроено симметрично¶

    v := <-ch

    Если отправитель уже ждёт — операции встречаются.

    Если в буфере есть данные — забираем следующий элемент.

    Если данных нет:

    получатель
↓
recvq
↓
парковка
↓
WAITING

    Канал может приостановить конкретную goroutine.

    поток ОС при этом не обязан ждать вместе с ней.

    48. sudog: зачем отдельная запись ожидания¶

    Очереди канала хранят ожидания через sudog.

    Упрощённо:

    hchan.recvq

sudog → sudog → sudog
  │       │       │
  ▼       ▼       ▼
  G       G       G

    sudog связывает конкретную goroutine с конкретным объектом синхронизации.

    Почему не хранить просто *g?

    Потому что одна G через select может одновременно присутствовать в нескольких очередях ожидания.

    Это связь «многие ко многим».

    49. Небуферизованный канал — встреча сторон¶

    ch := make(chan int)

    cap(ch) == 0.

    Пользовательского буфера нет.

    Отправка может завершиться, когда есть получатель.

    Получение — когда есть отправитель.

    G-отправитель
   │
   │ значение
   ▼
G-получатель

    Модель встреча сторон объясняет это лучше, чем фраза «очередь длины ноль».

    50. Канал потокобезопасный. Бесплатным он от этого не стал¶

    Если:

    100 goroutines
↓
один горячий канал

    можно получить:

    конкуренция за внутреннюю блокировку
↓
трафик линии кеша
↓
парковка / пробуждение
↓
работа планировщика

    Потокобезопасность гарантирует корректность.

    Не бесконечную масштабируемость.

    51. Буфер не создаёт пропускную способность¶

    Пусть:

    производитель = 10 000 сообщ./с
потребитель = 1 000 сообщ./с

    Буфер на 100 заполнится быстро.

    Буфер на миллион — позже.

    Но разница скоростей никуда не делась.

    Большой буфер меняет:

    • время до насыщения;
    • использование памяти;
    • задержку сообщения в очереди.

    Он не делает потребителя быстрее.

    52. close(ch)¶

    После:

    close(ch)
    • новые отправки приводят к panic;
    • уже накопленные значения можно дочитать;
    • после опустошения буфера получение возвращает нулевое значение и ok=false;
    • ожидающие получатели получают возможность продолжить работу.

    Закрытие канала — событие синхронизации.

    Это не просто изменение одного логического флага.

    53. nil-канал¶

    var ch chan int

    Отправка в него никогда не становится готовой.

    Получение тоже.

    На первый взгляд странно.

    Но в select это превращается в удобный способ выключить ветку.

    54. select: одна goroutine ждёт сразу несколько событий¶

    select {
case v := <-a:
    use(v)

case b <- result:
    sent()

case <-ctx.Done():
    cancel()
}

    Высокоуровневая модель:

    Выполнить одну из операций обмена, которая сейчас готова.

    Но теперь новый вопрос.

    Что делать, если готовы сразу несколько?

    Спецификация не задаёт приоритет по порядку case.

    Одна из готовых операций выбирается псевдослучайно.

    То есть:

    первая ветка в тексте
≠
высший приоритет

    55. Если ничего не готово, начинается самое интересное¶

    select {
case <-a:
case <-b:
case <-c:
case <-d:
}

    Goroutine одна.

    Ждать нужно четыре канала.

    Она не может четыре раза отдельно «уснуть» на каждом канале.

    Рантайм должен зарегистрировать одно выполнение сразу во всех нужных очередях ожидания.

    Вот здесь снова появляется sudog.

    56. Почему select сначала перемешивает проверки¶

    Если рантайм всегда проверял бы:

    a
потом b
потом c

    первая готовая ветка получала бы систематическое преимущество.

    Поэтому текущая реализация формирует псевдослучайный порядок проверки.

    Это уменьшает постоянный перекос.

    Но строгой справедливости спецификация всё равно не обещает.

    57. Почему внутренние блокировки каналов нужно брать в одном порядке¶

    select может работать сразу с несколькими каналами.

    Представим две goroutine.

    Первая:

    лок A
лок B

    Вторая:

    лок B
лок A

    Получили классическую взаимную блокировку из-за разного порядка захвата блокировок.

    Поэтому рантайм задаёт согласованный порядок внутренних блокировок каналов.

    Модель:

    набор каналов
↓
единый порядок
↓
захватываем внутренние локи одинаково

    58. Упрощённый алгоритм select¶

    Если убрать детали конкретной реализации, остаётся понятная последовательность.

    Шаг 1. Проверить ветки¶

    Для получения:

    есть ожидающий отправитель?
есть значение в буфере?
канал закрыт?

    Для отправки:

    есть ожидающий получатель?
есть место в буфере?
канал закрыт?

    Если ветка готова — выполняем её.

    Шаг 2. Если есть default¶

    Ничего не готово:

    default
↓
возврат без ожидания

    Goroutine не приостанавливается.

    Шаг 3. Если default нет¶

    Нужно ждать.

    Рантайм создаёт нужные sudog, регистрирует их в очередях каналов и приостанавливает одну G.

    59. Одна G — несколько sudog¶

    канал A recvq ──→ sudog ──┐
канал B recvq ──→ sudog ──┤
канал C sendq ──→ sudog ──┤
                             ▼
                             G

    Теперь событие может произойти на любом канале.

    Допустим, победил B.

    G становится RUNNABLE.

    Но регистрации в A и C ещё нужно удалить.

    Вот почему select значительно сложнее обычного if.

    60. nil-канал как выключенная ветка¶

    var ch <-chan int

    select {
case v := <-ch:
    use(v)

case <-ctx.Done():
    return
}

    Если:

    ch == nil

    первая ветка никогда не готова.

    То есть:

    nil-канал
=
отключённая ветка `select`

    Это удобный приём для конечных автоматов.

    61. select + default: как случайно получить активный цикл¶

    for {
    select {
    case v := <-ch:
        process(v)

    default:
    }
}

    Если ch пуст:

    select
↓
default
↓
цикл
↓
select
↓
default
↓
...

    Goroutine не приостанавливается.

    Она постоянно выполняется и съедает CPU.

    Получаем:

    «ничего не делает»
+
100% одного ядра CPU

    default превращает ожидание в активный опрос.

    Это должен быть осознанный выбор.

    62. select не является планировщиком приоритетов¶

    Если готовы несколько веток, нельзя обещать:

    обслуживаем строго по очереди

    или:

    верхняя ветка важнее нижней

    Если нужен настоящий приоритет, циклическое обслуживание или веса — такую политику строят отдельно.

    select решает другую задачу:

    Подождать одну из нескольких операций обмена.

    63. Диагностика проблем каналов и select¶

    Сервис начинает «висеть».

    Число goroutine растёт.

    В профиле goroutine видим:

    [chan send]
[chan receive]
[select]

    Теперь задаём конкретные вопросы:

    кто производитель?
кто потребитель?
какова ёмкость буфера?
какова реальная скорость сторон?
кто перестал читать?
кто отвечает за закрытие канала?
как заканчивается жизненный цикл?

    Для времени ожидания полезны:

    профиль блокировок
go tool trace

    То есть проблема канала диагностируется через очередь и жизненный цикл, а не только через строку ch <- x.

    64. Контекст: магии опять не будет¶

    ctx, cancel := context.WithTimeout(
    context.Background(),
    2*time.Second,
)
defer cancel()

    Популярное упрощение:

    контекст — специальный механизм рантайма, который умеет останавливать goroutine.

    Нет.

    context.Context — обычный интерфейс:

    type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done() <-chan struct{}
    Err() error
    Value(key any) any
}

    А отмена остаётся кооперативной.

    Контекст сообщает:

    Эта работа больше не нужна.

    Код должен этот сигнал заметить.

    65. Контекст — цепочка объектов¶

    ctx := context.Background()

ctx = context.WithValue(ctx, requestIDKey, requestID)

ctx, cancel := context.WithTimeout(ctx, time.Second)

ctx = context.WithValue(ctx, userKey, user)

    Получается примерно:

    valueCtx(user)
↓
timerCtx
↓
valueCtx(requestID)
↓
backgroundCtx

    Каждый новый контекст обычно оборачивает родительский.

    Поэтому context — не одна большая map.

    Это цепочка объектов.

    66. Отмена образует дерево¶

    корень, cancelRoot := context.WithCancel(context.Background())

a, _ := context.WithCancel(корень)
b, _ := context.WithCancel(корень)

a1, _ := context.WithCancel(a)
a2, _ := context.WithCancel(a)

    Логически:

              корень
         /    \
        a      b
      /   \
    a1     a2

    Вызываем:

    cancelRoot()

    Отмена распространяется вниз по дереву.

    Контекст переносит жизненный цикл родительской операции в дочерние.

    67. Что концептуально находится внутри отменяемого контекста¶

    Текущая реализация cancelCtx содержит примерно такие компоненты:

    родительский контекст
mutex
Done
дочерние контексты
ошибка
причина отмены

    Точная структура — деталь реализации.

    Причинность важнее:

    родитель должен знать потомков
+
нужно хранить состояние отмены
+
нужно безопасно работать из нескольких goroutine

    Поэтому внутри появляются Mutex, атомарные операции и канал.

    68. Done() использует канал как широковещательный сигнал¶

    Нужно уведомить:

    100 goroutines

    Если отправить одно значение:

    done <- struct{}{}

    его получит один получатель.

    А закрытие:

    close(done)

    делает получение готовым для всех текущих и будущих получателей.

    Вот почему ctx.Done() естественно реализуется через закрытие канала.

    69. Done создаётся лениво¶

    Не каждый контекст вообще вызывает:

    ctx.Done()

    Зачем тогда сразу создавать канал?

    Текущий cancelCtx создаёт его только при необходимости.

    Упрощённо:

    WithCancel
↓
создали контекст
↓
Done() не вызывали
↓
канал можно не создавать

    Характерный принцип:

    Не платить за механизм, который конкретный объект не использует.

    70. Как дочерний контекст подключается к родителю¶

    child, cancel := context.WithCancel(parent)

    Стандартная библиотека должна обеспечить:

    родитель отменён
↓
дочерний контекст отменён

    Если родитель — обычный отменяемый контекст стандартной библиотеки, дочерний контекст регистрируется среди его потомков.

    parent
├── child1
├── child2
└── child3

    Теперь родитель знает, кому распространять отмену.

    71. Что реально делает cancel()¶

    Упрощённо:

    записать ошибку / причину
↓
закрыть Done
↓
отменить дочерние контексты
↓
очистить связи
↓
при необходимости отсоединиться от родителя

    То есть одна строка:

    cancel()

    может превратиться в обход целого дерева.

    72. Отмена не убивает goroutine¶

    go func() {
    for {
        doCPUWork()
    }
}()

    Где-то:

    cancel()

    Что случится?

    Ничего.

    Goroutine не читает контекст.

    Чтобы отмена работала, код должен сотрудничать:

    go func() {
    for {
        select {
        case <-ctx.Done():
            return

        default:
            doCPUWork()
        }
    }
}()

    Или блокирующий API должен принимать ctx:

    db.QueryContext(ctx, ...)
req = req.WithContext(ctx)

    Модель:

    контекст подаёт сигнал
↓
код замечает сигнал
↓
код прекращает ненужную работу

    73. WithTimeout добавляет таймер¶

    context.WithTimeout(parent, 2*time.Second)

    Концептуально:

    таймер
↓
срок истёк
↓
отмена дочернего контекста
↓
Done закрывается
↓
отмена идёт дальше по дереву

    То есть тайм-аут — это отмена, запланированная по времени.

    74. Почему CancelFunc нужно вызывать вручную¶

    ctx, cancel := context.WithTimeout(parent, time.Minute)
defer cancel()

    Можно подумать:

    Через минуту тайм-аут всё равно сработает.

    Да.

    Но если работа завершилась через 20 ms, зачем ещё почти минуту держать ненужный таймер и связи дерева контекстов?

    Под нагрузкой:

    100 000 запросы
↓
создали контексты с тайм-аутом
↓
работа закончилась быстро
↓
cancel забыли
↓
лишние контексты и таймеры живут до дедлайна

    Поэтому своевременный cancel() — часть управления ресурсами.

    75. Value — цепочка, а не бесплатная map¶

    context.WithValue(parent, key, value)

    Концептуально:

    valueCtx(key3)
↓
valueCtx(key2)
↓
valueCtx(key1)
↓
корень

    Поиск значения идёт вверх по цепочке, пока не встретится нужный ключ.

    Поэтому значения контекста предназначены прежде всего для метаданных конкретного запроса.

    Это плохой универсальный контейнер зависимостей.

    Проблема здесь чаще архитектурная: зависимости становятся неявными.

    76. Пользовательская реализация Context может сделать распространение отмены дороже¶

    Если стандартная библиотека не может напрямую присоединиться к обычному cancelCtx родителя, ей всё равно нужно обеспечить:

    parent.Done()
↓
отмена child

    В запасном варианте может понадобиться отдельная goroutine, ожидающая отмену родителя или дочернего контекста.

    Один и тот же публичный API может иметь разные внутренние пути в зависимости от конкретной реализации.

    77. Массовая отмена под нагрузкой¶

    Представим:

    корень
├── 3000 задачи
├── 3000 задачи
└── 4000 задачи

    Теперь:

    cancelRoot()

    Логически — одна операция.

    Физически:

    обойти потомков
↓
закрыть Done
↓
разбудить тысячи goroutines
↓
тысячи G становятся RUNNABLE
↓
планировщик получает всплеск работы

    Логическое состояние меняется быстро.

    Последствия всё равно должны быть исполнены реальными goroutine на реальном CPU.

    78. Контекст HTTP-запроса: вот где механизм становится полезен бэкенду¶

    Типичный запрос:

    контекст HTTP-запроса
│
├── запрос к БД
├── исходящий HTTP-запрос
├── воркер A
└── воркер B

    Клиент разорвал соединение:

    контекст запроса отменён
↓
запрос к БД получает сигнал отмены
↓
исходящий HTTP-запрос отменяется
↓
воркеры завершаются
↓
ресурсы освобождаются раньше

    Контекст переносит жизненный цикл одной операции через несколько уровней бэкенда.

    79. Как контекст ломают¶

    func handler(w http.ResponseWriter, r *http.Request) {
    go process(context.Background())
}

    HTTP-запрос закончился.

    Клиент ушёл.

    Но process получил Background().

    Связь жизненного цикла разорвана:

    запрос отменён
↓
фоновая работа продолжает выполняться

    Иногда это правильно.

    Но тогда это должна быть осознанная фоновая операция со своим жизненным циклом.

    80. Дочерний дедлайн не расширяет более ранний родительский¶

    Пусть у родительского контекста осталось две секунды.

    Внутри:

    context.WithTimeout(parent, 10*time.Second)

    Дочерний контекст не получает дополнительные десять секунд поверх родительского.

    Родительская отмена всё равно отменит его раньше.

    То есть время жизни дочерней операции ограничено временем жизни родительской, если мы явно не отсоединили её.

    81. Контекст сам по себе не создаёт обратное давление¶

    Контекст ограничивает время жизни работы.

    Он не ограничивает количество одновременно начатых операций.

    Но отмена помогает не выполнять работу, которая уже никому не нужна.

    Без распространения отмены:

    тайм-аут входящего запроса
↓
вызывающая сторона уже прекратила ожидание
↓
бэкенд продолжает запрос к БД
↓
продолжает RPC
↓
держит соединение из пула
↓
тратит CPU
↓
результат выбрасывается

    С распространением:

    тайм-аут входящего запроса
↓
cancel
↓
работа внешних зависимостей заканчивается раньше
↓
ресурсы освобождаются

    Под перегрузкой разница может быть огромной.

    83. Что происходит под нагрузкой¶

    Простая строка:

    results = append(results, item)

    может означать:

    cap закончился
↓
новое выделение памяти
↓
копирование
↓
поток выделений в хип
↓
работа GC

    Строка:

    value := cache[key]

    может означать:

    хеширование
↓
метаданные Swiss Table
↓
пробирование
↓
сравнение ключа
↓
промахи кеша

    Строка:

    jobs <- job

    может означать:

    внутренняя блокировка канала
↓
буфер заполнен
↓
sudog
↓
sendq
↓
парковка
↓
планировщик

    Строка:

    cancel()

    может означать:

    обход дерева отмены
↓
закрытие Done
↓
тысячи goroutines становятся RUNNABLE
↓
всплеск работы планировщика

    Вот на этом уровне конструкции языка превращаются в механику бэкенда под нагрузкой.

    84. Диагностика¶

    Срезы и удержание памяти¶

    Симптом:

    хип неожиданно растёт

    Смотрим профиль хипа.

    Ищем:

    • большие []byte;
    • большие []T;
    • удерживаемые базовые массивы;
    • горячие места с append;
    • маленькие срезы, удерживающие крупные выделения памяти.

    map¶

    Симптом:

    CPU вырос

    Смотрим профиль CPU.

    Проверяем:

    • хеширование;
    • операции с map;
    • выделения памяти;
    • GC;
    • конкуренцию вокруг внешнего mutex.

    Сложный ключ тоже имеет цену: его нужно хешировать и сравнивать.

    Каналы и select¶

    Симптом:

    задержка ↑
goroutines ↑

    Смотрим:

    • профиль goroutine;
    • профиль блокировок;
    • go tool trace.

    Ищем:

    chan send
chan receive
select

    Потом восстанавливаем жизненный цикл производителей и потребителей.

    Контекст¶

    Симптом:

    работа продолжает жить после завершения запрос

    Ищем:

    • потерянную цепочку распространения отмены;
    • context.Background() внутри пути обработки запроса;
    • операции, которые игнорируют ctx.Done();
    • забытые CancelFunc;
    • фоновые goroutine без собственного жизненного цикла.

    85. Границы гарантий¶

    Важно не смешивать уровни.

    Язык и API гарантируют¶

    • семантику массивов и срезов;
    • len, cap, append;
    • поведение map;
    • семантику интерфейсов;
    • поведение типизированного nil;
    • семантику отправки, получения и закрытия каналов;
    • правила select;
    • контракт context.Context.

    Текущая реализация¶

    • точный алгоритм роста среза;
    • внутреннее устройство структур рантайма;
    • детали Swiss Tables;
    • HashTrieMap внутри sync.Map;
    • hchan;
    • sudog;
    • конкретный алгоритм select;
    • поля cancelCtx;
    • ленивое создание Done.

    Эти детали полезны для понимания и диагностики.

    Но прикладной код не должен зависеть от их неизменности.

    Что важно запомнить¶

    1. Массив содержит элементы и копируется как значение.
    2. Срез — дескриптор над базовым массивом; несколько срезов могут разделять одни данные.
    3. append иногда пишет в старый массив, иногда создаёт новый, поэтому cap и совместное использование памяти имеют реальные последствия.
    4. Маленький срез способен удерживать огромный базовый массив.
    5. Текущий встроенный map использует Swiss Tables; выигрыш связан прежде всего с плотными метаданными и локальностью памяти.
    6. Обычная map не потокобезопасна. Сложность рантайма не заменяет синхронизацию.
    7. Текущий sync.Map использует HashTrieMap и остаётся специализированным инструментом.
    8. Интерфейс хранит динамический тип и данные; поэтому типизированный nil может быть != nil.
    9. Канал — объект синхронизации с буфером и очередями ожидания; небуферизованный канал лучше понимать как встреча сторон.
    10. Горячий канал способен стать точкой конкуренции за ресурс; большой буфер не создаёт пропускную способность.
    11. select регистрирует одну goroutine сразу в нескольких очередях ожидания и не гарантирует строгий приоритет веток.
    12. nil-канал полезен как отключённая ветка select.
    13. context.Context — интерфейс и цепочка объектов; отмена распространяется по дереву.
    14. Отмена кооперативна: cancel() не останавливает произвольную goroutine силой.
    15. Забытый CancelFunc и потерянная цепочка отмены могут удерживать ресурсы и продолжать уже ненужную работу.
    16. Под нагрузкой важно видеть не только синтаксис, но и скрытые выделения памяти, хеширование, блокировки, очереди ожидания, приостановку и пробуждение goroutine.

    Финальная модель¶

    синтаксис
↓
дескриптор / объект рантайма
↓
устройство памяти
↓
выделение памяти / хеширование / синхронизация
↓
планировщик / GC / кеш CPU
↓
поведение под нагрузкой
↓
профили / трассировка
↓
конкретная инженерная причина

    Главный инженерный вывод:

    Удобные конструкции Go специально скрывают большую часть механики. Пока нагрузка маленькая, это экономит мышление. Под нагрузкой скрытые детали становятся наблюдаемыми: срез начинает удерживать память, map упирается в хеширование и локальность, канал превращается в очередь ожидания, select — в регистрацию нескольких ожиданий, а один cancel() — в массовое пробуждение goroutine. Поэтому хорошая ментальная модель должна начинаться с синтаксиса, но не заканчиваться на нём.
