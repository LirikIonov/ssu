    4. Go under the hood¶

    В этой лекции мы разберём структуры, которыми Go-разработчик пользуется постоянно:

    • arrays;
    • slices;
    • len / cap;
    • append;
    • underlying array;
    • maps;
    • старая реализация hash table;
    • Swiss Tables;
    • sync.Map;
    • interfaces;
    • nil interface;
    • type assertion;
    • channels;
    • select;
    • context;
    • cancellation tree.

    Главная идея лекции простая:

    синтаксис Go часто скрывает значительно более сложную структуру данных.

    Мы пишем:

    s = append(s, x)

    и видим одну строку.

    Runtime может:

    1. проверить capacity;
    2. вычислить новый capacity;
    3. выделить новый объект;
    4. скопировать старые элементы;
    5. обновить slice descriptor;
    6. оставить старый backing array жить, если на него ещё кто-то ссылается.

    Мы пишем:

    v := m[key]

    и видим индексирование.

    Под ним находятся:

    hash
  ↓
directory
  ↓
table
  ↓
group
  ↓
control word
  ↓
candidate slots
  ↓
key equality

    Мы пишем:

    <-ctx.Done()

    и кажется, что context — какой-то специальный механизм runtime.

    На самом деле там дерево объектов, обычные channels, mutex, atomic operations, timers и распространение отмены от родителя к потомкам.

    Поэтому задача этой лекции — перестать воспринимать эти конструкции как магию языка.

    1. Сначала разделим типы по модели хранения¶

    У нас есть:

    array
slice
map
interface
channel
context

    Но копируются они совершенно по-разному.

    Упрощённая модель:

    Тип Что находится в переменной
    [N]T сами элементы
    []T descriptor массива
    map[K]V ссылка на runtime-структуру
    interface информация о типе + данные
    chan T ссылка на runtime channel
    context.Context interface на один из объектов цепочки context

    Именно отсюда растёт значительная часть странного поведения.

    2. Arrays¶

    Начнём с самой простой структуры.

    a := [4]int{10, 20, 30, 40}

    Ментальная модель:

    a
┌────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │
└────┴────┴────┴────┘

    Array является непосредственно последовательностью элементов.

    Спецификация Go определяет массив как последовательность фиксированного количества элементов одного типа. Причём длина входит в тип массива. Поэтому [4]int и [5]int — разные типы.

    var a [4]int
var b [5]int

    Типы:

    [4]int
[5]int

    разные.

    2.1 Копирование массива¶

    Рассмотрим:

    a := [3]int{1, 2, 3}
b := a

b[0] = 100

fmt.Println(a)
fmt.Println(b)

    Получим:

    [1 2 3]
[100 2 3]

    Почему?

    Потому что:

    b := a

    копирует весь array value.

    Схематично:

    a
┌───┬───┬───┐
│ 1 │ 2 │ 3 │
└───┴───┴───┘

b
┌───┬───┬───┐
│ 1 │ 2 │ 3 │
└───┴───┴───┘

    Это две независимые области данных.

    Спецификация прямо относит arrays к self-contained values: значение массива содержит полную копию своих данных.

    Отсюда ещё одно следствие.

    func process(a [1_000_000]int) {
}

    Семантически параметр передаётся по значению.

    Это не значит, что каждый конкретный машинный вызов обязательно будет реализован тупым миллионным копированием — компилятор имеет право оптимизировать код.

    Но семантика языка остаётся:

    process получает собственное значение [1_000_000]int

    Именно поэтому большие массивы редко передают таким образом.

    3. Slice¶

    И здесь начинается самое интересное.

    Очень распространённое упрощение:

    slice — динамический массив.

    Для первых десяти минут изучения языка оно терпимо.

    После этого начинает мешать.

    Более точная модель:

    slice — маленький descriptor, который описывает участок другого массива.

    Спецификация говорит практически именно это: slice описывает contiguous segment некоторого underlying array.

    Концептуально:

    type slice struct {
    ptr *T
    len int
    cap int
}

    Это учебная модель. Текущий internal ABI действительно представляет slice как pointer + len + cap.

    На 64-битной архитектуре это обычно три машинных слова:

    ┌──────────────┐
│ data pointer │ 8 bytes
├──────────────┤
│ len          │ 8 bytes
├──────────────┤
│ cap          │ 8 bytes
└──────────────┘

    То есть примерно 24 байта самого descriptor.

    Элементов внутри этих 24 байт нет.

    4. Underlying array¶

    Создадим:

    s := []int{10, 20, 30, 40}

    Ментально нужно видеть две сущности.

    Slice descriptor¶

    s
┌──────────┐
│ ptr ───────────────┐
│ len = 4  │         │
│ cap = 4  │         │
└──────────┘         │
                     ↓

    Underlying array¶

    ┌────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │
└────┴────┴────┴────┘

    Теперь:

    a := s

    Что копируется?

    Только descriptor:

    s                              a
┌──────────┐                  ┌──────────┐
│ ptr ─────┼──────┐           │ ptr ─────┼──────┐
│ len = 4  │      │           │ len = 4  │      │
│ cap = 4  │      │           │ cap = 4  │      │
└──────────┘      │           └──────────┘      │
                  │                              │
                  └───────────┬──────────────────┘
                              ↓
                  ┌────┬────┬────┬────┐
                  │ 10 │ 20 │ 30 │ 40 │
                  └────┴────┴────┴────┘

    Поэтому:

    a[0] = 999

    изменит данные, которые видит s.

    fmt.Println(s) // [999 20 30 40]

    И вот здесь становится понятно, почему фраза:

    slice передаётся по значению

    технически абсолютно верная и практически часто неправильно понимаемая.

    Передаётся по значению slice descriptor.

    Underlying array остаётся общим.

    5. len и cap¶

    Для slice:

    len = сколько элементов сейчас входит в логический slice
cap = сколько элементов доступно от ptr до конца доступной части underlying array

    Например:

    a := [6]int{10, 20, 30, 40, 50, 60}

s := a[1:4]

    Получаем:

    a:

index      0    1    2    3    4    5
         ┌────┬────┬────┬────┬────┬────┐
         │ 10 │ 20 │ 30 │ 40 │ 50 │ 60 │
         └────┴────┴────┴────┴────┴────┘
                ↑
                ptr

s = [20 30 40]

len = 3
cap = 5

    Почему cap = 5?

    Потому что от 20 до конца underlying array:

    20 30 40 50 60

    пять элементов.

    Спецификация определяет capacity именно через доступную часть underlying array.

    6. Reslicing¶

    Вот почему работает:

    s := a[1:4]

s = s[:5]

    И получится:

    [20 30 40 50 60]

    Первоначальный len был 3.

    Но cap был 5.

    Следовательно:

    s[:5]

    не требует новой памяти.

    Мы просто меняем descriptor:

    len: 3 → 5

    Underlying array остаётся тем же.

    7. append¶

    Теперь возьмём главный источник сюрпризов.

    s = append(s, 42)

    У append есть принципиально два сценария.

    7.1 Capacity хватает¶

    Допустим:

    len = 3
cap = 8

    Есть свободное место:

    ┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │    │    │    │    │    │
└────┴────┴────┴────┴────┴────┴────┴────┘
                ↑
             append

    Runtime может записать значение прямо туда.

    Получаем:

    ptr = тот же
len = 4
cap = 8

    Нового массива нет.

    8. Когда capacity закончилась¶

    Теперь:

    len = 4
cap = 4

    и выполняется:

    s = append(s, 50)

    В существующем массиве места больше нет.

    Runtime должен получить новый backing store.

    Текущий runtime.growslice:

    1. вычисляет новую capacity;
    2. выделяет новый backing array;
    3. копирует старые элементы;
    4. возвращает новый slice descriptor.

    Схема:

    старый array

┌────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │
└────┴────┴────┴────┘

            │
            │ copy
            ↓

новый array

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │    │    │    │
└────┴────┴────┴────┴────┴────┴────┴────┘

    После этого:

    s.ptr

    указывает уже на новый массив.

    9. Почему результат append нужно присваивать¶

    Вот теперь становится понятно требование:

    s = append(s, x)

    а не:

    append(s, x)

    append может вернуть descriptor с другим pointer.

    Старый descriptor ничего об этом не знает.

    10. Как растёт capacity¶

    Иногда можно встретить правило:

    slice всегда растёт в два раза.

    Устаревшее и слишком грубое упрощение.

    В текущем Go 1.27 nextslicecap использует примерно такую стратегию:

    • для небольших capacity используется удвоение;
    • после порога 256 начинается плавный переход к росту примерно в 1.25x;
    • если сразу нужно намного больше места, capacity может быть установлена непосредственно под необходимый размер;
    • фактическая capacity дополнительно зависит от округления размера allocator'ом.

    То есть код:

    oldCap := cap(s)
s = append(s, x)
newCap := cap(s)

    не должен строить бизнес-логику на предположении:

    newCap == oldCap * 2

    Это implementation detail.

    Go гарантирует семантику append.

    Конкретная стратегия роста — решение runtime.

    11. Самая неприятная особенность append: aliasing¶

    Рассмотрим:

    a := make([]int, 3, 5)
a[0] = 1
a[1] = 2
a[2] = 3

b := a[:2]

b = append(b, 100)

    Что станет с a?

    Разбираем.

    Изначально:

    underlying array

┌───┬───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 0 │ 0 │
└───┴───┴───┴───┴───┘

a: len=3 cap=5
b: len=2 cap=5

    У b capacity хватает.

    Поэтому:

    append(b, 100)

    пишет в третий элемент того же массива:

    ┌───┬───┬─────┬───┬───┐
│ 1 │ 2 │ 100 │ 0 │ 0 │
└───┴───┴─────┴───┴───┘

    Следовательно:

    fmt.Println(a)

    даст:

    [1 2 100]

    Вот здесь абстракция slice начинает протекать.

    12. Как ограничить capacity дочернего slice¶

    Есть full slice expression:

    b := a[:2:2]

    Теперь:

    len(b) = 2
cap(b) = 2

    Следующий:

    b = append(b, 100)

    вынужден получить другой underlying array.

    Это полезно, когда функция получает часть массива и не должна случайно модифицировать данные за пределами логического диапазона.

    13. Slice и удержание памяти¶

    Теперь production-проблема.

    Допустим, мы получили огромный буфер:

    data := make([]byte, 100<<20)

    100 MB.

    Нам нужны первые десять байт:

    header := data[:10]
return header

    На уровне бизнес-кода кажется:

    мы возвращаем 10 bytes

    На уровне GC ситуация может выглядеть так:

    header.ptr
    │
    ↓
100 MB backing array

    Пока жив slice, GC видит ссылку на underlying allocation.

    И вся большая allocation может оставаться reachable.

    Если это повторяется для множества запросов:

    маленькие slices
      ↓
удерживают
      ↓
огромные backing arrays
      ↓
heap растёт
      ↓
GC сканирует больше памяти
      ↓
memory pressure

    Если нужна независимая маленькая копия:

    result := append([]byte(nil), data[:10]...)

    или:

    result := slices.Clone(data[:10])

    Цена — копирование.

    Инженерный компромисс:

    zero-copy
    ↕
retained memory
    ↕
explicit copy

    Что важно запомнить про slice¶

    1. Slice не содержит сами элементы.
    2. Slice descriptor содержит pointer, len и cap.
    3. Копирование slice копирует descriptor.
    4. Разные slices могут разделять один underlying array.
    5. append иногда пишет в тот же array, иногда создаёт новый.
    6. После realloc старые slices продолжают ссылаться на старый array.
    7. Маленький subslice способен удерживать большой allocation.
    8. Точный алгоритм роста capacity не является гарантией языка.

    14. Maps¶

    Теперь структура, которая исторически дала особенно много неправильных учебных моделей.

    На уровне языка:

    m := map[string]int{
    "alice": 10,
    "bob":   20,
}

    Map позволяет найти value по key.

    Но возникает вопрос:

    если элементов миллион,
почему runtime не перебирает миллион keys?

    Потому что ключ сначала превращается в hash.

    Абстрактная модель:

    key
 ↓
hash(key)
 ↓
некоторое место в hash table
 ↓
поиск кандидатов
 ↓
key equality
 ↓
value

    Среднее время lookup при нормальной работе hash table близко к O(1).

    Но это средняя алгоритмическая оценка.

    Фактическая стоимость включает:

    hash computation
+
memory accesses
+
cache misses
+
collision handling
+
key comparison

    15. Map — reference-like value¶

    Спецификация определяет map value как ссылку на implementation-specific структуру данных.

    Поэтому:

    a := map[string]int{
    "x": 1,
}

b := a

b["x"] = 100

    После этого:

    fmt.Println(a["x"])

    получим:

    100

    a и b работают с одной map.

    16. nil map¶

    var m map[string]int

    Здесь:

    m == nil

    Читать можно:

    fmt.Println(m["x"]) // 0

    len:

    len(m) // 0

    delete допустим.

    Но:

    m["x"] = 1

    даст panic:

    assignment to entry in nil map

    Спецификация определяет nil map как пустую для чтения, но добавлять в неё элементы нельзя.

    17. Историческая реализация Go map¶

    Здесь важно поставить временную границу.

    До Go 1.24 builtin map использовал другую hash-table implementation.

    Go 1.24 переключил builtin map на новую реализацию на основе Swiss Tables.

    Поэтому старые статьи с:

    hmap
bmap
B
tophash
overflow bucket
oldbuckets
nevacuate

    описывают историческую реализацию.

    Они полезны для понимания эволюции, но больше не являются описанием текущего builtin map.

    18. Старая модель: buckets¶

    Упрощённо старый map выглядел так:

    hmap
 │
 ├── bucket 0
 ├── bucket 1
 ├── bucket 2
 ├── bucket 3
 ...

    Количество основных buckets было связано с:

    2^B

    Каждый bmap содержал восемь slots.

    Концептуально:

    bucket

tophash:
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ h0 │ h1 │ h2 │ h3 │ h4 │ h5 │ h6 │ h7 │
└────┴────┴────┴────┴────┴────┴────┴────┘

keys:
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ k0 │ k1 │ k2 │ k3 │ k4 │ k5 │ k6 │ k7 │
└────┴────┴────┴────┴────┴────┴────┴────┘

values:
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ v0 │ v1 │ v2 │ v3 │ v4 │ v5 │ v6 │ v7 │
└────┴────┴────┴────┴────┴────┴────┴────┘

    Hash использовался примерно следующим образом:

    hash
 ├── часть → выбор bucket
 └── часть → быстрый fingerprint/tophash

    Runtime сначала проверял маленький tophash.

    Полное сравнение ключа делалось только для подходящих кандидатов.

    19. Что происходило при collision¶

    Если несколько keys попадали в один bucket:

    bucket
┌───────────┐
│ 8 slots   │
└─────┬─────┘
      │ overflow
      ↓
┌───────────┐
│ 8 slots   │
└─────┬─────┘
      │ overflow
      ↓
┌───────────┐
│ ...       │
└───────────┘

    Получалась linked structure из overflow buckets.

    И здесь появляется проблема для CPU.

    Lookup превращается в:

    прочитать bucket
↓
проверить metadata
↓
нет?
↓
перейти по pointer
↓
прочитать следующий bucket

    Каждый pointer chase потенциально означает cache miss.

    20. Grow старого map¶

    Если map становился слишком плотным, создавался новый массив buckets.

    Но переносить огромную map за одну операцию было бы неприятно:

    один Store()
↓
копирование миллиона элементов
↓
latency spike

    Поэтому старая реализация использовала incremental evacuation.

    Хранились одновременно:

    buckets
oldbuckets
nevacuate

    Часть операций постепенно переносила старые buckets в новую таблицу.

    Получалась амортизация работы:

    большая миграция

    размазывалась по множеству последующих операций.

    Это очень важный инженерный паттерн:

    большие O(N) работы в runtime часто стараются разбивать, чтобы уменьшить worst-case latency отдельной пользовательской операции.

    21. Почему map переделали¶

    Старый дизайн работал много лет.

    Проблема заключалась преимущественно в locality.

    Современный CPU очень чувствителен к тому, какие данные находятся рядом в памяти.

    Pointer chasing:

    bucket
  ↓
overflow
  ↓
overflow

    плохо дружит с caches.

    Поэтому появилась другая модель.

    22. Swiss Tables¶

    Начиная с Go 1.24 builtin map построен на дизайне Swiss Table.

    Главная смена модели:

    старый map:
bucket + overflow chains

Swiss:
groups + open addressing + compact metadata

    23. Group¶

    В текущей реализации одна group содержит 8 slots.

    Рядом располагается 8-byte control word.

    control bytes

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ c0 │ c1 │ c2 │ c3 │ c4 │ c5 │ c6 │ c7 │
└────┴────┴────┴────┴────┴────┴────┴────┘

slots

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ k/v│ k/v│ k/v│ k/v│ k/v│ k/v│ k/v│ k/v│
└────┴────┴────┴────┴────┴────┴────┴────┘

    Control byte кодирует:

    empty
deleted
или
часть hash

    Текущая реализация делит hash на:

    H1 = верхние биты
H2 = нижние 7 бит

    H2 хранится в control byte занятого slot.

    24. Зачем H2¶

    Допустим, ищем:

    m["kirill"]

    Вместо:

    сравнить key0
сравнить key1
сравнить key2
...

    runtime сначала получает:

    H2(searchKey)

    и сравнивает его с metadata всей group.

    Например:

    ищем H2 = 53

control:

12  91  53  38  53  empty  7  deleted
         ↑       ↑

    Получаем кандидаты:

    slot 2
slot 4

    И только там делаем полноценное сравнение keys.

    Текущий runtime сравнивает metadata всех восьми slots с помощью битовых операций; идея Swiss Table как раз позволяет проверить группу кандидатов значительно плотнее, чем последовательное сравнение каждого ключа.

    25. False positive H2¶

    H2 содержит только 7 bits.

    Значит два разных hash вполне могут иметь одинаковый H2.

    Это нормально.

    Swiss Table никогда не считает совпадение H2 доказательством равенства keys.

    Алгоритм:

    H2 совпал?
    │
    ├── нет → пропускаем slot
    │
    └── да
         ↓
       Equal(key)
         │
         ├── false → collision
         └── true → нашли

    В комментариях runtime вероятность случайного совпадения конкретного 7-bit H2 оценивается примерно как 1/128.

    26. Open addressing¶

    Swiss Table не строит длинную цепочку overflow buckets.

    Если нужная group не содержит ключ, начинается probing.

    Текущая реализация Go использует quadratic probing.

    Упрощённо:

    hash
 ↓
initial group
 ↓
group A
 ↓
group B
 ↓
group D
 ↓
...

    Конкретная последовательность определяется probing algorithm.

    Поиск прекращается, когда найден подходящий ключ или достигнута group с empty slot, которая доказывает, что дальше ключа в этой probe sequence быть не должно.

    27. Tombstones¶

    Теперь попробуем удалить элемент.

    Наивное решение:

    slot occupied
↓
delete
↓
slot empty

    Но это может сломать lookup.

    Предположим:

    A
↓ collision
B
↓ collision
C

    Key оказался в C.

    Удаляем элемент из B и делаем его empty.

    Теперь lookup начинает с A.

    Доходит до B.

    Видит:

    empty

    и решает:

    дальше probe sequence искать бессмысленно

    Хотя ключ лежит в C.

    Поэтому существует состояние:

    deleted

    или tombstone.

    Оно означает:

    элемента здесь больше нет,
но lookup не должен здесь останавливаться

    Текущая Swiss implementation Go использует именно такую схему.

    28. Load factor¶

    Swiss Table нельзя забивать до 100%.

    Нужные empty slots обеспечивают завершение probing.

    В текущей реализации используется максимальная средняя загрузка около:

    7 / 8

    slots.

    Это implementation detail.

    Студенту полезнее понимать причинность:

    слишком высокая заполненность
↓
длиннее probe sequences
↓
больше memory accesses
↓
lookup деградирует

    Поэтому hash table намеренно оставляет свободное пространство.

    29. Grow Swiss map¶

    Тут Go усложняет классический Swiss Table.

    Если сделать одну огромную Swiss table и при grow полностью переразложить её, получим latency spike.

    Поэтому Go использует несколько tables и directory.

    Текущая архитектура:

    Map
 │
 ↓
Directory
 │
 ├── Table A
 ├── Table B
 ├── Table C
 └── ...

    Верхние bits hash определяют table.

    Внутри table работает Swiss probing.

    Go использует вариант extendible hashing: отдельная table может grow независимо. До текущего implementation limit table может удваиваться, после чего split'ится на две tables; текущий maxTableCapacity равен 1024 slots. Это внутренняя деталь Go 1.27, а не контракт языка.

    Получаем:

    hash
 │
 ├── high bits → directory/table
 │
 └── остальные bits → probing внутри table

    Так большая map разбивается на несколько независимо растущих областей.

    30. Почему Swiss Table быстрее¶

    Слово «Swiss» само по себе ничего не объясняет.

    Причинная цепочка:

    compact metadata
↓
несколько fingerprints читаются вместе
↓
меньше полных key comparisons
↓
данные располагаются плотнее
↓
меньше pointer chasing
↓
лучше cache locality
↓
меньше memory stalls

    То есть выигрыш происходит не потому, что придумали другой математический Big O.

    И старая, и новая hash table имеют примерно O(1) lookup в среднем.

    Разница возникает в константах:

    cache lines
branches
pointer chasing
key comparisons
memory bandwidth

    Вот здесь теория алгоритмов встречается с реальным CPU.

    31. make(map, hint)¶

    m := make(map[string]int, 100_000)

    100_000 — capacity hint.

    Это не означает:

    map максимум на 100000 элементов

    и не означает:

    runtime выделит ровно 100000 slots

    Спецификация говорит, что это initial space approximately для указанного количества элементов; map при необходимости продолжает расти.

    Но хороший hint уменьшает количество промежуточных grows и allocations.

    Для backend это особенно заметно при:

    rows → map
JSON aggregation → map
batch processing → map
cache warmup → map

    если размер приблизительно известен заранее.

    32. Map и concurrency¶

    Очень опасное заблуждение:

    раз map внутри runtime настолько сложная, наверное runtime сам синхронизирует доступ.

    Нет.

    Обычная map не предназначена для произвольного concurrent read/write.

    Например:

    go func() {
    m["x"] = 1
}()

go func() {
    fmt.Println(m["x"])
}()

    Это data race.

    Runtime содержит проверки некоторых concurrent map operations и может завершить программу ошибкой вроде:

    concurrent map read and map write

    Но этот механизм не является synchronization primitive.

    Правильная модель:

    map
+
Mutex/RWMutex

    или архитектура, где map принадлежит одной goroutine.

    Либо специализированный sync.Map.

    33. sync.Map¶

    Теперь особенно важный version trap.

    Огромное количество материалов в интернете объясняет sync.Map через:

    read
dirty
misses

    Это действительно была реализация стандартной библиотеки.

    Например, исходники Go 1.24 и Go 1.25 содержали:

    mu
read
dirty
misses

    и readOnly map.

    Но в текущих Go 1.26/1.27 sync.Map уже использует:

    internal/sync.HashTrieMap[any, any]

    Поэтому разберём обе модели.

    34. Старый sync.Map: read / dirty¶

    Исторически структура выглядела концептуально так:

    sync.Map
 │
 ├── read   ← быстрый concurrent path
 │
 ├── dirty  ← новые/изменяемые entries
 │
 ├── misses
 │
 └── mutex

    read читался через atomic pointer.

    Популярные keys можно было читать без глобального mutex.

    Если key отсутствовал в read, но read.amended == true, приходилось смотреть в dirty под lock.

    Каждый такой slow-path lookup увеличивал:

    misses

    Когда количество misses становилось достаточно большим относительно dirty, runtime считал:

    мы слишком часто платим за slow path

    и продвигал:

    dirty → read

    Это очень интересная адаптивная идея:

    дорогая перестройка структуры

    происходит тогда, когда уже накопилось достаточно работы, которая оправдывает эту перестройку.

    35. entry старого sync.Map¶

    Entry содержал atomic pointer к interface value.

    Состояния примерно:

    value
nil
expunged

    expunged был специальным sentinel для удалённого entry.

    Это позволяло обновлять многие существующие значения атомарно без глобального lock, а structural mutations проводить через dirty под mutex.

    Но теперь это историческая implementation model.

    36. Текущий sync.Map: HashTrieMap¶

    В текущем Go sync.Map — тонкая обёртка:

    type Map struct {
    _ noCopy
    m isync.HashTrieMap[any, any]
}

    Hash trie можно представить как дерево, путь по которому определяется hash ключа.

    В текущей реализации каждый внутренний node имеет 16 children.

    Почему 16?

    Берётся 4 bits hash на каждом уровне:

    4 bits
↓
0..15

    Следующие 4 bits:

    ещё один уровень

    И так далее.

    Схема:

    hash:

1011 0010 1111 0100 ...
│    │    │
│    │    └────────→ следующий уровень
│    └─────────────→ следующий уровень
└──────────────────→ root child

    37. Load в HashTrieMap¶

    Lookup:

    key
 ↓
hash(key)
 ↓
root
 ↓ 4 bits
child
 ↓ 4 bits
child
 ↓
...
 ↓
entry

    Переходы выполняются через atomic pointer loads.

    Для read-heavy workload это принципиально важно:

    Load

    может обходить дерево без общего глобального mutex.

    38. Store в HashTrieMap¶

    Для изменения структуры всё равно нужна синхронизация.

    Но lock локализован на конкретном internal node.

    Упрощённо:

    найти место вставки
↓
lock нужного indirect node
↓
повторно проверить состояние
↓
insert / expand
↓
unlock

    То есть:

    не один mutex на всю map

    а более granular synchronization.

    Если два keys изменяют разные части trie, потенциально уменьшается contention.

    39. Hash collision в HashTrieMap¶

    Может случиться:

    hash(key1) == hash(key2)

    Путь в trie будет полностью одинаковым.

    Тогда бесконечно строить следующие уровни бессмысленно.

    Текущая implementation использует overflow list у leaf entry для настоящих полных hash collisions.

    Это редкий slow path.

    40. Когда использовать sync.Map¶

    Документация самой стандартной библиотеки подчёркивает, что sync.Map специализирована, а большинство кода выигрывает от обычной typed map плюс явная синхронизация. Среди целевых сценариев указаны read-mostly/write-once entries и работа разных goroutines преимущественно с различными keys.

    Почему обычная:

    map[K]V + sync.RWMutex

    часто удобнее?

    Потому что можно поддерживать сложный invariant:

    mu.Lock()

m1[id] = ...
m2[id] = ...
counter++

mu.Unlock()

    sync.Map синхронизирует операции над самой map.

    Она не делает автоматически атомарным ваш бизнес-invariant из пяти операций.

    Что важно запомнить про map¶

    1. map — hash-based структура.
    2. Реализация map изменилась в Go 1.24.
    3. Старые hmap/bmap/overflow относятся к pre-Go-1.24.
    4. Текущий builtin map использует Swiss Tables.
    5. Swiss Table делает lookup через compact control metadata и probing.
    6. Tombstone нужен, чтобы delete не ломал probe chain.
    7. Реальный выигрыш Swiss Tables связан прежде всего с CPU cache locality и количеством memory accesses.
    8. sync.Map также изменила внутреннюю реализацию.
    9. Текущий sync.Map использует concurrent hash trie.
    10. Обычная map не становится thread-safe из-за сложного runtime implementation.

    41. Interfaces¶

    Теперь тип, который выглядит совершенно безобидно:

    var x any = 42

    Но возникает вопрос:

    Как interface может хранить одновременно:

    42
"hello"
*User
[]byte
http.Handler

    Размеры этих объектов совершенно разные.

    Ответ:

    interface хранит информацию о динамическом типе и representation значения.

    В текущем ABI empty interface (any) концептуально имеет layout:

    type EmptyInterface struct {
    Type *Type
    Data unsafe.Pointer
}

    А interface с methods:

    type NonEmptyInterface struct {
    ITab *ITab
    Data unsafe.Pointer
}

    42. Static type и dynamic type¶

    var x any = 42

    У переменной есть:

    static type = any
dynamic type = int
dynamic value = 42

    Это принципиально разные понятия.

    Например:

    func printValue(v any) {
}

    Компилятор знает только:

    v : any

    Но в runtime:

    dynamic type

    может быть чем угодно.

    43. Empty interface¶

    Ментально:

    any

┌──────────────┐
│ type pointer │ ───→ runtime metadata for int
├──────────────┤
│ data         │ ───→ representation of 42
└──────────────┘

    Уточнение: конкретный способ хранения data зависит от dynamic type. Internal ABI допускает direct interface representation для некоторых односоставных pointer-sized values; в остальных случаях data указывает на значение. Это implementation detail, поэтому учебную модель лучше держать как «type information + data representation».

    44. Non-empty interface и itab¶

    Допустим:

    type Writer interface {
    Write([]byte) (int, error)
}

    Теперь runtime нужно знать не только concrete type.

    Нужно ещё понимать:

    как concrete type реализует конкретный interface

    Для этого используется ITab.

    В текущем ABI она содержит:

    interface type
concrete type
type hash
method function pointers

    Модель:

    interface value
┌──────────┐
│ itab ──────────────┐
├──────────┤         │
│ data     │         │
└──────────┘         │
                     ↓
             ┌───────────────────┐
             │ interface type    │
             │ concrete type     │
             │ method pointers   │
             └───────────────────┘

    При вызове:

    w.Write(data)

    interface dispatch может использовать найденный method entry.

    45. Interface conversion не обязательно означает allocation¶

    Распространённое упрощение:

    положили value в interface — получили heap allocation.

    Не обязательно.

    Allocation зависит от:

    • concrete type;
    • representation;
    • escape analysis;
    • дальнейшего lifetime;
    • оптимизаций compiler.

    Правильный способ узнать:

    go build -gcflags="-m=2"

    и benchmark:

    go test -bench=. -benchmem

    А не угадывать по внешнему виду interface.

    46. nil interface¶

    Вот один из классических Go traps.

    var err error = nil

fmt.Println(err == nil)

    Получим:

    true

    Внутри:

    interface

type = nil
data = nil

    То есть:

    (nil, nil)

    47. Typed nil внутри interface¶

    Теперь:

    type MyError struct{}

func (*MyError) Error() string {
    return "error"
}

var e *MyError = nil
var err error = e

    Проверяем:

    fmt.Println(err == nil)

    Получим:

    false

    Почему?

    Потому что interface выглядит концептуально так:

    dynamic type = *MyError
dynamic value = nil

    То есть:

    (*MyError, nil)

    Первое поле interface уже не nil.

    А nil interface требует:

    (nil, nil)

    48. Практический баг¶

    func findUser() error {
    var err *MyError

    // ...
    return err
}

    Кажется:

    err == nil

    значит функция возвращает nil.

    Но происходит conversion:

    *MyError → error

    И возвращается:

    (*MyError, nil)

    Следовательно:

    if err := findUser(); err != nil {
    // зайдём сюда
}

    Поэтому typed nil — не экзотика runtime.

    Это реальный production bug.

    49. Type assertion¶

    v, ok := x.(string)

    Что мы спрашиваем у runtime?

    имеет ли interface x dynamic type,
совместимый с string?

    Для concrete type assertion runtime может проверить type information.

    Для assertion к non-empty interface требуется проверить, реализует ли dynamic concrete type нужный interface; runtime использует и кэширует соответствующую ITab.

    50. Assertion с ok¶

    s, ok := v.(string)

    Если тип неправильный:

    s = ""
ok = false

    Паники нет.

    51. Assertion без ok¶

    s := v.(string)

    Если dynamic type несовместим:

    panic

    Например:

    interface conversion: interface {} is int, not string

    Поэтому в boundary code:

    JSON
plugin
generic container
reflection-like APIs

    чаще нужен ok.

    Что важно запомнить про interface¶

    1. Interface value содержит dynamic type information и data.
    2. Static type переменной и dynamic type значения — разные вещи.
    3. any и interface с methods имеют разные internal representations.
    4. Для non-empty interface runtime использует ITab.
    5. Nil interface означает отсутствие и dynamic type, и dynamic value.
    6. Typed nil внутри interface обычно не равен nil.
    7. Interface conversion не означает автоматически heap allocation.
    8. Type assertion работает с runtime type information.

    52. Channels¶

    Теперь конструкция, которую особенно опасно объяснять фразой:

    channel — потокобезопасная очередь.

    Почему опасно?

    Потому что unbuffered channel вообще не хранит очередь пользовательских элементов.

    Более точная модель:

    channel — runtime synchronization object, который может содержать ring buffer и очереди ожидающих senders/receivers.

    53. chan value¶

    ch := make(chan int, 4)

    Переменная ch является reference-like value.

    Она указывает на runtime object hchan.

    В текущем runtime hchan содержит, среди прочего:

    qcount
dataqsiz
buf
elemsize
closed
sendx
recvx
recvq
sendq
lock

    Модель:

    chan value
    │
    ↓
┌─────────────────────┐
│ hchan               │
│                     │
│ qcount              │
│ capacity            │
│ buffer pointer      │
│ send index          │
│ receive index       │
│ send wait queue     │
│ receive wait queue  │
│ closed              │
│ mutex               │
└─────────────────────┘

    54. Buffered channel¶

    ch := make(chan int, 3)

    Буфер можно представить как circular queue:

    ┌────┬────┬────┐
│ 10 │ 20 │    │
└────┴────┴────┘
 ↑         ↑
recvx     sendx

    Runtime хранит:

    qcount = количество элементов
dataqsiz = capacity
sendx
recvx

    При достижении конца indices закольцовываются.

    55. Send в buffered channel¶

    ch <- value

    Возможны несколько ситуаций.

    Есть ожидающий receiver¶

    sender
  │
  └────────→ receiver

    Значение может быть передано ожидающей goroutine.

    Receiver нет, buffer не заполнен¶

    value
  ↓
ring buffer

    Buffer full¶

    Sender должен ждать.

    Runtime помещает информацию об ожидающей goroutine в:

    sendq

    и паркует goroutine.

    56. Receive¶

    v := <-ch

    Аналогично:

    Есть waiting sender¶

    Можно согласовать операцию с ним.

    В buffer есть данные¶

    Берём следующий элемент.

    Данных нет¶

    Receiver попадает в:

    recvq

    и goroutine паркуется.

    57. sudog¶

    Как положить goroutine в очередь ожидания channel?

    Runtime использует структуру sudog.

    Упрощённо:

    hchan.recvq

sudog → sudog → sudog

  │       │       │
  ↓       ↓       ↓
  G       G       G

    sudog представляет ожидание конкретной goroutine на конкретном synchronization object.

    Когда операция может продолжиться:

    runtime
↓
убирает sudog из очереди
↓
goready(g)
↓
goroutine снова runnable

    То есть blocking channel operation не означает:

    OS thread должен стоять и ждать

    Паркуется goroutine.

    Scheduler может использовать thread для другой работы.

    58. Unbuffered channel¶

    ch := make(chan int)

    Capacity:

    0

    Никакого пользовательского ring buffer нет.

    Send может завершиться только при наличии receiver.

    Receive — при наличии sender.

    Модель:

    sender G
   │
   │ value
   ↓
receiver G

    Это rendezvous.

    Runtime может копировать значение непосредственно между sender и receiver.

    Поэтому:

    unbuffered channel = очередь длины ноль

    формально иногда помогает.

    Но ментальная модель rendezvous значительно полезнее.

    59. Channel lock¶

    В hchan существует внутренний lock.

    Он защищает state канала и связанные sudog structures.

    Это значит, что:

    100 goroutines
↓
один hot channel

    могут получить:

    contention
cache-line bouncing
goroutine parking/wakeup
scheduler work

    Channel thread-safe.

    Это не означает:

    channel бесплатный

    60. Что происходит под нагрузкой¶

    Например:

    jobs := make(chan Job, 100)

for i := 0; i < 1000; i++ {
    go producer(jobs)
}

for i := 0; i < 10; i++ {
    go worker(jobs)
}

    Если producers значительно быстрее consumers:

    buffer заполняется
↓
producers начинают блокироваться
↓
sendq растёт
↓
много parked goroutines
↓
scheduler постоянно будит следующие

    С одной стороны, это естественный backpressure.

    С другой:

    один канал

    может стать synchronization hotspot.

    Поэтому размер channel buffer — часть архитектуры нагрузки, а не декоративное число.

    61. close¶

    close(ch)

    Channel переходит в closed state.

    Новые sends запрещены:

    ch <- x

    даст panic.

    Receive продолжает работать.

    Если buffer ещё содержит элементы:

    receive buffered values

    После опустошения:

    v, ok := <-ch

    возвращает:

    zero value
false

    Close также пробуждает ожидающие goroutines.

    62. nil channel¶

    var ch chan int

    ch == nil.

    Send:

    ch <- 1

    будет ждать бесконечно.

    Receive:

    <-ch

    тоже будет ждать бесконечно.

    Спецификация прямо определяет nil channel как никогда не готовый к communication.

    Это кажется бесполезным.

    Но через минуту пригодится в select.

    Что важно запомнить про channels¶

    1. Channel — runtime synchronization structure.
    2. Buffered channel содержит circular buffer.
    3. Unbuffered channel работает как rendezvous sender/receiver.
    4. sendq и recvq хранят ожидающие goroutines через sudog.
    5. Blocked goroutine паркуется через scheduler.
    6. Внутри channel есть synchronization lock.
    7. Hot channel способен стать contention point.
    8. Buffer создаёт ограниченную очередь и механизм backpressure.
    9. Nil channel никогда не готов.

    63. select¶

    Теперь:

    select {
case v := <-a:
    use(v)

case b <- result:
    sent()

case <-ctx.Done():
    cancel()
}

    Высокоуровневая модель:

    выбрать одну операцию, которая сейчас может выполниться.

    Но что делать runtime, если готовы сразу три?

    Спецификация требует выбрать одну из готовых communication operations pseudo-random образом. Поэтому порядок case не задаёт приоритет.

    64. Почему select сложно реализовать¶

    Представим:

    select {
case <-a:
case <-b:
case <-c:
case <-d:
}

    Если ничего не готово, goroutine должна ждать одновременно:

    a
b
c
d

    Но goroutine одна.

    Она не может физически:

    gopark(a)
gopark(b)
gopark(c)
gopark(d)

    четыре раза.

    Runtime должен зарегистрировать одно ожидание сразу во всех channel queues.

    65. Как работает selectgo¶

    Текущий runtime делает примерно следующие фазы.

    Фаза 1. Формируется случайный poll order¶

    Cases перемешиваются.

    Зачем?

    Если всегда проверять сверху вниз:

    case <-a
case <-b

    то a получит систематический приоритет.

    Runtime формирует permuted poll order.

    66. Фаза 2. Lock order¶

    Select работает сразу с несколькими channels.

    Если locks захватывать случайно:

    G1:
lock A
lock B

G2:
lock B
lock A

    получаем classic lock-order deadlock.

    Поэтому runtime сортирует channels по адресу и получает единый lock order.

    После этого locks берутся в согласованном порядке.

    67. Фаза 3. Проверить готовые cases¶

    Runtime проходит cases в randomized poll order.

    Для receive проверяет:

    есть waiting sender?
есть buffered value?
channel closed?

    Для send:

    есть waiting receiver?
есть место в buffer?
channel closed?

    Если case готов:

    выполняем
↓
return

    68. Фаза 4. default¶

    Если ничего не готово и присутствует:

    default:

    runtime разблокирует channels и сразу выполняет default.

    Goroutine не паркуется.

    69. Фаза 5. Зарегистрироваться на всех channels¶

    Если default нет:

    ничего не готово
↓
нужно уснуть

    Для каждого case runtime получает sudog.

    Одна goroutine оказывается зарегистрирована:

    channel A recvq ──→ sudog ──┐
channel B recvq ──→ sudog ──┤
channel C sendq ──→ sudog ──┤
                            ↓
                            G

    После этого:

    gopark

    70. Один case победил¶

    Допустим, значение пришло в B.

    B пробуждает goroutine.

    Но registrations в A и C ещё существуют.

    После wakeup runtime снова блокирует channels и удаляет проигравшие sudog entries.

    В исходниках это буквально разделено на проход:

    pass 1 — найти готовый case
pass 2 — enqueue на channels
sleep
pass 3 — dequeue unsuccessful cases

    Вот почему select — гораздо более сложная операция, чем обычный if.

    71. Nil channel как выключенный case¶

    Теперь nil channel становится полезным.

    var ch <-chan int

    В select:

    select {
case v := <-ch:
    ...
case <-ctx.Done():
    ...
}

    Если:

    ch == nil

    первый case никогда не готов.

    То есть:

    nil channel
=
disabled select case

    Очень удобный паттерн для state machine.

    72. select + default и busy loop¶

    Плохой код:

    for {
    select {
    case v := <-ch:
        process(v)
    default:
    }
}

    Если ch пуст:

    select
↓
default
↓
loop
↓
select
↓
default
↓
...

    Goroutine никогда не паркуется.

    Получаем:

    100% CPU

    и backend может внезапно начать греть ядро, хотя «ничего не делает».

    default превращает blocking select в polling.

    Это осознанный архитектурный выбор.

    73. Fairness select¶

    Нельзя обещать:

    каждый channel будет обслуживаться строго по очереди

    Выбор среди готовых cases pseudo-random.

    Это уменьшает систематический bias.

    Но strict fairness guarantee здесь нет.

    Если нужен строгий scheduling policy:

    priority queue
round robin
weighted scheduler

    его нужно строить явно.

    75. context¶

    Теперь финальный слой.

    ctx, cancel := context.WithTimeout(
    context.Background(),
    2*time.Second,
)
defer cancel()

    Очень легко создать миф:

    context — специальная магическая сущность для отмены goroutine.

    Нет.

    Во-первых:

    Context

    — обычный interface.

    У него четыре метода:

    Deadline()
Done()
Err()
Value()

    Во-вторых, cancellation остаётся cooperative.

    Context не может насильно остановить произвольную goroutine.

    76. Context как цепочка объектов¶

    Берём:

    ctx := context.Background()

ctx = context.WithValue(ctx, requestIDKey, requestID)

ctx, cancel := context.WithTimeout(ctx, time.Second)

ctx = context.WithValue(ctx, userKey, user)

    Получается примерно:

    valueCtx(user)
      │
      ↓
timerCtx
      │
      ↓
valueCtx(requestID)
      │
      ↓
backgroundCtx

    Каждый новый context обычно оборачивает parent.

    77. cancellation tree¶

    Для cancellation структура становится деревом.

    root, cancelRoot := context.WithCancel(context.Background())

a, _ := context.WithCancel(root)
b, _ := context.WithCancel(root)

a1, _ := context.WithCancel(a)
a2, _ := context.WithCancel(a)

    Логически:

                 root
            /    \
           a      b
         /   \
       a1     a2

    Вызываем:

    cancelRoot()

    Отмена распространяется вниз:

    root
↓
a
↓ ↓
a1 a2

и

root
↓
b

    Именно поэтому документация говорит, что cancellation parent context отменяет все derived contexts.

    78. cancelCtx¶

    В текущей реализации ключевой тип концептуально содержит:

    parent Context
mutex
done
children
err
cause

    Исходник:

    type cancelCtx struct {
    Context

    mu       sync.Mutex
    done     atomic.Value
    children map[canceler]struct{}
    err      atomic.Value
    cause    error
}

    Здесь уже видна вся механика.

    Никакой мистики.

    79. Done channel создаётся лениво¶

    Интересная оптимизация.

    ctx.Done()

    должен вернуть channel.

    Но не каждый context когда-либо используется через Done.

    Зачем сразу создавать channel для каждого?

    В текущем cancelCtx он хранится через atomic.Value и создаётся lazy при первом Done().

    Получается:

    WithCancel
↓
cancelCtx создан
↓
Done ни разу не вызван
↓
channel allocation можно избежать

    80. Как child подключается к parent¶

    При создании:

    child, cancel := context.WithCancel(parent)

    вызывается логика propagateCancel.

    Если parent является обычным cancelable context стандартной библиотеки, child регистрируется в:

    parent.children

    под mutex.

    Схема:

    parent.cancelCtx
│
├── child1
├── child2
└── child3

    81. Что делает cancel()¶

    При:

    cancel()

    текущий cancelCtx.cancel примерно:

    1. ставит err;
    2. записывает cause;
    3. закрывает done;
    4. проходит по children;
    5. вызывает cancellation каждого child;
    6. очищает children;
    7. при необходимости удаляет себя из parent.

    То есть:

    cancel(parent)
↓
close(parent.Done)
↓
cancel(child1)
↓
cancel(child2)
↓
cancel(child3)

    82. Почему close(channel) идеально подходит для cancellation¶

    Нужно сообщить:

    событие произошло

    не одному consumer.

    А всем:

    100 goroutines должны увидеть cancellation

    Если посылать значения:

    done <- struct{}{}

    одно значение получит один receiver.

    Закрытие channel:

    close(done)

    делает receive готовым для всех текущих и будущих receivers.

    Поэтому:

    ctx.Done()

    использует именно broadcast через close.

    83. Cancellation не убивает goroutine¶

    Вот код:

    go func() {
    for {
        doCPUWork()
    }
}()

    Внешний:

    cancel()

    ничего с этой goroutine автоматически не сделает.

    Она вообще не смотрит на context.

    Нужно:

    go func() {
    for {
        select {
        case <-ctx.Done():
            return
        default:
            doCPUWork()
        }
    }
}()

    Или underlying blocking API должен принимать context:

    db.QueryContext(ctx, ...)
req = req.WithContext(ctx)

    Модель:

    context sends cancellation signal
↓
code observes signal
↓
code voluntarily terminates operation

    84. timerCtx¶

    context.WithTimeout(parent, 2*time.Second)

    строится поверх deadline.

    Текущий timerCtx использует runtime timer через time.AfterFunc.

    Когда deadline наступает:

    timer fires
↓
cancel(...)
↓
Done closes
↓
children canceled

    85. Зачем обязательно вызывать cancel¶

    ctx, cancel := context.WithTimeout(parent, time.Minute)
defer cancel()

    Иногда думают:

    timeout всё равно через минуту сработает, зачем cancel?

    Потому что child связан с parent.

    Документация прямо предупреждает: если не вызвать CancelFunc, parent может продолжать удерживать child и его descendants до отмены parent, а связанный timer также продолжает существовать до своего deadline. go vet проверяет использование CancelFunc по control-flow paths.

    В backend:

    100k requests
↓
создали contexts
↓
работа завершилась за 20 ms
↓
timeout был 30 sec
↓
cancel забыли
↓
лишние contexts/timers остаются жить

    Получаем unnecessary memory pressure.

    86. Value — это тоже цепочка¶

    context.WithValue(parent, key, value)

    не превращает context в огромную map.

    Концептуально строится:

    valueCtx(key3)
    ↓
valueCtx(key2)
    ↓
valueCtx(key1)
    ↓
root

    Поиск:

    ctx.Value(key1)

    идёт по цепочке contexts, пока не найдёт matching key.

    Следствие:

    Context.Value нельзя воспринимать как бесплатный универсальный dependency container.

    Глубокая цепочка увеличивает стоимость lookup.

    Главная проблема обычно даже не performance, а потеря явных dependencies API.

    Context values предназначены прежде всего для request-scoped metadata.

    87. Необычный случай: custom Context¶

    Интересный internal detail.

    Что если parent — пользовательская реализация Context, а стандартная библиотека не может получить её cancelCtx?

    Текущий propagateCancel имеет несколько путей.

    Сначала пытается присоединиться непосредственно к parent cancelCtx.

    Если parent предоставляет механизм AfterFunc, используется он.

    В общем fallback-case создаётся отдельная goroutine:

    go func() {
    select {
    case <-parent.Done():
        child.cancel(...)
    case <-child.Done():
    }
}()

    То есть custom Context способен сделать обычный:

    WithCancel(customParent)

    дороже, вплоть до дополнительной goroutine.

    Вот пример того, почему знание internals иногда имеет практический смысл.

    88. Cancellation tree под нагрузкой¶

    Представим один root:

                    root
          /      |      \
       1000    1000    1000
       tasks    tasks    tasks

    Теперь:

    cancelRoot()

    Требуется:

    обойти descendants
↓
закрыть Done channels
↓
разбудить множество goroutines
↓
они становятся runnable
↓
scheduler должен их обработать

    Логически cancellation почти мгновенная.

    Физически:

    10 000 blocked goroutines

    90. Как context ломают¶

    Типичная ошибка:

    func handler(w http.ResponseWriter, r *http.Request) {
    go process(context.Background())
}

    Request закончился.

    Но новая goroutine получила:

    Background()

    Связь с lifetime HTTP request уничтожена.

    Теперь:

    client disconnected
↓
request canceled
↓
background process продолжает работать

    Иногда именно это нужно.

    Но это должно быть осознанное detach operation.

    91. Deadline propagation¶

    Представим:

    incoming request timeout = 2 s

    Внутри handler:

    ctx, cancel := context.WithTimeout(r.Context(), 10*time.Second)

    Этот child фактически не получит десять секунд, если parent истекает через две.

    Текущий WithDeadline проверяет parent deadline и не пытается расширить уже более ранний deadline.

    Модель:

    parent deadline: 2s
child asks:      10s

effective lifetime:
2s

    Child не может пережить cancellation parent без явного detach.

    92. Context как механизм backpressure¶

    Context сам не ограничивает throughput.

    Но он ограничивает lifetime работы.

    Без cancellation:

    upstream timeout
↓
response уже никому не нужен
↓
backend продолжает DB query
↓
продолжает RPC
↓
занимает connection pool
↓
занимает CPU
↓
результат выбрасывается

    С propagation:

    upstream timeout
↓
cancel
↓
downstream work прекращается
↓
resources освобождаются раньше

    При высокой нагрузке это способно разделить:

    система деградировала, но восстановилась

    и:

    система продолжила выполнять уже бесполезную работу и сама себя добила

    Что важно запомнить про context¶

    1. Context — interface, не магическая runtime primitive.
    2. Derived contexts образуют цепочку и cancellation tree.
    3. cancelCtx хранит children.
    4. Done — channel, закрытие которого работает как broadcast.
    5. Cancellation распространяется от parent к descendants.
    6. Cancellation cooperative: goroutine должна её наблюдать.
    7. WithTimeout использует timer.
    8. CancelFunc нужно вызывать для своевременного освобождения ресурсов.
    9. WithValue формирует цепочку contexts, а не обычную hash map.
    10. Массовый cancel способен разбудить огромное число goroutines одновременно.

    96. Главный инженерный вывод¶

    Все рассмотренные abstractions достаточно маленькие и удобные на уровне языка.

    Именно поэтому ими легко злоупотребить.

    slice

    скрывает ownership памяти.

    map

    скрывает hash table и memory locality.

    interface

    скрывает dynamic type representation.

    channel

    скрывает synchronization, parking и scheduler.

    select

    скрывает регистрацию ожидания сразу в нескольких synchronization objects.

    context

    скрывает дерево cancellation и массовое пробуждение goroutines.

    Хорошая ментальная модель поэтому выглядит так:

    syntax
↓
descriptor / runtime object
↓
memory
↓
synchronization
↓
scheduler / allocator / GC
↓
поведение под нагрузкой

    Если смотреть на Go только через синтаксис:

    append
map
interface
channel
select
context

    выглядят почти тривиально.

    Если посмотреть под abstraction boundary, становится видно, где появляются реальные production-проблемы:

    aliasing
allocations
memory retention
hash collisions
cache misses
lock contention
goroutine parking
wake-up storms
cancellation leaks

    Именно поэтому «знать Go» — это в какой-то момент перестать видеть только:

    s = append(s, x)

    и начать видеть возможную цепочку:

    append
→ growslice
→ allocation
→ copy
→ heap
→ GC
→ latency

    То же самое для:

    map
→ hash
→ Swiss group
→ cache lines

channel
→ hchan
→ sudog
→ scheduler

context
→ cancellation tree
→ channel close
→ goroutine wakeup
→ backend resource release

    Это и есть уровень, на котором структуры данных Go становятся частью инженерной модели backend, а не набором конструкций языка.
