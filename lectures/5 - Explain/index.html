    5. PostgreSQL: Explain¶

    Техническая лекция. Основная версия — PostgreSQL 18. На 11 ноября 2026 года PostgreSQL 19 еще находится на стадии кандидата на выпуск, стабильный релиз запланирован на 19 ноября. Основные механизмы, которые мы будем разбирать, применимы и к предыдущим версиям.

    1. Почему PostgreSQL вообще нужен планировщик?¶

    Предположим, у нас есть таблица с десятью миллионами заказов.

    SELECT *
FROM orders
WHERE customer_id = 42;

    На первый взгляд задача элементарная: найти заказы клиента 42.

    Но как именно их искать?

    PostgreSQL может прочитать таблицу целиком, проверить customer_id у каждой строки и отбросить неподходящие.

    Если есть индекс по customer_id, можно воспользоваться им. Индекс позволит найти ссылки на подходящие строки, после чего PostgreSQL сможет получить сами строки из таблицы.

    Есть и третий вариант: сначала собрать через индекс ссылки на подходящие строки, сгруппировать обращения к страницам таблицы и затем прочитать необходимые страницы.

    Все три способа возвращают одинаковый результат.

    Но стоимость выполнения у них разная.

    Допустим, клиенту 42 принадлежит всего три заказа. Читать десять миллионов строк ради трех результатов было бы расточительно.

    А теперь изменим условие:

    SELECT *
FROM orders
WHERE customer_id > 0;

    Предположим, ему соответствует 99% таблицы.

    Индекс есть. Но зачем через него получать ссылки практически на каждую строку, затем обращаться к соответствующим страницам таблицы?

    Последовательное чтение может оказаться существенно дешевле.

    Получается, наличие индекса само по себе не определяет оптимальный способ выполнения запроса. Важны количество подходящих строк, их физическое расположение, объем данных, стоимость доступа и другие условия.

    Вот здесь и появляется планировщик PostgreSQL — планировщик и оптимизатор запросов.

    Он строит варианты выполнения SQL-запроса, оценивает их стоимость и выбирает один из них.

    Но возникает вопрос: откуда он знает, сколько строк соответствует условию?

    Он ведь еще не выполнял наш SELECT.

    Это ключевая проблема, которую мы будем постепенно разбирать.

    1.1. Два основных участника¶

    Планировщик

    Получает обработанное представление SQL-запроса, использует статистику таблиц, индексов и стоимости операций, сравнивает допустимые планы и выбирает способ выполнения.

    ↓

    План выполнения

    Дерево операций: откуда читать строки, как фильтровать, соединять, сортировать и агрегировать данные.

    ↓

    Исполнитель

    Выполняет узлы выбранного плана, обращается к индексам и страницам таблиц, проверяет условия и возвращает результат.

    Планировщик работает с прогнозами. Исполнитель — с реальными данными.

    Отсюда два инструмента:

    • EXPLAIN показывает выбранный план и прогноз планировщика.
    • EXPLAIN ANALYZE действительно выполняет запрос и дополняет план фактическими измерениями.

    Сравнивая прогноз и реальность, мы можем понять, где модель планировщика ошиблась и к каким последствиям это привело.

    2. Как читать дерево EXPLAIN¶

    Начнем с запроса:

    EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 42;

    Предположим, для него выбран следующий план.

    Условный пример плана. Числа иллюстративные.

    Index Scan using idx_orders_customer on orders
  (cost=0.43..28.50 rows=5 width=64)
  Index Cond: (customer_id = 42)

    Здесь пока все просто: один узел Index Scan.

    Добавим сортировку:

    SELECT *
FROM orders
WHERE customer_id = 42
ORDER BY total_amount DESC;

    Возможный план:

    Sort
  Sort Key: total_amount DESC
  -> Index Scan using idx_orders_customer on orders
       Index Cond: (customer_id = 42)

    Внешний узел Sort получает строки от дочернего узла Index Scan.

                  Sort
   Получает строки, сортирует
       и отдает результат
                ↑
           Index Scan
  Ищет строки по индексу
         customer_id

    План принято читать с нижних узлов вверх, но при этом нужно понимать, кто запускает их выполнение.

    В типичной модели исполнитель использует интерфейс, похожий на итератор: родитель запрашивает следующую строку у дочернего узла.

    Например, Sort должен получить строки от Index Scan, прежде чем сможет полностью отсортировать их.

    Для простого Index Scan получение строк может быть потоковым: нашли очередную подходящую строку — передали наверх.

    У Sort поведение другое. Обычная сортировка должна собрать входные строки, прежде чем сможет выдать первую отсортированную строку.

    И вот это принципиально.

    Два SQL-запроса могут вернуть одинаковое количество строк, но один начнет отдавать результат практически сразу, а другой сначала потратит существенное время на подготовку.

    Для описания этой разницы в плане существуют два значения cost.

    3. Расчетная стоимость (cost) — что оценивает PostgreSQL¶

    Посмотрим на строку:

    Seq Scan on orders
  (cost=0.00..18500.00 rows=100000 width=64)

    Разберем:

    cost=0.00..18500.00
     ^       ^
     |       |
   startup  total

    3.1. Начальная стоимость (startup cost)¶

    Startup cost — расчетная стоимость работы, которую нужно выполнить до того, как узел сможет выдать первую строку.

    У обычного Seq Scan она часто близка к нулю.

    Почему?

    Потому что последовательное сканирование может начать отдавать подходящие строки без предварительного чтения всей таблицы.

    А у Sort начальная стоимость бывает большой.

    Сортировка должна получить и обработать входные данные до выдачи первой строки.

    3.2. Полная стоимость (total cost)¶

    Total cost — расчетная стоимость выполнения узла до завершения, то есть до выдачи всех его строк.

    И здесь есть две важные детали.

    Первая: cost измеряется в условных единицах, а не в миллисекундах.

    cost=0.00..18500.00

    Это не 18 500 миллисекунд, не 18,5 секунды и не 18 500 операций ввода-вывода.

    Это число из внутренней модели стоимости PostgreSQL.

    Вторая: стоимость родительского узла включает расчетную стоимость его дочерних узлов.

    Поэтому нельзя взять cost каждого узла дерева, сложить все числа и получить общую стоимость запроса.

    Получится двойной учет.

    3.3. Откуда берутся условные единицы¶

    PostgreSQL использует набор коэффициентов стоимости.

    При стандартных настройках PostgreSQL 18:

    Параметр Значение Что моделирует
    seq_page_cost 1.0 Последовательный доступ к странице
    random_page_cost 4.0 Непоследовательный доступ к странице
    cpu_tuple_cost 0.01 Обработка строки
    cpu_index_tuple_cost 0.005 Обработка записи индекса
    cpu_operator_cost 0.0025 Вычисление оператора или функции

    Это относительные коэффициенты, определяющие предпочтения планировщика. Значения для конкретного экземпляра PostgreSQL можно изменить.

    Возьмем простейшую таблицу:

    • 100 000 строк;
    • 1000 страниц данных;
    • никаких условий WHERE;
    • без параллельного выполнения.

    Упрощенная формула последовательного сканирования:

    seq_page_cost — расчетная стоимость последовательного чтения одной страницы; cpu_tuple_cost — расчетная стоимость обработки одной строки. В этой учебной модели мы считаем, что дополнительных условий и вычислений нет, и сканирование доходит до конца таблицы. Все стоимости выражены в условных единицах, а не в миллисекундах.

    Стоимость Seq Scan =
    (Количество страниц таблицы × seq_page_cost)
  + (Количество обрабатываемых строк × cpu_tuple_cost)

    Для таблицы из 1 000 страниц и 100 000 строк подставляем стандартные коэффициенты seq_page_cost = 1,0 и cpu_tuple_cost = 0,01:

    Чтение страниц:    1 000 × 1,0  = 1 000
Обработка строк: 100 000 × 0,01 = 1 000
                                 -----
Итого:                           2 000 условных единиц

    Получаем приблизительный план:

    Seq Scan on orders
  (cost=0.00..2000.00 rows=100000 width=...)

    Теперь добавим:

    WHERE status = 'PAID'

    PostgreSQL должен вычислять условие для просматриваемых строк.

    Если для упрощения считать стоимость проверки одной операцией с коэффициентом cpu_operator_cost, появится дополнительная величина:

    Проверка условия: 100 000 строк × 0,0025 = 250
Итого с фильтром: 2 000 + 250 = 2 250 условных единиц

    Расчетная стоимость полного сканирования увеличится примерно до 2250.

    Заметь: если условию соответствует 10% строк, последовательное сканирование все равно должно проверить все строки таблицы.

    Меньшее число строк в результате не означает пропорционального уменьшения работы.

    Полная реальная формула сложнее: есть стоимость выражений, особенности хранения, параметры доступа и другие слагаемые. Но этот пример показывает главный принцип формирования cost.

    3.4. Почему random_page_cost = 4.0?¶

    При индексном поиске PostgreSQL может обращаться к страницам таблицы в непоследовательном порядке.

    Для жестких дисков случайные обращения особенно дороги. На SSD разница меньше, но не исчезает автоматически.

    Кроме того, планировщик учитывает ожидаемый эффект кеширования.

    Поэтому random_page_cost = 4.0 — модель усредненной относительной стоимости, а не утверждение, что любой случайный доступ физически в четыре раза медленнее последовательного.

    На некоторых системах с быстрыми накопителями и хорошим кешированием уменьшение random_page_cost может улучшить выбор планов.

    Но менять его только ради одного медленного запроса опасно: параметр влияет на стоимость доступа для множества запросов.

    3.5. Почему минимальная полная стоимость не всегда определяет выбор¶

    Предположим, планировщик сравнивает два варианта:

    План Начальная стоимость Полная стоимость
    A 2 1000
    B 300 500

    Если нужны все строки, вариант B выглядит выгоднее.

    Но что изменится при:

    SELECT *
FROM orders
LIMIT 1;

    Возможно, достаточно получить одну строку.

    План A способен сделать это почти сразу. План B тратит больше работы до первого результата.

    Следовательно, планировщик учитывает, сколько строк потребуется родительскому узлу. Для LIMIT он может оценивать частичную стоимость плана, а для EXISTS особенно важна возможность быстро получить первую строку.

    Инженерный вывод: большие значения cost сами по себе не свидетельствуют о проблеме. Важны сравнение альтернативных планов и соответствие расчетной модели фактическому выполнению.

    4. Число строк (rows) и ширина строки (width): прогноз результата узла¶

    Возьмем:

    Seq Scan on orders
  (cost=0.00..2250.00 rows=10000 width=64)
  Filter: (status = 'PAID')

    rows=10000 означает, что планировщик ожидает получить из этого узла примерно 10 000 строк.

    При этом таблица может содержать 100 000 строк.

    Почему указано только 10 000?

    Потому что условие status = 'PAID', по оценке планировщика, пройдет примерно для 10% строк.

    Это называется селективность (selectivity) условия.

    Селективность = количество подходящих строк / общее количество строк

    Если селективность 0,1:

    Ожидается: 100 000 × 0,1 = 10 000 строк

    Здесь скрывается одна из важнейших причин неоптимальных планов PostgreSQL.

    Планировщик может ошибиться в селективности.

    Он ожидает 10 000 строк, а фактически получает 900 000.

    Тогда индексный доступ, который казался выгодным, может привести к огромному количеству обращений к страницам таблицы.

    И наоборот: PostgreSQL может ожидать почти всю таблицу, выбрать Seq Scan, хотя в действительности запрос возвращает несколько строк.

    4.1. Оценка количества строк (rows) описывает выход узла¶

    Важно различать:

    • сколько строк узел прочитал или рассмотрел;
    • сколько строк узел передал родителю.

    rows в плане описывает ожидаемое количество выходных строк.

    Например:

    Seq Scan on orders
  (rows=10000)
  Filter: (status = 'PAID')

    Сканирование может просмотреть 100 000 строк, отбросить 90 000 и выдать 10 000.

    При добавлении EXPLAIN ANALYZE мы сможем увидеть, сколько строк действительно было возвращено и сколько отклонено фильтром.

    4.2. Расчетная ширина строки (width)¶

    rows=10000 width=64

    width=64 означает оценку среднего размера одной выходной строки в байтах.

    Почему планировщику нужен размер строки?

    Допустим, сортировка должна обработать миллион строк.

    В одном случае каждая строка занимает в среднем 16 байт.

    В другом — 500 байт.

    Объем данных отличается более чем в 30 раз.

    Это влияет на:

    • оценку затрат на обработку данных;
    • память для сортировок и промежуточных структур;
    • возможность обработки в оперативной памяти;
    • стоимость передачи строк между узлами.

    width — расчетный показатель, который зависит в том числе от выбранных столбцов и статистики. Он не равен обязательно размеру исходной строки на диске.

    Например:

    SELECT id
FROM orders;

    и

    SELECT *
FROM orders;

    могут иметь разные width, даже когда читают одну и ту же таблицу.

    5. EXPLAIN ANALYZE: где прогноз встречается с реальностью¶

    Теперь выполним:

    EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE status = 'PAID';

    Условный результат:

    Seq Scan on orders
  (cost=0.00..2250.00 rows=10000 width=64)
  (actual time=0.025..18.400 rows=12000 loops=1)
  Filter: (status = 'PAID')
  Rows Removed by Filter: 88000
  Buffers: shared hit=1000

Planning Time: 0.200 ms
Execution Time: 19.100 ms

    Сразу заметна принципиальная разница.

    Планировщик ожидал 10 000 строк. Исполнитель вернул 12 000.

    Расхождение небольшое: оценка примерно соответствует реальности.

    Но теперь представим, что фактически получилось 900 000 строк.

    Значит, оценка ошиблась в 90 раз.

    Именно такие расхождения нужно искать при анализе медленных запросов, потому что от них зависит выбор способа выполнения.

    5.1. Фактическое время (actual time)¶

    actual time=0.025..18.400

    Оба числа измеряются в миллисекундах.

    Первое — среднее время до выдачи первой строки за один запуск узла.

    Второе — среднее время до завершения выдачи строк за один запуск узла.

    При loops=1 это времена единственного выполнения.

    Для обычного сканирования первое значение часто небольшое: узел быстро нашел первую строку.

    Для Sort первое значение может быть гораздо больше — сортировке нужно предварительно обработать входные данные.

    Но здесь появляется важная тонкость: измеренное время узла включает работу его дочерних узлов, если он их вызывает.

    Поэтому нельзя бездумно складывать значения actual time по всему дереву.

    5.2. Число запусков (loops) — сколько раз выполнялся узел¶

    rows=12000 loops=1

    Узел был выполнен один раз.

    А теперь представим:

    Index Scan using idx_orders_customer on orders
  (actual time=0.012..0.035 rows=3 loops=10000)

    Это означает, что узел запускался 10 000 раз.

    Показатели actual time и rows в такой строке усреднены за один запуск узла.

    Следовательно:

    Всего строк ≈ 3 строки за запуск × 10 000 запусков = 30 000

    И ориентировочная суммарная стоимость по измеренному времени выполнения этого узла за все запуски:

    Сумма времен узла ≈ 0,035 мс × 10 000 запусков = 350 мс

    Последняя величина — сумма времен работы узла, а не обязательно 350 мс дополнительного времени всего запроса: вложенные измерения и параллельное выполнение требуют отдельной интерпретации.

    Вот здесь легко ошибиться.

    Можно увидеть actual time=0.035 и решить, что индекс работает практически бесплатно.

    Но десять тысяч повторных запусков меняют картину.

    Именно поэтому actual time нельзя интерпретировать без loops.

    6. Последовательное сканирование (Seq Scan): почему оно иногда быстрее индекса¶

    Рассмотрим:

    SELECT *
FROM orders
WHERE status = 'PAID';

    План:

    Seq Scan on orders
  Filter: (status = 'PAID')

    Что происходит физически?

    Таблица PostgreSQL хранится в файлах, организованных в страницы. Обычно размер страницы составляет 8 КиБ.

    Внутри страниц таблицы находятся версии строк. PostgreSQL использует MVCC, поэтому при чтении исполнитель должен учитывать видимость версий строк для текущего снимка транзакции.

    Упрощенная последовательность:

    1. Получить страницу таблицы. Через буферный менеджер PostgreSQL.
    2. Найти доступные версии строк. Проверить условия видимости MVCC.
    3. Вычислить фильтр. Например, status = 'PAID'.
    4. Передать подходящие строки. В родительский узел плана.
    5. Перейти к следующей странице. Продолжать до завершения или остановки родителем.

    Для чтения больших объемов PostgreSQL может использовать последовательный доступ, предварительное чтение страниц и специальные стратегии работы с буферным кешем.

    А индексный поиск может требовать отдельных обращений к страницам, которые физически находятся далеко друг от друга.

    6.1. Когда последовательное сканирование выгодно¶

    Предположим:

    • таблица занимает 100 000 страниц;
    • запрос возвращает 90% строк;
    • строки физически распределены по всей таблице.

    Если идти через обычный индекс, может потребоваться прочитать множество записей индекса, а затем обратиться практически ко всем страницам таблицы.

    Последовательное сканирование часто дешевле.

    В таком случае Seq Scan — вполне обоснованное решение планировщика.

    6.2. Когда последовательное сканирование становится проблемой¶

    Изменим запрос:

    SELECT *
FROM orders
WHERE customer_id = 42;

    Допустим, возвращается 5 строк из 10 миллионов, но PostgreSQL все равно использует Seq Scan.

    Тогда стоит проверить:

    • существует ли подходящий индекс;
    • какую селективность ожидает планировщик;
    • актуальна ли статистика;
    • можно ли использовать индекс с данным условием;
    • какова реальная стоимость альтернативного плана.

    Особенно важно сравнить rows и actual rows.

    Если планировщик ожидал найти 5 миллионов строк, но нашел пять, перед нами сильная ошибка оценки селективности.

    Однако даже здесь нельзя утверждать, что виновата именно статистика. Индекс может отсутствовать, быть неподходящим или не поддерживать требуемое выражение.

    7. Сканирование по индексу (Index Scan): почему B-дерево не означает дешевое чтение¶

    Теперь создадим индекс:

    CREATE INDEX idx_orders_customer
ON orders(customer_id);

    Выполним:

    EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 42;

    Возможный результат:

    Index Scan using idx_orders_customer on orders
  Index Cond: (customer_id = 42)

    Что реально происходит?

    Для обычного индекса на основе B-дерева PostgreSQL ищет подходящие записи в индексной структуре.

    Запись содержит информацию, позволяющую найти соответствующую версию строки в таблице. В частности, для обычной таблицы это идентификатор строки TID, включающий номер страницы и позицию внутри страницы.

                     B-tree index
        Поиск customer_id = 42
                       |
                       v
  TID (10, 4)  TID (850, 2)  TID (9000, 8)
       |             |             |
       v             v             v
     Page 10       Page 850     Page 9000
              Heap таблицы

    Условная иллюстрация: три подходящие записи индекса ссылаются на три разные страницы таблицы.

    Теперь неприятный вопрос.

    Что будет, если индекс вернул миллион подходящих записей, а соответствующие строки расположены на сотнях тысяч страниц?

    Появляется большое количество обращений к таблице.

    Даже если все страницы находятся в памяти, это означает дополнительную работу буферного менеджера, обращения к разным областям памяти и проверки видимости.

    Если данные отсутствуют в оперативной памяти, стоимость может стать еще выше.

    Именно поэтому индекс может существовать и корректно работать, но планировщик предпочтет последовательное сканирование.

    7.1. Почему физический порядок строк важен¶

    Предположим, индекс построен по created_at.

    Если строки вставлялись примерно в хронологическом порядке, соседние значения индекса часто ссылаются на близко расположенные страницы таблицы.

    Если данные многократно обновлялись или вставлялись в произвольном порядке, связь логического порядка индекса с физическим размещением строк может быть слабее.

    Статистика correlation в pg_stats помогает планировщику учитывать связь порядка значений столбца с физическим порядком строк таблицы.

    При высокой корреляции диапазонный Index Scan может быть существенно выгоднее, чем при случайном расположении строк.

    8. Сканирование по битовой карте (Bitmap Scan): промежуточная стратегия¶

    Мы увидели две крайности.

    Seq Scan читает таблицу последовательно.

    Index Scan находит подходящие записи через индекс, но может выполнять множество разрозненных обращений к таблице.

    Что если нам подходит, например, 5% строк?

    Читать всю таблицу может быть дорого. Но и выполнять множество случайных обращений неудобно.

    Здесь появляется сканирование по битовой карте.

    Типичный план выглядит так:

    Bitmap Heap Scan on orders
  Recheck Cond: (total_amount > 9000)
  -> Bitmap Index Scan on idx_orders_amount
       Index Cond: (total_amount > 9000)

    8.1. Как строится битовая карта по индексу (Bitmap Index Scan)¶

    Сначала PostgreSQL проходит по индексу и собирает ссылки на потенциально подходящие строки в структуру TIDBitmap.

    Она позволяет сгруппировать найденные позиции по страницам таблицы.

    Упрощенный пример:

    Индекс нашел строки:

Page 10, offset 3
Page 800, offset 7
Page 10, offset 15
Page 500, offset 2
Page 800, offset 12

    В результате можно представить данные так:

    Page 10  → offsets 3, 15
Page 500 → offset 2
Page 800 → offsets 7, 12

    Теперь Bitmap Heap Scan обходит страницы таблицы в подходящем порядке и получает нужные строки.

    В результате уменьшается количество хаотичных переходов между страницами.

          Bitmap Index Scan
  Собрать подходящие TID по индексу
               |
               v
            TIDBitmap
     Сгруппировать по страницам
               |
               v
       Bitmap Heap Scan
  Читать подходящие страницы и строки

    Это полезный компромисс, но за него приходится платить.

    Сначала нужно собрать битовую карту. Это требует памяти и времени.

    Кроме того, обход по таблице не сохраняет порядок строк по ключу индекса. Поэтому последующий ORDER BY может потребовать отдельной сортировки.

    8.2. Пересечение и объединение битовых карт (BitmapAnd, BitmapOr)¶

    PostgreSQL может комбинировать результаты нескольких индексов.

    Например:

    SELECT *
FROM orders
WHERE customer_id = 42
  AND total_amount > 5000;

    Пусть есть два независимых индекса:

    CREATE INDEX idx_orders_customer
ON orders(customer_id);

CREATE INDEX idx_orders_amount
ON orders(total_amount);

    Планировщик может выбрать:

    Bitmap Heap Scan on orders
  Recheck Cond: (
    customer_id = 42
    AND total_amount > 5000
  )
  -> BitmapAnd
       -> Bitmap Index Scan on idx_orders_customer
            Index Cond: (customer_id = 42)
       -> Bitmap Index Scan on idx_orders_amount
            Index Cond: (total_amount > 5000)

    Первый индекс дает набор TID по клиенту.

    Второй — по сумме заказа.

    BitmapAnd находит пересечение наборов.

    BitmapOr может аналогично объединять наборы для подходящих условий OR.

    При этом составной индекс (customer_id, total_amount) в ряде случаев будет выгоднее, поскольку позволяет сразу ограничивать поиск по обоим столбцам, не создавая два отдельных набора.

    8.3. Точная и приближенная битовая карта¶

    Теперь добавим нагрузку.

    Запрос вернул огромное количество TID. Bitmap растет и начинает потреблять существенную память.

    Но память ограничена.

    PostgreSQL умеет переходить от точного хранения позиций отдельных строк к более грубому представлению для части страниц.

    Есть два варианта:

    • Точная: битовая карта содержит точные позиции строк для страницы.
    • Приближенная: битовая карта отмечает страницу как потенциально содержащую подходящие строки, без точного списка всех позиций.

    План может сообщать:

    Heap Blocks: exact=5000 lossy=800
Rows Removed by Index Recheck: 12000

    На 800 страницах информация была менее точной.

    Поэтому исполнитель должен повторно проверить индексное условие у кандидатов с этих страниц.

    Отсюда Recheck Cond.

    Но важная деталь: само наличие строки Recheck Cond в плане не доказывает, что все строки проходили повторную проверку. Для обычных точных битовых карт, построенных по B-дереву, повторная проверка условия может не потребоваться. Существуют также индексные методы доступа, возвращающие приблизительные совпадения, для которых проверка необходима.

    Rows Removed by Index Recheck показывает количество кандидатов, отвергнутых повторной проверкой.

    В рабочей системе большое количество lossy-страниц и повторных проверок — повод оценить стоимость битовой карты, объем возвращаемых данных и настройки памяти для рабочих операций.

    9. Фильтр (Filter) и условие индекса (Index Cond): почему цена отличается¶

    Рассмотрим индекс:

    CREATE INDEX idx_orders_customer
ON orders(customer_id);

    И запрос:

    SELECT *
FROM orders
WHERE customer_id = 42
  AND status = 'PAID';

    Возможный план:

    Index Scan using idx_orders_customer on orders
  Index Cond: (customer_id = 42)
  Filter: (status = 'PAID')

    Здесь PostgreSQL выполняет две логически разные операции.

    Index Cond определяет условие, которое индекс может использовать для поиска или ограничения кандидатов.

    Filter применяется к строкам, полученным узлом сканирования, чтобы отбросить неподходящие.

    Для нашего примера:

    1. По индексу находится customer_id = 42.
    2. Исполнитель получает кандидатов.
    3. Проверяет status = 'PAID'.
    4. Возвращает подходящие строки.

    Теперь представим:

    Index Scan using idx_orders_customer on orders
  (actual time=0.100..250.000 rows=10 loops=1)
  Index Cond: (customer_id = 42)
  Filter: (status = 'PAID')
  Rows Removed by Filter: 999990

    Это условный диагностический пример.

    Индекс привел нас к миллиону кандидатов, а фильтр оставил только десять.

    Мы прочитали и проверили огромный объем данных ради маленького результата.

    9.1. Что может изменить составной индекс¶

    Создадим:

    CREATE INDEX idx_orders_customer_status
ON orders(customer_id, status);

    Для того же SQL можно получить:

    Index Scan using idx_orders_customer_status on orders
  Index Cond: (
    (customer_id = 42)
    AND (status = 'PAID')
  )

    Теперь оба условия могут использоваться при поиске по индексу.

    Это может значительно сократить число кандидатов и обращений к таблице.

    Но составной индекс занимает место, увеличивает стоимость записи и обслуживания. Его эффективность зависит от запросов и распределения данных.

    9.2. Строки, отклоненные фильтром (Rows Removed by Filter)¶

    Еще один полезный счетчик:

    Rows Removed by Filter: 500000

    Это количество строк, отклоненных фильтром.

    Если узел выполнялся несколько раз, значение представлено как среднее на один запуск, с округлением.

    Например:

    Rows Removed by Filter: 100
loops=1000

    Ориентировочно это 100 000 отклоненных строк за все запуски.

    Необходимо также помнить, что Rows Removed by Filter не включает все возможные виды работы. Например, неподходящие записи, исключенные непосредственно условиями индексного поиска, не обязаны попадать в этот счетчик.

    9.3. Когда дополнительный фильтр вполне нормален¶

    Предположим:

    Index Scan
  Index Cond: (customer_id = 42)
  Filter: (status = 'PAID')
  Rows Removed by Filter: 2

    Ради двух отклоненных строк создавать и поддерживать новый составной индекс, скорее всего, бессмысленно.

    Само наличие Filter не говорит о плохом плане.

    Важна стоимость работы, выполненной до фильтрации.

    10. Сортировка (Sort): почему ORDER BY может начать писать на диск¶

    Возьмем:

    SELECT *
FROM orders
WHERE status = 'PAID'
ORDER BY total_amount DESC;

    Возможный план:

    Sort
  Sort Key: total_amount DESC
  -> Seq Scan on orders
       Filter: (status = 'PAID')

    Сначала PostgreSQL получает подходящие строки.

    Затем сортирует их по total_amount.

    Если строк мало, сортировка обычно выполняется в оперативной памяти.

    Пример:

    Sort
  Sort Key: total_amount DESC
  Sort Method: quicksort  Memory: 512kB

    Видим алгоритм сортировки и использованную память.

    А теперь пусть вместо нескольких тысяч строк нам нужно отсортировать пять миллионов.

    Рабочий объем может оказаться больше доступной для сортировки памяти.

    PostgreSQL может использовать внешнюю сортировку, записывая промежуточные данные во временные файлы.

    Sort
  Sort Key: total_amount DESC
  Sort Method: external merge  Disk: 256000kB

    Число условное, но диагностический смысл точен: сортировка потребовала временного хранения на диске.

    10.1. Что ограничивает память сортировки¶

    Основной параметр:

    SHOW work_mem;

    work_mem ограничивает объем памяти для отдельной подходящей операции выполнения запроса — например, сортировки. При превышении лимита операция может перейти к работе с временными файлами.

    Но важный момент: work_mem не является общим ограничением памяти одного SQL-запроса.

    Предположим:

    • один запрос содержит три одновременно активных узла сортировки;
    • одновременно работают 50 запросов;
    • каждому узлу разрешено до 64 МиБ.

    Теоретический масштаб памяти только для этих узлов:

    3 сортировки × 50 одновременных запросов × 64 МиБ = 9 600 МиБ

    Почти 9,4 ГиБ.

    Это не прогноз точного RSS — операции могут потреблять меньше, выполнять работу в разное время и использовать дополнительные механизмы. Но модель показывает, почему бездумное глобальное увеличение work_mem опасно.

    С параллельными работниками потенциальное потребление еще сложнее.

    10.2. LIMIT меняет алгоритм¶

    SELECT *
FROM orders
ORDER BY total_amount DESC
LIMIT 10;

    Нужно найти десять максимальных значений.

    PostgreSQL может использовать ограниченную сортировку с кучей:

    Sort Method: top-N heapsort  Memory: 25kB

    Вместо хранения и полноценной сортировки всех входных строк можно поддерживать небольшой набор лучших кандидатов.

    Однако при отсутствии подходящего индекса исполнитель все равно может быть обязан прочитать все входные строки, чтобы узнать, какие десять действительно максимальные.

    LIMIT 10 сам по себе не означает чтение десяти строк.

    10.3. Когда индекс позволяет обойтись без сортировки¶

    Создадим:

    CREATE INDEX idx_orders_amount
ON orders(total_amount);

    Теперь запрос:

    SELECT *
FROM orders
ORDER BY total_amount DESC
LIMIT 10;

    может воспользоваться обратным обходом B-дерева:

    Limit
  -> Index Scan Backward using idx_orders_amount
       on orders

    Индекс предоставляет порядок, который требуется запросу.

    Отдельный узел Sort становится не нужен.

    Но вот здесь абстракция снова начинает протекать.

    Если убрать LIMIT 10 и запросить все десять миллионов строк, обход индекса может потребовать множества обращений к таблице.

    Планировщик вправе выбрать Seq Scan + Sort, даже если индекс уже хранит ключи в нужном порядке.

    Инженерный вывод: оптимизация ORDER BY — выбор между стоимостью получения строк в готовом порядке и стоимостью получения строк с последующей сортировкой.

    11. Буферные обращения (BUFFERS): сколько страниц затронул запрос¶

    До сих пор мы разбирали вычислительную часть.

    Но в рабочей системе PostgreSQL часто ограничен стоимостью доступа к памяти и накопителю.

    Добавим:

    EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 42;

    Условный вывод:

    Index Scan using idx_orders_customer on orders
  (actual time=0.080..4.500 rows=50 loops=1)
  Index Cond: (customer_id = 42)
  Buffers: shared hit=120 read=35

    Разберем.

    11.1. shared hit¶

    shared hit=120

    Это число успешных обращений к блокам, которые уже находились в общем буферном кеше PostgreSQL — shared_buffers.

    PostgreSQL смог использовать эти страницы без необходимости заново читать их из файлов таблиц или индексов.

    120 попаданий не означают 120 уникальных страниц.

    Одна и та же страница могла использоваться много раз и давать несколько попаданий.

    11.2. shared read¶

    shared read=35

    Это число обращений, при которых требуемого блока не оказалось в shared_buffers и потребовалось прочитать его из файлового слоя.

    Но означает ли это, что PostgreSQL физически прочитал 35 страниц с SSD?

    Не обязательно.

    Посмотрим на путь доступа:

           Executor PostgreSQL
 Запрашивает блок таблицы или индекса
                 |
                 v
    PostgreSQL shared_buffers
     Найдено → shared hit
                 |
                 v
    Файловый кеш ОС / page cache
  Промах shared_buffers; чтение может
         обслужиться из RAM ОС
                 |
                 v
               Storage
 Физическое чтение при отсутствии
          нужных данных в кеше

    Это упрощенный путь обычного буферизованного чтения. Детали зависят от конфигурации ввода-вывода.

    Получается:

    shared read=35

    говорит об отсутствии страниц в shared_buffers при соответствующих обращениях.

    Но не дает точного числа физических операций чтения накопителя.

    ОС могла обслужить часть чтений из файлового кеша ОС. Это прямо согласуется с разграничением буферной статистики PostgreSQL и кеша файловой системы в документации.

    11.3. Остальные показатели BUFFERS¶

    Показатель Значение
    shared hit Попадания в общий буферный кеш
    shared read Чтения блоков при отсутствии в общем буферном кеше
    shared dirtied Страницы, впервые сделанные грязными в рамках учета запроса
    shared written Записи ранее загрязненных страниц, выполненные данным процессом
    local hit/read Обращения к локальным буферам временных таблиц
    temp read/written Чтение и запись блоков временных рабочих файлов

    Здесь особенно важно различать dirtied и written.

    Если запрос изменил страницу, она может стать грязной — загрязненной.

    Но ее непосредственная запись на накопитель не обязана произойти в рамках того же запроса. Она может выполняться позже соответствующими механизмами PostgreSQL.

    В то же время shared written может отражать запись страницы, измененной ранее.

    Поэтому shared dirtied и shared written не являются синонимами.

    11.4. Почему сумма буферных обращений по узлам обманывает¶

    Предположим:

    Sort
  Buffers: shared hit=10000
  -> Seq Scan
       Buffers: shared hit=10000

    Можно ли утверждать, что запрос выполнил 20 000 обращений?

    Нет.

    Показатели родительского узла включают данные дочерних узлов.

    Для этого примера верхний Sort может показывать те же 10 000 обращений, которые были произведены при чтении строк дочерним Seq Scan.

    Нужно анализировать иерархию, а не складывать одинаковые счетчики.

    11.5. Большой shared hit тоже может означать проблему¶

    Допустим:

    Index Scan
  Buffers: shared hit=3000000 read=0

    Все данные в оперативной памяти.

    Можно ли успокоиться?

    Нет.

    Три миллиона обращений к страницам могут означать значительную работу по поиску, получению буферов, проверкам и обработке строк.

    Под высокой конкуренцией эта работа потребляет CPU и создает давление на подсистему памяти.

    Отсутствие физических чтений не гарантирует дешевый запрос.

    11.6. Как измерить время ввода-вывода¶

    При включенном:

    SHOW track_io_timing;

    PostgreSQL может дополнительно отображать время операций чтения и записи.

    Настройка обычно требует повышенных привилегий для изменения.

    В плане могут появиться показатели вроде:

    I/O Timings: shared read=42.500

    Это измеренное время соответствующей операции ввода-вывода в миллисекундах.

    Его нельзя автоматически считать временем работы физического диска: операции могут проходить через кеш и файловую систему.

    Зато показатель помогает обнаружить, что существенная доля времени запроса связана с получением блоков.

    Под нагрузкой его полезно сопоставлять со статистикой ввода-вывода, ожиданиями процессов и характеристиками накопителя.

    12. Оценки планировщика: откуда PostgreSQL знает количество строк¶

    Мы подошли к центральному вопросу.

    Планировщик выбирает между Seq Scan, Index Scan, Bitmap Scan и другими операциями по расчетной стоимости.

    Но стоимость во многом зависит от количества строк.

    А количество строк заранее неизвестно.

    Неужели PostgreSQL выполняет запрос один раз для оценки, а потом еще раз для получения результата?

    Нет. Это сделало бы планирование слишком дорогим.

    Вместо этого PostgreSQL хранит статистическую модель данных.

    Она создается и обновляется командой ANALYZE, в том числе автоматически через механизм автоматического сбора статистики.

    12.1. Статистика размера таблицы¶

    Для начала планировщику нужно примерно понимать, сколько строк и страниц содержит таблица.

    Эти сведения доступны через pg_class.

    SELECT
    relname,
    reltuples,
    relpages
FROM pg_class
WHERE oid = 'orders'::regclass;

    Например:

    relname | reltuples | relpages
--------+-----------+---------
orders  | 1000000   | 15000

    reltuples — приблизительное количество строк.

    relpages — приблизительное количество страниц.

    Эти показатели не обновляются после каждой вставки или удаления строки. PostgreSQL корректирует их при обслуживании таблицы и может масштабировать оценку количества строк с учетом текущего физического размера таблицы.

    Поэтому reltuples не нужно воспринимать как точный аналог COUNT(*).

    Но знать общий размер недостаточно.

    Планировщику требуется ответить на другой вопрос:

    WHERE status = 'PAID'

    Какую долю таблицы вернет это условие?

    12.2. pg_stats: статистика распределения значений¶

    Проверим:

    SELECT
    attname,
    null_frac,
    n_distinct,
    most_common_vals,
    most_common_freqs,
    histogram_bounds,
    correlation
FROM pg_stats
WHERE schemaname = 'public'
  AND tablename = 'orders';

    Важные поля:

    Поле Что описывает
    null_frac Доля значений NULL
    n_distinct Оценка количества различных значений
    most_common_vals Часто встречающиеся значения (MCV)
    most_common_freqs Частоты этих значений
    histogram_bounds Границы статистической гистограммы
    correlation Корреляция порядка значений с физическим порядком строк

    Дополнительно есть avg_width — средняя ширина значения столбца, используемая в оценке объема данных.

    Эти статистики вычисляются по выборке строк. Поэтому даже свежая статистика остается приближенной.

    12.3. MCV — почему status нельзя оценивать равномерно¶

    Представим миллион заказов.

    Распределение статусов:

    Статус Доля строк
    PAID 80%
    NEW 15%
    CANCELLED 5%

    Условное распределение для объяснения селективности.

    Если планировщик просто разделит миллион строк на три статуса, он получит примерно 333 333 строки на каждый.

    Но действительное распределение сильно неравномерно.

    Для запроса:

    WHERE status = 'PAID'

    ожидается около 800 000 строк.

    А для:

    WHERE status = 'CANCELLED'

    всего около 50 000.

    MCV позволяет сохранить распространенные значения и их частоты.

    Планировщик может учитывать, что PAID встречается гораздо чаще CANCELLED.

    Это напрямую влияет на выбор между последовательным и индексным доступом.

    12.4. n_distinct: когда точная частота неизвестна¶

    Предположим, customer_id имеет примерно 100 000 различных значений и распределен относительно равномерно между миллионом строк.

    Если конкретного значения нет в MCV, планировщик может использовать оценку на основе количества различных значений с учетом других статистических сведений.

    Упрощенная модель:

    Селективность ≈ 1 / 100 000

    Тогда:

    Ожидается: 1 000 000 × (1 / 100 000) = 10 строк

    Это работает достаточно хорошо для почти равномерного распределения.

    А теперь один клиент создал 200 000 заказов, остальные — значительно меньше.

    Равномерная модель перестает отражать реальность.

    Если популярное значение обнаружено при сборе статистики и попало в MCV, оценка может существенно улучшиться.

    В PostgreSQL отрицательное значение n_distinct также имеет особый смысл: оно обозначает оценку доли различных значений относительно числа строк, а не отрицательное количество уникальных значений.

    12.5. Гистограмма: как оценить диапазон¶

    Теперь запрос:

    SELECT *
FROM orders
WHERE total_amount BETWEEN 1000 AND 5000;

    Как оценить долю строк, попадающих в диапазон?

    Считать каждое значение слишком дорого.

    PostgreSQL может использовать статистическую гистограмму.

    Упрощенно представим, что границы подобраны так, чтобы между соседними границами находились примерно равные доли значений, не включенных в список MCV.

    Например:

    0 ── 100 ── 300 ── 1000 ── 5000 ── 100000

    Расстояния по числовой шкале разные, поскольку распределение неравномерное.

    Планировщик оценивает, в какую часть распределения попадают границы условия.

    Это значительно полезнее предположения, что суммы заказов равномерно распределены между минимумом и максимумом.

    Но гистограмма имеет конечную детализацию.

    Если большинство значений концентрируется внутри очень узкого диапазона, а статистика грубая, оценка может ошибаться.

    12.6. Корреляция: одна колонка, две разные физические стоимости¶

    Мы уже обсуждали Index Scan.

    Соседние записи B-дерева могут ссылаться на соседние страницы таблицы либо на страницы, расположенные далеко друг от друга.

    Показатель correlation помогает оценивать это различие.

    Важная тонкость: значения около +1 означают сильную прямую связь порядков, около -1 — сильную обратную. Для оценки локальности оба случая могут быть полезны.

    Значения около нуля указывают на слабую связь между порядком столбца и физическим порядком строк.

    Индекс по created_at может быть выгоден на таблице, заполненной хронологически, и заметно дороже на таблице, где значения времени случайно распределены по таблице.

    Селективность сообщает, сколько строк потребуется. Корреляция помогает оценить, насколько дорогим может оказаться доступ к ним.

    13. Где оценки планировщика ломаются: зависимые столбцы¶

    А вот здесь начинается самое интересное.

    Предположим, есть миллион заказов.

    Из них:

    • 100 000 имеют статус PAID;
    • 100 000 созданы через канал APP;
    • все заказы со статусом PAID созданы через APP.

    Выполним:

    SELECT *
FROM orders
WHERE status = 'PAID'
  AND channel = 'APP';

    Планировщик знает селективность каждого условия:

    Доля заказов PAID = 0,1 (10%)

    Доля заказов APP = 0,1 (10%)

    Если предположить, что условия независимы:

    Оценка совместной доли при независимости = 0,1 × 0,1 = 0,01 (1%)

    Получится:

    Ожидается: 1 000 000 × 0,01 = 10 000 строк

    Планировщик ожидает десять тысяч строк.

    Но фактически их сто тысяч!

    Ошибка в десять раз.

    Почему?

    Потому что статус и канал в нашем наборе данных полностью связаны друг с другом.

    Независимость условий оказалась неправильным предположением.

    13.1. Почему это опасно для выполнения запроса¶

    Предположим, PostgreSQL использует полученную оценку как количество строк на входе следующей операции.

    Вместо 10 000 строк туда поступает 100 000.

    Если это сортировка, ей потребуется больше времени и памяти.

    Если это внутренняя сторона соединения, выбранный алгоритм может оказаться неудачным.

    Если это построение хеш-таблицы, ее размер может превысить первоначальные ожидания.

    Таким образом, ошибка оценки распространяется дальше по дереву.

    Неправильная селективность
Ожидали 10 000 строк, получили 100 000
               ↓
Неправильная стоимость операций
Доступ и обработка оказываются дороже прогноза
               ↓
Неудачный выбор плана
Выбранный путь рассчитан на другой объем данных
               ↓
Повышенное потребление ресурсов
Больше CPU, обращений к страницам, памяти или временных файлов
               ↓
Рост задержки под нагрузкой
Система дольше обслуживает запросы и хуже переносит конкуренцию

    13.2. Расширенная статистика¶

    PostgreSQL поддерживает многоколоночную статистику — расширенная статистика.

    Например:

    CREATE STATISTICS orders_status_channel_stats (mcv)
ON status, channel
FROM orders;

ANALYZE orders;

    Теперь PostgreSQL может собирать статистику распространенных сочетаний двух столбцов.

    Это позволяет учитывать, что пара:

    ('PAID', 'APP')

    встречается намного чаще, чем следовало бы из предположения независимости.

    Есть несколько разновидностей расширенной статистики:

    Вид Для чего применяется
    mcv Частые сочетания значений нескольких столбцов
    dependencies Функциональные зависимости между столбцами
    ndistinct Количество различных сочетаний, особенно для оценок группировок

    Они решают разные проблемы.

    Например, dependencies полезна для некоторых условий равенства, когда значение одного столбца определяет или почти определяет значение другого.

    Но ее применение ограничено: она не является универсальным решением для любых JOIN, LIKE или диапазонных условий.

    Важно и другое: расширенная статистика собирается по явно определенным наборам столбцов. PostgreSQL не строит ее автоматически для всех возможных комбинаций — стоимость такого подхода была бы слишком высокой.

    14. Почему ANALYZE иногда помогает, а иногда вообще ничего не исправляет¶

    Есть известный совет:

    «Запрос начал тормозить? Выполни ANALYZE».

    Иногда это действительно помогает.

    Например, вчера в таблице было 100 000 строк, а после массового импорта стало 20 миллионов.

    Статистика могла перестать соответствовать актуальному состоянию данных.

    Обновление:

    ANALYZE orders;

    позволяет пересчитать оценки и помогает планировщику выбрать более подходящий план при последующем планировании запроса.

    Но почему иногда после ANALYZE ничего не меняется?

    Возможные причины:

    Причина Что происходит
    Недостаточная детализация Выборка и статистические структуры плохо отражают распределение
    Зависимые условия Обычная статистика по отдельным столбцам не отражает совместное распределение
    Неподходящий индекс Планировщику нечего выбрать для эффективного доступа
    Неверная модель стоимости Коэффициенты плохо соответствуют характеристикам системы и нагрузки
    Неподходящая форма запроса SQL-выражение ограничивает доступные способы использования индекса
    Кешированный план В некоторых сценариях план зависит от режима работы подготовленных запросов и используемых параметров

    Для увеличения детализации статистики отдельного столбца:

    ALTER TABLE orders
ALTER COLUMN total_amount
SET STATISTICS 1000;

ANALYZE orders;

    Значение 1000 увеличивает целевой объем статистики по сравнению с обычной настройкой 100.

    Но улучшение оценки не гарантировано. Кроме того, растут затраты на сбор и хранение статистики.

    15. Почему EXPLAIN не показывает реальную задержку HTTP-запроса¶

    Предположим:

    Planning Time: 0.250 ms
Execution Time: 12.500 ms

    Приложение при этом измеряет 120 мс от вызова SQL до получения результата.

    Где потерялись остальные 107 миллисекунд?

    Сначала разберем, что измеряет сам PostgreSQL.

    Planning Time — время построения и оптимизации плана после разбора и переписывания запроса. Время синтаксического разбора и переписывания в него не входит.

    Execution Time — время работы исполнителя, включая соответствующую инициализацию и завершение. Для запросов с триггерами есть дополнительные нюансы учета их выполнения.

    Но обычный EXPLAIN ANALYZE не отправляет набор результирующих строк клиенту.

    Поэтому в нем не учитывается вся стоимость сериализации результата, сетевой передачи и обработки данных приложением.

    В PostgreSQL 18 есть дополнительная возможность:

    EXPLAIN (
    ANALYZE,
    BUFFERS,
    SERIALIZE TEXT
)
SELECT *
FROM orders
WHERE status = 'PAID';

    Она позволяет дополнительно измерить сериализацию выходных значений в текстовое представление.

    Это особенно полезно для широких строк, сложных типов и TOAST-значений, хранящихся вне основной строки.

    Но сетевую отправку результата EXPLAIN все равно не воспроизводит.

    Поэтому:

    HTTP latency
    ├── ожидание получения соединения из пула
    ├── отправка SQL
    ├── разбор и планирование на сервере
    ├── выполнение на сервере
    ├── передача результатов
    ├── декодирование строк клиентом
    └── работа приложения

    Execution Time — только часть этой картины.

    Практическое следствие: нельзя обвинять PostgreSQL в 120 мс задержки только потому, что запрос выполняется через PostgreSQL.

    И наоборот, 12 мс внутри PostgreSQL могут быть существенной проблемой, если запрос вызывается тысячи раз в секунду.

    16. Как инструмент измерения влияет на результат¶

    EXPLAIN ANALYZE добавляет инструментирование узлов плана.

    Нужно собирать счетчики строк, время выполнения, количество запусков и другую статистику.

    Это создает дополнительную работу.

    На коротких узлах, которые выполняются огромное количество раз, стоимость измерений может быть заметной относительно полезной работы.

    Если нам нужны прежде всего реальные количества строк и обращения к буферам, можно отключить детальное измерение времени узлов:

    EXPLAIN (
    ANALYZE,
    BUFFERS,
    TIMING OFF
)
SELECT *
FROM orders
WHERE customer_id = 42;

    actual rows и loops останутся, но времена отдельных узлов отображаться не будут.

    Общее Execution Time продолжит измеряться.

    Это полезно при исследовании запросов с множеством очень коротких итераций.

    Если нужен формат для программного анализа:

    EXPLAIN (
    ANALYZE,
    BUFFERS,
    FORMAT JSON
)
SELECT *
FROM orders
WHERE customer_id = 42;

    JSON удобен для автоматизированного сравнения планов, анализа оценок и построения инструментов диагностики.

    16.1. Осторожно с изменяющими запросами¶

    Для SELECT команда обычно безопасна в смысле отсутствия изменений строк, хотя функции внутри запроса могут иметь побочные эффекты.

    А вот:

    EXPLAIN ANALYZE
DELETE FROM orders;

    действительно выполнит удаление.

    Для изолированного эксперимента можно использовать:

    BEGIN;

EXPLAIN (ANALYZE, BUFFERS, WAL)
UPDATE orders
SET status = 'PAID'
WHERE customer_id = 42;

ROLLBACK;

    Изменения строк будут отменены при откате транзакции.

    Однако сам эксперимент уже мог создать нагрузку, получить блокировки, сгенерировать WAL и выполнить другие действия. Последовательности и внешние побочные эффекты также не обязательно откатываются.

    В рабочей системе подобные измерения требуют осторожности.

    17. Как читать плохой план в рабочей системе¶

    Теперь соберем все в единую методику.

    Предположим, SQL-запрос серверного приложения стал выполняться 15 секунд вместо обычных 100 мс.

    Мы получили план и видим:

    Nested Loop
  (cost=... rows=100 ...)
  (actual time=... rows=100000 loops=1)

  -> Seq Scan on customers
       (cost=... rows=100 ...)
       (actual time=... rows=100000 loops=1)

  -> Index Scan using idx_orders_customer on orders
       (cost=... rows=1 ...)
       (actual time=0.050..0.100 rows=1 loops=100000)
       Index Cond: (customer_id = customers.id)

    Числа условные.

    Здесь первый интересный симптом:

    rows=100
actual rows=100000

    Планировщик ожидал сто клиентов.

    Фактически получил сто тысяч.

    Второй симптом:

    Index Scan
loops=100000

    Внутренний индексный поиск выполнялся сто тысяч раз.

    Третий:

    actual time=0.050..0.100

    Один поиск кажется дешевым.

    Но:

    Сумма времен внутренних запусков ≈ 100 000 × 0,100 мс
                                    = 10 000 мс (10 секунд)

    Получается примерно десять секунд суммарного измеренного времени внутреннего узла.

    Вот почему поверхностный анализ EXPLAIN часто приводит к неправильным выводам.

    Можно увидеть Index Scan, решить, что индекс есть и все хорошо, и пропустить настоящую причину.

    Ошибка началась выше — в оценке числа строк. Именно она привела к огромному количеству повторных индексных поисков.

    Исправление может заключаться в актуализации или расширении статистики, изменении запроса, подходящих индексах либо выборе другого плана через корректную настройку модели стоимости.

    Простое увеличение work_mem или добавление случайного индекса эту причинно-следственную цепочку не исправит.

    17.1. Быстрая диагностика по симптомам¶

    Что видно в плане Что проверить первым
    rows=10, actual rows=100000 Селективность, статистика, зависимости столбцов
    loops=100000 Почему родитель повторно запускает дочерний узел
    Много Rows Removed by Filter Условия доступа, составные индексы, число кандидатов
    Большой shared read Рабочий набор, кеш, измерение времени ввода-вывода
    Большой shared hit при медленном запросе Повторная работа с буферами, CPU, количество сканирований
    Sort Method: external merge Объем сортировки, work_mem, возможность получить нужный порядок через индекс
    Heap Blocks: lossy=... Точность битовой карты, количество кандидатов, повторные проверки
    Высокий Execution Time при правильных rows Стоимость выбранных операций, ввод-вывод, повторения, конкуренция

    Если ошибки оценки нет, а запрос все равно медленный, следующий шаг — смотреть фактическую стоимость доступа и обработки данных.

    Один только EXPLAIN не раскроет все причины ожиданий под нагрузкой. Например, ожидания блокировок и конкуренция за ресурсы требуют сопоставления с другими механизмами наблюдаемости PostgreSQL.

    18. Практика: проверяем работу планировщика¶

    Нам нужна таблица, на которой можно воспроизвести разные способы доступа, ошибки оценок и проблемы сортировки.

    Работаем в отдельной учебной базе.

    Эксперимент 0. Подготовка данных¶

    Создадим таблицу с 500 000 заказов.

    DROP TABLE IF EXISTS explain_orders;

CREATE TABLE explain_orders AS
SELECT
    n::bigint AS id,
    (n % 10000 + 1)::int AS customer_id,
    CASE
        WHEN n % 10 = 0 THEN 'PAID'
        ELSE 'NEW'
    END AS status,
    CASE
        WHEN n % 10 = 0 THEN 'APP'
        ELSE 'WEB'
    END AS channel,
    (n % 10000)::int AS amount,
    timestamp '2026-01-01'
        + (n % 180) * interval '1 day'
        AS created_at,
    repeat('x', 120) AS payload
FROM generate_series(1, 500000) AS s(n);

CREATE INDEX idx_explain_customer
ON explain_orders(customer_id);

CREATE INDEX idx_explain_amount
ON explain_orders(amount);

VACUUM (ANALYZE) explain_orders;

    Здесь специально созданы два свойства.

    Первое: один customer_id соответствует примерно 50 заказам.

    Второе: status и channel полностью зависимы. Все заказы PAID имеют канал APP.

    Отключим параллельное выполнение для учебных экспериментов, чтобы упростить интерпретацию планов:

    SET max_parallel_workers_per_gather = 0;

    Настройка действует в текущей сессии.

    Эксперимент 1. последовательное сканирование¶

    EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status
FROM explain_orders
WHERE status = 'NEW';

    Ожидаем увидеть Seq Scan.

    Почему?

    Статус NEW имеют 90% строк, а индекса по статусу нет.

    Нужно посмотреть:

    • rows и actual rows;
    • Rows Removed by Filter;
    • Buffers: shared hit/read;
    • Execution Time.

    Затем запустить запрос повторно.

    Обратить внимание, изменились ли обращения к кешу и время выполнения.

    Если показатели изменились, объяснить их через состояние кешей и нагрузки, а не считать второй запуск абсолютным эталоном.

    Эксперимент 2. сканирование по индексу¶

    EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM explain_orders
WHERE customer_id = 42;

    Ожидаем Index Scan, поскольку индекс по customer_id существует, а подходящих строк мало.

    Сравним число выходных строк и количество обращений к буферам с предыдущим экспериментом.

    Обратим внимание: Buffers включает работу как с индексом, так и с таблицей.

    Теперь запросим более широкий диапазон:

    EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM explain_orders
WHERE customer_id BETWEEN 1 AND 9000;

    Условию соответствует большая доля таблицы.

    Посмотрим, поменяет ли планировщик стратегию.

    Эксперимент 3. сканирование по битовой карте¶

    EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM explain_orders
WHERE amount BETWEEN 2000 AND 2500;

    Это примерно 5% строк.

    PostgreSQL может выбрать Bitmap Heap Scan, но конкретный результат зависит от статистики и параметров стоимости.

    Если он выбрал другой план, сравним альтернативу в отдельной транзакции:

    BEGIN;

SET LOCAL enable_seqscan = off;
SET LOCAL enable_indexscan = off;

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM explain_orders
WHERE amount BETWEEN 2000 AND 2500;

ROLLBACK;

    Эти настройки позволяют исследовать стоимость альтернативного способа доступа. Использовать их как постоянное решение для рабочей системы не следует.

    При сканировании по битовой карте смотрим Bitmap Index Scan, Bitmap Heap Scan, Recheck Cond и Heap Blocks.

    Эксперимент 4. Фильтр против условия индекса¶

    EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM explain_orders
WHERE amount BETWEEN 1000 AND 1500
  AND status = 'PAID';

    У нас есть индекс только по amount.

    Поэтому ожидаем, что условие по amount сможет участвовать в индексном поиске, а условие по status придется проверять дополнительно.

    Теперь добавим составной индекс:

    CREATE INDEX idx_explain_amount_status
ON explain_orders(amount, status);

ANALYZE explain_orders;

    Повторим EXPLAIN.

    Сравним, какие условия оказались в Index Cond, сколько кандидатов было отклонено и как изменились буферные обращения.

    При этом планировщик не обязан выбирать новый индекс, если считает другую стратегию дешевле.

    Эксперимент 5. Специально ломаем сортировку¶

    Ограничим память сортировки:

    BEGIN;

SET LOCAL work_mem = '64kB';

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, payload
FROM explain_orders
ORDER BY created_at, amount DESC;

ROLLBACK;

    На таком объеме ожидаем внешнюю сортировку с временными файлами.

    Ищем:

    Sort Method: external merge
Disk: ...
Buffers: temp read=... written=...

    Теперь повторим с:

    SET LOCAL work_mem = '64MB';

    в новой транзакции, сохранив тот же запрос.

    Сравним метод сортировки, время, временные файлы и использование памяти.

    Затем исследуем LIMIT:

    EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM explain_orders
ORDER BY created_at DESC
LIMIT 10;

    Возможно появление top-N heapsort.

    Нужно объяснить, почему объем памяти небольшой, хотя исполнитель все равно должен изучить большой набор входных строк.

    Эксперимент 6. Ломаем planner estimates¶

    Теперь самое содержательное.

    EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM explain_orders
WHERE status = 'PAID'
  AND channel = 'APP';

    Фактически подходящих строк 50 000.

    Обычная статистика по отдельным столбцам может привести к оценке порядка 5000, поскольку оба условия по отдельности имеют селективность 10%.

    Посмотрим реальную оценку в rows.

    Теперь создадим многоколоночную статистику:

    CREATE STATISTICS explain_status_channel (mcv)
ON status, channel
FROM explain_orders;

ANALYZE explain_orders;

    Повторим запрос.

    Ожидаем, что оценка приблизится к фактическим 50 000 строкам.

    Обрати внимание: сам SQL не изменился. Индексов мы не добавляли.

    Изменилась статистическая модель, которую использует планировщик.

    Это один из самых полезных экспериментов для понимания PostgreSQL.

    Эксперимент 7. Индексное сканирование без чтения таблицы¶

    Это небольшой дополнительный эксперимент для понимания Index Scan.

    EXPLAIN (ANALYZE, BUFFERS)
SELECT amount
FROM explain_orders
WHERE amount BETWEEN 1000 AND 1010;

    Поскольку запросу нужны только значения amount, которые есть в B-дереве, PostgreSQL может использовать Index Only Scan.

    Но остается вопрос MVCC: как проверить видимость строки, если мы не читаем таблицу?

    Здесь используется карта видимости.

    Для страниц, отмеченных как all-visible, можно избежать обращения к таблице для проверки видимости. В остальных случаях потребуется посетить соответствующую строку таблицы.

    План показывает:

    Heap Fetches: ...

    Чем больше таких обращений, тем меньше практическая выгода от сканирования только по индексу.

    Это демонстрирует, почему даже наличие всех необходимых столбцов в индексе не гарантирует полностью автономного чтения по индексу.

    После практики вернем стандартную настройку сессии:

    RESET max_parallel_workers_per_gather;

    19. Что происходит под нагрузкой¶

    Теперь перенесем наши наблюдения в контекст серверного приложения.

    Предположим, один запрос выполняется за 20 мс.

    Сервис вызывает его 500 раз в секунду.

    Даже если все данные находятся в оперативной памяти, суммарная работа значительна.

    Если запрос делает большое количество обращений к буферам, создает временные файлы или повторно выполняет внутренние индексные поиски, при росте конкуренции могут появиться новые ограничения.

    Важно различать несколько сценариев.

    Ограниченный ресурс Возможный симптом Что измерять
    CPU Высокая загрузка при преимущественно кешированных данных CPU, узлы плана, число обработанных строк
    Оперативная память и буферный кеш Рост shared read, вытеснение полезных страниц BUFFERS, статистика кеша
    Накопитель Рост задержек ввода-вывода, временные файлы сортировки измерение времени ввода-вывода, temp read/written
    Память сортировок Переход на внешнюю сортировку слиянием при больших результатах Sort Method, Disk, work_mem
    Планирование Существенное время подготовки сложных планов Planning Time, статистика планирования
    Повторные сканирования Огромные loops при небольшом времени одной итерации loops, actual time, rows

    Еще один нюанс: PostgreSQL обычно выбирает план до начала его исполнения. Если фактическое количество строк оказалось намного больше ожидаемого, исполнитель не обязан автоматически перестроить весь запрос на более выгодный алгоритм.

    Поэтому неправильная оценка может дорого обходиться на протяжении всего выполнения.

    Для поиска проблемных SQL в работающей системе полезен pg_stat_statements.

    Он позволяет анализировать накопленные показатели по запросам: частоту выполнения, суммарное и среднее время, разброс длительностей, обращения к блокам и другие метрики.

    Сначала находим запросы, которые действительно создают нагрузку. Затем исследуем их конкретные планы с помощью EXPLAIN.

    Это эффективнее, чем оптимизировать произвольный SQL, который выглядит некрасиво, но выполняется два раза в сутки.

    20. Итоговая модель EXPLAIN¶

    После этой лекции важно удерживать семь принципов.

    1. Планировщик работает с оценками. Количество строк, размеры данных, селективность и стоимость операций определяют выбор плана.

    2. cost — относительная оценка затрат. Она позволяет сравнивать допустимые планы и зависит от параметров модели стоимости. Ее нельзя напрямую переводить в миллисекунды.

    3. rows описывает выход узла. Сравнение с actual rows показывает, насколько точными оказались предположения планировщика.

    4. actual time нужно читать вместе с loops. Дешевый отдельный запуск может превратиться в дорогую операцию при тысячах повторений.

    5. Seq Scan, Index Scan и Bitmap Scan решают одну задачу разными способами. Их эффективность зависит от селективности, физического расположения строк, кешей и стоимости доступа.

    6. BUFFERS раскрывает работу со страницами PostgreSQL. Попадания в кеш и чтения блоков не равнозначны уникальным страницам или физическим операциям ввода-вывода накопителя.

    7. Ошибки оценок способны определять производительность всего дерева. Поэтому диагностику нужно начинать с расхождений между прогнозируемым и фактическим количеством строк, а затем исследовать реальную стоимость выполнения.

    Итоговая инженерная цепочка:

    SQL → статистика → оценки селективности → стоимость альтернатив → выбранный план → выполнение → обращения к страницам → измерения → диагностика.
