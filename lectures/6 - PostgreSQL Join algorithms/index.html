    Лекция 6. PostgreSQL: алгоритмы соединения таблиц¶

    Основная лекция, обязательный материал. Технический ориентир — PostgreSQL 18. Основная тема: логика соединений, физические алгоритмы Nested Loop, Hash Join, Merge Join, порядок соединения таблиц, потребление памяти и диагностика через EXPLAIN ANALYZE.

    Терминология: понятия объясняются по-русски. Имена SQL-конструкций, операторов плана, параметров PostgreSQL и внутренних функций сохраняются в исходном написании — именно так они выглядят в запросах, настройках и EXPLAIN. Например, rows — оценка количества строк, loops — число запусков, Hash Cond — условие хеш-соединения.

    Формат: цельный теоретический разбор с короткими SQL-примерами, расчетами и диагностикой. SQL-примеры и планы, для которых не сказано обратного, иллюстративные: конкретный план зависит от схемы, индексов, статистики и конфигурации. Лабораторных заданий и вопросов студентам нет.

    1. Одна операция JOIN — разные результаты и разные механизмы¶

    1.1. Проблема: что означает «соединить таблицы»¶

    У нас есть клиенты и их заказы:

    customers                        orders
id | name                        id | customer_id | amount
---+--------                    ---+-------------+-------
 1 | Анна                         11 | 1           | 900
 2 | Борис                        12 | 1           | 1200
 3 | Вера                         13 | 2           | 300

    Задача: получить имя клиента и сумму его заказа.

    SELECT c.name, o.amount
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id;

    Результат:

    Анна  | 900
Анна  | 1200
Борис | 300

    Почему Анна появилась два раза? Потому что соединение работает с парами строк, удовлетворяющими условию, а SQL по умолчанию сохраняет повторяющиеся результаты. Наличие двух заказов дает две подходящие пары.

    Теперь посчитаем физическую цену. Представим десять миллионов заказов и сто тысяч клиентов. SQL задает, какие строки должны оказаться в ответе, однако не требует конкретной последовательности поисков. PostgreSQL должен выбрать способ построить пары без чрезмерного количества чтений, сравнений и промежуточных данных.

    Здесь возникают два разных уровня.

    • Логическое соединение задает смысл результата: какие пары считать совпавшими и что делать со строками без совпадений.
    • Физический алгоритм соединения задает способ получить результат: вложенные циклы (Nested Loop), соединение через хеш-таблицу (Hash Join) или соединение слиянием (Merge Join).

    Одно логическое INNER JOIN может исполняться любым из трех методов, если условия допускают соответствующий алгоритм. Название JOIN в SQL само по себе не обещает Hash Join в плане.

    1.2. Что значит INNER JOIN¶

    INNER JOIN — внутреннее соединение. Возвращает каждую пару левой и правой строк, для которой условие ON истинно.

    Для нашего примера Вера не попадет в результат, поскольку у нее нет заказа. Анна попадет дважды.

    Математическая модель для отношения A и B:

    A ⋈θ B = {(a,b) | a ∈ A, b ∈ B, θ(a,b) = TRUE}

    Это учебная модель множеств; SQL обычно работает с мультимножествами, где повторения сохраняются. Поэтому число выходных строк может быть больше числа строк в каждой таблице.

    При совпадении ключей с частотами a_k в левой таблице и b_k в правой количество строк внутреннего соединения по равенству:

    N_INNER = Σ по всем ключам k (a_k × b_k)

    Например, у ключа 42 имеется 1 000 строк слева и 2 000 справа. Только этот ключ образует 2 000 000 пар. Какой бы алгоритм PostgreSQL ни выбрал, все эти строки придется сформировать, если SQL действительно их запрашивает. Иногда причина медленного JOIN — объем корректного результата, а не ошибка реализации.

    1.3. LEFT JOIN: сохраняем левую сторону¶

    SELECT c.name, o.amount
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id;

    Результат:

    Анна  | 900
Анна  | 1200
Борис | 300
Вера  | NULL

    LEFT JOIN — левое внешнее соединение. Все совпавшие пары формируются как при внутреннем соединении. Если для левой строки не нашлось ни одного совпадения, PostgreSQL добавляет одну результирующую строку с NULL в столбцах правой стороны.

    Тонкость: если у клиента есть три подходящих заказа, он даст три строки. LEFT JOIN не превращает множество заказов в один заказ. И если совпадение нашлось, отдельная «дополнительная» строка с NULL для этого клиента не создается.

    Отсюда нижняя граница мощности результата левого внешнего соединения: при отсутствии последующего WHERE каждая левая строка даст как минимум одну результирующую строку. Но результат может быть значительно больше левой таблицы из-за совпадений «один ко многим».

    1.4. ON и WHERE при LEFT JOIN — разные этапы¶

    Попробуем выбрать заказы дороже 1 000:

    SELECT c.name, o.amount
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.id AND o.amount > 1000;

    Получим:

    Анна  | 1200
Борис | NULL
Вера  | NULL

    Почему Борис сохранился? Его заказ не удовлетворяет всему условию ON, поэтому для Бориса не нашлось подходящей правой строки. Левое соединение сохранило Бориса и выдало NULL справа.

    Теперь перенесем условие:

    SELECT c.name, o.amount
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.amount > 1000;

    Теперь осталась только Анна с заказом 1 200.

    Вторая форма сначала применяет семантику левого соединения, затем фильтрует готовые строки. Для Бориса 300 > 1000 ложно, для Веры NULL > 1000 дает неизвестно (UNKNOWN). WHERE сохраняет только TRUE.

    Это принципиально для дальнейшего чтения Join Filter и Filter в EXPLAIN. Внешнее соединение обязывает исполнитель различать условия, влияющие на сам факт совпадения, и условия, отбрасывающие уже сформированный результат.

    1.5. SEMI JOIN: нужен факт существования¶

    Предположим, нам нужны клиенты, у которых есть хотя бы один заказ. Запрашивать каждую пару не требуется.

    SELECT c.id, c.name
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
);

    Результат:

    1 | Анна
2 | Борис

    Полусоединение (SEMI JOIN) возвращает каждую подходящую левую строку один раз, если справа найдено хотя бы одно совпадение. В PostgreSQL это обычно внутренний тип операции, который планировщик может построить из подходящего EXISTS, IN и других выражений. В SQL не нужно писать выдуманную конструкцию SEMI JOIN.

    Преимущество механизма: для конкретной левой строки можно прекратить поиск справа после первого подтвержденного совпадения. При обычном INNER JOIN такого права нет: необходимо сформировать все подходящие пары.

    Важно: SEMI JOIN не делает DISTINCT над произвольным результатом INNER JOIN. Он сохраняет кратность самих левых строк и проверяет существование подходящей правой строки для каждой из них. Обычная конструкция INNER JOIN с SELECT c.* может возвращать одну левую строку несколько раз.

    1.6. ANTI JOIN: нужен факт отсутствия¶

    Другой запрос: клиенты без заказов.

    SELECT c.id, c.name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
);

    Результат:

    3 | Вера

    Антисоединение (ANTI JOIN) возвращает левую строку, для которой не существует ни одной подходящей правой строки.

    Исполнителю достаточно найти первое совпадение, чтобы исключить левую строку. Но для подтверждения отсутствия иногда приходится исчерпать весь подходящий поиск справа.

    А вот эквивалентность с NOT IN требует осторожности:

    WHERE c.id NOT IN (SELECT o.customer_id FROM orders AS o)

    Если подзапрос способен вернуть NULL, SQL использует трехзначную логику. Даже при отсутствии равного значения результат NOT IN может оказаться UNKNOWN, и строка не пройдет WHERE.

    Например, для клиента с id=3 и правым набором (1, 2, NULL) выражение 3 NOT IN (1,2,NULL) имеет значение UNKNOWN. NOT EXISTS с обычным условием равенства o.customer_id = c.id сохраняет нужную семантику отсутствия совпадающей строки. Поэтому NOT EXISTS часто проще и безопаснее для этой задачи.

    Еще один знакомый шаблон:

    SELECT c.id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.customer_id IS NULL;

    Здесь проверяется o.customer_id IS NULL: это именно столбец правой стороны, участвующий в строгом условии соединения. Для любой действительно совпавшей пары он не может быть NULL, поэтому фильтр оставляет только клиентов без заказов. PostgreSQL способен распознавать такую конструкцию как Anti Join.

    Часто встречается вариант WHERE o.id IS NULL, когда orders.id — первичный ключ. При гарантированном NOT NULL он может выражать ту же бизнес-логику, но возможность преобразования в Anti Join зависит от доказательств, доступных планировщику конкретной версии. Для ясного намерения удобно использовать NOT EXISTS; оптимизацию проверяем через EXPLAIN.

    1.7. Важная граница: INNER, LEFT, SEMI, ANTI — это логика результата¶

    Логический вид Что возвращается Сколько правых совпадений нужно найти
    INNER Все подходящие пары Все, если нужен полный результат
    LEFT Подходящие пары; при отсутствии — левая строка с NULL справа Все подходящие пары для совпавших строк
    SEMI Левая строка, если совпадение существует Достаточно первого
    ANTI Левая строка, если совпадений нет Нужно доказать отсутствие; первое совпадение позволяет отвергнуть строку

    Nested Loop, Hash Join, Merge Join отвечают уже на вопрос как именно выполнять эту логику. Физическая стратегия может меняться без изменения ответа SQL.

    Что важно запомнить. У внутреннего соединения повторения сохраняются; у левого внешнего важна последовательность применения ON и WHERE; SEMI и ANTI проверяют существование и отсутствие совпадения. Логика определяет обязательные строки результата, а физический алгоритм — стоимость их получения.

    2. Nested Loop: когда повторять поиск разумно, а когда катастрофически дорого¶

    2.1. Самая очевидная реализация¶

    Возьмем простое соединение:

    SELECT c.id, o.id
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id;

    Самый простой способ: взять первую строку клиентов, пройти заказы, найти совпадения, затем повторить для второго клиента.

    для каждой строки из внешнего источника:
    для каждой строки из внутреннего источника:
        если условие соединения истинно:
            вернуть пару

    Это алгоритм вложенных циклов (Nested Loop). Он имеет два входа:

    • Внешний источник (outer) — строки, по которым выполняется внешний цикл.
    • Внутренний источник (inner) — источник, который повторно запускается для очередной внешней строки.

    Здесь outer и inner — роли входов физического узла. Внешний источник Nested Loop не означает логический LEFT OUTER JOIN. Даже внутреннее соединение INNER JOIN имеет внешний и внутренний входы алгоритма.

    2.2. Где ломается наивный вложенный цикл¶

    Предположим:

    • customers — 100 000 строк;
    • orders — 10 000 000 строк;
    • поиск справа не ограничен индексом;
    • требуется проверить большинство сочетаний.

    Количество проверяемых пар в самой простой модели:

    N_pairs = 100 000 × 10 000 000 = 1 000 000 000 000 = 10¹²

    Триллион проверок. Даже если одна проверка кажется дешевой, результат заведомо опасен.

    Грубая вычислительная сложность полного вложенного перебора — O(N × M). Но эту оценку нельзя автоматически переносить на любой план Nested Loop. Главный вопрос: что делает внутренний источник при очередном запуске?

    2.3. Индекс превращает внутренний цикл в адресный поиск¶

    Создадим индекс:

    CREATE INDEX orders_customer_id_idx ON orders(customer_id);

    Теперь возможен план:

    Nested Loop
  -> Seq Scan on customers c
  -> Index Scan using orders_customer_id_idx on orders o
       Index Cond: (customer_id = c.id)

    Для каждой строки клиента исполнитель использует конкретный c.id как параметр индексного поиска по заказам. Это параметризованное индексное сканирование.

    Вместо повторного просмотра всех десяти миллионов заказов выполняется ограниченный поиск B-tree. Если клиентов слева немного, а для каждого находится несколько заказов, такой план может быть отличным.

    Но индексный поиск тоже стоит денег. Он предполагает обращение к страницам индекса, а при чтении остальных столбцов — к страницам таблицы, проверку видимости строк и вычисление дополнительных условий. Сотни тысяч маленьких поисков способны дать значительную суммарную нагрузку.

    Для учебной оценки:

    C_NL ≈ C_outer + N_outer × C_inner_per_run + C_pairs

    Это упрощенная формула: PostgreSQL учитывает стоимость первого и повторных запусков, возможное кеширование, условия завершения и другие детали.

    Например, 200 клиентов по 0,04 мс внутреннего поиска — порядка 8 мс суммарных поисков. Но 200 000 клиентов с тем же средним временем — уже около 8 секунд последовательной работы внутреннего узла. Реальное время может отличаться из-за кеширования и конкуренции.

    2.4. loops показывает цену повторения¶

    Условный план с измерениями:

    Nested Loop  (actual time=0.050..8200.000 rows=200000 loops=1)
  -> Seq Scan on customers c
       (actual time=0.020..120.000 rows=100000 loops=1)
  -> Index Scan using orders_customer_id_idx on orders o
       (actual time=0.015..0.070 rows=2 loops=100000)
       Index Cond: (customer_id = c.id)

    Читаем внимательно:

    • Внешний узел отдал 100 000 клиентов.
    • Внутренний индексный узел запускался 100 000 раз.
    • actual rows=2 означает среднее число возвращенных строк за один запуск.
    • Вторая величина actual time=...0.070 также усреднена по одному запуску.

    Оценочный суммарный объем работы внутреннего узла — 100 000 × 2 = 200 000 возвращенных строк. Оценочная сумма времени его запусков — 100 000 × 0,070 = 7 000 мс. Ее нельзя прибавлять к времени родителя как отдельную добавку: время родительского узла уже включает дочернюю работу.

    Если пользователь видит Index Scan и делает вывод «есть индекс, значит все хорошо», он пропускает loops=100000 — ключевой признак повторной работы.

    2.5. Когда PostgreSQL способен остановить внутренний поиск¶

    Для SEMI JOIN при первой подходящей правой строке дальнейшие совпадения этой левой строки не нужны.

    Для ANTI JOIN найденное совпадение означает, что левую строку возвращать нельзя.

    Следовательно, внутренний источник может не выполняться до конца при каждом запуске. Это меняет стоимость Nested Loop по сравнению с обычным внутренним соединением.

    Но у антисоединения есть обратная сторона: если совпадения нет, поиск должен подтвердить отсутствие — вплоть до исчерпания доступных кандидатов. Большое количество левых строк без совпадений при неэффективном внутреннем доступе способно оказаться дорогим.

    2.6. Materialize и Memoize: две разные оптимизации повторений¶

    Materialize может сохранить ранее прочитанные строки внутреннего источника, чтобы повторный проход не перечитывал его нижележащий источник заново.

    Nested Loop
  -> Seq Scan on a
  -> Materialize
       -> Seq Scan on b

    Если внутренний источник не зависит от текущего значения внешней строки, повторное получение уже сформированного набора из памяти или временного хранилища может быть дешевле повторного чтения таблицы. Но строки по-прежнему могут повторно проверяться на условие соединения. Materialize не устраняет саму необходимость обработать кандидатов.

    Memoize — кеширование результатов параметризованного внутреннего поиска по значениям параметров.

    Nested Loop
  -> Seq Scan on events e
  -> Memoize
       Cache Key: e.customer_id
       -> Index Scan using customers_pkey on customers c
            Index Cond: (id = e.customer_id)

    Предположим, миллион событий относится всего к ста клиентам. Без кеширования можно повторить миллион однотипных поисков клиентов. С Memoize результаты для уже встречавшегося customer_id могут возвращаться из локального кеша узла. Но нужны память и ведение кеша. Когда ключи почти всегда уникальны, попаданий мало, а расходы остаются.

    В EXPLAIN ANALYZE у Memoize видны показатели вроде Hits, Misses, Evictions, Memory Usage. Обратить внимание: Memoize и Materialize решают разные задачи. Первый кеширует результат по параметру, второй позволяет повторно прочитать сохраненный поток.

    2.7. Когда Nested Loop выигрывает¶

    Он особенно привлекателен, когда внешний источник дает мало строк, внутренний поиск хорошо ограничивается индексом и можно быстро получить первые результаты.

    Также Nested Loop важен для условий, которые не поддерживаются хеш-соединением или соединением слиянием. Например:

    SELECT *
FROM ranges AS r
JOIN points AS p ON p.value BETWEEN r.low AND r.high;

    Для такого диапазонного условия физические альтернативы зависят от доступных индексных методов и формы запроса; обычный Hash Cond по равенству здесь не возникает. Вложенные циклы остаются универсальным механизмом сопоставления строк.

    Признаки возможной проблемы: много внешних строк, большой loops внутреннего узла, дорогие повторные посещения страниц, высокие Buffers: shared hit/read и большие потери кандидатов после фильтрации.

    Инженерный вывод. Nested Loop сам по себе не плохой. Цена определяется количеством запусков и стоимостью одного внутреннего запуска. Для диагностики всегда перемножаем масштаб повторений, проверяем индексные ограничения, число найденных кандидатов и реальный результат.

    3. Hash Join: платим памятью, чтобы избежать повторного поиска¶

    3.1. Почему одного Nested Loop недостаточно¶

    Допустим, нужно соединить миллион заказов с сотней тысяч клиентов. У таблицы клиентов нет полезного индекса, а попытка повторно прочитать ее для каждого заказа означает огромную работу.

    Но мы ведь соединяем по равенству:

    SELECT o.id, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id;

    Если известен ключ клиента, почему бы не построить структуру для быстрого поиска по нему? Приходит знакомая идея — хеш-таблица. Она позволяет сопоставить ключу список строк, имеющих этот ключ.

    Hash Join — хеш-соединение. Его основной сценарий — соединение по условию равенства, для которого PostgreSQL поддерживает хеширование ключей.

    3.2. Сторона построения и сторона поиска¶

    У хеш-соединения два входа:

    1. Сторона построения (build side) — из строк этого входа строится хеш-таблица.
    2. Сторона поиска (probe side) — строки этого входа по очереди ищут совпадения в готовой структуре.

    В типичном плане PostgreSQL 18 сторона построения находится под узлом Hash, а другой источник передается непосредственно узлу Hash Join:

    Hash Join
  Hash Cond: (o.customer_id = c.id)
  -> Seq Scan on orders o             -- сторона поиска
  -> Hash
       -> Seq Scan on customers c     -- сторона построения

    Дерево показывает, что исполнитель должен сначала получить строки для построения хеш-таблицы, затем искать в ней совпадения для строк заказов. Если планировщик поменяет стороны местами и это допустимо семантикой, структура плана изменится.

    Важная тонкость: логические левая и правая таблицы SQL и физические сторона построения/сторона поиска — разные понятия. Для внутреннего соединения PostgreSQL вправе поменять входы. Для внешних соединений такая свобода ограничена необходимостью сохранять строки определенной стороны.

    3.3. Что действительно хранится в хеш-таблице¶

    Сильно упрощенная схема:

    customers:
(1, 'Анна')
(2, 'Борис')
(3, 'Вера')

            hash(id)
                |
                v
           номер корзины
                |
                v
     список записей с этим хешем

    Корзина (bucket) — часть хеш-таблицы, куда попадают записи с соответствующим хешем ключа. Хеш-значение используется для быстрого отбора кандидатов, но само равенство ключей все равно должно быть проверено. Разные ключи способны иметь одинаковый хеш — это коллизия.

    Если у одного customer_id справа несколько строк, нужно вернуть все подходящие пары. Поэтому структура хранения должна поддерживать несколько записей на один ключ. Хеш-таблица не превращает соединение «многие ко многим» в поиск единственной строки.

    После построения исполнитель читает заказ, вычисляет хеш o.customer_id, находит соответствующую корзину и проверяет ключи кандидатов.

    Здесь важно разделять:

    • Хеширование — вычисление числа для перехода к небольшой группе кандидатов.
    • Проверка равенства — установление настоящего совпадения ключей.
    • Дополнительные условия — например, сравнение сумм, дат или других столбцов после определения кандидатов по ключу.

    3.4. Что обозначает Hash Cond¶

    Hash Cond в плане — условие хеш-соединения. Например:

    Hash Join
  Hash Cond: (o.customer_id = c.id)

    Оно показывает выражения, по которым PostgreSQL получает хеш-значения и сопоставляет кандидатов. Условие должно подходить для хеш-соединения. В типичном случае это равенство двух ключей.

    А теперь добавим условие, которое нельзя непосредственно использовать как хеш-ключ:

    SELECT o.id, c.id
FROM orders AS o
JOIN customers AS c
  ON o.customer_id = c.id
 AND o.amount >= c.min_amount;

    Возможное представление:

    Hash Join
  Hash Cond: (o.customer_id = c.id)
  Join Filter: (o.amount >= c.min_amount)
  -> Seq Scan on orders o
  -> Hash
       -> Seq Scan on customers c

    Hash Cond определяет кандидатов по равенству. Join Filter дополнительно проверяет пару строк, уже сопоставленную по хеш-ключу. Строки, не прошедшие этот фильтр, не становятся результатом внутреннего соединения.

    У внешнего соединения добавляется важное правило: отсутствие пары, выдержавшей все условия ON, может привести к выдаче строки сохраняемой стороны с NULL справа (или слева для соответствующего вида соединения). Поэтому Join Filter нельзя бездумно перемещать в обычный Filter после внешнего соединения.

    3.5. Стоимость при достаточной памяти¶

    Если хеш-таблица полностью помещается в оперативную память, базовая работа приближенно состоит из:

    • прочитать N_build строк и построить структуру;
    • прочитать N_probe строк и выполнить поиск для каждой;
    • проверить коллизии и дополнительные условия;
    • сформировать все подходящие пары.

    Упрощенная сложность при разумном распределении хешей:

    O(N_build + N_probe + N_result)

    Здесь N_result нельзя выбрасывать. Если два входа имеют тысячи одинаковых ключей, количество возвращаемых пар может быть огромным даже при хорошей хеш-функции.

    По сравнению с вложенным полным перебором выигрыш очевиден: вместо многократного просмотра правой таблицы мы один раз подготавливаем структуру поиска. Но появляется новая цена — память для строк стороны построения и служебных структур.

    3.6. Почему work_mem — не весь ответ¶

    Для хеш-операций PostgreSQL 18 использует расчетный предел памяти:

    M_hash_budget = work_mem × hash_mem_multiplier

    По умолчанию work_mem = 4MB, а hash_mem_multiplier = 2.0. Поэтому базовый расчетный предел для одной хеш-операции равен приблизительно 8 МиБ. Это параметры по умолчанию, а не глобальный потолок памяти всего запроса. https://www.postgresql.org/docs/18/runtime-config-resource.html

    Например, сто тысяч строк по 64 байта полезных данных занимают примерно 6,4 МБ до учета ссылок, заголовков, выравнивания, корзин и вспомогательных структур. Поэтому «данные влезают в 8 МБ по сумме размеров колонок» не гарантирует, что хеш-таблица поместится в заданный бюджет.

    Кроме того, один SQL может содержать несколько хеш-операций и сортировок; несколько запросов могут исполняться одновременно. Если каждый серверный процесс рассчитывает на значительный объем оперативной памяти, давление на память сервера растет.

    3.7. Где память закончилась: разбиение на партии¶

    Предположим, сторона построения слишком велика. Полностью хранить ее в памяти нельзя. Что делать?

    PostgreSQL может использовать разбиение на партии (hash batches). Строки распределяются по партиям на основе частей хеш-значения. В памяти обрабатывается одна партия, а данные других партий временно сохраняются для последующей обработки.

    Учебная схема:

    Сторона построения: 1 000 000 строк
        |
        v
  распределение по хешу
        |
        +--> партия 0: построить хеш-таблицу в оперативную память
        +--> партия 1: временный файл
        +--> партия 2: временный файл
        +--> партия 3: временный файл

Сторона поиска:
        |
        +--> партия 0: искать сразу
        +--> партия 1: сохранить для обработки позже
        +--> партия 2: сохранить для обработки позже
        +--> партия 3: сохранить для обработки позже

    После завершения текущей партии исполнитель переходит к следующей: загружает ее часть стороны построения, формирует хеш-таблицу и обрабатывает соответствующие строки стороны поиска.

    Таким способом PostgreSQL может выполнить соединение при нехватке оперативной памяти ценой записи и чтения временных файлов. Не следует представлять это как гарантированное равномерное разбиение: распределение ключей может быть перекошенным, а реальная обработка учитывает различные ограничения и специальные случаи.

    3.8. Batches, Buckets, Memory Usage¶

    Счетчики из EXPLAIN ANALYZE:

    Hash Join
  Hash Cond: (o.customer_id = c.id)
  -> Seq Scan on orders o
  -> Hash
       Buckets: 65536  Batches: 8  Memory Usage: 4096kB
       -> Seq Scan on customers c

    Их смысл:

    • Buckets — количество корзин хеш-таблицы.
    • Batches — количество партий, на которые разделена обработка.
    • Memory Usage — память, учтенная для хеш-структуры в данном выполнении.

    Batches: 1 обычно означает, что данной операции не потребовалось разбиение на несколько партий. Batches > 1 указывает на многопартийную обработку; в типичном случае она сопровождается временным ввод-вывод.

    План может сообщать, что количество партий увеличилось во время выполнения, например:

    Batches: 16 (originally 2)

    Это существенный сигнал: планировщик и начальный расчет исполнителя ожидали меньший объем памяти или другое распределение данных. По мере построения хеш-таблицы пришлось увеличить число партий. Но одного значения Batches недостаточно, чтобы вычислить время работы storage: нужны Buffers: temp read/written, время выполнения и характеристики ввод-вывод.

    3.9. Почему рост партий может сильно увеличить задержку¶

    Причинная цепочка:

    1. Планировщик недооценил размер стороны построения или фактический объем строк в памяти.
    2. При построении хеш-таблица приблизилась к допустимому пределу.
    3. Исполнитель увеличил число партий и распределил данные для отложенной обработки.
    4. Появились дополнительные записи и чтения временных файлов.
    5. Время соединения увеличилось, одновременно возросла конкуренция за ввод-вывод.

    В плане это может выглядеть так:

    Hash Join
  Hash Cond: (o.customer_id = c.id)
  Buffers: shared hit=... read=..., temp read=... written=...
  -> Seq Scan on orders o
  -> Hash
       Buckets: 65536  Batches: 16 (originally 1)
       Memory Usage: 8192kB
       -> Seq Scan on customers c

    Это условный пример. Главное — сочетание Batches, временных блоков и расхождений между ожидаемым и фактическим количеством строк.

    Отсюда запрет на механическое решение «давайте увеличим work_mem до гигабайта». При ста конкурентных запросах и нескольких рабочих узлах это может создать новую проблему — исчерпание оперативную память. Сначала нужно понять, почему структура не помещается: объем полезного результата, ширина строк, ошибка статистики, перекос ключей или действительно недостаточный бюджет памяти.

    3.10. Почему сторона построения обычно меньше, но не всегда¶

    Для внутреннего соединения построить хеш-таблицу по меньшему набору часто выгоднее: меньше оперативную память, быстрее подготовка, ниже риск временного ввод-вывод.

    Но выбор стороны зависит от семантики внешних/полусоединений, формы плана, доступных фильтров, оценок стоимости и других свойств. Поэтому выражение «Hash Join всегда строит таблицу по меньшему входу» — плохая универсальная модель.

    Также Hash Join имеет стоимость подготовки: до выдачи совпадений нужно подготовить необходимую хеш-структуру. Для маленькой внешней выборки Nested Loop с адресными индексными поисками может дать первый результат раньше, хотя полное соединение больших наборов через хеш-таблицу было бы дешевле.

    3.11. Что происходит под нагрузкой¶

    Возьмем 40 одновременных запросов, каждый из которых формирует хеш-таблицу с расчетным бюджетом 64 МиБ. Только эти структуры потенциально требуют масштаба

    40 × 64 МиБ = 2 560 МиБ

    При наличии нескольких хеш-узлов в запросе, сортировок, других серверных процессов и shared_buffers суммарное давление выше. Если увеличить бюджет памяти, можно уменьшить временный ввод-вывод отдельных запросов, но одновременно увеличить конкуренцию за оперативную память. Если оставить бюджет слишком маленьким, соединения массово перейдут на многопартийную обработку и создадут ввод-вывод.

    Значит, инженерный выбор — баланс памяти, временного ввод-вывод и параллельной нагрузки.

    Что важно запомнить. Hash Join строит структуру поиска на одной стороне, затем проверяет другую. Hash Cond задает хешируемое равенство; совпадение хешей требует проверки ключей. Память ограничивает размер структуры; Batches > 1 сигнализирует об обработке несколькими партиями. Для диагностики нужны Memory Usage, Buffers: temp, размеры входов и фактическое время.

    4. Merge Join: соединяем два упорядоченных потока¶

    4.1. Почему упорядоченность может заменить хеш-таблицу¶

    У нас два набора строк, упорядоченных по одному ключу:

    A:  1, 2, 4, 6, 8
B:  2, 3, 4, 4, 7

    Нужно соединить по равенству ключей.

    Если обойти первый поток, держа указатель на втором, можно двигать тот указатель, чей ключ меньше. Когда ключи равны — выдавать совпавшие пары.

    Не требуется строить хеш-таблицу по всем строкам. И не нужно повторять полный поиск второй таблицы для каждой строки первой.

    Это соединение слиянием (Merge Join).

    4.2. Базовый алгоритм без повторяющихся ключей¶

    Пусть оба входа упорядочены по возрастанию. Вначале:

    A → 1
B → 2

    Так как 1 < 2, строка A=1 не может иметь совпадения в оставшейся отсортированной части B. Передвигаемся по A.

    A → 2
B → 2

    Ключи равны — возвращаем пару. Затем передвигаем указатели по правилам алгоритма. Если A=4 и B=3, двигаем B. Если ключи снова совпали, возвращаем соответствующие строки.

    При отсутствии повторяющихся ключей и при уже отсортированных входах стоимость сравнения ключей имеет порядок:

    O(N + M)

    Но это лишь часть полной стоимости плана. Нужно еще получить входы в требуемом порядке.

    4.3. Где берется правильный порядок¶

    PostgreSQL может получить нужные последовательности двумя основными способами.

    Способ А: индексы B-tree. Если индекс дает строки в порядке ключа соединения и такой обход выгоден, отдельная сортировка может не потребоваться.

    Merge Join
  Merge Cond: (o.customer_id = c.id)
  -> Index Scan using orders_customer_id_idx on orders o
  -> Index Scan using customers_pkey on customers c

    Способ Б: отдельные узлы Sort. Если чтение таблицы дешевле выполнить последовательно, PostgreSQL может получить строки через Seq Scan, затем отсортировать.

    Merge Join
  Merge Cond: (o.customer_id = c.id)
  -> Sort
       Sort Key: o.customer_id
       -> Seq Scan on orders o
  -> Sort
       Sort Key: c.id
       -> Seq Scan on customers c

    Второй вариант включает стоимость обеих сортировок, их процессор, память и возможные временные файлы. Если сортировки дорогие, Hash Join может оказаться предпочтительнее.

    4.4. Что показывает Merge Cond¶

    Merge Cond — условие соединения слиянием, по которому сопоставляются упорядоченные потоки.

    Merge Join
  Merge Cond: (o.customer_id = c.id)

    Обычный случай — равенство ключей, для которых PostgreSQL умеет согласованно сортировать и сравнивать значения. У произвольного неравенства a.x < b.x нет автоматического права стать Merge Cond. Условия пригодности зависят от операторов и их классов.

    Как и у хеш-соединения, дополнительные условия пары могут остаться в Join Filter:

    Merge Join
  Merge Cond: (o.customer_id = c.id)
  Join Filter: (o.amount > c.min_amount)

    Сначала ключи приводят нас к группе кандидатов. Затем фильтр решает, какая из этих пар действительно подходит.

    4.5. Повторяющиеся ключи ломают модель «каждый поток читаем один раз»¶

    Возьмем:

    A:  1, 1, 2
B:  1, 1, 1, 2

    По ключу 1 нужно вернуть 2 × 3 = 6 пар. По ключу 2 — еще одну.

    Простое продвижение обоих указателей после первой пары потеряет большинство результатов.

    Поэтому соединение слиянием должно уметь запоминать начало группы совпавших строк и повторно обходить группу. В реализации используются механизмы отметки позиции и возврата к ней (mark/restore); в подходящих планах может появиться Materialize.

    Учебная последовательность:

    A: первая строка ключа 1
B: запомнить начало группы ключа 1
   пройти все три строки B с ключом 1 → три пары
A: вторая строка ключа 1
B: вернуться к началу группы ключа 1
   пройти те же три строки → еще три пары
A: перейти к ключу 2
B: продвинуться к ключу 2

    Возникает стоимость повторного чтения группы. Даже если сортировка позволила почти линейно пройти входы, количество результатов и повторений внутри групп может быть большим.

    4.6. Почему actual rows может выглядеть странно¶

    В PostgreSQL EXPLAIN ANALYZE для Merge Join иногда показывает у внутреннего входа больше фактически возвращенных строк, чем имеется уникальных строк в исходном отношении.

    Это может происходить потому, что при повторном обходе группы исполнитель снова получает те же самые строки от внутреннего источника. Счетчик отражает выдачу строк узлом, включая повторные выдачи, а не число уникальных физических строк таблицы.

    Поэтому в диагностике соединения слиянием нельзя бездумно сравнивать actual rows внутреннего дочернего узла с COUNT(*) таблицы, если план использует повторный обход совпадающих ключей. https://www.postgresql.org/docs/18/using-explain.html

    4.7. Merge Join и память¶

    Часто говорят: «соединение слиянием почти не использует память». Это справедливо для самого сопоставления уже упорядоченных потоков в простом случае, но перестает быть полной моделью, когда требуются Sort и хранение групп повторяющихся ключей.

    Сортировки подчиняются собственным ограничениям work_mem и при нехватке оперативной памяти способны использовать временные файлы. Materialize также может хранить промежуточные данные в памяти или использовать временное хранилище.

    Следовательно, сравнение Merge Join и Hash Join по потреблению памяти требует смотреть на весь план, а не только на верхнюю строку Merge Join.

    4.8. Когда Merge Join выгоден¶

    Он привлекателен, если оба потока уже имеют подходящий порядок или стоимость его получения оправдана; данные велики; соединение требует множества совпадений; а использование общей большой хеш-таблицы нежелательно или дорого.

    Особенно интересен случай, когда дальнейшая часть запроса тоже требует порядок по ключу. Поток от соединения слиянием может оказаться полезен следующему узлу, однако SQL без ORDER BY не гарантирует порядок возвращаемых клиенту строк, даже если текущий физический план использует отсортированные входы.

    Когда Merge Join невыгоден: оба входа огромны и не отсортированы, а для подготовки нужны дорогостоящие внешние сортировки; либо один вход очень маленький, и Nested Loop с индексом проще и быстрее.

    Инженерный вывод. Merge Join превращает упорядоченность входов в экономию поиска. Его цена — получить этот порядок и правильно обработать группы повторяющихся ключей. В EXPLAIN ищем Merge Cond, Sort, Materialize, объемы групп, временные файлы и реальную стоимость дочерних узлов.

    5. Порядок соединений: PostgreSQL выбирает не только алгоритм, но и последовательность¶

    5.1. Почему трех таблиц достаточно, чтобы возникла новая задача¶

    Пусть есть:

    • customers — 100 000 клиентов;
    • orders — 10 000 000 заказов;
    • payments — 10 000 000 платежей.

    Нужно найти заказы клиентов определенного типа с успешными платежами:

    SELECT o.id, p.id
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
JOIN payments AS p ON p.order_id = o.id
WHERE c.segment = 'VIP'
  AND p.status = 'SUCCESS';

    Можно соединить customers с orders, а затем результат с payments. А можно сначала соединить отфильтрованные платежи с заказами, затем проверить клиентов.

    Для внутренних соединений эти два варианта могут быть логически эквивалентны. Но количество строк на промежуточных этапах, потребление памяти и число поисков различаются.

    Упрощенная схема:

    Вариант А:
customers(VIP) + orders → промежуточный набор
промежуточный набор + payments(SUCCESS) → ответ

Вариант Б:
payments(SUCCESS) + orders → промежуточный набор
промежуточный набор + customers(VIP) → ответ

    Если VIP — всего 0,1% клиентов, часто выгодно использовать эту селективность раньше. Но если SUCCESS составляет 0,001% платежей, ранняя фильтрация платежей может быть еще выгоднее. Самих долей недостаточно: нужны также индексы, кратности соответствий и цена обработки промежуточных строк.

    Это выбор порядка соединения (join order) — самостоятельная часть работы планировщика.

    5.2. Что именно меняется при выборе порядка¶

    Рассмотрим абстрактные отношения A, B, C.

    (A ⋈ B) ⋈ C
A ⋈ (B ⋈ C)

    При допустимой перестановке для внутренних соединений оба плана возвращают одинаковые комбинации строк. Но первая операция может вернуть 100 строк в одной стратегии и 10 миллионов — в другой.

    Если к промежуточному набору применяется Hash Join, это меняет количество данных для хеш-таблицы. Если применяется Nested Loop, меняется число повторных поисков. Если Merge Join, может потребоваться другая сортировка.

    Следовательно, порядок соединения и физический алгоритм нельзя оптимизировать независимо. Планировщик должен сравнивать комбинации порядка, способов сканирования и алгоритмов соединения.

    5.3. Откуда планировщик знает мощность результата JOIN¶

    В прошлой лекции rows для одной таблицы оценивались через число строк и селективность WHERE. Для внутреннего соединения базовая учебная модель похожа:

    N_join_est ≈ N_A_est × N_B_est × s_join_est

    Здесь s_join_est — оцененная доля пар, удовлетворяющих условию соединения.

    Например, пусть A содержит 100 клиентов, B — 10 000 заказов. Каждому заказу соответствует один клиент из этих ста, распределение равномерно, NULL нет. Упрощенная модель равенства по идентификатору дает:

    s_join_est ≈ 1 / 100
N_join_est ≈ 100 × 10 000 × (1 / 100) = 10 000

    Это согласуется с реальностью: каждый заказ создает одну пару с клиентом.

    Но для реальных данных такой расчет осложняют:

    • разные частоты ключей с обеих сторон;
    • повторяющиеся значения;
    • NULL;
    • статистика самых частых значений (MCV);
    • количество различных значений (n_distinct);
    • уникальные ограничения, известные ключи и связи;
    • условия фильтрации, влияющие на фактическое распределение ключей.

    В PostgreSQL функцию оценки селективности соединения по равенству представляет, в частности, eqjoinsel. Она может использовать статистику обоих соединяемых столбцов, включая сопоставление популярных значений, а не просто делить произведение мощностей на произвольную константу. https://www.postgresql.org/docs/18/row-estimation-examples.html

    5.4. Особое ограничение многоколоночной статистики¶

    В предыдущей лекции мы разбирали:

    CREATE STATISTICS s (dependencies, mcv)
ON status, channel
FROM orders;

    Для фильтров по нескольким столбцам одной таблицы это может быть полезно.

    Но PostgreSQL 18 явно оговаривает, что расширенная статистика CREATE STATISTICS пока не используется планировщиком для оценки селективности условий соединения таблиц. Поэтому нельзя обещать, что многоколоночная MCV исправит любую ошибку rows на JOIN. https://www.postgresql.org/docs/18/sql-createstatistics.html

    Статистика может улучшить оценки входных таблиц до соединения, если на них есть подходящие собственные ограничения WHERE, но это другое место в модели. Здесь особенно важно не смешивать «плохая оценка фильтра одной таблицы» и «плохая оценка числа совпадений между таблицами».

    5.5. Перестановка INNER JOIN и ограничения LEFT JOIN¶

    Для внутренних соединений PostgreSQL обычно имеет значительную свободу выбора порядка, несмотря на то, как в SQL расставлены JOIN.

    Но с внешними соединениями требуется осторожность:

    SELECT *
FROM a
LEFT JOIN b ON a.id = b.a_id
JOIN c ON c.b_id = b.id;

    Простая произвольная перестановка таблиц может изменить, какие строки сначала получили NULL и какие были отфильтрованы последующим соединением. Планировщик вправе применять только семантически корректные преобразования.

    Это не означает, что LEFT JOIN всегда закрепляет весь порядок. Некоторые перестановки внешних соединений законны; для других нужно соблюсти зависимости. В PostgreSQL применяются правила допустимости таких преобразований.

    Практический вывод: явный порядок написания SQL не всегда совпадает с порядком физического плана, но у внешних и антисоединений свобода перестановки уже, чем у простого набора внутренних соединений.

    5.6. Как пространство вариантов становится слишком большим¶

    Для двух таблиц выбор невелик. Для шести и более появляются разные варианты группировки, порядка и алгоритмов. При увеличении количества таблиц число комбинаций быстро растет.

    Планировщик не может тратить на оптимизацию каждого SQL больше времени, чем его потенциальный выигрыш.

    Поэтому PostgreSQL обычно использует поиск по подмножествам отношений, сохраняя выгодные пути для промежуточных наборов. Внутри применяются представления вроде RelOptInfo, Path, и оценки стоимости альтернатив.

    В упрощенной модели:

    1. Построить возможные способы чтения каждой таблицы.
    2. Построить допустимые соединения пар таблиц.
    3. Оценить количество строк и стоимость разных физических алгоритмов.
    4. Сохранить полезные пути с учетом стоимости и свойств результата.
    5. Построить соединения из трех и более отношений.
    6. Выбрать подходящий итоговый путь и создать дерево выполнения.

    Но перебирать все комбинации для очень большого запроса невыгодно. Тогда PostgreSQL может использовать генетический оптимизатор (GEQO) — эвристический поиск хорошего порядка соединений без гарантии нахождения глобального минимума.

    Стандартный порог geqo_threshold в PostgreSQL 18 — 12 отношений, хотя фактическое срабатывание зависит от структуры запроса и настроек. https://www.postgresql.org/docs/18/planner-optimizer.html

    5.7. join_collapse_limit: почему SQL-порядок иногда имеет значение¶

    Параметр:

    SHOW join_collapse_limit;

    Стандартное значение — 8. Он ограничивает глубину преобразования явно записанных соединений в общий список отношений, на котором планировщик может рассматривать альтернативные порядки.

    При:

    SET join_collapse_limit = 1;

    планировщик в общем случае вынужден учитывать явно заданную структуру соединений, что может уменьшить время планирования, но также ограничить пространство доступных планов. Допустимость преобразований по-прежнему подчиняется семантике SQL.

    Настройка не является универсальным способом ускорения JOIN. Если заданный руками порядок плох, ограничение планировщика только закрепит неудачный выбор.

    5.8. Почему нельзя выбрать JOIN по одному количеству строк¶

    Предположим, первая стратегия создает промежуточный набор в 10 000 строк, а вторая — в 20 000. Кажется, что первая обязательно лучше.

    Но если первая требует дорогого Sort и многочисленных случайных обращений к heap, а вторая читает данные последовательно и формирует дешевую хеш-таблицу, итоговая стоимость может оказаться ниже у второй.

    То же относится к порядку строк. Два пути могут давать одинаковые результаты, но один сохраняет порядок, необходимый следующему Merge Join, а второй потребует дополнительной сортировки.

    Итак, решение о join order строится по полной оценочной стоимости дерева, а не по правилу «сначала соединяй самую маленькую таблицу».

    Что важно запомнить. Оценка rows после JOIN задает размер промежуточных наборов, выбор порядка меняет стоимость всех следующих операций, а логика внешних соединений ограничивает допустимые перестановки. При большом числе таблиц стоимость самого планирования становится отдельным компромиссом.

    6. EXPLAIN ANALYZE: расследуем медленный JOIN¶

    6.1. С чего начинать диагностику¶

    Предположим, запрос выполняется десять секунд. Первое желание — заменить Nested Loop на Hash Join. Но так легко лечить симптом, не поняв причину.

    Для начала получаем план с фактическими счетчиками:

    EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE o.created_at >= DATE '2026-11-01';

    Важно: EXPLAIN ANALYZE действительно выполняет запрос. На UPDATE, DELETE и других изменяющих операциях он вызывает реальные действия; в production требуется оценивать последствия. У SELECT тоже могут быть побочные эффекты функций и существенная нагрузка.

    Главные этапы чтения:

    1. Найти узел физического соединения и его дочерние входы.
    2. Сравнить rows и actual rows на каждом полностью выполненном узле.
    3. Посмотреть loops у внутреннего входа.
    4. Разобрать условия Hash Cond, Merge Cond, Join Filter, Filter, Index Cond.
    5. Проверить BUFFERS, временные блоки и память хеширования/сортировки.
    6. Определить первое место, где ожидания о данных или стоимости перестали совпадать с реальностью.

    6.2. Поля плана JOIN и их смысл¶

    Поле Как читать
    Hash Cond Условие хеш-соединения: по каким ключам находятся кандидаты
    Merge Cond Условие соединения отсортированных потоков
    Join Filter Условие для пары строк, которое не вошло в основной механизм соединения
    Filter Дополнительная фильтрация результата узла
    Index Cond Условие ограничения кандидатов индексным поиском
    Rows Removed by Join Filter Сколько проверенных кандидатов-пар отклонено условием соединения (среднее на запуск при нескольких loops)
    Rows Removed by Filter Сколько строк узла отброшено обычным фильтром (среднее на запуск)
    loops Сколько раз узел запускался; actual rows и actual time обычно усреднены за запуск
    Batches Число партий обработки хеш-соединения
    Memory Usage Учтенная память хеш-структуры
    Buffers: shared hit/read Обращения к общим буферам PostgreSQL; read не обязательно означает физическое чтение SSD
    Buffers: temp read/written Обращения к блокам временных рабочих файлов

    Буквальные имена полей оставлены по-английски, потому что именно такими их печатает PostgreSQL. Термины и смысл — на русском.

    6.3. Join Filter и Filter на внешнем соединении¶

    Возьмем:

    SELECT c.id, o.id
FROM customers AS c
LEFT JOIN orders AS o
  ON c.id = o.customer_id AND o.amount > c.min_amount
WHERE c.active;

    Условие o.amount > c.min_amount относится к определению совпадения пары. Если ни одна строка orders не соответствует всему ON, клиент может все равно остаться в ответе с NULL справа.

    Условие c.active — фильтрация итоговой строки. Неактивного клиента можно отбросить целиком.

    Оптимизатор может перемещать безопасные фильтры на более ранние стадии, поэтому буквальное расположение каждого условия в плане зависит от выбранных преобразований. Однако логическая разница сохраняется, и при внешнем соединении Join Filter и Filter не обязаны быть взаимозаменяемыми. Официальная документация PostgreSQL отдельно обращает внимание на это различие. https://www.postgresql.org/docs/18/using-explain.html

    6.4. Диагностический случай: индекс есть, а Nested Loop тормозит¶

    Условный план:

    Nested Loop  (actual time=0.1..9000.0 rows=300000 loops=1)
  Buffers: shared hit=1200000 read=20000
  -> Seq Scan on customers c
       (cost=... rows=100 ...)
       (actual time=... rows=100000 loops=1)
  -> Index Scan using orders_customer_id_idx on orders o
       (cost=... rows=3 ...)
       (actual time=0.01..0.08 rows=3 loops=100000)
       Index Cond: (customer_id = c.id)

    Первое существенное расхождение: планировщик ожидал 100 клиентов, а фактически получил 100 000. Это недооценка в 1 000 раз.

    Внутренний узел выполнен сто тысяч раз. Даже если каждый поиск сам по себе быстр, сумма работы большая.

    Причинная цепочка:

    Ошибка оценки входных клиентов
          ↓
Недооценка числа повторных поисков
          ↓
Выбран Nested Loop с индексным внутренним доступом
          ↓
100 000 запусков внутреннего узла
          ↓
Много обращений к буферам и рост задержки

    Что исследовать: статистику и фильтры по внешней таблице, фактическую селективность, стоимость альтернативного соединения, полезность индекса, количество попаданий/чтений буферов. Лечение может состоять в улучшении оценки или доступных путей. Указание принудительно отключить Nested Loop не устраняет ошибку статистики.

    6.5. Диагностический случай: Hash Join перешел на временные файлы¶

    Другой условный план:

    Hash Join  (actual time=150.0..4800.0 rows=1000000 loops=1)
  Hash Cond: (o.customer_id = c.id)
  Buffers: shared hit=..., temp read=16000 written=16000
  -> Seq Scan on orders o
       (actual rows=1000000 loops=1)
  -> Hash
       Buckets: 65536  Batches: 32 (originally 2)
       Memory Usage: 8192kB
       -> Seq Scan on customers c
            (actual rows=500000 loops=1)

    Что видно:

    • построение хеш-таблицы использовало большой вход;
    • фактическое число партий увеличилось;
    • есть значительное количество временных чтений и записей;
    • следует проверить, насколько rows на входе Hash отличался от прогноза.

    Возможные причины: недостаточно памяти для рабочего набора, недооцененная ширина строк, ошибки оценок количества строк, тяжелое распределение ключей и повторное разбиение. Корректный ответ зависит от измерений.

    Цена исправления: увеличение памяти для хеширования может уменьшить временный ввод-вывод в одном запросе, но увеличить общий расход оперативной памяти при большой конкуренции. Уменьшение ширины строк стороны построения или ранняя фильтрация иногда позволяют сэкономить память без глобальной перенастройки сервера — при условии, что планировщик действительно может воспользоваться такой формой запроса.

    6.6. Диагностический случай: Merge Join тратит время на подготовку¶

    Условный план:

    Merge Join
  Merge Cond: (o.customer_id = c.id)
  Buffers: temp read=8000 written=8000
  -> Sort
       Sort Key: o.customer_id
       Sort Method: external merge  Disk: 64000kB
       -> Seq Scan on orders o
  -> Sort
       Sort Key: c.id
       Sort Method: quicksort  Memory: 2048kB
       -> Seq Scan on customers c

    Merge Join на верхней строке не раскрывает всей цены. Первая сортировка не поместилась в память и использовала временный файл; вторая обработала строки в памяти.

    Диагностика: выяснить, есть ли способы получить данные уже упорядоченными, каковы реальные rows и width, достаточно ли work_mem с учетом конкуренции, может ли другой алгоритм соединения обойтись без сортировки.

    И еще: если есть большое число повторяющихся ключей, сам механизм соединения слиянием может повторно получать строки внутренней группы. Это не всегда означает реальное повторное чтение страниц таблицы, но может увеличивать обработку и выдачу промежуточных строк.

    6.7. rows против actual rows: как не найти ложную ошибку¶

    Рассмотрим:

    Limit  (actual rows=10 loops=1)
  -> Nested Loop  (cost=... rows=100000 ...)
       (actual rows=10 loops=1)
       ...

    Нельзя объявлять, что планировщик ошибся в десять тысяч раз. Верхний Limit остановил запрос после десяти строк, поэтому нижний узел не был выполнен до конца. rows=100000 описывает прогноз для полного выполнения, actual rows=10 — фактически запрошенную часть.

    Еще две ловушки:

    • При loops > 1 фактические показатели строк и времени узла усредняются за один запуск; общий масштаб требует учитывать число запусков.
    • При Merge Join повторный обход совпадающих ключей может приводить к многократной выдаче одной строки внутренним узлом, что влияет на счетчики.

    Следовательно, сначала проверяем, имели ли мы право сравнивать числа, и только потом вычисляем кратность ошибки.

    6.8. Стоимость соединения под нагрузкой: три ограниченных ресурса¶

    процессор. Большие Nested Loop с множеством мелких поисков, тяжелые проверки Join Filter, коллизии и массовая генерация пар повышают загрузку процессора. Данные могут уже находиться в кеше, но обработка все равно дорогая.

    Память. Хеш-таблицы, сортировки, материализованные промежуточные наборы и кеширование результатов потребляют оперативную память. work_mem не является лимитом оперативной памяти на весь SQL или процесс PostgreSQL.

    Ввод-вывод. Промахи в буферном кеше, временные файлы хеширования и сортировки, множественные обращения к heap и конкурирующие запросы могут увеличивать задержку. shared read показывает необходимость получить блок вне shared_buffers, но не позволяет напрямую посчитать физические чтения накопителя.

    Отсюда стратегия измерения: для каждого медленного узла связываем механизм → ограниченный ресурс → симптом в плане → возможную причину.

    6.9. Почему не нужно сразу менять все настройки¶

    В PostgreSQL существуют настройки enable_nestloop, enable_hashjoin, enable_mergejoin и другие переключатели способов планирования. Они полезны как средства диагностического исследования альтернатив.

    Однако отключение enable_nestloop не делает вложенные циклы физически невозможными для всех запросов: в некоторых ситуациях подходящей альтернативы нет. Глобальные настройки влияют на множество запросов.

    Более устойчивый порядок инженерной работы:

    1. Разобраться с логической корректностью SQL и типом соединения.
    2. Найти первый крупный разрыв между оцененными и фактическими объемами.
    3. Проверить условия соединения и доступные индексы.
    4. Измерить повторные запуски, память и временные файлы.
    5. Сравнить допустимые альтернативы по реальным измерениям.
    6. Исправить установленную причину и оценить эффект под типичной нагрузкой.

    6.10. Сводная таблица: какой алгоритм выбрать и что подозревать¶

    Алгоритм Основная идея Когда часто выгоден Главная цена и диагностические признаки
    Nested Loop Для каждой внешней строки искать совпадения справа Малый внешний набор, эффективный внутренний индекс, быстрая выдача первых строк Много запусков внутреннего узла, случайные обращения, высокие loops
    Hash Join Построить хеш-таблицу, затем искать в ней совпадения Большие наборы, равенство ключей, достаточно памяти Бюджет оперативной памяти, Batches > 1, временные файлы, большой результат
    Merge Join Сопоставить два отсортированных потока Готовый порядок или недорогая сортировка; большие упорядоченные входы Sort, временные файлы, повторные группы ключей, стоимость подготовки

    Это типичные условия, а не правила выбора «по одному признаку». PostgreSQL сравнивает стоимость целых допустимых деревьев, а ошибочная статистика может изменить результат такого сравнения.

    7. Итоговая модель лекции¶

    Мы начали с вопроса, как из логического соединения получается физическое исполнение. Теперь цепочка замыкается:

    SQL: INNER / LEFT / EXISTS / NOT EXISTS
          ↓
Логическая семантика: пары, сохранение строк, существование
          ↓
Оценка числа строк на входах и после соединения
          ↓
Генерация допустимых способов и порядков соединения
          ↓
Nested Loop / Hash Join / Merge Join
          ↓
Память, страницы, индексные поиски, сортировки, партии
          ↓
EXPLAIN ANALYZE: actual rows, loops, BUFFERS, Batches
          ↓
Диагноз: какое предположение оказалось неверным

    Семь инженерных выводов:

    1. Логический вид JOIN определяет правильный ответ; физический алгоритм определяет стоимость его получения. Их нельзя отождествлять.
    2. INNER JOIN сохраняет все подходящие пары. Повторяющиеся ключи способны создавать огромный результат; даже хороший алгоритм обязан его сформировать, если SQL требует все строки.
    3. Nested Loop оплачивается числом повторных внутренних поисков. При малой внешней выборке индекс может делать его очень выгодным; при большой — дорогое повторение становится главным риском.
    4. Hash Join меняет повторный поиск на построение хеш-таблицы. Память ограничена; при нехватке появляется разбиение на партии и временный ввод-вывод.
    5. Merge Join использует упорядоченность потоков. Стоимость сортировок и повторяющихся групп может определять большую часть общей задержки.
    6. join order влияет на размеры промежуточных наборов. Планировщик сопоставляет порядки соединений и алгоритмы вместе, с учетом статистики и ограничений семантики.
    7. Диагностика начинается с причин. Сравниваем оценки и факты, число запусков, условия узлов, память и буферы; не отключаем алгоритмы наугад.
