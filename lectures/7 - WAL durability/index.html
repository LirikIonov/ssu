    7. PostgreSQL: WAL и durability¶

    Основная лекция магистратуры · PostgreSQL 18 · обязательный материал.

    Рассматриваем 13 тем согласованной программы: WAL, shared_buffers, dirty pages, COMMIT, WAL record, LSN, fsync, synchronous_commit, checkpoint, crash recovery, full_page_writes, batch/group commit и transaction latency. Исходники — REL_18_STABLE, если явно не оговорено другое. Здесь формируем физическую и инженерную модель. Детальное устройство WAL buffers, C-кода вставки и resource managers относится к 07.1; аппаратные подробности storage — к 07.2; детальное устройство pg_control и REDO — к 07.3. Уже разобранные ранее planner, JOIN, MVCC и распределители памяти не повторяем; блоки 08–09 не затрагиваем.

    Условность примеров. Планы, миллисекунды, LSN и размеры записей в примерах учебные. Значения настроек сверяйте с реальным экземпляром: они зависят от версии, сборки и конфигурации. Время операций ОС и накопителя нельзя вывести из PostgreSQL cost units.

    0. Техническое расследование: COMMIT был успешным, а сервер выключился¶

    Начнем с транзакции, которая затрагивает несколько разных страниц таблиц и индексов:

    BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
INSERT INTO transfer_log(transfer_id, amount) VALUES (7001, 100);

COMMIT;

    Предположим, клиент получил ответ об успешном COMMIT. Через миллисекунду пропало питание. У одного перевода могло измениться несколько heap-страниц, индексных страниц и служебных структур. Все эти страницы физически расположены в разных местах файла или даже разных файлов. Как вернуть базу к состоянию, в котором перевод подтвержден целиком?

    Наивное решение: при COMMIT немедленно записать все измененные страницы на диск. Но изменения может делать много транзакций одновременно; одна и та же страница может содержать данные нескольких транзакций; одна транзакция может изменить сотни разных страниц. Синхронно записывать и подтверждать все эти страницы при каждом небольшом COMMIT — дорогая операция, а одиночная запись страницы сама по себе еще не атомарна относительно отключения питания.

    PostgreSQL использует другой инвариант: изменения можно записать в компактный журнал, а страницы таблиц синхронизировать позднее. Но нужно строго понимать, что именно журналируется, когда запись журнала становится долговечной и какие события можно переставлять.

    SQL UPDATE/INSERT
     │
     ├──► измененные страницы в shared_buffers
     │           │
     │           └──► dirty → запись data page позднее
     │
     └──► WAL records → WAL buffers → WAL write → WAL flush
                                                   │
                                    commit record ──┘
                                                   │
                                     подтверждение COMMIT

После сбоя: страницы с накопителя + долговечный WAL → REDO

    Эта схема показывает отношения между событиями. Фактически изменение страницы и формирование WAL выполняются согласованно в рамках операции; не следует понимать ее как право сначала сбросить грязную страницу на диск, а когда-нибудь затем создать WAL. Строгий порядок записи на долговечное хранилище проверим отдельно.

    1. WAL: зачем запись впереди данных¶

    1.1. Что гарантируем¶

    Долговечность (durability) в смысле ACID означает: если транзакция успешно подтверждена в синхронном режиме, ее изменения должны пережить предусмотренные моделью отказов сбои, в том числе остановку процесса и сбой ОС, если надежно работает подсистема постоянного хранения. Это не обещание против уничтожения единственной копии накопителя, ложного подтверждения fsync неисправным устройством или произвольного повреждения носителя.

    WAL (Write-Ahead Logging) — журнал предварительной записи. Главный порядок:

    WAL, необходимый для восстановления изменения страницы,
должен быть надежно сохранен ПРЕЖДЕ, чем измененная страница
окажется надежно записана в файл данных.

    В PostgreSQL это гарантируется через сопоставление page LSN и границы долговечно сохраненного WAL. Грязную страницу разрешено записать до COMMIT транзакции, если WAL изменений этой страницы уже синхронизирован. Поэтому нельзя объяснять систему правилом «страница на диск только после COMMIT» — это неправильное ограничение.

    1.2. Почему это дает производительность¶

    Без WAL маленький перевод может потребовать синхронизировать множество страниц нескольких файлов. С WAL, в обычном случае, для подтверждения требуется продвинуть долговечную границу последовательного потока журнала до записи о фиксации транзакции. Запись страниц можно отложить, сгруппировать, частично переиспользовать и выполнять фоном.

    Дешевле ли это всегда? Нет. На WAL тоже тратятся CPU, память, файловые записи и синхронизация. Если WAL становится узким местом, его последовательность превращается в общий ограниченный ресурс для конкурентных транзакций.

    1.3. Что WAL не означает¶

    • Не журнал SQL-команд. Из одной SQL-команды могут появиться разные WAL records, которые восстанавливают изменения страниц и служебное состояние.
    • Не гарантия записи data page при COMMIT. Страница может остаться грязной после подтверждения транзакции.
    • Не автоматический резервный экземпляр данных. WAL необходим для аварийного восстановления, но при утрате нужного журнала локальное восстановление невозможно.
    • Не способ отменить любые последствия вне PostgreSQL. Внешнее действие не возвращается назад с помощью WAL.

    1.4. Проверка модели отключением питания¶

    Представим две ситуации.

    Ситуация А: на диске старая страница; WAL изменения и записи COMMIT уже долговечны. После сбоя PostgreSQL сможет воспроизвести изменения из WAL.

    Ситуация Б: на диске уже новая страница; WAL изменения еще не долговечен. При обрыве записи страницы мы можем потерять единственный источник корректного восстановления. WAL-инвариант не допускает такой порядок надежного сброса.

    Итак, вся система держится на упорядочивании долговечных эффектов, а не на синхронной записи каждой таблицы.

    Главная модель раздела: журнал → долговечная граница журнала → разрешение записывать соответствующую страницу → восстановление при необходимости.

    2. Shared buffers: где реально меняется строка¶

    2.1. Версия страницы в памяти¶

    Таблицы и индексы PostgreSQL хранятся в файлах, разбитых на блоки; в обычной сборке размер блока 8 КиБ. При изменении строки исполнитель работает с буфером страницы в общем пуле shared_buffers. Если нужной страницы там нет, она загружается из файлового слоя.

    Файл таблицы на storage                shared_buffers
┌───────────┐                          ┌───────────┐
│ блок 100  │ ─────► загрузить ─────►  │ buffer #7 │
│ старое    │                          │ блок 100  │
└───────────┘                          └─────┬─────┘
                                           │ UPDATE
                                           ▼
                                      │ новые байты │
                                      │ dirty = yes │

    shared_buffers хранит рабочую копию страницы, а не самостоятельную долговечную версию. Общее слово «кеш» здесь опасно: нам важно, что именно в этой памяти PostgreSQL меняет данные и должен затем организовать надежную запись.

    2.2. Что изменяет UPDATE¶

    UPDATE accounts ... модифицирует физические структуры, включая страницы heap и при необходимости индексов. Для нашей темы достаточно следующего:

    1. PostgreSQL получает нужные буферы и координирует доступ к их содержимому.
    2. Модификация страницы и регистрация требуемого WAL согласуются как одна операция изменения состояния.
    3. Для страницы фиксируется идентификатор последнего относящегося к ней изменения журнала — page LSN.
    4. Буфер помечается грязным.
    5. SQL может завершиться, хотя соответствующая страница еще не записана в data file.

    Мы не углубляемся в устройство версий строк — оно уже относится к ранее пройденному MVCC. Для WAL принципиально количество и расположение физических изменений, а не SQL-синтаксис сам по себе.

    2.3. Почему буфер можно менять многократно¶

    Представим, что 1000 транзакций последовательно увеличивают счетчик на одной странице. Между их изменениями эта страница не обязана записываться на диск 1000 раз. Она может оставаться в памяти с последним состоянием, пока WAL фиксирует необходимую последовательность изменений.

    Дисковая страница: x = 0
RAM: x = 1 → x = 2 → ... → x = 1000
WAL: последовательность зарегистрированных изменений
Дисковая страница позднее: x = 1000

    В реальности часть изменений может оказаться на других страницах и журнал может содержать дополнительную информацию. Схема показывает экономию записей data pages, а не количество или формат WAL records.

    2.4. Где граница shared_buffers и файлового кеша ОС¶

    У PostgreSQL есть собственный пул буферов. ОС может дополнительно держать файловые страницы в своем кеше. Запись из PostgreSQL в файл через системный вызов еще не означает, что накопитель гарантированно удержит байты после потери питания. Именно поэтому позже понадобятся fsync и понятие WAL flush.

    Инженерный вывод: UPDATE работает с памятью и регистрирует журнал; подтвержденный COMMIT не требует, чтобы каждая затронутая heap-страница уже покинула shared_buffers.

    3. Dirty pages: почему запись откладывается и кто за нее платит¶

    3.1. Dirty ≠ на диске¶

    Грязная страница (dirty page) — буфер, содержимое которого отличается от надежно сохраненной версии соответствующей страницы файла. Даже если операционная система уже приняла какие-то байты в свой файловый кеш, вопрос долговечности остается отдельным.

    clean: RAM соответствует версии файла данных
UPDATE: изменили RAM, buffer → dirty
write: передаем новую страницу в файловый слой
sync: обеспечиваем требуемую надежность записей файла

    Данные могут успеть записаться в файл до фиксации транзакции. Это нормально: восстановление и сведения о статусе транзакции обеспечат корректную логическую картину. Dirty bit связан с необходимостью записать страницу, а не с тем, зафиксированы ли все транзакции, чьи изменения она содержит.

    3.2. Кто записывает грязные страницы¶

    Background writer (bgwriter) старается заранее записывать грязные буферы, уменьшая вероятность того, что процессу запроса придется делать эту работу при потребности в свободном буфере.

    Checkpointer выполняет работу по контрольной точке: обеспечивает запись и синхронизацию необходимых страниц, чтобы ограничить объем работы при будущем crash recovery.

    Client backend тоже может столкнуться с необходимостью записи буфера, например при выборе жертвы для замещения. Значит, даже когда приложению кажется, что оно только меняет одну строку, оно может косвенно оплатить дополнительную файловую работу.

    Нельзя приписывать одному bgwriter обязанность синхронно сохранять все изменения к моменту COMMIT.

    3.3. Защита правила WAL при записи страницы¶

    Пусть последний изменивший страницу WAL record заканчивается на LSN = L_page. Перед надежной записью страницы PostgreSQL должен обеспечить:

    durable_wal_lsn >= L_page

    Если журнал еще не синхронизирован до этой позиции, его необходимо продвинуть. Иначе на storage может оказаться новая версия страницы, для которой не существует надежного описания изменений.

    Важное следствие: сохранение грязной страницы и подтверждение COMMIT — разные причины потребовать WAL flush. На практике checkpoint, запись при вытеснении и фиксация транзакции взаимодействуют через общую долговечную границу журнала.

    3.4. Что произойдет под нагрузкой¶

    В спокойном режиме страницы постепенно записываются в фоне. Добавим много конкурентных изменений, затрагивающих широкий набор страниц.

    • Растет поток dirty buffers.
    • Фоновые процессы должны успевать готовить и записывать их.
    • При замещении буфера backend может столкнуться с записью грязной страницы.
    • Синхронизация файлов во время checkpoint добавляет нагрузку на накопитель.
    • Если WAL и data files конкурируют за одно устройство, рост data-page I/O способен увеличить задержку WAL flush и тем самым задержку COMMIT.

    Признаки исследуем через узкоспециализированные счетчики pg_stat_bgwriter и pg_stat_checkpointer; общую диагностику ожиданий оставим блоку 08.

    Главная модель: dirty pages — отложенный долг по записи data files. WAL делает такую отсрочку корректной; фоновая запись и checkpoint определяют, когда и какой ценой долг погашается.

    4. COMMIT: когда транзакция становится подтвержденной¶

    4.1. Факт изменения страницы не равен фиксации¶

    Вот транзакция:

    BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

    После UPDATE в памяти и WAL уже могли появиться изменения. Но клиент еще не получил подтверждение. Если сервер упадет здесь, транзакция не должна превратиться в частично зафиксированный перевод.

    Для успешного подтверждения необходимо зарегистрировать факт фиксации транзакции. В журнале для этого формируется commit record. Он отделяет физическую историю изменений от решения, что все изменения транзакции стали зафиксированными.

    4.2. Два уровня состояния: физический и транзакционный¶

    Неприятный вопрос: если WAL о первом UPDATE попал на диск, а WAL о COMMIT — нет, что сделает REDO?

    Механизм восстановления может воспроизвести физические изменения страницы, описанные долговечным WAL. Это не означает, что транзакция логически считается зафиксированной. Статус транзакции и отсутствие надежного подтверждения не позволят выдать ее изменения как результат завершенной транзакции.

    Для понимания достаточно разделить:

    • Физическое состояние страниц: какие байты были изменены и воспроизведены.
    • Состояние транзакции: какие изменения подтверждены и должны быть видимы как зафиксированные.

    Подробности хранения статусов и MVCC относятся к ранее пройденной теме; здесь нужна только граница между WAL REDO и зафиксированностью.

    4.3. Синхронный COMMIT: что ожидаем¶

    Для обычного локального synchronous_commit = on без настроенного ожидания синхронных standby основной порядок следующий:

    1. Зарегистрировать необходимые изменения и запись о фиксации.
    2. Получить целевую позицию WAL, покрывающую commit record.
    3. Обеспечить долговечное сохранение WAL до требуемой позиции.
    4. Завершить протокол подтверждения и вернуть успешный ответ.

    Это не означает синхронную запись всех data pages. А запись журнала до позиции COMMIT покрывает все предшествующие записи того же потока, в том числе WAL изменений данной транзакции.

    4.4. Потерянный ответ и неопределенный исход¶

    Предположим, PostgreSQL сделал WAL flush, зафиксировал транзакцию, но сетевое соединение оборвалось до доставки ответа. Клиент видит timeout.

    Возможны два состояния: транзакция уже успешно зафиксирована либо еще не была зафиксирована. Timeout не различает их.

    Для backend это практическая граница durability: нельзя автоматически трактовать таймаут после отправленного COMMIT как ROLLBACK. Безопасное прикладное решение основано на проверке результата по бизнес-идентификатору операции и контроле повторного применения; реализацию протокола идемпотентности здесь не рассматриваем.

    4.5. Когда COMMIT не создает обычной WAL-записи¶

    У некоторых транзакций, например только читающих данные без операций, требующих фиксации изменений, нет необходимости создавать обычную запись физического COMMIT для изменения постоянных данных. Поэтому число команд COMMIT со стороны приложения не обязано точно совпадать с числом соответствующих WAL commit records и тем более с числом fsync.

    Главный вывод: подтверждение транзакции определяется достижением необходимой границы долговечного WAL и транзакционным протоколом; изменения файлов данных могут сохраняться раньше или позже.

    5. WAL Record: из чего состоит восстановимая история¶

    5.1. Почему «WAL хранит SQL» неверно¶

    Одна команда:

    UPDATE accounts SET balance = balance + 100 WHERE id = 42;

    может затронуть страницу строки, индексные страницы и служебные метаданные. В журнале PostgreSQL требуются записи, необходимые для повторного применения соответствующих физических операций, а не текст UPDATE с надеждой когда-нибудь выполнить его заново.

    Это важно для корректности. Во время восстановления нельзя просто повторить SQL в новой транзакции: условия, индексы, конкуренция и порядок изменений могли бы быть другими.

    5.2. Логическое устройство записи¶

    WAL record имеет общий заголовок с длиной, информацией о типе, связями по последовательности и контрольной суммой. Нагрузочная часть зависит от подсистемы, зарегистрировавшей изменение. На учебном уровне:

    ┌───────────────────────────────────┐
│ XLogRecord: общий заголовок        │
│ длина, xid, prev, rmgr, CRC и др. │
├───────────────────────────────────┤
│ ссылки/описания блоков             │
├───────────────────────────────────┤
│ данные изменений                  │
├───────────────────────────────────┤
│ при необходимости full-page image │
└───────────────────────────────────┘

    XLogRecord — структура текущей реализации. Названия C-полей и точная упаковка — материал 07.1. Сейчас важны три свойства:

    1. Журнал образует последовательность записей.
    2. Каждая запись имеет достаточно сведений, чтобы соответствующая подсистема могла применить изменение при REDO.
    3. Запись защищена контрольной суммой, позволяющей обнаруживать повреждение WAL record. Это не заменяет надежность накопителя.

    5.3. Мелкие изменения и полные образы страницы¶

    Для большинства операций журнал хранит необходимые изменения, а не целиком каждую страницу. Но при первом подходящем изменении страницы после checkpoint может потребоваться полный образ — full-page image (FPI), чтобы пережить частичную запись data page. Поэтому «одна измененная строка = несколько байт WAL» — плохая модель: даже короткое изменение способно создать запись с образом страницы порядка килобайт.

    5.4. Сегменты WAL¶

    WAL хранится в pg_wal. Это единый логический поток, разбитый на WAL-страницы и сегментные файлы; типичный сегмент — 16 МиБ, типичная WAL-страница — 8 КиБ. Сборка и initdb допускают другие размеры.

    Сегмент — единица файловой организации, а WAL record — единица зарегистрированного изменения. Запись может пересекать границы страниц. Не следует считать один segment одним коммитом или одной транзакцией.

    5.5. Как исследовать объем WAL одной операции¶

    Для грубого экспериментального масштаба можно читать pg_current_wal_insert_lsn() до и после исследуемых операций и вычислить разницу. Но на работающем сервере WAL формируется также другими backend-процессами — разница глобальных LSN не является точным счетчиком WAL исключительно данного SQL.

    Для SQL-наблюдения полезнее EXPLAIN (ANALYZE, WAL) в контролируемом окружении: он показывает записи, образы страниц и объем WAL, произведенные при выполнении анализируемого плана. Сам EXPLAIN ANALYZE реально выполняет изменяющий запрос; использовать его на production для UPDATE/DELETE без учета последствий нельзя.

    Главная модель: WAL records сохраняют физически восстановимую историю; SQL-текст и количество записей журнала не находятся в соотношении один-к-одному.

    6. LSN: общий порядок журнала и отдельные границы его сохранения¶

    6.1. Что такое LSN¶

    LSN (Log Sequence Number) — логическая позиция в WAL, которая монотонно увеличивается при продвижении журнала. Тип PostgreSQL — pg_lsn. Запись 0/16B6C50 — пример представления LSN в двух шестнадцатеричных частях, разделенных /.

    LSN позволяет упорядочивать действия и измерять расстояние в байтах между позициями. Это не отметка времени. Две WAL-записи с соседними LSN могут относиться к разным транзакциям.

    6.2. Три границы: insert, write и flush¶

    Построение WAL не завершает его долговечное сохранение.

                     insert LSN      write LSN        flush LSN
                 ──────────      ─────────       ─────────
WAL buffers:       вставлен
Файловый слой:                     записан
Storage:                                           sync завершен

Обычно: flush LSN ≤ write LSN ≤ insert LSN
    • Insert LSN: запись уже вставлена в внутренние WAL buffers.
    • Write LSN: журнал продвинут из внутренних буферов PostgreSQL в файловый слой; это еще не гарантия сохранения после потери питания.
    • Flush LSN: журнал синхронизирован настолько, что PostgreSQL считает его долговечным при корректном поведении ОС и storage.

    Именно третья граница важна для обычного синхронного COMMIT.

    6.3. Page LSN и инвариант WAL¶

    В заголовке data page содержится page LSN: позиция WAL последнего зарегистрированного изменения этой страницы. В примере:

    page LSN  = 0/2000800
flush LSN = 0/2000400

    Журнал еще не синхронизирован до нужной позиции. Значит, безопасная запись этой версии страницы на долговечное хранилище требует сначала продвинуть flush LSN.

    После:

    flush LSN = 0/2000A00

    требование для данной страницы выполнено.

    page LSN полезен и при REDO: если на странице уже есть состояние не старше требуемой WAL-записи, повторное применение соответствующего изменения обычно не требуется. Подробности исключений и алгоритма чтения страницы — 07.3.

    6.4. Измерение в PostgreSQL 18¶

    SELECT
    pg_current_wal_insert_lsn() AS insert_lsn,
    pg_current_wal_lsn()        AS write_lsn,
    pg_current_wal_flush_lsn()  AS flush_lsn;

    pg_current_wal_lsn() возвращает именно write-позицию. Название без слова write — частый источник путаницы.

    SELECT pg_size_pretty(
    pg_wal_lsn_diff('0/2000A00'::pg_lsn,
                    '0/2000400'::pg_lsn)::bigint
);

    pg_wal_lsn_diff() измеряет количество байт между позициями. Для демонстрационных LSN разница равна 0x600 = 1536 байтам.

    Запомнить: insert описывает готовность WAL в памяти; write — передачу файловому слою; flush — границу предполагаемой долговечности. Именно смешение этих трех состояний ломает большинство объяснений WAL.

    7. fsync: почему write() еще не означает надежную запись¶

    7.1. После write() данные могут быть в RAM ОС¶

    До сих пор у нас был единый термин «записать WAL». На деле есть несколько стадий:

    WAL buffer PostgreSQL
       │
       ▼
write()/pwrite() и файловые операции
       │
       ▼
кеш страниц ОС
       │
       ▼
команды синхронизации/сброса
       │
       ▼
накопитель, сообщивший о долговечном сохранении

    ОС может принять байты в свой кеш и вернуть успех из write(), хотя данные еще не стали устойчивыми к потере питания. Системные механизмы fsync() и fdatasync(), а также соответствующие режимы открытия файлов позволяют потребовать необходимую синхронизацию. Но даже здесь реальная гарантия зависит от корректности драйвера, файловой системы, контроллера и накопителя.

    Ключевая формулировка: PostgreSQL может гарантировать установленный порядок долговечных записей только при условии, что нижние уровни честно выполняют контракты синхронизации. Разбор PLP, кеша контроллера и команд устройства отложен до 07.2.

    7.2. Как связан XLogFlush и системный fsync¶

    На концептуальном уровне:

    Потребовалась долговечность до LSN = X
        │
        ▼
XLogFlush(X) — обеспечить требуемую flush-позицию
        │
        ├──► если durable WAL уже ≥ X, дополнительная работа не нужна
        │
        └──► иначе выполнить необходимые записи и синхронизацию
                        │
                        ▼
                flush LSN продвигается до X или дальше

    XLogFlush() — функция текущей реализации, доступная для изучения в 07.1. Это не синоним «каждый вызов выполняет отдельный fsync». Журнал может оказаться уже надежно записан другим процессом, а одно продвижение flush-позиции может покрывать несколько конкурентных транзакций.

    7.3. wal_sync_method¶

    В PostgreSQL поддерживаются несколько способов обеспечить синхронизацию WAL:

    wal_sync_method Принцип
    fdatasync fdatasync() после записи; стандартное значение на Linux и FreeBSD в PG18
    fsync fsync() для WAL-файла
    open_datasync Запись через файл, открытый с O_DSYNC
    open_sync Запись через файл с O_SYNC
    fsync_writethrough Платформозависимая синхронизация с дополнительными требованиями write-through

    Доступность и эффективность зависят от платформы. Сравнивать значения только по названию нельзя: на конкретном storage одна реализация может выигрывать, другая проигрывать. Основная лекция фиксирует различия, а системный уровень — 07.2.

    7.4. fsync=off: ошибка в трактовке риска¶

    SHOW fsync;
SHOW wal_sync_method;

    При fsync = off PostgreSQL прекращает надежно принуждать нужные записи к долговечному сохранению. После сбоя ОС или питания возможна не только потеря последних подтвержденных транзакций, но и необратимое повреждение согласованности файлов данных и WAL.

    Сравнение, которое нужно удержать:

    • fsync = on, synchronous_commit = off: есть риск потерять недавно подтвержденные транзакции, но сохранена стратегия согласованного восстановления при корректном storage.
    • fsync = off: ослаблены собственно гарантии последовательности надежных записей; возможна серьезная порча кластера при сбое ОС/оборудования.

    Отключать fsync на рабочей базе ради TPS недопустимо как обычный прием оптимизации. В документации PostgreSQL это допускается только для легко восстанавливаемых или одноразовых экземпляров.

    7.5. Как ведет себя система под нагрузкой¶

    Пусть накопитель в среднем выполняет требуемую синхронизацию за 0,7 мс. Если 1000 маленьких транзакций были бы строго последовательно синхронизированы по одной, только эта работа заняла бы примерно 700 мс. В реальности несколько транзакций могут разделить один WAL flush, а обработка может перекрываться с другими действиями. Поэтому число COMMIT нельзя механически приравнивать числу физических синхронизаций.

    Важнее измерять:

    • количество WAL writes и WAL fsyncs;
    • суммарное время этих операций;
    • число транзакций и интенсивность WAL;
    • p50/p95/p99 наблюдаемой задержки подтверждения;
    • конкурентную нагрузку и состояние устройства.

    В PG18 WAL I/O находится в pg_stat_io, а не в старых полях pg_stat_wal. К этому вернемся в разделе 13.

    Главная модель: write сообщает о передаче данных файловому слою; flush задает границу надежности, на которую опирается стандартный COMMIT.

    8. synchronous_commit: какую гарантию выбирает транзакция¶

    8.1. Наивное представление: «COMMIT всегда делает fsync»¶

    Теперь проверим очевидное допущение. Если каждая транзакция всегда ждет надежной записи своего WAL, небольшие некритичные операции могут оплачивать ненужную задержку. Но в PostgreSQL предусмотрен выбор момента, после которого клиенту разрешено вернуть успех.

    Основная настройка:

    SHOW synchronous_commit;

    Она контролирует, какой уровень обработки WAL должен быть достигнут до сообщения об успешной фиксации. Это настройка момента подтверждения, а не того, будут ли в принципе регистрироваться WAL records.

    8.2. Локальная гарантия: on и off¶

    При обычном локальном on транзакция, которая требует WAL-синхронизации, ждет локального WAL flush, покрывающего фиксацию.

    При off транзакция может подтвердиться до того, как ее WAL станет долговечным. Изменения доступны другим транзакциям как зафиксированные при работающем сервере, но после аварийного завершения последние подтвержденные изменения могут исчезнуть.

    synchronous_commit = on:
  WAL record → локальный WAL flush → ответ OK

synchronous_commit = off:
  WAL record → логический COMMIT → ответ OK
                    │
                    └──► WAL flush позднее

    Ключевая тонкость: off не превращает одну транзакцию в «частично подтвержденную» после recovery. Если ее commit record не пережил сбой, восстановленное состояние будет соответствовать отсутствию этой транзакции как успешно зафиксированной. В документации PG18 верхняя граница окна риска описана как до трех интервалов wal_writer_delay при нормальной работе механизма WAL writer. Это ориентир механизма, не обещание поведения неисправного storage.

    8.3. Как включить off только на одну транзакцию¶

    BEGIN;
SET LOCAL synchronous_commit = off;

INSERT INTO diagnostic_events(event_type, created_at)
VALUES ('heartbeat', clock_timestamp());

COMMIT;

    Это иллюстрация конфигурации, предполагающая существующую таблицу diagnostic_events; выполнение меняет данные. SET LOCAL действует до конца текущей транзакции.

    Для какого класса данных прием уместен? Для событий, которые можно восстановить или потеря небольшой свежей порции которых явно разрешена требованиями. Для финансового списания, подтвержденного внешнему миру, такой выбор обычно недопустим.

    8.4. Все пять режимов и граница темы¶

    В PostgreSQL 18 допустимы off, local, remote_write, on, remote_apply.

    Режим Локальное ожидание Дополнительное ожидание при настроенном синхронном standby
    off Не ждет обязательного локального flush Нет
    local Ждет локального WAL flush Нет
    remote_write Ждет локального WAL flush Подтверждение записи WAL в файловый слой standby
    on Ждет локального WAL flush Подтверждение flush WAL на standby
    remote_apply Ждет локального WAL flush Подтверждение применения записи на standby

    Если не настроены синхронные standby, local, remote_write, on и remote_apply имеют одинаковую локальную гарантию. Удаленные режимы упоминаются только для правильной интерпретации параметра; устройство репликации относится к другим курсам и здесь не раскрывается.

    У off есть исключения: некоторые операции, требующие особой согласованности с файловой системой (например DROP TABLE), а также подготовка двухфазной транзакции, выполняются синхронно независимо от выбранного режима. Поэтому нельзя считать synchronous_commit=off универсальной отменой всякого ожидания.

    8.5. Что измерять и чего нельзя обещать¶

    off может уменьшить задержку коротких транзакций, если значительную ее часть занимал WAL flush. Но если задержка определяется дорогостоящей работой до COMMIT, результат будет небольшим. И наоборот, успешный async COMMIT не равен долговечно подтвержденному результату, поэтому изменение политики может нарушить требования приложения даже при лучшем TPS.

    Вывод: synchronous_commit — явный выбор контракта подтверждения. Нельзя сравнивать производительность двух режимов, игнорируя различия их гарантий.

    9. Checkpoint: зачем сбрасывать страницы, если WAL уже долговечен¶

    9.1. Проблема бесконечного REDO¶

    Допустим, сервер работает месяц, каждый день записывает тысячи гигабайт WAL, а страницы данных никогда целенаправленно не синхронизирует. После сбоя для восстановления понадобилось бы воспроизвести огромную историю изменений.

    Контрольная точка (checkpoint) ограничивает этот долг. Она устанавливает такое состояние файлов данных, при котором для аварийного восстановления достаточно начать REDO с известного рубежа журнала.

    9.2. Что входит в checkpoint¶

    В общих чертах checkpointer:

    1. Определяет рубеж контрольной точки и набор изменений, которые необходимо учесть.
    2. Обеспечивает запись грязных страниц, относящихся к контрольному рубежу, с соблюдением WAL-инварианта.
    3. Обеспечивает требуемую синхронизацию файлов данных.
    4. Формирует checkpoint record и фиксирует информацию, необходимую для следующего старта recovery.

    В результате изменения до redo-рубежа этой контрольной точки гарантированно представлены в сохраненных data files так, что их не нужно повторно восстанавливать с более ранних WAL-записей. Важная тонкость: checkpoint record и его redo LSN могут указывать на разные позиции журнала. Глубокая организация этой процедуры — 07.3.

    9.3. Почему checkpoint не обязан остановить весь мир¶

    Проверка модели: если для checkpoint надо сбросить тысячи страниц, не получится ли большой скачок задержки?

    PostgreSQL старается распределять запись по времени, а не выполнять весь объем одновременно. На это влияет checkpoint_completion_target. При типичном значении 0.9 работа планируется на значительную часть интервала до следующей контрольной точки.

    Важно понимать компромисс: запись можно сгладить, но нельзя отменить потребность в физической записи накопленных dirty pages. И в конце checkpoint может потребоваться синхронизация файлов, которая создает заметный пик I/O.

    9.4. Когда запускается checkpoint¶

    В PostgreSQL 18 основные настройки:

    SHOW checkpoint_timeout;
SHOW max_wal_size;
SHOW checkpoint_completion_target;
SHOW checkpoint_warning;

    Ориентиры стандартной конфигурации: checkpoint_timeout = 5min, max_wal_size = 1GB, checkpoint_completion_target = 0.9. Контрольная точка может начинаться по времени либо по давлению объема WAL. max_wal_size — мягкая цель, а не гарантированный предел каталога pg_wal: реальный объем может ее превысить. При отсутствии новых WAL изменений очередной checkpoint может быть пропущен.

    9.5. Две противоположные крайности¶

    Очень частые checkpoint:

    • больше работы по синхронизации файлов;
    • больше повторных full-page images после новых контрольных точек;
    • чаще возможные всплески I/O;
    • потенциально меньше хвост WAL для последующего crash recovery.

    Очень редкие checkpoint:

    • меньше частых операций checkpoint и FPI на том же наборе страниц;
    • больше WAL между гарантированными рубежами;
    • потенциально длительное восстановление после сбоя;
    • другой профиль фоновой записи и использования дискового пространства.

    Следовательно, нельзя выбирать checkpoint_timeout только по одному показателю TPS. Это компромисс между обычной нагрузкой и будущей ценой восстановления.

    9.6. Bgwriter и checkpointer — две разные задачи¶

    bgwriter стремится снизить вероятность, что backend будет сам писать грязные буферы при их замещении. checkpointer должен завершить конкретную долговечную границу для файлов данных и ограничить будущий REDO. Первый оптимизирует доступность буферов, второй закрывает обязательство контрольной точки.

    9.7. Как измерять checkpoint в PG18¶

    SELECT
    num_timed,
    num_requested,
    num_done,
    buffers_written,
    write_time,
    sync_time
FROM pg_stat_checkpointer;

    Здесь num_timed и num_requested включают запросы checkpoint, которые могли быть пропущены; num_done отражает реально выполненные. write_time и sync_time описывают соответствующие фазы checkpoint/restartpoint, это не средняя задержка пользовательского COMMIT.

    Главная модель: checkpoint — управление максимальным долгом по восстановлению. Он оплачивает запись data pages сегодня, чтобы не пришлось воспроизводить слишком длинную историю WAL завтра.

    10. Crash Recovery: что происходит после внезапной остановки¶

    10.1. Сначала различим тип отказа¶

    Сбой одного backend-процесса и потеря питания всего сервера оставляют разные условия. При сбое процесса PostgreSQL может принять решение о перезапуске серверного окружения и восстановлении согласованного состояния. При остановке ОС исчезают ее кеши и volatile RAM. Если устройство надежно сохранило байты, достижимые через flush, PostgreSQL должен уметь восстановить согласованное состояние.

    Здесь предполагаем аварийную потерю памяти и сохранность тех байтов, которые накопитель честно подтвердил как долговечные.

    10.2. Откуда начинается REDO¶

    PostgreSQL использует сведения о последней пригодной контрольной точке и соответствующем redo LSN, затем последовательно читает требуемые WAL records. Для изменения страниц применяются redo-операции, восстанавливающие физическое состояние данных.

    Аварийное включение
       │
       ▼
Найти пригодную checkpoint-информацию
       │
       ▼
Получить redo LSN
       │
       ▼
Читать долговечный WAL в порядке записей
       │
       ▼
Применять требуемые изменения к страницам
       │
       ▼
Восстановить согласованное транзакционное состояние
       │
       ▼
Продолжить обычную работу

    За отправной точкой стоит файл pg_control и checkpoint record. Его бинарная структура и все состояния запуска относятся к 07.3.

    10.3. Почему можно повторять WAL без двойного применения¶

    На data page хранится page LSN. Если страница уже отражает данное изменение или более позднее, исполнитель REDO обычно может пропустить повторное применение этой записи к странице. Это один из механизмов идемпотентности восстановления физических изменений.

    Если страница старее, REDO применяет необходимые изменения. Если в WAL хранится full-page image, она также может восстановить целостное состояние страницы перед применением дальнейших изменений.

    10.4. Пример четырех временных точек сбоя¶

    Вернемся к переводу.

    Момент сбоя Что уже долговечно Ожидаемый результат после корректного recovery
    A. До устойчивого сохранения WAL изменений Нужных записей может не быть Незавершенная транзакция не подтверждается; ее изменения не могут считаться долговечными
    B. Изменения в WAL есть, COMMIT record еще не долговечен Физические изменения могут быть восстановимы, факт фиксации — нет Транзакция не считается успешно зафиксированной
    C. Commit record уже долговечен, data page еще старая WAL содержит необходимую историю и фиксацию REDO восстанавливает подтвержденные изменения
    D. Data page записана частично Нужны предшествующий WAL и механизм защиты страницы Full-page image позволяет исправить torn page при выполнении условий защиты

    Критически важно не говорить «все WAL-записи до сбоя — это все успешные транзакции». REDO восстанавливает физическую историю; транзакционная фиксация определяется отдельно.

    10.5. Почему не требуется общее физическое UNDO каждой страницы¶

    Физическая страница может содержать эффекты изменения, транзакция которого так и не была подтверждена. Для такого случая PostgreSQL использует модель видимости и состояния транзакций; незавершенные транзакции после recovery не превращаются в успешно зафиксированные.

    В рамках этой лекции важно следствие: нет необходимости перезаписывать все измененные страницы обратно в предыдущее физическое состояние с помощью отдельного классического UNDO-журнала. Механизм восстановления и транзакционные статусы совместно обеспечивают согласованность. Структуру MVCC повторно не разбираем.

    10.6. Сколько длится recovery¶

    Время зависит от расстояния между REDO-началом и концом долговечного WAL, количества записей, чтений страниц данных, CPU работы redo-операций, наличия FPI и производительности накопителя. Время восстановления не вычисляется как «размер WAL / скорость SSD» без учета операций со страницами и структуры журнала.

    В обычном режиме база платит за более частые checkpoint; в режиме аварии — за количество работы, оставшейся после последнего checkpoint. Эти расходы нельзя оптимизировать независимо.

    10.7. Что WAL не сможет восстановить¶

    Если отсутствует необходимый WAL record, накопитель испортил файл журнала, или хранилище ложно подтвердило синхронизацию, инвариант восстановления может оказаться нарушен. WAL — механизм восстановления на основании сохранившейся надежной истории, а не инструмент генерации утраченной информации.

    Инженерный вывод: crash recovery — последовательное REDO от известного рубежа на фоне различения физического состояния страниц и факта фиксации транзакций.

    11. full_page_writes: зачем WAL иногда содержит всю страницу¶

    11.1. Новая проблема: запись 8 КиБ не обязана быть атомарной¶

    Представим страницу данных размером 8 КиБ. ОС начала ее записывать на накопитель. Устройство успело сохранить первые секторы, затем питание пропало. На носителе осталась смесь старых и новых байтов.

    Нормальная страница: [старые 8 КиБ]
Новая страница:      [новые 8 КиБ]
Torn page:           [новые 4 КиБ | старые 4 КиБ]  (учебный пример)

    Это torn page, частично записанная страница. Граница разрыва не обязана приходиться ровно на 4 КиБ; она зависит от устройства и файловой подсистемы. Если WAL содержал только небольшое описание изменения, этого может быть недостаточно для восстановления всей внутренне согласованной страницы с перемешанными старыми и новыми байтами.

    11.2. Full-page image¶

    В PostgreSQL при full_page_writes=on при первом подходящем изменении страницы после checkpoint в WAL записывается полный образ страницы (full-page image, FPI). Если после аварии disk page оказалась частично записанной, можно восстановить целый образ страницы из WAL и затем применить последующие изменения.

    Почему после каждого checkpoint? Потому что восстановление начинается с контрольного рубежа. Нужен надежный образ первой измененной после него страницы; дальше обычные redo-изменения могут продвигать ее состояние.

    11.3. Временная линия одной страницы¶

    Checkpoint завершен
       │
       ├── первое изменение page A → WAL record + FPI(A)
       │
       ├── второе изменение page A → обычный WAL record (типично)
       │
       ├── третье изменение page A → обычный WAL record (типично)
       │
       └── следующий checkpoint → новый рубеж защиты

    Это учебная модель: точный выбор полного образа зависит от специфики WAL-регистрации страниц, page LSN, hint-bit updates и иных условий. Но утверждение «каждый UPDATE всегда журналирует 8 КиБ» неверно, как и обратное «WAL всегда содержит только несколько измененных байтов».

    11.4. Цена безопасности¶

    Пусть после checkpoint впервые изменились 100 000 разных страниц. Даже без учета сжатия и дополнительного содержимого это соответствует потенциальному масштабу:

    100 000 × 8192 байта = 819 200 000 байт ≈ 781,25 МиБ

    Это не прогноз полного WAL: FPI может исключать свободную область страницы, сжиматься и иметь накладные расходы, а перечень страниц зависит от поведения СУБД. Расчет нужен, чтобы почувствовать масштаб нагрузки от первого изменения множества страниц.

    При следующем checkpoint тот же массив страниц может снова потребовать FPI при следующем изменении. Значит, слишком частые checkpoint способны увеличить WAL traffic на рабочей нагрузке с большим набором изменяемых страниц.

    11.5. wal_compression¶

    SHOW full_page_writes;
SHOW wal_compression;

    Сжатие полных образов страниц снижает их размер в WAL, если данные хорошо сжимаются, ценой дополнительной CPU-работы при формировании и декодировании. В PostgreSQL 18 поддерживаются pglz, а при соответствующей сборке — lz4 и zstd. Вариант on исторически означает pglz.

    Эффект зависит от содержимого страниц: уже сжатые данные и случайные байты дают меньший выигрыш. Нельзя обещать фиксированный коэффициент сжатия.

    11.6. Почему нельзя просто выключить full_page_writes¶

    SHOW full_page_writes;

    При off PostgreSQL перестает обеспечивать штатную защиту от частично записанных страниц посредством FPI. При определенных гарантиях файловой системы и накопителя такой риск может решаться на нижнем уровне, но это требует доказанной атомарности. По умолчанию в PG18 full_page_writes = on; для рабочей базы необоснованно отключать его ради сокращения WAL опасно.

    Контрольные суммы помогают обнаруживать некоторые повреждения, но сами по себе не восстанавливают утраченную целую страницу. Подробную связь checksums и storage оставим 07.2.

    Главная модель: WAL нужен не только для последовательного повторения изменений. FPI защищает от ситуации, когда сама исходная дисковая страница оказалась физически неполной.

    12. Batch Commits и Group Commit: почему 1000 транзакций не требуют 1000 fsync¶

    12.1. Три похожих названия, три разных механизма¶

    Сначала разделим:

    1. Одна большая транзакция: приложение выполняет несколько INSERT/UPDATE и один COMMIT.
    2. Batch SQL: приложение передает несколько операций SQL эффективнее по протоколу, но это само по себе не гарантирует один COMMIT.
    3. Group Commit: несколько разных транзакций могут дождаться одного общего продвижения долговечного WAL.

    Нельзя подменять одно другим. В основной теме WAL нас особенно интересует третье.

    12.2. Единый журнал — условие для объединения синхронизаций¶

    Пусть три backend-процесса вставили commit records, заканчивающиеся на таких позициях:

    T1: COMMIT LSN = 0/100100
T2: COMMIT LSN = 0/100200
T3: COMMIT LSN = 0/100300

    Если синхронизация продвинула flush LSN до 0/100300, она покрыла все предшествующие позиции:

    flush LSN >= LSN(T3)
        ⇒ WAL до T1, T2 и T3 долговечен

    Поэтому трем транзакциям не обязательно запускать три отдельных аппаратных flush. Один процесс может выполнить синхронизацию до достаточно поздней границы, а остальные обнаружат, что их требования уже выполнены.

    12.3. Конкуренция может помочь группировке¶

    На небольшом числе последовательных транзакций каждое подтверждение может само инициировать синхронизацию. При наличии большого числа конкурентных коротких транзакций их WAL-записи могут накопиться до одной операции flush.

    Это неожиданная сторона конкуренции: при определенном профиле нагрузки средняя стоимость синхронизации на транзакцию уменьшается.

    Но общая нагрузка на WAL buffers, CPU, файловый слой и очередь ожиданий растет. Поэтому Group Commit не означает бесконечной масштабируемости TPS.

    12.4. commit_delay и commit_siblings¶

    SHOW commit_delay;
SHOW commit_siblings;

    commit_delay задает дополнительное ожидание перед инициированием WAL flush (в микросекундах). commit_siblings определяет минимальное число других активных транзакций, при котором PostgreSQL рассматривает такую задержку как потенциально полезную. При fsync=off задержка не используется.

    По умолчанию commit_delay = 0. Group Commit все равно может происходить естественным образом: общий лог и конкурентные запросы создают возможность разделить синхронизацию без искусственной паузы.

    Добавление commit_delay может увеличить throughput при достаточной конкуренции, но добавляет задержку в хвост отдельной транзакции. Его нельзя автоматически рекомендовать как ускорение.

    12.5. Числовая симуляция¶

    Учебные предположения:

    1000 транзакций
одна физическая синхронизация занимает 0,5 мс
один flush способен покрыть WAL 20 транзакций

    Если бы flush происходил отдельно на каждую транзакцию, суммарное время синхронизаций составляло бы:

    1000 × 0,5 мс = 500 мс

    При идеальных группах по 20:

    1000 / 20 = 50 flush
50 × 0,5 мс = 25 мс

    Мы уменьшили суммарное число и стоимость flush-операций. Но это не означает, что весь запрос завершится за 25 мс или TPS вырастет ровно в 20 раз. Остались обработка SQL, WAL insertion, CPU, ожидания, запись data pages и протокольная работа.

    12.6. Цена одной большой прикладной транзакции¶

    Может возникнуть идея объединить миллион изменений в один BEGIN ... COMMIT. При этом уменьшается число границ подтверждения и может улучшиться пакетная запись, но растут длительность транзакции и удерживаемые ею ресурсы, увеличивается объем работы до подтверждения, а откат крупной бизнес-операции меняет ее семантику. Управление транзакциями и блокировками детально рассматривалось или будет рассматриваться в других блоках; здесь фиксируем только принцип: уменьшение числа COMMIT не делает выполнение бесплатным.

    Главная модель: WAL — один упорядоченный поток; flush до поздней позиции покрывает ранние commit records, поэтому несколько транзакций могут разделить синхронизацию.

    13. Transaction Latency: как гарантия долговечности превращается в p95¶

    13.1. Из каких компонентов складывается задержка¶

    Теперь соберем весь путь от SQL до подтверждения:

    T_transaction = T_execute_updates
              + T_register_WAL
              + T_finish_transaction
              + T_wait_for_required_WAL_flush
              + T_client_response
              + другие необходимые накладные расходы

    Это учебная декомпозиция для поиска причины, а не точная формула измеряемых независимых фаз. Некоторые операции перекрываются по времени; другие выполняются внутри уже показанных. Сетевое ожидание, пул соединений и HTTP-обработка относятся к более широкой задержке backend-запроса, а здесь нас интересует цена завершения транзакции на стороне PostgreSQL.

    13.2. Секунды могут появиться после быстрых UPDATE¶

    Предположим, сами изменения записей заняли 2 мс, а ответ на COMMIT получен через 80 мс. Это не доказывает, что fsync именно этой транзакции длился 78 мс. Возможно:

    • WAL flush уже выполнялся другим процессом;
    • накопитель обслуживает конкурирующие операции записи data pages;
    • возникла очередь к сериализуемому ресурсу WAL;
    • совпали фазы checkpoint и пользовательского write workload;
    • приложение измеряет также сеть и ожидание соединения.

    Диагноз требует раздельно измерять генерацию WAL, файловые записи, синхронизации и общий путь транзакции.

    13.3. Наблюдение 1: сколько WAL генерирует кластер¶

    SELECT
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes::bigint) AS wal_generated,
    wal_buffers_full,
    stats_reset
FROM pg_stat_wal;

    Для PostgreSQL 18 эти столбцы подтверждены документацией:

    • wal_records — количество зарегистрированных WAL records;
    • wal_fpi — число полных образов страниц;
    • wal_bytes — объем сгенерированного WAL;
    • wal_buffers_full — события, когда запись WAL инициировалась из-за заполнения внутренних буферов.

    Это накопленная статистика всего кластера с момента сброса, а не текущий TPS или счетчик конкретной транзакции. Для анализа нагрузки нужны интервальные дельты, полученные между двумя моментами наблюдения.

    13.4. Наблюдение 2: что стоит write и fsync WAL в PG18¶

    В PostgreSQL 18 счетчики WAL I/O находятся в pg_stat_io:

    SELECT
    backend_type,
    context,
    writes,
    write_bytes,
    write_time,
    fsyncs,
    fsync_time
FROM pg_stat_io
WHERE object = 'wal'
ORDER BY backend_type, context;

    Значения write_time и fsync_time заполняются при включенном track_wal_io_timing. При выключенном измерении нули не означают, что работа физически бесплатна.

    SHOW track_wal_io_timing;

    Важное отличие от старых версий: поля wal_write, wal_sync, wal_write_time, wal_sync_time удалены из pg_stat_wal в PostgreSQL 18. Переносить старые диагностические запросы без адаптации нельзя.

    pg_stat_io показывает агрегированную работу по типам backend-процессов и контекстам. Его fsyncs нельзя отождествлять с числом команд COMMIT. У WAL есть также контекст init, в котором учитывается инициализация сегментов: при исследовании собственно записи/синхронизации журналов необходимо смотреть значение context.

    13.5. Наблюдение 3: checkpoint и фоновая запись¶

    SELECT
    num_timed,
    num_requested,
    num_done,
    write_time,
    sync_time,
    buffers_written
FROM pg_stat_checkpointer;

SELECT buffers_clean, maxwritten_clean, buffers_alloc
FROM pg_stat_bgwriter;

    Рост sync_time checkpointer не является прямой мерой ожидания одного COMMIT, но способен указывать на значительную конкурирующую нагрузку файловой подсистемы. Высокие значения maxwritten_clean показывают, что background writer регулярно достигал собственного предела очищения буферов.

    13.6. Наблюдение 4: WAL от конкретной операции¶

    В отдельном учебном экземпляре или безопасном окружении:

    EXPLAIN (ANALYZE, WAL, BUFFERS, TIMING OFF)
UPDATE accounts
SET balance = balance + 1
WHERE id = 42;

    Команда реально выполняет UPDATE. Для SELECT, не выполняющего WAL-логируемых изменений, отсутствие WAL records естественно. Для UPDATE в EXPLAIN можно увидеть записи WAL, FPI и общий объем WAL, но это не измеряет автоматически время долговечного COMMIT: измерение работы SQL и измерение подтверждения транзакции требуют раздельной интерпретации.

    13.7. Какая причина соответствует какому признаку¶

    Наблюдение Первая гипотеза Что проверить дальше
    Очень много wal_bytes Приложение создает большой поток зарегистрированных изменений Интенсивность обновлений, ширина изменений, FPI
    Растет wal_fpi Много первых изменений страниц после checkpoint Частоту checkpoint, долю FPI, сжатие WAL
    Растет wal_buffers_full При построении WAL приходится сбрасывать заполненные буферы Интенсивность вставки журнала, параметры wal_buffers, конкуренцию
    Высокие fsync_time и fsyncs в pg_stat_io для wal Дорогие синхронизации журнала Измерения по интервалам, storage, конкурентные commits
    Большой write_time для wal Высокая стоимость файловой записи WAL Пропускную способность I/O, объем WAL, файловый слой
    Растут num_requested, sync_time checkpoint Слишком частые или дорогие контрольные точки checkpoint_timeout, max_wal_size, график генерации WAL
    Высокая задержка при небольших WAL I/O Тормозит не только durable WAL Время выполнения SQL, конкуренцию и другие части транзакции

    Это таблица гипотез, а не способ установить причинность по одному накопленному счетчику. Измерения сравниваются на одинаковом интервале под сопоставимой нагрузкой.

    13.8. Throughput и latency: что происходит с ростом конкуренции¶

    Обозначим:

    • TPS — число завершенных транзакций в секунду;
    • latency — время от начала операции до полученного подтверждения;
    • p95 — порог, ниже которого укладывается 95% измерений;
    • concurrency — количество одновременно находящихся в системе операций.

    Пока конкуренции немного, дополнительная параллельность может помочь Group Commit — общий WAL flush обслуживает несколько транзакций. Но затем общий WAL-ресурс, CPU или storage насыщаются. Очередь ожидающих транзакций начинает расти, даже если число fsync на транзакцию продолжает уменьшаться.

    Учебная картина:

    Мало конкуренции:    TPS растет, p95 невысокий
Умеренная нагрузка:   группировка flush улучшает эффективность
Насыщение ресурса:    TPS почти не растет, p95 заметно увеличивается
Перегрузка:          очередь и хвост задержек растут резко

    Нельзя делать вывод о производительности по одному максимальному TPS. Для backend важны скорость и границы задержки под целевой конкурентной нагрузкой, причем с сохранением требуемого контракта durability.

    13.9. Почему отдельные настройки нельзя крутить независимо¶

    checkpoint_timeout влияет на частоту checkpoint и объем FPI; max_wal_size — на условия контрольной точки; synchronous_commit — на момент ответа клиенту; fsync — на фундаментальную надежность синхронизации; wal_compression — на объем WAL и CPU. Эти параметры воздействуют на разные компоненты.

    Плохой подход: увеличить все лимиты памяти, отключить fsync и назвать рост TPS оптимизацией. Так мы изменили требования к надежности и условия конкуренции, не установив настоящего узкого места.

    Правильный процесс: определить гарантию, установить симптом, измерить ограниченный ресурс, изменить одну обоснованную причину, повторить измерение на том же профиле нагрузки.

    Главная модель раздела: успешный COMMIT — конкретный контракт durable WAL; задержка определяется работой, необходимой для достижения этой границы, и состоянием конкурирующих ресурсов.

    14. Четыре временные линии: что именно выживает после аварии¶

    Это итоговая проверка всей лекции. Предполагаем обычное логируемое изменение постоянной таблицы, fsync=on, full_page_writes=on, исправную файловую систему и накопитель.

    14.1. Изменили RAM, но WAL еще не flush¶

    Data page на диске: старая
Shared buffer:        новая, dirty
WAL insert:           выполнен
WAL flush:            еще не достиг изменения
COMMIT:               не подтвержден

    Потеря питания уничтожит volatile-изменения. Успешного долговечного COMMIT не было. Страница данных не должна оказаться надежно записанной раньше ее WAL.

    14.2. WAL изменения flush, но commit record не flush¶

    WAL изменения:        долговечен
WAL COMMIT:           недолговечен либо отсутствует
Data page:            может быть старой или новой

    После recovery физические изменения могут быть восстановлены, но транзакция не считается подтвержденной. Это демонстрирует разделение WAL REDO и фиксации.

    14.3. WAL до COMMIT flush, но data page еще старая¶

    WAL изменения:        долговечен
WAL COMMIT:           долговечен
Data page:            старая

    Обычный успешный синхронный COMMIT уже вправе ответить клиенту. После сбоя REDO применит недостающие изменения; подтвержденная транзакция не должна исчезнуть.

    14.4. DATA page частично записана¶

    WAL с full-page image: долговечен
Data page:                torn write

    Recovery восстанавливает целое состояние страницы из подходящего FPI и необходимого хвоста WAL. Защита зависит от full_page_writes и корректного порядка WAL/data writes.

    Из этих четырех сценариев студент должен уметь объяснить, почему «COMMIT записывает страницу», «write равен fsync», «WAL хранит SQL» и «на диске не бывает незавершенных изменений» — неправильные объяснения работы PostgreSQL.

    16. Семь инженерных выводов¶

    1. WAL разрешает откладывать запись data pages. Для сохранения подтвержденных транзакций достаточно долговечной истории изменений и их фиксации, даже если сами страницы таблиц еще старые.
    2. shared_buffers и dirty pages отражают рабочую память, а не гарантию сохранения. Страницы могут записываться до или после COMMIT при соблюдении WAL-инварианта.
    3. WAL insert, write и flush — разные границы. Стандартная локальная долговечность COMMIT опирается на flush-позицию, а не на факт вставки записи в RAM или успешного write().
    4. synchronous_commit меняет контракт подтверждения, а fsync=off ломает защитный механизм. Эти настройки не взаимозаменяемы.
    5. Checkpoint сокращает стоимость будущего REDO ценой текущей файловой работы. Частота влияет также на число FPI и объем WAL.
    6. full_page_writes закрывает риск torn page. Краткое описание изменения может оказаться недостаточным, если физическая запись страницы оборвалась посередине.
    7. Group Commit уменьшает число необходимых синхронизаций на транзакцию, но не отменяет конкуренцию. Под нагрузкой нужно отдельно измерять WAL generation, WAL I/O, checkpoint и задержку ответа.
