    09.0. PostgreSQL Migrations, Backup & Connection Pooling¶

    Основная лекция магистратуры · PostgreSQL 18 · REL_18_STABLE · блок 9.
    Состав: ровно 14 согласованных тем: миграции (1–6), backup/restore (7–9), управление соединениями (10–14).
    Предыдущие блоки: SQL planner/executor, MVCC, блокировки, WAL, crash recovery и VACUUM уже изучены. Здесь обращаемся к их следствиям, не пересказывая механизмы.
    Оговорка о версиях: синтаксис и поведение PostgreSQL проверены по документации PostgreSQL 18; сведения о database/sql — по документации Go; особенности PgBouncer — по актуальной официальной документации. Схемы и расчеты с условными значениями являются учебными примерами, а не измерениями действующего сервера.

    0. Инцидент: миграция прошла, приложение запустилось, сервис недоступен¶

    Представим backend-сервис с таблицей orders на десятки миллионов строк. После релиза одновременно происходят три события. Новый код ожидает колонку external_id, которой нет на части экземпляров схемы. Миграционный скрипт добавляет индекс обычным CREATE INDEX, и запись заказов встает в очередь. Чтобы «помочь базе», мы увеличиваем число экземпляров приложения и размер каждого пула. После этого новые подключения упираются в max_connections. У нас есть ночной SQL-дамп, но команда восстановления на тестовом окружении ни разу не запускалась.

    В такой ситуации не помогает знание того, что ALTER TABLE меняет структуру таблицы, а pg_dump делает резервную копию. Нужно связать три эксплуатационных контракта:

    Релиз приложения ──> контракт схемы ──> допустимые изменения на живой БД
                                                  │
                                                  ▼
                                  контроль отказа и восстановление
                                                  │
                                                  ▼
                                поток запросов ──> ограниченный пул

    Первый контракт — совместимость. Старая и новая версии приложения могут одновременно работать с одной схемой. Второй — восстановимость. Данные можно вернуть в измеримое время и с приемлемой потерей. Третий — емкость соединений. Каждый экземпляр сервиса не должен бесконтрольно увеличивать количество серверных процессов PostgreSQL.

    Сегодня пройдем полный путь: подготовим безопасную миграцию, оценим цену DDL, создадим и проверим резервную копию, вычислим RPO/RTO, затем ограничим физические соединения и разберем, что делает PgBouncer. Вопросы из Lock Manager, VACUUM и WAL Internals считаем уже известными; здесь важны инженерные последствия.

    I. Миграции схемы: изменяем контракт работающей системы¶

    1. Database migrations: как координировать изменение схемы¶

    1.1. Почему «один SQL-файл» перестает быть простым¶

    На локальной машине миграция выглядит безобидно:

    ALTER TABLE orders ADD COLUMN external_id text;

    В production три сложности появляются одновременно. Первая: кто знает, применялась ли эта команда к конкретному окружению? Вторая: что делать, если мигратор потерял соединение после отправки COMMIT и не узнал результат? Третья: как избежать того, что два экземпляра приложения начнут выполнять миграции параллельно?

    Под миграцией базы данных будем понимать версионированное преобразование схемы и, иногда, данных, для которого зафиксированы порядок, ожидаемое состояние до/после, правила исполнения и восстановления после ошибки.

    Типичная таблица истории (ее схема зависит от инструмента):

    version description applied_at checksum status
    17 add external_id 2026-11-18 hash... success
    18 create orders index — hash... pending

    Название и наличие колонок не являются стандартом PostgreSQL. Это договоренность мигратора. Состояние success полезно только тогда, когда обновление истории корректно согласовано с самой операцией изменения схемы.

    1.2. Транзакционная миграция¶

    PostgreSQL поддерживает транзакционный DDL для множества операций:

    BEGIN;
ALTER TABLE orders ADD COLUMN external_id text;
INSERT INTO schema_migrations(version) VALUES ('017');
COMMIT;

    При ошибке до COMMIT изменения транзакции откатываются. Но есть исключения: например, CREATE INDEX CONCURRENTLY нельзя выполнять внутри явного transaction block. Поэтому требование «все миграции всегда оборачиваем в один BEGIN» неверно. Мигратор должен различать транзакционные и нетранзакционные шаги.

    Неопределенный результат — другая проблема. Клиент отправил COMMIT, затем сеть оборвалась. Коммит мог состояться либо не состояться. Повторная отправка команды без чтения фактического состояния опасна. Надежный порядок: подключиться заново → прочитать историю миграций и реальные объекты схемы → определить состояние → выполнить безопасную следующую операцию. Одной проверки IF NOT EXISTS иногда недостаточно: объект с таким именем может иметь не ту структуру.

    1.3. Кто единственный применяет миграцию¶

    Если у нас 20 экземпляров сервиса, запуск DDL из main() каждого экземпляра создает гонку при развертывании. Надежнее выделить миграции в отдельный контролируемый этап релиза либо использовать проверенный мигратор с координацией, блокировкой выполнения и таблицей состояния. Параллельно запускаемые экземпляры приложения должны уметь работать с переходной схемой.

    Инструменты golang-migrate, Goose и Flyway по-разному организуют версионирование, транзакции и блокировки. Для курса принцип важнее названия: DDL выполняется один раз в контролируемой последовательности, а ошибка оставляет диагностируемое состояние.

    1.4. Versioned и repeatable migrations¶

    Версионированная миграция (V017__...) выполняется согласно порядку и не должна незаметно менять смысл задним числом. Повторяемые миграции, где инструмент их поддерживает, используются для объектов, содержание которых допустимо обновлять при изменении файла (например, некоторых SQL-функций). Они не превращают любой разрушительный DDL в безопасно повторяемый.

    Нужно хранить примененный артефакт миграции вместе с версией приложения: у команды должны быть воспроизводимые сведения о том, какой именно SQL был запущен и на каком окружении.

    1.5. Production-цена и диагностика¶

    При зависшей миграции нас интересует не только статус скрипта. Смотрим, какой процесс сейчас выполняет команду, ждет ли она ресурс, какой запрос ее блокирует, сколько времени остается по лимитам, завершилась ли транзакция и какие каталоги/индексы появились. Инструменты блока 8 уже дают такой диагностический путь.

    Минимальный чек-лист перед запуском: оценка объема затрагиваемой таблицы; проверка совместимости обеих версий кода; таймаут на ожидание блокировки; отдельное окно наблюдения; способ повторного запуска; проверка результата SQL и метаданных; откат приложения без обязательного возврата схемы назад.

    Инженерный вывод. Миграция является частью протокола релиза. Надежность определяется контролем порядка и состояния, а не только правильным синтаксисом SQL.

    2. Schema as Contract: две версии приложения и одна база¶

    2.1. Где ломается модель «сначала поменяем БД, потом код»¶

    В production релиз обычно не атомарен. На одном сервере еще работает версия A, на другом уже запущена версия B. Обе пишут в ту же таблицу. Поэтому новая схема должна в течение переходного периода удовлетворять обоим клиентам.

    Пример. Старая версия читает и пишет customers.full_name. Новая хочет отдельно first_name, last_name.

    A (старая версия) ──── SELECT/UPDATE full_name ─────┐
                                                    ├── customers
B (новая версия) ──── SELECT/UPDATE first_name, ────┘
                                           last_name

    Если немедленно DROP COLUMN full_name, все оставшиеся экземпляры A сломаются. Если B сначала начнет читать только новые колонки без backfill, исторические записи окажутся пустыми.

    2.2. Контракт чтения и контракт записи¶

    Полезно составить матрицу:

    Версия кода Старая схема Переходная схема Финальная схема
    A: работает с full_name Да Да Нет
    B-переходная: понимает оба формата Нет/зависит от кода Да Да/зависит от кода
    C: только новые поля Нет Да, после переноса Да

    Здесь таблица — проектное обязательство. Для каждого выпуска нужно явно знать: какие колонки читаются, какие пишутся, допустимы ли NULL, какие ограничения уже работают и что случится при откате бинарника на предыдущую версию.

    Backward compatibility в миграции означает сохранение корректной работы старого приложения при применении новой схемы. Иногда дополнительно нужна forward compatibility переходной версии — способность читать еще не полностью перенесенные данные.

    2.3. Схема — это шире списка колонок¶

    Контракт включает типы, значения по умолчанию, проверки, уникальность, NOT NULL, допустимые значения enum/справочников, индексные предпосылки производительности и существование объектов. Особенно опасны изменения, которые внешне выглядят косметическими: переименование поля, сужение типа, изменение семантики NULL, ужесточение constraint.

    Изменение DEFAULT влияет на будущие вставки, но не переписывает автоматически значения старых строк. Это важно для постепенного релиза: старая версия, которая не указывает колонку в INSERT, может начать получать новое значение раньше переключения бизнес-логики.

    2.4. Откат бинарника ≠ откат данных¶

    После выкладки B часть пользователей уже записала новые данные. Если миграция удалила старую колонку или преобразовала тип с потерей информации, возврат к A не восстанавливает утраченное. Поэтому основной способ безопасного возврата часто состоит в откате приложения при сохранении расширенной схемы. Обратное преобразование данных требуется отдельно оценивать и тестировать.

    Инженерный вывод. Схема — публичный контракт для нескольких одновременно существующих версий приложения. Операции следует планировать по матрице совместимости, а не по желаемому окончательному DDL.

    3. Backward-Compatible Migrations: безопасные и опасные шаги¶

    3.1. Добавляем nullable-колонку¶

    ALTER TABLE customers ADD COLUMN first_name text;
ALTER TABLE customers ADD COLUMN last_name text;

    Новая структура не требует немедленного заполнения старых строк. Старая версия продолжает работать с full_name. Но приложение B обязано корректно читать NULL, пока данные не перенесены.

    3.2. DEFAULT — когда быстро, а когда дорого¶

    В PostgreSQL 18 добавление колонки с неволатильным DEFAULT обычно сохраняет вычисленное значение в метаданных. Старые строки физически не переписываются сразу:

    ALTER TABLE orders
  ADD COLUMN source text DEFAULT 'web';

    У новых строк значение задается обычным механизмом DEFAULT, а при чтении прежних строк PostgreSQL подставляет сохраненное значение. Это позволяет выполнить операцию быстро даже на большой таблице, хотя кратковременная блокировка DDL все равно нужна. Команда с волатильным DEFAULT вроде clock_timestamp() требует иной работы, вплоть до переписывания таблицы и индексов. Эта оптимизация — конкретное свойство PostgreSQL 18, а не универсальная гарантия любого DDL.

    Полезно различать:

    -- Не меняет старые строки:
ALTER TABLE orders ALTER COLUMN source SET DEFAULT 'api';

-- Может потребовать дорогой операции на большой таблице:
ALTER TABLE orders ADD COLUMN captured_at timestamptz
  DEFAULT clock_timestamp();

    3.3. Новые ограничения: проверку можно отделить от введения правила¶

    Если требуется начать проверять новый инвариант, часто можно отделить добавление ограничения от валидации исторических строк:

    ALTER TABLE orders
  ADD CONSTRAINT orders_total_nonnegative
  CHECK (total_amount >= 0) NOT VALID;

-- Исправляем старые нарушения отдельной контролируемой операцией.

ALTER TABLE orders
  VALIDATE CONSTRAINT orders_total_nonnegative;

    После первого шага новые и обновляемые строки должны удовлетворять правилу. Исторические данные еще не проверены целиком. VALIDATE CONSTRAINT проверит существующие строки отдельно, используя совместимый с обычными изменениями режим блокировки (SHARE UPDATE EXCLUSIVE для соответствующей таблицы). При этом сканирование все равно потребляет I/O и CPU.

    Новое в PostgreSQL 18: NOT VALID поддерживается также для ограничений NOT NULL. Поэтому возможен поэтапный вариант:

    ALTER TABLE orders
  ADD CONSTRAINT orders_external_id_nn
  NOT NULL external_id NOT VALID;

-- Предварительно заполнить external_id в существующих строках.

ALTER TABLE orders
  VALIDATE CONSTRAINT orders_external_id_nn;

    Применимость синтаксиса и план блокировок проверяем на целевой PostgreSQL 18; на старых версиях аналогичный подход строился, например, через валидный CHECK (col IS NOT NULL) и последующий SET NOT NULL.

    3.4. Переименование колонки — несовместимый контракт¶

    ALTER TABLE customers RENAME COLUMN full_name TO display_name;

    Само изменение каталога может быть быстрым, но старый код, продолжавший использовать full_name, немедленно начинает падать. Время выполнения DDL не отражает риск релиза. Более безопасная стратегия для длинного окна совместимости — добавить новое поле, перенести данные, переключить код и только затем удалить старое.

    3.5. Изменение типа и сужение допустимых значений¶

    bigint → integer, text → varchar(16), изменение numeric scale/precision, ужесточение NOT NULL — требуют отдельного анализа существующих данных и поведения обеих версий. Некоторые преобразования типов могут пройти без rewrite, но многие требуют переработки физического представления таблицы. Избегаем правила «ALTER TYPE всегда быстро» и столь же неверного «ALTER TYPE всегда переписывает таблицу».

    Инженерный вывод. Безопасная миграция — последовательность маленьких совместимых шагов с проверками инвариантов. Даже метаданные, изменяемые за миллисекунды, могут нарушить контракт приложения.

    4. Expand / Migrate / Contract: безопасный переход с full_name на два поля¶

    4.1. Почему три слова не являются алгоритмом сами по себе¶

    Expand → Migrate → Contract часто рисуют как три блока. Но между первым и третьим блоком приложения продолжают писать данные. У нас возникает гонка: backfill прочитал старый full_name, клиент изменил его через старый API, а backfill позднее записал уже устаревшие first_name/last_name. В результате база не падает и SQL не возвращает ошибки, но данные расходятся.

    Поэтому протокол должен задавать источник истины для каждого этапа, правило записи, способ повторной обработки и условие переключения чтения.

    4.2. Фаза Expand: добавляем поля и совместимый код¶

    ALTER TABLE customers ADD COLUMN first_name text;
ALTER TABLE customers ADD COLUMN last_name text;

    Пока старая версия использует только full_name, новая переходная версия должна принимать старый формат и, если бизнес-семантика допускает, формировать оба представления. Простое разделение произвольного полного имени по пробелу нельзя выдавать за корректное для всех языков и фамилий преобразование: это отдельная предметная задача. Для учебного алгоритма предположим, что правила преобразования определены и проверены бизнесом.

    Дальше необходимо выбрать стратегию источника истины:

    • Переходная двойная запись в одной транзакции. Код при изменении имени сохраняет full_name, first_name, last_name согласованно. Обе версии кода должны оставаться совместимыми с этим форматом. Если старая версия продолжает писать только full_name, одной новой двойной записи недостаточно: нужен механизм синхронизации или ограничение окна сосуществования.
    • Временное представление через чтение из старого поля. Пока исторические строки не перенесены, новая версия строит ответ из full_name, если новые поля пусты; чтение новых колонок включается позже.
    • Вынесенная синхронизация. В отдельных архитектурах согласование обеспечивается триггером либо другим управляемым механизмом. Это повышает сложность и требует отдельной проверки порядка и ошибок.

    Выбор зависит от возможности изменить все писатели одновременно. Нельзя заявлять, что «dual-write решает все», если старые экземпляры продолжают записывать только одну сторону контракта.

    4.3. Фаза Migrate: ограничиваем стоимость backfill¶

    На таблице в 80 млн строк такой SQL может создать огромную транзакцию:

    UPDATE customers
SET first_name = ..., last_name = ...
WHERE first_name IS NULL;

    Он создаст много новых версий, увеличит WAL, удержит ресурсы до завершения, а при ошибке откатит большое количество работы. Правильнее переносить данные небольшими порциями с ключом прогресса и наблюдением за задержками.

    Учебный шаблон (правило выделения имен обозначено условной функцией; не запускайте без определения этой функции):

    -- УЧЕБНЫЙ ПСЕВДО-SQL: parse_name(...) — бизнес-функция,
-- которая в реальной системе должна быть определена заранее.
WITH batch AS (
    SELECT id
    FROM customers
    WHERE id > :last_id
    ORDER BY id
    LIMIT 1000
)
UPDATE customers AS c
SET first_name = parse_name(c.full_name).first,
    last_name  = parse_name(c.full_name).last
FROM batch AS b
WHERE c.id = b.id
  AND c.first_name IS NULL;

    Для воспроизводимого исполняемого примера с простым преобразованием возьмем таблицу, где значение уже подготовлено в отдельном столбце:

    -- Транзакция одной небольшой порции; :from_id/:to_id задает приложение.
UPDATE customers
SET first_name = staging_first_name,
    last_name  = staging_last_name
WHERE id >= $1 AND id < $2
  AND first_name IS NULL AND last_name IS NULL;

    Интервалы по id удобны для возобновления, но не обязательно покрывают строки, вставленные позднее в «старый» интервал. Поэтому после основного прохода необходим повторный контроль остатка и правило синхронизации конкурентных записей.

    Ключевые ограничения на batch: число обработанных строк; максимальная длительность одной транзакции; интенсивность записи WAL; влияние на рабочие запросы; состояние репликации, если она используется; место на диске; возможность остановить и продолжить. Объем порции выбирается измерением, а не универсальной константой 1000.

    4.4. Гонка между backfill и клиентской записью¶

    T1  Backfill читает full_name = 'A B'
T2  Приложение меняет full_name = 'C D'
T3  Backfill сохраняет first_name='A', last_name='B'
T4  Новая версия читает 'A B', хотя full_name уже 'C D'

    Если batch читает значения и обновляет их в одной SQL-команде, вычисление происходит по версиям и блокировкам этой команды, но это не отменяет проблем с параллельной логикой на разных представлениях. Для строгой корректности нужен согласованный протокол: например, единственный источник истины в переходном периоде и атомарное обновление обоих представлений, либо версия записи и проверка актуальности на момент применения backfill. Конкретный вариант определяется бизнес-инвариантами.

    4.5. Условие переключения чтения¶

    Нельзя переключать код только потому, что миграционный скрипт вернул UPDATE N. Перед переключением проверяем:

    SELECT count(*) AS not_migrated
FROM customers
WHERE first_name IS NULL OR last_name IS NULL;

    Такая проверка осмысленна, только если NULL в новых колонках по контракту запрещен для всех записей. Если бизнес допускает неполное имя, нужен другой признак завершения. Далее проверяются расхождения между старым и новым представлениями, а также продолжающиеся писатели старого формата.

    4.6. Contract: последним шагом удаляем старый контракт¶

    Только когда все версии приложения и вспомогательные процессы перестали читать/писать full_name, можно планировать:

    ALTER TABLE customers DROP COLUMN full_name;

    Удаление колонки не обязательно немедленно вернет место файловой системе: PostgreSQL 18 обычно помечает колонку невидимой и постепенно избавляется от старого физического содержимого при переписывании версий строк. Указание «потом DROP COLUMN» не означает «после DROP размер heap уменьшится на размер поля».

    4.7. Реальный rollback¶

    При ошибке новой версии во время Migrate обычно откатывают приложение к совместимой версии, оставляя новые поля. Если новый код уже писал данные только в новый формат и старое поле осталось без обновлений, возврат к старому бинарнику может быть невозможен без обратной синхронизации. Поэтому проверка rollback — обязательная часть протокола, а не импровизация после инцидента.

    Инженерный вывод. Expand/Migrate/Contract — протокол согласованного изменения двух контрактов во времени. Самая тяжелая часть — корректность одновременных записей и критерий завершения переноса.

    5. Dangerous ALTER TABLE: почему стоимость DDL непредсказуема по длине SQL¶

    5.1. Три класса операций¶

    Первый класс — metadata-only: изменение системных каталогов без физического обхода всех строк. Второй — validation scan: чтение большой таблицы ради проверки ограничения. Третий — table rewrite: создание нового физического представления таблицы, перенос строк и обслуживание зависимых структур. Реальная операция может объединять несколько этих работ.

    Изменение PostgreSQL 18 Типичная физическая цена Важная оговорка
    ADD COLUMN без сложных ограничений Метаданные Краткий сильный lock все равно возможен
    ADD COLUMN DEFAULT 'x' Метаданные Если default неволатильный
    ADD COLUMN DEFAULT clock_timestamp() Rewrite Волатильное значение для существующих строк
    SET DEFAULT Метаданные Не исправляет старые строки
    DROP COLUMN Обычно метаданные Размер файла сразу не уменьшается
    ADD CONSTRAINT CHECK (...) Проверка данных NOT VALID отделяет валидацию
    ALTER COLUMN TYPE Часто rewrite Есть бинарно-совместимые исключения
    SET NOT NULL Обычно проверка данных В PG18 можно разделить ввод и validation

    Это типичные механизмы из документации, не полная матрица блокировок. Отдельные формы ALTER TABLE имеют специальные правила и исключения.

    5.2. Почему быстрое DDL может задержать весь сервис¶

    Допустим, само изменение каталога занимает 2 мс, но ему нужен ACCESS EXCLUSIVE. Старый запрос удерживает конфликтующий lock 20 секунд. DDL встает в очередь. Новые запросы, конфликтующие с ожидающим DDL, тоже могут начать ожидать. Получается каскад задержек от операции, физическая работа которой ничтожна.

    Нагрузка выглядит так:

    S1: длительный SELECT ─────────────────────────── COMMIT
S2:               ALTER TABLE → WAIT ───── RUN ── COMMIT
S3:                        SELECT → WAIT ───────── RUN
S4:                        UPDATE → WAIT ───────── RUN

    Сами режимы блокировок мы уже разбирали в 08.2. Здесь достаточно инженерного следствия: время ожидания DDL определяется транзакциями вокруг него, а не только числом измененных байтов.

    Для ограниченного ожидания можно использовать:

    BEGIN;
SET LOCAL lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN source text;
COMMIT;

    Если блокировка не получена вовремя, транзакция откатится с ошибкой. Это полезнее, чем оставлять миграцию в неопределенно долгой очереди. Но lock_timeout не ограничивает время всех вычислений; для ограничения времени команды отдельно существует statement_timeout с собственной семантикой.

    5.3. Rewrite и временное место¶

    Таблица в 400 ГиБ не меняется «на месте» просто потому, что SQL короткий. Операция rewrite может потребовать новый heap и перестроенные индексы, дополнительные записи и I/O. Во время такого преобразования может временно потребоваться объем места, сопоставимый с размером старых объектов, и заметные ресурсы для WAL/других операций. Нельзя закладывать правило «есть еще 10 ГиБ свободно, значит хватит».

    В PostgreSQL документация отдельно отмечает, что rewrite формы ALTER TABLE имеют MVCC-оговорки: для транзакций с ранее взятым snapshot переписанная таблица может выглядеть пустой. Это редкая, но важная эксплуатационная граница: такие изменения требуют тестирования окна совместимости и поведения долгоживущих транзакций.

    5.4. DROP COLUMN: почему диск не освободился¶

    Удаление колонки из логической схемы не означает, что PostgreSQL переписал все физические tuples. Старое место может сохраняться до появления новых версий строк или отдельного rewrite. Требование уменьшить физический размер сразу — отдельная дорогая операция с другим профилем блокировок и I/O.

    5.5. Как оценить риск до запуска¶

    На целевой базе смотрим размер таблицы и индексов:

    SELECT
    pg_size_pretty(pg_relation_size('orders')) AS heap,
    pg_size_pretty(pg_indexes_size('orders')) AS indexes,
    pg_size_pretty(pg_total_relation_size('orders')) AS total;

    Проверяем SQL-операцию на тестовой БД сопоставимого размера и распределения данных; фиксируем блокировки, объем изменения файлов, длительность и I/O. Для production заранее составляем список «что считать успехом» и «при каких признаках остановиться».

    Инженерный вывод. Риск DDL складывается из совместимости схемы, блокировки, объема физической работы и условий конкурентной нагрузки. Время одиночного выполнения на пустой таблице не переносится в production.

    6. CREATE INDEX CONCURRENTLY: индекс без длительного запрета записи¶

    6.1. Почему обычный CREATE INDEX мешает работе сервиса¶

    В таблице orders нет индекса по customer_id. Планировщик вынужден делать дорогие чтения. Кажется, достаточно выполнить:

    CREATE INDEX orders_customer_idx ON orders(customer_id);

    Но обычное построение индекса на живой таблице блокирует конкурентные модификации строк до завершения создания. Если операция займет 40 минут, backend-сервис может потерять возможность принимать заказы. При этом обычные читатели обычно продолжают выполнять SELECT.

    CREATE INDEX CONCURRENTLY специально снижает это ограничение:

    CREATE INDEX CONCURRENTLY orders_customer_idx
ON orders(customer_id);

    Конкурентные INSERT, UPDATE, DELETE продолжаются, но построение дороже и требует нескольких транзакционных стадий.

    6.2. Почему нужно больше одного прохода¶

    Пока мы строим индекс, таблица меняется. Одного сканирования недостаточно, чтобы гарантировать полноту результатов на границе старых и новых версий. Документация PostgreSQL 18 описывает два сканирования таблицы с ожиданиями транзакций до/после соответствующих фаз.

    Упрощенная временная схема:

    Регистрация индекса INVALID
          │
          ▼
Ожидание старых изменяющих транзакций
          │
          ▼
Скан №1 (строим индекс; DML продолжается)
          │
          ▼
Ожидание соответствующих транзакций
          │
          ▼
Скан №2 (дополняем индекс)
          │
          ▼
Ожидание необходимых старых снимков
          │
          ▼
Помечаем индекс VALID

    Точные ожидания зависят от формы индекса и снимков; формальная последовательность и флаги каталогов будут предметом 09.1. Здесь принцип: меньше блокировки записи означает больше координации и дополнительное I/O.

    6.3. Нельзя внутри BEGIN миграции¶

    BEGIN;
CREATE INDEX CONCURRENTLY orders_customer_idx ON orders(customer_id);
-- ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block

    Поэтому создаем отдельный нетранзакционный шаг, а мигратор должен фиксировать его результат отдельно. Смешивать его в одном миграционном файле с транзакционными операциями без понимания поведения инструмента опасно.

    6.4. Ошибка оставляет INVALID index¶

    При нарушении уникальности, deadlock или иной ошибке PostgreSQL может оставить в каталоге невалидный индекс, который еще занимает место и может создавать стоимость обновления. Для уникального индекса важно еще хуже: уникальность может начать проверяться раньше, чем весь индекс будет объявлен валидным. Некоторые ошибки уникальности могут появляться у других транзакций уже во время построения.

    Проверить состояние:

    SELECT
    c.relname AS index_name,
    i.indisvalid,
    i.indisready,
    pg_size_pretty(pg_relation_size(c.oid)) AS index_size
FROM pg_index AS i
JOIN pg_class AS c ON c.oid = i.indexrelid
WHERE i.indrelid = 'orders'::regclass;

    При невалидном индексе сначала устанавливаем, что именно произошло и не используется ли объект другой операцией. Типовой путь — DROP INDEX CONCURRENTLY (тоже вне transaction block), затем исправление причины и повторное создание; для ряда случаев возможен REINDEX INDEX CONCURRENTLY.

    6.5. Наблюдаем прогресс¶

    SELECT
    pid, relid::regclass AS table_name,
    index_relid::regclass AS index_name,
    command, phase,
    blocks_total, blocks_done,
    tuples_total, tuples_done,
    lockers_total, lockers_done
FROM pg_stat_progress_create_index;

    Не следует трактовать blocks_done / blocks_total как общий процент завершения всей команды: фазы различаются, а ожидания транзакций могут занимать существенную часть общего времени.

    Инженерный вывод. CONCURRENTLY защищает сервис от длительной остановки DML, но увеличивает стоимость работы и добавляет состояния частичной готовности. В production нужна отдельная стратегия мониторинга и восстановления после ошибки.

    Резюме раздела I¶

    1. Миграции — упорядоченный протокол с явным состоянием применения.
    2. Совместимость определяется одновременно работающими версиями приложения.
    3. Безопасная миграция отделяет расширение схемы, перенос данных и удаление старого контракта.
    4. Дороговизна DDL определяется не только объемом данных, но и очередью блокировок.
    5. CREATE INDEX CONCURRENTLY позволяет записи продолжаться, однако требует нескольких проходов, отдельных транзакционных стадий и обработки INVALID индекса.

    II. Backup & Restore: копия есть, но можно ли вернуть сервис?¶

    7. pg_dump: согласованный логический снимок работающей базы¶

    7.1. Снимок не означает копирование файлов PostgreSQL¶

    После миграции произошла ошибка приложения и удалены важные данные. Нашей команде говорят: «Ночью делался pg_dump; восстановимся». Начнем с вопроса: что конкретно сохранил pg_dump?

    pg_dump экспортирует логическое определение объектов и данные одной базы. В формате plain это SQL-команды для воссоздания объектов и данных. В архивных форматах сохраняется структура, которую способен интерпретировать pg_restore. pg_dump не копирует побайтно файлы heap, B-tree, системные страницы и текущий WAL; это важное отличие от физической резервной копии.

    # Plain SQL: удобно читать, восстанавливается через psql.
pg_dump -h db.internal -U backup_user -d appdb \
  --format=plain --file=/backup/appdb.sql

# Custom archive: гибкое восстановление через pg_restore.
pg_dump -h db.internal -U backup_user -d appdb \
  --format=custom --file=/backup/appdb.dump

# Directory archive: пригоден для параллельного dump.
pg_dump -h db.internal -U backup_user -d appdb \
  --format=directory --jobs=4 --file=/backup/appdb.dir

    В примерах /backup — отдельное безопасное хранилище с достаточным местом, а способ передачи пароля должен быть безопасным (например, настроенная аутентификация или защищенный .pgpass, без пароля в командной строке).

    7.2. Как снимок остается согласованным при конкурентных UPDATE¶

    Во время выгрузки приложение продолжает вставлять, обновлять и удалять строки. pg_dump использует транзакционный согласованный snapshot: каждая таблица читается в согласованном логическом состоянии. Существующие записи могут меняться в live-базе, но выгрузка строится по определенным правилам видимости. Не требуется останавливать все пользовательские транзакции только ради логического снимка.

    Однако это не означает полного отсутствия блокировок. Выгрузка захватывает необходимые блокировки отношений, которые могут конфликтовать с DDL. При параллельном dump есть отдельная защита от опасной очереди блокировок: worker использует NOWAIT при повторном получении подходящего lock; при конфликте с ожидающим exclusive DDL выгрузка может завершиться ошибкой вместо вечного ожидания.

    Также согласованность snapshot ограничена базой и видом экспортируемых объектов. Отдельные внешние системы, очереди сообщений, данные файлового хранилища и содержимое других БД не становятся атомарно согласованными с SQL-дампом сами собой.

    7.3. Форматы и цена выбора¶

    Формат Команда Основной плюс Основное ограничение
    Plain -Fp Читаемый SQL; psql Меньше гибкости при выборочном/параллельном restore
    Custom -Fc TOC, выборочный restore, -j при восстановлении Не является обычным SQL-текстом
    Directory -Fd Параллельный dump и restore; несколько файлов Нужно сохранять каталог целиком
    Tar -Ft Архив в одном файле Ограничения parallel/избирательного восстановления

    pg_dump -j N создает leader-соединение плюс соединения workers, использует синхронизированные snapshot и увеличивает нагрузку на PostgreSQL и storage. Параллельный dump поддерживается для directory format. Нельзя путать количество jobs с безопасным уровнем параллелизма на загруженной машине.

    7.4. Почему pg_dump не сохраняет весь кластер¶

    pg_dump работает с одной БД. Роли, tablespaces и ряд глобальных объектов принадлежат уровню кластера. Для их выгрузки используется, например:

    pg_dumpall -h db.internal -U admin_user --globals-only \
  --file=/backup/globals.sql

    Даже с pg_dumpall нужно отдельно учитывать конфигурацию инстанса, секреты, сертификаты, внешние расширения и системные зависимости. Восстановить SQL без роли-владельца или требуемого extension может оказаться невозможно без подготовки окружения.

    7.5. В какой момент backup считается завершенным¶

    Успешный exit code pg_dump подтверждает, что утилита завершила экспорт согласно своей логике. Еще нужно проверить существование и доступность результата, целостность передачи в защищенное хранилище, политику хранения, права доступа и возможность выполнения pg_restore/psql. Заголовок или размер файла не доказывают, что все бизнес-данные потом восстановятся корректно.

    Инженерный вывод. pg_dump создает согласованную логическую выгрузку одной БД. Он полезен для переноса, выборочного восстановления и некоторых сценариев backup, но не заменяет физическое резервное копирование с WAL-архивированием при строгих RPO/RTO.

    8. pg_restore: восстановить объекты — только половина задачи¶

    8.1. Чем отличается SQL-скрипт от архива¶

    Plain dump — SQL-текст, поэтому обычно используется:

    createdb -h restore-db.internal -U restore_user appdb_test
psql -h restore-db.internal -U restore_user -d appdb_test \
  -v ON_ERROR_STOP=1 -f /backup/appdb.sql

    Custom/directory dump передаем pg_restore:

    pg_restore -h restore-db.internal -U restore_user \
  -d appdb_test --exit-on-error \
  /backup/appdb.dump

    Использование --exit-on-error важно для автоматизации: без явного режима остановки некоторые ошибки могут накапливаться, а восстановление продолжать выполнять другие объекты.

    8.2. TOC: почему порядок важен¶

    Архив содержит table of contents (TOC) — список восстанавливаемых объектов и их зависимостей. Для простого понимания удобно разделить работу на три стадии:

    PRE-DATA: схемы, типы, таблицы, функции, базовые определения
     │
     ▼
DATA:     загрузка строк / COPY / большие объекты
     │
     ▼
POST-DATA: индексы, триггеры, многие ограничения

    Восстанавливать индекс на пустой таблице и затем вставлять миллион строк часто дороже, чем загрузить данные и построить индекс после. Но точный порядок выбирается механизмом зависимостей архива и опциями восстановления.

    Посмотреть TOC:

    pg_restore --list /backup/appdb.dump > /backup/toc.list

    Выборочный restore возможен через --table, --schema, --section, --use-list. Здесь нужна дисциплина: восстановление только одной таблицы может не восстановить все объекты, от которых она зависит. Перед запуском проверяем содержимое выбранного набора и подготовку целевой БД.

    8.3. Параллельный restore: быстрее, но дороже¶

    pg_restore -h restore-db.internal -U restore_user \
  -d appdb_test --jobs=6 --exit-on-error \
  /backup/appdb.dump

    -j поддерживается для custom и directory архивов с подходящим входом. Сильное увеличение jobs повышает одновременно потребление CPU, I/O, памяти и числа подключений. Если storage насыщен или идет конкуренция за один объект, ускорение перестает быть линейным.

    Отдельное условие: --jobs нельзя комбинировать с --single-transaction. Это не ограничение конкретного драйвера: параллельные workers используют разные соединения, а единая транзакция охватывает одно соединение.

    8.4. Три режима транзакционного восстановления¶

    По умолчанию pg_restore выполняет команды в отдельных транзакциях. Вариант:

    pg_restore -d appdb_test --single-transaction \
  --exit-on-error /backup/appdb.dump

    дает all-or-nothing для выполняемых команд, но удерживает множество блокировок и создает длинную транзакцию; для большой БД этот вариант может быть дорогим или непрактичным.

    PostgreSQL 18: есть также --transaction-size=N, который объединяет команды восстановления в группы до N объектов, например:

    pg_restore -d appdb_test --transaction-size=1000 \
  --exit-on-error /backup/appdb.dump

    Это компромисс между числом транзакций и объемом удерживаемых ресурсов. Данный режим не превращает весь restore в одну атомарную операцию: если один из поздних batches завершился ошибкой, предыдущие могли быть уже зафиксированы. Для продакшн-восстановления выбираем целевую отдельную БД/кластер и явно проверяем результат.

    8.5. --clean, --if-exists, ownership¶

    pg_restore --clean --if-exists --no-owner --no-acl \
  -d appdb_test /backup/appdb.dump

    --clean формирует удаления объектов, подлежащих восстановлению. Если направить такую команду в живую рабочую БД, последствия могут быть разрушительными. --if-exists уменьшает шум некоторых удалений, но не делает операцию безопасной. --no-owner/--no-acl меняют восстановление собственников и прав: после них нужно восстановить правильный эксплуатационный контракт безопасности.

    8.6. Проверка после восстановления¶

    Нельзя завершать процедуру на сообщении «pg_restore finished». Нужны технические и бизнес-проверки:

    SELECT count(*) FROM orders;
SELECT min(created_at), max(created_at) FROM orders;
SELECT count(*) FROM orders WHERE customer_id IS NULL;

    Но сами по себе эти SQL-примеры только иллюстрируют проверки; реальные условия должны отражать инварианты конкретного приложения. Дополнительно проверяем доступ приложений, расширения, ограничения, индексы, права ролей, выполнение бизнес-сценариев, фактическое время восстановления и отсутствие критических ошибок в логах.

    После массового восстановления может потребоваться актуализация статистики планировщика; это эксплуатационная операция, а не замена проверки данных.

    Инженерный вывод. Restore — реконструкция зависимой схемы и данных под нагрузкой на ресурсы. Критерий успеха — работающее приложение с проверенными инвариантами, а не отсутствие ошибок у одной команды.

    9. RPO / RTO: что обещает команда эксплуатации¶

    9.1. Два разных измерения потери¶

    RPO (Recovery Point Objective) — максимальная допустимая потеря подтвержденных бизнес-данных по времени. RTO (Recovery Time Objective) — максимально допустимое время возвращения сервиса в работоспособное состояние.

    Представим: авария в 15:00, последний пригодный снимок 01:00. Если восстановление из него дает состояние на 01:00, фактическая потенциальная потеря достигает 14 часов. Даже если копия переносится за 10 минут, RPO этой стратегии не становится 10 минутами.

    И наоборот: резервные копии могут позволять восстановление почти к моменту аварии благодаря непрерывному WAL-архивированию, но возврат большого кластера и проверка приложений займут часы. Тогда хорошее RPO соседствует с плохим RTO.

    9.2. Считаем на конкретном примере¶

    Цель:   RPO <= 5 мин, RTO <= 45 мин.
Авария: 15:00.
Последняя ночная логическая копия: 02:00.
Проверенный restore: 2 ч 10 мин.

    Ночная выгрузка одна не выполняет ни RPO, ни RTO. Нужно менять технологию и частоту защиты данных, производительность восстановления либо договоренность с бизнесом. Даже выгрузка каждые 5 минут могла бы оказаться непригодной для большой БД из-за стоимости и длительности самой операции.

    Для строгих требований PostgreSQL предоставляет физическую копию кластера с нужным диапазоном архивированного WAL и PITR. Эти инструменты позволяют восстанавливать согласованное состояние до выбранной точки, но доступность всех необходимых WAL-файлов и корректность цепочки backup становятся частью гарантии. Внутренний алгоритм REDO мы уже изучали в блоке 7.

    9.3. Логический, физический и непрерывный backup¶

    Механизм Что сохраняет Для чего подходит Главная граница
    pg_dump Логические объекты/данные одной БД Перенос, выборочное восстановление Не обеспечивает PITR по WAL
    pg_basebackup Физические файлы кластера и связанные данные Восстановление кластера, база для PITR Зависит от корректности physical backup и WAL
    Incremental physical backup Измененные блоки относительно предыдущих копий Снижение объема больших копий Требует всю цепочку и pg_combinebackup
    WAL archiving + physical base backup Базовая копия плюс последовательный WAL Восстановление к заданной точке Пропущенный требуемый WAL нарушает восстановление

    PostgreSQL 18 поддерживает инкрементальные физические backup через pg_basebackup --incremental; инкрементальную копию нельзя запускать как полноценный кластер, пока не сформирован synthetic full через pg_combinebackup из полного набора зависимостей. Для проверки физической копии предусмотрен pg_verifybackup. Эти средства изучим глубже в 09.2, сейчас важно понимать принцип и границы.

    9.4. Приближенная оценка RTO¶

    Реальное время восстановления можно разложить:

    [ T_{RTO} \approx T_{discover} + T_{prepare} + T_{copy} + T_{restore} + T_{replay} + T_{verify} + T_{switch}. ]

    Для логического restore часто доминируют загрузка данных и построение индексов. Для физического могут доминировать копирование файлов и replay накопленного WAL. Параметры схемы, размер архивов, скорость сети/storage и число workers меняют соотношение.

    Если нужно передать 800 ГиБ при реальных 400 МиБ/с, даже идеальное только копирование занимает примерно:

    [ 800 \cdot 1024 / 400 = 2048\text{ с} \approx 34\text{ мин}. ]

    Это нижняя оценка для данного ограниченного этапа, не полный RTO. Учитываем сеть, распаковку, обработку файлов, replay, верификацию и переключение трафика.

    9.5. Резервная копия должна пережить тот же инцидент¶

    Копия на том же диске, в том же аккаунте без изоляции прав или с теми же разрушительными учетными данными может исчезнуть вместе с рабочей БД. Надежная схема включает отдельное размещение, разграничение прав, контроль целостности, политики удержания, защиту от несанкционированной перезаписи и регулярные упражнения по восстановлению.

    Необходимы практические доказательства: восстановление в чистом окружении, измерение фактического RTO, проверка достигнутой точки по бизнес-данным, проверка приложений и фиксация результатов. Backup без испытания restore остается гипотезой о восстановимости.

    9.6. Как расследовать превышение RPO/RTO¶

    Если время восстановления не укладывается в цель, не начинаем с абстрактного «сервер медленный». Разбиваем процесс по стадиям: ожидание доступности копии, пропускная способность передачи, распаковка, создание схемы, загрузка данных, индексы, восстановление прав, запуск API и проверка. На каждом шаге измеряем реальные байты/сек, CPU, I/O и длительность. Если потеря данных велика — проверяем частоту и непрерывность сохранения необходимых WAL/копий и целевую точку восстановления.

    Инженерный вывод. RPO и RTO — измеряемые условия работы системы. Существование файла backup.dump не доказывает выполнение ни одного из них.

    Резюме раздела II¶

    1. pg_dump экспортирует согласованный логический снимок одной базы; глобальные объекты требуют отдельного учета.
    2. Согласованность выгрузки не означает отсутствие взаимодействия с DDL и нагрузки на систему.
    3. pg_restore восстанавливает граф зависимых объектов; -j ускоряет лишь при достаточных ресурсах.
    4. В PostgreSQL 18 --transaction-size позволяет управлять размером транзакционных групп при restore.
    5. RPO — допустимая потеря данных, RTO — допустимая длительность полного возврата сервиса.
    6. Восстановимость доказывается репетициями, проверкой зависимостей и бизнес-инвариантов.

    III. Connection Pooling: тысячи запросов и ограниченное число backend-процессов¶

    10. database/sql pool: где запрос ждет до PostgreSQL¶

    10.1. Почему sql.DB — не один socket¶

    Go-приложение создает db, запускает несколько горутин и вызывает QueryContext. Очень удобная модель: каждая горутина просто посылает SQL в базу. Но PostgreSQL не выполняет бесконечное число команд по одному физическому соединению одновременно. Для независимых конкурирующих запросов нужны доступные физические соединения; Go database/sql управляет их повторным использованием.

    *sql.DB — потокобезопасный менеджер пула. Он может поддерживать несколько открытых соединений, выдавать свободное соединение для операции, создавать новые в пределах ограничений и ставить запрос в очередь, когда все заняты. sql.DB не обязан открывать физическое соединение непосредственно в момент создания объекта; при обычном sql.Open подключение часто устанавливается позже.

    100 goroutine ──► *sql.DB
                     │
            ┌────────┴────────┐
            ▼                 ▼
       12 InUse          8 Idle / capacity
            │                 │
            └────────┬────────┘
                     ▼
             Физические sockets
                     ▼
             PostgreSQL backend

    Количество горутин не равно числу открытых соединений. И наоборот: соединение может быть открыто, но простаивать в пуле.

    10.2. Четыре основных параметра¶

    func configureDB(db *sql.DB) {
    db.SetMaxOpenConns(20)
    db.SetMaxIdleConns(10)
    db.SetConnMaxIdleTime(2 * time.Minute)
    db.SetConnMaxLifetime(30 * time.Minute)
}

    Нужны импорты стандартной библиотеки database/sql и time. Конкретный драйвер PostgreSQL подключается отдельно; его здесь не выбираем.

    • SetMaxOpenConns(20): не более двадцати одновременно открытых физических соединений данного sql.DB, включая занятые и свободные. По умолчанию лимит не задан.
    • SetMaxIdleConns(10): не более десяти соединений сохранять idle для повторного использования. Это не максимальная параллельность операций.
    • SetConnMaxIdleTime: после установленного времени простоя соединение становится кандидатом на закрытие. Закрытие зависит от жизненного цикла пула и его уборки.
    • SetConnMaxLifetime: ограничение максимального времени существования соединения, а не максимальной длительности одного SQL-запроса. Соединение, выполняющее операцию, не прерывается посередине только из-за достижения lifetime; оно закрывается при подходящем возвращении/проверке.

    Изменения параметров имеют цену. Слишком маленький MaxOpenConns создает очередь, слишком большой — перенасыщает PostgreSQL backend-процессами; слишком маленький MaxIdleConns провоцирует создание подключений; чрезмерно короткий lifetime вызывает churn и новые аутентификации.

    10.3. Когда соединение возвращается в пул¶

    При db.ExecContext соединение обычно возвращается после завершения операции. При db.QueryContext надо закрывать Rows и дочитывать/обрабатывать результат корректно:

    rows, err := db.QueryContext(ctx,
    `SELECT id, status FROM orders WHERE customer_id=$1`, customerID)
if err != nil { return err }
defer rows.Close()

for rows.Next() {
    var id int64
    var status string
    if err := rows.Scan(&id, &status); err != nil { return err }
    // Обрабатываем строку без длительных внешних вызовов.
}
return rows.Err()

    Если держать Rows открытым и внутри цикла выполнять долгую сетевую работу, физическое соединение может оставаться занятым существенно дольше исполнения запроса на PostgreSQL. При QueryRowContext результат нужно завершить через Scan.

    Транзакция через db.BeginTx закрепляет соединение на время Tx; оно возвращается в общий пул после успешного Commit либо Rollback. Если забыть завершить транзакцию, можно исчерпать пул даже при быстром SQL. Для sql.Conn как выделенного соединения вызов Close обязателен после завершения использования.

    10.4. Время ожидания свободного соединения¶

    Представим: MaxOpenConns=10, пришло 100 независимых запросов, каждый удерживает соединение примерно 40 мс. Десять начали работу, остальные ждут. При идеальном равномерном обслуживании очередь потребует примерно десять волн, поэтому хвостовая задержка может вырасти на сотни миллисекунд до учета сети и приложения. Настоящее поведение зависит от распределения времени обслуживания и планирования очереди; эти числа иллюстративны.

    В приложении наблюдаем накопительную статистику:

    s := db.Stats()
fmt.Printf("open=%d in_use=%d idle=%d wait_count=%d wait=%s\n",
    s.OpenConnections, s.InUse, s.Idle,
    s.WaitCount, s.WaitDuration)

    WaitCount и WaitDuration — накопительные счетчики, поэтому для анализа интервала надо вычислить разницу между двумя измерениями. WaitCount не означает число клиентов, ожидающих прямо сейчас. Если InUse регулярно упирается в MaxOpenConnections, а за интервал растут WaitCount и WaitDuration, вероятна насыщенность пула. Далее выясняем, почему соединения удерживаются долго: SQL, длительная транзакция, обработка Rows, сеть, зависшее приложение.

    10.5. Почему context.Context важен именно здесь¶

    QueryContext и ExecContext могут учитывать отмену запроса как при ожидании свободного соединения, так и при дальнейшей работе — в пределах поведения драйвера и конкретного этапа. Контекст с deadline не обеспечивает мгновенную физическую отмену SQL на сервере при любом сбое сети, поэтому проверяются и клиентское завершение, и состояние backend.

    Пример использования:

    ctx, cancel := context.WithTimeout(parent, 800*time.Millisecond)
defer cancel()

var count int64
err := db.QueryRowContext(ctx,
    `SELECT count(*) FROM orders WHERE customer_id=$1`, customerID,
).Scan(&count)
if err != nil { return err }

    Если бюджет запроса 800 мс, а 700 мс ушло на ожидание пула, оставшееся время на SQL и сеть сокращается до ~100 мс. Добавление индекса здесь может не исправить p99, пока проблема находится в пуле.

    10.6. Настраиваем на основании времени удержания¶

    Для начальной оценки используют закон Литтла в стационарном режиме:

    [ L = \lambda W, ]

    где L — среднее число одновременно занятых соединений, λ — интенсивность завершенных операций в секунду, W — среднее время удержания физического соединения в секундах. Например, при 500 операций/с и среднем удержании 20 мс получаем L≈10. Это средняя загрузка, не готовый размер пула: нужен запас на вариацию времени, пики, транзакции и целевую задержку ожидания.

    Если усложнить приложение так, что время удержания выросло до 80 мс при том же потоке, среднее число одновременно необходимых соединений становится 40. Такой рост не обязательно связан с планом выполнения SQL; он может происходить из-за внешних вызовов внутри транзакции.

    Инженерный вывод. Для Go важно измерять задержку получения соединения отдельно от SQL. sql.DB — самостоятельная очередь ограниченного ресурса, а неверный размер пула способен создавать деградацию до PostgreSQL.

    11. max_connections: бюджет на уровне PostgreSQL¶

    11.1. Откуда берется ресурсная цена соединения¶

    Обычное клиентское соединение PostgreSQL обслуживает отдельный серверный backend process. Каждому нужны служебные структуры, память процесса, локальное состояние сессии, ресурсы сокета и участие в общесерверной конкуренции. Дополнительные соединения не создают пропорционально дополнительные CPU и I/O.

    SHOW max_connections;
SHOW reserved_connections;
SHOW superuser_reserved_connections;

SELECT count(*) AS client_backends
FROM pg_stat_activity
WHERE backend_type = 'client backend';

    В PostgreSQL 18 параметр max_connections по умолчанию обычно равен 100 (но может зависеть от окружения); он задается при старте сервера. Часть слотов может быть зарезервирована для специальных ролей и суперпользователей. Увеличение лимита требует перезапуска и повышает потребление некоторых ресурсов, включая shared memory.

    11.2. Почему приложение может упереться в лимит после горизонтального масштабирования¶

    12 экземпляров сервиса  ×  30 MaxOpenConns = 360
+ batch workers         ×  20                 20
+ администрирование                              10
Итого потенциальный спрос                       390

    Это потенциальное, а не фактическое число соединений: sql.DB может не открыть все соединения сразу. Однако при пике разные экземпляры способны попытаться занять эти слоты одновременно. При max_connections=100 некоторые подключения будут отвергнуты еще до выполнения SQL. Увеличение только количества инстансов приложения способно ухудшить доступность базы.

    11.3. Connection budget¶

    Практический расчет начинается с определения реального лимита, резерва под администратора/системные процессы и других клиентов. Затем устанавливаем долю для каждого сервиса:

    [ B_{apps} = B_{usable} - B_{other clients} - B_{operational reserve}. ]

    Если приложения используют локальные пулы без внешнего мультиплексирования, сумма их возможных одновременных соединений должна соответствовать выбранному бюджету. При динамическом масштабировании учитываем максимальное число реплик, а также кратковременное сосуществование старых и новых экземпляров во время rolling deployment.

    Нельзя раздать каждому сервису одинаковый лимит «по 50» и надеяться, что одновременно он никому не понадобится. Бюджет рассчитывается по совокупности всех потребителей.

    11.4. Почему просто поднять лимит — сомнительное лечение¶

    Если PostgreSQL ограничен CPU, I/O или конкуренцией за ресурсы, новые backend-процессы могут увеличить переключения контекста, потребление памяти и очереди. TPS стабилизируется или ухудшается, p99 растет. Поэтому сравниваем результаты при разных размерах общего пула и фиксируем: throughput, latency, CPU, I/O, wait events, ошибки подключения, количество active/idle backend.

    Типовой график имеет область роста пропускной способности, затем насыщение и возможную деградацию. Оптимум определяется нагрузкой и конфигурацией, а не универсальной формулой «число ядер × N».

    11.5. Административный резерв¶

    reserved_connections в PostgreSQL 18 предназначен для ролей с pg_use_reserved_connections; superuser_reserved_connections — для суперпользовательского доступа при исчерпании обычных слотов. Эти резервы нужны, чтобы в инциденте сохранялась возможность диагностики. Если сервисную роль сделать суперпользователем ради доступа в переполненную базу, мы разрушим назначение резерва.

    Инженерный вывод. max_connections — лимит на конечный ресурс PostgreSQL. Управлять им следует совместно с пулом каждого приложения и планом масштабирования.

    12. PgBouncer: два разных количества соединений¶

    12.1. Для чего нужен внешний посредник¶

    У нас 12 экземпляров сервиса, каждый поддерживает собственный Go-пул. Даже при небольшом среднем SQL-трафике эти пулы могут хранить десятки idle соединений каждый. PostgreSQL при этом держит соответствующие backend processes.

    PgBouncer — специализированный легковесный пулер PostgreSQL-протокола. Он принимает клиентские соединения приложений и переиспользует более ограниченный набор серверных соединений к PostgreSQL. Но уровень переиспользования зависит от выбранного pool_mode.

    12 Go instances
    │  (много client connections)
    ▼
┌─────────────────────────┐
│        PgBouncer        │
│  очередь + server pool  │
└───────────┬─────────────┘
            │ (меньше server connections)
            ▼
       PostgreSQL
       backend processes

    PgBouncer не ускоряет один SQL-запрос за счет магии. Его основная выгода — уменьшение стоимости большого числа клиентских подключений и управление конкуренцией за конечные серверные соединения.

    12.2. Важные параметры¶

    Учебный пример pgbouncer.ini (аутентификацию, TLS и полномочия нужно настроить отдельно):

    [databases]
appdb = host=postgres.internal port=5432 dbname=appdb

[pgbouncer]
listen_addr = 127.0.0.1
listen_port = 6432
pool_mode = transaction
default_pool_size = 30
reserve_pool_size = 5
max_client_conn = 1000
max_prepared_statements = 100
    • max_client_conn ограничивает клиентские подключения к самому PgBouncer; он не равен числу backend PostgreSQL.
    • default_pool_size задает максимум серверных соединений на пару база/пользователь при отсутствии override; при нескольких парах общая сумма может быть больше 30.
    • reserve_pool_size допускает дополнительный резерв в условиях ожидания по настроенным правилам.
    • pool_mode определяет, когда серверное соединение освобождается для другого клиента.
    • max_prepared_statements влияет на поддержку именованных подготовленных команд на уровне протокола в transaction/statement pooling; подробнее в теме 14.

    На реальной системе дополнительно надо обеспечить правильные auth_type, auth_file/auth_query, сетевую безопасность, TLS, лимиты файловых дескрипторов и политику отказов. Не следует копировать этот фрагмент как готовую безопасную конфигурацию production.

    12.3. Важная математическая тонкость: число пулов¶

    Если default_pool_size=30, есть две базы и три набора пользователей, может существовать несколько отдельных серверных пулов. Тогда фраза «PgBouncer держит максимум 30 соединений к PostgreSQL» неверна без анализа конфигурации. К бюджетированию добавляются max_db_connections, max_user_connections, особенности forced-user и другие ограничения, если они настроены.

    12.4. Где образуется очередь¶

    Если все серверные соединения в пуле заняты, следующий клиентский запрос ждет освобождения подходящего сервера. При этом подключение клиента к PgBouncer может оставаться установленным.

    Для диагностики подключаемся к специальной административной базе PgBouncer (с нужными правами):

    SHOW POOLS;
SHOW STATS;
SHOW CLIENTS;
SHOW SERVERS;

    SHOW POOLS дает cl_waiting, sv_active, sv_idle, maxwait и другие показатели. SHOW STATS отражает агрегированные запросы/транзакции и интервальные характеристики. При росте cl_waiting и maxwait мы видим очередь перед PostgreSQL, а не обязательно блокировку внутри СУБД.

    Административная консоль PgBouncer использует свои ограничения протокола (в частности, simple query protocol), поэтому некоторые драйверы, безусловно использующие extended protocol, для этих команд не подходят. Для демонстраций проще psql с соответствующими правами.

    Инженерный вывод. PgBouncer отделяет число клиентских подключений от числа серверных. После его установки нужно диагностировать очереди на двух уровнях, иначе узкое место просто переместится и станет менее очевидным.

    13. Session pooling: совместимость ценой низкого мультиплексирования¶

    13.1. Когда PgBouncer освобождает server connection¶

    В session pooling серверное соединение закрепляется за клиентом на всю клиентскую сессию и возвращается в пул после ее завершения. Если клиент держит подключение открытым, но ничего не выполняет, серверное соединение может оставаться за ним.

    Client A CONNECT ───────────────────── DISCONNECT
          │                               │
          └──── Server connection S1 ─────┘
          BEGIN, SELECT, COMMIT, idle, ...

    Это позволяет сессионным механизмам PostgreSQL работать так, как ожидает клиент: серверная сессия остается той же самой между транзакциями.

    13.2. Почему это удобно, но не всегда экономит backend slots¶

    Сервис может поддерживать 200 idle клиентских подключений; в session pooling многие из них продолжают удерживать серверные подключения. Если вместо этого клиентская сессия короткая и подключения освобождаются быстро, повторное использование заметно улучшится. Эффективность зависит от жизненного цикла клиентских соединений.

    Модель «PgBouncer гарантирует в десять раз меньше backend» не выдерживает session pooling с долгоживущими клиентами. При этом посредник все равно может управлять лимитами и очередями, но большого мультиплексирования внутри долгих сессий не будет.

    13.3. Какие функции сохраняют сессионный смысл¶

    Session pooling соответствует ожиданиям для SET, сессионных временных таблиц, SQL-level PREPARE, LISTEN, session-level advisory locks и других механизмов, привязанных к конкретному backend, с обычными оговорками PostgreSQL и PgBouncer. Эти функции сами по себе не являются универсально безопасными для любого жизненного цикла приложения, но сессионная привязка сервера сохраняется.

    Инженерный вывод. Session pooling выбирают, когда важна привычная семантика сессии или приложение пока не готово к transaction pooling. Цена — серверное соединение может оставаться занятым в период клиентского простоя.

    14. Transaction pooling: максимум переиспользования, минимум сессионных предположений¶

    14.1. Сервер выдается на время транзакции¶

    В transaction pooling PgBouncer закрепляет серверное соединение только на время транзакции и возвращает его в пул после ее завершения. Следующая транзакция того же клиентского соединения может попасть на другой backend PostgreSQL.

    Client A:  BEGIN ── SQL ── COMMIT        BEGIN ─ SQL ─ COMMIT
                │                              │
Server:        S1                             S3

Client B:            BEGIN ─ SQL ─ COMMIT
                           │
Server:                   S2

    В autocommit режиме одиночная команда обычно образует самостоятельную транзакцию. Если приложение держит транзакцию открытой во время внешнего HTTP-вызова, серверное соединение останется закрепленным на весь этот период: PgBouncer не освобождает его просто потому, что PostgreSQL в этот момент не выполняет SQL.

    14.2. Почему session state начинает протекать¶

    Клиент может выполнить:

    SET search_path = tenant_a;
SELECT * FROM orders;

    В session pooling это два запроса одной физической серверной сессии. В transaction pooling следующий запрос может выполняться в другой сессии; предположение о сохранении search_path становится неверным. Для параметров, которые должны жить только в транзакции, подходит:

    BEGIN;
SET LOCAL statement_timeout = '500ms';
SELECT ...;
COMMIT;

    SET LOCAL ограничивает настройку текущей транзакцией. Но это не означает, что любое изменение session state автоматически становится допустимым после добавления BEGIN: нужно проверять конкретный механизм и его поддержку PgBouncer.

    14.3. Таблица совместимости¶

    Возможность PostgreSQL Session Transaction

    Session-level SET/RESET Да Нет гарантии сохранения

    Эта таблица обобщает официальную PgBouncer feature map. Реальную совместимость следует тестировать на конкретных версиях драйвера, PgBouncer и приложении.

    14.4. Почему prepared statements — тонкий вопрос¶

    Есть два разных механизма, которые разработчики называют «prepared statements».

    SQL-level:

    PREPARE get_order(bigint) AS
SELECT * FROM orders WHERE id = $1;
EXECUTE get_order(42);

    Это состояние PostgreSQL-сессии. После смены backend в transaction pooling такой объект может отсутствовать.

    Protocol-level prepared statements: клиент использует сообщения extended query protocol (Parse, Bind, Execute, ...). Современный PgBouncer умеет отслеживать именованные подготовленные запросы на протокольном уровне и обеспечивать наличие соответствующего statement на выбранном серверном соединении, если max_prepared_statements задан ненулевым.

    Следовательно, утверждение «prepared statements всегда несовместимы с transaction pooling» устарело. Необходимо определить конкретный вид подготовки, версию PgBouncer, параметр и поведение драйвера. На разбор wire protocol можно перейти в углублении 09.3; сейчас достаточно разграничить два механизма.

    14.5. Откуда берется выигрыш и почему TPS не растет бесконечно¶

    Если тысяча клиентов выполняет короткие транзакции редко, transaction pooling позволяет обслуживать их значительно меньшим числом серверных соединений, потому что каждая серверная сессия быстро возвращается в общий пул. Но если 200 операций одновременно занимают сервер в течение секунды, пул из 20 backend способен обслужить лишь ограниченное количество таких операций в единицу времени.

    С уменьшением пула PostgreSQL может работать стабильнее благодаря меньшей конкуренции, однако после некоторой границы очередь PgBouncer начнет расти. Мы управляем trade-off между потреблением серверных ресурсов, временем ожидания и пределом пропускной способности. Это проверяется нагрузкой, а не выбором режима «transaction» как универсальной оптимизации.

    14.6. Сценарий совместимости с Go¶

    database/sql не обещает, что последовательные db.ExecContext без явной sql.Tx выполняются на одном физическом соединении. Поэтому код, зависящий от сессионного состояния между разными вызовами db.Exec, уже содержит скрытое предположение о пуле даже без PgBouncer. В transaction pooling это ограничение становится еще очевиднее.

    Правильный контракт: операции, которые должны составлять атомарную единицу и использовать локальные настройки, выполняются внутри одной sql.Tx; session-level функции разрешаются только после отдельной проверки совместимости выбранного режима.

    14.7. Как отличить насыщение Go-пула от насыщения PgBouncer и PostgreSQL¶

    Симптом Где искать сначала Основные измерения
    Go WaitCount и WaitDuration растут Локальный Go-пул DB.Stats, время получения соединения
    PgBouncer cl_waiting, maxwait растут Серверные пулы PgBouncer SHOW POOLS, SHOW STATS
    too many clients already Подключения к PostgreSQL max_connections, резерв, состав backend
    PgBouncer без очереди, запросы медленные PostgreSQL или сеть pg_stat_activity, wait events, query stats
    После смены режима исчезает состояние сессии Неподходящий pooling mode SET, temp tables, PREPARE, LISTEN
    Транзакции держат сервер по секунде между запросами Приложение Длительность Tx и внешние вызовы внутри нее

    Один p99 может включать три части: ожидание в database/sql, ожидание server connection в PgBouncer, выполнение/ожидание внутри PostgreSQL. Без разделения стадий можно бесконечно оптимизировать SQL, хотя проблема находится в первой очереди.

    Инженерный вывод. Transaction pooling особенно полезен для множества коротких транзакций и приложений без зависимостей от session state. Он требует контрактной проверки совместимости и измерения задержок на всех уровнях.

    Резюме раздела III¶

    1. sql.DB управляет физическими подключениями и имеет собственную очередь ожидания.
    2. MaxOpenConns ограничивает соединения данного процесса; общий бюджет считается по всем экземплярам.
    3. max_connections ограничивает конечные ресурсы PostgreSQL; его увеличение не создает CPU/I/O.
    4. PgBouncer отделяет клиентские подключения от серверных и добавляет самостоятельную точку ожидания.
    5. Session pooling сохраняет сессионный контракт; transaction pooling повышает повторное использование ценой ограничений на session state.
    6. Protocol-level named prepared statements при соответствующей настройке PgBouncer могут работать в transaction pooling.

    IV. Собираем расследование целиком¶

    15. Сквозной сценарий: один релиз, три взаимосвязанных отказа¶

    Нумерация этого раздела служебная: это итоговый сценарий, а не новая тема утвержденного списка 1–14.

    Шаг 1. На тесте миграция прошла за секунду¶

    В production ALTER TABLE ждет блокировку. Сразу проверяем, что кодовая версия A еще работает с переходной схемой; выясняем блокирующую транзакцию уже знакомыми инструментами pg_stat_activity и pg_blocking_pids(). Не заставляем приложение ждать DDL бесконечно — у миграционного этапа есть лимит ожидания и состояние для безопасного повторения.

    Шаг 2. Создание индекса перешло в третью фазу ожидания¶

    Запущен CREATE INDEX CONCURRENTLY; он выполняет дополнительные проходы и ожидает старые транзакции. Смотрим pg_stat_progress_create_index.phase, флаги pg_index.indisvalid/indisready, размер индекса и состояние сессий. Если операция неуспешна, не считаем индексы «либо есть, либо нет» — проверяем невалидное промежуточное состояние.

    Шаг 3. Новый код записывает в две структуры¶

    Переходная версия приложения должна соблюдать контракт старой версии и не терять обновления во время backfill. Контрольный запрос ищет неперенесенные данные; отдельная проверка ищет расхождения. При ошибке мы откатываем только тот компонент, для которого заранее доказана совместимость, а не автоматически удаляем новые колонки.

    Шаг 4. Удалили данные — открыли копию, но восстановление не готово¶

    Проверяем формат и полноту backup, наличие глобальных объектов, обязательных extensions, права ролей и возможность корректно запустить pg_restore. На изолированном стенде измеряем время по стадиям и проверяем инварианты приложения. Если бизнес требует RPO в минутах, одной ночной логической выгрузки недостаточно — необходим иной план защиты данных.

    Шаг 5. Масштабируем API — и PostgreSQL перестает принимать соединения¶

    Считаем совокупный пул: максимальное число экземпляров при rolling deployment, MaxOpenConns каждого, другие сервисы, административный резерв. Если запросы ждут еще на уровне Go, смотрим DB.Stats. Если очередь после PgBouncer — SHOW POOLS. Если сервер перегружен — смотрим PostgreSQL. Нельзя анализировать любую задержку как «медленный SELECT».

    Шаг 6. Переключаем PgBouncer на transaction pooling и обнаруживаем потерю session state¶

    Проверяем все зависимости от SET, LISTEN, temp tables, SQL-level PREPARE и session advisory locks. Для протокольных prepared statements отдельно оцениваем настройку max_prepared_statements. Если совместимость не подтверждена, остаемся на session pooling для нужного маршрута либо исправляем клиентскую логику.

    16. Что измерять до и после изменений¶

    Операция Риск Измерение Признак успешного результата
    DDL Длинная очередь блокировок Ожидание lock, длительность, число ожидающих Нет устойчивого роста latency и ошибок
    Backfill Большие транзакции, WAL/I/O, гонки Batch latency, rows/s, остаток, сверка Данные согласованы, batch можно продолжить
    CREATE INDEX CONCURRENTLY Долгое построение, INVALID index Progress view, indisvalid, ошибки Индекс VALID, запросы не потеряли доступность
    pg_dump Нагрузка, неполная защита Exit status, длительность, размер, проверка Дамп восстанавливается на отдельном стенде
    pg_restore Долгий RTO, нехватка ресурсов Время фаз, jobs, SQL errors Проверенные объекты и бизнес-инварианты
    sql.DB pool Ожидание до БД InUse, WaitCount/Duration за интервал Контролируемая очередь при заданном p99
    PgBouncer Ожидание server connection cl_waiting, maxwait, sv_active Бюджет backend соблюден без лишних отказов

    Здесь нет одной универсальной метрики «база здорова». Каждая операция имеет собственную цену и отдельную точку наблюдения.

    17. Главная модель блока 9¶

    1. Миграция — распределенное изменение контракта во времени. Все версии приложения должны быть совместимы с переходной схемой, пока не завершится переключение.
    2. Дешевое изменение метаданных может быть дорогим для доступности. Очередь блокировок и длительность транзакций способны превратить миллисекундный DDL в инцидент.
    3. Backup проверяется restore. Успешное создание дампа не доказывает достижение RPO/RTO; нужны регулярные восстановления, проверка целостности и бизнес-инвариантов.
    4. Соединения — конечный ресурс. Go-пулы, PgBouncer и PostgreSQL образуют разные уровни очередей; измеряем каждый по отдельности.
    5. Session pooling и transaction pooling предоставляют разные контракты. Максимальное переиспользование серверных соединений возможно лишь при отказе от небезопасных предположений о сессионном состоянии.
    6. Изоляция проблем важнее размера конфигурации. Увеличение лимита, количества workers или числа экземпляров без измерений может ухудшить ситуацию.
