    6.3. PostgreSQL — хеш-записи, перераспределение партий и временные хранилища¶

    Углубленная техническая лекция. Ориентир — PostgreSQL 18, реализация REL_18_STABLE. Продолжение основной лекции №6 и углубления 06.2. Рассматриваем физический путь записи через HashJoinTuple, плотное выделение памяти, перераспределение партий, а затем tuplestore, BufFile и SharedTuplestore. Не рассматриваем WAL, COMMIT, fsync, checkpoint и восстановление после сбоя.

    Статус примеров. Приведенные числовые хеш-коды, размеры кортежей, конфигурации памяти и планы являются учебными примерами, а имена C-структур, функций, ключевые формулы и ветвления сверены с PostgreSQL 18. Во всех вычислениях используется обычный Markdown без LaTeX.

    Главный вопрос: PostgreSQL держит в памяти часть хеш-соединения, затем неожиданно превышает бюджет. Как он находит каждую уже записанную строку, куда перемещает ее, почему пары не теряются, когда появляются временные файлы, и почему при сильном перекосе увеличение числа партий может перестать помогать?

    0. Что планировщик передал исполнителю¶

    В 06.1 планировщик оценил стоимость соединения и выбрал дерево. В 06.2 мы уже выяснили, что Hash Join строит временную хеш-таблицу и может обрабатывать вход по партиям.

    Hash Join
  Hash Cond: (o.customer_id = c.id)
  -> Seq Scan on orders o
  -> Hash
       -> Seq Scan on customers c

    Hash — внутренний вход соединения. Именно он подготавливает данные для поиска. В PostgreSQL построение выполняется через MultiExecHash(); сам узел Hash не использует обычный интерфейс «верни очередную строку» для основной операции. При обычном соединении по строгому равенству строки с NULL в ключе не могут образовать совпадение; соответствующие ветви исполнителя вправе не помещать их в основные хеш-корзины. Для некоторых внешних соединений такие строки обрабатываются отдельно, чтобы корректно выдать несопоставленные строки.

    Нам предстоит ответить на два независимых вопроса. Первый — как храним строки в памяти и как меняем их распределение по партиям. Второй — как сохраняем строки для последующего чтения: на уровне одного процесса и нескольких процессов. Для этих задач применяются разные структуры; важно их не смешивать.

    1. Что хранится внутри HashJoinTuple¶

    1.1. Ключа недостаточно¶

    SELECT o.id, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id;

    Построенная по customers хеш-таблица должна хранить данные, нужные для получения c.name. Кроме ключа, нужны сведения для обхода коллизий и вычисленный хеш.

    В PostgreSQL 18 внутреннее представление устроено примерно так (сокращенный фрагмент реальной структуры src/include/executor/hashjoin.h):

    typedef struct HashJoinTupleData
{
    union
    {
        struct HashJoinTupleData *unshared;
        dsa_pointer shared;
    } next;

    uint32 hashvalue;
    /* Затем в памяти располагается MinimalTuple */
} HashJoinTupleData;

    next.unshared — обычный адрес следующего элемента цепочки в рамках одного процесса. next.shared — указатель-смещение для разделяемой области памяти, поскольку виртуальные адреса разных процессов могут не совпадать. hashvalue — 32-битный хеш-код ключа, а MinimalTuple — сохраненное компактное представление входной строки.

    Важно: MinimalTuple не обязан включать все столбцы исходной таблицы. Исполнитель сохраняет то, что поступило из дочернего узла плана. Однако это больше одного ключа, если вышестоящим узлам нужны дополнительные столбцы.

    1.2. Где начинается MinimalTuple¶

    В заголовке определены макросы:

    #define HJTUPLE_OVERHEAD MAXALIGN(sizeof(HashJoinTupleData))
#define HJTUPLE_MINTUPLE(hjtup) \
    ((MinimalTuple) ((char *) (hjtup) + HJTUPLE_OVERHEAD))

    MAXALIGN округляет размер заголовка к подходящей для платформы границе выравнивания. На типичной 64-битной архитектуре выровненный заголовок составляет 16 байт; эта цифра зависит от ABI и не является гарантией SQL или PostgreSQL на любой машине.

    Адрес HashJoinTuple
       |
       v
+------------------------+
| next                   | 8 байт в типичной 64-битной сборке
+------------------------+
| hashvalue              | uint32 = 4 байта
+------------------------+
| выравнивание           | условные 4 байта
+------------------------+ <- HJTUPLE_MINTUPLE
| MinimalTuple.t_len     |
| поля заголовка         |
| значения столбцов      |
| ...                    |
+------------------------+

    Размер сохраненной хеш-записи до выравнивания для следующей аллокации:

    record_bytes = HJTUPLE_OVERHEAD + tuple->t_len

    Внутри плотного блока следующий элемент начинается с выровненного смещения:

    next_offset = offset + MAXALIGN(record_bytes).

    Важная оговорка: это шаг по логически размещенным записям. Реально выделенная память и служебная статистика расхода могут отличаться от простой суммы размеров кортежей из-за выравнивания и накладных расходов блоков.

    1.3. Расход памяти на миллион записей¶

    Зададим учебные размеры: выровненный заголовок — 16 байт, MinimalTuple — 56 байт. Одна запись занимает 72 байта.

    1 000 000 × 72 = 72 000 000 байт ≈ 68,66 МиБ

    У массива из 65 536 корзин по 8 байт на указатель:

    65 536 × 8 = 524 288 байт = 512 КиБ

    Итого более 69 МиБ, еще без дополнительных блоков и служебных структур. Нельзя рассчитывать размер соединения по формуле «количество записей × размер ключа».

    2. dense_alloc и HashMemoryChunk: как разместить миллионы строк¶

    2.1. Цена миллионов отдельных выделений¶

    Если вызывать palloc() на каждую маленькую хеш-запись, появляются накладные расходы на обслуживание выделений, метаданные и выравнивание. Выигрыш от хеширования частично съедается распределителем памяти.

    PostgreSQL 18 использует dense_alloc() — плотное выделение памяти из блоков HashMemoryChunk.

    В hashjoin.h заданы:

    #define HASH_CHUNK_SIZE ((Size) (32 * 1024))
#define HASH_CHUNK_THRESHOLD (HASH_CHUNK_SIZE / 4)

    Обычный блок — 32 КиБ. Порог — 8 КиБ: слишком большие записи получают отдельный блок.

    HashMemoryChunk
+-----------------------------+
| Заголовок блока             |
| ntuples, maxlen, used, next |
+-----------------------------+
| HashJoinTuple №1            |
+-----------------------------+
| HashJoinTuple №2            |
+-----------------------------+
| ...                         |
+-----------------------------+
| Свободные байты             |
+-----------------------------+

    used — количество занятых байт в буфере блока; maxlen — доступная емкость. Переход к следующей записи происходит по MAXALIGN(HJTUPLE_OVERHEAD + tuple->t_len).

    2.2. Почему блоки полезны при перестройке¶

    Цепочки корзин описывают порядок поиска. Но сами записи расположены последовательно внутри блоков. Значит, PostgreSQL может пройти все текущие записи физически по блокам, даже если перестраивает или очищает массив указателей на корзины.

    Учебный псевдокод:

    for chunk in chunks:
    offset = 0
    while offset < chunk.used:
        tuple = запись в chunk по offset
        обработать(tuple)
        offset += MAXALIGN(размер tuple)

    Именно такой обход используется при ExecHashIncreaseNumBatches() и при изменении количества корзин. Он избавляет от необходимости удалять записи по одной из старых цепочек.

    2.3. Где живут блоки и временные файлы¶

    Для непараллельного хеш-соединения HashJoinTableData содержит ссылку на связанные контексты памяти:

    • hashCxt — контекст хеш-операции;
    • batchCxt — память рабочей партии, которую можно сбросить перед следующей;
    • spillCxt — объекты, необходимые для временных файлов и переживающие сброс batchCxt.

    HashJoinTableData хранится в контексте самого запроса; крупные рабочие структуры размещаются в дочерних контекстах. Это позволяет освобождать память целой партии. Если бы временный файловый буфер был выделен из batchCxt, сброс текущей партии уничтожил бы буфер файла, который должен продолжить существовать для будущих партий.

    Инженерная мысль: срок жизни объекта определяется тем, будет ли он нужен после смены партии. Контекст памяти должен соответствовать именно этому сроку.

    3. Корзины и партии на уровне битов¶

    3.1. Две независимые оси распределения¶

    nbuckets — количество корзин текущей хеш-таблицы. nbatch — число партий всего соединения. Сначала вычисляется один 32-битный хеш, затем по нему получаются обе координаты.

    Для PostgreSQL 18, при степенях двойки, существенная часть ExecHashGetBucketAndBatch():

    *bucketno = hashvalue & (nbuckets - 1);

if (nbatch > 1)
    *batchno = pg_rotate_right32(hashvalue, log2_nbuckets)
               & (nbatch - 1);
else
    *batchno = 0;

    Это циклический сдвиг вправо (rotate right), а не обычный hashvalue >> log2_nbuckets. При небольших числах партий нижние значимые для партии биты часто совпадут, но при очень больших хеш-таблицах ротация позволяет продолжать использовать битовые позиции с учетом перехода через границу 32-битного значения. Данная операция — деталь реализации PostgreSQL 18.

    3.2. Разбор nbuckets = 8¶

    Для восьми корзин нужны три бита:

    log2_nbuckets = 3, а маска корзины равна 7 = 000111₂.

    Возьмем хеш-коды как заданные числа, без предположения, что стандартная хеш-функция действительно вернет эти значения для конкретных SQL-ключей.

    Хеш Двоичное представление Корзина h & 7 Партия при nbatch=2 Партия при nbatch=4
    5 000101 5 0 0
    13 001101 5 1 1
    21 010101 5 0 2
    29 011101 5 1 3
    37 100101 5 0 0
    45 101101 5 1 1
    53 110101 5 0 2
    61 111101 5 1 3

    Все восемь хешей попали в одну корзину 5. Однако они распределяются по партиям, потому что для партии используются следующие биты хеша.

    3.3. Ручной расчет для h = 21¶

    hashvalue = 21 = 010101₂
nbuckets = 8
bucket = 21 & 7 = 5

После циклического сдвига на 3:
нижние два бита соответствуют (21 >> 3) = 2 = 10₂

nbatch=2:
batch = 2 & 1 = 0

nbatch=4:
batch = 2 & 3 = 2

    Что произошло? Хеш 21 раньше относился к партии 0, а после увеличения числа партий с двух до четырех относится к партии 2.

    Для хеша 37:

    37 >> 3 = 4 = 100₂
при nbatch=2: 4 & 1 = 0
при nbatch=4: 4 & 3 = 0

    Хеш 37 остается в партии 0.

    3.4. Почему при увеличении партии не идут назад¶

    Поскольку nbatch всегда степень двойки и увеличивается удвоением, новая маска сохраняет старые младшие биты номера партии и добавляет следующий бит.

    nbatch = 2 -> маска 001₂
nbatch = 4 -> маска 011₂
nbatch = 8 -> маска 111₂

    Если ранее партия была b, новая партия после удвоения — либо b, либо b + old_nbatch (при фиксированном nbuckets). То есть запись может остаться в прежней партии или попасть в более позднюю. В более раннюю она не переедет.

    Это инвариант алгоритма. Именно он позволяет отложить часть перераспределения до момента чтения соответствующего файла. Если бы записи могли возвращаться к уже завершенным партиям, соединение пришлось бы запускать заново или хранить дополнительные данные.

    3.5. Корзины и партии не являются одинаковыми вещами¶

    У Batches=4 могут быть тысячи корзин в рабочей хеш-таблице. Корзина отвечает на вопрос «где искать кандидатов сейчас?», партия — «когда нужно обрабатывать эту строку?». Коллизия корзины не означает совпадение ключей; совпадение номера партии не означает совпадение ключей.

    Далее увидим, как при переполнении исполнитель меняет nbatch и вынужден пройти по всем уже размещенным записям рабочей партии.

    4. ExecHashIncreaseNumBatches(): точный ход перераспределения¶

    4.1. Момент переполнения¶

    Предположим, PostgreSQL начал строить хеш-таблицу для партии 0. Планировщик ожидал определенную ширину и число строк, а фактически получает существенно больше записей. После очередной вставки ExecHashTableInsert() обнаруживает, что расчетный объем структуры превышает spaceAllowed. Это рабочий предел, полученный первоначально из бюджета хеш-операции; текущее использование отслеживается через spaceUsed и spacePeak.

    Прежде чем добавлять партии, в PostgreSQL 18 есть еще одна проверка, к которой вернемся в разделе 5: ExecHashIncreaseBatchSize() иногда предпочитает увеличить допустимый объем хеш-таблицы. Если эта оптимизация не сработала, вызывается ExecHashIncreaseNumBatches().

    Разберем именно непараллельный случай. Параллельная реализация использует иные фазы и отдельный механизм согласования.

    4.2. Последовательность действий исполнителя¶

    Логика ExecHashIncreaseNumBatches() из nodeHash.c в PostgreSQL 18:

    1. Проверить growEnabled: если рост партий уже отключен, выйти.
    2. Убедиться, что удвоение nbatch не приводит к переполнению целочисленных и размерных ограничений.
    3. Проверить, не дешевле ли расширить бюджет хеш-таблицы через ExecHashIncreaseBatchSize().
    4. Вычислить new_nbatch = old_nbatch * 2.
    5. Создать при первом многопартийном переходе массивы innerBatchFile и outerBatchFile либо расширить их. Место выделения — spillCxt; сами файловые объекты для пустых партий создаются лениво.
    6. Изменить hashtable->nbatch. Если намечено увеличение количества корзин, изменить и nbuckets с соответствующим log2_nbuckets.
    7. Сбросить указатели старого массива корзин. Запомнить список старых блоков HashMemoryChunk, а список новых блоков начать с пустого.
    8. Пройти все записи старых блоков по физическим смещениям, а не по старым цепочкам корзин.
    9. Для каждой записи пересчитать bucketno и batchno из ранее вычисленного hashvalue.
    10. Если новая партия равна curbatch, скопировать запись через dense_alloc() в новый блок, пересвязать ее в новой корзине.
    11. Если номер новой партии больше curbatch, записать hashvalue и MinimalTuple во временный файл соответствующей партии через ExecHashJoinSaveTuple(). Уменьшить учет занятой памяти и увеличить счетчик перенесенных записей.
    12. Освободить старый блок и продолжить. Внутри долгого обхода вызывается CHECK_FOR_INTERRUPTS() — запрос остается отменяемым.
    13. После обхода проверить, помогло ли дробление. Если перенесены все записи или ни одна, отключить дальнейший рост nbatch (growEnabled = false).

    Существенно, что ExecHashIncreaseNumBatches() не обязан выполнять повторное чтение всех ранее отложенных файлов прямо в момент переполнения. Он обрабатывает записи текущей рабочей хеш-таблицы, а старые файлы переоцениваются при последующем чтении соответствующих партий.

    4.3. Псевдокод близко к реальному механизму¶

    Следующий код специально сокращен и объясняет последовательность; это не компилируемая копия исходника:

    if (!hashtable->growEnabled)
    return;

if (ExecHashIncreaseBatchSize(hashtable))
    return;

hashtable->nbatch *= 2;
ensure_batch_file_arrays(hashtable);

/* При необходимости обновить количество корзин. */
maybe_resize_bucket_array(hashtable);
clear_bucket_heads(hashtable);

oldchunks = hashtable->chunks;
hashtable->chunks = NULL;

long ninmemory = 0;
long nfreed = 0;

for (chunk = oldchunks; chunk != NULL; chunk = nextchunk)
{
    for (offset = 0; offset < chunk->used; /* ниже */)
    {
        HashJoinTuple ht = entry_at(chunk, offset);
        MinimalTuple tuple = HJTUPLE_MINTUPLE(ht);
        Size size = HJTUPLE_OVERHEAD + tuple->t_len;
        int bucketno, batchno;

        ninmemory++;
        ExecHashGetBucketAndBatch(hashtable, ht->hashvalue,
                                  &bucketno, &batchno);

        if (batchno == hashtable->curbatch)
        {
            HashJoinTuple copy = dense_alloc(hashtable, size);
            memcpy(copy, ht, size);
            copy->next.unshared = hashtable->buckets.unshared[bucketno];
            hashtable->buckets.unshared[bucketno] = copy;
        }
        else
        {
            ExecHashJoinSaveTuple(tuple, ht->hashvalue,
                                  &hashtable->innerBatchFile[batchno],
                                  hashtable);
            hashtable->spaceUsed -= size;
            nfreed++;
        }

        offset += MAXALIGN(size);
        CHECK_FOR_INTERRUPTS();
    }

    pfree(chunk);
}

if (nfreed == 0 || nfreed == ninmemory)
    hashtable->growEnabled = false;

    Обрати внимание: для сохранившихся записей происходит копирование в новые блоки. Было бы ошибкой вообразить, что PostgreSQL просто изменил битовую маску и указатели прежних корзин автоматически стали корректны. Структуру приходится физически перестроить.

    4.4. Полная симуляция: партия 0 разделилась надвое¶

    Пусть до переполнения:

    nbuckets = 8
nbatch = 2
curbatch = 0

В рабочей памяти:
  h=5, h=21, h=37, h=53

В отложенном innerBatchFile[1]:
  h=13, h=29, h=45, h=61

    Предположим, каждая сохраненная запись весит 72 байта, и все помещены в один или несколько блоков. Числа маленькие только для демонстрации; настоящий лимит памяти здесь не моделируем.

    Переполнение запускает переход nbatch: 2 -> 4. Вычисляем новые номера:

    Хеш в текущей RAM Партия раньше Партия теперь Действие
    5 0 0 Копировать в новую рабочую структуру
    21 0 2 Записать в innerBatchFile[2]
    37 0 0 Копировать в новую рабочую структуру
    53 0 2 Записать в innerBatchFile[2]

    В результате:

    РАБОЧАЯ ПАМЯТЬ, batch 0:
  bucket 5: 5 -> 37 (порядок зависит от вставки)

ФАЙЛ, batch 1, создан раньше:
  13, 29, 45, 61

ФАЙЛ, batch 2, создан при перераспределении:
  21, 53

ФАЙЛ, batch 3:
  пока может отсутствовать

    Ключевой вопрос: а разве хеши 29 и 61 не должны теперь лежать в партии 3?

    Должны. Однако они пока находятся в файле старой партии 1. PostgreSQL не обязан немедленно переписывать весь файл. Когда придет время обрабатывать партию 1, он прочитает записи и пересчитает для них новую принадлежность:

    13 -> batch 1, остается для обработки
29 -> batch 3, отложить снова
45 -> batch 1, остается для обработки
61 -> batch 3, отложить снова

    Этот прием работает благодаря инварианту: при увеличении числа партий запись может перейти только к более поздней партии. Нельзя потерять совпадения, потому что записи с одинаковым хешем всегда получают одинаковый номер партии в одной конфигурации.

    4.5. Почему нельзя забыть о внешней стороне соединения¶

    Пока мы говорили о внутренней стороне (Hash). Но результаты будут неправильными, если внутреннюю запись перенесли в партию 2, а соответствующий ей заказ поискали в партии 0 и выбросили.

    Поэтому внешняя сторона тоже распределяется по партиям. Для текущей партии 0 PostgreSQL выполняет поиск по оперативной хеш-таблице. Строки для будущих партий записываются в outerBatchFile[batchno].

    При смене партии ExecHashJoinNewBatch():

    1. Завершает обработку текущей партии и освобождает ненужные временные данные.
    2. При необходимости пропускает заведомо бесполезные партии, но с учетом семантики внешних соединений и того, росло ли nbatch.
    3. Меняет curbatch и сбрасывает рабочую хеш-таблицу (ExecHashTableReset()).
    4. Перематывает файл внутренней стороны, заново загружает хеш-записи текущей партии. При загрузке возможен новый рост nbatch; часть записей тогда перенаправляется в еще более поздние партии.
    5. Закрывает обработанный внутренний файл, перематывает внешний файл и начинает выдавать совпадения.

    Важная деталь: при LEFT JOIN нельзя безусловно пропустить партию, если в ней нет внутренних записей. Внешние строки без совпадений все равно должны быть выданы с NULL на правой стороне. Аналогичные ограничения существуют для других внешних соединений. Поэтому проверка «можно ли пропустить партию» учитывает вид соединения, а не только наличие данных в двух файлах.

    4.6. Почему некоторые партии приходится читать даже без пары файлов¶

    Предположим, в старом файле innerBatchFile[1] лежит хеш 29, который после увеличения nbatch должен попасть в партию 3. При этом в outerBatchFile[1] может вообще не быть строк.

    Наивный алгоритм решил бы: «внешняя партия 1 пуста, значит, ее можно пропустить и удалить внутренний файл».

    И потерял бы хеш 29, который позже потребуется для партии 3.

    Поэтому в PostgreSQL предусмотрены отдельные проверки с nbatch_original и nbatch_outstart. Если число партий выросло после соответствующего этапа обработки, файл приходится прочитать хотя бы ради перенаправления записей в будущие партии.

    Это важная гарантия корректности, которую легко упустить при описании многопартийного соединения одним рисунком.

    4.7. Цена такого перераспределения¶

    Каждое увеличение nbatch требует пройти по уже находящимся в памяти записям текущей партии. Для оставшихся выполняются копирование и создание новых цепочек корзин; для перенесенных — запись временных файлов.

    Позже возможны дополнительные чтения и повторные записи, если число партий выросло уже после первоначального размещения данных.

    Следовательно, Batches: 32 (originally 2) означает не только наличие тридцати двух партий. За ним могут скрываться несколько этапов перераспределения, дополнительное копирование строк и временный ввод-вывод.

    Что запомнить после раздела 4¶

    1. Удвоение nbatch меняет вычисление принадлежности записи партии.
    2. PostgreSQL физически обходит записи по HashMemoryChunk, формирует новые блоки и пересвязывает корзины.
    3. Уже отложенные файлы можно корректировать позднее, при чтении, поскольку записи переходят только в более поздние партии.
    4. При смене партии загружается ее внутренний набор, после чего обрабатывается соответствующая внешняя часть.
    5. Внешние соединения и динамический рост числа партий запрещают безусловно пропускать некоторые кажущиеся пустыми партии.

    5. Когда дальнейшее дробление перестает работать¶

    5.1. Неправильная модель: «удвоим партии, и память уменьшится вдвое»¶

    Это утверждение было бы верно примерно при равномерном распределении хешей. Если все записи имеют одинаковое значение hashvalue, вычисление batchno возвращает одну и ту же партию для всех.

    1 000 000 записей с hashvalue = 37

nbatch = 2   -> все в партии 0
nbatch = 4   -> все в партии 0
nbatch = 8   -> все в партии 4
nbatch = 16  -> все в партии 4

    Мы увеличили количество партий, но не разделили группу. Если при обработке партии 4 снова нужно столько же памяти, ничего принципиально не изменилось.

    Так бывает не только при миллионах одинаковых SQL-ключей. Разные ключи теоретически могут иметь одинаковый полный 32-битный хеш. Одинаковый хеш не означает равенство исходных значений: проверка SQL-равенства все равно обязательна.

    5.2. nfreed == 0 и nfreed == ninmemory¶

    В конце ExecHashIncreaseNumBatches() стоят счетчики:

    • ninmemory — сколько записей было просмотрено при перераспределении;
    • nfreed — сколько записей перенесено из текущей рабочей памяти в файлы будущих партий.

    Если nfreed == 0, все записи остались в текущей партии. Дробление никак не уменьшило ее объем.

    Если nfreed == ninmemory, ни одной записи не осталось в текущей партии. В текущей эвристике это тоже считается признаком бесполезного перераспределения и отключает дальнейший рост.

    В обоих случаях выполняется:

    hashtable->growEnabled = false;

    Причина — не бесконечное терпение PostgreSQL к переполнению, а невозможность бесконечно удваивать nbatch в надежде разделить записи с одинаковыми хешами.

    После отключения роста рабочая партия может превысить рассчитанный бюджет. В худшем случае это создает давление на память backend-процесса и может закончиться ошибкой выделения памяти. Бюджет work_mem × hash_mem_multiplier — параметр планирования рабочих операций, а не аппаратная защита от любых выбросов потребления памяти.

    5.3. Особенность PostgreSQL 18: ExecHashIncreaseBatchSize()¶

    Здесь появляется механизм, отсутствующий в наивной модели «переполнение → всегда новые партии».

    У каждой отложенной партии могут существовать два BufFile: для внутренней и внешней стороны. Каждый использует собственный буфер ввода-вывода, обычно порядка BLCKSZ.

    При очень большом числе партий память на файловые буферы сама становится существенной.

    В PostgreSQL 18 до очередного удвоения nbatch вызывается ExecHashIncreaseBatchSize(). Она сравнивает ориентировочный дополнительный объем памяти файловых буферов:

    batchSpace = nbatch × 2 × BLCKSZ

    с уже разрешенным объемом хеш-таблицы spaceAllowed.

    Если:

    spaceAllowed <= batchSpace,

    реализация предпочитает удвоить spaceAllowed, а число партий оставить прежним. Это может уменьшить общий расход памяти по сравнению с созданием еще большего числа буферизованных файлов и предотвратить взрыв числа партий.

    Числовой пример при BLCKSZ=8192:

    nbatch = 512
batchSpace = 512 × 2 × 8192
           = 8 388 608 байт = 8 МиБ

spaceAllowed = 8 МиБ

8 МиБ <= 8 МиБ -> допустимый объем хеша удваивается
nbatch остается 512

    Это деталь реализации PostgreSQL 18, и она требует аккуратной интерпретации. Система не получает новую физическую RAM: она изменяет внутренний бюджет, потому что еще более крупный набор партий мог бы обойтись дороже за счет файловых буферов. Это осознанный компромисс между RAM под записи и RAM под механизмы временного хранения.

    5.4. Почему увеличение корзин не решает проблему партий¶

    В PostgreSQL существуют два разных механизма роста:

    • ExecHashIncreaseNumBuckets() — увеличивает число корзин, уменьшая среднюю длину цепочек при достаточно различающихся хешах;
    • ExecHashIncreaseNumBatches() — увеличивает число партий, пытаясь сократить рабочий объем строк, одновременно находящихся в RAM.

    Больше корзин ускоряет поиск кандидатов, но не уменьшает количество сохраняемых записей.

    Больше партий уменьшает текущий рабочий набор при благоприятном распределении, но добавляет временные файлы и повторную работу.

    И ни одна из этих мер не устраняет миллион реальных совпадений SQL, если одному ключу обеих сторон соответствует множество строк.

    5.5. skew — оптимизация популярных хешей¶

    В обычном многопартийном хеш-соединении PostgreSQL может отдельно учитывать популярные значения внешней стороны. Для них создаются специальные хеш-корзины (skew), чтобы соответствующие записи внутренней стороны могли участвовать в обработке первой партии без ненужной записи и чтения временных файлов.

    Статистика MCV внешнего входа используется для определения полезных популярных значений. SKEW_HASH_MEM_PERCENT в PostgreSQL 18 составляет 2: отдельной структуре выделяется небольшая доля общего бюджета хеш-таблицы.

    Но оптимизация skew экономит временный ввод-вывод для популярных значений; она не устраняет необходимость формировать все реальные результирующие пары.

    Что запомнить после раздела 5¶

    1. Число партий не гарантирует равномерное разделение данных.
    2. При одинаковых хешах дополнительный бит номера партии не разделит группу.
    3. Если перенесены все или ни одной записи, PostgreSQL 18 может отключить дальнейший рост партий.
    4. Перед увеличением партий исполнитель сравнивает стоимость дополнительной памяти под хеш с стоимостью новых файловых буферов.
    5. Увеличение корзин и увеличение партий решают разные проблемы; их нельзя смешивать.

    6. BufFile: что именно записывается во временный файл¶

    6.1. Почему BufFile появляется раньше tuplestore¶

    При многопартийном непараллельном Hash Join отложенные записи записываются через ExecHashJoinSaveTuple() непосредственно в BufFile — буферизованный временный файл.

    Важно: здесь не создается отдельный tuplestore для каждой партии. Это разные механизмы, хотя оба могут использовать общий нижележащий интерфейс BufFile. Для некоторых специальных случаев, например хранения строк с NULL-ключами при определенной семантике внешнего соединения, используется и tuplestore; но обычные файлы партий — это BufFile напрямую.

    6.2. Точный формат одной сохраненной записи¶

    В PostgreSQL 18 ExecHashJoinSaveTuple() делает по смыслу следующее:

    BufFileWrite(file, &hashvalue, sizeof(uint32));
BufFileWrite(file, tuple, tuple->t_len);

    То есть сохраняются:

    +---------------------------+
| hashvalue: uint32         | 4 байта
+---------------------------+
| MinimalTuple.t_len        | uint32, первые 4 байта кортежа
+---------------------------+
| остальная часть MinimalTuple  |
+---------------------------+

    Зачем сохранять hashvalue? Чтобы при повторной загрузке не обязательно вычислять хеш еще раз из значений ключа. Чтобы восстановить размер записи, достаточно прочитать первые два 32-битных числа: хеш и t_len.

    В ExecHashJoinGetSavedTuple() действительно считываются два значения uint32 в одном вызове BufFileReadMaybeEOF(), затем выделяется память по длине и дочитываются остальные байты MinimalTuple.

    Важно не путать две цены:

    • RAM: HJTUPLE_OVERHEAD + tuple->t_len плюс выравнивание и накладные расходы блоков;
    • временный файл: sizeof(uint32) + tuple->t_len на сохраненную запись, плюс накладные расходы буферизации и файловой системы.

    При tuple->t_len = 56:

    RAM-запись при заголовке 16 байт: 16 + 56 = 72 байта
Временная запись: 4 + 56 = 60 байт

    Это объясняет, почему нельзя автоматически умножать Memory Usage узла Hash на два и получать точный объем записи/чтения временных файлов.

    6.3. Что буферизует BufFile¶

    BufFile — интерфейс к временным файлам с небольшим буфером в памяти. Он работает поверх файлового слоя PostgreSQL (fd.c) и обеспечивает логическую позицию чтения/записи.

    Когда Hash Join передает в BufFileWrite() десятки тысяч небольших записей, не нужно обязательно выполнять отдельный системный вызов write() для каждой записи. Данные накапливаются в буфере и сбрасываются более крупными порциями.

    При чтении BufFile также может возвращать байты из собственного буфера. Файловая система и ОС могут дополнительно обслуживать операции из своего кеша страниц.

    ExecHashJoinSaveTuple
     |
     v
BufFileWrite: небольшой буфер процесса
     |
     v
Файловый интерфейс PostgreSQL / File
     |
     v
Кеш файловой системы ОС
     |
     v
Временное файловое хранилище при необходимости

    Это упрощенная схема обычного буферизованного ввода-вывода. Не всякий вызов BufFileWrite() немедленно превращается в физическую запись на SSD.

    6.4. Почему BufFile имеет несколько физических сегментов¶

    Для больших временных данных логический BufFile может представлять несколько физических файлов. В реализации есть numFiles, массив файлов и позиция внутри текущего сегмента.

    При достижении предельного размера физического файла интерфейс переходит к следующему сегменту. Для пользователя BufFile остается логическим потоком байтов. Системные функции чтения и записи знают, в какой физический сегмент и смещение обращаться.

    Таким образом, один логический файл партии в памяти исполнителя не обязательно равен одному физическому файлу на уровне ОС.

    6.5. Ленивое создание и срок жизни¶

    При подготовке массива партий PostgreSQL создает массив указателей innerBatchFile[] и outerBatchFile[]. Но сами файловые объекты создаются при первой записи в конкретную партию.

    Если партия осталась пустой, нет смысла открывать для нее временный файл.

    BufFileCreateTemp(false) вызывается из ExecHashJoinSaveTuple(), причем буфер и служебный объект выделяются в spillCxt. Это гарантирует, что они переживут сброс рабочей памяти очередной партии. После обработки файлы закрываются и освобождаются как временные ресурсы.

    6.6. Чем временная рабочая запись отличается от WAL¶

    Это место специально не должно уводить нас к следующей лекции.

    Файлы BufFile в данном контексте — временное рабочее состояние текущего выполнения SQL, позволяющее продолжить вычисление JOIN при нехватке RAM. Если запрос прервался, такие файлы не нужны для восстановления результата транзакции.

    Они не являются постоянными таблицами, индексами и не представляют собой журнал долговечности изменений. Их назначение — промежуточная обработка данных.

    6.7. Как оценить цену работы с временными файлами¶

    Пусть по сторонам соединения отложено 75 МиБ и 375 МиБ записей в их файловом представлении.

    Объем записи ≈ 75 + 375 = 450 МиБ
При однократном последующем чтении ≈ 450 МиБ
Всего ≈ 900 МиБ логического временного ввода-вывода

    При дальнейших перераспределениях затраты могут быть выше. При 20 одновременно выполняющихся похожих запросах совокупная работа может составить много гигабайт. Это создает давление на файловый кеш ОС, накопитель, CPU для копирования и буферизацию PostgreSQL.

    Следующий вопрос: если мы хотим перечитывать один и тот же поток строк из JOIN много раз, достаточно ли нам простого файлового интерфейса BufFile? Нет: нужны указатели чтения и логика хранения кортежей. Здесь появляется tuplestore.

    7. tuplestore: поток строк, который можно прочитать повторно¶

    7.1. Почему BufFile недостаточно для Materialize¶

    Возьмем план:

    Nested Loop
  -> Seq Scan on a
  -> Materialize
       -> Seq Scan on b

    Предположим, внешний источник A возвращает 1000 строк, а B — 500. Вложенным циклам может потребоваться до 500 000 выдач внутренних строк.

    Если для каждой строки A заново выполнять Seq Scan on b, получится тысяча повторных сканирований исходного источника. Но если B не зависит от очередного значения A, можно сохранить его строки и затем многократно перечитывать.

    Для этого Materialize использует tuplestore. Это структура хранения последовательности кортежей, а не просто поток байтов. Она знает, где заканчивается одна строка и начинается другая, как возвращать их в TupleTableSlot и как поддерживать несколько позиций чтения.

    7.2. Что хранится в оперативной памяти¶

    Состояние Tuplestorestate содержит, в частности:

    • memtuples — массив ссылок на сохраненные строки, когда они еще помещаются в память;
    • memtupcount и memtupsize — количество элементов и емкость массива;
    • allowedMem и availMem — рабочий бюджет и оставшуюся часть памяти;
    • myfile — BufFile, если пришлось перейти к временному хранению;
    • readptrs — указатели чтения;
    • context — контекст, владеющий хранимыми строками.

    При tuplestore_puttupleslot() входная строка копируется в MinimalTuple и поступает в хранилище. Она не должна оставаться ссылкой на изменяемый слот дочернего узла: тот скоро будет переиспользован для следующей строки.

    Дочерний узел -> TupleTableSlot
                        |
                        v
                    Создать копию MinimalTuple
                        |
                        v
                    memtuples[]
                      [0] -> tuple A
                      [1] -> tuple B
                      [2] -> tuple C
                      ...

    Важное следствие: материализация — это дополнительное копирование и удержание памяти. Она экономит получение данных от нижележащего узла, но не убирает работу по чтению сохраненных строк.

    7.3. Три состояния TSS¶

    В PostgreSQL 18 используются три основных состояния:

    Состояние Смысл
    TSS_INMEM Строки пока хранятся в оперативной памяти
    TSS_WRITEFILE Хранилище перешло к записи во временный файл
    TSS_READFILE Выполняется чтение ранее сохраненных строк из файла

    Типичная последовательность:

    TSS_INMEM
   |
   | память перестала вмещать сохраненные строки
   v
TSS_WRITEFILE
   |
   | нужно прочитать сохраненные данные
   v
TSS_READFILE
   |
   | затем снова потребуется добавить строки
   v
TSS_WRITEFILE

    Эти переходы не означают, что PostgreSQL создает новое хранилище при каждом переключении. Меняется режим работы с тем же логическим потоком и позициями чтения/записи.

    7.4. Почему сначала копируют строки в RAM, а потом сбрасывают их в файл¶

    Пока в памяти есть место, tuplestore хранит кортежи без файловой работы. Это позволяет быстро перечитывать промежуточные данные.

    Когда объем превышает бюджет, создается BufFile, а сохраненные строки переводятся в файловое представление. Последующие строки записываются туда же.

    Нужно различать ограничения: work_mem влияет на переход к временному файлу, но не означает, что память под хранилище физически всегда равна ровно этому числу байт. Есть служебные структуры, размеры массивов и контексты памяти.

    7.5. Указатели чтения: почему их может быть несколько¶

    У tuplestore есть TSReadPointer. В нем хранятся состояние достижения конца, индекс следующей строки при чтении из RAM, либо номер файлового сегмента и смещение, если данные уже лежат во временном файле.

    При нескольких читателях одного хранилища можно сохранять независимые позиции, не повторяя исходное сканирование.

    Сохраненный поток:
  A, B, C, D, E, F

Указатель №0 -> следующая C
Указатель №1 -> следующая F

    Флаги возможностей могут разрешать возврат к началу (EXEC_FLAG_REWIND), чтение назад (EXEC_FLAG_BACKWARD) или сохранение отмеченной позиции (EXEC_FLAG_MARK). Конкретный набор возможностей определяется потребностями родительского узла.

    Важно: это локальное состояние внутри одного backend-процесса, а не автоматическая потокобезопасная структура для произвольного совместного доступа разных процессов.

    7.6. Почему Materialize может начать отдавать строки до конца входа¶

    Плохая учебная модель: «материализовать — значит сначала полностью прочитать вход».

    В общем случае Materialize может читать и сохранять строки постепенно. Родитель запросил одну строку — Materialize может взять ее из хранилища либо получить у дочернего узла и сохранить. Полное предварительное чтение не всегда требуется.

    Однако если родитель затем запрашивает возврат, будут использоваться сохраненные строки. Если поток ранее был получен только наполовину, оставшуюся часть можно получать от дочернего узла по мере необходимости.

    7.7. Конкретная цена повторного чтения¶

    Пусть b возвращает 500 строк, а внешний a — 1000 строк.

    Без материализации при обычном повторном внутреннем сканировании объем работы может составить:

    1000 сканирований × 500 строк = 500 000 получений строк из b

    С Materialize:

    Чтение из b: приблизительно один полный проход по 500 строк
Выдача через Materialize: до 500 000 строк

    Даже если данные полностью в RAM, считывание сохраненных кортежей и проверка условий соединения остаются. Если хранилище перешло на временный файл, повторные чтения способны создавать дополнительный ввод-вывод.

    tuplestore особенно хорошо подходит, когда исходный дочерний план дорог, а сохраненные данные относительно малы либо часто используются повторно.

    7.8. Merge Join и отмеченная позиция¶

    Упорядоченные входы:

    A: 1, 1, 2
B: 1, 1, 1, 2

    Для двух строк A с ключом 1 нужно сопоставить каждую с тремя правыми строками того же ключа. Да: получаем 2 × 3 = 6 пар. После обработки первой строки A для второй снова нужен проход по сохраненной правой группе. Перечитав B1..B3 для первой строки A, исполнитель должен вернуться к началу группы для второй строки A.

    Для этого используется возможность сохранения и восстановления позиции (ExecMarkPos() / ExecRestrPos()), которую может предоставить соответствующий дочерний путь. Узел Materialize через tuplestore — один из способов обеспечить требуемое повторное чтение.

    Так tuplestore связывает сразу две темы JOIN: повторные проходы Nested Loop и возврат к группам одинаковых ключей Merge Join.

    Что запомнить после раздела 7¶

    1. tuplestore хранит логический поток кортежей, а BufFile — буферизованный байтовый файловый поток.
    2. Строки в tuplestore копируются и удерживаются в памяти до перехода к файлу либо освобождения.
    3. Состояния TSS_INMEM, TSS_WRITEFILE, TSS_READFILE описывают текущий способ хранения и чтения.
    4. Наличие нескольких указателей и возможности rewind/mark позволяет повторно читать данные без перезапуска нижележащего плана.
    5. Материализация уменьшает повторную работу нижележащего узла, но не устраняет повторные выдачи и проверки строк.

    8. SharedTuplestore: почему параллельному JOIN нужно другое хранилище¶

    8.1. tuplestore одного процесса нельзя просто разделить указателем¶

    Обычный tuplestore хранит адреса строк в локальном адресном пространстве backend-процесса. Эти адреса не имеют универсального смысла для соседнего процесса PostgreSQL. Кроме того, разные исполнители должны согласованно распределять работу и понимать, какой участок сохраненных данных уже прочитан.

    Параллельный хеш JOIN может использовать несколько рабочих процессов, которые записывают строки в отложенные партии, а затем читают их для совместного поиска.

    Здесь используется SharedTuplestore — механизм совместного временного хранения кортежей между backend-процессами.

    8.2. Что действительно разделяется¶

    Очень важный момент: слово Shared не означает, что все сохраненные строки обязательно находятся в одной большой общей хеш-таблице в RAM.

    У SharedTuplestore разделяемыми являются управляющее состояние и сведения о доступных частях файлов. Сами временные данные сохраняются в файлах, которые доступны участникам через SharedFileSet и BufFile.

        Работник 1              Работник 2              Работник 3
      |                        |                       |
      +------------+-----------+-----------------------+
                   |
                   v
     Разделяемое управляющее состояние (DSM)
       - участники
       - позиции чтения частей
       - легковесные блокировки
                   |
                   v
            SharedFileSet
          /       |       \
         /        |        \
  Буферный файл A  B       C
       |            |       |
       +------------+-------+
                    |
                    v
          Сохраненные кортежи

    DSM — динамическая разделяемая память PostgreSQL. SharedFileSet — набор доступных участникам временных файлов. Это другой механизм, чем DSA, выделяющий объекты в разделяемом адресном пространстве для общей хеш-таблицы.

    8.3. Кто пишет файлы¶

    Для параллельного варианта каждый участник может создавать собственный временный файл и записывать в него свои строки. SharedTuplestoreAccessor содержит номер участника, локальный буфер записи и ссылку на файл.

    В исходниках используется:

    sts_puttuple(accessor, meta_data, tuple);

    В качестве meta_data для хеш-партий может передаваться уже вычисленный hashvalue.

    Это позволяет сохранить кортежи разных процессов без необходимости превращать каждый отдельный sts_puttuple() в запись в один глобальный файл под общей блокировкой. Согласование требуется на уровне распределения частей работы и завершения фаз.

    8.4. Как устроен дисковый блок SharedTuplestore¶

    В sharedtuplestore.c PostgreSQL 18 задано:

    #define STS_CHUNK_PAGES 4

    В стандартной сборке BLCKSZ=8192, поэтому типичная порция составляет четыре страницы, то есть 32 КиБ.

    Внутри блока SharedTuplestoreChunk есть ntuples — количество записей и overflow — сведения о продолжении большой записи за пределами обычного блока.

    Содержимое порции состоит из последовательно сохраненных строк и возможных небольших дополнительных метаданных. Порции служат единицами выдачи работы читающим процессам.

    Не путать с HashMemoryChunk! Оба могут иметь размер 32 КиБ, но первый — дисковая порция в SharedTuplestore, второй — блок плотного размещения хеш-записей в RAM.

    8.5. Как читатели не обрабатывают одну порцию дважды¶

    При параллельном сканировании несколько работников должны разобрать сохраненный набор без пропусков и без дублирования.

    Управляющее состояние содержит сведения о следующих порциях для чтения. Читающий работник получает очередную доступную порцию с синхронизацией, затем обрабатывает ее локально.

    Сохраненные порции:
  [0] [1] [2] [3] [4] [5] [6] [7]

Worker 1: [0] [3] [6]
Worker 2: [1] [4] [7]
Worker 3: [2] [5]

    Это учебный пример распределения, не обещание именно такого порядка. Существенен инвариант: каждый участок параллельного сканирования выдается для обработки одному участнику. При изменении скорости работников реальное распределение может быть иным.

    Для этого в интерфейсе используются sts_begin_parallel_scan() и sts_parallel_scan_next().

    8.6. Почему нужна граница между записью и чтением¶

    Если первый работник начал читать общий временный набор, а другой еще не завершил запись, возникает вопрос: знает ли читатель, что доступны все необходимые части?

    Для многопартийного параллельного JOIN PostgreSQL согласует фазы. Перед переходом к чтению участники вызывают sts_end_write() для своих записей, а затем синхронизируют завершение построения или распределения.

    Это позволяет отделить фазу формирования временного набора от фазы его параллельного потребления.

    В обычном tuplestore один процесс может записывать и читать уже доступную часть потока до завершения всего входа. Для SharedTuplestore характерен иной контракт: параллельное сканирование сохраненного набора с распределением порций между участниками. Не следует считать его обычным tuplestore, к которому просто добавили mutex.

    8.7. Как SharedTuplestore связан с Parallel Hash¶

    В Parallel Hash одна общая хеш-структура может строиться несколькими участниками в разделяемой памяти. Если соединение многопартийное, отложенные строки внутренней и внешней стороны сохраняются с помощью SharedTuplestore.

                       Parallel Hash Join
                           |
             +-------------+-------------+
             |                           |
             v                           v
        Общая хеш-таблица             Поздние партии
        DSA + корзины                   SharedTuplestore
        для текущей партии              + SharedFileSet
             |                           |
             v                           v
        Прямой поиск                Загрузка партии
                                          |
                                          v
                                    Общая хеш-таблица

    Во время построения общей хеш-таблицы параллельные участники согласуют изменения через барьеры. В фазах перераспределения могут использоваться, в частности, PHJ_GROW_BATCHES_ELECT, PHJ_GROW_BATCHES_REALLOCATE, PHJ_GROW_BATCHES_REPARTITION и PHJ_GROW_BATCHES_DECIDE.

    Это значительно сложнее непараллельного случая: при изменении числа партий необходимо согласованно пересоздать размещение данных, а не позволить одному работнику использовать новую маску, пока остальные используют старую.

    8.8. Почему параллельное перераспределение отличается от обычного¶

    В обычном Hash Join при переполнении текущая рабочая партия может быть переразмечена немедленно, а уже отложенные файлы — при последующей загрузке.

    В Parallel Hash изменение количества партий согласуется в фазе построения. При росте числа партий участники перераспределяют данные текущей общей хеш-структуры и ранее отложенных партий в новый набор временных файлов, затем проверяют, помещаются ли ожидаемые партии в бюджет памяти.

    Поэтому нельзя переносить псевдокод ExecHashIncreaseNumBatches() на ExecParallelHashIncreaseNumBatches() без дополнительных механизмов синхронизации и разделяемой памяти.

    Что запомнить после раздела 8¶

    1. SharedTuplestore обеспечивает обмен временными кортежами между процессами через общие метаданные и файловый слой.
    2. Записывающие процессы могут иметь собственные файлы, а читающие распределяют порции между собой.
    3. SharedTuplestore использует порции страниц; их размер и порядок выдачи — детали реализации.
    4. Общая хеш-таблица в DSA и временное разделяемое хранилище партий — два разных объекта.
    5. В Parallel Hash изменение числа партий требует согласования участников и перераспределения данных в рамках отдельной последовательности фаз.

    9. Сравнение трех временных механизмов¶

    После внутреннего устройства теперь можно точно объяснить, что именно делает каждый механизм.

    Что дает Буферизацию и файловый доступ Копии строк, rewind, mark/restore, несколько указателей Координацию записи и разделенное чтение порций
    Возможное ограничение Ввод-вывод, число файловых буферов work_mem, временный ввод-вывод Синхронизация, файловый ввод-вывод, распределение нагрузки

    9.1. Почему Materialize не обязан ускорить каждое соединение¶

    Вариант без материализации:

    1000 повторных чтений маленькой таблицы из shared_buffers

    Вариант с материализацией:

    Один проход по дочернему узлу
+ копирование строк в tuplestore
+ 1000 повторных чтений сохраненных строк

    Если дочерний узел очень дешев и возвращает мало строк, выигрыш может оказаться небольшим. При тяжелом внутреннем сканировании или дорогом расчете дочерних выражений экономия может быть значительной.

    Если материализация не помещается в память, повторное чтение временного файла может съесть заметную часть выгоды. При этом один и тот же запрос может изменять фактическую задержку из-за различий состояния файлового кеша и конкуренции за I/O.

    9.2. Почему много Batches не означает ровно столько проходов исходной таблицы¶

    Фраза «Batches=32, значит PostgreSQL перечитал таблицу 32 раза» неверна.

    Типичный непараллельный алгоритм сначала обрабатывает исходные потоки и сохраняет строки будущих партий, а затем перечитывает временные файлы, содержащие соответствующие части. В отдельных случаях динамического перераспределения временные записи могут проходить дополнительные циклы.

    Поэтому необходимо анализировать временный ввод-вывод и число обработанных строк, а не умножать размер исходной таблицы на Batches без понимания механизма.

    9.3. Почему временное хранение не равно SSD-I/O¶

    BufFileWrite() сначала может заполнить собственный буфер. Затем данные поступают в файловый слой ОС. Даже после записи в файл они могут находиться в кеше страниц ОС; физическая запись на накопитель может произойти позднее. Аналогично чтение временного файла может обслуживаться из файлового кеша.

    Временный файловый ввод-вывод остается реальной нагрузкой на систему памяти и файловую подсистему. Однако temp read/written из EXPLAIN нельзя автоматически считать числом реальных операций чтения и записи физических устройств.

    10. Диагностика: как увидеть стоимость этих механизмов в PostgreSQL¶

    10.1. Базовый EXPLAIN¶

    Для анализа существующего запроса:

    EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
SELECT o.id, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id;

    EXPLAIN ANALYZE действительно выполняет запрос. Для изменяющих SQL это важно, но наш пример с SELECT служит лишь иллюстрацией чтения плана. Параметры памяти при желании можно исследовать локально для учебной сессии.

    Предположим, получили условный фрагмент:

    Hash Join
  Hash Cond: (o.customer_id = c.id)
  Buffers: shared hit=40000 read=1200,
           temp read=18000 written=18000
  -> Seq Scan on orders o
  -> Hash
       Buckets: 65536
       Batches: 32 (originally 2)
       Memory Usage: 8192kB
       -> Seq Scan on customers c

    Разбираем по слоям:

    1. Batches: 32 (originally 2) — число партий выросло во время исполнения. Значит, первоначальная модель не обеспечила достаточное распределение в рамках рабочего бюджета либо столкнулась с неблагоприятным распределением.
    2. Buckets: 65536 — число корзин хеш-таблицы, не число временных файлов.
    3. Memory Usage: 8192kB — измеренный пик учетного расхода хеш-структуры. Это не совокупный предел памяти всей сессии, всего запроса или всех параллельных работников.
    4. temp read/written — обращения к блокам временных рабочих файлов; при стандартном размере блока 8 КиБ 18000 блоков соответствуют около 140,6 МиБ за каждое направление учета. Это не обязательно число уникальных страниц и не точное число физических I/O операций SSD.
    5. Показатели родительского Hash Join могут включать работу дочерних узлов. Складывать их со всеми дочерними значениями Buffers нельзя.

    10.2. Связь размера строк и переполнения¶

    Предположим, у Hash одинаковое actual rows=1 000 000 в двух запросах, но разный состав сохраняемых данных.

    -- Нужен только идентификатор:
SELECT o.id
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id;

-- Нужны дополнительные данные клиента:
SELECT o.id, c.name, c.description
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id;

    При некоторых планах второй запрос вынужден сохранять более широкие строки внутренней стороны. Он может перейти к большему числу партий даже при правильной оценке количества клиентов.

    Значит, при анализе Hash нужно проверять число строк и их ширину, а также расположение вычислений в дереве плана. В зависимости от выбранного плана промежуточные значения могут формироваться до построения хеш-таблицы или позже.

    10.3. Распределение ключей против ошибки статистики¶

    Две ситуации могут давать похожий симптом Batches:

    Сценарий А. Планировщик ожидал 100 тысяч строк, получил миллион. Первоначальный расчет размера хеш-таблицы ошибся из-за количества строк.

    Сценарий Б. Ожидал и получил миллион, но большинство строк имеют один популярный хеш. Распределение партий не уменьшает рабочий набор.

    Исправления различаются. В первом случае важна статистическая модель числа строк. Во втором — свойства ключей и ограничения самого алгоритма разбиения.

    10.4. Что означают temp read / written¶

    BUFFERS различает:

    • shared hit/read — работу с блоками постоянных таблиц и индексов через общий буферный кеш;
    • temp read/written — обращения к блокам временных рабочих файлов сортировки, хеширования, материализации и других операций;
    • local hit/read — локальные буферы временных таблиц, это отдельная категория.

    Особенно важно: временные рабочие файлы JOIN и временные SQL-таблицы — разные механизмы. Поэтому рост temp read/written не доказывает использование временной таблицы CREATE TEMP TABLE.

    Если активирован track_io_timing, можно получить дополнительные временные показатели ввода-вывода; их следует интерпретировать с учетом файлового кеша ОС.

    10.5. Как увидеть повторную запись из-за роста партий¶

    Одного поля Batches недостаточно для точного подсчета стоимости перестройки.

    Полезно сравнить:

    Первоначальные Batches
Фактические Batches
Пик Memory Usage
Количество входных строк
temp read/written
Execution Time

    Если Batches выросло много раз и temp written велик, это согласуется с несколькими этапами перераспределения и сохранением отложенных данных. Но конкретное количество таких этапов по одному EXPLAIN восстановить нельзя.

    Batches: 32 (originally 2) показывает начальное и конечное число партий, а не полный журнал 2 -> 4 -> 8 -> 16 -> 32 с продолжительностями и размерами каждого этапа.

    10.6. Наблюдение на уровне базы и сервера¶

    В production полезны:

    • pg_stat_database.temp_files и temp_bytes — совокупные показатели созданных временных файлов и записанных в них данных по базе;
    • pg_stat_statements — если расширение установлено, накопленная статистика вызовов, времени и временных блоков для SQL;
    • log_temp_files — запись информации о больших временных файлах в лог при их удалении, если настройка включена;
    • temp_file_limit — ограничение допустимого объема временных файлов для процесса с соответствующими оговорками реализации;
    • EXPLAIN (ANALYZE, BUFFERS, TIMING OFF) — позволяет получить счетчики с меньшей стоимостью детального измерения времени узлов.

    Отдельно следует сопоставлять временный ввод-вывод с нагрузкой на файловую систему, использованием RAM и конкурирующими запросами. temp_bytes — не количество физических операций SSD и не оценка задержки конкретного SQL.

    10.7. Что проверять при нескольких параллельных JOIN¶

    Необходимо различать:

    • обычный Hash под параллельным планом, когда разные работники могут строить свои хеш-таблицы;
    • Parallel Hash — общую хеш-структуру с динамической разделяемой памятью и согласованием фаз.

    В первом варианте расход памяти на построение может дублироваться. Во втором меньше дублируется структура, но появляются синхронизация, общие метаданные и временные наборы партий.

    При диагностике смотрим Workers Planned, Workers Launched, статистику по работникам, число партий и временный ввод-вывод. Ускорение не обязано расти пропорционально числу работников.

    Семь главных выводов¶

    1. HashJoinTupleData содержит ссылку цепочки и вычисленный хеш, а после выровненного заголовка располагается MinimalTuple с данными строки.
    2. dense_alloc() хранит множество записей в блоках HashMemoryChunk размером около 32 КиБ, сокращая накладные расходы на отдельные выделения и облегчая перестройку структуры.
    3. В PostgreSQL 18 партия вычисляется через pg_rotate_right32; при удвоении числа партий новая маска может оставить строку в прежней партии либо перенести ее в более позднюю.
    4. ExecHashIncreaseNumBatches() перераспределяет записи текущей рабочей структуры по физическим блокам, а не просто заменяет число в заголовке хеш-таблицы.
    5. При сильном перекосе хешей дальнейшее удвоение партий может не уменьшить рабочий объем; PostgreSQL способен отключить рост и превысить расчетный бюджет памяти.
    6. BufFile, tuplestore и SharedTuplestore устроены по-разному: байтовый временный файл, локальный поток кортежей с повторным чтением и межпроцессное хранилище порций соответственно.
    7. В production недостаток RAM для JOIN способен превратиться в массовое копирование, временный ввод-вывод и конкуренцию между запросами; причина определяется по распределению строк и хешей, памяти, партиям и измерениям.

    Куда еще можно копнуть в пределах JOIN¶

    Первый следующий слой — механизм выделения и освобождения памяти PostgreSQL для хеш-операций. Разбор MemoryContext, dense_alloc, palloc, DSA и границ жизни партии объяснит, почему Memory Usage не равен точному общему RSS backend-процесса и что именно освобождается при ExecHashTableReset().

    Второй слой — синхронизация Parallel Hash до операций с общей памятью. По состояниям барьеров и атомарным операциям станет понятно, почему участники не могут произвольно начать поиск до завершения построения и перераспределения. Это полезно для диагностики слабого масштабирования параллельных JOIN.

    Оба слоя остаются внутри темы исполнения соединений и не требуют переходить к WAL и долговечности транзакций.
