    8.1. PostgreSQL Monitoring & Wait Events Internals: от наблюдения к доказательству причины задержки¶

    Углубленная лекция магистратуры · PostgreSQL 18 · REL_18_STABLE · блок 8, продолжение лекции 08.

    Предмет: внутренняя организация текущей активности, накопительной статистики, pg_stat_statements, queryid, wait events и LWLocks как наблюдаемого источника конкуренции; точность измерений и диагностика под нагрузкой. Механика heavyweight Lock Manager, очереди row locks и VACUUM/freezing разбираются отдельно в 08.2 и 08.3. Темы блока 9 здесь отсутствуют.

    Исполнение примеров: только тестовая БД PostgreSQL 18. Для просмотра чужих SQL и ожиданий нужна соответствующая роль, обычно pg_read_all_stats. Названия системных функций и структур ниже относятся к ветке REL_18_STABLE; подробности уровня структур и порядка вызовов являются текущей реализацией, а не стабильным внешним API.

    0. Инцидент: «PostgreSQL сообщает разные правды»¶

    Сервис работал со средним временем ответа около 20 мс. После увеличения нагрузки p99 достиг 4–6 секунд. CPU стабильно ниже 30%. В pg_stat_activity одновременно видим тридцать active backend-процессов. Администратор смотрит pg_stat_statements: число вызовов почти не растет, хотя сервис каждую секунду отправляет новые SQL. В другом окне у части backend-процессов wait_event уже исчез, а значения по статистике таблиц сохраняются прежними. Создается впечатление, что PostgreSQL ведет противоречивый учет.

    Почему так? Потому что мы сравнили три разных измерительных прибора. Один публикует текущий статус процесса. Второй накапливает завершенные операции и периодически переносит счетчики в разделяемую память. Третий агрегирует стоимость SQL-структур и хранит результаты отдельно. У каждого свой момент фиксации события, своя задержка публикации и своя гранулярность.

    Первое обманчивое упрощение: «Есть одна таблица статистики, значит сервер в каждой строке отражает одну согласованную фотографию системы». Это не гарантируется. В действительности источники собираются разными путями, а даже state и wait_event не являются атомарной парой с общим timestamp. PostgreSQL предпочитает дешевое наблюдение без глобальной остановки backend-процессов. Плата за это — частичная и асинхронная картина.

    Наша цель — проследить механизм от строки C-кода, сообщающей ожидание, до SQL-запроса, который администратор запускает при расследовании. Для каждого прибора обсудим, что он измеряет, что пропускает, какую цену добавляет и каким дополнительным наблюдением подтвердить гипотезу.

                           ┌─ Текущая активность ─── PgBackendStatus ── pg_stat_activity
Backend processes ─────┼─ Текущие ожидания ───── PGPROC.wait_event_info ── pg_wait_events
                       ├─ Накопительные счетчики ─ локальные pending → shared stats
                       └─ Цена SQL-шаблонов ────── pg_stat_statements (extension)

ОС / CPU / диск ────── отдельная реальность: PostgreSQL видит только то, что измеряет.

    Ключевой вопрос: как на наблюдаемых данных доказать «запрос ждал LWLock», а не просто обнаружить совпадение во времени?

    I. Как PostgreSQL публикует текущую активность¶

    1. pg_stat_activity: почему процесс обязан сообщать о себе¶

    1.1. Backend и область PgBackendStatus¶

    Когда PostgreSQL обслуживает клиентское соединение, соответствующий backend-процесс выполняет SQL независимо от наших диагностических запросов. Администратор не должен останавливать этот процесс, чтобы спросить, что он делает. В общем случае сервер использует разделяемую память (shared memory): процесс публикует компактную запись о текущем состоянии, а другой процесс ее читает.

    В src/backend/utils/activity/backend_status.c находится массив BackendStatusArray с элементами PgBackendStatus. При инициализации PostgreSQL резервирует места для возможных backend и вспомогательных процессов. Запись содержит PID, тип backend, состояние, время начала запроса и транзакции, OID БД и пользователя, query_id и другие метаданные. Строка SQL, application_name и ряд других строк живут в отдельных разделяемых буферах, на которые ссылается запись.

    Вызов pgstat_report_activity(state, cmd_str) обновляет статус конкретного backend. Это нормальная часть исполнения запросов, а не работа внешнего мониторинга. Поэтому pg_stat_activity может показать active, idle, idle in transaction и последний/текущий текст SQL без сбора из журнала запросов.

    client socket → backend PID=42100
                    │
                    ├─ обрабатывает SQL
                    ├─ pgstat_report_activity(...)
                    ▼
      shared memory: PgBackendStatus[ProcNumber]
        state, query_start, xact_start, query_id
        указатель → текст SQL (ограниченный буфер)
                    │
                    ▼
     соседний backend читает pg_stat_activity

    Нужно различать PID, который может со временем переиспользоваться ОС, и внутренний слот процесса (ProcNumber), который тоже не является вечным идентификатором. Для привязки к конкретной сессии полезна пара pid + backend_start, а для графа приложения — application_name и собственный идентификатор операции.

    1.2. Кто и когда пишет в общий статус¶

    Публикация состояния происходит на определенных этапах обработки команды: переход к исполнению, завершение команды, переход к ожиданию клиента, начало/конец транзакции. Нет гарантии, что каждый шаг приложения соответствует отдельной смене state; PostgreSQL показывает состояние собственного backend, а не логическую стадию REST-обработчика.

    Например, backend может завершить UPDATE и перейти в idle in transaction: SQL уже закончился, но транзакция и ее ресурсы продолжают жить. Поле query при простое содержит текст последнего запроса, а query_start в этом состоянии — время старта последней команды. Пытаться вычислить длительность текущего выполнения как now() - query_start для idle — ошибка диагностики.

    SELECT pid, backend_start, application_name,
       state, wait_event_type, wait_event,
       query_start, xact_start, state_change,
       CASE WHEN state = 'active'
            THEN clock_timestamp() - query_start END AS active_age,
       CASE WHEN xact_start IS NOT NULL
            THEN clock_timestamp() - xact_start END AS transaction_age,
       CASE WHEN state LIKE 'idle%'
            THEN clock_timestamp() - state_change END AS idle_age
FROM pg_stat_activity
WHERE backend_type = 'client backend'
ORDER BY xact_start NULLS LAST, pid;

    clock_timestamp() использован намеренно: now() (transaction_timestamp()) внутри долгой диагностической транзакции не меняется. При коротком автономном SELECT это не существенно; при многократном чтении внутри одного BEGIN — критично. Сам набор значений из pg_stat_activity при этом может кешироваться в локальном снимке транзакции, о чем поговорим ниже.

    1.3. Конкурентная запись и чтение: st_changecount¶

    Что если диагностический backend читает запись в момент, когда владелец обновляет state, времена и строку запроса? Без защиты можно получить «полусобранную» запись — старый state с новыми полями. Ставить одну глобальную тяжелую блокировку на каждый SELECT диагностики было бы дорого: мониторинг смог бы остановить сервер, который пытается измерить.

    PostgreSQL использует счетчик изменений st_changecount и протокол повторного чтения. Писатель помечает начало изменения (счетчик становится нечетным), копирует новое состояние, затем помечает завершение (счетчик снова четный). Читатель запоминает версию перед копированием и после него. Если версии различаются или обнаружена нечетная версия, чтение повторяется.

    /* Концептуальная схема. Реальные макросы и барьеры — в backend_status.h. */
writer:
    PGSTAT_BEGIN_WRITE_ACTIVITY(beentry);
    beentry->st_state = state;
    /* ... обновление прочих полей и текстовых буферов ... */
    PGSTAT_END_WRITE_ACTIVITY(beentry);

reader:
    do {
        pgstat_begin_read_activity(beentry, before);
        copy_status_and_strings_to_local_memory();
    } while (!pgstat_end_read_activity(beentry, before));

    Здесь есть тонкость: протокол обеспечивает согласованность прочитанного набора полей конкретной записи в рамках принятого протокола, но не создает глобальный снимок всех backend-процессов в один момент. Пока читали PID A, PID B уже мог завершиться. А для wait_event используется отдельный источник — его обновления не синхронизируются со сменой state как единая транзакция мониторинга. Таким образом, даже корректный reader не способен обещать атомарную фотографию всей системы.

    Исходники PostgreSQL 18: backend_status.c, pgstat_report_activity(), pgstat_read_current_status(); соответствующие макросы в src/include/utils/backend_status.h.

    1.4. Цена track_activity_query_size¶

    Текст текущего запроса хранится в заранее выделенной области. Размер задает track_activity_query_size (обычное значение по умолчанию — 1024 байта), и параметр задается на старте сервера. В PostgreSQL 18 код расчета разделяемой памяти содержит произведение размера текстового буфера на число слотов, а не выделение по фактической длине активных SQL. Даже если половина клиентов выполняет SELECT 1, резервирование все равно есть.

    Упрощенная оценка только для буфера текстов: при 2000 слотах и 16 КиБ на слот потребуется приблизительно 31,25 МиБ против около 1,95 МиБ при 1 КиБ. Дополнительно существует локальная копия при считывании статусов. Поэтому «поставим 1 МБ, чтобы видеть любой SQL» может дорого обойтись по памяти, особенно на сервере с большим числом backend.

    SHOW track_activities;
SHOW track_activity_query_size;
SHOW max_connections;

    Содержимое query может включать секреты и персональные данные, особенно если клиент подставляет литералы. Мониторинг нельзя бездумно открывать всем пользователям или логировать целиком.

    1.5. Права и пределы точности¶

    pg_stat_activity — SQL-интерфейс для метаданных, а не источник истории. Короткий SQL, завершившийся между опросами, никогда не появится в выборке. Другие сессии могут быть показаны с усеченными или скрытыми подробностями в зависимости от прав. Роль pg_read_all_stats подходит для диагностического пользователя лучше, чем выдача полного суперпользователя.

    Отдельная ловушка: если track_activities = off, часть полей текущей активности недоступна, хотя наличие соединения остается наблюдаемым. И еще: один серверный процесс может быть параллельным worker, а не клиентским соединением; всегда смотрите backend_type и при необходимости leader_pid.

    Инженерный вывод: у pg_stat_activity отличная временная локальность, но нет непрерывной истории. Она нужна для поиска симптома «кто ждет сейчас», а не для ранжирования всех запросов за сутки.

    2. Почему state и wait_event могут расходиться¶

    2.1. Два независимых источника в одном SELECT¶

    Интуитивная модель: раз строки в pg_stat_activity выглядят как единая структура, значит state = active и wait_event = Lock были получены в один такт процессора. На практике state читается из опубликованного backend status, а wait event — из связанного с процессом PGPROC.wait_event_info. Вызовы пишут эти сведения по разным поводам. Официальная документация PostgreSQL 18 прямо предупреждает, что столбцы не синхронизируются между собой с целью снижения накладных расходов, поэтому могут встречаться кратковременные расхождения.

    Время ───────────────────────────────────────────────────────────────▶
backend:   active ──────────── active ───────────── idle
wait:      NULL ── LWLock ──── NULL ── IO ──────── ClientRead
reader:           ▲ snapshot fields          ▲ event field read
                  разные моменты наблюдения

    Значит, отдельный снимок с state='idle' и неожиданным wait_event — повод повторить замер, а не доказательство повреждения статистики.

    2.2. Снимок текущей активности внутри диагностической транзакции¶

    В pgstat_read_current_status() читающий backend делает локальную копию массива статусов и повторно использует ее в пределах диагностической транзакции. Это помогает коррелировать несколько запросов по состояниям, но вводит неожиданность при ручном анализе: вы нажимаете «выполнить запрос еще раз», а видите старые query_start и state.

    -- Сессия диагностики. Показывает эффект кеширования состояния.
BEGIN;
SELECT pid, state, query_start FROM pg_stat_activity;
-- В другой сессии начните и завершите любой запрос.
SELECT pid, state, query_start FROM pg_stat_activity;
SELECT pg_stat_clear_snapshot();
SELECT pid, state, query_start FROM pg_stat_activity;
ROLLBACK;

    Для живого расследования удобнее выполнять повторные выборки в autocommit. Если нужен единый взгляд на несколько агрегированных представлений, напротив, придется сознательно выбрать подходящий режим кеширования, а не механически всегда сбрасывать снимок.

    2.3. pg_wait_events: словарь, а не счетчик времени¶

    В PostgreSQL 18 системное представление pg_wait_events предоставляет расшифровку известных событий (type, name, description). Его можно соединить с pg_stat_activity, чтобы вместо криптической метки получить человеческое описание.

    SELECT a.pid, a.application_name, a.state,
       a.wait_event_type, a.wait_event,
       w.description
FROM pg_stat_activity a
LEFT JOIN pg_wait_events w
  ON w.type = a.wait_event_type
 AND w.name = a.wait_event
WHERE a.wait_event IS NOT NULL
ORDER BY a.pid;

    Что этот запрос не показывает: сколько миллисекунд процесс уже находился в данном ожидании и сколько раз попадал в него за прошлый час. Стандартные wait_event-поля — текущее состояние, у них нет встроенной накопительной «длительности ожидания по типам на SQL». Для приблизительной временной доли потребуется выборочное наблюдение (sampling) или специализированный сборщик событий.

    II. Накопительная статистика PostgreSQL: как счетчик добирается до SELECT¶

    3. Два конвейера статистики с принципиально разными часами¶

    3.1. Текущая активность и cumulative stats не используют один и тот же конвейер¶

    Пока выполняется UPDATE, backend может менять локальные счетчики обращений к страницам, чтения, количества строк и других операций. Постоянно писать каждое приращение в общие структуры было бы дорого: тысячи процессов конкурировали бы за одну и ту же память. Поэтому PostgreSQL 18 накапливает большую часть cumulative statistics сначала в памяти самого backend, а затем периодически переносит их в структуры shared memory.

    Выполнение SQL в backend A
  ├─ report current state ──────────▶ PgBackendStatus (почти сразу)
  ├─ report wait begin/end ─────────▶ PGPROC.wait_event_info (по событию)
  └─ count access ──▶ local pending ──▶ pgstat_report_stat()
                                           │
                                           ▼
                                  shared cumulative stats
                                           │
                                  pg_stat_database / pg_stat_io / ...

    Это объясняет привычную загадку: запрос уже выполняется, но в накопительной статистике он как будто еще не создал новых операций. Не потому что сервер ленится считать. Он еще не обязан публиковать все накопленные значения.

    3.2. Почему данные переносятся с задержкой¶

    В ветке PostgreSQL 18 подсистема pgstat.c использует механизм pgstat_report_stat() и минимальный интервал публикации PGSTAT_MIN_INTERVAL — обычно 1000 мс. Backend, завершивший активную работу и переходящий к простоям, публикует накопленные изменения при подходящих обстоятельствах; долго выполняющийся запрос не обязан каждую секунду показывать все новые счетчики.

    Реальный механизм сложнее таймера «каждую секунду»: учитываются pending-записи, возможность получить внутренние средства синхронизации, принудительные и отложенные flush. Нельзя обещать жесткую задержку ровно одну секунду. Кроме того, отдельные виды статистики имеют собственные точки обновления.

    /* Имена из подсистемы PostgreSQL 18; схема без деталей реализации. */
#define PGSTAT_MIN_INTERVAL 1000

/* По мере работы backend обновляет локальные pending counters. */
/* При допустимой точке публикации: */
pgstat_report_stat(/* force = */ false);
/* переносит накопленные изменения в shared statistics, если можно */

    Термин flush статистики означает перенос счетчиков в shared memory; его не надо путать с fsync WAL. Здесь мы обсуждаем наблюдаемость, а не гарантию сохранения транзакций.

    3.3. Почему PostgreSQL 18 обходится без отдельного collector process¶

    На старых версиях PostgreSQL существовала самостоятельная архитектура сборщика статистики, через которую передавались сообщения. В PostgreSQL 15 подсистема была переработана: накопительные данные теперь живут в разделяемой памяти, а процессы обновляют их через механизм локального накопления и публикации. Применять к PostgreSQL 18 старую модель «backend послал UDP-сообщение stats collector, тот записал файл» — техническая ошибка.

    Современная система использует разделяемые хеш-структуры, записи статистики по видам объектов и внутренние средства синхронизации для безопасного объединения. Идея: не превращать каждое увеличение счетчика в глобальный конфликт. Каждый backend сначала изменяет собственный дешевый локальный учет, а в общие данные обращается гораздо реже.

    При штатном завершении экземпляра накопительная статистика сохраняется в pg_stat и может пережить перезапуск. После нештатного завершения такая статистика сбрасывается. Это не характеризует долговечность пользовательских таблиц — счетчики мониторинга имеют другой жизненный цикл.

    3.4. Четыре момента времени у одного события¶

    Для одного SQL полезно мысленно держать четыре момента:

    1. T0 — начало запроса: backend публикует active; наблюдается query_start.
    2. T1 — работа: локальные счетчики увеличиваются; по необходимости появляются и исчезают wait events.
    3. T2 — конец выполнения: агрегатор SQL может обновить статистику pg_stat_statements по успешному завершению соответствующей фазы; backend меняет состояние.
    4. T3 — перенос накопительных счетчиков: другие cumulative views получают приращение после публикации.

    В зависимости от того, в какой момент и каким запросом смотреть на систему, можно увидеть разные части одного события. Не сравнивайте счетчики разных источников, не указав окна и момент наблюдения.

    4. stats_fetch_consistency: почему читатель тоже кеширует значения¶

    4.1. Еще один кеш — на стороне диагностического backend¶

    Представим, что писатель уже перенес счетчики в shared memory. Почему диагностический SELECT все равно возвращает старое значение? Потому что по умолчанию PostgreSQL 18 использует stats_fetch_consistency = cache. Первый запрос к cumulative statistics по определенному объекту кеширует данные до конца текущей транзакции диагностического backend. Это защита от внутренней несогласованности нескольких обращений в одном SQL и лишнего чтения.

    Параметр имеет три режима:

    Режим Что делает читающий backend Цена и когда применять
    none Каждый доступ к cumulative stats повторно читает shared memory Хорош для одноразовых частых запросов мониторинга; данные могут меняться между чтениями
    cache (по умолчанию) При первом чтении кеширует статистику конкретного объекта до конца транзакции Баланс согласованности и памяти; повторный SELECT внутри BEGIN видит старые значения
    snapshot При первом обращении готовит общий снимок доступных статистических данных соответствующей области Лучше для согласованного анализа нескольких счетчиков; цена памяти и построения снимка растет с числом объектов 
    SHOW stats_fetch_consistency;
SET stats_fetch_consistency = 'none';
SELECT datname, xact_commit, xact_rollback
FROM pg_stat_database
WHERE datname = current_database();

    Параметр влияет на чтение накопительных счетчиков. Нельзя утверждать, что none превращает всю pg_stat_activity в атомарную и абсолютно свежую выборку. В этой подсистеме отдельная логика локального снимка активностей.

    4.2. pg_stat_clear_snapshot() и pg_stat_force_next_flush() — разные операции¶

    pg_stat_clear_snapshot() сбрасывает кешированные статистические данные и снимки читающей сессии, чтобы при следующем запросе получить их снова. Это не распоряжение всем другим backend немедленно опубликовать свои pending-счетчики.

    pg_stat_force_next_flush() просит текущий backend принудительно перенести собственные накопленные статистические изменения при следующей подходящей точке публикации. Функция полезна для тестирования подсистемы; она не выполняет глобальную синхронизацию состояния всех процессов и не заменяет завершение SQL.

    -- Читающий процесс:
SELECT pg_stat_clear_snapshot();

-- В СЕССИИ, которая сама только что создавала нагрузку:
SELECT pg_stat_force_next_flush();
-- При следующем вызове механизма публикации ее локальные счетчики
-- будут перенесены без обычного ограничения минимальным интервалом.

    Даже после обеих операций нет обещания «все счетчики из всех backend теперь отражают одну миллисекунду». Следовательно, мониторинговые дашборды корректнее строить как наблюдаемые тренды и дельты за окна, а не как бухгалтерскую сверку каждого SQL до единицы в реальном времени.

    4.3. Учитываем собственную статистику текущей транзакции¶

    Для таблиц существуют pg_stat_xact_all_tables, pg_stat_xact_user_tables и родственные представления. Они позволяют конкретному backend увидеть статистику текущей транзакции, которая еще не попала в общие накопительные представления. Это полезно как демонстрация причинной цепочки «локальный счетчик существует → общий счетчик позже».

    -- Тестовая таблица, созданная заранее:
BEGIN;
SELECT count(*) FROM demo_stats WHERE id > 0;
SELECT relid::regclass, seq_scan, seq_tup_read
FROM pg_stat_xact_user_tables
WHERE relid = 'demo_stats'::regclass;
COMMIT;

    Счетчики зависят от выбранного плана, поэтому для демонстрации предварительно стоит оценить EXPLAIN, а не обещать seq_scan = 1 для любого набора данных. В уроке важен сам механизм текущих транзакционных счетчиков.

    4.4. Что означает сброс счетчиков после сбоя¶

    Кратковременный сбой экземпляра PostgreSQL может привести к обнулению накопительных статистических счетчиков, хотя данные пользовательских таблиц восстановились корректно по WAL. Если система мониторинга вычисляет rate = (counter_new - counter_old) / seconds, на таком перепаде получится отрицательная дельта. Ее нужно распознавать как перезапуск/сброс, а не как «отрицательное число транзакций».

    SELECT stats_reset FROM pg_stat_database
WHERE datname = current_database();

SELECT stats_reset FROM pg_stat_bgwriter;

    Не вызывайте без причины pg_stat_reset(): сброс некоторых статистических счетчиков способен повлиять на решения autovacuum. Подробная механика очистки остается за 08.3.

    Итог раздела: наблюдаемый счетчик — результат производящего события, отложенной публикации и правил чтения. Дельта между двумя SELECT — это не всегда все события, произошедшие между ними в реальном времени.

    III. pg_stat_statements: как PostgreSQL группирует SQL и измеряет его цену¶

    5. Зачем отдельная подсистема, если уже есть pg_stat_activity¶

    5.1. Завершенный запрос исчезает с экрана¶

    В сервисе запрос UPDATE accounts SET balance = balance + 10 WHERE id = 42 выполняется 8 мс. Мы опрашиваем pg_stat_activity один раз в секунду. Шансы поймать именно этот запрос невелики. Но если таких SQL миллион в минуту, они могут составить главный источник нагрузки. Нужно накапливать стоимость повторяющихся запросов, не храня каждое исполнение в подробном журнале.

    pg_stat_statements — поставляемое с PostgreSQL расширение. Оно измеряет статистику планирования и исполнения SQL и группирует запросы с эквивалентной после анализа структурой. Его задача — получить ответ «какие классы запросов потребляют больше всего времени и ресурсов».

    SELECT ... WHERE id = 100       ┐
SELECT ... WHERE id = 200       ├─ одна структурная группа
SELECT ... WHERE id = 300       ┘
              │
              ▼
      (dbid, userid, queryid, toplevel)
              │
              ▼
 calls, total_exec_time, rows, block counters,
 WAL, JIT, parallel-worker counters и т. д.

    Группировка экономит память, но стирает последовательность отдельных обращений. Агрегатор не хранит полноценную трассировку каждого SQL и не вычисляет p95/p99 по вызовам.

    5.2. Подключение: код расширения работает внутри backend¶

    Расширение требует shared_preload_libraries, поскольку резервирует общие структуры памяти и регистрирует обработчики (hooks) на стадии запуска сервера. Простого CREATE EXTENSION без предварительной загрузки библиотеки недостаточно. Для SQL-представления CREATE EXTENSION выполняют в нужной базе; сбор происходит на уровне всего экземпляра для разных БД.

    # postgresql.conf; после изменения нужен рестарт PostgreSQL
shared_preload_libraries = 'pg_stat_statements'
compute_query_id = on
pg_stat_statements.max = 10000
pg_stat_statements.track = top
pg_stat_statements.track_planning = off

    CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SHOW shared_preload_libraries;
SHOW compute_query_id;
SELECT * FROM pg_stat_statements_info;

    compute_query_id = auto также может активировать вычисление ID при наличии подходящего модуля. Удобно включать on явно для предсказуемой диагностической среды. Настройки и число допустимых записей влияют на дополнительную общую память и конкуренцию при обновлениях.

    5.3. Где именно встраивается pg_stat_statements¶

    В contrib/pg_stat_statements/pg_stat_statements.c расширение регистрирует обработчики на нескольких этапах исполнения, например post_parse_analyze_hook, planner_hook, ExecutorStart_hook, ExecutorRun_hook, ExecutorFinish_hook, ExecutorEnd_hook и обработчик utility-команд. Это текущий механизм PostgreSQL 18, полезный для понимания того, что именно измеряет подсистема.

    /* Выдержка с опущенными деталями — имена реальных hooks. */
prev_planner_hook = planner_hook;
planner_hook = pgss_planner;

prev_ExecutorStart = ExecutorStart_hook;
ExecutorStart_hook = pgss_ExecutorStart;

prev_ExecutorEnd = ExecutorEnd_hook;
ExecutorEnd_hook = pgss_ExecutorEnd;

    Механизм позволяет измерять время стадий и прирост доступных счетчиков. Например, обработчик планирования может зафиксировать время и разницу показателей BufferUsage, а обработчики Executor — показатели исполнения. Передать в агрегатор время чужого SQL, который еще не завершился, нельзя по обычному пути финального учета исполнения: его финальная статистика еще не сформирована.

    5.4. Почему plans и calls не обязаны совпадать¶

    В одной архитектуре приложения запрос может один раз планироваться и много раз исполняться с сохраненным планом. Тогда plans будет меньше calls. Иногда запрос успешно спланирован, но исполнение завершилось ошибкой, из-за чего набор обновленных счетчиков может различаться. В любом случае plans имеет смысл только при pg_stat_statements.track_planning = on; иначе он обычно равен нулю независимо от реальной работы planner.

    SELECT queryid, plans, calls,
       round(total_plan_time::numeric, 1) AS plan_ms,
       round(total_exec_time::numeric, 1) AS exec_ms,
       left(query, 100) AS query_sample
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database
              WHERE datname = current_database())
ORDER BY total_exec_time DESC
LIMIT 10;

    Следует помнить: длительность агрегированного исполнения включает ожидания, произошедшие в пределах измеряемого исполнения, и не обязана совпадать с временем всего пользовательского HTTP-запроса (сеть, приложение, иные SQL и очереди могут быть вне учета).

    6. queryid: как разные тексты превращаются в одну группу¶

    6.1. Простая модель «хешируем строку SQL» ломается¶

    Пусть два запроса отличаются только константой:

    SELECT balance FROM accounts WHERE id = 10;
SELECT balance FROM accounts WHERE id = 20;

    Если вычислить хеш исходного текста, значения будут различаться. Тогда миллион запросов с разными id займет миллион записей статистики — неприемлемо. Поэтому PostgreSQL вычисляет идентификатор на основе проанализированного дерева запроса (post-parse-analysis query tree), игнорируя значения определенных констант и учитывая существенные элементы структуры. Механизм внутренней сериализации/хеширования дерева нередко называют query jumbling; в исходниках фигурируют JumbleQuery и queryId.

    Текст SQL
    │
    ▼
Parse → Parse analysis (имена → объекты/типы)
    │
    ▼
Query tree — структурные поля, выражения, OID
    │
    ▼
JumbleQuery → representation → 64-bit queryid
    │
    ▼
Группировка pg_stat_statements + текст-представитель

    Это идентификатор структуры, а не отпечаток букв SQL и не криптографический хеш с гарантированной уникальностью. Документация предупреждает о редких коллизиях и об отсутствии обещания стабильности через major upgrades.

    6.2. Почему один текст может получить разные queryid¶

    Рассмотрим два подключения с разным search_path. В обоих выполняется текст SELECT * FROM items. Если это разные таблицы с разными OID, смысл запросов различен. Анализатор привязывает имя к конкретному объекту; queryid может отличаться даже при одинаковом исходном SQL.

    Другой пример — удаление и создание функций и таблиц. Изменения каталожных OID и особенностей внутреннего дерева могут влиять на идентификатор. queryid допустимо использовать для связывания логов и агрегатов в пределах сопоставимого окружения, но нельзя делать его вечным бизнес-ключом или надежным межкластерным идентификатором.

    -- Тест: создайте две одноименные таблицы в разных схемах.
CREATE SCHEMA IF NOT EXISTS a;
CREATE SCHEMA IF NOT EXISTS b;
CREATE TABLE IF NOT EXISTS a.items (id integer);
CREATE TABLE IF NOT EXISTS b.items (id integer);

SET search_path = a, public;
SELECT * FROM items;
SET search_path = b, public;
SELECT * FROM items;

SELECT queryid, calls, left(query, 100)
FROM pg_stat_statements
WHERE query ILIKE '%from items%';

    Наблюдаемый результат зависит от накопленной статистики и настроек; перед экспериментом удобно работать в отдельной учебной БД, чтобы не путаться с другими запросами.

    6.3. Что означает нормализованный текст $1¶

    В колонке query pg_stat_statements обычно показывает представительный текст группы с заменой подходящих констант параметрами $1, $2 и т. д. Этот текст формируется на основе одного из исходных текстов, а не генерируется из абстрактного дерева с одинаковым стилем. Поэтому пробелы, алиасы и оформление могут выглядеть по-разному даже при одинаковой семантике.

    Выполнено:
  SELECT balance FROM accounts WHERE id = 17;
  SELECT balance FROM accounts WHERE id = 18;

В агрегате может быть:
  SELECT balance FROM accounts WHERE id = $1;
  calls = 2

    Параметризация отображения не означает, что клиентские SQL автоматически стали prepared statements. Это формат хранения текста в статистике. Также совпадение структур не означает одинаковый план и одинаковую скорость: распределение значений, статистика колонок и параметры могут менять план исполнения. Здесь связь с пройденными лекциями по planner, но заново их не открываем.

    6.4. Ключ записи — шире одного queryid¶

    Формальная группировка pg_stat_statements зависит от dbid, userid, queryid и признака toplevel. Поэтому один и тот же SQL, выполняемый разными ролями, может находиться в разных строках. Для сводной статистики по приложению агрегируйте сознательно, а для расследования безопасности и различий прав не смешивайте разные базы и пользователей без основания.

    SELECT dbid, userid, toplevel, queryid,
       calls, total_exec_time,
       left(query, 120) AS query
FROM pg_stat_statements
WHERE queryid IS NOT NULL
ORDER BY total_exec_time DESC
LIMIT 15;

    pg_stat_activity.query_id полезен для сопоставления текущего SQL с агрегатом, если вычисление ID включено и права позволяют его видеть. Но pg_stat_activity отражает в первую очередь верхнеуровневый SQL, тогда как при pg_stat_statements.track = all агрегатор дополнительно учитывает вложенные вызовы. Нельзя ожидать идеального соответствия по каждой глубине вызовов.

    7. Внутреннее хранение и цена агрегирования¶

    7.1. Почему недостаточно хранить длинные SQL в shared memory¶

    Расширение использует общую хеш-структуру статистических записей с ограничением pg_stat_statements.max. Длительность, число вызовов, счета блоков и прочие числовые поля хранятся в общих структурах. Представительные тексты SQL хранятся в отдельном дисковом файле, чтобы огромный текст запроса не занимал фиксированную shared-memory запись.

    Это выгодно для памяти, но создает отдельную границу надежности мониторинга. Если файл текстов становится слишком большим, подсистема может отбросить тексты, сохранив счетчики и queryid: колонка query станет NULL. Это не означает, что PostgreSQL потерял выполненные запросы или пользовательские данные. Он утратил только представительные строки для диагностики.

    7.2. Что происходит при большом числе разных структур¶

    Если число уникальных структур превышает pg_stat_statements.max, подсистема вытесняет сведения о наименее активно исполнявшихся запросах. Счетчик dealloc в pg_stat_statements_info показывает количество таких вытеснений. Высокий рост dealloc означает, что окно агрегирования теряет длинный хвост запросов. При этом частые и дорогие структуры обычно остаются, а редкие могут исчезать прежде, чем мониторинг успеет их прочитать.

    SELECT dealloc, stats_reset
FROM pg_stat_statements_info;

SELECT current_setting('pg_stat_statements.max') AS max_entries,
       count(*) AS current_entries
FROM pg_stat_statements;

    Первый SELECT из представления возвращает сведения о вытеснениях, а не число ошибок запросов. Второй сравнивает ограничение с текущим количеством записей; это косвенный сигнал, не заменяющий динамику dealloc.

    7.3. Как возникает горячая точка в самой статистике¶

    Представим, что 500 backend-процессов каждую секунду выполняют очень короткий, одинаковый SQL. Они должны накопить стоимость в одной и той же статистической записи. Подсистема использует синхронизацию для обновления общих счетчиков. Если для каждого вызова еще и отслеживается время планирования, конкуренция и накладные расходы могут стать заметными. Документация отдельно предупреждает о цене pg_stat_statements.track_planning для множества конкурентных запросов с одинаковой структурой.

    500 backend processes
  ├── exec same query ─┐
  ├── exec same query ─┼─▶ one aggregate entry (same queryid + context)
  └── exec same query ─┘         ↑ synchronization / update cost

Увеличение подробности измерения → дополнительные записи и конкуренция.

    Конкретную функцию блокировки расширения оставляем в исходниках; здесь важен инженерный компромисс: подробная статистика не бесплатна. Включаем дорогое измерение по подтвержденной диагностической необходимости, измеряем overhead A/B и при необходимости возвращаем настройку.

    7.4. Особенности pg_stat_statements.track¶

    При top собираются верхнеуровневые команды, непосредственно пришедшие от клиента (типичный default). all добавляет вложенные SQL, например из функций; none выключает сбор SQL-статистики. Режимы различаются и по количеству потенциально учитываемых структур, и по стоимости учета, и по тому, насколько легко потом трактовать calls.

    Если запрос вызывает функцию с SQL внутри, в all вы можете увидеть отдельный внешний SQL и внутренние SQL: складывать total_exec_time этих вложенных записей как независимые непересекающиеся затраты неверно, так как интервалы могут перекрываться. Для анализа систематической нагрузки сначала рассматривайте toplevel и характер вложенности, затем агрегируйте осторожно.

    7.5. Планирование и исполнение — разные счетчики¶

    track_planning = on включает поля plans, total_plan_time, mean_plan_time и другие. Указанные суммы могут перекрываться с обработкой отдельных вложенных операций, а само планирование не всегда исполняется на каждом вызове. Сравнение затрат planner и executor должно учитывать контекст prepared statements и кеширования планов, подробно изученный в соседних лекциях.

    SELECT queryid, calls, plans,
       round(mean_plan_time::numeric, 3) AS avg_plan_ms,
       round(mean_exec_time::numeric, 3) AS avg_exec_ms,
       round(stddev_exec_time::numeric, 3) AS stddev_exec_ms
FROM pg_stat_statements
WHERE toplevel
ORDER BY total_exec_time DESC
LIMIT 20;

    Поля min_exec_time и max_exec_time полезны для грубой оценки разброса, но не дают p99. Даже большой stddev_exec_time не указывает момент возникновения проблемы без временной привязки.

    8. Правильное ранжирование: количество, суммарное время, ожидания¶

    8.1. Почему «самый медленный запрос» — часто неверная цель¶

    Сравним два шаблона:

    Шаблон Вызовов за окно Среднее время Суммарное время
    A: редкий отчет 20 800 мс 16 000 мс
    B: получение статуса 900 000 4 мс 3 600 000 мс

    Запрос B потребляет значительно больше суммарного времени backend-исполнения, хотя каждый вызов быстрее в 200 раз. При этом total_exec_time — сумма интервалов по конкурентным вызовам: она может быть больше реального времени измерения. 3 600 000 мс агрегированного времени за минуту не означают, что сервер работал 60 минут. Если 100 запросов ждали одновременно, их времена складываются.

    SELECT queryid, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 3) AS mean_ms,
       round(stddev_exec_time::numeric, 3) AS stddev_ms,
       left(query, 110) AS query_sample
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database
              WHERE datname = current_database())
ORDER BY total_exec_time DESC
LIMIT 20;

    8.2. Как отделить CPU от I/O по косвенным признакам¶

    shared_blks_hit — доступ к странице через shared buffers. shared_blks_read — чтение страницы с точки зрения PostgreSQL, которое может обслуживаться page cache ОС, поэтому вовсе не обязано означать физический I/O накопителя. При включенном track_io_timing доступны времена соответствующих операций чтения/записи. Но нулевой или маленький I/O time не доказывает, что остаток времени целиком съел CPU: запрос мог ждать locks, IPC, LWLocks и сетевой стек.

    SELECT queryid, calls,
       shared_blks_hit, shared_blks_read,
       round(shared_blk_read_time::numeric, 1) AS read_ms,
       temp_blks_written, wal_bytes,
       left(query, 90) AS sample
FROM pg_stat_statements
ORDER BY shared_blk_read_time DESC
LIMIT 15;

    Если track_io_timing = off, время чтения обычно нулевое и это отсутствие измерения, а не «диск работает бесплатно».

    8.3. Почему нужно собирать дельты за окно¶

    Суммарный счетчик с момента сброса показывает историческую картину. Допустим, тяжелый SQL один раз выполнялся вчера и набрал 30 минут total_exec_time. Сегодня он может вообще не запускаться, но останется на первом месте. Для диагностики «что изменилось за последние пять минут» снимаем две выборки одного набора ключей и сравниваем приращения.

    T0: calls=100 000, total_exec_time=250 000 ms
T1: calls=160 000, total_exec_time=310 000 ms

Δcalls = 60 000
Δtime  = 60 000 ms
Среднее на этом окне ≈ Δtime / Δcalls = 1 мс

    Учтите сброс pg_stat_statements_reset(), вытеснение записи (dealloc), рестарт и возможную смену queryid при изменении объектов. Отрицательные дельты нельзя превращать в корректную скорость вызовов. Для полноценного временного графика храним снимки с фиксированным интервалом вне PostgreSQL — в системах наблюдаемости приложения.

    8.4. Почему ожидания не превратить в готовое p99 по SQL¶

    Мы получаем mean_exec_time, min_exec_time, max_exec_time, stddev_exec_time и calls, но из этих агрегатов нельзя точно восстановить 99-й перцентиль. Например, два набора задержек с одинаковым средним и дисперсией могут иметь разные хвосты. Встроенная статистика wait_event показывает текущее ожидание, а не историческую разбивку всех запросов по фазам.

    Для ответа «p99 этого SQL скачет во время ожидания конкретного типа» соединяем наблюдение: временной ряд p99 на стороне приложения + выборку активных wait events + рост агрегированных затрат SQL + контекст ОС. Для более строгой атрибуции нужны трассы или специализированный инструмент, регистрирующий интервалы ожиданий, и следует оценивать его overhead.

    IV. Wait events и LWLocks: от машинного ожидания до метки в SQL¶

    9. Что именно представляет собой wait event¶

    9.1. Почему «активный» backend может не выполнять работу¶

    Во время SQL процесс может добровольно перестать продвигаться: он ждет освобождения блокировки, страницы, ответа другого процесса, файловой операции или клиента. Это не обязательно выражается высокой загрузкой CPU. На уровне операционной системы поток может спать, но PostgreSQL знает о конкретной точке ожидания только тогда, когда разработчики сервера явно инструментировали соответствующий участок кода.

    wait_event_type — категория; wait_event — название конкретной точки. Оба значения отображают текущую ситуацию, а не историю. Если событие слишком короткое, диагностический SELECT может ни разу не попасть в нужный интервал.

    SELECT pid, state, wait_event_type, wait_event,
       clock_timestamp() - query_start AS query_age,
       left(query, 90) AS query_sample
FROM pg_stat_activity
WHERE wait_event IS NOT NULL
ORDER BY wait_event_type, wait_event, pid;

    Не стоит называть любое ожидание «проблемой»: ClientRead у idle-сессии обычно штатный простой, а Timeout/PgSleep ожидаем при pg_sleep(). И наоборот, wait_event IS NULL не равнозначно «процесс занят CPU»: он может находиться между измеряемыми точками, быть вытеснен ОС или исполнять неинструментированный код.

    9.2. Поле PGPROC.wait_event_info¶

    В реализации PostgreSQL состояние ожидания хранится в wait_event_info структуры PGPROC для процесса. Значение кодирует класс ожидания и конкретный идентификатор. Через функции pgstat_get_wait_event_type() и pgstat_get_wait_event() оно превращается в текстовые поля SQL. Этот путь отдельный от массива PgBackendStatus.

    Backend enters wait point
    │
    ▼
pgstat_report_wait_start(wait_event_info)
    │
    ▼
PGPROC.wait_event_info = encoded category + event id
    │
    ▼
pg_stat_get_activity() reads event metadata
    │
    ▼
pg_stat_activity.wait_event_type / wait_event
    │
    ▼
pgstat_report_wait_end() clears current wait

    В реальной сборке это минималистичная операция обновления состояния, рассчитанная на частые вызовы. Именно поэтому PostgreSQL не ведет в базовом поле историю миллисекунд по каждой точке: поддержание полных пер-процессных гистограмм и счетчиков всех ожиданий дало бы дополнительную стоимость на горячем пути.

    9.3. Подключение wait events к коду¶

    На уровне C инструментирование обычно выглядит как «перед потенциальным ожиданием опубликовать идентификатор; после завершения очистить». Вызывающий код обязан корректно оформлять границы, в том числе при сложных сценариях прерывания.

    /* Упрощенный фрагмент для объяснения, не копировать как patch. */
pgstat_report_wait_start(WAIT_EVENT_SOME_OPERATION);
perform_potentially_blocking_operation();
pgstat_report_wait_end();

    В некоторых реализациях WaitEventSet или LWLock функции обновляют состояние внутри общей инфраструктуры, и прикладной код вручную не оборачивает каждый вызов. Имена констант WAIT_EVENT_* не обязаны совпадать один-в-один с напечатанным текстом в pg_wait_events; для некоторых классов используется упакованная категория и идентификатор tranche.

    9.4. Таблица категорий: одна метка — один класс причины¶

    Тип Что ожидает backend Корректная первая гипотеза
    Client Данные от клиента или возможность отправить данные Проверить сеть и потребителя результата
    Lock Heavyweight lock Найти владеющую/опережающую транзакцию или процесс
    LWLock Внутренний краткоживущий lock shared memory Ищем конкуренцию внутри подсистемы по названию tranche
    IO Конкретную файловую/дисковую операцию Коррелируем с pg_stat_io и ОС
    IPC Событие другого процесса PostgreSQL Выясняем роль взаимодействующих backend
    BufferPin Освобождение pin на буфере Проверяем удержание buffer pin, например открытым cursor
    Timeout Истечение таймера, управляемого сервером Может быть штатным сном или throttle
    Activity Новую работу внутри служебного процесса Обычно штатный idle background worker
    Extension Условие, определенное расширением Смотрим документацию конкретного модуля

    Другие категории PostgreSQL 18 (включая тестовые injection points) допускаются — полный перечень берем из pg_wait_events и документации текущей версии. Не приписываем классу IO автоматически физическое чтение SSD: страница могла быть удовлетворена page cache ОС; инструментированное ожидание отражает путь PostgreSQL, а не полную картину контроллера накопителя.

    10. Lock и LWLock: почему одна буква меняет расследование¶

    10.1. Пример обычного transaction wait¶

    В основной лекции 08 мы видели: транзакция A обновила строку и не завершилась; B пытается изменить ту же строку и ждет. В поле wait event у B нередко Lock/transactionid. Значит, конкретная текущая точка — ожидание тяжелой блокировки, обеспечивающей согласование транзакций.

    A: BEGIN → UPDATE(id=1) ─────────────── COMMIT
B:                UPDATE(id=1) ── WAIT ─┘→ продолжение

B: state = active
   wait_event_type = Lock
   wait_event = transactionid  (типичный случай)

    Для Lock у нас есть механика поиска блокировщиков (pg_blocking_pids()) и pg_locks. Тонкости очередей и внутреннего Lock Manager — предмет лекции 08.2.

    10.2. Что защищает LWLock¶

    LWLock — легковесный lock PostgreSQL для защиты коротких критических участков и общих структур: отображения страниц на буферы, метаданных процесса, отдельных операций в подсистемах WAL и статистики. У него режимы LW_SHARED и LW_EXCLUSIVE. В типичном пути быстрое получение основывается на атомарных операциях над состоянием lock; если это не получилось, процесс может перейти к ожиданию и проснуться после освобождения ресурса.

    Модель «LWLock — просто маленький mutex» полезна только до первого вопроса о нагрузке. У механизма есть конкурентное состояние, очереди ожидателей, пробуждение и компромисс между короткой активной попыткой получения и парковкой процесса. Конкретные шаги LWLockAcquire зависят от версии; в этой лекции достаточно понять, почему названия tranche помогают локализовать узкий внутренний ресурс.

    Backend A                      LWLock X                  Backend B
     │                       unlocked                        │
     ├─ atomic acquire ─────▶ held SH/EX                       │
     │                         │       ◀── try acquire ───────┤
     │                         │           conflict          │
     │                         │       ◀── wait / sleep ─────┤
     ├─ release ─────────────▶ free / wake                    │
     │                         └──────── grant ─────────────▶│

    10.3. Почему LWLocks короткие, но под нагрузкой дорогие¶

    Каждый отдельный LWLock может удерживаться микросекунды. Но если тысяча backend-процессов пытается обновить одну и ту же структуру, очереди и накладные расходы синхронизации накапливаются. Длина задержки зависит не только от длительности одного критического участка, но и от частоты конфликтов, распределения данных, аппаратных свойств памяти и планирования процессов ОС.

    Сценарий: при большом числе процессов повышается конкуренция за LWLock/BufferMapping. CPU может быть заметно занят координацией и управлением буферами, а не полезным SQL. Простое увеличение числа клиентских соединений способно усилить contention. Подробные алгоритмы и средства синхронизации оставляем следующему слою, а здесь учимся обнаружить конкретную точку.

    10.4. Примеры LWLock из PostgreSQL 18¶

    Событие Защищаемый механизм Как интерпретировать всплеск
    BufferMapping Сопоставление блока данным shared buffer Конкуренция вокруг отображения страниц в buffer pool
    BufferContent Доступ к содержимому страницы в памяти Конкуренция за конкретные буферные страницы
    ProcArray Общие данные о процессах и XID, получение snapshots Интенсивная работа с информацией о текущих транзакциях
    WALInsert Вставка данных WAL в буферы Конкуренция при генерации WAL
    WALWrite Координация записи WAL Возможное ожидание сериализованных действий записи журнала
    PgStatsData, PgStatsHash Общие статистические структуры Конкуренция внутри самой системы статистики
    LockManager Внутреннее устройство таблиц тяжелых блокировок Это LWLock над метаданными lock manager, не ожидание строки

    Названия взяты из словаря wait events PostgreSQL 18. Они указывают зону, но не окончательную причину. Например, WALWrite не означает, что вся задержка — физический fsync: часть времени может быть ожиданием внутренней синхронизации. Измерения разделяемых блоков и ОС нужны для различения.

    10.5. Три похожих имени — три разных ожидания¶

    Сравним:

    • Lock / transactionid: клиентский SQL ждет завершения транзакции другого участника.
    • LWLock / LockManager: backend ждет доступа к внутренней структуре учета тяжелых блокировок.
    • LWLock / BufferContent: backend ждет доступа к странице данных в shared buffers.

    Смешивать их в один показатель «blocked SQL» — потерять механизм. В первом случае ищем владельца транзакции. Во втором исследуем массовую конкуренцию на внутренних структурах. В третьем связываем ожидание с горячими страницами и типом нагрузки.

    pg_blocking_pids() не является универсальным определителем «кто держит LWLock»: он предназначен для анализа ожиданий, обслуживаемых heavyweight lock manager. Для LWLock нужен другой набор наблюдений и нередко профилирование исходного пути.

    11. События IO, IPC, Client, BufferPin: неоднозначные симптомы¶

    11.1. IO: ожидание определенной операции, но где именно задержка?¶

    PostgreSQL публикует события вроде IO/DataFileRead, IO/DataFileWrite, IO/WALSync и другие названия, соответствующие конкретным точкам в коде. В PostgreSQL 18 также присутствуют события, связанные с асинхронным I/O, например AioIoCompletion и операции через io_uring на поддерживаемых платформах. Точное наличие отдельных путей зависит от настроек и поддерживаемого backend AIO.

    Прежде чем обвинять SSD, проверяем: не обрабатывается ли read через page cache ОС, не выполняется ли запись в файловый кеш, не ограничивает ли операцию сам PostgreSQL. Используем статистику I/O и инструменты ОС. Вспышка IO без подтвержденного роста задержки чтения на уровне ОС дает только гипотезу.

    SELECT backend_type, object, context,
       reads, read_time, writes, write_time, fsyncs, fsync_time
FROM pg_stat_io
WHERE object IN ('relation', 'wal')
ORDER BY backend_type, object, context;

    Для оценки времени операций включают track_io_timing и, где уместно, track_wal_io_timing с учетом цены измерения времени. В PostgreSQL 18 структура pg_stat_io включает статистику WAL, поэтому старые советы опираться на несуществующие в 18-м поля pg_stat_wal.wal_sync_time нужно перепроверять по версии.

    11.2. IPC: backend ждет другой backend¶

    Пример — IPC/BufferIo: backend может ждать I/O, которое для буфера уже выполняет другой процесс. Это не то же самое, что его собственный IO/DataFileRead. С точки зрения пользовательского SQL время теряется, но причина лежит в координации внутренних процессов. Аналогично IPC при параллельной работе может означать ожидание готовности других workers.

    Наблюдение IPC должно приводить к вопросу «с кем взаимодействует текущий процесс?», а не к автоматическому выводу «сломалась сеть». На сервере PostgreSQL IPC в данном контексте — межпроцессное взаимодействие внутри экземпляра.

    11.3. ClientRead и ClientWrite — приложение тоже может тормозить базу¶

    ClientRead обычно означает ожидание данных от клиента. У простоев это штатно. Но когда транзакция открыта и backend ожидает следующую команду, задержка клиента способна продлевать время удержания транзакционных ресурсов. ClientWrite у active-запроса может означать, что PostgreSQL пытается отправить результат, но клиент медленно читает сокет.

    SELECT state, wait_event, count(*) AS sessions
FROM pg_stat_activity
WHERE wait_event_type = 'Client'
GROUP BY state, wait_event
ORDER BY sessions DESC;

    Ловушка: высокий ClientRead не следует считать «медленной сетью» без уточнения состояния, возраста транзакций и того, чего сервер вообще ждет. Он может ждать, потому что backend завершил работу и клиент больше ничего не прислал.

    11.4. BufferPin: не путать pin с content LWLock¶

    Pin — механизм удержания буфера при использовании, чтобы его нельзя было неожиданно вытеснить из buffer pool. При BufferPin backend может ждать возможности получить эксклюзивный доступ к pin; удержание другим процессом, например при открытом курсоре, способно продлить ожидание. Это другой механизм, чем защита содержимого страницы при LWLock/BufferContent.

    Тонкость нужна для диагностики. Рекомендация «посмотрите на индекс и ускорьте SELECT» не объясняет проблему buffer pin. Следует определить жизненный цикл читателя буфера и его взаимодействие с другими процессами. Полная механика pinning относится к internals буферного менеджера; здесь мы используем событие как диагностическую подсказку.

    11.5. Timeout/PgSleep — контрольный эксперимент¶

    Чтобы увидеть ожидание, не создавая транзакционных блокировок, запустите в сессии A:

    SELECT pg_sleep(8);

    Пока идет сон, в сессии B:

    SELECT pid, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE query LIKE '%pg_sleep(8)%'
  AND pid <> pg_backend_pid();

    Обычно увидим active вместе с Timeout / PgSleep. Значит, десятки active не обязаны исполнять CPU-инструкции непрерывно. Пример намеренно искусственный, но он точно отделяет состояние выполняющейся команды от текущего механизма ожидания.

    12. От ожидания к проблеме под нагрузкой¶

    12.1. Почему 50 ожидателей иногда дешевле одного горячего цикла¶

    Ожидающий backend может спать и не расходовать много CPU. Добавим сто процессов, все ждущие один ресурс: растут число соединений, используемая память процессов, очередь работы и время ответа приложения. CPU остается низким, но throughput падает, а p99 ползет вверх. Нагрузку ограничивает сериализованный ресурс, даже если два свободных процессорных ядра простаивают.

    Одновременных SQL:     10      30       100        300
Ожидающих ресурс:       0       12        79        278
CPU:                  18%      24%       27%        29%
Throughput:          растет  плато    плато/падение падение
p99 latency:          25мс    150мс     1.8с       5.2с

    Числа иллюстративны. Это классическое «масштабируем нагрузку, но увеличиваем очередь ожиданий». Узкая точка может быть SQL row lock, LWLock, I/O или внешний клиент; определяем ее по типу и динамике wait events, а не по проценту загрузки CPU.

    12.2. Почему увеличение max_connections не устраняет проблему¶

    Если все запросы конкурируют за одно место, увеличение допустимого числа backend позволяет большему числу запросов одновременно ждать. Память и стоимость управления процессами возрастают, локальный ресурс остается прежним. Нагрузка на LWLocks иногда даже усиливается. Настройку лимитов соединений мы рассматриваем только как контекст диагностики; способы управления пулами — отдельный блок курса и здесь не разбираются.

    12.3. Ловушка последовательного опроса¶

    Представим, что опрос pg_stat_activity занимает 10 мс при большом числе соединений. Между чтением первой и последней записи процессы изменили свои состояния. Запрос в SQL выглядит как одна таблица, но истинная система эволюционирует, а статус каждого backend относится к своему моменту публикации.

    Можно уменьшить неопределенность коротким интервалом наблюдения и повторными выборками, однако у частого опроса появляется собственная цена. Для серьезной атрибуции времени приходится проектировать измерение так, чтобы его нагрузка была меньше наблюдаемого эффекта.

    V. Наблюдаемость как измерительный эксперимент¶

    13. Sampling wait events: сколько ожиданий мы на самом деле видим¶

    13.1. Почему короткое ожидание часто исчезает между опросами¶

    Пусть backend ждет LWLock 5 мс в каждом случайном интервале длительностью 1000 мс, а мы опрашиваем pg_stat_activity раз в секунду. Упрощенная вероятность застать один такой интервал в случайной фазе равна отношению длительностей: p = 5 / 1000 = 0,005, или 0,5%. При 100 независимых случайных наблюдениях шанс увидеть событие хотя бы один раз:

    [ P(\text{поймать хотя бы раз}) = 1 - (1-p)^n = 1 - (0.995)^{100} \approx 39.4\%. ]

    Даже сотня наблюдений не гарантирует обнаружение короткого ожидания. А если таймер опроса и нагрузка периодичны и синхронизированы, предположение о независимости рушится — возможен устойчивый пропуск событий. Поэтому «ни разу не увидели LWLock» означает лишь отсутствие зарегистрированного ожидания в выбранные моменты.

    13.2. Что доля samples действительно означает¶

    При достаточно случайной и репрезентативной выборке доля наблюдений LWLock/BufferMapping приближает долю wall-clock времени процесса в данном состоянии. Это полезный метод для поиска преобладающих ожиданий на множестве backend-процессов. Но он не определяет число операций ожидания: одно ожидание в 100 мс и сто ожиданий по 1 мс дают одинаковое суммарное время, но радикально разные события на уровне синхронизации.

    Ожидание A: ─────────── 100 ms ──────────    1 событие
Ожидание B: 1+1+1+ ... +1 ms (100 раз)       100 событий

Одинаковая длительность ≠ одинаковое число конфликтов.

    У sampling есть смещение по процессам: долго спящий backend попадает чаще, чем короткая активная операция, а медленный запрос может чаще попадать в опрос просто потому, что живет дольше. Поэтому count(samples) нельзя объявлять count(SQL calls).

    13.3. Как корректно собрать временной ряд SQL¶

    Для диагностического стенда можно периодически сохранять небольшую выборку pid, backend_start, state, wait_event_type, wait_event, clock_timestamp() в отдельную таблицу или собирать во внешнем мониторинге. Однако циклический SQL, опрашивающий pg_stat_activity каждые 10 мс, создает новые backend-запросы, считывает общую память и сам искажает нагрузку.

    Удобная модель: начать с интервала 0,5–2 секунды, собрать несколько минут, проверить стоимость самого опроса, затем уменьшать интервал только если низкое разрешение мешает гипотезе. Это рекомендация по методике, не встроенное требование PostgreSQL; оптимальный интервал зависит от частоты событий и размера экземпляра.

    -- Пример одного снимка; запускать повторно извне, а не бесконечным SQL-циклом.
SELECT clock_timestamp() AS observed_at,
       pid, backend_start, state, wait_event_type, wait_event,
       query_id, application_name
FROM pg_stat_activity
WHERE backend_type = 'client backend';

    Для мониторинга, который только читает накопительные счетчики, полезен stats_fetch_consistency = none, но на выборочную природу wait events это не влияет.

    14. Причинная атрибуция: связываем четыре разных прибора¶

    14.1. Слои наблюдения¶

    Доказательная диагностика складывается из независимых источников:

    1. Приложение: p95/p99, длительность транзакционной операции, ошибки и корреляционный идентификатор запроса.
    2. pg_stat_activity: какие backend-процессы сейчас active, idle, waiting, что известно о транзакции.
    3. pg_stat_statements / cumulative views: какие структуры SQL имеют высокий вклад за наблюдаемое окно, как меняются I/O и WAL-счетчики.
    4. ОС и накопитель: реально ли исчерпаны CPU, IOPS, throughput, есть ли очередь диска или задержка планирования процесса.

    Ни один из источников сам не строит все причинные связи. Корректный вывод требует согласования времени, нагрузочного эксперимента и возможности опровергнуть альтернативную гипотезу.

    14.2. Диагностическая матрица «симптом → проверка → исключение»¶

    Симптом Первое наблюдение Что еще проверить
    p99 высокий, CPU низкий active + wait_event_type Доля ожиданий по времени, root blocker, приложение
    Много LWLock/BufferMapping Сэмплы wait events Конкуренция и частота работы с buffer pool, OS CPU
    Много LWLock/ProcArray Всплески вокруг снимков транзакций Массовые короткие транзакции, число процессов
    Много IO/DataFileRead pg_stat_io, track_io_timing Page cache ОС, latency файловой системы

    pg_stat_statements не растет Наличие активных незавершенных SQL Flush-сроки других счетчиков, включенность модуля
    Показания застыли внутри BEGIN stats_fetch_consistency и локальный снимок pg_stat_clear_snapshot(), autocommit

    Таблица описывает гипотезы, а не автоматические диагнозы. Например, ProcArray показывает, что нужно исследовать доступ к общей информации о транзакциях; она сама по себе не доказывает наличие долгого BEGIN.

    14.3. Временная ось вместо бессвязных скриншотов¶

    Представим пять минут наблюдений:

    14:00:00  нагрузка ↑
14:00:10  одновременно active 20 → 180
14:00:12  sample LWLock/BufferMapping ↑
14:00:15  throughput выходит на плато
14:00:20  p99 30 ms → 2.1 s
14:01:00  снижаем concurrency
14:01:05  LWLock samples ↓, p99 ↓

    Это сильнее одного скриншота. Изменили независимую переменную — число конкурентных запросов; увидели воспроизводимую реакцию wait events, задержки и пропускной способности. Следующий шаг — найти конкретную вызывающую нагрузку операцию, сопоставив queryid и aggregate time. При этом связь является диагностическим подтверждением, но окончательный механизм при сложной ситуации может потребовать профилирования.

    14.4. Пример аналитической сводки текущих ожиданий¶

    SELECT wait_event_type, wait_event,
       count(*) AS sessions,
       count(*) FILTER (WHERE state = 'active') AS active_sessions,
       max(clock_timestamp() - query_start)
         FILTER (WHERE state = 'active') AS max_active_age
FROM pg_stat_activity
WHERE wait_event IS NOT NULL
GROUP BY wait_event_type, wait_event
ORDER BY sessions DESC, wait_event_type, wait_event;

    Важная оговорка: max_active_age — длительность текущего SQL, а не длительность конкретного ожидания. Если backend выполняет запрос 30 секунд, а LWLock ждет последние 2 мс, запрос покажет 30 секунд. Нельзя приписывать все 30 секунд LWLock по одному снимку.

    14.5. Как исследовать долгую транзакцию без перехода к VACUUM internals¶

    Наблюдаем xact_start, backend_xid, backend_xmin, состояние и ожидания. backend_xid может отсутствовать до назначения реального XID; backend_xmin показывает известный горизонт видимости, когда он существует. Долгое BEGIN само по себе еще не доказывает, что процесс удерживает старый snapshot или блокирует очистку. Также возможна опасная транзакция без длинного активного SQL.

    SELECT pid, application_name, state,
       clock_timestamp() - xact_start AS xact_age,
       backend_xid, backend_xmin,
       wait_event_type, wait_event,
       left(query, 110) AS last_or_current_query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start, pid
LIMIT 30;

    При idle in transaction мы фиксируем возраст и потенциально удерживаемые ресурсы, проверяем соседние ожидания и только потом выбираем действие. Алгоритм VACUUM, freezing и расчет пределов wraparound — содержание 08.3; в 08.1 достаточно отличать возраст транзакции от возраста XID и понимать границы наблюдения.

    15. Цена мониторинга: когда измерение само ухудшает p99¶

    15.1. Источники overhead¶

    • track_activities: публикация текущего статуса; базовый механизм дешев, но размер сохраняемого текста влияет на память.
    • track_counts: локальное накопление и публикация счетчиков; требуется для ряда автоматических решений сервера.
    • track_io_timing, track_wal_io_timing: вызовы часов вокруг операций; цена зависит от платформы и интенсивности I/O.
    • pg_stat_statements.track_planning: дополнительные точки измерения и обновления агрегатов; может усиливать конкуренцию при множестве одинаковых коротких запросов.
    • Частый опрос pg_stat_activity и других представлений: CPU, чтение shared memory, формирование локальных снимков, передача результатов клиенту.
    • Длительное хранение сырых SQL в логах: потенциальные секреты и рост затрат на хранение.

    15.2. Точный счетчик ≠ бесплатный счетчик¶

    Допустим, операция длится 0,1 мс, а добавленное измерение требует нескольких дополнительных переходов к системным часам и синхронизирует общий агрегатор. Даже небольшой абсолютный overhead при миллионах коротких SQL становится заметным. Поэтому измерять нужно сам overhead, а не только значение замеряемой метрики.

    Проверка: сравнить throughput/p95/p99 при одинаковой нагрузке до и после включения детального измерения, удостоверившись, что система не находится в другом тепловом/кешевом состоянии. Для интегральной нагрузки чаще полезнее низкочастотные метрики и выборочное профилирование, чем тотальный трассинг каждого шага.

    15.3. Почему pg_stat_statements_reset() — инструмент с последствиями¶

    Сброс позволяет получить чистое окно, но одновременно удаляет накопленную историю текущих шаблонов SQL. На общей production-системе сброс может нарушить работающие дашборды и скрыть долгосрочную тенденцию. Предпочтительнее хранить последовательные snapshots и вычислять дельты; сброс выполнять лишь в согласованном тесте или при понятной эксплуатационной необходимости.

    Точно так же глобальный pg_stat_reset() влияет на другие системы оценки активности. Для учебных экспериментов используем отдельную БД и договоренное окно.

    VI. Практическое доказательство механизмов: запустили → наблюдали → объяснили¶

    16. Подготовка исследовательского стенда¶

    Для эксперимента нужны PostgreSQL 18, отдельная БД и три подключения: psql A, psql B, psql OBS. Расширение pg_stat_statements должно быть заранее подключено согласно разделу 5. Достаточно одной таблицы для чтения и одного проверочного SQL.

    CREATE TABLE IF NOT EXISTS demo_stats (
    id bigint PRIMARY KEY,
    payload text NOT NULL
);
INSERT INTO demo_stats
SELECT g, repeat('x', 40)
FROM generate_series(1, 10000) AS g
ON CONFLICT (id) DO NOTHING;
ANALYZE demo_stats;

SET application_name = 'pg08_1_observer';

    Для именования клиентских сессий используйте application_name в каждом подключении (pg08_1_A, pg08_1_B, pg08_1_OBS). Тогда результат легко отличать от остальных серверных процессов. Служебные команды SET запускайте в соответствующих сессиях.

    17. Эксперимент A: одна команда — два состояния наблюдения¶

    17.1. Выполнили долгую команду¶

    В сессии A:

    SET application_name = 'pg08_1_A';
SELECT pg_sleep(12);

    Пока она работает, в сессии OBS:

    SELECT application_name, state, wait_event_type, wait_event,
       clock_timestamp() - query_start AS age
FROM pg_stat_activity
WHERE application_name = 'pg08_1_A';

    Ожидаемый механизм: state = active, wait_event_type = Timeout, wait_event = PgSleep. CPU при этом не обязан быть занят запросом. После окончания команды строка перейдет в состояние простоя, а query_start будет означать время последней команды.

    17.2. Проверили кеш снимка¶

    В OBS начните BEGIN, прочитайте pg_stat_activity, завершите сон в A, затем еще раз прочитайте представление в OBS. Сравните значения с результатом после SELECT pg_stat_clear_snapshot(). Если второй запрос повторно использовал локальную копию, он может выглядеть застывшим. Конкретные видимые значения зависят от момента первой выборки; для ясной демонстрации сделайте A снова активным между чтениями.

    BEGIN;
SELECT state, query_start FROM pg_stat_activity
WHERE application_name = 'pg08_1_A';
-- В A выполните новую команду.
SELECT state, query_start FROM pg_stat_activity
WHERE application_name = 'pg08_1_A';
SELECT pg_stat_clear_snapshot();
SELECT state, query_start FROM pg_stat_activity
WHERE application_name = 'pg08_1_A';
ROLLBACK;

    Доказанный тезис: ожидание и состояние — текущие сведения backend, но сам читатель способен держать локальную фотографию статусов до конца своей транзакции.

    18. Эксперимент B: локальные счетчики и задержка публикации¶

    В A запустите отдельный SQL, затрагивающий много строк. Затем в OBS посмотрите pg_stat_user_tables и pg_stat_xact_user_tables (во время соответствующей транзакции — в самом A). Разделите два эффекта: завершение операции и публикация pending-счетчиков, а затем отдельный кеш чтения.

    -- A
BEGIN;
SELECT count(*) FROM demo_stats WHERE id > 0;
SELECT relid::regclass, seq_scan, seq_tup_read
FROM pg_stat_xact_user_tables
WHERE relid = 'demo_stats'::regclass;
COMMIT;

-- OBS (autocommit)
SELECT relid::regclass, seq_scan, seq_tup_read
FROM pg_stat_user_tables
WHERE relid = 'demo_stats'::regclass;

    Не надо ожидать фиксированное число seq_scan: оно зависит от плана и возможных эффектов предыдущих запусков. Ключевое наблюдение — отложенная публикация общей статистики. После повторного запуска опроса можно получить обновленные значения. Сравниваем без самостоятельного вызова pg_stat_reset() на боевом экземпляре.

    19. Эксперимент C: queryid и нормализация¶

    В A выполните:

    SELECT payload FROM demo_stats WHERE id = 100;
SELECT payload FROM demo_stats WHERE id = 200;
SELECT payload FROM demo_stats WHERE id = 300;

    В OBS:

    SELECT queryid, calls, total_exec_time, query
FROM pg_stat_statements
WHERE query ILIKE '%demo_stats%'
  AND query ILIKE '%payload%'
ORDER BY calls DESC;

    Ожидаем группировку структурно одинаковых SQL с подставленными параметрами, например WHERE id = $1. Затем поэкспериментируйте с search_path на двух одноименных таблицах и обсудите, почему идентичный текст иногда относится к разным семантическим объектам.

    Доказанный тезис: queryid относится к структуре проанализированного SQL в конкретном окружении; его нельзя трактовать как хеш исходного текста.

    20. Эксперимент D: два разных типа ожидания на разных причинах¶

    Первый случай — pg_sleep(12) и Timeout/PgSleep. Второй случай повторяет пример основной лекции 08: A удерживает изменение строки, B пытается изменить ту же строку. Наблюдаем Lock/transactionid (частый, но не единственно возможный вывод для подобных ожиданий).

    -- A
BEGIN;
UPDATE demo_stats SET payload = 'hold' WHERE id = 1;
-- Не завершать до измерения.

-- B
UPDATE demo_stats SET payload = 'try' WHERE id = 1;
-- Запрос будет ожидать завершения A.

-- OBS
SELECT pid, application_name, state,
       wait_event_type, wait_event,
       clock_timestamp() - query_start AS age
FROM pg_stat_activity
WHERE application_name IN ('pg08_1_A', 'pg08_1_B');

-- A после наблюдения
ROLLBACK;

    Важно: здесь специально создается ожидание. SQL B продолжится после завершения A. Это эксперименты для локальной учебной БД, не для production. Механику того, кто кого блокирует и как формируется очередь, мы уже прошли в 08; внутренняя реализация lock manager пойдет в 08.2.

    21. Эксперимент E: снимки метрик и ограничение интерпретации¶

    Снимите два чтения pg_stat_statements с интервалом 30–60 секунд при повторной нагрузке, сравните calls и total_exec_time. Параллельно через pg_stat_activity соберите несколько текущих ожиданий, затем сопоставьте с p99 тестового клиента.

    SELECT clock_timestamp() AS observed_at,
       queryid, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       left(query, 80) AS sample
FROM pg_stat_statements
WHERE query ILIKE '%demo_stats%'
ORDER BY total_exec_time DESC;

    Доказательство требует честной формулировки результата: сумма total_exec_time за окно выросла на X, число вызовов выросло на Y, доля samples определенного wait event изменилась, а p99 приложения изменился на Z. Из таких наблюдений можно выдвинуть причинную гипотезу; нельзя утверждать точную длительность ожидания LWLock для каждого SQL без событийной трассировки.

    VII. Финальное расследование и инженерная модель¶

    22. Собираем инцидент из начала лекции¶

    Вернемся к системе: p99 пять секунд, CPU 25%, pg_stat_activity показывает много active, а pg_stat_statements почти не растет. Теперь у нас есть последовательность:

    1. Проверяем временные границы. pg_stat_activity сообщает текущую активность; накопительные счетчики могут отставать, а pg_stat_statements обновляется по своим точкам завершения стадий и правилам агрегирования.
    2. Проверяем снимок наблюдателя. Если диагностика идет внутри длинного BEGIN, завершаем транзакцию или вызываем pg_stat_clear_snapshot() по назначению.
    3. Классифицируем ожидания. Lock, LWLock, IO, IPC, Client — разные механизмы. Не объединяем их в «система тормозит».
    4. Собираем несколько моментов наблюдения. Фиксируем observed_at, PID, backend_start, query_id, state, wait event и имя приложения.
    5. Сопоставляем с агрегатом. Для top-level SQL за одинаковое окно смотрим Δcalls, Δtotal_exec_time, блоки и время I/O.
    6. Сопоставляем с ОС и приложением. Нужны CPU, I/O и latency на стороне клиента, иначе атрибуция остается неполной.
    7. Проверяем гипотезу нагрузочным изменением. Меняем интенсивность конкурентных запросов и фиксируем, исчезает ли соответствующее ожидание и улучшается ли p99.

    Важный инженерный принцип: измерение само имеет семантику и стоимость. Когда мы ее знаем, видимое противоречие между счетчиками превращается в понятную задержку публикации, различие гранулярности либо осознанную неопределенность наблюдения.

    23. Семь вещей, которые должны остаться в голове¶

    1. Текущая активность, накопительные счетчики и агрегаты SQL — три разных источника. Они обновляются в разные моменты и решают разные задачи.
    2. PgBackendStatus дает дешевое наблюдение без остановки всех backend-процессов. st_changecount помогает безопасно скопировать запись, но не создает атомарный снимок целого сервера.
    3. Cumulative statistics в PostgreSQL 18 накапливаются локально и переносятся в shared memory. Они могут отставать; диагностический reader дополнительно кеширует данные по stats_fetch_consistency.
    4. pg_stat_statements группирует по post-parse-analysis структуре. queryid зависит от окружения, редкие записи вытесняются, representative SQL text может исчезнуть, p99 не хранится.
    5. wait_event показывает текущую инструментированную точку ожидания. NULL не доказывает работу на CPU, а один sample не измеряет длительность ожидания.
    6. Lock, LWLock, IO, IPC, Client требуют разных гипотез и инструментов. LWLock защищает внутренние структуры; ожидание SQL-транзакции устроено иначе.
    7. Под нагрузкой важна причинная корреляция. Дельты за окно, выборочное наблюдение, метрики ОС и повторный эксперимент надежнее единственного снимка.
