    9.1. PostgreSQL Schema Migration Internals¶

    Углубленная лекция магистратуры · PostgreSQL 18 · REL_18_STABLE · блок 9.
    Точка входа: завершены 09.0, блоки 5–8. Уже известны MVCC, WAL, блокировки, состояние backend-процессов и CREATE INDEX CONCURRENTLY на уровне API. Здесь открываем их внутреннюю реализацию при изменении схемы.
    Границы: только schema migration internals. Резервное копирование и пулы соединений оставлены для 09.2 и 09.3. Примеры предназначены для отдельной учебной БД; опасные команды на production запускают только после проверки плана миграции.
    О версиях: точный SQL и свойства каталогов относятся к PostgreSQL 18. Имена исходных функций и этапы ниже — детали реализации REL_18_STABLE, а не обещания стабильности внутреннего API. Фрагменты C, помеченные «схема», намеренно сокращены и не являются текстом для компиляции.

    0. Инцидент: изменение на миллисекунду остановило систему на минуту¶

    У нас таблица orders, в ней 60 миллионов заказов. Требуется добавить новое поле. DBA смотрит на команду:

    ALTER TABLE orders ADD COLUMN source text;

    Операция не должна переписывать десятки гигабайт. На тестовой базе она выполняется практически мгновенно. Значит ли это, что в рабочей системе ее можно выполнить в любой момент?

    Нет. Представим: один backend уже держит ACCESS SHARE из долгого запроса. Наша миграция пытается получить ACCESS EXCLUSIVE и встает в очередь. Новые короткие SELECT, которые сами совместимы с первым читателем, могут оказаться за ожидающей сильной блокировкой. Через несколько секунд в сервисе растут p99, горят таймауты, соединения приложения забиваются ожиданиями. SQL миграции еще не выполнился — он только ждет права начать.

    Вот и главный вопрос лекции: где фактически находится цена изменения схемы — в размере данных, метаданных, ожидании блокировки, проверке ограничений, построении нового физического файла или в неудачно выбранном моменте публикации изменения?

    Сегодня спустимся до tablecmds.c, каталогов pg_class/pg_attribute/pg_constraint, нового relfilenode, состояний pg_index и конкретных стадий конкурентного индексирования. В конце соберем протокол миграции, который можно диагностировать, прервать и продолжить безопасно.

    Сквозной пример. Используем две таблицы:

    CREATE TABLE customers (
    id bigint PRIMARY KEY,
    full_name text NOT NULL,
    version bigint NOT NULL DEFAULT 0
);

CREATE TABLE orders (
    id bigint PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers(id),
    amount bigint NOT NULL,  -- сумма в копейках
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

    Число строк и объемы для production-расчетов будут условными. Таблицы из SQL здесь маленькие: механизмы наблюдаем локально, нагрузочные следствия моделируем отдельно.

    I. DDL execution pipeline: от SQL до системных каталогов¶

    1. Почему DDL нельзя свести к «изменению файла таблицы»¶

    Популярная модель: ALTER TABLE открывает файл с данными, меняет его формат и завершает работу. Первая проблема — многие DDL вообще не трогают строки. Вторая — структуру отношения описывает сразу несколько системных каталогов. Третья — несколько подкоманд одного ALTER TABLE должны проверяться и применяться в согласованном порядке, иначе можно создать промежуточную схему, которая не соответствует сама себе.

    Для PostgreSQL схема — состояние каталогов плюс физические отношения плюс инвалидация кеша метаданных. Исполнитель SQL сначала должен найти объект, проверить права и зависимости, определить необходимый lock, подготовить изменение каталогов, при необходимости проверить существующие строки либо переписать таблицу, после чего новая схема становится видимой другим транзакциям при фиксации.

    1.1. Как SQL попадает в tablecmds.c¶

    Концептуальная цепочка:

    SQL text
  │
  ▼
Parser → AlterTableStmt
  │
  ▼
Utility command execution (ProcessUtility)
  │
  ▼
AlterTable() / AlterTableInternal()
  │
  ▼
ATController()
  ├─ Phase 1: ATPrepCmd()       — проверка и очередь работ
  ├─ Phase 2: ATRewriteCatalogs() — изменение каталогов
  └─ Phase 3: ATRewriteTables()   — сканирование, проверки, rewrite при необходимости
  │
  ▼
COMMIT → другие backend видят новую схему

    Исходник: src/backend/commands/tablecmds.c. Имена приведены для внутренней реализации PostgreSQL, а не как пользовательский API.

    Упрощенное представление кода контроллера:

    /* Схема управления ALTER TABLE, без вспомогательных параметров */
ATController(...)
{
    foreach (cmd in commands)
        ATPrepCmd(&work_queue, relation, cmd, ...);

    ATRewriteCatalogs(&work_queue, ...);
    ATRewriteTables(..., &work_queue, ...);
}

    Почему три этапа? Например, команда одновременно добавляет колонку и ограничение к ней. Сначала нужно установить зависимость подкоманд и подготовить рабочее состояние, затем согласованно обновить определения объектов, потом проверять строки с уже подготовленным описанием будущей схемы. Для некоторых действий дополнительная работа отсутствует; для других весь третий этап становится дорогим.

    1.2. Что находится в очереди ALTER TABLE¶

    AlteredTableInfo — рабочая структура для отношения, обрабатываемого ALTER TABLE. В ней собираются подкоманды по проходам, информация о новых типах и атрибутах, признаки требуемого rewrite и планы проверок. Смысл не в том, чтобы запомнить набор C-полей. Смысл в другом: решение переписывать таблицу принимается в процессе подготовки и исполнения DDL; оно не выводится из длины SQL.

    Внутренняя реализация использует упорядоченные проходы (AlterTablePass), поскольку удаление зависимых объектов, изменение типов, добавление колонок и последующая проверка ограничений имеют разные требования к порядку. Вывод: если несколько операций объединены в один ALTER TABLE, PostgreSQL не обязан физически исполнять их строго слева направо как независимые строки скрипта.

    1.3. Почему каталог — это тоже данные¶

    Основные объекты:

    Каталог Что хранит Что исследуем
    pg_class отношения: таблицы, индексы, TOAST oid, relfilenode, relkind, reltoastrelid, relrewrite
    pg_attribute колонки отношения attnum, atttypid, attisdropped, atthasmissing, attmissingval
    pg_attrdef выражения DEFAULT и generation adrelid, adnum, pg_get_expr(adbin, adrelid)
    pg_constraint ограничения contype, convalidated, conenforced, conrelid, conindid
    pg_index состояние и свойства индекса indisready, indisvalid, indislive, indcheckxmin
    pg_depend зависимости объектов что допустимо удалить / поменять

    Это обычные отношения PostgreSQL с транзакционной семантикой. Изменения их записей выполняются средствами СУБД, а не непосредственным редактированием файлов администратором. Но есть еще проблема: текущий backend может держать в памяти старое описание relation.

    1.4. Relcache, catcache и invalidation¶

    Чтобы не читать системные каталоги при каждом обращении к таблице, PostgreSQL использует кеши описаний отношений (relcache) и записей системных каталогов (catcache/syscache). Если один backend изменил схему, другие не должны продолжать бесконечно считать старую схему действующей.

    Поэтому изменение каталога сопровождается механизмами инвалидации кешей. Сообщения об инвалидации заставляют backend-процессы отказаться от устаревших представлений в соответствующих безопасных точках. Операции DDL и блокировки обеспечивают, чтобы работающий запрос не продолжил обращаться к отношению по несовместимому определению.

    Неудачное упрощение: «DDL завершился — значит каждый процесс сразу буквально перепрочитал все каталоги». На практике применяются кеши и механизмы invalidation; обновление выполняется по необходимости и в согласовании с завершением команд и транзакций. Цена метаданных здесь обычно мала по сравнению с переписыванием данных, но она влияет на корректность и планирование транзакции.

    1.5. Какая блокировка нужна до первого шага¶

    Разберем короткий пример:

    BEGIN;
SET LOCAL lock_timeout = '1500ms';
ALTER TABLE orders ADD COLUMN delivery_note text;
COMMIT;

    Добавление колонки в типичном варианте требует ACCESS EXCLUSIVE. Пока эта блокировка не получена, даже подготовка дешевого изменения каталога не делает команду «безопасной для чтения». Время нужно разделять:

    общая задержка DDL = время ожидания lock
                    + время изменения каталогов
                    + время проверки / rewrite
                    + время фиксации

    В PostgreSQL многие операции ALTER TABLE требуют ACCESS EXCLUSIVE, если для конкретной формы не заданы более слабые требования. ACCESS EXCLUSIVE конфликтует с обычным ACCESS SHARE читающего SELECT. Мы уже изучили матрицу конфликтов в блоке 8; здесь интересует инженерная цена DDL.

    Если ALTER TABLE написан внутри большого BEGIN вместе с длительным backfill, сильная блокировка может удерживаться до окончания всей транзакции, даже если собственно каталог был изменен мгновенно. Поэтому нужно отделять короткий DDL от долгой обработки данных.

    1.6. Очередь блокировок: тридцать секунд простоя за одну строку SQL¶

    Время        A: долгий SELECT       B: ALTER TABLE         C: новые SELECT
T0           ACCESS SHARE
T1                                  просит ACCESS EXCLUSIVE
T2                                  WAIT
T3                                                         просят ACCESS SHARE
T4                                                         могут ждать за B
T30          завершается
T31                                  получает lock, меняет каталог
T32                                  COMMIT
T33                                                         продолжают работу

    Не каждое новое чтение обязано проходить в обход ожидающего писателя. Lock manager учитывает порядок ожидающих запросов, поэтому DDL может создать очередь до фактического изменения таблицы. Под нагрузкой это проявляется как рост p99 при небольшом CPU.

    Диагностика на отдельной БД:

    SELECT pid, state, wait_event_type, wait_event,
       clock_timestamp() - query_start AS query_age,
       pg_blocking_pids(pid) AS blocked_by,
       left(query, 160) AS query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY query_start NULLS LAST;

    Повторно устройство pg_stat_activity здесь не разбираем. Достаточно знать, что запрос DDL может находиться в active и одновременно ждать Lock.

    Инженерный вывод раздела: любой план миграции должен отдельно оценивать (1) lock acquisition, (2) каталог, (3) проверку, (4) физическую переработку данных, (5) публикацию результата транзакции. «На тесте выполнилось быстро» ничего не говорит о стоимости ожидания блокировки в production.

    II. Metadata-only changes: когда строки физически остаются прежними¶

    2. Fast ADD COLUMN DEFAULT: колонка появилась без обновления каждой строки¶

    Допустим, хотим добавить origin, чтобы каждому старому заказу показывать значение legacy.

    ALTER TABLE orders
ADD COLUMN origin text NOT NULL DEFAULT 'legacy';

    На таблице в 60 миллионов строк это выглядит как операция, которой придется обновить 60 миллионов tuple. Но в PostgreSQL 18 для неволатильного выражения DEFAULT работает fast path: результат выражения можно вычислить один раз и сохранить в метаданных, не переписывая старые строки.

    2.1. В чем физическая проблема¶

    До команды старая tuple содержала физические значения для N атрибутов. После команды логическая схема описывает N+1 атрибут. Если попытаться прочитать N+1-й атрибут непосредственно из старой tuple, его байтов там нет.

    Почему PostgreSQL может все равно вернуть 'legacy'? Потому что функция извлечения значения учитывает описание атрибута. В каталоге pg_attribute существуют поля:

    atthasmissing = true
attmissingval = {'legacy'}

    attmissingval — одноэлементный массив типа anyarray, содержащий логическое значение атрибута, когда его совсем нет в старой tuple. Для новых строк PostgreSQL записывает явное значение согласно правилам INSERT/DEFAULT.

    2.2. Пошагово: старая физическая tuple и новая логическая схема¶

    До ALTER TABLE                           После ALTER TABLE
----------------------------------      --------------------------------------
pg_attribute: id, amount, status         pg_attribute: id, amount, status, origin
Heap tuple:   [1][100][new]             Heap tuple:   [1][100][new]   (без origin)
                                                                  │
SELECT origin                                                     ▼
                                      Tuple descriptor → missing value 'legacy'

    Это объясняет, почему объем heap может остаться прежним и почему запрос начинает возвращать новое поле сразу после COMMIT. Значение будет материализовано в физической записи при последующей операции, которая формирует новую tuple, или при переписывании таблицы. После полного rewrite каталог обычно больше не нуждается в режиме missing value для этой колонки.

    2.3. Проверяем сами метаданные¶

    CREATE TABLE fast_default_demo (id bigint PRIMARY KEY);
INSERT INTO fast_default_demo VALUES (1), (2);

ALTER TABLE fast_default_demo
ADD COLUMN origin text NOT NULL DEFAULT 'legacy';

SELECT attname, atthasmissing, attmissingval
FROM pg_attribute
WHERE attrelid = 'fast_default_demo'::regclass
  AND attname = 'origin';

SELECT id, origin FROM fast_default_demo ORDER BY id;

    Ожидаем atthasmissing = true и отображение legacy для обеих старых строк. Эти наблюдения подтверждают метаданный механизм; конкретный вывод attmissingval зависит от клиента SQL.

    2.4. Почему now() и clock_timestamp() отличаются¶

    ALTER TABLE orders ADD COLUMN assigned_at timestamptz DEFAULT now();

    now() относится к STABLE-функциям: ее результат стабилен внутри текущей транзакции и подходящ для единичного вычисления при fast path. Все старые строки получат одинаковое значение, соответствующее выполнению DDL. А вот clock_timestamp() — VOLATILE: отдельные вычисления потенциально отличаются. Для сохранения семантики PostgreSQL должен применить выражение к строкам, поэтому добавление колонки с volatile DEFAULT требует table rewrite.

    -- Этот вариант может переписать всю таблицу:
ALTER TABLE orders ADD COLUMN sampled_at timestamptz
    DEFAULT clock_timestamp();

    Здесь важна волатильность выражения, а не наличие или отсутствие круглых скобок. Также полный rewrite могут потребовать добавление stored generated column, identity column или колонки доменного типа с ограничениями. Для PostgreSQL 18 виртуальная generated column при добавлении не требует rewrite, но имеет свою семантику вычисления.

    2.5. Изменение DEFAULT после добавления — новая операция¶

    ALTER TABLE orders ALTER COLUMN origin SET DEFAULT 'api';

    Это меняет поведение будущих вставок, где колонка явно не задается. Старые строки не станут 'api'. Они могут по-прежнему получать legacy из attmissingval; явно сохраненные значения останутся как были.

    Так мы получаем три независимых сущности: значение в старой tuple, missing value старого атрибута и текущее выражение DEFAULT для новых операций. Смешать их — значит ошибочно переписать бизнес-данные при миграции.

    2.6. Почему fast path не означает zero downtime¶

    Каталог меняется быстро, но ACCESS EXCLUSIVE все равно нужен. Ожидание блокировки может занять минуты. Более того, если приложение после миграции начинает активно читать новую колонку, то при последующих модификациях tuple она будет материализоваться, и физический рост данных распределится во времени.

    Цена решения: fast path устраняет одномоментный I/O переписывания, но не отменяет совместимость приложений, блокировки DDL и будущую стоимость хранения нового атрибута.

    3. DROP COLUMN: почему диск не освободился¶

    ALTER TABLE orders DROP COLUMN origin;

    Может ли PostgreSQL удалить байты поля из каждой tuple за миллисекунды? Нет. Для быстрого логического удаления он помечает колонку в pg_attribute как dropped:

    attisdropped = true
atttypid    = 0

    Физическое положение остальных атрибутов в старых строках должно оставаться интерпретируемым, поэтому запись о выброшенной колонке сохраняет часть технических свойств типа. SELECT * больше не показывает колонку, новый SQL не может к ней обратиться, но старые байты могут еще находиться в heap.

    SELECT attnum, attname, attisdropped, atttypid
FROM pg_attribute
WHERE attrelid = 'orders'::regclass
  AND attnum > 0
ORDER BY attnum;

    Чтобы реально устранить старые данные из физического представления всех строк, нужен переписывающий шаг, например подходящая операция, приводящая к table rewrite. Обычно сначала оценивают, окупается ли это: дополнительный I/O и риск недоступности могут быть выше экономии диска.

    Вывод: логическое отсутствие колонки не доказывает физическое освобождение места. Даже pg_column_size и размер relation нужно интерпретировать с учетом старых tuple и правил хранения.

    4. Metadata-only, scan-only и rewrite: три разные стоимости¶

    Мы уже видели два SQL-запроса почти одинаковой длины, один из которых быстрый, а другой может обойти все строки. Для инженерной оценки удобно выделить три класса:

    Класс Пример Работа Главная цена
    Metadata-only ADD COLUMN nullable, неволатильный DEFAULT, DROP COLUMN изменить каталоги ожидание и удержание DDL lock
    Scan / validation VALIDATE CONSTRAINT, проверка NOT NULL просканировать существующие строки, проверить условие чтение данных, CPU, блокировки заданного режима
    Rewrite volatile DEFAULT, требующее преобразования ALTER TYPE построить новое физическое представление I/O, место, WAL, длительная блокировка, перестройка индексов

    Это учебная классификация, а не универсальное правило для каждой комбинации атрибутов и параметров. Реальный путь зависит от выражения DEFAULT, типа, зависимостей, наличия ограничений и состава подкоманд одного ALTER. Поэтому при подготовке production-миграции нас интересует не название оператора само по себе, а конкретная его форма на заданной версии PostgreSQL.

    III. Table rewrite: когда новая схема требует нового физического отношения¶

    5. ALTER COLUMN TYPE: одна команда, два возможных пути¶

    Предположим, старое приложение хранит сумму заказа в целых копейках как bigint, а новое хочет тип numeric(14,2) в рублях. Мы пишем:

    ALTER TABLE orders
ALTER COLUMN amount TYPE numeric(14,2)
USING amount::numeric / 100;

    В этом примере мы одновременно меняем тип и семантику единицы измерения: переводим целые копейки в рубли. В реальной миграции округление, диапазоны и точность должны проверяться отдельно. Важнее для нашей темы следующее: выражение USING требует вычисления нового физического значения каждой строки.

    У типов различаются размер, представление в tuple, выравнивание, правила сравнения и зависимые индексы. Поэтому нельзя просто заменить OID типа в pg_attribute и объявить работу законченной. PostgreSQL в общем случае должен построить новую версию отношения.

    5.1. Когда rewrite можно избежать¶

    Типы иногда имеют бинарно совместимые представления. Если USING не меняет содержимое значения, а преобразование допускает сохранение физической последовательности байтов, table rewrite может быть не нужен.

    Официальная документация PostgreSQL 18 указывает на такие исключения для бинарно совместимых типов или некоторых доменов без ограничений. Например, изменение text на совместимый varchar без изменения collation может избежать переписывания таблицы и даже перестройки соответствующего индекса, если его логическое поведение остается эквивалентным.

    Но из факта отсутствия table rewrite не следует, что не нужно перестраивать индекс. Изменение collation, операторного класса или семантики порядка способно сделать старую индексную структуру логически неправильной.

    Нужно отдельно решить два вопроса:

    1. Можно ли сохранить старое представление heap tuple?
    2. Можно ли сохранить старые индексные ключи и порядок?

    Это разные проверки. Успешность одной не гарантирует вторую.

    5.2. Как работает rewrite на уровне отношения¶

    Упрощенная схема физического пути:

    orders (старая таблица)
OID relation = 16400
old relfilenode = 16400
   │
   │ последовательно читаем tuple
   ▼
вычисление новых значений + проверка ограничений
   │
   ▼
новое физическое отношение / новые страницы
new relfilenode = 17821
   │
   ├─ перестройка необходимых индексов
   ├─ согласованное обновление catalog metadata
   └─ завершение транзакции
   ▼
orders (тот же логический объект/OID)
новый relfilenode

    Здесь номера условные. oid — идентификатор логического объекта в системных каталогах. relfilenode — идентификатор физического файла для обычного отношения. Он может поменяться при переписывании, даже когда oid остается тем же. Для mapped relations pg_class.relfilenode = 0, поэтому универсальнее исследовать pg_relation_filenode().

    При rewrite PostgreSQL строит новый физический набор страниц, формирует новые tuple, обновляет связанные структуры и в рамках DDL переключает отношение на новое хранение. Старыe файлы не становятся пользовательскими данными, доступными по старому SQL-имени.

    5.3. Как проверить, что переписывание действительно состоялось¶

    CREATE TABLE rewrite_demo (
    id bigint PRIMARY KEY,
    payload integer NOT NULL
);
INSERT INTO rewrite_demo
SELECT g, g FROM generate_series(1, 10000) AS g;

SELECT 'rewrite_demo'::regclass::oid AS relation_oid,
       pg_relation_filenode('rewrite_demo'::regclass) AS filenode_before,
       pg_relation_size('rewrite_demo'::regclass) AS heap_bytes_before;

ALTER TABLE rewrite_demo
ALTER COLUMN payload TYPE text
USING payload::text;

SELECT 'rewrite_demo'::regclass::oid AS relation_oid,
       pg_relation_filenode('rewrite_demo'::regclass) AS filenode_after,
       pg_relation_size('rewrite_demo'::regclass) AS heap_bytes_after;

    Ожидается тот же OID логической таблицы и изменение filenode в данном примере. Учитываем, что вывод команды SELECT ... before нужно сохранить отдельно: оба запроса не выполняются в одном SQL-выражении автоматически.

    5.4. Зачем нужен новый файл, а не модификация старого «на месте»¶

    Предположим, мы изменяем каждую строку внутри старого файла и на 60% работы возникает ошибка преобразования:

    строки 1–35 млн: новый формат
строки 35–60 млн: старый формат

    Такое состояние плохо совместимо с транзакционной атомарностью DDL и откатом. Построение нового физического отношения позволяет подготовить согласованную структуру отдельно, затем зафиксировать переключение в рамках транзакции. В реализации участвуют механизмы создания storage и изменения catalog mappings, а WAL обеспечивает необходимые гарантии долговечности согласно уже изученному блоку 7.

    Это дорого: возможны большой объем записи, необходимость временного свободного места, существенная генерация WAL, а также полная перестройка индексов. В таблице с крупными TOAST-значениями нужно отдельно учитывать реальную структуру данных, а не только размер основного heap.

    5.5. Важная MVCC-оговорка при rewrite¶

    Обычное MVCC-чтение позволяет увидеть старую версию строки. Но переписывающий ALTER TABLE в PostgreSQL относится к операциям, не полностью безопасным для старых снимков (not MVCC-safe). Официальная документация предупреждает: после фиксации rewrite транзакция со снимком, созданным до DDL, может увидеть таблицу пустой, если до начала DDL она не обращалась к этой таблице.

    Почему условие такое специфическое? Транзакция, успевшая обратиться к таблице до DDL, обычно удерживает совместную для чтения table-level блокировку, которая не позволила бы переписывающему DDL получить необходимую сильную блокировку до завершения этой транзакции.

    Получается, переписывание relation — это граница, на которой обычную интуицию «всегда доступны старые строки по старому snapshot» необходимо уточнять. В основной теме MVCC мы уже разбирали видимость tuple; здесь меняется само физическое отношение.

    5.6. Операции с TOAST и индексами¶

    Не следует думать, что стоимость rewrite определяется только размером pg_relation_size(table). В сложной схеме участвуют связанные индексы, TOAST-отношение, metadata и дополнительное пространство на диске. Поэтому для предварительной оценки полезно снять три величины:

    SELECT
    pg_size_pretty(pg_relation_size('orders')) AS heap,
    pg_size_pretty(pg_indexes_size('orders')) AS indexes,
    pg_size_pretty(pg_total_relation_size('orders')) AS total;

    pg_total_relation_size учитывает связанное хранение, поэтому нижней оценкой стоимости часто будет несколько проходов по существенной доле этих данных. Но размер на диске не равен точному числу байтов, которые обязательно будут прочитаны или записаны: работают shared buffers, page cache, особенности индексов и физических сегментов.

    6. Сколько стоит rewrite: считаем ресурсную модель¶

    Пусть таблица занимает 180 ГиБ heap, индексы — 60 ГиБ, а эффективная скорость последовательной записи при данном фоне нагрузки — 300 МиБ/с.

    Самая грубая нижняя оценка только записи нового heap:

    [ T_{heap write} \approx \frac{180 \times 1024 \text{МиБ}}{300 \text{МиБ/с}} \approx 614 \text{с} \approx 10.2 \text{мин}. ]

    Это 10 минут без учета чтения старого heap, вычисления преобразований, построения новых индексов, WAL и fsync, TOAST, конкурирующих запросов и колебаний производительности storage.

    Если среда демонстрирует 300 МиБ/с только на отдельном тестовом стенде, а в production устройство уже выполняет другой I/O, реальное время может оказаться значительно больше. Излишняя точность при такой оценке создает ложную уверенность.

    6.1. Дисковая емкость¶

    Во время rewrite могут одновременно существовать старые данные и новые создаваемые файлы. Плюс возникают WAL и промежуточные структуры. Поэтому проверка «есть 180 ГиБ свободного места для таблицы 180 ГиБ» слишком оптимистична.

    Для подготовки нужно задать ресурсную модель:

    Peak extra disk ≳ new heap + indexes rebuilt + temporary files
                  + WAL until recycled/archived + safety margin

    Точное число зависит от операции, схемы, настроек PostgreSQL и процессов, которые удерживают WAL. Для большого изменения безопаснее испытать план на копии с репрезентативными данными и измерить пиковое использование диска, а не объявлять коэффициент 2× универсальным правилом.

    6.2. Что произойдет, если rewrite упадет на половине¶

    Если ошибка произошла внутри транзакционного DDL, изменения SQL-схемы откатываются. Но ресурсы уже могли быть потрачены: десятки гигабайт прочитанных и записанных данных, WAL, временное пространство и время недоступности. Внешний наблюдатель увидит не «никакой миграции не было», а реальную деградацию, после которой конечная схема вернулась к прежнему виду.

    Rollback гарантирует транзакционную семантику изменений, но не возвращает потраченное время CPU/IO и не делает попытку бесплатной.

    6.3. А если внутри USING ошибка конверсии¶

    ALTER TABLE customer_contacts
ALTER COLUMN phone TYPE bigint USING phone::bigint;

    При встрече строки с телефонным номером вроде +7 (999) ... конверсия может завершиться ошибкой. Если таблица большая, это произойдет после длительной обработки.

    Инженерный порядок обратный:

    1. Подготовить проверку формата и измерить долю некорректных значений.
    2. Исправить данные отдельными ограниченными пакетами.
    3. Проверить все критические крайние случаи.
    4. Только затем запускать физическую миграцию.

    Здесь источником надежности выступает качество входных данных, а не скорость выполнения ALTER.

    7. Как наблюдать rewrite и не путать его с обычным выполнением SQL¶

    Для CREATE INDEX есть отдельное progress view. Для произвольной операции ALTER TABLE ... ALTER COLUMN TYPE нет общего публичного pg_stat_progress_alter_table, который выдавал бы точный процент завершения физического rewrite. Это важное эксплуатационное ограничение.

    Можно наблюдать активный backend, ожидаемые и удерживаемые блокировки, размер relation, системные счетчики I/O, нагрузку на файловую систему и WAL. Но эти показатели — косвенные. Они не гарантируют корректного прогноза оставшегося времени.

    Изменение pg_relation_filenode() после завершения — хороший диагностический признак создания нового физического отношения, а не онлайн-процент прогресса. Внутри незавершенного DDL объект rewrite также может быть скрыт от обычного snapshot, поэтому попытки читать каталоги из второй сессии имеют ограничения видимости.

    Инженерный вывод раздела: для потенциального rewrite готовим место, окно доступности, предварительную проверку данных, план наблюдения и критерии прерывания. Если команда должна выполняться при активном трафике, ищем способ разбить изменение на совместимые этапы, а не надеемся, что DDL «как-нибудь пройдет».

    IV. Constraint validation: разделяем введение правила и проверку истории¶

    8. Новое ограничение на большую таблицу¶

    Предположим, бизнес теперь запрещает отрицательную сумму заказа. В таблице 60 миллионов строк. Если сразу сделать:

    ALTER TABLE orders
ADD CONSTRAINT orders_amount_positive CHECK (amount >= 0);

    PostgreSQL должен убедиться, что уже существующие строки удовлетворяют правилу. На большой таблице это дорого. Кроме того, режим блокировки при таком объединенном DDL может мешать конкурентным операциям на весь период проверки.

    Новый вопрос: можно ли сразу начать отвергать плохие новые записи, а исторические проверить отдельно?

    Да, для поддерживаемых типов ограничений существует NOT VALID.

    9. Две фазы: NOT VALID и VALIDATE CONSTRAINT¶

    -- Короткое создание определения ограничения:
ALTER TABLE orders
ADD CONSTRAINT orders_amount_positive
CHECK (amount >= 0) NOT VALID;

-- Отдельный длинный проход по старым строкам:
ALTER TABLE orders
VALIDATE CONSTRAINT orders_amount_positive;

    После первого шага новые и изменяемые строки должны удовлетворять check-constraint. Исторические данные пока не проверены глобально. Второй шаг проверяет уже существующие строки. PostgreSQL может выполнять валидацию, не блокируя обычные конкурентные изменения так, как это делал бы долгий сильный DDL lock, потому что изменения уже контролируются новым правилом.

    VALIDATE CONSTRAINT для CHECK/NOT NULL в PostgreSQL 18 использует SHARE UPDATE EXCLUSIVE на проверяемой таблице. Для FOREIGN KEY также важны блокировки связанного отношения. Конкретный набор объектов нужно смотреть отдельно.

    9.1. Откуда известно, проверен ли constraint¶

    В pg_constraint есть два независимых признака:

    • conenforced — включено ли принудительное применение;
    • convalidated — выполнена ли проверка существующих данных.

    Пример:

    SELECT conname, contype, conenforced, convalidated,
       pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid = 'orders'::regclass
ORDER BY conname;

    До VALIDATE ожидаем convalidated = false, после успешной проверки — true. Это полезно для мигратора: повторный запуск должен опираться на фактическое состояние каталога, а не только на запись о завершении командного процесса.

    9.2. Почему новая запись уже защищена¶

    Представим, что историческая строка имеет amount = -10. Она пока хранится в таблице, потому что ограничение добавлено NOT VALID. Но транзакция пытается вставить новый заказ с amount = -5: она получает ошибку ограничения.

    Если другая транзакция обновляет старую строку с отрицательным значением, check применяется к результирующей записи. Приложение должно учитывать такие исторические нарушения при переходе на новое правило; иначе любое обновление «старого» заказа может внезапно сломаться.

    Обратите внимание: NOT VALID помогает избежать длинной начальной проверки под сильной блокировкой, но не обещает, что валидация обязательно пройдет. Ее результат зависит от исторических данных.

    9.3. А что, если валидация нашла нарушение¶

    Команда завершается ошибкой. Состояние самого существующего ограничения NOT VALID сохраняется, если оно было создано и зафиксировано отдельной транзакцией. Поэтому правильно:

    ADD ... NOT VALID → COMMIT
       │
       ▼
находим и исправляем исторические нарушения
       │
       ▼
VALIDATE → успешно → convalidated = true

    Если обе операции необдуманно положены в общий BEGIN, длительные работы и сильные блокировки могут оказаться связаны в одну транзакцию. Разделение фаз помогает контролировать риски независимо.

    10. PostgreSQL 18: NOT NULL NOT VALID¶

    Здесь действительно произошло изменение относительно старых версий. В PostgreSQL 18 ограничение NOT NULL представлено в pg_constraint как contype = 'n' и может быть добавлено с NOT VALID с последующей отдельной проверкой.

    ALTER TABLE orders
ADD COLUMN external_id text;

-- Подходит для PostgreSQL 18:
ALTER TABLE orders
ADD CONSTRAINT orders_external_id_nn
NOT NULL external_id NOT VALID;

-- Заполняем исторические значения отдельными пакетами.
-- Новые/изменяемые строки уже обязаны удовлетворять ограничению.

ALTER TABLE orders
VALIDATE CONSTRAINT orders_external_id_nn;

    Опасный момент: нельзя вводить новое обязательное поле в тот момент, когда старая версия приложения все еще вставляет строки без этого поля и не получает корректного DEFAULT. База будет правильно отвергать INSERT, но релиз окажется несовместимым. Поэтому техническая возможность разделить проверку и введение правила не отменяет протокол совместимости приложений из 09.0.

    10.1. Почему NOT NULL иногда не требует второго сканирования¶

    Для ALTER COLUMN ... SET NOT NULL PostgreSQL может избежать полного просмотра таблицы, если уже существует валидное CHECK-ограничение, из которого следует отсутствие NULL, и оно не удаляется в той же команде. Тогда ранее доказанный инвариант используется повторно. Это еще один пример, когда стоимость DDL зависит от состояния каталогов, а не только от SQL-оператора.

    ALTER TABLE orders
ADD CONSTRAINT ext_nn_proof CHECK (external_id IS NOT NULL) NOT VALID;

-- после заполнения исторических данных:
ALTER TABLE orders VALIDATE CONSTRAINT ext_nn_proof;

-- валидный CHECK может позволить обойти повторный scan:
ALTER TABLE orders ALTER COLUMN external_id SET NOT NULL;

    Это альтернативный путь, характерный и для более ранних версий PostgreSQL. Для 18 предпочтение между двумя способами зависит от принятой схемы миграций и совместимости с другими окружениями.

    10.2. Проверка без массовых UPDATE — почему это выгодно¶

    Для валидации нужно читать существующие версии и вычислять предикат. В общем случае не требуется заново записывать каждую строку. Поэтому стоимость ближе к O(N) по читаемым tuple, но без обязательного создания нового heap и новых индексных файлов.

    Под нагрузкой это все равно потребляет I/O, процессор, shared buffers и может конкурировать с пользовательскими запросами. Режим более слабой табличной блокировки позволяет многим обычным UPDATE/INSERT продолжаться, но не делает сканирование бесплатным.

    10.3. Где NOT VALID применять нельзя¶

    Нельзя переносить модель на любое ограничение автоматически. Для UNIQUE и PRIMARY KEY роль обеспечения уникальности выполняет соответствующая индексная структура. «Добавим UNIQUE NOT VALID, а потом проверим» — не универсальная форма, эквивалентная CHECK.

    Для крупной таблицы типовой путь уникальности — отдельно создать уникальный индекс конкурентно, проверить его состояние и затем, если требования позволяют, привязать индекс к constraint через ALTER TABLE ... ADD CONSTRAINT ... USING INDEX. У этого финального DDL тоже есть правила и короткие lock-секции. Путь подробно раскроем в следующем разделе, не возвращаясь к устройству B-tree.

    Инженерный вывод: при проверке ограничений управляем двумя независимыми обязательствами: (1) запрещать новые нарушения с момента переключения контракта; (2) доказать корректность истории. Их разделение снижает длительность сильных блокировок, но переносит ответственность за последовательность миграции на команду.

    V. Concurrent Index Building: как создавать индекс, пока таблица меняется¶

    11. Почему обычный CREATE INDEX проще и дешевле¶

    Для большой таблицы нужно добавить поиск заказов по статусу и дате:

    CREATE INDEX orders_status_created_idx
ON orders (status, created_at);

    Обычный CREATE INDEX должен построить согласованный набор ключей из таблицы, которая в тот момент могла бы активно меняться. Один из простых способов обеспечить согласованность — на время построения запретить конкурентные изменения, сохранив чтение. PostgreSQL делает это посредством соответствующей блокировки отношения (SHARE).

    Такое индексирование удобно при остановленном потоке записи или в maintenance window. Под нагрузкой сотни INSERT и UPDATE будут ждать. С ростом очереди транзакций приложение может заполнить свой пул соединений, а значит даже обращения, которым индекс вообще не нужен, начнут страдать косвенно.

    Переходим к:

    CREATE INDEX CONCURRENTLY orders_status_created_idx
ON orders (status, created_at);

    На пользовательском уровне обещание звучит просто: можно продолжать вставлять, менять и удалять строки. Но как построить полную структуру, когда данные меняются прямо во время обхода? Первая модель «прочитаем таблицу один раз» ломается.

    12. Три транзакционных этапа создания индекса¶

    В PostgreSQL 18 concurrent build — несколько транзакций и два прохода по таблице, между которыми есть обязательные ожидания. Состояние индекса публикуется постепенно в системном каталоге.

    T1. Зарегистрировать индекс в каталогах
    pg_index: indisready = false, indisvalid = false
                  │ COMMIT
                  ▼
     ожидание существующих writers
                  │
T2. Первый scan: построить индекс
    индекс еще не разрешен для пользовательского SELECT
                  │ COMMIT
                  ▼
     pg_index: indisready = true, indisvalid = false
     новые изменения таблицы начинают обслуживать этот индекс
                  │
     ожидание старых writers
                  │
T3. Второй проход / validation
     дополняем индекс пропущенными конкурентными версиями
                  │
     ожидание старых snapshots
                  │
     pg_index: indisready = true, indisvalid = true
                  │ COMMIT
                  ▼
     индекс доступен планировщику (с дополнительными оговорками)

    Здесь блоки T1/T2/T3 — логические стадии, а не буквальная копия всех вспомогательных транзакций и переходов кода. Суть проверяется официальной документацией CREATE INDEX и состояниями pg_index.

    12.1. Зачем сначала indisvalid = false¶

    На первой стадии индекса физически еще нет в полном виде. Планировщик не должен использовать его для поиска строк: в нем могли бы отсутствовать подходящие записи, и SQL тихо вернул бы неполный результат. Поэтому метаданные явно маркируют индекс как невалидный для запросов.

    Индекс уже получает имя, OID и запись каталога. Это объясняет диагностическую ситуацию «индекс существует, но EXPLAIN его не рассматривает». Сам факт успешного CREATE в системном каталоге не доказывает готовность.

    12.2. Почему после первого прохода нужно обслуживать новые INSERT/UPDATE¶

    Первый scan построил ключи для увиденного состояния таблицы. Пока он выполнялся, другие транзакции вставляли, изменяли и удаляли записи. Если после первого scan продолжить игнорировать новые изменения, валидатор никогда не сможет догнать движущуюся цель.

    Поэтому появляется промежуточное состояние:

    indisready = true
indisvalid = false

    Обычные операции записи теперь поддерживают индекс, но обычные читающие запросы не могут на него полагаться. Это важная и дорогая асимметрия: индекс уже замедляет запись, еще не ускоряя чтение.

    12.3. Что ищет второй scan¶

    Валидация должна добрать записи, которые могли быть пропущены первым проходом и необходимы для корректности итогового индекса. Это требует сравнения данных таблицы с уже построенной индексной структурой с учетом параллельных изменений.

    В pg_stat_progress_create_index это видно через стадии:

    • index validation: scanning index;
    • index validation: sorting tuples;
    • index validation: scanning table.

    Реальные действия зависят от выбранного index access method и условий; для понимания достаточно знать, что это самостоятельная работа поверх первого построения, а не «повторная проверка существования таблицы».

    12.4. Зачем ждать старые snapshots после validation¶

    Последний scan убедился в полноте индекса в выбранном отношении ко времени. Но backend с более старым snapshot потенциально способен видеть старые версии строк и интерпретировать индекс согласно своей видимости. Слишком ранняя публикация полного индекса для всех запросов нарушила бы согласованность.

    Поэтому перед окончательной публикацией PostgreSQL ждет транзакции, чьи снимки могут оказаться проблемными. В документации особо описаны сложные случаи с partial/expression indexes, а также взаимодействие со snapshot старых транзакций, выполняющихся в других таблицах.

    Главный вывод: на завершающей стадии конкурентного создания индекса прогресс сканирования может быть 100%, но команда все равно ждет. Ускорять диск бесполезно, если узкое место — возраст другого snapshot.

    13. Как состояние индекса представлено в pg_index¶

    Важные поля:

    Поле Что означает
    indisready Индекс готов принимать изменения от DML
    indisvalid Индекс пригоден для SQL-планов (с учетом дополнительных ограничений)
    indislive Индекс считается живым; false означает процесс удаления
    indcheckxmin Дополнительное ограничение на использование при слишком старых snapshot из-за возможных HOT-цепочек
    indisunique Индекс объявлен уникальным; это само по себе не утверждает indisvalid

    Проверяем:

    SELECT
    c.relname AS index_name,
    i.indisready,
    i.indisvalid,
    i.indislive,
    i.indcheckxmin,
    i.indisunique,
    pg_get_indexdef(i.indexrelid) AS definition
FROM pg_index AS i
JOIN pg_class AS c ON c.oid = i.indexrelid
WHERE i.indrelid = 'orders'::regclass
ORDER BY c.relname;

    Можно встретить indisvalid = true, но слишком старый snapshot все еще временно не может использовать индекс из-за indcheckxmin. Поэтому полезно различать глобальную валидность каталогов и применимость индекса к отдельному снимку.

    13.1. Почему флагов несколько¶

    Один булев ready не способен выразить требования одновременно к reader и writer:

    Нужно ли поддерживать индекс при INSERT?     indisready
Можно ли использовать индекс в SELECT?       indisvalid (+ условия)
Можно ли вообще учитывать его как живой?     indislive

    Эта структура данных появляется непосредственно из алгоритма конкурентного построения. Сначала мы должны начать догонять новые записи, затем доказать полноту индекса, а только потом разрешить им читать данные.

    13.2. Что происходит с уникальным индексом¶

    CREATE UNIQUE INDEX CONCURRENTLY
orders_external_id_uidx ON orders (external_id);

    Уникальность в конкурентном построении имеет особую цену. В PostgreSQL ее проверка начинает применяться к конкурентным транзакциям при начале второго scan, еще до окончательной валидности индекса. Другие запросы уже могут получать unique_violation, хотя CREATE INDEX CONCURRENTLY еще не завершился. Более того, при сбое на второй стадии оставшийся невалидный индекс может продолжать обеспечивать проверку уникальности.

    Плохое упрощение: «если индекс INVALID, он ни на что не влияет». Он может продолжать потреблять ресурсы при записи и в ряде случаев влиять на проверку уникальности. Поэтому оставленный после сбоя объект нельзя считать безобидным мусором.

    14. Почему CREATE INDEX CONCURRENTLY запрещен внутри BEGIN¶

    BEGIN;
CREATE INDEX CONCURRENTLY orders_status_created_idx
ON orders (status, created_at);
COMMIT;

    Такой код завершится ошибкой. Построение требует отдельных транзакционных стадий, собственных снимков и публикации промежуточных состояний. Внешняя пользовательская транзакция не может просто охватить их одной общей границей COMMIT.

    Система миграций обязана поддерживать специальный нетранзакционный шаг:

    -- Вне явного transaction block:
SET lock_timeout = '2s';
SET statement_timeout = '30min';

CREATE INDEX CONCURRENTLY orders_status_created_idx
ON orders (status, created_at);

RESET statement_timeout;
RESET lock_timeout;

    Если используется соединение из управляемого пула и произошла ошибка, сначала определяем, какие параметры сессии действительно остались выставлены, и восстанавливаем состояние; слепо продолжать следующий шаг на той же сессии опасно.

    Отдельно важно: CREATE INDEX CONCURRENTLY на родительской partitioned table в PostgreSQL 18 напрямую не поддерживается. Для большой partitioned table можно строить индексы на партициях конкурентно, а затем создавать/присоединять родительский partitioned index через поддерживаемую последовательность операций, чтобы минимизировать время запрета записи.

    15. Сбой: почему остается INVALID index¶

    Предположим, мы создали большой индекс, первая стадия завершилась, вторая нашла нарушение уникальности или возник deadlock. Команда завершилась ошибкой, но запись индекса осталась в каталоге.

    Почему PostgreSQL просто не откатил весь CREATE INDEX? Потому что отдельные стадии уже зафиксированы самостоятельными транзакциями. Общей пользовательской транзакции вокруг всей операции нет.

    Возможные состояния после ошибки:

    индекс не завершен
   ├─ каталог содержит объект с indisvalid = false
   ├─ физический индекс может занимать заметный объем диска
   ├─ indisready может быть true: новые записи его обслуживают
   └─ UNIQUE-проверка в отдельных случаях уже действует

    Это не доказательство того, что данные таблицы повредились. Сама таблица продолжает работать, но инфраструктура накопила частично подготовленный объект.

    15.1. Правильное расследование¶

    1. Прочитать состояние pg_index и точное определение индекса.
    2. Убедиться, что нет другой конкурентной операции и индекс больше не строится.
    3. Проверить причину ошибки: нарушение уникальности, старый snapshot, I/O, lock timeout, нехватка места.
    4. Только после этого выбирать повторное создание или реконструкцию.

    Обычно для невалидного индекса рекомендуют:

    DROP INDEX CONCURRENTLY IF EXISTS orders_external_id_uidx;

-- После устранения причины:
CREATE UNIQUE INDEX CONCURRENTLY
orders_external_id_uidx ON orders (external_id);

    DROP INDEX CONCURRENTLY тоже нельзя выполнять в явном блоке транзакции; у него дополнительные ограничения. В некоторых случаях возможен REINDEX INDEX CONCURRENTLY, но в целом перед выбором варианта нужно учитывать состояние конкретного индекса и зависимости. Удалять корректный production-индекс без анализа нельзя.

    15.2. Почему IF NOT EXISTS не гарантирует правильного повторного запуска¶

    CREATE INDEX CONCURRENTLY IF NOT EXISTS orders_external_id_uidx
ON orders (external_id);

    Если объект с именем уже существует, команда может только выдать уведомление и ничего не строить. PostgreSQL не гарантирует, что такой индекс имеет нужную структуру, валиден или вообще создан с нужным предикатом.

    Следовательно, IF NOT EXISTS полезно для некоторых идемпотентных операций, но не заменяет проверки фактического состояния схемы. В migration runner необходимо сверять pg_get_indexdef() и флаги pg_index, особенно после неопределенного результата выполнения.

    16. Как измерять прогресс index build, а не гадать¶

    SELECT
    pid,
    relid::regclass AS table_name,
    index_relid::regclass AS index_name,
    command,
    phase,
    lockers_total,
    lockers_done,
    current_locker_pid,
    blocks_total,
    blocks_done,
    tuples_total,
    tuples_done
FROM pg_stat_progress_create_index;

    Рассмотрим, что означают основные фазы:

    phase Что происходит Что ограничивает
    waiting for writers before build ожидание транзакций, писавших в таблицу открытые транзакции
    building index физическое построение CPU, heap/index I/O
    waiting for writers before validation ожидание потенциальных writers активные транзакции
    index validation: scanning index чтение индекса index I/O
    index validation: sorting tuples сортировка сведений для проверки CPU, память, temporary I/O
    index validation: scanning table поиск пропусков в таблице heap I/O
    waiting for old snapshots ожидание старых снимков длительные транзакции

    В любой момент число blocks_done / blocks_total характеризует текущую фазу, а не обязательно процент выполнения всей команды. Если сейчас написано waiting for old snapshots, счетчики блоков не дадут оценку времени ожидания. Важно уметь интерпретировать метрики по стадии алгоритма.

    16.1. Когда нужен current_locker_pid¶

    Если phase — одна из стадий waiting, полезно посмотреть current_locker_pid: конкретный backend, которого сейчас ожидает построение. Затем проверяем его транзакцию, запрос и владельца приложения с помощью известных средств диагностики.

    Не следует по умолчанию убивать этот backend: он может выполнять критическую транзакцию. Правильная эксплуатационная последовательность — выявить источник долгого удержания, оценить возможность штатного завершения и только затем принимать решение о прерывании.

    16.2. Что происходит под длительной нагрузкой¶

    Если запись в таблицу продолжается с высокой скоростью, первый scan создает основной объем данных индекса, второй догоняет пропущенные версии, а в промежутке новые операции записи уже работают с индексом. Значит, у нас одновременно есть:

    • дополнительные записи в индекс при DML;
    • чтение heap при сканировании;
    • сортировка и чтение index pages при validation;
    • удержание ресурсов backend-процессом;
    • ожидания других транзакций на некоторых стадиях.

    Цена online-индексирования — не только дополнительная длительность одной команды. Оно временно увеличивает общую стоимость работы системы.

    16.3. Что не гарантирует CONCURRENTLY¶

    Этот режим избегает длительного запрета обычных INSERT/UPDATE/DELETE из-за сильной table-level блокировки, но не обещает нулевого влияния на производительность. CPU, I/O, дисковое пространство, каталоги, вычисление предикатов и ожидание транзакций остаются ограниченными ресурсами. Одинаковые показатели p99 до и во время индексирования в рабочей среде — не гарантированное свойство PostgreSQL, а результат конкретной емкости и текущей нагрузки.

    Инженерный вывод раздела: конкурентное построение — протокол с промежуточными состояниями. Успешная миграция завершается не фактом существования имени индекса, а проверенной его валидностью и отсутствием нежелательных остатков после неудачных попыток.

    VI. Online backfill: переносим данные, пока пользователи продолжают писать¶

    17. Почему backfill — самостоятельная конкурентная задача¶

    После fast ADD COLUMN новая структура уже существует, но исторические данные не заполнены. Мы хотим разделить customers.full_name на first_name и last_name.

    ALTER TABLE customers ADD COLUMN first_name text;
ALTER TABLE customers ADD COLUMN last_name text;

    Наивный путь:

    UPDATE customers
SET first_name = split_part(full_name, ' ', 1),
    last_name  = split_part(full_name, ' ', 2);

    На большой таблице это одна огромная транзакция. Она удерживает большое количество изменений до COMMIT, создает WAL, старые tuple, нагрузку на индексы, обслуживающие процессы очистки и продолжительность восстановления после ошибки. Кроме того, она конкурирует с пользовательскими UPDATE.

    Мы уже разбирали физическую стоимость UPDATE в блоке 8. Здесь новый вопрос: как выполнить преобразование данных постепенно, сохраняя согласованность старого и нового контракта?

    17.1. Откуда возникает гонка¶

    T1  Backfill прочитал full_name = 'Иван Петров'
T2  API изменил full_name = 'Иван Сидоров'
T3  Backfill записал first_name='Иван', last_name='Петров'
T4  Новое приложение читает ('Иван', 'Петров') — устаревшее значение

    Системная команда UPDATE может технически корректно отработать и при этом сформировать бизнес-рассогласование. Инвариант требует заранее выбрать источник истины и протокол конкурентных изменений.

    18. Правильная последовательность перехода приложения¶

    Примерная последовательность развертывания:

    1. Expand schema
   добавлены nullable-поля
       │
2. Deploy compatible writer
   новые записи поддерживают оба представления
       │
3. Backfill
   заполнить историю маленькими пакетами
       │
4. Reconciliation
   сравнить старое и новое, исправить расхождения
       │
5. Switch reads
   новая версия читает новый контракт
       │
6. Stop legacy writes → Contract
   убрать старое поле лишь после завершения перехода

    Это знакомая схема из 09.0. Новое здесь — точный критерий безопасности каждой границы. Перед backfill должны быть исключены неконтролируемые старые writers, которые меняют только full_name. Пока они существуют, нужен дополнительный механизм синхронизации, например переходный код, совместимый триггер или отдельный протокол записи; выбор зависит от архитектуры системы.

    18.1. Пакетная запись по первичному ключу¶

    Простой вариант с keyset-диапазонами:

    -- :lo и :hi — границы небольшого пакета, задаваемые мигратором.
UPDATE customers
SET first_name = split_part(full_name, ' ', 1),
    last_name  = split_part(full_name, ' ', 2)
WHERE id >= :lo AND id < :hi
  AND first_name IS NULL
  AND last_name IS NULL;

    Одна порция выполняется и фиксируется отдельно. WHERE ... IS NULL предотвращает перезапись строк, где переходный writer уже установил новые значения. Для реальной базы с неполными именами нужно определить бизнес-правило парсинга, иначе корректность миграции не доказана.

    Ограничение: пара first_name IS NULL AND last_name IS NULL может быть недостаточным признаком «еще не перенесено», если NULL является допустимым бизнес-значением. Тогда нужен явный флаг состояния миграции, версия данных или другой надежный критерий.

    18.2. Порции через SKIP LOCKED¶

    Если несколько работников выбирают записи из одной таблицы, можно использовать уже изученный SKIP LOCKED как механизм разделения работы. Здесь он выступает инструментом backfill, а не новой темой о блокировках.

    WITH batch AS (
    SELECT id
    FROM customers
    WHERE first_name IS NULL AND last_name IS NULL
    ORDER BY id
    LIMIT 500
    FOR UPDATE SKIP LOCKED
)
UPDATE customers AS c
SET first_name = split_part(c.full_name, ' ', 1),
    last_name  = split_part(c.full_name, ' ', 2)
FROM batch
WHERE c.id = batch.id
RETURNING c.id;

    Все выполняется одной короткой транзакцией. SKIP LOCKED пропускает занятые строки, но при высокой конкуренции может постоянно обходить одни и те же записи. Поэтому окончательная сверка обязательна: нулевое число строк в конкретном пакете не доказывает, что в таблице вообще не осталось неперенесенных строк.

    18.3. Цена обновления пакета¶

    Пусть один пакет содержит 500 строк и занимает 100 мс вместе с фиксацией. При 1 млн строк нам потребуется примерно 2000 пакетов, то есть чистое время порядка 200 секунд. Но это условный расчет: на практике меняются порядок чтения страниц, локи, конкуренция с трафиком, частота checkpoint и нагрузка на storage.

    Чаще всего следует регулировать скорость потребления ресурса, а не пытаться закончить backfill минимальным возможным временем. Можно ограничить число workers, размер пакета, скорость транзакций и предусмотреть паузу между порциями.

    18.4. Как избежать перезаписи новой версии старой¶

    Если обе стороны пишут оба представления, нужно определить единственный источник истины на каждый этап. Например:

    • До переключения чтения главным полем остается full_name; совместимый writer поддерживает новые колонки атомарно в той же транзакции.
    • Backfill обновляет только строки, для которых новые значения еще не установлены, и проверяет актуальное full_name внутри того же UPDATE.
    • После полной сверки источник истины переключается на новые поля; старый контракт поддерживается переходным кодом до окончания развертывания.

    Гарантия корректности зависит от того, что одновременно не живет неподконтрольный код, записывающий только одну сторону. Если такой writer существует, необходимо явно зафиксировать правило синхронизации. Ни SKIP LOCKED, ни batching сами по себе проблему контракта не решают.

    19. Как доказать, что backfill завершился¶

    Одна команда UPDATE 0 не означает завершение миграции. Она могла пропустить заблокированные строки, остановиться на ограниченном диапазоне ID или быть выполненной до фиксации последних пользовательских транзакций.

    Нужна совокупность проверок:

    SELECT count(*) AS missing
FROM customers
WHERE first_name IS NULL OR last_name IS NULL;

    И отдельная проверка бизнес-эквивалентности двух представлений. Например, сравнение нормализованной конкатенации может служить первичным индикатором, но для имен с пробелами и составными фамилиями потребуется реальный доменный инвариант.

    Измеряем прогресс на устойчивом срезе, контролируем число ошибок, повторно проверяем после переключения writer, затем разрешаем чтение новых полей. Условие Contract: больше нет работающих версий приложения, которым нужен старый столбец, и новая схема прошла проверку целостности.

    Инженерный вывод: online backfill — это протокол согласования конкурентных записей. Нагрузочное ограничение решается пакетами и измерениями, а корректность — порядком изменения writers/readers и проверкой инвариантов.

    VII. Failed DDL, неопределенный результат и безопасное продолжение¶

    20. Три разных вида неудачи миграции¶

    Пусть оркестратор отправил команду изменения схемы. Не всякая ошибка означает одинаковый результат.

    Сценарий Что знаем Правильное действие
    Ошибка до начала изменения DDL мог не получить lock Проверить состояние и повторить по политике
    Ошибка внутри транзакционного DDL Изменения транзакции откатились Сверить каталоги, устранить причину
    Соединение оборвалось при/после COMMIT Результат не определен по ответу клиента Прочитать фактическое состояние другой сессией
    Сбой многотранзакционного concurrent index Часть стадий могла быть зафиксирована Проверить pg_index, при необходимости cleanup

    «Повторим SQL в цикле» — опасный план. Операция может быть частично завершенной на уровне протокола релиза, а не на уровне одного SQL-transaction.

    20.1. Идемпотентность уровня схемы¶

    Идемпотентная миграция — это преобразование, которое при повторном выполнении проверяет ожидаемые предусловия и приводит систему к тому же корректному конечному состоянию. IF EXISTS и IF NOT EXISTS являются только синтаксическими помощниками.

    Например, наличие orders_external_id_uidx ничего не говорит о его колонках, уникальности, predicate, collation или валидности. Настоящая проверка конечного состояния должна учитывать структурное определение объекта и нужные флаги каталогов.

    20.2. Почему откат не всегда означает возврат к исходной бизнес-схеме¶

    Сам PostgreSQL умеет откатывать транзакционный DDL. Но многошаговый релиз может состоять из уже закоммиченных шагов: новая колонка, backfill, опубликованная новая версия приложения, индекс, проверка constraint. Для этой операции «откатить транзакцию» уже невозможно: мы должны принимать решение о восстановлении протокола с текущего фактического состояния.

    В системе миграций нужны как минимум:

    • версия ожидаемой схемы и исходные SQL-артефакты;
    • контрольная сумма и результат каждого шага;
    • признак того, какие операции могут выполняться внутри транзакции;
    • предварительные условия для повторного запуска;
    • явные SQL-проверки конечных инвариантов.

    В 09.2 мы будем разбирать резервное восстановление, но здесь это сознательно не смешиваем с runtime-компенсацией частично примененного релиза.

    21. Две пары таймаутов: lock timeout и время всей операции¶

    Для короткого metadata-only DDL чаще всего основная угроза — долгое ожидание lock. Поэтому задаем маленький lock_timeout, а не оставляем операцию в очереди на неопределенное время.

    BEGIN;
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '15s';
ALTER TABLE orders ADD COLUMN provider_ref text;
COMMIT;

    lock_timeout отсчитывается при попытке получить блокировку, statement_timeout ограничивает выполнение команды целиком. Важный факт: statement_timeout измеряет в том числе ожидания, поэтому при меньшем statement_timeout отдельный lock_timeout может оказаться практически недостижим.

    Для длительного index build нужны другие значения: короткое ожидание некоторых блокировок при контролируемом плане, но достаточно большое общее время, иначе команда успеет выполнить половину дорогой работы и завершится по таймауту с невалидным индексом.

    21.1. Почему idle in transaction особенно опасно рядом с DDL¶

    Можно выполнить короткий ALTER TABLE, а затем час держать транзакцию открытой. Короткий SQL уже закончен, но транзакционные блокировки еще удерживаются. Поэтому migration runner обязан явным образом фиксировать короткие DDL-транзакции и не смешивать их с ожиданием ответов внешних сервисов.

    21.2. Почему миграцию иногда лучше отказать быстро¶

    Представим, что сильная блокировка требуется на миллисекунды, но в текущий момент один запрос выполняется 40 секунд. Если поставить lock_timeout = 2s, DDL быстро завершится с ошибкой. Это штатное эксплуатационное решение: мы не доказали, что изменение схемы некорректно, но отказались создавать длительную очередь запросов ради удачного момента применения.

    Дальше планировщик релиза может повторить попытку в другом временном окне, после проверки текущих транзакций. Это лучше, чем незаметно превратить короткую миграцию в недоступность приложения.

    VIII. Production diagnostics: как расследовать стоимость миграции¶

    22. Сначала выясняем класс выполняемой работы¶

    Когда DDL «завис», первая проверка — состояние backend и стадия алгоритма.

    SELECT a.pid, a.application_name,
       a.state, a.wait_event_type, a.wait_event,
       clock_timestamp() - a.query_start AS query_age,
       clock_timestamp() - a.xact_start  AS xact_age,
       pg_blocking_pids(a.pid) AS blockers,
       left(a.query, 180) AS sql
FROM pg_stat_activity AS a
WHERE a.query ILIKE '%ALTER TABLE%'
   OR a.query ILIKE '%CREATE INDEX%'
ORDER BY a.query_start NULLS LAST;

    Это лишь первый снимок. SQL-текст может быть усечен; также не все фазы DDL определяются одним представлением. Если команда CREATE INDEX — следующим шагом читаем pg_stat_progress_create_index. Если ALTER COLUMN TYPE — отделяем ожидание lock от I/O, но не обещаем точный процент rewrite без специальных измерений.

    22.1. Система не перегружена CPU, но p99 растет¶

    Обычно это признак ожидания, а не обязательно ошибочного SQL-плана. Проверяем:

    • Есть ли ожидающий ACCESS EXCLUSIVE от DDL?
    • Кто удерживает несовместимую блокировку?
    • Не создал ли DDL очередь новых SELECT/UPDATE?
    • Не находится ли приложение в состоянии, когда все его соединения заняты ожидающими SQL?

    Здесь возвращаемся к связи блокировки и сервиса: один DDL с неправильно выбранным временем запуска может вызвать каскадное накопление запросов. Оптимизация кода самого ALTER TABLE не поможет до освобождения lock.

    22.2. Диск заполнен во время миграции¶

    Предположение «rewrite занимает столько же, сколько старый heap» могло быть неверным. Собираем фактические размеры таблицы, индексов, связанного хранения, временных файлов и WAL. Проверяем пределы свободного пространства и операции, которые еще продолжат создавать файлы.

    Узкий ресурс следует диагностировать отдельно: медленный storage вызывает долгий rewrite, нехватка места вызывает отказ; оба сценария могут оставить приложение в деградированном состоянии и потребовать отдельного recovery-плана. Для вопросов WAL durability отсылаем к блоку 7 без пересказа его механизма.

    22.3. Индекс строится, но в SQL-плане его нет¶

    Проверяем три гипотезы, строго по порядку:

    1. indisvalid=false — индекс еще строится или остался после сбоя.
    2. indcheckxmin=true — индекс может быть временно недоступен некоторым старым снимкам.
    3. Индекс валиден, но planner выбирает другой план по стоимости, статистике или селективности.

    Третий случай относится к изученному блоку 5: здесь достаточно признать, что валидность индекса — условие доступности для планировщика, но не гарантия выбора Index Scan.

    22.4. DDL завершился, а приложение падает¶

    Это уже проблема schema contract: некоторые экземпляры читают старое имя колонки, не передают новое обязательное поле или ожидают старые значения DEFAULT. Проверяем конфигурацию одновременно работающих версий приложения и точное состояние схемы.

    Иногда надежный откат — вернуть старый бинарник, сохранив расширенную схему. Удалять новые данные только для формального «rollback DDL» без необходимости опасно.

    23. Контрольное расследование: один релиз, три независимые причины задержки¶

    Соберем одну последовательность.

    Шаг 1. Мигратор добавляет source text NOT NULL DEFAULT 'legacy'. Это fast metadata-only операция. Но до ее начала он ждет ACCESS EXCLUSIVE 20 секунд. Симптом: множество ожидающих SELECT, CPU низкий. Причина: lock queue. Исправление: короткий lock timeout и перенос выполнения в допустимое окно.

    Шаг 2. Затем мигратор меняет amount bigint на numeric. На учебном стенде выполнение было быстрым; в production 180 ГиБ heap, 60 ГиБ indexes, интенсивная запись. Симптом: высокая запись, рост WAL, большой расход диска, длительное удержание блокировки. Причина: физический rewrite. Исправление: переоценить стратегию изменения типа, возможно перейти к совместимой новой колонке и длительному backfill с контролем нагрузки.

    Шаг 3. В конце запускается CREATE UNIQUE INDEX CONCURRENTLY на external_id. Первый scan завершился, второй обнаружил дубликат. Симптом: скрипт завершился ошибкой, индекс есть, indisvalid=false, при этом записи стали дороже. Причина: многотранзакционное построение оставило промежуточное состояние. Исправление: найти и устранить дубликаты, убрать невалидный индекс и повторить построение; затем проверить pg_index и бизнес-инвариант уникальности.

    Три одинаково неприятных пользовательских симптома — и три принципиально разных механизма. Если не различать их, лечение будет случайным.

    Не все столбцы таблицы можно выразить одной встроенной метрикой PostgreSQL. Для задержки приложения и I/O нужны также метрики уровня сервиса, ОС и storage.

    24.1. Критерии прерывания¶

    Перед запуском определяем, когда считаем операцию небезопасной: длительность ожидания lock, рост p99, число ожидающих соединений, скорость заполнения диска, появление ошибок. Прерывать уже выполняющееся CREATE INDEX CONCURRENTLY можно, но затем обязательно проверять промежуточное состояние. Для rewrite остановка не возвращает уже потраченный I/O.

    24.2. Модель времени завершения¶

    Для долгой работы полезно записать:

    [ T_{migration} = T_{wait} + T_{scan} + T_{transform} + T_{write} + T_{index} + T_{validate} + T_{commit}. ]

    Это инженерная модель, а не точное разложение внутренних фаз PostgreSQL: некоторые виды работы перекрываются по времени. Она полезна тем, что заставляет спросить о каждом механизме отдельно. Для metadata-only операции доминирует T_wait; для rewrite — I/O и блокировка; для concurrent index — scan плюс ожидания старых транзакций.

    IX. Итоговая модель для backend-разработчика¶

    25. Что теперь нужно держать в голове¶

    1. DDL — транзакционное изменение каталога с возможной физической работой. PostgreSQL координирует его через ATController, очереди подкоманд, каталог и lock manager.
    2. Быстрый ADD COLUMN DEFAULT использует missing value. attmissingval позволяет вернуть значение, которого нет в старой физической tuple, но операция все равно может ждать сильную блокировку.
    3. Rewrite — создание нового физического представления. Он может менять relfilenode при неизменном OID, требует места, I/O и часто перестройки индексов; присутствует особая оговорка о старых MVCC snapshots.
    4. Constraint validation — самостоятельная фаза. NOT VALID и VALIDATE разделяют введение правила для новых данных и проверку истории. В PostgreSQL 18 это распространяется также на NOT NULL.
    5. Concurrent index — многотранзакционный протокол. Промежуточные состояния indisready и indisvalid обусловлены необходимостью сначала догонять новые записи, затем доказать полноту индекса.
    6. Сбой миграции требует чтения фактической схемы. Особенно после неопределенного COMMIT и неудачного CREATE INDEX CONCURRENTLY.
    7. Онлайн-перенос данных безопасен только при согласованном протоколе writers/readers. Пакеты ограничивают нагрузку; сохранение бизнес-инвариантов требует отдельного доказательства.

    26. Минимальный production-чек-лист¶

    Перед миграцией должны существовать: матрица совместимости версий приложения; классификация каждой DDL-команды по lock/scan/rewrite; данные о размерах таблиц и индексах; план свободного места; lock и statement timeouts; алгоритм выполнения неатомарных шагов; проверки готового каталога; критерии возврата приложения; план работы с неопределенным результатом; мониторинг задержек и блокирующих процессов.

    После миграции проверяем pg_get_indexdef, indisvalid, состояние pg_constraint, наличие нужных колонок, объем не перенесенных строк и работоспособность обеих поддерживаемых версий приложения. Нормальный статус migration runner без этих проверок не является инженерным доказательством корректности.

    27. Куда копнуть глубже — без автоматического расширения программы¶

    Первый следующий слой — ATRewriteTables() и ATRewriteTable() на уровне записи каждого нового tuple. Это ответит, как PostgreSQL конструирует новый heap, какие поля старой и новой tuple descriptor сравнивает, когда вычисляет USING, как обрабатывает индексы и каким образом готовится переключение relfilenode. Полезно для точного прогноза стоимости нестандартных ALTER TABLE, но выходит за необходимые рамки 09.1.

    Второй — конкурентный B-tree build до отдельных состояний snapshot и index tuple. Это позволит формально доказать, почему двух проходов достаточно и в каких моментах возможна временная несовместимость старых snapshots. Этот слой нужен, если требуется исследование исходников indexcmds.c, index.c и validate_index() по шагам.

    Третий — Schema migration safety в распределенном релизе. Здесь можно формализовать протокол перехода между двумя версиями приложения и несколькими одновременно записывающими экземплярами: инварианты, состояния, точки возврата, контроль консистентности и доказательство отсутствия lost update во время backfill.

    Все три — предложения. В текущей лекции подробно раскрыты механизмы, необходимые для production-решений о DDL; материал 09.2 (резервные копии) и 09.3 (connection pooling) не затрагивается.
