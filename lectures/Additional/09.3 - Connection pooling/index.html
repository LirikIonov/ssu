    9.3. PostgreSQL Connection Pooling Internals¶

    Углубленная лекция магистратуры · PostgreSQL 18 (REL_18_STABLE) · Go database/sql · PgBouncer.
    Продолжение: 09.0 — назначение pooling, max_connections, session/transaction pooling. 09.1–09.2 — миграции и backup. В лекциях 05–08 уже разобраны SQL executor, MVCC, блокировки и диагностика; повторять их алгоритмы здесь не будем.
    Цель: понять физическую стоимость подключения, алгоритмы выдачи соединений, вложенные очереди, совместимость драйвера с transaction pooling и поведение системы при массовой конкуренции или потере PostgreSQL.
    Границы: в центре именно путь соединения и его жизненный цикл. Wire protocol используется настолько, насколько он объясняет PgBouncer, prepared statements, отмену и состояние сессии. Полный разбор байтов протокола предлагается как отдельный следующий слой, а не подменяет эту лекцию.
    Точность: пользовательские свойства PostgreSQL относятся к версии 18; фрагменты database/sql описывают актуальную реализацию Go, но не являются гарантиями публичного API. Возможности PgBouncer зависят от установленной версии и конфигурации. Примеры конфигурации учебные; не копировать их с паролями/лимитами в production без тестирования.

    0. Инцидент: добавили экземпляры Go-сервиса — PostgreSQL стал отвечать медленнее¶

    У нас есть сервис обработки платежных поручений. Два экземпляра приложения обслуживают 800 запросов в секунду. Средний SQL выполняется быстро, база имеет запас CPU. Менеджер просит удвоить пропускную способность. Масштабируем приложение до восьми экземпляров. И внезапно p99 вместо 45 мс становится 2 секунды; иногда появляется remaining connection slots are reserved..., а в Go растет WaitDuration.

    Очевидная модель звучит привлекательно: больше реплик приложения → больше параллельных SQL → больше TPS. Теперь проверим, где она ломается. Каждый экземпляр Go имеет собственный sql.DB; каждый sql.DB может открыть множество физических соединений; PostgreSQL на обычном подключении выделяет отдельный backend process. Когда приложение создает новые реплики, оно размножает не только обработчики HTTP, но и бюджеты подключений. Если этим никто не управляет, конкурентность начинает расти в месте, где ограниченными ресурсами являются память, CPU, пропускная способность дисков и внутренние структуры СУБД.

    Но даже после ограничения числа подключений задача не закончена. Запрос может провести 300 мс в очереди database/sql, потом 200 мс в очереди PgBouncer и лишь 4 мс внутри PostgreSQL. Если смотреть только pg_stat_statements, SQL прекрасен. Пользователю от этого не легче.

    Нам нужна модель нескольких последовательных очередей:

    HTTP request / goroutine
         │  ожидает свободную запись в локальном pool
         ▼
Go database/sql (per instance)
         │  TCP: client connection to PgBouncer
         ▼
PgBouncer: client socket + pool queue
         │  выделяется server connection
         ▼
PostgreSQL backend process
         │  Parse/Bind/Execute, CPU/I/O/locks
         ▼
Result → PgBouncer → Go rows/tx → HTTP response

    Важное замечание: одна бизнес-операция не равна одному SQL, один SQL не равен одному соединению, соединение не равно одновременно выполняемой работе. Мы будем измерять длительность удержания соединения отдельно от длительности SQL и искать, на каком уровне появилась очередь.

    0.1. Что конкретно будем доказывать¶

    1. Подключение PostgreSQL имеет цену. Ограничивать число физически созданных backend-процессов полезно, но одного ограничения недостаточно.
    2. sql.DB — конкурентный пул с очередью. Он может тормозить запрос до первого байта, отправленного серверу.
    3. PgBouncer предоставляет второй уровень выдачи ресурсов и может разделять небольшой серверный пул между множеством клиентов.
    4. Режим transaction pooling меняет привычную связь «логическая сессия клиента ↔ физическая сессия PostgreSQL». Это влияет на state, SET, prepared statements и отмену запросов.
    5. Timeout и ошибка соединения не всегда раскрывают результат предыдущего COMMIT; безопасные повторы требуют бизнес-идемпотентности.
    6. Размер пула подбирают с измерением throughput, очереди и p99; универсального «пул равен числу ядер» нет.

    В примерах используем ledgerdb и условного пользователя app_user; пароли и внутренние адреса в файле отсутствуют. Команды SHOW POOLS, SHOW STATS исполняются через административную базу PgBouncer, а не внутри обычной SQL-базы PostgreSQL.

    I. Что стоит одно физическое соединение¶

    1. Жизненный цикл PostgreSQL connection: сокет еще не означает готовую SQL-сессию¶

    Представим: клиент открывает TCP-соединение к порту PostgreSQL. Значит ли это, что запрос уже можно выполнять? Нет. Сначала необходимо пройти протокольный startup и аутентификацию, затем создать состояние backend-сессии.

    1.1. Последовательность от Dial до ReadyForQuery¶

    Go driver                Linux / PostgreSQL                  Backend
    │  TCP connect              │                               │
    ├───────────────────────────►│                               │
    │  SSLRequest / TLS, если применимо                        │
    ├───────────────────────────►│                               │
    │  StartupMessage(user, database, options)                  │
    ├───────────────────────────►│ проверка pg_hba.conf            │
    │                            │ запуск/инициализация backend ├─►
    │◄───────────────────────────┤ Authentication request        │
    ├───────────────────────────►│ authentication response       │
    │◄───────────────────────────┤ AuthenticationOk              │
    │◄───────────────────────────┤ ParameterStatus              │
    │◄───────────────────────────┤ BackendKeyData               │
    │◄───────────────────────────┤ ReadyForQuery                 │
    │  можно отправлять SQL      │                               │

    Здесь изображена логическая последовательность; реальное взаимное расположение некоторых шагов зависит от способа аутентификации, TLS и реализации ОС. До ReadyForQuery пользовательский SQL выполнять нельзя. BackendKeyData передает данные, используемые для последующей отмены запросов, а ParameterStatus — параметры сессии. Это часть PostgreSQL frontend/backend protocol, а не поведение конкретного Go-драйвера.

    С PostgreSQL 18 важно знать и тонкость версии протокола: появилась версия 3.2, расширяющая формат секретного ключа отмены. Клиенты, PgBouncer и прокси могут договариваться о поддерживаемом варианте протокола; проверять реальную совместимость следует на используемых версиях. Сам факт использования PostgreSQL 18 не гарантирует, что каждый посредник говорит на протоколе 3.2.

    1.2. Где рождается backend process¶

    Классическая модель PostgreSQL — process-per-connection: процесс postmaster принимает новое подключение и обеспечивает отдельный backend process для пользовательской сессии. На Unix-подобных ОС создание обычно использует fork/exec-подобный платформенный механизм, но конкретные операции запуска не являются универсальным API-контрактом. Сессия имеет собственное адресное пространство и доступ к общей памяти экземпляра, включая shared buffers и служебные структуры.

    PostgreSQL instance
├── postmaster / управляющий процесс
├── shared memory (shared buffers, lock tables, stats ...)
├── backend PID 3101 → session A → connection A
├── backend PID 3102 → session B → connection B
└── backend PID 3103 → session C → connection C

    Backend process ≠ выделенное ядро CPU. Сотни backend-процессов могут в течение секунды неоднократно попадать в состояние сна, ожидать клиента или ресурса. Планирует их ОС. Десять тысяч соединений не дают десять тысяч одновременно исполняемых запросов и не создают десять тысяч ядер.

    1.3. Состав стоимости подключения¶

    Физическое соединение потребляет несколько ресурсов:

    • Сокеты и файловые дескрипторы: одно соединение имеет клиентскую и серверную сетевую сторону; нужны буферы и FD.
    • Процесс и память: backend имеет private memory, стек и служебные объекты. Показатель RSS процесса нельзя просто просуммировать по всем PID, поскольку shared memory будет учтена несколько раз.
    • Инициализация: аутентификация, параметры, каталоговая информация, session state, TLS и потенциальные сетевые RTT; создание соединения дороже выдачи уже существующего.
    • Накладные расходы конкурентности: планирование процессов, работа с общей памятью, внутренними очередями, общими счетчиками и синхронизацией.
    • Резерв ресурсов выполнения: активный SQL может потреблять дополнительную память операций, например сортировки или hash-таблиц; такие затраты масштабируются с активными операциями, а не исключительно с количеством соединений.

    Нельзя утверждать, что каждый backend «всегда стоит 10 МБ» или что одна сессия всегда требует отдельный work_mem. Реальное потребление зависит от версии PostgreSQL, workload, состояния сессии и плана запроса. Измерять его нужно на конкретной системе, исключая повторный учет общих страниц.

    1.4. Разделяем три времени¶

    Определим:

    • T_connect — от начала dial до готового ReadyForQuery;
    • T_acquire — ожидание выдачи уже созданного соединения локальным или внешним пулом;
    • T_execute — обмен сообщениями SQL и обработка на стороне PostgreSQL.

    Первый запрос нового клиента может платить за все три. При переиспользовании соединения T_connect исчезает из горячего пути, но T_acquire остается. При перегрузке именно он может стать доминирующим.

    Концептуальный профиль задержки:

    TOTAL 280 ms
  Go pool wait               130 ms
  PgBouncer server wait       95 ms
  PostgreSQL execution         7 ms
  Network + decode + app      48 ms

    Это иллюстративное разложение, не результат измерения. Важна техника расследования: не путать измеренные pg_stat_statements.mean_exec_time с полным временем обработки HTTP-запроса. Кроме того, драйвер может выдавать соединение из sql.DB, которое в действительности соединено только с PgBouncer, поэтому ожидание серверного connection появляется позднее.

    1.5. Где смотреть стоимость открытия¶

    На сервере:

    SELECT pid, application_name, client_addr, backend_start, state,
       wait_event_type, wait_event
FROM pg_stat_activity
WHERE backend_type = 'client backend'
ORDER BY backend_start DESC;

    На клиенте фиксируем длительность db.PingContext(ctx) при холодном старте и отдельно измеряем ожидание локального DB.Stats(). Операция sql.Open сама по себе не обязана открывать физическое соединение: она создает объект DB и проверяет аргументы на уровне драйвера, а реальный доступ можно проверить через PingContext.

    При расследовании login storm сопоставляем всплеск backend_start, rate новых подключений, CPU постмастера/процессов, ожидания TLS/auth и логи PgBouncer. Прежде чем увеличивать пул, выясняем, не порождают ли сами лимиты частую ротацию соединений.

    2. max_connections: глобальный предел и бюджет под несколько приложений¶

    2.1. Почему нельзя просто поставить 5000¶

    max_connections — предельное число конкурентных клиентских подключений к PostgreSQL. Значение обычно требует перезапуска и влияет на выделение некоторых ресурсов сервера, в том числе shared memory. В PostgreSQL 18 присутствуют два уровня резерва: reserved_connections для ролей с pg_use_reserved_connections и superuser_reserved_connections для суперпользователей.

    Проверка:

    SHOW max_connections;
SHOW reserved_connections;
SHOW superuser_reserved_connections;
SELECT count(*) FILTER (WHERE backend_type = 'client backend') AS clients,
       count(*) FILTER (WHERE state = 'active') AS active
FROM pg_stat_activity;

    Формула учебного бюджетирования:

    connection budget for application ≈
  max_connections
  − reserved superuser/admin slots
  − other applications
  − monitoring and operational headroom

    Слот подключения — лишь один ресурс. Увеличение max_connections поднимает допустимое число конкурирующих backend-процессов; если PostgreSQL уже перегружен, это может усилить очереди внутри СУБД. На практике увеличение лимита без измерений нередко переносит проблему с отказа в подключении на рост p99 SQL.

    2.2. Умножение пулов при горизонтальном масштабировании¶

    Предположим:

    8 Go pods × SetMaxOpenConns(40) = 320 возможных соединений
PostgreSQL max_connections = 180
6 административных/служебных слотов оставлены в резерв

    Не утверждаем, что все 320 соединений обязательно откроются. SetMaxOpenConns задает верхний предел, а создание идет по спросу. Но в пик каждая реплика может дойти до своего лимита. Соответственно, суммарный теоретический пик многократно превышает разрешенный бюджет PostgreSQL.

    Если в систему добавили еще четыре реплики, общий максимум становится 480. И это происходит без изменения кода обращения к БД. Поэтому число экземпляров приложения входит в расчет наряду с величиной локального пула.

    2.3. Почему RSS не равен произведению «размер backend × соединения»¶

    Процессы разделяют shared buffers и другие области. Сумма RSS всех PID многократно посчитает общие страницы. Для оценки вклада конкретных процессов на Linux полезнее PSS из /proc/<pid>/smaps_rollup, а для общей емкости — cgroup memory, память процессов и база операционных измерений. При этом дополнительные private allocations SQL могут значительно превышать базовые затраты idle-сессии.

    Таким образом, правильный capacity planning требует эксперимента с характерными запросами, а не умножения абстрактных мегабайт на max_connections.

    2.4. Вывод первого раздела¶

    Новый клиент может создать отдельный backend process, но не дает гарантированную пропускную способность. Pooling нужен, чтобы переиспользовать дорогие физические соединения и ограничивать работу раньше, чем она захлестнет PostgreSQL. Теперь посмотрим, как этот механизм уже встроен в Go.

    II. Go database/sql: внутренняя очередь до первого SQL¶

    3. sql.DB — менеджер соединений и конкурентный ресурс¶

    Типичная ошибка начинается с такого кода:

    func Handle(ctx context.Context, dsn string) error {
    db, err := sql.Open("pgx", dsn)
    if err != nil { return err }
    defer db.Close()
    return db.QueryRowContext(ctx, "SELECT 1").Scan(new(int))
}

    Этот пример специально плохой: при вызове из каждого HTTP-запроса он создает отдельный pool и почти не переиспользует физические соединения. При высоком RPS мы превращаем пул в фабрику подключений. Правильно создать один долгоживущий *sql.DB на конфигурацию сервиса и передавать его обработчикам.

    Далее используются имена sql.DB, sql.Tx, sql.Conn из standard library. Для реального PostgreSQL нужен SQL-драйвер; в коде ниже _ "github.com/jackc/pgx/v5/stdlib" — явная внешняя зависимость, она служит только адаптером database/sql.

    3.1. Безопасная базовая конфигурация¶

    package main

import (
    "context"
    "database/sql"
    "log"
    "os"
    "time"

    _ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
    db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
    if err != nil { log.Fatal(err) }
    defer db.Close()

    db.SetMaxOpenConns(12)                  // экспериментальный предел
    db.SetMaxIdleConns(6)                   // <= max open
    db.SetConnMaxIdleTime(2 * time.Minute) // удалить долгий idle
    db.SetConnMaxLifetime(30 * time.Minute)

    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()
    if err := db.PingContext(ctx); err != nil { log.Fatal(err) }

    var n int
    if err := db.QueryRowContext(ctx, "SELECT 42").Scan(&n); err != nil {
        log.Fatal(err)
    }
    log.Printf("answer=%d stats=%+v", n, db.Stats())
}

    Числа 12, 6, 2 минуты и 30 минут — пример для измерений, не рекомендованные глобальные значения. Lifetime может закрывать соединения и провоцировать reconnect в пике; ротация должна быть согласована с сетевой инфраструктурой, серверными timeout и нагрузкой. sql.Open может возвращать объект без физического подключения; именно PingContext проверяет доступность.

    3.2. Что означает «получить connection»¶

    Внутри database/sql есть массив свободных соединений и учет числа открытых/открываемых. Типичный путь запроса на соединение:

    QueryContext / ExecContext / BeginTx
            │
            ▼
     DB.conn(ctx, strategy)
            │
      есть свободное?
       ├─ да ─► проверить lifetime/состояние ─► выдать
       └─ нет
            │
    numOpen < maxOpen (или лимита нет)?
       ├─ да ─► создать через driver.Connector ─► выдать
       └─ нет ─► зарегистрировать запрос в connRequests
                           │
                           ▼
                  ждать доступности или ctx.Done()

    Идея публичного API: если лимит открытых соединений достигнут, новая операция ждет. Конкретные названия freeConn, connRequests, numOpen, connectionOpener, driverConn — детали реализации Go, которые полезно читать в src/database/sql/sql.go, но нельзя использовать как обещание стабильной внутренней структуры на будущие версии.

    3.3. connRequests: откуда берется очередь и кто пробуждает горутину¶

    В реализации Go ожидание не обязательно означает создание дополнительного OS thread. Горутина может ждать результат через канал запроса, пока другой запрос не вернет connection. Часть работы по открытию новых физических соединений выполняется служебным механизмом connectionOpener.

    Псевдокод, отражающий архитектуру (не копия исходника Go):

    func acquire(ctx context.Context) (conn, error) {
    lockPool()
    if idle := takeFreeConn(); idle != nil { unlockPool(); return idle, nil }
    if canOpenAnother() { reserveSlot(); unlockPool(); return dial(ctx) }

    request := enqueueRequest()  // ожидание свободного conn
    unlockPool()
    select {
    case result := <-request:
        return result.conn, result.err
    case <-ctx.Done():
        removeRequest(request)
        return nil, ctx.Err()
    }
}

    На реальном пути есть дополнительные проверки: срок службы соединения, драйверные ErrBadConn, reset session, race cancellation/return, счетчики и работа с mutex. Существенная причинно-следственная цепочка остается: лимит → очередь → ожидание context → либо выдача, либо отказ.

    Когда Rows закрыты, одиночный SQL завершен или Tx.Commit/Rollback освободил ресурс, соединение может быть передано ожидающему запросу, а не сразу помещено в свободный список. Так система не обязана каждый раз инициировать новый TCP dial.

    3.4. Когда соединение реально возвращается¶

    Разные API удерживают ресурс по-разному:

    API Когда ресурс обычно освобождается Частый дефект
    DB.ExecContext После завершения команды Игнорировать ошибку, повторять бесконтрольно
    DB.QueryContext После закрытия/исчерпания Rows Забыть rows.Close() или не дочитать курсор
    DB.QueryRowContext После Scan() Создать Row, долго не вызывать Scan
    DB.BeginTx После Commit() / Rollback() Ждать HTTP/gRPC в открытой транзакции
    DB.Conn(ctx) После Conn.Close() Навсегда закрепить физическое соединение

    Семантика Rows важна. Даже если SQL на сервере закончился, ресурс может оставаться занят клиентским чтением или обработкой результата. Код правильно закрывает Rows, проверяет rows.Err() и использует контекст:

    rows, err := db.QueryContext(ctx, `SELECT id FROM jobs WHERE state = 'ready'`)
if err != nil { return err }
defer rows.Close()
for rows.Next() {
    var id int64
    if err := rows.Scan(&id); err != nil { return err }
    // Быстрый сбор результата; длительную работу вынести за пределы цикла.
}
return rows.Err()

    Если внутри for rows.Next() мы ходим во внешний API по 500 мс на каждую строку, то удерживаем connection и тормозим чужие запросы, даже если PostgreSQL уже подготовил данные. При больших результатах и сетевом streaming момент освобождения зависит от драйвера и протокола, но правило остается: не держать Rows открытыми дольше необходимого.

    3.5. Tx как закрепленный connection¶

    Открытая транзакция принадлежит одному физическому соединению. Это необходимо для последовательности BEGIN → SQL → COMMIT на одном backend process; и локальный пул, и PgBouncer не могут раздать это соединение другой бизнес-операции посередине транзакции.

    func reserve(ctx context.Context, db *sql.DB, id int64) (err error) {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil { return err }
    defer tx.Rollback() // безопасная страховка на всех ранних выходах

    _, err = tx.ExecContext(ctx,
        `UPDATE reservations SET status = 'taken' WHERE id = $1`, id)
    if err != nil { return err }
    return tx.Commit()
}

    Здесь defer tx.Rollback() после успешного Commit просто вернет ErrTxDone, который игнорируется; это распространенный корректный шаблон. Но нельзя во время транзакции «параллельно» выполнять другие операции через db: они могут пойти через другое физическое соединение и оказаться вне ожидаемого контекста. Используем методы самого tx.

    3.6. Коварный deadlock на пуле из одного соединения¶

    // СПЕЦИАЛЬНО ДЕФЕКТНЫЙ пример.
db.SetMaxOpenConns(1)
tx, _ := db.BeginTx(ctx, nil) // удерживает единственный conn
var n int
err := db.QueryRowContext(ctx, "SELECT 1").Scan(&n) // ждет другой conn
_ = err
tx.Rollback()

    Вызов через db ожидает соединение, уже удерживаемое tx. Если после ожидающего запроса расположен единственный Rollback, операция до него не дойдет до истечения context. Это типичный pool deadlock, который совершенно не обязан отображаться как deadlock PostgreSQL в pg_locks: запрос еще не отправлен серверу.

    Корректный вариант в рамках той же транзакции — tx.QueryRowContext. Главное диагностическое следствие: если в pg_stat_activity нет соответствующего SQL, исследуем очередь клиента до PostgreSQL.

    3.7. Четыре настройки пула и их реальные компромиссы¶

    Настройка Что ограничивает Цена слишком малого Цена слишком большого
    SetMaxOpenConns(n) Всего одновременно открытых соединений Очередь и ожидание выдачи Много серверных сессий и конкуренции
    SetMaxIdleConns(n) Сколько свободных оставить Частые подключения в следующем burst Лишние idle-сессии/FD
    SetConnMaxIdleTime(d) Время простоя для переиспользования Чрезмерный churn Долгое удержание соединений
    SetConnMaxLifetime(d) Допустимый возраст reused connection Частая ротация/дополнительный dial Долгие stale-соединения при определенных сетевых сценариях

    Коннекты, которым пора закрыться по lifetime, могут закрываться лениво — при последующем использовании. Пул не обещает немедленного удаления каждого idle connection точно в миллисекунду окончания интервала. SetMaxOpenConns(0) по умолчанию означает отсутствие ограничения на стороне database/sql; у SetMaxIdleConns значение по умолчанию в текущей реализации — 2.

    3.8. Читаем DBStats как диагностику ожиданий¶

    s := db.Stats()
log.Printf("open=%d in_use=%d idle=%d waits=%d waited=%s",
    s.OpenConnections, s.InUse, s.Idle, s.WaitCount, s.WaitDuration)

    WaitCount и WaitDuration — накопительные счетчики. Их абсолютные значения после недели работы мало что скажут. Нужно измерять изменения за интервал:

    ΔWaitCount    = WaitCount(t2)    − WaitCount(t1)
ΔWaitDuration = WaitDuration(t2) − WaitDuration(t1)
mean wait of recorded waits ≈ ΔWaitDuration / ΔWaitCount

    Это средняя длительность завершившихся ожиданий за период, а не p95 и не число ожидающих прямо сейчас. DBStats не раскрывает текущую длину очереди напрямую; для нее понадобятся дополнительные метрики и трассировка стадии получения соединения. InUse = OpenConnections - Idle по текущей реализации, причем учитываются также соединения в процессе открытия; не стоит трактовать его как точное число CPU-занятых backend-процессов.

    3.9. Context ограничивает ожидание клиента, но не отменяет бизнес-неопределенность¶

    QueryContext и BeginTx используют context для ожидания и операций драйвера. Если context истек во время ожидания в database/sql, запрос мог вообще не уйти в PostgreSQL. Если истек после отправки SQL, отмена зависит от поддержки драйвера и состояния сети. После отправленного COMMIT timeout не доказывает ни фиксацию, ни откат: без достоверного ответа результат может быть неопределен для клиента.

    Этот вопрос вернется в разделе про сетевые аварии и повторные попытки. Пока запомним: контекст — механизм ограничения времени и отмены работы, а не магическое подтверждение транзакционного результата.

    4. Почему маленькая задержка SQL превращается в огромный p99: модель очередей¶

    Перед тем как вводить PgBouncer, нужно понять: что вообще значит «достаточно соединений»? Ответ будет связан с интенсивностью поступления операций и временем, в течение которого каждое соединение занято.

    4.1. Little's Law: сколько операций одновременно находится в системе¶

    Для устойчивой системы при корректном выборе границ измерения действует закон Литтла:

    [ L = \lambda W, ]

    где L — среднее число операций в выбранной части системы; λ — средняя интенсивность поступления/завершения операций (операций в секунду); W — среднее время, проведенное операцией в этой части системы (секунды).

    Для занятых соединений без ожидания выдачи пулом используем время удержания соединения S_hold, а не весь HTTP-response time:

    [ C_{busy} \approx \lambda_{db} \cdot S_{hold}. ]

    Пример: 2000 DB-операций/с × 0,012 с = 24 одновременно занятых соединения в среднем. Если есть 32 серверных соединения, получаем условную среднюю загрузку 24/32 = 75%. Это только точка отсчета для эксперимента, потому что всплески, хвосты распределения и неоднородные запросы влияют на очереди значительно сильнее среднего.

    И еще одна ловушка: 2000 HTTP requests/sec не обязательно означают 2000 DB-операций/sec. Один HTTP-запрос может выполнить пять SQL последовательно, а другой не обращаться к базе. Для расчетов нужно использовать реальный поток операций, запрашивающих соединение, и период его удержания.

    4.2. Почему нельзя подставлять только pg_stat_statements.mean_exec_time¶

    Предположим, SQL выполняется на стороне СУБД за 4 мс, но Go-код после QueryContext лениво читает результат в течение 20 мс. Среднее время занятости соединения будет ближе к 24 мс плюс сетевые накладные расходы. При том же λ = 2000/s расчет уже дает около 48 одновременно занятых соединений вместо 8.

    Если дополнительно приложение начинает внешнюю RPC-операцию внутри sql.Tx, время удержания вырастает до 120 мс: 2000 × 0,12 = 240 одновременно занятых соединений. Конфигурация с 32 серверными соединениями окажется перегружена задолго до роста среднего CPU PostgreSQL.

    SQL execution:          [==== 4 ms ====]
Rows decoding:                            [========== 20 ms ==========]
External RPC inside Tx:                                            [======== 96 ms ========]
Connection is occupied: [========================== 120 ms =================================]

    Вывод: оптимизация плана на 1 мс может дать меньший выигрыш, чем сокращение времени удержания транзакции на 100 мс.

    4.3. Почему при загрузке около 100% очередь растет взрывным образом¶

    Пусть пул обслуживает не больше c операций одновременно, а средняя продолжительность удержания соединения — S. В идеализированной однородной модели его сервисная емкость примерно c/S операций в секунду. Если новые операции поступают быстрее, чем система может их обслужить, очередь будет увеличиваться, пока не сработают timeout, отказ или внешний backpressure.

    При c = 20, S = 10 ms идеализированная емкость — 2000/s. На практике безопасная постоянная нагрузка может быть ниже из-за распределения времен, всплесков, сетевых задержек и общей СУБД. Более того, сами S под нагрузкой меняются, поэтому формула не является точным предсказанием TPS.

    Рассмотрим условный burst в 300 запросов, которым внезапно потребовался pool size 20. Даже если каждая операция занимает ровно 10 мс, очередь будет обслужена лишь за несколько последовательных волн. Последним операциям придется ждать около 140 мс до выдачи. А SQL по-прежнему занимает 10 мс.

    4.4. Admission control и backpressure¶

    Ограничение соединений — разновидность допуска к ресурсам. Оно защищает PostgreSQL от бесконечного параллелизма ценой появления очереди перед базой. Если очередь тоже не ограничивать по времени или размеру, HTTP-сервис получит рост числа ожидающих горутин, таймауты клиентов и увеличение потребления памяти.

    Инженерный выбор состоит из трех параметров: лимит параллельной работы, допустимое ожидание выдачи и политика отказа/снижения нагрузки. Следует определять их по SLO. Если клиентский дедлайн 200 мс, бессмысленно держать его 190 мс в очереди до начала SQL, который в норме занимает 30 мс.

    Для production измеряем раздельно время ожидания локального pool, PgBouncer queue и время обработки сервером. Важнейшая практика — устанавливать дедлайны, которые согласованно покрывают весь путь и оставляют место на возврат ответа.

    III. PgBouncer: второй pool между клиентом и PostgreSQL¶

    5. Архитектура: зачем прокси нужен собственный учет двух видов connection¶

    Мы ограничили локальный пул до 12 соединений на экземпляр, но экземпляров восемь. В худшем случае остается 96 подключений. При увеличении реплик до двадцати — уже 240. Что делать, если нужно сохранить множество логических клиентов, но не наращивать число backend-процессов PostgreSQL?

    PgBouncer принимает клиентские соединения и поддерживает отдельные серверные соединения к PostgreSQL. Это два независимых набора сокетов и два жизненных цикла.

    5.1. Схема двухстороннего прокси¶

    Go pod A ─ 12 client sockets ─┐
Go pod B ─ 12 client sockets ─┤
Go pod C ─ 12 client sockets ─┤
Go pod D ─ 12 client sockets ─┼─► PgBouncer: 48 client connections
                              │        │
                              │        ├─ 20 server connections
                              │        │        │
                              └────────┘        ▼
                                       PostgreSQL: 20 backend PID

    В режиме transaction pooling клиентский socket не обязан постоянно владеть серверным socket. Прокси назначает серверное соединение только на период транзакции и возвращает его в общий пул после завершения. В результате десятки или сотни долгоживущих приложенческих TCP-соединений могут использовать существенно меньше backend-процессов PostgreSQL.

    Здесь важно следующее ограничение: один server connection в каждый момент способен обслуживать только одного назначенного клиента/транзакцию. Прокси не превращает 20 серверных соединений в 100 одновременно выполняющих SQL backend-процессов. Его задача — мультиплексировать спрос во времени и ограничить число физических backend-сессий.

    5.2. Состояния client/server объектов¶

    PgBouncer ведет состояние своих подключений. Полезная ментальная модель:

    Client A: connected  ──► waiting  ──► linked to Server 7 ──► unlinked
Client B: connected  ──► waiting ────────────────┐
                                                  │
Server 7: idle ──► active(client A) ──► idle ────┴─► active(client B)

    Точные внутренние структуры и переходы зависят от версии PgBouncer. Общая архитектура реализуется в файлах src/objects.c, src/client.c, src/server.c, src/pooler.c и соседних частях исходного проекта. Это сетевой прокси со своим событийным циклом, а не дополнительный экземпляр PostgreSQL с SQL executor. Он проксирует сообщения протокола и управляет назначением соединений.

    Не следует автоматически считать, что PgBouncer умеет распараллелить одну SQL-транзакцию между backend-процессами. Пока транзакция активна, ее session state принадлежит конкретному серверному соединению.

    5.3. Что такое «один pool» в PgBouncer¶

    В типовой конфигурации отдельный пул серверных соединений создается для пары (database, user). Это не всегда один глобальный pool на весь прокси.

    ledgerdb / app_user     → pool A (e.g. 20)
ledgerdb / report_user  → pool B (e.g. 20)
auditdb  / app_user     → pool C (e.g. 20)

    Следствие: default_pool_size = 20 не обязательно ограничивает все подключения данного экземпляра PgBouncer двадцатью. Несколько пар database/user могут создать несколько пулов, и суммарный бюджет серверных соединений нужно считать по всем пулам, включая резервные подключения и другие экземпляры прокси.

    Тонкость конфигурации [databases]: если указан принудительный серверный user, многие клиентские пользователи могут использовать общий серверный пул с этой ролью. Это влияет на модель безопасности и изоляции; так делать можно только осознанно. Не забываем различать имя клиента на входе и роль подключения на PostgreSQL.

    5.4. Два лимита, которые постоянно путают¶

    Параметр PgBouncer На что действует Практическое следствие
    max_client_conn Число клиентских сокетов, принимаемых PgBouncer Определяет число одновременных клиентских подключений, а не размер server pool
    default_pool_size Базовый лимит серверных соединений на пару database/user Ограничивает число PostgreSQL backend sessions, привязанных к этому pool
    reserve_pool_size Дополнительные серверные соединения сверх основного pool при условиях timeout Позволяет временно увеличить расход ресурсов PostgreSQL
    max_db_connections Общий предел серверных подключений для database в PgBouncer Нужен, если несколько user-pool должны делить общий бюджет
    max_user_connections Общий предел серверных подключений пользователя Ограничивает суммарную емкость по всем его пулам

    reserve_pool_size не является «бесплатным» запасом. Когда PgBouncer откроет дополнительные server connections, PostgreSQL увидит реальные новые backend-процессы. У резервов тоже должен быть лимит в бюджете max_connections.

stats_users = pgbouncer_stats

    Это фрагмент, который не запустится без корректных ролей, auth_file, PostgreSQL и сервиса PgBouncer. В production потребуются безопасная конфигурация frontend/backend TLS, проверка секретов и политики доступа, запрет открытого admin listener, корректный ulimit -n, метрики и отказоустойчивое развертывание. Величины лимитов подобраны для демонстрации, не для банка.

    5.6. Почему max_client_conn может потребовать увеличения FD¶

    Для клиентского сокета нужен файловый дескриптор. Для каждого server connection — еще один. PgBouncer дополнительно использует слушающие сокеты, файлы журналов и другие FD. Поэтому max_client_conn = 5000 не означает, что ОС должна разрешить ровно 5000 дескрипторов. В худшем случае потребуется заметно больше, особенно при нескольких серверных пулах.

    Проверять нужно системные ограничения числа открытых файлов, фактическое потребление FD и зависимость от TLS. И снова важна архитектура: сокращение числа server connections не избавляет PgBouncer от стоимости принятия и поддержания client sockets.

    5.7. Как PgBouncer понимает, что SQL-транзакция завершилась¶

    PostgreSQL wire protocol содержит сообщение ReadyForQuery. В нем сервер сообщает состояние транзакции:

    'I' — idle, вне блока транзакции
'T' — внутри блока транзакции
'E' — внутри блока транзакции, завершившейся ошибкой

    При BEGIN и нескольких SQL-командах состояние остается T (или E после ошибки) до завершения транзакции. После успешного COMMIT или ROLLBACK сервер возвращается к I. Это дает прокси наблюдаемую протокольную границу, когда серверную сессию можно безопасно переназначить при transaction pooling.

    Client A         PgBouncer          PostgreSQL
BEGIN  ────────────► ────────────────► ReadyForQuery(T)
UPDATE ────────────► ────────────────► ReadyForQuery(T)
COMMIT ────────────► ────────────────► ReadyForQuery(I)
                     release server connection
Client B         ◄─ server connection now available

    Внимание: Sync не завершает явно начатую транзакцию. Он завершает цикл extended protocol, после чего ReadyForQuery сообщает фактическое состояние. Поэтому «пришел Sync» и «можно освободить backend» — не синонимы.

    5.8. Административная консоль PgBouncer¶

    Обычно подключаются к специальной виртуальной базе pgbouncer через psql с разрешенной административной/статистической ролью:

    psql 'host=127.0.0.1 port=6432 dbname=pgbouncer user=pgbouncer_stats'

    В консоли:

    SHOW POOLS;
SHOW STATS;
SHOW CLIENTS;
SHOW SERVERS;
SHOW DATABASES;
SHOW CONFIG;

    Команды выполняются в консоли PgBouncer. Обычная SQL-база PostgreSQL на 5432 не понимает SHOW POOLS. Еще одна особенность: административная консоль PgBouncer использует простой протокол запросов; некоторые драйверы, всегда выбирающие extended query, для нее не подходят. psql — хороший инструмент именно для этого случая.

    5.9. Что означает SHOW POOLS¶

    Наиболее полезные поля:

    Поле Как читать Что подозревать
    cl_active Подключенные клиенты, связанные с сервером либо пока не ожидающие выдачу Само по себе не число выполняемых SQL
    cl_waiting Клиенты, ждущие server connection Источник PgBouncer queue delay
    sv_active Серверные соединения, назначенные клиентам Фактическая занятость server pool
    sv_idle Немедленно пригодные свободные серверные соединения Запас емкости

    cl_active включает некоторых клиентов, которые просто подключены и пока не ждут сервера. Поэтому cl_active = 100 не доказывает 100 SQL одновременно. Важно совместно смотреть sv_active, cl_waiting и серверные metrics.

    5.10. Почему SHOW STATS не показывает p99¶

    SHOW STATS дает агрегаты, например total_query_count, total_xact_count, total_query_time, total_xact_time, total_wait_time, а также avg_query_time, avg_xact_time, avg_wait_time. В документации PgBouncer длительности представлены в микросекундах. Средние значения рассчитываются за интервал статистики (stats_period), накопительные — за время жизни процесса.

    avg_wait_time = 1000 μs означает среднее около 1 мс у измеряемых ожиданий. Это не означает, что ни один клиент не ждал 2 секунды. Периодически проверяем cl_waiting, maxwait и внешние p95/p99 клиентского ожидания.

    5.11. Принципиальная цена PgBouncer¶

    PgBouncer сам расходует CPU, память, сокеты, производит проксирование и может стать узким местом. TLS с обеих сторон добавляет обработку, а высокий сетевой throughput создает нагрузку на сетевой стек. Добавление внешнего пула оправдано, когда он устраняет более дорогую проблему или упрощает управление количеством физических PostgreSQL backend-процессов.

    Результат: мы получили второй уровень admission control. Теперь самое сложное — выбрать момент освобождения server connection, не сломав смысл PostgreSQL-сессии.

    6. Session pooling и transaction pooling: кто владеет состоянием сессии¶

    Договорились, что server connection дорого. Почему же PgBouncer не освобождает его после каждого SQL, как только получен результат? Потому что SQL выполняется в рамках сессии, у которой есть состояние, и это состояние меняется командами.

    6.1. Session pooling: привычный контракт PostgreSQL¶

    В режиме session один клиентский connection получает серверный connection на время логической клиентской сессии. Серверный connection обычно возвращается после отключения клиента. Если Go держит sql.DB с 12 свободными, но живыми client connections, эти клиенты могут удерживать 12 backend-процессов PostgreSQL через PgBouncer даже при отсутствии активного SQL.

    client A: CONNECT ─────────────────────────────── DISCONNECT
server 1:       ╔════ assigned to A ════════════╗  free
                │ SQL... IDLE... SQL... IDLE...│

    Плюс: сохраняется привычная семантика серверной сессии. Можно использовать session-level GUC, временные таблицы, LISTEN, prepared statements, session advisory locks при правильном управлении их жизненным циклом. Минус: из двадцати server connections легко получить двадцать совершенно idle, но закрепленных клиентских сессий.

    Если клиентов 200, а server pool 20, 180 могут ждать выдачу, даже если первые двадцать выполняют SQL лишь по 1% времени. В этом случае session pooling почти не решает задачу мультиплексирования длинноживущих клиентских соединений.

    6.2. Transaction pooling: сохраняем только контракт транзакции¶

    В режиме transaction PgBouncer выделяет серверную сессию на время одной транзакции. Клиент A выполнил короткий SQL в autocommit — серверная сессия сразу может быть назначена клиенту B. Клиент A позже начинает новую транзакцию — PgBouncer может выдать ему другой backend process.

    time ─────────────────────────────────────────────────────────────►
client A  [SELECT-1]           [BEGIN ─ UPDATE ─ COMMIT]   [SELECT-2]
client B           [SELECT]                                 [UPDATE]
server X  [A]───────[B]────────────────────────[A]───────────────[B]
server Y                                 [A]──────────────────────

    Схема условная. В момент одной транзакции клиент A связан только с одним backend; на следующей транзакции он может получить другой. Одно и то же серверное соединение может обслуживать разных клиентов последовательно, потому что PgBouncer отслеживает транзакционные границы.

    Контракт становится другим: между транзакциями нельзя полагаться на произвольный session state, созданный в предыдущей транзакции. Если случайно все операции попадают на один серверный connection, баг может не проявляться неделями; затем при росте нагрузки прокси назначает другой backend — и приложение ломается.

    6.3. Как показать смену backend-процесса¶

    В нескольких параллельных psql-сессиях через PgBouncer выполним:

    SELECT pg_backend_pid();
SELECT pg_sleep(0.2);
SELECT pg_backend_pid();

    При transaction pooling значения PID могут различаться, но одинаковые значения тоже допустимы: свободный backend может быть выбран повторно. Для воспроизводимого наблюдения создаем конкурентные запросы нескольких клиентов, получаем SHOW POOLS и сравниваем SHOW SERVERS. В session pooling PID внутри непрерывной сессии должен оставаться привязанным к одному серверному соединению, пока нет обрыва/переподключения.

    Не стоит превращать pg_backend_pid() в постоянный business identifier клиента при transaction pooling: он характеризует PostgreSQL backend, обслуживающий текущую транзакцию, а не приложение.

    6.4. Пример разрушения сессионной настройки¶

    -- Клиент A, transaction pooling
SET search_path TO tenant_a, public;
-- SET завершился как отдельная транзакция, server connection освободился

SELECT * FROM orders;
-- Следующая транзакция могла получить другой backend и другой search_path.

    Это опасный сценарий: нарушение логической изоляции данных через непредсказуемую сессионную настройку. PgBouncer имеет специальное отслеживание некоторых startup parameters, но произвольный SET/RESET несовместим с обычным контрактом transaction pooling. Не нужно пытаться решить проблему включением одного «сброса сессии» после каждой транзакции: это меняет поведение и не делает state межтранзакционно переносимым.

    Надежная стратегия — либо не зависеть от серверного search_path между транзакциями, либо явно выбирать schema в SQL/через разрешенную модель, либо использовать SET LOCAL внутри той же явной транзакции:

    BEGIN;
SET LOCAL search_path = tenant_a, public;
SELECT * FROM orders;
COMMIT;

    Здесь все команды до COMMIT выполняются на одном server connection. SET LOCAL действует только в пределах текущей транзакции, поэтому его эффект не требуется переносить между серверами. При строгой изоляции tenant данные и права нужно проектировать отдельно; одна настройка search_path не заменяет авторизацию и защиту объектов.

    6.5. Совместимость распространенных функций¶

    Возможность PostgreSQL Session pooling Transaction pooling Почему
    Обычные SQL/транзакции Да Да Server connection удерживается до завершения транзакции
    SET сессионного параметра Да Нельзя полагаться Следующая транзакция может получить другую сессию
    SET LOCAL внутри BEGIN...COMMIT Да Да Состояние ограничено одной транзакцией
    LISTEN Да Нет Слушатель должен постоянно владеть одной сессией
    NOTIFY Да Да Команда отправки уведомления не требует сохранить сессию
    Temp table ON COMMIT DROP Да Да при корректном использовании Объект живет в рамках транзакции
    Temp table PRESERVE ROWS Да Нет Объект сохраняется в физической серверной сессии
    Cursor WITH HOLD Да Нет Потребность в курсоре после конца транзакции
    Session advisory lock Да Нет Lock относится к серверной сессии

    SQL PREPARE/EXECUTE Да Нет Создается серверный state по имени

    Это концептуальная таблица для PgBouncer с возможностями, описанными в актуальной документации. Строгую матрицу для вашей версии проверяйте по https://www.pgbouncer.org/features.html; специфические расширения и драйверы могут добавлять ограничения.

    6.6. Почему транзакция продолжает удерживать server connection, даже когда ничего не делает¶

    BEGIN;
UPDATE accounts SET reserved = reserved + 1 WHERE id = 10;
SELECT pg_sleep(30);
COMMIT;

    Во время pg_sleep backend не выполняет полезной работы, но находится внутри активной транзакции. PgBouncer не может безопасно передать его другому клиенту. После UPDATE он также удерживает транзакционные ресурсы. Если клиент выполняет BEGIN и уходит в состояние idle in transaction, занятие server pool может длиться бесконечно до timeout или завершения соединения.

    Поэтому transaction pooling дает выигрыш при коротких транзакциях с большой долей времени ожидания между ними. Для работы, которая удерживает транзакцию по 30 секунд, экономия серверных соединений будет значительно меньше. Архитектура приложения влияет на результат сильнее, чем галочка в ini-файле.

    6.7. Место statement pooling¶

    PgBouncer поддерживает третий режим, statement: соединение освобождается после команды, а явные транзакции из нескольких команд запрещаются. В этой лекции он нужен лишь как граница: он подходит специализированным сценариям, но для транзакционных backend-сервисов, использующих BEGIN...COMMIT, обычно не является прямой заменой transaction pooling. Детального разбора здесь не требуется.

    6.8. Почему server_reset_query работает иначе в двух режимах¶

    В session pooling при возврате backend после отключения клиента полезно очистить session state, чтобы следующий клиент не унаследовал SET, temp tables или SQL prepared statements. В конфигурации PgBouncer типичный server_reset_query = DISCARD ALL. Это имеет цену: часть подготовленной работы надо выполнять снова.

    В transaction pooling server_reset_query по умолчанию не применяется при каждой транзакции. Приложение само обязано не использовать состояние, выходящее за транзакционные границы. Параметр server_reset_query_always существует для особых случаев, но не превращает transaction pooling в session pooling и может сделать несовместимое приложение просто предсказуемо ломающимся.

    Инженерный вывод: сохранение сессионного состояния и высокий коэффициент повторного использования server connections находятся в конфликте. Эту цену нужно выбирать на уровне архитектуры клиента, а не маскировать настройками прокси.

    IV. Prepared statements: самый частый источник скрытой несовместимости¶

    7. Что именно драйвер «подготавливает» на сервере¶

    Мы переключили PgBouncer в transaction. Сразу появился отчет: иногда команда возвращает prepared statement "stmt_1" does not exist, а иногда — prepared statement "stmt_1" already exists. Почему все происходило нормально до появления прокси?

    7.1. Два механизма с похожим названием¶

    SQL-level preparation — это явные команды:

    PREPARE find_account(bigint) AS
SELECT balance FROM accounts WHERE id = $1;

EXECUTE find_account(42);
DEALLOCATE find_account;

    PREPARE создает именованный объект в текущей серверной сессии PostgreSQL. Если следующая команда попала на другой backend, имя может отсутствовать либо относиться к другому объекту. PgBouncer не переписывает обычные SQL-команды PREPARE/EXECUTE как протокольные prepared statements.

    Protocol-level named prepared statement создается через сообщение Parse расширенного протокола PostgreSQL. Клиент может затем отправить Bind и Execute, ссылаясь на заранее названный statement. Для PgBouncer это структурированное протокольное сообщение; он способен отслеживать его и переписывать имена, если поддержка включена.

    Эти два подхода часто называются одним словом «prepared statement», но для transaction pooling их совместимость принципиально различается.

    7.2. Extended query protocol: Parse, Bind, Execute, Sync¶

    Упрощенная последовательность:

    Client                                               PostgreSQL
Parse(name="q1", sql="SELECT ... WHERE id=$1") ───────► ParseComplete
Bind(portal="", statement="q1", params=[42]) ────────► BindComplete
Execute(portal="") ──────────────────────────────────► DataRow / CommandComplete
Sync ────────────────────────────────────────────────► ReadyForQuery(I)

    Parse создает серверное подготовленное описание запроса, Bind связывает значения параметров и portal, Execute исполняет. Sync запрашивает завершение цикла; если явная транзакция открыта, ReadyForQuery(T) сигнализирует, что backend все еще занят клиентской транзакцией.

    Разбор формы отдельных пакетов оставим следующему техническому слою. Сейчас достаточно понять, что имя prepared statement существует в пространстве конкретного PostgreSQL backend process, а PgBouncer пытается создать стабильную абстракцию поверх множества таких процессов.

    7.3. Что делает max_prepared_statements > 0¶

    Начиная с PgBouncer 1.21 поддерживается отслеживание протокольных именованных prepared statements в transaction pooling (при соответствующей настройке). Механизм концептуально такой:

    Client A: Parse "find" = SELECT ... WHERE id=$1
              │
              ▼
PgBouncer: сопоставить SQL с внутренним ID
           client(A, "find") → PGBOUNCER_7
              │
              ▼
Server S1: подготовить PGBOUNCER_7 при необходимости
              │
              ▼
Client A later gets Server S2
              │
              ▼
PgBouncer: S2 еще не знает PGBOUNCER_7
           → выполнить подготовку на S2
           → Bind/Execute с новым именем

    При разных клиентах одинаковый SQL может получить одинаковый внутренний идентификатор в PgBouncer, а на серверном соединении подготовка выполняется по мере потребности. Параметр max_prepared_statements ограничивает размер LRU-кеша подготовленных statements на одном server connection. При вытеснении потребуется повторная подготовка, увеличивающая стоимость горячего пути.

    Никакого общего глобального плана SQL для всех backend-процессов PostgreSQL при этом не возникает: у них по-прежнему собственные server-side prepared statements. Прокси хранит соответствия и автоматизирует повторную подготовку на конкретном сервере.

    7.4. Почему max_prepared_statements = 0 меняет картину¶

    При значении 0 (по умолчанию в некоторых версиях/конфигурациях) указанное отслеживание protocol-level named prepared statements выключено. Если драйвер ожидает сохранение имени между транзакциями, оно может исчезнуть при смене backend. Поэтому настройку нельзя обсуждать без конкретного драйвера и способа выполнения запросов.

    Включение поддержки тоже не гарантирует, что приложение, использующее произвольные session-level операции, теперь полностью совместимо с transaction pooling. Оно закрывает одну конкретную категорию зависимости от server-side state.

    7.5. Пример с pgx/v5: почему режим исполнения важен¶

    pgx/v5 по умолчанию может использовать extended protocol с кешированием prepared statements (cache_statement). При несовместимом PgBouncer это создает проблему, если proxy не отслеживает подготовку. У pgx существуют режимы exec, simple_protocol и другие; параметр конфигурации default_query_exec_mode позволяет выбрать стратегию исполнения. Например, для целевого тестирования альтернативы prepared cache:

    postgres://app_user@pgbouncer:6432/ledgerdb?default_query_exec_mode=exec

    Это пример URI без пароля. QueryExecModeExec использует extended protocol, но не использует named prepared statement cache по модели cache_statement. Это может изменить издержки, работу с типами и семантику кодирования отдельных пользовательских типов. simple_protocol еще сильнее меняет протокол и способ интерполяции параметров — включать его автоматически ради «исправления ошибки» не следует.

    Обязательно тестируем выбранный драйвер и режим на сценариях: подготовка, изменение схемы, переподключение, смена backend, одновременные транзакции, COMMIT/ROLLBACK, отмена. Кэш prepared statements может инвалидироваться после DDL и давать ошибки независимо от PgBouncer; это отдельный механизм.

    7.6. Стоимость и диагностика prepared cache¶

    PgBouncer SHOW STATS предоставляет, среди прочего, показатели total_client_parse_count, total_server_parse_count, total_bind_count при включенной поддержке prepared statements. Если приложению приходится постоянно готовить statements на серверных соединениях, ожидаемый выигрыш от кэша может исчезнуть.

    Диагностические вопросы:

    1. Клиент использует SQL PREPARE или протокольный Parse?
    2. Какой режим pgx/другого драйвера включен?
    3. Достаточно ли большой max_prepared_statements на server connection?
    4. Не происходит ли постоянная ротация server connections?
    5. Совпадает ли число новых server-side preparations с ожидаемым числом уникальных запросов и подключений?
    6. Есть ли сообщения already exists / does not exist и воспроизводятся ли они только с transaction pooling?

    Вывод: совместимость prepared statements — это вопрос конкретных протокольных сообщений, состояния физического backend и поддержки прокси, а не абстрактной надписи «prepared=true» в конфигурации приложения.

    V. Отказы, cancel и таймауты: как не превратить сбой в лавину подключений¶

    8. Сначала выясняем, где клиент провел свое время¶

    У нас три последовательных этапа ожидания, каждый со своей точкой отмены:

    [Go local acquire] → [PgBouncer queue] → [PostgreSQL operation] → [response]
      (A)                  (B)                    (C)              (D)

    Если случился timeout, без разметки по этапам трудно понять, где была задержка. Поэтому строим временной бюджет одного запроса и приводим взаимосвязанные параметры к одному SLO.

    8.1. Слои timeout: кому принадлежит каждый¶

    Слой Инструмент Что ограничивает
    HTTP/Go context.WithTimeout Общий дедлайн вызова, включая локальное ожидание, если передан в API
    Go pool DB.SetMaxOpenConns + context Параллелизм и длительность ожидания свободного connection
    PgBouncer query_wait_timeout Ожидание server connection; при превышении отключает клиента
    PgBouncer server_connect_timeout Установление и login server connection
    PgBouncer idle_transaction_timeout / transaction_timeout Избыточно долгую idle/overall транзакцию; могут отключать клиента
    PostgreSQL statement_timeout Время выполнения SQL-команды на стороне сервера
    PostgreSQL lock_timeout Ожидание получения блокировки, если именно она является проблемой
    TCP/driver Dial timeout, TLS timeout, keepalive Сетевые этапы, зависят от драйвера и ОС

    Настройки нельзя свести к одному «всем поставить 5 секунд». Если PgBouncer оборвет клиента через query_wait_timeout = 5 s, а Go context истекает через 200 ms, пользователь все равно увидит 200 ms timeout; внешний прокси может некоторое время обрабатывать прекращение. Если, напротив, PgBouncer держит очередь 120 секунд, приложение обязано иметь собственный ограниченный дедлайн на ожидание.

    8.2. Как работает отмена запроса в протоколе PostgreSQL¶

    В PostgreSQL CancelRequest отправляется через отдельное соединение с данными, выданными backend при startup (BackendKeyData). Причина: основной backend может быть занят выполнением SQL и не обязан постоянно читать новые клиентские команды из уже использующегося канала.

    При наличии PgBouncer становится сложнее:

    Client logical connection A ──► PgBouncer ──► currently Server S7
        │                           ▲
        └── CancelRequest ──────────┘
                                    │
                       Найти выполняющийся backend
                                    │
                                    └──► PostgreSQL S7: cancel

    Proxy должен сопоставить клиентскую отмену с текущим назначенным backend, поскольку за жизнь клиентской сессии server connection мог измениться. А если PgBouncer за load balancer представлен несколькими экземплярами, новый TCP connection для отмены может попасть не к тому экземпляру, который обрабатывает запрос. В PgBouncer для сложных топологий существуют механизмы peers/forwarding cancel requests. Их корректность проверяют по конкретной версии и topology.

    В PostgreSQL 18 протокол 3.2 изменил формат секретного ключа отмены; при обновлении прокси и драйверов нужно тестировать negotiation/cancel end-to-end. Нельзя обещать, что формат пакетной отмены одинаков на всех версиях.

    8.3. Cancel не сообщает, был ли уже выполнен COMMIT¶

    Представим:

    T1: client sends COMMIT
T2: PostgreSQL commits successfully
T3: network connection drops before client sees CommandComplete
T4: client receives timeout / EOF

    На T4 приложение не знает, зафиксирована ли транзакция. Отправить еще один COMMIT бесполезно: это уже другая сессия и другая транзакция. Бездумно повторить всю операцию опасно: можно списать деньги второй раз.

    Инженерное решение остается на уровне бизнес-идемпотентности: уникальный operation ID, устойчивый ключ операции, проверка результата в БД после неопределенного исхода и согласование ожидаемого состояния. Это не новая лекция про транзакционные алгоритмы; здесь важно следствие для любой стратегии reconnect/retry.

    8.4. Reconnect storm: когда все клиенты одновременно решили переподключиться¶

    После короткого сбоя PostgreSQL теряет серверные соединения PgBouncer. Приложения получают сетевые ошибки, их локальные пулы начинают открывать новые клиентские соединения; PgBouncer пытается восстановить свои server pools. Если все клиенты одновременно повторяют запросы без ограничения скорости, получается двойной шторм: dial + retry SQL.

    PostgreSQL restart
   │
   ├─ old server connections invalid
   ├─ thousands of client retries
   ├─ PgBouncer opens new server connections
   ├─ authentication + TLS + backend initialization spike
   └─ очереди растут, дедлайны истекают, retry усиливает шторм

    В приложении нужно ограничивать параллелизм повторов, использовать bounded retry с jitter/backoff только для операций, безопасность повторения которых доказана, и сохранять общий request deadline. В PgBouncer есть server_login_retry, server_connect_timeout, резервные/ожидательные настройки. На операционной стороне полезен controlled restart/rolling update, когда это возможно.

    Отдельное правило: создавать новый sql.DB на каждую ошибку — плохой способ восстановить соединение. database/sql уже управляет жизненным циклом и выбраковкой дефектных connections через поддерживаемые драйверные механизмы.

    8.5. TLS с двух сторон PgBouncer¶

    При использовании PgBouncer между приложением и СУБД возникают две независимые сетевые границы:

    Go client ══ TLS #1 ══ PgBouncer ══ TLS #2 ══ PostgreSQL

    Шифрование на клиентской стороне не доказывает, что соединение PgBouncer → PostgreSQL тоже защищено. Сертификаты, политика проверки сервера, требования к имени хоста и логика повторного соединения конфигурируются для каждой границы. Подмена «раньше TLS до базы, теперь TLS до прокси» может неожиданно изменить фактическую модель безопасности.

    8.6. Session state после обрыва соединения¶

    При потере физического соединения исчезают session-level объекты: подготовленные statements на этом backend, session-level advisory locks, LISTEN и временные таблицы, завязанные на сессию. Go driver может заново подключиться, но не обязан автоматически восстановить все пользовательское session state.

    Следовательно, в session pooling необходимо проектировать re-initialization по необходимости и контролировать reconnect. В transaction pooling лучше минимизировать межтранзакционный server state с самого начала.

    VI. Production: sizing, измерения и расследование деградации¶

    9. Правильный размер пула нельзя получить одной константой¶

    Вернемся к нашему инциденту. У нас восемь Go-подов, в каждом SetMaxOpenConns(20). Перед PostgreSQL стоят два экземпляра PgBouncer, у каждого default_pool_size = 40 для одной пары database/user. PostgreSQL разрешает 120 соединений. Можно считать, что теперь все безопасно?

    Посчитаем потолок:

    Go clients maximum: 8 × 20 = 160
PgBouncer #1 server pool: 40
PgBouncer #2 server pool: 40
Total potential PostgreSQL server connections: 80
PostgreSQL max_connections: 120

    В показанной конфигурации основной бюджет серверных connections не превышает 80, если действительно имеется одна соответствующая пара database/user, нет дополнительных пулов, reserve и других клиентов. Но эти оговорки критичны: четыре роли × две базы, резервные пулы, сторонние сервисы и административные connections могут полностью изменить итог.

    Затем нужно проверить способность БД обслуживать нагрузку. Если PostgreSQL способен выполнять при данной смеси запросов лишь 700 транзакций в секунду, наличие 80 backend-процессов не даст 2000 TPS; запросы будут ждать внутри СУБД или PgBouncer.

    9.1. Connection budget — сумма всех потребителей¶

    Для многоуровневой системы используем бюджет не одного сервиса, а всего кластера:

    PostgreSQL max_connections = 120
  reserve superuser and privileged = 6
  monitoring / console / maintenance = 8
  other applications = 16
  safety headroom = 10
──────────────────────────────────────
available PgBouncer server budget ≈ 80

    Числа учебные; статус конкретных резервов определяется reserved_connections, superuser_reserved_connections и правами ролей. В примере остаются 80 для пула приложения. Если PgBouncer развернут в двух экземплярах, предварительный ориентир — не больше ~40 основных server connections на экземпляр при равномерной нагрузке. Но нужно также учесть reserve_pool_size, дополнительные пары user/db и аварийные ситуации, когда весь трафик переходит на один экземпляр.

    Самая частая ошибка: выделить каждому PgBouncer по 80, потому что «на PostgreSQL доступно 80». Два экземпляра могут суммарно открыть 160 серверных connections.

    9.2. Разделяем емкость по трем слоям¶

    Слой Какой ресурс лимитируем Что в очереди Чем наблюдаем
    HTTP/service Одновременная бизнес-работа Request/goroutine APM, active requests, queue, latency
    Go database/sql Client connections к PgBouncer Ожидающие goroutine DBStats.WaitCount, WaitDuration, InUse, Idle
    PgBouncer Server connections к PostgreSQL cl_waiting SHOW POOLS, SHOW STATS
    PostgreSQL Реальное исполнение SQL и ресурсы Ожидания CPU/I/O/locks pg_stat_activity, pg_stat_statements, OS metrics

    В нормальной системе желательно знать, на каком именно уровне мы хотим допустить очередь. Локальная очередь Go быстро реагирует на context и ограничивает объем клиентских запросов к PgBouncer. Очередь PgBouncer полезна для объединения клиентских пулов множества реплик, но при долгом ожидании клиенты удерживают свои подключения к прокси. Перегрузка внутри PostgreSQL обычно наиболее дорогая, потому что там уже используются backend-процессы и ресурсы СУБД.

    9.3. Измеряем database/sql в динамике¶

    Псевдоэкспорт метрик на Go с использованием standard library (хранить прошлую выборку и экспортировать Prometheus можно отдельно):

    func logPool(db *sql.DB, prev *sql.DBStats) sql.DBStats {
    now := db.Stats()
    if prev != nil {
        dw := now.WaitCount - prev.WaitCount
        dt := now.WaitDuration - prev.WaitDuration
        var mean time.Duration
        if dw > 0 { mean = dt / time.Duration(dw) }
        log.Printf("open=%d inuse=%d idle=%d waited=%d avg_wait=%s",
            now.OpenConnections, now.InUse, now.Idle, dw, mean)
    }
    return now
}

    WaitCount — число зарегистрированных ожиданий, а не текущая длина очереди. Если InUse постоянно упирается в лимит и ΔWaitCount быстро растет, есть признак saturation локального пула. Однако причина может быть и в длительном удержании connections транзакциями/Rows; увеличивать лимит нужно только после измерения hold time.

    Один DBStats не дает полную p99 задержки выдачи. Для production обычно добавляют наблюдение на границе операции (активная трассировка acquisition и SQL). Это должно быть совместимо с API выбранного драйвера и не вносить существенную избыточную нагрузку.

    9.4. Измеряем PgBouncer без догадок¶

    В административной консоли:

    SHOW POOLS;    -- cl_waiting / sv_active / sv_idle / maxwait
SHOW STATS;    -- avg_wait_time / avg_xact_time / avg_query_time
SHOW CLIENTS;  -- видим клиентские соединения
SHOW SERVERS;  -- видим server connections к PostgreSQL

    Что означает типичная запись: cl_waiting = 60, sv_active = 20, sv_idle = 0, maxwait = 3.2? Пул серверных соединений занят, 60 клиентов ждут, один из них более трех секунд. Это симптом, а не автоматически доказанная причина. Возможно, пул объективно слишком мал при свободной СУБД. А возможно, PostgreSQL исполняет тяжелые SQL по 2 секунды, и расширение пула ухудшит проблему.

    Сопоставляем avg_xact_time и avg_query_time. Если avg_xact_time намного больше avg_query_time, стоит проверить время бездействия внутри транзакций и операционную логику клиентов. avg_wait_time полезен как агрегат, но не заменяет p99. Учитываем, что SHOW STATS обновляет усреднения периодически, поэтому мгновенная картина может отличаться от исторических счетчиков.

    9.5. Что смотреть в PostgreSQL¶

    SELECT state, wait_event_type, wait_event, count(*) AS n
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state, wait_event_type, wait_event
ORDER BY n DESC;

    Анализируем реальные запросы и состояние backend-процессов. Но если подавляющая часть клиентов ждет в PgBouncer, PostgreSQL не увидит их как отдельные backend sessions. Отсутствие 500 ожидающих процессов в pg_stat_activity в таком случае — нормальный результат работы pooling.

    Сервер может быть загружен CPU без выраженного wait_event, может ждать I/O или блокировки. Диагностику конкретного SQL, его плана и причин ожидания мы уже проходили в лекциях 05–08. Здесь связываем этот вывод с решением о числе серверных connections.

    9.7. Пример: растет latency, а pg_stat_statements показывает 6 мс¶

    Симулируем рабочую картину:

    Traffic: 1600 operations/s
Go pool: 8 pods × 16 connections
PgBouncer: 2 instances × 24 server connections
PostgreSQL: 48 server backends from PgBouncer

Measured:
  average SQL = 6 ms
  average connection hold time = 35 ms
  Go WaitCount +5000/minute
  PgBouncer cl_waiting ≈ 15 ... 80
  HTTP p99 = 1700 ms

    λ × S_hold = 1600 × 0.035 = 56 означает около 56 одновременно занятых server connections в среднем, если указанное время удержания действительно приходится на server connection. У нас доступно 48, так что такая нагрузка не может устойчиво обслуживаться без очереди или изменения среднего времени удержания. Этот расчет уже находит возможную первопричину.

    Увеличение PgBouncer с 48 до 80 connections может уменьшить ожидание, если PostgreSQL способен исполнять больше активных транзакций без деградации. Но полезнее сначала выяснить, почему S_hold = 35 ms при SQL 6 ms. Если приложение удерживает connection во время 29 ms синхронного бизнес-кода, убираем эту задержку из транзакции; тогда необходимая средняя конкурентность может упасть с 56 до ~10. Это значительно лучше простой раздачи дополнительных backend-процессов.

    Замечание про формулы: нельзя смешивать среднее время удержания Go connection с временем удержания server connection PgBouncer. Они могут различаться: Go connection может простаивать как клиентский socket, не занимая server connection. Для λ × S выше выбираем одну границу измерения и считаем ее последовательно.

    9.8. Пошаговая настройка вместо «увеличить все»¶

    1. Определяем целевые throughput, p95/p99 и предельную долю ошибок на конкретном workload.
    2. Измеряем количество DB-операций на HTTP-запрос и время удержания Go/серверного connection.
    3. Определяем безопасную верхнюю границу PostgreSQL connections с учетом всех пользователей и экземпляров PgBouncer.
    4. Выбираем разумные начальные размеры sql.DB и PgBouncer, оставляя запас на мониторинг и административный доступ.
    5. Нагружаем систему при стабильном потоке, затем делаем кратковременные bursts и reconnect/failover сценарии.
    6. Сравниваем уменьшение queue wait с ростом SQL p99, CPU, памяти, I/O, sv_login и ошибок.
    7. Проверяем совместимость transaction pooling и драйвера на всей используемой функциональности, не только на SELECT 1.
    8. Фиксируем измеренные параметры, пределы и деградационный режим. Повторяем эксперимент после изменения числа pods, SQL-профиля или версии PgBouncer.

    Никакого универсального «по 10 connections на ядро» здесь нет. Формулы позволяют обнаружить противоречия, а реальный capacity test определяет рабочую конфигурацию.

    VII. Демонстрация: нагрузили, нашли очередь, исправили¶

    10.1. Минимальный тестовый стенд¶

    Для этой лекции достаточно отдельных PostgreSQL 18, PgBouncer и Go-приложения. Важно иметь два DSN:

    DATABASE_URL_DIRECT   → PostgreSQL :5432
DATABASE_URL_PGBOUNCER → PgBouncer :6432 / ledgerdb

    Оба DSN задаются через переменные окружения в локальном стенде; логировать реальные пароли нельзя. Для сравнения нужны одинаковые схема, данные, SQL и параметры времени. В production нельзя специально отключать подключения или вызывать массовые cancel на рабочей БД.

    10.2. Создаем безопасную учебную нагрузку¶

    Простейший запрос, способный удерживать серверное соединение контролируемое время:

    SELECT pg_sleep(0.025);

    Это искусственная нагрузка: она имитирует длительность занятости server connection, но почти не использует CPU/диск PostgreSQL. Из-за этого итоговый TPS нельзя переносить на реальную базу. Зато удобно изучать именно механизм очереди и различать локальную и внешнюю saturation.

    Для следующего эксперимента используем короткий реальный SQL (SELECT 1) и сравним его со pg_sleep. При наличии внешних пользовательских транзакций важно видеть количество одновременно открытых Tx, а не только число SQL-команд.

    10.3. Исполняемый Go-проверяльщик пула¶

    Внешняя зависимость только драйвер github.com/jackc/pgx/v5/stdlib; concurrency и статистика — standard library. Этот код запускаем только на учебном стенде с заданным ограничением общего числа операций.

    package main

import (
    "context"
    "database/sql"
    "fmt"
    "log"
    "os"
    "strconv"
    "sync"
    "sync/atomic"
    "time"

    _ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
    dsn := os.Getenv("DATABASE_URL")
    if dsn == "" { log.Fatal("DATABASE_URL is required") }
    poolSize := 4
    if v := os.Getenv("POOL_SIZE"); v != "" {
        n, err := strconv.Atoi(v)
        if err != nil || n < 1 { log.Fatal("invalid POOL_SIZE") }
        poolSize = n
    }
    db, err := sql.Open("pgx", dsn)
    if err != nil { log.Fatal(err) }
    defer db.Close()
    db.SetMaxOpenConns(poolSize)
    db.SetMaxIdleConns(poolSize)

    ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
    defer cancel()
    if err := db.PingContext(ctx); err != nil { log.Fatal(err) }

    const requests = 100
    const concurrency = 40
    var ok, failed atomic.Int64
    tasks := make(chan struct{}, requests)
    for i := 0; i < requests; i++ { tasks <- struct{}{} }
    close(tasks)

    var wg sync.WaitGroup
    start := time.Now()
    for i := 0; i < concurrency; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for range tasks {
                op, stop := context.WithTimeout(ctx, 2*time.Second)
                var ignored any
                err := db.QueryRowContext(op,
                    "SELECT pg_sleep(0.025)").Scan(&ignored)
                stop()
                if err != nil { failed.Add(1) } else { ok.Add(1) }
            }
        }()
    }
    wg.Wait()
    stats := db.Stats()
    fmt.Printf("elapsed=%s ok=%d failed=%d\n", time.Since(start), ok.Load(), failed.Load())
    fmt.Printf("open=%d inuse=%d idle=%d waits=%d wait_time=%s\n",
        stats.OpenConnections, stats.InUse, stats.Idle,
        stats.WaitCount, stats.WaitDuration)
}

    Параметр POOL_SIZE позволяет сравнивать 2, 4, 8, 16 соединений при одинаковом числе задач. Для PostgreSQL-драйвера Scan(&ignored) с pg_sleep возвращает одну NULL-колонку; *any допускает NULL. Если драйвер сообщает особенности обработки результата, альтернативой является SELECT 1 FROM pg_sleep(0.025) с Scan(&n) — она явно возвращает целое число.

    Запуск:

    # DSN задается вне командной строки в окружении стенда
POOL_SIZE=2  go run .
POOL_SIZE=8  go run .
POOL_SIZE=16 go run .

    Для модуля потребуется импортировать драйвер: go mod init example.com/pooldemo и go get github.com/jackc/pgx/v5/stdlib в отдельном каталоге. Команды не фиксируют версию драйвера: в воспроизводимом семестровом стенде ее надо зафиксировать через go.mod/go.sum.

    Смотрим, как изменяются WaitCount, общее время выполнения и количество завершенных операций. После появления PgBouncer дополнительно наблюдаем SHOW POOLS и SHOW STATS.

    10.4. Эксперимент 1 — локальная очередь Go¶

    Шаг 1: подключаемся напрямую к PostgreSQL, ограничиваем Go pool двумя соединениями и запускаем 40 workers. Предсказываем: большинство workers ждут локальную выдачу, а SQL на сервере одновременно выполняют не более двух клиентов данного sql.DB.

    Шаг 2: во время теста выполняем:

    SELECT count(*) FROM pg_stat_activity
WHERE application_name = 'pooldemo'
  AND backend_type = 'client backend';

    Для точной фильтрации добавляем application_name=pooldemo в DSN; иначе запрос может показывать ноль. Увидим максимум порядка размера локального пула, а не числа горутин. WaitCount увеличится даже при низком CPU PostgreSQL. Это и есть доказательство, что задержка может находиться до сервера.

    Шаг 3: увеличиваем POOL_SIZE. Очередь уменьшается до определенного предела; после достижения емкости сервера эффект исчезает или становится отрицательным.

    10.5. Эксперимент 2 — очередь PgBouncer¶

    Подключаем Go к PgBouncer в transaction pooling. Поставим на учебном стенде default_pool_size = 2, а локальный Go pool — 10. Во время нагрузки смотрим в админ-консоли:

    SHOW POOLS;

    Ожидаем sv_active около двух при устойчивом спросе, sv_idle = 0 и рост cl_waiting. В отличие от предыдущего эксперимента, локальный Go pool может иметь свободную емкость либо удерживать клиентские соединения, ожидающие PgBouncer. pg_stat_activity показывает реальные server backends PgBouncer, а не всех его клиентов.

    Построим причинную цепочку: Go выдал connection → PgBouncer принял запрос → его server pool исчерпан → клиент ждет, хотя PostgreSQL не видел этот SQL как отдельную выполняемую команду.

    10.6. Эксперимент 3 — сломанное состояние между транзакциями¶

    В transaction pooling последовательно выполним:

    SET application_name = 'attempted_state';
SELECT current_setting('application_name');

    Этот пример не является надежным тестом несохранения состояния, поскольку application_name входит в параметры, которые PgBouncer умеет отслеживать специально. Поэтому для проверки ошибки лучше использовать SET произвольного session GUC, например SET work_mem='8MB', затем читать SHOW work_mem на другом backend при конкурентной нагрузке. Даже здесь совпадение прежнего значения возможно случайно, и нельзя считать его подтверждением корректной архитектуры.

    Для строгой семантической проверки используем session-specific объект:

    CREATE TEMP TABLE session_demo (n int) ON COMMIT PRESERVE ROWS;
INSERT INTO session_demo VALUES (1);
-- Между следующими транзакциями PgBouncer может сменить backend.
SELECT * FROM session_demo;

    Сценарий специально несовместим с transaction pooling. Он может падать с relation does not exist, случайно работать при попадании на тот же backend либо обнаружить чужое состояние на переиспользованном backend. Запускать только в изолированной среде. Исправление — не зависеть от temp table за пределами транзакции или использовать session pooling для такого клиента.

    10.7. Эксперимент 4 — prepared statements и смена режима¶

    Сравниваем одну SQL-операцию:

    • direct PostgreSQL с pgx default cache_statement;
    • PgBouncer transaction pooling с max_prepared_statements = 0;
    • PgBouncer transaction pooling с положительным max_prepared_statements;
    • PgBouncer transaction pooling с драйверным default_query_exec_mode=exec.

    Для теста важно много транзакций, конкурентность и смена server backends. Единичный запрос ничего не доказывает. Измеряем ошибки, число server-side parse и latency; отдельно проверяем, не поменялась ли семантика передачи параметров. Команды SQL PREPARE следует рассматривать отдельно: настройка отслеживания протокольных подготовок не переносит их между серверными соединениями.

    10.8. Эксперимент 5 — reconnect storm и потерянный ответ¶

    В лаборатории останавливаем PostgreSQL или разрываем один тестовый backend connection (не production). Наблюдаем:

    • увеличение ошибок и изменение sv_login/SHOW SERVERS при восстановлении;
    • попытки клиента переоткрыть соединение;
    • ограничение максимума подключений в Go и PgBouncer;
    • затраты холодного startup;
    • дедлайны и порядок безопасных повторов.

    В отдельном тесте имитируем потерю ответа после изменения данных и проверяем идемпотентность операции по ее бизнес-ключу. Отправка повторного SQL без такой защиты в платежном сценарии недопустима.

    11.1. Что студент должен уметь после лекции¶

    1. По схеме приложения определить количество локальных и потенциальных серверных соединений, учитывая replicas, user/database pools, reserves и другие сервисы.
    2. Объяснить, как sql.DB выдает соединение, где ожидает горутина и чем отличаются Rows, Tx, Conn по времени удержания.
    3. Разложить latency на ожидание Go-pool, ожидание PgBouncer, работу PostgreSQL и network/app overhead.
    4. По DBStats, SHOW POOLS и pg_stat_activity установить уровень saturation.
    5. Объяснить границу транзакции через ReadyForQuery(I/T/E) и назвать session-level возможности, которые теряются при transaction pooling.
    6. Отличить SQL PREPARE от protocol-level named prepared statements и выбрать совместимую конфигурацию драйвера/прокси.
    7. Планировать timeout/retry при разрыве соединения, не делая ложного вывода о результате COMMIT.
    8. Рассчитать начальную емкость по λ × S_hold, а затем проверить ее нагрузочными измерениями.

    11.2. Главные причинно-следственные связи¶

    1. Каждый физический PostgreSQL connection имеет стоимость, поэтому безлимитное создание backend-процессов под нагрузкой дорого и опасно.
    2. Локальный пул создает очередь раньше SQL. При saturation большая часть задержки может быть невидима PostgreSQL.
    3. PgBouncer снижает число server connections, мультиплексируя запросы во времени, но не увеличивает физическую вычислительную емкость PostgreSQL.
    4. Session pooling сохраняет физическую сессию, transaction pooling освобождает ее после транзакции; за выигрыш платим ограничением session state.
    5. Время удержания соединения определяет необходимую конкурентность. Длинные Rows, транзакции и внешние операции внутри Tx повышают спрос на pool.
    6. Prepared statements живут в конкретном backend. PgBouncer может отслеживать протокольные подготовки, но не любые SQL-команды и session-level состояния.
    7. Сбой сети разрывает связь «отправили команду» ↔ «получили подтверждение». Повторная бизнес-операция должна быть безопасна при неопределенном исходе.

В текущем блоке достаточно модели; подробный разбор имеет смысл только при работе с драйверами или прокси.
