    1. Архитектура процессора, память и NUMA¶

    Эта лекция нужна как фундамент перед темами:

    • atomic operations;
    • CAS;
    • memory ordering;
    • cache coherence;
    • MESI;
    • false sharing;
    • sync.Mutex;
    • contention;
    • поведение backend под нагрузкой.

    Пока мы пишем обычный прикладной код, процессор можно воспринимать как абстрактную машину:

    программа
↓
CPU
↓
результат

    Но эта модель начинает ломаться, когда появляются вопросы:

    • почему один CAS дешевый, а множество CAS по одной переменной плохо масштабируются;
    • почему атомарная операция вообще имеет цену;
    • почему sync.Mutex не сводится к бесконечному CAS;
    • что такое cache miss;
    • почему два независимых поля могут мешать друг другу;
    • почему один и тот же Go-код работает на x86-64 и ARM64, хотя машинные инструкции разные.

    Чтобы это понимать, нужно сначала разобрать несколько уровней ниже языка.

    1. CPU не работает с DRAM на каждой инструкции¶

    Возьмем простую операцию:

    c := a + b

    Наивная модель:

    CPU читает a из RAM
CPU читает b из RAM
CPU складывает
CPU записывает c в RAM

    Если бы современный процессор работал так постоянно, он большую часть времени ждал бы память.

    Причина проста: CPU и DRAM живут в разных временных масштабах.

    Процессор с частотой около 4 GHz имеет период одного такта:

    1 / 4 000 000 000
≈ 0.25 ns

    Доступ к DRAM может занимать десятки наносекунд, условно:

    ~60–120 ns

    Если взять 100 ns:

    100 ns / 0.25 ns
≈ 400 тактов CPU

    Для процессора это огромная задержка.

    Поэтому между вычислительными блоками CPU и основной памятью существует иерархия:

    Execution Units
      ↓
Registers
      ↓
L1 Cache
      ↓
L2 Cache
      ↓
L3 / LLC
      ↓
DRAM

    Дальше уже идут устройства хранения:

    SSD
HDD

    И еще дальше могут находиться данные по сети.

    Главная идея:

    чем ближе данные к вычислительным блокам CPU, тем быстрее к ним доступ, но тем меньше таких данных можно хранить.

    2. Регистры¶

    Самое близкое к вычислительным блокам CPU хранилище — регистры.

    Упрощенно:

    Registers
   ↓
Execution Units
   ├── ALU
   ├── FPU
   ├── SIMD units
   └── Load/Store units

    ALU — Arithmetic Logic Unit.

    Она выполняет базовые целочисленные операции:

    ADD
SUB
AND
OR
XOR
SHIFT
COMPARE

    Например:

    mov rax, 10
mov rbx, 20
add rax, rbx

    После выполнения:

    RAX = 30

    RAX и RBX — архитектурные регистры x86-64.

    Что такое регистр¶

    Регистр — очень маленькое и очень быстрое хранилище непосредственно внутри CPU core.

    Это не RAM.

    Это не cache.

    Данные уже находятся рядом с execution units, поэтому операции над ними очень быстрые.

    Цена этого свойства — количество.

    Регистров мало.

    В них невозможно разместить:

    гигабайты heap
миллионы объектов
огромные массивы

    Поэтому регистры находятся на вершине пирамиды:

    максимально быстро
минимальный объем

    3. Архитектурные и физические регистры¶

    ISA показывает программе фиксированный набор регистров.

    Например x86-64:

    RAX
RBX
RCX
RDX
RSI
RDI
RSP
RBP
R8–R15

    Это архитектурные регистры.

    Но современный процессор обычно содержит больше внутренних физических регистров.

    Причина — register renaming.

    Допустим программа несколько раз изменяет RAX.

    На уровне ISA это один и тот же регистр:

    RAX

    Но процессор может хранить разные версии значения в разных физических регистрах:

    архитектурный RAX
        ↓
physical register 41

следующая версия RAX
        ↓
physical register 73

    Это помогает убрать ложные зависимости между инструкциями и выполнять больше операций параллельно.

    Уже здесь появляется важное разделение:

    ISA
↓
что процессор показывает программе

microarchitecture
↓
как конкретный CPU реализует это внутри

    4. Stack и heap не являются уровнями рядом с L1/L2/L3¶

    Это важно не смешивать.

    Когда мы говорим:

    stack
heap

    мы обсуждаем организацию памяти программы и runtime.

    Когда говорим:

    registers
L1
L2
L3
DRAM

    мы обсуждаем аппаратную иерархию хранения данных.

    Объект из heap прямо сейчас может находиться в L1 cache.

    Значение из stack frame компилятор вообще может оставить только в регистре.

    Поэтому такая схема неправильна:

    register
→ cache
→ stack
→ heap
→ RAM

    Правильнее:

    логическая организация программы:
stack / heap / globals
        ↓
виртуальные адреса памяти
        ↓
аппаратная иерархия:
registers / caches / DRAM

    Это две разные модели одной системы.

    5. Зачем нужен CPU cache¶

    Проблема уже видна:

    CPU быстрый
DRAM медленная

    Если каждое чтение данных требует обращения к DRAM, процессор будет простаивать сотни тактов.

    Идея cache:

    хранить часто используемые данные максимально близко к CPU.

    Cache — небольшая быстрая память, в которой процессор держит копии участков основной памяти.

    Допустим в DRAM есть:

    address 0x1000
value = 42

    После чтения копия может оказаться в L1:

    DRAM:
0x1000 → 42

L1:
0x1000 → 42

    При следующем обращении процессору не обязательно снова идти в DRAM.

    Если нужные данные уже находятся в cache:

    cache hit

    Если их там нет:

    cache miss

    6. Cache прозрачен для обычной программы¶

    Обычная программа не пишет:

    прочитать x из L1

    или:

    положить y в L2

    Программа работает с адресами памяти:

    0x12345678

    А CPU hardware сама решает:

    • есть ли нужные данные в cache;
    • на каком уровне они находятся;
    • что загрузить;
    • что вытеснить;
    • когда записать изменения дальше.

    Для программы существует память.

    Под ней работает автоматическая cache hierarchy.

    7. Почему cache быстрее DRAM¶

    CPU cache обычно строится на SRAM.

    Оперативная память компьютера — в основном DRAM.

    Очень грубо:

    SRAM
→ быстрее
→ дороже
→ занимает больше площади

    DRAM
→ медленнее
→ плотнее
→ дешевле

    Поэтому разумно сделать:

    десятки KB L1
сотни KB или MB L2
десятки MB L3

    Но сделать десятки гигабайт памяти со скоростью L1 практически невозможно по площади, цене, энергопотреблению и latency.

    Отсюда несколько уровней cache.

    8. L1 cache¶

    L1 — ближайший к core cache.

    Обычно он разделен на:

    L1I — Instruction Cache
L1D — Data Cache

    То есть:

    Core
├── L1I
├── L1D
└── Execution Units

    L1I хранит машинные инструкции.

    L1D хранит данные.

    L1 очень маленький — обычно десятки KiB.

    Но главное свойство L1:

    минимальная latency.

    CPU хочет получать данные оттуда буквально за несколько тактов.

    9. L2 cache¶

    Если данных нет в L1:

    L1 miss

    CPU ищет их дальше.

    Следующий уровень:

    L2

    L2 больше L1, но медленнее.

    Упрощенно:

    Core
├── L1
└── L2

    Размер уже может измеряться сотнями KiB или несколькими MiB.

    Если нужные данные найдены:

    L2 hit

    Если нет:

    L2 miss
→ искать дальше

    10. L3 / LLC¶

    Следующий уровень часто называют:

    L3

    или:

    LLC — Last Level Cache

    Учебная модель:

    Core 0       Core 1       Core 2       Core 3
 L1           L1           L1           L1
 ↓            ↓            ↓            ↓
 L2           L2           L2           L2
   \           \           /           /
            L3 / LLC
                ↓
               DRAM

    L3:

    • намного больше L1/L2;
    • медленнее;
    • часто используется несколькими ядрами.

    Но фраза:

    L3 — один общий кусок памяти для всех cores

    является учебным упрощением.

    Реальные CPU могут иметь:

    • несколько L3 slices;
    • clusters;
    • chiplets;
    • внутренний ring;
    • mesh interconnect;
    • отдельные coherence domains.

    Для первой модели достаточно:

    L1 — маленький и очень быстрый
L2 — больше и медленнее
L3 — еще больше и еще медленнее
DRAM — намного больше и намного медленнее

    11. 3D Cache¶

    Современный LLC необязательно целиком размещен в одной плоскости compute die.

    Например AMD использует 3D V-Cache.

    Дополнительный SRAM die размещается вертикально относительно вычислительного кристалла:

    ┌─────────────────────┐
│ дополнительный SRAM │
└──────────┬──────────┘
           │
┌──────────▼──────────┐
│ cores + base cache  │
└─────────────────────┘

    Для программы базовая модель не меняется.

    Это по-прежнему L3/LLC.

    Преимущество:

    больше working set помещается в LLC
→ меньше LLC misses
→ меньше обращений к DRAM

    Для нашей дальнейшей темы MESI принципиально ничего не меняется.

    12. Cache line¶

    Теперь самая важная деталь перед cache coherence.

    Cache обычно работает не с отдельными переменными, а блоками памяти.

    Такой блок называется:

    cache line

    Типичный размер на современных x86-64 и многих ARM-системах:

    64 bytes

    Допустим:

    var x int64

    Размер x:

    8 bytes

    Но CPU обычно загружает не только эти восемь байт.

    Он загружает всю cache line:

    0x1000                              0x103F
│                                      │
▼                                      ▼
┌──────────────────────────────────────┐
│ x │ y │ z │       другие данные     │
└──────────────────────────────────────┘
                64 B

    Мы попросили x.

    В cache приехали и соседние данные.

    13. Почему память кешируется блоками¶

    Программы обычно обладают locality.

    Temporal locality¶

    Если данные понадобились сейчас, есть шанс, что они понадобятся снова.

    Spatial locality¶

    Если понадобился адрес X, часто скоро потребуются данные рядом с ним.

    Например:

    for i := range values {
    sum += values[i]
}

    Элементы slice лежат последовательно.

    Когда CPU загружает одну cache line, в нее попадает сразу несколько элементов.

    Следующие итерации часто уже получают данные из cache.

    14. Cache hit и cache miss¶

    CPU хочет прочитать данные.

    Сначала проверяется ближайший cache:

    L1

    Нашлись:

    L1 hit

    Не нашлись:

    L1 miss

    Идем в L2:

    L2 hit

    или:

    L2 miss

    Дальше:

    L3 / LLC

    Если и там нет:

    LLC miss
→ DRAM

    Одна и та же memory load может стоить несколько тактов или несколько сотен тактов в зависимости от того, где находятся данные.

    15. Что еще хранится рядом с cache line¶

    Cache должен знать не только сами данные.

    Ему нужно понимать:

    какому участку памяти соответствует эта line?

    Поэтому концептуально cache entry содержит:

    tag
+
data
+
metadata

    Упрощенно:

    ┌─────────────────────────────────┐
│ TAG │ STATE │    64 B DATA      │
└─────────────────────────────────┘

    tag помогает определить адрес.

    state будет нужен для cache coherence.

    Например:

    Modified
Exclusive
Shared
Invalid

    То есть состояния MESI появляются не из воздуха: hardware и так должна хранить metadata о cache lines.

    16. Вытеснение cache lines¶

    Cache конечен.

    Например:

    L1 = десятки KiB

    а программа работает с сотнями MiB данных.

    Все одновременно не поместится.

    Поэтому старые cache lines приходится вытеснять:

    старые данные
↓
eviction
↓
освобождение места
↓
новая cache line

    CPU использует replacement policies, пытаясь оставить данные, которые с большей вероятностью понадобятся снова.

    17. Что происходит при записи¶

    При чтении модель простая:

    memory
→ cache
→ core

    При записи возникает вопрос:

    если CPU изменил копию в cache, когда обновится DRAM?

    Один распространенный подход:

    write-back cache

    CPU изменяет cache line локально.

    Line становится modified/dirty.

    Запись дальше может произойти позже.

    Поэтому временно возможно:

    cache = новое значение
DRAM  = старое значение

    Это нормальная ситуация.

    И отсюда дальше естественно появляется состояние MESI:

    M — Modified

    18. DRAM¶

    DRAM:

    Dynamic Random Access Memory

    Это то, что обычно называют оперативной памятью:

    RAM

    Например:

    16 GB DDR5
32 GB DDR5
128 GB DDR5

    DRAM используется как основная рабочая память процессов.

    19. Почему DRAM называется Dynamic¶

    Очень грубо один бит DRAM хранится через:

    capacitor
+
transistor

    Электрический заряд постепенно утекает.

    Поэтому содержимое приходится регулярно обновлять:

    refresh

    Отсюда:

    Dynamic

    DRAM существенно плотнее SRAM.

    Поэтому можно относительно дешево получить десятки и сотни гигабайт памяти.

    Цена:

    DRAM намного медленнее CPU cache

    20. Memory Controller¶

    CPU не взаимодействует с DRAM как с магическим плоским массивом.

    Между ядрами и памятью находится memory controller.

    В современных системах он обычно интегрирован в CPU package.

    Упрощенно:

    CPU cores
   ↓
cache hierarchy
   ↓
interconnect
   ↓
Memory Controller
   ↓
DDR channels
   ↓
DIMMs

    Memory controller преобразует запросы процессора в операции DRAM.

    21. DRAM внутри тоже не плоская¶

    Для программы RAM выглядит примерно:

    address → value

    Физически организация сложнее:

    channel
↓
DIMM
↓
rank
↓
bank
↓
row
↓
column

    Поэтому разные обращения могут иметь разную стоимость.

    Например:

    row hit

    означает, что нужная row уже открыта.

    Это дешевле.

    Если нужно переключить row:

    row miss

    операция дороже.

    Для этой лекции глубже идти не нужно.

    Главный вывод:

    DRAM сама имеет topology и внутренние задержки, но для CPU она все равно заметно медленнее cache.

    22. SSD¶

    SSD:

    Solid State Drive

    Это уже не оперативная память, а persistent storage.

    После отключения питания данные сохраняются.

    Современные SSD обычно используют NAND flash.

    Упрощенно:

    CPU
↓
RAM
↓
PCIe / SATA
↓
SSD Controller
↓
NAND Flash

    SSD-контроллер сам выполняет много работы:

    logical → physical mapping
wear leveling
garbage collection
error correction
flash management

    Современный SSD — фактически отдельная маленькая вычислительная система.

    23. NVMe и SATA SSD¶

    SATA создавался в эпоху традиционных накопителей.

    NVMe проектировался уже для быстрых flash-накопителей и работает поверх PCIe.

    Поэтому NVMe обычно дает:

    • меньшую latency;
    • большую пропускную способность;
    • больше parallelism.

    Но относительно CPU cache даже быстрый NVMe очень медленный.

    Условно:

    L1
~1 ns

NVMe random read
~десятки–сотни μs

    Разница — много порядков.

    24. HDD¶

    HDD:

    Hard Disk Drive

    Здесь данные хранятся магнитно на вращающихся пластинах.

    Внутри есть механика:

    вращающийся диск
+
движущаяся головка

    Для случайного чтения нужно:

    1. переместить головку на нужную дорожку;
    2. дождаться нужного сектора;
    3. прочитать данные.

    Получаем:

    seek time
+
rotational latency

    Поэтому random access измеряется миллисекундами.

    Для CPU миллисекунда — гигантский промежуток времени.

    25. SSD и HDD не являются продолжением CPU cache hierarchy¶

    Нельзя строго рисовать:

    register
→ L1
→ L2
→ L3
→ DRAM
→ SSD
→ HDD

    как одну аппаратную cache hierarchy.

    Строго:

    registers
L1
L2
L3
DRAM

    относятся к memory subsystem CPU.

    А:

    SSD
HDD

    — storage.

    Чтобы CPU начал работать с данными с SSD, они обычно должны попасть в DRAM:

    SSD
↓
I/O
↓
kernel
↓
DRAM / page cache
↓
CPU caches
↓
registers

    26. Сеть находится еще дальше¶

    Теперь представим:

    resp, err := http.Get(...)

    Данные находятся уже не на локальном storage.

    Путь может выглядеть так:

    process
↓
kernel
↓
socket
↓
NIC
↓
network
↓
switches / routers
↓
другая машина
↓
ее kernel
↓
ее application

    Потом ответ идет обратно.

    Это задержки совсем другого класса.

    27. Latency и bandwidth — разные вещи¶

    Очень частая ошибка — смешивать задержку и пропускную способность.

    bandwidth отвечает:

    сколько данных можно передать за единицу времени?

    latency отвечает:

    сколько ждать конкретную операцию?

    Например NVMe SSD может давать несколько GB/s sequential throughput.

    Но одно случайное чтение все равно может занимать десятки микросекунд.

    Сеть может быть 100 Gbit/s, но RTT между машинами от этого не становится нулевым.

    Для cache, atomics и synchronization особенно важна именно latency.

    28. Сравнение задержек¶

    Возьмем CPU около 4 GHz.

    Один cycle:

    ~0.25 ns

    Очень грубый порядок величин:

    Операция Примерная latency Эквивалент при 4 GHz
    простая операция над регистрами ~0.25–1 ns ~1–4 cycles
    L1 hit ~1 ns ~4 cycles
    L2 hit ~3–5 ns ~12–20 cycles
    L3 / LLC hit ~10–30 ns ~40–120 cycles
    DRAM ~60–120 ns ~240–480 cycles
    remote NUMA DRAM ~100–300+ ns сотни–1000+ cycles
    NVMe SSD random read ~50–200 μs сотни тысяч cycles
    SATA SSD ~100–500 μs сотни тысяч–миллионы cycles
    HDD random access ~5–15 ms десятки миллионов cycles
    быстрый LAN / datacenter RTT ~0.1–1 ms сотни тысяч–миллионы cycles
    Internet RTT ~5–200+ ms десятки–сотни миллионов cycles

    Это не нормативные числа.

    Конкретные значения зависят от:

    • CPU;
    • cache topology;
    • DRAM;
    • NUMA;
    • storage;
    • нагрузки;
    • сети.

    Нас интересуют порядки величин.

    29. Перевод задержек в человеческий масштаб¶

    Теперь сделаем искусственную, но наглядную аналогию.

    Представим:

    L1 access = 1 секунда

    Тогда примерно:

    L1
1 секунда

L2
несколько секунд

L3
десятки секунд

DRAM
1–2 минуты

NVMe SSD
около суток

HDD
несколько месяцев

10 ms network RTT
несколько месяцев

100 ms network RTT
несколько лет

    Это не измерительная таблица, а масштабная модель.

    Она показывает главное:

    для CPU даже DRAM уже медленная. SSD, HDD и сеть находятся практически в другой временной вселенной.

    30. Почему современный CPU настолько сложный¶

    Теперь становятся понятнее:

    cache
prefetching
branch prediction
out-of-order execution
speculative execution
multiple execution units

    Одна из центральных задач CPU:

    не простаивать в ожидании данных.

    Если одна инструкция ждет память:

    load A

    процессор пытается найти другие независимые операции:

    B = x + y
C = q * r

    и выполнять их, пока A еще не готов.

    Иначе один cache miss мог бы останавливать значительную часть процессора на сотни cycles.

    31. ISA и microarchitecture¶

    Теперь переходим к архитектурам процессоров.

    Когда говорят:

    x86-64
ARM64
MIPS
PowerPC
RISC-V

    речь прежде всего идет об ISA:

    Instruction Set Architecture

    ISA — программно видимый интерфейс процессора.

    Она определяет:

    • набор инструкций;
    • архитектурные регистры;
    • способы адресации;
    • поведение инструкций;
    • memory ordering;
    • атомарные primitives.

    Но ISA не описывает полностью внутреннее устройство CPU.

    Например:

    Intel Core
AMD Zen

    выполняют одну и ту же ISA:

    x86-64

    но имеют разную microarchitecture.

    Итого:

    ISA
= что CPU обещает software

    microarchitecture
= как конкретный процессор реализует эти обещания

    32. CISC¶

    CISC:

    Complex Instruction Set Computer

    Историческая идея:

    ISA предоставляет богатый набор сравнительно сложных инструкций.

    Главный современный пример:

    x86

    Инструкция может непосредственно работать с памятью.

    Например:

    add qword ptr [rax], 1

    На уровне ISA это одна инструкция.

    Логически:

    прочитать память
→ прибавить
→ записать

    33. RISC¶

    RISC:

    Reduced Instruction Set Computer

    Историческая идея:

    • более простые инструкции;
    • более регулярное кодирование;
    • load/store architecture;
    • арифметика преимущественно работает с регистрами.

    Типовая модель:

    LOAD
↓
ADD
↓
STORE

    Например условно:

    load  r1, [address]
add   r1, r1, 1
store [address], r1

    34. RISC не означает простой CPU¶

    Это важное разрушение упрощения.

    Современный ARM core может содержать:

    • сложный branch predictor;
    • out-of-order execution;
    • speculative execution;
    • множество физических регистров;
    • несколько execution pipelines;
    • сложную cache hierarchy;
    • hardware prefetchers.

    То есть:

    RISC ISA

    не означает:

    простой физический процессор

    35. Современный x86 тоже не исполняет все как монолитные сложные инструкции¶

    Современный x86 CPU получает:

    x86 instruction

    и часто разбивает ее на внутренние операции:

    micro-ops

    Условно:

    x86 instruction
      ↓
decoder
      ↓
micro-ops
      ↓
scheduler
      ↓
execution units

    Поэтому старое противопоставление:

    CISC = сложный
RISC = простой

    слишком грубое.

    Сегодня важнее отдельно понимать ISA и microarchitecture.

    36. x86 / x86-64¶

    Историческая линия:

    8086
→ 80286
→ 80386
→ 80486
→ Pentium
→ x86-64

    Одна из главных особенностей x86 — огромная обратная совместимость.

    Архитектура десятилетиями расширялась:

    • новые режимы;
    • новые инструкции;
    • SIMD;
    • новые регистры;
    • 64-битный режим.

    64-битное расширение x86 первоначально разработала AMD.

    Поэтому:

    AMD64

    и:

    x86-64

    относятся к одной современной ISA-линии.

    В Go:

    GOARCH=amd64

    37. ARM / AArch64¶

    ARM исторически относится к RISC-семейству.

    Современная 64-битная архитектура:

    AArch64

    В повседневной речи обычно:

    ARM64

    В Go:

    GOARCH=arm64

    Сегодня ARM используется:

    • в смартфонах;
    • Apple Silicon;
    • AWS Graviton;
    • Ampere;
    • embedded;
    • SBC;
    • серверных системах.

    Классическая идея:

    load
→ compute
→ store

    Но современные высокопроизводительные ARM cores внутри — сложные superscalar out-of-order процессоры.

    38. MIPS¶

    MIPS — классическая RISC-архитектура.

    Она удобна для обучения, потому что хорошо показывает:

    load
compute
store

    Например:

    lw   $t0, 0($t1)
add  $t0, $t0, $t2
sw   $t0, 0($t1)

    Исторически MIPS использовался:

    • SGI;
    • networking equipment;
    • embedded;
    • PlayStation;
    • Nintendo 64.

    Сегодня его значение сильно снизилось, но как учебный пример RISC он полезен.

    39. PowerPC / POWER¶

    PowerPC — еще одна важная RISC-линия.

    Использовался:

    • Apple до перехода на Intel;
    • GameCube;
    • Wii;
    • Xbox 360;
    • PlayStation 3.

    Родственная серверная линия IBM:

    POWER

    до сих пор используется.

    PowerPC и POWER исторически связаны, но это не просто два названия одного и того же современного продукта.

    40. SPARC¶

    SPARC — RISC-архитектура Sun Microsystems.

    Исторически:

    Sun
Solaris
SPARC

    Интересная особенность:

    register windows

    При вызовах функций процессор использовал перекрывающиеся окна регистров.

    Идея — уменьшить стоимость function calls.

    Сегодня SPARC почти исчез из mainstream, но исторически архитектура важна.

    41. RISC-V¶

    RISC-V — современная открытая ISA.

    Ключевая идея:

    base ISA
+
extensions

    Например:

    RV64I

    и расширения:

    M — multiply/divide
A — atomics
F — floating point
D — double precision
V — vectors

    Для нас особенно важно:

    A — Atomics

    Потому что позже можно сравнить:

    Go atomic
↓
x86 atomic instructions
ARM atomics
RISC-V atomics

    42. Itanium / IA-64¶

    Короткий, но полезный исторический эксперимент.

    Intel и HP разработали:

    IA-64

    Процессоры назывались:

    Itanium

    Важно:

    IA-64 != x86-64

    Это совершенно другая архитектура.

    Itanium использовал подход:

    EPIC
Explicitly Parallel Instruction Computing

    Идея:

    значительную часть поиска instruction-level parallelism выполнить заранее в compiler.

    Современный out-of-order CPU сам во время исполнения пытается определить:

    • какие инструкции независимы;
    • что можно выполнять параллельно;
    • что ждет память.

    Itanium хотел перенести больше этой работы на compiler.

    Проблема в том, что compiler заранее не знает:

    cache miss
branch misprediction
memory latency
runtime data

    В итоге Itanium не заменил x86.

    x86-64 оказался гораздо успешнее.

    43. Другие архитектуры, которые полезно знать по названию¶

    Motorola 68000¶

    CISC-семейство.

    Использовалось:

    Macintosh
Amiga
Atari ST
Sega Mega Drive

    Хорошее напоминание, что x86 была не единственной CISC-архитектурой.

    DEC Alpha¶

    64-битная RISC-архитектура DEC.

    Известна в том числе слабой memory model.

    Полезна как исторический пример при обсуждении memory ordering.

    IBM z/Architecture¶

    Линия:

    System/360
→ System/370
→ ...
→ z/Architecture

    До сих пор используется в mainframe.

    Go поддерживает:

    GOARCH=s390x

    Это хороший пример того, насколько долго может жить архитектурная линия.

    44. Общая карта ISA¶

    Очень грубо:

    CISC
├── x86 / x86-64
└── Motorola 68k

RISC
├── ARM
├── MIPS
├── PowerPC / POWER
├── SPARC
├── RISC-V
└── DEC Alpha

EPIC
└── Itanium / IA-64

    Важно:

    это классификация ISA и исторических архитектурных идей, а не мера сложности современного CPU.

    45. Современный CPU может состоять из нескольких кристаллов¶

    Классическая учебная картинка CPU:

    ┌─────────────────────┐
│ cores               │
│ caches              │
│ memory controller   │
│ I/O                 │
└─────────────────────┘

    Один монолитный silicon die.

    Но современные процессоры могут собираться из нескольких кристаллов:

    chiplets

    Например условно:

    ┌───────────┐        ┌───────────┐
│   CCD 0   │        │   CCD 1   │
│ cores     │        │ cores     │
│ cache     │        │ cache     │
└─────┬─────┘        └─────┬─────┘
      │                    │
      └────────┬───────────┘
               │
          interconnect
               │
          ┌────▼────┐
          │ I/O Die │
          │ IMC     │
          │ PCIe    │
          └────┬────┘
               │
              RAM

    Почему это делают:

    • маленькие dies проще производить;
    • выше yield;
    • можно смешивать разные техпроцессы;
    • проще масштабировать количество cores;
    • дешевле строить линейку процессоров.

    Цена:

    разные части CPU теперь физически находятся на разном расстоянии друг от друга.

    46. Infinity Fabric¶

    У AMD различные компоненты CPU связываются через семейство interconnect:

    Infinity Fabric

    Через него может идти:

    • inter-chiplet traffic;
    • memory traffic;
    • coherence traffic;
    • I/O traffic.

    Поэтому:

    Core A
→ данные в своем CCD

    и:

    Core A
→ данные, связанные с другим CCD

    могут иметь разную стоимость.

    Даже фраза:

    внутри одного CPU

    больше не означает:

    все одинаково близко

    47. NUMA¶

    Теперь естественно появляется NUMA.

    NUMA:

    Non-Uniform Memory Access

    Неравномерный доступ к памяти.

    Главная идея:

    стоимость обращения к RAM зависит от того, какой CPU/core выполняет код и где физически находится нужная память.

    48. UMA¶

    Сначала простая модель:

    Core 0 ─┐
Core 1 ─┼── Memory Controller ── RAM
Core 2 ─┤
Core 3 ─┘

    Все cores обращаются к одной системе памяти примерно одинаковым путем.

    Это:

    Uniform Memory Access

    49. Классический NUMA¶

    Теперь двухсокетный сервер:

    NUMA node 0                     NUMA node 1

┌───────────────┐               ┌───────────────┐
│ CPU cores     │               │ CPU cores     │
│               │               │               │
│ Memory Ctrl   │               │ Memory Ctrl   │
└───────┬───────┘               └───────┬───────┘
        │                               │
      DRAM 0                          DRAM 1
        │                               │
        └──────── interconnect ─────────┘

    Для CPU 0:

    DRAM 0

    — local memory.

    А:

    DRAM 1

    — remote memory.

    50. Что происходит при remote memory access¶

    Core из node 0 хочет данные, физически подключенные к node 1.

    Запрос идет:

    Core
↓
local interconnect
↓
socket-to-socket interconnect
↓
remote socket
↓
remote memory controller
↓
remote DRAM

    Ответ идет обратно.

    Поэтому:

    remote memory latency
>
local memory latency

    Дополнительно расходуется bandwidth межпроцессорного interconnect.

    Отсюда слово:

    Non-Uniform

    51. Причем здесь Memory Controller¶

    Связь прямая.

    Современные серверные CPU имеют собственные integrated memory controllers.

    Условно:

    Socket 0
↓
IMC 0
↓
RAM 0

    и:

    Socket 1
↓
IMC 1
↓
RAM 1

    Память физически подключена к конкретному memory controller.

    Поэтому один процессор получает ее локально, другой — через interconnect.

    52. AMD и NUMA¶

    У AMD инфраструктурой связи компонентов служит Infinity Fabric.

    Упрощенно:

    CCD
CCD
CCD
 ↓
Infinity Fabric
 ↓
IOD / Memory Controllers
 ↓
DRAM

    В многосокетных системах через межсоединения проходит и remote memory traffic.

    Важно:

    Infinity Fabric != NUMA

    Infinity Fabric — interconnect.

    NUMA — свойство всей memory topology.

    Но interconnect является одним из механизмов, через которые реализуется remote NUMA access.

    53. Intel и NUMA¶

    У Intel фундаментальная проблема та же.

    В многосокетных Xeon:

    Socket 0                      Socket 1
   │                             │
  IMC                           IMC
   │                             │
 RAM 0                         RAM 1
   │                             │
   └────────── UPI ──────────────┘

    UPI:

    Ultra Path Interconnect

    Раньше использовался QPI:

    QuickPath Interconnect

    Внутри самого CPU Intel также использует собственные interconnect, например mesh в части серверных поколений.

    То есть современный CPU уже сам по себе напоминает небольшую распределенную систему.

    54. Chiplets и NUMA — не одно и то же¶

    Это важно.

    Chiplet topology означает:

    части CPU физически размещены на нескольких dies

    NUMA означает:

    операционная система видит области памяти с разной стоимостью доступа

    Они связаны, но:

    chiplet != NUMA node

    Не каждый chiplet отображается ОС как отдельный NUMA node.

    Физическая topology может быть сложнее topology, которую видит операционная система.

    55. Зачем ОС знать о NUMA¶

    Если ОС знает topology, она может пытаться размещать computation и memory ближе друг к другу.

    Идеальный случай:

    CPU node 0
↓
thread
↓
memory allocated on node 0

    Получаем local access.

    Хуже:

    CPU node 0
↓
thread
↓
memory on node 1

    Тогда постоянно возникает remote traffic.

    На больших машинах это может влиять на:

    • throughput;
    • tail latency;
    • memory bandwidth;
    • масштабирование parallel workload.

    56. Что NUMA означает для Go¶

    Go предоставляет высокоуровневую модель:

    goroutines
scheduler
heap
GC

    Но под ней находится реальное железо.

    Goroutine может выполняться на разных OS threads и cores.

    Heap приложения может занимать физические страницы на разных NUMA nodes.

    На обычном backend-сервисе это часто не проблема.

    Но если появляются:

    • десятки или сотни cores;
    • огромный heap;
    • memory-intensive workload;
    • очень высокий throughput;
    • жесткие требования к tail latency;

    то hardware topology начинает проявляться.

    Важно не делать неправильный вывод:

    каждая миграция goroutine автоматически означает remote NUMA access.

    Так говорить нельзя.

    Но физическая locality действительно может начать влиять на производительность больших систем.

    57. Где здесь cache coherence¶

    Теперь у каждого core может быть собственный L1.

    Например:

    Core 0 L1             Core 1 L1

counter = 100         counter = 100

    Оба прочитали одну cache line.

    Пока оба только читают — проблемы нет.

    Теперь Core 0 хочет:

    counter = 101

    Получаем потенциально:

    Core 0 L1
counter = 101

Core 1 L1
counter = 100

    Какая копия актуальная?

    Эту проблему решает:

    cache coherence

    58. MESI и уровни cache¶

    MESI — классическая учебная модель cache coherence.

    Состояния:

    M — Modified
E — Exclusive
S — Shared
I — Invalid

    Важно не сформировать неправильную картину.

    Не нужно представлять:

    отдельный MESI для L1
+
отдельный MESI для L2
+
отдельный MESI для L3

    Правильнее:

    coherence охватывает систему caching agents и cache hierarchy в целом.

    Учебно:

    Core 0                  Core 1
 L1                      L1
 ↓                       ↓
 L2                      L2
   \                     /
        L3 / LLC
            ↓
           DRAM

    Реальный CPU может использовать:

    MESI
MESIF
MOESI
directory-based coherence
vendor-specific protocols

    Metadata о владельцах и sharers может быть распределена по разным уровням системы.

    Для нашей лекции MESI нужна как ментальная модель:

    кто может читать line?
кто может писать?
кто владеет актуальной копией?
какие копии надо инвалидировать?

    59. Почему все это нужно перед CAS¶

    Теперь посмотрим на:

    atomic.CompareAndSwapInt64(&state, 0, 1)

    На уровне Go это одна операция.

    Под ней может находиться цепочка:

    Go atomic
↓
machine atomic instruction
↓
cache line
↓
получение права на запись
↓
cache coherence
↓
invalidation других copies
↓
atomic read-modify-write

    Если один core работает с line, которая уже находится локально, все относительно дешево.

    Если 32 cores одновременно работают с одной line:

    Core 0
Core 1
Core 2
...
Core 31
   ↓
одна cache line

    начинается борьба за ownership.

    Отсюда потом появляются:

    cache-line ping-pong
false sharing
atomic contention

    И становится понятно, почему sync.Mutex не может быть просто:

    while CAS fails {
    retry
}

    60. Итоговая карта¶

    Соберем весь путь:

    Go code
↓
compiler
↓
ISA
↓
machine instructions
↓
CPU microarchitecture
↓
registers
↓
L1 / L2 / L3
↓
memory controller
↓
DRAM

    На современных системах добавляются:

    chiplets
interconnect
NUMA

    Если несколько cores работают с одной памятью:

    cache coherence

    Если они конкурируют за одну cache line:

    ownership
invalidation
MESI
CAS
contention

    А уже поверх этого:

    sync.Mutex
spinning
runtime semaphore
scheduler
goroutine parking

    Что важно запомнить¶

    1. Регистры — самое близкое к execution units и самое быстрое хранилище, но их очень мало.

    2. Архитектурные регистры ISA и физические регистры внутри современного OoO CPU — разные уровни модели.

    3. Stack и heap описывают организацию памяти программы. Registers/cache/DRAM описывают аппаратную memory hierarchy.

    4. CPU cache хранит копии памяти рядом с ядрами, чтобы процессор как можно реже ждал DRAM.

    5. L1, L2 и L3 существуют потому, что невозможно получить память одновременно огромную, дешевую и такую же быструю, как L1.

    6. Cache работает cache lines, а не отдельными Go-переменными. Типичный размер line — 64 bytes.

    7. Cache hit и cache miss радикально отличаются по стоимости.

    8. DRAM — основная рабочая память машины: большая и сравнительно дешевая, но существенно медленнее cache.

    9. SSD и HDD — persistent storage. CPU не работает с ними обычными load/store: данные сначала должны попасть в DRAM.

    10. Latency различается на порядки:

    register / L1 → ns
DRAM          → десятки–сотни ns
SSD           → десятки–сотни μs
HDD           → ms
network       → μs–сотни ms

    1. x86-64, ARM64, MIPS, PowerPC, RISC-V — ISA.

    2. CISC, RISC, EPIC — архитектурные подходы и исторические семейства идей, а не мера сложности современного CPU.

    3. Современные x86 и ARM cores внутри оба являются сложными superscalar out-of-order машинами.

    4. Современный CPU может состоять из нескольких chiplets, поэтому hardware topology уже не обязана быть плоской.

    5. NUMA означает, что не вся RAM одинаково близка ко всем CPU cores.

    6. Infinity Fabric у AMD и UPI у Intel — interconnect. Они связаны с NUMA topology, но сами по себе не являются NUMA.

    7. MESI — учебная модель cache coherence всей системы кешей, а не отдельный независимый механизм для L1, L2 и L3.

    8. После этой модели можно нормально разбирать:

    CAS
→ atomic instructions
→ memory ordering
→ MESI
→ false sharing
→ cache-line ping-pong
→ sync.Mutex
