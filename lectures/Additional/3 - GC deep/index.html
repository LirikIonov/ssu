    3. Go GC internals и memory allocator¶

    Версионная привязка: материал ориентирован на Go 1.27.x.

    Здесь важно различать три уровня:

    • устойчивая учебная модель — идеи, которые полезно помнить между версиями Go;
    • публичное поведение runtime — то, на что можно опираться при эксплуатации;
    • детали текущей реализации — mcache, mspan, mcentral, Green Tea internals и конкретные функции runtime. Они могут меняться между версиями.

    Основная лекция про память отвечает на вопросы:

    что такое stack и heap?
почему значение escape'ится?
что делает GC?
как пользоваться pprof?

    Эта лекция открывает следующий слой:

    компилятор решил:
"нужна heap allocation"

                    │
                    ▼

а что дальше физически делает runtime?

    Нас будет интересовать вся цепочка:

    source code
    ↓
escape analysis
    ↓
heap allocation
    ↓
mcache / mspan / mcentral / mheap
    ↓
heap growth
    ↓
GC pacer
    ↓
concurrent marking
    ↓
write barriers
    ↓
mark workers + assists
    ↓
sweep
    ↓
scavenger
    ↓
OS

    Главная идея лекции:

    Memory management в Go — это не отдельный «сборщик мусора». Это работающая одновременно система allocator + GC + scheduler + virtual memory ОС.

    Блок 1. От new(T) до куска памяти¶

    1. Почему нельзя объяснить heap словами «runtime выделил память»¶

    Возьмем простой код:

    type User struct {
    ID   int64
    Name string
}

func newUser() *User {
    u := User{
        ID:   42,
        Name: "Alice",
    }
    return &u
}

    Компилятор видит, что адрес u покидает функцию.

    Упрощенно:

    u
↓
escape analysis
↓
escapes to heap

    На основной лекции этого было достаточно.

    Теперь задаем следующий вопрос:

    Где runtime возьмет память под User?

    Самый наивный вариант:

    new(User)
↓
обращение в Linux
↓
дай мне 32 байта

    Такой allocator был бы катастрофически дорогим.

    Почему?

    Потому что backend может выполнять миллионы allocations в секунду.

    Если каждая allocation превращается в системный вызов:

    application
↓
kernel
↓
VM subsystem
↓
application

    стоимость memory management становится огромной.

    Поэтому runtime работает крупными блоками памяти и самостоятельно раздает из них маленькие объекты.

    Ментальная модель:

    ОС выдает Go большие области памяти
               ↓
Go runtime управляет ими сам
               ↓
приложение получает маленькие объекты

    Это первая фундаментальная идея allocator.

    2. Масштабы памяти¶

    Очень полезно сразу разделить уровни.

    объект Go
   ↓
slot внутри span
   ↓
span
   ↓
runtime pages
   ↓
большие области virtual memory
   ↓
memory mappings ОС
   ↓
physical pages

    Это разные сущности.

    Когда код делает:

    p := new(User)

    мы говорим:

    «выделился объект».

    Runtime внизу думает уже другими категориями:

    size class
span class
free bitmap
runtime page
page allocator

    ОС вообще не знает, что существует User.

    Для ядра это просто страницы virtual memory процесса.

    3. Почему allocator построен иерархически¶

    Backend выполняется параллельно.

    Пусть:

    GOMAXPROCS = 8

    и одновременно тысячи goroutines создают объекты.

    Наивная схема:

    G1 ─┐
G2 ─┤
G3 ─┤
... ├── global allocator lock
Gn ─┘

    Тогда быстрый код:

    x := new(RequestContext)

    может упираться в общий mutex allocator.

    Получается:

    CPU cores растут
↓
goroutines растут
↓
конкуренция за один allocator lock растет
↓
масштабирование ломается

    Поэтому Go использует многоуровневый allocator:

    локальный быстрый путь
        ↓
общий более дорогой путь
        ↓
глобальный page allocator
        ↓
ОС

    В текущем runtime учебная цепочка выглядит так:

    P
↓
mcache
↓
mspan
↓
mcentral
↓
mheap
↓
page allocator
↓
OS

    Но важно читать ее правильно.

    Это не означает:

    каждая allocation проходит через все уровни.

    Наоборот.

    Цель архитектуры состоит именно в том, чтобы обычная allocation закончилась как можно выше.

    4. Fast path маленькой allocation¶

    Для большинства небольших объектов идеальный путь:

    goroutine выполняется на P
        ↓
у P уже есть подходящий mspan
        ↓
в span есть свободный slot
        ↓
runtime забирает slot
        ↓
готово

    То есть:

    P
↓
mcache
↓
cached mspan
↓
free bitmap
↓
slot

    Без:

    mcentral
mheap
mmap
глобального allocator lock

    Именно это делает частую маленькую allocation достаточно дешевой.

    Но позже мы увидим важную вещь:

    Дешевая allocation сейчас еще не означает дешевый объект за весь его жизненный цикл.

    Что важно запомнить¶

    1. ОС не обслуживает каждый new(T) отдельно.
    2. Runtime получает память крупными блоками и сам делит ее на объекты.
    3. Allocator специально имеет локальный fast path.
    4. Иерархия существует, чтобы редкие дорогие операции амортизировать на множество дешевых allocations.
    5. Объект Go, span, runtime page и physical page ОС — разные уровни.

    Углубление. Что реально происходит между new(T) и mcache¶

    До этого мы использовали удобную модель:

    new(T)
↓
escape
↓
heap
↓
mcache

    Теперь раскроем промежуточный слой.

    Для heap allocation compiler должен передать runtime как минимум две критические характеристики:

    размер allocation
+
есть ли внутри pointers, которые должен видеть GC?

    Для обычного пути это исторически приводит к логике вокруг:

    newobject / newarray
↓
mallocgc

    В Go 1.27 появился дополнительный fast path: для ряда allocations меньше 80 байт compiler может вызвать size-specialized allocation routine. Смысл не в новом allocator, а в том, что часть решений уже известна на compile time:

    generic malloc path:

size?
scan / noscan?
size class?
branches
↓
allocation

    против:

    specialized path:

размер уже известен
class уже известен
часть branches исчезает
↓
allocation

    То есть Go 1.27 ускоряет не поиск памяти каким-то новым принципом, а сокращает bookkeeping и branching вокруг очень частого small-allocation path.

    Allocation — это не один вызов¶

    Условно текущую реализацию можно представить так:

    compiler
↓
newobject / specialized allocation stub
↓
malloc path
↓
small or large?
│
├── small
│   ↓
│   spanClass
│   ↓
│   mcache текущего P
│   ↓
│   free slot?
│   ├── yes → вернуть address
│   └── no  → refill
│              ↓
│            mcentral
│              ↓
│            mheap
│              ↓
│          page allocator
│
└── large
    ↓
    mheap / page allocator

    Но common case не проходит всю эту цепочку.

    Если подходящий span уже cached у P и в нем есть свободный slot, allocation заканчивается очень высоко.

    Почему runtime знает про noscan¶

    Рассмотрим:

    type A struct {
    X uint64
    Y uint64
}

    и:

    type B struct {
    X *User
    Y uint64
}

    Даже если оба объекта попадают в похожий size class, allocator должен сохранить для GC принципиально разную информацию:

    A
↓
pointer-free
↓
noscan

B
↓
contains pointer
↓
scan

    Поэтому allocator и collector нельзя считать независимыми подсистемами.

    Allocator уже при создании объекта готовит heap так, чтобы GC позже мог быстро ответить:

    где объекты?
какого они размера?
какие области содержат pointers?
какую metadata надо сканировать?

    Allocation участвует в GC pacing¶

    Heap растет именно через allocations.

    Поэтому рядом с allocation path существует heap accounting и проверка:

    не пора ли стартовать GC?

    Концептуально:

    allocate
↓
heapLive изменился
↓
trigger condition?
│
├── no  → продолжить
└── yes → инициировать GC cycle

    Получается первый сквозной feedback loop:

    application allocation
↓
allocator
↓
heap accounting
↓
GC pacer
↓
возможно новый GC cycle

    Именно поэтому allocation rate напрямую связан с частотой GC.

    Инженерный вывод¶

    Нужно перестать воспринимать:

    new(T)

    как локальное событие:

    дали N bytes

    Более точная модель:

    new(T)
↓
compiler выбрал allocation path
↓
runtime выбрал class/span
↓
обновилась allocator metadata
↓
обновился heap accounting
↓
возможно появился GC pressure

    Одна конкретная allocation может быть очень дешевой.

    Но поток allocations меняет состояние всей memory-management системы.

    Блок 2. Почему allocator привязан к P¶

    5. Возвращаем G / M / P¶

    Из лекции про scheduler:

    G = goroutine
M = OS thread
P = scheduler resource

    Для выполнения Go-кода M обычно нужен P.

    Упрощенно:

    G
↓
M + P
↓
CPU

    И вот allocator тоже привязан к P.

    У каждого P есть свой allocator cache:

    P0 → mcache0
P1 → mcache1
P2 → mcache2
P3 → mcache3

    Почему это хороший дизайн?

    Потому что количество goroutines может быть огромным:

    100
10 000
1 000 000

    А количество реально параллельно выполняемого Go-кода ограничено количеством P.

    Если сделать allocator cache на goroutine:

    1 000 000 goroutines
↓
1 000 000 allocator caches

    Получаем чудовищный объем metadata.

    Если сделать один общий cache:

    все P
↓
один lock

    получаем contention.

    Per-P cache дает компромисс:

    число caches ≈ число единиц параллельного выполнения

    6. Почему именно P, а не M¶

    Можно спросить:

    Почему allocator cache не привязан к OS thread M?

    Потому что M — исполнитель, который может:

    • блокироваться в syscall;
    • появляться;
    • исчезать;
    • менять P.

    P лучше отражает именно право выполнять Go-код.

    Для runtime удобно хранить hot state рядом с P:

    scheduler local run queue
allocator cache
GC local work

    Это общий архитектурный паттерн Go runtime:

    сначала работай локально
↓
как можно реже координируйся глобально

    Мы увидим его еще несколько раз.

    7. Что такое mcache на человеческом языке¶

    Название mcache легко понять неправильно.

    Это не:

    один большой кусок свободной памяти

    Гораздо точнее:

    mcache — набор подготовленных allocator resources, которые конкретный P может использовать без общего lock.

    Внутри концептуально есть ссылки на spans разных классов:

    mcache
│
├── spanClass A → mspan
├── spanClass B → mspan
├── spanClass C → mspan
├── spanClass D → mspan
└── ...

    Например условно:

    mcache P0

8-byte noscan      → span #101
16-byte scan       → span #533
24-byte noscan     → span #401
32-byte scan       → span #829
48-byte noscan     → span #711
...

    Когда нужно выделить объект:

    размер + contains pointers?
↓
spanClass
↓
нужный mspan

    8. Почему fast path не требует общего lock¶

    Представим:

    P0 использует mcache0
P1 использует mcache1

    В нормальной ситуации P0 не пытается одновременно выделять из allocator cache P1.

    Поэтому:

    P-local state
↓
нет конкурентного доступа в common case
↓
нет необходимости брать глобальный lock

    Это важный момент.

    Go allocator быстрый не потому, что:

    «malloc написан очень оптимизированно».

    Главная архитектурная причина:

    Частый путь специально построен так, чтобы избегать глобальной синхронизации.

    Блок 3. mspan — центральная единица allocator¶

    9. Проблема маленьких объектов¶

    Пусть мы постоянно создаем структуру размером около 40 байт.

    type Entry struct {
    A uint64
    B uint64
    C uint64
    D uint64
    E uint32
}

    Реальные программы создают объекты сотен разных размеров. Если без системы смешивать их в памяти:

    13 B
840 B
39 B
5 B
2048 B
61 B
...

    очень быстро появляется сложная fragmentation problem.

    Runtime использует size classes.

    10. Size class¶

    Идея:

    Не поддерживать отдельный allocator для каждого возможного размера.

    Вместо этого диапазоны размеров округляются до фиксированных классов.

    Для маленьких размеров:

    1–8 B   → slot 8 B
9–16 B  → slot 16 B
17–24 B → slot 24 B
25–32 B → slot 32 B
33–48 B → slot 48 B
49–64 B → slot 64 B
65–80 B → slot 80 B
...

    Пусть объект требует:

    37 B

    Он попадает в:

    48 B size class

    и получает slot:

    48 B

    Внутри:

    37 B полезные данные
11 B внутренний waste

    Это internal fragmentation.

    11. Зачем платить за internal fragmentation¶

    Потому что мы резко упрощаем allocator.

    Вместо:

    найди мне случайный непрерывный кусок ≥37 B

    можно делать:

    дай следующий свободный 48-byte slot

    Trade-off:

    фиксированные size classes
↓
быстрый allocator
+
предсказуемое размещение
-
немного потерянной памяти

    12. Что такое mspan¶

    mspan — структура runtime, которая описывает непрерывный набор runtime pages.

    Для small objects span обычно используется под один span class.

    mspan для 48-byte objects

┌──────┬──────┬──────┬──────┬──────┬──────┐
│ 48 B │ 48 B │ 48 B │ 48 B │ 48 B │ ...  │
└──────┴──────┴──────┴──────┴──────┴──────┘

    Каждый прямоугольник — потенциальный object slot.

    mspan
≠
один объект

    Один span обычно содержит множество slots.

    13. Runtime page¶

    mheap управляет памятью с granularity runtime page.

    В Go 1.27 runtime page:

    8192 bytes = 8 KiB

    Span может занимать одну или несколько таких pages:

    mspan
│
├── runtime page 0
├── runtime page 1
├── runtime page 2
└── runtime page 3

    Это implementation detail Go runtime.

    runtime page
≠
physical page Linux

    14. Пример span в цифрах¶

    Предположим учебно:

    span size = 8192 B
slot size = 64 B

    Тогда:

    8192 / 64 = 128 slots

    Когда приложение делает 100 allocations по 64 байта, runtime может обслужить их из одного уже подготовленного span.

    100 allocations
≠
100 обращений к OS

    15. allocBits¶

    Runtime должен знать, какие slots заняты.

    slot:      0 1 2 3 4 5 6 7
allocBits: 1 1 0 1 1 0 0 1

    Где:

    1 = allocated
0 = free

    Нужно выделить следующий объект:

    найти подходящий 0
↓
зарезервировать slot
↓
вернуть address

    16. freeindex¶

    Если каждый allocation начинать с slot 0, runtime будет снова и снова пересматривать занятые места.

    Поэтому span хранит информацию, откуда продолжать поиск свободного slot.

    slot:       0 1 2 3 4 5 6 7
allocBits:  1 1 1 1 0 0 1 0
freeindex:          ↑

    17. Почему mspan важен не только allocator¶

    Позже GC тоже будет работать с этими же spans.

    allocator:
какие slots заняты?

GC:
какие objects живы?

sweeper:
какие slots можно снова считать свободными?

    mspan — место встречи:

    allocation
GC marking
sweeping

    Что важно запомнить¶

    1. Size class — обмен небольшой internal fragmentation на быстрый allocator.
    2. mspan — metadata для run runtime pages, разбитого на slots одного класса.
    3. Один span содержит много объектов.
    4. Allocator хранит bitmap состояния slots.
    5. mspan используется и allocator, и GC.

    Углубление. Что реально хранит mspan¶

    Учебная модель:

    mspan
=
несколько runtime pages
+
slots одного class

    хороша, но для понимания allocator/GC взаимодействия надо увидеть metadata.

    Концептуально текущий mspan хранит сведения примерно такого класса:

    start address
number of pages
element size
number of elements
allocation count
free-search position
allocation bitmap
mark bitmap
span class
scan / noscan
sweep generation
zeroing state
span state

    Не надо запоминать названия полей исходника.

    Важно понимать, зачем каждый класс metadata существует.

    elemsize, nelems, allocCount¶

    Для small-object span runtime знает:

    размер span
размер slot

    и отсюда:

    nelems = сколько slots помещается в span

    Например:

    span = 8 KiB
slot = 64 B

8192 / 64 = 128 slots

    Если:

    allocCount == nelems

    span заполнен.

    Если после sweep:

    allocCount == 0

    весь span потенциально можно вернуть на page-level allocator.

    Это принципиальная граница:

    мертвый отдельный object
≠
свободный span

    freeindex и bitmap¶

    Runtime не хочет после каждой allocation начинать поиск свободного slot сначала:

    slot 0?
slot 1?
slot 2?
...

    Он хранит progress поиска.

    Дополнительно текущая реализация кеширует окно allocation bitmap в машинном слове, чтобы поиск свободного slot свести к быстрым bit operations.

    Условно:

    bitmap span
↓
64-bit window
↓
find-first-free bit
↓
slot

    Это хороший пример общей темы runtime:

    частая операция превращается в локальный и предсказуемый hot path.

    Allocation bitmap и mark bitmap отвечают на разные вопросы¶

    Allocator спрашивает:

    slot занят?

    Collector спрашивает:

    object reachable в текущем GC cycle?

    Поэтому концептуально существуют два разных состояния:

    allocation state
GC marking state

    Sweep потом сопоставляет их:

    allocated = yes
marked = no
↓
dead
↓
slot становится reusable

    sweepgen¶

    После GC runtime должен различать spans:

    уже swept
еще не swept
cached в mcache
sweeping прямо сейчас

    Если allocator начнет выдавать slots из span с metadata предыдущего cycle, можно получить corruption allocator state.

    Ментальная модель:

    GC cycle N закончился
↓
span содержит mark results N
↓
перед повторным allocation span должен пройти sweep N
↓
только после этого free slots безопасны для reuse

    Почему lifecycle span ограничен фазами GC¶

    Collector может получить heap pointer и искать соответствующий span.

    Если span metadata в этот момент мгновенно исчезает и переиспользуется для другого назначения, pointer lookup может увидеть уже чужое состояние.

    Поэтому переходы span state во время concurrent GC ограничены.

    Это уже correctness, а не optimization.

    Zeroing тоже часть allocator design¶

    После старого объекта в slot физически могут остаться bytes.

    Go обязан обеспечить корректное zero value.

    Наивный вариант:

    object dead
↓
немедленно memset(0)

    может zero'ить memory, которая никогда больше не понадобится.

    Runtime предпочитает откладывать zeroing до реального reuse там, где это допустимо:

    free memory
↓
новая allocation
↓
zero when needed

    Это улучшает temporal locality и избегает бесполезной работы.

    Почему mspan центральный¶

    mspan связывает:

    heap layout
+
size segregation
+
allocation state
+
GC mark state
+
sweep lifecycle
+
zeroing

    Поэтому это не просто "кусок памяти", а единица координации allocator и collector.

    Для каждого span class существует центральное управление spans.

    mcentral[64-byte noscan]

    span A
    span B

    span C

    mcentral не является мешком отдельных free objects. Свободные object slots находятся внутри mspan.

    27. Почему mcache получает span, а не один object¶

    lock mcentral
↓
выдать один object
↓
unlock

    Миллионы allocations → миллионы lock/unlock.

    Правильнее:

    редко:
mcache получает span

часто:
mcache раздает из него много objects

    28. Contention переносится с hot path¶

    Performance pattern:

    не обязательно удалить synchronization полностью
↓
нужно убрать ее с каждого hot-path operation

    Углубление. mcentral — не просто "следующий уровень после mcache"¶

    Упрощенная картинка:

    mcache empty
↓
mcentral
↓
дай новый span

    верна, но скрывает важную связь со sweeping.

    mcentral хранит spans, а не free objects¶

    Это принципиально.

    Не так:

    mcentral
├── object
├── object
├── object

    А так:

    mcentral[spanClass]
├── span A
├── span B
└── span C

    Свободные slots находятся внутри самих spans.

    Partial и full¶

    Для одного spanClass runtime должен различать:

    partial
→ в span есть хотя бы один reusable slot

full
→ все slots заняты

    Но после GC появляется еще одно измерение:

    swept
unswept

    Условно:

                     swept       unswept
partial            A             B
full               C             D

    Это объясняет, почему refill иногда внезапно делает больше работы.

    Allocation-driven sweeping¶

    P запросил новый span у mcentral.

    Идеальный случай:

    partial swept span exists
↓
забрать span
↓
готово

    Но может быть:

    partial swept empty
↓
есть unswept spans

    Runtime может взять unswept span, выполнить sweep и только потом решить:

    нашлись free slots?

    То есть allocation path иногда выполняет часть cleanup предыдущего GC cycle.

    Это важная причинная цепочка:

    allocation
↓
mcache refill
↓
mcentral
↓
span еще stale/unswept
↓
sweep work
↓
allocation latency

    Частый fast path остается дешевым.

    Но refill path уже связывает allocator и collector напрямую.

    Почему не sweep'ить все мгновенно после mark termination¶

    Можно было бы:

    mark закончился
↓
STW
↓
sweep всего heap
↓
resume

    Но это создало бы длинную pause.

    Вместо этого Go распределяет sweep work:

    background sweep
+
allocation-driven sweep

    Цена снова размазывается по времени.

    Почему runtime ограничивает поиск среди unswept spans¶

    Если mcentral бесконечно перебирает старые full spans в надежде найти там один free slot:

    refill latency

    становится плохо ограниченной.

    Текущая реализация использует ограниченный budget попыток и после этого предпочитает получить свежий span.

    Trade-off:

    чуть больше memory
↔
предсказуемее allocation latency

    Это очень backend-ориентированное решение.

    Runtime сознательно иногда предпочитает небольшой space overhead длинной задержке на hot path.

    Даже metadata пытаются не сталкивать на cache line¶

    В текущем mheap массив mcentral содержит padding, чтобы разные central locks не делили одну cache line.

    Почему?

    Потому что иначе два независимых span classes могли бы получить:

    lock A
lock B

    логически независимые, но физически находящиеся в одной cache line.

    И мы получили бы уже знакомый:

    false sharing
↓
cache-line ping-pong

    То есть тема CPU cache из предыдущей лекции буквально проявляется внутри allocator design.

    Heap arena¶

    Go heap разбит на крупные arenas виртуального адресного пространства.

    На большинстве 64-bit non-Windows платформ текущая реализация использует arena порядка:

    64 MiB

    Arena — не один объект и не один span.

    Это крупная единица организации address space и heap metadata.

    Для каждой arena runtime хранит metadata, позволяющую быстро отвечать:

    этот address принадлежит Go heap?
какой span покрывает эту page?
где metadata для scanning?

    Причем эта metadata сама хранится вне обычного GC heap.

    Почему?

    Потому что collector не должен собирать собственные критические структуры.

    Address → arena → span¶

    Пусть collector встретил pointer:

    0xc012345678

    Ему нужно быстро определить:

    heap?
↓
arena?
↓
span?
↓
object?

    Вместо глобального поиска по всем allocations runtime использует адресную арифметику и индексируемые tables.

    Мы платим memory metadata, чтобы critical lookup был быстрым.

    Page allocator тоже имеет локальный fast path¶

    У P есть не только object-level mcache.

    В текущем runtime есть и небольшой per-P pageCache.

    Условно:

    P
├── mcache      → object slots
└── pageCache   → runtime pages

    Это два разных уровня кеширования.

    Current page cache хранит bitmap окна runtime pages:

    base address
+
free-page bitmap
+
scavenged-page bitmap

    Для 64 runtime pages по 8 KiB это окно:

    64 × 8 KiB = 512 KiB

    Fast path для одной page концептуально:

    bitmap
↓
find first free bit
↓
clear bit
↓
base + index*pageSize

    Опять тот же design:

    часто
→ локально
→ bit operations
→ без global lock

    Global page allocator¶

    Когда локального page cache недостаточно, runtime идет в общий page allocator.

    Он управляет free pages через:

    bitmap
+
summary structure

    Одного bitmap мало.

    Пусть heap большой и нужен run:

    128 contiguous pages

    Линейно обходить миллионы page bits дорого.

    Поэтому поверх bitmap используются многоуровневые summaries, организованные как radix tree.

    Учебно:

    root summary
↓
есть ли подходящий free run в большом region?
↓
следующий уровень
↓
следующий уровень
↓
chunk bitmap
↓
конкретные pages

    Большие неподходящие regions можно быстро пропускать.

    Contiguous free memory¶

    Очень важный вывод:

    free pages много

    не означает:

    есть большой contiguous run

    Например:

    F U F U F U F U

    где:

    F = free
U = used

    Свободных pages половина, но request на четыре contiguous pages здесь не помещается.

    Virtual memory != physical RAM¶

    Большая reservation virtual address space не означает такой же RSS.

    Нужно различать:

    virtual address reservation
mapping / ready memory
resident physical pages

    На 64-bit системах virtual address space дешев.

    Physical RAM — нет.

    Runtime использует эту разницу, чтобы упростить heap layout и metadata.

    Если heap нужно реально расширить:

    page allocator
↓
heap growth
↓
runtime OS abstraction
↓
mmap / VirtualAlloc / platform mechanism

    Но:

    1 small object
≠

    Pointer-containing tiny objects потребовали бы сложной индивидуальной GC metadata внутри совместно размещенного block.

    Поэтому tiny allocator применяется к objects без pointers.

    A dead
B alive

    может означать, что весь tiny block пока нельзя освободить.

    Trade-off:

    немного retention
↔
меньше allocator overhead

    Что важно запомнить¶

    1. Small objects обслуживаются size classes.
    2. Large objects идут ближе к page allocator.
    3. Tiny pointer-free objects могут делить 16-byte block.
    4. Чем дальше путь уходит от mcache, тем он дороже.
    5. Allocator decisions тесно связаны с GC.

    Углубление. Fragmentation: почему "свободная память есть" еще ничего не означает¶

    Non-compacting GC оставляет объекты на месте.

    Это дает:

    stable addresses
нет массового перемещения live heap
проще pointer semantics
проще runtime/cgo interaction

    Но цена — fragmentation.

    Нужно различать несколько уровней.

    Internal fragmentation¶

    Объект:

    37 B

    попал в:

    48 B slot

    Потеря:

    11 B

    Эти bytes находятся внутри уже выделенного slot и не могут обслужить другой object.

    Span-level fragmentation¶

    Представим span:

    [dead][dead][LIVE][dead][dead][dead][dead][dead]

    Почти весь span свободен.

    Allocator может использовать dead slots для новых objects того же spanClass.

    Но page allocator не может просто забрать pages всего span:

    внутри еще есть LIVE object

    Scavenger тоже не может вернуть такие pages OS как полностью свободный heap run.

    Отсюда ситуация:

    live heap небольшой

    но:

    RSS заметно выше

    без классического leak.

    Page-level fragmentation¶

    Пусть page allocator видит:

    F U F U F U F U

    Свободных pages много.

    Но request:

    дай 4 contiguous pages

    здесь не удовлетворяется.

    Следовательно:

    total free bytes

    не описывает полностью usable free memory.

    Size classes уменьшают хаос, но не отменяют fragmentation¶

    Size segregation помогает:

    объекты похожего размера
→ живут вместе
→ slots легко reuse'ить

    Но free slot класса 48 B нельзя просто отдать object на 2 KiB.

    Для смены класса должен освободиться span целиком и вернуться на page-level allocator.

    Lifetime distribution важна не меньше размера¶

    Типичный backend pattern:

    request
↓
1000 temporary objects
↓
999 умерли
1 object попал в long-lived cache

    Если этот survivor удерживает span:

    span почти пуст

    но его pages остаются частью live span.

    Это один из механизмов, через который маленький retained object способен косвенно удерживать больше resident memory, чем кажется по его собственному размеру.

    Не надо превращать это в правило:

    1 object всегда удерживает целые мегабайты

    Размер эффекта зависит от span layout и workload.

    Но причинная цепочка реальна.

    Инженерный вывод¶

    Неверная модель:

    GC удалил 3 GiB objects
↓
RSS обязан сразу упасть на 3 GiB

    Более точная:

    objects dead
↓
sweep освободил slots
↓
какие spans стали полностью free?
↓
какие pages можно вернуть page allocator?
↓
что может release scavenger?
↓
что kernel реально reclaim'нул?

    Это несколько разных стадий.

word 2 → scalar
word 3 → pointer

    GC не обязан считать каждое число потенциальным pointer.

    Это важно.

    При conservative scanning случайное число, похожее на address, могло бы ложно удерживать object live.

    Precise metadata позволяет этого избежать.

    Stack scanning не означает одну огромную STW¶

    Во время mark runtime может кратко остановить конкретную goroutine, просканировать stack и продолжить ее выполнение.

    Концептуально:

    G running
↓
нужно просканировать stack
↓
G остановлена для scan
↓
stack pointers shaded
↓
G resumes

    Это отличается от модели:

    остановить все приложение
↓
просканировать все stacks
↓
запустить все обратно

    Короткие глобальные STW transitions все равно остаются, но основная mark work concurrent.

    Новые allocations во время mark¶

    Новый object не должен случайно стать garbage только потому, что collector еще не обошел его обычным graph traversal.

    В текущем runtime новые heap objects во время mark считаются live для текущего cycle.

    Учебно:

    allocated during mark
↓
black for current cycle

    Иначе получили бы:

    application создала object
↓
collector его еще не видел
↓
collector освободил object

    что очевидно недопустимо.

    Почему завершение mark — distributed termination problem¶

    Проверки:

    global queue empty

    недостаточно.

    Work может находиться:

    P0 local work
P1 local work
P2 worker currently scanning
root jobs
write-barrier buffers

    Поэтому mark termination требует доказать:

    roots exhausted
+
local/global work exhausted
+
workers не породят новую незарегистрированную work
+
barrier protocol сохраняет invariant

    Это уже не обычный DFS из учебника по алгоритмам.

    Блок 11. Зачем write barrier¶

    49. Concurrent graph mutation¶

    Было:

    A → B

    GC уже просмотрел A.

    Application делает:

    A → C

    Heap graph изменился прямо во время tracing.

    Без дополнительного механизма collector может потерять reachable object.

    50. STW было бы проще¶

    application stopped
↓
heap graph frozen
↓
GC спокойно обходит graph

    Но это дает большие pauses.

    Concurrent GC выбирает более сложный путь: application продолжает работать, а runtime поддерживает correctness специальными barriers.

    Блок 12. Write barrier¶

    51. Что это¶

    Упрощенно:

    обычный store:
slot = newPointer

    во время mark phase становится концептуально:

    GC bookkeeping
+
slot = newPointer

    Компилятор/runtime оптимизируют этот path, но смысл такой: pointer mutation должна быть видима collector.

    52. Old и new pointers¶

    before:
slot → old

after:
slot → new

    Hybrid write barrier сохраняет tracing invariant так, чтобы collector не потерял важные references при concurrent mutation.

    53. Почему barrier стоит CPU¶

    check
bookkeeping
buffer/shade
store

    GC cost распределяется не только по background workers. Часть цены платит mutator.

    54. Barrier работает по фазам¶

    Упрощенно:

    GC off
↓
barrier mostly off

concurrent mark
↓
barrier on

    Углубление. Что именно защищает hybrid write barrier¶

    Текущий Go runtime использует hybrid barrier, сочетающий deletion-style и insertion-style защиту.

    Имена алгоритмов важны меньше, чем две разные опасности.

    Опасность 1. Удаляем старую ссылку¶

    Было:

    A → B

    Mutator делает:

    A → C

    Старая ссылка на B исчезает.

    Если B еще не был корректно учтен collector, его нельзя просто потерять из tracing graph.

    Поэтому barrier учитывает old pointer до overwrite.

    Опасность 2. Устанавливаем новую ссылку¶

    Collector уже обработал A.

    Mutator пишет:

    A → C

    Если C еще не учтен, может возникнуть:

    processed A
↓
unseen C

    Insertion часть barrier не дает новой reachable ссылке исчезнуть из поля зрения collector.

    Упрощенный pseudocode¶

    Концептуально:

    writePointer(slot, new):
    shade(old value from slot)

    if current stack is still grey:
        shade(new)

    *slot = new

    Реальная implementation оптимизирована, но этот pseudocode показывает смысл.

    Почему учитывается состояние stack¶

    Пока stack goroutine еще не просканирован, mutator способен перенести pointer:

    stack
↓
heap

    и collector должен не потерять такой referent.

    После scan stack ситуация проще: root set этой goroutine для текущей фазы уже учтен.

    Write barrier тоже имеет fast path¶

    Плохой вариант:

    каждая pointer write
↓
global lock
↓
global GC queue

    убил бы scalability.

    Поэтому текущий runtime использует per-P write-barrier buffering.

    Учебно:

    pointer write
↓
barrier fast path
↓
append pointer information в P-local buffer
↓
continue mutator

    Когда buffer заполняется:

    buffer full
↓
slow path
↓
flush to GC work

    Опять тот же runtime pattern:

    локально часто
глобально редко

    Почему barrier tax не равен STW¶

    Стоимость barrier размазана по mutator execution:

    branch
bookkeeping
buffer writes
occasional flush
cache pressure

    Поэтому:

    STW = 200 μs

    не означает:

    GC почти бесплатный

    Concurrent GC специально переносит большую часть стоимости из длинных pauses в постоянный throughput tax.

    Блок 13. Green Tea GC¶

    55. Старая проблема: pointer chasing¶

    найди A
↓

↓
найди B
↓
scan B

    Но физически:

    A → page 100
B → page 8000

    Heap tracing может упираться в memory subsystem CPU, а не в арифметику.

    Вместо беспорядочного object-at-a-time scan runtime старается группировать работу по spans/pages.

    span 1:
    A
    C
    E

span 40:
    B

span 900:
    D

    Цель:

    лучше reuse cache lines
меньше повторной metadata work
лучше locality

    58. Что для разработчика не изменилось¶

    heap object
↓
unreachable
↓

    Green Tea — implementation detail current runtime.

    59. Mark и scan — не одно и то же¶

    marked = object обнаружен reachable
scanned = outgoing pointers обработаны

    Возможное состояние:

    marked = yes
scanned = no

    60. Снова per-P locality¶

    Scheduler:

    P → local run queue → steal/global

    Allocator:

    P → mcache → mcentral

    GC:

    P → local work → share/steal

    Общий runtime pattern:

    Горячую работу держим локально, глобальную координацию делаем реже.

    Что важно запомнить¶

    1. Concurrent GC обязан учитывать изменения heap graph.
    2. Write barrier сохраняет correctness tracing.
    3. Barrier добавляет runtime cost к части pointer writes.
    4. Green Tea оптимизирует locality marking/scanning work.
    5. Green Tea — detail current runtime, не гарантия спецификации.

    Углубление. Green Tea ниже уровня "лучше locality"¶

    Сказать:

    Green Tea группирует работу по pages

    недостаточно.

    Нужно понять, что именно поменялось.

    Старый graph flood¶

    Классическая marking worklist была object-oriented:

    найден object A
↓
положили A в worklist
↓
scan A
↓
нашли B, C, D
↓
положили B, C, D

    Получается pointer chasing:

    page 10
↓
page 900
↓
page 31
↓
page 7000

    Следующий address зависит от pointer, который мы только что загрузили.

    CPU плохо видит будущее.

    Hardware prefetcher и out-of-order execution имеют мало возможностей спрятать latency.

    Green Tea меняет единицу scheduling work¶

    Основная идея:

    worklist хранит pages
а не отдельные objects

    Но объекты все равно надо различать.

    Для object slots на page ведется состояние концептуально:

    seen
scanned

    seen:

    мы нашли pointer на object

    scanned:

    мы обработали outgoing pointers object

    Работа для page примерно:

    seen - scanned

    То есть:

    видели
но еще не сканировали

    Почему page может снова попасть в queue¶

    Page A уже была обработана.

    Позже scanning page B нашел еще один ранее unseen object на A.

    Тогда:

    page A
↓
снова становится GC work
↓
снова попадает в queue

    Green Tea сознательно допускает повторную постановку page, потому что хочет накопить несколько объектов одной locality region и обработать их вместе.

    Почему queue-like scheduling полезен¶

    Старый graph flood быстро уходил по pointer chain:

    A → B → C → D

    Green Tea дает page время накопить work.

    Условно:

    нашли object 1 на page X
↓
page X queued

пока X ждет:
нашли object 2 на X
нашли object 3 на X
↓
X dequeued
↓
несколько objects сканируются подряд

    Это batching.

    Связь с CPU caches¶

    Graph traversal:

    load pointer
↓
непредсказуемый next address
↓
cache miss
↓
load pointer
↓
следующий miss

    Green Tea пытается превратить часть этого поведения:

    много коротких случайных scans

    в:

    меньше более длинных scans по соседним данным

    Выигрыш:

    • выше шанс reuse cache lines;
    • metadata page чаще остается в cache;
    • меньше pressure на shared work queues;
    • меньше stalls на memory subsystem.

    Получается цепочка:

    GC algorithm
↓
memory access pattern
↓
CPU cache behavior
↓
GC CPU time

    Почему стали возможны vector instructions¶

    Когда processing становится регулярным на уровне page, появляются одинаковые bitmaps:

    seen
scanned
pointer/scalar layout

    Упрощенная логика:

    seen - scanned
↓
active object bitmap
↓
expand по словам объектов
↓
AND с pointer bitmap
↓
active pointers

    Это уже хорошо ложится на wide vector registers и bit operations.

    На современных amd64 CPU Green Tea способен использовать AVX-512 accelerated scanning path при наличии нужной hardware support.

    Но:

    Green Tea != "AVX-512 GC"

    Главная идея — page-oriented locality.

    Vectorization стала следствием более регулярного алгоритма.

    Почему эффект зависит от workload¶

    Если heap в основном:

    []byte
large noscan buffers

    scan work и так может быть небольшой.

    Если GC занимал:

    2% CPU

    даже двукратное ускорение части collector не даст фантастического end-to-end результата.

    Другой случай — pointer-rich heap и заметный GC CPU.

    Там locality improvements могут быть гораздо важнее.

    87. Почему runtime не отдает все сразу¶

    Если traffic скоро вернется, повторное использование уже mapped pages дешевле, чем постоянно отдавать и снова получать их от kernel.

    reuse speed
↔

    Углубление. Sweep и scavenger работают на разных картах мира¶

    Sweep думает объектами и spans:

    mark state
↓
object dead?
↓
slot free

    Scavenger думает pages:

    какие heap pages runtime реально не нужны?
↓
можно ли снять physical backing?

    Это разные задачи.

    Почему free slot еще нельзя отдать OS¶

    Span:

    [free][free][LIVE][free]

    Allocator может использовать free slots.

    Но physical page все еще содержит live object.

    Нельзя сказать kernel:

    эти 8 KiB мне больше не нужны

    пока page нужна активному span.

    Для release нужен более высокий уровень свободы:

    runtime page больше не нужна live spans

    Scavenged page не обязана исчезать из virtual address space¶

    После scavenging концептуально возможно:

    virtual address
→ остается частью Go heap layout

physical backing
→ может быть reclaimed kernel

    Позже runtime снова использует тот же address и physical backing появляется заново через OS VM mechanism.

    Поэтому:

    virtual memory

    и:

    resident physical memory

    нельзя смешивать.

    Почему scavenger не должен быть максимально агрессивным¶

    Представим:

    12:00 traffic spike
heap grows to 8 GiB

12:01 traffic falls
6 GiB become free

12:02 traffic spike again

    Если runtime немедленно отдал все OS:

    release
↓
через минуту снова fault/map/zero

    получаем memory-management churn.

    Если ничего не отдавать:

    RSS остается высоким

    Нужен trade-off:

    reuse speed
↔
low resident footprint

    Tight memory budget может приблизить scavenging к hot path¶

    Если memory limit очень жесткий:

    runtime пытается держать footprint
+
allocation требует pages

    allocator и scavenger начинают сильнее взаимодействовать.

    Это одна из причин, почему слишком маленький GOMEMLIMIT может увеличить стоимость allocation даже помимо частоты GC.

    RSS — внешний взгляд¶

    Heap metadata может уже говорить:

    objects dead
slots free
some pages released

    а RSS показывает residency глазами kernel.

    Поэтому:

    GC закончился
↓
RSS обязан мгновенно стать live heap

    — неверная модель.

    Что важно запомнить¶

    1. Small heap allocation в common case обслуживается локально через per-P allocator state. Дорогие глобальные уровни нужны в основном для refill и роста heap.
    2. mspan — ключевая единица, связывающая allocator и GC. Span описывает run runtime pages и для small objects разбит на slots одного span class.
    3. Размер объекта — только половина истории. Наличие pointers определяет scan/noscan и напрямую влияет на работу collector.
    4. GC cost определяется не только live heap. Важны allocation rate, scannable heap, roots, shape pointer graph и memory budget.
    5. Concurrent GC не бесплатный. Цена распределена между background workers, write barriers и mutator assists.
    6. Green Tea с Go 1.26 — текущая реализация default collector. Его ключевая идея — улучшить locality marking/scanning work.
    7. Heap goal и GC trigger — разные понятия. Pacer должен начать collector заранее.
    8. Mutator assist напрямую связывает allocations с request latency. Allocating goroutine может сама выполнять GC work.
    9. Sweep и scavenger решают разные задачи. Sweep возвращает memory allocator'у Go; scavenger помогает вернуть physical backing ОС.
    10. HeapAlloc, free heap, released heap и RSS нельзя смешивать. Они описывают разные слои memory management.
    11. GOMEMLIMIT — soft runtime budget, cgroup limit — внешний hard constraint. Между ними нужен запас.
    12. Главная optimization strategy — уменьшать ненужные allocations и pointer-rich live data после измерений, а не механически крутить GC knobs.

    Финальный инженерный вывод:

    В Go heap allocation — не просто операция «взяли память». Это вход в целую runtime-систему. Fast path может быть очень дешевым, но объект способен позже породить mark work, write-barrier work, assists, sweep work, RSS pressure и kernel memory-management work. Поэтому настоящая цена allocation проявляется не только в момент ее выполнения, а на всем жизненном цикле объекта.
