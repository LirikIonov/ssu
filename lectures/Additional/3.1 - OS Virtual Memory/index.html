    3.1. Виртуальная память ОС: от адреса Go до физической RAM¶

    Дополнительная углублённая лекция к теме «Память Go, GC и pprof».

    Главная задача этой лекции — открыть слой справа от цепочки:

    GC
↓
sweep
↓
scavenger
↓
ОС

    Нас интересует, что именно происходит после того, как рантайм Go решил:

    Эти страницы мне больше не нужны.

    И обратный путь:

    Откуда вообще берётся физическая память, когда Go начинает пользоваться новым виртуальным диапазоном?

    0. Где заканчивается Go и начинается ОС¶

    В предыдущем блоке мы уже дошли до:

    Go object
↓
slot
↓
mspan
↓
runtime page
↓
mheap
↓
page allocator
↓
scavenger
↓
ОС

    До этого момента рантайм Go говорит на своём языке:

    object
slot
span
runtime page
heap

    Операционная система этих сущностей не знает.

    Для неё есть:

    process
virtual address
mapping
page
physical memory
permissions
resident / non-resident

    И вот здесь очень легко сделать неправильный вывод:

    GC освободил объект → RAM освободилась.

    Нет.

    Более точная цепочка:

    object unreachable
↓
GC не отметил его живым
↓
sweep сделал slot reusable
↓
span может стать пустым
↓
runtime pages могут стать свободными
↓
scavenger сообщает ОС, что backing можно вернуть
↓
ядро решает, что реально делать с physical pages

    Между:

    объект мёртв

    и:

    физическая RAM снова доступна системе

    несколько независимых стадий.

    1. Зачем вообще нужна виртуальная память¶

    Начнём с слишком простой модели:

    у процесса 8 GiB памяти
↓
адрес 0x1234
↓
конкретная ячейка в DIMM

    Так современная ОС не работает.

    Процесс видит виртуальное адресное пространство.

    CPU instruction
↓
virtual address
↓
translation
↓
physical address

    Для программы существует удобная иллюзия:

    адреса идут почти как обычное пространство чисел

    Но физическая RAM под ними может:

    • находиться в разных местах;
    • вообще пока отсутствовать;
    • быть выгружена;
    • быть общей с другим mapping;
    • быть file-backed;
    • поменять physical frame без изменения указателя в программе.

    Зачем вся эта сложность?

    Потому что виртуальная память даёт:

    • изоляцию процессов;
    • защиту страниц;
    • отдельные адресные пространства;
    • lazy allocation;
    • memory-mapped files;
    • copy-on-write;
    • возможность управлять resident memory независимо от виртуальных адресов;
    • удобную основу для reclaim и swap.

    2. Виртуальный адрес не означает занятую RAM¶

    Представим, что процессу зарезервировали:

    10 GiB virtual address space

    Это ещё не означает:

    10 GiB physical RAM already occupied

    Нужно разделить несколько уровней:

    virtual address space
↓
mapping
↓
usable / committed memory
↓
resident physical memory

    Это одна из ключевых моделей всей лекции.

    Большой VSS может означать:

    у процесса большой виртуальный диапазон

    и почти ничего не говорить о том, сколько физической памяти реально находится в RAM.

    3. Виртуальные страницы¶

    Операционная система не переводит каждый байт отдельно.

    Адресное пространство делится на страницы.

    Типичная учебная модель:

    4 KiB page

    Виртуальный адрес можно представить как:

    virtual page number
+
offset inside page

    Например:

    virtual address
↓
[ virtual page ][ offset ]

    Если размер страницы 4 KiB:

    offset = 12 младших бит

    потому что:

    2^12 = 4096

    Нас сейчас интересует идея, а не конкретный формат каждой ISA.

    4. Page table¶

    Теперь вопрос:

    Кто переводит виртуальную страницу процесса в физическую страницу?

    Для этого существуют таблицы страниц (page tables).

    Учебно:

    virtual page
↓
page table
↓
physical frame

    Запись таблицы страниц может содержать не только физический адрес.

    Ей также нужны признаки вроде:

    present?
readable?
writable?
executable?
user-accessible?
dirty?
accessed?

    Конкретный набор битов зависит от архитектуры и ОС.

    Главная идея:

    Виртуальная память — это ещё и система прав доступа.

    Именно поэтому один процесс не может просто взять произвольный указатель и читать память другого процесса.

    5. Многоуровневые таблицы страниц¶

    Если бы под каждую возможную виртуальную страницу процесса существовала заранее огромная плоская таблица, мы потратили бы много памяти только на переводы адресов.

    Поэтому современные системы используют многоуровневые структуры.

    Учебно:

    virtual address
↓
level 1
↓
level 2
↓
level 3
↓
page table entry
↓
physical frame

    На x86-64 конкретных уровней может быть четыре или пять в зависимости от режима.

    Для этой лекции важнее другое:

    Перевод адреса сам по себе требует доступа к памяти.

    И если делать полный обход page tables для каждого load/store, система станет очень медленной.

    6. MMU¶

    Перевод адресов выполняется аппаратно при помощи MMU — Memory Management Unit.

    Упрощённо:

    CPU хочет load virtual address
↓
MMU
↓
translation
↓
physical memory

    Программа не вызывает:

    translateAddress()

    на каждое обращение.

    Это часть аппаратного выполнения инструкций.

    Но теперь новая проблема:

    каждый memory access
↓
page-table walk
↓
ещё несколько memory access

    Получается дорого.

    Нужен кеш переводов.

    7. TLB¶

    TLB — Translation Lookaside Buffer.

    Это кеш недавних переводов:

    virtual page
→
physical frame

    Учебная цепочка:

    virtual address
↓
TLB
├── hit
│   ↓
│   physical address готов
│
└── miss
    ↓
    page-table walk
    ↓
    translation cached in TLB

    Теперь важное разделение:

    data cache miss
≠
TLB miss

    В первом случае CPU знает physical address, но нужных данных нет в кеше.

    Во втором случае CPU ещё должен понять:

    К какой физической странице вообще относится виртуальный адрес?

    Это разные виды задержки.

    8. Почему размер страницы влияет на TLB¶

    Пусть:

    page size = 4 KiB

    Одна запись TLB покрывает 4 KiB виртуального пространства.

    Если процесс активно работает с огромным объёмом случайно разбросанных данных:

    рабочий набор переводов > TLB capacity

    начинаются TLB misses.

    Можно использовать более крупные страницы.

    Например концептуально:

    2 MiB

    Теперь одна запись TLB покрывает гораздо больше памяти.

    Плюс:

    меньше translations
↓
меньше TLB pressure

    Цена:

    более грубая гранулярность
↓
больше потенциального waste
↓
сложнее управление памятью

    9. Huge pages и THP¶

    На Linux существуют большие страницы и механизм Transparent Huge Pages.

    Идея:

    много соседних обычных страниц
↓
более крупное отображение
↓
меньше TLB entries

    Но огромные страницы — не универсальная оптимизация.

    Они могут:

    • улучшить TLB behaviour;
    • уменьшить page-table overhead;
    • ухудшить гранулярность reclaim;
    • увеличить внутренний waste;
    • создавать дополнительные накладные расходы на collapse/split.

    В рамках этой лекции важно понять компромисс.

    Не нужно превращать THP в обязательный production-тюнинг.

    10. Page fault: это не обязательно ошибка¶

    Процесс выполняет:

    load [virtual address]

    MMU смотрит translation и обнаруживает:

    нужной resident page сейчас нет

    Происходит page fault.

    Очень важно:

    Page fault — не обязательно баг программы.

    Это штатный механизм виртуальной памяти.

    Учебно:

    instruction
↓
обращение к странице
↓
страница сейчас недоступна обычным путём
↓
CPU trap
↓
kernel page-fault handler
↓
ядро разбирает причину
↓
делает страницу доступной
↓
инструкция повторяется

    11. Когда page fault действительно означает ошибку¶

    Например процесс обращается:

    к адресу, который ему вообще не отображён

    или:

    пытается писать в read-only mapping

    Тогда kernel не может просто подготовить нормальную страницу.

    В Unix-подобной системе результатом может стать:

    SIGSEGV

    Но огромное количество page faults в нормальной работе связано с законной ленивой подстановкой страниц.

    12. Minor page fault¶

    Minor fault — fault, для обработки которого не нужно читать данные с медленного внешнего накопителя.

    Например:

    • first touch новой anonymous memory;
    • copy-on-write;
    • страница уже есть в page cache;
    • zero-page механизм;
    • mapping существует, но PTE нужно обновить.

    Цена есть:

    trap в kernel
+
обработка VM metadata
+
обновление page table
+
возврат в процесс

    Но дискового I/O может не быть.

    13. Major page fault¶

    Major fault — для получения данных требуется реальное I/O.

    Например:

    file-backed page отсутствует в RAM
↓
нужно читать storage

    или:

    anonymous page выгружена в swap
↓
нужно прочитать её обратно

    Здесь мы перескакиваем из мира:

    десятки / сотни наносекунд

    в мир:

    микросекунд / миллисекунд

    Поэтому major page faults способны разрушить p99.

    14. Demand paging¶

    Допустим процесс получил большой виртуальный диапазон.

    Наивная модель:

    запросили 10 GiB
↓
ОС немедленно выделила 10 GiB physical RAM
↓
обнулила всё

    Это дорого и часто бессмысленно.

    Вместо этого работает demand paging.

    виртуальный диапазон существует
↓
часть страниц физически ещё не backed
↓
процесс касается страницы
↓
page fault
↓
kernel выдаёт physical page

    RAM появляется по требованию.

    15. Почему большой make не всегда сразу равен такому же RSS¶

    Учебный эксперимент:

    buf := make([]byte, 4<<30)

    Логически у процесса появился огромный массив.

    Но если реальные страницы ещё почти не трогались, физическое использование памяти может расти иначе, чем виртуальный диапазон.

    Теперь:

    for i := 0; i < len(buf); i += 4096 {
    buf[i] = 1
}

    Мы касаемся страниц.

    Получаем:

    page fault
↓
physical backing
↓
RSS растёт

    Это очень хороший способ руками увидеть:

    virtual memory
≠
resident memory

    16. Zero page¶

    Новая anonymous memory должна логически читать как нули.

    Но система не обязана заранее физически создавать миллиарды нулевых байт.

    Учебно можно представить:

    много virtual pages
↓
пока только читаются
↓
могут логически ссылаться на общую read-only zero page

    Когда процесс хочет записать:

    write
↓
нужна собственная physical page
↓
fault
↓
выдать zeroed page

    Главная идея:

    Семантика «там нули» не означает «ОС уже физически записала нули во весь диапазон».

    17. Copy-on-write¶

    Теперь два mapping могут временно использовать одну physical page.

    mapping A ─┐
           ├── physical page
mapping B ─┘

    Пока оба читают:

    ничего копировать не нужно

    Один начинает писать:

    write
↓
protection fault
↓
kernel
↓
создать private copy
↓
перенаправить mapping
↓
продолжить

    Это copy-on-write (COW).

    Классический пример — fork, но нам важнее сама модель:

    Физическое копирование можно отложить до реальной записи.

    18. Anonymous memory¶

    Anonymous memory — память, не привязанная напрямую к содержимому обычного файла.

    Типичные примеры:

    heap
stack
anonymous mmap

    Если её содержимое нужно сохранить при вытеснении из RAM, ОС не может просто сказать:

    потом перечитаю исходный файл

    Исходного файла нет.

    Нужен другой backing, например swap.

    19. File-backed memory¶

    Другой класс:

    file-backed mapping

    Страница соответствует содержимому файла.

    Например:

    исполняемый файл
shared library
memory-mapped file
page cache

    Если чистую file-backed страницу нужно освободить из RAM:

    её можно просто выбросить

    Потом:

    если снова нужна
↓
перечитать файл

    Это фундаментально отличается от dirty anonymous memory.

    20. Page cache¶

    Обычное чтение файла часто выглядит:

    read()
↓
kernel
↓
page cache
├── hit
│   ↓
│   данные уже в RAM
│
└── miss
    ↓
    storage I/O
    ↓
    page cache
    ↓
    процесс

    То есть RAM используется не только Go heap.

    ОС активно использует свободную память под кеш файловых данных.

    Отсюда важный вывод:

    «RAM занята» само по себе ничего не говорит о проблеме.

    Часть памяти может быть легко reclaimable page cache.

    21. Что значит resident¶

    Виртуальная страница может существовать в адресном пространстве процесса, но её physical backing может не находиться сейчас в RAM.

    Когда physical page реально присутствует в оперативной памяти и учитывается как принадлежащая working set / resident set, говорят о resident memory.

    Упрощённо:

    virtual page
↓
resident?
├── yes → physical page в RAM
└── no  → возможно fault при следующем access

    22. RSS¶

    На Unix-подобных системах часто смотрят RSS — Resident Set Size.

    Учебно:

    Сколько страниц процесса сейчас резидентно в физической памяти.

    Но:

    RSS
≠
Go live heap

    RSS может включать:

    • Go heap;
    • стеки;
    • runtime metadata;
    • код;
    • shared libraries;
    • file-backed mappings;
    • anonymous mappings;
    • native memory;
    • shared pages с особенностями учёта.

    Поэтому:

    HeapAlloc = 500 MiB
RSS = 1.2 GiB

    само по себе не доказывает утечку.

    23. Как Go доходит до ОС¶

    Возвращаемся к рантайму.

    mheap
↓
page allocator
↓
platform-specific memory layer
↓
OS VM subsystem

    На этом уровне Go скрывает различия платформ.

    Для аллокатора сверху идея одна:

    зарезервировать адресное пространство
сделать память пригодной для использования
сообщить, что страницы можно reclaim'нуть
полностью освободить mapping

    Ниже конкретный API зависит от ОС.

    24. Linux: mmap¶

    Один из основных механизмов Linux VM:

    mmap

    Он создаёт mapping в виртуальном адресном пространстве процесса.

    Учебно:

    process
↓
mmap
↓
virtual range

    Это может быть:

    • anonymous memory;
    • file-backed mapping;
    • shared/private mapping.

    Сам факт mapping ещё не означает, что весь диапазон уже resident.

    25. Linux: munmap¶

    munmap удаляет mapping.

    virtual range existed
↓
munmap
↓
range no longer mapped

    После этого обращение к старому адресу уже не является нормальным доступом к прежней памяти.

    Но Go scavenger не обязан каждый раз полностью сносить виртуальный диапазон только потому, что физические страницы временно не нужны.

    И здесь появляется madvise.

    26. Linux: madvise¶

    madvise позволяет сообщить ядру дополнительную информацию о диапазоне памяти.

    В контексте scavenger нас интересует идея:

    этот диапазон остаётся частью virtual layout
↓
но физическое содержимое сейчас можно считать ненужным

    В зависимости от режима и версии рантайм может использовать варианты вроде:

    MADV_FREE
MADV_DONTNEED

    У них различается точная семантика.

    Для лекции главное:

    Go может сохранить виртуальный диапазон и отдельно ослабить требования к его physical backing.

    27. MADV_DONTNEED: учебная модель¶

    Очень грубо:

    эти страницы сейчас не нужны
↓
ядро может немедленно отбросить содержимое
↓
следующий access получит заново подготовленную страницу

    Это полезно для понимания сильного reclaim-сигнала.

    Но конкретное поведение и бухгалтерия RSS зависят от ядра и режима.

    28. MADV_FREE: учебная модель¶

    Идея более ленивая:

    данные можно считать discardable
↓
пока памяти хватает, страницы могут ещё физически оставаться
↓
при pressure kernel может reclaim'нуть их

    То есть:

    Go уже не считает данные нужными

    не обязано мгновенно превратиться в:

    RSS упал прямо сейчас

    29. Linux: почему RSS после scavenger может вести себя неинтуитивно¶

    Даже если рантайм уже сообщил:

    страницы можно reclaim'нуть

    ядро управляет physical memory глобально.

    Оно учитывает:

    • pressure;
    • тип страниц;
    • текущую reclaim policy;
    • активность;
    • cgroup;
    • другие процессы.

    Поэтому:

    heap released

    и:

    RSS мгновенно уменьшился

    не являются одним событием.

    30. Windows: другая терминология, та же базовая задача¶

    На Windows очень наглядно разделяются стадии:

    reserve
commit
resident

    Это полезная модель даже для разработчика, который не пишет WinAPI.

    31. MEM_RESERVE¶

    Резервирование:

    VirtualAlloc(..., MEM_RESERVE, ...)

    Учебно означает:

    Этот диапазон виртуальных адресов закреплён за процессом.

    Но это ещё не означает, что под весь диапазон уже выделена resident RAM.

    Получаем:

    virtual address space reserved

    32. MEM_COMMIT¶

    Commit:

    VirtualAlloc(..., MEM_COMMIT, ...)

    Означает уже более сильное обязательство системы:

    Эти страницы доступны для использования процессом.

    При этом физическая RAM всё равно может материализоваться лениво при реальном доступе.

    Поэтому полезная модель:

    reserve
≠
commit
≠
resident

    33. MEM_DECOMMIT¶

    Если backing больше не нужен:

    VirtualFree(..., MEM_DECOMMIT)

    Учебно:

    данные страниц больше не нужны
↓
commit можно снять
↓
виртуальный диапазон остаётся зарезервирован

    Это очень хорошо соответствует нашей общей модели:

    virtual address сохраняется
↓
physical backing можно освободить

    34. MEM_RELEASE¶

    Полное освобождение:

    VirtualFree(..., MEM_RELEASE)

    означает уже:

    вернуть системе сам диапазон виртуальных адресов

    Итого:

    RESERVE
→ адреса принадлежат процессу

COMMIT
→ память можно использовать

DECOMMIT
→ backing освобождается,
  адреса остаются зарезервированы

RELEASE
→ освобождается и виртуальный диапазон

    35. Windows Working Set¶

    На Windows ближайший аналог привычной идеи resident memory — Working Set.

    Учебно:

    Набор страниц процесса, которые сейчас находятся в физической RAM.

    Поэтому:

    Committed memory
≠
Working Set

    Страница может оставаться committed для процесса, но временно выйти из Working Set.

    При следующем использовании она может снова стать resident.

    36. Windows Commit¶

    Commit отвечает на другой вопрос:

    Какой объём памяти система обязалась backing'овать для процессов?

    Это не то же самое, что:

    сколько страниц сейчас физически сидит в RAM

    И не то же самое, что:

    сколько виртуальных адресов зарезервировано

    Полезное разделение:

    Virtual Size
Commit
Working Set

    37. Windows Private Bytes¶

    Private Bytes используют как ещё одну диагностическую величину процесса.

    Она ближе к приватной committed memory процесса.

    Но опять:

    Private Bytes
≠
Working Set

    Одна величина про commit.

    Другая про residency.

    Их нельзя механически сравнивать как «правильную» и «неправильную память».

    38. Working Set trimming¶

    При memory pressure Windows может уменьшать working set процесса.

    страница была resident
↓
ядро решило вытеснить её из working set
↓
виртуальный mapping остаётся
↓
commit может оставаться

    Если страница снова потребуется:

    fault
↓
возврат страницы в working set

    Отсюда:

    Страница вышла из RAM — это ещё не означает, что процесс освободил адрес или снял commit.

    39. Windows pagefile¶

    Для приватной памяти системе нужен backing, когда физическая RAM недоступна.

    Одним из механизмов служит pagefile.

    Учебно:

    private committed page
↓
может перестать быть resident
↓
её содержимое должно где-то сохраниться
↓
pagefile

    Когда страница снова нужна:

    page fault
↓
pagefile I/O
↓
страница возвращается в RAM

    Это уже дорогой путь.

    40. Windows memory compression¶

    Современная Windows также умеет сжимать часть памяти.

    Идея:

    редко используемая страница
↓
compress
↓
занимает меньше RAM

    Это промежуточный механизм между:

    держать страницу полностью resident

    и:

    отправить её в pagefile

    Для backend-разработчика главное:

    Working Set может уменьшаться не только потому, что приложение само освободило объекты.

    41. macOS: снова Unix-подобная VM-модель¶

    Darwin использует familiar VM API:

    mmap
munmap
madvise

    Go на macOS работает через platform-specific слой рантайма.

    Учебная цепочка:

    mheap
↓
runtime VM layer
↓
mmap / madvise / munmap
↓
Darwin VM

    42. macOS: reusable memory¶

    Для scavenger Go на macOS важна идея reusable memory.

    Упрощённо:

    Go больше не нуждается в physical contents
↓
MADV_FREE_REUSABLE
↓
Darwin может считать страницы reclaimable

    Если диапазон снова начинает использоваться:

    MADV_FREE_REUSE

    Это ещё одна реализация общей модели:

    virtual range жив
↓
physical backing может быть отдан

    43. macOS Memory Pressure¶

    На macOS смотреть только на:

    Free Memory

    особенно вредно.

    Система активно использует RAM.

    Поэтому Activity Monitor показывает интегральный показатель:

    Memory Pressure

    Он лучше отражает:

    • доступность памяти;
    • compression;
    • swap;
    • эффективность reclaim;
    • способность системы удовлетворять новые запросы.

    44. Compressed memory в macOS¶

    Когда RAM становится тесной, macOS может сжимать менее активно используемые страницы.

    обычная resident page
↓
compress
↓
данные остаются в RAM
↓
занимают меньше места

    Плюс:

    меньше немедленного I/O

    Цена:

    CPU на compression/decompression

    То есть память снова меняется на CPU.

    45. Когда compression уже недостаточно¶

    Если pressure продолжает расти:

    RAM pressure ↑
↓
compression ↑
↓
этого недостаточно
↓
swap

    Потом страница снова нужна:

    swap I/O
↓
decompression при необходимости
↓
страница resident

    Задержка заметно выше обычного доступа к RAM.

    46. Одна задача — три ОС¶

    Сведём базовую модель:

    Задача Linux Windows macOS
    Создать виртуальный диапазон mmap MEM_RESERVE mmap
    Сделать память доступной mapping / faults MEM_COMMIT mapping / faults
    Backing больше не нужен madvise MEM_DECOMMIT MADV_FREE_REUSABLE
    Полностью убрать mapping munmap MEM_RELEASE munmap
    Resident-метрика RSS Working Set resident memory
    Pressure-механизмы reclaim / swap trimming / compression / pagefile compression / swap

    Термины разные.

    Фундаментальная задача одна:

    отделить виртуальный адрес
от физической страницы

    и уметь управлять residency.

    47. Reclaim: RAM становится мало¶

    Теперь общий вопрос для любой ОС:

    Что делать, если свободной физической памяти мало?

    Упрощённо:

    memory pressure
↓
найти страницы, которые можно reclaim'нуть

    Дальше всё зависит от типа страницы.

    48. File-backed pages reclaim'ить проще¶

    Есть чистая страница файла.

    file-backed
clean

    Её содержимое уже существует на диске.

    Значит kernel может:

    выбросить physical page из RAM

    А если страница снова понадобится:

    прочитать файл заново

    Это не бесплатно.

    Но не нужно заранее писать страницу в swap.

    49. Dirty file-backed pages¶

    Если страница файла изменена:

    dirty

    просто выбросить её нельзя.

    Сначала нужно сохранить изменения:

    writeback
↓
storage
↓
только потом reclaim

    Это уже мост к будущей лекции про page cache, dirty pages, writeback и fsync.

    Здесь глубже пока не идём.

    50. Anonymous pages reclaim'ить сложнее¶

    Anonymous page не имеет исходного файла, из которого её можно просто перечитать.

    Если её содержимое нужно сохранить:

    anonymous page
↓
swap

    или другой platform-specific backing.

    Именно поэтому anonymous memory под давлением отличается от чистого page cache.

    51. Swap¶

    Плохое упрощение:

    Swap включается только после полного исчерпания RAM.

    Реальные политики сложнее.

    ОС может заранее балансировать:

    • page cache;
    • anonymous pages;
    • активность;
    • reclaimability;
    • будущие потребности.

    Для backend нас интересует эффект:

    горячая страница ушла из RAM
↓
понадобилась снова
↓
fault
↓
storage I/O
↓
latency на порядки выше DRAM

    52. Thrashing¶

    Вот где память начинает ломать всю систему.

    Пусть:

    рабочий набор приложения
>
реально доступная RAM

    Тогда:

    страницы вытесняются
↓
через секунду снова нужны
↓
page fault
↓
возвращаем
↓
вытесняем другие
↓
они снова нужны

    Получаем thrashing.

    Система занята движением страниц вместо полезной работы.

    53. Как выглядит thrashing снаружи¶

    Можно увидеть:

    latency огромная
throughput падает
disk I/O высокий
major faults растут
swap активен
CPU ведёт себя странно

    CPU может не быть честными 100%.

    Он может просто постоянно ждать память и I/O.

    54. Cold start и first-touch¶

    Новая реплика процесса поднялась.

    Код уже запущен.

    Но:

    • page cache холодный;
    • TLB холодный;
    • data cache холодный;
    • части anonymous memory ещё не fault'ились;
    • JIT тут нет, но данные и mappings всё равно должны прогреться.

    Первые запросы могут получить:

    page faults
+
cache misses
+
disk reads

    Поэтому:

    latency после рестарта

    может отличаться от steady state.

    55. Где здесь NUMA¶

    Связываем с предыдущим допом.

    virtual page
↓
page table
↓
physical page
↓
physical page находится на NUMA node

    Page table отвечает:

    Какая physical page соответствует адресу?

    NUMA добавляет:

    Насколько эта physical page близка текущему CPU?

    То есть одна технология не заменяет другую.

    Они работают на разных уровнях.

    56. Linux-контейнер не является маленькой отдельной машиной памяти¶

    Очень полезное разрушение модели:

    В pod лимит 1 GiB, значит процесс просто видит компьютер с 1 GiB RAM.

    Нет.

    Процесс использует обычную VM-подсистему Linux.

    Но сверху cgroup ведёт учёт и накладывает отдельную границу.

    Go process
↓
Linux VM
↓
cgroup accounting
↓
memory limit

    Физически host может иметь:

    256 GiB RAM

    Но конкретному cgroup разрешён другой бюджет.

    57. Что делает cgroup¶

    Cgroup контролирует ресурсы группы процессов.

    Для памяти интересны:

    • учёт;
    • pressure;
    • reclaim;
    • ограничения;
    • события OOM.

    На уровне backend достаточно модели:

    процесс использует память
↓
kernel делает memory charge cgroup
↓
cgroup приближается к limit
↓
reclaim / pressure
↓
при жёстком нарушении возможен OOM

    58. Почему HeapAlloc < container limit ничего не гарантирует¶

    Пусть:

    HeapAlloc = 600 MiB
memory.max = 1 GiB

    Кажется, запас 400 MiB.

    Но процесс и cgroup могут учитывать ещё:

    goroutine stacks
runtime metadata
native memory
cgo
mmap
file-backed memory
page cache accounting
fragmentation
temporary bursts

    И:

    600 MiB heap

    не превращается автоматически в:

    процесс использует только 600 MiB

    59. GOMEMLIMIT и cgroup limit¶

    Связь:

    GOMEMLIMIT
→ мягкий бюджет рантайма

memory.max
→ жёсткая граница cgroup

    Рантайм Go старается управлять своей памятью вокруг soft budget.

    Но hard boundary принадлежит kernel.

    Если:

    GOMEMLIMIT = memory.max

    без запаса, любой:

    • native allocation;
    • всплеск;
    • дополнительный stack;
    • mapping;
    • фрагментация;

    может привести к жёсткому давлению.

    60. Почему нужен headroom¶

    Учебно:

    container hard limit
↓
минус запас
↓
GOMEMLIMIT

    Размер запаса нельзя дать одной универсальной константой.

    Он зависит от:

    • workload;
    • cgo;
    • количества goroutine;
    • размера стеков;
    • native libraries;
    • mmap;
    • интенсивности I/O;
    • характера burst.

    Нужны нагрузочные измерения.

    61. OOM бывает разный¶

    Полезно разделить два класса.

    Ошибка внутри процесса¶

    Рантайм не может получить необходимую память.

    allocation
↓
OS memory operation failed
↓
runtime cannot continue
↓
fatal failure

    OOM со стороны cgroup/kernel¶

    memory charge
↓
hard boundary
↓
reclaim не спас
↓
OOM handling
↓
process may be killed

    Это разные механизмы.

    62. Почему Kubernetes пишет OOMKilled¶

    Для контейнерного backend важна цепочка:

    pod/container
↓
cgroup memory limit
↓
process memory usage
↓
hard limit pressure
↓
kernel OOM handling
↓
container process killed
↓
Kubernetes sees exit reason
↓
OOMKilled

    Это не означает автоматически:

    GC не сработал.

    Причина может быть:

    • слишком большой live set;
    • native memory;
    • GOMEMLIMIT без запаса;
    • burst;
    • утечка;
    • page cache/accounting;
    • неправильный resource limit.

    63. Linux: что смотреть в /proc¶

    Для процесса:

    /proc/<pid>/status
/proc/<pid>/smaps
/proc/<pid>/smaps_rollup

    Они позволяют увидеть разные аспекты:

    • virtual size;
    • resident memory;
    • anonymous;
    • file-backed;
    • private/shared mappings;
    • детализацию mappings.

    Не нужно учить все поля.

    Нужно понимать, какой вопрос задаём.

    64. pmap¶

    pmap помогает посмотреть виртуальные mappings процесса.

    Полезный вопрос:

    Откуда вообще взялся большой виртуальный диапазон?

    Или:

    Какие mapping занимают адресное пространство?

    Это уже уровень ниже Go heap profile.

    65. vmstat¶

    Для системного pressure:

    vmstat

    Нас интересуют паттерны:

    • free memory;
    • swap in/out;
    • runnable tasks;
    • I/O;
    • faults косвенно через другие инструменты;
    • системная нагрузка.

    66. Minor и major faults в Linux¶

    На Linux можно наблюдать число faults процесса и системы.

    Полезная модель:

    minor faults много
→ часто normal VM activity

major faults растут
→ есть storage-backed misses
→ потенциально серьёзная latency

    Но один счётчик без контекста не является диагнозом.

    67. Cgroup v2: memory.current¶

    memory.current

    показывает текущее использование памяти cgroup по его правилам учёта.

    Это уже намного ближе к вопросу:

    Насколько контейнер приблизился к своему реальному kernel limit?

    чем один HeapAlloc.

    68. memory.max¶

    memory.max

    — жёсткая верхняя граница cgroup v2.

    Если:

    current → max

    система начинает жить в режиме высокого давления.

    Дальше возможны reclaim и OOM-механизмы.

    69. memory.events¶

    Очень полезная идея диагностики:

    memory.events

    позволяет увидеть, что cgroup переживал события memory pressure / limit / OOM соответствующего типа.

    То есть вместо:

    Наверное pod убило по памяти.

    можно проверить kernel accounting.

    72. Почему free RAM сама по себе почти бесполезна¶

    Плохой диагноз:

    Free = 200 MiB
↓
катастрофа

    ОС специально старается использовать свободную RAM под полезные вещи:

    • page cache;
    • файловые данные;
    • другие кеши.

    Если память легко reclaimable:

    мало free

    может быть полностью нормальным состоянием.

    Нужно смотреть pressure и reclaim behaviour.

    73. Практика 1: virtual ≠ resident¶

    Написать программу, которая получает большой буфер.

    Сначала почти не трогает страницы.

    Смотреть:

    virtual size
RSS / Working Set

    Потом пройти по буферу с шагом страницы:

    for i := 0; i < len(buf); i += 4096 {
    buf[i] = 1
}

    Снова снять метрики.

    Ожидаемая модель:

    виртуальный диапазон появился раньше
↓
resident memory выросла после first touch

    74. Практика 2: first-touch и page faults¶

    Создать большой массив.

    Первый проход:

    страницы ещё не resident
↓
faults

    Второй проход:

    страницы уже присутствуют
↓
faults меньше

    Измерить время первого и второго проходов.

    Цель:

    Увидеть цену материализации physical pages.

    77. Практика 5: memory pressure¶

    В изолированной лабораторной среде приблизить рабочий набор к доступной памяти.

    Что важно запомнить¶

    1. Процесс работает с виртуальными адресами, а не напрямую с адресами DIMM.
    2. Page table связывает virtual page с physical frame.
    3. TLB кеширует переводы адресов; TLB miss и data-cache miss — разные события.
    4. Зарезервированная виртуальная память не равна занятой физической RAM.
    5. Page fault — штатный механизм виртуальной памяти, а не обязательно ошибка.
    6. Minor fault не требует чтения с накопителя; major fault обычно требует внешнего I/O.
    7. Demand paging позволяет выдавать physical backing только при фактическом доступе.
    8. Anonymous и file-backed memory по-разному ведут себя при reclaim.
    9. Page cache использует RAM как кеш файловых данных и конкурирует за физическую память с другими потребителями.
    10. RSS показывает resident pages процесса, а не только живой Go heap.
    11. На Windows нужно разделять Virtual Size, Commit и Working Set.
    12. На macOS memory pressure может приводить сначала к compression, затем к swap.
    13. Go scavenger использует platform-specific VM API, но общая модель virtual range сохраняется → backing можно reclaim'нуть одинакова.
    14. GOMEMLIMIT — мягкий бюджет рантайма; cgroup memory.max — жёсткая граница ядра.
    15. HeapAlloc < container limit не гарантирует отсутствие OOM.
    16. Thrashing возникает, когда рабочий набор существенно превышает доступную RAM и страницы постоянно ходят между RAM и backing storage.
    17. При диагностике памяти нужно сопоставлять Go metrics, OS resident metrics и container accounting.
    18. Освобождение Go-объекта, освобождение слота, release страницы и уменьшение RSS — разные события.

    Главный инженерный вывод:

    Go управляет объектами, span и runtime pages. Физической RAM управляет ядро ОС. Между ними лежит слой виртуальной памяти: page tables, TLB, page faults, residency и reclaim. Поэтому метрика живого Go heap описывает только один слой системы. Чтобы понимать memory incident целиком, нужно уметь пройти путь от Go-объекта до физической страницы и обратно.
