    3.2. Linux memory reclaim глубже: LRU/MGLRU, swap, PSI, cgroup v2 и OOM¶

    Углублённая лекция к теме виртуальной памяти ОС.

    Конкретные структуры и эвристики reclaim зависят от версии и конфигурации ядра Linux. Отдельно различаем устойчивую модель, публичные интерфейсы Linux и детали текущей реализации.

    Зачем открывать этот слой¶

    В предыдущей лекции мы дошли до:

    Go
↓
виртуальная память
↓
physical pages
↓
resident / non-resident
↓
page fault
↓
reclaim

    Слово reclaim пока выглядело почти магически:

    RAM заканчивается — ядро что-то освобождает.

    Теперь откроем это «что-то».

    Пусть на машине:

    RAM = 32 GiB

    а workload вместе с page cache и другими потребителями хочет:

    40 GiB

    Linux должен решить:

    1. какие страницы вообще можно забрать;
    2. какие страницы, скорее всего, скоро не понадобятся;
    3. можно ли их просто выбросить;
    4. нужно ли сначала сохранить данные;
    5. есть ли swap;
    6. какой cgroup должен платить за pressure;
    7. когда reclaim ещё имеет смысл;
    8. когда уже нужен OOM killer.

    Главная цепочка:

    memory pressure
↓
reclaimable pages
↓
anonymous / file-backed
↓
LRU / MGLRU
↓
aging
↓
eviction
↓
refault feedback
↓
kswapd / direct reclaim
↓
swap / zswap
↓
PSI
↓
cgroup v2
↓
memory.high / memory.max
↓
memcg OOM
↓
OOM killer

    А продакшен-цепочка:

    working set ↑
↓
reclaim ↑
↓
application stalls ↑
↓
PSI ↑
↓
page faults / swap I/O ↑
↓
p99 ↑
↓
throughput ↓
↓
OOM risk ↑

    1. Reclaim не означает «стереть случайную страницу»¶

    RAM заполнена.

    Ядро не может выбрать любые 4 KiB и просто их забыть.

    У страницы может быть содержимое, которое нельзя потерять:

    heap процесса
dirty page файла
anonymous memory

    Поэтому сначала нужно понять, что за память перед нами.

    2. File-backed pages¶

    Страница соответствует содержимому файла:

    исполняемый файл
shared library
mmap файла
page cache

    Если страница чистая:

    clean file-backed page

    её содержимое уже есть на storage.

    Значит resident-копию можно выбросить:

    drop page from RAM
↓
если снова понадобится
↓
прочитать файл

    Это делает чистые file-backed pages хорошими кандидатами для reclaim.

    3. Dirty file-backed pages¶

    Если страница изменена:

    page cache
↓
dirty

    копия в RAM новее storage.

    Просто выбросить её нельзя.

    Нужно:

    writeback
↓
storage
↓
page clean
↓
reclaim

    Вот здесь memory pressure начинает зависеть от скорости storage.

    4. Anonymous pages¶

    Anonymous memory не имеет обычного файла, из которого её можно перечитать.

    Типичные примеры:

    heap
stack
anonymous mmap

    Если её содержимое нужно сохранить, а RAM хочется освободить:

    anonymous page
↓
swap

    Без swap пространство вариантов reclaim уже.

    5. Рабочий набор¶

    Рабочий набор (working set) — данные, которые workload реально активно использует.

    Пусть процесс имеет:

    10 GiB virtual memory

    но постоянно работает только с:

    2 GiB

    Если эти 2 GiB помещаются в RAM:

    горячие данные остаются resident

    и reclaim может выбирать холодные страницы.

    Если:

    working set > available RAM

    начинается постоянная борьба за residency.

    6. Откуда появляется идея LRU¶

    Ядро не знает будущее.

    Оно использует прошлое как эвристику:

    страницу использовали недавно
→ вероятно, скоро понадобится снова

страницу давно не использовали
→ хороший кандидат на eviction

    Отсюда семейство LRU-подходов.

    7. LRU не означает идеальную очередь всех страниц¶

    LRU — Least Recently Used.

    Наивная модель:

    самая недавно использованная
↓
...
↓
самая старая

    и вытесняем хвост.

    Но отслеживать точный порядок каждого memory access было бы слишком дорого.

    Реальный Linux использует приближённое aging и batched-структуры.

    То есть:

    LRU в ядре — эвристика давности использования, а не идеальный список каждой операции чтения.

    8. Классическая active/inactive модель¶

    Удобная традиционная схема:

    active
inactive

    Страница подтверждает активность:

    → ближе к active

    Давно не подтверждала:

    → ближе к inactive

    Reclaim чаще ищет жертв среди холодной части.

    Но две корзины довольно грубо описывают возраст.

    9. Почему двух корзин мало¶

    На большой машине полезно отличать:

    использовали секунду назад
10 секунд назад
минуту назад
давно

    Если возраст оценивается плохо:

    горячая page ошибочно evicted
↓
быстрый refault
↓
лишний fault / I/O

    Поэтому появляется более детальная generational-модель.

    10. MGLRU¶

    MGLRU — Multi-Gen LRU.

    Это альтернативная реализация LRU в Linux, оптимизирующая page reclaim под memory pressure.

    Важно:

    Доступность и включённость MGLRU зависят от ядра и конфигурации. Это не универсальная гарантия любого Linux.

    Учебная модель:

    youngest generation
↓
...
↓
oldest generation

    Недавно подтверждённо горячие страницы — моложе.

    Холодные — старше.

    Eviction начинается со старых кандидатов.

    11. Aging и eviction¶

    В MGLRU полезно разделять:

    aging

    и:

    eviction

    Aging отвечает:

    Какие страницы всё ещё горячие и к какому поколению их относить?

    Eviction:

    Какие старые страницы действительно вытеснять?

    Эти процедуры образуют feedback loop reclaim.

    12. Откуда ядро знает, что page использовалась¶

    MMU/page tables помогают отмечать обращения.

    Упрощённо:

    процесс трогал page
↓
page-table metadata отражает access
↓
aging замечает активность
↓
page остаётся молодой

    MGLRU использует page-table walks и другие механизмы для сбора этой информации.

    Точный алгоритм — implementation detail.

    13. Refault¶

    Страницу вытеснили.

    Через короткое время она понадобилась снова:

    evict
↓
fault
↓
page returns

    Это refault.

    Частые refault означают:

    Мы вытесняем данные, которые на самом деле входят в working set.

    Это один из важнейших сигналов качества reclaim.

    14. MGLRU использует feedback¶

    Текущая MGLRU-модель учитывает refault-поведение anon/file страниц и использует feedback для выбора eviction policy.

    Учебно:

    evict
↓
наблюдаем refault
↓
корректируем решение,
что лучше защищать, а что вытеснять

    Это адаптивная политика.

    15. swappiness — не процент swap¶

    Плохое упрощение:

    vm.swappiness=60 означает «использовать swap на 60%».

    Нет.

    swappiness влияет на относительную склонность reclaim выбирать anonymous memory по отношению к file-backed memory.

    Это tuning hint политики reclaim.

    Не целевой процент заполнения swap.

    16. Swap меняет пространство решений¶

    Без swap:

    anonymous page
↓
нельзя просто выбросить,
если данные ещё нужны

    Со swap:

    anonymous page
↓
записать backing в swap
↓
physical frame можно освободить

    Цена:

    swap I/O
+
future page-in latency

    17. Swap out¶

    Упрощённо:

    anonymous page resident
↓
reclaim chooses page
↓
write to swap
↓
PTE больше не указывает на resident frame
↓
RAM frame free

    Процесс продолжает жить.

    Но будущий access станет дорогим.

    18. Swap in¶

    load/store
↓
page fault
↓
page is in swap
↓
storage read
↓
physical page
↓
mapping restored
↓
instruction continues

    Это major fault.

    Для request path такой fault может быть огромным вкладом в p99.

    19. Swap не всегда зло¶

    Swap может:

    • вытеснить действительно холодную anonymous memory;
    • оставить RAM горячему working set;
    • дать системе больше времени до OOM.

    Плохо становится при:

    hot working set > RAM
↓
swap out
↓
swap in
↓
swap out
↓
swap in

    Это уже thrashing.

    20. zswap¶

    zswap — сжатый кеш для страниц, уходящих в swap.

    page going to swap
↓
compress
↓
store compressed in RAM
↓
возможно пока не писать на swap device

    Trade-off:

    CPU на compression
↔
меньше swap I/O

    Но pressure никуда не исчезает.

    21. Когда начинается reclaim¶

    У Linux есть watermarks свободной памяти.

    Для этой лекции достаточно:

    free memory комфортная
↓
обычные allocations

free memory снижается
↓
background reclaim усиливается

allocation не получает pages достаточно быстро
↓
direct reclaim

    Теперь появляется принципиально важное различие.

    22. kswapd¶

    kswapd — kernel thread фонового reclaim.

    Учебно:

    free pages опускаются ниже желаемого уровня
↓
kswapd wakes
↓
scans reclaimable memory
↓
frees pages
↓
restores reserve

    Цель:

    Делать дорогую работу заранее, чтобы прикладной поток не платил её целиком на allocation path.

    23. Direct reclaim¶

    Когда background reclaim не успевает:

    application thread
↓
allocation needs pages
↓
not enough pages
↓
direct reclaim
↓
scan / reclaim
↓
allocation continues

    Вот здесь memory pressure напрямую превращается в application latency.

    24. Direct reclaim в backend¶

    Go-handler:

    handler
↓
allocation
↓
runtime asks OS for pages
↓
kernel allocation path
↓
direct reclaim
↓
handler stalls

    Снаружи:

    обычная аллокация стала медленной

    А Go GC при этом может быть полностью здоров.

    25. Reclaim тратит несколько ресурсов¶

    Reclaim может включать:

    • LRU scanning;
    • page-table metadata;
    • dropping clean pages;
    • writeback dirty file pages;
    • swapping anonymous pages;
    • cgroup accounting.

    Поэтому memory pressure способен одновременно увеличить:

    CPU
I/O
latency

    26. Reclaim efficiency¶

    Условно:

    просканировали 1 000 000 pages
↓
освободили 5 000

    Мы потратили CPU, а memory почти не получили.

    Полезная модель:

    scan много
steal мало
↓
reclaim efficiency плохая

    27. pgscan и pgsteal¶

    В /proc/vmstat есть группы счётчиков, отражающих scanning и реально reclaimed pages.

    Точные имена зависят от ядра и контекста.

    Инженерный вопрос:

    сколько страниц мы просмотрели?
↓
сколько реально удалось забрать?

    28. Thrashing¶

    Рабочий набор больше доступной RAM:

    page A нужна
↓
page B evicted

page B нужна
↓
page C evicted

page C нужна
↓
page A evicted

    Система занята движением страниц вместо полезной работы.

    Это thrashing.

    29. Почему CPU может быть не 100%¶

    Во время thrashing задачи могут ждать:

    • memory reclaim;
    • swap I/O;
    • page faults;
    • writeback.

    Поэтому:

    CPU = 50%
p99 = ужасный

    не противоречие.

    Ограничение сейчас не арифметический CPU.

    30. PSI¶

    Нужна метрика:

    Сколько времени workload реально не может продвигаться из-за нехватки ресурса?

    Linux даёт PSI — Pressure Stall Information.

    Для memory:

    /proc/pressure/memory

    Примерный формат:

    some avg10=... avg60=... avg300=... total=...
full avg10=... avg60=... avg300=... total=...

    31. PSI some¶

    some означает:

    Хотя бы часть задач stalled из-за данного ресурса.

    Например:

    часть запросов stuck в reclaim
↓
другие всё ещё работают

    Это degradation, но система ещё продвигается.

    32. PSI full¶

    full означает:

    Все non-idle задачи одновременно stalled на ресурсе.

    Для memory это намного тяжелее:

    полезный workload почти целиком не продвигается

    Продолжительное full хорошо соответствует модели тяжёлого thrashing.

    33. Почему PSI лучше процента RAM¶

    Система A:

    RAM used = 95%
PSI ≈ 0

    Система B:

    RAM used = 75%
PSI высокий

    Вторая может быть намного хуже для SLO.

    PSI измеряет влияние дефицита ресурса на выполнение работы, а не просто заполненность.

    34. PSI windows¶

    avg10
avg60
avg300

    дают короткий, средний и длинный тренд.

    total — накопленное время stalls.

    В инциденте важна динамика и корреляция с p95/p99.

    35. PSI triggers¶

    Можно регистрировать пороги:

    за заданное окно накопилось слишком много stall time
↓
monitor получает событие

    Это позволяет реагировать на:

    workload реально страдает

    а не только на:

    memory > 90%

    36. Cgroup v2¶

    С контейнерами вопрос меняется:

    Какая группа процессов должна испытывать pressure и в каких границах?

    Memory controller cgroup v2 учитывает, среди прочего:

    • anonymous memory;
    • page cache;
    • kernel structures;
    • TCP socket buffers.

    Поэтому:

    container memory
≠
Go heap

    37. memory.current¶

    memory.current

    показывает текущее использование памяти cgroup и его потомков по правилам memory controller.

    Это одна из ключевых величин контейнера.

    38. memory.stat¶

    Разбивает usage по категориям.

    Вместо:

    контейнер использует 900 MiB

    можно спрашивать:

    сколько anon?
сколько file?
сколько slab?
сколько faults?
есть ли refaults?

    39. Working-set counters в cgroup¶

    Полезны counters вроде:

    workingset_refault_anon
workingset_refault_file
workingset_activate_anon
workingset_activate_file

    Их смысл:

    reclaim'нули
↓
данные быстро вернулись?

    Это помогает увидеть pressure на working set.

    40. Fault counters¶

    В memory.stat полезны:

    pgfault
pgmajfault

    Связка:

    pgmajfault ↑
+
storage/swap I/O ↑
+
p99 ↑

    уже содержательная гипотеза.

    41. memory.min¶

    memory.min — жёсткая reclaim protection внутри effective boundary.

    Учебно:

    usage <= effective memory.min
↓
обычный reclaim эту память не трогает

    Если unprotected reclaimable memory больше нет:

    OOM может наступить раньше

    То есть protection тоже является ограниченным ресурсом.

    42. memory.low¶

    memory.low — best-effort protection.

    Если cgroup укладывается в effective low:

    ядро старается не reclaim'ить его память,
пока есть менее защищённые кандидаты

    Но это не абсолютная гарантия.

    При сильном pressure low-protected memory тоже может попасть под reclaim.

    43. memory.min и memory.low не резервируют DIMM¶

    Плохая модель:

    memory.low=1G означает, что ядро заранее отложило 1 GiB физической RAM именно этому контейнеру.

    Нет.

    Это политика выбора жертв reclaim.

    Она влияет на:

    кого трогать раньше
кого защищать дольше

    Но это не отдельный физический банк памяти.

    44. memory.high¶

    memory.high — граница, после которой workload начинает платить тяжёлый reclaim/throttling.

    memory.current > memory.high
↓
processes throttled
↓
direct reclaim / heavy pressure

    И принципиальный момент:

    Превышение memory.high само по себе не запускает OOM killer.

    Это слой контролируемой деградации до hard limit.

    45. Почему memory.high особенно интересен backend-инженеру¶

    Пусть:

    memory.high = 900 MiB
memory.max  = 1 GiB

    Сервис вышел за high:

    процесс жив
↓
requests начинают платить reclaim cost
↓
p99 растёт
↓
throughput падает

    При этом:

    OOMKilled = 0

    То есть контейнер может быть серьёзно деградирован задолго до OOM.

    46. memory.max¶

    memory.max — жёсткая граница memory controller.

    Если cgroup достиг max и reclaim не может вернуть использование вниз:

    OOM path
↓
OOM killer может быть invoked внутри cgroup

    Это уже containment.

    Учебная формула:

    memory.high
→ throttle / reclaim

memory.max
→ hard limit / possible OOM

    47. Почему первый байт выше memory.max не обязательно мгновенно убивает процесс¶

    Перед OOM ядро пытается вернуть память.

    Упрощённо:

    new charge
↓
usage около max
↓
memcg reclaim
↓
достаточно progress?
├── да → allocation продолжается
└── нет → OOM state

    Поэтому перед kill обычно уже есть признаки pressure.

    48. memory.events¶

    Очень полезный файл для расследования.

    Содержит counters вроде:

    low
high
max
oom
oom_kill
oom_group_kill

    Интерпретация:

    high растёт
→ cgroup регулярно throttled/reclaimed из-за high

max растёт
→ workload постоянно упирается в hard boundary

oom растёт
→ allocation доходила до OOM state

oom_kill растёт
→ OOM killer реально убивал процессы

    49. memory.events.local¶

    Обычный memory.events может учитывать события потомков по иерархии.

    memory.events.local нужен, когда требуется:

    события именно текущего cgroup

    Это важно на сложных деревьях cgroup.

    50. memory.reclaim¶

    Cgroup v2 позволяет запросить proactive reclaim:

    echo "1G" > memory.reclaim

    Смысл:

    попросить kernel попытаться reclaim'ить память target cgroup

    Но важно:

    • ядро может reclaim'ить больше или меньше;
    • это не полный эквивалент естественного pressure;
    • подсистемы могут реагировать иначе, чем на реальный shortage.

    Это диагностический и управляющий инструмент.

    Не точный симулятор OOM.

    51. memory.swap.current¶

    Показывает swap usage текущего cgroup и потомков.

    Полезно смотреть вместе:

    anon
swap.current
pgmajfault
memory.pressure

    Одна цифра swap usage не говорит, страдает ли workload прямо сейчас.

    52. memory.swap.max¶

    memory.swap.max ограничивает swap usage cgroup.

    Если лимит достигнут:

    дальнейший swap-out anonymous memory ограничен

    Значит у reclaim меньше вариантов.

    При большом anon working set это может приблизить memcg OOM.

    53. memory.swap.max=0 — не магическая оптимизация¶

    Плюс:

    нет swap-out для cgroup
↓
меньше риска огромной page-in latency

    Минус:

    cold anonymous pages нельзя убрать в swap
↓
меньше reclaim options
↓
OOM может наступить раньше

    Это trade-off.

    Не универсальная рекомендация.

    54. memory.pressure¶

    Cgroup v2 экспортирует PSI именно для конкретной группы:

    memory.pressure

    Это очень сильная метрика.

    Она отвечает:

    Сколько времени workload внутри cgroup реально stalled из-за memory pressure?

    55. memory.high + PSI¶

    Если:

    memory.current ≈ memory.high

    и одновременно:

    PSI some ↑

    значит reclaim уже влияет на выполнение задач.

    Если:

    PSI full ↑

    система ближе к тяжёлому pressure/thrashing режиму.

    56. Memory usage и memory pressure — разные вещи¶

    Два контейнера:

    A:
current = 900 MiB / 1 GiB
PSI ≈ 0

B:
current = 700 MiB / 1 GiB
PSI высокий

    По percentage used хуже выглядит A.

    По реальному влиянию на workload — B.

    Это важная инженерная мысль:

    Memory — stateful resource. Процент использования не описывает состояние системы целиком.

    57. OOM — это не «в машине осталось 0 байт»¶

    Более точная модель:

    Ядро не смогло удовлетворить конкретную allocation в конкретных constraints после доступных reclaim-механизмов.

    Constraints могут включать:

    • global memory;
    • NUMA;
    • cpuset;
    • memcg;
    • allocation type.

    Поэтому OOM всегда имеет контекст.

    58. Global OOM¶

    Система в целом не может удовлетворить allocation.

    Reclaim не спасает.

    Тогда возможен global OOM killer.

    Его задача:

    убить victim
↓
освободить память
↓
вернуть системе progress

    Это recovery mechanism.

    59. Memcg OOM¶

    Cgroup достиг:

    memory.max

    Host при этом может иметь много свободной RAM.

    Но isolation говорит:

    этому workload больше памяти нельзя

    Если reclaim внутри cgroup не спас:

    memcg OOM

    Victim выбирается внутри cgroup.

    60. Почему pod может OOMKill'нуться на свободной node¶

    Например:

    node free = 40 GiB

container memory.max = 1 GiB
container usage ≈ 1 GiB

    Контейнер просит ещё.

    Для host:

    проблемы нет

    Для memcg:

    hard boundary reached

    Результат:

    memcg OOM
↓
process killed
↓
container runtime sees death
↓
Kubernetes reports OOMKilled

    61. OOM score¶

    Для процессов Linux предоставляет:

    /proc/<pid>/oom_score
/proc/<pid>/oom_score_adj

    oom_score_adj позволяет сдвигать вероятность выбора процесса.

    Но это не способ отменить физику:

    защитили один process
↓
memory shortage никуда не исчез
↓
kernel выберет другого victim

    62. memory.oom.group¶

    Если workload состоит из нескольких процессов, убийство только одного может оставить систему полуживой.

    Cgroup v2 позволяет:

    memory.oom.group = 1

    Учебная идея:

    cgroup рассматривается как единый workload
↓
OOM kill применяется к группе целиком или не применяется

    Это механизм сохранения целостности workload.

    63. OOM killer не определяет «виноватого»¶

    OOM killer не проводит архитектурный postmortem.

    Он решает задачу:

    Как освободить память и вернуть progress системе?

    Victim selection — survival heuristic.

    Причину инцидента всё равно нужно расследовать отдельно.

    64. Kubernetes и cgroup v2¶

    Полезно разделять уровни:

    Kubernetes resource policy
↓
kubelet / container runtime
↓
cgroup v2
↓
Linux memory controller

    Не нужно механически считать, что любое поле Kubernetes один-в-один означает все интерфейсы cgroup.

    Но hard memory limit контейнера в итоге реализуется через kernel memory control.

    65. Timeline до OOMKilled¶

    t0  memory.current растёт

t1  background reclaim активнее

t2  PSI some растёт

t3  direct reclaim появляется в allocation path

t4  refault / swap / writeback растут

t5  p99 растёт

t6  memory.events high может расти

t7  usage подходит к max

    Если мониторить только OOMKilled, мы узнаём об инциденте последними.

    67. Сценарий: Go heap маленький, cgroup почти полный¶

    Например:

    Go live heap = 400 MiB

    • page cache;
    • native allocations;
    • mmap;
    • stacks;
    • socket buffers;
    • slab;
    • shared/file memory.

    Вывод:

    Heap profile — не профиль всей memory charge контейнера.

    68. Сценарий: Go GC нормальный, p99 растёт¶

    GC CPU = 5%
STW короткая
heap стабилен

    Но:

    memory PSI ↑
direct reclaim ↑
major faults ↑

    Причина:

    kernel reclaim

    А не Go GC.

    69. Два feedback loop¶

    У Go:

    allocation pressure
↓
GC
↓
assist

    У Linux:

    resident pressure
↓
reclaim
↓
fault / swap / stall

    Они могут работать одновременно.

    И усиливать друг друга.

    70. Слишком маленький GOMEMLIMIT¶

    GOMEMLIMIT ↓
↓
Go GC чаще
↓
assist CPU ↑
↓
application CPU ↓
↓
latency ↑

    Linux PSI при этом может быть низким.

    То есть сервис тормозит на уровне рантайма Go.

    71. Слишком высокий GOMEMLIMIT¶

    GOMEMLIMIT близок к memory.max
↓
heap получает почти весь budget
↓
headroom для остальных категорий мал
↓
memcg reclaim
↓
PSI ↑
↓
OOM risk ↑

    Мы уменьшили GC CPU.

    Но купили больше kernel reclaim.

    72. Go scavenger и Linux reclaim — не одно и то же¶

    Go scavenger:

    runtime уже знает:
эти heap pages ему не нужны
↓
сообщает ОС

    Linux reclaim:

    kernel испытывает memory pressure
↓
сам ищет reclaimable pages

    Первое — инициатива Go memory manager.

    Второе — системная политика ядра.

    73. Здоровый reclaim¶

    Пример:

    pressure немного вырос
↓

↓
нашёл cold clean file pages
↓
освободил memory
↓
hot working set остался resident
↓
PSI почти нулевой
↓

    Это нормальная работа VM.

    90. Плохой вывод: «page cache украл память»¶

    Linux использует свободную RAM под page cache намеренно.

    При pressure clean file cache обычно хороший reclaim candidate.

    Проблема появляется, когда:

    • страницы постоянно refault;
    • dirty cache требует writeback;
    • protections ограничивают выбор;
    • anon working set слишком велик.

    Большой page cache сам по себе нормален.

    91. Плохой вывод: «swap used > 0 — сервер умирает»¶

    Холодные pages могли давно уйти в swap и больше не использоваться.

    Нужны:

    swap-in/out rate
major faults
PSI
latency

    А не один SwapUsed.

    92. Плохой вывод: «PSI some > 0 — авария»¶

    Короткие небольшие stalls возможны.

    Смотрим:

    • величину;
    • длительность;
    • тренд;
    • связь с SLO.

    full намного тяжелее, потому что отражает одновременный stall всех non-idle задач.

    93. Плохой вывод: «MGLRU решает нехватку RAM»¶

    Пусть:

    working set = 64 GiB
available RAM = 16 GiB

    Более умный eviction не создаст ещё 48 GiB.

    MGLRU может уменьшить лишние refaults и overhead.

    Физический capacity limit остаётся.

    94. Плохой вывод: «OOM killer выбирает виноватого»¶

    OOM killer выбирает victim ради освобождения памяти и progress.

    Это survival-механизм.

    Архитектурную причину инцидента всё равно ищет инженер.

    105. Что является implementation detail¶

    К этому относятся:

    • точные структуры MGLRU;
    • число generations;
    • конкретные aging heuristics;
    • scan budgets;
    • внутренние watermarks;
    • точная OOM badness heuristic;
    • набор некоторых vmstat counters конкретной версии.

    Их нужно понимать, но не превращать в вечный контракт.

    Что важно запомнить¶

    1. Reclaim ищет страницы, которые можно освободить с минимальным ущербом working set.
    2. Clean file-backed page можно drop'нуть и перечитать; anonymous memory обычно требует swap, если содержимое нужно сохранить.
    3. LRU — приближённая модель давности, а не идеальный список каждого access.
    4. MGLRU использует несколько поколений и refault feedback, чтобы лучше отделять hot pages от cold pages.
    5. Working set важнее общего virtual size процесса.
    6. Refault показывает, что недавно evicted данные снова понадобились.
    7. kswapd делает background reclaim; direct reclaim заставляет прикладной поток самому платить за shortage памяти.
    8. Direct reclaim способен ухудшать backend latency при полностью нормальном Go GC.
    9. Swap расширяет reclaim options для anonymous memory, но page-in создаёт дорогие major faults.
    10. Swap usage сам по себе не диагноз; важны swap I/O, major faults, PSI и latency.
    11. PSI измеряет время, потерянное workload из-за pressure. some означает stall части задач, full — одновременный stall всего non-idle workload.
    12. memory.current показывает usage cgroup, а memory.stat объясняет его состав.
    13. memory.min — hard reclaim protection, memory.low — best-effort protection.
    14. memory.high создаёт throttling/reclaim pressure и не должен сам по себе запускать OOM killer.
    15. memory.max — hard cgroup limit; если reclaim не спасает, возможен memcg OOM.
    16. memory.events позволяет увидеть high/max/OOM до и после аварии.
    17. memory.swap.max меняет доступные reclaim strategies для anonymous memory.
    18. Memcg OOM может произойти даже при большом запасе RAM на host.
    19. OOM killer восстанавливает progress системы, а не определяет «виноватый» процесс.
    20. Go GC pressure и Linux reclaim pressure — разные слои, которые могут усиливать друг друга.
    21. Для memory incident нужно вместе смотреть Go metrics, cgroup accounting, PSI, faults, reclaim и backend latency.
    22. OOMKilled — последний симптом цепочки; degradation часто начинается намного раньше.

    Главный инженерный вывод:

    Linux memory reclaim — не аварийная кнопка, которая включается за секунду до OOM. Это постоянно работающая система управления working set. Backend начинает платить за shortage RAM тогда, когда его потоки входят в direct reclaim, страницы refault'ятся и PSI растёт. OOM killer появляется уже в конце цепочки, когда доступные способы вернуть memory progress перестали работать.
