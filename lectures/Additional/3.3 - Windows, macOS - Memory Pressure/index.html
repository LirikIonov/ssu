    3.3. Управление памятью Windows и macOS глубже: Working Set, Commit, сжатие и swap¶

    Сравнительная углублённая лекция после лекции об освобождении памяти Linux.

    Цель — понять, как две другие массовые настольные и серверные платформы решают ту же базовую задачу:

    виртуальная память
↓
физическая RAM
↓
давление на память
↓
сокращение рабочего набора / освобождение памяти
↓
сжатие / pagefile / swap
↓
страничная ошибка
↓
задержка приложения

    Конкретные внутренние структуры и эвристики зависят от версии ОС. В лекции отдельно отмечаем устойчивую модель и детали, зависящие от платформы.

    Зачем эта лекция после Linux¶

    После Linux легко закрепить слишком узкую модель:

    давление на память
↓
LRU / MGLRU
↓
освобождение памяти
↓
swap
↓
cgroup

    Но это модель Linux.

    Windows и macOS решают ту же физическую проблему:

    RAM конечна, а процессов и виртуальной памяти больше.

    Но называют сущности иначе и используют другие механизмы управления резидентностью.

    Главная сравнительная карта:

                        ОБЩАЯ ПРОБЛЕМА

виртуальное адресное пространство
        ↓
физические страницы
        ↓
рабочий / резидентный набор
        ↓
давление на память
        ↓
что можно вытеснить из RAM?
        │
        ├── Windows
        │   сокращение Working Set
        │   состояния Transition / Standby
        │   сжатие памяти
        │   pagefile
        │
        └── macOS
            резидентная / wired / очищаемая память
            сжатие
            swap
            Memory Pressure

    Нам важно научиться видеть общую физику за разными терминами.

    0. Что у всех ОС одинаково¶

    Во всех трёх системах процесс работает с:

    виртуальные адреса

    А физическая RAM управляется ядром.

    Поэтому:

    виртуальный адрес существует
≠
физическая страница резидентна

    И:

    процесс выделил память
≠
вся она сейчас находится в RAM

    Это фундаментальная модель и для Linux, и для Windows, и для macOS.

    1. Что меняется между ОС¶

    Различаются:

    • термины;
    • учёт;
    • политика освобождения памяти;
    • сжатие;
    • семантика swap/pagefile;
    • инструменты диагностики;
    • лимиты процессов/контейнеров;
    • пользовательские метрики.

    Но вопрос ядра везде один:

    Какие данные должны остаться в дорогой быстрой RAM прямо сейчас?

    2. Windows: три разных понятия, которые нельзя смешивать¶

    Для Windows нужно разделить минимум:

    виртуальное адресное пространство (Virtual Address Space)
Commit
Working Set

    Это три разных уровня.

    Наивная модель:

    процесс выделил 2 GiB
↓
он использует 2 GiB RAM

    может быть полностью неправильной.

    3. виртуальное адресное пространство (Virtual Address Space)¶

    Процесс имеет собственное виртуальное адресное пространство.

    В нём можно:

    зарезервировать диапазон адресов

    не выделяя под него сразу физическую память.

    Это очень хорошо видно через WinAPI:

    VirtualAlloc

    с флагом:

    MEM_RESERVE

    4. MEM_RESERVE¶

    Учебная модель:

    VirtualAlloc(..., MEM_RESERVE, ...)
↓
диапазон виртуальных адресов закреплён за процессом

    Но:

    физическая RAM ещё не обязана быть выделена
обеспечение через pagefile ещё не обязано быть выделено

    То есть:

    резервирование
=
владение адресным диапазоном

    5. MEM_COMMIT¶

    Теперь процесс хочет память, которую действительно можно использовать.

    MEM_COMMIT

    Учебно:

    Система берёт обязательство обеспечить обеспечение памяти для этих страниц.

    Backing обеспечивается комбинацией:

    RAM
+
ёмкость pagefile

    При этом реальная физическая страница может появиться лениво при первом обращении.

    Значит:

    commit
≠
резидентная

    6. Объём Commit¶

    Windows должна знать:

    Сколько приватной памяти система уже пообещала обеспечение памяти'овать?

    Отсюда понятие объём Commit (commit charge).

    Упрощённо:

    процесс коммитит страницы
↓
общий системный Commit ↑

    Commit — не текущая занятость RAM.

    Это обязательство системы обеспечить обеспечение памяти.

    7. Лимит Commit¶

    Commit не может расти бесконечно.

    Система имеет лимит Commit.

    Учебно:

    доступная ёмкость для обеспечения памяти
≈
RAM
+
ёмкость pagefile
-
служебные ограничения

    Не нужно воспринимать формулу как точный арифметический контракт.

    Главная идея:

    Pagefile увеличивает не только возможность выгрузки страницы, но и общий бюджет Commit системы.

    8. Почему можно получить ошибку выделения памяти при ещё свободной RAM¶

    Плохая модель:

    Если есть свободная RAM, VirtualAlloc(MEM_COMMIT) всегда должен сработать.

    Нет.

    Можно упереться в:

    лимит Commit

    даже если картина свободная физическая RAM не выглядит катастрофической.

    Windows должна гарантировать обеспечение памяти, учтённой в Commit.

    9. Working Set¶

    Working Set процесса — страницы его виртуального адресного пространства, которые сейчас резидентны в физической RAM.

    виртуальные страницы
↓
подмножество, которое сейчас резидентно
↓
Working Set

    То есть:

    Working Set
=
резидентный набор процесса

    10. Commit и Working Set — разные оси¶

    Пример:

    Process A
Commit = 4 GiB
Working Set = 800 MiB

    Это возможно.

    Процесс имеет обязательство обеспечение памяти на 4 GiB.

    Но прямо сейчас только 800 MiB его вытесняемая память резидентная.

    Другой пример:

    Commit = 1 GiB
Working Set = 900 MiB

    Совсем другой профиль резидентность.

    11. Почему Working Set постоянно меняется¶

    Working Set не является «объёмом памяти процесса навсегда».

    Страницы входят в него:

    страничная ошибка обработана
↓
страница становится резидентной
↓
добавляется в Working Set

    И выходят:

    давление на память
↓
сокращение Working Set
↓
страница удаляется

    Это динамическая структура.

    12. Мягкая страничная ошибка¶

    Процесс обращается к странице, которой сейчас нет в его Working Set.

    Но данные уже находятся в RAM.

    Например страница:

    • в Working Set другого процесса;
    • в состоянии Transition;
    • была заранее подгружена;
    • ленивое выделение нулевой страницы может быть удовлетворена без чтения хранилище обеспечения.

    Тогда fault можно разрешить без реального чтения с диска.

    Это мягкая страничная ошибка.

    13. Жёсткая страничная ошибка¶

    Страница отсутствует в RAM.

    Нужно читать хранилище обеспечения:

    pagefile

    или:

    файл, отображённый в память

    Это жёсткая страничная ошибка.

    Цена намного выше:

    ввод-вывод накопителя
↓
задержка

    14. Почему счётчик Page Faults/sec легко неправильно читать¶

    Много страничные ошибки:

    не обязательно много дисковый ввод-вывод

    Потому что большая часть может быть мягкие страничные ошибки.

    Для инцидента производительности важнее отделять:

    мягкие страничные ошибки

    от:

    больших страничных ошибок / чтение страниц

    И смотреть реальные storage-события.

    15. Сокращение Working Set¶

    RAM становится нужна другим потребителям.

    менеджер памяти Windows может уменьшать Working Set процессов:

    Working Set процесса
↓
вытеснить менее ценные страницы
↓
получить больше доступной физической памяти

    Страница перестаёт быть резидентная у процесса.

    Но это не означает автоматически:

    виртуальный адрес освобождён
Commit освобождён

    16. Страница после сокращение рабочего набора не обязана сразу попасть на диск¶

    Очень важный момент.

    Страница может покинуть Working Set, но остаться в RAM в состоянии, подобном Transition/Standby.

    Учебно:

    в Working Set
↓
сокращение рабочего набора
↓
не в Working Set процесса
↓
всё ещё физически кешируется в RAM

    Если процесс быстро обратится снова:

    малая страничная ошибка
↓
страница возвращается в Working Set

    Без ввод-вывод накопителя.

    17. Почему это полезно¶

    Если любую вытесненную страницу мгновенно писать на storage или полностью уничтожать:

    короткий всплеск давления
↓
огромный объём ввода-вывода
↓
через миллисекунды данные снова нужны

    Это было бы очень дорого.

    Поэтому Windows имеет промежуточные состояния физических страниц.

    18. Модель состояния Standby¶

    Для учебной модели полезно представить:

    Working Set
↓
сокращение рабочего набора
↓
кеш в состояниях Standby / Transition
↓
страница всё ещё в RAM

    Пока memory не перепрофилировали под другую задачу, данные можно вернуть быстро.

    Точные внутренние списки страниц — реализация Windows.

    Не пользовательский API.

    19. Изменённая страница¶

    Если физическая страница изменена:

    dirty

    и её обеспечение памяти должен сохраняться, просто repurpose её нельзя.

    Нужно:

    записать в хранилище обеспечения
↓
страницу можно использовать повторно

    В зависимости от типа страницы обеспечение памяти может быть:

    pagefile
файл, отображённый в память
файловое обеспечение

    20. Pagefile¶

    Pagefile — хранилище обеспечения для части приватной виртуальной памяти, учтённой в Commit.

    Учебно:

    приватная committed-страница
↓
недостаточно ценна, чтобы оставаться резидентной
↓
содержимое страницы можно записать в pagefile
↓
физическую страницу можно переиспользовать

    Позже:

    процесс обращается к странице
↓
большая страничная ошибка
↓
чтение из pagefile
↓
Working Set

    21. Pagefile не равен «дополнительная медленная RAM»¶

    Так говорить слишком просто.

    Pagefile выполняет несколько ролей в общей модели Commit и подкачки Windows.

    Но по performance полезна цепочка:

    горячая страница покинула RAM
↓
pagefile обеспечение памяти
↓
снова нужна
↓
большая страничная ошибка
↓
задержке накопителя

    22. Почему pagefile может быть полезен даже при большой RAM¶

    Без pagefile бюджет Commit и варианты управления приватной памятью могут быть меньше.

    Холодные приватные страницы нельзя так же гибко вынести из RAM.

    Поэтому:

    pagefile существует

    не равно:

    система обязательно активно трэшит

    Нужно смотреть реальную активность подкачки.

    23. Приоритет памяти (Memory Priority)¶

    Windows умеет учитывать приоритет памяти процесса/потока как подсказка.

    Идея:

    страницы с низким приоритетом
↓
при прочих равных вытесняются раньше

    Это позволяет приложению сообщить:

    Эти данные фоновой нагрузки менее ценны для резидентность.

    Важно:

    это подсказка.

    Не абсолютная гарантия.

    24. Почему приоритет памяти логична¶

    Два массива:

    A — горячий кеш запросов
B — фоновое сканирование файлового индекса

    Если давление одинаково вытесняет их случайно:

    горячий кеш может пострадать

    Приоритет памяти (Memory Priority) позволяет дать ядру дополнительную информацию о ценности страниц.

    25. Системный файловый кеш Windows¶

    Windows кеширует файловые данные в памяти.

    Учебно:

    чтение файла
↓
Cache Manager
↓
системный файловый кеш
├── попадание → RAM
└── промах → накопитель

    Записи также могут идти через кеширование отложенной записи.

    То есть физическая RAM Windows используется не только Working Set'ами обычных приложений.

    26. Большой системный кеш сам по себе не означает утечку¶

    Свободная RAM предназначена для использования.

    Файловый кеш может быть полезной памятью.

    При давлении на память часть её данных может уйти из RAM.

    Проблема начинается, когда поведение кеша вытесняет более полезный рабочий набор и создаёт страничные ошибки/ввод-вывод.

    27. Сжатие памяти Windows¶

    Современная Windows умеет сжимать часть памяти.

    Идея:

    страница холодная
↓
вместо немедленного выгрузки страницы
↓
сжимать
↓
оставить данные в RAM в меньшем объёме

    Это уменьшает число больших страничных ошибок по сравнению с немедленным уходом на диск.

    28. Цена сжатие памяти¶

    Сжатие экономит RAM.

    Но требует:

    CPU

    А при повторном использовании:

    распаковку

    Получаем компромисс:

    меньше ввод-вывод накопителя
↔
больше CPU

    29. Сжатие не отменяет pagefile¶

    Если давление продолжает расти:

    сжатие insufficient
↓
активность подкачки / pagefile

    Сжатие — промежуточный механизм.

    Не бесконечная дополнительная память.

    30. Цепочка давления на память Windows¶

    Упрощённо:

    потребность в RAM ↑
↓
доступные страницы ↓
↓
сокращение Working Set ↑
↓
мягкие страничные ошибки ↑
↓
сжатие ↑
↓
если давление ещё растёт
↓
pagefile / больших страничных ошибок ↑
↓
задержка приложения ↑

    Конкретная последовательность не является строгой машина состояний.

    Это инженерная модель возможных механизмов.

    31. Когда начинается трэшинг на Windows¶

    Рабочий набор всех активных приложений значительно больше доступной физическая память.

    Получаем:

    сокращение рабочего набора
↓
страница снова нужна
↓
fault
↓
вытеснить другую страницу
↓
fault

    Если хранилище обеспечения постоянно участвует:

    больших страничных ошибок
↓
дисковый ввод-вывод
↓
пропускная способность рушится

    32. Давление Commit и давление на физическую память — разные проблемы¶

    Можно упереться в:

    Commit Limit

    или:

    давление на физическую память

    Это не одно и то же.

    Давление Commit:

    система пообещала слишком много обеспеченной памяти

    Давление на физическую память:

    слишком большой активный резидентный рабочий набор

    Диагностика должна сначала понять, какой сценарий происходит.

    33. Windows Job Objects: аналог границы ресурсов¶

    Для группы процессов Windows предоставляет Job Objects.

    Можно ограничивать:

    committed-память процесса
память всего Job, учтённая в Commit

    То есть:

    процесс/Job пытается превысить лимит Commit
↓
Commit завершается ошибкой

    Это не прямая копия Linux cgroup.

    Но архитектурная роль похожа:

    Ограничить ресурсы группы процессов.

    34. Почему лимит памяти Job Object — это лимит Commit, а не лимит Working Set¶

    Важно не перепутать.

    Лимит памяти Job относится к:

    памяти, учтённой в Commit

    То есть ограничение формулируется вокруг обязательства обеспечение памяти.

    Это другая ось, чем:

    сколько сейчас резидентная в RAM

    35. Память контейнеров Windows: ментальная модель¶

    Windows-контейнеры в конечном счёте тоже используют механизмы управления ресурсами Windows.

    Для курса достаточно:

    контейнер / группа процессов
↓
лимиты Job/ресурсов
↓
учёт Commit/ресурсов
↓
менеджер памяти Windows

    Не нужно притягивать Linux cgroup-термины один в один.

    36. Рантайм Go на Windows¶

    Текущий рантайм Go использует Windows VM API напрямую.

    Упрощённо:

    sysReserveOS
↓
VirtualAlloc(MEM_RESERVE)

sysAllocOS
↓
VirtualAlloc(MEM_RESERVE | MEM_COMMIT)

sysUnusedOS
↓
VirtualFree(MEM_DECOMMIT)

sysUsedOS
↓
VirtualAlloc(MEM_COMMIT)

sysFreeOS
↓
VirtualFree(MEM_RELEASE)

    Это очень наглядно связывает Scavenger Go с Windows VM.

    37. Что означает MEM_DECOMMIT для Scavenger Go¶

    Go решил:

    эти страницы хипа сейчас не нужны

    На Windows:

    VirtualFree(..., MEM_DECOMMIT)

    может снять обязательство обеспечить память с диапазона.

    При этом:

    зарезервированный виртуальный диапазон может сохраниться

    Если память понадобится снова:

    VirtualAlloc(..., MEM_COMMIT)

    38. Почему путь рантайма Windows хорошо объясняет общую модель¶

    Получаем почти идеальную схему:

    RESERVE
→ адресное пространство

COMMIT
→ обязательство обеспечить память

резидентная
→ Working Set

DECOMMIT
→ обеспечение памяти больше не нужен

RELEASE
→ адресный диапазон возвращён

    Это четыре разных состояния/уровня.

    39. Диагностика Windows: Task Manager¶

    Диспетчер задач полезен для первого взгляда.

    Но нельзя останавливаться на одной колонке Memory.

    Нас интересуют разные вопросы:

    Working Set?
Commit?
приватная память?
системный Commit?
доступная RAM?
активность подкачки?

    40. Performance Monitor¶

    Для серьёзной диагностики Windows нужен PerfMon.

    Полезные идеи:

    Memory\Committed Bytes
Memory\Commit Limit
Process\Working Set
Process\Private Bytes
Memory\Pages Input/sec
Memory\Pages Output/sec

    Конкретный набор зависит от вопроса.

    41. Committed Bytes¶

    Отвечает на вопрос:

    Какой потребность в Commit сейчас существует в системе?

    Сравниваем с:

    Commit Limit

    Если Commit близок к лимиту:

    давление Commit

    42. Working Set¶

    Отвечает:

    Сколько вытесняемая память процесса сейчас резидентная?

    Это моментальный снимок.

    Под давлением на память ОС может сокращать Working Set.

    Поэтому одно и то же приложение на машине с 64 GiB и 16 GiB RAM может показывать разные Working Set.

    43. Private Bytes¶

    Используется как мера приватной памяти процесса, учтённой в Commit.

    Это не equivalent:

    использование RAM

    И не equivalent:

    Working Set

    Если Private Bytes стабильно растёт, это повод расследовать приватный Commit/удержание.

    44. Pages Input/sec и Pages Output/sec¶

    Для инцидента подкачки нужно смотреть реальное движение страниц.

    Pages Output/sec полезен, когда подозреваем:

    система выталкивает приватная pages ради освобождения RAM

    Но один счётчик всегда читаем вместе с:

    • задержка диска;
    • Working Set;
    • доступная память;
    • больших страничных ошибок;
    • задержка приложения.

    45. RAMMap¶

    Sysinternals RAMMap показывает физическую память по типам.

    Полезные вопросы:

    сколько файловый кеш?
сколько Working Set процессов?
какие списки страниц?
что занимает физическая RAM?

    Это хороший инструмент, когда:

    Task Manager говорит «RAM занята»

    а непонятно чем.

    46. VMMap и Process Explorer¶

    Для конкретного процесса полезны инструменты Sysinternals:

    VMMap
Process Explorer

    Они помогают отделять:

    • зарезервировано;
    • учтённую в Commit;
    • приватная;
    • отображённая;
    • образ;
    • рабочий набор.

    То есть диагностировать именно виртуальную структуру процесса.

    47. WPR/WPA и набор обращавшихся страниц (reference set)¶

    Working Set зависит от текущего давления на память и сокращения Working Set.

    Для сценарного исследования Microsoft предлагает понятие набора обращавшихся страниц (reference set) через Windows Performance Recorder/Analyzer.

    Идея:

    какие страницы нагрузка реально трогал во время сценария?

    Это лучше отвечает на вопрос реального объёма памяти, к которому обращалась нагрузка, чем один моментальный Working Set.

    48. Windows: симптом → гипотеза¶

    Сценарий:

    Private Bytes стабильны
Working Set уменьшается
мягкие страничные ошибки растут

    Гипотеза:

    сокращение Working Set

    Данные всё ещё принадлежат процессу.

    Но резидентность уменьшается.

    49. Windows: другой сценарий¶

    Committed Bytes → Commit Limit
↓
ошибки Commit в `VirtualAlloc`

    Это исчерпание Commit.

    Добавить RAM может помочь.

    Увеличить pagefile тоже может изменить ёмкость Commit.

    Это другой механизм, чем трэшинг Working Set.

    50. Windows: сильное давление на память¶

    сокращение Working Set ↑
↓
сжатая память ↑
↓
активность pagefile ↑
↓
больших страничных ошибок ↑
↓
задержка диска ↑
↓
задержка запросов ↑

    Бэкенд может тормозить при полностью нормальном Go GC.

    51. Windows: что важно запомнить перед macOS¶

    1. Reserve, Commit и Resident — разные уровни.
    2. Working Set показывает резидентные вытесняемые страницы процесса.
    3. Commit показывает обязательство обеспечить память.
    4. Сокращение Working Set не освобождает виртуальный адрес и не обязательно снимает Commit.
    5. Вытесненная страница может остаться в RAM и вернуться через малая страничная ошибка.
    6. Большая страничная ошибка требует ввод-вывод хранилища обеспечения.
    7. Сжатие меняет RAM на CPU и уменьшает часть давление жёстких страничных ошибок.
    8. Pagefile участвует в commit/модели подкачки.
    9. Job Object limits могут ограничивать памяти, учтённой в Commit группы процессов.
    10. При инциденте памяти Go на Windows нужно смотреть не только хип Go, но Working Set, Commit и подкачка.

    52. macOS: та же виртуальная память, другая модель давления¶

    macOS построена поверх Darwin/XNU и Mach VM.

    Базовая цепочка знакомая:

    процесс
↓
виртуальное адресное пространство
↓
отображения VM
↓
резидентные страницы
↓
давление на память
↓
сжатие / освобождение памяти / swap

    Но пользовательская диагностика здесь устроена заметно иначе, чем в Windows.

    Главный термин:

    Memory Pressure

    53. Mach VM¶

    У каждого процесса есть собственное виртуальное адресное пространство.

    Mach поддерживает:

    VM map
VM objects
физические страницы
pmap

    Не нужно уходить в исходники XNU.

    Учебная модель:

    виртуальный диапазон
↓
запись карты VM
↓
объект VM / обеспечение памяти
↓
физические страницы

    54. Почему большая аллокация не означает немедленное занятие RAM¶

    Apple VM давно использует выделение страниц по требованию.

    Учебно:

    выделить большой виртуальный диапазон
↓
отображение существует
↓
физические страницы отсутствуют
↓
первом обращении
↓
fault
↓
обнулённая физическая страница
↓
отображение обновлено

    Это та же фундаментальная модель, что мы уже видели в Linux и Windows.

    55. pmap¶

    На уровне XNU/Mach:

    pmap

    связывает архитектурно-зависимую таблицу страниц с VM-системой.

    Для лекции достаточно:

    VM map
→ логическая карта виртуальных диапазонов

pmap
→ низкоуровневое отображение виртуальный → физический

    56. Резидентная память¶

    Как и в других ОС:

    виртуальный адрес существует
≠
page резидентная

    Процесс может иметь большой адресное пространство.

    Но физическая RAM занимает только резидентная часть.

    В macOS Activity Monitor не даёт одной «истинной» цифры всей памяти приложения.

    Нужно читать контекст.

    57. Wired Memory¶

    Wired Memory — память, которую система должна держать в RAM и не может просто вытеснить обычным подкачка/освобождение памяти.

    Упрощённо:

    wired
↓
должна оставаться резидентной

    Отсюда:

    Wired Memory уменьшает количество RAM, которое можно свободно перераспределять между pageable workloads.

    58. App Memory¶

    Activity Monitor показывает:

    App Memory

    как память, используемую приложениями.

    Это пользовательская агрегированная метрика.

    Она полезна как обзор.

    Но для глубокого расследования одного процесса нужны:

    vmmap
Instruments
vm_stat

    59. Cached Files¶

    macOS использует свободную RAM под файловый кеш.

    Учебно:

    чтение файла
↓
cache
↓
RAM

    Пока давление на память низкий, кешированные файлы — полезное использование памяти.

    Если давление растёт:

    кеш можно освободить

    Поэтому:

    мало свободной RAM

    само по себе не означает аварии.

    60. Memory Pressure¶

    Apple специально выводит отдельный показатель:

    Memory Pressure

    Он учитывает не только свободную память.

    В пользовательской документации Apple прямо связывает его с:

    • свободную память;
    • скорость swap;
    • закреплённая память;
    • кешированную файловую память.

    Идея:

    Насколько эффективно текущая подсистемы памяти удовлетворяет запросы нагрузка?

    61. Почему Memory Pressure информативнее Free Memory¶

    Система A:

    Free = 500 MiB
Memory Pressure = зелёный

    Система может быть здоровой.

    Потому что:

    • файловый кеш reclaimable;
    • сжатие работает;
    • swap почти не нужен;
    • нагрузка продвигается.

    Система B:

    Free = 2 GiB
Memory Pressure = красный

    может испытывать тяжёлую динамическую проблему.

    Один снимок свободную память недостаточен.

    62. Зелёный / жёлтый / красный¶

    Activity Monitor показывает:

    зелёный
жёлтый
красный

    Учебная интерпретация:

    зелёный
→ система эффективно управляет памятью

жёлтый
→ давление растёт

красный
→ подсистемы памяти испытывает сильное давление

    Это диагностическая агрегация.

    Не низкоуровневый машина состояний ядра.

    63. Сжатие в macOS¶

    Когда RAM становится тесной, macOS может сжимать менее активно используемую память.

    Учебно:

    неактивная / холодная страница
↓
сжимать
↓
хранить сжатое представление в RAM
↓
освободить часть физической ёмкости

    Плюс:

    не нужно сразу идти на storage

    64. Почему сжатие вообще выгодна¶

    Допустим:

    4 KiB page

    сжимается до:

    1 KiB

    Вместо:

    занимать 4 KiB RAM

    она занимает условно:

    1 KiB сжатое представление в RAM

    Мы освобождаем capacity.

    Цена:

    CPU на сжатие
+
CPU на распаковку

    65. Сжатие — ещё один обмен памяти на CPU¶

    При низком давление:

    страницы резидентная
↓
обычный access

    При сжатие:

    сжатое представление
↓
нужно развернуть при повторном использовании
↓
работу CPU

    Но это часто дешевле:

    ввод-вывод SSD

    Поэтому сжатие может отсрочить swap.

    66. Почему сжатая память не является свободную память¶

    Сжатая страница всё ещё занимает RAM.

    Просто меньше.

    Поэтому:

    Compressed = 4 GiB

    не означает:

    4 GiB RAM освободились

    Это означает:

    Часть логической памяти сейчас хранится в сжатое представление.

    67. Когда сжатие становится дорогой¶

    Если рабочий набор большой и данные постоянно переходят:

    распаковывать
↓
use
↓
сжимать
↓
распаковывать

    CPU начинает заметно тратиться на управление памятью.

    Получаем аналог трэшинга, только часть давления сначала живёт внутри RAM.

    68. Swap в macOS¶

    Если сжатие недостаточно:

    давление на память ↑
↓
swap

    Часть данных перемещается на системный накопитель.

    Activity Monitor показывает:

    Swap Used

    Но снова:

    Swap Used > 0

    не является автоматическим диагнозом.

    Нужно смотреть:

    • Memory Pressure;
    • динамику swap;
    • задержка приложения;
    • сжатая память;
    • реальную нагрузку.

    69. Загрузка страницы из swap¶

    Когда данные в swap снова нужны:

    обращение к памяти
↓
страница недоступна
↓
fault
↓
чтение с накопителя
↓
RAM
↓
continue

    На современных SSD это намного быстрее старых HDD.

    Но всё равно на порядки медленнее доступа к DRAM.

    70. Почему Apple Silicon не отменяет давление на память¶

    На Apple Silicon единая память объединяет физическую память для CPU/GPU и других подсистем в общей архитектуре.

    Это меняет topology и устраняет часть копирований между отдельными пулы памяти.

    Но:

    физическая память всё равно конечна

    Поэтому остаются:

    • сжатие;
    • swap;
    • давление;
    • вытеснение/освобождение;
    • задержка при дефиците памяти.

    71. Единая память (Unified Memory) делает конкуренцию шире¶

    На классической дискретной системе:

    CPU RAM
GPU VRAM

    могут быть отдельными бюджетами.

    На Apple Silicon многие потребители делят объединённую память.

    Значит давление может приходить не только от:

    процесс Go

    но и от:

    • нагрузки GPU;
    • обработки медиа;
    • других приложений;
    • кешей;
    • системных служб.

    72. Почему бэкенд-процесс на Mac может тормозить из-за чужой нагрузки¶

    Разработчик запускает:

    Go-сервис
+
Docker/VM
+
IDE
+
браузер
+
видеозвонок

    Все конкурируют за физическая память.

    Сервис сам может иметь стабильный heap.

    Но системного давления на память растёт.

    Получаем:

    сжатие ↑
swap ↑
задержка страничных ошибок ↑
p99 сервиса ↑

    Это особенно полезно помнить при локальных тестах производительности.

    73. macOS очищаемая память (purgeable memory)¶

    Darwin/macOS также поддерживает идеи очищаемые кеши.

    Приложение или фреймворк может хранить данные, которые:

    полезны
но могут быть выброшены при давление

    Это хорошая архитектурная идея:

    cache
≠
обязательное состояние

    Чем больше данных можно безопасно восстановить, тем больше свободы у менеджера памяти.

    74. Почему кеш должен быть очищаемым по смыслу¶

    Если приложение хранит:

    огромный cache

    но система не знает, что его можно восстановить, память выглядит как обязательная.

    Если cache может быть отброшен:

    давление
↓
очистить кеш
↓
не нужен swap для этих данных

    Общая идея совпадает с чистым страничным кешем Linux:

    Восстанавливаемые данные дешевле освобождать, чем уникальное изменяемое состояние.

    75. macOS swap и износ SSD¶

    Иногда обсуждение давление на память сводят к:

    Swap убивает SSD.

    Такой вывод слишком грубый.

    Нас в бэкенд-курсе интересуют:

    • реальный объём записи в swap;
    • частоту;
    • нагрузка;
    • задержка;
    • давление.

    Современная система проектируется с учётом swap.

    Но постоянный тяжёлый swap — признак того, что рабочий набор плохо помещается в RAM.

    76. vm_stat¶

    Основной системный инструмент:

    vm_stat

    Он показывает статистику виртуальной памяти.

    Набор счётчики может зависеть от версии.

    Полезные категории могут включать:

    • free;
    • active;
    • inactive;
    • speculative;
    • wired;
    • compressed;
    • загрузки/выгрузки страниц;
    • страничные ошибки.

    Нужно смотреть динамику.

    77. Почему одна строка vm_stat мало полезна¶

    Снимок:

    Свободных страниц = N

    не отвечает:

    • растёт ли сжатие;
    • есть ли постоянную активность swap;
    • насколько быстро возникают страничные ошибки;
    • какой процесс создаёт давление.

    Нужно:

    vm_stat 1

    или повторные наблюдения.

    78. memory_pressure¶

    Утилита:

    memory_pressure

    даёт системный взгляд на доступность памяти и давление.

    Она полезна для:

    системная проблема?
или
только конкретный process?

    79. vmmap¶

    Для конкретного процесса:

    vmmap <pid>

    показывает структуру виртуальных отображения и области памяти.

    Можно увидеть:

    • типы областей;
    • виртуальные размеры;
    • информацию о резидентных/изменённых страницах;
    • общие/приватные отображения;
    • области аллокатора.

    Это macOS-аналог глубокого взгляда на адресное пространство процесса.

    80. Activity Monitor¶

    Для первого уровня:

    Memory Pressure
Physical Memory
Memory Used
App Memory
Wired Memory
Compressed
Cached Files
Swap Used

    Сильная сторона Activity Monitor:

    Он сразу показывает системную динамику, а не только память одного процесса.

    81. Instruments¶

    Для приложений Apple экосистема даёт Instruments.

    Полезные направления:

    • Allocations;
    • Leaks;
    • VM Tracker;
    • Time Profiler.

    Для Go-процесса нативные инструменты не заменяют:

    pprof
`runtime/metrics`

    Но помогают видеть слой виртуальной памяти ОС/процесса.

    82. Рантайм Go на macOS¶

    Текущий рантайм Go использует Darwin VM через:

    mmap

munmap

    Упрощённо:

    sysAllocOS
↓

sysUnusedOS
↓

sysUsedOS

↓

    83. MADV_FREE_REUSABLE¶

    Когда Scavenger Go решил:

    физическое содержимое больше не нужны

    на Darwin он может использовать:

    MADV_FREE_REUSABLE

    Идея:

    виртуальный диапазон сохраняется
↓
ядро может освободить физическую память

    Плюс этот механизм участвует в корректном учёте памяти Darwin.

    84. MADV_FREE_REUSE¶

    Если Go снова хочет использовать диапазон:

    MADV_FREE_REUSE

    помогает сообщить ядру:

    эта повторно используемая область снова используется

    То есть API рантайма macOS явно отражает жизненный цикл повторного использования.

    85. Почему Scavenger Go на macOS не равен сжатию¶

    Две разные системы.

    Scavenger Go:

    рантайм Go говорит:
эти страницы хипа мне не нужны

    macOS сжатие:

    ядро говорит:

    Что важно запомнить¶

    1. Windows разделяет виртуальное адресное пространство (Virtual Address Space), Commit и Working Set. Их нельзя складывать в одну метрику «память процесса».
    2. MEM_RESERVE закрепляет адресный диапазон, MEM_COMMIT создаёт обязательство обеспечить память, а Working Set показывает текущую резидентность.
    3. Сокращение Working Set уменьшает резидентный объём процесса, но не обязано освобождать виртуальный адрес или Commit.
    4. Малую страничную ошибку можно обработать без ввода-вывода хранилища обеспечения; большая страничная ошибка требует чтения pagefile или отображённого файла.
    5. Pagefile участвует и в подкачке, и в системной ёмкости Commit.
    6. Windows сжатие памяти меняет RAM на CPU и может уменьшать число больших страничных ошибок.
    7. Job Objects могут ограничивать объём памяти, учтённой в Commit процесса или группы процессов.
    8. Текущий рантайм Go на Windows использует VirtualAlloc/VirtualFree: резервирование/commit/decommit/release напрямую соответствуют жизненному циклу VM.
    9. macOS использует Mach VM и управляет давлением через освобождение памяти, сжатие и swap.
    10. Memory Pressure в macOS полезнее одной Free Memory, потому что отражает эффективность подсистемы памяти с учётом swap, закреплённой и кешированной памяти.
    11. Compressed Memory остаётся памятью в RAM, просто в более плотном представлении.
    12. Сжатие экономит RAM ценой CPU; swap добавляет задержку накопителя.
    13. На Apple Silicon единая память не отменяет давление: физический бюджет памяти всё равно конечен и делится несколькими подсистемами.
    14. Scavenger Go на macOS использует MADV_FREE_REUSABLE, сохраняя повторно используемое виртуальное отображение и позволяя ядру освобождать физическое обеспечение памяти.
    15. Достижимый объект Go может быть холодным для ОС: GC сохранит его, а ОС может сжать или выгрузить его физические страницы.
    16. Метрики хипа Go и метрики памяти ОС отвечают на разные вопросы и должны анализироваться вместе.
    17. Working Set на Windows и резидентная память на macOS зависят от системного давления на память, поэтому тест памяти нельзя интерпретировать вне состояния всей машины.
    18. Swap Used > 0 и Compressed > 0 сами по себе не являются аварией. Важны динамика, страничные ошибки и активность подкачки и задержка.
    19. Интенсивная подкачка на любой ОС означает переход от задержки DRAM к задержке накопителя и поэтому особенно опасна для p95/p99.
    20. Для прод-инцидента нужно восстановить цепочку: живой набор Go → виртуальная память → резидентность → давление → сжатие/pagefile/swap → страничные ошибки → задержка.

    Главный инженерный вывод:

    Windows и macOS используют разные API и разные эксплуатационные метрики, но решают одну физическую задачу: оставить горячий рабочий набор в RAM и вытеснить менее ценные данные с минимальной ценой. Windows особенно удобно учит разделять резервирование, Commit и Working Set; macOS — смотреть на давление на память, сжатие и swap как на единую динамическую систему. В обоих случаях Go GC отвечает за достижимость объектов, а ОС отдельно решает, должны ли страницы этих объектов прямо сейчас находиться в физической RAM.
