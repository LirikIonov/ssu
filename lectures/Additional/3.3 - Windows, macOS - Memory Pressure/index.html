    3.3. Windows и macOS memory pressure глубже: Working Set, Commit, compression и swap¶

    Сравнительная углублённая лекция после Linux memory reclaim.

    Цель — понять, как две другие массовые desktop/server-платформы решают ту же базовую задачу:

    virtual memory
↓
physical RAM
↓
memory pressure
↓
trimming / reclaim
↓
compression / pagefile / swap
↓
page fault
↓
application latency

    Конкретные внутренние структуры и эвристики зависят от версии ОС. В лекции отдельно отмечаем устойчивую модель и platform-specific детали.

    Зачем эта лекция после Linux¶

    После Linux легко закрепить слишком узкую модель:

    memory pressure
↓
LRU / MGLRU
↓
reclaim
↓
swap
↓
cgroup

    Но это модель Linux.

    Windows и macOS решают ту же физическую проблему:

    RAM конечна, а процессов и виртуальной памяти больше.

    Но называют сущности иначе и используют другие механизмы управления residency.

    Главная сравнительная карта:

                        COMMON PROBLEM

virtual address space
        ↓
physical pages
        ↓
working set / resident set
        ↓
memory pressure
        ↓
what can leave RAM?
        │
        ├── Windows
        │   Working Set trimming
        │   transition / standby
        │   memory compression
        │   pagefile
        │
        └── macOS
            resident / wired / purgeable
            compression
            swap
            Memory Pressure

    Нам важно научиться видеть общую физику за разными терминами.

    0. Что у всех ОС одинаково¶

    Во всех трёх системах процесс работает с:

    virtual addresses

    А физическая RAM управляется ядром.

    Поэтому:

    virtual address exists
≠
physical page resident

    И:

    process allocated memory
≠
all of it is currently in RAM

    Это фундаментальная модель и для Linux, и для Windows, и для macOS.

    1. Что меняется между ОС¶

    Различаются:

    • термины;
    • accounting;
    • reclaim policy;
    • compression;
    • swap/pagefile semantics;
    • инструменты диагностики;
    • process/container limits;
    • пользовательские метрики.

    Но вопрос ядра везде один:

    Какие данные должны остаться в дорогой быстрой RAM прямо сейчас?

    2. Windows: три разных понятия, которые нельзя смешивать¶

    Для Windows нужно разделить минимум:

    Virtual Address Space
Commit
Working Set

    Это три разных уровня.

    Наивная модель:

    процесс выделил 2 GiB
↓
он использует 2 GiB RAM

    может быть полностью неправильной.

    3. Virtual Address Space¶

    Процесс имеет собственное виртуальное адресное пространство.

    В нём можно:

    reserve address range

    не выделяя под него сразу физическую память.

    Это очень хорошо видно через WinAPI:

    VirtualAlloc

    с флагом:

    MEM_RESERVE

    4. MEM_RESERVE¶

    Учебная модель:

    VirtualAlloc(..., MEM_RESERVE, ...)
↓
диапазон виртуальных адресов закреплён за процессом

    Но:

    physical RAM = ещё не обязана быть выделена
pagefile backing = ещё не обязано быть выделено

    То есть:

    reserve
=
владение адресным диапазоном

    5. MEM_COMMIT¶

    Теперь процесс хочет память, которую действительно можно использовать.

    MEM_COMMIT

    Учебно:

    Система берёт обязательство обеспечить backing для этих страниц.

    Backing обеспечивается комбинацией:

    RAM
+
pagefile capacity

    При этом actual physical page может появиться лениво при first touch.

    Значит:

    commit
≠
resident

    6. Commit charge¶

    Windows должна знать:

    Сколько приватной памяти система уже пообещала backing'овать?

    Отсюда понятие commit charge.

    Упрощённо:

    process commits pages
↓
system-wide committed memory ↑

    Commit — не текущая occupancy RAM.

    Это обязательство системы обеспечить backing.

    7. Commit limit¶

    Commit не может расти бесконечно.

    Система имеет commit limit.

    Учебно:

    available backing capacity
≈
RAM
+
pagefile capacity
-
служебные ограничения

    Не нужно воспринимать формулу как точный арифметический контракт.

    Главная идея:

    Pagefile увеличивает не только возможность page-out, но и общий commit budget системы.

    8. Почему можно получить allocation failure при ещё свободной RAM¶

    Плохая модель:

    Если есть free RAM, VirtualAlloc(MEM_COMMIT) всегда должен сработать.

    Нет.

    Можно упереться в:

    commit limit

    даже если картина free physical RAM не выглядит катастрофической.

    Windows должна гарантировать backing committed memory.

    9. Working Set¶

    Working Set процесса — страницы его виртуального адресного пространства, которые сейчас resident в физической RAM.

    virtual pages
↓
subset currently resident
↓
Working Set

    То есть:

    Working Set
=
resident view процесса

    10. Commit и Working Set — разные оси¶

    Пример:

    Process A
Commit = 4 GiB
Working Set = 800 MiB

    Это возможно.

    Процесс имеет обязательство backing на 4 GiB.

    Но прямо сейчас только 800 MiB его pageable memory resident.

    Другой пример:

    Commit = 1 GiB
Working Set = 900 MiB

    Совсем другой профиль residency.

    11. Почему Working Set постоянно меняется¶

    Working Set не является «объёмом памяти процесса навсегда».

    Страницы входят в него:

    page fault resolved
↓
page becomes resident
↓
added to Working Set

    И выходят:

    memory pressure
↓
Working Set trimming
↓
page removed

    Это динамическая структура.

    12. Soft page fault¶

    Процесс обращается к странице, которой сейчас нет в его Working Set.

    Но данные уже находятся в RAM.

    Например страница:

    • в Working Set другого процесса;
    • в transition state;
    • была prefetched;
    • demand-zero allocation может быть удовлетворена без чтения backing store.

    Тогда fault можно разрешить без реального чтения с диска.

    Это soft page fault.

    13. Hard page fault¶

    Страница отсутствует в RAM.

    Нужно читать backing store:

    pagefile

    или:

    memory-mapped file

    Это hard page fault.

    Цена намного выше:

    storage I/O
↓
latency

    14. Почему счётчик Page Faults/sec легко неправильно читать¶

    Много page faults:

    не обязательно много disk I/O

    Потому что большая часть может быть soft faults.

    Для performance-инцидента важнее отделять:

    soft faults

    от:

    hard faults / page reads

    И смотреть реальные storage-события.

    15. Working Set trimming¶

    RAM становится нужна другим потребителям.

    Windows memory manager может уменьшать Working Set процессов:

    process Working Set
↓
trim less valuable pages
↓
more available physical memory

    Страница перестаёт быть resident у процесса.

    Но это не означает автоматически:

    virtual address released
commit released

    16. Страница после trim не обязана сразу попасть на диск¶

    Очень важный момент.

    Страница может покинуть Working Set, но остаться в RAM в transition/standby-подобном состоянии.

    Учебно:

    in Working Set
↓
trim
↓
not in process Working Set
↓
still physically cached in RAM

    Если процесс быстро обратится снова:

    soft fault
↓
page returns to Working Set

    Без storage I/O.

    17. Почему это полезно¶

    Если любую trimmed page мгновенно писать на storage или полностью уничтожать:

    короткий burst pressure
↓
огромный I/O
↓
через миллисекунды данные снова нужны

    Это было бы очень дорого.

    Поэтому Windows имеет промежуточные состояния физических страниц.

    18. Standby-подобная модель¶

    Для учебной модели полезно представить:

    Working Set
↓
trim
↓
standby / transition-like cache
↓
page still in RAM

    Пока memory не перепрофилировали под другую задачу, данные можно вернуть быстро.

    Точные внутренние page lists — реализация Windows.

    Не пользовательский API.

    19. Dirty page¶

    Если physical page изменена:

    dirty

    и её backing должен сохраняться, просто repurpose её нельзя.

    Нужно:

    write to backing store
↓
page becomes reusable

    В зависимости от типа страницы backing может быть:

    pagefile
memory-mapped file
file cache backing

    20. Pagefile¶

    Pagefile — backing store для части committed/private virtual memory.

    Учебно:

    private committed page
↓
not valuable enough to remain resident
↓
page content can be written to pagefile
↓
physical frame reused

    Позже:

    process accesses page
↓
hard fault
↓
pagefile read
↓
Working Set

    21. Pagefile не равен «дополнительная медленная RAM»¶

    Так говорить слишком просто.

    Pagefile выполняет несколько ролей в общей commit/paging модели Windows.

    Но по performance полезна цепочка:

    hot page left RAM
↓
pagefile backing
↓
needed again
↓
hard fault
↓
storage latency

    22. Почему pagefile может быть полезен даже при большой RAM¶

    Без pagefile commit budget и варианты управления private memory могут быть меньше.

    Холодные private pages нельзя так же гибко вынести из RAM.

    Поэтому:

    pagefile exists

    не равно:

    система обязательно активно thrash'ит

    Нужно смотреть реальную paging activity.

    23. Memory priority¶

    Windows умеет учитывать memory priority процесса/потока как hint.

    Идея:

    low-priority pages
↓
при прочих равных trim раньше

    Это позволяет приложению сообщить:

    Эти данные background-workload менее ценны для residency.

    Важно:

    это hint.

    Не абсолютная гарантия.

    24. Почему memory priority логична¶

    Два массива:

    A — hot request cache
B — background file index scan

    Если pressure одинаково вытесняет их случайно:

    hot cache может пострадать

    Memory priority позволяет дать ядру дополнительную информацию о ценности страниц.

    25. System file cache Windows¶

    Windows кэширует file data в памяти.

    Учебно:

    read file
↓
Cache Manager
↓
system file cache
├── hit → RAM
└── miss → storage

    Записи также могут идти через write-back caching.

    То есть физическая RAM Windows используется не только Working Set'ами обычных приложений.

    26. Большой system cache сам по себе не означает leak¶

    Свободная RAM предназначена для использования.

    File cache может быть полезной памятью.

    При pressure часть её данных может уйти из RAM.

    Проблема начинается, когда cache behaviour вытесняет более полезный рабочий набор и создаёт faults/I/O.

    27. Memory compression Windows¶

    Современная Windows умеет сжимать часть памяти.

    Идея:

    страница холодная
↓
вместо немедленного page-out
↓
compress
↓
оставить данные в RAM в меньшем объёме

    Это уменьшает число hard faults по сравнению с немедленным уходом на disk.

    28. Цена memory compression¶

    Compression экономит RAM.

    Но требует:

    CPU

    А при повторном использовании:

    decompression

    Получаем trade-off:

    меньше storage I/O
↔
больше CPU

    29. Compression не отменяет pagefile¶

    Если pressure продолжает расти:

    compression insufficient
↓
paging / pagefile activity

    Compression — промежуточный механизм.

    Не бесконечная дополнительная память.

    30. Windows pressure chain¶

    Упрощённо:

    RAM demand ↑
↓
available pages ↓
↓
Working Set trimming ↑
↓
soft faults ↑
↓
compression ↑
↓
если pressure ещё растёт
↓
pagefile / hard faults ↑
↓
application latency ↑

    Конкретная последовательность не является строгой state machine.

    Это инженерная модель возможных механизмов.

    31. Когда начинается thrashing на Windows¶

    Рабочий набор всех активных приложений значительно больше доступной physical memory.

    Получаем:

    trim
↓
page needed again
↓
fault
↓
trim another page
↓
fault

    Если backing store постоянно участвует:

    hard faults
↓
disk I/O
↓
throughput collapses

    32. Commit pressure и physical pressure — разные проблемы¶

    Можно упереться в:

    Commit Limit

    или:

    physical memory pressure

    Это не одно и то же.

    Commit pressure:

    system promised too much backing

    Physical pressure:

    слишком большой active resident working set

    Диагностика должна сначала понять, какой сценарий происходит.

    33. Windows Job Objects: аналог resource boundary¶

    Для группы процессов Windows предоставляет Job Objects.

    Можно ограничивать:

    per-process committed memory
job-wide committed memory

    То есть:

    process/job tries to commit above limit
↓
commit fails

    Это не прямая копия Linux cgroup.

    Но архитектурная роль похожа:

    Ограничить ресурсы группы процессов.

    34. Почему Job Object memory limit — это commit limit, а не Working Set limit¶

    Важно не перепутать.

    Job memory limit относится к:

    committed memory

    То есть ограничение формулируется вокруг обязательства backing.

    Это другая ось, чем:

    сколько сейчас resident в RAM

    35. Windows container memory: ментальная модель¶

    Windows-контейнеры в конечном счёте тоже используют механизмы Windows resource governance.

    Для курса достаточно:

    container/process group
↓
job/resource limits
↓
commit/resource accounting
↓
Windows memory manager

    Не нужно притягивать Linux cgroup-термины один в один.

    36. Go runtime на Windows¶

    Текущий Go runtime использует Windows VM API напрямую.

    Упрощённо:

    sysReserveOS
↓
VirtualAlloc(MEM_RESERVE)

sysAllocOS
↓
VirtualAlloc(MEM_RESERVE | MEM_COMMIT)

sysUnusedOS
↓
VirtualFree(MEM_DECOMMIT)

sysUsedOS
↓
VirtualAlloc(MEM_COMMIT)

sysFreeOS
↓
VirtualFree(MEM_RELEASE)

    Это очень наглядно связывает Go scavenger с Windows VM.

    37. Что означает MEM_DECOMMIT для Go scavenger¶

    Go решил:

    эти heap pages сейчас не нужны

    На Windows:

    VirtualFree(..., MEM_DECOMMIT)

    может снять backing commitment с диапазона.

    При этом:

    reserved virtual range может сохраниться

    Если память понадобится снова:

    VirtualAlloc(..., MEM_COMMIT)

    38. Почему Windows-runtime путь хорошо объясняет общую модель¶

    Получаем почти идеальную схему:

    RESERVE
→ адресное пространство

COMMIT
→ backing obligation

resident
→ Working Set

DECOMMIT
→ backing больше не нужен

RELEASE
→ адресный диапазон возвращён

    Это четыре разных состояния/уровня.

    39. Диагностика Windows: Task Manager¶

    Task Manager полезен для первого взгляда.

    Но нельзя останавливаться на одной колонке Memory.

    Нас интересуют разные вопросы:

    Working Set?
Commit?
Private memory?
system-wide committed?
available RAM?
paging activity?

    40. Performance Monitor¶

    Для серьёзной диагностики Windows нужен PerfMon.

    Полезные идеи:

    Memory\Committed Bytes
Memory\Commit Limit
Process\Working Set
Process\Private Bytes
Memory\Pages Input/sec
Memory\Pages Output/sec

    Конкретный набор зависит от вопроса.

    41. Committed Bytes¶

    Отвечает на вопрос:

    Какой commit demand сейчас существует в системе?

    Сравниваем с:

    Commit Limit

    Если committed близок к limit:

    commit pressure

    42. Working Set¶

    Отвечает:

    Сколько pageable memory процесса сейчас resident?

    Это momentary view.

    Под pressure ОС может trim Working Set.

    Поэтому одно и то же приложение на машине с 64 GiB и 16 GiB RAM может показывать разные Working Set.

    43. Private Bytes¶

    Используется как мера private committed memory процесса.

    Это не equivalent:

    RAM usage

    И не equivalent:

    Working Set

    Если Private Bytes растёт стабильно, это повод расследовать private commit/retention.

    44. Pages Input/sec и Output/sec¶

    Для paging-инцидента нужно смотреть реальное движение страниц.

    Pages Output/sec полезен, когда подозреваем:

    система выталкивает private pages ради освобождения RAM

    Но один счётчик всегда читаем вместе с:

    • disk latency;
    • Working Set;
    • available memory;
    • hard faults;
    • application latency.

    45. RAMMap¶

    Sysinternals RAMMap показывает физическую память по типам.

    Полезные вопросы:

    сколько file cache?
сколько process working sets?
какие page lists?
что занимает physical RAM?

    Это хороший инструмент, когда:

    Task Manager говорит «RAM занята»

    а непонятно чем.

    46. VMMap и Process Explorer¶

    Для конкретного процесса полезны инструменты Sysinternals:

    VMMap
Process Explorer

    Они помогают отделять:

    • reserved;
    • committed;
    • private;
    • mapped;
    • image;
    • working set.

    То есть диагностировать именно виртуальную структуру процесса.

    47. WPR/WPA и reference set¶

    Working Set зависит от текущего pressure и trimming.

    Для сценарного исследования Microsoft предлагает concept reference set через Windows Performance Recorder/Analyzer.

    Идея:

    какие страницы workload реально трогал во время сценария?

    Это лучше отвечает на вопрос активного memory footprint workload, чем один моментальный Working Set.

    48. Windows: симптом → гипотеза¶

    Сценарий:

    Private Bytes stable
Working Set falls
soft faults rise

    Гипотеза:

    Working Set trimming

    Данные всё ещё принадлежат процессу.

    Но residency уменьшается.

    49. Windows: другой сценарий¶

    Committed Bytes → Commit Limit
↓
VirtualAlloc commit failures

    Это commit exhaustion.

    Добавить RAM может помочь.

    Увеличить pagefile тоже может изменить commit capacity.

    Это другой механизм, чем Working Set thrashing.

    50. Windows: тяжёлый pressure¶

    Working Set trim ↑
↓
compressed memory ↑
↓
pagefile activity ↑
↓
hard faults ↑
↓
disk latency ↑
↓
request latency ↑

    Backend может тормозить при полностью нормальном Go GC.

    51. Windows: что важно запомнить перед macOS¶

    1. Reserve, Commit и Resident — разные уровни.
    2. Working Set показывает resident pageable pages процесса.
    3. Commit показывает backing obligation.
    4. Trim Working Set не освобождает virtual address и не обязательно снимает commit.
    5. Trimmed page может остаться в RAM и вернуться через soft fault.
    6. Hard fault требует backing-store I/O.
    7. Compression меняет RAM на CPU и уменьшает часть hard-fault pressure.
    8. Pagefile участвует в commit/paging модели.
    9. Job Object limits могут ограничивать committed memory группы процессов.
    10. При Go memory incident на Windows нужно смотреть не только Go heap, но Working Set, Commit и paging.

    52. macOS: та же виртуальная память, другая модель давления¶

    macOS построена поверх Darwin/XNU и Mach VM.

    Базовая цепочка знакомая:

    task
↓
virtual address space
↓
VM mappings
↓
resident pages
↓
memory pressure
↓
compression / reclaim / swap

    Но пользовательская диагностика здесь устроена заметно иначе, чем в Windows.

    Главный термин:

    Memory Pressure

    53. Mach VM¶

    У каждого процесса есть собственное виртуальное адресное пространство.

    Mach поддерживает:

    VM map
VM objects
physical pages
pmap

    Не нужно уходить в исходники XNU.

    Учебная модель:

    virtual range
↓
VM map entry
↓
VM object / backing
↓
physical pages

    54. Почему large allocation не означает immediate RAM¶

    Apple VM давно использует demand paging.

    Учебно:

    allocate large virtual range
↓
mapping exists
↓
physical pages absent
↓
first touch
↓
fault
↓
zeroed physical page
↓
mapping updated

    Это та же фундаментальная модель, что мы уже видели в Linux и Windows.

    55. pmap¶

    На уровне XNU/Mach:

    pmap

    связывает архитектурно-зависимую таблицу страниц с VM-системой.

    Для лекции достаточно:

    VM map
→ логическая карта виртуальных диапазонов

pmap
→ низкоуровневое отображение virtual → physical

    56. Resident memory¶

    Как и в других ОС:

    virtual address exists
≠
page resident

    Процесс может иметь большой address space.

    Но physical RAM занимает только resident subset.

    В macOS Activity Monitor не даёт одной «истинной» цифры всей памяти приложения.

    Нужно читать контекст.

    57. Wired memory¶

    Wired Memory — память, которую система должна держать в RAM и не может просто вытеснить обычным paging/reclaim.

    Упрощённо:

    wired
↓
must remain resident

    Отсюда:

    Wired memory уменьшает количество RAM, которое можно свободно перераспределять между pageable workloads.

    58. App Memory¶

    Activity Monitor показывает:

    App Memory

    как память, используемую приложениями.

    Это пользовательская агрегированная метрика.

    Она полезна как обзор.

    Но для глубокого расследования одного процесса нужны:

    vmmap
Instruments
vm_stat

    59. Cached Files¶

    macOS использует свободную RAM под файловый кеш.

    Учебно:

    file read
↓
cache
↓
RAM

    Пока memory pressure низкий, cached files — полезное использование памяти.

    Если pressure растёт:

    cache can be reclaimed

    Поэтому:

    little free RAM

    само по себе не означает аварии.

    60. Memory Pressure¶

    Apple специально выводит отдельный показатель:

    Memory Pressure

    Он учитывает не только free memory.

    В пользовательской документации Apple прямо связывает его с:

    • free memory;
    • swap rate;
    • wired memory;
    • file cached memory.

    Идея:

    Насколько эффективно текущая memory subsystem удовлетворяет запросы workload?

    61. Почему Memory Pressure лучше Free Memory¶

    Система A:

    Free = 500 MiB
Memory Pressure = green

    Система может быть здоровой.

    Потому что:

    • file cache reclaimable;
    • compression работает;
    • swap почти не нужен;
    • workload продвигается.

    Система B:

    Free = 2 GiB
Memory Pressure = red

    может испытывать тяжёлую динамическую проблему.

    Один снимок free memory недостаточен.

    62. Green / Yellow / Red¶

    Activity Monitor показывает:

    green
yellow
red

    Учебная интерпретация:

    green
→ system handles memory efficiently

yellow
→ pressure растёт

red
→ memory subsystem серьёзно напряжена

    Это диагностическая агрегация.

    Не низкоуровневый kernel state machine.

    63. Compression в macOS¶

    Когда RAM становится тесной, macOS может сжимать менее активно используемую память.

    Учебно:

    inactive / cold page
↓
compress
↓
store compressed representation in RAM
↓
free part of physical capacity

    Плюс:

    не нужно сразу идти на storage

    64. Почему compression вообще выгодна¶

    Допустим:

    4 KiB page

    сжимается до:

    1 KiB

    Вместо:

    занимать 4 KiB RAM

    она занимает условно:

    1 KiB compressed storage in RAM

    Мы освобождаем capacity.

    Цена:

    CPU на compression
+
CPU на decompression

    65. Compression — это ещё один обмен memory ↔ CPU¶

    При низком pressure:

    страницы resident
↓
обычный access

    При compression:

    compressed representation
↓
нужно развернуть при повторном использовании
↓
CPU work

    Но это часто дешевле:

    SSD I/O

    Поэтому compression может отсрочить swap.

    66. Почему compressed memory не является free memory¶

    Сжатая страница всё ещё занимает RAM.

    Просто меньше.

    Поэтому:

    Compressed = 4 GiB

    не означает:

    4 GiB RAM освободились

    Это означает:

    Часть логической памяти сейчас хранится в compressed representation.

    67. Когда compression становится дорогой¶

    Если рабочий набор большой и данные постоянно переходят:

    decompress
↓
use
↓
compress
↓
decompress

    CPU начинает заметно тратиться на memory management.

    Получаем аналог thrashing, только часть pressure сначала живёт внутри RAM.

    68. Swap в macOS¶

    Если compression недостаточно:

    memory pressure ↑
↓
swap

    Часть данных перемещается на startup disk.

    Activity Monitor показывает:

    Swap Used

    Но снова:

    Swap Used > 0

    не является автоматическим диагнозом.

    Нужно смотреть:

    • Memory Pressure;
    • swap dynamics;
    • application latency;
    • compressed memory;
    • actual workload.

    69. Page-in из swap¶

    Когда swapped data снова нужны:

    memory access
↓
page unavailable
↓
fault
↓
storage read
↓
RAM
↓
continue

    На современных SSD это намного быстрее старых HDD.

    Но всё равно на порядки медленнее доступа к DRAM.

    70. Почему Apple Silicon не отменяет memory pressure¶

    На Apple Silicon unified memory объединяет физическую память для CPU/GPU и других подсистем в общей архитектуре.

    Это меняет topology и устраняет часть копирований между отдельными memory pools.

    Но:

    physical memory всё равно конечна

    Поэтому остаются:

    • compression;
    • swap;
    • pressure;
    • eviction/reclaim;
    • latency under shortage.

    71. Unified memory делает конкуренцию шире¶

    На классической дискретной системе:

    CPU RAM
GPU VRAM

    могут быть отдельными бюджетами.

    На Apple Silicon многие потребители делят unified memory.

    Значит pressure может приходить не только от:

    Go process

    но и от:

    • GPU workloads;
    • media processing;
    • other apps;
    • caches;
    • system services.

    72. Почему backend-процесс на Mac может тормозить из-за чужого workload¶

    Разработчик запускает:

    Go service
+
Docker/VM
+
IDE
+
browser
+
video call

    Все конкурируют за physical memory.

    Сервис сам может иметь стабильный heap.

    Но system pressure растёт.

    Получаем:

    compression ↑
swap ↑
fault latency ↑
service p99 ↑

    Это особенно полезно помнить при локальных performance-тестах.

    73. macOS purgeable memory¶

    Darwin/macOS также поддерживает идеи purgeable/reclaimable caches.

    Приложение или framework может хранить данные, которые:

    полезны
но могут быть выброшены при pressure

    Это хорошая архитектурная идея:

    cache
≠
must-preserve state

    Чем больше данных можно безопасно recreate, тем больше свободы у memory manager.

    74. Почему cache должен быть purgeable по смыслу¶

    Если приложение хранит:

    огромный cache

    но система не знает, что его можно восстановить, память выглядит как обязательная.

    Если cache может быть отброшен:

    pressure
↓
purge cache
↓
не нужен swap для этих данных

    Общая идея совпадает с Linux clean page cache:

    Reconstructible data дешевле reclaim'ить, чем уникальное mutable state.

    75. macOS swap и SSD wear¶

    Иногда обсуждение memory pressure сводят к:

    Swap убивает SSD.

    Такой вывод слишком грубый.

    Нас в backend-курсе интересуют:

    • actual swap write volume;
    • frequency;
    • workload;
    • latency;
    • pressure.

    Современная система проектируется с учётом swap.

    Но постоянный тяжёлый swap — признак того, что working set плохо помещается в RAM.

    76. vm_stat¶

    Основной системный инструмент:

    vm_stat

    Он показывает статистику виртуальной памяти.

    Набор counters может зависеть от версии.

    Полезные категории могут включать:

    • free;
    • active;
    • inactive;
    • speculative;
    • wired;
    • compressed;
    • pageins/pageouts;
    • faults.

    Нужно смотреть динамику.

    77. Почему одна строка vm_stat мало полезна¶

    Снимок:

    Pages free = N

    не отвечает:

    • растёт ли compression;
    • есть ли swap churn;
    • насколько быстро страницы fault'ятся;
    • какой процесс создаёт pressure.

    Нужно:

    vm_stat 1

    или повторные наблюдения.

    78. memory_pressure¶

    Утилита:

    memory_pressure

    даёт системный взгляд на доступность памяти и pressure.

    Она полезна для:

    системная проблема?
или
только конкретный process?

    79. vmmap¶

    Для конкретного процесса:

    vmmap <pid>

    показывает структуру виртуальных mappings и memory regions.

    Можно увидеть:

    • region types;
    • virtual sizes;
    • resident/dirty information;
    • shared/private mappings;
    • allocator regions.

    Это macOS-аналог глубокого взгляда на address space процесса.

    Он сразу показывает системную динамику, а не только память одного процесса.

    82. Go runtime на macOS¶

    Текущий Go runtime использует Darwin VM через:

    mmap

    Упрощённо:

    sysAllocOS
↓

    83. MADV_FREE_REUSABLE¶

    Когда Go scavenger решил:

    physical contents больше не нужны

    на Darwin он может использовать:

    MADV_FREE_REUSABLE

    Идея:

    virtual range remains
↓
kernel may reclaim physical backing

    Плюс этот механизм участвует в корректном memory accounting Darwin.

    84. MADV_FREE_REUSE¶

    Если Go снова хочет использовать range:

    MADV_FREE_REUSE

    помогает сообщить kernel:

    эта reusable region снова используется

    То есть macOS runtime API явно отражает reuse lifecycle.

    85. Почему Go scavenger на macOS не равен compression¶

    Две разные системы.

    Go scavenger:

    Go runtime говорит:
эти heap pages мне не нужны

    macOS compression:

    kernel говорит:
эта ещё нужная memory холодная,
я попробую хранить её компактнее

    Первое:

    application/runtime ownership decision

    Второе:

    OS pressure policy

    86. Почему это разделение важно¶

    Сценарий A:

    Go heap освобождён
↓
scavenger отдаёт pages

    Это оптимально.

    Сценарий B:

    Go всё ещё считает objects live
↓
kernel compresses/swaps pages

    GC их не может удалить.

    OS только меняет способ physical storage.

    87. macOS pressure chain¶

    Учебно:

    physical demand ↑
↓

↓

↓

↓

↓

↓

    Это не строгая последовательность kernel states.

    Это причинная модель.

    88. Когда macOS начинает thrash'ить¶

    hot working set
>

    И данные начинают постоянно:

    compress

    89. Почему Mac может использовать почти всю RAM и быть быстрым¶

    Потому что:

    unused RAM

    не является целью.

    RAM должна использоваться:

    • приложениями;
    • cache;
    • filesystem data.

    Если system может легко reclaim'ить нужный объём:

    Memory Pressure green

    даже при небольшом free memory система здорова.

    115. Что нельзя делать на Windows¶

    Смотреть только Task Manager Memory¶

    Одна цифра может скрыть:

    commit
resident
shared
private

    Считать любой page fault disk fault¶

    Soft faults могут обходиться без storage.

    Считать Working Set полной стоимостью процесса¶

    Он зависит от pressure и trimming.

    Отключать pagefile как универсальную «оптимизацию»¶

    Это меняет commit/paging model.

    Сначала нужен конкретный workload и измерения.

    116. Что нельзя делать на macOS¶

    Считать маленькую Free Memory проблемой¶

    macOS специально использует RAM под полезные данные.

    Считать Compressed всегда плохим¶

    Умеренная compression может быть нормальной эффективной политикой.

    Считать Swap Used > 0 аварией¶

    Важна текущая activity и Memory Pressure.

    Объяснять любой slowdown Go GC¶

    System-wide pressure может быть сильнее runtime GC.

    117. Почему compression не бесплатна в обеих ОС¶

    Общая модель:

    pressure
↓
compress cold page
↓
RAM saved

    Но потом:

    page hot again
↓
decompress
↓
CPU

    При частых переходах:

    compression churn

    может стать самостоятельной нагрузкой.

    118. Почему storage latency всё равно остаётся последней стеной¶

    Когда compression недостаточно:

    pagefile / swap

    Теперь доступ стоит:

    storage I/O

    Даже быстрый NVMe намного медленнее DRAM.

    Поэтому heavy paging всегда опасен для tail latency.

    119. Windows и macOS не имеют прямого аналога Linux PSI в обычной модели¶

    Linux даёт очень прямую метрику:

    stall time due to pressure

    На Windows и macOS диагностика чаще собирается из нескольких сигналов.

    Windows:

    Working Set
paging
hard faults
commit
ETW/WPA

    macOS:

    Memory Pressure
compression

    То есть Linux PSI удобно отвечает на вопрос напрямую, а здесь картину чаще собираем композиционно.

    120. Memory Pressure macOS — closest high-level signal¶

    С точки зрения эксплуатации macOS:

    Memory Pressure

    Windows Performance Toolkit позволяет измерять reference set сценария:

    122. Почему working set важнее allocation size¶

    Приложение может выделить:

    20 GiB

    но горячо использовать:

    1 GiB

    OS может держать активный рабочий набор в RAM и вытеснить холодные данные.

    Другой процесс:

    allocated = 4 GiB
working set = 4 GiB hot

    может создавать больше pressure.

    123. Почему GC live heap и working set тоже разные вещи¶

    Go live heap:

    объекты достижимы

    Working set:

    какие physical pages реально нужны сейчас

    Долгоживущий Go cache может быть:

    live

    но редко используем.

    GC его не удалит.

    OS может compress/page его.

    Это два разных понятия «нужности».

    124. Очень важная модель: reachability ≠ hotness¶

    Go GC спрашивает:

    Есть ли путь от roots?

    OS memory manager:

    Насколько недавно эта physical page реально использовалась?

    Объект может быть:

    reachable
+
cold

    Тогда:

    Go сохраняет его
OS может вытеснить / compress

    Вот почему runtime GC и OS reclaim решают разные задачи.

    134. Что является implementation detail¶

    Windows:

    • конкретные working-set manager heuristics;
    • внутренние page lists;
    • compression implementation;
    • exact trimming policy;
    • exact page replacement heuristics.

    macOS:

    • compressor internals;
    • exact eviction policy;
    • swap heuristics;
    • XNU internal queues;
    • exact Memory Pressure formula.

    Эти детали меняются между версиями.

    Что важно запомнить¶

    1. Windows разделяет Virtual Address Space, Commit и Working Set. Их нельзя складывать в одну метрику «память процесса».
    2. MEM_RESERVE закрепляет адресный диапазон, MEM_COMMIT создаёт backing obligation, а Working Set показывает текущую residency.
    3. Working Set trimming уменьшает resident footprint процесса, но не обязан освобождать virtual address или commit.
    4. Soft fault можно разрешить без backing-store I/O; hard fault требует чтения pagefile или mapped file.
    5. Pagefile участвует и в paging, и в system commit capacity.
    6. Windows memory compression меняет RAM на CPU и может уменьшать число hard faults.
    7. Job Objects могут ограничивать committed memory процесса или группы процессов.
    8. Текущий Go runtime на Windows использует VirtualAlloc/VirtualFree: reserve/commit/decommit/release напрямую соответствуют VM lifecycle.
    9. macOS использует Mach VM и управляет pressure через reclaim, compression и swap.
    10. Memory Pressure в macOS полезнее одной Free Memory, потому что отражает эффективность memory subsystem с учётом swap, wired и cached memory.
    11. Compressed Memory остаётся памятью в RAM, просто в более плотном представлении.
    12. Compression экономит RAM ценой CPU; swap добавляет storage latency.
    13. На Apple Silicon unified memory не отменяет pressure: физический memory budget всё равно конечен и делится несколькими подсистемами.
    14. Go scavenger на macOS использует MADV_FREE_REUSABLE, сохраняя reusable virtual mapping и позволяя kernel reclaim physical backing.
    15. Reachable Go object может быть холодным для ОС: GC сохранит его, а OS может compress/page out его physical pages.
    16. Go heap metrics и OS memory metrics отвечают на разные вопросы и должны анализироваться вместе.
    17. Working Set на Windows и resident memory на macOS зависят от system pressure, поэтому benchmark memory нельзя интерпретировать вне состояния всей машины.
    18. Swap Used > 0 и Compressed > 0 сами по себе не являются аварией. Важны динамика, fault/paging activity и latency.
    19. Heavy paging на любой ОС означает переход от DRAM latency к storage latency и поэтому особенно опасен для p95/p99.
    20. Для production-инцидента нужно восстановить цепочку: Go live set → virtual memory → residency → pressure → compression/pagefile/swap → faults → latency.

    Главный инженерный вывод:

    Windows и macOS используют разные API и разные эксплуатационные метрики, но решают одну физическую задачу: оставить горячий working set в RAM и вытеснить менее ценные данные с минимальной ценой. Windows особенно удобно учит разделять reserve, commit и Working Set; macOS — смотреть на pressure, compression и swap как на единую динамическую систему. В обоих случаях Go GC отвечает за достижимость объектов, а ОС отдельно решает, должны ли страницы этих объектов прямо сейчас находиться в физической RAM.
