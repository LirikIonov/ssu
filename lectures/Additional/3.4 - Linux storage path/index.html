    3.4. Linux storage path глубже: page cache, dirty pages, writeback, write(), fsync(), block layer и NVMe/SSD¶

    Дополнительная углублённая лекция после блока про виртуальную память и memory reclaim.

    Главная задача — открыть путь:

    application
↓
write()
↓
page cache
↓
dirty pages
↓
writeback
↓
filesystem
↓
block layer
↓
NVMe
↓
SSD controller
↓
NAND

    И ответить на главный backend-вопрос:

    Когда данные действительно считаются сохранёнными?

    Зачем вообще лезть ниже write()¶

    Пишем:

    _, err := f.Write(data)

    err == nil.

    Опасное упрощение:

    write() вернулся без ошибки — данные уже на SSD.

    Нет.

    Часто реальная цепочка такая:

    application buffer
↓
system call
↓
kernel
↓
page cache
↓
dirty memory
↓
write() returns

    А storage увидит данные позже.

    Значит:

    write() success
≠
durability

    1. Три разных события¶

    Нужно сразу разделить:

    Данные приняло ядро¶

    write() returned

    Данные дошли по storage path¶

    writeback / block I/O completed

    Данные переживут crash/power loss¶

    durability boundary

    Если смешать эти уровни, невозможно нормально понимать:

    • WAL;
    • PostgreSQL commit;
    • fsync;
    • journaling;
    • SSD cache;
    • power-loss protection.

    2. Почему Linux вообще буферизует запись¶

    Наивный путь:

    write(fd, buf, 4096)
↓
device
↓
wait
↓
return

    Если каждый мелкий write() ждал реальный storage, latency была бы огромной.

    Поэтому Linux использует:

    page cache

    3. Page cache¶

    Page cache — кеш файловых данных в RAM под управлением ядра.

    Чтение:

    read()
↓
page cache
├── hit → RAM
└── miss → storage

    Запись:

    write()
↓
изменить page cache
↓
page dirty

    Физический storage может быть обновлён позже.

    4. Почему page cache полезен¶

    Он даёт:

    • кеш чтения;
    • объединение мелких writes;
    • readahead;
    • write coalescing;
    • асинхронный writeback;
    • hiding device latency.

    Цена:

    write() returned

    и:

    data durable

    разделены во времени.

    5. Buffered I/O¶

    Обычный файловый write в Linux чаще всего идёт через buffered I/O.

    Учебно:

    userspace buffer
↓
write()
↓
VFS
↓
filesystem
↓
page cache
↓
copy data
↓
mark dirty
↓
return

    То есть write() может завершиться до I/O на устройство.

    6. Dirty page¶

    Page cache содержит более новую версию данных, чем storage.

    SSD:
A B C D

page cache:
A B X D

    Страница:

    dirty = yes

    Пока writeback не завершён, storage остаётся старым.

    7. Clean page¶

    После успешного writeback:

    page cache contents
=
storage contents

    Страница становится clean.

    Теперь при pressure её проще выбросить:

    drop from RAM
↓
later read from storage if needed

    8. Почему dirty page нельзя просто reclaim'нуть¶

    Если её выбросить:

    new data lost

    Поэтому:

    dirty
↓
writeback
↓
clean
↓
reclaimable

    Memory pressure связывается со storage I/O.

    9. Копирование при buffered write¶

    Обычно kernel копирует данные:

    userspace
↓
copy_from_user
↓
page cache

    Получаем дополнительный memory traffic.

    Но взамен kernel получает контроль над caching и writeback.

    10. VFS¶

    write() не знает, работает файл на ext4, XFS или другом filesystem.

    Есть слой:

    VFS

    Учебно:

    syscall
↓
VFS
↓
filesystem implementation

    VFS унифицирует:

    • file descriptors;
    • inode;
    • file operations;
    • permissions;
    • offsets;
    • directory operations.

    11. File descriptor¶

    File descriptor — не файл как байты.

    Это integer handle:

    fd
↓
kernel file object
↓
inode / filesystem state

    Через него write() доходит до filesystem.

    12. Что происходит после dirtying¶

    Вопрос:

    Кто и когда отправляет dirty data вниз?

    Появляется:

    writeback

    13. Writeback¶

    Writeback — перенос dirty page cache на backing storage.

    dirty page
↓
filesystem writeback
↓
block I/O
↓
device

    Он может запускаться:

    • фоново;
    • при накоплении dirty memory;
    • при memory pressure;
    • по fsync;
    • при explicit sync;
    • при других filesystem events.

    14. Dirty bytes как очередь¶

    Очень полезная модель:

    dirty bytes
=
storage work backlog

    Если приложение создаёт dirty data со скоростью:

    λdirty

    а storage очищает:

    μwriteback

    то при:

    λdirty > μwriteback

    backlog растёт.

    15. Почему backlog нельзя растить бесконечно¶

    Dirty pages занимают RAM.

    Если storage отстаёт:

    Dirty ↑
↓
RAM increasingly occupied by unflushed data

    В какой-то момент kernel должен тормозить writers.

    16. Dirty thresholds¶

    Linux имеет настройки вроде:

    vm.dirty_background_ratio
vm.dirty_ratio

    и byte-варианты:

    vm.dirty_background_bytes
vm.dirty_bytes

    Учебная модель:

    dirty moderate
→ background writeback

dirty too high
→ writer throttling

    Точные эвристики зависят от версии ядра.

    17. balance_dirty_pages¶

    Если task создаёт dirty data слишком быстро:

    write()
↓
dirty accounting
↓
too much dirty memory
↓
balance_dirty_pages
↓
task sleeps / throttles

    И вот buffered write внезапно начинает чувствовать скорость storage.

    18. Почему write latency бывает пилообразной¶

    Пока dirty budget есть:

    write()
→ RAM
→ быстро

    Порог достигнут:

    throttling
↓
write latency spikes

    Writeback догоняет:

    Dirty ↓
↓
writes fast again

    Получаем характерную пилу.

    19. Почему это может не быть видно в Go CPU profile¶

    Goroutine может ждать внутри syscall/kernel path.

    Go handler
↓
write()
↓
kernel throttling
↓
sleep

    CPU profile приложения не обязан показывать «горячую функцию».

    Проблема — wall-clock wait.

    20. Writeback связан с filesystem¶

    Kernel знает:

    какой page cache page относится к какому inode

    Filesystem решает:

    • какие blocks использовать;
    • как обновить extents;
    • какие metadata изменить;
    • какое crash-consistency ordering нужно.

    Поэтому:

    dirty page
↓
filesystem
↓
block mapping

    21. Data и metadata¶

    Файл — не только payload.

    Есть:

    file data
size
timestamps
permissions
directory entry
block mapping
inode metadata

    Append может изменить и data, и metadata.

    Durability должна учитывать оба уровня.

    22. Почему fsync() не равен «запиши эти байты»¶

    fsync(fd) должен закрыть persistence obligations файла.

    Это может включать:

    dirty data
+
metadata required for retrieval
+
filesystem journal/order
+
device flush/FUA semantics

    Поэтому fsync() часто намного дороже write().

    23. fsync()¶

    Учебно:

    application
↓
fsync(fd)
↓
flush dirty data
↓
flush required metadata
↓
wait I/O completion
↓
close persistence ordering
↓
return

    Вот это уже durability boundary прикладного уровня.

    24. write() против fsync()¶

    Событие Что подтверждено
    write() вернулся kernel принял данные согласно syscall semantics
    writeback completed I/O по storage path завершено
    fsync() вернулся filesystem/OS выполнили durability contract
    device completion device подтвердил конкретную command semantics

    Это не одна и та же точка.

    25. fdatasync()¶

    fdatasync() ориентирован на:

    data
+
metadata required to retrieve data

    и может иметь более узкие metadata obligations, чем fsync().

    Он потенциально дешевле.

    Но:

    fdatasync always faster

    не является гарантией.

    26. O_SYNC и O_DSYNC¶

    Можно открыть файл с синхронной семантикой.

    Упрощённо:

    write()
↓
data cannot simply remain as ordinary dirty backlog
↓
sync obligations paid before return

    Цена durability переносится в каждый write.

    27. fsync() решил проблему файла. Но транзакция — это уже другой уровень¶

    К этому месту мы уже умеем делать одну важную вещь:

    write()
↓
page cache
↓
fsync()
↓
durability boundary файла

    То есть приложение может потребовать:

    Все необходимые изменения этого файла должны пережить crash согласно контракту filesystem/storage.

    Кажется, дальше база данных просто должна вызвать fsync().

    Но теперь меняем постановку задачи.

    Транзакция обычно изменяет не один непрерывный кусок одного файла.

    Она может затронуть:

    data page A
data page B
index page C
metadata D

    И все эти изменения логически должны образовать одну транзакцию.

    Новый вопрос:

    Как из durability отдельных writes построить durability и crash recovery целой транзакции?

    Вот здесь fsync() сам по себе уже недостаточен.

    28. Специально ломаем прямую запись data pages¶

    Пусть есть перевод денег:

    Account A: -100
Account B: +100

    Условно значения лежат на двух разных data pages:

    page A
page B

    Самая очевидная реализация:

    изменить A в RAM
изменить B в RAM
↓
write page A
write page B
↓
fsync data files
↓
COMMIT

    Теперь crash происходит в неприятный момент.

    Storage уже сделал durable:

    page A = новое состояние

    Но ещё не успел:

    page B = новое состояние

    После reboot:

    A = -100 применилось
B = +100 не применилось

    На storage появилось промежуточное состояние транзакции.

    Главный вывод:

    fsync() обеспечивает persistence уже отправленных файловых изменений, но сам по себе не создаёт recovery protocol для набора логически связанных изменений.

    29. Почему нельзя просто «правильно синхронно записать все страницы»¶

    Теоретически можно построить сложный протокол вокруг data pages.

    Но посмотрим на цену.

    Одна транзакция может изменить:

    page 17
page 821
page 44 103
index page 91
catalog page 4

    То есть commit-path превращается в:

    несколько random writes
+
несколько filesystem structures
+
durability ordering
+
ожидание storage

    Чем больше транзакция, тем больше объектов нужно синхронно довести до persistent state перед ACK клиенту.

    Для OLTP это очень дорого.

    Нам хочется свести критический commit-path к чему-то намного более простому:

    последовательный append
↓
одна durability boundary

    30. Какой объект удобно делать durable¶

    Вместо немедленной синхронной записи всех конечных data pages можно сначала сохранить компактное описание произошедших изменений.

    Учебно:

    transaction changed A, B, C
↓
encode recovery information
↓
append it to sequential log

    Теперь durable object на критическом пути:

    не десяток random data pages

    а:

    последовательный журнал

    Вот из этой потребности естественно появляется WAL.

    31. WAL: что это на этом уровне¶

    WAL — Write-Ahead Log.

    На текущем уровне нам достаточно определения:

    WAL хранит информацию, необходимую recovery-механизму базы данных, и записывается с таким ordering, чтобы изменения data pages не могли стать опасно durable раньше соответствующей информации в журнале.

    Учебная цепочка:

    transaction changes memory state
↓
generate WAL record
↓
append WAL
↓
make required WAL durable
↓
database may acknowledge durable commit

    А data pages живут своим более медленным жизненным циклом.

    32. Почему именно Write-Ahead¶

    Ключевое правило:

    WAL first
↓
data page later

    Точнее:

    Прежде чем изменённая data page может быть безопасно записана на persistent storage, WAL, необходимый для восстановления этой версии страницы, должен уже быть durable.

    Это и есть write-ahead rule.

    Слово:

    Ahead

    буквально означает:

    журнал обязан опередить data page по durability

    33. Что это даёт при crash¶

    Допустим data page успела попасть на storage.

    Если WAL уже durable:

    storage contains changed page
+
recovery information exists

    После crash база знает, как интерпретировать и восстанавливать состояние.

    Если data page ещё не успела записаться:

    storage contains old page
+
WAL contains recovery information

    Recovery может повторно применить нужные изменения.

    Мы получили возможность отвязать:

    transaction durability

    от:

    немедленной записи каждой data page на финальное место

    34. Важная точность: data page не обязана ждать COMMIT¶

    Здесь легко сформировать слишком простую модель:

    COMMIT
↓
только потом data pages можно писать

    Это не универсальное правило WAL-систем.

    Более точная модель:

    data page contains some change
↓
before this page is flushed
↓
corresponding WAL must already be durable

    То есть data page может в некоторых архитектурах попасть на storage:

    до transaction COMMIT

    если write-ahead condition выполнено.

    Как база потом отличает committed state от uncommitted и какой recovery protocol использует — это уже тема конкретной СУБД.

    Для PostgreSQL мы разберём это отдельно.

    35. Где появляется durable COMMIT¶

    Теперь другой вопрос:

    В какой момент клиенту можно сказать COMMIT OK?

    Для durable commit недостаточно, чтобы commit record просто существовал в RAM.

    Нужна цепочка:

    transaction work
↓
WAL records
↓
COMMIT record
↓
WAL flush / durability boundary
↓
только теперь ACK клиенту

    Главная формула:

    Durable commit можно подтвердить после того, как информация журнала, необходимая для восстановления этого commit после crash, стала durable.

    Это уже прямой мост от fsync() к транзакционной durability.

    36. Почему data pages можно не синхронизировать на каждом COMMIT¶

    После WAL flush transaction уже имеет durable recovery information.

    Data pages могут оставаться:

    dirty in memory

    и уходить на storage позже:

    background writer
checkpoint
ordinary writeback

    Получаем принципиальное разделение:

    commit latency
↓
WAL durability

data-file propagation
↓
background path

    Именно это позволяет не заставлять каждый commit синхронно записывать весь набор random data pages.

    37. Crash после ACK, но до записи data page¶

    Сценарий:

    WAL COMMIT durable
↓
client received COMMIT OK
↓
data page still old on storage
↓
machine crashes

    После restart:

    read durable WAL
↓
recovery
↓
reapply required changes
↓
data state reconstructed

    На высоком уровне это REDO:

    повторить изменения, которые должны быть durable,
но ещё не отражены в data files

    Точный recovery algorithm зависит от СУБД.

    38. WAL — не просто журнал аудита¶

    Плохая модель:

    WAL — файл, куда база логирует, что она делала.

    Слишком слабо.

    На текущем уровне WAL нужен ради:

    durability
+
crash recovery
+
write ordering
+
возможности откладывать data-page writes

    Он является частью протокола хранения.

    Не просто историей событий.

    39. Почему WAL обычно append-oriented¶

    Наш исходный problem:

    random data pages all over database

    Мы хотели заменить на:

    compact sequential durability stream

    Поэтому WAL естественно строится как append-oriented log:

    record
record
record
record
↓
sequential progression

    Storage намного проще эффективно обслуживать такой поток, чем множество мелких random durable updates.

    40. Но теперь каждый COMMIT требует flush¶

    Мы выиграли:

    много random durable data-page writes

    заменив их на:

    append WAL
+
durable flush

    Но durability boundary всё ещё дорогая.

    Наивно:

    T1
↓
fsync WAL

T2
↓
fsync WAL

T3
↓
fsync WAL

    При большом TPS storage быстро упрётся в latency flush.

    41. Group commit появляется сам¶

    Пусть несколько транзакций почти одновременно дошли до commit.

    Можно:

    T1 WAL ─┐
T2 WAL ─┼→ one WAL flush
T3 WAL ─┘

    После завершения одной durability operation:

    все commit records до durable position
↓
соответствующие transactions можно ACK

    Это group commit.

    Дорогая durability boundary амортизируется на несколько транзакций.

    42. Почему commit latency теперь зависит от fsync()¶

    Теперь цепочка уже прозрачная:

    transaction
↓
WAL append
↓
wait for durable WAL position
↓
fsync / equivalent persistence operation
↓
storage
↓
ACK

    Поэтому маленькая транзакция может менять всего сотню байт, но её latency всё равно зависеть от:

    durable flush latency

    А не от максимальных GB/s SSD.

    43. Database WAL и filesystem journal — разные журналы¶

    Теперь особенно важно не смешать два слоя.

    Database WAL¶

    Знает про:

    database pages
transactions
database recovery

    Его задача:

    восстановить корректное состояние СУБД

    Filesystem journal¶

    Знает про:

    inode
extents
directory metadata
filesystem consistency

    Его задача:

    восстановить корректную структуру filesystem

    Файловая система не знает:

    что такое банковский перевод
что такое PostgreSQL transaction
что такое row visibility

    А database WAL не отвечает за:

    целостность inode tree файловой системы

    44. Почему ext4 journal не заменяет PostgreSQL WAL¶

    Допустим filesystem после crash идеально восстановила:

    все inode
все extents
все directory entries

    Это ещё ничего не говорит о том:

    какая transaction committed
какие DB pages должны содержать какую logical version

    Filesystem видит bytes.

    Database видит transactional state.

    Поэтому нужны два recovery protocol на разных слоях.

    45. Почему PostgreSQL WAL не заменяет filesystem journal¶

    Обратная сторона.

    PostgreSQL может иметь идеальный WAL.

    Но его файлы всё равно хранятся:

    на filesystem

    Если filesystem после crash не может корректно восстановить свои metadata:

    файл может быть потерян / повреждён на уровне namespace/block mapping

    Database recovery не заменяет correctness нижнего storage layer.

    46. Где мы останавливаемся в этой лекции¶

    Здесь достаточно модели:

    fsync
↓
durable file primitive
↓
WAL
↓
transaction durability + recovery
↓
group commit

    Подробности конкретной PostgreSQL реализации оставляем на блок PostgreSQL:

    WAL record
LSN
WAL buffers
WAL writer
XLogFlush
checkpoint
REDO
full-page writes
replication
archive

    Сейчас они только перегрузили бы storage-path лекцию.

    47. Мост от storage к будущей лекции PostgreSQL¶

    Теперь полный путь commit уже можно нарисовать:

    SQL COMMIT
↓
database produces WAL
↓
WAL write
↓
Linux page cache / filesystem path
↓
fsync / persistence operation
↓
block layer
↓
NVMe
↓
SSD controller
↓
persistent media
↓
completion
↓
database sees WAL durable
↓

    А data pages:

    dirty database pages
↓

↓

    Вот теперь WAL действительно вытекает из fsync(), а не появляется внезапно отдельным термином.

    48. Journaling filesystem¶

    Filesystem тоже должен переживать crash.

    Например ext4/XFS используют журналирование metadata и ordering protocols.

    Упрощённо:

    filesystem change
↓
journal/log transaction
↓
persistent ordering
↓
metadata update

    fsync() может заставить закрыть эту цепочку для конкретного файла.

    49. Почему filesystem metadata вообще нужна durability¶

    Представим:

    new block contains correct data

    но после crash inode не знает, что этот block принадлежит файлу.

    Данные физически есть.

    Файл логически повреждён.

    Поэтому durability — это не только payload bytes.

    50. Delayed allocation¶

    Filesystem может отложить выбор physical blocks:

    write()
↓
page cache dirty
↓
later writeback
↓
allocate extents

    Плюсы:

    • крупнее extents;
    • меньше fragmentation;
    • лучше sequential placement.

    Цена:

    • placement решается позже;
    • ENOSPC может проявиться позже;
    • writeback path сложнее.

    51. Почему write() success не гарантирует отсутствие ENOSPC позже¶

    Buffered write мог лишь dirty'нуть page cache.

    Реальное block allocation:

    later

    Тогда:

    write() success
↓
delayed allocation
↓
writeback/fsync
↓
ENOSPC

    Durability-critical код должен обрабатывать поздние ошибки.

    52. Writeback I/O error¶

    То же с device failure:

    write()
↓
page cache
↓
return success
↓
later background I/O
↓
device error

    Поэтому один buffered write не является конечной точкой ошибки/durability.

    53. close() не заменяет fsync()¶

    Плохое упрощение:

    Закроем файл — всё точно запишется.

    Нет.

    close() закрывает descriptor.

    Если нужен explicit durable boundary:

    fsync / fdatasync / sync-open semantics

    должны быть частью протокола приложения.

    54. Directory durability¶

    Создание/rename файла меняет directory metadata.

    Crash-safe pattern часто включает:

    write temp
↓
fsync(file)
↓
rename
↓
fsync(directory)

    Потому что:

    file contents durable

    и:

    directory entry durable

    разные обязательства.

    55. Atomic rename¶

    rename() полезен как building block:

    old name
↓
atomically points to new inode/file state

    Но:

    atomic namespace update
≠
durable namespace after power loss

    Для второго нужен правильный sync protocol.

    56. mmap файла и page cache¶

    Memory-mapped file обычно использует тот же page cache.

    file
↓
page cache
├── read/write
└── mmap

    mmap не означает automatic bypass page cache.

    57. msync()¶

    Для modified mmap pages есть:

    msync()

    Он управляет синхронизацией mapping с backing file.

    Но filesystem metadata/durability semantics всё равно нужно понимать отдельно.

    58. Direct I/O¶

    O_DIRECT позволяет обойти обычный data page-cache path.

    Учебно:

    userspace buffer
↓
direct I/O
↓
filesystem/block layer
↓
device

    Но:

    O_DIRECT
≠
вообще никаких caches во всей системе

    У SSD остаются controller caches.

    59. Зачем DB может использовать Direct I/O¶

    Storage engine имеет собственный buffer pool.

    Если kernel тоже кэширует то же data:

    database buffer pool
+
page cache

    получаем double caching.

    Direct I/O позволяет БД сильнее контролировать:

    • caching;
    • eviction;
    • batching;
    • I/O scheduling.

    60. Цена Direct I/O¶

    Появляются ограничения:

    • alignment;
    • buffer lifetime;
    • I/O sizes;
    • filesystem/device rules.

    И приложение само отвечает за работу, которую раньше делал page cache.

    61. Buffered vs Direct¶

    Buffered I/O Direct I/O
    page cache bypass ordinary data page cache
    kernel caching application controls more
    удобно для мелких I/O alignment constraints
    write может быстро вернуть path ближе к device
    возможен double cache useful for DB buffer pools

    Ни один подход не универсально лучше.

    62. Переходим в block layer¶

    Filesystem решил:

    какие logical blocks нужно читать/писать

    Дальше:

    filesystem
↓
block layer
↓
device driver
↓
NVMe

    Это граница между filesystem semantics и устройством.

    63. Block device¶

    SSD/NVMe представлен Linux как block device.

    Filesystem переводит:

    file offset
↓
extent / block mapping
↓
logical block address

    Дальше filesystem уже работает через block I/O.

    64. bio¶

    Полезная историческая/учебная сущность block layer:

    bio

    Она описывает I/O:

    • страницы/buffers;
    • сектор/LBA;
    • направление;
    • flags;
    • размер.

    Учебно:

    filesystem
↓
"write these pages to these blocks"
↓
bio

    65. Request¶

    Block layer организует I/O в requests, которые dispatch'ятся драйверу.

    Упрощённо:

    bio
↓
request
↓
hardware queue
↓
driver

    Точные внутренние structures зависят от текущего blk-mq.

    66. Зачем block layer¶

    Он даёт общие механизмы:

    • queueing;
    • merging;
    • scheduling;
    • accounting;
    • device limits;
    • completion;
    • fairness.

    Filesystem не должен знать внутренности каждого controller.

    67. Blk-mq¶

    Современный Linux использует multi-queue block layer:

    blk-mq

    Идея:

    many CPUs
↓
local/software queues
↓
hardware queues
↓
device

    Зачем?

    Чтобы не получить:

    64 CPU
↓
one global block queue lock

    68. Знакомый runtime-паттерн¶

    Снова видим:

    hot path local
↓
global coordination less often

    То же было:

    • в Go scheduler;
    • в mcache;
    • в GC local work;
    • в Linux block layer.

    Причина одна:

    глобальная hot synchronization плохо масштабируется

    69. I/O scheduler¶

    Перед device dispatch может работать I/O scheduler.

    Для NVMe распространены политики вроде:

    none
mq-deadline

    Конкретный выбор зависит от kernel/device/workload.

    Scheduler может:

    • reorder;
    • merge;
    • enforce fairness;
    • влиять на latency.

    70. Почему NVMe часто не нужен HDD-style scheduler¶

    HDD:

    seek head

    дорогой.

    Reorder request'ов может радикально экономить механику.

    NVMe:

    • нет механической головки;
    • много hardware queues;
    • controller сам параллелит.

    Поэтому дополнительный сложный scheduler не всегда полезен.

    71. none не означает «очередей нет»¶

    Даже если scheduler:

    none

    остаются:

    • blk-mq queues;
    • driver queues;
    • NVMe submission queues;
    • controller queues;
    • NAND internal parallelism.

    Queueing никуда не исчезло.

    72. Queue depth¶

    Storage может выполнять много I/O одновременно.

    Количество outstanding commands:

    queue depth

    Слишком маленький queue depth:

    device недогружен

    Слишком большой:

    throughput высокий
↓
queueing latency высокий

    Это обычный throughput/latency trade-off.

    73. Little’s Law снова работает¶

    L = λW

    Для storage:

    outstanding requests
≈
IOPS × latency

    Если service rate не растёт, а очередь растёт:

    latency ↑

    Та же математика, что в connection pool и scheduler.

    74. NVMe¶

    NVMe — Non-Volatile Memory Express.

    Протокол проектировался под быстрые PCIe flash-устройства.

    Ключевые свойства:

    • много очередей;
    • большие queue depths;
    • низкий protocol overhead;
    • submission/completion model;
    • высокий parallelism.

    75. Submission Queue¶

    Driver помещает command в:

    NVMe Submission Queue

    Упрощённо command содержит:

    • opcode;
    • namespace;
    • LBA;
    • length;
    • buffer addresses;
    • flags.

    После этого controller нужно уведомить.

    76. Doorbell¶

    Driver обновляет:

    doorbell register

    Тем самым говорит controller:

    В submission queue появились новые команды.

    Дальше controller сам забирает work.

    77. Completion Queue¶

    После завершения:

    NVMe controller
↓
Completion Queue

    OS узнаёт о completion через:

    • interrupt;
    • polling;
    • hybrid mechanisms.

    Потом completion поднимается вверх по stack.

    78. Полный NVMe round trip¶

    block request
↓
NVMe submission queue
↓
doorbell
↓
controller
↓
flash operation
↓
completion queue
↓
interrupt/poll
↓
driver
↓
block completion
↓
filesystem
↓
waiting task wakes

    Вот что может скрываться под одним fsync().

    79. Interrupt против polling¶

    Interrupt:

    completion
↓
interrupt
↓
handler
↓
wake task

    Polling:

    CPU actively checks queue

    Polling тратит CPU.

    Но может уменьшить latency.

    Trade-off:

    CPU efficiency
↔
lowest latency

    80. SSD controller¶

    Под NVMe protocol находится сам SSD controller.

    Он делает:

    • command scheduling;
    • FTL;
    • garbage collection;
    • wear leveling;
    • ECC;
    • bad block management;
    • internal parallelism;
    • caching.

    Современный SSD — отдельная вычислительная система.

    81. NAND не является RAM¶

    В DRAM можно логически:

    write address

    и значение меняется.

    В NAND:

    program → page
erase → larger erase block

    Произвольный overwrite уже запрограммированных cells так не работает.

    Перед повторным использованием нужен erase более крупной области.

    82. FTL¶

    FTL — Flash Translation Layer.

    Он отображает:

    logical block address
↓
physical NAND location

    OS думает:

    LBA 12345

    Controller решает:

    die / plane / block / page

    Это ещё один слой виртуализации адресов.

    83. Out-of-place update¶

    Host пишет:

    LBA X

    Controller может реально:

    write new physical NAND page
↓
update mapping
↓
old physical page becomes invalid

    То есть физически запись часто идёт в другое место.

    84. Garbage collection внутри SSD¶

    Erase block содержит:

    valid pages
invalid pages
free pages

    Чтобы освободить его:

    copy remaining valid pages
↓
erase block
↓
block reusable

    Это internal garbage collection SSD.

    Да, GC у нас теперь есть и в Go, и в SSD — только задачи совершенно разные.

    85. Write amplification¶

    Host записал:

    1 GiB

    NAND мог физически записать:

    > 1 GiB

    из-за:

    • relocation;
    • GC;
    • metadata;
    • wear leveling.

    Отношение:

    physical NAND writes
/
host writes

    называют write amplification.

    86. Почему write amplification важен¶

    Чем он выше:

    internal work ↑
↓
latency ↑
↓
effective throughput ↓
↓
NAND wear ↑

    Storage может выглядеть медленным не потому, что host отправляет много данных, а потому что controller делает много внутренней работы.

    87. Over-provisioning¶

    SSD обычно имеет больше NAND capacity, чем отдаёт пользователю.

    Скрытая область нужна для:

    • GC;
    • wear leveling;
    • bad blocks;
    • free block reserve.

    Больше free internal space:

    GC easier
↓
write amplification lower
↓
sustained writes more stable

    88. Почему почти заполненный SSD может резко деградировать¶

    Когда free blocks мало:

    new write
↓
need internal GC
↓
copy valid pages
↓
erase
↓
write

    То есть одна host write может вызвать много background work.

    Поэтому:

    95% full

    и:

    50% full

    могут давать очень разную sustained latency.

    89. SLC cache¶

    Многие consumer SSD используют часть NAND как быстрый pseudo-SLC cache.

    Учебно:

    burst write
↓
SLC cache
↓
очень высокий throughput

    После заполнения:

    direct TLC/QLC programming
+
background folding
↓
throughput drops

    90. Почему короткий benchmark врёт¶

    Первые секунды:

    SLC cache empty
↓
5 GB/s

    Через минуту:

    cache exhausted
↓
700 MB/s

    Если production пишет долго:

    короткий benchmark

    не описывает sustained режим.

    91. Device DRAM cache¶

    Некоторые SSD имеют DRAM.

    Она может использоваться для:

    • FTL metadata;
    • mapping cache;
    • controller state;
    • buffering.

    Но возникает durability-вопрос:

    Если controller подтвердил command, данные уже persistent?

    Ответ зависит от device semantics.

    92. Volatile write cache¶

    Если device признал write завершённой, но data ещё только в volatile cache:

    power loss
↓
data lost

    Значит host должен уметь потребовать persistence.

    Появляются:

    flush
FUA

    93. Flush¶

    Учебная идея:

    Сделать ранее подтверждённые writes persistent согласно contract устройства.

    Цепочка:

    fsync
↓
filesystem ordering
↓
block layer
↓
device flush
↓
controller drains volatile state
↓
durability boundary

    94. FUA¶

    FUA — Force Unit Access.

    Идея:

    конкретная write
↓
completion только после нужной persistence semantics

    Filesystem/block layer может использовать FUA и flush в комбинации.

    95. Flush и FUA — разные операции¶

    Упрощённо:

    flush
→ сделать durable накопленные ранее writes

FUA
→ конкретная write должна считаться durable по completion

    Реальная sequence зависит от protocol/device/filesystem.

    96. Power Loss Protection¶

    Enterprise SSD могут иметь:

    PLP — Power Loss Protection

    Например capacitors дают controller время сохранить critical volatile state.

    Это особенно важно для:

    • database;
    • WAL;
    • metadata;
    • predictable durability.

    97. Почему consumer SSD и enterprise SSD — не одна категория¶

    Database полагается на storage durability contract.

    Consumer SSD может иметь:

    • маленький SLC cache;
    • большую latency variance;
    • слабее PLP;
    • aggressive GC;
    • firmware, ориентированный на desktop bursts.

    Enterprise device обычно оптимизируется под:

    • sustained write;
    • endurance;
    • predictable latency;
    • PLP.

    98. TRIM / discard¶

    Filesystem знает:

    эти logical blocks больше не нужны

    SSD controller этого сам не знает.

    TRIM/discard сообщает:

    these LBAs can be forgotten

    Это помогает:

    • internal GC;
    • free-space management;
    • write amplification.

    99. Online discard и fstrim¶

    Filesystem может:

    discard online

    или периодически:

    fstrim

    Trade-off:

    immediate metadata/device work
↔
batched discard later

    Конкретная политика зависит от filesystem/device.

    105. Почему batching критичен¶

    Было:

    1 record
↓

    Стало:

    100 records
↓
1 fsync

    Durability cost amortized.

    Это один из фундаментальных механизмов высокой производительности WAL.

    106. Tail latency fsync()¶

    Даже при хорошем average SSD может периодически выполнять:

    • internal GC;
    • wear leveling;
    • SLC folding;
    • FTL metadata work.

    Получаем:

    p50 = low
p99 = much higher
p99.9 = occasionally huge

    Для OLTP это критично.

    107. Queueing внутри устройства¶

    Даже если Linux queues короткие:

    SSD controller

    может иметь собственную internal queueing.

    Поэтому нужно различать:

    host queueing
device service time
device internal queueing

    108. IOPS — не вся история¶

    Спецификация:

    1 000 000 IOPS

    может быть измерена при:

    • QD64;
    • 4 KiB random read;
    • определённом mix;
    • fresh/preconditioned state.

    А DB workload:

    QD1
8 KiB
sync write

    совсем другой.

    109. Sequential bandwidth — не WAL latency¶

    7 GB/s sequential

    ничего не гарантирует про:

    8 KiB durable write + fsync at QD1

    Latency и bandwidth — разные характеристики.

    110. Random write¶

    Random writes усложняют FTL:

    • scattered mappings;
    • invalid pages;
    • relocation;
    • internal GC.

    Поэтому write amplification часто выше.

    111. Sequential write¶

    Sequential host writes легче агрегировать и размещать.

    Это одна из причин, почему:

    WAL append

    storage-friendly по сравнению с random in-place updates.

    112. Page cache и database buffer pool¶

    БД может иметь собственный buffer pool.

    Если kernel тоже хранит те же pages:

    DB cache
+
page cache

    получаем double caching.

    Другие engines используют Direct I/O, чтобы сильнее контролировать memory/storage path.

    113. WAL и page cache¶

    Даже WAL write может сначала попасть:

    userspace
↓
page cache

    Но transaction commit ждёт:

    sync boundary

    Поэтому:

    WAL write
≠
durable commit

    114. PostgreSQL-like commit path¶

    Учебно:

    transaction
↓
generate WAL record
↓
append WAL
↓
flush WAL
↓
commit acknowledged

    Data pages можно writeback'ить позже.

    Durability переносится на журнал.

    115. Что если durability отключить¶

    Если ack даётся после ordinary write:

    data may exist only in volatile layers

    При power loss:

    acknowledged transaction
↓
may disappear

    Это смена correctness contract.

    Не просто performance tuning.

    116. Device completion ещё нужно правильно понимать¶

    Completion означает:

    command completed according to command semantics

    Но persistence зависит от:

    • write cache mode;
    • flush;
    • FUA;
    • PLP;
    • firmware correctness.

    То есть:

    NVMe completion

    и:

    power-loss-safe durability

    связаны через protocol semantics.

    117. Почему UPS не заменяет storage semantics¶

    UPS снижает риск полного power loss.

    Но остаются:

    • kernel panic;
    • controller reset;
    • PCIe error;
    • firmware crash;
    • host reboot;
    • power path failure.

    Correctness строят на documented persistence protocol.

    118. Диагностика: iostat¶

    Базовый инструмент:

    iostat -x 1

    Смотрим идеи:

    • IOPS;
    • throughput;
    • request size;
    • queueing;
    • latency;
    • utilization.

    Названия колонок могут различаться между версиями sysstat.

    119. await¶

    Традиционно:

    await

    отражает среднюю latency I/O с учётом host-visible queueing.

    Нельзя читать:

    await = raw NAND latency

    Это агрегированная метрика всего видимого block path.

    120. %util¶

    Для старых single-queue devices:

    100%

    Для современного multi-queue NVMe:

    100% util

    не означает автоматически:

    никакой capacity больше нет

    Нужно смотреть:

    • latency;
    • queue depth;
    • IOPS;
    • device behaviour.

    показывает process I/O activity.

    Полезно связать:

    194. Нельзя путать crash consistency и durability¶

    Durability:

    Подтверждённые данные переживают crash согласно contract.

    Crash consistency:

    После crash структура данных остаётся в допустимом состоянии.

    Filesystem journal и WAL решают похожие, но не идентичные задачи на разных уровнях.

    195. WAL не заменяет filesystem¶

    WAL обеспечивает recovery protocol базы.

    Filesystem обеспечивает:

    • file namespace;
    • block mapping;
    • metadata consistency;
    • storage access.

    Database WAL работает поверх filesystem/storage semantics.

    196. Filesystem journal не заменяет database WAL¶

    Filesystem journal знает:

    filesystem metadata

    Он не знает:

    transaction invariant database

    Поэтому:

    ext4 journal

    не делает ненужным:

    PostgreSQL WAL

    Это разные уровни consistency.

    Что важно запомнить¶

    1. write() success обычно означает, что kernel принял данные, а не что NAND уже изменена.
    2. Page cache скрывает device latency и объединяет I/O, но создаёт промежуток между write и durability.
    3. Dirty pages — это накопленная очередь storage work.
    4. Если dirtying rate выше sustained writeback rate, backlog растёт и Linux начинает throttling writers.
    5. Memory pressure и writeback связаны: dirty pages нельзя просто reclaim'нуть без сохранения.
    6. fsync() — durability boundary, а не просто «ещё один write».
    7. fdatasync() имеет более узкий data-centric contract, но выигрыш зависит от filesystem.
    8. WAL переводит random durable updates в компактную sequential durability path.
    9. Group commit амортизирует стоимость durable flush.
    10. Filesystem journal и database WAL решают разные consistency-задачи.
    11. Delayed allocation улучшает placement, но может сдвигать часть ошибок к writeback/fsync.
    12. close() не является универсальной заменой fsync().
    13. Direct I/O убирает ordinary data page cache, но не делает storage path cache-free.
    14. Blk-mq масштабирует block I/O через multi-queue architecture.
    15. Queue depth — ограниченный ресурс: он повышает throughput, но увеличивает queueing latency.
    16. NVMe использует submission/completion queues и PCIe, но всё равно имеет очереди и protocol overhead.
    17. SSD controller скрывает FTL, garbage collection, wear leveling и internal scheduling.
    18. NAND требует out-of-place updates и erase более крупными блоками, поэтому SSD не является «RAM, которая не забывает».
    19. Internal SSD GC создаёт write amplification и tail-latency spikes.
    20. SLC cache может сильно завышать короткие consumer-SSD benchmarks.
    21. Flush/FUA нужны потому, что device может иметь volatile write cache.
    22. PLP — часть storage durability engineering.
    23. Sequential bandwidth не описывает QD1 fsync() latency.
    24. Высокий device IOPS из datasheet не переносится автоматически на WAL/OLTP workload.
    25. Для диагностики нужно последовательно идти: syscall → page cache/writeback → filesystem → block layer → device.
    26. strace, iostat, /proc/meminfo, pidstat, fio, eBPF и device telemetry отвечают на разные вопросы.
    27. Container overlayfs и I/O cgroup limits могут добавить latency выше physical device.
    28. Storage overload может перерасти в memory pressure через dirty pages.
    29. Memory pressure может перерасти в storage pressure через reclaim/writeback.
    30. Настоящая стоимость durable write определяется всей цепочкой от userspace до persistent media.

    Главный инженерный вывод:

    Linux storage path — это цепочка кешей, очередей и durability boundaries. Page cache делает обычный write() дешёвым, пока storage успевает догонять. fsync() возвращает физическую цену persistence обратно в request path. Ни NVMe, ни SSD не являются «мгновенным диском»: ниже block layer остаются queueing, controller, FTL, NAND, internal GC и volatile caches. Поэтому backend-разработчик должен различать «ядро приняло данные», «I/O завершилось» и «данные переживут crash».
