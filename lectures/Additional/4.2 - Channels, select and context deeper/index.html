    4.2. Каналы, select и context глубже¶

    Материал ориентирован на Go 1.27.x.

    Это продолжение обычной лекции Go under the hood и уже прочитанной Runtime deep.

    Здесь мы не повторяем G/M/P, sudog, gopark, goready, состояния горутин и общую механику парковки. Они считаются известным фундаментом.

    Нас интересует следующий слой:

    канал
↓
какой конкретно путь выбирает рантайм?

select
↓
как одна G регистрируется сразу на нескольких каналах?

context
↓
как отмена физически распространяется по дереву?

    Зачем открывать этот слой¶

    На основной лекции достаточно было модели:

    отправка
├── получатель уже ждет
├── есть место в буфере
└── парковка

получение
├── отправитель уже ждет
├── есть данные в буфере
└── парковка

    Для select:

    несколько операций
↓
зарегистрировать одну G в нескольких очередях ожидания
↓
парковка
↓
одна ветка победила
↓
убрать остальные регистрации

    Для context:

    parent
↓
children
↓
Done
↓
cancel

    Эта модель правильная.

    Но она оставляет несколько неудобных вопросов.

    Если получатель уже ждет, зачем вообще использовать буфер?

    Если значение отправителя лежит на его стеке, а получатель спит со своим стеком, кто и куда копирует байты?

    Если буферизованный канал заполнен и один отправитель уже припаркован, что именно делает следующий получатель?

    Почему close(ch) будит получатели и отправители по-разному?

    Как selectgo избегает дедлока, если один select одновременно берет локи нескольких каналов?

    Почему одна G может зарегистрироваться в десяти каналах, но проснуться должна ровно от одного?

    И наконец:

    Правда ли, что каждый дочерний Context требует отдельную горутину для распространения отмены?

    Нет.

    Вот это и разбираем.

    0. Сначала проведем границу с уже прочитанным рантаймом¶

    Уже известно:

    операция не может продолжаться
↓
создается/используется sudog
↓
G связывается с объектом ожидания
↓
gopark
↓
G → ожидающий

событие произошло
↓
goready
↓
G → RUNNABLE

    Уже известно и зачем sudog существует отдельно от G:

    одна G
↔
несколько ожиданий

    Особенно это важно для select.

    Поэтому дальше, когда увидим:

    sendq + sudog + парковка

    мы не будем снова открывать планировщик.

    Нас интересует то, что произошло до парковки и после пробуждения.

    2. make(chan T, n) — что вообще нужно создать¶

    Пишем:

    ch := make(chan Job, 128)

    На уровне языка:

    канал capacity = 128
element type = Job

    Рантайму нужно получить:

    hchan
+
память под 128 элементов Job

    И сразу появляется первый вопрос:

    Это всегда две отдельные аллокации?

    Нет.

    3. Что концептуально находится в hchan¶

    Текущая реализация содержит поля примерно такого смысла:

    hchan
├── qcount    — сколько элементов сейчас в буфере
├── dataqsiz  — емкость буфера
├── buf       — адрес кольцевого буфера
├── elemsize  — размер одного элемента
├── elemtype  — тип элемента
├── closed    — закрыт ли канал
├── sendx     — индекс следующей записи
├── recvx     — индекс следующего чтения
├── recvq     — ожидающие получатели
├── sendq     — ожидающие отправители
└── lock      — внутренний лок

    Названия полей — деталь реализации.

    Но инварианты важны.

    Для буферизованный канал:

    qcount > 0
→ recvq пуст

    и:

    qcount < dataqsiz
→ sendq пуст

    Почему?

    Если в буфере уже есть данные, получатель не должен ждать.

    Если в буфере есть свободное место, отправитель не должен ждать.

    Это не оптимизация.

    Это логическое следствие корректного состояния канала.

    4. Размер элемента проверяется при создании¶

    makechan получает описание типа элемента.

    Рантайму нужны:

    elem.Size
elem.Align
содержит ли elem Go-указатели

    Почему размер понятен:

    байты буфера
=
capacity × sizeof(T)

    Но зачем уже здесь знать про указатели?

    Сейчас увидим.

    5. Канал без буфера и канал с нулевым размером элемента¶

    Если:

    make(chan struct{})

    или:

    make(chan int)

    где capacity равен нулю, пользовательского массива элементов нет.

    Текущему рантайму достаточно выделить сам hchan.

    Учебно:

    hchan
+
байты буфера = 0

    Отдельный backing array не нужен.

    6. Буфер без Go-указателей: hchan и данные можно выделить вместе¶

    Например:

    make(chan [64]byte, 128)

    Элементы не содержат Go-указателей.

    Текущий makechan может сделать:

    одна аллокация

┌───────────────┬────────────────────────────┐
│     hchan     │ буфер                     │
│               │ [T][T][T][T]...            │
└───────────────┴────────────────────────────┘

    То есть:

    c = mallocgc(hchanSize + bufferBytes)
c.buf = адрес сразу после hchan

    Почему это удобно?

    • одна аллокация вместо двух;
    • метаданные и буфер физически рядом;
    • GC не нужно сканировать буфер на предмет Go-указателей.

    Последний пункт уже знаком из GC deep.

    7. Буфер содержит Go-указатели — путь другой¶

    Теперь:

    make(chan *Node, 128)

    или:

    type Job struct {
    User *User
}

make(chan Job, 128)

    буфер содержит Go-указатели.

    Текущая реализация делает отдельные объекты:

    hchan
↓
отдельный буфер, типизированный как T

    Почему?

    Потому что GC должен понимать карта указателей буфера.

    Получаем красивую связь с предыдущей лекцией:

    тип элемента канал
↓
карта указателей
↓
способ аллокации буфер
↓
работа GC

    Канал — синхронизационная конструкция.

    Но его физическая стоимость уже зависит от модели памяти.

    8. Цена буфера появляется еще до первой отправки¶

    Пусть:

    make(chan [4096]byte, 10_000)

    Логически:

    capacity = 10 000

    Физически:

    ≈ 40 MiB буфер

    То есть большой канал буфер — не абстрактное число.

    Это реальная память.

    И если элементы содержат указатели:

    больше памяти с указателями
↓
больше потенциальной scan-work GC

    Мы еще даже ничего не отправили.

    9. Теперь открываем chansend¶

    Пишем:

    ch <- value

    Компилятор в общем случае приводит нас к рантайм entry point отправки.

    Как компилятор делает lowering — оставим 4.3.

    Здесь начинаем с того момента, когда рантайм уже получил:

    c  → *hchan
ep → адрес отправляемого значения
block → можно ли ждать

    10. Nil-канал — особый случай еще до захвата лока¶

    Если:

    var ch chan int
ch <- 42

    то:

    c == nil

    блокирующий send:

    парковка forever

    Неблокирующий рантайм-путь:

    возврат false

    Никакого hchan.lock нет.

    Потому что самого hchan нет.

    11. Неблокирующая отправка имеет путь без лока¶

    Это особенно интересно для select с default и некоторых специализированных compiler paths.

    Текущий chansend умеет проверить:

    операция неблокирующая
+
канал еще не закрыт
+
канал сейчас заполненный
↓
send сейчас невозможен
↓
возврат false

    без захвата hchan.lock.

    12. Но мы прочитали два поля без общего лока. Это вообще корректно?¶

    Проверяются факты вроде:

    closed == 0
заполненный(c) == true

    Между чтениями состояние может измениться.

    То есть мы не получили атомарный snapsгорячий всей структуры.

    Почему ответ все равно корректен?

    Потому что неблокирующей операции не нужно доказать:

    Канал был полон в некоторый магический единый наносекундный момент, который мы сохранили навсегда.

    Ей нужно доказать:

    Существовал момент наблюдения, в который канал еще не был закрыт и send не мог завершиться немедленно.

    Свойства переходов состояния позволяют это вывести.

    Это пример более общей идеи:

    Иногда корректность lock-free быстрый путь строится не на полном snapsгорячий, а на монотонности и допустимом линейзационном моменте.

    Memory ordering мы уже разбирали.

    Здесь нас интересует применение этой идеи в канале.

    13. Обычный chansend: теперь берем лок¶

    Если быстрый путь не завершил операцию:

    lock(hchan)

    Первое, что нужно проверить под локом:

    closed?

    Если канал закрыт:

    unlock
↓
panic("send on closed канал")

    Это уже точная точка, где обычный send обнаруживает закрытие до регистрации ожидания.

    14. Первый предпочтительный путь: получатель уже ждет¶

    Под локом:

    recvq.dequeue()

    Если ожидающий получатель найден:

    отправляемое значение прямойly
↓
буфер не нужен

    Даже если канал буферизованный.

    Это важный момент.

    15. Почему ожидающий получатель важнее свободного места в буфере¶

    Пусть:

    емкость буфера = 100
буфер пустой
recvq содержит G2

    Приходит G1:

    ch <- value

    Можно было бы:

    G1 → буфер
потом
буфер → G2

    Но получатель уже известен.

    Тогда лишний промежуточный storage бессмыслен.

    Текущий рантайм делает прямая передача.

    16. Небуферизованный канал: встреча превращается в реальное копирование¶

    ch := make(chan Job)

    G2 уже выполняет:

    job := <-ch

    и припаркована.

    G1 выполняет:

    ch <- value

    Логически:

    G1
↓ value
G2

    Но физически где лежат данные?

    17. Значение отправителя может находиться на стеке G1¶

    Пусть:

    func send(ch chan Job) {
    j := Job{...}
    ch <- j
}

    j может находиться:

    стек G1

    получатель подготовил место назначения:

    стек G2

    Получаем необычную операцию:

    стек G1
↓
рантайм
↓
стек G2

    Без:

    heap object

    и без:

    канал буфер

    18. sendDirect: рантайм пишет в стек другой горутины¶

    В текущем рантайм есть специальный путь:

    sendDirect

    Его смысл:

    src → стек отправитель
dst → слот в стеке получатель
↓
скопировать T

    Это один из редких случаев, когда работающая горутина через рантайм инициирует запись в стек другой горутины.

    И вот здесь обычная модель Go начинает серьезно протекать.

    19. Почему обычного typedmemmove недостаточно¶

    GC обычно исходит из важного предположения:

    Запись в стек горутина выполняется самой этой горутина, пока она работает.

    Прямой канал handoff это предположение нарушает.

    Мы пишем в стек другой G.

    Для с указателями T нужно сохранить корректность GC.

    Поэтому текущий путь использует:

    typeBitsBulkBarrier
+
memmove

    а не просто обычный типизированный перенос как для область в хипе.

    20. Почему sg.elem нельзя просто прочитать и потом спокойно использовать¶

    sudog.elem может указывать в стек ожидающей G.

    Но стек Go умеет перемещаться.

    Значит:

    прочитали dst из sg.elem
↓
если сейчас случится безопасная точка и перемещение стека
↓
старый dst может устареть

    Поэтому между чтением sg.elem и использованием адреса рантайм не должен допустить окно, в котором стек назначения переедет.

    Эта проблема уже знакома из Runtime deep.

    Здесь видно конкретное место, где она влияет на реализацию канала.

    21. Прямая передача заканчивается пробуждением получателя¶

    После копирования:

    sg.success = true
↓
unlock(канал)
↓
goready(получатель)

    Механику goready не повторяем.

    Но важен порядок:

    сначала данные и состояние операции
↓
потом получатель снова может выполняться

    получатель должен проснуться уже в мире, где его операция завершена.

    22. Второй путь отправки: в буфере есть свободное место¶

    Если ожидающий получатель нет:

    qcount < dataqsiz

    Тогда:

    qp = chanbuf(c, sendx)
↓
`typedmemmove`(elemtype, qp, ep)
↓
sendx++
↓
если конец → sendx = 0
↓
qcount++

    И:

    unlock
возврат

    Никакого парковка.

    23. chanbuf(c, sendx) — адрес конкретной ячейки¶

    Учебно:

    buf
+
sendx × elemsize
↓
адрес ячейки

    То есть рантайм должен хранить:

    buf
sendx
elemsize

    Именно поэтому тип элемента нужен не только GC.

    Он нужен для адресной арифметики и корректного копирования.

    24. Кольцевой буфер: почему элементы не сдвигаются¶

    Пусть:

    capacity = 4

    Индексы:

    0 → 1 → 2 → 3 → 0

    После receive рантайм не делает:

    [B][C][D][_]
↓
сдвинуть все влево

    Он просто двигает recvx.

    После send — sendx.

    Получаем O(1) работу относительно длины очереди.

    25. qcount не вычисляется как sendx - recvx¶

    Можно было бы попытаться вывести число элементов только из индексов.

    Но в кольце:

    sendx == recvx

    может означать:

    буфер пустой

    или:

    буфер заполненный

    Нужно дополнительное состояние.

    Текущий hchan хранит:

    qcount

    явно.

    26. Третий путь отправки: продолжать нельзя¶

    Нет ожидающий получатель.

    буфер заполнен.

    Для блокирующий send:

    acquireSudog
↓
sg.elem → отправляемое значение
↓
sg.g → текущая G
↓
sendq.добавить в очередь(sg)
↓
парковка

    На этом месте останавливаемся.

    acquireSudog, gp.waiting, gopark, состояние G уже разобраны в Runtime deep.

    27. Но зачем sg.elem хранит адрес отправляемого значения¶

    отправитель припаркован.

    получатель придет позже.

    Нужно откуда-то получить значение.

    Можно было бы скопировать значение в отдельный heap-object при блокировке.

    Но это означало бы:

    каждый заблокированный send
↓
дополнительное копирование / storage

    Вместо этого sudog может ссылаться на исходный слот значения.

    Это быстрее.

    Цена — жесткая связь с жизненным циклом и перемещением стек.

    28. Проснулись после заблокированной отправки. Как понять почему?¶

    После gopark G продолжает выполнение внутри chansend.

    Возможны два принципиально разных события:

    получатель принял значение

    или:

    канал закрыли

    sudog.success позволяет различить эти пути.

    Успех:

    возврат true

    Закрытие:

    канал действительно closed?
↓
panic("send on closed канал")

    29. Почему panic выполняет отправитель, а не closechan¶

    Это важно.

    closechan может обнаружить ожидающего отправитель.

    Но panic должен возникнуть как результат его операции:

    ch <- value

    Поэтому closechan:

    помечает ожидание как неуспешное
↓
делает G runnable

    40. Текущий recv делает обмен за одну критическую секцию¶

    головная ячейка буфера → получатель

    и одновременно:

    ожидающий значение отправителя → освободившаяся ячейка

    То есть логически:

    до:

после:
[B][C][D][E]

    Но массив физически не сдвигается.

    41. Почему начало и конец очереди здесь попадают в одну физическую ячейку¶

    В полном ring буфер:

    sendx == recvx

    Это как раз двусмысленное состояние, для которого нам нужен qcount.

    recvx указывает на head.

    Но когда head забрали, эта же физическая ячейка становится позиция конца очереди для следующего элемента.

    Поэтому рантайм может:

    qp = chanbuf(c, recvx)

qp → получатель
отправитель → qp

    за один заход.

    42. Индексы после такой операции¶

    После полного получение из буфера с ожидающий отправитель:

    recvx++

    и:

    sendx = recvx

    с учетом переход через конец кольца.

    qcount остается:

    полным

    Потому что:

    один элемент ушел
+
один элемент сразу пришел

    То есть:

    qcount не меняется

    Это очень красивый инвариант.

    43. Почему этот путь полезен под нагрузкой¶

    В производитель/потребитель системе буфер постоянно около заполненный.

    Без специального пути:

    каждый receive
→ освободить место
→ отдельный отправитель пробуждение
→ новый lock
→ отдельная запись

    Со специальным путем:

    одна критическая секция
↓
получение из головы + запись ожидающего отправителя

    Меньше переходов между состояниями.

    Меньше лишней работы scheduler.

    44. Обычное получение из буфера¶

    qcount > 0

    тогда:

    qp = chanbuf(c, recvx)

↓
`typedmemclr`(qp)
↓

↓
при необходимости перейти в начало кольца
↓

    Почему typedmemclr?

    45. Почему освобожденную ячейку буфера нужно очищать¶

    Пусть:

    chan *User

    получатель забрал указатель.

    Если старый указатель останется физически в ячейка буфера:

    логически slot свободен
но байты все еще содержат *User

    Для GC это может создать нежелательное удержание или некорректную состояние указателей в типизированной памяти.

    Поэтому освобождаемая ячейка очищается тип-aware операцией.

    Связь с GC тут прямая.

    49. Теперь closechan¶

    Семантика уже известна.

    Но одна строка:

    close(ch)

    может затронуть:

    весь recvq
+
весь sendq

    То есть цена close зависит не только от самого hchan.

    Она зависит от числа ожидающих операций.

    50. Закрытие nil и повторное закрытие¶

    Текущий рантайм сразу защищает два случая:

    close(nil)
→ panic

    и:

    close(already closed)
→ panic

    Потом под hchan.lock:

    closed = 1

    Теперь нужно разобрать очереди.

    51. Сначала освобождаются ожидающие получатели¶

    Для каждого sudog в recvq:

    если есть место назначения
→ `typedmemclr`(место назначения)

    Затем:

    sg.success = false
gp.param = sg

    То есть проснувшийся получатель увидит:

    операция завершилась не обычным receive

    и получит zero value / ok=false.

    52. Потом разбираются ожидающие отправители¶

    Для каждого waiter из sendq:

    sg.elem = nil
sg.success = false
gp.param = sg

    Это еще не panic.

    Это подготовка результата.

    Сам отправитель после пробуждения продолжит chansend и дойдет до:

    send on closed канал

    53. Почему closechan не вызывает goready под локом¶

    Обрати внимание на дизайн.

    Под hchan.lock рантайм:

    1. переводит состояние канала в closed
2. извлекает waiters
3. готовит их результаты
4. складывает G во временный glist

    Потом:

    unlock(hchan)

    И только после этого:

    goready(получатель/отправитель)

    54. Почему это принципиально¶

    Комментарий рантайм прямо запрещает менять состояние другой G, удерживая hchan.lock.

    Причина связана со уменьшением стека и взаимными зависимостями runtime.

    Но даже на более общем уровне правило хорошее:

    внутри критическая секция
→ только изменить защищаемую структуру

после unlock
→ делать внешние действия / пробуждения

    Так критическая секция короче и безопаснее.

    55. close с большой очередью ожидания — это O(N) работа¶

    Пусть:

    recvq = 50 000 горутины

    close(ch) должен:

    пройти очередь
↓
подготовить 50 000 ожиданий
↓
после unlock сделать G runnable

    Логически:

    close

    выглядит как одна операция.

    Физически:

    работа пропорциональна числу waiters

    А после этого scheduler получает всплеск готовых к выполнению горутин.

    Механику scheduler всплеск уже знаем.

    56. Внутреннее устройство канала: что важно запомнить¶

    1. makechan знает размер и карта указателей элемента.
    2. буфер без Go-указателей может быть выделен вместе с hchan.
    3. chansend сначала предпочитает ожидающий получатель, потом буфер, потом парковка.
    4. ожидающий получатель получает прямая передача без промежуточной записи в буфер.
    5. Небуферизованный канал может копировать значение прямо между стеками разных горутин.
    6. Для такого стек-to-стек copy нужен специальный путь с учетом барьера GC.
    7. Buffered send использует sendx, получение из буфера — recvx.
    8. заполненный получение из буфера с ожидающий отправитель одновременно забирает head и кладет значение отправителя в ту же физическую ячейку.
    9. closechan по-разному подготавливает получатели и отправители.
    10. G пробуждаются уже после освобождения hchan.lock.

    57. Переходим к select¶

    Один канал теперь разобран.

    Но select меняет задачу:

    select {
case v := <-a:
    use(v)

case b <- x:
    sent()

case <-c:
    done()
}

    Одна G.

    Три потенциальных операции.

    Нужно:

    не пропустить готовую операцию
не получить deadlock на локи каналов
не зарегистрироваться дважды некорректно
проснуться только от одного `case`
после пробуждение убрать проигравшие регистрации

    Вот почему selectgo заметно сложнее if.

    58. Что уже сделал компилятор до selectgo¶

    Текущий рантайм получает массив case descriptors.

    Учебно:

    s`case`
├── канал
└── elem

    Где elem — адрес отправляемого или принимаемого значения.

    Кроме того, рантайм получает временную память под два порядка:

    pollOrder
lockOrder

    Важная деталь:

    Эти массивы находятся на стеке горутина, а не создаются как отдельные heap-объекты внутри selectgo.

    Как компилятор их строит — тема 4.3.

    59. Простой select может вообще не дойти до общего selectgo¶

    Текущий компилятор умеет переписывать простые формы вроде:

    0 `case`
1 `case`
1 `case` + default

    в более специализированный код.

    Поэтому:

    select syntax
≠
обязательно runtime.selectgo

    Мы это только фиксируем.

    Подробно lowering посмотрим в 4.3.

    60. Общий selectgo начинает с двух разных порядков¶

    Нужны:

    pollOrder

    и:

    lockOrder

    Почему нельзя один?

    Потому что они решают противоположные задачи.

    61. pollOrder: убрать систематический приоритет¶

    Если всегда проверять:

    `case` 0
`case` 1
`case` 2

    первый готовый case получит структурное преимущество.

    Поэтому рантайм строит псевдослучайную перестановку case.

    Это не строгая fairness-гарантия.

    Но это убирает постоянный перекос текстового порядка.

    62. Как строится pollOrder¶

    Текущий алгоритм добавляет case по одному.

    Для каждого нового элемента:

    n уже добавлено
↓
j = random[0..n]
↓
новый `case` меняется местами с позицией j

    Упрощенно:

    было:
[A B C]

добавляем D
j = 1

получаем:
[A D C B]

    Это incremental shuffle.

    Отдельный временный массив и отдельный второй проход для перемешивания не нужны.

    63. Nil-каналы вообще не попадают в рабочие порядки¶

    Если case использует:

    nil канал

    он никогда не станет готовый.

    Поэтому selectgo исключает такой case из:

    pollOrder
lockOrder

    И заодно очищает ссылку на element, чтобы GC не удерживал данные без необходимости.

    Это конкретный рантайм-эффект известной семантики nil-канал.

    64. lockOrder: совершенно другая задача¶

    Теперь два concurrent select.

    Первый использует:

    A, B

    Второй:

    B, A

    Если брать локи в текстовом или случайном порядке:

    G1: lock A
G2: lock B
G1: wait B
G2: wait A

    Получили deadlock внутри runtime.

    Нужен глобально согласованный порядок.

    65. Поэтому каналы сортируются по ключу рантайма¶

    Текущая реализация сортирует case по ключу hchan.

    Учебная модель:

    все select
↓
одна функция порядка каналов
↓
одинаковый набор каналы
→ одинаковый порядок lock

    Тогда cycle:

    A → B
и
B → A

    не возникает.

    66. Почему используется пирамидальная сортировка¶

    Текущий selectgo строит lockOrder через heap sort.

    Комментарий рантайм объясняет две цели:

    O(N log N)
+
constant стек footprint

    Почему не обычная удобная сортировка из standard library?

    Потому что мы уже внутри рантайм горячий путь и хотим контролировать память и стек.

    67. Несколько case на одном канале¶

    Один select может содержать несколько операций над тем же канал.

    Например:

    select {
case <-ch:
case ch <- x:
}

    lockOrder содержит case.

    Но sellock не берет один и тот же hchan.lock повторно для соседних entries одного канал.

    Иначе рантайм сам deadlock'нулся бы на нерекурсивном локе.

    68. Теперь все локи каналов взяты¶

    sellock(s`case`, lockOrder)

    После этого можно безопасно исследовать состояние всех участвующих каналы как согласованный набор относительно других операции с каналами, которые требуют тех же локи.

    И начинается первый проход.

    69. Проход 1: сначала ищем операцию, которую можно выполнить прямо сейчас¶

    selectgo идет по:

    pollOrder

    Для receive case проверяет:

    есть ожидающий отправитель?
есть данные в буфер?
канал closed?

    Для send case:

    канал closed?
есть ожидающий получатель?
есть место в буфер?

    Нашли готовый case:

    выполнить его сразу
↓
select завершен

    Никакой парковки.

    70. Почему готовый case нужно искать до регистрации ожиданий¶

    Представим:

    канал уже содержит данные

    Плохой алгоритм:

    создать sudog
↓
добавить в очередь
↓
парковка
↓
кто-то сразу пробуждение

    Мы создали служебную работу для операции, которую можно было закончить прямо сейчас.

    Поэтому:

    сначала дешевый готовый path
↓
только потом регистрация ожиданий

    Это повторяющийся дизайн runtime.

    71. Получение в первом проходе¶

    Порядок логически такой:

    ожидающий отправитель?
↓
буфер contains value?
↓
closed?

    Почему ожидающий отправитель проверяется раньше буфер?

    Для заполненный буферизованный канал ожидающий отправитель означает специальный путь:

    головная ячейка → получатель
ожидающий отправитель → освободившаяся ячейка

    То есть рантайм уже знает оптимальный переход состояния канал.

    72. Отправка в первом проходе¶

    Для send:

    closed?
↓
ожидающий получатель?
↓
буфер has space?

    Closed проверяется первым, потому что:

    send on closed канал

    всегда panic.

    Даже если где-то есть получатель.

    Семантика закрытия важнее потенциальной готовности другой стороны.

    73. default: если ничего не готово, можно сразу выйти¶

    Если select неблокирующий:

    select {
case <-a:
case b <- x:
default:
}

    и проход 1 не нашел готовый case:

    selunlock
↓
возврат default

    До создания sudog дело не доходит.

    То есть default меняет не только семантику.

    Он буквально отсекает всю вторую половину алгоритма ожидания.

    74. Ничего не готово, и default нет¶

    Вот теперь начинается настоящая блокировка.

    Нужно сделать одну G ожидающей сразу на нескольких операции с каналами.

    Для каждого case:

    acquireSudog
↓
sg.g = current G
↓
sg.isSelect = true
↓
sg.elem = address of `case` value
↓
sg.c = канал

    И потом:

    send `case` → sendq
receive `case` → recvq

    75. Одна G получает несколько sudog¶

    Пусть:

    select {
case <-a:
case <-b:
case c <- x:
case <-d:
}

    Получаем:

    a.recvq → sudog A ─┐
b.recvq → sudog B ─┤
c.sendq → sudog C ─┼→ G
d.recvq → sudog D ─┘

    Это уже было концептуально.

    Теперь важная новая деталь:

    Рантайм еще связывает эти sudog в собственный список gp.waiting.

    76. Почему gp.waiting строится в lockOrder¶

    selectgo собирает список ожиданий в том же порядке, в котором отсортированы локи каналов.

    Это нужно не для красоты.

    Позже selparkcommit должен:

    идти по gp.waiting
↓
безопасно отпускать локи каналов

    Если список уже упорядочен:

    одинаковые каналы идут рядом

    можно корректно отпускать каждый lock один раз.

    77. Почему регистрация выполняется под локами каналов¶

    Представим плохой алгоритм:

    проверили канал A
↓
ничего не готовый
↓
unlock A
↓
позже добавить в очередь waiter

    Между:

    unlock

    и:

    добавить в очередь

    отправитель может выполнить send.

    Он увидит:

    получатель нет

    и уйдет дальше.

    Потом получатель зарегистрируется.

    Сигнал уже потерян.

    78. Классическая проблема потерянного пробуждения¶

    Нужно атомарно по смыслу связать:

    проверили условие
+
зарегистрировали ожидание

    Такой же класс проблем встречается в condition variables, futex-подобных протоколах и других wait/пробуждение схемах.

    В selectgo локи каналов обеспечивают эту связь.

    79. Но теперь появилась новая проблема: как отпустить локи и припарковаться¶

    Мы уже зарегистрированы во всех очереди.

    Все локи каналов еще удерживаются.

    Нельзя:

    парковка

    оставив локи навсегда.

    Но нельзя и просто:

    unlock all
↓
потом парковка

    Почему?

    80. Окно между освобождением локов и парковкой¶

    Представим:

    unlock каналы
↓
отправитель приходит
↓
видит наш sudog
↓
goready(G)
↓
но G еще формально не припарковалась

    Получаем опасное race window вокруг состояния G.

    Нужен специальный commit-протокол парковки.

    81. selparkcommit¶

    selectgo вызывает:

    gopark(selparkcommit, ...)

    То есть parking функция обратного вызова специально знает про select.

    Его задача:

    подготовить G к безопасному взаимодействию со стеком
↓
зафиксировать parking state
↓
отпустить локи каналов
↓
разрешить окончательный парковка

    Это не повтор общего gopark.

    Это специализированный протокол commit для select.

    82. activeStackChans¶

    Почему selparkcommit вообще думает о стек?

    Потому что:

    sudog.elem

    может указывать в стек текущей G.

    После unlock канал другой поток рантайм сможет взаимодействовать с этими sudog.

    Одновременно стек Go может shrink/copy.

    Нужно сообщить стек machinery:

    у этой G есть активные ссылки каналов в стек

    Для этого существует состояние вроде:

    activeStackChans

    83. parkingOnChan¶

    Runtime также отмечает:

    G прямо сейчас входит в parking protocol на канал

    Через отдельное состояние.

    Когда selparkcommit завершает подготовку:

    parkingOnChan = false

    и только после нужных публикаций начинает отпускать локи каналов.

    Это деталь текущей реализации.

    Но причинность важна:

    перемещением стека, канал очереди и parking — не независимые подсистемы.

    84. Почему selparkcommit не должен обращаться к стеку после освобождения первого лока¶

    Как только отпущен первый лок канала:

    другая G может найти наш sudog
↓
сделать нас runnable
↓
эта G может начать выполняться на другом M

    То есть после unlock старый M должен считать:

    стек этой G уже потенциально принадлежит снова самой G

    Поэтому функция обратного вызова очень осторожно ограничивает, к чему обращается.

    85. Теперь G действительно спит¶

    После commit:

    G → ожидающий

    В очереди остается:

    несколько sudog

    Любой из участвующих каналы может стать готовым.

    Но победить должен только один case.

    И вот здесь появляется еще один механизм.

    86. Что если два канала становятся готовы почти одновременно¶

    G зарегистрирована:

    A.recvq
B.recvq

    Почти одновременно:

    отправитель A
отправитель B

    Оба находят соответствующий sudog.

    Если оба просто сделают:

    goready(G)

    мы получим двойное завершение одного select.

    Нужна арбитражная точка.

    87. selectDone¶

    У G есть атомарное состояние:

    selectDone

    Очередь ожидания при dequeue sudog от select пытается атомарно сделать:

    0 → 1

    Успел первым:

    этот `case` победил

    Не успел:

    другой `case` уже победил
↓
этот sudog устаревший

    88. Почему CAS нужен в waitq.dequeue¶

    Арбитраж не находится только внутри selectgo.

    Победитель обнаруживается в момент, когда конкретная операция с каналом извлекает waiter из своей очередь.

    Поэтому waitq.dequeue знает:

    sg.isSelect?

    Если да — участвует в выборе победителя.

    Получаем связь:

    канал очередь
↔
select state одной G

    89. Проигравший sudog может временно оставаться в очереди¶

    Победил case B.

    Но физически sudog A может еще лежать в:

    A.recvq

    Пока проснувшийся selectgo не выполнит очистка.

    Если в этот момент кто-то придет в A:

    `dequeue`
↓
видит select sudog
↓
CAS selectDone проигрывает
↓
пропускает устаревший waiter

    То есть очередь умеет самоочищаться от логически проигравших записей при встрече с ними.

    90. Кто передает победивший sudog обратно G¶

    операция с каналом, которая выиграла, перед пробуждением записывает waiter в:

    gp.param

    После пробуждение selectgo получает:

    sg := gp.param

    Теперь он знает:

    какое именно ожидание победило

    Но все остальные регистрации еще нужно удалить.

    91. G проснулась — проход 3¶

    Первое:

    снова взять все локи каналов

    Почему?

    Потому что сейчас будем изменять очереди ожидания.

    Без локи удалять sudog из нескольких concurrent очереди нельзя.

    92. Перед удалением связей рантайм очищает указатели, связанные со стеком¶

    Сначала:

    для всех sg в gp.waiting
↓
isSelect = false
elem = nil
c = nil

    И затем:

    gp.waiting = nil

    Только после этого можно постепенно освобождать sudog.

    Это снова связано с тем, что их поля могли указывать в стек.

    93. Победивший sudog уже удален из своей очереди¶

    операция с каналом, которая разбудила G:

    извлечение победителя

    уже выполнила.

    Поэтому в проход 3:

    если sg == победитель
→ не удаляем повторно
→ запоминаем выбранный `case`

    Для остальных:

    send `case`
→ dequeueSudoG из sendq

receive `case`
→ dequeueSudoG из recvq

    94. Потом все sudog возвращаются в пул рантайма¶

    Для каждого:

    releaseSudog

    То есть один блокирующий select на N case потенциально использует:

    N sudog

    на период ожидания.

    После завершения они переиспользуются.

    95. Проход 3 нужен не только для памяти¶

    Если проигравшие регистрации оставить:

    quiet канал
↓
тысячи старых sudog
↓
очередь растет

    Потом любой send/recv вынужден будет пропускать устаревший entries.

    Поэтому очистка — часть корректности и производительности.

    97. Сложность select уже видна из алгоритма¶

    Пусть N активных case.

    Нужно:

    построить pollOrder      ~ O(N)
построить lockOrder      ~ O(N log N)
проход 1                   ~ O(N)

    Если блокируемся:

    зарегистрировать N sudog ~ O(N)
проход 3 очистка           ~ O(N)

    Точная цена зависит от конкретного пути.

    Но важная модель:

    select не O(1) относительно числа case.

    98. Почему 2-case и 200-case select — разные по цене¶

    Синтаксис одинаков:

    select { ... }

    Но работа рантайм:

    2 `case`
→ маленькие массивы
→ мало локи
→ мало checks

200 `case`
→ большие порядки
→ сортировка
→ много локи каналов
→ потенциально 200 sudog
→ большой очистка

    Под высокой частотой это уже заметно.

    99. Но широкий select не обязательно блокируется¶

    Если проход 1 часто находит готовый case:

    проход 2
проход 3
парковка

    вообще не выполняются.

    То есть характер нагрузки важнее одной ширины syntax.

    Сравнивать нужно:

    готовый-heavy workload

    и:

    нагрузка, где `select` обычно блокируется

    100. Один горячий канал во множестве select¶

    Пусть тысячи горутины имеют:

    select {
case <-горячий:
case <-other:
}

    Каждый общий selectgo включает горячий в:

    lockOrder

    Получаем:

    много G
↓
один hchan.lock
↓
contention

    на уровне канала contention не исчезает от использования select.

    101. pollOrder не дает строгой справедливости¶

    Псевдослучайный порядок нужен, чтобы убрать систематический перекос.

    Но он не обещает:

    каждый готовый `case` получит ровно 1/N выборов

    на любом конечном отрезке.

    И не является механизмом:

    priority
weighted scheduling
round-robin SLA

    Если приложению нужна бизнес-политика выбора — ее строят отдельно.

    102. selectgo: что важно запомнить¶

    1. selectgo работает с двумя порядками: случайным pollOrder и детерминированным lockOrder.
    2. Nil-каналы исключаются из рабочих порядков.
    3. lockOrder нужен, чтобы несколько select не дедлочились на hchan.lock.
    4. Проход 1 ищет already-готовый operation.
    5. При default проход 2 вообще не нужен.
    6. Проход 2 регистрирует одну G во всех нужных очереди ожидания.
    7. Регистрация выполняется при удерживаемых локи каналов, чтобы не потерять пробуждение.
    8. selparkcommit связывает безопасный парковка, отпускание локи каналов и перемещаемый стек.
    9. selectDone гарантирует одного победителя.
    10. Проход 3 удаляет проигравшие регистрации.
    11. Стоимость блокирующий select растет с числом case.

    103. Теперь переходим к context¶

    После каналов и select легко построить новую слишком простую модель:

    context — это просто еще один Done-канал.

    Нет.

    Done — только внешняя точка наблюдения.

    Нужно еще решить:

    как дочерний контекст узнает об отмене родителя?
как родитель знает о дочернем контексте?
что если родитель — пользовательский `Context`?
что если родитель никогда не отменяется?
что если родитель поддерживает `AfterFunc`?
как убрать дочерний контекст, если он завершился раньше родителя?
как дедлайн встраивается в ту же схему?

    104. Напомним только устойчивую модель¶

    Из основной лекции известно:

    Context
→ цепочка оберток

отменяемый Context
→ родитель / потомки

cancel
→ `Done` закрыт
→ потомки отменяются

    И:

    отмена cooperative

    То есть cancel() не убивает произвольную G.

    Этого достаточно как фундамент.

    105. cancelCtx: какие инварианты ему нужны¶

    Текущая структура содержит примерно:

    cancelCtx
├── Context
├── mu
├── done
├── children
├── err
└── cause

    Нас интересуют не поля сами по себе.

    Нас интересуют требования:

    Done закрывается один раз
err устанавливается один раз
cause устанавливается один раз
children меняются конкурентно
отмена родителя должна дойти до потомков
повторный cancel безопасен

    106. done хранится через atomic.Value¶

    Почему не просто:

    done chan struct{}

    Потому что:

    Done() часто читается

    и:

    канал нужен не каждому context

    Текущая реализация сочетает:

    ленивое создание
+
быстрое чтение

    107. Done() создается лениво¶

    Первый вызов:

    ctx.Done()

    делает:

    атомарная загрузка
↓
канал уже есть?
├── да → возврат
└── нет
    ↓
    lock
    ↓
    проверить еще раз
    ↓
    make(chan struct{})
    ↓
    атомарная запись

    Это классическая двойная проверка под локом.

    108. Зачем ленивость вообще нужна¶

    Создаем:

    1 000 000 производных контекстов

    Но приложение никогда не читает:

    ctx.Done()

    Если канал создавать всегда:

    1 000 000 дополнительных объектов канала

    Пустая цена.

    Ленивый Done позволяет не платить.

    109. Что если cancel() произошел до первого Done()¶

    Очень красивый специальный случай.

    Если done еще nil:

    cancel
↓
не создавать новый уникальный канал

    Вместо этого можно сохранить:

    общий закрытый канал

    То есть уже отмененные контексты, у которых Done еще не был создан могут ссылаться на общий закрытый канал.

    Еще один пример:

    не платить за механизм,
если уникальный объект уже не нужен

    110. Err() тоже оптимизирован под частое чтение¶

    Текущая реализация хранит err в atomic.Value.

    Частый путь:

    err := атомарная загрузка

    без mu.

    Если ошибка уже есть, реализация дополнительно синхронизирует наблюдение с закрытием Done.

    Нам важна идея:

    Проверка состояния отмены — горячая операция, поэтому частый путь чтения стараются не вести через мьютекс.

    111. Теперь WithCancel(parent)¶

    Высокоуровнево:

    child, cancel := context.WithCancel(parent)

    Внутри:

    создать cancelCtx child
↓
propagateCancel(parent, child)

    И вот propagateCancel — центральный алгоритм блока context.

    112. Что должен гарантировать propagateCancel¶

    После возврата:

    если parent когда-нибудь отменится
↓
child тоже должен отмениться

    Но тип parent — интерфейс:

    Context

    Это может быть:

    • Background;
    • стандартный cancelCtx;
    • timerCtx;
    • обертка вокруг стандартного Context;
    • сторонняя реализация;
    • пользовательский тип.

    Нужен универсальный алгоритм.

    113. Первый вопрос: parent.Done() == nil?¶

    Done() == nil

    родитель никогда не сообщает об отмене.

    Пример:

    Background
WithoutCancel(...)

    Тогда:

    распространение отмены не нужна
↓
возврат

    Нет children регистрация.

    Нет функция обратного вызова.

    Нет горутина.

    select {

    ...
default:
}

    Если родитель уже отменен:

    child.cancel(...)
↓
возврат

    Регистрация у родителя бессмысленна.

    115. Самый дешевый нормальный путь: parentCancelCtx¶

    Теперь родитель еще жив.

    внутренний `*cancelCtx` родителя

    Если удалось:

    lock parent
↓

├── да → отменить дочерний контекст
└── нет

    ленивое create `children` map

    children[child] = struct{}{}
↓
unlock

    Все.

    Ни одной новой горутина.

    116. Вот почему стандартное дерево context не равно «горутина на ребро»¶

    Плохая модель:

    parent
→ горутина-наблюдатель
→ child

    для каждого дочернего контекста.

    В обычной цепочке стандартных contexts:

    parent.cancelCtx
↓
`children` map

    И отмена распространяется прямым обходом структуры.

    Это принципиально дешевле по горутина count.

    117. Но как parentCancelCtx находит внутренний cancelCtx через интерфейс?¶

    У Context нет публичного метода:

    GetUnderlyingCancelCtx()

    Стандартная библиотека использует внутренний ключ через:

    Value(&cancelCtxKey)

    Стандартный cancelCtx возвращает себя для этого специального ключа.

    Но одной проверки type assertion недостаточно.

    118. Почему дополнительно сравнивается Done()¶

    Представим кастомную обертка-реализацию:

    внутри содержит стандартный cancelCtx

    но переопределяет:

    Done() <-chan struct{}

    и возвращает другой канал.

    Если библиотека просто найдет внутренний cancelCtx через Value и зарегистрирует child прямо в нем:

    custom Done semantics будут обойдены

    Это может нарушить контракт обертка.

    Поэтому проверяется:

    Done(parent)
==
Done(found cancelCtx)

    Если не совпадает:

    быстрый путь запрещен

    Очень хороший пример defensive реализация.

    119. children map тоже создается лениво¶

    Parent может иметь:

    0 children

    Большую часть жизни.

    Зачем заранее делать:

    make(map[canceler]struct{})

    ?

    Поэтому map появляется только при первом реально зарегистрированном child.

    Еще одна локальная оптимизация:

    не платим за unused feature

    120. Цена большого ветвления уже видна¶

    Пусть:

    root
→ 100 000 прямых дочерних контекстов

    До cancel:

    `children` map ~ 100 000 entries

    Во время cancel:

    for child := range c.children
↓
child.cancel(...)

    То есть:

    cancel(root)

    имеет реальную работу O(number of потомков) в грубой модели.

    121. Но parentCancelCtx — не единственный путь¶

    Если родитель:

    не дает прямого доступа к стандартный `cancelCtx`

    нужно попробовать следующий механизм.

    Стандартная библиотека проверяет:

    родитель реализует `AfterFunc`?

    122. AfterFunc-путь¶

    Если родитель умеет:

    AfterFunc(func()) func() bool

    можно зарегистрировать функция обратного вызова:

    родитель отменен
↓
функция обратного вызова
↓
child.cancel(...)

    Преимущество:

    не нужна постоянная горутина-наблюдатель

    123. Но дочерний контекст может завершиться раньше родителя¶

    Зарегистрировали функцию обратного вызова у родителя.

    Потом дочерний контекст отменили вручную:

    cancelChild()

    Callback больше не нужен.

    Нужно:

    отписаться от родителя

    Для этого propagateCancel оборачивает parent специальным внутренним stopCtx, который хранит функцию остановки регистрации.

    124. removeChild должен понимать разные типы связи¶

    Если связь:

    parentCancelCtx.children

    тогда:

    lock parent
delete(children, child)
unlock

    Если связь была через:

    AfterFunc

    тогда:

    stop функция обратного вызова

    Одна функция removeChild скрывает оба пути.

    125. И только потом остается дорогой резервный путь¶

    Parent:

    Done != nil

    Но:

    не стандартный `cancelCtx`
не afterFuncer

    Контракт все равно требует распространение отмены.

    Остается универсальный способ:

    отдельная горутина

    126. Резервный путь: отдельная горутина¶

    Текущий путь концептуально:

    go func() {
    select {
    case <-parent.Done():
        child.cancel(...)

    case <-child.Done():
    }
}()

    То есть наблюдатель живет до первого из двух событий:

    родитель отменен
или
дочерний контекст отменен отдельно

    127. Почему второй case обязательный¶

    Без:

    case <-child.Done():
    return

    если дочерний контекст завершился раньше родителя:

    наблюдатель продолжал бы жить до отмены родителя

    Получили бы горутина retention.

    Поэтому отмена дочернего контекста сама завершает наблюдатель.

    128. Одинаковый API — разная внутренняя цена¶

    Код:

    ctx, cancel := context.WithCancel(parent)

    Родитель A:

    обычный cancelCtx
↓
`children` map

    Родитель B:

    поддерживает AfterFunc
↓
регистрация функция обратного вызова

    Родитель C:

    неизвестный пользовательский `Context`
↓
горутина-наблюдатель

    API одинаков.

    Модель стоимости — нет.

    129. Практический вывод про пользовательский Context¶

    Обычно собственные реализации Context не нужны.

    И теперь причина глубже, чем:

    Так рекомендует документация.

    Пользовательский родитель может:

    • отключить стандартный быстрый путь;
    • заставить propagateCancel использовать путь через AfterFunc;
    • в худшем случае породить отдельную горутину на child.

    Абстракция влияет на физическую стоимость.

    130. Собираем propagateCancel¶

    дочерний контекст создан
↓
parent.Done()

nil?
├── да
│   → родитель никогда не отменяется
│   → возврат
│
└── нет
    ↓
    родитель уже отменен?
    ├── да
    │   → отменить дочерний контекст immediately
    │
    └── нет
        ↓
        parentCancelCtx?
        ├── да
        │   → parent.children += child
        │   → возврат
        │
        └── нет
            ↓
            родитель реализует `AfterFunc`?
            ├── да
            │   → register функция обратного вызова

            │   → возврат
            │
            └── нет

    Это центральная схема context.

    131. Теперь вызываем cancel()¶

    Что должен сделать cancelCtx.cancel?

    Минимум:

    установить Err
установить Cause
закрыть Done
отменить children
очистить children
при необходимости убрать себя из parent

    Но порядок важен.

    132. Первый инвариант: повторная отмена ничего не делает¶

    Под mu:

    err уже non-nil?
├── да → unlock, возврат
└── нет → это первый cancel

    Поэтому:

    cancel()
cancel()
cancel()

    безопасно.

    Вторая и последующие операции почти сразу выходят.

    133. err и cause¶

    Первый cancel устанавливает:

    err

    и:

    cause

    Если отдельная cause не передана:

    cause = err

    Так общий механизм поддерживает и обычный CancelFunc, и CancelCauseFunc.

    134. Потом нужно закрыть Done¶

    Два случая.

    Канал уже создан:

    close(done)

    Канал еще ни разу не создавался:

    done = shared closedchan

    Не нужно делать:

    make(chan struct{})
↓
close

    ради канала, который никто раньше не наблюдал.

    135. Потом отменяются дочерние контексты¶

    Под parent lock:

    for child := range c.children {
    child.cancel(false, err, cause)
}

    Это рекурсивное распространение вниз.

    Обрати внимание:

    лок родителя удерживается
↓
берется лок дочернего контекста

    Значит структура дерева и порядок реализации должны избегать циклов родитель-потомок.

    Контексты образуют направленное дерево, а не произвольный граф.

    136. После обхода c.children = nil¶

    Почему не оставить map с уже отмененными потомками?

    Она больше не нужна.

    Кроме памяти, она удерживала бы ссылки на потомков.

    Поэтому после распространение отмены:

    c.children = nil

    освобождает структуру для GC.

    137. И только после unlock — removeFromParent¶

    Если текущий context отменили собственной CancelFunc, нужно убрать его из родителя.

    Но делать это, удерживая собственный mu, опасно:

    child.mu
↓
parent.mu

    при том что распространение отмены идет:

    parent.mu
↓
child.mu

    Получили бы возможность lock-order inversion.

    Поэтому:

    unlock child
↓
removeChild(parent, child)

    138. Вот где дизайн избегает дедлока¶

    Propagation:

    parent.mu
→ child.mu

    Self-removal:

    сначала child.mu released
→ потом parent.mu

    То есть одновременно:

    child.mu → parent.mu

    не удерживается.

    Это маленькая, но очень важная деталь.

    139. cancel() — не O(1)¶

    Пусть:

    root
├── 10 000 children
│   └── у каждого свои children

    Одна строка:

    cancelRoot()

    может означать:

    обход большого поддерева
+
close множества Done
+
очистку `children` maps
+
подготовку множества wakeups

    Логическая операция одна.

    Физической работы много.

    140. Время распространения отмены и время полного завершения — разные вещи¶

    Пусть cancel дошел до всех contexts.

    Это еще не значит:

    все горутины завершились

    Каждая работа должна:

    получить CPU
увидеть Done / Err
остановить собственную операцию
освободить ресурсы
возврат

    Поэтому измеряем отдельно:

    сколько занял cancel()

    и:

    сколько прошло до полного завершения workers

    141. Почему большое ветвление создает всплеск после cancel¶

    cancel() закрывает множество Done.

    Заблокированный горутины:

    select {
`case` <-ctx.Done():
}

    становятся готовы.

    Дальше знакомая цепочка:

    много G RUNNABLE
↓
scheduler очереди
↓
CPU finite
↓
completion растянута во времени

    Это уже слой Runtime deep.

    Здесь важно только увидеть источник всплеск:

    одно дерево cancellation

    142. removeChild: зачем ручной cancel() освобождает ресурсы раньше¶

    Представим:

    ctx, cancel := context.WithTimeout(parent, time.Minute)

    Работа завершилась за:

    20 ms

    Если cancel() не вызвать:

    родитель может продолжать держать дочерний контекст
timer продолжает жить
внутренние структуры остаются достижимыми

    до дедлайна или отмены родителя.

    Теперь правило:

    defer cancel()

    имеет понятный физический смысл.

    143. Переходим к timerCtx¶

    WithTimeout — это не отдельная система cancellation.

    Это:

    cancelCtx
+
дедлайн
+
timer

    Когда timer срабатывает:

    timer функция обратного вызова
↓
cancel(DeadlineExceeded)

    Дальше работает уже знакомое дерево.

    144. WithDeadline: сначала проверяется дедлайн родителя¶

    Пишем:

    context.WithDeadline(parent, d)

    Если у родителя уже есть дедлайн:

    parentDeadline < d

    то дочерний контекст все равно завершится раньше через родителя.

    Создавать отдельный timer на более позднее время бессмысленно.

    Текущая реализация возвращает более простой производный отменяемый контекст.

    145. Дедлайн уже прошел¶

    После подключения cancellation распространение отмены:

    duration := time.Until(d)

    Если:

    duration <= 0

    таймер не нужен.

    Сразу:

    cancel(DeadlineExceeded)

    и возврат.

    Еще один пример:

    не создаем механизм,
который уже не сможет понадобиться

    146. Дедлайн в будущем¶

    Если context еще жив:

    `timer = time.AfterFunc(duration, callback)`

    Callback:

    cancel(true, DeadlineExceeded, cause)

    То есть таймер только генерирует событие.

    Вся cancellation machinery остается той же.

    147. timerCtx.cancel¶

    При ручной или родительской отмене:

    cancelCtx.cancel(...)
↓
при необходимости removeChild
↓
lock
↓
timer.Stop()
↓
timer = nil
↓
unlock

    Зачем останавливать timer?

    Иначе функция обратного вызова может сработать позже, когда context уже давно не нужен.

    148. WithTimeout — просто удобная форма WithDeadline¶

    Высокоуровнево:

    WithTimeout(parent, timeout)

    делает:

    WithDeadline(parent, now + timeout)

    То есть внутренне отдельного timeout-protocol нет.

    Есть дедлайн + таймер + отмена.

    149. Много WithTimeout — это много реальных таймеров¶

    Пусть сервис делает:

    100 000 requests/s

    и для каждого создает несколько коротких WithTimeout.

    Если дедлайны действительно самостоятельны:

    много timer регистрации

    становятся отдельной рантайм-нагрузкой.

    Мы не открываем здесь timer subsystem.

    Но важно увидеть цену abstraction.

    150. context.AfterFunc¶

    Мы уже встретили его внутри propagateCancel.

    Public API позволяет:

    stop := context.AfterFunc(ctx, f)

    Смысл:

    ctx canceled
↓
запустить f

    Текущая реализация строит специальный дочерний контекст и использует sync.Once.

    151. Почему функция обратного вызова запускается в отдельной горутине¶

    Внутренний cancel path не должен выполнять произвольный пользовательский функция обратного вызова:

    под cancel lock

    Иначе:

    медленный f()
↓
держим внутренние локи
↓
блокируем распространение отмены

    Поэтому функция обратного вызова запускается отдельно.

    Еще один пример правила:

    Не исполнять произвольный внешний код внутри критической секции внутренней структуры.

    152. AfterFunc тоже можно остановить¶

    Возвращаемая функция:

    stop()

    пытается выиграть sync.Once.

    Если функция обратного вызова еще не начал запуск:

    stop → true

    и связанный child отменяется/отвязывается.

    Если функция обратного вызова уже начал:

    stop → false

    Это отдельный lifecycle.

    153. WithoutCancel хорошо показывает первую ветку propagateCancel¶

    detached := context.WithoutCancel(parent)

    У такого context:

    Done() == nil
Err() == nil
Дедлайн отсутствует

    Значит любой child, производный от него, не получает cancellation через старого parent.

    В propagateCancel это буквально:

    done == nil
↓
возврат

    Семантика API прямо превращается в дешевый рантайм path.

    154. Что происходит под нагрузкой: стандартное дерево context¶

    Большое число children не означает большое число наблюдатель горутины.

    Но означает:

    `children` map memory
+
работу вставки / удаления
+
стоимость обхода при cancel
+
удержание child до detach

    То есть стандартный путь дешевле резервный путь.

    Но не бесплатен.

    155. Что происходит под нагрузкой: пользовательский родительский Context¶

    Если быстрый путь и AfterFunc path недоступны:

    1 child
→ 1 горутина-наблюдатель

    Теперь:

    100 000 children
→ до 100 000 наблюдатель горутины

    Это уже:

    • стеки;
    • scheduler state;
    • горутина profile noise;

    root

↓

    158. Размер передаваемого значения — часть цены канала¶

    Сравним:

    chan uint64

    и:

    chan [64 << 10]byte

    Каждый successful send должен передать значение.

    прямая передача или буфер:

    копирование bytes

    никуда не исчезает.

    Канал не превращает большой object в бесплатное сообщение.

    159. Когда передавать указатель дешевле по копированию¶

    Можно сделать:

    chan *Large

    копируем один указатель

    меньше bytes copied
≠
бесплатная архитектура

    182. Разрушаем последние плохие упрощения¶

    «канал — просто потокобезопасная очередь»¶

    Нет.

    Небуферизованный канал вообще не имеет пользовательского буфер.

    прямая передача может писать значение прямо между стеками горутины.

    «Буферизованный канал всегда сначала кладет значение в буфер»¶

    Нет.

    Если получатель уже ждет:

    отправитель → получатель прямойly

    буфер обходится.

    «Получение из заполненного канала просто освобождает ячейку»¶

    Не всегда.

    Если отправитель уже ожидающий:

    головная ячейка → получатель
отправитель → тот же slot

    за одну критическую секцию.

    «close(ch) просто ставит closed=true»¶

    Нет.

    Он еще обходит очереди ожидания и подготавливает пробуждение всех waiters.

    «select случайно проверяет case»¶

    Слишком мало.

    Он строит:

    pollOrder
+
lockOrder

    а блокирующий path проходит регистрацию, парковка protocol и очистка.

    «Отмена Context — это горутина на каждого потомка»¶

    Нет.

    Стандартный путь использует:

    parent.children

    Watcher горутина — резервный путь для неизвестных реализацияs.

    «cancel() просто закрывает Done»¶

    Нет.

    Он сохраняет состояние, закрывает Done, рекурсивно отменяет children, очищает связи и при необходимости удаляет себя из parent.

    188. Что важно запомнить¶

    1. Текущий makechan выбирает способ аллокации с учетом размера буфер и наличия Go-указателей в элементах.
    2. hchan хранит кольцевой буфер, индексы, число элементов, очереди ожидания и внутренний лок.
    3. chansend предпочитает уже ожидающего получатель, затем свободный ячейка буфера, затем блокирующий path.
    4. ожидающий получатель позволяет обойти буфер даже у буферизованный канал.
    5. Небуферизованная отправка/receive может копировать значение напрямую между стеками разных горутин.
    6. Для стек-to-стек copy текущий рантайм использует специальный путь с учетом барьера GC.
    7. Буферизованный канал использует sendx, recvx и qcount; элементы физически не сдвигаются.
    8. Если буфер заполненный и отправитель уже ждет, receive одновременно забирает head и кладет значение отправителя в освободившуюся физическую ячейку.
    9. closechan обходит recvq и sendq, но делает G runnable только после освобождения лока канала.
    10. отправители после close просыпаются и завершают свою send operation через panic.
    11. Общий selectgo использует случайный pollOrder и детерминированный lockOrder.
    12. lockOrder предотвращает deadlock между select, работающими с несколькими каналы.
    13. Проход 1 ищет уже готовую operation; проход 2 регистрирует waiters; проход 3 удаляет проигравшие регистрации.
    14. selparkcommit нужен, чтобы корректно связать parking, отпускание локи каналов и перемещаемый стек.
    15. selectDone гарантирует, что из нескольких потенциальных канал events один select получает ровно одного победителя.
    16. Стоимость блокирующий select растет с числом активных case.
    17. cancelCtx.Done() создается лениво; отмененный до создания context может использовать общий закрытый канал.
    18. Стандартный propagateCancel обычно регистрирует child в parent.children без отдельной горутины.
    19. Если стандартный родительский Context недоступен, propagateCancel может использовать AfterFunc; горутина-наблюдатель — общий резервный путь.
    20. parentCancelCtx дополнительно проверяет соответствие фактического Done, чтобы не обходить семантику пользовательская оберткаs.
    21. cancel() — не простое изменение флага: он закрывает Done, рекурсивно отменяет потомков и очищает связи.
    22. Большой cancellation широкое ветвление имеет реальную стоимость и может создать массовый всплеск готовых к выполнению горутин.
    23. timerCtx добавляет timer поверх обычного cancelCtx; ранний cancel() останавливает таймер и разрывает связи раньше дедлайна.
    24. Забытый CancelFunc — это не только стиль: он может дольше удерживать context, parent регистрация и timer.
    25. Конкретные функции и структуры этой лекции — детали Go 1.27.x, а не контракт языка.

    Главный инженерный вывод:

    Канал, select и context выглядят как компактные языковые и библиотечные конструкции, но под нагрузкой они превращаются в конкретную работу: типизированное копирование данных, локи, кольцевые буферы, очереди ожидания, несколько sudog, сортировку и регистрацию select, обход деревьев cancellation, таймеры и массовые wakeups.
