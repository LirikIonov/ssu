    4.3. Компилятор Go под капотом: IR, SSA, lowering и машинный код¶

    Материал ориентирован на Go 1.27.x.

    Это завершение блока Go under the hood.

    В 4.1 мы открыли алгоритмы структур данных.

    В 4.2 — конкретные пути каналов, select и context.

    Теперь вопрос другой:

    Кто вообще решил, что строка Go-кода должна превратиться именно в этот вызов рантайма, эту ветку, эту проверку и эти машинные инструкции?

    Зачем открывать этот слой¶

    До сих пор мы рассуждали так:

    append
→ growslice

m[key]
→ Swiss Table

w.Write(buf)
→ ITab / динамический вызов

ch <- v
→ chansend

select
→ selectgo

    Это правильные рантайм-модели.

    Но в исходнике мы не пишем:

    runtime.growslice(...)
runtime.chansend(...)
runtime.selectgo(...)

    И тем более не пишем:

    CMP
JLS
CALL
MOVQ

    Значит между:

    Go исходник

    и:

    рантайм / CPU

    есть еще один большой слой.

    исходный код
↓
компилятор
↓
внутренние представления
↓
доказательства и оптимизации
↓
упрощение конструкций
↓
SSA
↓
привязка к архитектуре
↓
регистры / стек
↓
машинный код

    Эта лекция именно про него.

    0. Сразу проведем границу¶

    Мы не делаем курс по теории компиляторов.

    Не будем глубоко разбирать:

    • грамматики;
    • построение парсеров;
    • теорию доминаторов;
    • алгоритмы построения SSA;
    • graph coloring register аллокация;
    • linker internals;
    • ELF / Mach-O;
    • generics dictionaries;
    • полный Go ABI.

    Нам нужен прикладной вопрос:

    Что из моего Go-кода реально осталось после компилятора и почему?

    Главная цепочка:

    написали конструкцию
↓
выдвинули гипотезу о ее цене
↓
посмотрели решение компилятора
↓
посмотрели SSA
↓
посмотрели ассемблер
↓
измерили benchmark
↓
сверили модель с реальностью

    1. Первая плохая модель: «компилятор переводит строки Go прямо в ассемблер»¶

    Например:

    x := a + b

    Можно представить:

    строка Go
↓
ADD

    На маленьком примере это иногда почти выглядит правдой.

    Но теперь:

    s = append(s, x)

    Какая одна инструкция соответствует append?

    Никакая.

    Или:

    v := m[key]

    Какая одна инструкция означает:

    вычислить хеш
→ выбрать таблицу
→ пробировать Swiss Table
→ сравнить ключ

    ?

    Такой инструкции нет.

    Нужны промежуточные представления.

    2. Полная карта компилятора Go¶

    Для курса полезна такая модель:

    Сейчас эта схема выглядит как каталог терминов.

    Наша задача — сделать из нее причинную модель.

    3. Разбор исходника: компилятору сначала нужно понять структуру¶

    Пусть:

    result := a + b*c

    Компилятору недостаточно строки:

    result := a + b*c

    Нужно понять:

    assignment
└── add
    ├── a
    └── multiply
        ├── b
        └── c

    Иначе нельзя даже корректно применить приоритет операторов.

    4. Синтаксическое дерево еще почти повторяет исходник¶

    На этом уровне узлы соответствуют знакомым конструкциям:

    declaration
assignment
call
if
for
return
binary expression

    Это еще очень высокий уровень.

    Про mapaccess, growslice и регистры речи нет.

    5. Проверка типов: одного синтаксиса уже недостаточно¶

    Возьмем:

    x + y

    Это что?

    int + int?
float64 + float64?
string + string?
generic operation?

    Оператор один.

    Механика совершенно разная.

    Поэтому следующий слой:

    syntax
+
types

    6. Тип — это уже информация для будущего машинного кода¶

    var a int32
var b int64

    Компилятор знает:

    размер
signedness
alignment
operations
representation

    То есть тип в Go — не только проверка API.

    Он влияет на то, какие низкоуровневые операции вообще допустимы.

    7. Но синтаксическое дерево неудобно для всего компилятора¶

    Исторически и архитектурно текущий cmd/compile имеет собственные:

    компилятор types
компилятор IR

    После type checking выполняется переход к внутреннему представлению компилятора.

    Этот этап традиционно называется:

    noding

    В текущей архитектуре здесь участвует Unified IR.

    8. Зачем еще одно IR, если AST уже есть¶

    Плохая модель:

    AST уже описывает программу. Зачем еще одна структура?

    Потому что задачи разные.

    Синтаксическое дерево удобно для:

    что написал программист?

    Middle end нужен для:

    что компилятор уже доказал?
что можно переписать?
что можно удалить?
какая функция вызывается?
какие значения уходят за пределы текущего кадра?

    И представление начинает отходить от исходного текста.

    9. После этого переменная из исходника уже не священна¶

    x := f()
y := x + 1
return y

    После оптимизаций может не остаться отдельных сущностей:

    x
y

    как мы их видим в исходнике.

    Компилятору важна семантика.

    Не имена локальных переменных.

    10. Middle end: вот здесь компилятор начинает доказывать свойства программы¶

    До этого в основном отвечали:

    что написано?
какие типы?

    Теперь:

    что можно доказать?

    Например:

    этот код никогда не выполнится
эта функция достаточно мала для инлайнинга
у этого интерфейсного receiver известен конкретный тип
этот объект не переживает frame

    То есть middle end — слой доказательств о программе.

    11. Раннее удаление мертвого кода¶

    Пишем:

    if false {
    expensive()
}

    Язык позволяет описать ветку.

    Но компилятор уже знает:

    condition = false

    Значит:

    ветка недостижима
↓
ее можно удалить

    В машинный код ее вообще не обязано существовать.

    12. Это первая важная мысль всей лекции¶

    исходный код
≠
набор операций CPU

    Некоторый исходный код может:

    исчезнуть полностью

    Другой:

    развернуться в десятки операций

    Третий:

    превратиться в вызов рантайма

    13. Девиртуализация появляется еще до SSA¶

    Пусть:

    func use(w io.Writer) {
    w.Write(data)
}

    Обычно:

    конкретный тип receiver неизвестен
→ динамический вызов

    Но в конкретном месте компилятор может знать:

    w = *bytes.Buffer

    Тогда вызов через интерфейс можно переписать на конкретный method call.

    Это девиртуализация.

    Подробно к ней вернемся после SSA.

    14. Инлайнинг: вызов функции может исчезнуть¶

    func add(a, b int) int {
    return a + b
}

func f() int {
    return add(10, 20)
}

    Наивная модель:

    f
↓
CALL add
↓
RET

    Но зачем?

    Компилятор может подставить тело:

    10 + 20

    А затем вообще вычислить:

    30

    15. Инлайнинг важен не только из-за цены CALL¶

    Экономия:

    CALL / RET

    часто вообще не главный выигрыш.

    Главное:

    граница функции исчезла
↓
вызывающая функция видит тело вызываемая функция
↓
появились новые факты
↓
следующие оптимизации могут доказать больше

    Например:

    девиртуализация
→ инлайнинг
→ распространение констант
→ мертвый код elimination

    16. Эскейп-анализ тоже зависит от решений компилятора¶

    Сам механизм stack/heap уже разобран в лекции по памяти.

    Здесь новый вопрос:

    Почему изменение оптимизаций компилятора способно изменить результат эскейп-анализа?

    Потому что компилятор reasoning зависит от того, какую программу он видит после преобразований.

    17. Инлайнинг способен сделать время жизни значения понятнее¶

    Без инлайнинга:

    вызывающая функция
↓
call вспомогательная функция
↓
граница анализа

    После инлайнинга:

    тело вспомогательная функция
прямо здесь
↓
видно, куда реально уходит указатель

    Некоторые значения после этого могут перестать уходить в хип.

    18. Поэтому аллокация — не всегда свойство одной строки¶

    x := T{}

    Физический результат может зависеть от:

    место вызова
решения по инлайнингу
компилятор version
контекста использования

    Отсюда инженерное правило:

    Проверяем конкретный сборка, а не вспоминаем универсальное правило про синтаксис.

    19. После middle end приходит walk¶

    Вот здесь начинается особенно интересное.

    До walk программа все еще содержит много высокоуровневых Go-конструкций.

    Задача:

    сделать их проще

    чтобы следующие стадии работали уже не с каждой особенностью языка отдельно.

    20. У walk две большие задачи¶

    Первая:

    зафиксировать порядок вычислений

    Вторая:

    desugaring

    То есть:

    сложная конструкция языка
↓
набор более примитивных операций

    21. Почему порядок вычислений вообще нужно фиксировать¶

    Возьмем условный код:

    dst[f()] = g()

    Здесь:

    f()
g()

    могут иметь side effects.

    Компилятор не имеет права переставить observable behavior так, как ему случайно удобно.

    Поэтому он вводит temporaries и упрощает выражение, сохраняя семантику.

    22. После walk код становится уродливее, но удобнее компилятору¶

    Программист любит:

    v := m[key]

    Компилятору удобнее:

    вычислить map
вычислить key
подготовить тип
вызвать конкретный вспомогательная функция
загрузить результат

    Чем меньше высокоуровневой магии осталось, тем проще следующие фазы.

    23. Desugaring: как синтаксический сахар превращается в более примитивные операции¶

    Операции вроде:

    map
channel
select

    не обязаны оставаться самостоятельными конструкциями до машинный код.

    Компилятор заменяет их более примитивными операциями и вызовами рантайма.

    Вот здесь появляется стрелка:

    Go syntax
↓
рантайм вспомогательная функция

    которую мы до сих пор пропускали.

    24. Но append показывает, что lowering не обязательно равен одному CALL¶

    s = append(s, x)

    Можно было бы сделать:

    CALL runtime.append

    каждый раз.

    Но это было бы глупо.

    Частый случай:

    cap хватает

    можно выполнить прямо в сгенерированном коде.

    25. Поэтому уже сейчас фиксируем важную модель¶

    Высокоуровневая операция может стать:

    встроенный быстрый путь
+
рантайм медленный путь

    Например:

    append
├── емкости enough → local code
└── емкости не хватает → runtime.growslice

    Этот паттерн будет повторяться.

    26. Теперь появляется SSA¶

    После walk программа уже достаточно упрощена.

    Но обычное дерево все еще не идеально для агрессивных оптимизаций.

    Нужна форма, в которой:

    зависимости между вычислениями
и control flow

    видны максимально явно.

    Это SSA.

    27. SSA — Static Single Assignment¶

    Название можно перевести слишком буквально и ничего не понять.

    Главный смысл:

    Каждое SSA-значение определяется ровно один раз.

    Пишем:

    x := 1
x = x + 2
x = x * 10

    Учебно SSA:

    x1 = 1
x2 = x1 + 2
x3 = x2 * 10

    28. Зачем запрещать переопределение одного SSA-значения¶

    Обычная переменная:

    x

    в разные моменты означает разные значения.

    Чтобы понять:

    какой x используется здесь?

    нужно анализировать историю присваиваний.

    SSA превращает зависимости в явные ребра:

    x1
↓
x2
↓
x3

    Оптимизатору намного проще рассуждать.

    29. В SSA вообще нет обычного понятия локальной переменной¶

    Это важно.

    Плохая модель:

    SSA = Go-код, только x переименовали в x1, x2

    Нет.

    После преобразований:

    • исходные переменные могут исчезнуть;
    • одно выражение может стать несколькими SSA-значения;
    • несколько исходных сущностей могут схлопнуться;
    • часть значений вообще существует только как служебные состояния.

    SSA описывает вычисления.

    Не текст программы.

    30. Главные сущности SSA¶

    Для этой лекции достаточно трех:

    Value
Block
Memory

    Плюс:

    Phi

    для слияния control flow.

    31. SSA Value¶

    Например:

    v4 = Add64 <int> v2 v3

    Смысл:

    взять v2
взять v3
сложить
получить новое immutable value v4

    v4 потом может использоваться сколько угодно.

    Но определится только один раз.

    32. SSA-значение знает операцию и тип¶

    Условно:

    OpAdd64
<int>
args: v2, v3

    То есть компилятор уже находится намного ниже:

    a + b

    но еще выше конкретного:

    ADDQ BX, AX

    33. Block¶

    Функция — не просто список операций.

    Есть control flow.

    if x > 0 {
    f()
} else {
    g()
}

    Получаем:

            block 1
        x > 0
        /   \
       /     \
 block 2   block 3
    f          g
       \     /
        \   /
        block 4

    Это control-flow graph.

    34. Базовый блок¶

    Внутри basic block:

    управление входит
↓
операции идут последовательно
↓
управление выходит по известному набору ребер

    Нет произвольного прыжка в середину блока.

    Это удобная единица анализа.

    35. if в SSA¶

    Пусть:

    func choose(b bool) int {
    if b {
        return 10
    }
    return 20
}

    Учебно:

    b1:
    vCond = Arg b
    If vCond → b2 b3

b2:
    return 10

b3:
    return 20

    Здесь уже почти нет исходного синтаксиса if.

    Есть control-flow graph.

    36. А что если обе ветки присваивают значение и потом сходятся¶

    x := 0

if cond {
    x = 10
} else {
    x = 20
}

return x + 1

    SSA не может сделать:

    x = 10
x = 20

    Один SSA-value нельзя переопределить.

    37. Появляется Phi¶

            cond
       /    \
    x1=10  x2=20
       \    /
        \  /
      x3 = Phi(x1, x2)
           │
           ▼
        x3 + 1

    Phi означает:

    Если пришли из левой ветки — возьми x1. Если из правой — x2.

    38. Phi — не инструкция CPU¶

    Нельзя открыть ассемблер и обязательно найти:

    PHI

    Такой инструкции нет.

    Это сущность промежуточного представления.

    Позже компилятор преобразует ее в нужное размещение values и control flow.

    39. Первый сильный плюс SSA: распространение констант¶

    Пусть после других преобразований стало известно:

    v2 = Const64 10
v3 = Const64 20
v4 = Add64 v2 v3

    Компилятор может получить:

    v4 = Const64 30

    Операция сложения исчезла.

    40. Второй плюс: неиспользуемое значение видно явно¶

    Если:

    v7

    больше никто не использует и operation не имеет side effects:

    v7 можно удалить

    SSA dependency graph делает это намного проще.

    41. Но тут возникает неприятный вопрос¶

    Если SSA-value определяется один раз:

    как описать память?

    Ведь:

    *p = 10
*p = 20

    меняет одну и ту же память.

    Значит обычных immutable values недостаточно.

    42. Memory — специальный тип SSA¶

    У Go SSA есть служебный тип:

    mem

    Он означает:

    Состояние глобально наблюдаемой памяти после определенной последовательности side effects.

    Учебно:

    mem0
↓
Store(p, 10, mem0)
↓
mem1
↓
Store(p, 20, mem1)
↓
mem2

    43. Почему второй Store зависит от mem1¶

    Если написать:

    Store(p, 20, mem0)

    то компилятор логически разрешил бы считать две записи независимыми.

    Но они не независимы.

    Вторая должна видеть состояние после первой.

    Цепочка mem запрещает незаконное переупорядочивание.

    44. Load тоже зависит от Memory¶

    *p = 10
x := *p

    Учебно:

    mem0
↓
Store(p, 10) → mem1
↓
Load(p, mem1) → x

    Если load зависел бы от старого mem0, можно было бы прочитать старое значение.

    45. Вызов функции тоже участвует в цепочке состояния памяти¶

    f()

    Если компилятор не доказал обратное, функция потенциально может:

    • менять память;
    • читать память;
    • вызывать рантайм;
    • паниковать.

    Поэтому call обычно производит новое состояние memory.

    46. Зачем модель памяти SSA нужна backend-разработчику¶

    Оно объясняет:

    Почему компилятор не может просто переставлять любые операции ради красивого pipeline CPU.

    Оптимизация ограничена observable semantics.

    dependency доказана?
├── да → можно двигать
└── нет → порядок нужно сохранить

    49. Вычисление констант на этапе компиляции¶

    const x = 100 * 200

    Не нужен рантайм multiplication.

    Но важнее, что константы могут появиться после инлайнинга и других переписываний.

    Тогда folding срабатывает уже на коде, который в исходнике не выглядел константным.

    50. Удаление лишних проверок nil¶

    Язык требует корректного panic при недопустимом dereference.

    Он не требует:

    перед каждым dereference
→ отдельный CMP pointer, 0

    Если компилятор уже доказал, что pointer non-nil, проверка лишняя.

    51. Или fault CPU уже дает нужную семантику¶

    В некоторых случаях отдельная явная проверка nil тоже не нужна, если безопасный обращение к памяти сам гарантированно вызовет fault при nil так, как нужно рантайму.

    Конкретные формы — детали компилятора и архитектуры.

    Главная идея:

    гарантия языка
≠
обязательная отдельная инструкция проверки

    52. Проверки границ: один из лучших примеров доказательств компилятора¶

    Пишем:

    func sum(s []int) int {
    total := 0
    for i := 0; i < len(s); i++ {
        total += s[i]
    }
    return total
}

    Семантически каждый:

    s[i]

    обязан паниковать, если:

    i < 0
или
i >= len(s)

    53. Наивный машинный код¶

    В каждой итерации:

    CMP i, len
JAE panic
LOAD s[i]

    Но условие цикла уже говорит:

    i < len(s)

    Зачем доказывать это снова?

    54. Удаление проверок границ¶

    Компилятор может связать:

    с:

    index expression

    и доказать:

    индекс всегда допустим

    Тогда отдельный bounds-check исчезает.

    55. Семантика сохранилась, а инструкция исчезла¶

    Это очень важный шаблон:

    язык требует поведение
↓
компилятор доказал условие заранее
↓

    То же мышление будет работать и для:

    • проверка nil;
    • type dispatch;
    • ветка;
    • аллокация;
    • рантайм вспомогательная функция.

    56. Где BCE ломается¶

    Например компилятор не смог связать сложное выражение:

    j := transform(i)
sum += s[j]

    Если transform непрозрачна:

    j < len(s)?

    не доказано.

    Проверка остается.

    Компилятор отвечает:

    покажи доказательство,
которое поддерживает мой анализ

    Если форма кода мешает proof:

    проверка останется

    go сборка -gcflags='-d=ssa/check_bce/debug=1' .

    61. Теперь возвращаемся к append¶

    Это первый сквозной пример.

    В 4.1 мы начинали с:

    cap закончился
↓
runtime.growslice

    Но теперь спрашиваем:

    Кто проверил cap и кто решил, что growslice вообще нужен?

    Компилятор.

    62. append не превращается просто в CALL¶

    Для fixed-count append текущий SSA-generation path концептуально строит:

    ptr, oldLen, cap := s
newLen := oldLen + num

if uint(newLen) > uint(cap) {
    ptr, newLen, cap =
        runtime.growslice(ptr, newLen, cap, num, T)
}

записать новые элементы
↓
собрать новый slice descriptor

    То есть рантайм нужен только на медленном пути.

    63. Быстрый путь append¶

    Если:

    newLen <= cap

    тогда:

    никакой новой аллокации
никакого growslice
никакого копирования старого базового массива

    Нужно только:

    вычислить адрес
↓
записать новый элемент
↓
обновить len

    64. Почему это меняет чтение профиля CPU¶

    Если вы видите:

    runtime.growslice

    это не цена всех append.

    Это цена только тех:

    append,
которые перешли границу cap

    Миллионы успешных fast-path append могут вообще не попадать в этот стек.

    65. Модель машинного кода для append¶

    Концептуально:

    newLen = len + 1
↓
CMP newLen, cap
↓
JBE fast

slow:
CALL runtime.growslice

fast:
address = ptr + oldLen*sizeof(T)
STORE x

    Точные инструкции зависят от архитектуры.

    Но control flow по смыслу именно такой.

    66. Почему используется беззнаковое сравнение¶

    Кроме обычной проверки емкости компилятор path должен корректно учитывать переполнение.

    Учебно:

    newLen
↓
convert to unsigned for comparison
↓
compare with cap

    Беззнаковое сравнение помогает объединить часть проверок.

    Мы не уходим в конкретный asm trick.

    Важно:

    Даже одна проверка append уже является результатом специально спроектированного lowering.

    67. append(dst, src...) может идти другим путем подготовки¶

    dst = append(dst, src...)

    Не обязан попадать в ровно тот же SSA generation path, что:

    append(s, e1, e2, e3)

    Часть таких форм переписывается раньше.

    Еще один урок:

    одно имя builtin
≠
один компилятор path

    68. Go 1.27 умеет сильнее оптимизировать базовый массив растущего среза¶

    В текущем компиляторе есть отдельная оптимизация для некоторых срезов, у которых базовый массив:

    растет через несколько append

    и:

    выход за пределы функции происходит только в финальной точке

    Идея:

    промежуточные backing stores
→ держать на стеке

финальный результат
→ move2heap

    69. Зачем это нужно¶

    Без оптимизации:

    append
→ growslice аллокация 1
→ garbage

append
→ growslice аллокация 2
→ garbage

append
→ growslice аллокация 3
→ финальный срез уходит наружу

    Можно сократить часть промежуточных аллокаций в хипе.

    70. Это хороший предел глубины¶

    Мы не разбираем алгоритм этой оптимизации построчно.

    Нам важен вывод:

    Даже уже глубокая рантайм-модель growslice → heap аллокация может не описывать фактическую стратегию конкретной скомпилированной функции.

    Компилятор способен изменить placement до входа в рантайм.

    Текущий компилятор умеет девиртуализацию на основе профиля.

    тип receiver == Foo?
├── да → direct Foo.Method
└── нет → original indirect вызов через интерфейс

    То есть generic path сохраняется.

    Но горячий случай получает прямой вызов.

    прямой вызов

    94. Почему устаревший PGO-профиль может вредить¶

    Если нагрузка изменился:

    раньше Foo 99%
теперь Foo 20%

    Компилятор все еще может строить быстрый путь под старую горячую цель вызова.

    Получаем:

    лишняя проверка
+
частый резервный путь

    Поэтому PGO — не магическая кнопка.

    Профиль должен соответствовать реальной нагрузке.

    110. Возвращаемся к инлайнингу глубже¶

    111. Пример: вспомогательная функция скрывает константу¶

    func limit() int {
    return 16
}

        return 0
    }
    return s[15]
}

    Без инлайнинга:

    limit()
→ call

    После инлайнинга:

    limit() → 16

    И proof для проверка границ становится проще.

    112. Инлайнинг может повлиять на эскейп-анализ¶

    решение об инлайнинге

    113. У инлайнинга есть бюджет¶

    Почему не подставить все функции во все вызывающая функцияs?

    binary code size ↑
compile time ↑
instruction cache pressure ↑

    И рекурсия создает очевидные проблемы.

    Нужны эвристики и бюджеты.

    114. Конкретный бюджет инлайнинга — не контракт¶

    Поэтому:

    эта функция инлайнится сегодня

    не означает:

    обязана инлайниться всегда

    Прикладной код не должен зависеть от этого для корректности.

    117. Еще одна оптимизация компилятора: intrinsics¶

    Некоторые функции компилятор знает специально.

    Плохая модель:

    в исходнике CALL foo
→ в ассемблер CALL foo

    Не обязательно.

    Компилятор может сказать:

    я знаю семантику этой функции
↓

    118. Зачем intrinsics¶

    Операция может:

    • иметь прямую CPU instruction;
    • иметь эффективную SIMD-реализацию;
    • быть удобной для дальнейших SSA rewrites;
    • не нуждаться в полноценном вызов функции.

    124. amd64 и операнды в памяти¶

    load
↓

    иногда может схлопнуться в одну architecture-specific operation.

    На другой ISA такой формы может не быть.

    load

    число инструкций x86
vs

    128. Правила переписывания (rewrite rules)¶

    Много простых оптимизаций удобно задавать как:

    pattern
→ replacement

    Концептуально:

    x + 0
→ x

    или:

    x * 1
→ x

    129. Зачем правила переписывания вместо огромного if¶

    Пусть у нас тысячи локальных algebraic transformations.

    Если писать:

    if op == Add64 && right == 0 {
    ...
}

    для каждой комбинации, код оптимизатора быстро превращается в нечитаемую стену.

    Rewrite rules позволяют описывать:

    что ищем
↓
на что заменяем

    отдельно от механики обхода SSA.

    130. Но правило переписывания не заменяет сложный анализ¶

    Простое:

    x & 0
→ 0

    идеально.

    Но вопрос:

    может ли i в этом цикле когда-нибудь стать >= len(s)?

    требует анализа control flow и диапазонов.

    Для этого нужны специализированные passes вроде prove.

    131. Почему переписывания применяются повторно¶

    Одно преобразование может открыть следующее.

    A
↓
rewrite
B
↓
rewrite
C

    Например:

    (x + 0) * 1

    сначала:

    x * 1

    потом:

    x

    Поэтому lower применяет machine-specific rewrite rules до устойчивого состояния.

    136. Почему переменная исходника не равна одному регистру¶

    Пишем:

    Плохая модель:

    141. Живость указателей (pointer liveness)¶

    142. Почему liveness влияет на GC¶

    Пусть pointer больше не нужен:

    p := new(T)
use(p)
// p дальше логически мертв

    Если компилятор понимает:

    p dead

    GC не обязан держать объект живым только потому, что байты старого указателя когда-то лежали в стековом слоте.

    Точная liveness уменьшает ложное удержание.

    189. Разрушаем последние плохие упрощения¶

    «append вызывает growslice»¶

    Не всегда.

    cap хватает
→ local быстрый путь

cap не хватает
→ growslice

    «map — это рантайм magic»¶

    Не только.

    компилятор выбирает вспомогательная функция
↓
рантайм выполняет map algorithm

    «Interface call всегда косвенный»¶

    Нет.

    девиртуализация
→ прямой вызов
→ возможно инлайн

    «select всегда вызывает selectgo»¶

    Нет.

    Простые формы компилятор переписывает в более простые operations.

    «Bounds check есть на каждый s[i]»¶

    Не обязательно.

    Если компилятор доказал range:

    check исчезает

    «Функция написана — значит есть CALL»¶

    Не обязательно.

    Inlining или intrinsic может убрать вызов.

    «Локальная переменная живет в stack»¶

    Не обязательно.

    Она может:

    • исчезнуть;
    • быть register value;
    • иметь стековый слот;
    • уйти в хип.

    «Исходник рантайма показывает точный машинный путь»¶

    Не обязательно.

    Компилятор может заинлайнить, переписать или заменить intrinsic'ом.

    190. Что важно запомнить¶

    1. Текущий Go компилятор проходит через синтаксическое дерево / проверку типов, собственное IR, middle end, walk, общий SSA и архитектурно-зависимый lowering.
    2. walk фиксирует порядок вычислений и превращает высокоуровневые конструкции в более примитивные операции.
    3. SSA описывает вычисления через значения, basic blocks и явные зависимости, а не через исходные переменные.
    4. Phi объединяет значения из разных control-flow paths и не является CPU-инструкцией.
    5. Специальный SSA-тип mem связывает side effects и не дает незаконно переставлять операции с памятью.
    6. SSA passes могут удалить мертвый код, проверка nils, проверка границs и другие операции, если корректность уже доказана.
    7. Семантика языка может сохраняться даже когда соответствующая рантайм-проверка исчезла из машинный код.
    8. append имеет сгенерированный быстрый путь и вызывает runtime.growslice только при нехватке емкости.
    9. В Go 1.27 часть растущих slice backing stores в подходящих случаях может быть оптимизирована через stack аллокация и финальный move2heap.
    10. Операции map опускаются к специализированным вспомогательным функциям рантайма, выбранным с учетом операции и типа ключа.
    11. Concrete-to-преобразование к интерфейсу формирует ABI-представление Type/ITab + Data; синтаксис преобразование к интерфейсу сам по себе не доказывает аллокация.
    12. Статическая девиртуализация заменяет вызов через интерфейс конкретным прямым вызовом, когда цель вызова можно доказать.
    13. PGO-девиртуализация может добавить проверку горячей цели вызова и оставить исходный косвенный вызов как резервный путь.
    14. Девиртуализация особенно ценна тем, что может открыть инлайнинг и последующие оптимизации.
    15. Channel operations на стадии walk превращаются в рантайм calls, после чего работает уже разобранный протокол hchan.
    16. Простые формы select компилятор упрощает; общий selectgo нужен только для достаточно сложного multi-case пути.
    17. Inlining меняет не только цену вызова, но и видимость фактов для escape analysis, BCE и других оптимизаций.
    18. Intrinsic может заменить обычный вызов функции специализированными SSA-операциями и машинными инструкциями.
    19. Generic SSA отделяет общие оптимизации от конкретной ISA; lower превращает его в amd64/arm64-specific operations.
    20. Распределение регистров решает, какие SSA-значения живут в регистрах, а какие временно временно выгружаются в стек.
    21. Компилятор создает раскладку стекового кадра и metadata живости указателей, без которых точный GC не смог бы корректно сканировать стеки.
    22. -m=2, GOSSAFUNC, ssa/check_bce, -S и objdump отвечают на разные вопросы и используются после профилирования.
    23. Версия компилятора является частью профиля производительности приложения, но детали генерации кода не являются контрактом языка.
    24. Исследование компилятор internals должно начинаться с измеренного горячего пути, а не с случайного чтения ассемблер.
    25. Правильная цепочка: benchmark/профиль → гипотеза → диагностика компилятора → SSA → ассемблер → изменение → повторное измерение.
