    4.4. Go ABI, generics codegen и linker¶

    Материал ориентирован на Go 1.27.x.

    Это следующий слой после 4.3. Go compiler under the hood.

    В 4.3 мы дошли до машинного кода отдельной функции.

    Теперь появляются три новых вопроса:

    функция A вызывает функцию B
→ как они договариваются о передаче аргументов?

generic function работает с T
→ какой именно код выполняется для конкретного типа?

packages уже скомпилированы
→ как из symbols и relocations получается один executable?

    Ответы:

    ABI
↓
generics codegen
↓
linker

    Зачем открывать этот слой¶

    В прошлой лекции мы закончили примерно здесь:

    Go source
↓
IR
↓
SSA
↓
lowering
↓
register allocation
↓
machine code

    На первый взгляд:

    готово

    Но это машинный код отдельных функций и объектов компиляции.

    Программа еще должна решить:

    где caller положит аргументы?
где callee их найдет?
кто хранит return value?
как передать closure environment?
как вызвать generic body?
где взять конкретный runtime type для T?
кто соединит CALL с реальным адресом функции?
кто выбросит недостижимый код?
откуда runtime берет function name для stack trace?

    Пока эти вопросы не закрыты, путь:

    Go source
→ executable

    не закончен.

    0. Граница лекции¶

    Не превращаем тему в отдельный курс по системному программированию.

    Мы не разбираем глубоко:

    • полную спецификацию ELF;
    • Mach-O;
    • PE;
    • dynamic loader;
    • PLT / GOT;
    • все relocation types;
    • cgo ABI;
    • DWARF binary format;
    • внутренности каждого build mode;
    • алгоритмы linker layout;
    • конкретный encoding object files.

    Нас интересует причинная цепочка:

    вызов функции
↓
ABI contract
↓
generic specialization / dictionary
↓
symbols
↓
relocations
↓
reachability
↓
linker
↓
runtime metadata
↓
executable

    Часть I. Go ABI¶

    1. Начнем с самой простой функции¶

    func add(a, b int) int {
    return a + b
}

    Для программиста:

    a
b
↓
add
↓
result

    Для CPU нет понятий:

    параметр a
параметр b
return value

    CPU знает:

    registers
stack
memory
instruction pointer
call / branch

    Нужен контракт.

    2. ABI — двоичный контракт между частями программы¶

    ABI — application binary interface.

    Для вызова функции он отвечает как минимум:

    где передавать аргументы?
↓
какие registers?
какие stack slots?
↓
где лежат результаты?
↓
какие registers можно испортить?
↓
где return address?
↓
как устроен stack frame?

    Если caller и callee используют разные правила:

    caller положил a в RAX
callee ищет a на stack

    Оба куска кода по отдельности могут выглядеть корректно.

    Вместе они не работают.

    3. API и ABI — разные вещи¶

    API:

    func add(a, b int) int

    говорит:

    два int
→ один int

    ABI говорит:

    первый int → конкретное физическое место
второй int → конкретное физическое место
result → конкретное физическое место

    То есть:

    API
→ логический контракт

ABI
→ физический двоичный контракт

    4. Go имеет ABIInternal¶

    Текущий Go использует внутренний ABI:

    ABIInternal

    Все функции, определенные на Go, компилируются под него.

    Главное свойство:

    ABIInternal — внутренний, нестабильный контракт toolchain.

    Он может меняться между версиями Go.

    Прикладной код не должен от него зависеть.

    5. И есть ABI0¶

    Для пользовательского Go assembler существует стабильный стековый ABI:

    ABI0

    Упрощенно:

    ABIInternal
→ современный внутренний ABI Go

ABI0
→ стабильный стековый интерфейс для assembly boundary

    Они могут взаимодействовать через wrappers.

    6. Почему вообще понадобилось два ABI¶

    Исторически Go передавал аргументы в основном через stack.

    Это просто:

    caller
↓
положить arguments в stack frame
↓
callee читает из stack

    Но функция часто уже имеет нужные значения в CPU registers.

    Тогда получается:

    value уже в register
↓
STORE в stack
↓
CALL
↓
LOAD из stack

    Мы сделали лишний memory traffic только ради соглашения о вызове.

    7. Register-based calling convention¶

    Современный ABIInternal старается передавать аргументы и результаты через registers, когда это возможно.

    Идеальная цепочка:

    caller вычислил value в register
↓
этот register уже является argument register
↓
CALL
↓
callee использует register

    Вместо:

    register
↓
STORE
↓
stack
↓
LOAD
↓
register

    8. Но «arguments идут в registers» — слишком грубая модель¶

    Что делать с:

    func f(
    a int,
    s string,
    b []byte,
    x struct {
        P *Node
        N int
    },
) error

    string — два машинных компонента.

    Slice — три.

    Struct — несколько полей.

    Нужно общее правило разложения.

    9. ABI работает с компонентами значений¶

    На высоком уровне current ABI assignment делает:

    argument / result
↓
разложить тип на базовые компоненты
↓
попробовать назначить компоненты registers
↓
не помещается целиком?
→ весь argument/result в stack

    Ключевое слово:

    целиком

    10. Почему аргумент не хотят наполовину держать в registers, наполовину в stack¶

    Пусть:

    type S struct {
    A int64
    B int64
    C int64
}

    Представим:

    A → register
B → register
C → stack

    Потом callee делает:

    p := &s

    Теперь s нужен как единый объект в обычной memory layout.

    Пришлось бы:

    собрать register pieces
+
stack piece
↓
новая contiguous memory representation

    Цена и сложность.

    Поэтому current ABI предпочитает:

    argument помещается в доступные registers целиком?
├── да → register-assigned
└── нет → весь argument на stack

    11. Простые целые типы¶

    Например:

    func f(a int64, b uint32)

    На 64-bit architecture:

    a
→ integer argument register

b
→ следующий integer argument register

    Маленький uint32 не обязательно упаковывается рядом с другим значением в тот же register.

    Базовые values получают собственные register positions.

    12. Почему не паковать два uint32 в один 64-bit register¶

    Теоретически:

    a uint32
b uint32
↓
один register

    Экономим register.

    Но потом caller/callee должны:

    pack
unpack
mask
shift

    Registers на современных CPU обычно достаточно.

    Часто выгоднее:

    простая схема
+
меньше упаковки

    13. Pointer-like types¶

    Текущий ABI рассматривает как один pointer-sized component:

    *T
unsafe.Pointer
map
chan
func

    То есть:

    map[K]V

    в параметре функции физически передается как pointer-like runtime representation.

    Не вся hash table копируется в вызов.

    14. string раскладывается на два компонента¶

    Мы уже знаем representation:

    string
├── data pointer
└── len

    ABI может передать эти компоненты отдельно:

    data → integer register
len  → integer register

    если хватает register budget.

    15. Slice раскладывается на три компонента¶

    []T
├── data
├── len
└── cap

    Поэтому:

    func f(s []byte)

    может использовать несколько registers только для одного логического аргумента s.

    Вот где representation из обычной лекции напрямую влияет на calling convention.

    16. Interface тоже состоит из двух компонентов¶

    Из 4.1:

    empty interface
→ Type + Data

non-empty
→ ITab + Data

    ABI видит:

    два pointer-sized components

    Значит interface argument может потребовать два integer registers.

    17. Struct разлагается рекурсивно¶

    type S struct {
    A int64
    B *Node
}

    ABI пробует:

    A → integer register
B → integer register

    То есть struct не обязательно:

    копируется целиком в stack

    18. Но array — важное исключение¶

    Текущий ABI специально различает arrays.

    [0]T
→ ничего

[1]T
→ можно рекурсивно разложить элемент

[N]T, N > 1
→ register assignment fails
→ array целиком идет в stack

    Почему?

    19. Почему non-trivial array оставляют в stack¶

    Array предполагает индексирование:

    a[i]

    Если элементы разложены по несмежным registers:

    computed index
→ какой register выбрать?

    CPU не умеет динамически индексировать набор general-purpose registers как массив.

    В памяти:

    base + i*sizeof(T)

    естественно.

    Поэтому массивы длиной больше 1 текущий ABI оставляет stack-assigned.

    20. Важный принцип: assignment пробуется целиком¶

    Пусть type рекурсивно разложился на 6 integer components.

    Доступно только 5 argument registers.

    Текущий ABI не делает:

    5 в registers
1 в stack

    Он откатывает попытку:

    весь argument → stack

    21. Arguments и results используют один общий принцип¶

    Caller передает arguments.

    Callee возвращает results.

    Но register counters для results начинаются заново.

    То есть одни и те же физические registers могут использоваться:

    на входе
→ для arguments

на выходе
→ для results

    Это нормально.

    Call boundary разделяет эти моменты.

    22. Но stack space arguments и results раздельный¶

    Stack frame содержит отдельные области:

    stack-assigned arguments
↓
alignment
↓
stack-assigned results
↓
alignment
↓
spill area для register arguments

    Это уже не просто:

    все параметры подряд

    23. Spill area существует даже для register arguments¶

    Пусть argument передан в register.

    Caller все равно резервирует stack spill space для него.

    Но при обычном call это место может остаться неинициализированным.

    Зачем резервировать?

    24. Stack growth объясняет spill area¶

    Callee входит в функцию.

    Выясняется:

    текущего stack недостаточно

    Нужно:

    grow stack

    Но аргументы сейчас находятся в registers.

    Stack growth machinery может понадобиться сохранить call state.

    Caller заранее зарезервировал home/spill area.

    Получаем:

    register argument
↓
при необходимости spill
↓
stack growth
↓
restore

    25. Это связывает ABI с уже прочитанным stack growth¶

    В Runtime deep стек мог:

    grow
move

    Теперь видно условие корректности:

    ABI должен позволять рантайму пережить stack growth посреди function entry, не потеряв аргументы.

    Это одна из причин, почему calling convention проектируется вместе с runtime.

    26. Адрес register-assigned аргумента тоже требует memory representation¶

    Пишем:

    func f(x int) {
    p := &x
    use(p)
}

    На входе x может быть:

    register

    Но оператор:

    &x

    требует адрес.

    Адрес register не существует в обычной Go memory model.

    Нужно:

    spill x
↓
stack slot
↓
&slot

    Spill area дает удобное место.

    27. Значит register ABI не означает «аргументы никогда не попадают в stack»¶

    Они могут попасть туда:

    • из-за stack growth;
    • если callee берет адрес;
    • из-за register pressure;
    • для traceback/debug needs;
    • потому что сам аргумент не помещается в registers.

    Правильная модель:

    registers — предпочтительный транспорт через call boundary

    а не:

    stack больше не нужен

    28. amd64: текущий набор integer argument/result registers¶

    На amd64 current ABIInternal использует последовательность:

    RAX
RBX
RCX
RDI
RSI
R8
R9
R10
R11

    То есть 9 integer registers для аргументов и результатов.

    Для floating-point используются:

    X0–X14

    Это деталь ABIInternal Go 1.27.x, не контракт языка.

    29. Почему не используется обычный System V ABI напрямую¶

    Плохая модель:

    Мы на Linux amd64, значит Go обязан вызывать свои функции ровно по SysV ABI.

    Нет.

    Go compiler и runtime — одна управляемая система.

    Им выгодно иметь собственный ABI, учитывающий:

    • stack growth;
    • goroutine pointer;
    • closures;
    • reflection;
    • Go type layout;
    • GC metadata.

    При boundary с C/platform ABI нужны отдельные механизмы.

    30. amd64: специальные registers¶

    Current internal ABI резервирует специальные роли.

    Например:

    RSP → stack pointer
RBP → frame pointer
RDX → closure context pointer
R14 → current goroutine

    Это еще один пример:

    не все registers доступны allocator одинаково

    31. g в отдельном register¶

    Из runtime deep:

    G
→ текущая goroutine

    На amd64 Go держит current goroutine pointer в:

    R14

    Это позволяет runtime/compiler быстро обращаться к состоянию G без обычного function argument.

    Еще один пример скрытого контракта между runtime и generated code.

    32. arm64: больше argument registers¶

    Текущий arm64 ABIInternal использует:

    R0–R15

    для integer arguments/results.

    И:

    F0–F15

    для floating-point.

    То есть physical mapping отличается от amd64.

    33. arm64 имеет link register¶

    На amd64 CALL кладет return PC в stack.

    На arm64:

    R30

    является link register.

    Function prologue при необходимости сохраняет его в frame.

    Значит даже такой базовый вопрос:

    где return address?

    зависит от ISA.

    34. Но общий ABI algorithm остается единым¶

    Go старается иметь общую концепцию:

    разложить values
↓
назначить integer/fp registers
↓
не поместилось?
→ stack

    А затем architecture определяет:

    какие именно registers
какой stack alignment
какие special registers

    35. Почему 16 registers arm64 не означают автоматически «вызовы быстрее»¶

    Можно посчитать:

    arm64 argument registers = 16
amd64 = 9

    и сделать вывод:

    arm64 ABI лучше.

    Слишком просто.

    Реальная цена зависит от:

    • сигнатур функций;
    • register pressure внутри callee;
    • ISA;
    • compiler lowering;
    • microarchitecture;
    • memory behavior.

    ABI registers — только один слой.

    36. Return values тоже могут идти через registers¶

    func f() (int, string)

    Results логически:

    int
string.data
string.len

    Compiler/ABI может назначить:

    несколько result registers

    и избежать memory round-trip.

    37. Большой result может уйти в stack¶

    Если result не удается целиком назначить registers:

    result stack area

    Caller заранее знает, где callee запишет результат.

    То есть:

    callee writes
↓
caller-owned call frame area

    38. Это не «heap allocation для возврата struct»¶

    Очень важное разрушение.

    func f() BigStruct

    Большой result может передаваться через stack memory.

    Это не означает:

    BigStruct обязательно heap

    ABI stack result и Go heap allocation — разные понятия.

    39. Closure вызывает новую проблему¶

    func makeAdder(x int) func(int) int {
    return func(y int) int {
        return x + y
    }
}

    При вызове closure нужны:

    обычные arguments
+
closed-over environment

    Где передать environment?

    40. Func value — не просто code pointer¶

    Полезная current ABI-модель:

    func value
↓
closure object
├── entry PC
└── environment bytes / references

    Call closure должен передать:

    куда прыгнуть
+
где лежит environment

    41. Closure context register¶

    Каждая architecture выделяет специальный register для closure context.

    Например current amd64:

    RDX

    arm64:

    R26

    Перед closure call:

    closure object address
→ closure context register

    Обычные arguments продолжают идти по обычному ABI.

    42. Почему environment не делать первым обычным аргументом¶

    Можно было бы концептуально переписать:

    func(y int) int

    в:

    func(env *Closure, y int) int

    Но dedicated register:

    • отделяет hidden context от обычной сигнатуры;
    • упрощает generated wrappers;
    • не сдвигает обычное assignment аргументов.

    Это internal design choice.

    43. Method value похож на closure¶

    f := obj.Method
f(x)

    Нужно сохранить:

    receiver obj

    в function value environment.

    То есть method value физически становится близок к closure:

    entry code
+
captured receiver

    44. Static method call и method value — разные machine paths¶

    obj.Method(x)

    Compiler знает receiver прямо в call site.

    А:

    f := obj.Method
f(x)

    создает function value с captured receiver.

    Синтаксис похож.

    Физическая структура отличается.

    45. Теперь ABI0¶

    Пусть у нас Go assembly function.

    Stable assembly ABI исторически stack-based:

    caller
↓
arguments in stack ABI layout
↓
assembly body

    Но обычный Go caller работает через ABIInternal.

    Нужен переход.

    46. ABI wrapper¶

    Концептуально:

    ABIInternal caller
↓
wrapper
├── взять register arguments
├── разложить в ABI0 stack slots
↓
CALL ABI0 body
↓
взять stack results
↓
положить в ABIInternal result registers
↓
return

    Wrapper — реальный код.

    Но toolchain старается делать это прозрачно.

    47. Цена ABI boundary¶

    Если горячий код часто пересекает:

    ABIInternal ↔ ABI0

    может появиться:

    • перекладывание аргументов;
    • дополнительный wrapper call;
    • stack traffic.

    Для обычного pure Go этого почти не замечаем.

    Для assembly/cgo boundaries это уже реальная стоимость.

    48. Почему ABIInternal нестабилен¶

    Потому что Go team хочет иметь свободу менять:

    • register assignment;
    • stack conventions;
    • special registers;
    • optimizations;
    • runtime coordination.

    Если бы user assembly напрямую зависел от ABIInternal навсегда:

    любое улучшение ABI
→ ломает ecosystem

    Поэтому стабильный public assembly boundary отделен.

    49. ABI как часть производительности¶

    Один function call под нагрузкой:

    несколько register moves
CALL
RET

    почти неинтересен.

    Теперь:

    500 млн calls/s

    или:

    очень широкий signature

    или:

    частые wrappers

    Цена становится измеримой.

    Но начинаем все равно с профиля.

    50. Что важно запомнить по ABI¶

    1. ABI — физический контракт caller/callee, а не API.
    2. Go source functions используют нестабильный ABIInternal.
    3. Go assembler опирается на стабильный ABI0.
    4. Current ABIInternal предпочитает registers, но stack никуда не исчез.
    5. Composite values рекурсивно раскладываются на ABI components.
    6. Argument/result либо целиком register-assigned, либо целиком stack-assigned.
    7. Arrays длиной больше 1 — важное current исключение: они идут на stack.
    8. Caller резервирует spill area для register arguments.
    9. Spill area связан со stack growth и возможностью взять адрес argument.
    10. amd64 и arm64 используют разные physical registers при общем ABI design.
    11. Closure environment передается через специальный closure-context register.
    12. ABI wrappers соединяют ABIInternal и ABI0.
    13. Все точные register numbers и layout rules — детали текущего Go, а не спецификации языка.

    Часть II. Generics codegen¶

    51. Теперь появляется type parameter¶

    func Identity[T any](x T) T {
    return x
}

    На уровне языка все понятно:

    T
→ какой-то type argument

    Но машинный код требует конкретики:

    сколько bytes в T?
какие операции допустимы?
есть ли pointers?
как вернуть T?

    Как компилировать тело, пока T неизвестен?

    52. Две крайние стратегии¶

    Первая:

    полная мономорфизация

    Для каждого T:

    Identity[int]
Identity[string]
Identity[User]
Identity[*Node]
...

    отдельный machine code.

    53. Плюс полной мономорфизации¶

    Compiler знает concrete type.

    Можно максимально специализировать:

    sizeof(T)
layout
methods
operations

    И generated code может стать очень простым.

    54. Минус полной мономорфизации¶

    Пусть generic function используется с:

    500 type arguments

    Получаем:

    500 copies of code

    Цена:

    binary size ↑
compile time ↑
instruction cache pressure потенциально ↑

    55. Вторая крайность — одна полностью динамическая функция¶

    Можно было бы сделать:

    Identity(dynamicTypeInfo, pointerToValue)

    для всех T.

    Кода мало.

    Но compiler потерял много static information.

    Цена:

    runtime metadata loads
indirection
хуже inlining
хуже specialization

    56. Go использует промежуточную схему¶

    Текущая реализация комбинирует:

    shape types
+
stenciled generic bodies
+
runtime dictionaries
+
wrappers

    Не нужно запоминать все имена.

    Нужно понять, какую проблему решает каждый слой.

    57. Сначала обычная type instantiation¶

    Identity(42)

    Type checker выводит:

    T = int

    На уровне языка функция теперь имеет конкретную инстанциацию:

    Identity[int]

    Но это еще не означает:

    Compiler обязательно сделает уникальное полностью специализированное тело только для int.

    58. Type checking и codegen — разные стадии¶

    Type checker отвечает:

    какой concrete type argument?
валидна ли программа?

    Codegen отвечает:

    какое тело machine code использовать?
какая runtime metadata нужна?

    Эти вопросы нельзя смешивать.

    59. Shape type¶

    Compiler имеет специальные:

    shape types

    Внутренний package для них называется:

    go.shape

    Сам compiler помечает shape как representation:

    набора близко связанных типов

    для generics implementation.

    60. Плохое упрощение: shape = sizeof(T)¶

    Нет.

    Если два type имеют одинаковый size:

    8 bytes

    это не автоматически означает:

    одна shape

    Shape учитывает более глубокие representation constraints реализации.

    Правильно:

    Shape — внутренний compiler type для совместного codegen группы совместимых instantiations.

    61. Зачем shape вообще нужна¶

    Пусть:

    func Zero[T any]() T {
    var z T
    return z
}

    Если несколько type arguments могут использовать одинаковую code shape:

    не нужно обязательно генерировать полностью независимое body для каждого

    Можно:

    несколько instantiations
↓
одно shaped implementation

    62. Но shape теряет concrete identity типа¶

    Внутри shaped body compiler знает:

    representation shape

    Но иногда программе нужна именно concrete runtime type identity.

    Например:

    func Box[T any](x T) any {
    return x
}

    Чтобы построить interface:

    нужен *runtime type descriptor именно concrete T

    go.shape.X недостаточно.

    63. Значит нужен второй канал информации¶

    Shaped function знает:

    как работать с representation

    Но должна получить:

    какой concrete T вызвал эту instantiation?

    Вот здесь появляется:

    dictionary

    64. Dictionary — runtime metadata конкретной инстанциации¶

    Учебно:

    generic body for shape S
+
dictionary[int]

    или:

    generic body for shape S
+
dictionary[MyType]

    Один body.

    Разные dictionaries.

    65. Что может лежать в dictionary¶

    Текущий runtime dictionary может содержать секции с информацией вроде:

    runtime type descriptors
itab pointers
sub-dictionaries
method expressions для type parameters

    То есть dictionary не является:

    одним type ID

    Это таблица конкретных runtime данных, которые shaped body не может знать статически.

    66. Runtime type descriptors¶

    Пусть generic body делает:

    return any(x)

    Нужно сформировать:

    Type + Data

    из 4.1.

    Data можно построить по representation.

    Но Type должен указывать на:

    concrete T

    Dictionary дает соответствующий runtime type descriptor.

    67. itab в dictionary¶

    Пусть операция требует interface conversion:

    T → SomeInterface

    В runtime representation нужен:

    ITab(concrete T, interface)

    Если concrete T известен только instantiation dictionary:

    dictionary
↓
itab slot

    может дать готовую связь.

    68. Subdictionary¶

    Generic function может вызвать другую generic function:

    func Outer[T any](x T) {
    Inner[T](x)
}

    Outer работает с dictionary для T.

    Inner[T] тоже может требовать собственный dictionary.

    Значит:

    dictionary Outer
↓
subdictionary Inner[T]

    69. Method expression для type parameter¶

    Generic body может обращаться к method information, зависящей от T.

    Опять:

    shape

    не всегда достаточно.

    Concrete method expression может быть одним из dictionary slots.

    70. Как dictionary попадает в function¶

    Самая важная физическая модель:

    source:
F[T](x)

generated shaped body:
F[shape](dictionary, x)

    Dictionary становится скрытым параметром.

    71. И вот здесь generics упираются в ABI¶

    Hidden dictionary parameter тоже нужно передать:

    через register
или
через stack

    То есть generic codegen меняет фактическую generated signature.

    ABI должен назначить физическое место и dictionary, и обычным arguments.

    72. Generic function call в полном виде¶

    caller знает:
T = int
↓
выбрать shaped implementation
↓
найти dictionary[int]
↓
ABI assignment:
dictionary
x
other args
↓
CALL shaped body

    Теперь generics перестают быть чисто type-system feature.

    73. Dictionary pointer тоже создает register pressure на call boundary¶

    Обычная функция:

    x, y

    Generic shaped function:

    dictionary, x, y

    Появился дополнительный hidden argument.

    В большинстве функций это незаметно.

    Но физически он существует.

    74. Stenciling¶

    Термин удобно понимать так:

    Compiler создает конкретное исполняемое тело generic declaration для определенной shape/instantiation context.

    Не обязательно:

    один unique machine body на каждый T

    И не:

    один полностью dynamic body на все T мира

    75. Имена generated generic symbols можно увидеть¶

    В binary/object symbols появляются имена, связанные с:

    go.shape...

    и instantiations.

    Например через:

    go tool nm ./app

    можно увидеть, что generic codegen — не магия, а реальные symbols и data.

    76. Почему F[int] и F[MyInt] могут не означать две полностью независимые функции¶

    Если compiler считает их representation совместимой для shaped code:

    общий shaped body
+
разные dictionaries

    может быть выгоднее полного duplication.

    Но exact shape sharing — деталь реализации и версии.

    77. Почему нельзя строить performance reasoning только на type arguments¶

    Плохой вывод:

    Я вызвал generic с 100 типами, значит binary содержит ровно 100 полных копий функции.

    Не обязательно.

    Правильные инструменты:

    go tool nm
go tool objdump
binary size

    78. Generic constraints тоже влияют на возможный codegen¶

    func Add[T ~int | ~int64](a, b T) T {
    return a + b
}

    Constraint сообщает compiler:

    операция + разрешена

    Но concrete instruction width/shape все равно зависит от actual representation.

    79. Generic method call¶

    Теперь:

    func Call[T SomeConstraint](x T) {
    x.M()
}

    В обычном concrete code compiler хотел бы:

    devirtualize
↓
direct call

    Но receiver может быть:

    shape type

    80. Почему shape мешает обычной девиртуализации¶

    Compiler знает:

    shape

    Но не всегда знает, какой dictionary нужен concrete method implementation.

    Текущий devirtualizer прямо имеет случаи:

    receiver IsShape / HasShape
↓
не девиртуализировать обычным путем

    потому что вызову может понадобиться dictionary argument.

    81. Вот где abstraction имеет реальную цену¶

    Generic method path может сохранить:

    dictionary dependency

    там, где обычный concrete call мог бы стать:

    direct call
→ inline

    Это не значит:

    generics медленные

    Это значит:

    некоторые compiler proofs сложнее

    82. Но inlining может снова убрать часть dictionary machinery¶

    Если generic instantiation и call site достаточно concrete:

    inline
↓
dictionary loads становятся constants
↓
dead code / redundant loads исчезают

    То есть cost model снова зависит от optimization context.

    83. Поэтому dictionary overhead нельзя оценивать из исходника¶

    Нужно смотреть:

    generated body
↓
inline?
↓
dictionary slot load остался?
↓
method call direct/indirect?

    84. Generic type methods и wrappers¶

    Пусть:

    type Box[T any] struct {
    V T
}

func (b Box[T]) Get() T {
    return b.V
}

    Для concrete:

    Box[int]

    runtime method table / itab нужны concrete-looking methods.

    Но actual generic implementation может быть shaped.

    85. Wrapper соединяет concrete method table и shaped body¶

    Концептуально:

    method expected by itab:
Box[int].Get
↓
wrapper
↓
подставить dictionary[int]
↓
CALL shaped Get implementation

    Это очень похожая идея на ABI wrapper.

    Только здесь boundary:

    concrete instantiated method
↔
generic shaped implementation

    86. Почему wrapper нужен для itab¶

    Из 4.1:

    ITab.Fun[]

    должен содержать function pointers.

    Runtime хочет:

    обычную callable function
с concrete receiver signature

    Он не хочет каждый interface dispatch заново разбираться:

    какой dictionary?
какая shape?

    Wrapper заранее адаптирует вызов.

    87. Current compiler прямо генерирует такие wrappers¶

    Для instantiated generic types используются fully stenciled wrappers, которые вызывают shaped implementation с нужным dictionary.

    Учебная схема:

    interface dispatch
↓
concrete wrapper
↓
dictionary
↓
generic body

    88. Generic methods в Go 1.27¶

    Go 1.27 разрешил concrete methods с собственными type parameters.

    Например:

    type Mapper[E any] struct {
    Data []E
}

func (m Mapper[E]) Map[T any](f func(E) T) []T {
    out := make([]T, len(m.Data))
    for i, v := range m.Data {
        out[i] = f(v)
    }
    return out
}

    Теперь type parameters могут принадлежать не только function/type declaration, но и concrete method.

    89. Но generic interface methods все еще запрещены¶

    Интерфейс не может объявить:

    type I interface {
    M[T any](T)
}

    Почему это важное ограничение для codegen?

    90. Обычный interface dispatch имеет конечный method set¶

    Из 4.1:

    interface type
↓
фиксированный набор methods
↓
ITab.Fun[]

    Linker/runtime заранее могут подготовить:

    function pointers

    91. Generic interface method потребовал бы новые instantiations после dynamic dispatch¶

    Если бы было:

    i.M[int]()
i.M[string]()

    а concrete dynamic type i неизвестен до runtime:

    какие concrete generic method instantiations нужны?

    Ответ зависит одновременно от:

    dynamic receiver type
+
runtime-chosen interface value
+
type arguments call site

    Это намного сложнее closed-world compilation.

    92. Поэтому Go 1.27 проводит границу¶

    Разрешено:

    generic methods на concrete types

    Не разрешено:

    generic interface methods

    И обычный generic method сам по себе не может реализовать hypothetical generic interface method.

    Это design boundary языка.

    93. Code size trade-off¶

    Generics implementation балансирует:

    больше specialization
↓
быстрее / больше optimization potential
но
binary size ↑

больше sharing через shapes
↓
binary size ↓
но
dictionary machinery ↑

    Это classic компромисс:

    code size
↔
specialization

    94. Instruction cache тоже часть цены¶

    Если полностью размножить huge generic function для сотен T:

    text segment ↑
↓
instruction working set ↑
↓
i-cache pressure потенциально ↑

    Не только размер binary на диске.

    95. Но shared generic body тоже не бесплатен¶

    Dictionary-based sharing может добавить:

    hidden argument
metadata load
wrapper
indirection

    Какой вариант выгоднее — задача compiler design.

    96. Почему Go compiler имеет право менять эту стратегию¶

    Language specification гарантирует:

    семантику generics

    Она не гарантирует:

    shape name
dictionary layout
число generated functions
wrapper strategy

    Все это implementation detail.

    97. Production: где generics реально могут проявиться¶

    CPU profile может показать:

    generic wrapper
shaped function
interface path

    Binary size может вырасти.

    Но расследуем:

    конкретный hot instantiation

    а не:

    В проекте есть generics, значит проблема в них.

    98. Диагностика generics¶

    Минимальная цепочка:

    benchmark / CPU profile
↓
go tool nm
↓
найти shape/instantiation symbols
↓
objdump
↓
есть dictionary loads?
wrapper?
indirect call?
↓
-m=2 / SSA при необходимости

    99. Что важно запомнить по generics codegen¶

    1. Type instantiation и code generation — разные стадии.
    2. Current Go использует shape types для совместного codegen близких instantiations.
    3. Shape — не просто sizeof(T).
    4. Shaped body может терять concrete runtime identity T.
    5. Dictionary передает concrete runtime metadata инстанциации.
    6. Dictionary может содержать runtime types, itabs, subdictionaries и method-expression data.
    7. Dictionary физически становится скрытым argument generated function.
    8. Значит generics codegen напрямую связан с ABI.
    9. Generic method calls на shaped receivers сложнее девиртуализировать.
    10. Instantiated generic methods могут получать concrete wrappers для method tables/itabs.
    11. Inlining способен убрать часть dictionary overhead.
    12. Exact shape sharing, dictionary layout и generated symbols — детали current compiler.
    13. Go 1.27 добавил generic methods у concrete types, но не generic interface methods.
    14. Цена generics — компромисс specialization, code size и runtime metadata work.
    15. Диагноз ставится по generated code и профилю, а не по наличию [...] в исходнике.

    Часть III. Linker¶

    100. Компилятор еще не создал executable целиком¶

    После компиляции отдельных packages у нас есть:

    machine code fragments
data
runtime type metadata
symbols
relocations
export data

    Но пока нет одной окончательной карты:

    что лежит по какому адресу в готовой программе

    Этим занимается linker.

    101. Сначала разберемся с symbol¶

    Учебно symbol — именованный объект, который linker должен уметь найти.

    Например:

    main.main
runtime.chansend
mypkg.Process
type:*mypkg.User
go:string....
dictionary...
wrapper...

    У symbol есть:

    имя
тип/класс
данные или код
размер
references
relocations
attributes

    102. Почему function name нужен как symbol¶

    Package A содержит:

    func F() {}

    Package B вызывает:

    A.F()

    B при собственной компиляции может еще не знать:

    финальный virtual address A.F в executable

    Но он знает:

    symbol A.F

    Этого достаточно, чтобы оставить ссылку для linker.

    103. Relocation — отложенное связывание адреса¶

    Представим machine code:

    CALL ???

    Compiler/assembler знает:

    нужно вызвать symbol A.F

    Но exact displacement/address станет известен после layout.

    Он оставляет relocation:

    в этом месте
↓
после размещения symbols
↓
подставить reference на A.F

    104. Почему адрес нельзя всегда знать при компиляции package¶

    Потому что:

    package A
package B
runtime
standard library

    компилируются раздельно.

    Linker позже решит:

    какие symbols вообще войдут
в каком порядке
с каким alignment
в какие sections

    Адрес зависит от итоговой программы.

    105. Relocation — не только CALL¶

    Reference может быть:

    адрес global data
type descriptor
string data
method wrapper
dictionary
itab
runtime metadata

    То есть linker связывает не только control flow.

    Он связывает всю объектную граф-модель программы.

    106. Очень полезная модель: программа до linker — граф symbols¶

    main.main
├── calls app.Run
├── references type:Config
└── references string:"start"

app.Run
├── calls runtime.chansend
├── references type:Job
└── calls generic wrapper

generic wrapper
├── references dictionary
└── calls shaped body

    Relocations — ребра графа.

    Symbols — вершины.

    107. Linker сначала должен загрузить этот граф¶

    Object data из скомпилированных packages содержит:

    symbols
+
relocations
+
metadata

    Go linker имеет loader layer, который дает единое пространство symbols для дальнейших passes.

    Нас не интересует binary encoding object files.

    Нас интересует результат:

    единый symbol graph

    108. Reachability: нужен ли symbol программе вообще¶

    Пусть package содержит:

    func Used() {}

func NeverCalled() {}

    Если NeverCalled никем не достижим:

    зачем класть его machine code в executable?

    Можно удалить.

    109. Dead-code elimination linker¶

    Linker начинает с roots.

    Учебно:

    entry points
runtime-required roots
init tasks
exported/runtime-required metadata

    Дальше:

    mark root reachable
↓
пройти его relocations
↓
пометить referenced symbols
↓
повторять

    Это graph traversal.

    110. Недостижимые text symbols можно выбросить¶

    После reachability:

    symbol reachable?
├── да → оставить
└── нет → не включать как живой код

    Получаем linker dead-code elimination.

    Это отличается от compiler DCE из 4.3.

    111. Compiler DCE и linker DCE работают на разных масштабах¶

    Compiler DCE:

    внутри функции / package compilation

    Например:

    мертвый basic block

    Linker DCE:

    между symbols всей программы

    Например:

    целая функция
никогда не reachable из final program

    112. Почему package import не означает «весь package в binary»¶

    Импортировали library.

    В ней:

    1000 functions

    Используем:

    5 functions

    Reachability позволяет не тащить часть остальных.

    Но есть важные исключения и консервативные случаи.

    113. Interfaces ломают простую модель direct call graph¶

    Пусть:

    var w io.Writer = someValue
w.Write(buf)

    В binary call site содержит:

    interface method Write

    Но static graph может не иметь прямого:

    CALL (*MyWriter).Write

    Если linker смотрел бы только direct relocations:

    метод выглядел бы unused

    и мог бы быть удален ошибочно.

    114. Linker отслеживает interface method usage¶

    Compiler оставляет специальные marker relocations / metadata:

    этот concrete type используется как interface

    и:

    этот interface method реально вызывается

    Linker использует их для dead-method elimination.

    То есть:

    compiler
↔
linker

    снова имеют собственный скрытый контракт.

    115. Это продолжение истории ITab¶

    Из 4.1:

    ITab
→ method pointers

    Чтобы ITab содержал:

    method body должен остаться в executable.

    117. Reflection ломает closed direct-call world еще сильнее¶

    в исходнике отсутствует.

    Но runtime reflection может потребовать method.

    Если linker удалит его как unreachable:

    reflection сломается

    118. Поэтому reflection может удерживать больше methods¶

    После этого часть method reachability становится более консервативной.

    reflection
→ меньше возможностей dead-code elimination
→ binary size может вырасти

    Но это не означает:

    150. Что важно запомнить по linker¶

    1. После compiler/assembler программа еще состоит из symbols, data и relocations, а не финальных адресов.
    2. Symbol — именованный кусок code/data/metadata.
    3. Relocation — отложенная ссылка, которую linker разрешает после размещения symbols.
    4. До linker программу полезно представлять как graph symbols и references.
    5. Linker делает reachability analysis всей программы.
    6. Недостижимые code symbols могут быть удалены linker dead-code elimination.
    7. Compiler DCE и linker DCE работают на разных масштабах.
    8. Interface dispatch требует специальной method reachability, потому что direct call graph недостаточен.
    9. Reflection может заставить linker сохранять более широкий набор methods.
    10. Generic bodies, dictionaries, wrappers и instantiated type metadata становятся обычными symbols графа linker.
    11. Dictionary может тянуть runtime types, itabs и subdictionaries через relocations.
    12. Runtime type metadata является функциональной частью Go binary, а не только debug-данными.
    13. Linker назначает final addresses и применяет architecture-specific relocations.
    14. Linker строит pclntab, нужную runtime для function/file/line lookup.
    15. pclntab и DWARF — разные metadata systems.
    16. -w убирает DWARF, -s убирает symbol table/debug information согласно linker flags, но runtime-required metadata остается отдельной категорией.
    17. Go поддерживает internal/external link modes.
    18. cgo/platform integration может потребовать external linker.
    19. Final executable имеет platform file format, но эта лекция не требует изучения ELF/Mach-O/PE internals.
    20. Следующий слой после linker — OS loader и запуск процесса.

    206. Разрушаем плохие упрощения¶

    «ABI = где лежат аргументы в stack»¶

    Нет.

    Current Go использует registers + stack и специальные hidden contexts.

    «Register ABI означает stack больше не нужен»¶

    Нет.

    Stack нужен для frames, spills, large args, stack growth, results и metadata.

    «Struct всегда передается по pointer»¶

    Нет.

    Small struct может быть рекурсивно разложен по registers.

    «Большой return value = heap allocation»¶

    Нет.

    Он может быть stack-assigned по ABI.

    «Generics = полная мономорфизация как в шаблонах»¶

    Слишком грубо.

    Current Go использует shapes + dictionaries + stenciling/wrappers.

    «Dictionary = таблица методов»¶

    Слишком узко.

    Там могут быть runtime types, itabs, subdictionaries и method expressions.

    «Generic call всегда медленнее»¶

    Нет.

    Inlining/constant propagation могут убрать часть machinery.

    «Imported package целиком попадает в binary»¶

    Нет.

    Linker делает reachability/dead-code elimination.

    «Direct call graph полностью определяет reachability»¶

    Нет.

    Interfaces и reflection требуют дополнительной metadata.

    «-s -w удаляет всю информацию, нужную stack trace»¶

    Нет.

    Runtime metadata вроде pclntab — отдельный слой.

    «Linker просто склеивает файлы»¶

    Нет.

    Он решает reachability, layout, relocations, runtime metadata и platform output.

    212. Что важно запомнить¶

    1. ABI физически соединяет caller и callee.
    2. ABIInternal — нестабильный внутренний Go ABI; ABI0 — стабильный stack-based boundary для Go assembler.
    3. Current ABI передает values через registers, если весь argument/result может быть размещен там целиком.
    4. String, slice, interface и struct раскладываются на ABI components.
    5. Non-trivial arrays — важное исключение current ABI и проходят через stack.
    6. Register-assigned arguments имеют reserved spill/home area.
    7. Spill area нужен в том числе для stack growth и address-taking.
    8. amd64 current ABI использует 9 integer argument/result registers, arm64 — 16; exact mapping зависит от architecture.
    9. Closure вызывает функцию с дополнительным hidden closure-context register.
    10. ABI wrappers адаптируют ABIInternal и ABI0.
    11. Generic type instantiation не равна обязательной полной мономорфизации.
    12. Current compiler использует go.shape для shared shaped implementations.
    13. Dictionary возвращает shaped body concrete runtime information, потерянную при shape abstraction.
    14. Dictionary становится hidden argument и поэтому является частью фактической ABI signature generated function.
    15. Runtime dictionary может ссылаться на runtime types, itabs, subdictionaries и method expressions.
    16. Shaped receivers могут ограничивать обычную devirtualization из-за необходимости dictionary.
    17. Concrete wrappers адаптируют instantiated generic methods для itab/method-table calls.
    18. Go 1.27 поддерживает generic methods concrete types, но не generic interface methods.
    19. Generics codegen балансирует specialization и code size.
    20. После compiler code еще содержит symbolic references, которые должен разрешить linker.
    21. Symbol — вершина program graph; relocation — reference edge.
    22. Linker reachability удаляет недостижимый code на уровне всей программы.
    23. Interfaces и reflection усложняют reachability и dead-method elimination.
    24. Generic dictionaries/wrappers/type descriptors входят в linker symbol graph как обычные code/data dependencies.
    25. Linker назначает final addresses и применяет relocations.
    26. pclntab — runtime metadata для function/file/line lookup и не равна DWARF.
    27. DWARF в первую очередь нужен внешним debug tools.
    28. -w и -s управляют debug/symbol information, но runtime-required metadata — отдельная категория.
    29. Internal и external linking решают одну финальную задачу разными средствами.
    30. Главный диагностический набор темы: -S, go tool nm, go tool objdump, размер binary и профиль.
    31. Implementation details ABI/generics/linker не являются контрактом языка.
    32. Правильный инженерный путь всегда начинается с измеренного вопроса, а не с ручного чтения linker/compiler internals.

    Главный инженерный вывод:

    После 4.3 мы знали, как одна Go-функция превращается в машинный код. 4.4 закрывает пространство между функциями и между packages.
