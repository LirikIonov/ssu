    4.5. Запуск процесса глубже: executable, загрузчик ОС и dynamic linking¶

    Материал ориентирован на современный Linux, macOS и Go 1.27.x.

    Это продолжение 4.4. Go ABI, generics codegen и linker.

    В 4.4 мы закончили здесь:

    compiler
↓
linker
↓
executable

    Но executable пока просто лежит на диске.

    Новый вопрос:

    Что происходит между ./app и первой исполняемой инструкцией программы?

    И еще точнее:

    execve
↓
executable format
↓
loader
↓
virtual address space
↓
executable segments
↓
dynamic linker?
↓
relocations
↓
entry point
↓
Go runtime startup
↓
main.main

    Зачем открывать этот слой¶

    Наивная модель:

    есть binary
↓
OS запускает его
↓
main()

    Слишком грубо.

    У ядра есть файл.

    Внутри файла:

    headers
code
data
metadata

    Но процессу нужны:

    виртуальные адреса
права доступа к памяти
stack
arguments
environment
entry point
shared libraries

    И если binary динамически связан:

    часть symbols еще вообще не имеет окончательного runtime address

    Значит между:

    файл

    и:

    живой процесс

    существует отдельный загрузочный протокол.

    0. Граница с уже прочитанной виртуальной памятью¶

    В 3.x вопрос был:

    виртуальный адрес
↓
page tables
↓
физическая RAM
↓
page fault
↓
residency

    Это считаем известным.

    В 4.5 другой вопрос:

    Откуда вообще взялись виртуальные диапазоны процесса, в которых лежат код, данные и библиотеки?

    То есть:

    ELF / Mach-O
↓
loader
↓
VM mappings

    А потом уже знакомая система виртуальной памяти решает:

    какие страницы реально resident

    1. Executable — не просто массив машинных инструкций¶

    Плохая модель:

    binary file
=
machine code

    Нет.

    Файл должен еще описать:

    какой это формат?
для какой architecture?
какая точка входа?
что нужно отобразить в память?
по каким виртуальным адресам?
с какими правами?
нужен ли dynamic linker?
какие shared libraries нужны?

    Иначе ядро не знает, как интерпретировать bytes.

    2. На Linux основной формат — ELF¶

    ELF — Executable and Linkable Format.

    Один и тот же формат используется для:

    • executable;
    • shared objects;
    • object files;
    • core dumps.

    Но роли конкретных таблиц внутри файла различаются.

    3. ELF начинается с header¶

    Упрощенно ELF header содержит:

    magic
class
endianness
machine architecture
file type
entry point
program header location
section header location

    То есть первые bytes уже отвечают:

    Что это за файл и как его дальше разбирать?

    4. ELF magic¶

    Первые bytes:

    0x7f 'E' 'L' 'F'

    позволяют распознать ELF.

    Если kernel binary loader не узнает формат:

    он не может исполнять файл как ELF

    Дальше могут включаться другие handlers, например interpreter script через #!.

    5. ELF e_type¶

    Полезно различать:

    ET_EXEC
→ традиционный executable

ET_DYN
→ shared object
→ также используется PIE executable

    Почему PIE выглядит как ET_DYN?

    Потому что его code должен уметь жить при изменяемой load base.

    К этому вернемся при ASLR.

    6. ELF e_machine¶

    Поле отвечает:

    для какой ISA собран code?

    Например:

    x86-64
AArch64

    Ядро не может выполнить arm64 machine code на amd64 CPU без отдельного слоя эмуляции или трансляции.

    7. Entry point¶

    В ELF header есть:

    e_entry

    Это адрес точки, с которой нужно начать user-space execution после подготовки image.

    Очень важное разрушение:

    Для Go e_entry не указывает прямо на main.main.

    Сначала будет startup code рантайма.

    8. Sections и segments — не одно и то же¶

    Это один из самых частых источников путаницы.

    Sections:

    .text
.rodata
.data
.bss
.symtab
.debug_*
...

    удобны:

    • linker;
    • assembler;
    • debugger;
    • tools.

    Но kernel loader в первую очередь интересует:

    Program Header Table

    и:

    segments

    9. Почему loader не хочет грузить каждую section отдельно¶

    Представим executable:

    .text
.rodata
.eh_frame
.data
.bss

    Для загрузки процесса важнее:

    эти области можно читать + исполнять
эти только читать
эти читать + писать

    То есть loader хочет крупные VM regions.

    Sections могут быть сгруппированы в segments.

    10. Program Header Table¶

    ELF Program Header Table описывает segments.

    Каждая запись отвечает примерно:

    какой тип segment?
какой file offset?
какой virtual address?
сколько bytes в file?
сколько bytes в memory?
какие permissions?
какое alignment?

    Вот это уже почти инструкция загрузчику.

    11. PT_LOAD¶

    Главный тип:

    PT_LOAD

    означает:

    Этот диапазон executable image нужно отобразить в память процесса.

    Типичный executable имеет несколько PT_LOAD.

    Например:

    R--
R-X
R--
RW-

    Точная разбивка зависит от linker и platform.

    12. Поля PT_LOAD¶

    Особенно важны:

    p_offset
→ offset в executable file

p_vaddr
→ виртуальный адрес segment

p_filesz
→ сколько bytes реально лежит в file

p_memsz
→ сколько bytes segment должен занимать в memory

p_flags
→ R/W/X

    Получаем почти прямой рецепт mapping.

    13. Файл и виртуальная память связываются здесь¶

    Упрощенно:

    ELF PT_LOAD
↓
file offset X..Y
↓
virtual address A..B
↓
VM mapping

    После этого CPU может выполнять instruction по virtual address.

    А физические pages материализуются уже по правилам VM.

    14. Почему p_memsz может быть больше p_filesz¶

    Вот прекрасный вопрос.

    p_filesz = 100 KiB
p_memsz  = 10 MiB

    Откуда возьмутся остальные bytes?

    Обычно:

    zero-filled memory

    Вот здесь появляется .bss.

    15. .bss: гигантский нулевой массив не обязан занимать место в binary¶

    var buf [1 << 30]byte

    Логически:

    1 GiB zero-initialized global data

    Глупая реализация:

    binary содержит 1 GiB нулей

    Не нужна.

    В executable достаточно описать:

    в memory segment должен быть больше,
чем bytes, существующих в file

    Остальная часть при загрузке имеет zero semantics.

    16. Это прямой мост к demand paging¶

    Даже если:

    virtual mapping для BSS = 1 GiB

    это не означает:

    сразу заняли 1 GiB RAM

    Из VM-лекции:

    virtual
≠
resident

    Pages могут materialize при первом обращении.

    17. Permissions: почему code обычно R-X¶

    Code segment:

    read
execute
not write

    Data:

    read
write
not execute

    Это одна из базовых защит процесса.

    Плохая модель:

    вся память процесса — просто bytes

    Нет.

    Page table permissions участвуют в security contract.

    18. W^X¶

    Общая security-идея:

    Writable
XOR
Executable

    То есть memory обычно стараются не делать одновременно:

    W + X

    Если attacker может писать произвольные bytes в executable page:

    code injection становится намного проще

    19. Loader превращает ELF flags в VM protections¶

    Цепочка:

    PT_LOAD flags
↓
loader/kernel mapping
↓
page table permissions
↓
CPU MMU enforcement

    Вот как file metadata доходит до hardware protection.

    20. Значит ELF — это еще и описание будущего address space¶

    Не только:

    какие instructions выполнить

    Но:

    какие virtual regions создать

    Это ключевая модель.

    21. readelf -l¶

    Главный инструмент этой части:

    readelf -l ./app

    Показывает:

    Program Headers
LOAD segments
INTERP
DYNAMIC
GNU_STACK
GNU_RELRO
...

    Именно -l, а не только section table, отвечает на вопрос:

    Что loader собирается отображать?

    22. readelf -S¶

    readelf -S ./app

    показывает sections.

    Полезно сопоставить:

    section
↓
какой segment ее содержит

    Но не путать:

    section view

    с:

    loader view

    23. readelf -h¶

    readelf -h ./app

    Показывает:

    ELF class
machine
type
entry point
program headers

    Практика должна начинаться именно с:

    -h
-l
-S

    Часть II. execve¶

    24. Кто начинает загрузку executable¶

    Shell выполняет:

    ./app

    В конце цепочки нужен системный вызов семейства:

    execve

    25. Плохая модель: execve создает новый процесс¶

    Нет.

    execve заменяет program image текущего процесса.

    Если shell сначала создал child:

    fork / clone

    то дочерний process уже существует.

    Потом:

    execve

    заменяет его user-space program image.

    26. PID сохраняется¶

    до execve:
PID = X
работает старый program image

после execve:
PID = X
работает новый image

    То есть:

    exec
≠
создание нового PID

    27. Что меняется при execve¶

    Очень грубо:

    старые user-space mappings
↓
заменяются новым address-space image

    Создаются:

    новый code mapping
новый data mapping
новый stack
новая startup state

    Часть process attributes сохраняется, часть сбрасывается по правилам ОС.

    28. File descriptors могут пережить execve¶

    По умолчанию открытый file descriptor может остаться открытым через exec.

    Если установлен:

    FD_CLOEXEC

    kernel закрывает его при exec.

    29. Почему CLOEXEC существует¶

    Представим server:

    открыл secret fd
↓
запустил helper через exec

    Если fd случайно наследуется:

    новая программа получает доступ к ресурсу

    Утечка capability.

    Поэтому:

    close-on-exec

    — важная security/lifecycle семантика.

    30. execve получает argv и envp¶

    API концептуально:

    path
argv[]
envp[]

    После загрузки новая программа должна увидеть:

    os.Args

    и environment.

    Но main.main вызывается намного позже.

    31. Initial user stack¶

    Kernel формирует initial stack с данными вроде:

    argc
argv pointers
envp pointers
auxiliary vector
strings

    Учебно:

    initial stack
├── argc
├── argv[]
├── envp[]
├── auxv[]
└── raw strings

    Точная layout зависит от ABI/platform.

    32. Откуда берется os.Args¶

    Цепочка:

    execve argv
↓
kernel initial stack
↓
startup code / runtime
↓
Go runtime читает arguments
↓
os.Args

    То есть os.Args — результат bootstrapping от kernel ABI.

    33. Auxiliary Vector¶

    Помимо argv/env kernel передает:

    auxv

    Это пары:

    type
value

    с дополнительной startup-информацией.

    34. Что может быть в auxv¶

    Например:

    page size
program header address
random bytes
platform data
vDSO address

    Набор зависит от platform/architecture.

    35. Зачем auxv нужен¶

    Без него user-space startup пришлось бы узнавать часть platform state через дополнительные syscalls.

    Kernel уже знает данные при execve.

    Дешевле передать их сразу:

    kernel
↓
initial stack
↓
runtime / dynamic loader

    36. AT_RANDOM¶

    Интересный пример auxv.

    Kernel передает случайные bytes.

    Они могут использоваться user-space security mechanisms.

    Это показывает:

    часть security startup state
↓
существует еще до main

    37. vDSO¶

    Linux может отобразить специальный:

    vDSO

    в address space процесса.

    Это код, предоставленный kernel для части user-space operations.

    38. Идея vDSO¶

    Вместо полного:

    user
↓
syscall transition
↓
kernel
↓
return

    для некоторых операций можно использовать:

    user
↓
mapped vDSO code

    Конкретные functions зависят от architecture/kernel.

    39. vDSO тоже появляется как mapping процесса¶

    В:

    /proc/<pid>/maps

    можно увидеть:

    [vdso]
[vvar]

    Это не часть Go executable.

    Это mappings, добавленные kernel.

    40. execve и memory mappings¶

    Старые обычные program mappings не сохраняются.

    Новый executable получает новое address-space image.

    Это логично:

    заменили программу
↓
заменили ее code/data mappings

    41. Kernel не обязан читать executable целиком¶

    Плохая модель:

    execve
↓
прочитать весь binary в RAM
↓
start

    Нет.

    Loader создает file-backed mappings.

    42. Code pages могут загружаться лениво¶

    segment mapped
↓
code page еще не resident
↓
CPU впервые исполняет address
↓
page fault
↓
page cache / storage
↓
page resident

    Это уже знакомый demand paging.

    43. Большой executable не означает большой startup I/O сразу¶

    Binary:

    100 MiB

    Но startup может реально затронуть:

    малую часть code pages

    Остальные будут прочитаны только если выполнение до них дойдет.

    44. Это объясняет cold start¶

    Первый запуск:

    code pages cold
library pages cold
metadata cold
↓
page faults
↓
storage I/O
↓
startup latency ↑

    Повторный:

    page cache warm
↓
меньше дорогого I/O

    45. Startup page faults — не обязательно проблема¶

    При запуске:

    minor faults

    нормальны.

    Executable mappings, zero-filled data и libraries используют обычную VM machinery.

    Диагноз нужен, если faults становятся заметной частью latency.

    46. Container не меняет фундаментальный loader¶

    В Linux container:

    процесс
↓
тот же Linux kernel
↓
тот же ELF loader

    Container меняет окружение:

    mount namespace
filesystem view
cgroup
credentials

    Но binary загружает kernel хоста.

    47. Почему library может находиться в container, но отсутствовать на host¶

    Dynamic loader ищет dependency внутри:

    filesystem namespace процесса

    Container имеет другой root filesystem.

    Поэтому deployment нужно диагностировать внутри того же namespace, а не только на host.

    Часть III. ASLR и PIE¶

    48. Плохая модель: программа всегда загружается по одним адресам¶

    Предсказуемые addresses облегчают часть exploitation techniques.

    Поэтому современные ОС используют:

    ASLR

    Address Space Layout Randomization.

    49. Что может рандомизироваться¶

    Например base addresses:

    executable
shared libraries
stack
heap
mmap regions

    Точная policy зависит от ОС и типа binary.

    50. Traditional ET_EXEC¶

    Классический executable может быть связан под более фиксированную virtual layout.

    Это ограничивает свободу сдвигать весь image.

    51. PIE¶

    Position Independent Executable:

    code должен корректно работать
при изменяемом load base

    На ELF PIE обычно представлен как:

    ET_DYN

    52. Load base¶

    Вместо:

    F всегда 0x401000

    получаем:

    runtime address(F)
=
load base
+
relative offset(F)

    ASLR выбирает base.

    53. Position-independent code¶

    Код использует:

    PC-relative addressing
relative offsets
indirection tables

    там, где это выгодно.

    Это уменьшает зависимость от абсолютных адресов.

    54. Цена PIE¶

    Современные ISA хорошо поддерживают position-independent code.

    Но физически могут появляться:

    другие addressing modes
indirections
relocations

    Взамен основной executable image нормально участвует в ASLR.

    55. Проверяем PIE¶

    readelf -h ./app

    Смотрим:

    Type

    Запускаем несколько раз и сравниваем:

    /proc/<pid>/maps

    Ищем изменение base address.

    Часть IV. Dynamic linking¶

    56. Сначала статическая модель¶

    Самый простой executable:

    весь нужный code/data уже находится в binary

    Kernel:

    map PT_LOAD
↓
prepare stack
↓
jump to entry point

    User-space dynamic linker для shared dependencies не нужен.

    57. Зачем вообще shared libraries¶

    Представим много процессов, которым нужен один и тот же library code.

    Можно встроить его в каждый binary.

    Но можно:

    один .so file
↓
file-backed mappings
↓
несколько процессов

    Clean code pages могут физически делиться через page cache.

    58. Но shared libraries дают не только экономию¶

    Плюсы:

    • меньше дублирования code на диске;
    • централизованное обновление библиотеки при совместимом ABI;
    • переиспользование общего code.

    Цена:

    • runtime dependency;
    • loader startup;
    • symbol resolution;
    • compatibility;
    • deployment complexity.

    59. Как ELF сообщает, что нужен dynamic linker¶

    В Program Header Table может быть:

    PT_INTERP

    Он содержит pathname interpreter.

    Типичный glibc Linux:

    /lib64/ld-linux-x86-64.so.2

    или соответствующий путь другой architecture.

    60. Кто запускает interpreter¶

    Kernel ELF loader видит:

    PT_INTERP

    И подготавливает:

    main executable mappings
+
interpreter mappings

    Дальше user-space execution сначала попадает в dynamic linker.

    То есть:

    kernel
↓
ld-linux
↓
program

    61. Dynamic linker — user-space программа¶

    Это важное разрушение.

    ld-linux:

    не CPU magic
не обычная часть вашего main

    Это отдельный user-space runtime loader.

    Он:

    читает dynamic metadata
↓
загружает dependencies
↓
разрешает symbols
↓
применяет relocations
↓
передает управление program entry

    62. PT_DYNAMIC¶

    Динамически связанный ELF содержит dynamic information.

    Там встречаются entries вроде:

    DT_NEEDED
DT_STRTAB
DT_SYMTAB
DT_RELA / DT_REL
DT_RUNPATH

    Это входные данные dynamic linker.

    63. DT_NEEDED¶

    Каждая запись означает:

    нужна shared library X

    Например:

    libc.so.6

    Dynamic linker строит dependency graph.

    64. readelf -d¶

    readelf -d ./app

    Показывает Dynamic Section.

    Главный первый вопрос:

    есть ли NEEDED entries?

    Если нет:

    обычных shared-library dependencies может не быть

    65. ldd¶

    Для доверенного executable:

    ldd ./app

    помогает увидеть resolved dynamic dependencies.

    Но для недоверенного binary безопаснее предпочитать:

    readelf -d ./app

    потому что конкретная реализация ldd исторически может взаимодействовать с loader behavior.

    66. Как dynamic linker ищет library¶

    Упрощенно:

    DT_NEEDED name
↓
library search
↓
нашли file
↓
map shared object

    Search order зависит от loader/platform metadata.

    67. Источники search path¶

    В Linux/glibc могут участвовать:

    DT_RPATH
DT_RUNPATH
LD_LIBRARY_PATH
ld.so.cache
default library directories

    Точный priority зависит от конкретной комбинации.

    Для курса важнее понимать сам механизм поиска, а не заучивать весь порядок.

    68. Почему RUNPATH — deployment concern¶

    На ноутбуке:

    program starts

    В container:

    library not found

    Причина может быть:

    не найден shared object

    а не Go-код.

    Deployment artifact должен включать нужные libraries и корректный loader path.

    69. Shared object — тоже ELF¶

    .so содержит:

    ELF header
PT_LOAD
dynamic section
symbols
relocations

    Dynamic linker отображает ее segments в address space процесса.

    70. Где разместить shared library¶

    ASLR выбирает load region.

    Получаем:

    preferred relative layout
+
randomized base
↓
runtime addresses

    После этого часть references нужно доразрешить.

    71. Возвращаемся к relocations из 4.4¶

    Static linker смог разрешить:

    внутренние symbols,
известные final binary

    Но external shared symbol может получить окончательный runtime address только после загрузки .so.

    72. Dynamic relocation¶

    Учебно:

    relocation:
slot X должен ссылаться на symbol F
↓
dynamic linker нашел F
↓
записал runtime address F

    Вот что остается от линковки на startup.

    73. Почему не хочется переписывать executable text¶

    Если dynamic linker постоянно patch'ит:

    R-X code pages

    нужно временно делать code writable.

    Это хуже для security и sharing.

    Поэтому mutable addresses часто выносятся в специальные data structures.

    74. GOT¶

    Global Offset Table.

    Учебная модель:

    code
↓
GOT entry
↓
runtime address data/function

    Dynamic linker может изменить GOT entry.

    .text при этом остается executable/read-only.

    75. PLT¶

    Procedure Linkage Table.

    Упрощенно:

    CALL external F
↓
PLT entry
↓
GOT
↓
actual F

    Это один из способов организовать dynamic function calls через local stub.

    Точная machinery зависит от ISA/toolchain.

    76. Зачем GOT/PLT¶

    Они помогают совместить:

    position-independent code
+
dynamic addresses
+
read-only executable code

    То есть код не обязан содержать окончательный абсолютный адрес каждой external function.

    77. Lazy binding¶

    Function symbol можно разрешить не на startup.

    Первый вызов:

    CALL F@PLT
↓
GOT entry еще resolver
↓
dynamic resolver
↓
найти F
↓
переписать GOT
↓
вызвать F

    Повторный:

    PLT
↓
GOT
↓
F

    78. Зачем lazy binding¶

    Плюс:

    startup work меньше

    Если function никогда не вызовется:

    ее binding не понадобился

    Цена:

    первый call дороже

    79. Eager binding¶

    Альтернатива:

    resolve dynamic function symbols при startup

    Плюсы:

    нет first-call resolver path
ошибки symbol resolution проявляются раньше

    Минус:

    startup work больше

    80. LD_BIND_NOW¶

    Для glibc:

    LD_BIND_NOW=1 ./app

    просит eager resolution.

    Это хороший лабораторный эксперимент:

    startup cost
↔
first-call cost

    Если binary не использует dynamic loader, эффекта не будет.

    81. LD_DEBUG¶

    Полезный glibc diagnostic mechanism:

    LD_DEBUG=libs,reloc,bindings ./app

    Можно увидеть:

    library search
relocations
symbol bindings

    Для лаборатории отлично.

    Для production output слишком шумный.

    82. RELRO¶

    Часть relocation-related data нужна writable только во время loader setup.

    После:

    relocations применены

    ее можно сделать:

    read-only

    Это идея RELRO.

    83. Зачем RELRO¶

    Без защиты attacker при memory corruption может попытаться:

    переписать function pointer / relocation slot

    После:

    mprotect read-only

    атака усложняется.

    84. Full RELRO и eager binding логически связаны¶

    Если GOT entry планируется менять при первом lazy call:

    она должна оставаться writable

    Чтобы полностью защитить такие structures:

    resolve заранее
↓
сделать read-only

    Отсюда связь:

    eager binding
↔
full RELRO

    85. Symbol resolution¶

    Несколько objects могут экспортировать одинаковое имя.

    Dynamic linker должен решить:

    какой definition использовать

    В игру входят:

    symbol visibility
scope
weak/strong behavior
load order
interposition

    Глубоко rules здесь не разбираем.

    86. Symbol interposition¶

    Один loaded object может предоставить symbol, который будет выбран вместо другого.

    Это дает:

    instrumentation
compatibility tricks
LD_PRELOAD

    И одновременно усложняет optimization и security model.

    87. LD_PRELOAD¶

    Dynamic linker может загрузить library раньше обычных dependencies.

    Ее symbols участвуют в lookup.

    Применения:

    перехват malloc
трассировка
shim

    Но это механизм dynamic loader.

    88. Почему LD_PRELOAD не действует на обычный static binary¶

    Если executable:

    не запускает dynamic linker

    то environment variable:

    LD_PRELOAD

    просто некому обработать.

    Очень хорошая практическая граница static/dynamic linking.

    89. Shared library code pages могут быть общими¶

    Clean R-X pages:

    process A mapping ─┐
process B mapping ─┼→ одинаковые file-backed physical pages
process C mapping ─┘

    Это нормальное file-backed sharing.

    90. Но writable data не shared по той же модели¶

    Library globals:

    process-specific state

    Обычно требуют private/COW semantics.

    Relocation-modified pages тоже могут потерять часть физического sharing.

    91. Поэтому «dynamic всегда экономит RAM» слишком грубо¶

    Нужно учитывать:

    clean shared code
private data
relocation pages
page cache
number of processes
actual residency

    Статические binaries, запущенные из одного и того же файла, тоже могут делить clean file-backed text pages.

    169. NX/W^X/RELRO — разные protections¶

    175. Разрушаем плохие упрощения¶

    «OS загружает binary целиком в RAM»¶

    Нет.

    Создаются file-backed mappings, а pages fault'ятся по demand.

    «Sections — это то, что kernel грузит»¶

    Не совсем.

    Kernel loader в первую очередь работает с program segments.

    «.bss лежит в binary как нули»¶

    Нет.

    Memory size может быть больше file size.

    «execve создает новый process»¶

    Нет.

    Он заменяет program image текущего процесса.

    «Go binary всегда static»¶

    Нет.

    Нужно смотреть actual build.

    «Dynamic linker — часть kernel»¶

    Нет.

    Kernel запускает interpreter из PT_INTERP; дальнейшая link work идет в user space.

    «Dynamic linking означает поиск symbol по имени на каждый CALL»¶

    Нет.

    Bindings/relocations/GOT/PLT подготавливают addresses.

    «ASLR = PIE»¶

    Нет.

    ASLR — policy размещения.

    PIE — форма executable/codegen.

    «Shared library всегда экономит RAM»¶

    Слишком грубо.

    Нужны PSS/residency и конкретная модель sharing.

    «Entry point = main.main»¶

    Нет.

    Сначала runtime startup.

    182. Что важно запомнить¶

    1. Executable — структурированный файл, описывающий code/data и будущий process image.
    2. На Linux kernel loader в первую очередь использует Program Header Table, а не section table.
    3. Sections и segments решают разные задачи.
    4. PT_LOAD связывает file offset, virtual address, file size, memory size и permissions.
    5. p_memsz > p_filesz позволяет реализовать .bss без хранения всех нулей в file.
    6. Mapping executable segment не означает немедленную residency всех pages.
    7. Permissions R/W/X доходят от executable metadata до MMU.
    8. execve заменяет program image текущего процесса и не означает новый PID.
    9. FD_CLOEXEC определяет наследование file descriptor через exec boundary.
    10. Initial user stack содержит argv/env/auxv еще до runtime startup.
    11. auxv передает platform startup data.
    12. vDSO — mapping от kernel, а не часть executable.
    13. Demand paging позволяет читать code pages только при фактическом использовании.
    14. ASLR рандомизирует layout; PIE делает основной executable relocatable по base address.
    15. PT_INTERP указывает user-space dynamic linker.
    16. Dynamic linker загружает DT_NEEDED libraries и применяет runtime relocations.
    17. GOT/PLT помогают работать с dynamic addresses без постоянного patch executable text.
    18. Lazy binding переносит часть symbol-resolution cost на первый call.
    19. RELRO защищает relocation-related data после loader setup.
    20. Shared library code pages могут физически делиться, а writable/private data имеют другую модель.
    21. Pure-Go Linux binary часто может быть static, но Go binary не гарантированно static.
    22. cgo вводит platform ABI, external linking и shared-library dependencies.
    23. Mach-O/dyld решают на macOS ту же физическую задачу другими форматами.
    24. LC_SEGMENT_64 описывает loadable Mach-O segment; ASLR применяет slide.
    25. readelf, /proc/PID/maps, strace, LD_DEBUG, otool и vmmap отвечают на разные вопросы.
    26. Startup latency и steady-state latency нужно измерять отдельно.
    27. Entry point Go executable не равен main.main.
    28. 4.5 заканчивается в точке передачи управления Go runtime.
    29. Следующий слой — bootstrap самого Go runtime.
    30. Финальная модель: executable → loader → mappings → dynamic linker → entry point → runtime.

    Главный инженерный вывод:

    Linker в 4.4 создал executable, но executable еще не является работающим процессом. Ядро должно интерпретировать формат файла, построить виртуальное адресное пространство, назначить permissions, сформировать начальный stack и передать управление entry point. Если binary динамический, появляется еще один полноценный user-space этап: dynamic linker загружает libraries, разрешает symbols и применяет relocations.

    Поэтому startup backend-сервиса начинается раньше main.main, а cold-start latency может формироваться еще до инициализации Go runtime: на file-backed page faults, dynamic dependencies, relocations и loader work.
