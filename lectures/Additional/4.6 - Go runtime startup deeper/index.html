    4.6. Startup рантайма Go глубже: от rt0 до main.main¶

    Материал ориентирован на Go 1.27.x.

    Основная линия разбора — обычный executable, собранный Go toolchain; Linux/amd64 используется как главный конкретный пример, arm64 и другие платформы отмечаются там, где механизм отличается.

    Это продолжение 4.5. Запуск процесса глубже.

    В 4.5 мы остановились здесь:

    executable
↓
загрузчик ОС
↓
mappings
↓
entry point

    Теперь вопрос:

    Как из состояния «есть один поток ОС и несколько отображенных страниц executable» возникает полноценный Go runtime с G/M/P, allocator, GC, scheduler и пользовательским main.main?

    Зачем открывать этот слой¶

    В Runtime deep мы уже разобрали работающую машину:

    G
M
P
↓
run queues
↓
schedule
↓
findRunnable
↓
execute

    Но эта модель молча предполагает:

    G уже существуют
M уже существуют
P уже существуют
scheduler уже работает
allocator уже работает
GC уже инициализирован

    А кто создал все это?

    Вот здесь начинается bootstrap-проблема.

    0. Главная проблема bootstrap¶

    Обычный runtime-код хочет:

    выделять память
создавать goroutines
использовать scheduler
использовать locks
использовать maps
знать текущая G

    Но чтобы поднять эти механизмы, рантайму уже нужно выполнить код.

    Получается:

    чтобы запустить runtime,
нужен runtime

    Конечно, бесконечной рекурсии нет.

    Нужен минимальный набор сущностей, который существует до нормального рантайма.

    1. Что уже существует после 4.5¶

    загрузчик ОС закончил работу.

    Есть:

    virtual address space
↓
mapped executable code
mapped static data
initial thread
начальный стек ОС
argc / argv / env / auxv
CPU registers
entry point

    Для обычного Linux executable kernel передает управление точке входа.

    Но еще нет привычного Go-world.

    2. Чего еще нет¶

    На этой стадии нельзя мысленно рисовать:

    P0
local run queue
worker goroutines
GC workers
sysmon

    Их еще не создали.

    В начале у нас буквально:

    один поток ОС
+
статические bytes программы
+
stack от ОС

    3. Entry point на amd64¶

    Для обычного -buildmode=exe с internal linking current runtime имеет:

    _rt0_amd64

    Это entry point, в который приходит kernel.

    Начало очень маленькое:

    argc
argv
↓
runtime.rt0_go

    То есть:

    OS
↓
_rt0_amd64
↓
runtime.rt0_go

    4. Почему _rt0_amd64 почти ничего не делает¶

    У него нет задачи:

    поднять весь runtime

    Его задача — адаптировать platform entry convention к общей startup-функции:

    runtime.rt0_go

    На другой architecture будет другой маленький platform entry.

    5. Internal и external linking дают разные внешние входы¶

    При internal linking kernel может входить прямо в:

    _rt0_amd64

    При external linking platform C startup может вызвать symbol:

    main

    который затем тоже прыгает в:

    runtime.rt0_go

    То есть внешний путь может различаться.

    Общая Go-bootstrap линия сходится в rt0_go.

    6. Почему rt0_go написан на assembly¶

    В этот момент еще нельзя спокойно использовать обычный Go-код.

    Обычная Go function предполагает:

    валидный G
валидный M
корректный stack guard
ABI runtime state
возможность stack growth

    А мы как раз только собираемся это создать.

    Поэтому начало bootstrap — специальный assembly.

    7. Первый вопрос rt0_go: где вообще stack¶

    OS уже дала initial thread stack.

    Но Go runtime еще не знает его как:

    g.stack.lo
g.stack.hi

    Нужно превратить platform stack в runtime-aware system stack.

    8. Появляется g0¶

    Из Runtime deep мы знаем:

    g0
→ служебная G конкретного M
→ runtime/scheduler/system-stack work

    Но обычная модель:

    runtime создал G
→ выделил ей stack

    здесь не работает.

    Allocator еще не готов.

    9. g0 существует заранее¶

    Current runtime содержит статические globals:

    var (
    m0 m
    g0 g
)

    То есть linker уже поместил storage под них в data/BSS executable.

    После загрузчик ОС:

    memory для m0/g0 уже существует

    хотя runtime еще ничего не аллоцировал.

    10. Вот первый bootstrap-трюк¶

    обычные G/M
→ создаются runtime-механизмами

g0/m0
→ существуют как статические объекты executable

    То есть:

    Первый M и его g0 не создаются тем же механизмом, который потом создает остальные M/G.

    Иначе снова получили бы циклическую зависимость.

    11. Что такое m0¶

    m0 — runtime representation начальный поток ОС.

    ОС уже создала thread.

    Рантайму не нужно:

    pthread_create
clone
newosproc

    для первого M.

    Нужно сказать:

    этот уже существующий OS thread
→ будет m0

    12. Что такое g0 на старте¶

    g0 — служебная G m0.

    Ее stack:

    не выделен обычным stack allocator

    Вместо этого рантайм берет уже существующий:

    начальный поток ОС stack

    13. rt0_go задает stack bounds g0¶

    Концептуально:

    current SP
↓
оценить верх/низ initial stack
↓
g0.stack.lo
g0.stack.hi
↓
stackguard0
stackguard1

    Точные вычисления platform-specific.

    Но причинность важна:

    OS stack
↓
становится system stack g0

    14. Почему bounds сначала могут быть приблизительными¶

    Рантайм на самом раннем этапе знает не всю platform-specific информацию о размере stack.

    Поэтому bootstrap может:

    установить первоначальные bounds
↓
позже minit/platform code уточнит

    Это нормально.

    Нужна сначала достаточно корректная граница, чтобы безопасно продолжить startup.

    15. Почему g0 нужен прямо сейчас¶

    Следующие функции:

    runtime.args
runtime.osinit
runtime.schedinit

    уже являются Go/runtime-кодом.

    Для их вызова runtime должен иметь:

    текущая G

    И этой G становится g0.

    16. Но одной глобальной g0 недостаточно¶

    Дальше появятся несколько M:

    M0 → G0
M1 → G0_1
M2 → G0_2

    Runtime-функция должна быстро спросить:

    какая G сейчас выполняется на этом thread?

    Нельзя использовать одну глобальную переменную.

    17. getg()¶

    Во многих местах runtime встречается:

    getg()

    Ментальная модель:

    текущий OS thread
↓
быстро получить текущая G

    В нормальной работе это фундаментальная операция.

    Но startup должен сначала сделать ее возможной.

    18. Почему текущая G — thread-local state¶

    Пусть:

    M1 выполняет G17
M2 выполняет G42

    Если было бы:

    global currentG

    два M постоянно перезаписывали бы одно значение.

    Значит связь должна быть:

    OS thread
→ текущая G

    19. TLS и специальный g register¶

    Конкретный механизм зависит от architecture/platform.

    На amd64 current runtime сочетает:

    TLS slot
+
reserved register для g в ABIInternal

    На других architectures детали отличаются.

    Устойчивая модель:

    Каждый M должен иметь быстрый per-thread способ получить текущую G.

    20. Почему нельзя объяснять это только как «G лежит в TLS»¶

    Слишком грубо.

    Generated Go-код на некоторых architectures держит g в специальном register.

    TLS нужен в том числе:

    • при переходах между ABI;
    • cgo;
    • startup;
    • восстановлении runtime state.

    Поэтому точная формула:

    current-G mechanism
=
platform TLS + ABI/runtime conventions

    21. rt0_go настраивает TLS¶

    На amd64 early startup:

    setup TLS
↓
проверить, что TLS действительно работает
↓
записать g0

    Почему даже проверять?

    Потому что если TLS setup сломан:

    getg()
→ мусор

    а после этого любой runtime-код становится некорректным.

    22. Связь m0 ↔ g0¶

    После подготовки current-G state устанавливается логическая связь:

    m0.g0 = &g0
g0.m  = &m0

    Теперь:

    getg()
↓
g0
↓
g0.m
↓
m0

    Bootstrap получил минимальную runtime identity.

    23. Почему это центральный момент¶

    До:

    m0 ↔ g0

    есть просто:

    OS thread

    После:

    OS thread
↓
runtime M
↓
runtime G

    То есть рантайм впервые начинает понимать сам себя своими собственными сущностями.

    24. Но m0 еще не полноценный обычный M¶

    Важно не перепрыгнуть.

    Есть:

    m0/g0 identity

    Но еще не готовы:

    allm state
scheduler queues
P
allocator
GC
signal state

    m0 будет дополнительно инициализирован позже в schedinit.

    25. Optional cgo bootstrap¶

    Если используется cgo, early startup может вызвать:

    _cgo_init

    чтобы platform/C side помогла с:

    • TLS;
    • stack bounds;
    • platform thread state.

    После этого stack guards могут быть пересчитаны.

    26. Почему cgo path сложнее¶

    Теперь одновременно существуют два мира:

    Go runtime conventions
↔
C/platform thread runtime

    Startup должен согласовать их еще до нормальной работы scheduler.

    Но основную лекцию дальше ведем по pure-Go пути.

    27. CPU compatibility check¶

    На amd64 current startup может проверить required microarchitecture level:

    GOAMD64=v2/v3/v4

    через:

    CPUID
XGETBV
platform capability data

    Если CPU не поддерживает нужные features:

    программа завершается до обычного runtime startup

    28. Почему feature check находится так рано¶

    Compiler уже мог сгенерировать instructions, которые baseline CPU не поддерживает.

    Если продолжить:

    illegal instruction

    или некорректное выполнение.

    Поэтому:

    compiler assumption
↓
startup validates hardware

    до входа в основной runtime.

    29. Это мост к 4.3¶

    В 4.3:

    GOARCH / GOAMD64
↓
architecture lowering
↓
machine code

    В 4.6:

    machine starts
↓
runtime verifies required CPU level

    Toolchain assumptions встречаются с реальным железом.

    30. После минимального bootstrap можно вызывать runtime Go-функции¶

    Current amd64 startup дальше делает примерно:

    runtime.check
↓
runtime.args
↓
runtime.osinit
↓
runtime.schedinit

    И только потом:

    newproc(runtime.main)
↓
mstart

    Это центральная startup chain.

    31. runtime.args¶

    argc/argv пришли из загрузчик ОС из 4.5.

    runtime.args сохраняет их для дальнейшего runtime/OS initialization.

    Позже из этого мира появится:

    os.Args

    32. args — еще не package os¶

    В этот момент пользовательские packages еще не инициализированы.

    Runtime сам работает с raw startup arguments.

    То есть:

    kernel ABI
↓
runtime.args
↓
позже os package

    33. osinit¶

    Следующий шаг:

    runtime.osinit

    Его задача platform-specific:

    получить базовую информацию от OS,
нужную runtime startup

    34. Linux osinit¶

    Current Linux path инициализирует или получает данные вроде:

    число CPU на старте
huge-page related data
platform random/time support
часть vDSO/runtime OS state

    Нас интересует прежде всего:

    numCPUStartup

    35. Почему CPU count нужен до scheduler¶

    Скоро нужно создать:

    P

    Но сколько?

    Устойчивая цепочка:

    OS CPU environment
↓
osinit
↓
initial GOMAXPROCS
↓
procresize
↓
number of P

    36. Go 1.27 и container-aware GOMAXPROCS¶

    Current Go выбирает default GOMAXPROCS не только из простого NumCPU.

    Если GOMAXPROCS environment не задан, runtime может учитывать:

    logical CPU count
CPU affinity
Linux cgroup CPU throughput limit

    Это особенно важно в контейнерах.

    37. Но решение о P еще не принято¶

    osinit только собирает данные.

    Решение:

    сколько P реально создать

    будет в schedinit.

    И вот здесь начинается главный bootstrap-комбайн.

    Часть II. schedinit¶

    38. Название schedinit обманчиво¶

    Можно подумать:

    scheduler init
→ создать run queue
→ готово

    На практике current schedinit инициализирует значительную часть runtime foundation.

    Почему?

    Потому что scheduler зависит от:

    • allocator;
    • stacks;
    • метаданные рантайма;
    • GC state;
    • CPU feature tables;
    • locks;
    • M state.

    39. Bootstrap sequence прямо записана в runtime source¶

    Current source формулирует:

    call osinit
call schedinit
make & queue new G
call runtime.mstart

The new G calls runtime.main

    То есть это не наша учебная реконструкция.

    Это реальная архитектурная граница runtime.

    40. В начале schedinit инициализируются runtime locks¶

    Пока рантайм еще почти single-threaded:

    sched.lock
allglock
allpLock
panic locks
profiling locks
...

    получают lock rank / initial state.

    41. Почему lock infrastructure поднимают так рано¶

    Очень скоро runtime начнет создавать:

    P
goroutines
background threads

    После этого глобальные структуры станут concurrent.

    Лучше:

    locks готовы до concurrency

    а не:

    concurrency уже началась
→ теперь пытаемся создать locks

    42. World starts stopped¶

    Current schedinit явно переводит runtime в модель:

    world stopped

    Почему?

    Потому что на этом этапе:

    не должно быть обычных P, конкурентно исполняющих Go G

    Инициализация глобальных подсистем гораздо проще в stop-the-world мире.

    43. Здесь STW необычный¶

    Обычно STW:

    работающий мир
↓
остановить G
↓
что-то сделать
↓
запустить

    Bootstrap:

    мира еще не было
↓
он сразу считается stopped

    То есть первая STW-фаза началась раньше, чем возник working scheduler world.

    44. Early GODEBUG¶

    На Unix-like platforms runtime пытается прочитать:

    GODEBUG

    очень рано.

    Почему?

    Потому что некоторые debug/runtime options влияют на сам процесс инициализации:

    CPU features
GOMAXPROCS policy
runtime modes

    Их нельзя применять после того, как subsystem уже создана.

    45. moduledataverify¶

    До глубокого использования linker metadata runtime проверяет module data.

    Мост:

    4.4 linker
→ moduledata
→ 4.6 runtime verifies/initializes it

    Executable bytes стали runtime structures.

    46. Теперь начинается строгий порядок subsystem init¶

    Current schedinit последовательно выполняет:

    stackinit
randinit
mallocinit
cpuinit
maps.AlgInit
mcommoninit(m0)
modulesinit
typelinksinit
itabsinit
stkobjinit
...
gcinit
...
GOMAXPROCS calculation
procresize

    Этот порядок нельзя бездумно переставлять.

    47. Почему нельзя вызвать все init параллельно¶

    Runtime subsystem dependencies выглядят примерно:

    random
↓
hash/map seeds

allocator
↓
runtime allocations

moduledata
↓
types / itabs

allocator + metadata
↓
GC

GC + scheduler foundation
↓
P world

    Параллельный startup здесь только усложнил бы bootstrap.

    48. stackinit¶

    Обычные goroutines позже потребуют stack allocator.

    g0 уже имеет OS stack.

    Но normal G:

    newproc
↓
new stack

    должны использовать runtime stack machinery.

    stackinit подготавливает этот фундамент.

    49. Не повторяем stack allocator¶

    Мы уже знаем:

    goroutine stack
→ grows/copies

    Здесь новый факт:

    Stack subsystem становится готова в schedinit, до создания первой обычной runtime.main G.

    50. randinit¶

    Следующим current runtime поднимает internal randomness.

    Комментарий source специально требует:

    randinit
до
mallocinit
AlgInit
mcommoninit

    Почему randomness настолько фундаментальна?

    51. Randomness нужна самому runtime¶

    Примеры использования:

    hash seeds
per-M random state
runtime randomization

    То есть random subsystem — не пользовательский math/rand.

    Это внутренний primitive.

    52. mallocinit¶

    Теперь поднимается allocator.

    Из memory lecture мы знаем цепочку:

    mcache
mcentral
mheap
page allocator
arenas

    Здесь не перечитываем ее.

    Новый вопрос:

    Когда она появляется?

    Ответ:

    schedinit
↓
mallocinit

    53. До mallocinit нельзя свободно делать обычные runtime allocations¶

    Поэтому bootstrap до этого момента опирается на:

    • static globals;
    • initial stack;
    • заранее подготовленные data structures;
    • специальные no-allocation paths.

    Именно поэтому startup code выглядит необычно.

    54. После mallocinit bootstrap резко получает больше свободы¶

    Теперь можно поднимать структуры, которым требуется runtime allocation.

    Но еще:

    обычный scheduler world

    не запущен.

    Allocator и scheduler — разные границы готовности.

    55. cpuinit¶

    Теперь internal CPU package узнает доступные feature flags.

    Например на amd64 runtime заполняет flags вроде:

    HasAVX
HasFMA
HasPOPCNT
HasSSE41

    На arm64 — свои capabilities.

    56. Зачем feature flags после раннего CPU hard check¶

    Ранний rt0_go проверял:

    минимальный required GOAMD64 level

    cpuinit решает более общий вопрос:

    какие optional fast paths доступны?

    Это разные задачи.

    57. Compiler-generated code может читать runtime CPU flags¶

    В 4.3 мы говорили:

    intrinsic / architecture optimization

    Некоторые generated paths guarded runtime feature flags.

    cpuinit делает эти flags корректными.

    58. maps.AlgInit¶

    Current schedinit после cpuinit вызывает:

    maps.AlgInit()

    И source прямо предупреждает:

    maps, hash, rand

    Часть IV. runtime.main¶

    106. Но runtime.main все еще не пользовательский main¶

    Мы впервые выполняем обычную G.

    Но она принадлежит рантайму:

    runtime.main

    Ее задача:

    дозавершить runtime startup
↓
запустить фоновые runtime mechanisms
↓
выполнить init tasks
↓
только потом вызвать main.main

    107. runtime.main должна выполняться на m0¶

    Current runtime проверяет:

    getg().m == &m0

    Если нет:

    throw

    Почему это важно?

    Потому что startup initialization привязана к начальный поток ОС.

    108. mainStarted¶

    В начале current runtime.main устанавливается:

    mainStarted = true

    Смысл:

    рантайм дошел до normal main-M world

    После этого newproc может активнее будить/создавать M по обычным scheduler rules.

    109. До mainStarted thread creation intentionally ограничено¶

    Bootstrap хочет избежать ситуации:

    еще не закончена базовая инициализация
↓
другие M уже активно исполняют Go work

    Поэтому ранние фазы сознательно минимизируют concurrency.

    110. sysmon появляется здесь¶

    Если platform поддерживает sysmon:

    runtime.main
↓
systemstack
↓
newm(sysmon, nil, -1)

    То есть системный монитор запускается после того, как scheduler уже способен создавать M.

    111. Почему sysmon не запускается в schedinit¶

    В schedinit world еще stopped.

    P только создаются.

    Запуск отдельного M в середине bootstrap:

    сломал бы предположение о контролируемой инициализации

    Поэтому порядок:

    поднять runtime foundation
↓
запустить scheduler
↓
потом background monitor

    112. Не перечитываем sysmon¶

    Из Runtime deep уже знаем:

    preemption assistance
retake P
netpoll/timers related monitoring

    Здесь нужен только lifecycle:

    когда он появился?

    Ответ:

    runtime.main

    113. Startup thread lock¶

    Current runtime.main делает:

    lockOSThread()

    на период initialization.

    Это очень интересный механизм.

    114. Почему main goroutine временно закрепляется за начальный поток ОС¶

    Некоторые platform APIs требуют:

    вызывать init на main/стартовый поток ОС

    Например UI/graphics frameworks и другие thread-affine API.

    Go должен позволить package init() корректно взаимодействовать с такими платформами.

    115. Документированная гарантия¶

    runtime.LockOSThread документирует:

    все init functions выполняются на стартовый поток ОС

    Если init сам вызывает:

    runtime.LockOSThread()

    то пользовательский main может сохранить эту привязку к тому же thread.

    runtime.main:

    214. Разрушаем плохие упрощения¶

    «OS вызывает main.main»¶

    Нет.

    загрузчик ОС
↓
rt0
↓
bootstrap рантайма
↓
runtime.main
↓
package init
↓
main.main

    «Scheduler создает первый M»¶

    Нет.

    Первый OS thread уже существует.

    m0 — runtime representation этого потока.

    «Первый g0 создается как обычная goroutine»¶

    Нет.

    g0 — статический bootstrap object и использует initial system stack.

    «Allocator нужен, чтобы создать m0/g0»¶

    Наоборот.

    m0/g0 нужны, чтобы дойти до mallocinit.

    «P существует сразу после entry point»¶

    Нет.

    P появляются в schedinit → procresize.

    «После schedinit уже выполняется main»¶

    Нет.

    Сначала нужно:

    newproc(runtime.main)
↓
mstart
↓
schedule

    «GC включается одним шагом»¶

    Нет.

    gcinit
↓
позже
gcenable

    «Package init идет до scheduler»¶

    Нет.

    Scheduler уже работает, когда runtime.main выполняет package init.

    «До main нет других goroutines»¶

    init может создать их.

    «init() — единственное место скрытой startup work»¶

    Нет.

    Global variable initializers тоже входят в инициализация пакетов.

    «Process существует — значит приложение уже стартовало»¶

    Нет.

    PID может существовать, пока process еще находится в loader/runtime/package init.

    215. Что важно запомнить¶

    1. Go bootstrap рантайма начинается не с обычной goroutine, а с начальный поток ОС.
    2. _rt0_* адаптирует platform entry convention к runtime.rt0_go.
    3. m0 и g0 — статические bootstrap-объекты, существующие до allocator.
    4. Initial OS stack становится system stack g0.
    5. Early startup должен настроить механизм текущая G до вызова нормального runtime Go-кода.
    6. TLS/special-register details platform-specific; устойчивая модель — per-thread текущая G.
    7. m0.g0 и g0.m связывают platform thread с runtime сущностями.
    8. runtime.args → osinit → schedinit выполняются до создания первой обычная G.
    9. schedinit поднимает не только scheduler, но stack, randomness, allocator, CPU flags, map algorithms, M state, module/type/interface metadata и GC state.
    10. maps.AlgInit показывает, что даже фундаментальные Go constructs имеют startup prerequisites.
    11. gcinit подготавливает GC, а gcenable позже разрешает фоновый GC machinery.
    12. Initial GOMAXPROCS выбирается до procresize; текущая Go может учитывать affinity/cgroup CPU quota.
    13. procresize создает/инициализирует P и переводит runtime к состоянию, где P способны исполнять Go code.
    14. Первая обычная G запускает runtime.main, а не main.main.
    15. mstart → mstart0 → mstart1 → schedule переводит initial M в обычный scheduler lifecycle.
    16. С входом в schedule механика Runtime deep начинает работать в обычном режиме.
    17. runtime.main запускает sysmon и держит main G на стартовый поток ОС во время initialization.
    18. Init tasks вычислены toolchain/linker заранее и выполняются runtime в dependency order.
    19. Package initialization включает и variable initializers, и init() functions.
    20. init() выполняется main goroutine, но может создавать дополнительные goroutines.
    21. Тяжелая работа в init напрямую увеличивает cold-start latency до main.main.
    22. GODEBUG=inittrace=1 — основной инструмент для измерения инициализация пакетов.
    23. mainInitDone сигнализирует завершение initialization для runtime/cgo coordination.
    24. Только после init runtime освобождает startup-thread lock и вызывает main.main.
    25. main.main — не начало процесса, а конец длинного bootstrap pipeline.
    26. Для диагностики нужно разделять loader (4.5), bootstrap рантайма (4.6) и application initialization.
    27. Startup latency важна для autoscaling, Kubernetes, serverless, CLI и short-lived jobs.
    28. Runtime private symbols и exact call order — детали Go 1.27.x, а не контракт языка.

    Главный инженерный вывод:

    Go runtime не появляется мгновенно в точке входа процесса. Он bootstrap'ит сам себя слоями. Сначала использует уже существующие ресурсы ОС — initial thread и stack — и связывает их со статическими m0/g0. Затем в schedinit поднимает память, metadata, GC state и P. После этого создает первую обычную G с runtime.main, запускает scheduler, включает фоновые механизмы, выполняет инициализация пакетов и только затем передает управление пользовательскому main.main.

    Поэтому main.main — не начало жизни Go-процесса. Это точка, к которой процесс приходит уже с работающим scheduler, allocator, GC, метаданные рантайма и завершенной инициализацией всех packages.
