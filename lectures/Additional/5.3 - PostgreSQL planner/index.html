    05.3. PostgreSQL Planner Internals¶

    Углубленная теоретическая лекция для магистратуры. Технический ориентир — PostgreSQL 18 (REL_18_STABLE). Основная тема — планирование запросов к одной таблице: оценка количества строк, расчет условной стоимости, сохранение альтернатив и влияние ORDER BY / LIMIT. Отдельная лекция №6 посвящена JOIN и здесь не рассматривается.

    Формат: механизм → математическая модель → числовой расчет → ограничения → инженерный вывод. SQL используется как иллюстрация. Лабораторных заданий нет.

    Важное различие: публичные гарантии SQL и EXPLAIN, детали планировщика PostgreSQL 18, статистические допущения и специально упрощенные учебные формулы отмечены отдельно там, где это влияет на точность вывода.

    Блок 1. Cardinality Estimation — от статистики к rows¶

    Планировщик еще не выполнил запрос, однако уже оценивает число его выходных строк. Сначала разберем, на каких данных и математических предположениях стоит этот прогноз.

    1. Оценка количества строк: cardinality и selectivity¶

    1.1. Сначала запрос, который выглядит слишком простым¶

    Представим таблицу orders с миллионом заказов:

    SELECT id, total_amount
FROM orders
WHERE customer_id = 42;

    Планировщик может рассматривать последовательное чтение таблицы, поиск по индексу или получение строк через bitmap. Мы пока не выясняем, как он считает стоимость этих способов — это следующий блок. Сначала надо ответить на вопрос, без которого стоимость почти невозможно оценить: сколько строк пройдет через условие customer_id = 42?

    Если их пять, индекс выглядит привлекательным. Если их 900 000, картина совершенно другая. Но запускать запрос для подсчета строк заранее бессмысленно: ради выбора плана мы уже выполним значительную часть работы.

    Поэтому PostgreSQL опирается на заранее собранную статистику и оценивает количество строк.

    Два понятия:

    • Cardinality — количество строк (мощность набора данных). В этой лекции чаще всего это оценка числа строк в таблице или на выходе операции.
    • Selectivity — доля строк, удовлетворяющих условию, от 0 до 1.

    Для одной таблицы и одного фильтра учебная формула выглядит так:

    [ \hat N_{out}=\hat N_{base}\cdot\hat s ]

    Здесь ^ обозначает оценку:

    • (\hat N_{base}) — оцененное количество строк исходной таблицы;
    • (\hat s) — оцененная селективность предиката;
    • (\hat N_{out}) — оцененное количество строк на выходе фильтра.

    Если планировщик считает, что таблица содержит 1 000 000 строк, а условие пропускает 0,2%:

    [ \hat N_{out}=1\,000\,000\cdot0.002=2\,000. ]

    Никакой магии пока нет. Вся сложность спрятана в двух оценках: откуда миллион и откуда 0,002?

    Граница модели. Это формула для обычной фильтрации одной таблицы. Уточнения возникают для пустых таблиц, выражений, ограничений, партиций, уникальности, специфических предикатов и разных типов узлов. rows в EXPLAIN — целочисленная оценка на выходе конкретного узла; исполнитель может вернуть другое число.

    1.2. pg_class: что известно о размере таблицы¶

    Сначала PostgreSQL использует сведения о размере отношения (relation — таблицы, индекса и других объектов хранения), в том числе поля системного каталога pg_class:

    SELECT relname, relkind, reltuples, relpages
FROM pg_class
WHERE oid = 'orders'::regclass;
    • reltuples — оценка количества строк;
    • relpages — оценка количества страниц отношения;
    • relkind — вид отношения (r для обычной таблицы, i для обычного индекса и т. д.).

    Страница heap обычно равна 8 КиБ в стандартной сборке PostgreSQL, хотя размер страницы может задаваться при сборке сервера.

    Возможное состояние каталога:

    relname | reltuples | relpages
--------+-----------+---------
orders  | 1000000   | 10000

    Обратите внимание: reltuples не изменяется при каждом INSERT, а relpages не пересчитывается после каждой записи. Иначе система обслуживала бы счетчики статистики на горячем пути изменений данных, создавая дополнительную конкуренцию и затраты.

    Сведения обновляются операциями обслуживания, включая VACUUM, ANALYZE и отдельные DDL-операции. Между обновлениями они могут устаревать.

    1.3. Как оценка строк масштабируется по размеру файла¶

    Теперь предположим, что после последнего анализа таблица выросла с 10 000 до 15 000 страниц. Число страниц PostgreSQL способен получить сравнительно дешево, без чтения каждой строки. Поэтому он может скорректировать старую оценку плотности:

    [ \hat d=\frac{1\,000\,000}{10\,000}=100\quad\text{строк/страницу} ]

    [ \hat N_{current}\approx \hat d\cdot15\,000=1\,500\,000. ]

    Это упрощение логики масштабирования, которое документировано для планировщика. Детали учета размера зависят от вида отношения и состояния статистики.

    Но здесь модель сразу ломается.

    Допустим, первые миллион строк были короткими, а после обновления приложение начало хранить в каждой строке существенно более длинный JSON. Число страниц выросло, количество логических строк могло остаться примерно прежним. Использование старой плотности переоценит число строк.

    Или массово удалили данные. Физические страницы heap не обязаны сразу исчезнуть, а количество актуальных строк изменилось. Физический размер и логическая мощность связаны, но между ними нет постоянного коэффициента.

    Инженерный вывод: reltuples и relpages — не точные счетчики. Масштабирование помогает пережить умеренные изменения, но плохо объясняет изменение плотности хранения, массовые удаления и сильные структурные изменения данных.

    1.4. rows — результат оценки, а не обещание¶

    Рассмотрим гипотетический план:

    Seq Scan on orders
  (cost=0.00..25000.00 rows=2000 width=16)
  Filter: (customer_id = 42)

    rows=2000 описывает ожидаемый выход узла, а не число строк, которые Seq Scan прочитает физически. Полное последовательное сканирование может просмотреть всю таблицу ради 2 000 подходящих строк.

    А если выполнить:

    EXPLAIN (ANALYZE, TIMING OFF)
SELECT id, total_amount
FROM orders
WHERE customer_id = 42;

    то рядом появятся фактические показатели, например:

    (actual rows=1800 loops=1)

    Сравнение rows=2000 и actual rows=1800 говорит, что оценка близка к реальности. Но если фактически оказалось 180000, мы обнаружили ошибку примерно в 90 раз.

    В дальнейшем нам понадобится ответить, почему возникла ошибка, а не просто зафиксировать ее величину.

    Что важно запомнить после раздела 1¶

    1. Планировщик должен оценить объем результата до выполнения запроса.
    2. Для простой фильтрации ключевая модель — (\hat N_{out}=\hat N_{base}\hat s).
    3. pg_class дает приблизительный размер таблицы, а не актуальный COUNT(*).
    4. Физический размер помогает масштабировать старые оценки, но изменение плотности хранения нарушает простую модель.
    5. Крупное расхождение rows и actual rows — повод искать источник ошибки в оценках исходного размера или селективности.

    2. Как устроен ANALYZE: получить модель, не прочитав все строки¶

    2.1. Зачем вообще нужен отдельный процесс сбора статистики?¶

    Представим, что для каждого запроса планировщик обязан был бы выполнить:

    SELECT COUNT(*) FROM orders WHERE customer_id = 42;

    А затем построить план основного SQL. Это уничтожило бы смысл оптимизации. Поэтому тяжелую часть работы выносят из критического пути выполнения запросов: статистику периодически собирают, затем многократно используют при планировании.

    Команда:

    ANALYZE orders;

    собирает статистику содержимого таблицы. VACUUM (ANALYZE) тоже может обновлять ее. В обычной конфигурации PostgreSQL автоматически инициирует анализ через autovacuum/auto-analyze при достаточном числе изменений.

    Здесь три разных временных масштаба:

    1. INSERT/UPDATE/DELETE меняют реальные данные.
    2. ANALYZE периодически формирует новый статистический снимок распределения.
    3. Планировщик очередного запроса использует имеющиеся оценки.

    Между пунктами 1 и 2 всегда возможно расхождение.

    2.2. Почему ANALYZE обычно использует выборку¶

    Пусть в таблице миллиард строк. Полное вычисление всех распределений после каждой серии изменений было бы слишком дорогим.

    Поэтому ANALYZE для большой обычной таблицы формирует статистическую выборку (sample) — набор строк, по которому пытается восстановить свойства всей таблицы.

    Внутри исходного кода PostgreSQL используется отбор страниц и строк с элементами резервуарной выборки (reservoir sampling). Смысл такого подхода: получить достаточно представительную совокупность значений, не сохраняя и не пересчитывая все строки.

    Схематично:

    Физические страницы таблицы
      ↓ отбор страниц
Выбранные страницы
      ↓ получение выборки строк
Образец значений столбцов
      ↓ статистические вычисления
null_frac, n_distinct, MCV, histogram, correlation ...
      ↓
pg_statistic / pg_statistic_ext_data

    Это упрощенная схема. Конкретный алгоритм учитывает видимые и мертвые версии строк, оценки плотности и особенности отношений; он не сводится к равновероятному SQL ORDER BY random() LIMIT ....

    2.3. Что регулирует default_statistics_target¶

    Для обычных столбцов базовый параметр:

    SHOW default_statistics_target;

    Стандартное значение PostgreSQL 18 — 100.

    Его смысл — целевой уровень детализации собираемой статистики. В частности, он ограничивает число часто встречающихся значений и разрешение гистограммы, а также влияет на размер выборки.

    Можно задавать цель для отдельного столбца:

    ALTER TABLE orders
ALTER COLUMN customer_id
SET STATISTICS 1000;

    На уровне реализации для обычной статистики часто используется ориентир порядка 300 × target выбираемых строк: при target=100 получается около 30 000 строк, при target=1000 — около 300 000. Это характеристика текущего алгоритма сбора статистики, а не обязательная гарантия API: итоговая выборка может быть меньше, а отдельные типы статистики и обработчики устроены по-своему.

    Зачем увеличивать цель? Чтобы точнее оценивать сложное распределение с большим количеством различных значений, пиками частоты и узкими диапазонами.

    Но цена очевидна: больше работы ANALYZE, больше памяти/места для статистики и потенциально больше работы планировщика с расширенными данными.

    Неправильное упрощение: «Поставим SET STATISTICS 10000, и оценки станут точными». Выборка даже большого размера не устраняет логические ошибки модели и не гарантирует обнаружение очень редких значений.

    2.4. Математика погрешности выборки¶

    Возьмем упрощенную вероятностную модель: независимая равновероятная выборка (n) строк, условию удовлетворяет доля (p) таблицы.

    Оценка доли (\hat p) имеет стандартную ошибку порядка:

    [ SE(\hat p)\approx\sqrt{\frac{p(1-p)}{n}}. ]

    Для частого значения (p=0.1), выборка (n=30\,000):

    [ SE\approx\sqrt{\frac{0.1\cdot0.9}{30000}}\approx0.00173. ]

    Это около 0,17 процентного пункта стандартной ошибки. Приблизительная ошибка в несколько десятых процентного пункта для популярного значения часто приемлема.

    Теперь редкое значение (p=10^{-5}): один случай на 100 000 строк.

    Среднее количество его попаданий в выборку:

    [ E[X]=np=30\,000\cdot10^{-5}=0.3. ]

    При той же простой модели вероятность вообще не увидеть значение:

    [ P(X=0)=(1-p)^n\approx e^{-np}=e^{-0.3}\approx0.741. ]

    То есть примерно 74% вероятности, что редкое значение отсутствует в конкретной выборке. Само значение при этом существует в таблице.

    Необходимо оговорить: эти формулы описывают идеализированную случайную выборку. Реальное страничное семплирование и неоднородное размещение строк дают дополнительные эффекты. Но главную причину ошибок они показывают правильно.

    Инженерный вывод: статистика очень хорошо описывает крупные массивы популярных значений и может недостаточно точно отражать редкие события. Для сильно асимметричных данных один и тот же customer_id нельзя оценивать так же уверенно, как массовый статус PAID.

    2.5. pg_statistic и pg_stats: где лежат результаты¶

    Фактические данные для одно-колоночной статистики хранятся в системном каталоге pg_statistic.

    Он содержит базовые поля и несколько типизированных слотов статистики. В зависимости от типа данных и доступных операторов слот может хранить MCV, гистограмму, корреляцию или специализированную информацию.

    Для объяснения и диагностики удобнее представление pg_stats:

    SELECT
    attname, null_frac, avg_width, n_distinct,
    most_common_vals, most_common_freqs,
    histogram_bounds, correlation
FROM pg_stats
WHERE schemaname = 'public'
  AND tablename = 'orders';

    pg_stats показывает статистику в читаемом виде и ограничивает видимость данными таблиц, которые пользователь имеет право читать. Непосредственный доступ к pg_statistic ограничен строже: статистика способна раскрывать значения из пользовательских таблиц.

    Новая модель появляется после ANALYZE. Создание таблицы или нового статистического объекта само по себе не означает, что уже существуют актуальные сведения о его значениях.

    2.6. Когда срабатывает auto-analyze¶

    Автоматический анализ не запускается после каждого измененного заказа. В PostgreSQL для него используется пороговая модель:

    [ T_{analyze}=T_{base}+\alpha N, ]

    где:

    • (T_{base}) — autovacuum_analyze_threshold (стандартно 50);
    • (\alpha) — autovacuum_analyze_scale_factor (стандартно 0.1);
    • (N) — оценка числа строк таблицы (reltuples).

    Для миллиона строк:

    [ T_{analyze}=50+0.1\cdot1\,000\,000=100\,050. ]

    То есть при стандартной настройке может потребоваться порядка 100 тысяч изменений, учитываемых механизмом автосбора статистики, прежде чем таблица станет кандидатом на новый анализ.

    Это не означает немедленного запуска в момент достижения порога: существуют периодическая проверка, очередность работ и ограничения фоновых процессов.

    А теперь проблемный случай. Приложение загрузило 40 000 новых заказов, причем все они относятся к одному ранее редкому клиенту. Общий процент изменений невелик, но распределение именно customer_id изменилось резко.

    Автоматический механизм знает приблизительное число изменений; он не анализирует семантику этих изменений заранее. Поэтому актуальность статистики «в целом по таблице» и актуальность распределения конкретной колонки — разные вещи.

    Особые случаи:

    • Временные таблицы не анализируются фоновым autovacuum; для них статистика собирается в сессии.
    • Партиции могут анализироваться отдельно, но родительская партиционированная таблица не получает автоматический ANALYZE просто вследствие изменения дочерних партиций. Это важно для общей статистики; устройство партиционирования оставляем за рамками.

    Что важно запомнить после раздела 2¶

    1. ANALYZE вычисляет приближенную статистику заранее, чтобы планировщик не сканировал таблицу перед каждым запросом.
    2. Для больших таблиц используется выборка; случайная погрешность сохраняется даже сразу после анализа.
    3. default_statistics_target регулирует детализацию, а вместе с ней стоимость сбора и хранения статистики.
    4. Частое значение легко обнаружить в образце; очень редкое может в него вообще не попасть.
    5. Auto-analyze учитывает объем изменений и потому может запаздывать относительно изменения распределения критически важной колонки.

    3. Статистика распределения значений: что означает каждый показатель¶

    3.1. Почему среднее количество строк на значение мало что объясняет¶

    Пусть в таблице миллион заказов и три возможных статуса:

    Статус Фактическая доля Строк
    PAID 80% 800 000
    NEW 15% 150 000
    CANCELLED 5% 50 000

    Если знать только n_distinct=3, возникает соблазн оценивать каждое равенство как (1/3). Для PAID это ошибка более чем вдвое, а для CANCELLED — более чем в шесть раз.

    Нам нужно описание формы распределения. PostgreSQL использует несколько взаимодополняющих статистик.

    3.2. null_frac: часть данных, которая не проходит обычные сравнения¶

    Если:

    null_frac = 0.08

    то около 8% строк имеют NULL в данном столбце.

    Для условия:

    WHERE amount = 500

    строки с amount IS NULL не удовлетворяют условию: обычное сравнение с NULL дает SQL UNKNOWN, а WHERE отбирает только TRUE.

    Поэтому общая доля, доступная для сравнения ненулевых значений, примерно:

    [ P(amount\ne NULL)=1-null_frac=0.92. ]

    Это потребуется в формулах для MCV и остаточного распределения.

    При этом IS NULL — отдельное условие, для которого null_frac является непосредственным полезным источником оценки.

    3.3. n_distinct: сколько разных значений существует¶

    n_distinct — оценка числа различных ненулевых значений столбца.

    Семантика поля имеет два режима:

    • n_distinct = 200 — оценено около 200 различных значений в целом;
    • n_distinct = -0.25 — число различных значений растет пропорционально числу строк, примерно 25% от количества строк;
    • n_distinct = -1 — характерная оценка уникального столбца: примерно столько же различных значений, сколько строк.

    Для таблицы на миллион строк:

    [ n_distinct=-0.25\Rightarrow\hat D\approx250\,000. ]

    Зачем нужны отрицательные значения? Колонка со статусом заказа обычно имеет относительно фиксированное множество состояний, даже если число заказов выросло в десять раз. А в колонке external_request_id практически каждый новый заказ может приносить новое значение. Одно и то же фиксированное число уникальных значений плохо отражает такой рост.

    Важно: значение -1 — статистическая модель зависимости от размера, а не SQL-ограничение UNIQUE. Гарантии ограничения и оценки статистики — разные источники информации.

    3.4. most_common_vals и most_common_freqs: самые популярные значения¶

    most_common_vals (MCV) — список наиболее частых значений столбца, а most_common_freqs — соответствующие оценки частот от общего количества строк таблицы, а не только от числа ненулевых значений.

    Например:

    most_common_vals  = {PAID,NEW,CANCELLED}
most_common_freqs = {0.80,0.15,0.05}

    Если конкретное значение попало в MCV, PostgreSQL может взять оценку его частоты прямо из списка.

    Но здесь важно не допустить нового упрощения: MCV содержит частоту, полученную из выборки, а не абсолютно точную частоту во всей таблице. «Точное совпадение с записью MCV» означает, что оценщик использует ее частоту непосредственно, без предположения равномерности по остальным значениям.

    Если список ограничен, в него попадают только наиболее информативные значения. Остальные моделируются иначе.

    3.5. histogram_bounds: не равные интервалы по оси X¶

    Гистограмма PostgreSQL для подходящих упорядочиваемых типов хранит границы приблизительно равных по наполнению интервалов (equi-depth histogram).

    Пусть без MCV осталось 100 000 значений, и мы построили пять интервалов:

    0 ─── 100 ─── 200 ─── 400 ─── 1000 ─── 5000
  20%     20%     20%      20%       20%

    Ширина интервалов в числовых значениях сильно различается. Но каждый содержит примерно одинаковую долю населения той части распределения, для которой построена гистограмма.

    Это не гистограмма фиксированной ширины 0–1000, 1000–2000 и т. д. PostgreSQL хранит границы, отражающие фактические квантили выборки.

    Еще одна важная деталь: значения из MCV исключаются из гистограммы. Иначе популярные значения были бы учтены дважды.

    Гистограмма дает высокую плотность информации для диапазонных предикатов вроде <, >= и BETWEEN, но с конечным разрешением и предположениями о распределении внутри каждого интервала.

    3.6. avg_width: почему статистика размера влияет на будущий план¶

    Поле avg_width оценивает средний размер значения столбца в байтах.

    Предположим, два запроса фильтруют одинаковые 100 000 строк:

    SELECT id FROM orders WHERE status = 'PAID';

    и

    SELECT id, payload FROM orders WHERE status = 'PAID';

    У второго запроса выходная строка шире. Для последующих операций это может означать больший объем памяти, копирования и передачи данных. В плане это отражается через width и стоимость вышестоящих операций.

    Однако avg_width не следует отождествлять с размером строки на диске. На физическое представление влияют заголовки, выравнивание, NULL, переменные поля, TOAST и другие механизмы. Отдельную модель физического хранения разбирать здесь не требуется.

    3.7. correlation: связь порядка значений с физическим размещением¶

    correlation принимает значения от -1 до +1 и описывает статистическую связь порядка значений в столбце с физическим порядком строк в heap.

    • Около +1: значения растут вместе с физическим порядком.
    • Около -1: значения убывают вместе с физическим порядком.
    • Около 0: сильного упорядоченного соответствия нет.

    Например, в таблице, заполняемой хронологически, created_at часто обладает высокой корреляцией с физическим порядком строк. После многочисленных вставок со старыми датами или перестроений расположение может стать менее упорядоченным.

    Почему это важно? Если индексный диапазон ведет к близко расположенным страницам heap, чтение этих строк часто дешевле, чем обращения к совершенно разрозненным страницам.

    Не путать два вида связи:

    • correlation в pg_stats — одна колонка ↔ физический порядок heap;
    • зависимости из CREATE STATISTICS — значения нескольких колонок ↔ друг другу.

    Их используют для разных оценок. Внутреннюю формулу учета correlation в cost_index разберем во втором блоке лекции 05.1.

    3.8. Почему статистика хранится несколькими структурами¶

    Можно спросить: зачем столько полей — нельзя ли сохранить один огромный словарь «значение → частота»?

    Для status это действительно удобно. Но для request_id, timestamp или непрерывного amount число различных значений может быть огромным.

    Полный словарь сделал бы сбор и хранение статистики дорогостоящими. И планирование перестало бы быть дешевой операцией.

    Поэтому PostgreSQL сочетает:

    1. массу NULL отдельно;
    2. популярные значения как MCV;
    3. остальные значения как более грубое распределение, в том числе гистограмму и n_distinct;
    4. физическую упорядоченность через correlation.

    Это компромисс точность ↔ размер статистики ↔ стоимость ANALYZE ↔ скорость планирования.

    Что важно запомнить после раздела 3¶

    1. n_distinct описывает число разных значений, но ничего не обещает об их равномерности.
    2. MCV хранит популярные значения и оценки их частот.
    3. Гистограмма делит оставшуюся совокупность значений на примерно равные по количеству интервалы.
    4. null_frac нужно учитывать, чтобы не приписывать значениям массу строк с NULL.
    5. correlation описывает физическую локальность в таблице и не равен зависимости двух колонок.

    4. Математика селективности: как получаются числа rows¶

    Теперь у нас есть статистическая модель. Пора пройти по формулам.

    4.1. Оценка =: значение найдено в MCV¶

    Возьмем модель таблицы на миллион строк:

    N = 1 000 000
status = 'PAID' встречается с частотой 0.60

    Если PAID обнаружен в MCV и соответствующая частота равна 0.60:

    [ \hat s(status=\text{'PAID'})=0.60, ]

    [ \hat N_{out}=1\,000\,000\cdot0.60=600\,000. ]

    Обратите внимание на слово «оценка». Число может немного отличаться от реального из-за семплирования.

    4.2. Оценка =: значения нет в MCV¶

    Пусть теперь статистика по status устроена иначе:

    N = 1 000 000
null_frac = 0.05
n_distinct = 12
MCV = {PAID, NEW}
MCV frequencies = {0.60, 0.25}

    Значит:

    • NULL занимают 5%;
    • два частых значения — 60% и 25%;
    • остальная ненулевая масса — 10%;
    • из 12 различных значений два уже присутствуют в MCV;
    • остаток содержит примерно 10 различных значений.

    Для неизвестного в MCV значения CANCELLED грубая оценка при допущении равномерности остатка:

    [ \hat s =\frac{1-f_{NULL}-\sum f_{MCV}}{D-K}, ]

    где (D) — n_distinct, (K) — число элементов MCV.

    [ \hat s=\frac{1-0.05-(0.60+0.25)}{12-2}=\frac{0.10}{10}=0.01. ]

    [ \hat N_{out}=1\,000\,000\cdot0.01=10\,000. ]

    А теперь вопрос: что если CANCELLED реально встречается только в 20 строках, а остальные 99 980 строк остатка приходятся на другие значения?

    Планировщик, не располагая этой информацией, оценит CANCELLED как примерно 10 000 строк. Ошибка — 500 раз.

    В реальном eqsel есть дополнительные проверки, ограничения оценки и специальные случаи, поэтому приведенная формула — ключевая статистическая модель, а не полная построчная реализация функции. Она соответствует принципу, описанному в официальном разборе оценки строк PostgreSQL.

    4.3. Почему «значения нет в MCV» не означает «значения нет в таблице»¶

    MCV — короткий список частых значений, а не каталог всех возможных значений.

    Отсутствие клиента 42 в MCV говорит только о том, что для него нет отдельной сохраненной частоты. Планировщик распределяет остаточную массу по неизвестным значениям.

    Не менее важная ситуация: планировщик может выдать положительную оценку для несуществующего значения. Он не обязан знать точное множество всех ключей таблицы, если это нельзя установить из иных доступных ограничений и статистики.

    Это объясняет типичную картину:

    EXPLAIN: rows=500
EXPLAIN ANALYZE: actual rows=0

    Отсутствие данных — обычная ситуация, а не доказательство «сломавшегося» планировщика.

    4.4. Оценка < и > через гистограмму¶

    Предположим, в столбце нет отдельной существенной MCV-массы, NULL нет, а гистограмма имеет шесть границ и пять равновероятностных интервалов:

    0 | 100 | 200 | 400 | 1000 | 5000

    Каждый интервал отвечает приблизительно за 20% значений.

    Нужно оценить:

    WHERE amount < 250

    Весь первый интервал 0–100 подходит. Весь второй 100–200 тоже. Для третьего интервала 200–400 граница 250 находится на четверти числового расстояния:

    [ q=\frac{250-200}{400-200}=\frac{50}{200}=0.25. ]

    Если для оценки внутри интервала принять приблизительную линейную интерполяцию:

    [ \hat s\approx\frac{2+0.25}{5}=0.45. ]

    Для миллиона строк получим 450 000.

    Но что будет, если почти все значения третьего интервала сосредоточены между 390 и 400? Тогда линейная интерполяция преувеличит долю значений ниже 250.

    Гистограмма хранит положение границ и массу интервалов, но не полное распределение внутри каждого интервала. Это ее фундаментальное ограничение.

    Также стоит помнить, что сравнение может быть целочисленным, строковым или временным. Интерполяция и поправки зависят от типа, доступных операторов и внутренних функций оценки. Для некоторых типов есть специфические эвристики; универсальная формула числовой линейной интерполяции — учебная модель.

    4.5. Когда одновременно есть MCV, NULL и histogram¶

    Теперь более реалистичная ситуация:

    null_frac = 0.05
сумма частот всех MCV = 0.30
оставшаяся масса = 0.65

    Пусть для условия amount < 250:

    • сумма частот тех MCV, которые удовлетворяют условию, равна 0.20;
    • гистограмма оставшейся части оценивает долю удовлетворяющих условию в 0.45.

    Тогда:

    [ \hat s=\underbrace{0.20}{\text{подходящие MCV}} +\underbrace{0.65}\cdot \underbrace{0.45}_{\text{доля по histogram}}. ]}

    [ \hat s=0.4925. ]

    [ \hat N_{out}=492\,500. ]

    Гистограмма описывает только оставшиеся 65% ненулевых данных. Она не должна повторно оценивать популярные значения и NULL.

    Этот расчет демонстрирует общую модель, описанную в официальной документации: отдельно оценить MCV, отдельно остаток, затем объединить.

    4.6. BETWEEN: почему две границы сложнее одной¶

    Запрос:

    WHERE amount BETWEEN 100 AND 500

    эквивалентен:

    WHERE amount >= 100 AND amount <= 500

    Хочется просто умножить селективности двух сравнений. Но это не независимые события: попадание в условие >= 100 меняет вероятность условия <= 500.

    Если известна приближенная функция распределения (F(x)=P(X\le x)), то для непрерывной учебной модели:

    [ P(100\le X\le500)\approx F(500)-F(100). ]

    Для дискретных значений нужна корректировка границ: математически точное выражение — (F(500)-P(X<100)). PostgreSQL использует специализированную логику для пар противоположно направленных диапазонных условий, чтобы избежать наивного независимого перемножения.

    Например, если:

    [ P(X\ge100)=0.9,\quad P(X\le500)=0.4, ]

    то независимое перемножение даст (0.9\cdot0.4=0.36). Однако при непрерывной модели без массы в граничных точках диапазонная селективность ближе к:

    [ 0.9+0.4-1=0.3. ]

    Эта разница влияет на rows еще до выбора способа доступа.

    4.7. Условия AND и OR: базовая вероятностная модель¶

    Для двух независимых условий (A), (B):

    [ P(A\land B)=P(A)P(B). ]

    Например:

    WHERE status = 'PAID'
  AND amount > 5000

    Если (s_A=0.2), (s_B=0.1), независимая оценка:

    [ \hat s=0.2\cdot0.1=0.02. ]

    Миллион строк превращается в 20 000.

    Для OR при независимости:

    [ P(A\lor B)=P(A)+P(B)-P(A)P(B). ]

    С теми же долями:

    [ \hat s=0.2+0.1-0.02=0.28. ]

    Получаем 280 000.

    Умножение и сложение работают только при соответствующих допущениях. PostgreSQL применяет и специальные оценки для известных сочетаний условий, и расширенную статистику; выводить точную механику любого SQL из двух школьных формул было бы неверно.

    4.8. Вероятности условные, а планировщик часто знает только безусловные¶

    Точная формула совместной селективности:

    [ P(A\land B)=P(A)P(B\mid A). ]

    Независимость означает особый случай:

    [ P(B\mid A)=P(B). ]

    А теперь предположим, что каждый заказ со статусом PAID обязательно относится к каналу APP. Тогда:

    [ P(APP\mid PAID)=1. ]

    При (P(PAID)=0.1) и (P(APP)=0.1):

    • независимая оценка: (0.1\cdot0.1=0.01);
    • реальная совместная доля: (0.1\cdot1=0.1).

    Мы получили ошибку ровно в десять раз. Следующий раздел объясняет, какой механизм PostgreSQL использует для таких случаев.

    Что важно запомнить после раздела 4¶

    1. Равенство популярному значению оценивается по MCV; отсутствие значения в MCV включает эвристику остаточной массы.
    2. Диапазоны оцениваются по гистограмме, но точность ограничена разрешением и предположениями внутри интервалов.
    3. MCV, гистограмма и NULL покрывают разные части распределения и не должны учитываться дважды.
    4. AND и OR легко оценивать при независимости; зависимые условия требуют дополнительных данных.
    5. Специализированная оценка BETWEEN полезнее наивного перемножения нижней и верхней границ.

    5. Extended Statistics: когда независимость колонок разрушает оценку¶

    5.1. Один и тот же запрос, ошибка в сто раз¶

    Рассмотрим таблицу на 10 000 строк с двумя числовыми колонками:

    a = i % 100
b = i % 100

    Каждое значение от 0 до 99 встречается сто раз. Колонки всегда равны друг другу.

    Запрос:

    SELECT *
FROM t
WHERE a = 1 AND b = 1;

    Для каждого одиночного условия:

    [ P(a=1)=0.01,\quad P(b=1)=0.01. ]

    По независимой модели:

    [ \hat s=0.01\cdot0.01=0.0001, ]

    [ \hat N=10\,000\cdot0.0001=1. ]

    Но реально a=1 автоматически означает b=1. Следовательно:

    [ P(a=1\land b=1)=0.01, ]

    [ N_{actual}=100. ]

    Оценка в сто раз меньше реальности.

    Этот пример соответствует опубликованному демонстрационному случаю в документации PostgreSQL 18, где план первоначально содержит rows=1, а после сбора многоколоночной статистики — rows=100.

    5.2. Почему обычная статистика двух колонок не спасает¶

    Обычный pg_stats может точно знать для обеих колонок:

    n_distinct = 100
для значения 1 частота = 0.01

    Но это две маргинальные частоты: (P(a=1)) и (P(b=1)).

    По ним нельзя однозначно восстановить совместную вероятность (P(a=1,b=1)).

    Две таблицы могут иметь одинаковые распределения каждого столбца в отдельности и совершенно разное совместное распределение:

    • в первой колонке b всегда равна a;
    • во второй значения b случайно перемешаны по строкам.

    Их одно-колоночные MCV и n_distinct могут совпадать. Различается именно связь между колонками.

    5.3. CREATE STATISTICS: запросить сбор совместной статистики¶

    PostgreSQL позволяет явно обозначить интересующее сочетание колонок:

    CREATE STATISTICS t_ab_stats (dependencies, mcv, ndistinct)
ON a, b
FROM t;

ANALYZE t;

    Здесь две разные операции:

    1. CREATE STATISTICS регистрирует объект статистики и виды собираемых сведений.
    2. ANALYZE получает выборку и вычисляет эти сведения.

    Объекты регистрируются в pg_statistic_ext, сами расширенные данные — в pg_statistic_ext_data. Для просмотра существует pg_stats_ext; содержимое многоколоночной MCV можно раскрыть функцией pg_mcv_list_items.

    Рассмотрим три вида статистики по отдельности.

    5.4. dependencies: функциональные зависимости¶

    Говорят, что (A\to B), если значение A определяет значение B. Классический пример: корректный ZIP-код может определять город, хотя один город может содержать несколько ZIP-кодов.

    Для совпадающих колонок a и b степень зависимости близка к 1.

    Коэффициент (f) в статистике зависимостей отражает, насколько хорошо выполняется связь. Он может быть между 0 и 1:

    • (f=1): полная функциональная зависимость;
    • (f\approx0): сильной зависимости нет;
    • промежуточные значения: связь частичная.

    В документируемой модели PostgreSQL для двух подходящих условий исходная идея:

    [ P(A,B)\approx fP(A)+(1-f)P(A)P(B). ]

    Однако реальная реализация использует уточнение, чтобы совместная селективность не превысила отдельную селективность каждого условия:

    [ \boxed{\hat s_{AB}\approx f\min(s_A,s_B)+(1-f)s_As_B.} ]

    Именно это выражение описано в исходниках src/backend/statistics/dependencies.c (при более чем двух условиях используется более сложное последовательное применение зависимостей).

    Подставим:

    [ s_A=0.1,\quad s_B=0.2,\quad f=0.75. ]

    [ \hat s_{AB}=0.75\cdot0.1+0.25\cdot(0.1\cdot0.2) =0.075+0.005=0.08. ]

    Для миллиона строк это оценка 80 000.

    Проверьте крайние случаи мысленно:

    • при (f=0) получим независимую модель: (0.02), или 20 000 строк;
    • при (f=1) получим (\min(0.1,0.2)=0.1), или 100 000 строк.

    Чем сильнее зависимость, тем меньше второе условие считается способным дополнительно уменьшить результат.

    5.5. Почему dependencies могут ошибаться даже при f=1¶

    Теперь интересный случай.

    Пусть поле postal_code определяет city:

    postal_code=94105 → city='San Francisco'

    Запрос 1:

    WHERE postal_code = '94105'
  AND city = 'San Francisco'

    Условия совместимы. Из зависимости действительно следует, что city почти не уменьшает результат.

    А теперь запрос 2:

    WHERE postal_code = '94105'
  AND city = 'Los Angeles'

    Если данные непротиворечивы, результат пустой.

    Но статистика dependencies описывает силу общей зависимости, не полное отображение каждого ZIP-кода в каждый город. Она может трактовать оба условия как совместимые и давать положительную оценку.

    Здесь становится понятно ограничение этого метода: знание, что B зависит от A, не раскрывает, какому именно B соответствует конкретное A.

    Дополнительные ограничения в PostgreSQL 18: функциональные зависимости применяются прежде всего к простым условиям равенства колонки константе и подходящим IN со списками констант. Они не являются универсальным механизмом коррекции произвольных диапазонов, LIKE, сложных выражений или сравнений двух колонок.

    5.6. Многоколоночные MCV: хранить конкретные сочетания¶

    Для предыдущей ситуации полезнее mcv:

    CREATE STATISTICS zip_city_mcv (mcv)
ON postal_code, city
FROM addresses;

ANALYZE addresses;

    Многоколоночная MCV хранит частые комбинации значений. Она может сообщать, что сочетание:

    ('94105', 'San Francisco')

    имеет определенную частоту, а сочетание:

    ('94105', 'Los Angeles')

    не встречается в найденных популярных комбинациях.

    Тут нужно быть точным: отсутствие пары в MCV не доказывает нулевую частоту во всей таблице, потому что список неполный и собран по выборке. Но MCV обычно лучше представляет конкретные сочетания, чем глобальная функциональная зависимость.

    В состав данных MCV входят:

    • frequency — оцененная доля строк с данным сочетанием;
    • base_frequency — произведение отдельных маргинальных частот, то есть ожидаемая доля при независимости.

    Пример:

    Сочетание frequency base_frequency
    (PAID, APP) 0.10 0.01

    Здесь статистика непосредственно показывает: совместное сочетание встречается примерно в десять раз чаще, чем прогнозирует независимая модель.

    Это полезно не только для равенств: многоколоночная MCV может помогать оценивать разные поддерживаемые комбинации ограничений на соответствующие столбцы. Но конкретная применимость определяется видом предикатов и логикой планировщика.

    5.7. ndistinct: число различных сочетаний¶

    Обычная статистика говорит:

    n_distinct(a) = 100
n_distinct(b) = 100

    Но сколько существует различных пар (a,b)?

    Если значения независимы и встречаются во всех комбинациях, их может быть до 10 000 (при достаточном числе строк).

    Если b=a, различных пар только 100:

    (0,0), (1,1), ..., (99,99)

    Статистика ndistinct помогает планировщику оценивать число различных комбинаций — особенно для операций вроде GROUP BY a,b.

    Важная граница: ndistinct не следует считать главным средством исправления селективности произвольного WHERE a=... AND b=.... Для совместных фильтров обычно важнее dependencies и многоколоночная mcv. Иначе легко получить красивый объект статистики, который не влияет на искомую оценку.

    5.8. Почему PostgreSQL не строит статистику для всех комбинаций автоматически¶

    Для таблицы с 30 столбцами количество пар:

    [ C(30,2)=\frac{30\cdot29}{2}=435. ]

    Количество троек:

    [ C(30,3)=4060. ]

    Количество всех непустых сочетаний:

    [ 2^{30}-1=1\,073\,741\,823. ]

    Разумеется, далеко не все сочетания нужны реальным запросам. Автоматически собирать и поддерживать статистику для миллиарда возможных наборов колонок абсурдно.

    Поэтому пользователь явно выбирает значимые группы через CREATE STATISTICS. Это разумный компромисс между временем анализа, объемом каталога и качеством оценок для действительно используемых предикатов.

    Что важно запомнить после раздела 5¶

    1. Две точные одно-колоночные статистики не определяют совместное распределение двух столбцов.
    2. dependencies оценивает силу функциональной зависимости; она может не распознать несовместимые конкретные значения.
    3. mcv хранит популярные пары или наборы значений и помогает обнаружить отличие от независимой модели.
    4. ndistinct оценивает число разных сочетаний, а не является универсальной поправкой к любому WHERE.
    5. Расширенная статистика не появляется сама по себе: объект нужно создать, затем собрать данные через ANALYZE.

    6. Ошибки Cardinality Estimation: когда статистическая модель оказывается недостаточной¶

    6.1. Как измерять ошибку и не обманывать себя¶

    Пусть:

    estimated rows = 100
actual rows    = 100000

    Оценка занижена в:

    [ \frac{100\,000}{100}=1000\text{ раз}. ]

    Для ненулевых значений можно вводить показатель кратности ошибки:

    [ q=\max\left(\frac{N_{actual}}{N_{estimated}}, \frac{N_{estimated}}{N_{actual}}\right). ]

    Он показывает величину расхождения независимо от направления. Но направление тоже важно:

    • actual > estimated — недооценка, опасна при выборе операций, рассчитанных на маленький объем;
    • actual < estimated — переоценка, способна привести к отказу от выгодного индекса или к избыточно консервативному плану.

    Если фактически 0 строк, деление на ноль недопустимо; нужно фиксировать нулевой результат отдельно, а для агрегированных отчетов применять явно определенную методику обработки нулей.

    В EXPLAIN ANALYZE следует сравнивать оценки и фактические строки одного и того же узла. Если узел выполнялся многократно, actual rows обычно показывает среднее на запуск, поэтому без учета loops нельзя интерпретировать абсолютный объем работы.

    6.2. Сценарий А: неравномерность внутри неизвестного остатка¶

    Вернемся к оценке значения, отсутствующего в MCV:

    [ \hat s=\frac{\text{остаточная масса}}{\text{число остальных значений}}. ]

    Это ровно то место, где планировщик вынужден предполагать приблизительную равномерность остатка.

    Если одна редкая категория стала очень популярной, но не попала в статистическую выборку или не получила индивидуальной записи в MCV, оценка будет неверной.

    Симптом: два запроса с одной колонкой и разными конкретными значениями имеют похожие rows в планах, но фактическое количество строк резко различается.

    Причинная цепочка: ограниченный MCV → усреднение остатка → ошибочная селективность конкретного значения → неправильный прогноз числа строк.

    6.3. Сценарий Б: значение на границе гистограммы¶

    Допустим, гистограмма описывает верхнюю границу created_at, достигнутую при последнем анализе.

    После этого в таблицу вставили большое число заказов с более поздними датами.

    Запрос:

    WHERE created_at >= timestamp '2026-11-01'

    может оказаться вне диапазона старой гистограммы. Теперь планировщику приходится использовать эвристику для области, которую статистика плохо описывает.

    Новая часть распределения могла содержать 10 строк или миллион строк. По старым границам это не установить.

    Симптом: запросы к «самым свежим» данным оцениваются хуже, чем запросы к историческому диапазону.

    Причинная цепочка: монотонно растущий столбец → статистика отстает → новые значения вне старых histogram bounds → ошибочная оценка диапазона.

    6.4. Сценарий В: статистика свежая, но условия зависимы¶

    В таблице status='PAID' и channel='APP' имеют селективности по 0.1, но встречаются строго вместе.

    Даже только что выполненный ANALYZE по отдельным колонкам может дать:

    [ 0.1\cdot0.1=0.01 ]

    вместо фактических (0.1).

    Симптом: одиночные условия оцениваются корректно, совместное AND — сильно неверно.

    Причинная цепочка: верные маргинальные распределения → ошибочное предположение независимости → недооценка комбинации → необходимость extended statistics.

    Это принципиально другая проблема, чем устаревшая статистика. Повторять обычный ANALYZE здесь недостаточно: нужно изменить сам набор доступных сведений.

    6.5. Сценарий Г: выборка не видит редкое значение¶

    Миллионные таблицы часто содержат «тяжелых» клиентов, крупные группы событий, всплески аномальных статусов.

    Если значение встречается реже частоты, при которой его можно надежно увидеть в выборке, оценка опирается на обобщение. Если значение внезапно стало массовым, а статистика еще не обновилась, ошибку усиливают сразу два фактора.

    Симптом: ошибка встречается только для отдельных значений или в короткий период после массовой загрузки.

    Причинная цепочка: ограниченная выборка + изменчивое распределение → нет точной частоты → равномерная оценка остатка → ошибка на порядки.

    6.6. Сценарий Д: размер таблицы и распределение изменились независимо¶

    Планировщик может относительно успешно масштабировать reltuples по текущему числу страниц. Но этот прием корректирует размер, а не распределение конкретного значения.

    Предположим:

    • раньше миллион строк, 10% PAID;
    • после загрузки еще миллион строк, и почти все новые строки PAID;
    • актуальная статистика по статусам не собрана.

    Планировщик способен догадаться, что таблица стала больше, но продолжить применять старую селективность 10%.

    Итоговая ошибка может остаться большой даже при неплохой оценке общего количества строк.

    Инженерный вывод: рассматривать reltuples и селективность отдельно. Хорошая оценка базы не гарантирует хорошую оценку WHERE.

    6.7. Какие изменения реально устраняют проблему¶

    Причина Что требуется изменить в модели Что не гарантирует исправления
    Устаревшие частоты Новый ANALYZE после изменения распределения Переключение способов сканирования
    Недостаточная выборка Повысить statistics target для нужной колонки Глобально завысить target всем столбцам
    Зависимые колонки CREATE STATISTICS (mcv/dependencies) + ANALYZE Повторять обычный ANALYZE без extended stats
    Неудачная оценка диапазона Улучшить актуальность и разрешение histogram; исследовать форму данных Считать BETWEEN независимыми сравнениями
    Особенности выражения Статистика по выражению, если поддерживается и уместна Предполагать, что статистика исходного столбца автоматически описывает любую функцию от него
    Частые изменения небольшой доли таблицы Пересмотреть частоту анализа критичных таблиц Надеяться, что общий порог всегда отражает перемены важных значений

    Заметьте: это не набор магических команд. Каждая мера исправляет конкретный источник неопределенности.

    6.8. Почему даже идеальная оценка строк не гарантирует быстрый запрос¶

    Предположим, rows вычислен точно. Все равно остаются вопросы:

    • сколько страниц таблицы понадобится прочитать;
    • насколько строки разбросаны по heap;
    • находятся ли нужные страницы в кеше;
    • какова стоимость обработки каждого кандидата;
    • сколько памяти потребуется сортировке.

    Ответы превращают оценку rows в cost model. Это содержание блока 2 лекции 05.1.

    Для завершения текущей темы нам важно другое: если rows ошибочны, то все последующие расчеты получают неверные исходные данные. Поэтому оценка cardinality — фундамент, на котором строится дальнейший выбор плана.

    6.9. Единый разбор от SQL до оценки¶

    Сведем все в один пример.

    Есть миллион строк. Планировщик знает:

    reltuples / пересчитанная оценка N = 1 000 000
P(status='PAID') = 0.10
P(channel='APP') = 0.10

    Запрос:

    SELECT id
FROM orders
WHERE status = 'PAID'
  AND channel = 'APP';

    Модель 1. Только одно-колоночная статистика.

    [ \hat N=1\,000\,000\cdot0.10\cdot0.10=10\,000. ]

    Факт. Все оплаченные заказы приходят через приложение, поэтому действительное количество — 100 000.

    Модель 2. Известна полная функциональная зависимость.

    [ f=1,\qquad \hat s=\min(0.10,0.10)=0.10. ]

    [ \hat N=100\,000. ]

    Модель 3. Известна совместная MCV-пара.

    Для (PAID, APP) в расширенной MCV оценена частота 0.10, а base_frequency=0.01. Планировщик получает основание корректировать наивное перемножение.

    На этом завершена цепочка:

    pg_class → размер отношения
         ↓
ANALYZE → выборка
         ↓
pg_statistic → частоты, гистограмма, NDV
         ↓
selectivity функций условий
         ↓
extended statistics для зависимых условий
         ↓
оценка rows
         ↓
[следующий блок: cost model и выбор пути]

    Что важно запомнить после раздела 6¶

    1. Ошибка rows возникает либо в оценке размера исходной таблицы, либо в селективности, либо в сочетании обоих факторов.
    2. Свежая статистика может быть недостаточной по составу, даже если она актуальна по времени.
    3. Редкие значения, быстрые изменения распределения, неравномерный остаток и зависимые условия — типичные источники крупных ошибок.
    4. Для каждого класса ошибок существует свой механизм улучшения статистической модели.
    5. Правильные rows еще не гарантируют правильный cost, но неправильные rows дают плохую основу для всей дальнейшей оптимизации.

    Блок 2. PostgreSQL Cost Model — от rows к стоимости¶

    Блок 1 дал оценку количества строк. Но у получения одних и тех же 10 000 строк может быть принципиально разная цена: все страницы таблицы, множество отдельных heap-обращений, построение bitmap или сортировка после чтения. Теперь разберем расчетную модель каждой альтернативы — без смешения формул реального кода с учебными приближениями.

    7. Модель стоимости PostgreSQL¶

    7.1. У нас уже есть rows. Почему этого недостаточно?¶

    Представим таблицу orders, в которой миллион строк. После анализа статистики планировщик ожидает, что условие вернет десять тысяч строк:

    SELECT id, amount, payload
FROM orders
WHERE amount BETWEEN 1000 AND 1999;

    Ожидаемая селективность — 1%. Пусть по amount существует B-tree индекс.

    Возможны разные стратегии:

    1. Пройти последовательно по всей таблице и проверить условие для каждой строки — Seq Scan.
    2. Найти ключи в B-tree и по ссылкам из индекса получать строки таблицы — Index Scan.
    3. Собрать ссылки на подходящие строки в bitmap, сгруппировать их по страницам и прочитать heap — Bitmap Index Scan вместе с Bitmap Heap Scan.

    Количество подходящих строк одинаковое. Работа с данными — разная. Значит, оценка rows должна превратиться в другую величину, отражающую предполагаемые затраты.

    PostgreSQL использует cost-based optimizer — планировщик, который оценивает стоимость допустимых способов выполнения и сравнивает альтернативы.

    7.2. Что такое cost: единицы, которыми нельзя расплатиться¶

    В EXPLAIN мы видим:

    Seq Scan on orders  (cost=0.00..22500.00 rows=10000 width=...)

    22500.00 — условные единицы стоимости, сформированные моделью. Это не миллисекунды, не байты и не счетчик системных вызовов.

    В качестве базовой единицы традиционно взята условная стоимость последовательного получения одной страницы (seq_page_cost = 1.0). Остальные параметры задают относительную цену других видов работы.

    Два плана можно сравнивать в одинаковой конфигурации, при одинаковых предположениях и входных данных:

    Plan A: cost=0.00..22500.00
Plan B: cost=12.00..11000.00

    Планировщик считает B дешевле при полном получении результата, если остальные ограничения и требуемые свойства результата сопоставимы.

    Но отсюда не следует, что B выполнится в 22500 / 11000 ≈ 2.05 раза быстрее. Стоимости приблизительны, зависят от статистики и не отражают точно состояние кешей, конкуренцию процессов и конкретные задержки storage.

    В документации есть полезная тонкость: теоретически стоимость можно масштабировать и под миллисекунды. PostgreSQL не запрещает этого. На практике нет единой точной калибровки для разнородной нагрузки, поэтому обычная модель использует относительные величины.

    7.3. startup_cost и total_cost: два разных вопроса к одному пути¶

    У каждого пути — Path, то есть кандидата на выполнение части запроса — есть две оценки:

    • startup_cost — стоимость работы до выдачи первой строки;
    • total_cost — суммарная стоимость пути, если потребовать все строки.

    Рассмотрим две стратегии получения строк в порядке amount:

    A. Index Scan
   startup=5, total=30000

B. Seq Scan + Sort
   startup=18000, total=20500

    Числа условные.

    Если клиенту нужны все строки, B выглядит дешевле. Но если требуется только первая строка, у A может быть преимущество. Сортировка без ограничений часто должна сначала прочитать и упорядочить входные данные.

    В costsize.c прямо описано приближение для стоимости получения части результата:

    [ C_{\text{partial}}=C_{\text{startup}}+ \left(C_{\text{total}}-C_{\text{startup}}\right) \frac{N_{\text{needed}}}{N_{\text{path}}}. ]

    Это оценочная интерполяция, применяемая там, где планировщик может ожидать неполное потребление результата. Она не обещает, что любой узел физически умеет остановиться пропорционально числу строк. LIMIT подробно разберем в блоке 3, а здесь важно понять причину существования двух cost.

    7.4. Аддитивная модель: что складывается¶

    Упрощенно стоимость полного пути можно выразить так:

    [ C_{\text{total}} = C_{\text{startup}} + C_{\text{I/O}} + C_{\text{CPU}} + C_{\text{other}}. ]

    Слагаемые зависят от способа выполнения.

    Для сканирования таблицы могут учитываться:

    • число страниц heap и их условная стоимость;
    • число обрабатываемых версий строк;
    • стоимость вычисления выражений WHERE;
    • стоимость получения данных через индекс;
    • стоимость формирования выходных значений (projection, или вычисление целевого списка);
    • затраты на промежуточные структуры, например bitmap или сортировку.

    Аддитивность модели не означает независимость физических затрат. В реальном процессе работа с памятью, CPU и I/O перекрывается; кеширование зависит от других запросов; заранее определить точную стоимость такого взаимодействия сложно.

    Нас интересует сравнение альтернатив, а не идеальная физическая симуляция сервера.

    7.5. Почему нельзя складывать cost разных узлов EXPLAIN¶

    Пусть план выглядит так:

    Sort  (cost=30000.00..30250.00)
  -> Seq Scan on orders  (cost=0.00..20000.00)

    Sort получает строки от дочернего Seq Scan. Стоимость дочернего пути уже включена в стоимость родителя. Сложив 30250 + 20000, мы посчитаем чтение таблицы дважды.

    Правильная модель:

    [ C_{\text{Sort,total}} = C_{\text{input,total}} + C_{\text{sorting}} + C_{\text{output}}. ]

    Это объясняет, почему верхний узел дерева может иметь самую высокую стоимость, даже если его собственные операции относительно дешевы.

    7.6. Какие данные реально поступают в функции стоимости¶

    В исходниках PostgreSQL ключевые структуры следующие:

    Структура Что содержит и почему нужна
    RelOptInfo Оценки rows, tuples, pages, сведения о базовом отношении и доступных путях
    Path Оцениваемые rows, startup_cost, total_cost, способ выполнения, требования к порядку результата
    IndexOptInfo Сведения об индексе: число страниц, столбцы, свойства метода доступа и т. д.
    QualCost Две части стоимости выражения: startup и per_tuple
    PathTarget Выходные выражения пути и их стоимость; ее часть может вычисляться для каждой выдаваемой строки

    Имена C-структур и функций здесь — детали реализации PostgreSQL 18, а не элементы SQL-стандарта. Они нужны, чтобы понимать математику в costsize.c.

    Особенно важна граница между:

    • baserel->tuples: сколько строк предполагается просмотреть в исходном отношении;
    • path->rows: сколько строк ожидается отдать наверх после фильтрации.

    У этих значений разные роли. Через несколько разделов мы увидим, почему путать их дорого.

    Что важно запомнить после раздела 7¶

    1. rows сообщает о прогнозируемом количестве строк, cost — о прогнозируемых затратах на их получение.
    2. Две части cost позволяют учитывать работу до первого результата и работу до получения всех строк.
    3. Стоимость родителя включает стоимость дочернего пути; суммирование cost по дереву неверно.
    4. Модель оценивает условные операции, а реальная задержка зависит от фактического исполнения и нагрузки.
    5. Базовая единица стоимости выбрана для сравнения планов, поэтому перевод cost → миллисекунды без калибровки некорректен.

    8. Коэффициенты стоимости: от страниц к CPU¶

    8.1. Почему планировщик вообще задает цену операции константой?¶

    Рассмотрим один и тот же SQL на разных серверах.

    На первом сервере данные часто читаются с жесткого диска. Случайные обращения дорогие. На втором таблица почти целиком помещается в память. Непоследовательный доступ к страницам оказывается значительно дешевле.

    Сама логика SQL не изменилась. А вот стоимость Index Scan относительно Seq Scan стала другой.

    Чтобы сравнивать пути, PostgreSQL задает набор коэффициентов. Для PostgreSQL 18 стандартные значения следующие.

    Параметр По умолчанию Что представляет в модели
    seq_page_cost 1.0 Последовательное получение страницы
    random_page_cost 4.0 Непоследовательное получение страницы
    cpu_tuple_cost 0.01 Обработку строки исполнителем
    cpu_index_tuple_cost 0.005 Обработку записи индекса
    cpu_operator_cost 0.0025 Вычисление типичного оператора/функции
    effective_cache_size 4GB Оценку эффективного объема кеша для планирования

    Это настройки cost model, а не результаты аппаратных измерений. Для реальных операций цена существенно меняется в зависимости от условий.

    8.2. Почему random_page_cost = 4, а не 1?¶

    Вернемся к B-tree.

    Индекс находит подходящие TID — идентификаторы позиций версий строк в heap. Если близкие ключи ссылаются на далекие страницы, чтение будет непоследовательным. Это исторически дорого для магнитных накопителей.

    Однако значение 4.0 вовсе не означает, что современный случайный I/O всегда в четыре раза медленнее последовательного. Оно уже предполагает, что многие непоследовательные обращения попадут в кеши.

    На сервере с горячим рабочим набором модель random_page_cost=4 может переоценивать накладные расходы индексного доступа. Тогда снижение значения до, например, 1.1 или 1.5 иногда меняет выбор пути.

    Но важна причинная цепочка:

    Уменьшили random_page_cost
        ↓
Непоследовательные страницы в модели дешевле
        ↓
Index Scan и другие пути с индексным доступом выигрывают чаще
        ↓
Меняются планы многих запросов, а не только проблемного

    Тонкость: random_page_cost может быть установлен равным seq_page_cost для полностью кешированной базы. Но при этом стоит пересмотреть относительную цену CPU, поскольку даже попадание в RAM имеет стоимость.

    8.3. Что оплачивает cpu_tuple_cost¶

    Частая ошибка — интерпретировать cpu_tuple_cost как стоимость сравнения одного числа.

    В модели это базовая стоимость обработки кортежа (строки). Само вычисление условия WHERE добавляет стоимость выражения.

    Для фильтра:

    WHERE amount > 1000

    учебная модель одной проверки:

    [ C_{\text{CPU per tuple}} \approx C_{\text{tuple}} + C_{\text{operator}} = 0.01 + 0.0025 = 0.0125. ]

    А если условие содержит несколько операторов и вызовы функций, стоимость выражения будет выше. PostgreSQL использует cost_qual_eval() и связанные механизмы для расчета QualCost.

    Стоимость функций не всегда сводится к cpu_operator_cost: функции могут иметь заданную стоимость через механизм pg_proc.procost, и планировщик учитывает эту информацию. Поэтому умножение числа символов > и = на 0.0025 не является общей формулой SQL.

    8.4. Как cpu_index_tuple_cost соотносится с cpu_tuple_cost¶

    При Index Scan PostgreSQL может обрабатывать записи индекса, а потом соответствующие строки heap. В модели присутствуют обе категории работы.

    Для B-tree-кандидата на поиск по одному условию упрощенный фрагмент оценки индексного метода доступа имеет вид:

    [ C_{\text{index CPU}} \approx N_{\text{index entries}} \left(C_{\text{index tuple}} + C_{\text{operator}}\right). ]

    Для 10 000 найденных индексных записей:

    [ 10000(0.005+0.0025)=75. ]

    Но это еще не полная стоимость Index Scan. Остались стоимость страниц индекса, посещений heap, обработки heap-кортежей и дополнительных фильтров.

    Вот почему фраза «индекс читает только 10 000 строк» слишком груба: физически могут быть тысячи страниц и две структуры хранения.

    8.5. effective_cache_size: самый частый неверный вывод¶

    Параметр называется так, будто PostgreSQL выделяет указанную память под кеш запроса.

    В действительности effective_cache_size — предположение планировщика о количестве страниц, которые могут эффективно кешироваться для запроса, с учетом PostgreSQL и кеша ОС.

    Он:

    • не выделяет RAM;
    • не меняет shared_buffers;
    • не гарантирует, что конкретные страницы находятся в памяти;
    • влияет на расчет ожидаемых повторных обращений к страницам при индексном доступе.

    Например:

    SHOW effective_cache_size;
SHOW shared_buffers;

    Эти параметры выполняют разные функции. shared_buffers управляет общим буферным пулом PostgreSQL. effective_cache_size влияет на предположения оптимизатора.

    В функции index_pages_fetched() кешевой бюджет распределяется пропорционально размеру оцениваемого отношения относительно суммарного размера отношений, задействованных в запросе. Это очень грубая модель. Она важна, поскольку позволяет оценивать повторное получение страниц, а не считать каждую ссылку TID отдельным физическим чтением.

    8.6. Что можно переопределить в tablespace¶

    seq_page_cost и random_page_cost допускают переопределение на уровне tablespace. Это полезно, когда разные отношения физически находятся на накопителях с разными свойствами.

    Но временные файлы, создаваемые внешними сортировками, не используют tablespace-specific коэффициенты по тем же правилам, что обычные сканы. В модели сортировки есть собственное упрощенное допущение о цене временного I/O.

    Значит, установка более дешевых страниц для tablespace с таблицей не обязана сделать дешевле любую операцию, встречающуюся в плане.

    8.7. Почему универсальная модель неизбежно ошибается¶

    Те же параметры должны работать на запросах, где:

    • часть страниц горячая, а часть холодная;
    • несколько backend-процессов конкурируют за CPU, RAM и I/O;
    • накопитель имеет разную задержку при разной глубине очереди;
    • страницы heap физически фрагментированы;
    • операторы затрачивают разное количество CPU на разные значения.

    Константы описывают среднюю относительную стоимость для класса операций. В отдельных запросах они дают ошибку.

    Инженерный вывод: сначала диагностируем статистику и свойства выбранного пути. Изменение глобальных коэффициентов — уже действие над моделью для всего workload, требующее понимания последствий.

    Что важно запомнить после раздела 8¶

    1. Коэффициенты стоимости задают относительную цену, а не точную продолжительность операций.
    2. random_page_cost влияет на привлекательность индексного доступа, но сама реальная цена случайного доступа зависит от кешей и накопителя.
    3. cpu_tuple_cost, cpu_index_tuple_cost, cpu_operator_cost описывают разные компоненты обработки.
    4. effective_cache_size — расчетное предположение; память оно не резервирует.
    5. Глобальная настройка влияет на большое количество потенциальных планов, поэтому ее нельзя бездумно подбирать под один запрос.

    9. Математика Seq Scan: теперь считаем стоимость руками¶

    9.1. Одна учебная таблица для всех следующих разделов¶

    Чтобы при сравнении методов чтения не менять исходные данные посреди рассуждения, зададим одну модель.

    Отношение orders (все числа гипотетические):

    Обозначение Значение Смысл
    N 1 000 000 Оцененное число кортежей для расчета обработки полного сканирования
    T 10 000 Страниц heap
    BLCKSZ 8 KiB Размер страницы обычной сборки
    P_seq 1.0 seq_page_cost
    P_rand 4.0 random_page_cost
    C_tuple 0.01 cpu_tuple_cost
    C_index_tuple 0.005 cpu_index_tuple_cost
    C_op 0.0025 cpu_operator_cost
    I_leaf 2 000 Условное количество листовых страниц B-tree

    Здесь N соответствует статистической оценке baserel->tuples, а не точному количеству физически существующих версий строк: в heap могут оставаться мертвые версии, создающие дополнительную реальную работу до очистки.

    Последнее число нужно только для учебного приближения стоимости чтения B-tree. В реальной системе индекс имеет собственную статистику, структуру, глубину и параметры метода доступа.

    Предположим, что SELECT требует столбец payload, которого нет в индексе. Тогда обычный Index Only Scan для этого запроса не подходит: при индексном способе доступа придется обращаться к heap.

    Проверяем условие:

    SELECT id, amount, payload
FROM orders
WHERE amount BETWEEN 1000 AND 1999;

    Селективность считаем равной s = 0.01, то есть планировщик ожидает 10 000 подходящих строк. Для простоты оценим проверку диапазона как одно условное вычисление оператора стоимостью 0.0025 на входную строку. В настоящем плане BETWEEN обычно переписывается в два сравнения, поэтому его полная стоимость фильтра будет отличаться. Числа ниже демонстрируют бухгалтерию модели, а не воспроизводят точный вывод EXPLAIN для этого текста SQL.

    9.2. Кодовое ядро cost_seqscan()¶

    В src/backend/optimizer/path/costsize.c существенная часть оценки устроена так (псевдофрагмент с сохранением смысловых имен):

    // I/O: каждая страница базового отношения
// учитывается как последовательное получение.
disk_run_cost = spc_seq_page_cost * baserel->pages;

// Стоимость проверки условий и другой обработки строки.
get_restriction_qual_cost(root, baserel, param_info, &qpqual_cost);
startup_cost += qpqual_cost.startup;
cpu_per_tuple = cpu_tuple_cost + qpqual_cost.per_tuple;
cpu_run_cost = cpu_per_tuple * baserel->tuples;

// Выходные выражения оплачиваются по числу выдаваемых строк.
startup_cost += path->pathtarget->cost.startup;
cpu_run_cost += path->pathtarget->cost.per_tuple * path->rows;

path->startup_cost = startup_cost;
path->total_cost = startup_cost + cpu_run_cost + disk_run_cost;

    Это сокращенный, объясняющий фрагмент, без веток параллельного исполнения и прочих деталей. Смысловые слагаемые соответствуют исходникам PostgreSQL 18.

    В математической форме для обычного непараллельного случая:

    [ C_{\text{seq,total}} = C_{\text{qual,start}} + C_{\text{target,start}} + T P_{\text{seq}} + N\left(C_{\text{tuple}} + C_{\text{qual/tuple}}\right) + N_{out} C_{\text{target/tuple}}. ]

    Здесь:

    • N — все строки, которые сканирование предполагает обработать;
    • N_out — ожидаемые выходные строки;
    • T — все страницы heap;
    • C_qual/tuple — стоимость условия на одну просматриваемую строку;
    • C_target/tuple — стоимость формирования выходных выражений.

    Критическая деталь: CPU на проверку WHERE умножается на N, а стоимость выходных выражений — на N_out.

    9.3. Ручной расчет: страницы¶

    Стоимость последовательного получения страниц:

    [ C_{\text{I/O}}=T\cdot P_{\text{seq}} =10000\cdot1=10000. ]

    Почему берутся все 10 000 страниц, хотя условию соответствуют лишь 10 000 строк?

    Потому что без другого способа локализовать значения условие придется проверять при сканировании всей таблицы. Доля подходящих строк не освобождает Seq Scan от чтения страниц, содержащих неподходящие строки.

    9.4. Ручной расчет: CPU¶

    Условная цена обработки одной просмотренной строки:

    [ C_{\text{CPU/tuple}}=0.01+0.0025=0.0125. ]

    Для миллиона строк:

    [ C_{\text{CPU}}=1\,000\,000\cdot0.0125=12\,500. ]

    Если вычисление целевого списка в этой учебной модели дополнительно ничего не стоит, получаем:

    [ \boxed{C_{\text{seq,total}}=10000+12500=22500.} ]

    При нулевых startup-затратах выражений:

    Seq Scan on orders  (cost=0.00..22500.00 rows=10000 width=...)

    Это иллюстративная строка EXPLAIN, полученная из оговоренных параметров. Она не заявлена как результат запуска PostgreSQL.

    9.5. Меняем селективность: что происходит со стоимостью¶

    А теперь меняем только условие:

    • запрос A возвращает 100 строк;
    • запрос B возвращает 10 000 строк;
    • запрос C возвращает 500 000 строк.

    Если все три запроса используют Seq Scan по одной таблице и цена проверки условия одинакова, основной расчет остается тем же:

    Селективность rows на выходе Условный Seq Scan total cost
    0.01% 100 22 500
    1% 10 000 22 500
    50% 500 000 22 500

    В реальности отличаться могут цена условия, выходные выражения, иные свойства плана. Но неизменная часть модели предельно показательна.

    Для полного последовательного сканирования мы платим за обработку всех просмотренных строк. Селективность непосредственно влияет на число выходных строк и косвенно — на стоимость последующих операций.

    9.6. Как дорогая функция меняет картину¶

    Предположим, в WHERE появился дорогой предикат, которому планировщик назначил стоимость 0.2 условных единицы на строку вместо 0.0025.

    Тогда:

    [ C_{\text{CPU}}=1\,000\,000\cdot(0.01+0.2)=210\,000. ]

    И всего:

    [ C_{\text{seq}}=10000+210000=220000. ]

    Теперь на стоимость сильнее влияет CPU, чем число страниц.

    Но есть тонкость: PostgreSQL может переставлять допустимые условия и использовать короткое вычисление логических выражений. Не каждое условие обязательно вычисляется для каждой строки, поэтому это числовое сравнение показывает порядок влияния стоимости, а не гарантированную инструкционную последовательность для любого WHERE.

    9.7. Где здесь физическая реальность¶

    cost_seqscan предсказывает условную цену чтения всех страниц. Сам исполнитель получает их через буферный менеджер. Если страницы уже находятся в shared_buffers, физического чтения накопителя может не быть. Если их там нет, они могут оказаться в page cache ОС. Если отсутствуют и там — потребуется работа storage.

    Модель стоимости не отслеживает фактическое состояние каждой страницы при каждом запуске. Этим объясняется возможность одного и того же cost при разном Execution Time.

    При этом CPU-работа по проверке фильтра сохраняется даже при горячих данных, хотя детали видимости и выполнение могут быть оптимизированы.

    9.8. Инженерный вывод¶

    Если Seq Scan выбран для результата из пяти строк, нас интересуют две вещи:

    1. Какая альтернатива доступна для ограничения доступа к данным?
    2. Какие затраты планировщик приписывает этой альтернативе?

    Пока альтернативу не посчитали, фраза «сканирование всей таблицы — плохо» остается мнением. Следующий раздел даст численный ответ.

    Что важно запомнить после раздела 9¶

    1. cost_seqscan включает цену всех страниц таблицы и цену обработки всех просматриваемых строк.
    2. rows после фильтра влияет на выходные выражения, но не делает сам Seq Scan пропорционально дешевле.
    3. Цена сложного фильтра может доминировать над I/O.
    4. Одинаковый расчетный cost может соответствовать разному фактическому времени из-за кешей, ОС и конкуренции.
    5. Из исходников следует проверяемая формула: страничная часть + CPU по baserel->tuples + выходные выражения по path->rows.

    10. Математика Index Scan: стоимость индекса — только начало¶

    10.1. Простая модель ломается на обращениях к heap¶

    Вернемся к нашему SQL:

    SELECT id, amount, payload
FROM orders
WHERE amount BETWEEN 1000 AND 1999;

    По amount создан B-tree индекс. Кажется, теперь можно просто пройти по индексным записям нужного диапазона. Ведь из миллиона строк нам нужны лишь 10 000.

    Но индекс хранит ключи и ссылки на версии строк. Поле payload хранится в heap и в наш индекс не включено. Значит, индексная часть должна указать, где находятся нужные версии строк, а executor — получить их из heap.

    Схематично:

                B-tree
       [amount → TID]
               |
      10 000 подходящих TID
               |
        обращения к heap
               |
       проверка MVCC
               |
      формирование результата

    Цена складывается минимум из трех частей:

    [ C_{\text{Index Scan}} \approx C_{\text{index AM}} + C_{\text{heap I/O}} + C_{\text{heap CPU}} + C_{\text{other}}. ]

    Здесь index AM — метод доступа к индексу (index access method). Для B-tree у PostgreSQL есть собственная функция оценки стоимости. Другие индексные методы могут использовать другие оценщики.

    10.2. Что действительно делает cost_index()¶

    На уровне реализации PostgreSQL 18 cost_index() сначала обращается к amcostestimate конкретного индексного метода. Для B-tree используется оценщик btcostestimate() из selfuncs.c, который опирается на общую логику genericcostestimate() и дополнительные сведения о B-tree.

    Метод доступа возвращает несколько ключевых чисел:

    indexStartupCost
indexTotalCost
indexSelectivity
indexCorrelation
indexPages

    Смысл:

    • indexStartupCost — часть стоимости индексного поиска до начала выдачи результата;
    • indexTotalCost — стоимость работы индексного метода доступа, без стоимости чтения всех требуемых страниц heap;
    • indexSelectivity — доля строк таблицы, к которым придется обращаться из-за индексных ограничений;
    • indexCorrelation — насколько порядок ключей индекса связан с физическим порядком строк heap;
    • indexPages — оценка страниц индекса, затрагиваемых поиском.

    После этого cost_index() оценивает количество кандидатов и стоимость чтения основной таблицы. Это принципиальное разделение: B-tree оценивает свой участок работы, общая cost model — остальную часть.

    Ключевой сокращенный фрагмент логики:

    amcostestimate(root, path, loop_count,
               &indexStartupCost, &indexTotalCost,
               &indexSelectivity, &indexCorrelation,
               &index_pages);

startup_cost += indexStartupCost;
run_cost += indexTotalCost - indexStartupCost;

tuples_fetched = clamp_row_est(
    indexSelectivity * baserel->tuples);

// Далее вычисляются обращения к heap и стоимость CPU.

    Сразу видно отличие от Seq Scan: здесь не все строки таблицы обязаны стать кандидатами для чтения.

    10.3. Index Cond и Filter влияют на стоимость по-разному¶

    Возьмем запрос:

    SELECT id, amount, payload
FROM orders
WHERE amount BETWEEN 1000 AND 1999
  AND status = 'PAID';

    Пусть индекс есть только по amount.

    Возможный план:

    Index Scan using idx_orders_amount on orders
  Index Cond: ((amount >= 1000) AND (amount <= 1999))
  Filter: (status = 'PAID')

    Важная граница:

    • indexSelectivity относится к ограничениям, используемым индексным методом; она определяет число кандидатов на чтение heap;
    • фильтры, которые остаются после индексного поиска (qpquals), могут уменьшить итоговое path->rows, но не уменьшат объем чтения heap, уже вызванный индексными условиями.

    Предположим, индексное условие дает 10 000 кандидатов, а status = 'PAID' оставляет 100.

    Тогда выходной rows может равняться 100, но стоимость получения кандидатов из индекса и heap рассчитывается из числа 10 000.

    Поэтому запрос, возвращающий сто строк, может быть дорогим даже при правильной оценке его конечного rows.

    10.4. Сколько страниц heap затронут десять тысяч TID?¶

    Казалось бы, достаточно взять 10 000 TID = 10 000 страниц. Но это неверно: разные версии строк могут находиться на одной странице. Обратная крайность — ожидать ровно сто страниц, исходя из ста строк на страницу. Это предполагало бы идеальную физическую группировку.

    Нужна модель распределения ссылок по страницам.

    Для недостаточно коррелированного индексного доступа PostgreSQL использует приближение Mackert–Lohman, реализованное в index_pages_fetched().

    Обозначим:

    • T — число страниц heap;
    • n — число кандидатов (tuples_fetched);
    • b — рассчитанная эффективная доля кеша, доступная этому отношению.

    Сначала доля кеша приближенно распределяется по отношению к общему объему рассматриваемых данных:

    [ b\approx\left\lceil \frac{C_{\text{effective cache}}\cdot T} {T_{\text{relations}}+I_{\text{considered}}} \right\rceil. ]

    В коде используются root->total_table_pages и index_pages с защитой от нулевых значений. Здесь упрощено только обозначение.

    Если b >= T, используется ветка:

    [ \boxed{ F_{\text{uncorr}}(n,T)= \min\left(T,\left\lceil\frac{2Tn}{2T+n}\right\rceil\right). } ]

    Это не точное число различных страниц, найденное из фактических TID. Это приближение количества обращений, построенное на предположениях о распределении данных и кешировании.

    10.5. Ручной расчет Mackert–Lohman¶

    Возьмем данные нашей таблицы:

    [ T=10000,\qquad n=10000. ]

    Пусть кешевой бюджет достаточно велик, чтобы в используемой формуле выполнялось b >= T.

    Тогда:

    [ F_{\text{uncorr}}= \left\lceil\frac{2\cdot10000\cdot10000}{20000+10000}\right\rceil =\lceil6666.\overline{6}\rceil =6667. ]

    Получается примерно 6 667 обращений к страницам heap для 10 000 кандидатов.

    Если доступ к таким страницам оценивается как непоследовательный:

    [ C_{\text{heap I/O,max}} = 6667\cdot4=26668. ]

    Сравним с Seq Scan из предыдущего раздела:

    [ C_{\text{seq,total}}=22500. ]

    Индексный способ уже проигрывает по одной только стоимости heap I/O, до учета чтения самого B-tree и CPU на обработку строк.

    Вот почему даже при селективности 1% индекс может проигрывать последовательному сканированию. Важна локальность ссылок.

    10.6. А что, если кеша не хватает? Вторая ветка модели¶

    Для небольшого кешевого бюджета b < T в исходниках применяется кусочная формула.

    Введем границу:

    [ L=\frac{2Tb}{2T-b}. ]

    Тогда до этой границы используется прежнее выражение:

    [ F(n)=\left\lceil\frac{2Tn}{2T+n}\right\rceil, \qquad n\le L. ]

    После границы:

    [ \boxed{ F(n)=\left\lceil b+(n-L)\frac{T-b}{T}\right\rceil, \qquad n>L. } ]

    Смысл этой ветки: часть ранее прочитанных страниц уже могла быть вытеснена из эффективного кеша, поэтому будущие обращения могут потребовать повторных получений страниц.

    Разберем отдельно:

    [ T=10000,\quad b=2000,\quad n=10000. ]

    [ L=\frac{2\cdot10000\cdot2000}{20000-2000} =\frac{40000000}{18000}\approx2222.22. ]

    Поскольку n > L:

    [ F\approx\left\lceil2000+(10000-2222.22)\cdot0.8\right\rceil =\lceil8222.22\rceil=8223. ]

    Оценка выше, чем 6667 при большом кеше.

    Получается, снижение доступного кеша делает индексный путь менее привлекательным, хотя SQL, число подходящих строк и сам индекс не изменились.

    Ограничение: F отражает модель ожидаемой работы с буферами при выбранных допущениях. Нельзя автоматически приравнивать это число к показателю shared read или физическим чтениям SSD из реального EXPLAIN ANALYZE.

    10.7. Корреляция: почему один и тот же индекс бывает дешевым и дорогим¶

    Возьмем два физически разных состояния той же таблицы.

    Состояние A. Строки относительно amount лежат почти в случайном порядке.

    Состояние B. Таблица физически упорядочена примерно по amount.

    Оба индекса содержат те же ключи. Количество подходящих строк по-прежнему 10 000.

    Но в состоянии B соседние ключи B-tree обычно ссылаются на близкие страницы heap. По этой причине посещение heap дешевле в модели.

    Для предельной корреляции PostgreSQL оценивает число затронутых страниц приближенно как:

    [ F_{\text{corr}}=\left\lceil sT\right\rceil. ]

    При s = 0.01:

    [ F_{\text{corr}}=\lceil0.01\cdot10000\rceil=100. ]

    Если страниц больше нуля, стоимость рассчитывается как одно непоследовательное получение и последовательное чтение остальных:

    [ C_{\text{heap I/O,min}}= P_{\text{rand}}+(F_{\text{corr}}-1)P_{\text{seq}}. ]

    Подставим:

    [ C_{\text{heap I/O,min}}=4+(100-1)\cdot1=103. ]

    Мы получили два сценария для тех же десяти тысяч строк:

    Физическое распределение Расчет heap I/O
    Слабая корреляция, большой кеш 26 668
    Почти идеальная корреляция 103

    Разница более чем в 250 раз только для страничной части модели. Это не обещание такого ускорения реального запроса: CPU и обход индекса остаются, фактическое время зависит от кеширования и других расходов.

    10.8. Почему используется квадрат корреляции¶

    В PostgreSQL расчет между крайними случаями интерполируется по квадрату indexCorrelation:

    [ \boxed{ C_{\text{heap I/O}} = C_{\max}+r^2(C_{\min}-C_{\max}), } ]

    где r = indexCorrelation, обычно в диапазоне от -1 до +1.

    Пояснение:

    • если r=0, получаем стоимость некоррелированного случая;
    • если r=1 или r=-1, получаем хорошо упорядоченный случай;
    • если r=0.5, доля интерполяции равна 0.25, поскольку 0.5² = 0.25.

    При наших значениях:

    [ C_{\max}=26668,\qquad C_{\min}=103. ]

    Для r=0.5:

    [ C_{\text{heap I/O}}= 26668+0.25(103-26668) =20026.75. ]

    Для r=0.9:

    [ C_{\text{heap I/O}}= 26668+0.81(103-26668) =5150.35. ]

    Откуда взялся именно квадрат? В исходниках это эвристика с прямой пометкой авторов о ее условности. Это не математическая теорема о B-tree или MVCC. Но знак корреляции действительно не обязан менять ценность локального физического порядка: движение по страницам в прямом и обратном направлении может быть эффективно в обоих случаях.

    10.9. От стоимости heap до полного Index Scan¶

    Теперь добавим остальные компоненты.

    Для обычного непараллельного сканирования без дополнительных фильтров:

    [ C_{\text{index,total}} \approx C_{\text{index AM,total}} + C_{\text{heap I/O}} + N_{\text{candidates}}C_{\text{tuple}} + C_{\text{target}}. ]

    Если есть дополнительный Filter, к CPU по кандидатам добавляется стоимость его вычисления.

    Важно: это объясняющая запись. В cost_index() стоимость индексного метода уже разделена на его startup и run, а CPU-стоимость выходных выражений учитывается по выходным rows. Не следует прибавлять еще раз компоненты, уже включенные index AM.

    Для конкретного ручного примера нам нужно назначить стоимость B-tree. В самой реализации это делает btcostestimate(): он учитывает статистику индекса, индексные ограничения и другие особенности. Для преподавательского расчета зададим отдельное приближение, отличающееся от алгоритма PostgreSQL:

    [ C_{\text{index AM,toy}}= 4\left(3+\lceil 2000s\rceil\right) +Ns(0.005+0.0025). ]

    В нем:

    • 3 — условно три страницы пути спуска B-tree;
    • 2000s — условное число листовых страниц, читаемых при доле s;
    • Ns — условное число обработанных индексных записей;
    • стоимость каждой страницы индекса для простоты равна 4.

    Это не формула btcostestimate(). Мы используем ее лишь как публично оговоренную, воспроизводимую цену индексной части, чтобы сосредоточиться на точных формулах cost_index() для heap.

    При s=0.01, n=10000:

    [ C_{\text{index AM,toy}}= 4(3+20)+10000(0.0075)=92+75=167. ]

    CPU обработки heap-кандидатов:

    [ C_{\text{heap CPU}}=10000\cdot0.01=100. ]

    Итого:

    • при r=0: 167 + 26 668 + 100 = 26 935;
    • при r=1: 167 + 103 + 100 = 370.

    Сравним с Seq Scan = 22 500.

    Планировщик может обоснованно отвергнуть индексный доступ для слабокоррелированного случая и предпочесть его при хорошей физической локальности.

    50% 500 000 10 000 7 762.00 52 762 17 765 22 500

    Это сравнение расчетных учебных альтернатив, а не вывод исполняемого PostgreSQL. Здесь видно два свойства:

    1. При плохой локальности index+heap-путь становится дорогим раньше, чем можно ожидать, глядя только на селективность.
    2. При высокой корреляции тот же B-tree способен оставаться выгодным даже при относительно большой доле строк.

    Фактические пороги выбора между планами нельзя получить из универсального правила «индекс выгоден до X%». Они определяются значениями cost model, статистикой, физическим размещением и самим запросом.

    10.11. Что еще меняет стоимость Index Scan¶

    Повторные сканирования. В cost_index() параметр loop_count влияет на модель кеширования. Для повторяющегося чтения PostgreSQL может оценивать совместную нагрузку нескольких сканирований, а затем распределять стоимость на одно. Здесь мы не обсуждаем, откуда берутся такие повторения: их сценарии войдут в следующую лекцию про соединения.

    Index Only Scan. Когда нужные значения есть в индексе, PostgreSQL может уменьшить ожидаемые heap-обращения пропорционально оцененной доле all-visible страниц (allvisfrac). Но MVCC и visibility map определяют, удастся ли действительно обходиться без heap. Подробный механизм вынесен в отдельную лекцию 05.2 Executor Internals.

    Стоимость индексной части. Метод доступа может учитывать дополнительные условия, сложность ключей и особенности индекса. У разных AM расчет различается. Число уровней B-tree не является всей стоимостью индексного поиска.

    Дополнительный Filter. Если индекс выдал 100 000 кандидатов, а фильтр оставил сто, стоимость heap-обращений не становится равной стоимости чтения ста строк.

    Что важно запомнить после раздела 10¶

    1. Полный Index Scan платит за индекс и за heap, если требуемые строки нельзя получить только из индекса.
    2. indexSelectivity определяет объем кандидатов для heap, а path->rows может быть меньше из-за дополнительного фильтра.
    3. index_pages_fetched() оценивает обращения к страницам с поправкой на кеширование; это не точный счетчик реального I/O.
    4. Корреляция физического порядка строк с ключом индекса заметно меняет расчетную цену heap, а интерполяция использует r².
    5. Порог выгодности индекса зависит от доступных путей, распределения TID и стоимости страниц, а не от одной магической селективности.

    11. Математика Bitmap Scan: от случайных TID к сгруппированным страницам¶

    11.1. Проблема, которую обычный Index Scan оставил нерешенной¶

    Возьмем нашу таблицу с миллионом строк. Сканирование по индексу для s=1% дает 10 000 кандидатов. При слабой корреляции модель Index Scan предсказывает огромное количество непоследовательных обращений к heap.

    Вариант Seq Scan тоже не идеален: он вынужден читать всю таблицу.

    А теперь представим, что сначала мы соберем все подходящие TID, сгруппируем их по номеру страницы, а затем прочитаем heap в удобном порядке.

    Это идея Bitmap Heap Scan.

    Ожидаемый план:

    Bitmap Heap Scan on orders
  Recheck Cond: ((amount >= 1000) AND (amount <= 1999))
  -> Bitmap Index Scan on idx_orders_amount
       Index Cond: ((amount >= 1000) AND (amount <= 1999))

    Обратите внимание: Bitmap Index Scan формирует bitmap потенциально подходящих позиций, а Bitmap Heap Scan использует ее для получения строк. У двух частей разная стоимость.

    11.2. Что хранит bitmap в логической модели¶

    Представим набор кандидатов:

    TID (page=100, offset=7)
TID (page=500, offset=2)
TID (page=100, offset=12)
TID (page=20,  offset=3)

    После группировки:

    page 20  -> offset 3
page 100 -> offsets 7, 12
page 500 -> offset 2

    Теперь не нужно получать страницу 100 дважды только потому, что подходящие записи индекса обнаружены в разных позициях потока.

    Но есть цена:

    • сначала нужно найти все подходящие позиции и построить bitmap;
    • bitmap занимает память;
    • доступ по heap обычно теряет порядок ключа B-tree;
    • при нехватке памяти bitmap может стать lossy, увеличив число проверяемых кандидатов.

    Физические детали разберем отдельно в 05.2 Executor Internals. Здесь считаем стоимость.

    11.3. Из каких компонентов состоит cost_bitmap_heap_scan()¶

    Для обычного одиночного сканирования логика близка к следующей:

    [ C_{\text{bitmap,total}} \approx C_{\text{bitmap build}} + C_{\text{heap pages}} + C_{\text{candidate CPU}} + C_{\text{target}}. ]

    Внутри cost_bitmap_heap_scan():

    pages_fetched = compute_bitmap_pages(
    root, baserel, bitmapqual, loop_count,
    &indexTotalCost, &tuples_fetched);

startup_cost += indexTotalCost;

// Стоимость чтения heap зависит от pages_fetched / T.
run_cost += pages_fetched * cost_per_page;

// Стоимость проверки кандидатов.
cpu_per_tuple = cpu_tuple_cost + qpqual_cost.per_tuple;
run_cost += cpu_per_tuple * tuples_fetched;

    Это сокращенная схема, сохраняющая логику исходников. В настоящем коде присутствуют дополнительные ветви, в том числе для параллельного выполнения и стоимости целевого списка.

    Ключевой момент: получение bitmap включается в startup cost. Для выдачи первой строки обычно требуется завершить поиск индексных кандидатов и подготовить структуру.

    Отсюда компромисс с обычным Index Scan: bitmap способен уменьшить цену обращения к множеству страниц, но требует предварительной работы.

    11.4. Расчет стоимости построения bitmap¶

    compute_bitmap_pages() получает стоимость индексной части через cost_bitmap_tree_node().

    Для одного IndexPath упрощенно:

    [ C_{\text{bitmap build}} = C_{\text{index AM,total}} +0.1\cdot C_{\text{operator}}\cdot N_{\text{index rows}}. ]

    Последнее слагаемое — небольшая эвристическая плата за работу со структурой bitmap. Оно есть в исходниках, чтобы bitmap не выглядел совершенно бесплатным по сравнению с обычным индексным поиском.

    При N_index rows=10000:

    [ 0.1\cdot0.0025\cdot10000=2.5. ]

    Если использовать нашу условную стоимость индексной части 167, получаем:

    [ C_{\text{bitmap build}}=167+2.5=169.5. ]

    Важно: полное чтение диапазона из индекса — уже часть startup-работы bitmap. Нельзя сравнивать Index Scan и Bitmap Scan, считая построение bitmap нулевым по времени.

    11.5. Оценка количества страниц heap¶

    Для одного bitmap-сканирования PostgreSQL применяет следующую оценку:

    [ F_{\text{bitmap}}= \min\left(T,\left\lceil\frac{2Tn}{2T+n}\right\rceil\right). ]

    Фактически это та же форма Mackert–Lohman, соответствующая случаю без повторного чтения страницы в рамках одного обхода.

    При T=10000, n=10000:

    [ F_{\text{bitmap}}=6667. ]

    Но разве это не то же число, что мы получили для некоррелированного Index Scan?

    Число страниц совпало, а цена каждой страницы в bitmap-модели будет иной.

    11.6. Почему стоимость одной страницы у Bitmap Scan нелинейна¶

    Если bitmap указывает всего на две страницы из десяти тысяч, эти страницы придется получить разрозненно.

    А если он указывает практически на все десять тысяч, доступ становится похож на последовательное чтение большого диапазона heap.

    Поэтому в cost_bitmap_heap_scan() применяется интерполяция:

    [ \boxed{ P_{\text{bitmap page}}= P_{\text{rand}} -\left(P_{\text{rand}}-P_{\text{seq}}\right) \sqrt{\frac{F}{T}}, \qquad F\ge2. } ]

    Для F < 2 используется P_rand.

    Что происходит при разных долях страниц:

    Доля страниц F/T Расчет при P_rand=4, P_seq=1
    1% 4 - 3·√0.01 = 3.70
    25% 4 - 3·√0.25 = 2.50
    50% 4 - 3·√0.50 ≈ 1.88
    100% 4 - 3·√1 = 1.00

    Эта формула не утверждает, что накопитель физически ускоряется точно по квадратному корню. Это эвристика PostgreSQL для смешанного характера чтения страниц.

    11.7. Ручной расчет стоимости Bitmap Heap Scan¶

    Для нашего диапазона:

    [ F=6667,\qquad T=10000. ]

    Стоимость одной страницы:

    [ P_{\text{bitmap page}}= 4-3\sqrt{\frac{6667}{10000}} \approx1.55045. ]

    Стоимость heap I/O:

    [ C_{\text{heap I/O}}= 6667\cdot1.55045\approx10336.84. ]

    Теперь CPU.

    В cost_bitmap_heap_scan() PostgreSQL консервативно включает полную стоимость условий сканирования в qpqual_cost. Оценщик фактически допускает необходимость повторной проверки условий на всех кандидатах, хотя при точной bitmap и подходящем индексном методе фактический executor может избегать части проверок.

    Для учебного условия, стоимость которого принята равной одному cpu_operator_cost на кандидата:

    [ C_{\text{heap CPU}}=10000(0.01+0.0025)=125. ]

    Стоимость построения bitmap из предыдущего пункта:

    [ C_{\text{bitmap build}}=169.5. ]

    Сумма:

    [ \boxed{ C_{\text{bitmap,total}} \approx169.5+10336.84+125=10631.34. } ]

    Получается:

    Seq Scan            ≈ 22 500
Index Scan, r=0      ≈ 26 935
Bitmap Heap Scan    ≈ 10 631

    Это оценки по одной и той же учебной модели. Детали индексной части мы явно задали извне. В настоящем PostgreSQL btcostestimate() вычисляет их по своей логике.

    Почему bitmap оказался выгоднее? Он получил ту же ориентировочную группу страниц, но смог оценить их чтение значительно дешевле благодаря группировке TID по heap-страницам.

    11.8. Сравнение трех методов при разной селективности¶

    Для воспроизводимости оставляем все предположения из раздела 10:

    • N=1 000 000, T=10 000;
    • Seq Scan с одной условной проверкой WHERE на строку: 22 500;
    • некоррелированный обычный Index Scan (r=0);
    • индексная часть оценивается ранее оговоренной учебной, а не внутренней B-tree формулой;
    • для bitmap достаточная память, чтобы исключить расчетную потерю точности;
    • один проход, без параллельности;
    • стоимость формирования результата принята равной нулю.
    Селективность Строк-кандидатов Seq Scan Index Scan, r=0 Bitmap Heap Scan
    0.01% 100 22 500 418 ≈388
    0.1% 1 000 22 500 3 850 ≈2 970
    1% 10 000 22 500 26 935 ≈10 631
    10% 100 000 22 500 42 562 ≈12 837
    50% 500 000 22 500 52 762 ≈24 137

    Почему при 50% Seq Scan дешевле? Bitmap уже затрагивает практически все heap-страницы, но добавляет стоимость полного прохода по большой части индекса, построения bitmap и обработки кандидатов.

    Почему при 0.01% по общей стоимости в учебной таблице bitmap вышел чуть дешевле Index Scan? Наша формула действительно так считает: интерполяция дает небольшой выигрыш в heap I/O. Но startup cost bitmap существенно выше и не позволяет выдавать первую строку до завершения построения bitmap. Кроме того, реальная стоимость B-tree и эвристики отличаются от нашей схематичной цены. Следовательно, из таблицы нельзя делать вывод «Bitmap всегда лучше при редком условии». Это было бы ложное универсальное правило.

    11.9. work_mem, exact и lossy: стоимость ошибки памяти¶

    Bitmap — структура, живущая в памяти. Когда количество записей становится слишком большим, PostgreSQL может представить часть страниц менее точно, переходя к lossy bitmap.

    В compute_bitmap_pages() оценивается число доступных записей структуры:

    maxentries = tbm_calculate_entries(work_mem * 1024);

    Сравнивается расчетное число страниц heap_pages и доступная емкость maxentries.

    При нехватке памяти код использует грубую оценку:

    [ N_{\text{lossy pages}}\approx \max\left(0, F_{\text{heap}}-\frac{E_{\max}}{2}\right). ]

    Затем число кандидатов для обработки увеличивается с учетом доли страниц, ставших lossy. В этой части PostgreSQL моделирует вероятность того, что кандидатом станет строка, которая раньше могла быть исключена по точной bitmap.

    Это снова оценочная, а не точная модель числа реальных кандидатов.

    Инженерный эффект:

    Мало памяти для TIDBitmap
        ↓
Часть страниц представлена без точных offset
        ↓
Исполнитель проверяет дополнительные строки heap
        ↓
Больше CPU на recheck
        ↓
Bitmap Heap Scan может стать дороже ожидаемого

    Здесь не следует путать два термина: work_mem относится к разным рабочим операциям PostgreSQL, но TIDBitmap не использует тот же алгоритм перехода на диск, что external sort. У bitmap при дефиците памяти основная компенсация — потеря точности, а у сортировки — временные файлы. Это разные механизмы с разной ценой.

    11.10. Что происходит с порядком строк¶

    B-tree способен предоставлять значения в порядке ключей. Обычный Index Scan может сохранить этот порядок для последующего ORDER BY.

    Bitmap Heap Scan сортирует обращения по страницам heap, а не по amount. Поэтому его выход обычно не удовлетворяет требуемому порядку ключа индекса.

    Следствие для:

    SELECT id, amount, payload
FROM orders
WHERE amount BETWEEN 1000 AND 1999
ORDER BY amount;

    Планировщик должен сравнить не только стоимость получения подходящих строк:

    Index Scan (готовый порядок)

vs

Bitmap Heap Scan + Sort

vs

Seq Scan + Sort

    Может оказаться, что Index Scan дороже на этапе чтения, но дешевле по всему плану, поскольку исключает последующую сортировку.

    Теперь становится понятно, зачем в cost model появляется следующий блок.

    Что важно запомнить после раздела 11¶

    1. Bitmap Index Scan создает структуру ссылок; Bitmap Heap Scan читает строки по этим ссылкам.
    2. Построение bitmap входит в startup-стоимость; группировка TID может снижать цену heap-доступа.
    3. Стоимость страницы bitmap-модель интерполирует через sqrt(F/T) между random_page_cost и seq_page_cost.
    4. При дефиците памяти bitmap может стать lossy, что увеличивает объем повторных проверок.
    5. Bitmap помогает на множестве кандидатов, но теряет готовый порядок B-tree и может потребовать Sort.

    12. Математика Sort: почему порядок строк может стоить дороже поиска¶

    12.1. Мы нашли подходящие строки. Теперь нужно их упорядочить¶

    Добавим к нашему запросу сортировку:

    SELECT id, amount, payload
FROM orders
WHERE amount >= 90000
ORDER BY amount;

    Для продолжения математической модели предположим, что условию соответствует 10% таблицы, то есть 100 000 строк.

    Seq Scan отдаст строки в порядке их физического расположения в heap. Этот порядок обычно не удовлетворяет ORDER BY amount.

    Bitmap Heap Scan отдаст строки в порядке обхода heap-страниц, а не в порядке ключей B-tree.

    Index Scan по B-tree amount способен отдавать строки в нужном порядке. Но при плохой корреляции он дорого получает строки из heap.

    Следовательно, возникло новое сравнение:

    Вариант A:  Index Scan                  → порядок уже подходит
Вариант B:  Seq Scan + Sort             → сортируем после сканирования
Вариант C:  Bitmap Heap Scan + Sort     → сортируем после bitmap

    На этом уровне важно различать стоимость чтения и стоимость получения нужного порядка.

    12.2. cost_sort() и cost_tuplesort() отвечают за разные части¶

    В исходниках PostgreSQL 18 обычный расчет Sort разделен на два слоя:

    • cost_tuplesort() оценивает саму сортировку, без стоимости получения входных строк;
    • cost_sort() вызывает cost_tuplesort(), затем прибавляет полную стоимость входного пути.

    Сокращенный фрагмент:

    cost_tuplesort(&startup_cost, &run_cost,
               tuples, width,
               comparison_cost, sort_mem,
               limit_tuples);

startup_cost += input_cost;

path->startup_cost = startup_cost;
path->total_cost = startup_cost + run_cost;

    Здесь input_cost — стоимость получения всех входных строк. Поэтому у обычной полной сортировки startup_cost может включать и полное чтение таблицы, и работу сортировки.

    Важный вывод: Sort — типичный блокирующий узел. До первой отсортированной строки ему обычно нужно получить весь необходимый вход. При LIMIT возможна ограниченная сортировка (bounded sort), но необходимость прочитать входные строки без подходящего индекса часто сохраняется.

    12.3. Зачем cost_tuplesort() нужны и rows, и width¶

    Входные параметры:

    • tuples — количество сортируемых строк N;
    • width — оцененная средняя ширина выходной строки в байтах;
    • sort_mem — доступная сортировке рабочая память в килобайтах;
    • limit_tuples — требуемое число первых результатов, если есть подходящее ограничение;
    • comparison_cost — дополнительная цена сравнения сверх базовой модели.

    Кажется, width нужен лишь для статистики. Но это не так.

    Пусть сортируются 100 000 строк:

    100 000 строк по 32 байта
100 000 строк по 512 байт

    Число сравнений для полного сортирования может быть одного порядка. Но затраты памяти различаются многократно. Вторая сортировка с большей вероятностью выйдет за work_mem и перейдет к работе с временными файлами.

    PostgreSQL использует приблизительную функцию relation_byte_size():

    [ B_{\text{input}}=N\cdot \left(\operatorname{MAXALIGN}(width)+ \operatorname{MAXALIGN}(\operatorname{SizeofHeapTupleHeader})\right). ]

    Здесь MAXALIGN — округление до нужного для платформы выравнивания, а заголовок отражает оценочный служебный расход на кортеж.

    Поэтому width=64 и 100 000 строк в стандартной 64-битной конфигурации дают для этой конкретной оценки приблизительно:

    [ B_{\text{input}} =100000(64+24)=8\,800\,000 \text{байт} \approx8.39 \text{МиБ}. ]

    Это оценка, используемая cost model. Она не обязана совпадать с фактическим пиковым RSS узла сортировки и не является измерением размера строк в heap.

    12.4. Полная сортировка в памяти: N log₂ N¶

    Когда расчетный объем помещается в доступную рабочую память, cost_tuplesort() для полной сортировки исходит из приближенно N·log₂N сравнений.

    Стоимость одного сравнения по умолчанию принимается равной:

    [ C_{\text{compare}}= C_{\text{extra compare}} + 2C_{\text{operator}}. ]

    При C_extra compare = 0:

    [ C_{\text{compare}}=2\cdot0.0025=0.005. ]

    Тогда:

    [ \boxed{ C_{\text{sort CPU}}\approx 0.005\cdot N\log_2N. } ]

    Для N=100000:

    [ \log_2 100000\approx16.60964. ]

    [ C_{\text{sort CPU}} \approx0.005\cdot100000\cdot16.60964 =8304.82. ]

    Кроме того, cost_tuplesort() начисляет небольшую стоимость извлечения строк из результата сортировки:

    [ C_{\text{sort output}}=N\cdot C_{\text{operator}} =100000\cdot0.0025=250. ]

    Итого собственная цена полного сортирования в памяти:

    [ C_{\text{sort, RAM}}\approx8304.82+250=8554.82. ]

    Если входной Seq Scan стоил 22 500, получаем:

    [ \boxed{ C_{\text{Seq + Sort,RAM}} \approx22500+8554.82=31054.82. } ]

    При этом startup cost обычной сортировки близок к:

    [ 22500+8304.82=30804.82, ]

    а ее total cost включает и дополнительную плату за извлечение всех выходных строк.

    12.5. Почему work_mem способен изменить оценку¶

    Сначала пусть:

    work_mem = 16 MiB

    Наши расчетные 8.39 MiB помещаются в бюджет. Поэтому для полной сортировки используется модель работы в RAM.

    Теперь установим в мысленном эксперименте:

    work_mem = 4 MiB

    Расчетный объем данных превышает доступную память:

    [ 8.39 \text{МиБ}>4 \text{МиБ}. ]

    PostgreSQL рассматривает внешнюю сортировку с временными файлами.

    Подчеркнем границу: реальное поведение tuplesort зависит от размеров кортежей, служебных структур, ключей, управления памятью и версии PostgreSQL. cost_tuplesort() выбирает ветку своей модели по приближенным размерам.

    12.6. Внешняя сортировка: почему появляются runs и merge passes¶

    Если весь набор не помещается в память, его можно сортировать частями.

    Общая схема:

    Поток N строк
      |
Формируем отсортированные части (runs)
      |
Записываем части во временные файлы
      |
Сливаем несколько частей за проход
      |
Получаем общий отсортированный поток

    Run — отсортированная последовательность, полученная как промежуточный результат. Merge pass — проход слияния таких последовательностей.

    В реальном PostgreSQL детали tuplesort сложнее: используются специализированные структуры и адаптация к ресурсам. Для оценки стоимости планировщик применяет приближение.

    Сначала число страниц расчетного объема:

    [ P_{\text{sort}}= \left\lceil\frac{B_{\text{input}}}{\text{BLCKSZ}}\right\rceil. ]

    При B_input=8 800 000 и странице 8192 байта:

    [ P_{\text{sort}}= \left\lceil\frac{8800000}{8192}\right\rceil =1075. ]

    Оценка числа исходных отсортированных последовательностей:

    [ R\approx\frac{B_{\text{input}}}{B_{\text{work_mem}}} =\frac{8800000}{4\cdot1024\cdot1024} \approx2.10. ]

    Далее планировщик оценивает порядок слияния M (merge order), зависящий от доступной памяти и внутренних ограничений. Число проходов приближенно:

    [ P_{\text{merge passes}} =\max\left(1,\left\lceil\log_M R\right\rceil\right). ]

    Для нашего малого числа исходных последовательностей допустимо принять P_merge passes = 1.

    12.7. Цена временного I/O¶

    В исходниках используется приближение объема временного I/O:

    [ N_{\text{page accesses}} =2\cdot P_{\text{sort}}\cdot P_{\text{merge passes}}. ]

    Множитель 2 моделирует запись и последующее чтение промежуточных данных на проход слияния.

    PostgreSQL условно считает, что 75% обращений последовательные, а 25% — непоследовательные:

    [ C_{\text{temp/page}}= 0.75P_{\text{seq}}+0.25P_{\text{rand}}. ]

    При стандартных параметрах:

    [ C_{\text{temp/page}}=0.75\cdot1+0.25\cdot4=1.75. ]

    Для 1075 страниц и одного прохода:

    [ N_{\text{page accesses}}=2\cdot1075=2150. ]

    Итого:

    [ C_{\text{temp I/O}}=2150\cdot1.75=3762.5. ]

    При этом сама сортировка все еще требует расчетных сравнений:

    [ C_{\text{sort CPU}}\approx8304.82. ]

    Значит, собственная цена внешней сортировки:

    [ C_{\text{sort,external}} \approx8304.82+3762.5+250 =12317.32. ]

    Добавим входной путь:

    [ \boxed{ C_{\text{Seq + Sort,external}} \approx22500+12317.32=34817.32. } ]

    Сравним:

    work_mem Оцененный путь сортировки Цена Seq Scan + Sort
    16 MiB В памяти ≈31 054.82
    4 MiB С временным I/O ≈34 817.32

    Здесь экономия памяти породила дополнительную стоимость ввода-вывода.

    Однако глобальное увеличение work_mem имеет цену: оно распространяется на разные рабочие операции и конкурирующие запросы. Само по себе увеличение лимита под одну сортировку может повысить риск перерасхода RAM в production.

    12.8. Что меняет LIMIT: bounded heap-sort¶

    Снова рассмотрим:

    SELECT id, amount, payload
FROM orders
WHERE amount >= 90000
ORDER BY amount DESC
LIMIT 10;

    Нужно выдать только десять строк в заданном порядке.

    Сортировка может поддерживать ограниченный набор лучших кандидатов в куче. Для K=10 элементов порядок вычислительной сложности становится примерно:

    [ O(N\log K) ]

    вместо:

    [ O(N\log N). ]

    Иными словами, не обязательно хранить и сортировать все сто тысяч строк целиком.

    В PostgreSQL 18 cost_tuplesort() для bounded-сценария использует следующую оценку сравнений:

    [ \boxed{ C_{\text{topN,start}}\approx C_{\text{compare}}\cdot N\log_2(2K). } ]

    Множитель 2K — особенность эвристики cost model для сглаживания перехода между обычной и ограниченной сортировкой. Это не математическое требование алгоритма кучи.

    Подставим N=100000, K=10:

    [ C_{\text{topN,start}} \approx0.005\cdot100000\cdot\log_2 20 \approx2160.96. ]

    Это значительно меньше 8304.82 для полной сортировки по всем строкам.

    Но здесь ловушка: чтобы найти действительно лучшие десять строк, сортировка при отсутствии подходящего готового порядка должна рассмотреть все входные строки.

    Значит, стоимость чтения таблицы 22 500 остается существенной. LIMIT 10 уменьшает часть CPU и памяти, но не превращает полный Seq Scan в чтение десяти строк.

    Условия, при которых планировщик выбирает bounded sort, определяются сравнением расчетного объема вывода с рабочей памятью и относительным размером ограничения. LIMIT не всегда означает именно top-N heapsort: это один из возможных алгоритмов.

    12.9. Индексное чтение в готовом порядке против Seq Scan + Sort¶

    Теперь вернемся к примеру с селективностью s=10%.

    Из таблицы раздела 10:

    Index Scan при r=0:  42 562
Index Scan при r=1:   3 565

    Мы также посчитали:

    Seq Scan + Sort в RAM: 31 054.82

    Для некоррелированного индекса:

    [ 42562>31054.82. ]

    Таблицу выгоднее последовательно просканировать и отдельно отсортировать, чем получать строки в правильном порядке путем дорогих обращений к heap.

    При почти идеальной корреляции:

    [ 3565<31054.82. ]

    Индексное чтение в готовом порядке выглядит намного дешевле.

    Добавим Bitmap Heap Scan + Sort при достаточном work_mem:

    [ C_{\text{Bitmap + Sort}} \approx12837+8554.82=21391.82. ]

    Получаем четыре расчетные альтернативы для одного запроса, зависящие от физического порядка:

    Путь Расчетная стоимость в нашей модели
    Index Scan, корреляция 0 42 562
    Seq Scan + Sort 31 054.82
    Bitmap Heap Scan + Sort 21 391.82
    Index Scan, корреляция 1 3 565

    Разумеется, оба значения корреляции описывают два разных физических состояния данных, поэтому их нельзя одновременно считать альтернативными затратами одного и того же снимка таблицы. Остальные строки таблицы помогают увидеть границу выбора способа выполнения.

    А теперь вопрос, который закрывает весь блок: почему наличие индекса по ORDER BY не заставляет PostgreSQL выбирать Index Scan?

    Потому что сохранение порядка — лишь одно полезное свойство пути. Планировщик сравнивает полную стоимость выполнения, включая получение строк и альтернативную сортировку.

    12.10. Важное упрощение в исходниках: cost_sort не знает всего¶

    В реализации cost_sort() передаются pathkeys — сведения о требуемом порядке. Но код оценки обычной сортировки не моделирует детально каждый вариант сравнения каждого ключа.

    Он использует среднюю условную стоимость сравнения, число строк, ширину и доступную память.

    А реальный исполнитель может сортировать:

    • маленькие целые числа;
    • длинные строки с коллацией;
    • составные ключи из нескольких полей;
    • выражения, требующие вычислений и чтения дополнительных данных.

    Два набора по 100 000 строк одинаковой ширины способны иметь разную фактическую цену сравнения.

    Это одна из причин, почему точные rows и width еще не обеспечивают точного прогноза времени.

    12.11. Стоимость ширины строки и TOAST¶

    Широкие значения влияют на оценку памяти сортировки. Но в PostgreSQL есть механизм TOAST — хранение некоторых крупных значений в сжатом виде или вне основной строки.

    Поэтому width в EXPLAIN не всегда соответствует объему данных, который исполнитель физически читает и разворачивает в каждом случае.

    Пример:

    SELECT id, payload
FROM orders
ORDER BY amount;

    И:

    SELECT id
FROM orders
ORDER BY amount;

    Эти запросы могут иметь разные расчетные ширины и разную стоимость хранения строк при сортировке. Но важно также понимать, какие значения реально хранятся в промежуточных структурах и когда происходит получение TOAST-данных.

    Детальный разбор поведения executor, TOAST и фактической памяти tuplesort относится к следующему техническому слою.

    12.12. Что будет под нагрузкой¶

    Предположим, одна сортировка потребляет до 64 МиБ рабочей памяти. Несколько конкурирующих запросов могут одновременно выполнять несколько сортировок.

    work_mem применяется к соответствующим рабочим операциям, а не как единый жесткий лимит потребления памяти всей транзакции или всего сервера.

    С одной стороны, слишком маленькая память увеличивает вероятность временного I/O. С другой — слишком большой лимит увеличивает суммарное потребление RAM при конкурентной работе.

    В плане это может проявляться как:

    Sort Method: quicksort  Memory: ...

    или:

    Sort Method: external merge  Disk: ...
Buffers: temp read=... written=...

    Здесь Sort Method и Buffers при EXPLAIN ANALYZE отражают фактическое выполнение. А cost_sort заранее оценивал возможные затраты по приближенной статистике и настройкам.

    Стратегия диагностики:

    Ожидаемые rows и width
          ↓
Предсказанный объем сортировки
          ↓
Сопоставление с work_mem
          ↓
План: in-memory или external cost
          ↓
Фактический Sort Method и temp blocks
          ↓
Почему оценка совпала или разошлась с реальностью

    Если большой Sort ожидаем, имеет смысл сначала определить возможность получить результат в нужном порядке через другой путь и оценить цену этого пути. Само увеличение work_mem не всегда оптимальное решение.

    Что важно запомнить после раздела 12¶

    1. cost_sort учитывает стоимость чтения входа, cost_tuplesort оценивает собственную стоимость сортировки.
    2. Полная сортировка в памяти моделируется как N log₂N сравнений; bounded top-N — приблизительно как N log₂K.
    3. rows задает число элементов, а width и work_mem влияют на оценку перехода к временному I/O.
    4. При внешней сортировке модель добавляет временные чтения и записи, используя эвристическое смешение последовательной и непоследовательной стоимости страниц.
    5. Индекс по ключу сортировки может избавить от Sort, но при слабой локальности heap стоимость такого чтения иногда выше Seq Scan + Sort.
    6. LIMIT способен уменьшить затраты на сортировку без устранения затрат на чтение входного набора.

    13. Как планировщик выбирает оптимальный Path¶

    13.1. Продолжим с места, где остановилась cost model¶

    Для объяснения выбора Path возьмем отдельную учебную конфигурацию таблицы orders. Здесь изменятся физический размер и расчетные стоимости: сравнения ниже относятся только к этому примеру и не должны механически сопоставляться с числами разделов 9–12.

    Характеристики:

    • 1 000 000 строк;
    • 20 000 страниц heap;
    • средняя выходная строка в рассматриваемом запросе — около 96 байт;
    • существуют B-tree индексы по customer_id и created_at;
    • статистика показывает, что условие customer_id = 42 возвращает приблизительно 10 000 строк.

    Запрос:

    SELECT id, customer_id, created_at, amount
FROM orders
WHERE customer_id = 42;

    В первых двух блоках мы научились раскладывать эту задачу на две части:

    1. Cardinality estimation: сколько строк будет получено? Примерно 10 000.
    2. Cost model: сколько стоят допустимые способы получить эти строки? Это уже оценка стоимости чтения таблицы, индекса, heap, обработки условий и вспомогательных структур.

    Предположим, получили три иллюстративных, а не снятых с реального сервера, набора оценок:

    Альтернатива Startup cost Total cost Ожидаемые выходные строки
    Seq Scan 0 32 500 10 000
    Index Scan 0.43 1 830 10 000
    Bitmap Heap Scan 225 1 650 10 000

    Казалось бы, все ясно: выберем Bitmap Heap Scan, поскольку его total_cost = 1650 меньше остальных.

    Для данного запроса без ORDER BY и LIMIT, при прочих равных, это может оказаться правильным выбором.

    Но теперь добавим:

    ORDER BY created_at DESC
LIMIT 10;

    Что изменилось? Само условие customer_id = 42 не изменилось. Статистика для него тоже. Однако требуемый результат теперь должен быть упорядоченным, причем нам нужны всего десять первых строк.

    Значит, планировщику нужно оценивать больше свойств, чем одно число total_cost.

    Именно поэтому PostgreSQL сравнивает не готовые текстовые деревья EXPLAIN, а специальные объекты Path.

    13.2. Path: описание способа выполнения до появления итогового дерева¶

    Внутреннее понятие Path — кандидат на выполнение некоторой части запроса. Это облегченная структура, в которой содержится информация, необходимая для принятия решения планировщиком.

    Для нашей темы важны:

    • Тип способа доступа — последовательное сканирование, индексное, bitmap, сортировка и т. д.;
    • Ожидаемые строки (rows) — сколько результата дает кандидат;
    • startup_cost — затраты до появления первой выходной строки;
    • total_cost — затраты, если кандидат выполняется до конца;
    • pathkeys — какие гарантии порядка выходных строк дает кандидат;
    • pathtarget — какие выражения/колонки формируются;
    • Сведения о возможности параллельного выполнения и другие свойства, влияющие на допустимость и сравнение альтернатив.

    Во внутреннем коде PostgreSQL 18 есть структуры Path, IndexPath, BitmapHeapPath, SortPath, LimitPath. Для обычного Seq Scan используется базовый Path с типом узла T_SeqScan; отдельная специальная структура для него не требуется.

    Концептуально:

    SQL-запрос
    |
    v
Оценка количества строк
    |
    v
Создание кандидатов Path
    |
    +-- Path (pathtype=T_SeqScan)
    +-- IndexPath
    +-- BitmapHeapPath
    +-- ...
    |
    v
Оценка и сравнение
    |
    v
Выбранный Path
    |
    v
create_plan(...)
    |
    v
Дерево Plan -> executor

    Это учебная схема. Реальная последовательность включает дополнительные стадии, преобразования запроса, формирование верхних отношений, добавление путей для сортировки и ограничения результата.

    Разница между Path и Plan фундаментальна:

    • Path — гипотеза планировщика о способе выполнения со стоимостью и свойствами;
    • Plan — выбранная структура узлов, которую будет исполнять executor.

    PostgreSQL не обязан построить и исполнить все возможные Plan, чтобы выбрать лучший. Он сравнивает стоимость и свойства кандидатов до выполнения запроса.

    Уровень гарантии: SQL и EXPLAIN — пользовательские интерфейсы PostgreSQL. Названия структур Path, RelOptInfo, PathKey, алгоритм add_path — детали реализации PostgreSQL 18. Они не являются гарантиями SQL-стандарта.

    13.3. RelOptInfo: где планировщик хранит альтернативы¶

    Планировщику нужно где-то сохранять кандидатов. Для одной таблицы используется внутренняя структура RelOptInfo, которая содержит в том числе список рассматриваемых путей pathlist и информацию об оценках отношения.

    Концептуально:

    RelOptInfo: orders
  rows: 10 000              <- после условий WHERE
  pathlist:
    Path (T_SeqScan)        cost=0..32500, pathkeys=[]
    IndexPath               cost=0.43..1830, pathkeys=[...]
    BitmapHeapPath          cost=225..1650, pathkeys=[]

    В данном наброске IndexPath может относиться к индексу по customer_id и потому не обязан обеспечивать ORDER BY created_at. Если планировщик рассматривает индекс по created_at, появится другой кандидат с иным порядком и условиями фильтрации.

    Почему нельзя сразу оставить только кандидата с минимальным total_cost?

    Представим два пути, возвращающих одни и те же строки:

    Path Startup Total
    A 0.5 3 000
    B 200 1 500

    Если требуется весь результат, B дешевле.

    Если требуется несколько первых строк, A может быть намного выгоднее.

    Следовательно, оба пути могут оказаться полезными. Раннее удаление A было бы ошибкой.

    13.4. add_path: почему планировщик не хранит бесконечное число вариантов¶

    А теперь другая крайность.

    Допустим, на одной таблице десять индексов, несколько подходящих условий, разные варианты сортировки и дополнительные свойства путей. Если сохранять любой кандидат, расход времени и памяти на планирование будет расти.

    Поэтому при добавлении очередного пути PostgreSQL пытается отбросить явно проигрывающие альтернативы.

    Ключевая функция реализации — add_path() в src/backend/optimizer/util/pathnode.c.

    Ее удобно понимать как поиск недоминируемых кандидатов.

    Путь B доминирует путь A, если при сопоставимых допустимых свойствах B не хуже A по важным измерениям и лучше хотя бы по одному из них.

    В реальной реализации анализируются не только startup и total, но и порядок строк, число строк в некоторых случаях, параметры/зависимости пути, пригодность к параллельному исполнению и специальные приоритеты отключенных типов узлов.

    Для учебного случая с одинаковыми выходными строками, порядком и прочими свойствами можно начать с двух чисел:

    [ C_{s,B} \le C_{s,A}, \qquad C_{t,B} \le C_{t,A}. ]

    Если оба неравенства выполняются, A обычно нет смысла сохранять: B стартует не дороже и полностью выполняется не дороже.

    Пример:

    Path Startup Total Вывод
    A 15 1 500 Проигрывает B
    B 10 1 300 Доминирует A

    Однако:

    Path Startup Total Вывод
    C 1 2 000 Очень дешевый старт
    D 100 1 000 Дешевое полное выполнение

    Ни один путь не доминирует другой по обоим показателям.

    Здесь возникает знакомая из оптимизации идея границы Парето: сохраняем варианты, каждый из которых может выиграть при определенной цели.

    Это только модель для понимания. PostgreSQL использует конкретные правила сравнения, допуски к близким оценкам (fuzz factor) и дополнительные ограничения. Для PostgreSQL 18 важно также поле disabled_nodes: при сравнении путей меньшее количество отключенных узлов имеет приоритет над числовыми значениями startup/total cost. Этим объясняется, почему enable_seqscan = off теперь не следует представлять как простое прибавление огромной константы к cost — эта старая модель была изменена. Поведение подтверждается compare_path_costs() в pathnode.c и комментариями в costsize.c. Такие настройки в обычном режиме не являются простым математическим «бесконечным cost».

    Почему нельзя оставить все «почти одинаковые» пути¶

    Планировщик должен сам завершить работу за приемлемое время.

    Если в списке хранятся тысячи кандидатов, каждый новый путь придется сравнивать со многими существующими. Дополнительная работа планировщика становится самостоятельным ограниченным ресурсом.

    Поэтому PostgreSQL отбрасывает часть вариантов до появления окончательного плана. Это осознанный компромисс между качеством поиска и стоимостью самого планирования.

    13.5. pathkeys: почему порядок строк — часть стоимости решения¶

    Теперь вернемся к:

    SELECT id, created_at, amount
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC;

    Результат должен быть отсортирован по created_at DESC.

    Есть минимум два принципиальных подхода:

    1. Получить строки любым относительно дешевым способом и затем выполнить Sort.
    2. Получить строки сразу в требуемом порядке, если подходящий индекс это позволяет.

    Например, при наличии подходящего B-tree индекса с нужными ведущими ключами PostgreSQL может получить требуемый порядок непосредственно из Index Scan.

    Внутренние pathkeys кодируют гарантию упорядоченности выходного потока. Их важно воспринимать как свойство результата пути, а не как указатель на конкретный индекс.

    Path A:
  cost:     100..1200
  pathkeys: []
  результат: порядок не гарантирован

Path B:
  cost:     0.4..1800
  pathkeys: [created_at DESC]
  результат: уже отсортирован

    Если запросу требуется порядок по created_at DESC, путь B может избавить нас от отдельного Sort.

    Хотя его полный индексный доступ дороже (1800 > 1200), окончательный план нужно сравнивать так:

    [ C(A + \text{Sort}) \quad \text{против} \quad C(B). ]

    Если сортировка стоит еще условные 900 единиц, получаем:

    [ 1200 + 900 = 2100 > 1800. ]

    Тогда B выгоднее.

    Но если сортировка стоит всего 100 единиц:

    [ 1200 + 100 = 1300 < 1800, ]

    путь A с последующей сортировкой дешевле.

    Здесь суммы используются для учебной иллюстрации добавочной работы сортировки; в реальном PostgreSQL cost_sort формирует стоимость верхнего пути с учетом входного пути, и слепо суммировать total_cost двух уже посчитанных родительских узлов нельзя.

    Что именно учитывает порядок¶

    Семантика порядка включает не только имя столбца:

    • направление: ASC или DESC;
    • порядок NULLS FIRST / NULLS LAST;
    • применимые правила сравнения значений и collation;
    • последовательность ключей при сортировке по нескольким выражениям.

    Поэтому индекс (a, b) не способен безусловно удовлетворить любой ORDER BY с этими двумя столбцами.

    Например, обычный индекс (a ASC, b ASC) обеспечивает совместимый порядок a ASC, b ASC при прямом обходе и a DESC, b DESC при обратном. Для ORDER BY a ASC, b DESC обычно нужен специально сформированный порядок ключей либо дополнительная сортировка.

    Отдельная тонкость: планировщик использует классы эквивалентности выражений (EquivalenceClass) и связанные с ними PathKey, так что логически эквивалентные выражения могут разделять свойства порядка. Это уже внутренняя модель PostgreSQL, а не буквальное текстовое сравнение ORDER BY с определением индекса.

    13.6. Частично отсортированный поток и Incremental Sort¶

    Предположим, нужен порядок:

    ORDER BY customer_id, created_at DESC

    А доступный индекс гарантирует только:

    customer_id ASC

    Может ли PostgreSQL использовать это знание?

    Да. Если входные строки уже разбиты на группы с одинаковым customer_id в правильном порядке, можно сортировать created_at DESC внутри каждой группы, а не обязательно сортировать весь результат как один массив.

    Для этого предусмотрен Incremental Sort.

    Схематично:

    Incremental Sort
  Sort Key: customer_id, created_at DESC
  Presorted Key: customer_id
  -> Index Scan ...

    Последовательность:

    1. Вход дает строки, упорядоченные по customer_id.
    2. Executor получает группу строк с одинаковым customer_id.
    3. Сортирует группу по оставшимся ключам.
    4. Отдает готовую группу и переходит к следующей.

    По сравнению с обычной полной сортировкой это может уменьшить потребление памяти и время до первых строк.

    Но если одна группа огромна, ее сортировка все равно может быть дорогой. Кроме того, появляются затраты на обнаружение границ групп и работу с несколькими порциями.

    Инженерный вывод: при ORDER BY планировщик выбирает еще и свойства промежуточного потока. Наличие «более дешевого чтения» недостаточно для определения самого дешевого плана целиком.

    13.7. Когда Bitmap Scan проигрывает несмотря на дешевую стоимость чтения¶

    Предположим, условие селективно на несколько процентов и Bitmap Heap Scan имеет total_cost=1600, тогда как Index Scan — total_cost=2200.

    Для простого WHERE bitmap может быть привлекательнее.

    Но bitmap организует посещение heap по страницам, фактически теряя порядок индексных ключей. Если требуется ORDER BY по индексируемому столбцу, Bitmap Heap Scan обычно нуждается в последующей сортировке.

    Индексный путь может выдавать строки в требуемом порядке сразу.

    Bitmap Heap Scan (1600)
     + Sort (дополнительная работа)

против

Index Scan (2200, нужный порядок уже есть)

    Разница особенно заметна при LIMIT, когда индекс способен прекратить поиск очень рано. Этот механизм подробно разберем в разделе 14.

    13.8. Какие варианты вообще попадают на рассмотрение¶

    Планировщик сравнивает доступные способы выполнения, а не любые вообразимые алгоритмы.

    Например:

    • Для B-tree индекса, пригодного для условия поиска, могут строиться соответствующие IndexPath.
    • Несколько индексов могут участвовать в bitmap-альтернативах.
    • При отсутствии нужного индекса подходящего индексного пути может вообще не быть.
    • Для определенных запросов возможен Index Only Scan, но его стоимость зависит в том числе от ожидаемых обращений к heap для проверки видимости.
    • Возможность параллельного доступа зависит от узла, размера отношения, настроек и других ограничений.

    Нельзя сказать: «PostgreSQL сравнил Seq Scan и индексный план, решил, что Seq Scan быстрее», если индексного плана с требуемой семантикой вообще не существовало.

    Сначала проверяем допустимость альтернативы. Потом сравниваем стоимость.

    13.9. set_cheapest и заключительный выбор¶

    На определенных стадиях PostgreSQL выделяет среди сохранившихся путей наиболее выгодные варианты, в том числе по полной стоимости. Одна из функций реализации — set_cheapest().

    Но итоговый путь верхнего уровня может учитывать и требование получить лишь часть строк. Для такого выбора в planner.c используется get_cheapest_fractional_path().

    После выбора лучшего верхнего Path вызывается create_plan(), который создает дерево исполнительных узлов.

    Промежуточный смысл:

    pathlist после add_path
       |
       +-- дешево выдать первую строку
       +-- дешево выдать все строки
       +-- заранее отсортированный поток
       +-- другие полезные свойства
       |
       v
Учет требований запроса
       |
       v
Выбранный итоговый Path
       |
       v
create_plan

    Важно: «оптимальный Path» означает оптимальный по расчетной модели среди рассмотренных и сохранившихся кандидатов. Это еще не доказательство его фактической минимальной задержки.

    13.10. Почему планировщик не обязан найти глобально лучший реальный план¶

    Есть три независимые причины.

    Первая — прогнозы приближенные. Мы не знаем точного числа будущих строк и реальной стоимости работы с ними.

    Вторая — альтернативы ограничены. Не любой мыслимый вариант исполнения доступен, а число кандидатов приходится контролировать ради скорости планирования.

    Третья — цель формализована через модель стоимости. Реальные задержки зависят от условий, которых этот скалярный cost не отражает в точности.

    В результате планировщик отвечает на конкретный инженерный вопрос:

    «Какой из доступных путей ожидается наиболее выгодным, если статистика и стоимость операций примерно соответствуют нашим предположениям?»

    Это разумная инженерная стратегия. Она позволяет быстро строить хорошие планы для большого числа запросов, но ее точность ограничена входной моделью.

    Главное после раздела 13¶

    1. Path — кандидат с оценками и свойствами, а Plan — дерево для executor.
    2. PostgreSQL сохраняет несколько путей, когда они выигрывают в разных измерениях: startup, total и порядке результата.
    3. add_path() отбрасывает доминируемые варианты, сокращая стоимость планирования.
    4. ORDER BY превращает свойство pathkeys в экономически значимое преимущество.
    5. Выбор пути происходит по расчетной модели и среди доступных альтернатив.

    14. LIMIT и частичная стоимость плана¶

    14.1. Один SQL-предикат, два разных инженерных требования¶

    Начнем с двух запросов:

    -- Запрос A: нужны все подходящие заказы.
SELECT *
FROM orders
WHERE customer_id = 42;

    -- Запрос B: нужны только десять подходящих заказов.
SELECT *
FROM orders
WHERE customer_id = 42
LIMIT 10;

    Предикат одинаковый. Поэтому для полного выполнения дочернего сканирования расчетное количество строк может быть одинаковым: rows=10000.

    Но у запросов разные условия завершения.

    Запрос A должен получить весь результат. Для B достаточно десяти строк, если они существуют.

    Исполнитель PostgreSQL устроен так, что многие узлы могут выдавать строки постепенно. Родительский узел запрашивает очередную строку; дочерний узел производит ее. Когда Limit получил достаточно строк, он может перестать запрашивать новые.

    Здесь появляются две независимые величины:

    • Стоимость получить все строки пути;
    • Стоимость получить только нужную долю его строк.

    Именно из-за этого LIMIT способен изменить выбор плана, даже если он не изменил исходную статистику по таблице.

    14.2. Почему total_cost дочернего узла не уменьшается при LIMIT¶

    Представим иллюстративный план:

    Limit  (cost=0.43..2.63 rows=10 width=96)
  -> Index Scan using idx_orders_customer on orders
       (cost=0.43..2200.43 rows=10000 width=96)
       Index Cond: (customer_id = 42)

    Внутри Index Scan по-прежнему указано:

    rows=10000
cost=0.43..2200.43

    Почему? EXPLAIN показывает оценку дочернего узла как если бы его потребовали выполнить до конца.

    А верхний Limit учитывает, что достаточно первых десяти строк.

    При первом взгляде кажется, будто PostgreSQL обязан потратить 2200.43, раз это написано внутри плана.

    Но эта стоимость соответствует полному исполнению Index Scan.

    Если родитель останавливает дочерний узел раньше, соответствующая часть его работы вообще не выполняется.

    В этом примере план предполагает, что десять строк удастся получить при небольшой доле полного сканирования. Формулы покажем дальше.

    Числа в примере специально подобраны для иллюстрации интерполяции. Это не точный вывод PostgreSQL по созданной таблице; реальный Limit учитывает дополнительные детали оценки выходных строк и границ стоимости.

    14.3. Главная формула: стоимость получения доли результата¶

    У пути известны:

    • (C_s) — startup cost;
    • (C_t) — total cost;
    • (N) — ожидаемое количество выходных строк при полном выполнении;
    • (k) — требуемое количество строк.

    Для пути, стоимость которого условно нарастает по мере выдачи строк, можно построить приближение:

    [ f = \min!\left(1,\frac{k}{N}\right) ]

    [ \boxed{C_{\text{fraction}}(f) = C_s + f\,(C_t-C_s)} ]

    Это ключевая математическая идея, используемая в сравнении частичной стоимости путей. В коде PostgreSQL существует функция compare_fractional_path_costs().

    Но интерпретировать формулу нужно правильно.

    Она не утверждает, что физический executor выполняет ровно (f) всех операций или что реальная задержка растет строго линейно. Это расчетная эвристика на уровне Path, основанная на уже полученных оценках.

    Для некоторых узлов почти вся работа приходится на startup; для других работа действительно может накапливаться при выдаче строк.

    Разбор на числах¶

    Два кандидата возвращают по 10 000 строк при полном исполнении:

    Path Startup Total
    A: потоковый индексный доступ 0.4 2 200
    B: bitmap-доступ 150 1 200

    Без LIMIT дешевле B:

    [ 1200 < 2200. ]

    Добавим LIMIT 10:

    [ f = \frac{10}{10000}=0.001. ]

    Для A:

    [ C_A(0.001)=0.4+0.001(2200-0.4) =0.4+2.1996=2.5996. ]

    Для B:

    [ C_B(0.001)=150+0.001(1200-150) =150+1.05=151.05. ]

    Итог:

    Path Для полного результата Для первых 10 строк, по модели
    A 2200 2.60
    B 1200 151.05

    Победитель поменялся.

    Это и есть математическая причина, почему LIMIT может переключить план с bitmap на потоковое индексное сканирование.

    14.4. Почему исходный порядок важен даже при отсутствии ORDER BY¶

    У предыдущего расчета есть тонкость.

    Мы предполагаем, что подходящие строки в среднем будут поступать достаточно равномерно. Но фактическая последовательность строк может отличаться от такой модели.

    Для индексного доступа по точному условию customer_id = 42 это часто разумная модель: мы уже находимся внутри ограниченного диапазона индекса.

    Для последовательного сканирования с дополнительным Filter ситуация сложнее.

    Например:

    SELECT *
FROM orders
WHERE status = 'PAID'
LIMIT 10;

    Если PAID встречается с вероятностью s=0.01 и строки распределены приблизительно независимо, для получения десяти успешных строк можно ожидать рассмотрения порядка:

    [ E[N_{\text{checked}}] \approx \frac{10}{0.01}=1000 ]

    строк.

    Это полезная вероятностная модель, но она опирается на предположение о распределении совпадений по потоку.

    Теперь представим таблицу с миллионом строк, где все PAID находятся в последних 10% физического порядка.

    При Seq Scan первые десять подходящих строк появятся только после чтения большой части таблицы.

    Глобальная статистика может правильно сообщать, что PAID — распространенное значение, но не обязательно точно описывает его расположение относительно направления чтения.

    Следовательно:

    Небольшой LIMIT
    !=
Гарантированное малое количество обработанных строк

    Это один из важнейших источников непредсказуемости LIMIT на неравномерно расположенных данных.

    14.5. ORDER BY + LIMIT: почему индекс может превратиться из проигравшего в победителя¶

    Теперь другой запрос:

    SELECT id, created_at, amount, payload
FROM orders
ORDER BY created_at DESC
LIMIT 10;

    Предположим, есть B-tree индекс по created_at.

    PostgreSQL рассматривает две естественные стратегии:

    A. Seq Scan -> Sort -> Limit

B. Index Scan Backward -> Limit

    В полной выборке A может быть дешевле, потому что последовательное чтение таблицы и последующая сортировка требуют меньше разрозненных посещений heap, чем индексный обход всех строк.

    Но при LIMIT 10 B способен получить десять строк в индексном порядке и завершить работу.

    Расчет¶

    Пусть таблица содержит миллион строк. Для учебной иллюстрации оценим:

    Путь до применения Limit Startup Total Rows
    A: Seq Scan + Sort 18 000 24 000 1 000 000
    B: Index Scan Backward 0.4 45 000 1 000 000

    Здесь индексный путь значительно хуже, если читать всю таблицу:

    [ 45000 > 24000. ]

    Но нужно только десять строк:

    [ f=\frac{10}{1000000}=0.00001. ]

    Для B:

    [ C_B(f)=0.4+0.00001(45000-0.4) \approx 0.85. ]

    Для A:

    [ C_A(f)=18000+0.00001(24000-18000) =18000.06. ]

    В этой модели индексный путь выигрывает с огромным запасом.

    Почему startup у A такой большой?

    Потому что обычный Sort должен прочитать вход, прежде чем определить первый элемент глобально отсортированного результата.

    Даже если он применит ограниченную сортировку (top-N heapsort), прочитать исходный поток для определения десяти лучших строк все равно потребуется.

    Неожиданный нюанс про top-N¶

    Для полного Sort стоимость сравнения элементов обычно имеет масштаб (O(N\log N)).

    Для поддержания десяти лучших из миллиона строк можно использовать структуру с затратами порядка (O(N\log 10)) на сравнения и небольшим объемом памяти.

    Это значительно уменьшает CPU и RAM на сортировку, однако не дает информации о максимальных значениях до просмотра всех строк.

    Следовательно, top-N heapsort может быть дешевым алгоритмом сортировки, сохраняя блокирующее поведение относительно входного потока.

    Индекс отличается тем, что уже хранит ключи в подходящем порядке, поэтому чтение всего исходного отношения не требуется.

    14.6. LIMIT не всегда означает «прямо прочитать N строк»¶

    Рассмотрим три разных случая.

    Случай A. Индекс соответствует сортировке¶
    SELECT id, created_at
FROM orders
ORDER BY created_at DESC
LIMIT 10;

    Подходящий индекс может сразу дать нужную последовательность. Часто достаточно обработать небольшую часть индекса и heap, если требуемые строки доступны.

    Случай B. Подходящего индекса нет¶
    SELECT id, amount
FROM orders
ORDER BY amount DESC
LIMIT 10;

    Без способа получить значения в нужном порядке PostgreSQL должен рассмотреть все потенциальные строки, чтобы найти десять максимальных.

    LIMIT сокращает размер результата и память bounded sort, но не обязан сокращать чтение таблицы.

    Случай C. Индекс подходит к ORDER BY, но условие фильтрует почти все¶
    SELECT id, created_at
FROM orders
WHERE tenant_id = 42
ORDER BY created_at DESC
LIMIT 10;

    Допустим, есть индекс по created_at, но нет эффективного индексного доступа, одновременно ограничивающего tenant_id.

    PostgreSQL может идти по created_at в обратном порядке и проверять Filter: (tenant_id = 42).

    Если последние десять заказов этого tenant старые, до них придется пройти множество новых заказов других tenant.

    Условный симптом:

    Limit
  -> Index Scan Backward using idx_orders_created_at on orders
       Filter: (tenant_id = 42)
       Rows Removed by Filter: 850000

    Наличие индекса, соответствующего ORDER BY, еще не гарантирует эффективный LIMIT при дополнительном фильтре.

    Здесь снова встретились две оценки:

    1. Сколько всего строк удовлетворяет tenant_id = 42?
    2. Как быстро эти строки встретятся при чтении по created_at DESC?

    Обычная однотабличная статистика может достаточно хорошо отвечать на первый вопрос и гораздо хуже — на второй.

    14.7. Математика LIMIT на примере трех способов чтения¶

    Вернемся к одной таблице и условию, возвращающему 10 000 строк.

    Пусть есть три иллюстративных пути:

    Path Startup Total Rows
    Seq Scan 0 32 500 10 000
    Index Scan 0.43 1 830 10 000
    Bitmap Heap Scan 225 1 650 10 000

    Для полного результата:

    [ 1650 < 1830 \ll 32500 ]

    Побеждает bitmap.

    Для LIMIT 10:

    [ f = 0.001. ]

    [ C_{\text{seq}}=0+0.001\cdot32500=32.5 ]

    [ C_{\text{index}}=0.43+0.001(1830-0.43) \approx 2.26 ]

    [ C_{\text{bitmap}}=225+0.001(1650-225) =226.425 ]

    Побеждает индекс.

    Для LIMIT 5000:

    [ f = 0.5. ]

    [ C_{\text{seq}}=16250 ]

    [ C_{\text{index}}=0.43+0.5(1830-0.43) \approx915.22 ]

    [ C_{\text{bitmap}}=225+0.5(1650-225)=937.5 ]

    Индекс еще немного выгоднее по этой модели.

    При LIMIT 7000:

    [ f=0.7. ]

    [ C_{\text{index}}=0.43+0.7(1830-0.43) \approx1281.13 ]

    [ C_{\text{bitmap}}=225+0.7(1650-225)=1222.5 ]

    Уже выгоднее bitmap.

    Где граница переключения?¶

    Решим уравнение равенства оценок:

    [ 0.43+f(1830-0.43)=225+f(1650-225). ]

    [ 0.43+1829.57f=225+1425f. ]

    [ 404.57f=224.57. ]

    [ \boxed{f\approx0.5551}. ]

    При (N=10000) это соответствует примерно:

    [ k\approx5551. ]

    Получаем важный результат: в учебной модели существует расчетная точка, после которой предпочтение меняется с индексного на bitmap-путь.

    В реальном PostgreSQL точное место переключения зависит от стоимости верхних узлов, статистики, допустимых путей, дискретных решений и множества деталей. Но механизм хорошо виден именно через математическое сравнение.

    14.8. Почему нельзя просто считать LIMIT бесплатным¶

    Теперь добавим требование:

    SELECT *
FROM orders
WHERE amount > 1000
ORDER BY amount DESC
LIMIT 10;

    Если индекс обеспечивает и фильтрацию, и порядок, он может быстро остановиться.

    Если единственный допустимый путь — Seq Scan + Sort, сначала нужно прочитать все подходящие строки и определить лучшие десять.

    Даже если итоговый Limit выдает всего десять строк, это не отменяет работу под ним.

    Ключ к чтению плана — не смотреть только на:

    Limit (rows=10)

    а развернуть дерево:

    Limit
  -> Sort                <- блокирующая подготовка
       -> Seq Scan        <- может прочитать всю таблицу

    или:

    Limit
  -> Index Scan Backward <- поток с уже нужным порядком

    Две одинаковые строки LIMIT 10, две разные физические стратегии и две разные цены.

    14.9. OFFSET: почему дорогие страницы пагинации нельзя оправдать небольшим LIMIT¶

    Теперь запрос:

    SELECT id, created_at
FROM orders
ORDER BY created_at DESC, id DESC
OFFSET 990000
LIMIT 10;

    Вроде бы снова нужно только десять строк.

    Но перед ними исполнитель должен пропустить 990 000 строк в требуемом порядке.

    На уровне числа строк путь должен произвести примерно:

    [ N_{\text{consumed}}=\text{OFFSET}+\text{LIMIT} =990000+10=990010. ]

    Пусть индексный путь для миллиона строк имеет:

    [ C_s=0.4, \qquad C_t=40000. ]

    Если оценивать чтение большого начального префикса по линейной модели, доля:

    [ f=\frac{990010}{1000000}=0.99001. ]

    И стоимость оказывается почти полной:

    [ C\approx0.4+0.99001(40000-0.4) \approx39600.40. ]

    Несмотря на LIMIT 10, запрос должен пройти почти весь индексный поток.

    Как OFFSET отражается в модели LimitPath¶

    В реализации PostgreSQL функция, строящая LimitPath, корректирует отдельно startup и total стоимости дочернего пути с учетом пропускаемых и возвращаемых строк.

    Упрощенная модель при (N) ожидаемых строках, (o) пропускаемых и (k) возвращаемых:

    [ C_{\text{startup,limit}} \approx C_s+\frac{o}{N}(C_t-C_s) ]

    [ C_{\text{total,limit}} \approx C_s+\frac{\min(N,o+k)}{N}(C_t-C_s). ]

    При корректном учете границ эти формулы отражают главное: пропуск строк требует работы.

    Это не попытка дословно воспроизвести весь код create_limit_path(). Реальная реализация предусматривает особые случаи неизвестных границ, округления и корректировки rows.

    Где возникает инженерное решение¶

    Для последовательной пагинации по стабильному ключу иногда подходит подход по последнему полученному ключу (keyset pagination):

    SELECT id, created_at
FROM orders
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 10;

    При подходящем индексе он позволяет ограничить диапазон доступа и избежать пропуска огромного числа предыдущих строк.

    Этот фрагмент приведен только для объяснения цены OFFSET; отдельные вопросы стабильности пагинации, изменения данных и API-контрактов здесь не рассматриваем.

    14.10. LIMIT без ORDER BY: результат может измениться после перепланирования¶

    Рассмотрим:

    SELECT id
FROM orders
LIMIT 10;

    SQL не обещает конкретный порядок строк, если нет ORDER BY.

    Планировщик может выбрать один способ доступа сегодня и другой завтра — например, после изменения статистики или параметров стоимости.

    Если порядок обхода поменялся, набор из первых десяти строк тоже может поменяться.

    Это корректное поведение.

    Причинно-следственная цепочка:

    Нет ORDER BY
    -> допустимы разные порядки выдачи
    -> planner выбирает способ доступа по cost
    -> LIMIT останавливает поток после N строк
    -> изменившийся путь может дать другие N строк

    Даже ORDER BY created_at не гарантирует стабильный порядок между строками с одинаковым created_at. Если для бизнеса нужна воспроизводимая граница, полезно добавить уникальный ключ в сортировку:

    ORDER BY created_at DESC, id DESC

    Это требование корректности результата, а не только производительности.

    14.11. Incremental Sort и частичная выдача результата¶

    Обычная полная сортировка вынуждена увидеть весь вход, прежде чем уверенно выдать первую строку глобального порядка.

    Incremental Sort способен использовать уже отсортированный префикс ключей.

    Представим:

    SELECT customer_id, created_at, amount
FROM orders
ORDER BY customer_id ASC, created_at DESC
LIMIT 20;

    Индекс может давать поток, упорядоченный по customer_id, но не по created_at DESC внутри каждого клиента.

    Incremental Sort группирует строки по customer_id, сортирует первую группу и начинает выдачу, пока последующие группы еще не прочитаны.

    Если первые группы небольшие, LIMIT 20 может сработать после обработки ограниченной части входа.

    Но если первый customer_id имеет миллион строк, даже первая группа требует большой работы. Поэтому планировщик снова опирается на оценки распределения данных, а фактическая выгода не гарантирована.

    Важно разделять:

    • Свойство порядка на входе — Presorted Key;
    • Алгоритм завершения сортировки — Incremental Sort;
    • Факт ранней остановки — родительский Limit прекратил запросы к дочернему узлу.

    Три механизма работают вместе, но решают разные задачи.

    14.12. Почему LIMIT может не ускорить работу вообще¶

    Обобщим ситуации, когда небольшой результат не означает небольшой объем вычислений.

    Условие запроса Почему LIMIT может почти не помочь
    ORDER BY без подходящего порядка во входе Надо изучить все входные строки для нахождения лучших N
    Filter отбрасывает большинство ранних кандидатов Нужно проверить много строк, пока найдутся N подходящих
    Большой OFFSET Сначала нужно произвести и пропустить OFFSET строк
    Большая первая группа при Incremental Sort Первая порция сортировки все равно дорогая
    Очень малая фактическая селективность Для получения N совпадений придется пройти большой диапазон
    Данных фактически меньше, чем LIMIT Узел будет выполнен до исчерпания результата
    Промахи кеша и дорогое получение первых страниц Даже короткий путь может иметь значительную фактическую задержку

    Есть еще специальный вариант FETCH FIRST n ROWS WITH TIES: он может вернуть больше n строк, если значения на границе сортировки совпадают. Для такого запроса нельзя механически ожидать, что после выдачи ровно n строк поток гарантированно остановится.

    14.13. cursor_tuple_fraction: что если клиент читает результат постепенно¶

    LIMIT — наиболее очевидный случай, когда нужны первые строки.

    Но есть и другой сценарий: клиент открывает курсор и может получить только часть результата.

    Для планирования соответствующих запросов PostgreSQL имеет настройку:

    SHOW cursor_tuple_fraction;

    Ее стандартное значение — 0.1.

    Она задает планировщику предположение о доле строк курсора, которую, вероятно, будут читать. Меньшее значение может усилить предпочтение «быстрого старта»; значение 1.0 делает акцент на полной стоимости.

    Почему это важно?

    Потому что «сколько строк реально заберет клиент» — часть требований к оптимизации. Без такой информации планировщик будет использовать допущение, которое может не совпадать с фактическим потреблением.

    Но это не универсальный способ ускорять SELECT. Изменение параметра влияет на определенные сценарии работы с курсорами, а не превращает любой запрос в потоковый индексный поиск.

    Главное после раздела 14¶

    1. LIMIT позволяет выбирать путь по стоимости получения части строк, а не только всего результата.
    2. Учебное приближение: (C(f)=C_s+f(C_t-C_s)).
    3. Самый дешевый полный путь может проиграть пути с меньшим startup cost.
    4. ORDER BY + LIMIT особенно выгоден, если индекс сразу обеспечивает нужный порядок.
    5. Sort, фильтры и большой OFFSET могут уничтожить ожидаемую выгоду ранней остановки.
    6. LIMIT без полного ORDER BY не гарантирует воспроизводимого состава результата.

    15. Ограничения Cost-Based Optimizer¶

    15.1. Что оптимизирует PostgreSQL — и почему этого недостаточно для гарантии минимальной задержки¶

    В предыдущих разделах мы получили множество возможных Path и научились сравнивать их стоимость. Математическая постановка выглядит так:

    [ P^* = \arg\min_{P \in \mathcal{P}} \widehat{C}(P), ]

    где:

    • (\mathcal{P}) — рассматриваемые допустимые пути;
    • (\widehat{C}(P)) — оценка стоимости пути по модели планировщика;
    • (P^*) — выбранный путь.

    Для запроса с LIMIT критерием может выступать стоимость получения нужной части результата. Для запроса с ORDER BY рассматриваются пути, удовлетворяющие требуемому порядку, либо пути, дополненные сортировкой.

    Здесь решающую роль играет значок оценки над (C). Планировщик сравнивает предсказанные затраты, а не измеренное будущее время.

    Его модель может выбрать:

    [ \widehat{C}(A) < \widehat{C}(B), ]

    хотя при конкретном выполнении окажется:

    [ T_{\text{actual}}(A) > T_{\text{actual}}(B). ]

    Это допустимая ситуация. Она показывает, что какая-то предпосылка модели не совпала с реальными условиями.

    Чтобы диагностировать такое расхождение, нужно последовательно проверить три слоя:

    1. Статистика и селективность: правильно ли посчитано количество строк?
    2. Стоимость доступа: правильно ли оценена работа с индексом, heap, CPU и памятью?
    3. Условия выполнения: соответствует ли реальная среда усредненным предположениям модели?

    15.2. Ошибка cardinality: когда последствия растут быстрее ошибки статистики¶

    Планировщик ожидает:

    rows=100

    А при полном исполнении узел возвращает:

    actual rows=100000

    Введем отношение:

    [ E_{rows} = \frac{R_{\text{actual}}}{R_{\text{estimated}}}. ]

    Получаем:

    [ E_{rows}=\frac{100000}{100}=1000. ]

    Ошибка в тысячу раз.

    Рассмотрим запрос:

    SELECT *
FROM orders
WHERE customer_id = 42;

    Допустим, когда статистика собиралась, у клиента было сто заказов. После миграции данных оказалось сто тысяч. Однако статистика не успела обновиться.

    Планировщик считает условие очень селективным и выбирает индексный доступ. Реально индекс возвращает намного больше кандидатов, вызывая большое количество обращений к heap. В этих условиях последовательное сканирование могло бы оказаться дешевле.

    Но плохая cardinality не всегда означает плохой индекс. Если выбранный индекс покрывает запрос или строки физически хорошо локализованы, даже большой результат может обслуживаться эффективно. Нужно анализировать полную стоимость, а не только число строк.

    Почему статистика ошибается¶

    Причины уже известны из блока 1: устаревший ANALYZE, недостаточная выборка, неравномерные распределения, значения вне MCV, грубая гистограмма, зависимые столбцы и ограниченная многоколоночная статистика.

    Еще одна важная граница: статистика по столбцу может верно оценивать, сколько строк удовлетворяет условию, и недостаточно точно описывать, где именно эти строки встретятся при обходе определенного индекса.

    Когда расхождение rows вообще не ошибка¶

    Если дочерний узел остановлен верхним Limit, его расчетная оценка рассчитана для полного выполнения, а фактическое число строк отражает только выполненную часть.

    Limit (actual rows=10)
  -> Index Scan (rows=100000, actual rows=10)

    Сравнение 100000 / 10 здесь бессмысленно как мера ошибки оценки: план мог остановиться после десяти строк по требованию родителя.

    Это одна из ловушек поверхностного чтения EXPLAIN ANALYZE.

    15.3. Верная cardinality, но неправильная физическая цена чтения¶

    Пусть планировщик ожидает 50 000 строк и исполнитель возвращает 49 800. Оценка близка к факту.

    Можно ли утверждать, что выбранный план должен работать быстро?

    Нет. rows описывает объем выходного потока. Для физической стоимости важны еще число страниц, локальность обращений и степень кеширования.

    На стоимость влияют:

    • seq_page_cost и random_page_cost;
    • effective_cache_size;
    • корреляция ключа индекса с физическим порядком heap;
    • количество посещаемых страниц индекса и таблицы;
    • необходимость обработки и проверки версий строк;
    • фактическое состояние общего буферного кеша и файлового кеша ОС.

    Предположим, что на одной машине почти вся таблица находится в RAM, а на другой рабочий набор данных сильно превосходит размер доступного кеша. При одинаковой статистике и одинаковых коэффициентах планировщик способен построить один и тот же план. Но фактическая задержка выполнения будет существенно различаться.

    Следовательно, правильная оценка количества строк — необходимая часть модели, но далеко не вся модель.

    effective_cache_size не выделяет память¶

    С этим параметром часто связана неправильная ментальная модель:

    «Укажу effective_cache_size = 32GB, и PostgreSQL получит 32 ГиБ кеша».

    Так не работает. effective_cache_size — предположение планировщика о суммарном эффективном объеме кеша, доступного запросу. Оно не выделяет память и не заменяет shared_buffers.

    Его изменение влияет на относительную привлекательность некоторых планов. Но если физической памяти по-прежнему не хватает, никакая запись в конфигурации не материализует недостающий RAM.

    Это хороший пример разницы между настройкой модели и настройкой ограниченного ресурса.

    15.4. Физический порядок данных: почему correlation тоже приближение¶

    В блоке 2 мы связывали выгодность индексного доступа с корреляцией порядка значений и физического расположения строк.

    Если строки вставлялись в порядке created_at, диапазонный индексный обход может получать соседние TID, указывающие на близкие страницы heap.

    Если таблица содержит множество обновлений, исторических загрузок и перемешанных данных, та же последовательность индексных ключей может приводить к множеству удаленных друг от друга страниц.

    Но статистическая correlation описывает общую картину, а не точную последовательность блоков для каждого будущего условия WHERE.

    Представим, что в целом хронология хорошо соответствует физическому порядку. При этом конкретный исторический диапазон недавно массово изменяли. Строки в этом диапазоне могут быть расположены хуже, чем типичные строки таблицы.

    В таком случае расчетная стоимость индексного чтения будет основана на агрегированной модели. Фактическая локальность для выбранного диапазона может отличаться.

    Итог: даже если количество найденных строк оценено достаточно точно, объем работы по доступу к страницам может оказаться другим.

    15.5. Кеширование и конкуренция: почему одинаковый SQL имеет разную цену во времени¶

    Возьмем запрос, который вчера выполнялся за 20 мс, а сегодня за 300 мс. SQL не изменился, индекс остался, EXPLAIN показывает то же дерево.

    Что могло поменяться?

    Состояние кеша. При холодном запуске часть страниц приходится получать из файлового слоя, а при повторном выполнении значительная их часть уже находится в RAM.

    Профиль соседних запросов. Другие сессии могут вытеснять полезные страницы из кеша и создавать конкуренцию за CPU.

    I/O-конкуренция. Одновременно работающие процессы могут увеличить очередь на накопителе и стоимость получения каждой недостающей страницы.

    Блокировки и ожидания. Задержка может включать время ожидания ресурсов, которое не следует объяснять неправильным random_page_cost.

    Изменение физического рабочего набора. После массовой записи и обновлений страницы могут занимать больше места и иначе размещаться в heap.

    Планировщик не знает точного будущего расписания всех этих процессов. Он работает с усредненными коэффициентами и статистикой.

    Поэтому числа вида:

    cost=0.43..2500.00

    не обещают ни 2500 ms, ни постоянную задержку при холодном и горячем кеше, ни одинаковое время при одном и ста конкурентных клиентах.

    15.6. Почему cost-параметры нельзя безнаказанно настроить под один медленный запрос¶

    Набор коэффициентов стоимости:

    seq_page_cost
random_page_cost
cpu_tuple_cost
cpu_index_tuple_cost
cpu_operator_cost

    управляет относительной ценой CPU и доступа к страницам.

    Допустим, после анализа одного запроса разработчик решил уменьшить random_page_cost: индексный доступ сразу стал выглядеть выгоднее.

    Но теперь другие запросы, возвращающие значительную долю таблицы, тоже могут получить предпочтение индексного доступа, хотя для них последовательное чтение дешевле.

    Получается:

    Один набор коэффициентов
    |
    +-- маленькие выборки
    +-- большие выборки
    +-- хорошо коррелированные данные
    +-- случайно расположенные строки
    +-- горячий кеш
    +-- холодный кеш

    Один набор параметров не способен идеально описать все сочетания.

    Поэтому документация PostgreSQL советует рассматривать коэффициенты как усредненную характеристику реальной рабочей нагрузки. Идеальная подгонка к одному запросу может ухудшить множество других.

    Отдельные коэффициенты чтения страниц можно переопределять на уровне tablespace, если данные действительно размещены на носителях с существенно разными характеристиками. Но и такие настройки не превращают модель в датчик текущей очереди I/O.

    15.7. Prepared statements: когда планировщик не знает конкретного значения параметра¶

    Представим таблицу с миллионом заказов:

    • status = 'PAID' встречается в 95% строк;
    • status = 'CANCELLED' встречается в 5%.

    Для этих значений может быть выгоден разный доступ к таблице.

    Теперь backend выполняет один параметризованный SQL:

    PREPARE find_orders(text) AS
SELECT *
FROM orders
WHERE status = $1;

    Возникает вопрос: может ли оптимизатор учитывать, какое значение параметра пришло сегодня?

    Зависит от вида плана.

    Custom plan строится с учетом параметров текущего выполнения. Это позволяет принимать разные решения для PAID и CANCELLED.

    Generic plan предназначен для повторного использования с разными параметрами. Он экономит стоимость планирования, но не учитывает конкретное текущее значение $1 так же, как custom plan.

    Компромисс¶

    [ \text{экономия времени планирования} \quad\leftrightarrow\quad \text{качество специализированного плана}. ]

    В стандартном автоматическом режиме PostgreSQL 18 для параметризованного prepared statement сначала обычно строит custom plans при первых пяти выполнениях, затем оценивает применимость generic plan, сравнивая его расчетную стоимость с оценками custom plans и учитывая экономию на планировании.

    Это деталь текущей реализации, а не гарантия SQL-стандарта.

    Настройка plan_cache_mode позволяет влиять на выбор между auto, force_custom_plan и force_generic_plan.

    Для нашей лекции главное следствие такое: одинаковый SQL-текст с разными параметрами может получать разные планы, а переиспользуемый общий план может оказаться неудачным для редкого или очень частого значения.

    Протокол PostgreSQL и реализация prepared statements в драйверах относятся к отдельному техническому слою.

    15.8. Почему executor не перестраивает весь план после первых плохих измерений¶

    Рассмотрим такой сценарий:

    1. Планировщик оценивает запрос и выбирает Index Scan.
    2. Начинается выполнение.
    3. После первых сотен тысяч строк становится видно, что данных гораздо больше, чем предполагалось.
    4. Стоимость индексного доступа резко возрастает.

    Можно было бы ожидать, что PostgreSQL автоматически прервет индексный доступ и переключится на Seq Scan.

    Но обычный исполнитель PostgreSQL не гарантирует такого глобального динамического перепланирования посреди запроса.

    План строится перед выполнением. EXPLAIN ANALYZE позволяет после выполнения сравнить прогноз с реальностью, однако найденная ошибка оценки сама по себе не перестраивает задним числом выбранную стратегию.

    Это цена архитектурного компромисса:

    • планирование выполняется до работы с основным объемом данных;
    • исполнитель получает заранее выбранное дерево;
    • стоимость и сложность непрерывной перестройки плана не входят в обычную модель исполнения.

    Поэтому важно, насколько качественной была исходная статистика.

    15.9. Минимальный cost и минимальный p95 — разные цели¶

    Предположим, оптимизатор оценил:

    [ \widehat{C}(A)=900, \qquad \widehat{C}(B)=1100. ]

    А фактические задержки при определенном состоянии среды оказались такими:

    [ T(A)=120\text{ мс},\qquad T(B)=75\text{ мс}. ]

    Это сконструированный пример, показывающий возможное расхождение порядка предпочтений.

    Backend часто оценивают по:

    p95 latency < 100 ms

    Но cost model PostgreSQL не минимизирует p95 всего HTTP-запроса. Она сравнивает оценочные затраты выполнения SQL-плана.

    End-to-end задержка дополнительно включает ожидание соединения в пуле, передачу SQL, сериализацию результата, сетевое взаимодействие и работу приложения.

    Даже внутри PostgreSQL p95 зависит от различий между холодным и горячим кешем, переменной нагрузки и редких дорогостоящих ожиданий.

    Значит, минимальный расчетный cost — разумный критерий выбора плана, но не контракт на задержку сервиса.

    15.10. Планирование само стоит CPU и времени¶

    Пока мы рассчитывали cost для путей, могло возникнуть впечатление, что планировщик выполняет эту работу бесплатно.

    Бесплатное закончилось.

    Построение статистических оценок, генерация Path, сравнение кандидатов и конструирование окончательного Plan потребляют ресурсы.

    Именно поэтому add_path() отбрасывает доминируемые варианты. Сохранять все возможные кандидаты ради теоретически идеального выбора было бы слишком дорого по времени и памяти.

    Именно поэтому generic plans могут быть выгодны при частом повторном исполнении похожих запросов: они позволяют экономить на повторном планировании.

    В EXPLAIN ANALYZE различаются:

    Planning Time: ... ms
Execution Time: ... ms

    При этом Planning Time не равно стоимости полного цикла обработки запроса в приложении, а cost-оценки узлов не включают все возможные накладные расходы подготовки SQL и сетевого обмена.

    Инженерный вывод: оптимизатор должен быть достаточно точным, но и достаточно быстрым. Дополнительная точность имеет смысл только тогда, когда ее цена оправдана ожидаемым выигрышем.

    15.11. Как интерпретировать расхождение прогноза и фактического времени¶

    Вместо интуитивного «индекс плохой» полезнее пройти причинную цепочку.

    Наблюдение Что оно означает и чего не доказывает
    rows близко к actual rows Cardinality в данном узле хорошая, но цена доступа может быть неверной
    rows в сотни раз меньше actual rows Возможна ошибка статистики, но сначала исключаем раннюю остановку узла и особенности loops
    shared read вырос Больше чтений при промахах в shared_buffers, однако это не всегда физические чтения SSD
    shared hit велик при медленном запросе Данные кешированы, но обращений и CPU-работы может быть очень много
    Sort Method: external merge Сортировка использовала временные файлы; нужно учитывать ее входной объем и память
    Limit вернул 10 строк Ничего не говорит само по себе о количестве обработанных строк внизу дерева
    План не изменился, время выросло Возможны кеш, конкуренция, I/O-очереди, ожидания и изменение окружения

    Есть еще инструментальная тонкость: EXPLAIN ANALYZE дополнительно измеряет узлы и может создавать заметные накладные расходы для очень коротких операций. Для оценки количества строк и обращений к буферам без измерения времени каждого узла существует TIMING OFF.

    В этом блоке мы не изучаем устройство инструментирования executor — оно относится к отдельному 05.2 Executor Internals.

    15.12. Три теоретические аварии модели¶

    Авария A. «Клиенту приписали миллион заказов»¶

    До массовой загрузки по customer_id=42 было 50 строк, а после стало 200 000. Статистика устарела.

    Планировщик продолжает оценивать очень селективный предикат и предпочитает индекс. Фактически множество heap fetches делает запрос дорогим.

    Нарушена предпосылка: количество строк соответствует прежнему распределению.

    Какой показатель выдаст проблему: estimated rows против actual rows при полном исполнении.

    Авария B. «Количество строк правильное, но страницы разбросаны»¶

    Планировщик ожидал 50 000 строк, получил 50 100, но физическая локальность оказалась существенно хуже расчетной.

    Нарушена предпосылка: цена получения страниц близка к оцененной.

    Что важно: BUFFERS, информация об I/O, физическое распределение строк и реальный рабочий набор.

    Авария C. «LIMIT 10, но первые десять находятся в самом конце»¶
    SELECT id, created_at
FROM orders
WHERE tenant_id = 42
ORDER BY created_at DESC
LIMIT 10;

    При обратном чтении индекса по времени исполнитель долго не находит подходящие строки. Почти все ранние кандидаты отклоняются Filter.

    Нарушена предпосылка: подходящие строки встретятся достаточно быстро в выбранном порядке обхода.

    Что выдаст проблему: большое число строк, отклоненных фильтром, и дорогая работа дочернего Index Scan, несмотря на маленький Limit.

    Все три ситуации могут выглядеть как «PostgreSQL выбрал не тот план», но механизмы у них совершенно разные.

    15.13. Последнее разрушение упрощения «планировщик всегда выбирает самый дешевый план»¶

    Это выражение верно лишь с оговорками.

    Точная формулировка: PostgreSQL выбирает путь с предпочтительной расчетной стоимостью, учитывая требования запроса и доступные свойства путей, среди альтернатив, которые удалось создать и сохранить по правилам оптимизатора.

    Почему не стоит говорить просто «самый дешевый»?

    Потому что:

    • стоимость приблизительна;
    • количество строк приблизительно;
    • startup и total дают разные критерии;
    • ORDER BY требует оценивать порядок выходного потока;
    • LIMIT меняет интересующую долю результата;
    • часть кандидатов отбрасывается в ходе поиска;
    • среда меняется под нагрузкой;
    • фактическое время не обязано соответствовать расчетному порядку путей.

    Это не набор исключений для запоминания. Это следствия одной инженерной идеи: планировщик решает сложную задачу выбора быстро, пользуясь доступной статистической моделью вместо выполнения всех вариантов.

    Главное после раздела 15¶

    1. Cost-Based Optimizer работает с оценкой затрат, а не с заранее известной задержкой.
    2. Серьезные ошибки rows часто приводят к плохим решениям, но правильные rows не гарантируют хороший план.
    3. Физическая локальность, кеширование и конкурентная нагрузка определяют реальную стоимость страниц.
    4. Коэффициенты стоимости нельзя без риска настраивать по единственному запросу.
    5. Generic plan уменьшает стоимость планирования, но может оказаться невыгодным для некоторых значений параметров.
    6. LIMIT меняет расчетную цель, однако сам по себе не гарантирует малую работу.
    7. Минимальный cost не является обещанием минимального p95 backend-запроса.

    Итоговая модель планировщика PostgreSQL 18¶

    SQL / предикаты / ORDER BY / LIMIT
              ↓
pg_class + статистика ANALYZE
              ↓
Оценка selectivity и выходных rows
              ↓
Cost model каждого допустимого способа
  - Seq Scan          → CPU + все heap pages
  - Index Scan        → индекс + heap + correlation + cache
  - Bitmap Heap Scan  → bitmap + сгруппированные heap pages
  - Sort              → rows + width + work_mem + temp I/O
              ↓
Создание и сравнение Path
  - startup_cost / total_cost
  - pathkeys и другие свойства
  - удаление доминируемых альтернатив
              ↓
ORDER BY / LIMIT → свойства порядка и доля результата
              ↓
Выбранный Path → create_plan() → executor
              ↓
EXPLAIN ANALYZE: реальные строки, время и буферы
              ↓
Сравнение прогноза и действительной работы

    Семь инженерных выводов¶

    1. Кардинальность — первая гипотеза. rows вычисляется из статистики, а не подсчитывается заранее исполнением того же запроса.
    2. Селективность зависит от распределения. MCV, гистограммы, доля NULL и зависимости между столбцами объясняют большую часть ошибок оценок для одной таблицы.
    3. Стоимость — относительная модель. cost объединяет CPU и страничный доступ в условных единицах; это не миллисекунды и не прогноз p95.
    4. Индекс не дает бесплатного heap. Случайное расположение TID способно сделать Index Scan дорогим даже при правильной оценке rows.
    5. Bitmap и Sort оплачиваются отдельно. Они могут экономить I/O или обеспечивать порядок, но требуют предварительной работы и ограниченной памяти.
    6. Порядок и LIMIT меняют критерий выбора. План для всех строк может проиграть при запросе первых десяти, а блокирующий Sort или большой OFFSET способны лишить LIMIT ожидаемой выгоды.
    7. Минимальный расчетный cost — условный выбор. Качество решения определяется актуальностью статистики, приближениями модели и реальным состоянием системы под нагрузкой.

Понятия Path, RelOptInfo, Cost, PathKey, add_path() и названия функций стоимости — особенности реализации PostgreSQL 18. Формулы с пометками «учебная» и toy не претендуют на буквальное воспроизведение всех внутренних ветвей кода.

    1. PostgreSQL 18 — Using EXPLAIN — семантика дерева плана, cost, rows, width, LIMIT и интерпретация узлов.
    2. PostgreSQL 18 — Statistics Used by the Planner — обычная и расширенная статистика, MCV, гистограммы, функциональные зависимости.
    3. PostgreSQL 18 — Planner Statistics Details — расчет селективности на конкретных распределениях.
    4. PostgreSQL 18 — Query Planning — коэффициенты стоимости, параметры планировщика, effective_cache_size.
    5. PostgreSQL 18 — Planner/Optimizer — Path и построение окончательного дерева Plan.
    6. PostgreSQL 18 — Indexes and ORDER BY — порядок B-tree, выбор между индексным обходом и сортировкой.
    7. PostgreSQL 18 — LIMIT and OFFSET — частичные результаты, нестабильность порядка и цена OFFSET.
    8. PostgreSQL 18 — PREPARE — generic/custom plans.
    9. Исходный код PostgreSQL 18 — costsize.c — cost_seqscan, cost_index, cost_bitmap_heap_scan, cost_tuplesort, интерполяция стоимости.
    10. Исходный код PostgreSQL 18 — selfuncs.c — eqsel, диапазонные оценки, стоимость индексного метода.
    11. Исходный код PostgreSQL 18 — analyze.c — алгоритмы статистической выборки.
    12. Исходный код PostgreSQL 18 — dependencies.c — оценка функциональных зависимостей.
    13. Исходный код PostgreSQL 18 — pathnode.c — добавление путей, disabled_nodes, сравнение стоимости и создание LimitPath.
    14. Исходный код PostgreSQL 18 — planner.c — выбор финального пути с учетом частичной стоимости.
    15. Исходный код PostgreSQL 18 — tuplesort.c — механика сортировки, которую здесь учитываем через стоимостные эвристики.
