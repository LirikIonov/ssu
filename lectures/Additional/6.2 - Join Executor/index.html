    06.2. PostgreSQL — внутреннее устройство исполнителя JOIN¶

    Углубленная техническая лекция. Основной ориентир — PostgreSQL 18, исходники ветки REL_18_STABLE. Продолжаем лекцию №6 и углубление 06.1. Разбираем физическое выполнение Hash Join, Nested Loop и Merge Join, устройство временных структур, повторные запуски и параллельное выполнение. Вопросы WAL, COMMIT, контрольных точек и восстановления после сбоя оставляем для отдельной лекции №7.

    Формат: техническое расследование, ручные разборы алгоритмов, небольшие фрагменты SQL, реальные названия внутренних функций и условные примеры EXPLAIN. Лабораторных заданий нет. Все формулы записаны обычным текстом Markdown без LaTeX.

    Главный вопрос: планировщик уже выбрал дерево. Какие конкретно объекты создает исполнитель PostgreSQL, какие строки и страницы он перемещает, как реагирует на нехватку памяти и где при большой нагрузке исчезает производительность?

    0. Какое дерево передается исполнителю¶

    В углублении 06.1 мы рассматривали стоимость альтернативных соединений. Планировщик оценивал количество пар, стоимость повторных индексных поисков, цену построения хеш-таблицы и сортировок, а затем выбирал подходящий Path. Из него формируется дерево Plan.

    Например:

    Hash Join
  Hash Cond: (o.customer_id = c.id)
  -> Seq Scan on orders o
  -> Hash
       -> Seq Scan on customers c

    На этом работа планировщика закончилась. Дальше узлы выполняются, получают строки от дочерних узлов и отдают строки родителям. Многие узлы работают по принципу «дай следующую строку»: родитель обращается к ExecProcNode() дочернего узла. Но не каждый узел может сразу вернуть строку.

    Seq Scan способен выдавать строки по мере обхода таблицы. Обычный Sort должен подготовить упорядоченный набор. Hash Join сначала должен построить хеш-таблицу из внутреннего входа. Узел Hash здесь вообще особенный: обычный интерфейс «верни следующую строку» для его основной операции не применяется; построением управляет MultiExecHash(), вызываемый соединением.

    Поэтому у одного SQL могут одновременно существовать две стоимости: работа до первой выходной строки и работа до полного завершения. А еще разные узлы могут несколько раз запускать или повторно читать своих потомков. Это объясняет, почему loops иногда измеряется сотнями тысяч, а некоторые узлы возвращают одни и те же промежуточные строки несколько раз.

    Для понимания Executor Internals будем разбирать не определения узлов, а их внутренние состояния и ресурсы.

    1. Hash Join Internals: от строки до цепочки в корзине¶

    1.1. Зачем исполнителю вообще нужна собственная хеш-таблица¶

    Возьмем запрос:

    SELECT o.id, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id;

    Допустим, клиентов 100 000, а заказов 10 миллионов. При Nested Loop можно искать клиента для каждого заказа по индексу. Но если нужен почти весь объем, получатся миллионы повторных поисков.

    Другой подход: один раз прочитать клиентов, построить для них временную хеш-таблицу, затем один раз пройти по заказам и сопоставить ключи.

    customers                       orders
   |                               |
   v                               v
Вычислить хеш(id)             Вычислить хеш(customer_id)
   |                               |
   v                               v
Построить хеш-таблицу   --->   Найти кандидатов по хешу
                                   |
                                   v
                           Проверить равенство
                                   |
                                   v
                           Выдать подходящую пару

    Здесь сторона построения (build side) — customers, сторона поиска (probe side) — orders. В дереве PostgreSQL вход под Hash — внутренняя сторона соединения; другая сторона — внешняя. Это физические роли входов, не надо путать их с логическим LEFT JOIN.

    Важно: временная хеш-таблица Hash Join — не хеш-индекс PostgreSQL. Она существует для конкретного выполнения запроса и не сохраняется как постоянный индекс таблицы. Наличие CREATE INDEX ... USING hash для хеш-соединения не требуется.

    1.2. Что хранится в памяти: HashJoinTableData, корзины и строки¶

    Учебная модель «ключ → строка» полезна, пока не появятся повторяющиеся ключи. Если у одного клиента десять заказов, а у другого три, из одной корзины можно получить несколько кандидатов. Более того, разные ключи могут иметь одинаковый хеш или попасть в одну корзину.

    В PostgreSQL хеш-соединение использует структуры HashJoinTableData и HashJoinTupleData (реализация в hashjoin.h, nodeHash.c, nodeHashjoin.c).

    Концептуально хеш-таблица включает:

    • массив указателей на корзины (buckets);
    • цепочки хеш-записей внутри корзин;
    • для каждой хеш-записи — рассчитанный hashvalue, ссылку на следующую запись и сохраненное представление строки;
    • служебные поля: число корзин, число партий, текущая партия, учет памяти, временные файлы для отложенных партий.

    Сохраненная строка обычно представлена компактным MinimalTuple. Это не обязательно весь исходный кортеж со всеми колонками таблицы: под Hash поступает результат дочернего плана с нужными на данном уровне столбцами и выражениями. Однако служебный заголовок, указатель цепочки, выравнивание и таблица корзин тоже требуют памяти. Поэтому оценка по формуле число строк × ширина ключа сильно занизит размер.

    buckets[0] -> [hash=... | tuple] -> [hash=... | tuple] -> NULL
buckets[1] -> NULL
buckets[2] -> [hash=... | tuple] -> NULL
buckets[3] -> [hash=... | tuple] -> [hash=... | tuple] -> NULL

    В однопроцессном варианте PostgreSQL использует в том числе плотное выделение памяти для множества хеш-записей — dense_alloc(). Это уменьшает накладные расходы по сравнению с отдельным вызовом общего выделителя на каждую строку. Память организована через контексты PostgreSQL; отдельные контексты позволяют освобождать данные партии группой.

    1.3. От хеш-кода к корзине: почему нужны несколько проверок¶

    Для каждого ключа вычисляется хеш — 32-битное значение hashvalue в рассматриваемых структурах PostgreSQL 18. При составном ключе используются хеш-функции его составляющих с комбинированием результатов.

    Упрощенная схема выбора корзины при количестве корзин, равном степени двойки:

    bucket = hashvalue & (nbuckets - 1)

    Для примера возьмем всего восемь корзин и двоичный хеш 101101:

    nbuckets = 8
hashvalue = 101101₂ = 45
bucket = 45 & 7 = 5

    Реальный код работает с полноценными хешами и учитывает разбиение на партии. Здесь показываем только принцип выделения части битов.

    Теперь другой ключ дает хеш с теми же младшими тремя битами. Оба окажутся в корзине 5. Это коллизия корзины. Она еще не означает совпадение ключей.

    А если два различных значения действительно дали одинаковый полный хеш? Тогда даже сравнение hashvalue не позволит их различить.

    Поэтому поиск идет примерно так:

    1. Вычислить хеш ключей строки со стороны поиска.
    2. Найти нужную корзину.
    3. Пройти цепочку кандидатов этой корзины.
    4. Отбросить кандидатов с неподходящим hashvalue.
    5. Выполнить настоящее условие равенства Hash Cond для оставшихся кандидатов.
    6. Проверить дополнительные условия соединения, если они есть.
    7. Сформировать результирующую строку.

    Это важно: совпадение хеша никогда не подменяет SQL-равенство. Допустимые для хеш-соединения операторы и функции хеширования обязаны согласовываться: если два значения равны по оператору соединения, их хеши должны быть совместимы.

    1.4. Почему много одинаковых ключей опаснее простой коллизии¶

    Представим две таблицы, каждая содержит по 10 000 строк с ключом 42.

    A: 10 000 строк с key=42
B: 10 000 строк с key=42

    Обычный внутренний JOIN по равенству обязан вернуть:

    10 000 × 10 000 = 100 000 000 пар

    Здесь все строки действительно совпадают. Даже совершенная хеш-функция не может уменьшить обязательный объем результата.

    Теперь второй случай: множество разных ключей попадает в одну корзину, но не равны друг другу. Результата мало, а проверок кандидатов много. Становится дорогим именно проход по цепочкам и сравнение условий.

    Следовательно, различаем два вида перекоса:

    • Перекос частот ключей: один ключ встречается чрезвычайно часто и создает много реальных совпадений.
    • Перекос хеш-распределения: множество разных значений скапливается в части корзин или партий, увеличивая число проверок и неравномерность работы.

    Диагностировать их одинаково нельзя. При первом случае огромный результат может быть неизбежен. При втором важны хеш-распределение, селективность и особенности структур.

    1.5. В каком порядке вызываются узлы: конечный автомат Hash Join¶

    У ExecHashJoinImpl() есть состояние, которое сохраняется между обращениями родительского узла за следующей строкой. Это конечный автомат: набор состояний и правил перехода между ними.

    Основные состояния PostgreSQL 18:

    Состояние Назначение
    HJ_BUILD_HASHTABLE Построить хеш-таблицу внутренней стороны
    HJ_NEED_NEW_OUTER Получить следующую строку внешней стороны
    HJ_SCAN_BUCKET Просмотреть кандидатов подходящей корзины
    HJ_FILL_OUTER_TUPLE Если требуется, выдать внешнюю строку без совпадения
    HJ_FILL_INNER_TUPLES Если требуется, выдать оставшиеся внутренние строки без совпадений
    HJ_NEED_NEW_BATCH Перейти к следующей партии данных

    Для обычного INNER JOIN важнейшая последовательность:

    HJ_BUILD_HASHTABLE
        |
        v
HJ_NEED_NEW_OUTER -- нет строк --> конец текущей партии
        |
        v
HJ_SCAN_BUCKET -- найден кандидат --> проверка условий --> выдача пары
        |                                  |
        +-- есть еще кандидат <-----------+
        |
        +-- кандидаты закончились --> HJ_NEED_NEW_OUTER

    После выдачи очередной пары узел не забывает текущую строку поиска и позицию в цепочке. Следующий вызов продолжит обработку, а не построит хеш-таблицу заново.

    Для внешних, полу- и антисоединений появляются дополнительные переходы: учет того, была ли найдена пара, выдача строк с NULL и раннее прекращение поиска там, где это допускает семантика.

    1.6. Hash Cond, Join Filter и Filter: в какой момент пара считается совпавшей¶

    Рассмотрим:

    SELECT o.id, c.id
FROM orders AS o
LEFT JOIN customers AS c
  ON c.id = o.customer_id
 AND o.amount >= c.min_amount
WHERE o.status = 'PAID';

    Возможный фрагмент плана:

    Hash Left Join
  Hash Cond: (o.customer_id = c.id)
  Join Filter: (o.amount >= c.min_amount)
  -> Seq Scan on orders o
       Filter: (status = 'PAID')
  -> Hash
       -> Seq Scan on customers c

    Hash Cond используется для поиска кандидатов через хеш и проверки соответствующего равенства. Join Filter дополнительно определяет, удовлетворяет ли полученная пара условию ON. Для LEFT JOIN пара, отклоненная условием соединения, не засчитывается как найденное совпадение, поэтому при отсутствии других подходящих пар внешняя строка должна быть выдана с NULL на правой стороне.

    Обычный Filter действует на результат соответствующего узла; в приведенном плане условие статуса безопасно применено еще при чтении заказов.

    В исходниках nodeHashjoin.c важна граница между joinqual и otherqual: первая группа условий определяет факт совпадения для семантики внешних соединений, вторая — дальнейшую выдачу результата.

    1.7. Почему LIMIT 1 не делает Hash Join бесплатным¶

    Внешнее индексное сканирование иногда может почти сразу отдать первую строку. А хеш-соединение обычно должно сначала завершить построение хеш-таблицы внутренней стороны, прежде чем начать выдавать пары.

    Limit 1
  -> Hash Join
       -> Seq Scan on orders
       -> Hash
            -> Seq Scan on customers

    Даже если Limit остановит поиск после первой найденной пары, построение хеш-таблицы уже потребовало чтения внутреннего входа. При многопартийном соединении могут понадобиться и дополнительные подготовительные действия.

    Это не делает Hash Join неправильным: для полного результата или больших входов он может быть значительно дешевле альтернатив. Но теперь видно, почему startup_cost отличается от total_cost и почему LIMIT способен изменить выбор алгоритма еще на стадии планирования.

    Главное после раздела 1¶

    1. Хеш-таблица JOIN — временная структура конкретного исполнения, а не постоянный индекс.
    2. Корзина содержит цепочку кандидатов; совпадение хеша обязательно дополняется проверкой реального равенства.
    3. MinimalTuple, заголовки, указатели и массив корзин потребляют память помимо самих ключей.
    4. Повторяющиеся ключи могут создать огромный корректный результат; коллизии разных ключей создают лишние проверки.
    5. Hash Join работает как конечный автомат: построение, получение внешней строки, обход корзины, переход между партиями.
    6. Большая часть построения выполняется до первой выходной пары, поэтому маленький LIMIT не устраняет эту цену.

    2. Hash Join: партии, перераспределение и временные файлы¶

    2.1. Модель одной хеш-таблицы сломалась на памяти¶

    Пока все хорошо: построили таблицу клиентов, прошли по заказам, нашли совпадения. Но допустим, сторона построения состоит из миллиона широких строк.

    Для иллюстрации примем:

    Строк для построения:              1 000 000
Средний расход на хеш-запись:       100 байт (учебное допущение)
Только записи:                      около 100 МБ
Дополнительно:                      корзины, указатели, служебная память

    А бюджет хеш-операции — 8 МиБ. Все записи одновременно не помещаются.

    Основные параметры:

    SHOW work_mem;
SHOW hash_mem_multiplier;

    При стандартных значениях PostgreSQL 18:

    work_mem = 4MB
hash_mem_multiplier = 2.0

Расчетный бюджет хеш-операции ≈ 4 МиБ × 2 = 8 МиБ

    Этот бюджет относится к отдельной хеш-операции, а не ко всем SQL-запросам сервера. При параллельной работе и большом числе соединений совокупный расход может быть значительно выше. И это не абсолютный предел выделения памяти при любых аварийных распределениях: ниже увидим случай, когда исполнитель вынужден продолжать работу с превышением расчетного бюджета.

    Значит, нужна стратегия, которая использует оперативную память для одной части данных, а остальные обрабатывает позже.

    Эта стратегия называется многопартийное хеш-соединение (multi-batch hash join), а реализация сочетает работу в RAM с временными файлами — гибридное хеш-соединение.

    2.2. Корзина и партия: два разных уровня деления¶

    Корзина (bucket) — группа кандидатов для поиска внутри хеш-таблицы текущей партии.

    Партия (batch) — часть входных данных, которую будем обрабатывать отдельно, чтобы не хранить все строки в оперативной памяти одновременно.

    Для выбора обычно используются разные группы битов хеш-кода. Упрощенная модель:

    bucket = hashvalue & (nbuckets - 1)
batch  = (hashvalue >> log2(nbuckets)) & (nbatch - 1)

    Пусть nbuckets = 8, nbatch = 4, а хеш равен 101101₂ (45):

    Нижние 3 бита:  101₂ = 5       -> bucket 5
Следующие 2:    01₂  = 1       -> batch 1

    В PostgreSQL 18 настоящий расчет партии использует pg_rotate_right32(hashvalue, log2_nbuckets) & (nbatch - 1): циклический сдвиг вправо, а не обычный оператор >>. Для показанных небольших значений номера партии совпадают с учебной формулой, но в общем случае операции различаются. Количество корзин и партий выбирается как степень двойки. Вывод для студента: увеличение числа партий означает использование дополнительных разрядов уже вычисленных хешей, а не обязательное повторное вычисление SQL-ключей для каждого переноса.

    Ключи, которым нужен один и тот же номер партии, можно обрабатывать вместе. Разные партии допустимо обрабатывать последовательно, поскольку равные ключи должны получать совместимые хеши и попадать в одну партию.

    2.3. Как PostgreSQL выбирает первоначальное число партий¶

    ExecChooseHashTableSize() получает оценку числа строк внутреннего входа и их средней ширины. Затем оценивает размер одной хеш-записи, служебные расходы, память под массив корзин и допустимый объем памяти.

    В исходниках PostgreSQL 18 используются, в частности:

    • HJTUPLE_OVERHEAD — дополнительные байты хеш-записи;
    • MAXALIGN(...) — выравнивание;
    • NTUP_PER_BUCKET — целевое наполнение корзины, в рассматриваемом коде ориентир 1;
    • get_hash_memory_limit() — бюджет хеш-операции;
    • выбор числа корзин и партий, обычно степеней двойки.

    Условная оценка памяти:

    M_needed ≈ N_inner × (ширина сохраненной строки + накладные расходы)
           + nbuckets × размер указателя корзины

    Если M_needed <= M_hash, достаточно одной партии (Batches: 1). Если нет, выбирается несколько партий. Число нельзя безоговорочно вычислять как ceil(M_needed / M_hash): корзины, выравнивание, перекос значений и ограничения реализации меняют расчет.

    В нашем примере 100 МБ записей при бюджете 8 МиБ требуют существенно больше одной партии; в учебной модели ближайшая подходящая степень двойки могла бы быть 16 или 32. Реальное значение получит исполнитель на основе своей оценки размеров.

    2.4. Первый проход: что остается в RAM, а что записывается¶

    Рассмотрим первоначальные четыре партии. Исполнитель строит хеш-таблицу внутренней стороны. Записи, относящиеся к текущей партии 0, остаются в памяти. Записи будущих партий направляются во временные файлы.

    Внутренняя сторона (customers)
              |
         вычислить хеш
              |
       определить партию
              |
       +------+------+------+------+
       |             |             |
    batch 0       batch 1       batch 2/3
       |             |             |
       v             v             v
   Хеш-таблица    Временный    Временные
      в RAM         файл          файлы

    Затем читаются строки внешней стороны (orders). Для текущей партии выполняется обычный поиск по хеш-таблице. Строки, предназначенные для будущих партий, также сохраняются во временных файлах.

    Внешняя сторона (orders)
              |
      batch 0? ---- да ---> проверка по хеш-таблице в RAM
              |
             нет
              |
              v
        файл соответствующей партии

    Зачем сохранять обе стороны? Потому что для партии 1 нам позже понадобятся и ее построенная сторона, и ее строки поиска. Просто записать «лишних клиентов» недостаточно: при следующем проходе надо сопоставлять их с соответствующими заказами.

    В обычном непараллельном варианте для этих данных применяется временный файловый интерфейс BufFile, а сохранением записей занимается ExecHashJoinSaveTuple(). В паре со строкой сохраняется информация, позволяющая использовать вычисленный хеш при повторном чтении.

    2.5. Следующая партия: что конкретно делает ExecHashJoinNewBatch()¶

    Когда партия 0 закончилась, исполнитель не начинает исходный SQL заново.

    Он переходит к следующей партии:

    1. Очищает хеш-данные предыдущей партии, освобождая ее рабочую память.
    2. Выбирает следующую непустую партию с учетом семантики соединения.
    3. Загружает из временного файла строки внутренней стороны этой партии и строит для них хеш-таблицу.
    4. Читает соответствующие сохраненные строки внешней стороны.
    5. Ищет совпадения и выдает результат.
    6. Повторяет процесс до завершения всех партий.

    За переход отвечает ExecHashJoinNewBatch(), а состояние основного автомата — HJ_NEED_NEW_BATCH.

    Обрати внимание: рабочая хеш-таблица переиспользует бюджет памяти между партиями. Идея не в том, чтобы держать одновременно 32 независимые хеш-таблицы на 8 МиБ каждая. Обычно в памяти находится рабочая структура текущей партии, а не все партии сразу.

    2.6. Что происходит, если памяти не хватило уже во время построения¶

    Вот теперь основная проблема лекции. Планировщик рассчитал две партии, исходя из оцененных rows и width. Но фактические строки оказались шире или распределились хуже.

    Планировали: 2 партии
Начали строить партию 0
Получили слишком большой расход памяти

    В непараллельной реализации вызывается ExecHashIncreaseNumBatches(). Число партий может удваиваться:

    2 -> 4 -> 8 -> 16 -> 32

    Но это не просто изменение числа в структуре.

    Исполнитель должен перераспределить уже сохраненные в оперативной памяти хеш-записи по новой схеме партий:

    • то, что по-прежнему принадлежит текущей партии, остается в RAM;
    • то, что оказалось в другой партии, записывается в соответствующий временный файл;
    • освобожденная память уменьшает размер текущей хеш-таблицы;
    • новые поступающие строки распределяются по новой схеме.

    Уже записанные в старые файлы записи нельзя считать навсегда классифицированными по новой схеме. При последующей обработке файлов данные могут дополнительно перераспределяться с учетом выросшего nbatch. Поэтому реальная стоимость роста партий — это не только один перенос по памяти, но и возможный дополнительный временный ввод-вывод.

    2.7. Разберем перераспределение на битах¶

    Пусть для простоты три младших бита хеша выбирают корзину. При nbatch = 2 для партии используется один следующий бит.

    bucket: bits 0..2
batch:  bit 3

    При увеличении до nbatch = 4 используется еще один бит:

    bucket: bits 0..2
batch:  bits 3..4

    Тогда прежняя партия 0 разделится на новую 0 и новую 2, а прежняя партия 1 — на новую 1 и 3. В общем случае разделение происходит за счет новых разрядов хеша.

    Например, запись с hashvalue = 0b100101:

    hashvalue = 37
bucket = 37 & 7 = 5

При nbatch = 2:
  batch = (37 >> 3) & 1 = 0

При nbatch = 4:
  batch = (37 >> 3) & 3 = 0

    А запись с hashvalue = 0b101101 (45):

    bucket = 45 & 7 = 5

При nbatch = 2:
  batch = (45 >> 3) & 1 = 1

При nbatch = 4:
  batch = (45 >> 3) & 3 = 1

    Чтобы увидеть перенос именно при удвоении, возьмем hashvalue = 0b10000 (16):

    bucket = 16 & 7 = 0

При nbatch = 2:
  batch = (16 >> 3) & 1 = 0

При nbatch = 4:
  batch = (16 >> 3) & 3 = 2

    Эта запись раньше относилась к партии 0, а теперь к партии 2. Ее придется отложить.

    Это иллюстрация распределения битов, а не трассировка точных значений хеш-функций PostgreSQL для конкретного типа данных.

    2.8. Почему Batches: 32 (originally 2) — действительно важный симптом¶

    Условный план:

    Hash Join
  Hash Cond: (o.customer_id = c.id)
  Buffers: temp read=16000 written=16000
  -> Seq Scan on orders o
  -> Hash
       Buckets: 65536
       Batches: 32 (originally 2)
       Memory Usage: 8192kB
       -> Seq Scan on customers c

    Он показывает три наблюдения:

    • Buckets: 65536 — число корзин хеш-таблицы, используемое при выполнении;
    • Batches: 32 (originally 2) — фактическое число партий выросло относительно первоначального;
    • Memory Usage: 8192kB — измеренная память хеш-структуры, а не суммарная память всего SQL-запроса.

    Buffers: temp read/written относится к временным рабочим блокам, которые могут использоваться этим соединением и включенными в него узлами. Цифры условные: они не обязаны быть пропорциональными Batches, поскольку размер записей, количество проходов и другие операции влияют на объем.

    Ключевой момент: Batches = 32 не означает, что PostgreSQL 32 раза полностью прочитал исходную таблицу orders и 32 раза исходную таблицу customers. В типичной схеме исходные входы читаются для первоначального разбиения, а затем обрабатываются сохраненные данные отдельных партий. Дополнительный ввод-вывод приходится на временные файлы и возможное перераспределение.

    2.9. Перекос, который нельзя исправить дальнейшим увеличением партий¶

    Теперь специально ломаем идею «не поместилось — делим еще».

    Предположим, большая часть строк имеет одинаковый ключ и одинаковый полный хеш. При любом увеличении числа партий такие строки продолжат попадать в одну партию.

    batch 0: 1 000 000 строк с hash = H
batch 1: 0

Удвоили число партий:
  batch 0: 1 000 000 строк с hash = H
  новые партии: 0

    Увеличение nbatch не помогает, поскольку одинаковые хеши не могут быть разбросаны по разным партиям без нарушения гарантии нахождения совпадений.

    В реализации PostgreSQL предусмотрена защита: если при перераспределении не освобождено ни одной записи или освобождены все записи, это указывает, что дальнейшее дробление не улучшает распределение. Тогда рост числа партий отключается.

    Но куда девать записи, которые все равно не помещаются?

    В этом исключительном случае исполнитель может продолжить работу с превышением расчетного бюджета памяти. Это осознанный компромисс ради завершения соединения. Поэтому work_mem × hash_mem_multiplier — бюджет планирования рабочих структур, а не обещание, что при любом распределении процесс никогда не превысит это значение.

    2.10. Оптимизация перекоса по частым значениям¶

    В непараллельном многопартийном Hash Join PostgreSQL имеет специальный механизм для популярных значений внешней стороны: хеш-структуру для перекошенных значений (skew hash table).

    Идея следующая. Если во внешнем потоке значительная доля строк имеет несколько особо популярных ключей, выгодно удерживать соответствующие записи внутренней стороны в памяти и обрабатывать эти внешние строки в первой партии, не отправляя их во временные файлы.

    Для выбора пригодных значений могут использоваться MCV-статистики внешнего отношения. Причем в исходниках предусмотрен ограниченный бюджет этой специальной структуры, а при нехватке места число обслуживаемых MCV сокращается.

    Зачем опираться на популярность внешних значений? Потому что экономия временного ввода-вывода особенно велика, когда одно значение очень часто приходит со стороны поиска.

    Но это оптимизация конкретного перекоса, а не универсальное решение. Если большая группа внутренних строк сама по себе не помещается в память и содержит один и тот же хеш, проблема принципиально сложнее.

    2.11. Что измерять при многопартийном Hash Join¶

    Основной запрос для диагностики:

    EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
SELECT o.id, c.id
FROM orders o
JOIN customers c ON c.id = o.customer_id;

    Смотрим не только имя алгоритма, а причинную цепочку:

    Симптом Вопрос Где искать ответ
    Batches > 1 Почему данные не помещаются в одну рабочую таблицу? Размер и ширина внутреннего входа, бюджет памяти
    Batches выросло Почему первоначальной оценки не хватило? rows/actual rows, ширина, распределение хешей
    Много temp read/written Сколько работы выполняется через временные файлы? BUFFERS, статистика временного ввода-вывода
    Большой Join Filter Не приходится ли многократно проверять дополнительные условия? Rows Removed by Join Filter, фактические пары
    Нормальные rows, но высокая задержка Что стоило дорого после оценки количества строк? Временный ввод-вывод, CPU, число совпадений, конкуренция

    На уровне базы доступны статистика временных файлов pg_stat_database.temp_files, temp_bytes; для конкретных запросов полезны показатели временных блоков в pg_stat_statements, если расширение установлено. Настройка log_temp_files позволяет регистрировать временные файлы по установленному порогу. При включенном track_io_timing можно сопоставить обращения с измеренным временем ввода-вывода.

    Нельзя автоматически «лечить» любое многопартийное соединение глобальным увеличением work_mem: несколько запросов и несколько хеш-операций могут одновременно потребовать память. Сначала нужно установить, нет ли ошибки оценки строк, слишком широкого промежуточного результата или резкого перекоса ключей.

    Главное после раздела 2¶

    1. Buckets определяет поиск внутри текущей хеш-таблицы; Batches делит входные данные на последовательно обрабатываемые части.
    2. Первоначальное число партий рассчитывается по оценке объема и памяти; оно может оказаться неправильным.
    3. Рост Batches означает перераспределение хеш-записей и дополнительную работу с временными файлами, а не просто смену счетчика.
    4. Временные файлы содержат отложенные записи обеих сторон соединения.
    5. Одинаковые хеши нельзя бесконечно разделять: при неэффективности роста PostgreSQL отключает дальнейшее дробление.
    6. Оптимизация популярных значений может уменьшить временный ввод-вывод, но не устраняет цену огромного корректного результата JOIN.
    7. Под нагрузкой оцениваем одновременно память, временный ввод-вывод, распределение ключей и количество выходных пар.

    3. Nested Loop Internals: повторные запуски и передача параметров¶

    3.1. Почему простой вложенный цикл остается важным алгоритмом¶

    Хеш-соединение обменяло повторные поиски на память и предварительную подготовку. Но теперь предположим, что внешняя сторона содержит всего десять клиентов, а по заказам существует индекс orders(customer_id).

    Зачем строить хеш-таблицу или читать все заказы, если можно выполнить десять коротких индексных поисков?

    SELECT c.id, o.id
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE c.segment = 'VIP';

    Возможный план:

    Nested Loop
  -> Seq Scan on customers c
       Filter: (segment = 'VIP')
  -> Index Scan using orders_customer_id_idx on orders o
       Index Cond: (customer_id = c.id)

    Алгоритм вложенных циклов не требует отдельной большой структуры для соединения. Но ему нужен механизм: как внутренний индексный узел узнает c.id очередной внешней строки, если исходный SQL содержит сравнение двух таблиц?

    3.2. Параметризованное сканирование: от c.id к ключу индекса¶

    Упрощенный цикл исполнителя:

    Получить клиента c
  |
  v
Запомнить c.id в параметрах исполнения
  |
  v
Подготовить внутренний Index Scan к новому поиску
  |
  v
Выдать все заказы, удовлетворяющие o.customer_id = c.id
  |
  v
Получить следующего клиента

    В PostgreSQL 18 это реализовано в nodeNestloop.c. Для соответствующего плана используется перечень параметров nestParams: элементы типа NestLoopParam связывают выражения внешней строки с внутренними параметрами исполнения.

    Сокращенная по смыслу последовательность настоящего кода:

    /* Пример из механизма ExecNestLoop(), сокращено. */
foreach(lc, nl->nestParams)
{
    NestLoopParam *nlp = (NestLoopParam *) lfirst(lc);
    ParamExecData *prm =
        &econtext->ecxt_param_exec_vals[nlp->paramno];

    prm->value = slot_getattr(outerTupleSlot,
                              nlp->paramval->varattno,
                              &prm->isnull);

    innerPlan->chgParam =
        bms_add_member(innerPlan->chgParam, nlp->paramno);
}
ExecReScan(innerPlan);

    Здесь:

    • TupleTableSlot — объект, через который узел передает текущую строку и ее значения;
    • ParamExecData — слот для значения параметра на уровне исполнителя;
    • chgParam — признак, что определенные параметры изменились и зависящему от них узлу требуется соответствующая повторная подготовка;
    • ExecReScan() — запрос повторного выполнения/перезапуска внутреннего узла с актуальными параметрами.

    После этого Index Scan использует новое значение в своем индексном условии.

    Это не отправка нового SQL по сети. Все происходит внутри одного backend-процесса, исполняющего уже подготовленное дерево плана. И не нужно путать ParamExecData с $1 клиентского подготовленного запроса: здесь речь о внутренних параметрах, передаваемых между узлами одного плана.

    3.3. Что именно означает ExecReScan()¶

    Наивная модель: «перезапуск = заново создать объект узла». Она неверна.

    Обычно ExecReScan() возвращает уже существующий узел исполнения в состояние, позволяющее снова выдавать строки. Например, для индексного поиска это означает обновление необходимых ключей и положения обхода; для Materialize — возможное возвращение к сохраненному потоку; для Memoize — поиск результата для новых параметров.

    Поэтому два одинаковых по числу loops плана могут делать принципиально разную физическую работу. В одном случае 100 000 loops — сто тысяч обращений к страницам индекса. В другом — сто тысяч дешевых повторных чтений сохраненного результата.

    Перезапуск — это семантика интерфейса исполнителя, а фактическая цена определяется видом дочернего узла.

    3.4. Разбор loops на конкретном плане¶

    Условный пример:

    Nested Loop
  (actual time=0.030..7500.000 rows=200000 loops=1)
  -> Seq Scan on customers c
       (actual time=0.010..110.000 rows=100000 loops=1)
  -> Index Scan using orders_customer_id_idx on orders o
       (actual time=0.012..0.070 rows=2 loops=100000)
       Index Cond: (customer_id = c.id)

    Разберем без спешки.

    Внешний Seq Scan: loops=1, получил 100 000 клиентов за один запуск.

    Внутренний Index Scan: loops=100000 — фактически выполнил сто тысяч индексных поисков. rows=2 — среднее число выданных строк за один запуск, поэтому общий результат сканирования приблизительно:

    2 × 100 000 = 200 000 строк

    actual time=0.012..0.070 — среднее время до первой строки и до завершения одного запуска внутреннего узла. Сумма времен его запусков приблизительно:

    0.070 мс × 100 000 = 7 000 мс

    Вот почему показатель 0.070 мс нельзя читать в отрыве от loops: общая работа заняла секунды, хотя отдельный поиск выглядит быстрым.

    Однако это не дополнительные семь секунд поверх actual time родительского Nested Loop. Измерение родителя уже включает работу дочерних узлов. И при параллельной работе сумма времен разных исполнителей не равна задержке запроса по настенным часам.

    3.5. Как число внешних строк превращается в стоимость¶

    Учебная модель:

    C_nested ≈ C_outer + N_outer × C_inner_search + C_pair_checks

    Пусть внешних клиентов 100, индексный поиск стоит 5 условных единиц, а получение клиентов — 100 единиц:

    C_nested ≈ 100 + 100 × 5 = 600

    Если фактически внешних строк 100 000:

    C_nested ≈ 100 + 100 000 × 5 = 500 100

    Вот почему ошибка планировщика в rows внешнего набора способна радикально ухудшить выбранный Nested Loop.

    Но это только первая модель. Реальный планировщик различает стоимость первого исполнения внутреннего пути и повторных запусков, учитывает cost_rescan(), параметризованный доступ, возможную материализацию или кеширование, а также раннюю остановку для соответствующих соединений.

    Следовательно, не надо брать total_cost внутреннего Index Scan из EXPLAIN, механически умножать его на видимый loops и прибавлять к cost родительского Nested Loop. В стоимости родителя ожидаемые повторения уже учтены на этапе планирования.

    3.6. Как изменяют работу SEMI, ANTI и LEFT¶

    У INNER JOIN исполнитель должен выдать все подходящие пары.

    У полусоединения (SEMI JOIN) для каждой внешней строки достаточно первого совпадения. При подходящем способе доступа внутренний поиск может прекратиться раньше.

    Для антисоединения (ANTI JOIN) первое совпадение исключает внешнюю строку. Но чтобы доказать отсутствие совпадений, часто приходится исчерпать внутренний поиск для данного ключа.

    При LEFT JOIN после отсутствия подходящих пар нужно сформировать внешнюю строку с NULL на правой стороне.

    Соответствующая логика находится непосредственно в ExecNestLoop(): сохраняется факт nl_MatchedOuter, проверяются условия соединения и дополнительные фильтры, при необходимости создается строка с пустой внутренней стороной.

    Цена зависит и от доли внешних строк, имеющих совпадения, и от того, как быстро можно обнаружить совпадение или убедиться в его отсутствии. Поэтому одинаковое количество внешних строк еще не означает одинаковую стоимость вложенных циклов.

    3.7. Почему loops > 1 не принадлежит только Nested Loop¶

    В EXPLAIN ANALYZE loops показывает количество выполнений любого узла, а не количество строк в таблице и не число SQL-запросов со стороны приложения.

    Примеры:

    Seq Scan on orders (... rows=1000000 loops=1)

    Один полный проход по миллиону строк — один запуск.

    Index Scan on orders (... rows=2 loops=100000)

    Сто тысяч отдельных запусков, в среднем по две выходные строки.

    Коррелированный подзапрос может запускаться для каждой строки внешнего источника без явного JOIN в тексте SQL. В параллельных планах один и тот же тип узла может выполняться несколькими процессами. В рекурсивных запросах рабочий набор может сканироваться по итерациям.

    Главный вопрос к loops: кто инициирует повторения и какая работа повторяется фактически? В ответе часто обнаруживается дорогой дочерний узел, а иногда — удачное кеширование, которое делает повторения дешевыми.

    Главное после раздела 3¶

    1. В Nested Loop внешняя строка передает значение во внутренний план через параметры исполнения.
    2. NestLoopParam, ParamExecData, chgParam и ExecReScan() обеспечивают повторный параметризованный поиск.
    3. ExecReScan() переиспользует узлы плана; он не обязан заново создавать исполнителя или повторять всю физическую работу.
    4. actual rows и actual time внутри узла показываются в среднем на запуск; loops нужен для понимания суммарной работы.
    5. loops бывает у любых повторно исполняемых узлов, не только у соединений.
    6. Полу- и антисоединения могут прекращать поиск при первом совпадении, а отрицательная проверка без подходящего индекса остается дорогой.

    4. Materialize и Memoize: два принципиально разных способа экономить повторную работу¶

    4.1. Если внутренний источник придется читать сто тысяч раз¶

    В предыдущем разделе мы поняли, что Nested Loop повторно обращается к внутреннему узлу. Но что если внутренняя сторона получает один и тот же поток при каждом повторе?

    Например:

    Nested Loop
  -> Seq Scan on small_a
  -> Materialize
       -> Seq Scan on small_b

    Можно прочитать small_b один раз и сохранять полученные строки для повторной выдачи. Так работает Materialize.

    А если каждый повтор получает разный параметр, но значения параметров часто повторяются? Тогда нужен другой механизм: кеш «значение параметра → результат соответствующего поиска». Это Memoize.

    Здесь важно не смешать две абстракции:

    Materialize: один поток -> сохранить -> перечитывать
Memoize:    ключ параметров -> список результатов для этого ключа

    4.2. Materialize: буферизация потока через tuplestore¶

    Узел Materialize (nodeMaterial.c) использует структуру tuplestore. Она может хранить промежуточные строки в оперативной памяти и, когда нужно, переносить данные во временный файл.

    В коде для подходящих режимов создается примерно такая структура:

    tuplestore_begin_heap(true, false, work_mem);

    Первый раз родитель запрашивает строку. Если она еще не сохранена, Materialize берет ее у дочернего узла и помещает в tuplestore. Когда родитель просит следующую строку, процесс продолжается. При повторном обходе уже полученные строки можно выдавать из хранилища.

    Materialize не обязан обязательно прочитать весь вход заранее. Он может сохранять строки постепенно, по мере того как их требует родитель. Если первое выполнение дочернего источника прервалось раньше, состояние и объем сохраненных данных определяют поведение следующих обращений.

    У tuplestore есть указатели чтения, возможность возврата к началу или к отмеченной позиции при соответствующих настройках. Поэтому он полезен не только для Nested Loop, но и для узлов, которым нужно возвращаться к уже прочитанным строкам, например в некоторых вариантах Merge Join.

    4.3. Почему Materialize экономит I/O, но не всегда экономит CPU¶

    Предположим, внутренняя таблица содержит 1000 строк, внешний источник — 10 000 строк.

    Без сохранения могло бы потребоваться заново прочитать те же 1000 строк для каждого внешнего значения.

    С материализацией исходный дочерний Seq Scan может выполниться один раз, а сохраненный поток — повторно выдаваться тысячи раз:

    Nested Loop
  -> Seq Scan on a
       (actual rows=10000 loops=1)
  -> Materialize
       (actual rows=1000 loops=10000)
       -> Seq Scan on b
            (actual rows=1000 loops=1)

    Числа условные и предполагают, что каждый повтор действительно потребляет весь сохраненный поток.

    Materialize избавил от десяти тысяч повторных чтений исходной таблицы, но не от десяти миллионов выдач сохраненных строк:

    1000 × 10000 = 10 000 000

    Если над ними нужно проверить условие соединения, соответствующая CPU-работа остается.

    А если tuplestore не помещается в рабочую память, он может использовать временный файл. Тогда экономия повторных обращений к исходной таблице частично обменивается на временный ввод-вывод и копирование промежуточных строк.

    4.4. Почему Materialize нельзя просто использовать для любых параметров¶

    Предположим, внутренний поиск зависит от текущего клиента:

    WHERE orders.customer_id = c.id

    Если сохранить результаты для клиента 1 и затем без проверки параметра вернуть их клиенту 2, получится неправильный результат.

    Следовательно, сам по себе Materialize не реализует кеш по параметрам. При изменении условий, влияющих на вход, хранилище должно быть корректно сброшено или пересоздано. Для выгодного повторного использования отдельных результатов разных ключей предназначен Memoize.

    Еще один терминологический момент: узел плана Materialize не равен конструкции WITH ... AS MATERIALIZED в SQL. Сходство названия не означает тождество назначения и поведения.

    4.5. Memoize: кеширование результата параметризованного поиска¶

    Теперь возьмем события и клиентов.

    logs:       100 000 строк
customers:     200 различных клиентов среди этих событий

    Запрос:

    SELECT e.id, c.name
FROM events AS e
JOIN customers AS c ON c.id = e.customer_id;

    Пусть планировщик выбрал Nested Loop, а внутренний поиск выполняется по первичному ключу клиента.

    Без кеша можно получить 100 000 индексных поисков. Но большинство событий ссылается на тех же 200 клиентов. Зачем каждый раз снова идти в индекс?

    Возможный план:

    Nested Loop
  -> Seq Scan on events e
  -> Memoize
       Cache Key: e.customer_id
       Cache Mode: logical
       Hits: 99800  Misses: 200  Evictions: 0  Overflows: 0
       Memory Usage: 30kB
       -> Index Scan using customers_pkey on customers c
            Index Cond: (id = e.customer_id)

    Это условные диагностические числа, показывающие работу кеша, когда все 200 ключей помещаются в память и каждый ключ впервые встречается ровно один раз.

    Механизм:

    1. Внешний источник передал параметр customer_id=7.
    2. Memoize проверил свой кеш. Записи нет — Miss.
    3. Выполнился внутренний Index Scan, полученный результат был сохранен под ключом 7.
    4. Встретился еще один customer_id=7.
    5. Memoize вернул сохраненные строки — Hit, без нового индексного поиска.
    6. Встретился customer_id=12 — отдельный ключ и отдельная запись кеша.

    При достаточной памяти число фактических запусков дочернего индексного поиска способно приблизиться к числу различных параметров, а не к количеству внешних строк.

    4.6. Что именно находится в Memoize¶

    В nodeMemoize.c используются собственная хеш-таблица кеша и структуры MemoizeKey, MemoizeEntry, MemoizeTuple.

    Учебное представление:

    Ключ параметров = (customer_id=7)
             |
             v
   MemoizeEntry { complete: true }
             |
             v
       [результат 1] -> [результат 2] -> ...

    Ключ может состоять из нескольких параметров. Кешируется набор строк результата внутреннего узла, а не только факт существования ключа. Для одного значения параметра может быть ноль, одна или несколько строк.

    Отсюда важный случай: нулевой результат тоже может кешироваться. Если для клиента с данным ключом ничего не найдено, повторная проверка того же ключа может закончиться попаданием в кеш с пустым результатом. Это особенно полезно, когда внешние строки часто ссылаются на отсутствующие значения и семантика запроса допускает такую проверку.

    Cache Mode: logical означает, что ключи сравниваются с использованием соответствующей логики равенства; Cache Mode: binary использует сравнение представления значений, пригодное для некоторых параметризованных сценариев. Конкретный режим выбирается планировщиком, а не оператором приложения.

    Кеш Memoize существует для соответствующего узла и выполнения запроса. Он не общий между запросами и сессиями и не является заменой shared_buffers, Redis или постоянного индекса.

    4.7. Почему у Memoize есть признак complete¶

    Теперь неприятный сценарий.

    При SEMI JOIN исполнителю иногда достаточно получить первую подходящую строку. Он может прервать чтение внутреннего узла, даже если для ключа существует двадцать строк.

    Предположим, Memoize сохранил только первую строку, а затем выполнение прекратилось. Если в следующем обращении вернуть эту запись как полный результат поиска, остальные девятнадцать строк потеряются.

    Поэтому в MemoizeEntry есть признак завершенности (complete). Пока дочерний источник не исчерпан, кеш не обязательно содержит все результаты данного ключа.

    Для некоторых случаев планировщик заранее знает, что по ключу может быть не более одной строки. Тогда применяется специальная оптимизация singlerow, позволяющая считать запись полной после первого результата.

    Общее правило: попадание по ключу полезно только тогда, когда сохраненный результат подходит для семантики текущего повторного чтения. Незавершенная запись не должна молча выдавать частичный результат как полный.

    4.8. Ограничение памяти, LRU и вытеснение¶

    Кеш не может расти бесконечно. В Memoize применяется ограничение памяти и вытеснение наименее недавно использованных записей (LRU).

    В реализации есть двусвязный список порядка использования. Новая запись добавляется в его конец. При попадании запись перемещается туда же. Когда память заканчивается, в первую очередь удаляются старые записи с начала списка.

    Самая старая запись                   Самая недавно использованная
      key=3  <->  key=5  <->  key=7  <->  key=12
        ^                                      ^
   кандидат на                               последний
    вытеснение                                 Hit

    Таким образом Memoize сохраняет часто повторяющиеся недавние результаты, но при огромном числе уникальных параметров начинает постоянно промахиваться и вытеснять записи.

    В EXPLAIN тогда растет Evictions. Это не ошибка корректности: после вытеснения нужный результат можно заново получить из дочернего плана. Но цена кеширования увеличивается, а выгода уменьшается.

    4.9. Что такое Overflows: даже одну запись не удается сохранить¶

    А теперь проблема серьезнее, чем заполненный кеш.

    Допустим, для одного ключа внутренний источник возвращает огромный набор строк, который не помещается в доступную кешу память. Вытеснение остальных ключей уже не помогает: текущая запись сама слишком большая.

    В таком случае Memoize может очистить недостроенную запись и перейти в режим обхода кеша (MEMO_CACHE_BYPASS_MODE) для текущего сканирования. Последующие строки передаются из дочернего источника без попыток сохранить весь результат в кеш.

    В диагностике растет Overflows.

    Принципиальное отличие от Hash Join: Memoize при нехватке памяти не раскладывает кешируемые результаты по партиям на диск. Он вытесняет старые записи или обходит кеш. Hash Join может использовать временные партии, Materialize — временное хранилище tuplestore, а Memoize сохраняет свои результаты только в пределах доступной кешу памяти.

    4.10. Когда Memoize действительно выгоден¶

    Для оценки полезно считать частоту попаданий:

    Hit rate = Hits / (Hits + Misses)

    Например:

    Hits:   99 800
Misses:    200

Hit rate = 99 800 / 100 000 = 99.8%

    При таких вводных повторные параметры почти всегда обслуживаются из кеша.

    А теперь другая таблица: 100 000 событий и почти 100 000 различных customer_id. Тогда большинство поисков выполняется впервые. Мы платим за хеширование параметров, учет записей и попытки кеширования, но почти не экономим индексные поиски.

    Особенно важны:

    • число различных значений параметров;
    • повторяемость значений и порядок их появления;
    • средний размер результата для одного ключа;
    • доступный объем памяти;
    • стоимость промаха — насколько дорог сам внутренний поиск.

    Частота попаданий сама по себе не равна ускорению. Кешировать очень дешевую операцию может быть невыгодно, а небольшая доля попаданий в крайне дорогой внутренний источник иногда все равно полезна.

    4.11. Сводное сравнение Materialize и Memoize¶

    Свойство Materialize Memoize

    Главное после раздела 4¶

    1. Materialize сохраняет поток и допускает его повторное чтение; заполнение может быть постепенным.
    2. Memoize сохраняет результаты отдельно по значениям параметров и способен резко сократить реальные индексные поиски.
    3. Materialize может использовать временные файлы; Memoize при нехватке памяти применяет LRU или обходит кеш.
    4. complete защищает от неправильного повторного использования частично заполненной записи.
    5. Высокий loops на Memoize при малом loops дочернего Index Scan — признак успешного устранения повторных поисков.
    6. Повторяющиеся ключи помогают Memoize, а почти уникальные ключи делают его менее выгодным.

    5. Merge Join Internals: состояния, повторяющиеся ключи и возврат позиции¶

    5.1. Почему для двух упорядоченных потоков хеш-таблица не нужна¶

    Предположим, оба входа уже упорядочены по ключу соединения:

    A: 1, 2, 4, 6
B: 2, 3, 4, 5

    Можно сравнивать текущие ключи двух потоков. Если слева меньше, продвигаем левую сторону. Если справа меньше — правую. Если ключи равны — выдаем подходящую пару.

    A=1, B=2  -> A меньше, двигаем A
A=2, B=2  -> совпадение, выдать пару
A=4, B=3  -> B меньше, двигаем B
A=4, B=4  -> совпадение, выдать пару

    Если ключи уникальны и нужный порядок уже обеспечен, основной проход очень дешев: число перемещений имеет порядок N_A + N_B.

    Но как только появляются повторяющиеся ключи, одних двух монотонно движущихся указателей недостаточно. Именно ради них в PostgreSQL есть механизм сохранения и восстановления позиции.

    5.2. Что требует Merge Join от входов¶

    Потоки должны быть упорядочены совместимым способом по ключам Merge Cond. Требуются подходящие правила сравнения, направление сортировки и обработка NULL. Для составного условия рассматриваются несколько ключей в согласованном порядке.

    Схематичный план:

    Merge Join
  Merge Cond: (o.customer_id = c.id)
  -> Index Scan using orders_customer_id_idx on orders o
  -> Index Scan using customers_pkey on customers c

    Или:

    Merge Join
  Merge Cond: (o.customer_id = c.id)
  -> Sort
       Sort Key: o.customer_id
       -> Seq Scan on orders o
  -> Sort
       Sort Key: c.id
       -> Seq Scan on customers c

    Здесь цена самого соединения должна рассматриваться вместе с ценой получения упорядоченных входов. Если нужны две большие сортировки, дешевый последовательный обход может начаться только после дорогой подготовительной работы.

    5.3. Разберем дубликаты вручную¶

    Пусть слева и справа находятся разные строки с одинаковыми ключами:

    Левая сторона (A):
  A1(key=1)
  A2(key=1)
  A3(key=2)
  A4(key=4)

Правая сторона (B):
  B1(key=1)
  B2(key=1)
  B3(key=1)
  B4(key=3)
  B5(key=4)

    Для ключа 1 нам требуется:

    (A1,B1), (A1,B2), (A1,B3)
(A2,B1), (A2,B2), (A2,B3)

    Это шесть пар — 2 × 3.

    Пройдем состояние вручную:

    Шаг Текущая левая Правая Действие
    1 A1(1) B1(1) Ключи равны. Запоминаем позицию B1; выдаем (A1,B1)
    2 A1(1) B2(1) Выдаем (A1,B2)
    3 A1(1) B3(1) Выдаем (A1,B3)
    4 A1(1) B4(3) Группа справа закончилась. Продвигаем левую сторону
    5 A2(1) B4(3) Ключ A2 равен сохраненному ключу 1; возвращаем правую позицию к B1
    6 A2(1) B1(1) Выдаем (A2,B1)
    7 A2(1) B2(1) Выдаем (A2,B2)
    8 A2(1) B3(1) Выдаем (A2,B3)
    9 A3(2) B4(3) A меньше, продвигаем A
    10 A4(4) B4(3) B меньше, продвигаем B
    11 A4(4) B5(4) Выдаем (A4,B5)

    Важна не точная последовательность служебных переходов на каждом байте, а необходимость возврата правого потока к началу группы. Иначе пары для A2 были бы потеряны.

    5.4. ExecMarkPos() и ExecRestrPos()¶

    В PostgreSQL для сохранения позиции внутреннего потока используется интерфейс:

    ExecMarkPos()  — запомнить позицию
ExecRestrPos() — восстановить ранее отмеченную позицию

    Узел Merge Join вызывает эти операции для внутреннего дочернего узла там, где нужны повторные проходы по группе совпадений.

    Но тут возникает новый вопрос: любой дочерний узел поддерживает возврат к уже выданным строкам?

    Нет. Поэтому внутренний путь для соединения слиянием должен иметь подходящую возможность сохранения/восстановления позиции. Иногда такую возможность дает сам способ чтения, иногда полезен дополнительный Materialize и его tuplestore. В определенных случаях планировщик знает, что возврат не потребуется, и может использовать вариант без этих операций.

    Значит, Materialize около Merge Join не является загадочной лишней копией таблицы. Он может выполнять вполне конкретную роль: предоставить возможность повторно прочитать группу строк.

    5.5. Merge Join как конечный автомат¶

    nodeMergejoin.c реализует несколько состояний, которые сохраняются между запросами очередной результирующей строки.

    5.6. Почему Merge Cond и Join Filter — разные этапы¶

    Например:

    SELECT *
FROM a
JOIN b
  ON a.key = b.key
 AND a.amount > b.threshold;

    Возможный план:

    Merge Join
  Merge Cond: (a.key = b.key)
  Join Filter: (a.amount > b.threshold)
  -> Sort ...
  -> Sort ...

    Merge Cond позволяет сопоставлять упорядоченные потоки по ключу. Join Filter проверяет дополнительное условие уже для пары-кандидата.

    Если один ключ встречается по тысяче раз с обеих сторон, получится до миллиона кандидатов для дополнительной проверки. Даже если Join Filter оставит всего сто пар, миллион проверок мог уже быть выполнен.

    Поэтому диагностический показатель Rows Removed by Join Filter важен: он может раскрыть большой объем работы после того, как основные ключи успешно сопоставились.

    5.7. Почему actual rows бывает больше числа физических строк¶

    Допустим, Merge Join вынужден повторно читать группу правых строк для нескольких одинаковых левых ключей. Внутренний узел может выдавать одни и те же сохраненные строки несколько раз.

    В EXPLAIN ANALYZE количество фактически выданных строк отражает выдачи узла, а не обязательно число различных физических строк исходной таблицы. Поэтому для некоторых узлов внутри соединения слиянием число выдач может быть больше исходного объема.

    Здесь снова нужно разбирать сочетание rows, actual rows, loops и позиции узла в дереве. Повторная выдача строки, дополнительный запуск узла и новое физическое чтение страницы — три разных события.

    5.8. Когда Merge Join становится дорогим¶

    Первый случай — требуется сортировать оба больших входа. Тогда цена входных Sort может оказаться выше цены соединения, особенно при внешней сортировке с временными файлами.

    Второй — много повторяющихся ключей. Тогда растут число формируемых пар и количество повторных чтений групп.

    Третий — дополнительные условия отклоняют большинство пар. Тогда исполнитель все равно выполняет сравнения и фильтрацию большого числа кандидатов.

    Четвертый — узел, обеспечивающий возврат к отмеченной позиции, сам требует памяти или временного ввода-вывода.

    Для заранее отсортированных данных и умеренного числа совпадений полезна модель:

    Работа Merge Join ≈ обход обоих входов + число формируемых/проверяемых пар

    Но это не основание автоматически присваивать алгоритму стоимость N + M независимо от количества повторений и требований к подготовке данных.

    Главное после раздела 5¶

    1. Merge Join сопоставляет два совместимо упорядоченных потока.
    2. При уникальных ключах основная работа близка к последовательному обходу двух входов.
    3. Повторяющиеся ключи требуют выдачи всех комбинаций соответствующих строк.
    4. Для повторных групп нужен механизм сохранения и восстановления позиции правого потока: ExecMarkPos() и ExecRestrPos().
    5. Не каждый дочерний узел способен возвращаться назад; для этого может понадобиться Materialize.
    6. Состояния EXEC_MJ_* показывают, как исполнитель сохраняет прогресс между выдачами результирующих строк.
    7. Стоимость сортировки и повторных групп может перевесить выгоду от последовательного сопоставления.

    6. Параллельное выполнение JOIN: общий хеш и цена синхронизации¶

    6.1. Почему четыре процесса не означают ускорение в четыре раза¶

    Теперь у нас четыре ядра, условно несколько миллионов строк для соединения и возможность запустить несколько рабочих процессов PostgreSQL.

    Самое очевидное предложение: «Каждый процесс выполнит четверть JOIN». Но что именно означает «четверть»? Если каждый процесс просто выполнит весь исходный план, мы получим повторную работу и, возможно, дублированный результат.

    Поэтому параллельный план должен делить входы и выходные строки корректно. В PostgreSQL используются частичные планы: рабочие процессы должны формировать разные части результата, а Gather собирает их для вышестоящих узлов.

    У соединений есть дополнительная сложность: внешнюю сторону можно разделить между процессами, но что делать с внутренней стороной и промежуточными структурами? Именно здесь обычное параллельное хеш-соединение принципиально отличается от Parallel Hash.

    6.2. Обычный Hash Join внутри параллельного плана: копия на каждого работника¶

    Пример схематичного плана:

    Gather
  Workers Planned: 4
  Workers Launched: 4
  -> Hash Join
       Hash Cond: (o.customer_id = c.id)
       -> Parallel Seq Scan on orders o
       -> Hash
            -> Seq Scan on customers c

    В этом варианте у каждого рабочего процесса может быть собственная хеш-таблица, построенная по всему внутреннему входу. Внешний параллельный скан, напротив, распределяет строки между процессами.

    В итоге:

    Worker 1: строит Hash(customers), ищет свою часть orders
Worker 2: строит Hash(customers), ищет свою часть orders
Worker 3: строит Hash(customers), ищет свою часть orders
Worker 4: строит Hash(customers), ищет свою часть orders

    Плюс лидер может участвовать в выполнении параллельного участка при соответствующих условиях.

    Это может быть разумно, если внутренняя сторона мала. Но если хеш-таблица занимает условные 100 МиБ, четыре независимые копии потребуют сопоставимого объема памяти каждая и повторят чтение/хеширование внутренней стороны.

    Например, только на сами четыре таблицы могло бы уйти около 400 МиБ вместо 100 МиБ — условная оценка без накладных расходов. Поэтому такое параллельное выполнение может плохо масштабироваться по памяти.

    6.3. Parallel Hash: одна разделяемая хеш-таблица¶

    Parallel Hash меняет именно организацию построения.

    Типичный план:

    Gather
  Workers Planned: 4
  Workers Launched: 4
  -> Parallel Hash Join
       Hash Cond: (o.customer_id = c.id)
       -> Parallel Seq Scan on orders o
       -> Parallel Hash
            -> Parallel Seq Scan on customers c

    Здесь несколько процессов совместно строят и используют одну разделяемую хеш-структуру в доступной им общей памяти, а не независимо создают ее полные копии.

          Worker 1 --\
      Worker 2 ---+--> Parallel Hash (общая структура)
      Worker 3 ---+
      Worker 4 --/
                       |
                       v
               Параллельный поиск
               по частям orders

    Для этого применяются области разделяемой памяти и механизмы PostgreSQL: динамическая разделяемая память (DSM) и динамическое выделение в разделяемой памяти (DSA). Внутренние структуры хеш-соединения используют совместно доступные указатели/смещения и операции синхронизации.

    Преимущество: уменьшаются дублирование построения внутренней стороны и число независимых больших хеш-таблиц.

    Цена: приходится координировать процессы и защищать совместные данные от конфликтующих обновлений.

    6.4. Зачем Parallel Hash нужны барьеры¶

    Один рабочий процесс уже закончил читать свою часть клиентов. Другой еще строит хеш-таблицу. Может ли первый начать поиск заказов?

    Если поиск начнется до того, как все необходимые записи внутренней стороны построены, он может пропустить совпадения.

    Значит, нужен механизм согласования фаз. PostgreSQL использует барьер (Barrier IPC): участники достигают точки синхронизации, а после выполнения необходимых условий переходят к следующей фазе.

    В исходниках nodeHashjoin.c, nodeHash.c, hashjoin.h присутствуют состояния построения вида:

    PHJ_BUILD_ELECT
PHJ_BUILD_ALLOCATE
PHJ_BUILD_HASH_INNER
PHJ_BUILD_HASH_OUTER
PHJ_BUILD_RUN
PHJ_BUILD_FREE

    Смысловой путь:

    Выбрать участника для начальной организации
                  |
                  v
Выделить общие структуры
                  |
                  v
Совместно обработать внутренний вход
                  |
                  v
При необходимости распределить внешний вход по партиям
                  |
                  v
Начать совместный поиск
                  |
                  v
Освободить разделяемые ресурсы

    Не надо воспринимать схему как один глобальный mutex вокруг каждого элемента: реализация использует специальные структуры, атомарные операции и фазовую синхронизацию. Участники могут присоединяться к работе не одновременно, поэтому каждому нужно определять, в какой фазе находится общий алгоритм.

    6.5. Параллельные партии: работа усложняется еще сильнее¶

    Если общая хеш-таблица помещается в память, совместное построение относительно просто понять. Но если нужны партии, возникает новая координация.

    Для разных партий PostgreSQL использует дополнительные состояния, связанные с выбором исполнителя начальных действий, выделением памяти, загрузкой, поиском, обработкой оставшихся непарных строк и освобождением структур:

    PHJ_BATCH_ELECT
PHJ_BATCH_ALLOCATE
PHJ_BATCH_LOAD
PHJ_BATCH_PROBE
PHJ_BATCH_SCAN
PHJ_BATCH_FREE

    Работники могут распределяться по разным партиям или совместно обрабатывать одну партию, если оставшихся партий недостаточно для всех.

    Для обмена временными данными между процессами применяется совместно доступное промежуточное хранилище, в том числе механизм SharedTuplestore. При увеличении числа партий нужно координировать перераспределение и предотвращать ситуации, когда одна часть исполнителей уже работает по новой схеме, а другая — по старой.

    Поэтому динамическое увеличение Batches при Parallel Hash — значительно более сложная операция, чем в однопроцессном варианте: распределенные участники должны согласованно перейти к новым структурам и фазам.

    6.6. Память в Parallel Hash: почему общий хеш не делает ее бесплатной¶

    В PostgreSQL 18 ExecChooseHashTableSize() при подходящих условиях сначала может попытаться построить одну партию с использованием объединенного бюджета хеш-памяти участников.

    Если даже с объединенным бюджетом одна партия не помещается, код переходит к расчету с обычным размером хеш-бюджета и многопартийной обработкой. Здесь важно видеть, что стратегия зависит от условий и числа работников; нельзя считать один и тот же постоянный лимит общим для любого параллельного плана.

    При этом PostgreSQL обычно применяет work_mem к рабочим операциям каждого процесса. Несколько работников увеличивают потенциальное потребление памяти всей системы. Это относится не только к хеш-таблицам, но и к сортировкам и другим узлам.

    Получается, Parallel Hash экономит на дублировании определенной структуры, но не устраняет память под состояние работников, буферы, временные файлы и промежуточные данные.

    6.7. Параллельные Nested Loop и Merge Join устроены иначе¶

    В документации PostgreSQL 18 есть важное ограничение для параллельных соединений:

    • У параллельного Nested Loop внутренняя сторона остается непараллельным планом, но запуски внутреннего поиска распределяются между участниками согласно разбиению внешних строк. Если это дешевый индексный поиск, такая схема может быть эффективной.
    • У параллельного Merge Join внутренняя сторона также остается непараллельным планом и может выполняться в каждом работнике полностью. Если внутри нее большая сортировка, повторная подготовка способна уничтожить ожидаемую выгоду.
    • У обычного параллельного Hash Join каждый работник может строить собственную хеш-таблицу; Parallel Hash позволяет совместное построение.

    Здесь нет универсального правила «parallel всегда быстрее». Выгодность определяется распределением работы и тем, какую часть операций требуется повторить у каждого участника.

    6.8. Что ограничивает масштабирование¶

    Даже при наличии свободных ядер задержка не обязана уменьшаться пропорционально числу рабочих процессов.

    Факторы:

    Повторяемая работа. В некоторых параллельных планах каждый работник заново выполняет внутренний план или его часть.

    Синхронизация. Построение общего хеша, переходы между фазами и распределение партий требуют согласованных действий.

    Перекос ключей. Если большая доля строк относится к одному ключу или одной партии, нагрузка может распределиться крайне неравномерно.

    Ввод-вывод. Несколько работников могут конкурировать за пропускную способность памяти и файлового слоя. Параллельный ввод-вывод не гарантирует линейного прироста пропускной способности.

    Сбор результатов. Gather должен передать результаты наверх. Если JOIN возвращает сотни миллионов пар, объем результирующего потока и работа ведущего процесса тоже могут стать ограничением.

    Доступность работников. Workers Planned и Workers Launched могут различаться. Если запланированные работники недоступны, исполнение пойдет с меньшим числом участников и может оказаться менее эффективным, чем ожидалось.

    6.9. Как читать EXPLAIN для параллельных соединений¶

    Используем:

    EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS)
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id;

    Если появился параллельный план, рассматриваем:

    • Workers Planned и Workers Launched — сколько процессов планировалось и сколько фактически запущено;
    • наличие именно Parallel Hash, а не просто Hash под Gather;
    • распределение фактических строк и времени по работникам, если оно отображается;
    • расход памяти и число партий;
    • временные чтения и записи;
    • стоимость Gather и общий объем выходных строк.

    В параллельном плане нельзя просто умножать среднее время одного узла на loops и выдавать это за время всего SQL. Несколько процессов могут выполнять работу одновременно, а показатели родителя включают дочерние узлы.

    Главное после раздела 6¶

    1. Параллельный план должен распределять выходные строки без дублирования результата.
    2. Обычный Hash Join внутри параллельного плана может строить собственную хеш-таблицу в каждом работнике.
    3. Parallel Hash позволяет совместно строить и использовать разделяемую хеш-структуру.
    4. Для согласованного построения, перераспределения партий и поиска нужны разделяемая память, атомарные операции и барьеры.
    5. Память, синхронизация, перекос ключей, ввод-вывод и сбор результатов ограничивают ускорение.
    6. Workers Launched и фактическая работа по процессам важнее предположения, что все запланированные работники всегда доступны.

    7. Производственная диагностика: от симптома к механизму¶

    Мы разобрали внутренние структуры. Теперь вернемся к реальному backend: SQL выполняется секунды вместо миллисекунд. Наша задача — установить, какая физическая работа стала дорогой.

    7.1. Сценарий А: Hash Join неожиданно записывает гигабайты во временные файлы¶

    Наблюдаем:

    Hash Join
  Buffers: temp read=150000 written=150000
  -> ...
  -> Hash
       Buckets: 65536
       Batches: 64 (originally 4)
       Memory Usage: 8192kB

    Причинная гипотеза:

    Планировщик оценил относительно маленький build input
                  |
                  v
Изначально выбрано 4 партии
                  |
                  v
Фактический размер или распределение оказались другими
                  |
                  v
Потребовалось 64 партии
                  |
                  v
Перераспределение + временные записи и чтения
                  |
                  v
Рост задержки и конкуренция за I/O

    Что проверяем:

    1. Разницу rows и actual rows для дочернего входа Hash.
    2. Среднюю ширину строк в плане (width) и фактическую структуру передаваемых данных; широкие строки повышают расход памяти.
    3. Наличие огромных частых ключей и количество выходных пар.
    4. work_mem, hash_mem_multiplier и число одновременно работающих запросов.
    5. temp read/written, temp_bytes, время ввода-вывода, если доступно.

    Небольшой расчет нижнего масштаба временного ввода-вывода. Допустим, после начальной обработки во временные файлы отложено 75 МиБ внутренней стороны и 375 МиБ внешней. Если записать и затем прочитать эти данные хотя бы по одному разу, получим:

    Временная запись: (75 + 375) МиБ = 450 МиБ
Временное чтение: (75 + 375) МиБ = 450 МиБ
Итого передано через временный файловый слой ≈ 900 МиБ

    Это учебная оценка без служебных накладных расходов, дополнительных проходов и повторного перераспределения. Но она сразу показывает, почему превращение одного хеш-соединения в многопартийное может заметно увеличить задержку.

    7.2. Сценарий Б: Batches растет, а проблема не исчезает¶

    Данные содержат чрезвычайно популярный ключ. После очередного удвоения партий почти все записи остаются вместе.

    Симптом: очень большой расход памяти либо крайне неравномерная работа, несмотря на попытки дробления. Один только Batches может не показать всей проблемы.

    Диагностика:

    • посмотреть частоты ключей в данных, если это допустимо по ресурсам и требованиям безопасности;
    • сопоставить количество строк внутренней стороны с количеством результирующих пар;
    • отличить обязательное размножение совпадений от коллизий и избыточных проверок;
    • помнить, что деление на партии по хешу не может разделить одинаковый полный хеш на разные партии.

    Инженерный вывод: иногда решение находится в селективности и форме запроса либо предварительном ограничении данных. Увеличение рабочего бюджета не уменьшит обязательное количество результатов, а еще большее число партий не решит неразделимый перекос.

    7.3. Сценарий В: Nested Loop выполняет 100 000 внутренних поисков¶

    Nested Loop
  -> Seq Scan on events e
       (actual rows=100000 loops=1)
  -> Index Scan on customers c
       (actual time=0.01..0.07 rows=1 loops=100000)

    Один поиск дешевый, но сумма измеренных времен внутренних запусков — около семи секунд. В параллельном плане эта сумма не равна настенному времени всего запроса; в данном условном примере рассматривается обычный последовательный Nested Loop.

    Что уточняем:

    • планировщик ожидал 100 000 внешних строк или ошибся на несколько порядков?
    • какова стоимость одного внутреннего поиска и сколько страниц он затрагивает?
    • насколько часто повторяются значения customer_id?
    • можно ли переиспользовать результат через Memoize при данной конфигурации?
    • насколько выгоднее был бы альтернативный алгоритм на этом объеме данных?

    Если ключи повторяются, Memoize может устранить большую долю физических поисков. Если ключи почти уникальны, кеширование мало поможет; выигрыш другого алгоритма придется оценивать отдельно.

    7.4. Сценарий Г: Memoize существует, но почти бесполезен¶

    Условный фрагмент:

    Memoize
  Cache Key: e.customer_id
  Cache Mode: logical
  Hits: 500  Misses: 99500  Evictions: 90000  Overflows: 0
  Memory Usage: 4096kB
  -> Index Scan ...

    Большинство поисков — промахи, много записей вытесняется. Кеш тратит ресурсы на управление собой, но редко помогает.

    Что проверяем: распределение и порядок параметров, число уникальных ключей, размер записи, стоимость внутреннего поиска. Нельзя просто сделать вывод, что «PostgreSQL неправильно реализовал кеш». Он выполняет корректную ограниченную политику хранения, но исходные данные почти не дают повторного использования.

    Если же Overflows высок, проблема отличается: результаты для некоторых отдельных ключей слишком велики, поэтому запись вообще не удается надежно сохранить в кеш.

    7.5. Сценарий Д: Merge Join быстро сопоставляет ключи, но долго готовится¶

    Merge Join
  Merge Cond: (a.key = b.key)
  -> Sort
       Sort Key: a.key
       Sort Method: external merge  Disk: 256000kB
       -> Seq Scan on a
  -> Sort
       Sort Key: b.key
       Sort Method: quicksort  Memory: 4096kB
       -> Seq Scan on b

    Здесь важно проверить время и временный ввод-вывод нижних сортировок, а также их rows и width.

    Возможные причины:

    • слишком большой вход;
    • отсутствие выгодного способа получить нужный порядок без полной сортировки;
    • нехватка памяти для сортировки;
    • ошибка оценки размера и ширины входа;
    • повторные группы и дополнительные условия после подготовки порядка.

    Не надо пытаться объяснить весь медленный JOIN «плохим алгоритмом слияния»: значительная стоимость могла возникнуть еще до первой пары.

    7.6. Сценарий Е: Parallel Hash использует четыре процесса, но ускорения нет¶

    План показывает Workers Launched: 4, однако реальное время почти не изменилось.

    Сначала выясняем, что именно параллельно:

    • это действительно Parallel Hash с общей структурой или обычный Hash, повторяемый каждым работником?
    • не размножается ли дорогое чтение внутреннего входа?
    • как распределились строки внешней стороны?
    • нет ли одного перегруженного пакета/ключа?
    • не ограничены ли все работники общей пропускной способностью памяти и временного ввода-вывода?
    • не стал ли Gather или огромный результирующий поток узким местом?

    Параллельное выполнение имеет смысл измерять по реальному времени запроса и суммарному использованию ресурсов. Более высокая загрузка всех ядер сама по себе не доказывает улучшения пропускной способности сервиса.

    7.7. Показатели EXPLAIN, которые нельзя путать¶

    Показатель Что означает Чего не означает
    loops Сколько раз узел был запущен Сколько строк таблицы он физически содержит
    actual rows Среднее число выданных строк за запуск узла Число уникальных физических строк
    actual time Среднее измеренное время узла за запуск Отдельное время, которое нужно прибавить к времени родителя
    Hash Cond Условие хеш-сопоставления Что совпадение хеша автоматически равно SQL-совпадению
    Join Filter Дополнительная проверка пары Что до этой проверки работа была бесплатной
    Buckets Число хеш-корзин Число уникальных ключей
    Batches Число частей хеш-соединения Число полных повторных сканирований исходной таблицы
    Memory Usage Память соответствующей структуры, как ее измеряет узел Вся память backend-процесса или всего SQL
    Buffers: temp read/written Число операций с временными рабочими блоками в учете PostgreSQL Точное число физических обращений к SSD
    Memoize Hits/Misses Повторное использование или отсутствие записи по параметру Автоматически измеренное ускорение всего запроса
    Workers Launched Фактически стартовавшие рабочие процессы Гарантия линейного ускорения

    Если нужны фактические количества строк и буферные обращения, но инструментирование времени множества мелких узлов существенно искажает результат, полезен режим:

    EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT ...;

    В этом режиме actual rows и loops сохраняются, времена отдельных узлов скрываются, а общая продолжительность выполнения измеряется.

              |

              |         |
              |         +--> Materialize / Memoize при необходимости
              |

              |               batches + временные файлы

    Семь инженерных выводов¶

    1. Планировщик и исполнитель решают разные задачи. Планировщик оценивает и выбирает алгоритм до запуска, исполнитель работает с фактическим объемом и распределением данных.
    2. Hash Join платит памятью за быстрые поиски. Коллизии и повторяющиеся ключи требуют настоящих проверок равенства, а огромные группы совпадений могут породить огромный корректный результат.
    3. Партии — способ ограничить оперативную память, а не бесплатное сжатие. При росте Batches появляются перераспределение и временный ввод-вывод; неразделимый перекос может заставить превысить бюджет.
    4. Nested Loop повторяет работу внутреннего узла. Ключ к анализу — loops, стоимость повторного запуска и возможности параметризованного индексного доступа.
    5. Materialize и Memoize экономят разные виды повторений. Первый повторно выдает поток, второй кеширует результаты по ключам; их поведение при нехватке памяти тоже отличается.
    6. Merge Join зависит от порядка и повторяющихся ключей. Для групп дубликатов нужен возврат к сохраненной позиции, а входные сортировки могут стать основной ценой плана.
    7. Параллельное выполнение не отменяет ограничений. Совместная хеш-таблица уменьшает дублирование, но требует синхронизации и конкурирует за память и ввод-вывод.

    Куда можно копнуть глубже внутри темы JOIN¶

    Первый следующий слой — точное устройство HashJoinTuple и распределение 32-битного хеша по bucket/batch, включая рост nbatch. Он закрывает вопрос, какие именно записи освобождаются и куда переносится каждая строка при перераспределении. Это полезно для объяснения случаев, когда Batches выросло, а расход памяти и временного ввода-вывода остается неожиданным.

    Второй слой — внутреннее устройство tuplestore, BufFile и SharedTuplestore именно как рабочих хранилищ JOIN. Он объяснит жизненный цикл файлов, повторное чтение групп и разницу между однопроцессным и разделяемым хранилищем. Это останется в рамках выполнения JOIN без перехода к теме долговечности транзакций.

    Оба слоя можно разобрать отдельно. Темы WAL, COMMIT, fsync, checkpoint и recovery сюда намеренно не включены.
