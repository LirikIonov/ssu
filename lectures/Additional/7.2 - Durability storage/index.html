    7.2. PostgreSQL durability & storage internals¶

    Углубленная лекция магистратуры · PostgreSQL 18 · REL_18_STABLE · темы 19–21 утвержденной программы.

    Продолжение лекций 07 «WAL и Durability» и 07.1 «WAL Internals». Здесь мы не повторяем устройство WAL buffers, XLogInsert, ресурсных менеджеров, checkpoint и REDO. Выясняем, какую гарантию дает ОС после записи WAL; как PostgreSQL обнаруживает повреждение страниц и журнала; что именно происходит, если сознательно отказаться от WAL для пользовательских таблиц. pg_control, организация checkpoint I/O и алгоритм crash recovery остаются для 07.3. Репликацию, backup, миграции и блокировки из блоков 8–9 не разворачиваем.

    Версионная особенность PostgreSQL 18. При создании нового кластера initdb теперь включает data checksums по умолчанию. Для их отключения служит --no-data-checksums. Кроме того, показатели WAL write/sync в PostgreSQL 18 надо читать из pg_stat_io, а не из удаленных полей pg_stat_wal. Перед применением примеров всегда сверяйте SHOW server_version;, SHOW data_checksums; и доступные поля представлений.

    О границах гарантии. «Сохранено на диск» в учебных схемах означает «подтверждено всем нижележащим слоям хранения согласно их контрактам». Это предполагает корректную реализацию ядра, файловой системы, драйвера, контроллера, накопителя и виртуальной инфраструктуры. fsync() не может исправить оборудование, которое лжет о завершении записи, или защитить от уничтожения единственной копии данных.

    Условность чисел. Размеры очередей и задержки в мысленных экспериментах иллюстративны. Синтаксис SQL и названия параметров относятся к PostgreSQL 18. Команды, опасные для настоящей базы, отдельно помечены.

    0. Начнем с неприятного вопроса: COMMIT вернул OK — где теперь наши байты?¶

    Мы уже знаем из лекции 07: в типичной синхронной транзакции PostgreSQL обязан подтвердить локальный flush WAL, необходимого для фиксируемой транзакции. Представим, что мы получили успешный ответ:

    BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT; -- клиент получил OK

    Формулировка «WAL сброшен на диск» подозрительно удобная. Где именно этот «диск»? Между пользовательским процессом PostgreSQL и энергонезависимыми ячейками SSD находятся ядро ОС, файловая система, очереди блочного устройства, драйвер, кеш контроллера, кеш самого накопителя, микропрограмма и физический носитель. У каждого слоя есть право временно держать данные в оперативной памяти. Некоторые из этих слоев вообще не принадлежат PostgreSQL.

    Именно здесь заканчивается уверенность разработчика, который видит только успешный write(). Он знает, что байты приняла операционная система. А переживут ли они внезапное отключение питания?

    PostgreSQL backend / WAL writer
             │
             │ write() / fdatasync() / fsync()
             ▼
          Linux VFS
             │
             ▼
     Page cache и inode
             │
             ▼
    Файловая система (ext4 / XFS / ...)
             │
             ▼
   Block layer, очереди, драйвер
             │
             ▼
     Контроллер / SSD firmware
             │
             ├── volatile DRAM cache
             ├── PLP-protected buffer (если есть)
             └── NAND / другое устойчивое хранилище

    Вопрос сегодняшней лекции: какое событие на этой цепочке дает PostgreSQL право ответить клиенту «ваша транзакция долговечна»? А потом следующий: как мы поймем, что сохраненные байты повреждены? И финальный: что, если часть данных мы вообще не собираемся восстанавливать после сбоя?

    Короткий маршрут:

    • 19. ОС и storage: путь write → page cache → sync → устройство; кэши, PLP, ложные подтверждения и задержки.
    • 20. Проверки целостности: 16-битный checksum страницы, 32-битный CRC-32C WAL, full-page image, обнаружение и пределы восстановления.
    • 21. UNLOGGED: физическая модель таблицы, отсутствие обычного WAL для ее содержимого, reset после crash, допустимая цена ускорения.

    19. ОС, файловая система и реальная долговечность¶

    19.1. Что конкретно делает write()¶

    Предположим, PostgreSQL записывает фрагмент файла WAL. В типичном Linux-пути с обычным буферизованным вводом-выводом системный вызов:

    ssize_t n = write(fd, wal_bytes, count);

    может успешно вернуть n == count, хотя устройство хранения еще не получило эти байты. Ядро скопировало или приняло соответствующие данные в свои структуры и страницы кеша, поставило их в очередь дальнейшей записи и сообщило о завершении текущей операции. Контракт успешного буферизованного write() по умолчанию не равен гарантии выживания при отказе питания.

    Сразу уточним две вещи. Во-первых, системный вызов может вернуть число меньше count, поэтому надежный вызывающий код обрабатывает частичные записи; нулевая длина в примере не рассматривается. Во-вторых, write() иногда действительно ждет ввода-вывода: например, при давлении на память, исчерпании dirty-лимитов, расширении файла или использовании синхронных флагов открытия. Его успех сам по себе все равно недостаточен для обобщения «все устойчиво на носителе».

    Ментальная модель:

    Момент t0: WAL есть в памяти PostgreSQL.
Момент t1: write() успешно вернул управление.
Момент t2: грязные страницы WAL находятся в page cache ОС.
Момент t3: ОС отправила команды записи устройству.
Момент t4: устройство подтвердило необходимое сохранение.

    t1, t3 и t4 не обязаны совпадать. Более того, в реальной системе отдельные интервалы пересекаются, потому что десятки операций выполняются конкурентно.

    Почему PostgreSQL вообще использует кеш ОС?¶

    Page cache позволяет группировать близкие записи, изменять несколько участков одной страницы, асинхронно отправлять I/O, отдавать чтения из RAM и не блокировать каждый write() до завершения записи NAND. Это увеличивает пропускную способность. Цена — возникает еще одна граница долговечности. При отключении питания обычная оперативная память ядра исчезает вместе с незавершенными записями.

    Здесь важно не спутать две памяти:

    Слой Кто управляет Что хранит Означает ли наличие долговечность
    shared_buffers PostgreSQL Страницы отношений в памяти СУБД Нет
    WAL buffers PostgreSQL Новые байты WAL до записи Нет
    Page cache ОС Ядро Файловые страницы, в том числе WAL и data files Нет
    Volatile cache контроллера/SSD Устройство Принятые, но еще неустойчивые записи Нет
    Неволатильная среда / защищенный PLP-домен Устройство Данные, сохранность которых гарантирована устройством При выполнении контракта устройства

    Переход из shared_buffers в page cache уже означает новое место хранения байтов, но еще не переход в энергонезависимое состояние.

    19.2. Dirty page ядра: что происходит после write()¶

    Слово «грязная страница» встречалось в лекции 07 применительно к буферу PostgreSQL. Теперь вторая версия того же понятия: dirty page page cache — страница файлового кеша, чье содержимое в RAM новее соответствующего устойчивого содержимого на устройстве.

    Это два независимых набора структур. Одна и та же логическая страница базы может находиться в shared_buffers, быть скопирована в page cache и позже оказаться на накопителе. При этом PostgreSQL и Linux по-разному учитывают собственные грязные страницы.

            PostgreSQL                          Linux
  buffer page изменена                 file-backed page
          dirty       ─── write() ───►     dirty
              │                              │
              │                              ├── background writeback
              │                              ├── memory pressure
              │                              └── fsync/fdatasync
              ▼                              ▼
   буфер позднее clean              I/O до накопителя

    Когда Linux запускает фоновую запись (writeback), он может передать dirty pages устройству без отдельного запроса PostgreSQL. Однако этот фоновый механизм не определяет момент, когда синхронную транзакцию разрешено подтвердить: нужный порядок PostgreSQL обеспечивается своим протоколом flush.

    Интересный эффект под нагрузкой. Первые тысячи write() могут выглядеть быстрыми, потому что складывают данные в RAM. Потом грязных страниц становится слишком много — система ограничивает темп записи или заставляет вызывающие процессы участвовать в writeback. Появляется резкий рост latency, хотя SQL и количество переданных байтов почти не менялись. Бесплатная буферизация закончилась.

    19.3. fsync() и fdatasync(): что именно требуется дождаться¶

    Типичные POSIX-интерфейсы:

    int fsync(int fd);
int fdatasync(int fd);

    fsync(fd) требует синхронизировать измененные данные файла и необходимые связанные метаданные. fdatasync(fd) может не принуждать к записи несущественные для последующего получения данных метаданные — например, времени последнего изменения, если соответствующая платформа допускает такую оптимизацию. Но изменение размера файла, без которого новые байты нельзя потом прочитать, должно быть учтено.

    Точная реализация определяется ОС и файловой системой. fdatasync не означает «отправить только полезную нагрузку, забыв про все метаданные».

    write(fd)
   │
   ├─► изменения попали в систему буферизации
   └─► вызов может завершиться до persistence

fdatasync(fd)
   │
   ├─► дождаться данных
   └─► дождаться метаданных, необходимых для доступа к данным

fsync(fd)
   │
   ├─► дождаться данных
   └─► дождаться требуемых метаданных файла

    Для гарантии сохранения самого имени файла после создания или переименования иногда недостаточно fsync файла: на POSIX-подобных файловых системах требуется соответствующая синхронизация каталога. Это особенно важно при работе с файлами, переключением сегментов и каталогами БД. Мы не станем разбирать здесь алгоритм checkpoint — достаточно понимать, что долговечность байтов файла и долговечность изменения структуры каталогов являются разными обязательствами.

    Важно: даже корректно завершившийся fsync() остается вызовом, опирающимся на контракт нижележащего хранилища. ОС может выдать flush-команды; только корректный контроллер и накопитель обеспечивают обещанное завершение.

    19.4. O_SYNC и O_DSYNC: синхронность можно привязать к каждому write()¶

    Вместо последовательности write(); fdatasync(); приложение может открыть файл с синхронными флагами:

    int fd = open(path, O_WRONLY | O_DSYNC);
/* или O_SYNC */
write(fd, data, n);

    На соответствующей платформе O_DSYNC придает операциям записи поведение синхронизации данных: успешное завершение write() означает выполнение требуемой операции сохранения данных и необходимых метаданных. O_SYNC требует более широкую синхронизацию данных и метаданных файла. На Linux O_SYNC включает семантику синхронной записи в отношении метаданных; O_DSYNC — более узкий вариант.

    O_SYNC — это флаг I/O, а не магический режим SSD. Он все так же проходит через файловую систему и устройство, которые обязаны честно исполнить запрос. На разных файловых системах и устройствах одна и та же комбинация флагов может давать разные задержки.

    Платой за синхронность каждой записи может стать потеря возможности объединять несколько маленьких записей до одного flush. Поэтому PostgreSQL позволяет выбирать wal_sync_method — способ реализовать обязательную синхронизацию WAL с использованием поддерживаемых ОС методов.

    19.5. wal_sync_method: что реально выбирает PostgreSQL 18¶

    Параметр определяет механизм принудительного сохранения WAL, а не место, где находится база, и не «уровень ACID». Документация PostgreSQL 18 перечисляет пять вариантов:

    wal_sync_method Системный механизм Где возникает обязательное ожидание
    open_datasync Открыть WAL с O_DSYNC При записи, которую флаг делает синхронной
    fdatasync Записывать обычным способом, затем fdatasync() На вызове синхронизации
    fsync Записывать обычным способом, затем fsync() На вызове синхронизации
    fsync_writethrough Специальный fsync() с write-through-семантикой там, где поддерживается На синхронизации, с требованиями платформы
    open_sync Открыть WAL с O_SYNC При синхронной записи

    На Linux и FreeBSD обычным значением по умолчанию является fdatasync, а не просто «первый поддерживаемый метод». Список реально доступных значений зависит от сборки и платформы.

    Проверка:

    SHOW wal_sync_method;
SHOW fsync;
SHOW synchronous_commit;

    Здесь три независимых вопроса:

    • fsync: требует ли PostgreSQL принудительного сохранения там, где это необходимо для согласованности кластера?
    • wal_sync_method: какой системный путь используется для WAL?
    • synchronous_commit: какие именно локальные/удаленные условия завершения COMMIT ожидает данная транзакция?

    Не выводите отсутствие fsync syscall из трассировки как доказательство отсутствия durability. При open_datasync или open_sync подтверждение встроено в сам write(); отдельного fdatasync() может не понадобиться.

    Что делают функции PostgreSQL¶

    В 07.1 мы проходили XLogWrite и XLogFlush. Теперь достаточно соединить их с ОС:

                      wal_sync_method = fdatasync
XLogWrite ── write()/pwrite() ──► page cache
XLogFlush ──────────────────────► fdatasync() ──► durable frontier

                  wal_sync_method = open_datasync
XLogWrite ── write() по FD с O_DSYNC ──────────► durable frontier

    Схема концептуальна: в реализации существуют совместная обработка flush-запросов, границы WAL-записей и конкурирующие процессы. Отдельный COMMIT не обязан физически вызывать один fdatasync лично и всегда. Нам важна достигнутая граница долговечности LSN, а не количество системных вызовов на SQL-транзакцию.

    19.6. Write-back и write-through: одно название, несколько уровней¶

    Write-back — слой может подтверждать завершение поступления записи до переноса байтов в следующий устойчивый уровень, оставляя их в своем кеше до будущего сброса. Write-through — запись сопровождается продвижением данных дальше по цепочке согласно контракту слоя, прежде чем операция считается завершенной.

    Опасная упрощенная фраза: «write-through означает, что в файловой системе нет кеша». Нет. У приложения, ядра, RAID-контроллера и SSD разные кеши и разные протоколы подтверждения. Наличие write-through на одном уровне ничего автоматически не говорит о режимах следующего.

    Пример цепочки:

     PostgreSQL
     │
 Linux page cache        ─── volatile, write-back
     │
 RAID controller DRAM    ─── возможно volatile write-back
     │
 SSD DRAM                ─── возможно volatile write-back
     │
 NAND / nonvolatile     ─── сохранено физически

    Если RAID-контроллер подтвердил запись, оставив ее только в незащищенной DRAM, а ядро поверило подтверждению как окончательному, весь правильный код PostgreSQL выше теряет смысл после пропадания питания. Поэтому документация PostgreSQL отдельно предупреждает о контроллерах и накопителях, которые подтверждают запись раньше надежного сохранения.

    Важно также различать write-through флаг на уровне POSIX и аппаратные режимы «write cache enabled/disabled» у SSD. Это связанные по смыслу, но технически разные интерфейсы.

    19.7. Что происходит ниже файловой системы: команды flush и барьеры порядка¶

    Представим, что данные WAL попали из page cache в очередь устройства. В системе могут существовать десятки команд, а устройство вправе оптимизировать порядок исполнения в рамках интерфейса. Чтобы обеспечить надежную точку синхронизации, хранилищу требуется способ отделить подтверждение приема от подтверждения долговечного завершения.

    Для типичных стеков используются аппаратные механизмы, концептуально соответствующие:

    • cache flush / flush cache: требование сохранить подходящие ранее принятые записи из volatile-кеша в устойчивое состояние;
    • FUA (Force Unit Access): для отдельных команд записи требовать сохранения в неволатильном домене перед завершением;
    • ordering / barriers: порядок, не позволяющий ключевым записи и подтверждению пройти небезопасную перестановку.

    В SATA, SCSI и NVMe названия и точная семантика команд различаются. PostgreSQL сам обычно не отправляет NVMe-команду — он обращается к API ОС, а соответствующие уровни преобразуют синхронизацию в операции файловой системы и блочного устройства.

    Не следует строить из этой схемы универсальную формулу «каждый fsync = ровно одна NVMe FLUSH». Ядро и файловая система могут объединять работу, а накопитель с защищенным кешем может подтвердить запрос быстро, потому что необходимый объем данных уже находится в защищенном домене.

    Сбой между сохранением WAL и data page¶

    Предположим, ОС записала dirty data page, но у нее еще нет устойчивого WAL, описывающего эту версию страницы. Это нарушает правило предварительной записи: после сбоя невозможно надежно восстановить согласованное состояние. PostgreSQL не должен разрешать такой сброс: механизм записи буферов обеспечивает нужную WAL flush-границу. Здесь fsync с реальным семантическим эффектом — нижележащая часть этого инварианта.

    19.8. PLP: почему «SSD с DRAM» не равен «опасный SSD»¶

    Power Loss Protection (PLP) — аппаратно-программная способность накопителя или контроллера пережить потерю внешнего питания и завершить либо гарантированно сохранить уже подтвержденные записи. Обычно она реализуется с помощью накопленной энергии, например конденсаторов, и протокола аварийного сброса данных и метаданных. Это описание возможного устройства, а не обязательный конструктивный признак всех моделей.

    Нужная нам гарантия: когда устройство подтвердило команду, требующую persistence, данные находятся в энергонезависимом или надежно защищенном домене, который переживет предусмотренное событие отключения питания.

    PLP не гарантирует:

    • восстановление после физического разрушения всего накопителя;
    • отсутствие ошибок firmware, битовых повреждений или некорректного обновления mapping tables;
    • атомарность любой пользовательской записи размером 8 КБ;
    • существование резервной копии или соблюдение требуемого RPO;
    • правильность поведения виртуального диска или RAID-контроллера выше SSD.

    Особенно важно: PLP и отсутствие torn pages — разные утверждения. Наличие защищенного кеша само по себе не доказывает атомарности записи PostgreSQL-страницы 8 КБ. Даже классический RAID-контроллер с батареей должен гарантировать корректную обработку нужного объема записи, а не только сохранение отдельных фрагментов.

    19.9. Почему fsync может быть быстрым на хорошем SSD¶

    Наивная оценка: fsync — значит «непременно ждать физического программирования каждой NAND-ячейки прямо сейчас». Но современное устройство может иметь защищенный буфер: когда запись успешно попала в него и защита гарантирована, устройство может выполнить требуемый контракт долговечности без ожидания полного переноса именно этих байтов в NAND в течение текущего вызова.

    Парадоксально, но надежная аппаратная защита иногда улучшает задержку синхронного подтверждения по сравнению с устройством, которое обязано постоянно выгружать volatile cache. За это платят стоимостью накопителя и его инженерной сложностью.

    Здесь нельзя утверждать, что «PLP ускоряет все fsync»: результат зависит от контроллера, очередей, файловой системы, состояния диска, заполненности SSD, garbage collection, нагрузки и того, что именно измерено.

    19.10. Мысленный эксперимент: где теряются данные при аварии¶

    Обозначим уровни:

    • A: WAL лежит только в WAL buffers PostgreSQL.
    • B: соответствующий write() завершился, байты есть в page cache ОС.
    • C: контроллер принял запись в volatile cache.
    • D: накопитель подтвердил требуемую долговечную синхронизацию.
    Событие Что можно заключить
    Упал только backend, ОС продолжает работать Буферы процесса утрачены; page cache и уже сохраненные файлы продолжают существовать. Дальше действует протокол запуска/восстановления СУБД.
    Аварийно остановилась ОС до D Состояние в B/C может исчезнуть. Последние записи без гарантированного flush нельзя считать долговечными.
    Пропало питание после корректного D WAL должен пережить сбой в пределах контракта storage.
    Устройство ложно заявило D, пока байты были в volatile cache PostgreSQL не может восстановить гарантию поверх ложного подтверждения.
    Физически уничтожен единственный накопитель Локальный fsync не создает копию; данные могут быть безвозвратно утрачены.

    Здесь не следует подменять состояние одной транзакции состоянием всего кластера. Условие synchronous_commit=off допускает потерю последних подтвержденных клиенту транзакций после аварии, но при правильно работающей подсистеме записи не предполагает повреждения структуры кластера. fsync=off делает аварийную несогласованность файлов возможной. Мы сравниваем разные риски.

    19.11. Параметры: что опасно трогать в production¶

    SHOW fsync; должен быть отправной точкой проверки долговечности. fsync=off допустим только для легко воспроизводимых или одноразовых кластеров, потому что после power loss или crash ОС база может получить неустранимую несогласованность, а не просто потерять последние несколько COMMIT. Это изменение не равно переходу в асинхронный COMMIT.

    wal_sync_method выбирают по возможностям платформы и подтвержденным тестам, учитывающим реальную durable latency и корректность. Оптимизировать его по одному среднему TPS без проверки отказоустойчивости — сомнительная победа.

    full_page_writes=off тоже снижает защиту от torn pages; мы подробно свяжем это с проверками страницы в теме 20. Суммировать все эти настройки в один переключатель «быстро/медленно» нельзя: они меняют разные части модели отказов.

    19.12. Нагрузка: от fsync к хвостовым задержкам¶

    Представим 300 конкурентных клиентов, каждый подтверждает небольшую транзакцию. При хорошем групповом подтверждении многие COMMIT могут использовать общий физический flush-рубеж. Но если устройство вдруг начинает долго подтверждать синхронизацию, возникает очередь ожидающих backend-процессов.

    Стабильный режим:                       Деградация хранения:

COMMIT ─┐                                 COMMIT ─┐
COMMIT ─┼─► WAL flush ─► OK               COMMIT ─┼─► [ очередь ] ─► долгий flush
COMMIT ─┘                                 COMMIT ─┘

p50 небольшой                           p50 может оставаться умеренным
p99 умеренный                           p99 резко увеличивается
TPS ограничен реальной скоростью         TPS выходит на потолок очереди/устройства

    Рост средней задержки и рост p99 имеют разные причины: большой систематический flush-cost против коротких периодов обслуживания длинных хвостов. Здесь могут влиять конкуренция за файл WAL, очереди блочного устройства, фоновые операции накопителя, writeback из других процессов и виртуализация. По одному значению fsync_time нельзя восстановить все распределение задержек.

    Как измерять в PostgreSQL 18¶

    SHOW track_wal_io_timing;

SELECT backend_type, context,
       writes, write_bytes, write_time,
       fsyncs, fsync_time
FROM pg_stat_io
WHERE object = 'wal'
ORDER BY backend_type, context;

SELECT wal_records, wal_fpi, wal_bytes, wal_buffers_full
FROM pg_stat_wal;

    Версионная ловушка: старые статьи советуют запрашивать wal_write_time и wal_sync_time из pg_stat_wal. В PostgreSQL 18 эти поля удалены; WAL I/O перенесен в pg_stat_io, а его измерение времени управляется track_wal_io_timing. В этом представлении fsyncs фиксирует операции issue_xlog_fsync; при синхронной записи через O_DSYNC видимое число отдельных fsync может быть небольшим и не отражать всю стоимость durability. Смотрите также writes и write_time.

    Статистика накопительная. Сравнивать корректно дельты за интервал, на одной конфигурации, при известном фоне; значение write_time / writes дает лишь усреднение измеренных операций и не является p99 транзакционного COMMIT.

    ОС: iostat -x 1 показывает активность и задержки устройства, pidstat -d — I/O по процессам, а измерения конкретного накопителя и виртуального диска помогают отличить базу от нижележащей системы. Метрики разных слоев не обязаны совпадать: SQL COMMIT, WAL write, fdatasync, flush в контроллере — это разные события.

    Главное из темы 19¶

    1. write() в стандартном буферизованном режиме обычно обещает прием данных ОС; fsync/fdatasync требуют дальнейшего сохранения.
    2. shared_buffers, page cache ОС и кеш SSD имеют независимые границы грязных данных и подтверждений.
    3. wal_sync_method выбирает путь I/O; на Linux PostgreSQL 18 по умолчанию обычно использует fdatasync.
    4. Контракт durability заканчивается там, где нижележащая система перестает честно исполнять запросы синхронизации.
    5. PLP уменьшает риск потери подтвержденных записей при power loss, но не равен atomic 8-КБ write и не заменяет копии данных.
    6. Под нагрузкой стоимость синхронизации превращается в очередь COMMIT и хвостовые задержки; измеряем ее в PostgreSQL 18 через pg_stat_io и ОС.

    20. Data Checksums, WAL CRC и обнаружение повреждений¶

    20.1. Долговечность еще не означает целостность¶

    Мы прошли через fsync и аппаратное подтверждение записи. Можно расслабиться? Представим другой инцидент: COMMIT был подтвержден вчера, сегодня сервер читает страницу счета и получает 8192 байта. Файловая система не вернула ошибку. Но один сектор содержит случайно изменившиеся биты, либо устройство прочитало устаревшую страницу по ошибочному физическому адресу.

    Для ОС операция могла выглядеть успешной: pread() получил нужное количество байтов. Как PostgreSQL поймет, что данные вообще имеют отношение к ожидаемой странице?

    Нам нужен контроль целостности. В PostgreSQL он реализован несколькими разными механизмами. Самое распространенное ошибочное упрощение — «в базе есть checksum, значит любой поврежденный файл будет восстановлен». Проверка отвечает прежде всего на вопрос «совпадает ли прочитанное с ожидаемым?». Для исправления требуется вторая достоверная копия, подходящая WAL-информация или другой способ реконструкции.

    Механизм Что защищает Когда проверяется Способен сам восстановить?
    Data page checksum Отдельная страница данных PostgreSQL При чтении страницы в буферный слой (когда проверка применима) Нет
    WAL CRC-32C Содержимое отдельной WAL-записи При чтении WAL в предусмотренных путях recovery/репликации Нет
    Full-page image (FPI) Полный образ страницы в WAL для REDO и защиты от torn page Используется при повторном применении соответствующего WAL Может восстановить страницу при наличии подходящего WAL и корректного образа

    Это три механизма с разными задачами и разной областью действия.

    20.2. Как выглядит страница с контрольной суммой¶

    Типичный блок PostgreSQL имеет размер 8 КБ; он задается параметрами сборки, поэтому это не универсальное свойство всех пользовательских установок. Начало обычной страницы таблицы или индекса занимает PageHeaderData, обычно 24 байта.

    0                                                    8191
┌────────────────────────────────────────────────────────┐
│ PageHeaderData (24 bytes)                              │
│  ├── pd_lsn         : последняя WAL-позиция страницы   │
│  ├── pd_checksum    : 16-битная контрольная сумма       │
│  ├── pd_flags ...                                      │
│  └── pd_lower, pd_upper, pd_special ...                │
├────────────────────────────────────────────────────────┤
│ ItemIdData, свободное место, tuples, special space ... │
└────────────────────────────────────────────────────────┘

    pd_checksum занимает только 2 байта. Это сразу говорит о компромиссе: checksum легкий и недорогой, но количество возможных значений ограничено. Контрольная сумма страницы не является криптографическим доказательством отсутствия модификации и не защищает от злонамеренного изменения данных.

    Она также не дублирует страницу и не хранит ее прежнее состояние. Одиночные 16 бит не могут восстановить испорченные 8192 байта. Их задача — достаточно дешево поймать широкий класс случайных ошибок ввода-вывода.

    20.3. Почему контрольная сумма зависит от номера блока¶

    Интуитивно хочется вычислить checksum от содержимого страницы и сравнивать с сохраненным значением. Но представим, что storage ошибочно переставил два блока местами. Каждый блок имеет исходные внутренние байты, и простая checksum от содержимого каждой страницы останется корректной. При этом логическая таблица разрушена.

    Поэтому pg_checksum_page(page, blkno) учитывает номер блока (blkno). Алгоритм вычисляет значение от страницы с временно обнуленным полем pd_checksum, затем смешивает его с номером блока и сокращает результат до 16 бит.

    Смысл фрагмента src/include/storage/checksum_impl.h:

    /* Псевдокод, сохраняющий порядок операций PostgreSQL */
old = page->pd_checksum;
page->pd_checksum = 0;
checksum = pg_checksum_block(page);
page->pd_checksum = old;
checksum ^= blkno;
return (uint16) ((checksum % 65535) + 1);

    Это не CRC-32C WAL. Внутреннее преобразование блока основано на быстрой смеси 32-битных значений и сокращается до 16-битного результата. Цель — быстрое обнаружение случайных повреждений во множестве страниц. Номер блока помогает заметить перенос страницы на неправильное место внутри отношения, но не превращает checksum в идентификатор отношения, таблицы, кластера или WAL-эпохи.

    Два ограничения модели:

    1. При 16-битном результате возможны коллизии: некоторые изменения байтов останутся незамеченными.
    2. Если некорректное содержимое было принято сервером и для него вычислена новая согласованная checksum, одна эта checksum не сообщит, что прикладные значения ошибочны.

    Отсюда следствие: data checksums полезны в системе защиты данных, но не гарантируют обнаружения всех логических и физических ошибок.

    20.4. Где checksum появляется при записи страницы¶

    Мы уже знаем, что страница меняется внутри PostgreSQL, а позже записывается в файл. Важный вопрос: зачем вычислять checksum при подготовке записи? Если пересчитывать ее при каждом изменении поля строки, цена и конкуренция вокруг страницы резко вырастут, хотя последующие изменения могут еще многократно переписать ту же страницу в памяти.

    Упрощенная последовательность:

    PostgreSQL изменяет buffer page
             │
             ▼
        Буфер dirty
             │
             ▼
Перед фактической записью page copy
             │
             ├── вычислить checksum по байтам и blkno
             └── поместить checksum в записываемый образ
             │
             ▼
      запись страницы в файл

    В PostgreSQL есть функции уровня PageSetChecksumCopy и PageIsVerifiedExtended, а место и способ их вызова зависят от пути буферизации. Ключевая идея: checksum должна соответствовать целостному образу, который записывается, а не произвольному промежуточному изменению строки. Само вычисление и контроль должны согласоваться с блокировками буфера и его жизненным циклом.

    При чтении блока с устройства PostgreSQL проверяет необходимые свойства заголовка и, если проверки страниц включены, сверяет checksum. Если страницу удалось взять из уже существующего shared buffer, повторное чтение с устройства может вообще не происходить; считать, что каждый SQL SELECT заново проверяет 8 КБ, было бы ошибкой.

    20.5. PostgreSQL 18: checksum включена по умолчанию¶

    Это версионно значимый момент. В более старых установках можно встретить кластеры без checksum. Для новых кластеров PostgreSQL 18 стандартное поведение initdb — data checksums включены. Явное отключение:

    initdb --no-data-checksums -D /path/to/new-pgdata

    Команда приведена для иллюстрации поведения initdb, а не как совет создавать production-кластер без защиты. Существующие кластеры при обновлении версии не обязаны автоматически менять ранее выбранный режим. Поэтому всегда проверяем состояние фактического экземпляра:

    SHOW data_checksums;

    Это настройка всего кластера, а не отдельного столбца, таблицы или базы. Она имеет характер состояния данных, а не переключателя, который следует произвольно менять в работающей системе.

    В PostgreSQL 18 инструмент pg_checksums умеет включать, отключать и проверять checksums в остановленном корректно кластере. Для изменения режима нельзя просто подать SQL SET data_checksums = on.

    20.6. pg_checksums: почему операция офлайновая¶

    Предположим, у нас 2 ТБ файлов отношений, а checksum раньше не вычислялась. Хотим включить ее. Программа должна пройти по страницам и записать новые значения pd_checksum. Если параллельно продолжают идти UPDATE и checkpoint, получится гонка между переупаковкой физической страницы и обычным жизненным циклом буфера.

    Поэтому документированный путь pg_checksums требует чистого завершения работы сервера. Некоторые команды:

    # Только на корректно остановленном кластере
pg_checksums --check   -D /path/to/pgdata
pg_checksums --enable  -D /path/to/pgdata
pg_checksums --disable -D /path/to/pgdata

    На практике это административная операция с планированием времени простоя, расходом I/O и резервной копией. --enable может переписывать блоки отношений; --disable изменяет метаданные режима и не означает, что физически «удалены» прежние байты checksum из каждой страницы. После выполнения состояние проверяют также через SHOW data_checksums после старта.

    Опасный флаг: pg_checksums --no-sync снимает ожидание надежной записи результатов этой операции; документация прямо предупреждает о риске повреждения data directory при последующем сбое ОС. Для production это не способ «быстрее закончить обслуживание».

    20.7. Что происходит при обнаружении bad checksum¶

    Рассмотрим обычное чтение страницы отношения. ОС успешно отдала байты, но checksum, вычисленная из полученного образа и номера блока, не совпала с pd_checksum.

    ReadBuffer / чтение файла
          │
          ▼
   8192 байта получены
          │
          ▼
 Проверка заголовка и checksum
          │
      ┌───┴────┐
      │        │
  совпало   mismatch
      │        │
  доступна    ошибка/предупреждение, запись статистики,
  буферная    обработка сбоя в зависимости от режима
  страница

    Конкретное сообщение и дальнейшая реакция зависят от кода чтения и настроек восстановления после ошибок. Характерные сообщения об ошибке checksum содержат идентификатор отношения и номер блока. Не нужно обещать, что любое повреждение будет немедленно обнаружено: если проблемная страница месяцами не читается, до чтения проверка может не произойти.

    SQL для мониторинга:

    SELECT datname,
       checksum_failures,
       checksum_last_failure
FROM pg_stat_database
ORDER BY checksum_failures DESC NULLS LAST;

    Значения счетчиков накопительные и могут быть NULL, если checksums отключены. Для общих отношений PostgreSQL предоставляет статистику в отдельной строке pg_stat_database с datname IS NULL. Даже единичный подтвержденный новый checksum failure требует расследования: пометка «всего один блок» не означает, что хранилище больше не повреждено.

    Не путайте временный рост blks_read с checksum failures; физические чтения, ошибки I/O и ошибки целостности — три независимых события.

    20.8. А можно «просто прочитать данные, игнорируя checksum»?¶

    В PostgreSQL есть параметр ignore_checksum_failure, который предназначен для аварийных восстановительных процедур. Его смысл — предоставить возможность прочитать потенциально поврежденные данные в контролируемом режиме, когда альтернативы уже рассмотрены. Он не делает данные корректными.

    Похожий параметр zero_damaged_pages еще опаснее для понимания: при определенных ошибках PostgreSQL может подставить пустую страницу, что позволяет продвинуться дальше, но означает потерю прежнего содержимого поврежденного блока.

    В production при новом checksum failure разумная последовательность:

    1. Сохранить логи, сведения об устройстве, параметры и точные координаты ошибки. Не запускать автоматическое «лечение» вслепую.
    2. Сверить доступные исправные реплики или резервные копии и определить, затронуты ли критичные отношения.
    3. Исследовать файловую систему, блочное устройство, RAID, память, ошибки ядра и сопутствующие сбои.
    4. Восстанавливать данные из доверенного источника или с использованием подтвержденного плана recovery, а не считать ignore_checksum_failure ремонтом.

    Мы не превращаем этот фрагмент в курс backup из блока 9; вывод для данной темы простой: отключение проверки не восстанавливает поврежденные байты.

    20.9. Почему WAL защищается другой контрольной суммой¶

    В WAL данные расположены не как независимые 8-КБ страницы таблицы. WAL — поток записей, которые могут пересекать границы WAL-страниц. У каждой физической WAL-записи имеется общий заголовок (XLogRecord) с полем xl_crc.

    PostgreSQL использует для WAL CRC-32C — 32-битную циклическую избыточную проверку на основе полинома Castagnoli. CRC рассчитывается по защищаемым байтам записи, включая ее полезное содержимое и необходимые заголовочные поля, исключая само поле CRC. Она позволяет обнаруживать множество случайных повреждений записи и неправильное чтение фрагментов.

    Зачем отличающийся алгоритм? Объем и границы WAL-записи меняются. Ее нужно проверять как целостный объект после чтения и сборки из WAL-страниц. Контрольная сумма страницы данных, зависящая от blkno, здесь не подходит в качестве прямой замены.

    Свойство Data page checksum WAL CRC-32C
    Размер сохраненного значения 16 бит 32 бита
    Единица защиты Страница данных WAL record
    Дополнительная привязка Номер блока Структура и последовательность полей записи
    Когда создается При подготовке образа страницы к записи При сборке WAL-записи
    Основная проверка При чтении страницы При чтении WAL для recovery/репликации
    Защита от злонамеренной подмены Нет Нет

    И CRC, и checksum работают в предположении случайных ошибок, а не атакующего, умеющего специально подбирать коллизии.

    20.10. Откуда берется CRC-32C в коде¶

    В лекции 07.1 мы уже разбирали сборку записи. Теперь посмотрим только на новый слой: как она получает контрольную сумму.

    В src/backend/access/transam/xloginsert.c используется последовательность макросов семейства:

    INIT_CRC32C(crc);
COMP_CRC32C(crc, data, data_len);
/* далее учитываются необходимые части записи */
FIN_CRC32C(crc);

    Это иллюстрация интерфейса CRC, а не полная копия XLogRecordAssemble(). В реальном коде поля и фрагменты обрабатываются в определенном порядке; некоторые заголовочные значения становятся окончательными на более поздней стадии. CRC вычисляется без включения значения самой CRC как входных данных.

    В зависимости от платформы PostgreSQL может использовать оптимизированный аппаратный CRC32C либо программный путь. Поддержка аппаратных инструкций уменьшает CPU-стоимость вычисления, но не меняет смысл и формат проверки. Этот механизм отличается от data page checksum — там другой алгоритм и другая размерность.

    20.11. Где WAL CRC проверяется и что она позволяет сказать¶

    При crash recovery, archive recovery и репликации WAL reader должен разобрать последовательность записей и проверить ее корректность. Сначала требуется прочитать соответствующие байты, при необходимости собрать запись, пересекающую страницу, проверить структурные ограничения, затем сверить CRC перед передачей корректной записи обработчику.

    WAL pages / files
       │
       ▼
   WAL reader
       │
       ├── assembled record
       ├── размеры, заголовки, внутренние ссылки
       └── CRC-32C
              │
       ┌──────┴──────┐
       │             │
      OK            mismatch
       │             │
       ▼             ▼
   rmgr / REDO   нарушение ожидаемого
                 WAL-формата или конца журнала

    Важная тонкость: не всякая некорректная последняя запись — «порча всей базы». Авария могла оборвать физическую запись самого хвоста WAL. Recovery обязан корректно определить действительный конец последовательности и обрабатывать ситуацию с учетом контекста. Однако повреждение необходимой WAL-записи посередине истории может сделать продолжение восстановления невозможным. Сам CRC не воспроизводит потерянное содержимое.

    Не следует трактовать «CRC совпала» как криптографическую подпись или полную гарантию отсутствия corruption. 32 бита — конечное число возможных значений; случайные коллизии принципиально возможны.

    20.12. Почему CRC WAL не защищает data page от torn write¶

    Теперь специально испортим простую модель. Наш WAL record полностью правильный, его CRC совпала. Но в момент аварии OS/SSD успел заменить только часть 8-КБ data page, а другая часть осталась прежней.

    До записи:
[AAAA][AAAA][AAAA][AAAA]  (четыре условных фрагмента)

Новая страница:
[BBBB][BBBB][BBBB][BBBB]

После оборванной записи:
[BBBB][BBBB][AAAA][AAAA]  ← torn page

    WAL CRC подтверждает, что сама WAL-запись корректна. Она не доказывает атомарность записи другой страницы в другом файле. Data checksum может обнаружить смесь двух версий, но уже знакомая проблема остается: как вернуть целиком правильный образ страницы?

    Здесь связь с темой 11 основной лекции: full_page_writes помогает пережить torn page, записывая подходящий полный образ измененной страницы в WAL. Мы не повторяем алгоритм checkpoint/REDO; рассматриваем только задачу защиты на границе storage.

    20.13. Full-page image: почему копия страницы появляется в WAL¶

    При обычной конфигурации full_page_writes=on после checkpoint первое WAL-журналируемое изменение страницы при соответствующих условиях может включать в WAL ее полный образ — full-page image (FPI). В WAL оказывается достаточно информации для замещения ранее сохраненной частично записанной страницы при последующем REDO.

    После checkpoint
        │
        ▼
Первая нужная модификация страницы P
        │
        ├── обычные сведения об изменении
        └── full-page image P в WAL (при выполнении условий)
                       │
                       ▼
        долговечный WAL подтвержден
                       │
              затем data page write
                       │
                    сбой питания
                       │
                       ▼
              REDO восстанавливает
              соответствующий образ

    Это не постоянная полная копия каждой страницы при каждом UPDATE. Такие образы добавляют объем WAL в выбранных ситуациях; в частности, на первом существенном изменении после checkpoint. FPI может сжиматься согласно wal_compression при поддерживаемом алгоритме (pglz, lz4, zstd), что меняет компромисс между CPU и объемом WAL.

    Ценность FPI: когда на диске осталась смесь двух версий, в корректно сохраненном WAL может существовать цельный образ, достаточный для восстановления. Предел: повреждение, которое возникло позже и не покрыто доступной историей восстановления, само по себе FPI не исправит.

    20.14. Checksums и FPI решают разные половины задачи¶

    Теперь сопоставим два инцидента.

    Сценарий А: торнадо между data write и power loss. Две половины страницы принадлежат разным версиям. После перезапуска доступный WAL содержит подходящую FPI. В этом случае recovery способен применить образ и вернуть согласованную страницу.

    Сценарий Б: тихая ошибка SSD через месяц. Старая страница была корректной после всех checkpoint, WAL-сегменты, нужные для ее давней модификации, давно удалены как ненужные для текущего восстановления. Один бит испортился на носителе. Data checksum выявляет ошибку при чтении, но нужного FPI в текущем WAL уже может не быть. Для восстановления потребуется доверенная копия или иной внешний источник.

    Ситуация Checksum обнаруживает? Может помочь FPI?
    Частичная запись страницы в момент crash Часто да, если поврежденный образ читается и checksum доступна Да, если в нужном WAL есть подходящая корректная запись
    Случайное позднее изменение блока на SSD Часто да при чтении Не обязательно: соответствующая история уже может отсутствовать
    Повреждение самой WAL-записи Data checksum не относится к WAL CRC обнаруживает ошибку; FPI внутри поврежденной записи тоже может быть недоступна
    SQL записал неверную бизнес-сумму Обычно нет: физический образ может быть корректным Нет, WAL воспроизводит те же физические изменения
    Утеряно все устройство Не на чем проверять Нужна внешняя сохраненная копия

    Обнаружение != восстановление. Это главный вывод темы 20.

    20.15. wal_log_hints: почему даже hint bit может создать WAL¶

    Hint bits — служебные флаги в строках, позволяющие ускорить последующие проверки состояния транзакции. Обычно такие вспомогательные изменения допускают особое обращение: их можно заново определить из состояния системы. Поэтому возникает соблазн не журналировать hint-бит как полноценное изменение данных.

    Но включим data checksums. В одном месте страницы поменялся бит, а физическая запись 8-КБ страницы уже получила новую checksum. Теперь представим частичную запись. Можно получить смесь прежнего образа и нового hint bit вместе с checksum, относящейся к другому набору байтов. Это дополнительный источник несоответствия при аварии.

    Параметр:

    SHOW wal_log_hints;
SHOW data_checksums;

    wal_log_hints=on требует WAL-журналирования соответствующих полных образов страниц при первых после checkpoint изменениях даже для hint-bit updates. Но PostgreSQL 18 документирует: если data checksums включены, изменения hint bits журналируются независимо от wal_log_hints, и сама настройка игнорируется. Поскольку checksums включены по умолчанию у новых кластеров 18, значение wal_log_hints=off не является доказательством отсутствия соответствующих WAL-записей.

    Здесь нельзя делать вывод «каждое чтение создает FPI»: все зависит от того, изменился ли hint bit, состояния страницы относительно checkpoint, способа журналирования и фактического пути выполнения.

    20.16. Важно: checksum проверяется при чтении, а не непрерывно¶

    Представим таблицу на 500 ГБ. Вчера поврежден один блок, которым никто не пользуется. Все запросы в пределах горячего рабочего набора проходят успешно, а checksum_failures остается нулевым.

    Это не противоречие. PostgreSQL обычно проверяет страницу при чтении с хранения, а не непрерывно сканирует каждую страницу каждого файла. Также если страница уже находится в shared buffers, повторное чтение файла не обязательно. Значит, отсутствие зафиксированных ошибок не подтверждает целостность каждого байта всего кластера.

    Можно использовать управляемые проверки на остановленном кластере с pg_checksums --check или отдельные процедуры контрольного чтения данных. Но полная проверка может требовать существенного I/O и должна проводиться с пониманием влияния на обслуживание и SLA. Контрольная сумма данных не проверяет логическую структуру всех B-tree-индексов; для этого существуют иные методы анализа, но в данном блоке мы не разворачиваем соседнюю тему.

    20.17. Какие данные покрываются проверками¶

    Документация PostgreSQL 18 прямо ограничивает область защиты. Data page checksums относятся к страницам данных; они не означают единый checksum для каждого внутреннего файла кластера.

    Примеры, требующие отдельного понимания:

    • WAL records защищаются CRC-32C; они не являются data pages с pd_checksum.
    • pg_xact, pg_subtrans, pg_multixact и другие внутренние структуры не покрываются обычным checksum страниц данных. Для необходимых долговечных изменений там используются собственные протоколы и WAL-механизмы.
    • Временные файлы сортировки, материализации и промежуточных результатов не получают ту же защиту data page checksums и WAL.
    • Файлы состояния двухфазных транзакций pg_twophase используют собственную CRC-32C-защиту.
    • Full-page image, помещенная в WAL, включена в защищаемое CRC содержимое соответствующей WAL-записи.

    Поэтому слова «у нас включены checksums» следует переводить на инженерный язык: конкретные классы объектов проверяются в конкретные моменты определенными алгоритмами.

    20.18. Цена checksums и CRC: что оплачивает CPU, а что — I/O¶

    Вычисление data checksum — дополнительная работа CPU, обычно пропорциональная размеру обрабатываемой страницы, и дополнительная проверка на чтении. Сохранение pd_checksum требует записать соответствующий образ страницы, но не предполагает отдельной файловой операции на каждое обновление строки. WAL CRC-32C также добавляет CPU-работу, связанную с числом и размером WAL-записей.

    Для прикидки:

    CPU checksum работы ~ количество проверенных/записанных страниц × 8192 B
CPU WAL CRC работы ~ объем защищенного содержимого WAL

    Это качественная оценка, а не бенчмарк CPU-циклов и не обещание линейной зависимости latency. Применяются разные оптимизации, кеш-поведение и аппаратные инструкции. При медленном SSD цена checksum может быть скрыта за I/O, а на сервере с очень высокой пропускной способностью дополнительных CPU-инструкций может стать заметно больше. Под нагрузкой также важен косвенный эффект: включенные checksums вызывают соответствующее WAL-журналирование hint-bit изменений, что увеличивает возможный объем WAL, FPI и последующую стоимость storage.

    Ошибка измерения: сравнили два экземпляра с разными checkpoint, наполнением shared buffers и состоянием индексов — получили «checksum замедляет INSERT на 40%». Без фиксации остальных факторов это не вывод о checksum. Измерять нужно сопоставимые кластеры на одной версии, с одинаковой нагрузкой, данными, memory footprint и состоянием хранилища, выделяя отдельно CPU, байты WAL и задержку I/O.

    20.19. Диагностика повреждения: где нужен конкретный адрес¶

    Когда обнаружен mismatch, нужны координаты проблемы: отношение, fork, блок, база, tablespace. Имя SQL-таблицы само по себе недостаточно. Физическая структура может иметь отдельные файлы для main fork, free space map, visibility map, initialization fork; кроме того, блоки логической таблицы и соответствующих индексов — разные физические объекты.

    В журналах, помимо checksum failure, ищем:

    read / write / fsync errors
I/O error / EIO
short read
invalid page header
unexpected data beyond EOF
WAL record CRC mismatch

    Формулировки могут различаться; строки выше — классы симптомов, а не обещание буквального сообщения PostgreSQL для каждого дефекта. При аппаратной проблеме важно также посмотреть dmesg, SMART/NVMe health, RAID logs, сообщения гипервизора и инциденты по всей системе хранения.

    Полезно разделять пять событий:

    1. I/O error: устройство или ОС признало невозможность выполнить операцию.
    2. Checksum mismatch: байты отданы, но не соответствуют ожидаемой контрольной сумме.
    3. WAL CRC mismatch: чтение журнала обнаружило некорректную WAL-запись.
    4. Torn page: при записи получилась смесь разных версий страницы.
    5. Логическая ошибка приложения: физический формат и checksums могут быть полностью корректными.

    Разные причины требуют разного расследования. Массовая автоматическая попытка перезаписи подозрительных файлов может уничтожить улику и затруднить восстановление.

    Главное из темы 20¶

    1. В PostgreSQL 18 новые кластеры по умолчанию включают data page checksums; реальное состояние проверяется через SHOW data_checksums.
    2. pd_checksum — 16-битная проверка страницы с привязкой к номеру блока, не криптографическая подпись.
    3. Каждая WAL-запись защищается отдельной CRC-32C; ее проверяют при чтении соответствующего WAL.
    4. Full-page images позволяют восстановить определенные частично записанные страницы, когда нужный WAL сохранен и доступен.
    5. При включенных checksums hint-bit updates требуют WAL-журналирования независимо от значения wal_log_hints.
    6. Checksums обнаруживают только часть физических ошибок и, как правило, при чтении. Они не создают дополнительную копию данных.
    7. Измеряйте стоимость и риски отдельно: CPU checksum/CRC, объем WAL/FPI, ошибки хранения и восстановимость после инцидента.

    21. UNLOGGED Tables: осознанный отказ от долговечности содержимого¶

    21.1. Кажется, WAL дорогой. Может, просто не писать его для таблицы?¶

    Возьмем backend-задачу: сервис получает большой внешний файл, разбирает записи, проверяет формат и складывает их в промежуточную таблицу. Затем данные обрабатываются и переносятся в постоянные структуры. Если процесс перезапустится, внешний файл можно прочитать еще раз.

    Для чего во время этой промежуточной загрузки создавать WAL на каждую страницу временного набора данных? Если мы гарантированно можем восстановить информацию из входного источника, цена WAL может не окупаться. PostgreSQL предоставляет механизм UNLOGGED tables.

    CREATE UNLOGGED TABLE import_stage (
    batch_id    bigint NOT NULL,
    row_no      bigint NOT NULL,
    payload     jsonb NOT NULL
);

    Но вот здесь начинается самое интересное. Популярный вывод «UNLOGGED = таблица в RAM» неверен. Таблица занимает обычные файлы отношений, ее страницы проходят через shared buffers и файловую систему, и ее содержимое может нормально переживать чистые остановки сервера. PostgreSQL сознательно отказывается от возможности надежного восстановления ее содержимого после аварийного завершения.

    Проще сформулировать инженерный контракт:

    Схема UNLOGGED-таблицы сохраняется. Ее данные и соответствующие индексы допускается потерять после crash/unclean shutdown. Такой таблице нельзя доверять как долговечному источнику истины.

    Этот выбор касается конкретного физического отношения, а не всего кластера, в отличие от fsync=off.

    21.2. UNLOGGED vs обычная vs временная таблица¶

    Сначала уберем три похожих слова из одного ящика.

    Свойство Обычная таблица (LOGGED) UNLOGGED TEMPORARY
    Срок жизни схемы Постоянная Постоянная Обычно в пределах сессии
    Физические файлы на storage Да Да Да, при необходимости; локальные структуры буферизации
    Обычный WAL для изменения содержимого Да Нет Нет
    Содержимое после чистой остановки/старта Сохраняется Сохраняется Сессия уже закончена
    Содержимое после аварийной остановки Восстанавливается по WAL в пределах гарантий Сбрасывается Не сохраняется между сессиями
    Данные доступны на физическом standby По правилам репликации Нет Нет
    Индексы Обычные Автоматически unlogged Автоматически временные

    UNLOGGED пригодна для общей промежуточной таблицы, доступной разным соединениям и переживающей нормальные перезапуски. TEMP привязана к сессии и решает другую задачу. Оба варианта уменьшают WAL для содержимого, но имеют разные правила жизненного цикла и доступа.

    21.3. Почему UNLOGGED может ускорять запись¶

    Для обычной таблицы изменение затрагивает страницу отношения и требует соответствующих WAL-записей. Мы уже подробно разобрали этот путь. Для unlogged-отношения PostgreSQL не создает обычный WAL с физическими изменениями его пользовательских страниц. Это снимает часть работы: запись и сборку этих WAL-записей, соответствующий объем в pg_wal, связанные с ним CPU/копирование и необходимость WAL для восстановления таких изменений.

    Обычная таблица:                      UNLOGGED:

INSERT                                 INSERT
  │                                      │
  ├── data page dirty                    └── data page dirty
  ├── heap WAL                                  │
  ├── index WAL                                 ▼
  └── WAL write/flush                    запись файла позже
           │
           ▼
     запись файла позже

    Здесь диаграмма намеренно упрощена: работа с каталогами, транзакциями, файлами и другими logged-объектами может создавать WAL даже рядом с операциями над unlogged-таблицей. Нельзя обещать «после CREATE UNLOGGED TABLE глобальный pg_stat_wal.wal_bytes перестанет расти».

    UNLOGGED не отменяет:

    • файловую запись страниц таблицы;
    • работу shared buffers и соответствующую конкуренцию;
    • поддержание индексов, ограничения и проверки SQL;
    • MVCC, видимость изменений и транзакционные механизмы во время нормальной работы;
    • расход CPU на сериализацию строк, вычисление выражений и проверки;
    • необходимость физически размещать таблицу на накопителе.

    Поэтому прирост производительности зависит от профиля операции. Если нагрузка упирается в вычисление сложного выражения или поддержание большого индекса, удаление части WAL не обязано дать драматическое ускорение.

    21.4. Что именно не попадает в обычный WAL¶

    Ключевое различие — содержимое отношения и метаданные кластера.

    При вставке и обновлении строк UNLOGGED-таблицы обычное физическое журналирование heap-страниц отключено. Индексы такой таблицы тоже unlogged, поэтому их физическое содержимое также не должно восстанавливаться через обычные WAL-записи. При этом PostgreSQL продолжает журналировать те системные изменения, которые требуются, чтобы существование и описание отношения были согласованы с состоянием каталога после восстановления.

    Это позволяет после сбоя иметь правильную схему import_stage, хотя строки и рабочие структуры индексов сброшены.

    CREATE UNLOGGED TABLE
       │
       ├── описания таблицы в каталогах: сохранены
       ├── физическое содержимое: без обычного WAL
       └── стартовый образ отношения: init fork

    Не следует выводить из слова «unlogged», что вообще никакого WAL не создается во время INSERT или COMMIT такой транзакции: она может менять иные долговечные объекты, вызывать записи для транзакционного состояния и системных операций. Граница проходит по журналированию страниц пользовательского unlogged-отношения, а не по полной остановке WAL-подсистемы PostgreSQL.

    21.5. Как сервер помнит, что отношение unlogged¶

    У отношения в системном каталоге pg_class есть признак relpersistence:

    • p — permanent, обычное долговечное отношение;
    • u — unlogged;
    • t — temporary.

    Посмотрим для таблицы и ее индексов:

    SELECT c.oid::regclass AS relation,
       c.relkind,
       c.relpersistence,
       pg_relation_filepath(c.oid) AS path
FROM pg_class AS c
WHERE c.oid = 'import_stage'::regclass
   OR c.oid IN (
       SELECT indexrelid
       FROM pg_index
       WHERE indrelid = 'import_stage'::regclass
   )
ORDER BY c.relkind, relation;

    relpersistence='u' — состояние каталога, которое сервер использует при выборе физической семантики отношения. Путь pg_relation_filepath() указывает на основное расположение relation file в текущем кластере. Он не означает, что у отношения существует только один файл.

    Нужно также понимать, что имя файла строится из физического идентификатора отношения, который может меняться при некоторых операциях переписывания. Поэтому подставлять условный номер из SQL-имени таблицы в путь на диске нельзя.

    21.6. init fork: как обнулить таблицу и не разрушить ее структуру¶

    И вот теперь важная механика. Если после crash содержимое unlogged-таблицы нельзя доверять, как сделать ее пустой? Просто удалить все файлы? Но индекс — это не всегда последовательность строк. Даже пустой B-tree имеет начальную служебную структуру и заголовки, без которых объект не сможет работать.

    PostgreSQL использует initialization fork, или init fork. Для каждой unlogged-таблицы и каждого ее unlogged-индекса хранится начальный образ соответствующего типа отношения.

    До crash (пример логических файлов):

12345         — main fork: рабочие страницы таблицы
12345_fsm     — free space map (если существует)
12345_vm      — visibility map (если существует)
12345_init    — начальный образ для reset

После аварийного reset:

12345_init ─── копия ───► 12345 (пустая таблица)
прочие рабочие forks удаляются и восстанавливаются по необходимости

    Важно: «пустая» здесь означает логически пустая, а не обязательно файл длиной ноль байт. Например, начальное состояние индекса может содержать метастраницу или другую обязательную структуру. Поэтому init fork сохраняет корректный образ для данного access method.

    Это документированный механизм PostgreSQL 18 (Database Physical Storage → The Initialization Fork).

    21.7. Какая часть init fork нужна recovery¶

    Пройдем аварийное завершение:

    1. PostgreSQL создал UNLOGGED-таблицу и ее индекс. Метаданные и их стартовые образы сохранены в соответствии с механизмом СУБД.
    2. Приложение загрузило миллион строк. Страницы менялись в памяти и записывались в файлы. Обычный WAL этих пользовательских страниц не велся.
    3. Питание исчезло. На диске могла сохраниться произвольная смесь старых и новых рабочих страниц. Нет достаточной обычной WAL-истории, чтобы восстановить их согласованно.
    4. На следующем аварийном запуске PostgreSQL выявляет unlogged-отношения по их init fork, удаляет рабочие forks и копирует начальные образы.
    5. Сервер снова видит корректную пустую таблицу и соответствующий пустой индекс.

    Это гораздо надежнее попытки «прочитать все, что случайно осталось» и выдать пользователю частично сохранившиеся строки как логически корректные. После unclean shutdown unlogged-данные рассматриваются как целиком потерянные, даже если физически почти все байты пережили сбой.

    Механизм находится в src/backend/storage/file/reinit.c, где вызывается ResetUnloggedRelations(); его операции разделяются на удаление рабочих forks и восстановление из initialization forks. Мы называем функцию для привязки к исходникам, не разбирая здесь все проходы по каталогам и tablespaces — подробный общий порядок старта относится к 07.3.

    21.8. Чем чистая остановка отличается от аварийной¶

    Здесь ломается еще одно упрощение: «UNLOGGED всегда очищается при перезапуске». Нет.

    При чистой остановке PostgreSQL завершает требуемую работу с файловыми данными, и содержимое unlogged-отношений обычно сохраняется. После последующего нормального старта таблица содержит те же строки.

    После crash или unclean shutdown PostgreSQL обязан сбросить содержимое unlogged-отношений, потому что не может подтвердить их физическую согласованность через обычный WAL.

     INSERT 1000 rows
       │
       ├── clean stop → start  ─────► 1000 rows
       │
       └── crash / unclean → start ─► 0 rows

    Ветка «1000» справедлива для полностью завершенных и корректно зафиксированных изменений в данном примере, при исправном storage и штатной остановке. Нельзя использовать ее как обещание сохранности UNLOGGED при внезапной потере питания.

    Кроме того, «сервер PostgreSQL завершился» и «весь Linux выключился корректно» — разные события. Решение о reset опирается на состояние и процедуры старта кластера, а не на впечатление пользователя о том, что процесс просто «перезапустили».

    21.9. Почему индекс на UNLOGGED автоматически unlogged¶

    Допустим, данные таблицы после аварии сброшены, а индекс почему-то сохранил старые ключи и ссылки на прежние строки. Получилась бы внутренняя несогласованность: индекс указывает на исчезнувшие данные.

    Поэтому PostgreSQL делает индексы unlogged-таблицы unlogged автоматически:

    CREATE UNLOGGED TABLE cache_stage (
    id bigint PRIMARY KEY,
    payload text NOT NULL
);

CREATE INDEX cache_stage_payload_idx
    ON cache_stage (payload);

    Оба индекса физически принадлежат unlogged-отношению и после аварийного reset должны вернуться к корректному пустому состоянию. У каждого предусмотрен свой initialization fork, соответствующий его формату.

    Инженерный эффект: не нужно вручную пересоздавать обычные индексы после каждой аварии только потому, что данные unlogged-таблицы очищены. Но schema остается, а данные не становятся восстановленными: приложение должно снова заполнить staging/cache, если они нужны бизнес-процессу.

    21.10. Последовательности SERIAL и IDENTITY¶

    У unlogged-таблицы может быть автоинкрементный идентификатор:

    CREATE UNLOGGED TABLE stage_events (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payload text NOT NULL
);

    В PostgreSQL 18 документация CREATE TABLE уточняет: последовательности, создаваемые вместе с unlogged-таблицей для SERIAL или IDENTITY, также создаются unlogged. Это уменьшает риск некорректной комбинации durability и соответствует семантике временного набора данных.

    Но отсюда не следует, что последовательность гарантирует непрерывность значений или их повторяемость. Даже обычные sequence никогда не предназначались для строгой непрерывности номера без пробелов. После аварийного сброса unlogged-объектов нельзя строить бизнес-идентичность или требования аудита на значениях, которые могли быть потеряны вместе с содержимым.

    Отдельная последовательность, созданная независимо, имеет собственный relpersistence; не следует автоматически считать любую sequence unlogged только потому, что из нее читает unlogged-таблица.

    21.11. Почему UNLOGGED не является кэшем внутри RAM¶

    Обычный индекс и unlogged-индекс могут занимать одинаковое количество физических страниц. Операции поиска, проверок ограничений, вставки новых страниц и записи буферов продолжают работать с этими структурами. shared_buffers обслуживает unlogged-таблицу согласно стандартной логике буферизации для постоянных отношений.

    Под нагрузкой могут остаться прежними:

    • число heap/index pages, затронутых одной операцией;
    • стоимость обновления B-tree при уникальном индексе;
    • конкуренция за буферы и физические страницы;
    • расход RAM на рабочий набор;
    • чтения холодных блоков с накопителя;
    • давление фоновой записи data files.

    Именно поэтому один профиль нагрузки выигрывает сильно, а другой — незначительно. UNLOGGED выключает выбранную цену восстановления, но не превращает полноценную реляционную таблицу в map в оперативной памяти.

    21.12. Нагрузка: сравнение логирования и реальной записи¶

    Проведем мысленный эксперимент. В двух одинаково подготовленных таблицах по 10 миллионов строк, одинаковые индексы, одинаковые INSERT-пакеты. В одной таблице каждая модификация генерирует WAL для восстановления. Во второй обычный WAL ее содержимого не создается.

    Пример ожидаемых направлений, без выдуманных чисел:

    Измерение Возможное изменение с UNLOGGED Почему
    WAL bytes на операции Заметно меньше Нет обычного heap/index WAL содержимого
    CPU на подготовку WAL Меньше Меньше записей и работы с ними
    WAL flush pressure Может снизиться Меньше журналируемых данных
    Data file writes Остаются Страницы таблицы и индексов по-прежнему записываются
    Стоимость индексной вставки Почти та же логика B-tree все еще нужно поддерживать
    Latency отдельной транзакции Может снизиться, но не обязана Ограничитель может быть вне WAL
    Время восстановления содержимого после crash Становится задачей приложения PostgreSQL очищает unlogged-отношения

    Признак хорошей инженерной оценки: помимо средней TPS, измерены объем WAL, CPU и storage I/O, а также документирован объем данных, которые можно потерять, и время повторной загрузки.

    21.13. Почему pg_stat_wal не всегда показывает «ноль»¶

    Предположим, мы измеряем:

    SELECT wal_records, wal_fpi, wal_bytes
FROM pg_stat_wal;

    Затем вставляем 100 тысяч строк в UNLOGGED. Счетчики могли увеличиться. Значит ли это, что механизм не работает? Нет.

    pg_stat_wal — кластерные счетчики. Пока идет ваш тест, другие backend-процессы и системная активность могут генерировать WAL. Кроме того, DDL, изменения каталогов и иные durable-объекты сохраняют собственные требования. Счетчики не показывают, какая доля относится именно к исследуемой таблице.

    Для конкретного SQL в PostgreSQL доступен EXPLAIN с включенным счетчиком WAL:

    EXPLAIN (ANALYZE, BUFFERS, WAL)
INSERT INTO import_stage(batch_id, row_no, payload)
SELECT 10, g, jsonb_build_object('x', g)
FROM generate_series(1, 10000) AS g;

    Предупреждение: EXPLAIN ANALYZE действительно выполняет INSERT. На учебном экземпляре это допустимо, на production нужно сначала решить, можно ли вносить такие данные. Сам формат EXPLAIN WAL-метрик следует читать как счетчики соответствующего statement; не ожидайте, что полностью исчезнет любой WAL, если операция косвенно затрагивает другие структуры.

    21.14. Как корректно сравнить LOGGED и UNLOGGED¶

    Устраним распространенную ошибку тестирования: обычную таблицу загружают со всеми индексами, а unlogged — без них; затем выдают ускорение как заслугу WAL. Это сравнение разной работы.

    Минимальная экспериментальная пара:

    CREATE TABLE stage_logged (
    id bigint PRIMARY KEY,
    payload text NOT NULL
);

CREATE UNLOGGED TABLE stage_unlogged (
    id bigint PRIMARY KEY,
    payload text NOT NULL
);

    Одни и те же объемы и распределения данных, индексы, партии вставки, число соединений, конфигурация кластера. Измеряем по отдельности INSERT latency/TPS, WAL bytes, CPU, физические записи, время фоновой работы. Повторяем после прогрева и учитываем checkpoint- и cache-эффекты. Нельзя смешивать начальное создание таблиц, построение индексов и bulk INSERT в одну неразделенную цифру.

    Из результата важно сделать два вывода, а не один:

    1. Сколько ресурсов на обычное WAL-журналирование действительно удалось сэкономить?
    2. Сколько будет стоить повторно построить содержимое staging и индексы после crash, и приемлемо ли это по требованиям сервиса?

    Если rebuild занимает 40 минут, а поток данных нельзя повторно получить, цена оптимизации может быть неприемлемой независимо от красивого прироста TPS.

    21.15. Чем UNLOGGED отличается от synchronous_commit=off¶

    Здесь крайне важно не спутать два похожих компромисса.

    synchronous_commit=off для обычной таблицы: WAL для изменений все еще ведется. Клиент может получить успешный ответ до необходимого flush. После аварии возможно исчезновение последних транзакций, но при корректном fsync/storage база должна вернуться к согласованному состоянию. Уцелевшие WAL-записи и долговечная часть истории восстанавливаются обычным механизмом.

    UNLOGGED: нет обычной WAL-истории для физического содержимого конкретного отношения. После crash таблица возвращается в начальное пустое состояние, даже если некоторые ее data pages уже физически были на диске. Это сознательная потеря всей рабочей версии данного набора данных.

    Вопрос LOGGED + synchronous_commit=off UNLOGGED
    Генерируется WAL содержимого таблицы? Да Нет
    Может ли клиент видеть OK до локального WAL flush? Да Применимость зависит от других WAL-операций транзакции; сама таблица не получает обычной WAL-долговечности
    После crash теряется только часть последних транзакций? Да, по модели асинхронного commit Содержимое отношения сбрасывается целиком
    Поддерживается восстановление содержимого по WAL? Да, в пределах долговечной WAL-истории Нет
    Требуется rebuild данных после аварии? Обычно нет как следствие одного async commit Да, если данные необходимы приложению

    Эти две настройки отвечают на разные вопросы и выбираются по разным требованиям к данным.

    21.16. UNLOGGED и standby: почему повторить данные нечем¶

    Физическая потоковая репликация передает необходимые WAL-изменения. А у UNLOGGED нет обычных WAL-записей о содержимом страниц. Следовательно, standby не получает содержимое unlogged-отношения и не может поддерживать его в актуальном состоянии тем же механизмом, которым поддерживает обычные таблицы.

    В документации PostgreSQL 18 прямо сказано: содержимое unlogged-таблиц не реплицируется на standby. Это ограничение нельзя исправить тем, что мы установим более частые checkpoints или synchronous_commit=remote_apply: отсутствующую WAL-историю это не создаст.

    При проектировании backend-сервиса следует считать, что unlogged-содержимое локально для текущего первичного экземпляра и должно быть восстановимо вне физической репликации. Схема таблицы при этом существует в каталогах кластера; не нужно путать «схема не существует на реплике» с «данные недоступны».

    21.17. Что будет при failover или promote¶

    Предположим, primary использует UNLOGGED как локальный staging. Затем primary теряется, а standby получает роль нового primary. У нового primary нет актуального содержимого staging, потому что оно не передавалось через физический WAL. Поэтому сервис, который полагался на эту таблицу как на единственную очередь задач, может потерять задания.

    Сравните два дизайна:

    Дизайн А (опасный):
Клиент → UNLOGGED tasks → worker
            │
            └── единственная копия задания

Дизайн Б (допустимый):
Durable source → UNLOGGED staging → обработка → durable result
      │
      └── источник позволяет восстановить staging

    Ниже мы не открываем отдельный блок о распределенных очередях и exactly-once. Для этой темы достаточно критерия: восстановимость из внешнего достоверного источника должна быть предусмотрена до выбора UNLOGGED, а не придумана после инцидента.

    21.18. Как сменить физический режим отношения¶

    PostgreSQL предоставляет:

    ALTER TABLE import_stage SET LOGGED;
ALTER TABLE import_stage SET UNLOGGED;

    Но переключение режима затрагивает физическое устройство отношения и может требовать серьезной работы с данными, индексами и блокировками. Для ALTER TABLE действует правило уровня блокировки, и для такого изменения следует исходить из возможности длительной недоступности таблицы во время операции. Точные детали исполнения зависят от вида отношения, текущего размера, версии и состояния.

    Это не мгновенный переключатель «покажи тот же файл с другим флагом». Особенно опасно применять его к большим рабочим таблицам при высокой конкурентной нагрузке без отдельного плана выполнения.

    PostgreSQL 18 также указывает ограничения на такие операции для partitioned tables. Не следует механически переносить синтаксис SET LOGGED на произвольную иерархию партиций без проверки документации.

    21.19. Где UNLOGGED подходит, а где превращается в инцидент¶

    Подходит, если данные допускают полную потерю:

    • Промежуточное хранение результатов импорта, когда входной файл или поток зафиксирован надежно и может быть проигран повторно.
    • Локальный вычисляемый кеш, который автоматически прогревается из durable-источника.
    • Пересоздаваемые агрегаты обработки, если перезаполнение не нарушает SLA и не теряет единственное событие.
    • Учебные или одноразовые аналитические стенды без требований к восстановлению рабочего набора.

    Обычно опасно:

    • Балансы, платежные проводки, заказы, единственные записи о принятом запросе.
    • Единственная таблица задач фоновой обработки: потеря строки означает потерю работы.
    • Аудит и соответствие регуляторным требованиям.
    • Источник данных, требуемый после failover без повторной загрузки.
    • Место, где «потом восстановим» никто не превратил в проверенный алгоритм и оцененное время.

    Главный критерий выбора — не «мы хотим быстрый INSERT», а каков контракт хранения этих конкретных данных после любого нештатного завершения.

    21.20. Неочевидная цена UNLOGGED: восстановление переезжает в приложение¶

    Допустим, год без сбоев UNLOGGED ускоряет bulk insert на некоторую величину. Затем один раз на production происходит power loss. После старта staging пустой. Процесс повторной загрузки требует 200 ГБ сетевого трафика, 50 минут CPU и обращения к источнику, доступность которого ограничена.

    Стоимость WAL мы убрали с горячего пути и перенесли в другой бюджет:

    Обычная таблица:
ежедневная цена WAL → обычное recovery → данные возвращены

UNLOGGED:
меньшая ежедневная цена WAL → crash → пустая таблица
                                      │
                                      ▼
                         повторное получение и rebuild
                                      │
                                      ▼
                        downtime / CPU / сеть / риск

    Ускорение признается полезным только после сравнения полной стоимости владения: средняя нагрузка, вероятность отказов, ожидаемая потеря содержимого, время rebuild и требования бизнеса. Если сервис обещает, что принятая задача не будет утрачена, одна unlogged-таблица не может быть последней точкой ее сохранения.

    21.21. Короткое техническое расследование инцидента¶

    Симптом. В понедельник таблица import_stage содержала около 8 миллионов строк. Во вторник после аварийного запуска SELECT count(*) возвращает ноль. Ошибок восстановления обычных таблиц нет.

    Наивная гипотеза. «Кто-то выполнил TRUNCATE», «произошла потеря всех файлов», «сломался WAL».

    Проверка:

    SELECT relname, relpersistence
FROM pg_class
WHERE oid = 'import_stage'::regclass;

    Получаем relpersistence='u'. Проверяем журнал старта, состояние кластера, схему и индексы. Увидели аварийный restart; отсутствие содержимого соответствует контракту UNLOGGED. Нужно не обвинять WAL, а выяснить, существовал ли обещанный durable источник для пересоздания staging.

    Инженерный вывод. Корректная работа PostgreSQL может выглядеть для приложения как «пропали данные», если разработчик перепутал ускоренный staging и долговечное хранилище. Это ошибка контракта данных, а не обязательно ошибка движка.

    Главное из темы 21¶

    1. UNLOGGED — физически хранимая таблица с постоянной схемой, но без обычного WAL для содержимого.
    2. Она не является RAM-only таблицей и не освобождает от data-file I/O, индексов и MVCC.
    3. После чистой остановки данные сохраняются; после аварийной PostgreSQL сбрасывает содержимое.
    4. Для сброса используются initialization forks; индексы unlogged-таблицы тоже unlogged.
    5. Обычная физическая репликация не переносит содержимое unlogged-таблиц.
    6. synchronous_commit=off меняет момент подтверждения, UNLOGGED — саму возможность восстановить содержимое по WAL.
    7. Критерий применения — заранее проверенный способ пересоздания данных и приемлемое время этого процесса.

    Вернемся к транзакции с начала лекции:

                       Изменение logged data
                            │
                            ▼
                    WAL record + CRC-32C
                            │

Параллельно data pages: dirty → checksum → data file.
При torn page доступная FPI в WAL может восстановить страницу.
При поздней порче data checksum помогает обнаружить дефект.
UNLOGGED обходит обычную WAL-историю содержимого и сбрасывается после crash.

    Семь тезисов, которые должны остаться у инженера¶

    1. PostgreSQL доверяет контракту ОС и storage. fsync работает через несколько слоев, и ни один SQL-параметр не исправляет ложь неисправного накопителя.
    2. Прием записи, сохранение в page cache и долговечный flush — разные события. Механизм WAL строит порядок поверх этих различий.
    3. PLP защищает определенный объем подтвержденных данных от потери питания. Это не синоним атомарной 8-КБ записи и не гарантия от всех сбоев.
    4. Data checksum и WAL CRC-32C проверяют разные сущности. Первая привязана к странице и номеру блока, вторая — к WAL-записи.
    5. FPI позволяет восстановить определенные torn pages, но не заменяет независимую копию данных. Checksums обнаруживают проблему, не возвращают байты сами по себе.
    6. Для новых кластеров PostgreSQL 18 data checksums включены по умолчанию. Диагностика WAL I/O в 18 использует pg_stat_io.
    7. UNLOGGED переносит стоимость надежности из WAL на восстановление данных приложением. Выбирайте этот режим только при осознанном контракте полной потери содержимого после crash.
