    9.2. PostgreSQL Backup & Restore Internals¶

    Углубленная лекция магистратуры · PostgreSQL 18 · REL_18_STABLE · блок 9.
    Продолжение: 09.0 — назначение pg_dump, pg_restore, RPO/RTO; 09.1 — эволюция схемы. В блоке 7 уже разобраны WAL, pg_control, checkpoints, fsync, REDO и crash recovery. Здесь используем их как готовые механизмы и исследуем, как формируется, хранится, проверяется и восстанавливается backup.
    Границы: не повторяем алгоритмы WAL/recovery, не разбираем pooling и DDL internals. В центре — логический дамп, физический и инкрементальный backup, организация восстановления, проверка результата и операционные отказы.
    Безопасность: все команды восстановления и порчи копий выполняются только в изолированной среде. Пути /srv/pg-backups, /srv/pg-archive, /srv/pg-restore — учебные. В production обязательны контроль доступа, шифрование, резерв по месту, независимость хранилища и регламент восстановления.
    Точность версий: пользовательские возможности и параметры далее относятся к PostgreSQL 18; внутренние функции и структуры исходников — детали ветки REL_18_STABLE. Условные фрагменты C помечены как псевдокод, их нельзя компилировать без соответствующего окружения.

    0. Инцидент: backup есть, сервиса нет¶

    Представим платежный сервис. В 13:40 ошибочный SQL удалил исторические записи. Через десять минут стало понятно, что необходимо восстановить данные. В хранилище лежит архив, который каждую ночь успешно создается по cron. Мониторинг задачи показывает зеленую отметку. Значит ли это, что в 13:50 мы можем вернуть рабочую БД к 13:39?

    Пока нет. Нужно ответить как минимум на четыре вопроса. Первый: что именно хранится в архиве — SQL-команды, физические страницы кластера или набор измененных блоков? Второй: какому моменту времени соответствует копия и до какого момента сохранился WAL? Третий: существует ли полный набор зависимостей — роли, расширения, tablespaces, инкрементальные цепочки, ключи шифрования? Четвертый: удалось ли хоть раз поднять из копии отдельный PostgreSQL и проверить приложение?

    В этой лекции будем разбирать backup как последовательность проверяемых контрактов:

    Источник данных
    │  выбрать согласованную точку / снимок
    ▼
Снятие копии
    │  передать все необходимые данные
    ▼
Хранение
    │  сохранить целостность + зависимости + историю
    ▼
Верификация
    │  обнаружить повреждения и разрывы цепочки
    ▼
Изолированное восстановление
    │  поднять кластер / загрузить SQL / воспроизвести WAL
    ▼
Проверка приложения
    │  проверить схему, инварианты и готовность
    ▼
Подтвержденные RPO и RTO

    Зеленый exit code команды покрытия всей этой цепочки не гарантирует. Именно эта разница между созданной копией и восстановимым сервисом будет возвращаться в каждом разделе.

    В качестве сквозного примера возьмем БД ledgerdb с таблицами accounts, transfers, ledger_entries. Данные учебные; суммы храним целым количеством копеек. Некоторые операции показаны как команды в shell; используйте отдельный PostgreSQL 18 с ролью и каталогами, подготовленными специально для лабораторного стенда.

    I. Logical dump: как получить согласованный набор SQL и данных¶

    1. pg_dump: согласованный снимок без остановки записей¶

    1.1. С какого состояния должен быть снят логический dump¶

    Представим две таблицы: transfers хранит операцию перевода, ledger_entries — проводки. Транзакция приложения сначала вставляет строки, затем фиксируется. Если выгрузить одну таблицу в 12:00:01, а другую в 12:00:04 без согласованной точки чтения, можно получить неполный бизнес-набор.

    Обычное последовательное чтение нескольких таблиц в разных транзакциях для резервного копирования недостаточно. pg_dump открывает транзакцию с подходящим согласованным снимком MVCC, а затем использует его на протяжении выгрузки. Изменения, зафиксированные после выбранного снимка, в данных дампа не появляются; изменения, завершившиеся до него, рассматриваются по правилам видимости этого снимка.

                T0               T1             T2              T3
            │                │              │               │
Backend A   BEGIN/INSERT ─────────── COMMIT
pg_dump                      SNAPSHOT ────────────────── COPY tables
Backend B                                     INSERT/COMMIT
                                   │
                                   └─ строки B не становятся частью снимка

    Такой дамп логически согласован для данных выбранной БД по MVCC. Он не является глобальным атомарным снимком всех баз кластера, внешних сервисов, файлов на диске и всех последовательностей. Например, значения sequence (last_value, состояние генераторов) имеют собственную семантику и не дают полной транзакционной картины данных, как таблицы. Поэтому восстановление последовательностей важно проверять отдельно.

    Для снятия согласованного снимка PostgreSQL использует уже известные механизмы snapshot/MVCC; мы не повторяем устройство xmin, xmax и ProcArray. Нам важно следствие: логический dump фиксирует версию данных для чтения, но его построение длится реальное время и потребляет ресурсы сервера.

    1.2. Почему pg_dump не обязан блокировать обычные INSERT и UPDATE¶

    При чтении таблиц pg_dump обычно берет ACCESS SHARE, совместимую с нормальными DML-операциями. Конкурентные транзакции могут продолжать работу. Но ACCESS SHARE конфликтует с операциями, которым требуется ACCESS EXCLUSIVE: соответствующий DDL может оказаться в ожидании до завершения выгрузки.

    За согласованность по версиям отвечает MVCC. Блокировки отношений дополнительно защищают от исчезновения или опасного изменения структуры объектов, которые dump должен читать. Здесь работают две независимые защиты: снимок отвечает за какие версии строк видимы, а relation lock — за стабильность объекта для безопасной выгрузки.

    На живой базе масштабный dump может удерживать старый snapshot достаточно долго, чтобы ограничивать очистку старых tuple. Эта стоимость уже понятна из блока 8: затянувшаяся выгрузка может повысить накопление dead tuples и нагрузку на autovacuum, даже если приложение не видит прямых SQL-блокировок.

    1.3. Как данные превращаются в архив¶

    pg_dump — клиентское приложение. Оно подключается к серверу, получает сведения о схемах и объектах через системные каталоги, составляет порядок объектов и извлекает содержимое таблиц. Большой объем данных передается через COPY-подобный поток, а не через миллион отдельных SQL-запросов SELECT ... LIMIT ... OFFSET.

    В plain-формате результат концептуально выглядит так:

    CREATE TABLE public.accounts (
    id bigint NOT NULL,
    balance bigint NOT NULL
);

COPY public.accounts (id, balance) FROM stdin;
1   10000
2   25000
\.

ALTER TABLE ONLY public.accounts
    ADD CONSTRAINT accounts_pkey PRIMARY KEY (id);

    У архивных форматов данные и определения организуются отдельно, а список объектов доступен восстановителю. Это позволяет менять порядок восстановления отдельных частей без редактирования огромного SQL-файла.

    Исходники: src/bin/pg_dump/pg_dump.c, src/bin/pg_dump/pg_backup_archiver.c.

    1.4. Почему --serializable-deferrable — особая настройка¶

    Для задач переноса в аналитическую БД иногда требуется снимок, соответствующий последовательному порядку завершенных транзакций, а не просто MVCC-согласованность. pg_dump --serializable-deferrable может ждать подходящую безопасную точку для serializable-снимка. Это полезно для ряда отчетных сценариев, но способно задержать начало выгрузки.

    Для обычного disaster recovery этот режим обычно не приносит дополнительной пользы; он не превращает логический dump в PITR-резервную копию и не добавляет недостающие WAL. Документация PostgreSQL 18 специально отделяет такой сценарий от стандартного backup.

    1.5. Команды и реальные ограничения¶

    # Обычный архив одной БД: custom format.
pg_dump -h db.example.internal -U backup_reader \
  -d ledgerdb -Fc -f /srv/pg-backups/ledgerdb.dump

# Сценарий проверки DDL в очереди: ограничиваем ожидание
# начальных блокировок, вместо бесконечного зависания.
pg_dump -h db.example.internal -U backup_reader \
  -d ledgerdb -Fd -j 4 \
  --lock-wait-timeout=5s \
  -f /srv/pg-backups/ledgerdb.dir

    Пользователь backup_reader должен иметь достаточные права на читаемые объекты. Роль для полного дампа должна иметь доступ ко всем необходимым данным и метаданным; при недостаточных правах операция завершится ошибкой. Если применяется row-level security, необходимо отдельно понимать, как она влияет на экспорт: штатная конфигурация pg_dump стремится выгрузить всю таблицу и в неподходящих условиях может отказать, вместо того чтобы тихо создать неполный backup.

    Цена: pg_dump тратит CPU на сериализацию/сжатие, читает страницы из БД, нагружает сеть и storage приемника. Он может занимать ограниченное число backend-процессов и удлинять жизнь снимка; это нужно измерять. Для миллионов строк pg_dump -Fc — разумная опция переносимости, но ее пригодность для жесткого RTO еще придется проверять измерениями восстановления.

    1.6. Где ломается простая модель «дамп — копия базы»¶

    Роли и tablespaces относятся к объектам кластера, а pg_dump работает с одной базой. Для глобальных объектов существует pg_dumpall --globals-only. Сам по себе дамп БД не гарантирует наличие таких же ролей на целевом сервере. Расширения тоже требуют внимания: архив может содержать CREATE EXTENSION, но бинарные файлы и совместимая версия расширения должны существовать в целевом окружении.

    Логический дамп удобен для выборочного переноса схемы и данных, миграций между совместимыми версиями и аудируемого восстановления объектов. Он не сохраняет побайтовую физическую организацию heap, FSM, visibility map и т. п.; после восстановления это будет новая физическая база. Изученные ранее алгоритмы WAL не нужно воспроизводить вручную, но их механизм остается частью работы целевого сервера, принимающего SQL.

    Вывод темы 1. Согласованность логического dump основана на MVCC-снимке и защите объектов от опасного изменения. Его стоимость — длительное чтение, удержание снимка, нагрузка на server/client/network и необходимость отдельного восстановления глобальных зависимостей.

    2. Архив как граф зависимостей: Table of Contents (TOC)¶

    2.1. Почему «восстановить SQL в исходном порядке» недостаточно¶

    Пусть у нас таблица accounts, индекс accounts_pkey, внешний ключ из transfers и триггер. Индекс нельзя корректно построить до таблицы, а внешний ключ может потребовать существования обеих таблиц. Попытка параллельно отправить все CREATE и COPY без порядка приводила бы к ошибкам зависимостей.

    pg_dump собирает структуру объектов и сохраняет Table of Contents (TOC). У каждой записи есть идентификатор, тип объекта, имя и зависимости от других записей архива. Внутренние элементы представляют определение объекта, его данные или служебную операцию восстановления. В C-коде архива используется TocEntry; отношения зависимостей позволяют восстановителю планировать безопасный порядок.

    SCHEMA public
     │
     ├── TABLE accounts ──────┬── TABLE DATA accounts
     │                        └── INDEX accounts_pkey
     │
     └── TABLE transfers ─────┬── TABLE DATA transfers
                              └── FK transfers_account_id_fkey
                                      ▲
                                      │
                                 accounts_pkey

    Диаграмма иллюстрирует логическую зависимость и допустимый порядок. Фактический TOC дополнительно включает ownership, constraints, sequences, ACL, comments, extensions, большие объекты и другие виды записей.

    2.2. Три секции архива¶

    Секция Примеры Почему порядок важен
    pre-data схемы, типы, определения таблиц и многие первичные объекты создать структуру, в которую можно загружать данные
    data данные таблиц, large objects, значения sequences заполнить основу для последующих проверок
    post-data индексы, триггеры, ряд constraints и правил выполнять дорогие проверки/построения после основной загрузки

    Некоторые validated CHECK constraints включаются в более раннюю часть схемы; поэтому правило «все ограничения находятся в post-data» неверно. Точное распределение зависит от типа объекта и версии PostgreSQL. Надежнее смотреть фактическое содержимое архива.

    2.3. Инспектируем TOC до восстановления¶

    pg_restore --list /srv/pg-backups/ledgerdb.dump \
  > /srv/pg-backups/ledgerdb.toc

# Человек читает TOC, проверяет список ожидаемых объектов.
less /srv/pg-backups/ledgerdb.toc

# Пример выборочного восстановления объектов из отредактированного TOC:
pg_restore --use-list=/srv/pg-backups/ledgerdb.toc \
  -d ledgerdb_test /srv/pg-backups/ledgerdb.dump

    Список --use-list допускает выбор записей и изменение порядка. Но ручное удаление зависимых объектов может сделать восстановление невозможным или незавершенным. Это средство для осознанного выборочного восстановления, а не гарантия автоматического исправления некорректного TOC.

    2.4. Почему порядок объектов и порядок фиксации данных — разные вещи¶

    TOC описывает, в какой последовательности создавать объекты и загружать данные. MVCC-снимок определяет, какие значения попадут в таблицы. Эти две задачи независимы.

    Можно построить идеальный DAG зависимостей и одновременно выгрузить данные из двух несогласованных снимков. Получится технически восстанавливаемый архив с логической ошибкой. Можно, наоборот, иметь согласованные данные, но не иметь в окружении необходимого расширения — восстановление остановится при создании объектов.

    2.5. Граница применимости зависимостей¶

    pg_dump анализирует зависимости объектов внутри PostgreSQL. Он не знает о файле конфигурации backend-сервиса, API другого микросервиса, внешнем хранилище картинок или секретах в менеджере ключей. Если бизнес-инвариант размазан между PostgreSQL, Kafka и объектным хранилищем, один SQL-архив не обеспечивает согласованного снимка всей распределенной системы.

    Практический вывод: в паспорте backup нужно хранить scope (какие базы и объекты входят), prerequisites (роли, расширения, версии), consistency point (момент снимка) и restore procedure. Файл архива без этого описания может быть полезным, но полноценным планом DR не является.

    Вывод темы 2. TOC позволяет восстанавливать набор объектов как граф зависимостей. Он решает проблему порядка работ, но не добавляет отсутствующие права, бинарные расширения или транзакционную согласованность внешних систем.

    3. Параллельный pg_dump: один снимок, несколько worker-соединений¶

    3.1. Почему независимые процессы с READ COMMITTED здесь не подходят¶

    Мы хотим выгрузить одновременно четыре таблицы. Создаем четыре клиента, каждому говорим выполнить COPY. Если каждый начнет в произвольный момент, они могут получить разные MVCC-снимки и несовместимые состояния двух связанных таблиц.

    Для согласованного параллельного dump нужен синхронизированный снимок (synchronized snapshot). В PostgreSQL 18 лидер организует получение общего снимка, а worker-процессы импортируют согласованную точку чтения. Концептуально это соответствует pg_export_snapshot()/SET TRANSACTION SNAPSHOT, хотя точная последовательность действий в клиенте задается кодом pg_dump.

    Leader connection
  BEGIN; согласованный снимок S
  │
  ├── Worker 1: импорт S → COPY accounts
  ├── Worker 2: импорт S → COPY transfers
  ├── Worker 3: импорт S → COPY ledger_entries
  └── Worker 4: импорт S → COPY reference_data

Все worker читают видимые версии согласно S.

    pg_dump -j 4 использует пять подключений: одно лидирующее плюс четыре worker. Это необходимо включать в connection budget. Параллельный dump не означает, что одна гигантская таблица автоматически разделяется на четыре независимых равных участка: параллелизм достигается главным образом по объектам, и одна доминирующая таблица способна ограничить ускорение.

    3.2. Почему -j для dump требует directory-формат¶

    Одновременно пишущим worker нужен формат, в котором разные потоки могут безопасно создавать отдельные компоненты архива. Для pg_dump формат -Fd поддерживает такой режим; -Fc пригоден для параллельного восстановления, но pg_dump -j в custom-архив напрямую писать не умеет.

    # Параллельный dump: корректно.
pg_dump -d ledgerdb -Fd -j 6 \
  -f /srv/pg-backups/ledgerdb_2026_11_18.dir

# Параллельный dump в -Fc: некорректная комбинация.
# pg_dump -d ledgerdb -Fc -j 6 -f ledgerdb.dump

    В directory-архиве удобно отдельно видеть метаданные и файлы данных объектов. Это еще и упрощает распараллеливание чтения при восстановлении.

    3.3. Неприятная очередь блокировок во время backup¶

    Предположим, лидер уже получил ACCESS SHARE для таблицы. Затем другая сессия запросила ACCESS EXCLUSIVE, но не может получить его немедленно. Новый ACCESS SHARE от worker может встать за ожидающим DDL, хотя совместим с блокировкой лидера. Получается цепочка:

    Leader (держит ACCESS SHARE)
        │
DDL (просит ACCESS EXCLUSIVE)  → WAIT
        │
Worker (просит ACCESS SHARE)  → WAIT за DDL

    Если бы worker бесконечно ждал, dump мог бы сам себя заблокировать через очередь. Поэтому worker запрашивает дополнительный ACCESS SHARE с NOWAIT. Если lock нельзя взять немедленно, pg_dump прекращает работу с ошибкой: в очереди появилась несовместимая операция. Это специальная защита параллельного dump, а не доказательство, что PostgreSQL полностью лишен deadlock.

    3.4. Как диагностировать отсутствие ускорения¶

    Пусть имеется восемь таблиц по 30 GiB и одна таблица на 600 GiB. Всего 840 GiB. Даже с восемью worker время обработки 600-GiB таблицы задаст нижнюю границу: остальные worker могут закончить гораздо раньше и простаивать. А при едином storage досягаемый суммарный throughput ограничен скоростью чтения страниц, сетью и записью архива.

    Условная нижняя оценка:

    T_dump >= max(critical_table_bytes / worker_effective_speed,
              total_bytes / aggregate_end_to_end_bandwidth)

    Если 840 GiB фактически проходят через узкое звено 250 MiB/s, нижняя граница передачи составит около 57 минут без учета сжатия, метаданных, накладных расходов и конкуренции с приложением. Это расчетная оценка, а не измерение.

    В production смотрим одновременно: длительность backup, IOPS/throughput на источнике, трафик сети, скорость записи приемника, загрузку CPU клиента, возраст транзакций и ожидания операций.

    3.5. Практический протокол параллельного dump¶

    1. Зафиксировать список данных и объектов, которые должны входить в backup.
    2. Проверить свободное место и доступность каталога приемника.
    3. Выбрать число worker исходя из ограничений источника и connection budget.
    4. Установить ограничение ожидания начальных блокировок (--lock-wait-timeout).
    5. Сохранить stdout/stderr, exit code, метаданные запуска и хеш архива в отдельном журнале.
    6. Не считать архив готовым для DR до завершения тестового восстановления.

    Вывод темы 3. Синхронизированный snapshot решает согласованность нескольких worker. Остальные ограничения — число подключений, большая одиночная таблица, скорость storage и очередь DDL — остаются физическими и измеримыми.

    II. pg_restore: архив превращается в работающую базу¶

    4. Restore scheduler: зависимости, очереди задач и параллельная загрузка¶

    4.1. Что означает «параллельно восстановить базу»¶

    Создать 16 worker и бросить им SQL в произвольном порядке нельзя. Если данные таблицы еще не загружены, построение ее индекса не должно завершиться раньше загрузки. Если таблица назначения внешнего ключа отсутствует, проверка constraint не пройдет. Поэтому pg_restore выступает планировщиком задач на графе зависимостей.

    Источник — тот же TOC. У задач есть зависимости и состояние готовности. Scheduler выбирает разрешенные к запуску элементы и передает их worker. После выполнения обновляет доступность следующих задач. Внутреннюю организацию можно исследовать в src/bin/pg_dump/pg_backup_archiver.c — особенно в функциях параллельного восстановления; имена конкретных внутренних функций могут меняться в minor-ветке.

                      [создать схему]
                        │
                [создать таблицы]
                 ┌──────┴──────┐
                 ▼             ▼
             COPY A         COPY B
                 │             │
                 ▼             ▼
             INDEX A       INDEX B
                 └──────┬──────┘
                        ▼
                  ADD FOREIGN KEY

    Это учебный граф. Реальный pg_restore учитывает больше типов задач и дополнительные правила зависимостей.

    4.2. Предварительная, параллельная и завершающая фазы¶

    Для понимания Scheduler полезна модель трех крупных этапов:

    1. Pre-data: создать необходимые схемы, типы, таблицы и другие базовые объекты.
    2. Data / post-data, допускающие распараллеливание: загрузка таблиц, построение независимых индексов и некоторых constraints разными worker.
    3. Завершающие действия: ACL, объекты со специальными зависимостями и фиксация результата.

    В коде pg_backup_archiver.c присутствует работа с очередью ожидающих TOC entries и параллельными worker. Важна не точная структура списка, а инвариант: запуск задачи разрешен, если выполнены ее обязательные предшественники.

    4.3. Почему больше -j не всегда быстрее¶

    Пусть одна таблица содержит 500 GiB, а остальные вместе — 20 GiB. После небольшого этапа остальные worker завершат загрузку маленьких таблиц; единственная крупная операция останется на критическом пути. Дальше дополнительные worker могут помочь с индексами, но не обязаны ускорять физическое чтение единственного потока COPY.

    Кроме того, 16 worker одновременно строят индексы: несколько операций сортировки требуют памяти и используют временные файлы. Вместе они способны перегрузить storage и увеличить общее время восстановления. Разделяйте параллелизм, пропускную способность и время критического пути.

    T_restore >= max(длительность критического пути DAG,
                 общий объем I/O / доступная I/O-полоса)

    Формула — нижняя оценка. Дополнительно учитываются CPU на декомпрессию, построение индексов, проверка ограничений, сетевой транспорт и сериализация отдельных шагов.

    4.4. Какие параметры допустимы в PostgreSQL 18¶

    # Восстанавливаем в заранее созданную пустую учебную БД.
createdb ledgerdb_restore

pg_restore --dbname=ledgerdb_restore \
  --jobs=8 \
  --exit-on-error \
  --no-owner --no-acl \
  /srv/pg-backups/ledgerdb.dump

    --jobs для pg_restore работает с custom и directory архивами, и источник должен быть обычным файлом или каталогом, а не потоком stdin. В отличие от pg_dump -j, параллельное восстановление из -Fc допустимо.

    Опции --jobs и --single-transaction несовместимы: отдельные worker используют разные соединения и не могут быть помещены в одну общую клиентскую транзакцию. В PostgreSQL 18 есть промежуточный вариант --transaction-size=N, который группирует объекты в транзакции для непараллельного сценария, снижая накладные расходы без одной гигантской транзакции на все объекты. Нужно проверять конкретный набор опций перед запуском.

    4.5. Ошибки по умолчанию: восстановление «завершилось» с проблемами¶

    Важнейшая эксплуатационная тонкость: по умолчанию pg_restore при некоторых SQL-ошибках может продолжать работу, а в конце сообщить число ошибок. Для автоматизированного DR обычно нужен явный --exit-on-error, логирование stderr и проверка итогового exit code.

    set -o pipefail
pg_restore --dbname=ledgerdb_restore \
  --exit-on-error --verbose \
  /srv/pg-backups/ledgerdb.dump \
  2>&1 | tee /srv/pg-restore/restore.log

    Не следует восстанавливать поверх production-кластера ради проверки backup. Цель — отдельная база/кластер с контролируемыми ролями, изолированной сетью и отдельными данными.

    4.6. Почему ANALYZE после восстановления — часть готовности¶

    Логическое восстановление создает данные и индексы, но планировщику нужна актуальная статистика. После крупного restore обычно необходимо выполнить ANALYZE (или обеспечить ее в рамках регламента) и проверить планы критичных запросов.

    PostgreSQL 18 умеет экспортировать/восстанавливать определенную статистику оптимизатора через новые опции --statistics, но это не отменяет необходимости проверять фактическую пригодность статистики для восстановленного окружения. Сервер мог получить другие настройки, объем данных или распределение; бизнес-приложение нужно проверять запросами.

    ANALYZE public.accounts;
ANALYZE public.transfers;
ANALYZE public.ledger_entries;

    Вывод темы 4. Восстановление ограничено графом зависимостей и узким I/O/CPU-ресурсом. Повышение -j полезно до насыщения этого ресурса. Завершение импорта SQL — промежуточный этап: еще остаются анализ, проверки и переключение трафика.

    III. Physical backup: как переносить работающий кластер¶

    5. pg_basebackup: физическая копия без выключения PostgreSQL¶

    5.1. Почему обычный cp -r $PGDATA работающего сервера опасен¶

    Если просто скопировать файлы data directory во время работы PostgreSQL, разные файлы будут сняты в разные моменты. Часть страниц может относиться к состоянию до очередного checkpoint, другая — после. Копия может включать уже измененные метаданные и не включать соответствующие data pages. PostgreSQL работает с согласованностью, достигаемой в сочетании данных и необходимого WAL; один произвольный набор файлов не образует автоматически корректный backup.

    Физический backup — это копия кластера PostgreSQL как физической структуры: файлы отношений, системные каталоги, файлы состояния и другие необходимые компоненты. Она зависит от совместимости версии PostgreSQL и платформы. Ее нельзя воспринимать как универсальный SQL-архив для загрузки в произвольную версию сервера.

    pg_basebackup координируется с сервером по протоколу репликации и формирует базовую копию, которую можно сделать согласованной при восстановлении с нужным WAL. Физический backup — естественная основа PITR. Мы не повторяем работу REDO; важна граница: backup предоставляет отправную точку, WAL — историю изменений для достижения согласованного состояния и требуемого времени.

    5.2. Какие части нужны одновременно¶

      Работающий PostgreSQL 18
       │
       ├── PGDATA: физические файлы отношений и каталогов
       ├── tablespaces: файлы вне PGDATA, если созданы
       ├── backup metadata / backup_label
       └── WAL: диапазон для согласования и последующего PITR
                         │
                         ▼
                Физическая копия
                         │
                 recovery / replay
                         ▼
             Новый экземпляр PostgreSQL

    Физическая копия охватывает весь кластер, а не одну выбранную базу. При восстановлении попадают все базы, роли и другие глобальные объекты, соответствующие этой копии. При этом внешние зависимости операционной системы и приложения — конфигурации, сертификаты, расширения, секреты, настройки сервиса — требуют отдельного управления.

    Наличие backup_label и метаданных backup помогает серверу определить необходимые границы восстановления. Не следует самостоятельно модифицировать эти файлы в попытке «ускорить запуск»: корректный порядок задан средствами PostgreSQL.

    5.3. Полный backup: команда и ее реальные предпосылки¶

    # Отдельное хранилище, отдельная тестовая среда.
pg_basebackup \
  -h db.example.internal \
  -U repl_backup \
  -D /srv/pg-backups/full_2026_11_18 \
  -Fp -X stream -P --verbose

    -Fp — plain format, файлы разложены как в data directory. -X stream — параллельная потоковая передача необходимого WAL. -P показывает прогресс. Для подключения требуются соответствующая роль с правами репликации, доступ в pg_hba.conf, достаточное число max_wal_senders и место для файлов.

    При -X stream обычно используется второе replication connection для WAL. Таким образом, планировать ресурсы только под одно соединение backup ошибочно. Если архивирующее хранилище или сеть медленные, нужно отдельно контролировать удержание и накопление WAL, состояние slots (если используются) и свободное место.

    5.4. Почему -X stream не заменяет архивирование WAL для PITR¶

    Потоковый WAL, добавленный к base backup, обеспечивает диапазон, необходимый для приведения самой копии к согласованному состоянию. Но для восстановления к произвольному более позднему моменту нужны WAL-сегменты после окончания backup, сохраненные непрерывно до выбранной цели.

    T0               T1                T2                 T3
│ старт backup   │ конец backup    │ ошибка DELETE     │ обнаружение
│<-- WAL для согласованности -->│
                 │<------------ архив WAL ------------>│
                                      ↑
                              целевой PITR

    Если непрерывного архива нет, можно восстановить базовую копию, но возможности достичь времени непосредственно перед ошибкой могут отсутствовать. Утверждение «раз включили -X stream, значит доступен PITR в любой момент» неверно.

    5.5. Формат и компрессия: где сэкономили время, а где добавили работу¶

    Решение Выигрыш Цена / ограничение
    Plain (-Fp) готовая структура файлов, удобство локальной проверки множество файлов, размер и файловые операции
    Tar (-Ft) удобство транспортировки и архивирования требуется распаковка/подготовка, ограничения проверки WAL в pg_verifybackup
    Сжатие меньше сеть и storage при сжимаемых данных CPU на компрессию/декомпрессию, не всегда выгодно
    -X stream WAL передается параллельно с файлами дополнительное соединение и поток передачи
    Удаленный backup-host изоляция копий от сбоя основного сервера сеть и удаленное хранилище могут стать bottleneck

    Нужно измерять end-to-end время получения пригодной копии, а не только скорость чтения файлов. Сжатие на современном CPU может ускорить копирование по узкой сети и замедлить его при быстрой сети, если CPU уже насыщен. Единого оптимального уровня компрессии нет.

    5.6. Проверка наблюдаемого состояния backup¶

    Для операционного контроля полезны представление pg_stat_progress_basebackup на сервере и метрики сети/накопителя на обеих сторонах. Проверяем, что копирование движется, нет провала throughput, растущего отставания WAL и заполнения разделов.

    SELECT pid, phase, backup_total, backup_streamed,
       tablespaces_total, tablespaces_streamed
FROM pg_stat_progress_basebackup;

    Доступность некоторых счетчиков и их единицы уточняются по описанию представления PostgreSQL 18. Сами показатели прогресса не заменяют проверку финального backup manifest и результата пробного восстановления.

    5.7. Условная оценка затрат¶

    Пусть кластер содержит 800 GiB физических данных, а доступная сквозная скорость копирования 200 MiB/s. Нижняя оценка передачи:

    T_copy ≈ 800 GiB × 1024 MiB/GiB / 200 MiB/s
       ≈ 4096 s ≈ 68.3 min

    Но в эту оценку не вошли контрольные операции, дополнительный WAL, сжатие, файловые метаданные, задержки сети и throttling. Если хотим выполнить backup за 30 минут, нужная сквозная скорость порядка 800 × 1024 / 1800 ≈ 455 MiB/s. Изменение только параметра числа worker не создаст эту полосу из ничего.

    Вывод темы 5. Физический backup решает задачу копирования целого кластера, а не отдельных SQL-объектов. Его корректность зависит от непрерывности необходимого WAL, согласованности файлового набора и совместимости окружения; стоимость определяется физическим объемом и пропускной способностью пути копирования.

    6. Инкрементальный backup PostgreSQL 18: WAL summaries и измененные блоки¶

    6.1. Почему полный backup каждый день может оказаться слишком дорогим¶

    Сервис хранит 4 TiB данных. За сутки изменяется небольшая доля страниц, но полный backup заново читает и передает большую часть физических файлов. Если каждый день передавать 4 TiB по одной и той же сети, задача может не успевать завершиться до следующего окна обслуживания.

    Инкрементальный backup в PostgreSQL, доступный начиная с PostgreSQL 17, позволяет для ряда файлов отношений сохранять измененные блоки относительно опорной копии. В PostgreSQL 18 механизм использует предварительно подготовленные сводки WAL. Это сводки измененных блоков, а не полная архивация всех транзакционных записей.

    6.2. Как узнать, какие блоки изменились¶

    Пользовательская команда UPDATE сообщает логическую операцию, но для инкрементального физического backup нам нужен ответ вида «в relation R изменились блоки 14, 27 и 81». Информация выводится из WAL, поскольку там отражаются изменения страниц. Служебный процесс WAL summarizer обрабатывает WAL и формирует summary files.

    Ключевые параметры PostgreSQL 18:

    summarize_wal = on
wal_summary_keep_time = '14d'

    Значение 14d — пример настройки, выбирать его следует по максимальному промежутку между опорной и следующей инкрементальной копией с запасом. По умолчанию summarize_wal выключен. Summary files хранятся в pg_wal/summaries; срок хранения и непрерывность покрытия LSN критичны.

    WAL records ────────► WAL summarizer
                           │
                           ▼
                    pg_wal/summaries
                           │
                           ▼
              changed blocks per relation
                           │
                           ▼
            incremental pg_basebackup

    Не смешиваем два понятия: summary определяет какие блоки надо включить в инкрементальную копию; архив WAL нужен для восстановления состояния данных и PITR. Удаление архивного WAL и сохранение summaries не делают PITR возможным.

    6.3. Почему используется manifest предыдущей копии¶

    Инкрементальная копия требует опорного состояния. pg_basebackup --incremental принимает backup_manifest предыдущей физической копии. Manifest содержит сведения, включая границы backup и идентификатор кластера, необходимые для определения исходной точки сравнения.

    # Полная копия уже создана ранее:
# /srv/pg-backups/full/base ...
# /srv/pg-backups/full/backup_manifest

pg_basebackup -h db.example.internal -U repl_backup \
  -D /srv/pg-backups/inc_1 \
  -Fp -X stream \
  --incremental=/srv/pg-backups/full/backup_manifest \
  -P

    Второй incremental может ссылаться на manifest первого incremental (если цепочка корректна и поддерживается необходимое WAL summary coverage):

    pg_basebackup -h db.example.internal -U repl_backup \
  -D /srv/pg-backups/inc_2 \
  -Fp -X stream \
  --incremental=/srv/pg-backups/inc_1/backup_manifest \
  -P

    Если серверу не хватает summary files для промежутка между необходимыми LSN, инкрементальный backup завершается ошибкой. Нельзя заменить отсутствующий диапазон файлами summary «от соседнего дня»: требуется непрерывное корректное покрытие.

    6.4. Что означает «измененный блок», и почему экономия не равна доле измененных строк¶

    PostgreSQL работает со страницами. Если в одной странице 8 КБ изменилась единственная узкая tuple, инкрементальная физическая копия может включить весь соответствующий блок, а не только измененные байты строки. Если в течение суток весь объем 500 GiB таблицы был последовательно затронут небольшими UPDATE, инкрементальная копия окажется большой даже при маленьких логических изменениях.

    Есть и другая тонкость: не все файлы инкрементальны одинаково. Для non-relation files PostgreSQL включает содержимое полностью. Поэтому модель «раз изменилось 2% строк, инкрементальный архив обязательно равен 2% полной копии» не выполняется.

    Пример оценки (условный):

    Вид изменений Логически изменено Физически затронуто Последствие
    Изменили одну строку в 100 страницах 100 строк до 100 страниц backup включает страницы
    Обновили по одной строке на каждой из 10 млн страниц 10 млн строк ~76.3 GiB значительно больше объема новых значений
    Переписали relation или массово загрузили данные много большая доля файла выигрыш incremental может исчезнуть

    В третьем столбце второй строки использовано 10 000 000 × 8192 / 2^30 ≈ 76.3 GiB. Это оценка объема блоков без дополнительного формата, сжатия и других файлов.

    6.5. Почему incremental нельзя просто положить вместо PGDATA¶

    Инкрементальная копия не содержит все необходимые страницы исходного состояния. Она содержит новые/измененные блоки и метаданные, которые нужно соединить с предыдущими backup. Для этого используется pg_combinebackup.

    Full F0  ──────────┐
                   ├────► pg_combinebackup ────► Synthetic full
Inc I1  ──────────┤                              usable for restore
                   │
Inc I2  ──────────┘

    pg_combinebackup \
  /srv/pg-backups/full \
  /srv/pg-backups/inc_1 \
  /srv/pg-backups/inc_2 \
  -o /srv/pg-restore/synthetic_full

    Аргументы подаются от самой старой полной копии к последнему incremental. Программа проверяет структуру зависимостей и создает новый полный файловый набор. Она не отслеживает всю политику хранения вместо администратора. Если потерять промежуточный incremental, цепочка станет непригодной.

    6.6. Важное различие: размер хранения и скорость восстановления¶

    Инкрементальный backup может сократить ежедневную передачу и хранение, но восстановление потребует дополнительных действий: собрать synthetic full, проверить, разместить в PGDATA, обеспечить WAL и запустить PostgreSQL. Для жесткого RTO критичен не только размер ежедневного incremental, но и длина цепочки.

    Пример: полный набор 1 TiB и три incremental по 80, 120, 70 GiB. Для формирования synthetic full нужно прочитать значительную часть данных цепочки, сопоставить блоки и записать итоговый полный набор. Суммарные физические операции могут быть существенно больше объема последнего incremental. Поэтому «получили incremental за пять минут» ничего не говорит о времени полного восстановления.

    6.7. Политика цепочек¶

    Нельзя удалять reference manifest, базовую копию или промежуточный incremental, если от них еще зависит необходимая цепочка. Нельзя выставлять wal_summary_keep_time меньше интервала, при котором следующие incremental должны иметь возможность опереться на опорную копию. Необходимо отдельно удерживать архив WAL для выбранной политики PITR.

    Ресурс Кто использует Если утрачен
    Full backup F0 pg_combinebackup / restore цепочка F0→... неполна
    Incremental I1 дальнейшие incremental / combine нельзя собрать зависимые состояния
    Manifest reference сервер при следующем incremental нет корректной точки сравнения
    WAL summaries сервер при формировании incremental backup может отказать
    WAL archive PITR и recovery нельзя воспроизвести нужный временной диапазон

    Вывод темы 6. Инкрементальность — это алгоритм выбора физических страниц и управление цепочкой зависимостей. Ее цена переносится из ежедневного копирования в хранение истории, проверку цепочек и скорость формирования синтетической полной копии.

    IV. PITR: восстановление к выбранной точке времени¶

    7. PITR operations: что должно быть подготовлено до аварии¶

    7.1. Отличие PITR от восстановления ночного dump¶

    Если ошибка произошла в 13:40, ночной логический dump возвращает данные на момент ночного снимка. Чтобы восстановить состояние непосредственно перед ошибкой, нужен физический base backup плюс непрерывный доступный архив WAL до нужной цели. После восстановления base backup PostgreSQL применяет изменения в порядке WAL до установленной точки остановки.

    00:00          01:00                  13:39:59   13:40
  │ старт F0     │ конец F0                │        │
  ├──────────────┤                        │        │
  │  base backup │                        │   BAD DELETE
  └──────────────┴──── WAL archive ───────┤────────┤
                                          ▲
                                 recovery_target_time

    PITR не означает «SQL undo по журналу». Это воспроизведение WAL на копии кластера до согласованной точки. В лекциях 07.1 и 07.3 мы уже разобрали replay и выбор redo LSN, поэтому здесь только эксплуатационный протокол.

    7.2. Что требуется от WAL archiving¶

    Для непрерывного архивирования на источнике в общем случае нужны настройки вида:

    wal_level = replica
archive_mode = on
archive_command = '/usr/local/bin/pg-safe-archive "%p" "%f"'

    pg-safe-archive здесь условное имя административного скрипта, который должен надежно сохранять сегменты без перезаписи несовпадающих файлов, возвращать успешный код только после гарантированного сохранения и корректно обрабатывать повторные вызовы. В лекции мы не делаем вид, что простое cp в произвольную директорию решает всю задачу долговечности архива. Для production нужна проверенная реализация архивации или управляемое решение.

    archive_mode=on требует соответствующей конфигурации и перезапуска сервера при изменении этого параметра. archive_command может завершаться ошибкой, после чего PostgreSQL повторяет попытку; при длительном отказе архивного storage могут накапливаться WAL-сегменты в pg_wal. Следовательно, исправность архивирования — часть мониторинга доступности самого primary.

    7.3. Как отделить копию для DR от исходного сервера¶

    Нельзя разворачивать восстановление PITR прямо в data directory текущего primary. Процедура должна использовать отдельную машину/виртуальную среду и отдельный путь хранения. На этом экземпляре необходимо предотвратить случайную отправку клиентского трафика, запись в чужие внешние системы и пересечение сетевых адресов с production.

    Операционный порядок:

    1. Выбрать валидную полную физическую копию, лежащую до требуемого момента. При incremental — сначала собрать synthetic full.
    2. Проверить базовый набор и нужные файлы WAL по цепочке.
    3. Развернуть копию в пустой data directory изолированного PostgreSQL подходящей версии.
    4. Настроить чтение архива WAL через restore_command.
    5. Создать recovery.signal и задать цель остановки.
    6. Запустить сервер, наблюдать recovery и остановиться на цели.
    7. Проверить бизнес-данные, решить вопрос с timeline и только затем возвращать сервисный трафик по отдельному плану.

    7.4. Конфигурация recovery в PostgreSQL 18¶

    В конфигурации изолированного восстанавливаемого экземпляра:

    restore_command = 'cp /srv/pg-archive/%f "%p"'
recovery_target_time = '2026-11-18 13:39:59+03'
recovery_target_inclusive = on
recovery_target_action = 'pause'

    Файл-сигнал:

    # Только в PGDATA заранее развернутой копии, НЕ у primary.
touch /srv/pg-restore/pgdata/recovery.signal

    Значение времени — иллюстрация. В реальном инциденте необходимо установить точный момент плохого изменения и проверить, какие транзакции были уже зафиксированы к целевой точке. Не следует выбирать время «на глаз» и автоматически переключать боевой трафик без валидации.

    recovery_target_inclusive определяет включение транзакции, находящейся точно на границе восстановления. recovery_target_action = pause позволяет остановиться и исследовать состояние на цели, прежде чем окончательно завершать recovery. Для завершающего перехода к самостоятельному экземпляру потребуется осознанное возобновление/промоция и проверка состояния; процедура зависит от выбранной операции восстановления.

    7.5. Когда лучше цель по LSN или именованной точке¶

    Если известен четкий marker перед опасной операцией, можно создать restore point до ее выполнения:

    SELECT pg_create_restore_point('before_critical_change');

    При восстановлении указываем recovery_target_name. Также возможно восстановление к recovery_target_lsn, но этот вариант требует знания достоверной позиции. LSN и имя точки — альтернативы временной цели; одновременно выбирать несколько видов recovery_target_* нельзя.

    Оговорка: восстановление к именованной точке не гарантирует, что другие конкурентные транзакции после marker отсутствовали. В распределенном приложении необходимо оценить допустимость потерянных операций и провести бизнес-сверку.

    7.6. Почему timeline важен¶

    После выхода из recovery и начала самостоятельной истории записи сервер создает новую ветвь WAL timeline. Это позволяет отличать историю «до выбора точки восстановления» от новой истории, которая идет после восстановления.

    Timeline 1: ──── F0 ──────────────●─────X bad commit ──────►
                                  │
                                  └── Timeline 2: новые записи после PITR ──►

    Если при следующем восстановлении администратор выберет неправильную timeline, он может пойти по другой исторической ветви. План DR должен хранить идентификаторы timeline, необходимые history files и явно описывать выбор цели.

    7.7. Тонкость RPO: «архив включен» не значит «каждый COMMIT уже в архиве»¶

    Файлы WAL обычно архивируются по сегментам. После последнего полностью архивированного сегмента на primary могут существовать зафиксированные транзакции, чьи записи еще не дошли до независимого архива. При потере primary без доступа к его локальному WAL они будут потеряны.

    В худшем случае фактический RPO зависит от скорости поступления WAL, частоты переключения сегментов, задержки успешной архивации и устойчивости хранилища. archive_timeout может ограничивать время до переключения мало заполненного сегмента, но создает дополнительные расходы хранения и не делает само хранилище магически надежным.

    Вывод темы 7. PITR требует заранее подготовленной физической копии, непрерывной истории WAL и точного протокола выбора цели. Он может вернуть сервис к состоянию до ошибки, но скорость и полнота восстановления определяются измеренными характеристиками инфраструктуры и сохранившимися файлами.

    V. Verification: как отличить целую копию от пригодной к восстановлению¶

    8. pg_verifybackup: от checksum файла до проверки требуемого WAL¶

    8.1. Что именно нужно проверить¶

    За время хранения backup может пострадать из-за ошибки передачи, повреждения блока, ручного удаления файла, сбоя носителя или неправильной сборки каталога. Если файл называется base.tar.gz и успешно распаковывается, это доказывает лишь часть свойств архива. Необходимо отдельно проверить перечень файлов, их содержимое и необходимые границы WAL.

    В PostgreSQL 18 pg_basebackup обычно создает backup_manifest. Он содержит список файлов (без включенных WAL-файлов), размеры, необязательные контрольные суммы, сведения о WAL ranges и контрольную сумму самого manifest. Проверка данных выполняется отдельной утилитой pg_verifybackup.

    backup_manifest
   │
   ├── перечень файлов и размеры ────► существуют ли файлы?
   ├── checksums файлов ─────────────► совпадает ли содержимое?
   ├── system identifier ───────────► тот ли физический кластер?
   └── необходимый WAL range ───────► можно ли разобрать WAL?

    Разница принципиальна: checksum на отдельном файле проверяет совпадение байтов с manifest, но не доказывает, что восстановленный PostgreSQL удовлетворяет бизнес-инвариантам. Даже если все файлы целы, может не быть нужной версии расширения или необходимого ключа шифрования.

    8.2. Какие стадии выполняет pg_verifybackup¶

    Официальная документация PostgreSQL 18 описывает последовательность:

    1. Прочитать manifest, проверить его формат, собственную контрольную сумму и согласованность идентификатора системы с pg_control.
    2. Сопоставить ожидаемые файлы с фактическими: отсутствие, лишние файлы, размеры (предусмотрены исключения).
    3. По сохраненным контрольным суммам пересчитать содержимое файлов и найти несовпадения.
    4. Проверить наличие и возможность разбора необходимого WAL, используя pg_waldump.

    Для WAL-проверки есть ограничение: в текущей реализации она поддерживается для plain-format backup. Для tar backup рекомендуется --no-parse-wal (-n), иначе нельзя трактовать отсутствие WAL-проверки как подтверждение полноты.

    8.3. Команды для plain backup¶

    # Проверка отдельно сохраненного plain backup.
pg_verifybackup --progress \
  /srv/pg-backups/full_2026_11_18

# Если WAL хранится в отдельном каталоге:
pg_verifybackup \
  --wal-directory=/srv/pg-archive \
  /srv/pg-backups/full_2026_11_18

    Если pg_verifybackup завершился успешно, это доказывает прохождение предусмотренных утилитой статических проверок. Оно не гарантирует, что сервер запустится, что все расширения будут совместимы, что целевое состояние не содержит логической ошибки или что время восстановления уложится в RTO.

    8.4. Проверка tar backup¶

    pg_verifybackup \
  --format=tar \
  --no-parse-wal \
  /srv/pg-backups/full_tar

    Для физического backup в tar-формате pg_verifybackup может проверять файлы согласно manifest, но эта команда намеренно пропускает разбор WAL. Полноту истории WAL нужно проверять отдельной процедурой и пробным восстановлением.

    Не путать две опции:

    • --no-parse-wal пропускает проверку WAL;
    • --skip-checksums пропускает пересчет файловых контрольных сумм, сохраняя часть проверки списка файлов и размеров.

    Если мониторинг сообщает «backup verification successful», обязательно нужно понимать, какие проверки были отключены.

    8.5. Manifest checksums, data checksums и WAL CRC — три разных слоя¶

    Механизм Что защищает / обнаруживает Чего не гарантирует
    backup_manifest checksums совпадение файлов копии с ожидаемыми байтами логическую корректность данных и запуск БД
    Data checksums страниц повреждение физических data pages при чтении восстановление испорченной страницы без корректного источника
    WAL CRC повреждения в журнале изменений наличие всех нужных WAL-сегментов и бизнес-корректность
    Пробный restore возможность собрать и запустить конкретную копию гарантированно такой же RTO при будущей аварии
    Business validation ключевые инварианты данных отсутствие всех возможных скрытых ошибок

    Data checksums и WAL CRC подробно были в лекции 07.2. Здесь достаточно понимать, что контрольная сумма копии, контрольная сумма физической страницы и восстановимость бизнес-состояния проверяют разные свойства.

    8.6. Проверка инкрементальной цепочки¶

    К инкрементальному backup нельзя относиться как к самостоятельному полному PGDATA. Сначала требуется pg_combinebackup с полным набором зависимостей, затем проверка полученной полной копии и пробный запуск:

    pg_combinebackup \
  /srv/pg-backups/full \
  /srv/pg-backups/inc_1 \
  /srv/pg-backups/inc_2 \
  -o /srv/pg-restore/synthetic_full

pg_verifybackup /srv/pg-restore/synthetic_full

    Если артефакты копий хранятся в объектном storage, важно также проверить их доступность при реальной аварии, права на получение объектов и возможность загрузить достаточную полосу данных. Успешный manifest check не поможет, если учетные данные к storage потеряны вместе с primary.

    8.7. Проверяем копию без доверия к имени и времени файла¶

    Для каждого успешного backup желательно сохранять независимый паспорт:

    backup_id:      pg18-full-20261118-0100
cluster_id:     <system identifier>
postgresql:     18.x
backup_kind:    physical full / physical incremental / logical
started_at:     <UTC timestamp>
finished_at:    <UTC timestamp>
base_ref:       <reference backup ID or none>
wal_range:      <LSN range / archive availability>
manifest_hash:  <digest>
verify_status:  passed / failed / skipped
restore_drill:   date of last successful test

    Это пример структуры метаданных, а не формат, автоматически создаваемый PostgreSQL. Поля <...> заполняются фактическими данными. Полезно хранить паспорт отдельно от самого носителя копий, иначе их можно потерять одновременно.

    8.8. Отказ «контрольные суммы совпали, но данные все равно нельзя использовать»¶

    Допустим, backup сделан уже после ошибочного массового UPDATE. Все файлы целые; manifest в порядке. Проверка физической целостности закономерно успешна. Но приложение читает неверные балансы.

    Это не ошибка pg_verifybackup. Он проверил то свойство, которое ему поручено: байты и структуру копии. Восстановление правильного бизнес-состояния требует подходящей исторической точки PITR или другого логического источника. Физическая целостность и бизнес-корректность независимы.

    Вывод темы 8. Верификация backup — многоступенчатая процедура. pg_verifybackup сокращает вероятность пропустить дефекты файлов и WAL, но подтверждение пригодности к работе получается только после восстановления и прикладных проверок.

    9. Restore drills: измеряем реальный RTO вместо его обещания¶

    9.1. Почему нужно регулярно восстанавливать копию¶

    Пусть команда пишет в документе «RTO 30 минут». Затем выясняется, что архив размером 2 TiB хранится в удаленном объектном хранилище, один канал дает 150 MiB/s, а восстановление индексов занимает еще два часа.

    Число «30 минут» — пожелание, не технический результат. Реальный RTO должен быть проверен в условиях, приближенных к отказу. Для этого нужны регулярные restore drills — пробные восстановления с контролем результата.

    9.2. Жизненный цикл restore drill¶

    1. Выбрать случайный / заданный backup из retention window
    │
    ▼
2. Получить все зависимости и WAL из независимого хранилища
    │
    ▼
3. Восстановить в изолированную среду
    │
    ▼
4. Проверить запуск PostgreSQL и техническую целостность
    │
    ▼
5. Проверить критичные бизнес-инварианты
    │
    ▼
6. Измерить время, потерю данных, записать результат и причину отклонений

    Важно выбирать для тестов разные копии, в том числе из середины периода хранения и из длинных incremental chains. Если всегда проверять только вчерашнюю полную копию, ошибки удаления старых зависимостей обнаружатся слишком поздно.

    9.3. Раскладываем RTO на измеримые этапы¶

    Для физического восстановления:

    T_RTO = T_detect + T_decide + T_fetch + T_reconstruct
      + T_recovery + T_validate + T_switch

    Где:

    • T_detect — время обнаружения и подтверждения инцидента;
    • T_decide — время выбора точки и утверждения плана;
    • T_fetch — загрузка файлов из архивного storage;
    • T_reconstruct — pg_combinebackup или распаковка;
    • T_recovery — запуск PostgreSQL и достижение целевой точки;
    • T_validate — техническая и бизнес-проверка;
    • T_switch — безопасное переключение клиентского трафика.

    Для логического восстановления вместо T_reconstruct/T_recovery значительную часть времени занимают DDL, COPY, индексы, constraints, ANALYZE, подключение приложения. Мы не предполагаем, что эти этапы полностью последовательны: в реальной системе часть действий может перекрываться, но критический путь нужно измерять по времени событий.

    9.4. Расчет RTO на 800 GiB¶

    Пусть зафиксированы следующие условные значения:

    Этап Длительность
    Обнаружение и решение 8 мин
    Получение 800 GiB по эффективным 200 MiB/s 68.3 мин
    Подготовка и запуск 12 мин
    WAL replay до выбранной точки 19 мин
    SQL / бизнес-проверки 14 мин
    Переключение сервиса 7 мин
    Итого 128.3 мин

    Обещание RTO 30 минут при такой конфигурации не выполняется. Нужно изменить архитектуру хранения, расположение горячих копий, полосу данных, длину цепочки либо сам целевой показатель. Увеличение параметра параллелизма в pg_restore никак не ускорит удаленное получение полного физического backup, если именно оно задает нижнюю границу.

    9.5. Бизнес-инварианты для учебного ledger¶

    После восстановления недостаточно выполнить SELECT 1. Нужно проверить, что данные непротиворечивы и доступны приложению.

    -- Проверяем наличие ключевых таблиц.
SELECT to_regclass('public.accounts') AS accounts,
       to_regclass('public.transfers') AS transfers,
       to_regclass('public.ledger_entries') AS ledger_entries;

-- Проверяем отсутствие дублей, если бизнес-ключ должен быть уникален.
SELECT transfer_id, count(*)
FROM ledger_entries
GROUP BY transfer_id
HAVING count(*) > 2;

-- Двусторонняя проводка должна иметь нулевую сумму.
-- Предполагается signed_amount_cents со знаком.
SELECT transfer_id, sum(signed_amount_cents)
FROM ledger_entries
GROUP BY transfer_id
HAVING sum(signed_amount_cents) <> 0;

    Два SQL-запроса иллюстрируют пример инвариантов. Фактическая схема может включать комиссии, отмены, несколько проводок и другие правила; тогда простая проверка количества проводок неадекватна. Нельзя переносить эти условия в production без согласования с предметной моделью.

    9.6. Проверяем не только SQL, но и работоспособность приложения¶

    После восстановления нужно проверить: роли и секреты доступа; версии расширений; критические функции; настройки приложения; обработку запросов чтения и записи на тестовых данных; индексы и производительность; задания, которые не должны стартовать на резервном контуре; отсутствие отправки событий во внешние production-системы.

    Особенно опасно поднимать копию банковской или платежной БД в контуре, где фоновые обработчики автоматически начинают переотправлять события, выполнять платежи или отправлять уведомления. Restore drill должен проводиться с сетевой и прикладной изоляцией.

    9.7. RPO по факту, а не по расписанию backup¶

    Пусть была полная копия в 01:00, WAL архивируется непрерывно, но последний доступный сегмент завершился в 13:36, а ошибка случилась в 13:40. Если primary потерян и неархивированный WAL недоступен, максимальная восстановимая точка ограничена последним доступным WAL. Величина фактической потери данных зависит от исторического диапазона транзакций между этой точкой и отказом.

    В отчет после drill полезно включать:

    RPO_target: 5 min
RPO_observed: 4 min 20 sec
RTO_target: 60 min
RTO_observed: 78 min
Main_bottleneck: object-storage download
Missing_dependencies: none
Data_invariants: passed
Decision: RTO not met; mitigation required

    Это модель отчета с условными числами. При фактическом тестировании нужно фиксировать источник времени, таймлайн событий, точку восстановления и измеренные задержки.

    9.8. Когда копию можно считать действительно проверенной¶

    Минимальный критерий: нужные файлы доступны; архив распаковывается/собирается; сервер или база запускаются; команды проверки не находят нарушений; ключевые бизнес-инварианты выполнены; приложение может обслуживать тестовый сценарий; получены измерения RPO/RTO.

    Для критичного сервиса полезно дополнить периодическими восстановлением старой копии, испытанием потери одного backup storage, тестированием восстановления на новой инфраструктуре и проверкой доступности учетных данных и ключей дешифрования. Эти проверки выходят за рамки команд pg_dump и pg_basebackup, но прямо определяют ценность всей системы резервирования.

    Вывод темы 9. RTO — результат измерения полного критического пути восстановления. RPO — результат анализа реально доступной истории данных. Оба показателя требуют операционных испытаний, а не только корректных конфигурационных параметров.

    10. Failure scenarios: почему архивы превращаются в бесполезные файлы¶

    10.1. Проблема первая: потеря части WAL¶

    Есть полный backup и все файлы данных, но между ними и целевой точкой отсутствует один обязательный WAL-сегмент. Recovery не может корректно перейти через разрыв в истории. Даже если сегменты после разрыва имеются, этого недостаточно.

    Диагностика: проверка backup range, доступности WAL-архива, журналов восстановления, необходимых timeline history files и сохраненных идентификаторов цепочки. Меры: мониторинг archive failures и WAL lag, защита архива от удаления, независимое хранение, тестовые PITR.

    10.2. Проблема вторая: удаленный промежуточный incremental¶

    Полная копия F0 и последние I2/I3 лежат на месте. Но I1 удален по ошибочному retention-правилу. pg_combinebackup не может восстановить отсутствующие блоки, когда они должны были приходить из I1.

    Здесь проявляется системная ошибка: retention управлялся отдельными файлами по возрасту, а не графом зависимостей. Требуется хранить цепочки как единый набор, знать родительские backup ID и регулярно собирать synthetic full.

    10.3. Проблема третья: snapshot согласован, но потеряны внешние зависимости¶

    Логический архив ledgerdb.dump выгружен успешно. На целевой машине нет роли ledger_owner и требуемого расширения. Восстановление схемы завершается ошибками.

    Решение: заранее фиксировать pg_dumpall --globals-only, состав extensions, версии бинарных библиотек, tablespaces, конфигурацию locale/encoding и права; иметь репетируемый bootstrap целевого кластера. Не предполагать, что один файл дампа содержит окружение сервера.

    10.4. Проблема четвертая: закончился диск во время restore¶

    Backup занимает 600 GiB, но восстановление создает индексы и временные файлы, а filesystem имеет лишь 650 GiB свободного места. Скорость падает, затем операция завершается ошибкой.

    В расчетах учитываем отдельно: место под извлекаемый архив, распакованный PGDATA, новые индексы, временные сортировки, WAL, журналы и запас. Компрессия исходного архива не равна физическому размеру восстановленной БД.

    10.5. Проблема пятая: перепутали timeline или время¶

    Восстановление должно было остановиться непосредственно до опасного изменения, но оператор указал время без корректного часового пояса или выбрал другую ветвь WAL. Сервер успешно поднялся — с неправильными данными.

    Меры: хранить timestamps в UTC, явно указывать timezone в настройках PITR, фиксировать restore point/LSN, проверять timeline и выполнять предметную валидацию до переключения трафика.

    10.6. Проблема шестая: backup скомпрометирован вместе с primary¶

    Архивы лежат на доступном с primary томе под теми же привилегиями. Вредоносное ПО либо ошибочная автоматизация удаляют и рабочую БД, и все копии.

    Это проблема отказоустойчивости хранения: нужен отдельный security boundary, ограничение прав удаления, независимый retention/immutability где применимо, защита ключей и регулярные проверки, что резервное хранилище действительно можно использовать автономно.

    10.7. Проблема седьмая: большие логические дампы восстанавливаются слишком медленно¶

    Логический dump на 900 GiB получен за несколько часов. Во время DR операции загрузки данных и построения индексов занимают существенно больше выделенного времени. Наличие файла подтверждает только возможность попытаться выполнить restore, но не способность выполнить RTO.

    Диагностика: измерять скорость COPY, длительность построения крупных индексов, фазу post-data, CPU/I/O и ошибки. Инженерное решение: если логический restore не укладывается в бизнес-RTO, выбирать или добавлять подходящий физический backup-процесс, горячую копию и WAL-политику. Формат выбирается по задаче восстановления, а не по предпочтению одной команды.

    10.8. Проблема восьмая: backup успешно выполнен после уже произошедшей порчи данных¶

    Вчера система сохранила некорректные бизнес-значения. Сегодня backup создается и проходит проверки. Восстановление сегодняшней копии вернет те же некорректные значения.

    Поэтому retention должен позволять восстановиться к моменту до обнаруженной ошибки, а не только сохранять последнюю технически целую копию. Для длинных окон обнаружения ошибок потребуется длинная историческая глубина — с соответствующей ценой хранения и управления WAL.

    10.10. Диагностический порядок при аварии¶

    Не следует сразу запускать восстановление поверх единственной сохранившейся копии. Сперва сохраняем исходные артефакты, выбираем точку восстановления и фиксируем зависимые ресурсы. Затем разворачиваем изолированный экземпляр и оцениваем достижимость нужного RPO/RTO. Если одновременно имеется логический архив и физический backup, выбираем по характеру потери данных и требуемой granularity:

    • Удалена одна таблица: возможен выборочный логический restore в отдельную среду с последующим аккуратным переносом данных; физический PITR поднимается отдельно, если нужно извлечь состояние таблицы на исторический момент.
    • Потерян весь сервер: основной кандидат — проверенная физическая копия с нужным WAL; логический архив может быть полезен, но RTO надо подтвердить.
    • Логическая порча в прошлом: нужна историческая копия или PITR до момента порчи и дальнейшая предметная сверка.
    • Компрометация хранилища: требуются изолированные, доверенные копии и проверка их происхождения.

    Вывод темы 10. Восстановимость определяется самой слабой зависимостью цепочки: файлами данных, манифестом, WAL, учетными данными, платформой, пропускной способностью, точностью выбранной цели и проверкой приложения.

    VI. Сквозной производственный разбор: что делать в 13:50¶

    11. Сравниваем три стратегии восстановления одного инцидента¶

    В 13:40 ошибочная операция затронула ledger_entries. Есть следующие источники:

    • ночной pg_dump -Fc от 01:00;
    • полный физический backup от 00:00;
    • два incremental от предыдущих дней, не нужных для сегодняшнего сценария;
    • непрерывный WAL-архив с подтвержденным последним доступным сегментом около 13:39;
    • требование бизнеса: RPO до 5 минут, RTO до 90 минут.

    Вариант A: восстановить ночной pg_dump в отдельную БД. Получим состояние на момент снимка 01:00. Для точного возврата 13:39 потребуется дополнительный надежный источник изменений; одного дампа недостаточно. Этот вариант может быть полезен для выборочного возвращения справочника, который не изменялся в течение дня, но опасен для финансовых данных с активным трафиком.

    Вариант B: поднять физическую копию и использовать PITR до 13:39. Требуется получить базовую копию, все WAL до цели, запустить recovery и выполнить проверку бизнес-инвариантов. Если архив реально непрерывен до нужной границы, этот вариант потенциально обеспечивает нужный RPO. Достижимость RTO зависит от фактического времени доставки и восстановления.

    Вариант C: восстановить весь кластер непосредственно в production. До подтверждения правильной точки и инвариантов это рискованно. Ошибка при выборе цели может уничтожить доступный путь назад, а восстановленная инфраструктура может повторно запустить фоновые операции. Выбираем изолированный контур и сохраняем первичные артефакты.

    11.1. Дерево решений¶

    Что потеряно?
  │
  ├─ Отдельные объекты / строки
  │     ├─ есть подходящий SQL-дамп? → restore в отдельную БД
  │     └─ нужен исторический момент? → PITR отдельного кластера → извлечение
  │
  └─ Весь кластер / неизвестная порча
        ├─ есть full/synthetic backup + непрерывный WAL?
        │       └─ да → PITR в изолированной среде
        └─ нет → восстановление из доступной копии с явной оценкой потери

    11.2. Как посчитать ожидаемое время¶

    Допустим, объем восстановленного PGDATA 700 GiB, с архивного storage реально получаем 350 MiB/s. Нижняя граница только загрузки: 700 × 1024 / 350 ≈ 2048 секунд или 34.1 минуты. Допустим, combine/распаковка занимает еще 10 минут, recovery — 18 минут, прикладные проверки — 12 минут, переключение — 8 минут. Без учета времени обнаружения получается около 82 минут.

    Это близко к RTO 90 минут. Следовательно, запас минимален: сбой канала, медленный WAL replay или ручная ошибка нарушат цель. Нужно разрабатывать операционный запас и проверять p95 времени восстановления на нескольких тестах, а не принимать один удачный прогон за гарантированную скорость.

    11.3. Как сохранить возможность повторной попытки¶

    Полный backup, incremental chains и WAL архив считаем неизменяемыми источниками. Каждую новую попытку recovery делаем в новом пустом каталоге. Полученные журналы, manifest, выбранную цель и timeline сохраняем для воспроизводимости. Если обнаружили, что остановились слишком поздно, повторяем с исходной копии и другой целью; не рассчитываем «отмотать назад» уже поднятый кластер произвольным SQL.

    11.5. Операционный контракт backup-системы¶

    В конце у преподавателя и студентов должна остаться инженерная модель: корректная backup-система имеет контракт охвата, контракт консистентности, контракт хранения, контракт проверок и контракт времени восстановления. Если хоть один из них явно не определен, обещание RPO/RTO висит в воздухе.

    VII. Итоговые модели лекции¶

    1. pg_dump формирует согласованный логический снимок одной БД. Клиент собирает объекты, данные и их зависимости; непрерывный PITR из SQL-дампа автоматически не возникает.
    2. TOC и restore scheduler представляют восстановление как DAG. Порядок создания объектов и целостность MVCC-снимка — независимые задачи.
    3. Параллельный dump требует согласованного snapshot для всех worker. Его стоимость включает дополнительные подключения, длинное удержание снимка, конкуренцию за I/O и обработку DDL-конфликтов.
    4. Физический pg_basebackup дает основу восстановления целого кластера. Для PITR после него необходимо сохранять непрерывную доступную историю WAL.
    5. Инкрементальный backup работает с измененными физическими блоками. Он зависит от WAL summaries и цепочки манифестов; его нужно собирать через pg_combinebackup перед восстановлением.
    6. Checksum, manifest и pg_verifybackup обнаруживают часть повреждений. Реальную восстановимость и бизнес-корректность доказывает пробный restore с прикладными проверками.
    7. RPO/RTO измеряются на полном пути восстановления. Узким ресурсом может быть сеть, disk bandwidth, длина инкрементальной цепочки, WAL replay, построение индексов или проверка приложения.

    12. Практическое продолжение лекции: один эксперимент вместо набора формальных упражнений¶

    Для отдельного стенда PostgreSQL 18 предлагается сквозной сценарий:

    1. Создать ledgerdb с несколькими связанными таблицами; запустить поток конкурентных INSERT/UPDATE.
    2. Выполнить pg_dump -Fd -j 4, убедиться, что дамп читает согласованное состояние, и посмотреть TOC. Отдельно вызвать ожидающий DDL, наблюдая сценарий NOWAIT worker.
    3. Восстановить directory archive через pg_restore -j 4 и -j 1; измерить время COPY, создания индексов и общий critical path.
    4. Снять полный pg_basebackup -Fp -X stream и пройти pg_verifybackup.
    5. Включить summarize_wal, сгенерировать изменения, создать incremental, собрать synthetic full и проверить его.
    6. На изолированном сервере воспроизвести ошибочную транзакцию, затем выполнить PITR к сохраненному restore point до ошибки.
    7. Проверить ключевые SQL-инварианты, записать фактические RPO/RTO, объяснить различия вариантов.

    Этот сценарий должен выполняться на учебном окружении. Здесь он приводится как мост от internals к будущей практике; полноценное лабораторное задание с автоматической проверкой можно оформить отдельно.

    13. Что можно копнуть глубже внутри 09.2¶

    Следующий технический слой — внутренний scheduler pg_restore на уровне TocEntry, зависимостей и очереди готовых задач. Это закроет вопрос, почему при -j 16 восстановление иногда использует только один-два worker, хотя свободно много CPU. Практическая польза — точнее рассчитывать critical path и выяснять, что реально ограничивает RTO для конкретной схемы.

    Второй слой — формат WAL summary и выбор измененных блоков в incremental backup. Он поможет понять, почему небольшой объем логических UPDATE иногда дает неожиданно большой incremental, а также какие потери summary files делают создание следующих копий невозможным. Это прямое продолжение темы физических копий PostgreSQL 18.

    Оба слоя остаются внутри backup/restore; разворачивать их отдельными лекциями без согласования не требуется.

    VIII. Внутренние алгоритмы: три коротких псевдокода¶

    В предыдущих разделах мы сознательно не раскрывали устройство SQL-исполнителя и REDO: они уже изучены. Но у самого backup/restore остаются три алгоритма, без которых слово internals было бы слишком поверхностным. Ниже приведены учебные псевдокоды, объясняющие причинность; они не копируют побайтно C-код и не являются частью публичного API.

    14. Как pg_restore выбирает готовую работу¶

    У TOC entry есть идентификатор и зависимости. В момент старта разные записи имеют разное число невыполненных предшественников. Планировщик должен запускать только готовые записи и после их завершения уменьшать счетчики зависимостей.

    /* Псевдокод: логика DAG-планировщика, не исходник PostgreSQL */
for (Entry *e : toc_entries) {
    e->pending = count_required_predecessors(e);
    if (e->pending == 0) ready_queue.push(e);
}

while (has_work()) {
    while (free_worker_exists() && !ready_queue.empty()) {
        Entry *e = ready_queue.pop();
        dispatch_to_worker(e);
    }
    Entry *done = wait_for_completed_worker();
    for (Entry *dependent : dependents_of(done)) {
        if (--dependent->pending == 0)
            ready_queue.push(dependent);
    }
}

    Почему это важно под нагрузкой? Если один долгий COPY оказался предшественником пяти дорогих индексов, никакие дополнительные свободные worker не начнут эти индексы до завершения COPY. Физическое ограничение критического пути возникает из предметных зависимостей, а не из недостатка потоков. В реальном коде PostgreSQL есть дополнительные проходы и ограничения; эту модель используем для объяснения, а детали ищем в pg_backup_archiver.c.

    15. Зачем leader параллельного dump экспортирует снимок¶

    /* Псевдокод: смысл synchronized snapshot */
leader.begin_consistent_transaction();
SnapshotId s = leader.export_snapshot();

for (int i = 0; i < workers; i++) {
    Connection w = connect_to_database();
    w.begin_consistent_transaction();
    w.use_exported_snapshot(s); // до первого чтения в транзакции
    schedule_tables(w);
}

    Если убрать строку импорта снимка, worker 1 мог бы увидеть перевод до фиксации сопутствующей записи в другой таблице, а worker 2 — после фиксации. Дамп внешне успешно восстановится, но единой временной точки данных не будет. Важно также, что экспортированный снимок сохраняется только пока допустим соответствующий жизненный цикл экспортирующей транзакции: это не файл, который можно бесконечно повторно использовать.

    Реальный pg_dump использует синхронизированные snapshot-операции PostgreSQL, а не буквально этот цикл. Это объяснение гарантии согласованности для параллельных соединений.

    16. Почему WAL summary сокращает передачу, но не заменяет журнал¶

    /* Псевдокод: схема summarization и incremental backup */
for (WalRecord r : wal_range) {
    for (BlockRef b : referenced_relation_blocks(r))
        changed_blocks[b.relation].add(b.block_number);
}

for (Relation rel : cluster_relations) {
    for (BlockNo n : changed_blocks[rel])
        incremental_archive.write_block(rel, n);
}

    Эта модель намеренно упрощает обработку файловых операций, расширения/удаления relations и специальных видов файлов. Но она показывает фундаментальную причинность: summary нужна, чтобы выбрать физические блоки для копирования, тогда как последовательность WAL-записей нужна, чтобы повторно применить изменения до целевого согласованного состояния.

    Проверить только измененные блоки без full backup нельзя: неизмененные блоки остались в опорной копии. Поэтому инкрементальный файл требует pg_combinebackup. Пропуск summary в нужном интервале не может быть компенсирован тем, что кто-то знает итоговый LSN. Само значение LSN не содержит перечня измененных страниц.

    Инженерный итог: три алгоритма решают разные задачи — порядок восстановления (DAG), согласованность параллельной выгрузки (snapshot) и экономию физического копирования (changed-block summaries). Их симптомы под нагрузкой тоже различаются: простаивающие worker, противоречивый экспорт при ошибочной реализации и неожиданно большой incremental backup.
